EDF6 network event registry: DamageObject, Mission, SceneObject and ItemDrop

UniversalEngine RE & NetworkingNetworkingEDF 5EDF 6
Technical reference · EDF6 native-binary protocol registry and exact receiver/transport disassembly; no new multiplayer runtime test

When reconstructing multiplayer behavior, distinguish the gameplay packet class, the event protocol within class 4, and internal engine/job codes. They have different identifiers, different receiver paths, and different meanings. The native-binary census here is for the qualified EDF6 DLL studied in the 2026 research; do not treat these numbers as a universal cross-build ABI.

Three game traffic routes

Outer route Receiver/owner Application delivery Typical responsibility
Class 3 — 0x3300 SceneObjectReceiver Mode 1, not retained Periodic state, ordinary player transforms
Class 4 — 0x3400 EventController Mode 0, Sandlot RUDP Damage, HP-related events, mission/object events, immediate actions
Class 5 — 0x3500 NetworkBullet / BulletManager Mode 0, Sandlot RUDP for studied shipping senders Projectile creation, publication and later contact state

For the gameplay controller ID 3, the class-4 route is assembled as (controllerId << 12) | 0x400 = 0x3400. The event is then identified inside the event protocol, not by replacing the outer packet-class header with the event ID.

Do not synthesize protocol ID 5: its absence from this measured registry is not proof of a general reserved-slot rule. Nor should one infer the wire schema or stable field ABI from a symbolic protocol name alone.

Damage and HP are not simply part of walking position

The native Event_DamageObject is registered at protocol ID 1. Its EventBase dispatch path hands the event to the EventController builder, which uses the class-4 0x3400 lane and mode-0 retained RUDP. The numeric value 0x2B seen in a later DamageObject::OnEvent path is an internal event/job code, not protocol ID 0x2B.

Thus a user can report apparently correct positions while still seeing incorrect HP, hit reactions or target destruction. Do not diagnose all of those observations as one missing 0x3300 movement snapshot. Confirm separately whether the relevant DamageObject event was generated, serialized, reliably acknowledged, received, and actually applied.

Projectile data has its own third lane

EDF6 NetworkBullet registers a class-5 0x3500 receiver. In the audited shipping binary, all 23 direct send callsites of the public NetworkBullet sender selected mode=0, hence the reliable per-peer RUDP path, not ordinary class-3 mode-1 delivery. EDF5 had a homologous RUDP projectile path, so a claim that EDF6 simply made normal bullet traffic unreliable is unsupported.

However, retained delivery only recovers serialized bytes. It cannot restore omitted class-internal projectile state. Separate FlameBullet02, LightningBullet01, and SolidExpBullet01 investigations demonstrate that initial motion, RNG/path state, and detonation countdown can be missing from the published selector payload.

Evidence and testing boundary

The names, IDs, event routing, outer class IDs and mode selection are static binary evidence; the route is not a new endpoint established by independently sniffing a current live two-player session. For a network diagnosis, correlate both players' timestamps and the same object ID across class 3 snapshots, class 4 event records, class 5 bullet records, RUDP ACKs, and final in-world apply calls. See player-state packet lanes, RUDP behavior, and projectile reconstruction.
