FMB terrain and field records

UniversalMaps & NavigationMapsEDF 5EDF 6
Technical reference · Maintained inspector + exact native FMB variants; generic writer unresolved

At a glance

What it is: FMB carries field and terrain rendering data for EDF maps, including geometry-related chunks and a spatial directory.

Where it fits: It is different from an ordinary MDB model. The renderer can draw FMB terrain while the map's physical collision remains a separate problem.

Important distinction: The tables below describe researched layouts and sample-specific differences, not a universal writer for every FMB.

Worked example: three addresses, three meanings

Suppose an inspected FMB directory points to a hypothetical wrapper record at file offset 0x300. In the measured compressed-wrapper family, the interesting positions are:

AddressMeaningHow to use it
0x300 + 0x20 = 0x320Field holding the stored CMPL span lengthRead the wrapper's stored length here
0x300 + 0x24 = 0x324Start of the nested CMPL dataCheck its magic and decompress this inner payload
Decoded data +0x58Observed configuration byte in a sufficiently long decoded recordInspect after decompression, not at raw file offset 0x358

The addresses are invented for arithmetic illustration; the relative positions come from the documented inspector profile. The value of the decoded configuration byte is map-specific and cannot be obtained from a universal source→target increment. A correctly decoded leaf also does not prove that the enclosing spatial tree, material assignments or collision data are valid.

Binary container envelope

The maintained FMB inspector recognizes magic FMB\0 and at least 0x2C bytes of header. A later, more precise EDF6 version 0x110 study decoded the section roles below from native files and loader code. These named roles supersede the older inspector's placeholders for that exact profile; other historical/game versions still require separate checks.

Offset Field Use in the inspected family
0x00 FMB\0 Magic
0x04 u32 version Version value (record it, do not silently force one)
0x08 u32 directoryCount Number of chunk/directory offsets in the native EDF6 profile
0x0C u32 directoryOffset File offset of the absolute chunk-offset directory (observed 0x2C)
0x10 u32 layerTableOffset Trailing layer/material table position (end of last chunk)
0x14 u32 plantsTableOffset Plant/grass groups (table 2; empty form {0, 8})
0x18 u32 jitterTableOffset Jitter records (table 3)
0x1C u32 jitterCount 0x100 jitter records in the surveyed EDF6 profile
0x20 u32 shaderTableOffset Shader selector records (table 4)
0x24 u32 shaderRecordCount 0x15 in the surveyed EDF6 profile
0x28 u32 maximumDecodedLeafSize Largest decompressed leaf size, used as a buffer hint

The directory at directoryOffset contains directoryCount 32-bit absolute record offsets. Each must point inside the file. The inspector uses the next known record/section boundary to determine each record span. The newer source's precise table-2/3/4 semantics apply to the studied EDF6 0x110 family; the old generic field names were placeholders, not competing meanings for those same native bytes.

Recognizing compressed field records

In the measured wrapper layout, a record with CMPL at record offset +0x24 has its stored CMPL span length at record +0x20. The decoder unpacks that inner CMPL data and, where long enough, inspects the decoded byte +0x58.

wrapper_start + 0x20  -> stored compressed span length
wrapper_start + 0x24  -> 'CMPL' header
uncompressed_wrapper + 0x58 -> observed per-record configuration byte

The +0x58 byte is not governed by a universal +5 source→target formula. Native/paired profiles have different values and bindings. Recompressing a stream and obtaining a correct wrapper length does not prove correct terrain shader/config selection.

The inspector distinguishes recognizable compressed wrapper records from apparent spatial-tree records; unknown records are reported, not silently assigned a type. A generic writer needs a validated relationship among wrapper configuration, chunk table and spatial directory.

Spatial tree and map-dependent profile

For the audited native EDF6 family, tree records use a postorder directory; a node is stored after its children. The newer native-writer study identifies a 0x24-byte internal node (kind 0) with child-subtree starts at +0x1C and +0x20, and the root as the last directory entry. Each chunk begins with a kind word, center float3 and half-extents float3. Critically, the byte-exact target AABB is calculated in float32 from all vertex extrema in the subtree, not by simply unioning rounded child center/half-extents; a child-box union can be useful as a broad geometric check but is not the exact serializer rule. The corresponding source EDF5 representation in the investigated migration path is described as an explicit/preorder spatial tree. Therefore copying directory order or rounded child boxes is not a generic source→target conversion.

The same EDF6 0x110 profile defines kind 2 as a compressed leaf: +0x1C gives the inner CMPL displacement (observed 0x24), and +0x20 the stored CMPL span. Kind 1 represents a raw leaf, supported by the loader but not present in the surveyed stock set. Chunk starts are 4-byte aligned. The decoded leaf has 0x18-byte position/normal vertices and 0x3C-byte mesh records; its per-cell material-weight records are 0x50 bytes with four RGBA8 corner-weight groups. The fine grid is a material/splat grid, not the terrain's heightfield. Physical collision remains separate.

The same capacity words can bind to different config indices in different FMBs. A config index is file-local. Not every file has the same trailing resource table or 256 fields; do not hard-code a 16×16 grid or derive the placement topology from one donor map. The historical table above counts shader/config rows differently from the November source's native +0x24 shader-record count; these counts have not been shown to describe the same table and should not be silently equated.

The newer study reported byte-identical round-trips of three native FMBs, including a recompressed leaf, and a shader-selector survey across 9,753 meshes in 46 EDF6 FMB files. Those are source-reported finite offline checks, not an independently qualified universal EDF5→EDF6 writer or a replacement for the older native-variant census.

What conversion has actually proven

  • In several paired shared-map cases, decoded terrain streams were byte-identical or structurally reconciled while the outer FMB container still differed. A 257/257 stream match is not an exact whole-file rebuild.
  • The historic Desert FMB (114,829,863 B in the cited runtime branch) rendered successfully. That is direct evidence for the examined field-rendering path, not for all collision or authoring behavior.
  • Old statements that FMB itself supplies the physical floor collision were corrected: MAPO binding, MAD collision and related map data are separate dependencies.
  • IG_EDFROOM01/02 have no FMB in the studied map family; do not fabricate one to satisfy a supposed universal resource list.
  • The maintained fmb_tool.py is intentionally inspection-only for generic input. The full postorder/chunk-table/resynchronizing compressed-stream writer is not exposed as an unconditional converter; an explicit validated profile is required.

Practical parser/writer contract

Validate directory bounds and section offsets, decompress known wrappers independently, retain unknown records, reconstruct the correct file-local tree/config bindings, compare source-derived geometry and target-render behavior, and fail closed when the per-file profile is not established.

For related data see MAPB/MAPO and the map stack, native FMB config variants and physical collision versus AI navigation.

Evidence: maintained read-only converter/fmb/fmb_tool.py, current native FMB variant census and exact paired-source assertions. No claim of universal runtime-equivalent FMB authoring is made.

Historical sample observations are not reusable profile rules

Several early paired-map notes mention a decoded FMB configuration value of 0 versus a target Desert value of 0x0A, plus map-dependent index values. These notes are not proof of a universal source→target delta: the same source-family observations include native CAVE and Desert variants with different value sets, and the maintained FMB inspector expressly rejects unconditional +5 or any other single-map mapping. The exact field-index mapping needs the complete original paired sample.

Other finite observations include a reported mean terrain-height residual around −0.002 m, an assembled native-sized FMB of 50,055,192 bytes, and a ±1250 world-domain sample with zero median rendered displacement against its reference. Those are bounded historical measurements. Matching output size does not imply byte equality; matching rendered terrain does not prove FMB tree/config parity or floor collision.

Quad validation: when comparing a decoded terrain FMB stream with a generated stream, compare the expanded triangles, not just the number of serialized quads or stream bytes. Check vertex order/winding and corresponding triangles against the source/native geometry. The old provenance note on quad expansion was retained only as a partial quotation; no complete universal triangle-split rule is promoted from it.

The maintained converter/fmb/fmb_tool.py remains inspection-only: its own conversion command refuses a generic source-only FMB build until target postorder tree, chunk-table and compressed-stream profiles are established. This is a real format/profile generalization gap, distinct from the closed finite sample measurements above.

Historic Desert FMB directory regression: one table, not two

A retained August 2026 crash-hunt analyzed an EDF5 Desert 511-entry directory beginning at 0x2C and extending to 0x828 (511 × 4 bytes). Entries 0…20 addressed main field/wrapper records; entries 21…510 were tail record offsets in the same directory. An earlier script incorrectly treated the bytes from 0x100 onward as a separate table, then rebased only 0x100…0x828 when expanding the main area. The entries at 0x80…0x100 were left pointing at old positions, causing a later dispatcher to interpret compressed payload bytes as bogus record types and crash during load. A corrected rebuild shifted all affected tail entries from 0x80, preserving directory identity.

This is a finite, debugged directory-relocation failure in the measured Desert family, not a universal 511-entry rule for every FMB. A second historical experimental rebuild changed eight field types 1/2 → 3, +0x54: 0x101/0x202 → 0x303, and +0x58: 0/1 → 0x0A; that build loaded/rendered but did not fix floor collision. Never promote those finite type rewrites to a general floor or format conversion algorithm.
