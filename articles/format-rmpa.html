RMPA — route, shape, camera and spawn resource families

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: RMPA stores route and spatial information used by missions or maps, such as paths, points, shapes, cameras and spawns.

Where it fits: Its meaning and byte layout depend on who owns the resource: a mission, a map or a weather/MAE structure.

Important distinction: Treat the documented mission-owned layout as one researched profile, not a universal RMPA specification.

The measured mission-owned profile

The examined EDF5-to-EDF6 MISSION.RMPA work documents an EDF6 output with the \0PMR signature, version 1 and primarily big-endian fields. A later native EDF6 parser/source census identifies a 0x28-byte logical file header with four top-level (count, offset) pairs: routes at +0x08, shapes at +0x10, cameras at +0x18 and points at +0x20. These header-level offsets are measured from the file start.

An older mission conversion report calls its emitted header span 0x30 bytes. The extra eight bytes are not established as native header fields by the newer source; treat 0x28 as the documented logical header and 0x30 as a source-writer footprint/possible following alignment until the exact bytes of that writer are independently reconciled.

EDF6 record family Native source-reported size
Logical file header 0x28 bytes
Route section / other section 0x1C / 0x14 bytes
Waypoint 0x30 bytes
Route group 0x18 bytes
Shape set / shape / shape payload 0x14 / 0x24 / 0x38 bytes
Point set / point 0x14 / 0x34 bytes
Camera set / camera 0x24 / 0x68 bytes (no camera record in the surveyed native files)
Property-list header / property entry 0x08 / 0x08 bytes

The older writer also described a 0x40-byte shape-data span and a generic 0x20-byte group header. Those are not established native payload/section sizes by the later EDF6 profile, which distinguishes the record families above. Alignment or serialization differences remain possible; do not copy the earlier sizes into a parser without a matching binary sample.

Most file fields and UTF-16BE names are big-endian, but the newer source specifically found little-endian signed string offsets within 8-byte property entries, relative to the holding entry. The same source describes record-relative child/list offsets, 16-byte alignment for non-empty record arrays and a deduplicated UTF-16 string pool. One blanket byte-order or pointer-base rule is unsafe.

In that November 2026 study, the author reported walking all 865 surveyed EDF6 RMPAs under an emulated native parser and regenerating them byte-identically. This is strong source-reported offline binary evidence for that profile; it is not a new test here or proof that arbitrary edited RMPAs execute correctly in-game. Ownership still determines what the routes, shapes, points and weather references mean.

Waypoint identities and links

The studied mission source can number waypoints locally within routes, while the EDF6 target profile uses a flattened global sequence. In the audited MISSION.RMPA writer, global waypoint ordinal and preserved original gid are different identifiers. Outgoing route-local links are rebased by the route's cumulative starting index.

The bounded 141-mission offline audit accounted for 5,103 waypoints, 1,355 shapes, 3,387 spawn records and 6,665 literal script-to-RMPA references. These figures are validation-set counts, not binary limits or proof that every mission executes correctly in-game.

Worked example: route-local and global waypoint indices

Imagine a mission-owned source RMPA with two routes. Route A contains three waypoints, locally numbered 0, 1, 2; route B contains two, locally numbered 0, 1. If the target stores one flat waypoint sequence, the target ordinals are:

RouteSource-local indexTarget global ordinal
A0, 1, 20, 1, 2
B0, 13, 4

Therefore a link from B's local waypoint 0 to B's local waypoint 1 becomes a link from global ordinal 3 to 4. The separately preserved gid is not this global ordinal. This is an illustrative application of the researched mission-owned rebasing rule, not a byte-level sample from a shipped mission or a rule for map-owned RMPA.

Map-owned and MAE/weather resources

The CAVE501/CAVE503 map-RMPA studies have target-profile constants and structural rules requiring their own measurements. A map-owned writer may depend on MAPB placement identity. Do not import those rules into the mission-owned MISSION.RMPA writer, which was measured without a MAPB count input.

MAE/weather RMPA is a third context. Its resource bindings must be studied independently; neither the mission nor map profile automatically defines it.

For original EDF4.1 map-owned map.rmpa, exact source graph IDs were compared with complete EDF6-shaped native HKT terrain topology in two original SK maps: SK_SANGAKU01 has 290 nodes / 418 unduplicated reciprocal links, and SK_SANGAKU02 has 126 / 171. These are source graph cardinalities, not the file-header record sizes of EDF6 MISSION.RMPA above. LOW face/seam connectivity retained or recovered respectively 418/418 and 166/171 original links; an edge being native-terrain connected does not prove NPC traversal or a working map-RMPA serializer.
