EDF5 mission BVM: clean source vs EDF6 OLD_SCRIPT differences

ConversionMissions & ScriptingVM & source identityEDF 5EDF 6
Technical reference · Exact 141-mission source-vs-legacy byte/semantic audit; offline

Scope: the audited 141-mission shipping set in the EDF5→EDF6 comparison corpus. This is a byte-identity and game-script semantic distinction, not a description of a conversion program. The reference is bounded to the exact source set examined in the 27 August 2026 research and should not be generalized to arbitrary regional game editions.

Two similarly named BVM collections are not identical

The studied material included original EDF5 MISSION/.../MISSION.BVM files and a separately retained EDF5_OLD_SCRIPT tree on the EDF6 side. The names suggest the same script vintage, but exact binary comparison disproved equality:

Exact 141-pair comparison Observation
Original EDF5 shipping BVMs examined 141
Byte-identical pairs against corresponding EDF5_OLD_SCRIPT files 0 / 141
EDF6-side/legacy BVM larger by exactly 80 bytes 65 / 141
EDF6-side/legacy BVM larger by exactly 96 bytes 76 / 141
Other size deltas within the examined set 0

The whole 141-file comparison therefore shows a consistent altered binary envelope on the legacy EDF6-side files. It does not prove whether each added byte corresponds to one field or header without a separate structural analysis. In particular, it is not sound to assume that EDF5_OLD_SCRIPT is a byte-for-byte untouched copy of the original EDF5 data simply because the mission IDs match.

Which missions define the shipping set?

The canonical source comparison used 112 base campaign union IDs, 15 DLC1 and 14 DLC2 (141 total). The source-base union encompasses offline/online-only differences; it is not the same as the count of one mode-specific original binary list. It excludes optional stress fixtures and the separate EDF4.1/TEST/TGS material from the larger supplied 335-file BVM tree.

For the full sequence of IDs recorded in a historical converted MissionPack LIST, consult the 141-entry mission order reference. That is an ordering corpus; the clean original EDF5 MISSION.BVM source identity here is a different kind of evidence.

Semantic observations made against the clean BVM set

The source-only 141-mission comparison did not validate correctness merely by counting output files. Its retained exact audit recorded:

Source-derived observation Examined total / result
CreateEnemy2 sites recovered from original BVM 722
Corresponding generated CreateEnemy2 sites 722
Source spawn transactions inspected for ordering 3,471
Transaction order failures in the audited path 0
Mission AC files regenerated from the clean source and byte-identical to the historical R43 runtime-candidate output 141 / 141
Structural errors in that regenerated AC set 0

A focused compilation/source-equivalence suite reported 29/29 PASS. The four separately inspected frog-related resource variants were also reproduced byte-identically in that historical path. These results are strong offline source-to-artifact parity evidence, not proof that all 141 missions completed or behaved identically in EDF6 runtime.

Why the source matters for VM semantics

A target-side script can contain port decisions or layout changes absent from the original EDF5 VM. The source corpus contained a cvtstore stack rule: the assignment leaves the stored lvalue on the stack, so a call with side effects must not be evaluated twice. Similarly, source cuscall0 5014 used enum 15 for the tested background/fog event family, while unsupported cuscall0 3450 lacked a proven direct AngelScript SetAiSearchRadius binding.

The historical offline path separated that unresolved 3450 operation from a resource-level compatibility specialization. Later executable compatibility choices that omitted six such calls in DM006_2 do not retroactively make omission equivalent to original source semantics. Original BVM behavior, reference-port behavior and target runtime acceptance remain distinct evidence layers.

Interpreting the evidence safely

  1. Compare claims of exact source-script behavior against the verified original EDF5 BVM, not merely the EDF5_OLD_SCRIPT directory inside an EDF6 archive.
  2. Compare claims of target game runtime behavior against actual EDF6 tests. A byte-identical generated AC is an offline result.
  3. Keep the base-campaign union, each mode-specific LIST count and the 141-mission shipping set separate.
  4. Never infer an unknown BVM opcode mapping solely by matching AngelScript function names or by copying a historical converted script.
