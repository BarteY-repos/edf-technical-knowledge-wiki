EDF5 TeamManager: player net IDs, team relation rows and object sets

EDF 5Game technical referencesPlayers / enemy teams
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R133 test

The game maintains an array of team records. Each team has a container of game objects and a separate relation table used to distinguish hostility and friendliness. Looking up an online player's network ID therefore means walking team membership and checking the object's actual type, rather than indexing a fixed four-player array by net ID.

The player finder walks team 0's object container, uses an actual dynamic_cast<SoldierBase> and compares the network-player ID at player +0xF8. This ensures a team object is not automatically treated as a player. The note's hypothesis that team 0 includes allies and vehicles is unverified; only the use of the cast is observed.

A separate enemy-count approach sums member counts in teams whose relation from team 0 is hostile. This is a rough live container count, not guaranteed to match currently alive/visible enemies: the author explicitly notes that dead members might temporarily remain registered.

Mutating the team field does not update membership

In EDF5 the team ID on a player is at +0x218. A contributor verified that directly changing this field could make enemy hits connect, but a mission restart could crash because the manager's object set still contained the player under the old team. The team number and membership set have to stay consistent. The native team-changing helper exists and updates membership; direct field mutation does not emulate it.

Evidence: static TeamManager and player-lookup RE, with one historical contributor-verified team-switch failure. This is not a recommendation to edit game memory or a claim of consistent behavior across versions.
