EDF5 → EDF6: what actually needs conversion?

ConversionCross-game ConversionEDF 5EDF 6
Technical reference · Reconciled exact paired assets, native corpus and limited runtime evidence

EDF5 and EDF6 reuse recognizable names and resource roles, but the same filename extension does not guarantee that an EDF5 payload is valid inside EDF6. Reliable conversion works per subsystem and per observed target profile.

Conversion at a glance

Subsystem What the research establishes Unsafe shortcut
MDB model Vertex declarations, materials, texture bindings, bone/object relationships may differ Header version bump or one universal vertex stride
Material/shader Shader, ordered parameters, samplers, sampler state and vertex layout are coupled Rename the shader alone
Texture masks Native target pairs can be rebaked with family-specific packing One global FPR channel shuffle
CANM animation EDF5 0x200 to EDF6 0x300 changes channel layout and rotation representation Rewrite version field only
CAS wrapper Has independent generation and references surrounding CANM Assume the wrapper version equals CANM version
MAB Validated v15 0x03→0x83 migration changes internal pointer bases; 1,318 paired resources show separate content retargeting Assume all MAB offsets are absolute or treat re-encoding as gameplay parity
MAD collision Older Havok data must be structurally re-encoded into target hknp layouts Copy old motion/shape bytes into new headers
HKT/NVMD navigation Semantic geometry and target binary output are separately important Assume matching triangle counts prove correctness
Mission BVM → AC Event graph, scheduler, control/dataflow and engine API semantics need translation Text-only opcode replacement
Mission RMPA Dedicated target record layout and reference rebasing Reuse the map-RMPA converter
Archive/resource lookup Container and path identity must be preserved across packaging Rename every .trb to .mdx

Example: one MDB leaf mesh changes even when index count does not

A paired native palm example found an EDF5 leaf mesh with 888 vertices and 1,944 indices whose EDF6 counterpart had 1,380 vertices and the same 1,944 indices. Another paired leaf mesh changed 36 → 72 vertices, keeping 144 indices. Tangent/normal/UV seam splitting changed the vertex representation without changing the polygon index count.

The study also showed that an EDF5 snd_Map_Simple_Clip material does not generally map to one universal EDF6 shader: of 38 paired source materials, only one native target used snd_BRDF_Map_Simple_Clip; other target families differed. That one target still changed its parameter ABI. A shader-string-only experiment produced black leaves; restoring a coherent material contract resolved that observed failure.

This is a paired-case result, not a rule that every EDF5 leaf must increase its vertices by a fixed ratio.

Example: binormal migration must be contextual

In retained compatibility-pair research, TANGENT and TEXCOORD could remain stable while BINORMAL changed to:

EDF6 binormal = (-source.x, -source.y, -source.z, source.w)

The retained fixture measured 16,796 half-float binormals and 1,093 float32 binormals matching that sign behaviour; the 1,093 sampled float32 tangents matched exactly. This is a cross-game migration observation, not a command to negate binormals already correct inside a native EDF6 file.

Example: version numbers are not the animation format

The studied CANM generations differ in record size and semantic encoding:

  • EDF5: 0x200, roughly 0x20-byte channel records and Euler-radian animation representation;
  • EDF6: 0x300, roughly 0x30-byte channel records with XYZW base/multiplier/encoding fields and quaternion animation representation.

The associated CAS wrapper may be a separate generation. A conversion tool should parse both generations explicitly and retain unknown data safely instead of assuming that the first successful parse proves compatible animation behaviour.

Conversion evidence levels

A conversion can be:

  1. Structurally valid — reader/writer and invariants pass.
  2. Source-semantically reconciled — events, references or vertex/sample semantics are retained against studied source/target data.
  3. Target-runtime accepted — the exact modified asset/game build loads and behaves in the relevant test.
  4. Gameplay faithful — the particular behaviour has been compared at runtime, not inferred from file layout alone.

These are progressively stronger claims. A source-only PASS is valuable research but not automatic gameplay parity.

For the detailed rules, open MAB v15 pointer migration, MDB model structure, Native material families, Animation formats, Collision and navigation and Mission events.

Evidence status: exact paired same-asset source/target observations for several MDB/animation rules, sampled native shader corpora, source/binary collision research, mission translator and runtime case studies. No universal across-all-assets converter is claimed.
