EDF4.1 original Havok 2014: 21-file MAD/SHKT corpus and convex-contact limits

EDF 4.1Physics & CollisionPhysicsEDF 5EDF 6
Technical reference · EDF4.1 native source: 21/21 exact decoder consumption; offline 311 MOPP routes; target runtime not established

At a glance

What this page answers: EDF4.1 MAD and SHKT carry Havok 2014 Binary Tagfiles with source-specific shape graphs; they are not ready-made EDF6 hknp data.

How to read it: Read the five-map/sixteen-object sample and its exact decoder consumption separately from the later 18-map body census.

Evidence boundary: All 21 source files parsed in this scope. That does not prove cross-version physics compatibility or all proposed convex reductions.

Evidence: A read-only, exact-consumption audit of 21 original EDF 4.1 Binary Tagfile payloads dated 5 September 2026: 5 .MAD map collision files and 16 .SHKT object physics files. It is not an EDF6 gameplay test, and the original game assets are deliberately not shipped in this reference.

The format identity is precise but not a converter

All 21 examined payloads report Binary Tagfile version 5 and Havok SDK identification hk_2014.1.0-r1. The audited decoder consumed the exact payload byte count in all 21/21 cases; each source file has a separate SHA-256 and explicit source/payload sizes. This supports the original EDF4.1 serialization observations, not the assertion that EDF5 or EDF6 uses the same physical shape layout. A shared Havok family label does not make later hknp collision bodies compatible with EDF4.1 hkp shapes by renaming a header.

.MAD represents map-side physics/collision; .SHKT represents object-side physics. Neither is an EDF6 FMEP vegetation/texture-array container. An original .MAD can contain a large mixture of MOPP meshes and relatively simple shape primitives; the file extension alone does not predict triangle counts or convex representation.

These counts are audited offline shape-route coverage, not runtime collision success. The 311 direct MOPP mesh paths account for 283,381 vertices and 471,929 triangles in the source geometry survey. NW_KOUSOUBLD01 alone has 3,379 map rigid bodies, 248 accepted MOPP paths and 3,064 tested compact-primitive branches; it is not representative of the all-MOPP four-body cave.

Notice the separate notions of serialized object count, map rigid-body count, MOPP paths, primitive branches and triangle count. The original NW_KOUSOUBLD01.MAD reports 13,697 serialized Havok objects but 3,379 map rigid bodies. Conflating those counters would inflate the apparent number of physical actors.

Original shape graphs are not one universal mesh

Observed root/child families include hkpMoppBvTreeShape, hkpStorageExtendedMeshShape, hkpListShape, hkpConvexVerticesShape, hkpBoxShape, hkpCylinderShape, and translation/transform wrappers. In IG_TESTLIGHTMAP, 16 root MOPPs include 14 direct extended meshes and two MOPP-wrapped lists; NW_UNDERGROUND01 includes direct box and convex roots alongside lists and MOPPs. A target physics format must represent the effective contact surface and transformed shape, not just a leaf class name.

Five negative compact-convex candidates are meaningful

The compact branch had five failed map/body occurrences across two maps, representing three unique source body names. sk_car_sedan02_hk.polymsh and sk_car_minivan01_hk.polymsh each recur in IG_TESTLIGHTMAP and NW_KOUSOUBLD01: the high-vertex hulls did not satisfy the audited uint8 convex-reduction geometry budget (484 → 228 and 594 → 214 vertices in the error reports). nw_hct_koujimaku2.polymsh is a distinct failed hull with duplicate directed edge 1→0.

Those failures do not mean that the original map collision is invalid. They mean that this particular neutral compact representation was not qualified for those bodies. Blindly lowering vertex counts can change support, contact extents and gameplay geometry.

A separate exact EDF4.1/EDF5/EDF6 comparison of the two car shapes demonstrates why a support-surface-preserving approximation matters. For the selected minivan, source expanded half-extents and the derived target-oriented profile agreed within approximately 0.000328 in the reported comparison; the generated expanded-support difference from EDF4.1 was approximately 8.57e-8 for that comparison. This is a local geometric result, not proof of general convex equivalence or stable dynamics in EDF6.

Reader interpretation and remaining limits

  • The full 21-file source directory is in data/R158_EDF41_HAVOK2014_21_NATIVE_MAD_SHKT_SOURCE_CENSUS.csv (original filenames, sizes, versions and hashes; no game bytes).
  • Shape paths, original body totals and failure counts are in data/R158_EDF41_HAVOK2014_FIVE_MAP_COLLISION_BRANCH_COUNTS.csv and data/R158_EDF41_HAVOK2014_FIVE_COMPACT_CONVEX_NEGATIVE_CASES.csv.
  • This establishes a useful EDF4.1 source oracle for target collision contact, while EDF6's hknp shapes and welded/heightfield behavior require independent target-native and in-game evidence.
  • The audited stage for a production EDF4.1→EDF6 .MAD was not yet promoted by this source; no runtime certification follows from 21/21 exact decoding.

Later, broader 18-map MAD body census (R59; separate from the 21-file audit above)

The November 17 native original-EDF4.1 investigation examined 18 .MAD map archives and 18,520 hkpRigidBody instances — not the five MAD plus sixteen object SHKT payloads counted in the preceding R158 sample. It found 16,301 list roots, 1,608 MOPP roots, and smaller convex/primitive families; motion types 5/3/2 occurred 17,660 / 849 / 11 times. All 18 source hkpPhysicsSystem records set active=1, but this does not verify the running world's actual collision registration.

Most importantly, although hkpTypedBroadPhaseHandle declares collisionFilterInfo, 18,520/18,520 body instances omit an explicitly serialized value. Do not interpret omission as zero or a universal NPC collision layer. See the full native MAPB matrix and Havok-filter analysis, which also resolves the algebraic base-actor rotation order and separates that finding from still-unknown NPC contact behavior.
