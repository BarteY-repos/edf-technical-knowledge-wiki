Native MDB authoring: observed interoperability boundaries

UniversalModels & MDBModelsEDF 5EDF 6
Source-backed research / case study · Exact native

Ordinary EDF6 MDB models couple mesh geometry, ordered vertex declarations, materials and texture-resource identities. The contracts below come from sampled native static/map-model files plus bounded modified-game observations; they are not universal statements about every animated, weapon or vehicle model. See the MDB format reference for the wider structure and LOD relationships.

Per-mesh vertex-buffer and index contract

Field or conditionObserved contractImplementation consequence
Mesh vertex-buffer startEvery inspected native EDF6 multi-mesh static sample began each mesh buffer on a 0x10-byte boundary.Align each mesh buffer independently, not just the first mesh or outer data region.
Mesh triangle indexuint16; the representable range is 0x0000..0xFFFF.Never truncate a vertex reference or invent a 32-bit index mode for this established profile.
Oversized authored meshAn observed writer split a 65,538-vertex bucket into 65,535 + 3 vertices at triangle boundaries.Split and remap triangles per output mesh. Preserve the triangle multiset and split-corner UV/normal/tangent data.
Visually rigid geometrySome native static models still carry BLENDWEIGHT/BLENDINDICES lanes.Do not remove skin fields just because a prop does not visibly animate.

For a packed writer, nextVertexStart = (previousBufferEnd + 0xF) & ~0xF is an illustrative alignment calculation, not a claimed native stored formula. The measured convention does not prove that every unaligned MDB crashes a loader.

Vertex element width correction

The reconciled MDB field/type table treats format/type 1 as a 16-byte float32[4] value. An older 4-byte interpretation is superseded. This matters for declaration parsing, stride calculation and round-trip writing: using the obsolete width shifts every following element even if a header/version gate still accepts the file.

Do not infer the meaning of the four lanes solely from this width. The semantic role still comes from the owning vertex declaration/material profile.

Build Basic NC: three UV lanes and material identity

The sampled snd_BRDF_Map_Build_Basic_NC family uses a 76-byte native vertex stride. Across 28/28 examined native materials in this profile, the ordered texture slots were param_occlusion, dirt, albedo, normal and param_r_m_xxx_hr. Their logical texture-coordinate roles are:

UV channelObserved role in this material family
TEXCOORD0Close/tiled albedo, normal and packed roughness/metallic sampling.
TEXCOORD1Unique-surface occlusion.
TEXCOORD2Macro/dirt projection.

These are logical sampling roles. Preserve the actual ordered native vertex elements, occurrence indices and stream identity from the source; three arbitrarily ordered UV arrays do not establish byte-equivalent layout. See the native material-family reference for parameter and sampler contracts. Do not apply this Build-family mapping to every EDF6 shader.

Texture bindings and material-parameter bytes

MDB stores a material's logical texture-resource identity; the matching DDS payload and RAB entry metadata are separate resources. In a bounded modified-game observation, changing one MDB texture-table binding and providing the corresponding DDS altered the texture while geometry, UV/tangent streams, shader/parameter bytes and Havok collision remained unchanged. Another bounded observation found that selected material-parameter-byte overrides changed appearance without replacing the model.

Implementation rule: keep material binding, ordered sampler state, actual texture payload and geometry independently addressable while validating their cross-resource closure. The observations do not establish every shader parameter's visual meaning, permitted range or a general replacement policy.

Do not assume: Every ordinary _lod.mdb requires a dedicated LOD shader. Ordinary base-material families are found in LOD companions; FieldRender terrain follows a separate rendering path. Character/weapon/vehicle compositor profiles remain less comprehensively sampled than props.

Evidence level: Reconciled sample- and runtime-lineage-backed reverse census, not a universal EDF6 specification.

Runtime boundary for authored models

A nontrivial authored triangle mesh was observed drawing through the ordinary MDB path in a modified EDF6 runtime, with physics handled by separately authored Havok collision. This supports a bounded custom-geometry path and separation of visual MDB geometry from physical collision. It does not certify arbitrary declaration orders, shaders, skinning, LOD switching or stock-game acceptance.

CANM CAS cross game bartey

Source record: canm-cas-cross-game-bartey · Source evidence: static

CANM and CAS across games (BarteY's reading): EDF5 CANM is 0x200 with a roughly 0x20-byte channel and Euler-radian rotations, EDF6 CANM 0x300 with a roughly 0x30-byte channel (XYZW base and multiplier, an encoding, quaternion rotation), so a conversion rewrites the keys; the CAS wrapper generation and the CANM it holds vary independently, EDF6's CAS pointing into embedded or trailing CANM data; a MAB mapping between the games was left open.

Island4 static map case

Source record: island4-static-map-case · Source evidence: static

BarteY's "Island4" custom map as a static-map case study (a runtime-positive control in their modified game, then offline audits; one project, not a scaling law): the source art is one FBX mesh of 10 closed components and 109,658 triangles, about 10.33 x 5.86 x 11.75 m (its physics FBX about 9.72 x 5.14 x 11.19 m), and became a playable map as one root static render resource at scale 20 (anchor top_center_aabb, position [400.0, 108.35, -134.2688751220703], rotation zero, OBJ UV mode preserved; runtime bounds about 206.6 x 117.1 x 234.9 m), so a map needs no FieldRender terrain or many scene objects, only the whole world contract (geometry, placement, collision, weather, spawns, navigation, mission use). Their editor rebuilt the five-file runtime-positive family byte for byte. The first run looked chrome-like because the artist's packed texture holds R roughness, G metallic, B AO and the old material read it through a reflect / specular contract (a material-ABI mismatch, not a missing DDS); separately the single 4096 x 4096 atlas, UVs kept after the x20 scale, measured an area-weighted mean 9.25 px/m, a median 18.44 px/m, over 52.9 % of the surface under 5 px/m and strong anisotropy in places, so a corrected material alone will not sharpen close range and blind global UV multiplication would break seams and repeat baked regions.

MDB BC1 cutout ledger

Source record: mdb-bc1-cutout-ledger · Source evidence: static

The native Common_Clip foliage texture sk_pShrub003-df.dds in BarteY's corpus: in its top mip all 32,768 BC1 blocks use transparent mode (color0 <= color1) and 427,079 pixels select the transparent palette entry, a real native one-bit-alpha cutout path (not a rule that every cutout texture is BC1). Static, rigid map-model profiles carry BLENDWEIGHT and BLENDINDICES even on visually static pieces, giving 60, 68 and 76-byte layouts with one, two and three UV streams (not shown for every EDF6 MDB). BarteY's evidence ledger (ch. 16) grades the package: NATIVE_BYTES (record widths, FMB material / cell / orientation, DDS arrays), STATIC_DXBC (FieldRender projection modes 0 / 1 / 2, one Water pixel shader's R x A decode, the cubemap-array sample), RUNTIME_BOUND (some MDB and Common_Clip fixes, a named Desert render; not the whole custom port), EXTERNAL_REPORT (foliage thinning, fixed 0.8 alpha, water foam and fog, terrain MRT RGBA) and OPEN (exact final compositing, the second Water pixel shader dispatch, the native FieldRender SRV / sRGB override); two further statements of its register: BC1_UNORM (DXGI 71) versus the sRGB view (72) must be told by the bound view, and a mesh with working FMB rendering can still have broken floor collision (the FMB is visual; MAD, MAPO and Havok collision are separate).

MDB common clip cutout

Source record: mdb-common-clip-cutout · Source evidence: static

snd_BRDF_Map_Common_Clip carries no translucent_* parameters (native order alpha_clip, diffuse, metallic, normal_amount, roughness, specular_color, specular_diffuse_blend): the shader cuts out on albedo alpha against alpha_clip, so it is a cutout family, not one of the translucent (_Alpha) kind. In EDFModelUtility's preview a uniform albedo tint for specular_color was tried and looked wrong on real hardware (the model tool's specification), which the guide's specular rule (specular = lerp(specular_color, albedo x specular_color, metallic x specular_diffuse_blend)) explains; BarteY lists the preview's other mismatches (AO is not a glTF AO map, since occlusion scales normal length) as structural, not tuning (ch. 04).

MDB cutout mip coverage

Source record: mdb-cutout-mip-coverage · Source evidence: static

One-bit-alpha cutout mips: BarteY's 64x64 BC1 diagnostic kept its 50% transparent coverage down to 8x8 (2048, 512, 128 and 32 transparent texels at 64, 32, 16 and 8), but a plain opaque-majority downsampler gave 0 at 4x4, 2x2 and 1x1, and the paired LOD DDS began at 4x4, so the whole distant cutout chain was opaque. An opt-in coverage-preserving BC1 mip generator (fractional per-area alpha, an 8x8 Bayer-ranked tie breaker for the opaque / transparent count) kept 8 transparent texels at 4x4 and 2 at 2x2 (1x1 cannot show 0.5); the top level stays byte-identical. It is an authoring repair for cutouts only (not glass), not a recovered Sandlot algorithm, and its side-by-side render in EDF6 was still outstanding.

MDB edf5 edf6 migration

Source record: mdb-edf5-edf6-migration · Source evidence: static

An EDF5 to EDF6 MDB conversion is semantic, not a version bump: the paired same-asset models differ in tangent and binormal streams, UV and corner vertex splitting, shader family, material parameter ABI, textures and the object name graph, and changing only the version gave plausible but invalid hybrids. In one tangent-ized conversion the binormal XYZ was negated with W kept ((-x, -y, -z, w); 16,796 half-float and 1,093 float32 binormals matched, 1,093 float32 tangents byte-exact), a rule for that profile only; 12 audited conversion meshes kept float32 precision.

MDB import limits

Source record: mdb-import-limits · Source evidence: static

MDB mesh indices are 16-bit, so an importer must reject negative or above-65535 indices or split the geometry on triangle boundaries (never cast to unsigned short); in the sampled native multi-mesh MDBs each mesh's vertex buffer starts on a 16-byte boundary (useful when writing, not shown to be a loader requirement). FBX ByPolygonVertex attributes need vertex splitting by the whole corner tuple (control point, normal, tangent / binormal, every UV channel, skin data).

MDB legacy compositor open

Source record: mdb-legacy-compositor-open · Source evidence: unverified

Open question (BarteY, ch. 06): whether legacy non-BRDF shaders such as SND_CHARA_BASIC (specular_pow, specular_color, light_smooth) feed the same EDF6 compositor as the BRDF families is unknown; the evidence missing is the final pixel-shader output targets, the trace of those three parameters to them, whether the targets are the same logical attachments, and real draw render-target bindings. Known: legacy parameter ABIs survive in EDF6 content, specular_pow must not be read as roughness, old reflect / spec packed textures are not interchangeable with R/M/O packed ones, a shader-name-only swap from snd_Map_* to snd_BRDF_Map_* gives a coherent-looking but semantically wrong MDB, and one runtime-positive path of BarteY's earlier work kept the legacy ABI deliberately.

MDB lod clip notes

Source record: mdb-lod-clip-notes · Source evidence: static

An explicit _lod.mdb can keep its base model's materials (not every LOD uses snd_BRDF_Map_LOD or FarMap), and the native Common_Clip leaf sk_pShrub003-df.dds is a BC1 / DXT1 cutout (a reference, not proof every clip texture is BC1 or has one threshold).

MDB migration audit census

Source record: mdb-migration-audit-census · Source evidence: static

BarteY's paired EDF5 to EDF6 MDB audits: 63 of 63 HEIGEN models (about 2.0 MB of vertex lanes), 163 of 163 NW_EUROPE models (about 31 MB) and 76 of 76 DESERT models (about 6.5 MB) passed their structural and independent checks (validation counts of their corpus, not profile counts, not a game-acceptance proof). Their 162-material ABI census of the Desert RAB against the native HEIGEN507 plus NW_EUROPE01 signatures found every shader name present in the native set and exactly one unseen parameter / sampler ABI, the leaf material 1 of sk_ptree007_11m_shuro.mdb, which was also the only material whose shader name changed from the EDF5 source (a shader-name-only change builds a hybrid ABI that no native file has). That EDF5 palm is byte-identical in Desert and HEIGEN (decompressed MDB 53,806 bytes): its snd_Map_Simple_Clip leaf declares diffuse, specular_pow, specular_color, light_smooth, alpha_clip and an albedo-only sampler, while the one native snd_BRDF_Map_Simple_Clip declares diffuse, specular_color, specular_diffuse_blend, metallic, roughness and an albedo sampler. The 38 paired legacy Simple_Clip materials map as HEIGEN507's 30 to 17 Common, 12 Common_Clip and 1 LOD, NW_EUROPE01's 8 to 3 Common, 1 Common_Clip, 1 Simple_Clip and 3 Build-family shaders (the palm's native target is Common_Clip). An authored source bucket of 65,538 vertices was split at a triangle boundary into 65,535 + 3, not widened to 32-bit indices.

MDB native defaults notes

Source record: mdb-native-defaults-notes · Source evidence: static

Native defaults a generic "every new value = 1" fill gets wrong (ch. 10): snd_BRDF_Map_Common_Clip.alpha_clip is 0.5 in 42 of 44 retained materials (0.3435 in 2); Signboard.image_split raw u32 2; Build_Window.interior_wrap_count raw u32 4; Common_Light light_color is HDR (observed above 1, several different values); falloff, animation and switch fields are family-specific. A reflected Float3 has native type 2 / size 3 in the exactly recovered profiles (snd_BRDF_Map_Common.diffuse and .specular_color, Common_Light.light_color, Build_Window.diffuse / interior / specular_color, Signboard.diffuse / light_color / specular_color), whereas the tool's statistical default is size 4. Transparency is not told by name: snd_Map_Object_Glass has no _Alpha or _Clip suffix yet its profiles carry priority / layer / flags (glass: layer 2); the param_cm0_cm1 color-customization formula is in #model-material-guide-rules.

MDB no universal stride

Source record: mdb-no-universal-stride · Source evidence: static

There is no universal EDF6 MDB vertex stride or semantic order: the native-compatible profiles in BarteY's paired corpus use physical strides of 60, 68, 76 and 84 bytes, several UV streams in orders such as 0, 2, 1 and 1, 0, and some valid meshes keep float32 where another profile has half-float; rigid props can still carry BLENDWEIGHT and BLENDINDICES. A direct edit should keep the raw vertex stream, declaration order, duplicated semantics, sampler tails, TypeByte / SizeByte and the name-table references unchanged. The declaration formats seen: 1 float32x4 (often BLENDWEIGHT, 16 bytes), 4 float32x3 (12), 7 float16x4 (position, normal, tangent, binormal; 8), 12 float32x2 (TEXCOORD; 8), 21 uint8x4 (BLENDINDICES; 4) (matches #mdb-layout).

MDB object name refs

Source record: mdb-object-name-refs · Source evidence: static

In a paired EDF6 / v32 audit, 165 of 165 target objects resolved the first Object dword as a dedicated object-name reference whose text equals the bone / node name given by the second dword (the two indices need not be equal); the pointers in Name, Texture, Material, MaterialParameter, MaterialTexture, Object, MeshInfo and the declarations use each record's own entry- or field-relative base, not a file-relative one.

MDB param type4 raw u32

Source record: mdb-param-type4-raw-u32 · Source evidence: static

Material parameters of type = 4 are raw u32 lanes, not floats: snd_BRDF_Map_Signboard_Pattern.image_split = 2, its direction and boolean controls (pattern_x_dir, pattern_y_dir, use_scroll, use_scroll_time, switching_mask_split) 0 or 1, snd_BRDF_Map_Build_Window.interior_wrap_count = 4. Integer 2 is bytes 02 00 00 00 (as float32 about 2.8e-45); writing the numeric float 2.0 gives 00 00 00 40, a different value to the game (1 -> 00 00 80 3F, 4 -> 00 00 80 40 likewise). An untouched float round trip stays bit-exact; editing or inventing a type-4 value through a float path breaks it.

MDB profiles common counts rules

Source record: mdb-profiles-common-counts-rules · Source evidence: static

The Common family counts (ch. 08, HEIGEN plus Europe): snd_BRDF_Map_Common 101, _Common_Clip 44 (60-byte stride, alpha_clip 0/1 before the Common fields), _Common_Light 5 (60 bytes, light_color 2/3, sampler param_r_m_light_hr); BarteY's retained summary did not pin one declaration for all Common occurrences, so no stride is given for them. MDB profiles legacy

Source record: mdb-profiles-legacy · Source evidence: static

Older snd_Map_* material families coexist with the BRDF ones in the same maps (NW_EUROPE01): snd_Map_Build_Basic_NC (77 + 2 + 1), snd_Map_Build_Basic (49), snd_Map_Build_Simple_Clip (31 + 7), snd_Map_Object_NoAO_Light (7 + 2), snd_Map_Build_Simple_Alpha (6 + 1 + 1), snd_Map_Build_Basic_Parallax_NC (3), snd_Map_Build_DirtScroll (2); they use specular_pow, light_smooth, fall_off_amount / _scale / _offset, diffuse 2/4 and packed param_reflect_*_spec_hspec-style textures (param_reflect_cm0_spec_hspec, param_reflect_spec_lightmask_hlightmask, param_reflect_XXX_height_spec). The census holds no SND_CHARA_BASIC (character) material.

MDB reflection vs native parameters

Source record: mdb-reflection-vs-native-parameters · Source evidence: static

Reflected shader catalog against native MDB material instances (BarteY's second-pass cross-check of EDFModelUtility's databases, ch. 10): many reflected entries (SND_BRDF_MAP_COMMON, _COMMON_CLIP, _BUILD_WINDOW, _BUILD_PARA_NC, _SIGNBOARD_PATTERN, several legacy Build shaders) begin with m_instancing_array_stride (UInt scalar) which the observed native material parameter lists never contain; reflected parameter order differs from native order (reflection for snd_BRDF_Map_Common roughly diffuse, specular_diffuse_blend, specular_color, normal_amount, metallic, roughness; native diffuse, metallic, normal_amount, roughness, specular_color, specular_diffuse_blend); some legacy instances (snd_Map_Build_Simple_Clip, snd_Map_Object_NoAO_Light, snd_Map_Build_Basic_NC) omit metallic and roughness though the reflected catalog lists them, so the catalog says what a shader can consume, not what each MDB holds. Whether EDF6 requires native order is not proven (the research writers keep it).

MDB sampler order vs register

Source record: mdb-sampler-order-vs-register · Source evidence: static

Native sampler (texture slot) order against reflected register order, five BRDF profiles (ch. 10; the texture names match, the MDB slot order differs): Build_Basic_NC register albedo, normal, dirt, param_r_m_xxx_hr, param_occlusion vs MDB param_occlusion, dirt, albedo, normal, param_r_m_xxx_hr; Build_Window register window_frame_texture, interior_texture, normal, window_normal, param_r_m_xxx_hr vs MDB interior_texture, normal, param_r_m_xxx_hr, window_frame_texture, window_normal; Build_Para_NC register albedo, normal, dirt, param_r_m_h, param_occlusion vs MDB param_r_m_h, param_occlusion, dirt, albedo, normal; Build_DirtScroll register albedo, normal, dirt, param_r_m_cm0_hr, param_occlusion vs MDB param_occlusion, dirt, albedo, normal, param_r_m_cm0_hr; Signboard_Pattern register albedo, normal, param_r_m_occ_light, switching_mask vs MDB switching_mask, param_r_m_occ_light, albedo, normal. BarteY's writers preserve native order; that EDF6 rejects a reordered list is not shown.

MDB shader contract migration

Source record: mdb-shader-contract-migration · Source evidence: static

Of 38 paired EDF5 snd_Map_Simple_Clip materials only one EDF6 counterpart used snd_BRDF_Map_Simple_Clip (the others Common, Common_Clip, Build or LOD families), and even that one changed the whole parameter ABI; one palm's leaf mesh went from 888 to 1,380 vertices with the same 1,944 indices, another from 36 to 72 vertices with 144 indices, as EDF6 added tangent and binormal channels and packed textures. A shader-name-only conversion gave black leaves in BarteY's runtime experiment and a coherent source shader and material contract fixed it; no universal FPR / mask channel permutation converts the textures, some need re-baking.

Model material guide rules

Source record: model-material-guide-rules · Source evidence: unverified

The shader guide's model material rules that BarteY keeps for previews (the guide's author; family-specific native checks are in map-shaders.md#model-material-rules-r18): color = albedo.rgb x diffuse; with param_cm0_cm1 color = lerp(lerp(diffuse, change_color0, mask.r), change_color1, mask.g) x albedo; normal x = R x A x 2 - 1, y = G x 2 - 1, z = sqrt(max(1e-5, 1 - x^2 - y^2)), x and y scaled by normal_amount (0 disables, above 1 exaggerates, below 0 reverses, direction only), then the tangent basis and normalize; metallic = packed G x metallic, roughness = packed R x roughness (_hr: R x A x roughness); specular = lerp(specular_color, albedo x specular_color, metallic x specular_diffuse_blend), F0 = specular x (0.04 + 0.96 x metallic).

Normal length guide

Source record: normal-length-guide · Source evidence: unverified

The guide author's later clarification: the gbuffer stores normalXYZ = normalized normal x occlusion, so k = length(normalXYZ) is a light factor: ambient diffuse x about k^2, directional diffuse, directional specular and environment-tinted albedo x k, point lighting affected by k unevenly, and k below about 0.001 selects another composition path; normal_amount changes direction before the normalize and never gives a length above 1, occlusion makes k below 1. Not re-derived across the DXBC corpus (BarteY).
