Native MDB authoring: observed interoperability boundaries

UniversalModels & MDBModelsEDF 5EDF 6
Source-backed research / case study · Exact native

Observed native behavior: In the sampled EDF6 multi-mesh static corpus, each mesh vertex-buffer start was 16-byte aligned. This is a native-conformance observation, not proof every misaligned file crashes.

Implementation rule: Preserve per-mesh buffer alignment and respect practical 16-bit mesh-index limits. An authored source bucket with 65,538 vertices was split at triangle boundaries into 65,535 + 3 vertices rather than inventing a 32-bit index variant.

Vertex element width correction

The reconciled MDB field/type table treats format/type 1 as a 16-byte float32[4] value. An older 4-byte interpretation is superseded. This matters for declaration parsing, stride calculation and round-trip writing: using the obsolete width shifts every following element even if a header/version gate still accepts the file.

Do not infer the meaning of the four lanes solely from this width. The semantic role still comes from the owning vertex declaration/material profile.

Known exception: snd_BRDF_Map_Build_Basic_NC uses a non-obvious verified three-UV stream declaration/order. Semantic UV availability alone is insufficient; preserve native vertex declaration identity.

Observed native behavior: Texture identity in MDB material tables and DDS payload packaging are distinct. Isolated texture-table binding changes and material-parameter-byte overrides have bounded runtime-lineage evidence; do not generalize to every parameter and appearance range.

Do not assume: Every ordinary _lod.mdb requires a dedicated LOD shader. Ordinary base-material families are found in LOD companions; FieldRender terrain follows a separate rendering path. Character/weapon/vehicle compositor profiles remain less comprehensively sampled than props.

Evidence level: Reconciled sample- and runtime-lineage-backed reverse census, not a universal EDF6 specification.

Runtime-positive scope evidence for arbitrary authored geometry

The retained September R7 authoring line reached bounded runtime-positive evidence with a nontrivial authored triangle mesh used as ordinary MDB visual geometry while separately-authored Havok collision handled physics. This is important scope evidence: custom ordinary MDB geometry is not only an offline parser/writer hypothesis. It does not prove every shader, material, skinning or vertex-declaration combination.

Texture binding is a separate resource layer

A later R12 lineage isolated a custom-texture change by rewriting one MDB material texture resource identity and appending a custom DDS while keeping geometry, UV/tangent data, shader/parameter bytes and collision unchanged. The reusable rule is architectural: MDB logical texture binding and RAB/DDS payload/resource metadata are distinct layers. A converter/editor should be able to change one without silently rebuilding unrelated mesh/collision data.
