EDF6 CAS player groups, controller variables and safe trackless grafts

UniversalAnimationEDF 4.1EDF 6
Technical reference · Exact-build binary/class-lookup research; source-only graft logic

Why can a converted object appear to have valid bones and clips but still crash when its native EDF6 class spawns? The class can require named CAS controller groups (players) and variables that did not exist in EDF4.1.

The important distinction: player group, state and track

A CAS anmgroup owns named states (mcanm) and their animation/control data. A class may resolve an entire player group by name during construction. In the examined EDF6 path, a missing player can produce an invalid unchecked lookup. A missing state or clip within an existing player may instead be tolerated, which does not make the missing whole group safe.

The retained example is an EDF4.1 UfoCarrier301 grafted onto the target EDF6 UfoCarrier508 class: the EDF6 class looks for in_ring and out_ring animation players, representing motion absent from the old carrier. Removing their graphical motion is fine; omitting required names is not.

Variable (vcontrol) safety

A target EDF6 class may set controller variables by name every frame. The analyzed lookup for a missing setter target returns -1; the setter then treats that index as a valid array position and can write out of bounds. A missing getter-only variable can return 0.0, changing tuning behavior without an immediate crash.

Known requirements for the studied Berserker-like class include v_move_angle, v_move_velocity, v_tilt_dir and v_tilt_lerp during update, plus v_damage_reaction_ratio when hit. A vcontrol record in this family occupies 0x14 bytes:

Byte offset Field in measured record
+0x00 Relative name reference
+0x04 Mode flag; 0 plain variable, 1 follows a tcontrol
+0x08 Variable kind
+0x0C Initial float32 value
+0x10 Additional word / tcontrol index when applicable

A bounded graft may copy plain donor variables that the source CAS lacks. Variables coupled to another tcontrol require extra index rewriting and were intentionally refused by the retained safe implementation.

Trackless grafting for target-runtime compatibility

The source-compatible approach does not copy the donor's animation motion onto the EDF4.1 model. It inserts only missing named player/controller structures and appends trackless CANM clips preserving their donor names, loop flag, duration, step and frame count. The target class can find and trigger the required control paths without moving alien donor bones.

The measured graft procedure:

  1. Parse the source-compatible EDF6 CAS and the EDF6 donor CAS; reject other/unknown generations.
  2. Find target-required anmgroup names and plain vcontrol names that are missing from the source CAS.
  3. Append donor animation groups and their associated tcontrols, renumbering control indices against the target's existing table.
  4. Append corresponding CANM clips, but with zero tracks, and remap old clip indices inside appended tcontrols.
  5. Recompute signed relative offsets for strings and records after the new clip table has grown.
  6. Refuse data commands whose argument layout is not proven to contain only a tcontrol index.

The retained code permits data-command IDs 0 and 4 when their discriminator at +0x14 is 2; it treats mcanm +0x20 as a possible tcontrol index, with the special 0xBF800000 sentinel meaning no tcontrol. These are measured in that grafting path, not a specification of every possible custom CAS opcode.

Some class-required states can be aliases of existing states, preserving a compatible state name without inventing new movement. A separate hollow procedure clears clip track counts for placeholder donor motion while keeping the state/clip metadata. Only explicitly identified runtime-owned tracks should be stripped.

Practical failure signs

Symptom First thing to inspect
Immediate crash when object spawns Missing class-required anmgroup player name
Crash after updates or on taking damage Missing class-written vcontrol or invalid index
Model animates into donor pose Donor tracks were copied instead of adding trackless clips
Wrong clip or broken string New tcontrol/clip indices or relative offsets were not rebased
Odd lean/recoil without crash Missing getter-only variable reads zero or additive clip semantics changed

This information explains one measured class/controller ABI family, not a guarantee that every EDF6 class uses the same names or tolerates identical missing states.

Evidence: retained cas_graft.py, cas_legacy.py and cas_pose.py source; exact EDF6 binary lookup analyses described in those source comments. The grafted content is source-only compatibility evidence, not a new Windows/runtime PASS. For CANM channel bytes and Euler→quaternion handling, see actual cross-generation CAS/CANM conversion.

Deliberate missing variables versus true missing-controller defects

Do not graft every target-only CAS variable automatically. In the preserved EDF4.1 soldier profile, target v_vehicle_grip_l_ik_target and v_vehicle_grip_r_ik_target are intentionally left absent: target code checks -1 indices before writing, while the source CAS lacks a matching consumer. This is unlike a required player/control-variable absence that the native class dereferences unchecked. Related source-only policies for torso-axis mode and ledge-climb are in friendly soldier skeleton compatibility.

Absolute CANM clip rebasing is not a trackless graft

The studied EDF6 CAS 0x204 / CANM 0x300 format stores absolute local transforms in selected clips. If MDB bind translations change, a source absolute clip can pull a bone to the old position. A retained source-only rig/CAS rebasing procedure adjusts only supported translation channel bases and rejects shared channel indices that require incompatible deltas. It leaves additive clips and keyframes unchanged and avoids double application of root motion.
