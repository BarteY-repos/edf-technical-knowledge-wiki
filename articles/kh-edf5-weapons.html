EDF5 and EDF4.1 shared WeaponBase vtable design

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-weapon-fire-slots

EDF5's weapon vtables follow 4.1's design (../edf41/weapons.md#edf41-weaponbase-vtable, #edf41-weapon-tryfire): WeaponBase EB8EA8 has 33 slots; Weapon_BasicShoot EB9DE8 overrides 0, 2, 9, 13, 14 and 19. Slot 13 is Shot (398BA0: index mod +0x178, then 391D60, 4.1's 30FC50); slot 19 398A60 reads a command node's name (string EA5148) and reaches the try-fire 391C60, which tests ammo +0x8E8 and calls slot 13 with AmmoCount +0x1D0 - ammo (391D37), emptying the magazine after the burst at 391D4C as 4.1 does. BulletBase E99450 has 11 slots, SceneObject (EE0828) 10, as in 4.1; SolidBullet01 (E9C110) overrides 0, 2 and 9.

Basis: vtables by RTTI (scratch File_Storage/Logs/catalog/kh158_vt.py edf5); fn.py reads of 398BA0, 398A60, 391C60 (lines matched to 4.1's)

Addresses (build-specific RVAs unless indicated): EB8EA8, EB9DE8, 398BA0, 391D60, 398A60, EA5148, 391C60, 391D37, 391D4C, E99450, EE0828, E9C110

Stars

Weapon star levels read from player save

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-stars-from-save

A player's weapons get their stars from the save: the player spawn 311F40 reads the class [save + player*0x3E60 + 0x6D4C] and, in its usual mode (third argument 0), each equipped weapon row from [save + 0x6D24 + 4 x (player x 0xF98 + (class + 2) x 6 + slot)]; for each row it calls 3068B0(soldier, weapon file from 91930's record, &save[row x 12 + 0xEA10]), which copies those 8 star bytes, one per star slot, into the creation record's +0x58 (306929) and has the object factory 6138E0 build the weapon from its SGO. These are the bytes the loot roll raises (drop-items.md#loot-roll-class-share).

Basis: fn.py 311F40, 3068B0, --xref 91930, --xref 38C010

Addresses (build-specific RVAs unless indicated): 311F40, 312210, 31226D, 3122BF, 3068B0, 306929, 6138E0

WeaponBase constructor applying star statistics

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-star-slot

The WeaponBase constructor 38C010 (called by all 14 weapon class constructors) passes each star stat through the HQ's evaluator 8C8C0 (file-formats.md#hq-star-eval-float32) with the creation record's star bytes ([record+0x58], 38D19B), so the HQ's numbers and the game's are one computation. The evaluator takes star s = the byte at the array's third value (8C944, 8C962), cut to the fourth (top, 8C967): the third value is the star slot, as in EDF6 (../edf6/weapons.md#edf6-star-evaluator). It reads kind, slot and top as raw dwords and Ra, Mu as raw float32 (no type conversion).

Basis: fn.py 8C8C0, --xref 8C8C0 (13 calls in 38C010, one in 8C280), field names from the UTF-16 keys at each call (scratch File_Storage/Logs/catalog/annot_fields.py)

Addresses (build-specific RVAs unless indicated): 38C010, 38D19B, 8C8C0, 8C944, 8C962, 8C967

Thirteen star-evaluated weapon fields and offsets

Integer versus float star-array interpolation

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-star-int-rounding

Because 8C8C0 returns an int (x + 0.5, truncated) when the array's first value is an int in the SGO and a float otherwise, and 38C010 copies the result's raw bits, the SGO types must match the fields; they do in every weapon: AmmoCount, ReloadTime, FireCount, FireInterval, FireBurstInterval and LockonTime are ints, the rest floats, star array or plain (0 mismatches over 1187 weapons). So integer stats at stars round half up: ammo = int(v x ((1 - Ra) + Ra x (s/5)^Mu) + 0.5).

Basis: scratch File_Storage/Logs/catalog/probe5types.py over every weapon SGO in Root.cpk

Addresses (build-specific RVAs unless indicated): 8C9E4, 38C010

Falloff by charge and by ammo left

Charge and remaining-ammo falloff rules

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-falloff-apply

The falloff by charge and by ammo left (the JP wiki's チャージ and 残弾数 rows, atwiki edf5 page 307) is applied by 397580(record, weapon, r, exclude): f = pow(r, record +4) (9C8276); the record's int mask +0 picks the stats f scales, each from the record's own copy of the star-evaluated values (unless the bit is set in [exclude]): bit 3 ammo = trunc(AmmoCount x f) (clear: full AmmoCount), bit 4 FireCount = max(1, trunc(FireCount x f)), bit 1 AmmoDamage, bit 2 AmmoSize, bit 5 AmmoSpeed (so range), bit 6 AmmoExplosion (each x f), bit 0 weapon +0x8E0 = record +8 x 60 (EE66A8) x f (#weapon-falloff-recoil-field).

Basis: fn.py 397580, --xref 397580 (six calls: 39A190, 39A490, 39A910, 3A3FF0, 3A4110, 3A4240)

Addresses (build-specific RVAs unless indicated): 397580, 9C8276, 3975AD, 3975DF, 397610, 39763F, 397674, 3976A9, 3976DE, EE66A8

Accuracy adjustments during damage falloff

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-falloff-accuracy

Accuracy in the falloff (#weapon-falloff-apply), from the record's copy A of FireAccuracy (a spread): with mask bit 7 the spread becomes (A - 1) x g + 1, so it widens toward 1.0 as g falls; without bit 7 but with bit 8 it becomes A + 0.5 - 0.5 x g; g is f, or r itself when bit 9 is set.

Basis: fn.py 397580 (397713-39778A)

Addresses (build-specific RVAs unless indicated): 397713, 39774B, EE633C

Damage falloff over charge progress

Evidence: static · Build: steam-5d11de53 · Fact ID: chargeshoot-charge-share

Falloff by charge (Weapon_ChargeShoot, 39A190): r = 1 - [+0xBA4] / [+0x1C4], the charge still needed over the energy cost at stars (#weapon-star-fields); under 0.1 (EE6264) the weapon gets no ammo, otherwise record A applies with nothing excluded, so f = r^cp[4]. The constructor starts the weapon with no ammo and +0xBA4 = +0x1C4 (399B47, 399B51).

Damage falloff over remaining ammunition

Evidence: static · Build: steam-5d11de53 · Fact ID: falloff-by-ammo-left

Falloff by ammo left: r = c + (1 - c) x ammo left (+0x8E8) / AmmoCount (+0x1D0), applied with the ammo bit excluded ([exclude] = 8), so f = r^x. Weapon_ChargeShoot uses record B with c = cp[9] at each shot (39A56C) and after charging (39A966); Weapon_PreChargeShoot (constructor tail 3A3F09) has one record at +0x1200 = {mask cp[6], exponent cp[4], cp[5]} with c = cp[7] at +0x11F0, applied at 3A408E and 3A4170. c is 0.0 in all 66 such records, so the wiki's MIN is 0 for these weapons.

Basis: fn.py 39A490-39A5C6, 3A3EE9-3A4179; c census with scratch File_Storage/Logs/catalog/probe5falloff.py --all

Addresses (build-specific RVAs unless indicated): 39A56C, 39A5B9, 39A966, 39A9C2, 3A3F09, 3A3F7C, 3A408E, 3A4170

Native weapon route: controls, bullets and lock-on

Provenance: EDF Knowledge Hub revision 5b589ca, novae (ajane), EDF5 build steam-5d11de53. These are static code observations except the explicitly unverified lock-on gaps; inferred field meanings and untraced helper behavior are qualified below. None is a new live game test.

Soldier weapon sets, selection and fire command bytes

Weapon set storage (static): soldier +0x1590 points to the weapon array (count +0x15A0) and +0x15B0 to 0xA8-byte weapon-set records (count +0x15C0). Each set stores the ordered SGO slot list, active index +0x28, current weapon entry pointer +0x30, outgoing entry +0x38 and a state machine.

Equipped weapon (static): set zero's current weapon is reached via the double-indirect pointer [[[soldier+0x15B0]+0x30]]. Switching updates all sets to the same list index; only set zero takes the named held-weapon callback. Which classes have more than one live set was not established.

Selection commands (static): controller 2ED2A4..2ED5FF maps inputs to soldier bytes: +0xB54 next, +0xB5F previous and +0xB60..+0xB62 weapon shortcuts 1–3 (with keyboard-only paths in the observed bindings). Soldier update 308AE0 routes these to 306EB0, 307010 or 307170, after state gates. The precise meaning of the controller bank-selection flag was not traced.

Change transaction (static): 307880 hides and records the outgoing weapon, changes the active slot, calls old/new activation helpers and sets the incoming weapon's raise timer +0xE4 to 40 frames. The state machine schedules the transition; some animation ID arguments remain unverified.

Primary/secondary/reload routing (static): the soldier loop reads primary fire at +0xB50+i per set and writes weapon trigger request +0xD9 while movement/state gates allow it. Secondary requests +0xB52+i feed +0xDB; reload +0xB55 calls weapon slot 16 when allowed. Some command bytes are reused by civilian classes for other reactions; applying this map to all actors would be incorrect.

Edge conversion (static): WeaponBase::update 3900F0 converts the one-frame request +0xD9 into held +0xDA and rising edge +0xDD, then clears the request; secondary input uses +0xDB/+0xDC. It also decrements raise and shot cooldown timers. Repeated direct injection into the request field is a proposed mod route, not tested here.

BasicShoot firing condition (static): its node-machine callback uses the rising edge for burst configurations (FireBurstCount>1) or certain weapon flags, otherwise the held trigger. It requires ammo, no raise timer or cooldown, and an allowed weapon state before calling the native fire/spawn route.

Manual reload (static): 391180 dispatches a reload event when the weapon permits it; with a partially filled magazine it sets the remaining rounds to zero, applies a short cooldown and enters reload setup. Manually reloading discards the rounds remaining in the magazine.

Model bone, aim frame, muzzle and shot construction

Mounting record (static): WeaponBase resolves SGO ModelConstraint against the owner's skeleton, retaining a bone record at weapon+0xBB0 or logging an unresolved root. A render-only arm pose edit need not move the underlying world-space bone that the weapon follows.

Weapon basis (static): rows weapon+0xF0..0x120 are refreshed from the soldier's world transform +0x70..0xA0, both across the weapon array and in held-weapon callbacks; this is the native frame used downstream, not a direct camera-crosshair ray.

Muzzle modes (static): 3942A0 rebuilds a 0xE0-byte muzzle entry from bone and local transforms each weapon update and again before firing. Mode 0 transforms a local position through the bone; mode 1 uses the local/bone arrangement selected by fire_model_direction. No mode 2 was observed.

Shot origin (static): 391EC0 casts from mount to muzzle to pull a blocked muzzle back out of walls and builds a shot matrix from muzzle rows, fire vector, spread/accuracy and random seed. The traced matrix builder does not read a camera or target global; some downstream spawned effects were inferred from call shapes.

Bullet core, frame stepping, range damage and target messages

BulletMtSystem (static): global 125B088 coordinates bullet stepping through 146D80 and end-step 1474A0; each SolidBullet01 owns a core at bullet +0xE0 and steps core and effect records as part of the frame.

Copied payload fields (static, inferred names): core +0x274 speed, +0x278 life frames, +0x27C base damage, +0x280/+0x284 damage reduction, +0x288 explosion radius and +0x294 size line up with weapon star-evaluated fields. Core +0x230 supplies a separate damage multiplier.

Ready damage record (static): setup 142380 fills a persistent record at core +0xD0 with attacker handle, team, impulse, initial damage and radius/flags; its callback likely filters attackable targets, but that callback's semantics were not fully read.

Range attenuation (static): after movement, core step 144670 evaluates D×m+(D−D×m)×(1−t)^x, where m is AmmoDamageReduce, x its exponent and t is elapsed life fraction clamped 0..1. A hit receives the damage current on the impact frame, not only the weapon's initial value.

Damage dispatch (static): 143E90 queues object hits; direct-hit queues flush through 2D9720 as message 0x80000000 to target handlers reaching native HP application. Explosive cores divert to 145360 under flags, with special delayed/fuse behavior still inferred.

Area explosion (static): 145360 makes a sphere hit query through 2D83B0, optionally scaling base damage by an integer and excluding the directly struck object. The queried routine does not itself multiply by radius-based falloff; whether individual targets perform other scaling was not traced.

Lock-on parameter, cone, target tracking and release-to-fire

Weapon parameters (static): constructor 38C010 loads LockonType, LockonTargetType, distribution, auto-timeout, fire-end clear, angle, range, time, hold/failure times and maximum count into fields +0x510..+0x540. Lock speed +0x5B0 and range +0x5B4 multipliers start at 1; multi-target allowance +0x5AD starts at 0.

Support modifiers (static): soldier equipment routes parameter IDs 12, 13 and 16 to repeat-target allowance, lock speed and lock range respectively. Combination helper 307400 can take first, maximum, minimum, additive or multiplicative matches depending on mode. Exact human-readable SGO names of the three IDs were not independently read.

Search volume (static): 3912D0 constructs a weapon-space cone with angle and multiplied range. 1363B0 filters target kind/team, front-facing direction, distance and yaw/pitch. Picker 391720 chooses the lowest-scored eligible entry and respects whether another lock may target the same object.

Lock acquisition (static): 391380 gates the tick on weapon-visible/ready state, increments or loses a candidate's progress under LockonTime/LockonFailedTime and appends completed locks. It searches AttackTargetManager one candidate at a time, plays periodic tick and completed-lock sounds, and stops at its max lock count.

HomingShoot trigger states (static): Weapon_HomingShoot uses its own node-machine callbacks. Type 3/4 can fire during held trigger; other types commonly lock while held and fire or enter a firing sequence on release. The second firing-sequence state was not traced completely.

Spending locks (static): try-fire rejects an empty lock list, adapts shot count to distribution mode and passes each selected target handle to the bullet spawn. Distribution 1 advances target per bullet; distribution 0 shares a target for the whole shot. Lock persistence or deletion depends on auto-timeout flags.

Unverified — gaps: the homing missile's later target-steering code, exact equipment parameter names, several gate fields, firing state 39C5F0 and other LockonType values remain unknown. Spawn forwarding a handle does not alone prove the missile's full guidance path.
