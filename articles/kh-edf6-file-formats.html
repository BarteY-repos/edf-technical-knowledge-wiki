CANM channel-table 16-byte alignment

Evidence: static · Build: steam-678ccb46 · Fact ID: canm-channel-alignment

A CANM channel table must be 16-byte aligned: the track evaluation 1160500 reads quaternions stored in a channel with movaps xmm0,[rbx] at 1160620, which faults on a misaligned address (Windows reports a read of 0xFFFFFFFFFFFFFFFF); stock CAS files put the channel table at 0x1680, and rows are 48 bytes, so every row stays aligned when the table is. A crash dump of a tool-made CAS with its table moved to 0x6DDE4 (4 mod 16) matched CANM base + (0x6DDE4 - 0x1660) + 7*48 = rbx exactly. The time sampler is 11602D0.

Basis: a player's crash dump and the author's private mapping of EDF.dll running the two functions on stock, broken and fixed files (1254 samples each)

Addresses (build-specific RVAs unless indicated): 1160500, 1160620, 11602D0

MARC MAC header and record layout

Evidence: static · Build: steam-678ccb46 · Fact ID: marc-mac-layout

MARC (.mac) layout, held on all 45 shipped MAC files (re-packed byte for byte): 0x00 "MARC", 0x04 version 5, 0x08 data start 0x24 (the header size), 0x0C data region length = string table offset - 0x24 (padding included), 0x10 the sum of all file sizes (no padding), 0x14 directory offset relative to that field (dir = 0x14 + value; code 1186F0), 0x18 file count, 0x1C string table offset (absolute), 0x20 string table length in UTF-16 units. Files start at 0x24, each next one at the next 16-byte boundary, zero padding; the string table at align16(end of the last file) holds the unique names sorted by code point, UTF-16LE, NUL-terminated; the directory at align16(end of the string table), 0x18 bytes per file: name offset (relative to the entry), data offset (absolute), size, then three zero dwords, in the builder's order (not sorted). The lookup is a linear case-sensitive wcscmp over the directory (118713 / 11878A for map.mapo / map.mapb); no hashes or checksums. The same rules as havok-format.md#mad-marc-layout (one-file MADs); the wiki's "unknown" fields and its entry +0xC "always 1?" (its MARC page, below) do not hold.

Basis: the author's reading of the code and its encoder, which re-packs all 45 MAC files byte-identically

Addresses (build-specific RVAs unless indicated): 1186F0, 118713, 11878A

Full original format research — expand (3,869 characters)

map.mapb (inside a MAC; fields from the endian fixup 11FA40, record fixup 120A40, def fixup 1210A0): 0x00 "MAPB", 0x04 version 2; 0x08 / 0x0C UTF-16 string table offset / length in units (def names); 0x10 / 0x14 int-pair array offset / count; 0x18 / 0x1C def table offset / count (0x3C each); 0x20 / 0x24 placement record offset / count (0x48 each); 0x28..0x77 ten (offset, count) pairs (only byte-swapped); 0x78 a point / route block {vec3 offset, n, list offset, n} (fixup 11F6C0); 0x7C a second point block {0x10-byte points, u16 pairs, int list} (fixup 11F1A0); neither is sized by the record count (AI or marker points, inferred). Def (0x3C): +0x00 type (3 = terrain / far), +0x04 / +0x08 an embedded SGO parameter block (offset relative to +0x04, size), +0x0C name offset relative to +0x0C (ig_heigen507_2.fmep), +0x10 -1, +0x18 float, +0x1C near cull distance, +0x28 / +0x30 floats. Record (0x48): +0x00 def offset relative to the record, +0x04 position xyz, +0x10 rotation xyz in degrees, +0x1C variant / seed (0: the loader uses the sum of the GUID's four dwords, 11B27E; 1..8 on .mosb in city maps), +0x20 / +0x24 / +0x28 / +0x30 ints, +0x2C offset (relative to the record) to {int offset, int count} -> int32 child record indices (billboards on a building), +0x34 a 16-byte GUID (not unique: NW_DLCMAP601 / 602 ship 4,546 guardrails with one GUID), +0x44 far-only flag. Agrees with #mapb-record-sizes (60 / 72 bytes; the "instance token" is the GUID). map.mapo (fixup 11FE90; header offsets relative to the mapo start, entry offsets to the entry): 0x08 / 0x0C the per-record entries (0x1C, count = records), 0x10 / 0x14 (int, int, float) array, 0x20 / 0x24 0x3C object structs (the non-.fmep records), 0x28 / 0x2C int32 self-relative pointers to them, 0x30..0x44 vec3 / vec4 / vec4 arrays (a color palette among them), 0x48 / 0x4C the UTF-16 string pool (sorted, deduplicated, always last), 0x50 / 0x54 per-record named entries (0x0C), 0x58 / 0x5C 0x0C structs with nested lists. Per-record entry (0x1C; imul r8, idx, 0x1C at 116DAB, 116FD7, 11741A, 11AAEB): +0x00 offset to an {int, int} pair (.fmep pieces only), +0x04 / +0x08 offset into the 0x28 array / count 1, +0x0C float (1000 on rocks), +0x10 / +0x14 offsets to the model and collision names (sk_rock601a_m_gr.mdb / .hkt), +0x18 offset into the 0x58 array; the placement stores this entry in its desc (150AF0, desc +0x30) and the base Preload object keeps it at obj+0x18 with the record index at obj+0x3C (150BD0). Named entry (0x0C, indexed at 118D95): +0x00 a string with the decimal record index (all 45 maps), +0x04 / +0x08 a list of {count, offset} -> (float, int) pairs. Loading: 117F90 finds both in the MARC, fixes them up, sets loader +0x18 / +0x10, loads the MAD collision (collision.hkt, 190770) and calls 11E1E0, which sizes the per-record vector loader+0x118 (data +0x120, 16 bytes each) to the record count and runs up to 4 parallel tasks (114A40) calling 1169B0 per record (no fixed maximum; shipped maps reach 13,251 records); 1169B0 picks the class from the def name's extension (.mosb, .fmep -> .fmb, .mdx / HAS_ parameter) and passes the matrix, mapo entry and index; pass 2 11A3F0 walks them again. Collision is keyed by name: Preload_Fmex (1527D0) looks up <model> + hkt in the MAD container (18DD30 at 152E91) and builds the bodies with the object's own world matrix (13F400, matrix at obj+0x1200); no GUID appears in the MAD, the navmesh or elsewhere in the MAC, so a copied record gets its own collision. Only 11A3F0 and 11E1E0 use the record count and only 118CD0 the mapo +0x50 table; nothing sorts by GUID or position and there is no spatial grid. .FMB terrain files list chunk offsets at 0x2C (count at 0x08; this line first said 0x30, which the author's later fmb-format.md calls a misread, #fmb-layout), each chunk starting with int kind, center vec3, half-extent vec3.

Basis: the author's reading of the fixups and loaders ("H") and of all 45 maps; its tool rewrites the two files and the game data stays byte-identical elsewhere; not run in game

DSGO type-4 expression node encoding

Evidence: static · Build: steam-678ccb46 · Fact ID: dsgo-expr-opcodes

A DSGO type-4 node is an expression: node + its value = {u32 size, u32 offset} to a program of u32 opcodes that EDF.dll runs on a stack of values (6DF20, switch table 6E854, 14 cases): 0 end, 1 push the next double, 2 push a UTF-16 string (its bytes plus terminator rounded up to 4), 3 push node n of the same file (the next u32; an expression node is evaluated first, 55DB0 / 55620), 4 call built-in 0x80000000 + k (6EA20, table 6F370), 5 add (also joins strings), 6 subtract, 7 multiply, 8 divide, 9 remainder of the operands rounded to integers, 10 shift left, 11 shift right, 12 and, 13 or (10-13 on integers). Built-ins: 0 pow, 1 log2, 2 min, 3 max, 4 clamp(x, lo, hi), 5 saturate (clamp to 0..1, 1C369B0 = 1.0), 6 lerp(a, b, t) = a + (b - a) x t, 7-12 sin, cos, tan, asin, acos, atan (the CRT imports). GetDSGONodeValue 52F50 takes this path when 52EB0 reports type 4.

Basis: fn.py reads of each case; import names by scratch File_Storage/Logs/catalog/iatname.py; decoder _tools/catalog.py (DsgoExpr) run over every EDF6 SGO without a decoding failure

A chunk (FieldRender::PolygonChunk, a 0x1A0 make_shared block, data L at +0x10) holds per-instance state: its render object at L+0x30 (an Umbra object registered by Initialize: chunk index L+0xA0 / +0xF4, owner FieldRender L+0xA8, world OBB L+0xB0..+0xEF, world matrix L+0x100..+0x13F) and the geometry (vertex buffer L+0x140, meshes L+0x168..+0x187); the render object's draw (slot 1 10EE90) reaches the geometry only through L+0xF8, which the game sets to L itself, so two instances can share one decoded geometry. The chunk array is FieldRender +8 (count +0x18, 16-byte {chunk, control block}); the empty chunk constructor is 10C130, the task's field writes after its build 10CA9B..10CC44; type 0 nodes have no geometry or render object. A piece's destructor (vtable 176BF88 slot 2 153E50) takes its render objects out of Umbra (1104E0).

Binary formats and map-conversion contracts

This section reconciles the Knowledge Hub source records into the existing EDF6 file-format reference. Evidence is attributed, not independently re-tested. Unless stated otherwise, runtime-address observations concern steam-678ccb46; the standalone tools and port examples have their own scope.

CPK, @UTF and CRILAYLA

Static · BarteY, EDF6 Mod Platform HF5.48: this CPK reader places an entry at ContentOffset + (FileOffset - min(Toc.FileOffset)), validates archive bounds and normalizes DirName/FileName for case-insensitive lookup. This is a reader-specific base calculation, not a replacement for the separately documented 0x800 base used in the measured EDF6 CPK corpus: the interpretations coincide in some archives but need not in DX11.cpk, whose TOC is at the end.

Static · BarteY: a CPK/TOC packet carries a 16-byte leader (CPK or TOC ) and a little-endian packet size at +8; its table begins at +0x10. An encrypted @UTF table uses CRI's running XOR byte stream (low-byte seed 0x5F, multiply 0x15). In the plain table, offsets to rows, strings and data follow the big-endian table size; columns store a flag with storage nibble 0x10/0x30/0x50, typed values (integers, float, string or data) and a string-pool name offset. Schema and row bounds must be checked, not guessed from text strings.

Static · BarteY: CRILAYLA begins with CRILAYLA, little-endian unpacked-body length at +8 and compressed length at +0x0C. The final 0x100 stored bytes form the plain beginning of the output. The preceding bitstream is consumed backwards, writing the rest of the output backwards: a zero tag copies a literal byte, while a one tag reads a 13-bit distance and variable-length back-reference (minimum length 3). The expected extracted size is body length plus 0x100.

RAB, MRAB and EFARC metadata preservation

Static · BarteY, native_rab.hpp: the 0x20-byte RAB/SSA file record includes a self-relative signed name pointer, stored length, type index, preserved unknown word, two 32-bit timestamp words (ft1/ft2), a 32-bit absolute data offset at +0x18 and a retained final word z at +0x1C. The name table stores (name pointer, record index), alphabetically ordered. CMPL payloads report their unpacked size as a big-endian dword at blob +4. Preserve these fields, and reject duplicate exact names and out-of-range payloads; older notes that called the offset a u64 require this correction.

Static/offline samples · BarteY: retained-order RAB parse/rebuild was byte-identical for IG_CAVE503.RAB (5 entries), IG_HEIGEN507.RAB (279) and port-derived IG_DESERT508.RAB (424). Sample MRAB entry counts were 71 for E506_BIGGREY, 47 for E506_HA_BIGGREY and 28 for E506_HA_WEAPON; these are samples, not file-format caps. Type text is distinct from the archive-local type index; the per-record +0x0C hd flag matters. Names are record-relative, not file-absolute.

Static/round-trip comparison · novae, momotori01, ktaro: rebuilding ktaro's 21-entry MOD_NLP_EF228 EFARC with the EDF6VR rab.py produced the same 1,711,502-byte length; all 168 changed bytes were the 21 eight-byte FILETIME fields at record +0x10. This is not a byte-identical round trip. Its EFFECT, MODEL and TEXTURE types contain ESB, MDB and DDS respectively; compressed blocks use CMPL/LZSS.

Static CPK census · novae: Root.cpk contains 89 EFARCs, each with its own textures rather than a shared global pool. FlashBall02.DDS appears identically in 14 effect archives, while FlashRing11.DDS and FlashCross03.DDS each occur in five. Borrowing an existing effect therefore entails its ESB and named texture/model dependencies.

Classic SGO, DSGO and semantic CONFIG merges

Static · BarteY, native_sgo.hpp: classic SGO's 0x20-byte header stores version (normally 0x0102) at +4, variable count at +8, node table offset +0xC, name count at +0x10 and name table offset +0x14. Nodes are 12 bytes (type,size,value); integer/float have size 4, string lengths count UTF-16 units, and blob nodes 4/5 retain their distinct type codes. Embedded SGO blobs may be decoded recursively. The name table is sorted by UTF-16 text and maps back to variable indices; it is not necessarily variable order. Big-endian \0OGS changes byte and UTF-16 endianness.

Unverified · BarteY and SGOTT: a tool-recognized compact “2017 header” puts variable count at +4, fixed table start 0x10 at +8 and a name-pointer array offset at +0xC; each signed name pointer is relative to its own slot. The tool can parse/write this variant under synthetic version 0x0EDF2017, but no shipped example or game acceptance test was supplied. Do not treat it as a confirmed EDF6 on-disk variant.

Static · BarteY, native_dsgo.hpp: DSGO/OGSD stores node count at +8, with node-table and root pointers derived from header +4/+0xC (both 0x10 in the described writer). Each 16-byte node contains eight data bytes and a 64-bit type 0–4. Structures use a sub-header with child-index table and UTF-16-sorted name entries; children refer to node indices and may share nodes between parents. String references are node-relative; embedded payloads have their own length and skip-to-data fields. The graph cannot safely be converted by assuming a classic 12-byte SGO layout.

Static/offline corpus · BarteY: an .SGO suffix alone does not identify the serializer. Observed MISSIONLIST.OFFLINE.TXT.EN.SGO-type language tables were classic version 258, corresponding ...LIST.SGO files were DSGO, and certain deployed override text files were DSGO. Loading every override in game was not proven. Detect the binary magic per asset and validate weather DSGOs independently when porting.

Static · ktaro and novae: model-settings SGO carries MDB/CAS paths, distance-based LOD, ChangeParam, damage boxes/grids and embedded MAB/MTAB. MAB stores named attachment points (bone, geometry and embedded keys), clip events with timing and event settings; MTAB stores named material tracks, write modes and loops. Keys such as fire_model_direction, shell, camera or seat can be looked up by exact name; deleting them can break behavior. appeal_animation may have a separate MAB.

Static/offline port · BarteY: the studied EDF5 destruction-prop SGO template has 33 variables and its EDF6 target template 34, with one 16-byte-form conceptual record (0x682,1,4,0xFFFFFFFF) inserted at logical index 17. This is template-specific, not a universal instruction to add a variable to every SGO; native EDF6 prop templates can be reused for shared props.

Static/round trip only · BarteY, September 2026: a baseline CONFIG.SGO (27,826 bytes), an Air Raider mod (27,938) and an EDF5 mission-port version (41,592) were merged by baseline-relative semantic deltas to 41,704 bytes, without reported conflicts. The port adds six ModeList offline/online entries for MissionPack03–05; the mod adds weapon/vehicle IDs to specific SoldierInit arrays. Top-level variables are keyed by name, known tables by schema ID; unkeyed variable-length arrays do not have reliable element identity. A successful parser round trip does not establish successful in-game loading.

FMB terrain chunks and per-file profiles

Static · hajisensai / All Forces, novae: the FMB chunk-directory offsets start at 0x2C (not the older mistaken 0x30); the cited reader takes a count at +0x08. Each chunk begins with kind, center vec3 and half-extent vec3. Read the broader FMB layout section before applying a directory offset to an arbitrary variant.

Static/offline paired conversion · BarteY: FMB outer headers and directory/tree order differ between EDF5 and EDF6 even where 257/257 decoded terrain streams matched. In the inspector's header profile, +0x0C is the directory offset and +0x20/+0x24 select a chunk table; the decoded compressed-record byte +0x58 varies by record and file, so a fixed “config index +5” rule is invalid. EDF5 trees were preorder; EDF6 trees postorder. Neither FMB copying nor changing record class is a floor-collision conversion: MAPO/MAD provide the relevant separate object/collision contracts. EDFROOM01/02 lack FMB.

Static native EDF6 census · BarteY: IG_HEIGEN507.FMB has 511 directory entries, 27 config rows and a 1,658-byte string trailer; its four _ENKEI* profiles have 235–239 entries, 21 config rows and no trailer. MAPB/MAPO binary layout and runtime loading

Static · hajisensai / All Forces, novae: map.mapb starts MAPB, version 2 at +4. Header offsets/counts: strings +0x08/+0x0C, pair array +0x10/+0x14, 0x3C-byte definitions +0x18/+0x1C, 0x48-byte placements +0x20/+0x24. Ten other offset/count pairs occupy 0x28..0x77, and point/route structures follow at +0x78/+0x7C. Do not conflate these auxiliary point counts with placements.

Static · hajisensai / All Forces, novae: a MAPB definition (0x3C) carries type +0 (3 terrain/far), embedded SGO pointer and size +4/+8, self-relative name at +0x0C, and far distance at +0x1C. A placement (0x48) carries relative def reference +0, XYZ position +4, XYZ Euler degrees +0x10, variant/seed +0x1C, child-index list +0x2C, GUID +0x34 and far flag +0x44. GUIDs need not be unique in shipped data; zero seed can derive from their dwords. Drawing cutoff combines the definition with MAPO's per-record distance.

Static · hajisensai / All Forces, novae: MAPO header uses +0x08/+0x0C for 0x1C-byte placement companions, +0x10/+0x14 for (int,int,float) values, +0x20/+0x24 for 0x3C-byte object records, +0x28/+0x2C for relative pointers to them, +0x30..0x44 for vector/color arrays, +0x48/+0x4C for sorted/deduplicated UTF-16 strings, +0x50/+0x54 for 0x0C-byte named placement rows and +0x58/+0x5C for nested-list rows. Header offsets are MAPO-relative, entry references entry-relative.

Static · hajisensai / All Forces, novae: MAPO's 0x1C-byte per-placement record includes a possible FMep pair ref +0, object-array pointer/count +4/+8, float draw limit +0x0C, model and collision name refs +0x10/+0x14 and an int/int/float array ref +0x18 (not a T58 ref). A 0x0C-byte named row contains the decimal placement index string and a list of float/int pairs. Runtime preload keeps the MAPO companion alongside the placement index.

Static runtime trace · hajisensai / All Forces, novae, steam-678ccb46: loader 117F90 finds MAPB/MAPO in the MAC, fixes them up, loads MAD collision collision.hkt and dispatches up to four record-initialization tasks. 1169B0 chooses the resource class from suffix/parameters and receives each placement's matrix, MAPO companion and index; another pass traverses the resulting instances. Sample maps reach 13,251 records, not a fixed engine cap. Physical bodies are looked up by model name in MAD and instantiated with the object's transform; the placement GUID is not a MAD collision key.

Static crash diagnosis · BarteY: role suffix controls the registered parser. In a port, an MDB incorrectly registered as .trb was passed to the tree header reader, treating an MDB header word as a huge tree count; the bytes were intact but the chosen parser was wrong. Distinguish .mdx, .trb, .mosb and .fmep per MAPB entry. Never globally rename genuine tree entries. Visible geometry (RAB/MDB/MAPB) and physical bodies (MAD) are separate registries.

EDF5→EDF6 MAPB conversion, duplication and prop contracts

Static paired converter · BarteY: EDF5 MAPB definition/placement strides are 0x38/0x44, versus EDF6 0x3C/0x48. Conversion inserts a zero dword into each definition at +0x20 (rebasing fields moved after it), appends a dword to each placement and re-bases all self-relative def, name, embedded-SGO, LOD and placement-parent pointers, while preserving sentinel 0/-1. When tables are contiguous, t2Offset - t1Offset == t1Count * t1Stride identifies their original stride. Tail bytes are preserved but table positions move; a successful binary transformation still requires actual runtime validation.

CPK packet and @UTF table walk

Static source-reader study. Both the CPK header packet at file offset0 and the TOC packet at TocOffset start with 16-byte packet headers (four-byte tag and little-endian uint64 payload size at +8) followed by an @UTF table. A table may be masked using fixed keystream seed 0x655F and step 0x4115; the reader leaves an already visible @UTF unmasked. Table header is big-endian: body size at +4; from +8, version u16, row offset u16, string/data/table-name offsets u32, column count and row width u16, row count u32. Surveyed CPK tables use version0 and ACB version1. Archive entry keys include DirName, FileName, FileOffset, FileSize, ExtractSize; mismatch between extracted and stored sizes denotes CRILAYLA.

@UTF descriptor flags and column data types

Static. Descriptors begin at table-body +0x18, each with flags, u32 string-table offset for the column name, and an inline value for constant columns. High nibble 0x30 stores one constant in the descriptor, 0x10 omits the field (zero), and other modes store per-row values. Low nibble type mapping: 0/1 u8/s8, 2/3 u16/s16, 4/5 u32/s32, 6/7 u64/s64, 8 f32, 9 f64, 0xA string offset, 0xB data block {offset,length}. Row numeric values are big-endian.

Reported DX11.cpk identity

Static, build-specific. The author's Steam DX11.cpk SHA-1 is b80d56d0935464adf6b428164db81e463bd81284, corresponding in the source to Steam depot manifest 2291061/1491226774890510293. This is an identification fingerprint for that archive, not a guarantee for other game versions; SHA-256 and length are kept in the canonical EDF6 build notes.

Epic executable name is from an identification table

Two SGO serializers preserve values but not stock bytes

Static tooling comparison. The author's sgo.py offers write, which serializes arrays breadth-first with first-use string order, and write_depth_first, which serializes depth-first and sorts a shared name/string pool by UTF-16 code units, writing raw-area offset at header +0x1C. Both preserve parsed stock values but neither is byte-for-byte identical for every stock file. To modify a shader SGO, the source tool patches the original bytes by moving replacement raw blobs and shifting later string offsets rather than assuming round-trip byte identity.
