EDF6 RAB/MRAB composition: named entries, payload identity and cross-file dependencies

UniversalFormats & ContainersFile FormatsEDF 5EDF 6
Technical reference · Byte-identical archive rebuilds + four offline merge tests; cross-file image mapping unresolved

RAB/MRAB uses the SSA\0 container: its entries have names, types and independent payloads. Two mods can add different DDS textures to the same outer RAB path without overwriting each other, but a normal file-level overlay will keep only one provider's archive. The useful merge unit is the named SSA entry.

Identity and conflict model

A named entry is identified by its exact logical name. Its state includes its type string (rather than only its numeric type-table index), hd, ft1, ft2, z, and its opaque payload bytes/hash. Preserve unknown metadata and payloads rather than attempting to interpret the internals of DDS/MDB without a separate proven format-aware merge.

Two provider deltas Safe action
Different entry names are added or changed Merge both
Same entry added/changed to identical final state Deduplicate
Same name with different final type, metadata or payload Conflict
A deletes an entry that the other edits Conflict
A deletes an entry the other leaves unchanged Delete
Exact names differ only by case Keep identity distinction but warn for likely virtual-path collision

For type strings, retain the baseline table's order and append genuinely new types. Do not confuse the two mods' numeric type indices: identical integers can point at different strings after independent compilation.

Byte-exact observed controls

A retained rab_tool.py test used preserve_order=True and produced byte-identical parse → rebuild results on these exact files:

Measured archive Entries Size
IG_CAVE503.RAB 5 34,932,784 B
IG_HEIGEN507.RAB 279 88,866,805 B
Accepted IG_DESERT508.RAB 424 217,373,434 B

The studied E506 MRAB controls also used the same archive grammar: E506_BIGGREY contained 71 entries, E506_HA_BIGGREY 47, and E506_HA_WEAPON 28. These are sample-specific observations, not promises that any arbitrary RAB round-trips identically under every serializer setting.

Four offline PoC scenarios checked independent DDS additions, identical addition deduplication, same-name/different-payload conflict, and deletion versus unchanged/edited entries. The resulting archive was stable under another parse/rebuild. The test did not run a merged archive inside the game.

Image archives are related to mission metadata

MISSIONLIST.*.IMAGE.RAB is a logical companion of CONFIG.ModeList, mission LIST and localized TXT. Treat it as an entry-merge candidate, not an opaque last-wins file. But a successful SSA entry merge does not prove which preview image a changed LIST row selects. The later R29 mission-studio contract resolves that relationship for the studied EDF6 LIST format: LIST field2, with / normalized to _ and .dds appended, gives the entry identity. Unknown profiles must not automatically inherit that rule; see thumbnail binary and runtime provenance.

A safe composer must therefore mark mission-image archives cross_file_coupled and validate the resulting LIST/TXT/image relationship after a mission insertion or reorder. An archive can be byte-valid and still show the wrong thumbnail.

Know when entry merge is not the right approach

A pair of complete custom object/map families may need namespace rebasing of the whole resource closure, not entry merge at a shared vanilla path. Conversely, two different MDB/MAD/CAS/HKT payloads with the same embedded name cannot be byte-concatenated or patched without a separate schema-level merger. For opaque resources, identical hashes may deduplicate; differing hashes should fail closed.

See SSA binary header and entry layout, mission thumbnails and LIST linkage and SGO/DSGO semantic composition.
