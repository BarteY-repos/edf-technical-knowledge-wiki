EDF5 mission lifecycle: BVM state, Game Over, failure retention and ApplyResult

EDF 5Game technical referencesMissions and scripting
Technical reference · Contributor static analysis / source-graded observations; no new game runtime in R124

EDF5 stores campaign behavior in mission BVM bytecode interpreted by its mission runtime. The MissionMgr object owns the active MissionScript, and script state changes are distinct from which UI banner or result screen is currently visible. This matters when determining whether a mission has ended, failed, or actually committed its collected rewards and progress to save data.

Native mission-script lifecycle

The investigated MissionScript has states observed as 0 created, 1 started, 2 playing and later terminal/result states. Its result flag is separate from its execution state. EndMission(script, result) can be invoked from the mission BVM, debug control, pause menu, failed dialog and retry flow, with different result codes. A visible failure screen alone does not prove which exact final result has been committed.

The AngelScript Mission() native yields while a mission remains in the started/playing states; once a terminal state is reached, it returns the recorded result for higher-level menu logic. The original scripts layer several fades, sounds, layouts and result dialogs around that event.

Failure and Game Over

The source's MissionGameOverEvent script checks an all-players-down condition. Its failure sequence draws lyt_HUiMissionFailed.sgo, plays the failure jingle, opens the failed-result UI and ultimately calls EndMission according to the user's retry/exit choice. This is not the same as any arbitrary loss of one player's HP in co-op.

On a failed result, EDF5 retains a difficulty-dependent fraction of collected weapon and armor boxes: Easy 100%, Normal 75%, Hard 50%, Hardest 25% and Inferno 0%, using integer truncation. The retained source did not fully establish how every failed-screen branch later reaches the actual reward draw, so this should be described as a retained box-count result rule, not a guarantee of a particular item award.

Save commit and result order

ApplyResult(isMissionClear) first calls the pickup manager's loot-record commit routine. Only after that does its clear-only branch mark progress and perform relevant online result synchronization. ClearResult and a related reset routine clear mission counters. Because the commit and clear-only progress branch are separate, testing only the visible mission-complete banner is insufficient to prove weapon save data and progression were both recorded.

Mission numbers are list positions, not directory numbers

The folder mission/mNNN is an asset identifier; the on-screen mission number is the entry's position in missionlist.offline.list.sgo or missionlist.online.list.sgo. The source's original EDF5 list audit finds 110 offline and 111 online main missions, with tutorial and two late online missions producing the difference. Do not confuse those original-list measurements with the 112/111 and later 112/112 tables of a separately studied converted EDF5→EDF6 package.
