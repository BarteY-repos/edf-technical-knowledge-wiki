CMPL — compressed resource envelope inside EDF archives

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: CMPL is a compression wrapper around a piece of game data. It is not a model or an archive: its job is to turn stored compressed bytes back into the original resource.

Where it fits: A common reading path is RAB/MRAB entry → CMPL header → LZSS decompression → MDB model or DDS texture. CMPL also occurs in researched compressed FMB chunks.

Important distinction: The enclosing entry records how many bytes are stored; the CMPL header records how many bytes should come out after decompression.

Example (illustrative numbers): an archive entry might store 620 bytes of CMPL data. Its CMPL header could specify 1,024 output bytes. The first number includes the compression header; the second is the size after decompression.

Stored bytes versus uncompressed bytes

The measured SSA archive entry stores csize, the byte count of the stored blob, including any compression envelope. For a CMPL-encoded blob, source research identifies a big-endian 32-bit uncompressed size at payload offset +0x04.

That field is inside the resource blob, not an SSA directory field. Do not reinterpret the enclosing archive's little-endian offsets as CMPL fields, or confuse stored bytes with decompressed output bytes.

CMPL header and LZSS encoding

The EDF5/EDF6 format notes describe a CMPL payload with the following structure:

Position Field Documented meaning
+0x00 Four-byte CMPL signature Marks the compressed envelope
+0x04 Big-endian u32 Expected decompressed byte count
+0x08 onward LZSS-coded bytes Flagged literals and ring-buffer references

The documented decoder maintains a 4096-byte circular history buffer, initially writing at position 0xFEE (4078). A flag byte controls up to eight tokens, read least-significant bit first:

  • Flag bit 1: read one literal byte, emit it and append it to the history ring.
  • Flag bit 0: read two bytes b0, b1. Their big-endian packed word gives history position (b0 << 4) | (b1 >> 4) (12 bits), and copy length (b1 & 0x0F) + 3 (3–18 bytes). Emit the referenced bytes one at a time, appending each to the ring; both positions wrap modulo 4096. Copies can therefore overlap the bytes they are writing.

Implementation distinction: BlueAmulet's older description (2020) says one game implementation initialized only the first 4078 history bytes, leaving the last 18 unsafe to reference until written. By contrast, the later EDF6 FMB decoder study (reported 7 November 2026, function 3F540) describes a fully zeroed 4096-byte ring with the same starting position 0xFEE. These are source reports about different consumer paths/implementations; do not promote either initialization detail to a universal CMPL rule. A portable decompressor should choose and document its initialization behavior while validating all output and input bounds.

Worked example: eight literal bytes

This illustrative CMPL block produces the eight ASCII characters ABCDEFGH. It uses no back-references, so it is a simple way to see how the header and flag byte fit together:

43 4D 50 4C  00 00 00 08  FF  41 42 43 44 45 46 47 48
  1. 43 4D 50 4C spells CMPL in ASCII.
  2. 00 00 00 08 is the big-endian output size: eight bytes.
  3. FF is the flag byte. Its eight bits are all 1, so all eight following bytes are literal output bytes.
  4. 41 through 48 encode A through H. The decoder writes those bytes in order and stops when the declared eight-byte output is complete.

The stored CMPL block is 17 bytes (8-byte header, 1-byte flags and 8 literal bytes), while its output is 8 bytes. This is a valid demonstration of the framing, but it does not save space; real streams normally mix literals with references to earlier output.

Back-reference variant: the illustrative stream below produces ABCABC. Flag byte 07 means three literals (A, B, C) followed by a copy token. At that point the letters occupy ring positions 0xFEE–0xFF0. Packed bytes FE E0 select position 0xFEE and length 3, so the decoder copies ABC again:

43 4D 50 4C  00 00 00 06  07  41 42 43  FE E0

Both samples are constructed teaching data, not extracted EDF assets or a new in-game test. The header's output size is a separate termination/bounds contract: if compressed input ends before the declared output is produced, an extractor must report incomplete decoding rather than treat the partial buffer as a verified resource.

Termination differs by consumer: the November EDF6 FMB research reports that its decoder receives the stored CMPL byte count minus the 8-byte header and stops when that input runs out, without independently enforcing the declared decompressed count as an output limit. This makes the stored compressed length especially important for FMB leaves. The output-length check described above is a defensive extractor requirement, not proof that EDF6's FMB loader implements it.

If a member does not carry the CMPL signature, the cited source treats it as uncompressed data. Conversely, the signature alone is not proof that an inner MDB or another resource will load successfully in the game.

How to read a compressed resource

  1. Parse the containing archive and resolve the named entry.
  2. Validate its absolute data offset and stored csize against the outer file.
  3. Inspect the stored blob and identify whether it is CMPL or another payload family.
  4. Apply the appropriate compressed-blob decoder and validate the stated output size.
  5. Only then interpret the decompressed MDB, texture or other resource with its own format rules.

The source specifically distinguishes CMPL payloads from opaque/uncompressed entries. A parser must not assume that every archive member uses CMPL.

What decompression does not prove

A valid outer archive and successfully decompressed payload can still be rejected when the game loads the inner resource. One cross-game study uses an MDB crash case to illustrate this distinction. Packaging, decompression, resource parsing and runtime compatibility are separate checks.
