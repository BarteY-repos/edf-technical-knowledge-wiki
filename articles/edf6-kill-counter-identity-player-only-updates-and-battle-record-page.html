EDF6 kill counters and Battle Record: game-object names, player ownership and HQ rows

EDF 6Game technical referencesProgress and statistics
Technical reference · Source-scoped static analysis with contributor runtime marked; no new R129 game test

The native EDF6 kill counter follows an explicit object-name lookup. It does not count every destroyed object in a universal category, and it does not automatically inherit names from older EDF releases.

Kill messages and accepted counter names

The examined SoldierBase kill-message handler processes message 0x10000006. For a soldier with a local controller/pad object, the handler looks up the killed object's SGO field game_object_kill_counter and attempts to increment that named variable in the achievement store. If the name is absent from Achievement.sgo, the update does nothing.

That path explains two distinct observations: an NPC or a vehicle does not follow the local-player soldier's normal kill-message route, and a ported EDF4.1 enemy may bring a name EDF6 does not register. Some familiar names have also been reused for different enemy families: DragonKillCount refers to EDF6 tadpoles, Carrier1KillCount to teleportation ships, and AntHillKillCount to teleportation devices in the examined data. Exact name reuse matters more than apparent visual resemblance.

The source notes suggest that the achievement registry is local to each machine and does not receive an independent online synchronization channel. However, the route from a guest's enemy-death event back to the guest's player kill message was not fully traced. Therefore remote and guest kill ownership must remain partially unresolved.

Battle Record is a fixed presentation table

The HUiHQHistory page constructs 90 hard-coded rows; each contains a variable name, a display format and a scale factor. Formatting modes include integers, hours:minutes:seconds, a count suffix, percentages and meter values. A first pass checks the store and skips a KillCount row whose value is zero; a later pass looks up localized labels through StatusInfo_<name>.

This leads to two important distinctions: variables in the achievement registry and rows in the Battle Record UI are not the same set; a registered variable does not have to be shown, while a row that refers to an unknown name does not magically add that variable. The research also identified an unsafe sentinel-node read for a missing row name; the present wiki does not claim a tested gameplay failure from that path.
