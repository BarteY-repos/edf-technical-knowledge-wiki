EDF6 MissionPack selection crash: empty effective LIST and request identity

EDF 6Missions & ScriptingMissions
Technical reference · Direct observed Windows gameplay crash + native trace and later MP07 runtime PASS

A historical September 2026 EDF6 build exposed an unusually clean separation between loader timing, MissionPack identity/parity, mission-list data, and mission gameplay. The game crashed immediately on selecting a generated MP06 pack; neither the mission's map nor its AC/RMPA had run. Later tracing, allocation correction and a source-path fix led to a user-observed, complete offline Mission Clear for the studied MP07 pack. This is a qualified case study, not a general promise about all custom packs.

The observable crash

The generated pack existed and had a one-mission PackView with MISSION_001, an OFFLINE/ONLINE LIST, local text resources, and correctly hashed MISSION.AC and MISSION.RMPA. The loader reported configless loading of slot 6. Yet selecting MissionPack06 produced Windows exception 0xC0000094 (integer divide by zero) at EDF.dll+0xDD2A9 in the studied binary.

The analyzed game function computes a mission clear/progression ratio and divides by the currently selected mission count. At crash time that effective count was zero. That does not mean the generated LIST on disk contained zero rows. It means the game's effective selected LIST state was empty or unresolved at the moment the UI needed it.

Root cause 1: a request can arrive before the active slot is published

The R1C trace observed a legitimate CRI resource request:

/cri_bind/MISSION/MISSIONLIST_MISSIONPACK06.OFFLINE.LIST.SGO

At the file-open callback, MissionMgr+0x14FD0 still held -1, so a resolver that relied only on the manager's current active pack could not route the request to the custom provider. It incorrectly fell through to native lookup even though the requested path itself explicitly identified MP06.

The bounded R2 request-identity fix parses an exact managed MissionPackNN in the requested path, validates the managed slot/provider, and uses that identity before falling back to MissionMgr state. This fixes a timing race without globally routing arbitrary resource strings or requiring an extra native SetMode transition. The distinction is crucial: changing LIST contents or the compiler cannot repair a file lookup that never reaches the correct provider.

Root cause 2: old donor parity is a separate compatibility condition

The authored bundle used source slot MP03 (odd). The historical MPPP 1.0.2 validation path treats odd custom slots as the MP01 validation class and even slots as the MP02 class. The allocator had incorrectly assigned the bundle physical MP06, changing the parity of a legacy/donor-derived mode. A parity-preserving transaction migrated it to MP07, recorded MP06 as retired and prevented silent reuse of an old save namespace.

These are two independent, previously confounded problems. Correcting request routing does not automatically make the selected pack compatible with its donor validation profile. Equally, moving MP06 to MP07 without correcting the early request lookup could still leave an unresolved LIST read.

Do not conflate the historical R17 legacy-composer experiment (which never separately demonstrated a parity-flipped MP03→MP06 runtime PASS) with this later A2Z authored-MP06 negative and MP07 positive lineage. Both reinforce caution, but they are different test fixtures.

Generalizable debugging rules

  • When a pack-selection UI divides by a selected mission count of zero, first prove the runtime LIST read and resolved provider, not only the file's presence on disk.
  • Resource-request identity can precede MissionMgr active-slot state; an exact validated request path may be the only available authority during selection.
  • Preserve original legacy donor parity and save/progression identity unless a separate supported conversion policy overrides it. The later normal BASE_OWNED authored path has different entitlement rules.
  • Stop at the earliest failed gate: opening the LIST, launching a mission path, running AC/RMPA, and reaching Mission Clear are different boundaries.
  • Prefer transactional provider migration and retained namespace tombstones to silent slot renumbering.

See alias-free provider versus LIST mission paths, MissionPack07/08 tests, and donor-free BASE_OWNED policy.
