AngelScript mission events store the delay at event +0x58 and the EventType at +0x5C

Evidence: static · Build: steam-678ccb46 · Fact ID: as-event-type

AngelScript mission events store the delay at event +0x58 and the EventType at +0x5C; EVENT_TYPE_SYNC = 0, EVENT_TYPE_ASYNC = 1. The scheduler sorts ready events by delay (descending): ASYNC appends every ready event, SYNC keeps only the first (the greatest-delay ready event).

Basis: disassembly of the event scheduler, enum registration and CreateEvent implementation

Mission encounter report radius

Evidence: static · Build: steam-678ccb46 · Fact ID: encount-report-radius-bvm

Field-meaning correction: +0x470, although called an encounter-report radius by the script native, is the distance at which the object itself detects its target. +0x474 is the distance at which another object hears of that detection. The archived record's “how far an object reports its encounter” wording conflates the two. The BVM compatibility conclusion below remains a separate static finding.

Object +0x470 is the encounter report radius (how far an object reports its encounter): filled from the SGO's game_object_encount[0] (546118, re-read), the field EDF 4.1 keeps at +0x240 (edf41/missions.md#edf41-set-encount-report-radius). 228120(bvm - 0x30, handle, radius) is a BVM-style SetEncountReportRadius (it resolves the handle through 20C150; it and table 0 id 3020's 2288C0 share prologue and handle lookup), but no BVM table entry leads to it; AngelScript has its own native void SetEncountReportRadius(::Object , float ). The BVM native dispatcher 20FF70 (rsi = the script stack, r13 = the executor, r14 = this): table 0 id 3020's handler at 213D8B (sub rsi,0x10; lea rcx,[r14-0x30]; movss xmm2,[rsi+0x10]; mov edx,[rsi+8]; call 2288C0); table 1 (op 0x2D) jumps on the id's low 3 bits through the RVA table 2148BC (20FFF5..210014, edx = the id, rbx = the image base, re-read), whose entries 3, 4, 5 and 7 are 2100C3, the common end with no handler (mov rdx,rsi; mov rcx,r13; call 2276E0, the stack handed back); no EDF5 or EDF6 script and no converted EDF 4.1 script calls a table-1 id with those low bits (the author's check). Mission clear-mark calculation per player

Evidence: static · Build: steam-678ccb46 · Fact ID: mission-clear-bits

Mission clear marks: once per player, the clear function at 70D8C0 reads the difficulty [rcx+0x4C] (rcx = save) and the class [rcx+rbp+0x6E90], then loops SetBit (DFAB0) over save+0x57A4 (class, mission r14d, bit) from a start difficulty up to the cleared one (cmp edi,3 / cmovl: start 0 for Easy, Normal and Hard; the loop ends at 70D901). The bit lands in the byte [save + 0x57AC + class*0x200 + mission]: Easy 0x01, Normal 0x02, Hard 0x04, Hardest 0x08, Inferno 0x10.

Basis: FevGrave's disassembly notes in the patch; anchor 70D8CC unique

EDF Knowledge Hub record — original wording — expand (1,740 characters)

Object natives and their messages: ObjectAction (3200) in the native dispatcher 20FF70 (two-level jump tables 210014 / 21016D), case at 212A36: (handle, int) -> 20C150 (handle to object) -> SendMessage 1DA480(obj, 0x1000000D, &int) (EDF 4.1 sent 0x80000009); GetPartsObject (3300) 222470 builds {int group, int index, out weak} and sends 0x10000017 (EDF 4.1 0x80000012), returning the weak pointer as a script handle; Factor_ObjectDurability (9200) 221320 adds an EventFactor_ObjectDurability (RTTI name 179C908) to the event manager (rdi+0x138) when the object exists; SetEnemyGenerator / SetInstantEnemyGenerator (2100 / 2101, in 20FF70 from 211E90) send 0x20100 (the same number in EDF 4.1) with the block +0x08 kind (1 for 2101), +0x10 count, +0x14 interval (seconds x 60), +0x18 a float (the first float argument x a difficulty factor), +0x1C a byte flag, +0x20 the enemy SGO path (std::wstring), +0x40 int 1, +0x48 the unit index (EDF 4.1's block + 8). UfoMother511's OnMessage (slot 9 503A70) handles 0x20100, 0x20101, 0x20103 and 0x1000000D (others -> 504319; the generator cases at 503DFC / 503D03) and forwards 0x20100 to its N-th child unit by [data+0x48]; UfoCarrier508 hands 0x20100 to its generator component [this+0xD60] (6E1630), which reads +0x40 (always 1), and EDF6's generator levels, teams and activates what it spawns (6E335F). SetObjectDurability (3020) sets the minimum durability (damage-model.md#level-durability-natives; ApplyDamage clamps at 548172). November 2026: AngelScript event domains, generator factors and mission-port evidence

This section integrates the EDF6 mission-event-domains-and-generator-factors.md source records into the existing mission reference. It separates corpus-derived domain mapping from approximate syntax-based guesses and from source-reported mission-port runs. Absence of a script API function is not proof of absent native functionality.

Voice-script and game-script event handler placement

1,387 cue-bearing handler bodies split by actual script domain

Static corpus alignment. Among 44 original EDF5 missions shipped as EDF6 AngelScript, the source matched 1,387 event handlers containing spoken lines or voice cues by ordered cue signature: 1,176 resolve into the EDF6 voice_script path and 211 into game_script. Six signatures each match two candidate handlers (in M020_5, M032_5 or M058), but both candidates for each signature belong to the same domain. None of the cue-bearing bodies was left unmatched; ambiguity remains only at exact handler identity in those pairs.

High-game-domain missions and ambiguous handlers

Static. Domain census by mission (total cue handlers = voice/game): M079 94=45/49; M091_4 60=44/16; M021 54=47/7; M058 52=51/1; M020_5 46=44/2; M032_5 33=26/7. M001 Func_41 (TalkBegin, three Talk_AddSingle, TalkEnd) and M021 Func_38 (RadioBegin, TalkBegin, Talk_AddSingle, TalkEnd, RadioEnd, WaitVoice and event creation) are both game-domain. Two FR_AE065B* signatures each admit two game-domain handlers in M020_5, two in M058 admit two voice-domain handlers, and AE005_032_E has two matches in M032_5. Domain may be known even when exact matched handler is not.

Call-name heuristics misroute game-domain handlers

Static. RadioBegin occurs in 64/64 game-domain handlers and RadioEnd in 65/65, but TalkBegin and WaitVoice occur in both voice and game domains. An exploratory call-pattern classifier using obvious radio/speech and pure Talk patterns classified 1,121/1,387 bodies: 1,035 correct, 86 wrong, 266 abstentions. Of the 86 errors, 48 were in M079 and 14 in M091_4. Compiler routing must therefore use proven script ownership, not merely the presence of a dialogue API call.

Sync versus async voice handshake rule is wiki-derived

Static documentation, not binary-verified by this source. The existing wiki describes a synchronous EDF6 event type that coordinates a game-thread/voice-thread handshake through WaitVoice and GetTalkers; the asynchronous event type does not need that handshake. An original event marked multi==1 and mapped to the async type should not blindly retain those sync-only calls. Treat this as the current script-model reconciliation rule, not a new finding independently traced through EDF.dll.

Periodic and instant generators, cancellation and factors

Periodic SetEnemyGenerator versus finite instant generator

Static shipping-script contracts. SetEnemyGenerator(slot,resource,count,level,unit_interval,wave_interval,encountered) periodically emits count units per wave, spaces them by unit_interval and repeats after wave_interval until cancelled or its host dies. There is no total-spawn-limit argument in the recovered script signature. SetInstantEnemyGenerator(slot,resource,count,level,unit_interval,encountered) is finite; the corpus commonly pairs it with event factor Factor_WaitGeneratorEnd(host,slot), which participates in an event's condition test instead of blocking the executing script thread.

One-host slot cancellation and missing landing-complete factor

Static. CancelEnemyGenerator cancels one producer slot of a specified host. One historical helper iterates slots0–7, but that is not evidence that every native generator class implements eight active slots. Incoming Anchor scripts instantiate a generator and invoke E505_GENERATOR_ACTION_FALL. The recovered API has no Factor_E505Landed, Factor_ObjectActionEnd or WaitAnchorLanding. A timed Wait after fall is an approximation, not a signal that the landing animation or physics transition actually finished.

Factor_GeneratorEnemyCount counts hosts, not child enemies

Static source-script evidence. Factor_GeneratorEnemyCount(N) counts currently active generator hosts such as nests, carriers and generator objects; a shipping comment includes a Mother as a generator. Missions combine it with Factor_TeamObjectCount(TEAM_ID_ENEMY,N), proving the two observe distinct state. For living spawned enemies, use Factor_TeamObjectCount (all enemy-team objects), Factor_AreaTeamObjectCount (within an area), or Factor_GroupObjectCount (assigned group). Do not substitute host count for a pylon's live children.

No script cap parameter; native wave limit remains open

Static, bounded negative evidence. None of the recovered EDF6 script generator calls accepts an active-population cap or lifetime total cap. The source did not determine whether the native generator has a concealed host/slot/team live cap, how exceeding such a cap behaves, or whether wave_interval is measured from wave start versus previous batch end. EDF5's known native loop caps living spawns at its amount, but that is a cross-game comparison, not proof of identical EDF6 implementation.

Humanoid calls, MovingFortress modes and native fog composition

Humanoid cuscall families and 64-entry hash branch

Static. EDF6 Humanoid dispatcher 467200 retains four distinct call families: cuscall, cuscall1, cuscall2, cuscall3. Its cuscall1 branch computes id & 0x3F to select an entry from a 64-way jump table, then resolves collisions by full ID. This low-six-bit table index has no relation to EDF5 BVM's invalid instruction opcode range 0x39–0x3F; do not use that coincidence to reject legal custom call IDs.

No stock E506 low-stance custom call found

Bounded static negative result. The examined Humanoid custom-call branches do not write low-state timer +0x10F0, set EAC & 0x100 or reference low thunk 466E1C. E506's OnInitialize BVM sets up a thread and calls cuscall0/cuscall3; commands20 and25 differ in movement and turn speed, not crouch selection. No stock BVM custom call was found to force E506 D18 LOW state. This does not prove there is no other native gameplay route to that state.

Symbolic bitmask and mode constants, not arbitrary integers

Static mission API contract. Object::MovingFortress_Activate(weapon,mode) accepts weapon constants 1 MOVINGFORTRESS_BIG_CANNON, 2 MOVINGFORTRESS_CANNON, 4 MOVINGFORTRESS_SMALL_CANNON1, 8 MOVINGFORTRESS_SMALL_CANNON2, 16 MOVINGFORTRESS_SMALL_CANNON3, 32 MOVINGFORTRESS_SMALL_CANNON_GREEN; mode0 is MOVINGFORTRESS_FORT, mode1 MOVINGFORTRESS_MOVING. Preserve these symbolic domains when translating mission event calls instead of treating parameters as generic numeric slots.

Merman_FogScene requires environment and scene-effect changes

Static script composition. Merman_FogScene(second,near,far,apply_ratio) expands to five operations: EVENT_LIGHT_ENV_FADE_FOG_BG_APPLY, EVENT_LIGHT_ENV_FADE_FOG_COLOR, EVENT_LIGHT_ENV_FADE_FOG_DISTANCE, SceneEffect_Fog(...), then SceneEffect_StartFade(...). The direct public SceneEffect_Fog(float,float,float,float) alone spawns 400 (0x190) particles of size10 and forwards duration/speed/horizontal parameters. Dense short-visibility fog needs the three environment fades as well, not only particles.

Ported EDF5 mission failures, script types and weather-profile fixes

AngelScript type error can manifest as black mission screen

Source-reported port test. An early EDF5→EDF6 M008 (visible mission12) AngelScript port stopped at a black screen with compiler error Can't implicitly convert from 'bool' to 'int&', not a graphical error dialog. The port had dropped return values from IsAiMoveEnd(carrier01/2/3), assigned Boolean expressions to integer counters and kept a while(true) without the required break. Official EDF5 logic ORs negated movement-complete tests, adds carrier01_4 on higher difficulty, yields between checks and exits only after all relevant carriers finish. A later project sweep reported M008 loading; the failing code must not be treated as a correct donor pattern.

IsOnlineMode is Boolean in mission AngelScript

Source-reported M081 script port. EDF6 IsOnlineMode returns bool; comparing it with integer zero as in an EDF5 port (IsOnlineMode == 0) had to become IsOnlineMode == false for the tested M081 to load. A later combined build regressed for a different reason, so this establishes the specific return-type repair and does not license blanket conversion of every int-like flag into Boolean.

DM024 return-type repair and M018 local route grounding

Source-reported port checks. Correcting the object return type of DropBoat_SetCrew succeeded in DM024; a second use of that function in M075 was not tested. M018 Escape loaded the EDF6 DLC RM018/MISSION.RMPA opening NPC route, with four route groups and eleven waypoints, preserving route shape and spawn records. Its vertical correction was mission-local grounding, not a general rule to transform every RMPA coordinate set.

M200/M201 dense fog needs map-local CLOUDY environment assets

Source-reported modified mission run. EDF5 M200 (visible mission58, NW_JYOUSUICITY) and M201 (72, NW_KITAGUNICITY) loaded with valid SceneEffect_Fog(float,float,float,float) but remained visually clear under stock cloudy. The tested fix created map-local weather data from EDF5 CLOUDY RAB under separate E5CLOUDY names and changed that mission's PreloadMap/Map weather choice to e5cloudy, leaving native cloudy untouched. Dense fog requires matching environment fog distance, color and background, plus particles/event fades; repairing the script signature alone is insufficient.

M020_5 sandstorm difference originated in map environment profile

Static source comparison and reported failing port. M020_5's high-level sandstorm calls agreed with native EDF6 IG_2000MCITY601/evening examples, yet the modified mission looked wrong because its map environment/weather profile differed. The source warns against inventing a fog-distance multiplier, swapping in an unrelated map's weather, or copying 601's native weather assets blindly to another map. The fix belongs to the target map's own environment profile and its coupled mission weather selection, not an arbitrary global shader adjustment.

BVM container, function layout and exact compiler sizes

Source scope: fourteen static records from the contributor's bvm-container-and-native-signatures.md and the bvm41.py/missions.py parser, stack checker and native-dispatch emulation. These are documented script-compiler observations, not an independent proof that every native call is safe to execute in a game.

BVM header: ASCII BVM , 0x50 bytes of little-endian words: +04 header length 0x50; +08/+0C zero; +10 version 0x01150138; +14 value 2; +18/+1C global count and 32-bit-name-offset table (starts at 0x50); +20/+24 function count and table offset after globals; +28/+2C 0x200 stack-related fields; +30 code start; +34 function-code base (initializer's end); +38 string pool start; +3C script-name offset; +40 zero; +44 end of script name aligned to four; +48 zero; +4C size aligned to sixteen. The author's output pads with byte 0xBA. Its parser rejects another version word; EDF6 executor constructor 20DC10 was cited.

Function rows and emission order: each 16-byte row contains a stub offset relative to header +0x34, name offset, parameter-type byte offset and packed signature (low byte parameter count, upper bytes flags). Emitted code starts with the global initializer (global = constant, then end). For each table-order function, the contributor's representation includes an epilogue pushl 0; fp+ N; ret and body fp- N; storel 0; storel <parameters>... jumping to that epilogue. Function-table addresses point to final call stubs call <body>; end, not straight to those bodies. These orderings are important for byte-matching a stock script.

Opcode byte: op | (size << 6), where top two bits specify operand length 0/1/2/4 bytes. Encoded 0-length operands read as zero. The author's typed-opcode set is 01 04 05 06 07 09 0A 0B 1D 1E 1F 20 21 22 23 24 25 31, each followed by one type byte. Signed operands: push(15), pushla(18), jumps 26/27/28/34/35 and call(29); otherwise unsigned. Branch/call offsets are relative to the opcode address. Native dispatch uses 2C..2F with an ID operand. The parser rejects opcodes above 0x38.

Contributor's known opcode labels: 01 storei, 02 pop, 09 neg, 14 pushg, 15 push, 16 storeg, 17 pushl, 18 pushla, 19 storel, 1A pushs (pool byte offset), 1B fp+, 1C fp-, 1D and, 26 jz, 27 second conditional branch, 28 jmp, 29 call, 2A ret, 30 end, 33 push1, 34 jne, 35 another two-operand branch and 36 storeind. These are local disassembler names; unlisted opcode meanings are not inferred.

Stack checker: pushes minus pops is +1 for 03 14 15 17 18 1A 33; 0 for 09 0A 0B 11 12 13 1B 1C 1F 28 30; -1 for 01 02 04 05 06 07 08 0C 0D 0E 0F 10 16 19 1D 1E 20 21 22 23 24 25 26 27 2A 31 32; -2 for 34 35 36. A call consumes the callee's argument count and leaves its result count; natives use the traced signatures below. This is the author's modeled stack accounting, not an abstract guarantee of all opcode semantics.

String pool order: zero-terminated UTF-16LE strings packed without per-string alignment: literal strings once in first-pushs order, global names, function names, then all parameter-type bytes contiguously (01 integer, 02 float, 03 string), and finally the script name. pushs refers to a byte offset from the string-pool base.

Byte-identical layout heuristic: the compiler begins by reserving four operand bytes per instruction (conditional jumps 34/35 use two more), then chooses shorter sizes in forward instruction order. Under yet-unreduced following instructions, a forward jump fits one byte at ≤127 bytes, while a conditional jump or call fits ≤126; backward threshold is ≥-122. Two-/four-byte boundaries are +32767 and -32762. A semantically valid rebuild with a different fixed-point shrink schedule need not byte-match stock output. These thresholds belong to the author's reproduced _layout algorithm.

Signatures and upper flags: the lower byte supplies parameters; EDF6 function starters read the parameter count as a signed byte from table row +0x0C (source callsites 10ACB0B+0x37, 10ACC28+0x64), so counts ≥0x80 are not usable. A packed 0x100 flag is interpreted as one return value in shipped _SetupBarrier and CruiseAndRespawn, which callers then pop/store. Meaning of other high-bit flags has not been established.

Mission-script states and native loading lifecycle

These are contributor-attributed findings for the examined EDF6 Steam build, not universal addresses across releases. BVM and AngelScript executors expose corresponding state/result accessors but store their values at different offsets. Native control-flow and gameplay observations are distinguished below.

MissionMgr executor state and result slots

Source evidence: static disassembly and vtable reads. The current mission script executor is [MissionMgr+0x40], with the manager reached via [EDF+20B28A8]; this pointer can be null. Native 1F68B0(mgr) asks whether a script is still running. Its path calls executor slot 10 (22DA70), which reads slot 6 (+0x30) and considers any state other than 3 still active. Slot 7 (+0x38) reads the script result. For BVM implementation vtable 179D230, slot 6 222880 reads state +0x128, while slot 7 222870 reads result +0x12C. AngelScript implementation vtable 1793070 uses slots 1DDF40 and 1DDF30, reading state/result from [executor+0xE8]+0x2B8/+0x2B4 respectively. Do not read BVM offsets from an AngelScript object.

BVM state writes, completion and result propagation

Source evidence: static writes/xrefs. BVM state +0x128 becomes 1 at 222EDA during load (executor slot 2 222A70), 2 at 21FBC3 in native loading code, and 3 in the end handler, slot 3 220B40. State 2 corresponds to playing by comparison with the EDF5 pattern; this label is an inference. Slot 3 also writes the result +0x12C, stops BGM (7B2FF0, 7B0E50) and calls 11956C0. Native 1F6820(mgr) obtains the result from executor slot 7 or, with no executor, from MissionMgr +0x50. ExitMission at 1F67F0 writes its argument to manager +0x54 and calls executor slot 3; mission-start state 70F0B0 suspends the menu AngelScript context while 1F68B0 reports running and then returns 1F6820.

AngelScript BeginLoading and EndLoading

Source evidence: static native registrations, state-write search and xrefs. void BeginLoading is at 1ACB10 (declaration 1794F10, registration 1E69C6); void EndLoading is at 1B49D0 (declaration 1794F28, registration 1E6A6B). BeginLoading writes AngelScript state [this+8]+0x2B8 = 1, clears bit 0 of +0x2B0, calls UI manager code 119C600, stores the return at +0x50/+0x58 (loading-layout meaning inferred), and increments a busy counter at [2139AB0]+0x34 through 1133FC0. EndLoading sets the flag bit, writes state 2 at 1B4A56, decrements that counter and clears SeManager [20B2950]+0xD8. The shared atomic counter has uses in HQ jobs and the game loop, so it must not be interpreted as a mission-only signal. AngelScript state 3 is written at 1DDEC2; the BVM state-2 write is 21FBC3.

Plugin ExitMission(1) and the two executor types

Source evidence: static call-path analysis, cross-referenced to the separately source-reported offline clear test. A game-thread plugin call 1F67F0([EDF+20B28A8], 1) requests MISSION_RESULT_CLEAR and routes to virtual slot 3 (vtable+0x18) of either BVM or AngelScript executor. The AngelScript slot 1DDE90 records state 3 at [[executor+0xE8]+0x2B8] and result at +0x2B4; BVM slot 220B40 has its own matching completion path. AngelScript internal_Exit at 1BCFA0 reaches this same virtual end call through a registered std::function at [functions+0x48]; the auxiliary functions pointer is [executor+0xF8]. A reported clear/result screen does not establish identical reward, statistics or achievement behavior to normal mission completion.
