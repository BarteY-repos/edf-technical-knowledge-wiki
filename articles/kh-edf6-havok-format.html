EDF 6 — Havok Format (community source notes)

EDF 6Community Knowledge HubCollision & Physics
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Tagfile container

EDF6 Havok files are Havok 2020.1 binary tagfiles: magic TAG0, SDK version string 20200100

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-identity

EDF6 Havok files are Havok 2020.1 binary tagfiles: magic TAG0, SDK version string 20200100; section headers big-endian, DATA values little-endian. Engines: Havok Physics 2020 (hknp*), Havok AI (hkai*), Havok Animation (hka*, partly).

Basis: every game file

Attribution: ktaro, SHKT report (Spec §1) · 2026-10-16

Every section starts with an 8-byte header: u32 big-endian (bits 31-30 kind, 0 = has sub-sections, 1 = data

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-sections

Every section starts with an 8-byte header: u32 big-endian (bits 31-30 kind, 0 = has sub-sections, 1 = data; bits 29-0 total size including the header) and a 4-char tag. All EDF6 files: TAG0 (kind 0) holding SDKV ("20200100"), DATA, TYPE (kind 0: TST1 type-name strings, TNA1 type declarations, FST1 member-name strings, TBDY type bodies, TPAD padding) and INDX (kind 0: ITEM). No THSH (type hashes) or PTCH (patch table).

Basis: every game file

Attribution: ktaro, SHKT report (Spec §3.1) · 2026-10-16

Packed integers (TNA1, TBDY): first byte 0xxxxxxx 1 byte, 7 bits

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-packed-ints

Packed integers (TNA1, TBDY): first byte 0xxxxxxx 1 byte, 7 bits; 10xxxxxx 2 bytes, 14 bits (big-endian); 110xxxxx 3 bytes, 21 bits; 111xxxxx 4 bytes, 29 bits (27 in TNA1); 0xE8 (TNA1 only) 5 bytes, the next 4 are a big-endian u32 (for constants like 0x7FFFFFFF). TST1 / FST1 are NUL-terminated strings padded with 0xFF, referred to by index; a template argument named t... is a type argument, v... a value. TNA1: packed type count N (type 0 = none), then per type 1..N-1 its name index, argument count M and M pairs (name index, type index or number).

Basis: every game file

Attribution: ktaro, SHKT report (Spec §3.2-3.4) · 2026-10-16

TBDY records: packed type index, parent index, flags

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-tbdy

TBDY records: packed type index, parent index, flags; flags & 0x01 subTypeFlags; & 0x02 (kind >= 6) pointed / element type; & 0x04 version; & 0x08 byte size and alignment (low 12 bits; upper bits flags); & 0x10 abstract value; & 0x20 member count (low 16 bits) then per member name, flags, offset, type; & 0x40 interface count then (type, value) pairs. subTypeFlags & 0xFF: 0x00 void, 0x02 bool, 0x03 / 0x83 string (0x83 = hkStringPtr), 0x04 integer (0x200 signed; 0x2000 / 0x4000 / 0x8000 / 0x10000 = 8 / 16 / 32 / 64-bit), 0x05 float (0x1746 = float32), 0x06 pointer, 0x07 class, 0x08 array, 0x28 tuple (fixed array, for example hkVector4). Offsets are the serialized DATA layout, not the x64 in-memory one. A type with no objects in a file is declared in TNA1 without a TBDY body (hknpShapeInstance in the 31 files without compounds), so writing a new kind of object needs its body (and those of its parent and member types) added; same-named bodies are identical across all game files (258 types).

Basis: every game file

Attribution: ktaro, SHKT report (Spec §3.5) · 2026-10-16

INDX / ITEM: 12-byte entries (entry 0 = null): u32 flags (bits 0-23 type index

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-items-values

INDX / ITEM: 12-byte entries (entry 0 = null): u32 flags (bits 0-23 type index; bit 28 set = pointer target (object), clear = array / string elements; bit 29 = reached through an array or string), u32 offset from the start of the DATA payload, u32 element count. In DATA, pointers (hkRefPtr<T>, T*), arrays (hkArray<T>, count = the item's count) and strings (hkStringPtr, a char array including the NUL) are u32 item indices; hkReal is an IEEE float32; hkHalf16 is the upper 16 bits of a float32 (bfloat16, not IEEE half; 0x3F4C = 0.796875); hkUFloat8 is not decoded yet; tuples are a fixed number of elements; classes follow their TBDY members.

Basis: every game file

Attribution: ktaro, SHKT report (Spec §3.6-3.7, §3.8) · 2026-10-16

Writer rules that reproduce every game SHKT (316), navmesh (8 tested) and map collision.hkt (50) byte for byt…

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-writer-rules

Writer rules that reproduce every game SHKT (316), navmesh (8 tested) and map collision.hkt (50) byte for byte: item 1 is the root; pointer targets join an object queue in the order found, and after each object everything reachable from it without another pointer (its closure) is numbered breadth-first; inside an item, references are visited member by member across all elements (base-class members first), arrays over 1024 elements in chunks of 1024, strings deferred to the end of the item; equal strings share one item; empty arrays are null (no item has count 0); an object may be referenced from several places. DATA: objects in item order, each followed by its closure, every item aligned to its type's alignment with zero padding, DATA padded to 16. Type section order = the order the writer registered types; packed ints always shortest; TST1 / FST1 padded to 4 with 0xFF, TNA1 / TBDY with zeros; TPAD always empty.

Basis: round-trip tests (ktaro's tests/EdfHavok.Tests)

Attribution: ktaro, SHKT report (Spec §3.8) · 2026-10-16

Compressed mesh shapes (hknpCompressedMeshShape, data in hknpCompressedMeshShapeData.meshTree): sections hold…

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-encoding

Compressed mesh shapes (hknpCompressedMeshShape, data in hknpCompressedMeshShapeData.meshTree): sections[] hold firstPackedVertexIndex / numPackedVertices, firstSharedVertexIndex, firstPrimitiveIndex / numPrimitives. Packed vertex (32 bits): x low 11 bits, y next 11, z high 10; position = codecParms[0..2] + codecParms[3..5] x (x, y, z). Shared vertex (64 bits): x low 21, y next 21, z high 22; position = domain.min + (domain.max - domain.min) x (x / (2^21-1), y / (2^21-1), z / (2^22-1)). Primitive (4 bytes): four section-local vertex numbers; below numPackedVertices = packed vertex, else shared vertex sharedVerticesIndex[firstSharedVertexIndex + number - numPackedVertices]; 3rd = 4th: triangle, else quad (0-1-2, 0-2-3); 1st = 2nd: a convex shape from externShapes (decoy-screen pieces); DE AD DE AD = removed primitive, not counted in numTriangles (EDFROOM601 and others). Checked on all 17,827 such shapes (296 in objects, 17,531 in maps).

Basis: every game file decoded (triangle counts and domains match)

Attribution: ktaro, SHKT report (Spec §4.4) · 2026-10-16

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-kinds

The 296 compressed meshes of objects and weapons are of two kinds, never mixed: 82 convex-only (always one section holding 2 to 63 convex hulls: V601 TANK, V602 HELI, V603 FLAK, V607 ROBOTRUCK, V608 OLDROBOT (21 of them), V610 / V611 PTRUCK, PD601 DRONE, decoys, enemy weapons, MARTIAN and others) and 214 triangle-only (1 to 370 sections, 24 to 58,771 triangles: E510 FORTRESS, E511 MOTHERSHIP, E609 JORMUNGAND, E611 TIMESHIP, E613 CAPSULE, E614 GRANDMOTHER, E615 HORNETNEST, EV605 BARGABASE, E513 BARRIER, TRANSPORTER401BOX and others). hknpShape.flags is 4 and connectivity empty in all of them. Maps hold 17,531 more (compressed-mesh-encoding).

Compressed-mesh shape keys: key = section 8 | primitive within the section 1 (+1 for the second triangle of…

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-keys

Compressed-mesh shape keys: key = section << 8 | primitive within the section << 1 (+1 for the second triangle of a quad). bitsPerKey = numShapeKeyBits = the bits needed for the largest key (one exception); maxKeyValue = the largest key; numPrimitiveKeys = the number of triangles (convex kind: of convex shapes; two files off by 1 to 2); triangleIsInterior.numBits = largest key + 1 (convex kind: 2n - 1 for n hulls).

Basis: every game object and weapon mesh

Compressed-mesh trees

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-trees

Compressed-mesh trees. Section tree (sections[].nodes, Aabb4BytesCodec, 2n - 1 nodes for n primitives, at most 127 primitives per section): binary, preorder; an inner node's data = offset to its right child | 1 (the left child is the next node; offsets are even), a leaf's data = primitive << 1. In each xyz byte the high nibble h lowers the parent box's minimum and the low nibble l its maximum (parent box [lo, hi], width e): min = lo + e * h^2 / 226, max = hi - e * l^2 / 226 (single precision); choosing the largest h and l whose box still contains the child reproduces all 2,400 axes of the 82 convex meshes byte for byte. Top tree (meshTree.nodes, Aabb5BytesCodec, 2s - 1 nodes for s sections): preorder; an inner node has 0x80 in hiData and ((hiData & 0x7F) << 8 | loData) * 2 is the offset to the right child; a leaf holds the section number hiData << 8 | loData; a section's leafIndex is its leaf's node number (all 1,671 sections of the triangle kind check out: the leaf box contains the section's domain). SIMD tree (data.simdTree, hasSimdTree 1, isCompact 1): the compounds' 4-wide tree (node 0 empty, node 1 the root), leaf data = the primitive's key (a quad: its even key); keys complete except one primitive missing in BARGABASE.

Basis: every game mesh decoded; re-encoding the game's trees

Attribution: ktaro, EDF6 SHKT Editor 1.0 (research/15, Spec §4.4) · 2026-10-19

Compressed-mesh mass properties (hknpShapeMassProperties): the domain box itself (volume = the box's, center…

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-mass

Compressed-mesh mass properties (hknpShapeMassProperties): the domain box itself (volume = the box's, center = the box's center, inertia 1.5 x that of a solid box, 1.5 * m * (b^2 + c^2) / 12, principal axes = the shape's axes, majorAxisSpace stored as (0, 0, 0, 29999/30000)); the 1.5 holds even in files whose hull inertia factor is 1.0 (15 of 18). The mass is a round value (1 to 30,000; 31 distinct values in the convex kind; TRANSPORTER401BOX = volume x 1000) and equals bodyCinfo.mass in all 82 convex meshes but in only 86 of 214 triangle meshes. domain.min/max w: 0, 0.99 / 1.01 or junk, apparently unused.

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-convex-kind

Convex-kind compressed mesh, every field (all 82 verified against values computed from the hulls): externShapes = the convex instances (flags as in compounds: 0x40, translated 0x02, rotated 0x04, but a rotation of about 1e-16 counts as none, so a tolerance is needed; leafIndex 0 or 65535; shapeTag / destructionTag 65535; scale 1); meshTree.domain = Section.domain = the union of the hull boxes including convex radius; one section: codecParms = (3.40282e38 x 3, -inf x 3), all first* 0, numPackedVertices 0, numPrimitives = n, numDataRuns 1, page 0, leafIndex 0, layerData 0, flags 1; primitive k = (4j, 4j, 4, 4j) where 4j is a position in sharedVerticesIndex, which holds 4 words (146, 0, hull number, 0) per hull (hull order free); no packed or shared vertices; primitiveDataRuns one entry (value 65535, index 0, count n); meshTree.nodes one all-zero node; triangleIsInterior all 0; primitiveStoresIsFlatConvex 255; shape header type 8, dispatchType 3, flags 4, convexRadius 0, userData 0, shapeTagCodecInfo 0xFFFFFFFF.

Triangle-kind compressed mesh: a section holds at most 127 primitives, 107 own (packed) vertices and 198 shar…

Evidence: static · Build: steam-678ccb46 · Fact ID: compressed-mesh-triangle-kind

Triangle-kind compressed mesh: a section holds at most 127 primitives, 107 own (packed) vertices and 198 shared-vertex references; a primitive index below the section's packed-vertex count is its own vertex, otherwise sharedVerticesIndex[firstShared + index - numPacked]. Packed vertices (11/11/10 bits): the section's codecParms = (offset xyz = the minimum of its packed vertices, scale xyz = their width / (2047, 2047, 1023)); every axis uses its full range except 3 sections with a zero-width axis. Shared vertices (21/21/22 bits) are quantized against the whole mesh's domain; 79 % are used by several sections (section borders). Primitives (a, b, c, c) are triangles and (a, b, c, d) quads split into (a, b, c) and (a, c, d): 174,419 quads and 23,318 triangles; whether quads need coplanarity is not studied. primitiveDataRuns give each run of primitives a material tag (65535 or 0 here); section flags 0, page 0, layerData 0.

Basis: every triangle mesh decoded

Attribution: ktaro, EDF6 SHKT Editor 1.0 (research/15 §4) · 2026-10-19

triangleIsInterior of triangle-kind meshes is not understood: it is set on 112,419 of 372,156 keys (about 30…

Evidence: static · Build: steam-678ccb46 · Fact ID: triangle-is-interior

triangleIsInterior of triangle-kind meshes is not understood: it is set on 112,419 of 372,156 keys (about 30 %), only ever on triangles without open edges (no counterexample), and every simple geometric rule tried (all edges closed, flat, convex, no concave edge, same section, quad half) matches only 31 to 68 %. EDF.dll has no code that computes it (the string is referenced only from type information), so Havok's authoring tools produce it. Writing all 0 is the editor author's untested guess ("not interior"), probably only an optimization flag for skipping edge and vertex contacts; this is why the editor never writes triangle meshes.

Basis: statistics over every game mesh; one Ghidra string reference check

Attribution: ktaro, EDF6 SHKT Editor 1.0 (research/15 §4, Spec §7) · 2026-10-19

Flags that the Havok 2020 tagfile format defines but no EDF6 file uses: type flag 0x80 (attribute string foll…

Evidence: static · Build: steam-678ccb46 · Fact ID: tagfile-unused-flags

Flags that the Havok 2020 tagfile format defines but no EDF6 file uses: type flag 0x80 (attribute string followed by one packed value) and 0x100 (mutable, no value), and member flag 0x80 (a packed alignment value before the offset). In all game files type flags stay within 0x00-0x3D and member flags are only 0x20, 0x22, 0x24.

Basis: every game file; the flags come from external material (the Bartey kit) and a LibXenoverse2 audit

EDF.dll contains a reader for the legacy Havok binary tagfile format (hkSerialize::TagfileReadFormat2014, for…

Evidence: static · Build: steam-678ccb46 · Fact ID: legacy-tagfile-reader

EDF.dll contains a reader for the legacy Havok binary tagfile format (hkSerialize::TagfileReadFormat2014, format name "Binary Tagfile <=2014.2") and about 500 classes of the legacy physics engine (hkp*). The SHKT loader still looks for hknpPhysicsSceneData (physics-shkt.md#shkt-loader), so whether a legacy-format file such as RAGDOLL_TESTVEHICLE401.HKT (hkpPhysicsData) becomes bodies is unknown (not tested in game; later answered for the ragdoll path, which migrates it, and the map path, which crashes: physics-shkt.md#hkp-physics-migration).

Basis: strings in EDF.dll, confirmed by ktaro after the pointer in BarteY's kit

Attribution: ktaro, EDF6 SHKT Editor 1.0 (Spec §1.1, Usage §2 update 2026-10-11) · 2026-10-19

Constraint values (all 2,838 ragdoll constraints and limited hinges): bodyA = child, bodyB = parent

Evidence: static · Build: steam-678ccb46 · Fact ID: constraint-value-rules

Constraint values (all 2,838 ragdoll constraints and limited hinges): bodyA = child, bodyB = parent; transformA / transformB are the joint frames in each body's space, and their pivots coincide in model space (at most 0.8 mm over all 3,051 joints); atoms (ball-and-socket, stabilization) identical in every joint; motors disabled, target_bRca = the rotation of transformB. Limits are stored as radians plus 1/cos and tan computed from them: angle <= -pi or >= pi (float compare) or a plane limit of 0 -> sentinels (1/cos 2.11111, tan +-1.84467e19); a cone without a lower limit is stored as -100; within 0.03 of pi/2 -> the values for pi/2 -+ 0.03 computed in float (1/cos 33.3384, tan 33.3234); otherwise 1/cos and tan of the angle computed in double (matches all 6,484 values). Plane limits are stored as pi/2 + plane angle. The w of every body position is 1.

Basis: every game file

Attribution: ktaro, SHKT report (Spec §5.5, §5.7) · 2026-10-16

Map containers

.MAD = MARC v5 archive holding exactly one file, collision.hkt (all 50): 0x00 "MARC"

Evidence: static · Build: steam-678ccb46 · Fact ID: mad-marc-layout

.MAD = MARC v5 archive holding exactly one file, collision.hkt (all 50): 0x00 "MARC"; 0x04 version 5; 0x08 data offset 0x24; 0x0C name block position - 0x24 (= align16(0x24 + size) - 0x24); 0x10 data size; 0x14 entry table position - 0x14 (relative to that field); 0x18 file count 1; 0x1C name block position (absolute); 0x20 name length in UTF-16 units incl. terminator = 14; 0x24 the TAG0 file, zero-padded to 16; then UTF-16LE "collision.hkt\0" padded to 16; entry: s32 name offset relative to the entry (normally -0x20), u32 data offset (0x24), u32 data size, 12 zero bytes. Repacking by these rules reproduces all 50 game files byte for byte.

Basis: every game file

Attribution: ktaro, SHKT report (Spec §2.1) · 2026-10-16

Evidence: static · Build: steam-678ccb46 · Fact ID: nvmd-header

.NVMD (beside each navmesh, .NAVMESH.NVMD / .NAVMESH_H.NVMD) starts with the little-endian u32 'NVMD' (bytes 44 4D 56 4E) and version 0x130; the game checks both. The rest is not analyzed.
