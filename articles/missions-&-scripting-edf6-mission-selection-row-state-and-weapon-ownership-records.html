EDF6 mission selection and weapon ownership: row-state and save-record boundaries

EDF 6Missions & ScriptingMissions
Technical reference · Exact-build source RE notes and offline-checked helper; not fresh native runtime

Mission-select rows and one exact-build UI behaviour

The retained ported-content code documents the mission-selection list as an array of 0x14-byte rows in one target EDF6 binary. Its source model (ListRow) is:

Offset Size Meaning in retained source
+0x00 4 List-row index
+0x04 4 Displayed mission number (field 4)
+0x08 4 Row state
+0x0C 4 Branch value (field 5)
+0x10 1 + 3 padding Flag byte

The documented states are 0 = cleared; 1 = open; 2 = open branch (field5 == 1); 3 = locked but visible; 4 = locked and hidden. This distinction matters: hidden is not equivalent to completed or merely locked.

The source's narrow OpenAll path recognizes a freshly constructed list only when row zero has index 0/state 1 and every subsequent row has the corresponding index/state 4. It then changes those hidden rows to state 1 or 2 according to the branch field, before the engine's normal scan. The documented native scan opens the successor of a completed row. No save data is written in this UI-only operation, and already-cleared progress is not altered. If the initial list does not match the expected shape, the helper fails closed rather than blindly patching memory.

The source points to list construction around EDF.dll+0x8A2160..0x8A241A, with its stored row list at +0x8A1530; these addresses are build-specific.

Weapon possession records are not mission-row states

The retained game-status weapon row is 12 bytes: a little-endian uint32 flags word followed by eight star bytes. Within that flags word, bit 0 = owned and bit 2 = newly obtained. The source's ownership helper preserves all other bits. On first acquisition it sets owned/new and zeros the eight star bytes; on subsequent acquisition it leaves existing stars intact. A separate max-star path sets each to ten (after which the stock game applies actual weapon-specific caps).

A Disown operation clears owned and new flags while preserving stars. This distinction matters when a weapon or support action moves from the ordinary loadout to another interface or becomes ineligible: erasing star bytes would mutate progress rather than only availability.

The mod's content-name gate recognizes EDF6VC_E5_ and EDF6VC_E41_; it excludes EDF6VC_RETIRED_ and call-weapon names. These prefix rules are mod-defined, not universal properties of EDF6's inventory format.

Limits and implementation hygiene

This is a source-reviewed exact-build contract from components/compatibility/src/unlock_ported.h. It explains what was patched and why, not a blanket recommendation to unlock all stock missions. Verify the native addresses and row semantics for the target build. Separate mission-list visibility from saved progression, and inventory possession from star upgrades; the same memory operation should not silently implement both.
