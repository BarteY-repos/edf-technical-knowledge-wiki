MAE and weather — generic source-only boundary and the Desert508 exception

ConversionMaps & NavigationMapsEDF 5EDF 6
Source-backed research / case study · Generic open; Desert508 shipping runtime-closed

A generic EDF5→EDF6 weather/MAE conversion law is not globally closed. However, that generic uncertainty must not erase a narrower result: Desert508 weather is runtime-closed for every retained shipping mission that actually consumes it.

Why generic MAE/weather remains a separate problem

MAE is an EDF6-side map/environment role without a trivial one-to-one EDF5 twin. Target runtime weather is a composition of map/profile environment state, MAE data, RAB resources and script-side calls. A reference-assisted MAE that removes one loader blocker does not establish a lawful universal converter.

Likewise, profile values cannot be blindly copied or scaled across all maps. Paired evidence and runtime behavior remain necessary when promoting a generic rule.

Desert508 is a qualified source-derived exception

The retained EDF5 corpus was exhaustively decompiled/scanned for ig_desert508 use:

  • 335 retained MISSION.BVM files scanned;
  • exactly 2 consumers found;
  • DLC/DM018 uses evening;
  • DLC/DM020 uses sunset;
  • no retained mission BVM uses Desert508 fine, cloudy, cloudy2 or finecloud.

The production weather architecture is source-derived and port-owned:

  • standard target names IG_DESERT508_<PRESET>.MAE/.RAB;
  • target ig_desert508.rmpa plus source-derived modern weathers.dsgo in the MAE construction;
  • EDF5 Desert weather RAB payloads retained byte-exact;
  • no native EDF6 weather donor/template/carrier in the production path.

DM018 source drift correction

The EDF5 source BVM uses:

ig_desert508 + evening

A reconciled EDF6 AC had drifted to sunset in both PreloadMap and Map. The accepted correction changes exactly those two strings back to evening and leaves mission RMPA unchanged.

Accepted AC SHA-256:

a1100f07bc4d0fc7605af397216f789d920ce8772aedc186f9a00990ec269eb4

Direct runtime: PASS.

Correct evidence boundary

Two statements can simultaneously be true:

  1. generic source-only weather/MAE synthesis across arbitrary maps remains an open research problem;
  2. Desert508 shipping weather is closed because every retained consumer is runtime-positive on its source-authentic preset.

Do not downgrade the Desert508 release state merely because the generic converter remains imperfect, and do not generalize Desert508's success into a universal weather transform without new paired evidence.

A practical weather-resource completeness check

A studied EDF4.1→EDF6 map-port workflow had a specific failure class when the target environment record omitted required fields, including _brightnessFog. Its conservative weather-resource validator required the following names to exist:

_lights       _ambient        _sky           _envMap
_tone         _sun            _lowBloom      _highBloom
_fog          _brightnessFog  _farClipZ      _shadowOffset
_wind

It also required a non-empty, parseable weather RMPA and a non-empty RAB companion. These are a measured validation envelope for that source-to-target map workflow, not a claim that every game mode always needs every field in precisely the same way. Supplying these fields can prevent a known loader failure without proving that an independently synthesized weather scene looks or behaves like native EDF6 weather.

Some early EDF4.1 map ports reused native EDF6 donor weather/nav. Those resources can permit a map to load, but are not evidence of source-derived weather conversion, and donor NAV geometry may be incompatible with the source terrain. Treat environment acceptance and visual fidelity as separate checks.

FINE archive dependencies and CPK visibility are separate problems

The studied EDF5-derived Desert508 FINE pair contains an MAE (weather DSGO plus local-area RMPA) and a separate large RAB with four exact DDS resources. A later host-side search could not find those specific resources in the scanned vanilla EDF6 CPKs, even though their previously qualified identity existed in a preserved local weather RAB. This shows why a game resource path should not be equated with a directly discoverable CPK entry. The FINE MAE/RAB case study provides the bounded filenames and hashes; it does not establish generic native-FINE reconstruction.

Checking the environment binding independently of the visual profile

A correctly packaged MAE can still reference a missing environment area. The MAE/DSGO _envMap binding guide gives the measured _envMap[0] RMPA name lookup rule and validator contract. This is a structural identity check and does not establish that a borrowed or independently synthesized weather profile looks native.

The EDF5-to-EDF6 exposure-tone contract is three named lanes, not a guessed color grade

An exact source/target shader and weather-manager comparison recovered the EDF5 v2_Brightness / v2_BrightnessLerp / v2_ToneIntensity triple as active exposure controls. In the audited EDF5 weather manager, these map into the active renderer singleton at +0x68 / +0x6C / +0x70; the source-side defaults are 0.5 / 0.5 / 0.9. The same ComputeToneLerpSetting shader has a different constant-buffer layout across generations:

Constant-buffer byte offset EDF5 (16-byte buffer) EDF6 (16-byte buffer)
+0x00 g_tone_lerp_brightness_target g_tone_lerp_brightness_center
+0x04 g_tone_lerp_brightness_lerp g_tone_lerp_brightness_target
+0x08 g_tone_power g_tone_lerp_brightness_lerp
+0x0C padding g_tone_power

The EDF6 shader inserts the center-brightness lane at the front, shifting the three inherited meanings by four bytes. This, together with the exact source and target named-reader/renderer contract, supports the following semantic mapping in the studied source-only weather bridge:

EDF5 authored property EDF6 authored property Target runtime meaning
v2_Brightness v3_brightness EVENT_LIGHT_ENV_FADE_TONE_BRIGHTNESS
v2_BrightnessLerp v3_lerp EVENT_LIGHT_ENV_FADE_TONE_BRIGHTNESS_LERP
v2_ToneIntensity v3_intensity EVENT_LIGHT_ENV_FADE_TONE_POWER

The target-only v3_brightness_max=10.0 and v3_center_brightness=0.5 use the measured target constructor defaults. For an absent EDF5 old property, use its source constructor default; e.g. source brightness-lerp defaults to 0.5, whereas native target v3_lerp defaults to 0.2. A mixed old/new tone family in one source profile is ambiguous and must not be silently merged.

Across 18 source profiles in three map families, the audited source-only bridge introduced _tone as the only newly converted modern family in the comparison and reported 0 failures. The specific original IG_2000MCITY / Evening profile yielded _tone = [0.45, 10.0, 0.5, 0.85, 0.5] in the observed target serialization order. These are binary/source and offline mapping results, not a new visual-runtime PASS. The independent verifier reported 34/34 source/target checks, and its target-side predecessor 65/65 checks.

GroundColorR/G/B is a useful negative boundary: all three names are parsed into the original EDF5 profile at +0x140/+0x144/+0x148, but the examined active-profile consumers do not read those offsets. This supports omission in the limited conversion path; it does not prove that an undiscovered alias/hash-based consumer cannot exist. The old DOF, RGBC, SkyModelColor, ToneAdjust, and older bloom/color field names likewise lack exact named-reader matches in the examined executable. A missing name is not proof that a whole rendering feature disappeared.

Evidence scope: source-only exposure lineage and named-field analysis: EDF5_EDF6_TONE_LINEAGE_R71_OFFLINE_AUDIT_2026-09-05.md, its exact-build binary gate and EDF5_EDF6_GROUNDCOLOR_CONSUMER_AUDIT_R71_2026-09-05.json. See EDF5 exposure pipeline and EDF6 exposure pipeline for per-version shader behavior.

Source RAB inventory is distinct from MAE source serialization

For the sampled IG_DESERT508 weather archive family, the six recovered EDF5 RAB files are source-side SSA version 272 records. The exact source inventory must not be collapsed into one four-texture law: it yields four entries for FINE, FINECLOUD and SUNSET, but five for CLOUDY, CLOUDY2 and EVENING. The original sky-cube names differ across the six variants. The primary reason to preserve these native DDS names is resource resolution; their existence does not provide an EDF6 shader/visual parity claim.

The independent five-effective-MAE release audit later closed _envMap named-record binding, but it did not rerun all six original RABs in game. The practical evidence layers therefore remain: source RAB identity → target MAE serialization → embedded-name resolution → mission selection → visual runtime. Do not promote results across layers. See the Desert508 consumer and binding case.

Target weather _tone name order is not the native C++ member order

The exact-build EDF6 audit measured the serialized five-node tone field order as:

v3_brightness, v3_brightness_max, v3_center_brightness, v3_intensity, v3_lerp

But native named readers place those values in a different order in the target weather-manager object:

Authored key Observed target runtime member offset
v3_brightness_max +0x308
v3_center_brightness +0x30C
v3_brightness +0x310
v3_lerp +0x314
v3_intensity +0x318

Native event-kind evidence also distinguishes center brightness 24, target brightness 25, brightness interpolation 26 and tone power 27. This means an implementation cannot derive the order of native object members directly from the order of serialized DSGO values, or infer that all five properties existed in the EDF5 source. The exact target reader audit was 65/65 static gates PASS, not a new rendered-image or gameplay test. Source: EDF5_EDF6_EDF6_TONE_RUNTIME_CONTRACT_R69_OFFLINE_AUDIT_2026-09-05.json.
