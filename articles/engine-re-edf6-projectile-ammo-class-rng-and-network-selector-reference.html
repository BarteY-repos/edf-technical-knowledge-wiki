EDF6 projectile RNG: AmmoClass consumers and NetworkBullet selector reference

EDF 6Engine RE & NetworkingNetworking
Technical reference · Static canonical EDF6.dll and qualified 1,315 active weapon configurations; no paired runtime test

Scope: static analysis of one EDF6 EDF.dll build, SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916, joined to an audited 1,315 active-configuration WEAPONTABLE/star-state corpus. This is a reader reference for the game binary, not an SDK promise or an in-game synchronization test.

How a random state reaches a projectile

Common Weapon projectile creation at EDF+0x696FD0 derives a value from the 64-bit Weapon LCG. The engine writes the upper-derived projectile value to the class-specific Bullet InitParam +0x1A0 at EDF+0x69776D. BulletBase construction at EDF+0x22E9C0 loads the InitParam field and stores the zero-extended value in the finished BulletBase +0x130. They are different object layouts. Common BulletBase does not itself continuously consume +0x130; derived classes may do so.

state_next = (state * 0x5D588B656C078965 + 0x269EC3) mod 2^64

A subtle but important distinction: the class state can diverge after remote subtype1 reconstruction even when initial spread is deterministic. Of the 40 subtype1-capable weapons using these three families, 38 have FireSpreadType 0, one spread1 and one spread2. Their distribution is:

FlameBullet02 18 18 0

Separately, six always-subtype1 weapons have RNG-sensitive initial spread types 1/3; Lightning Rapid Bow T2 belongs to both groups. Thus the union is 45 subtype1-capable configurations, of which 35 are always subtype1. These are two related but distinct scopes, not conflicting counts.

Receiver catch-up and why eventual seed equality is not enough

Subtype1 publishes a cumulative shot target after the normal six-Weapon-update delay. A later receiver can catch up on shot count by creating missed projectiles locally. Under strict equal-seed and equal-total-update/projectile-step conditions, the current Weapon LCG can reconverge after that catch-up. Nevertheless the newly created projectile gets the receiver's later historical sample, not the sender's original sample. A later common NetworkBullet selector does not serialize the class-specific random fields in the table above. No automatic recovery of those historical values is established by the inspected recurring protocol.

This explains a possible static synchronization gap, not a guarantee that every visible multiplayer shot desynchronizes. The size and frequency of actual divergence require paired runtime traces.

Other true RNG consumers excluded from the subtype1 set

  • SpiderStringBullet03::OnUpdate (EDF+0x285700) advances +0x130 and derives a class scalar at +0x108C.
  • NapalmBullet01::OnUpdate (EDF+0x2641F0) derives a randomized spatial vector.
  • MissileBullet02::OnUpdate (EDF+0x26E4C0) derives and stores a randomized spatial vector around +0x15D0.
  • PlasmaBullet01 constructor (EDF+0x25B650) consumes Bullet-local RNG; another later code path uses process-global RNG and must not be conflated with the projectile state.

Simply matching a memory displacement like +0x130 is insufficient: for example LaserBullet02 and BarugaCannonBullet contain similarly named/positioned accesses that were not qualified as consumers of this Bullet-local LCG state.
