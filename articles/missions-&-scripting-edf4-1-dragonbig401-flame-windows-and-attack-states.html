EDF4.1 DragonBig401 — timed breath, glide versus hover and the EDF6 class mismatch

ConversionMissions & ScriptingMissionsEDF 4.1EDF 6
Technical reference · Exact-build class research and source-only compatibility implementation

The concrete class mismatch

EDF4.1's giant dragon breathes FlameBullet02 during attack windows keyed by MAB animation events 火炎開始 (“flame begin”) and 火炎終了 (“flame end”). The original weapon fires one projectile per simulation frame from a named MAB muzzle locator 発射口 in the locator's local +Z direction, with a random angular cone up to 0.2 radians.

The investigated EDF6 DragonSmall donor class instead fires FlameBullet01 fireballs, and its existing event dispatcher does not register the EDF4.1 pair. Merely importing the old mesh, CAS and MAB while keeping the class's new firing action does not preserve attack semantics. This is a direct example where a file parser can be correct while the port's gameplay is not.

Source event windows and firing direction

The retained compatibility research decodes each source attack state's MAB begin/end times, looks up the corresponding CAS state, and observes the active animation player. When the player enters that state's interval and the actor is alive, the adapter creates FlameBullet02 using the target projectile factory.

For each shot, the implementation:

  1. Reads the source muzzle world transform.
  2. Samples tilt 0 ... 0.2 radians and spin 0 ... 2π, constructs a normalized direction around the muzzle's local +Z.
  3. Builds the shot transform at the original muzzle position.
  4. Attaches a projectile parameter block, team ownership and owner weak reference.
  5. Uses the source projectile configuration for speed, lifetime, width, hit-stop, color and custom SGO parameters.
  6. Computes the documented source damage scaling as actor_level × 0.00375 in the examined class path.

The projectile factory and memory fields are exact-build native contracts. A generic script-level implementation cannot assume these offsets or that the projectile factory accepts another class's parameter structure.

Glide attack is a behavior choice, not a replacement fireball

The source 4.1 behavior chooses between two attack forms at approach:

Attack form Intended behavior
fly_glide_attack Pass over the target while breathing flame, return to glide after the clip
fly_attack Hover and breathe during the clip's source flame window

The studied branch makes the two choices with approximately equal probability. Replacing both with EDF6's donor fireball volley changes the animation, trajectory and damage opportunity. Source ranges also differ: the recorded wander radius was 500 units versus 100 in the donor's relevant sampled cruise path; the source-ground-fight radius was 500 rather than the donor field's 100. These are specific researched class constants, not default values for all aerial enemies.

The same adapter tracks knockdown animation states, a source settle/rest condition and return-to-glide behavior. Those systems must be handled independently of the flame projectile's emission window.

Why this matters for asset authors

A faithful enemy import must reconcile at least four distinct layers: model/locator data (MDB/MAB), timed clip events (CAS/MAB), native AI/state transitions and projectile class/parameter semantics. The presence of a visually correct flamethrower animation does not establish that shots use the source damage or fire at the source timings.

This is not a general animation retargeting recipe. An arbitrary donor class can require its own named CAS players, controller variables and init parameters; see CAS player/vcontrol ABI.

Scope and evidence

The retained edf41dragon.cpp documents exact EDF4.1 binary and EDF6 target-class reverse engineering and a source-only compatibility implementation whose hooks are conditional on the edf41_dragon SGO marker. Unmarked native EDF6 dragons remain on their original path. The R9 checkpoint is offline-qualified source work; it is not an independent new Windows/runtime verification of DragonBig401 in R63.

The original DragonBig sound-preset/bank mapping was later recovered statically from the source SGO/EXE in R14/R17: five sound roles plus a separate ragdoll-contact preset, using a shared dragon sound bank. Target DragonSmall slot 0 introduces an extra eight-frame-cooldown hurt roar absent from original DragonBig; its sound parity is not runtime-confirmed. See DragonBig401 source audio roles and MAB event timing.
