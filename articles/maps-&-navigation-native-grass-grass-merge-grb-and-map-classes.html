EDF6 vegetation: native grass registries versus EDF5-derived region GRB

EDF 6Maps & NavigationMaps
Technical reference · Three native MAC samples; source-only region authoring not runtime qualified

At a glance

What it is: Grass-species registries, regional GRB density data and MAPB object classes are three different concepts.

Where it fits: The often-cited Desert example is EDF5-derived content running in an EDF6 port, whereas HEIGEN and EUROPE observations are native EDF6 controls.

Important distinction: Do not promote a working port's regional rule into a universal native EDF6 algorithm, or treat object Class 6 as a universal grass-disable flag.

Critical provenance distinction: The commonly cited IG_DESERT508 / sk_grassleaf504a / ig_grassdens2small.grb sample is EDF5-source-derived content ported into EDF6, not an original shipping EDF6 map. The later direct source-provenance review explicitly corrected the earlier claim that its fixed GrassDens2Small rule graph was an exact native EDF6 oracle. It is still useful as source-authored data that has been observed working in an EDF6 port, but it cannot alone define Sandlot's original EDF6 region-density format.

By contrast, IG_HEIGEN507 and NW_EUROPE01 in the retained reference set are native EDF6 controls. Their directly observed vegetation data must be kept separate from the ported Desert example.

The five-entry native registry is not evidence that a five-species GrassDens2Small regional .grb exists: the inspected HEIGEN MAC has no explicit .grb block, and the corresponding MAPB/RMPA comparison did not establish a Desert-style density consumer. Native registry membership, a source port's regional GRB and engine-managed grass distribution are different evidence classes.

What the EDF5-derived Desert experiment actually proved

The recovered fixed GrassDens2Small source tree associates one sk_grassleaf504a species at slot 0 with explicit polygon boundaries. An EDF5-derived Desert build carrying that structure was reported to run with the grass behavior working inside EDF6. This is a positive compatibility observation, not an original-native authoring specification.

Reusing the same regional rule tree with another species such as native-HEIGEN sk_grassleaf501a was tested in a controlled source-only build but remained an unconfirmed substitution. Nor does the native HEIGEN registry prove a multi-species regional GRB. Hole polygons, branching/ambiguous loops, arbitrary numeric GRB parameters and generic multi-species GRB synthesis remain outside the established format semantics.

Why object Class 6 is not a global grass-exclusion flag

A specific ported Desert map experiment changed sk_base508exit01 from T1 Class 3 to Class 6. In that map the unwanted grass disappeared near the exit while other Class-3 base terrain retained vegetation. That isolated runtime outcome is valid for this specific ported asset and context.

It does not justify Class 6 = no grass globally. Native EDF6 NW_EUROPE01 uses Class 6 for streetlights, signs, benches, props and other objects; the class/role assignment is not a universal grass mask. Direct region inclusion geometry and engine vegetation behavior must be investigated separately from MAPB resource classes.

source reconciliation — native FMB grass versus GRB polygons: ktaro's later EDF6 static reader documents two separate generation paths. FMB plant category 0 uses the species keys in grass.merge.sgo to select layers of grass.merge.dds; a plant whose species is not registered is skipped. In the GRB path, the MAPB header's +0x78 area block lists float3 vertices and 12-byte area rows, each referring to 8-byte indexed triangles and a named .grb rules file in the MAC. This interpretation was observed by that reader on 8 GRB-bearing maps, and is more specific than the older inferred “point/route” label for that header field.

The new GRB rules interpretation has a weighted color-group choice, sizes, species entries and spacing (at least 0.1); the source says that species-group weights are not read. Its geometry generator repeatedly splits a triangle at the longest edge until area is below spacing² / 2 or depth reaches 40. Only an interior leaf carrying edge mark 0 produces a blade. A separate reported ground-placement pass casts a downward ray from (x, y + 20, z) to (x, y - 100, z) and adjusts height and tilt on a hit. The exact Havok collision-layer filter used by that ray remains undetermined; restricting it to terrain in the source viewer is an inference, not a measured native layer mask.

For bounded output checks, the contributor's offline viewer reported 282,909 FMB blades on IG_MOUNTAINVILLAGE, 17,699 GRB-only blades on NW_SEIYU, and 143,967 blades on IG_BASE502 from both paths. These are reported static/viewer counts, not independent game-render counts. They substantially improve the model of the native generator while leaving unrestricted authored-GRB compatibility and runtime qualification open. EDF6 grass blade: render, wind and placement (static source)

FMB cell-height detail: in the studied MAPO terrain row (.fmep), +0x00 points to a {count,8,float heights[]} block consumed once per non-empty growth cell, in group order and then row-major order regardless of species. FMB table 3 supplies 256 jitter records (angle, X/Z offsets and scale factor). A source-observed missing-ground sentinel height of 505.0 remains at that height rather than automatically dropping to terrain. This is distinct from the later downward ray on individual grass blades. The source also reports a square-distance versus stored squared-threshold relation for small-object LOD; it is not a general promise that arbitrary newly generated MLB data will match the game.

GRB leaf RNG draw order: ktaro's static reader consumes pseudorandom outputs for yaw (F × 4π), Z and X center jitter of ±half spacing, width, height, weighted color group and finally species index. The leaf triangle center supplies Y before ground placement. The color is read from the group after the one selected, modulo group count, in that source's code reading; whether this odd off-by-one is intentional in-game behavior remains unverified. Changing draw order when authoring a deterministic generator changes all subsequent placements, even when individual distributions look plausible.

Ground ray: FUN_180167990 casts from (x,y0+20,z) to (x,y0-100,z); a hit sets blade Y to the hit and tilts it with the surface normal. The precise order of the two inferred X/Z tilt rotations is not established. A miss keeps the original height. The real game uses Havok collision; a source-side viewer using render meshes is only an approximation.

Unresolved collision mask: ktaro's unreleased collision-layer table labels 17 as terrain, 16 as structures and 20 as utility/tree objects; selecting only terrain-like bodies is an inference supported by novae (ajane)'s visual report that grass does not grow on IG_CRATER601 building roofs even when its X/Z placement matches. The actual filter in FUN_1801060D0(g_CollisionFilter) has not been decoded or reconciled with the wider collision-mask census. Do not publish a hard-coded “grass ray = layer 17 only” authoring requirement.

Blade geometry and wind: the native grass vertex path (source shader address 18177D3E0) draws two two-sided quads crossing at right angles, eight corners total. Height, half-width, UV rectangle, yaw and scale determine the card. Wind bends upper vertices in the global wind direction, with position/time-based sine motion and a vertical-top attenuation term; lower vertices remain planted. The source's default wind-vector example is (-1,0) in X/Z, not a universal environmental constant.

Pixel fade and shadow cutout: the described grass shaders (181779070, shadow 18177CC90) apply distance alpha 1-saturate((distance-48.75)/(75-48.75)) under the sampled 75 m environment setting. That means fade begins at 48.75 m and occupies the final 26.25 m (35%) of that 75 m range; the source prose calling it the “last 0.65×75” confuses the start fraction with the fade span. The pixel shader further applies screen-position threshold thinning and rejects sampled texture alpha below 0.8; its shadow version also runs thinning and alpha rejection. The source does not fully explain the threshold sense, so exact parity of every dither bin remains open. The grass texture is the grass.merge.dds array, separate from arbitrary MDB model albedo.

Evidence: six anchored observations from ktaro's edf6/map-placed-object-rules.md in Knowledge Hub revision 5b589ca (EDF6 static reading, with novae/ajane's bounded visual reports where noted). They supplement the ported Desert experiment above without converting it into an original-stock EDF6 test.

Evidence status and open questions

  • Established: source-ported Desert regional rule structure, EDF6 runtime compatibility observation, native HEIGEN five-entry registry, native class distributions, absence of an explicit HEIGEN GRB block.
  • Still not established: complete compatibility for arbitrary newly-authored .grb regions, HEIGEN's full runtime vegetation behavior, arbitrary replacement species, the actual grass-ray collision-layer mask, or runtime/culling behavior of new regions. The November static generator reading narrows the former uncertainty about the basic GRB subdivision algorithm.
  • Do not infer: source-exact Desert port bytes = byte-exact original EDF6 native vegetation pipeline.
