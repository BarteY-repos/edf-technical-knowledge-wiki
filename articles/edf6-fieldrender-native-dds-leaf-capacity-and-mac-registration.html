EDF6 native FieldRender: DDS arrays, FMB leaves and MAC registration

EDF 6Maps & NavigationMaps
Technical reference · Original native EDF6 corpus + DLL disassembly + separate modified-game runtime diagnostics

The EDF6 FieldRender/FMEP terrain path is not an ordinary MDB prop. It spans terrain material and geometry records, DDS texture arrays, and map-container references. A correctly decoded part does not establish that the whole chain loads in-game. This reference combines original EDF6 native-asset observations with a separate, explicitly modified-game diagnostic sequence.

Evidence and boundaries

  • Original EDF6 source files: native FMB leaves and DDS from CAVE501, CAVE503, CAVE601_2, HEIGEN507 and BASE502, plus the directional HEIGEN507_ENKEIUP FMB; the September 2026 native-correlated audit decoded 1,477 leaves without errors and checked 20 DDS mip payloads against exact block-compressed sizes.
  • Modified EDF6 runtime observations: an experimental Island4 FieldRender branch encountered two distinct loader faults. This diagnoses resource lookup and native MAC directory parsing but does not establish successful custom FMEP gameplay.
  • Separate known playable route: Island4's static MDB map had a runtime-positive x20 R4C control; it is not proof that its later FMEP branch worked. The accepted Desert508 baseline is a different native-resource-continuity study, not a generic FMEP source-only recipe.

Native terrain DDS: the measured container contract

All 20 examined native terrain DDS payloads in this bounded corpus use DX10 headers, 2D texture arrays, complete mip chains, depth 1, flags = 0xA1007, caps = 0x401008 and caps2 = 0. The reported size checks were 20/20 exact, not just header-parse successes.

Texture role Dimensions Mip count
Full-resolution color 2048 × 2048 12
LOD color 512 × 512 10
Full-resolution normal 2048 × 2048 12
LOD normal 128 × 128 8

The array slice count is map-dependent, not a universal fixed four-slice rule:

Native EDF6 map Color slices Normal slices Reported normal DXGI value
CAVE501 4 3 77 (BC3_UNORM)
CAVE503 4 4 77 (BC3_UNORM)
CAVE601_2 5 3 77 (BC3_UNORM)
HEIGEN507 8 6 71 (BC1_UNORM)
BASE502 12 9 71 (BC1_UNORM)

All five native color profiles are reported as numeric DXGI 71, i.e. BC1_UNORM. Source terminology correction: one audit calls that value "BC1 sRGB"; according to the official Microsoft DXGI enumeration, BC1_UNORM_SRGB is 72, not 71. This article preserves the source's numeric value and does not silently turn it into 72 or infer the final shader's color-space sampling policy. The same enumeration distinguishes BC3_UNORM = 77 from BC3_UNORM_SRGB = 78.

Material records contain slice indices; the highest referenced index sets a minimum array length, not necessarily its exact native allocation. For example, BASE502's native color array contains 12 slices even though the cited maximum material index requires only 11. The one-material Island4 candidate referenced color slices 0 and 1 and normal slice 0, so its strict minima were 2 color / 1 normal; its test used 4/4. Overprovision by itself is not evidence of a broken DDS.

Native FieldRender FMB leaves: capacity is not the active material count

The corrected native audit found these wrapper counts; the six rows include one directional FMB without a separate full DDS-profile row:

A later paired Desert control additionally had 114/114 directional leaves with capacity=1, arity=1, config index 2, and a byte-identical nine-row shader-config block to the studied small terrain candidate. It is an independent profile check, not part of the 1,477-leaf corrected-five-map count. The accepted Desert main FMB and the deprecated DESERT508_WORKING_BEST_EFFORT file are different artifacts: the latter must not substitute for the former when asserting runtime provenance.

Interpretation: native EDF6 definitely permits capacity=1. Do not force a field to 2 because an earlier sample did not show 1. Conversely, do not infer every FMB leaf must use this minimal profile; native leaves with larger lists and material indices exist.

FMB tree and auxiliary fields: sample-grounded rules

The accepted Desert-versus-small-FMB comparison found an FMB directory whose leaves and internal tree nodes are decoded in postorder. Each leaf contributes its leaf ordinal; a type-0 tree node combines two child subtrees and stores the inclusive range of leaf ordinals. It does not store a split at a raw directory-entry index. The same study decoded a 256-leaf / 255-node Desert main tree, a 114-leaf / 113-node directional tree, and a 2-leaf / 1-node experimental candidate without tree-range errors.

The native directional Desert profile's nine-row config blob and eight-byte auxiliary block (00 00 00 00 08 00 00 00) were byte-identical to the studied candidate. A source-generated 256-row float4 lookup table had the same broad data domain as the native oracle but different exact bytes; no accepted gameplay experiment isolated the LUT as the loader's cause. Exact native geometry/tree format is an independent issue from locating FMB by resource name.

Runtime loader chain: why valid terrain files can still crash

The modified-game diagnostic sequence illustrates the engine's separate resource-lookup and map-directory contracts. It is included here to identify native reader semantics, not as a recipe for developing a particular editor.

Source-controlled observation What it shows What it does not show
Island4 initial FMEP tests: EDF+0x1170B7, fault address 0x4 Loader derives a sibling .fmb for a referenced .fmep, performs resource lookup, and dereferences record+4 with no observed NULL guard; corresponding FMB registration was missing from the MAC's externals.sgo DDS mip size or leaf capacity was proven wrong
Adding externals.sgo to MAC The next runtime log no longer showed the +0x1170B7 signature; the engine progressed past that lookup Map successfully rendered, or entire game was stable
Later observed EDF+0x19026A, fault address 0x0 A separate MAC directory-name relative-pointer problem was exposed in the investigated load That reported first-chance access violation is necessarily the terminal game crash site
Corrected MAC directory rel32 (static proof) The parser's directory and name pointer bases were reconstructed; bad directory target was 12 bytes off and corrected to 0 Post-correction gameplay was runtime-qualified

For this observed native MARC v5 directory parser, MAC header field +0x14 is a signed 32-bit displacement relative to the address of that field, pointing to the first 24-byte directory entry. At each directory entry, +0x00 is itself a signed rel32 from the entry to a UTF-16 resource name. The EDF.dll read site analyzed was EDF+0x1901F0; the loader used a relative-dword load and pointer addition at +0x190226…+0x190233, then read the UTF-16 name at +0x19026A.

This explains why a three-entry heuristic could appear to work, then fail when a fourth resource changed directory placement. The reported four-entry error targeted 0xB21C instead of the correct directory start 0xB210, producing a 12-byte pointer displacement and a zero name-relative field. The corrected value (header+0x14 = 0xB1FC) reaches 0xB210. These are a single measured MAC profile, not license to assume the same offset for unrelated formats or game builds.

The exact source-generated externals.sgo registered ss_island4_fmep.fmb while the map object graph referenced ss_island4_fmep.fmep; the resource names play different roles. The corrected R2F FIX1 package passed static and transaction checks, but the source record ends at runtime pending. In particular, it does not prove that the complete experimental FMEP terrain ever rendered successfully in that branch.

Rendering/material diagnosis is a separate axis

RenderDoc analysis of the static MDB Island4 control showed a real artist-material mismatch: its source texture packed roughness / metallic / AO into RGB, but the observed control shader bound that resource as a reflect/spec-style mask. A direct runtime dump matched the expected model prefix exactly, ruling out an outdated MDB/RAB for that sample. The tested legacy shader variants did not establish a complete artist-faithful material translation.

That finding should not be imported wholesale into FMEP's native terrain texture-array ABI. Static MDB shading, FieldRender DDS slices, FieldRender leaf materials, MAC resource registration, physical MAD collision and HKT/NVMD navigation are distinct contracts. Fixing one does not prove the others.

What is proved, and what remains open

Original game evidence: 20 native DDS payload byte-length matches; 1,477 correctly decoded FMB leaf wrappers; a native valid capacity-one pattern; distinct texture array sizes and normal formats per map. Binary loader evidence: precise field-relative MAC directory and name references for the studied EDF6 build. Modified runtime evidence: specific missing-FMB and subsequent bad-name failures, with the original missing-FMB signature no longer present after registration. Not proved: runtime success of the corrected custom FMEP branch; generic custom FMB authoring for arbitrary maps; stock-game inferences from an experiment-only asset; actual color-space treatment when the numeric DXGI enum is 71.
