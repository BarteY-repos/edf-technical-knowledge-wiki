Systemic FLAG index parity repair — 21 affected missions

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · M050 runtime-proven; 20 peers source/static-qualified

Patch 1.0.6 identified a converter-wide enum identity defect, not 21 unrelated mission bugs.

Root cause

EDF5 source logic can combine numeric flag producers such as:

FlagOn(n)
FlagOff(n)

with symbolic factor consumers such as:

Factor_FlagOn(FLAG_n)
Factor_FlagOff(FLAG_n)

The broken conversion path assigned generated symbolic flag enum ordinals by first-use order instead of preserving the source flag index. A producer could therefore set numeric flag n while a consumer named FLAG_n actually referred to a different generated ordinal.

The required invariant is:

FLAG_n == n

for the source flag identity domain.

Runtime discriminator — M050 / displayed Mission 59

M050 exposed the defect as a real softlock. Restoring source flag indices while retaining the source AllEnemyDestroy logic produced a user-confirmed runtime PASS in RC6. Easy/Hard correctly skip the high-difficulty wave and still reach final dialogue + Mission Clear.

M050 therefore proves the mechanism at runtime.

Qualification boundary

  • M050 mechanism: runtime PASS on an earlier RC;
  • remaining 20 repairs: source/static-qualified in the 1.0.6 build lineage;
  • exact finalized 11 October 1.0.6 package: per-mission runtime remains pending unless separately documented.

High-value regression targets include M098, M099, M047_2, M004, M005, M041, M045 and M046_3.

Converter rule

Do not assign semantic enum identities according to encounter order when the source domain already has stable numeric identities. Generated symbolic names must preserve the source numeric identity exactly.

This lesson generalizes beyond flags: whenever numeric producers and symbolic consumers meet, prove that the symbolic target domain is identity-preserving before using generated ordinal order.
