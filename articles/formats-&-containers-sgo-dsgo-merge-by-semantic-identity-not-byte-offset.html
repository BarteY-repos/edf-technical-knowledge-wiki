SGO/DSGO semantic merge

EDF 6Formats & ContainersFile Formats
Technical reference · Exact offline CONFIG three-way merge + synthetic semantic merge tests; runtime not established by merge itself

A mod that replaces an entire CONFIG.SGO can conflict at the file-path level with another mod even if the two mods edit unrelated logical data. Choosing a winner silently discards the other mod's changes. Concatenating their binary records is just as unsafe: SGO/DSGO uses relative pointers, typed nodes and tables whose physical order may not be semantic identity.

The correct three-way model

Take a known canonical vanilla baseline V, then compare every mod's independently supplied full-file replacement M1, M2 against that same baseline:

V (the game's exact original CONFIG.SGO)
├─ semantic_diff(V, M1) → delta A
└─ semantic_diff(V, M2) → delta B
                         ↓
              merge deltas by semantic path
                         ↓
                   reserialize SGO/DSGO

This is not a two-way diff between M1 and M2, because both contain huge unchanged baseline regions. It is also not an unconditional last-wins load order. The binary frontend/backend in the studied proof was sgott; the merger operated on structured JSON containing typed nodes (type, optional name, and value). Classic SGO and DSGO still need their respective serializers.

What identifies the same logical object?

Structure Identity policy Why
Top-level variable nodes Stable name, not serialized array position Native paired resources can reorder the same named variables
Known CONFIG tables Explicit schema-derived row keys, e.g. weapon ID Prevents mixing two distinct weapons with the same row position
Other record arrays Unique stable string, path or ID fields if proved Allows independent record insertions and field edits
Fixed-size unnamed tuple Position, provided length remains unchanged Index is meaningful only while shape is stable
Variable-length unkeyed array Conflict / manual review No defensible rule for matching old and new records

Nonconflicting operations: different fields, different keyed rows, identical writes to one field, or additions with distinct keys. Conflicts: different writes to one semantic field, deleting a row that another mod edits, or adding the same key with differing content. Competing reorder operations require special care if order controls gameplay or display; merely equal row sets is insufficient.

The historical PoC's preview could select a deterministic later winner under conflict. That preview behavior was not approval to use last-wins in production. Production should fail closed or require explicit user conflict policy.

Measured example: mission packs plus Air Raider equipment

A real September 2026 offline composition used three CONFIG.SGO inputs:

File Size
Canonical recompiled baseline 27,826 B
Air Raider replacement, byte-exact sgott round-trip 27,938 B
EDF5 mission-port replacement 41,592 B
Merged result 41,704 B

The mission port adds six ModeList entries for offline/online MissionPack03/04/05. The Air Raider mod expands named SoldierInit weapon/category arrays. For example, categories eLimpetGun01, eDrone_attacker01 and eDrone_airstrike01 add 302 and 331; eVehicleNone adds 8, 9, 10. The two change sets did not overlap. The result preserved both, had zero semantic conflicts, zero warnings, and recompiled with exact JSON-semantic round-trip. It is precisely 112 bytes larger than the mission-port file, matching the independent Air Raider delta.

The successful static/round-trip evidence is not a direct EDF6 runtime proof of arbitrary future CONFIG compositions.

Cross-file relationships make a single-file merge insufficient

CONFIG.ModeList, MISSIONLIST.*.LIST.SGO, localized TXT, preview-image RAB and save namespace (MissionPackNN.MST) may refer to the same logical campaign. Likewise WEAPONTABLE and WEAPONTEXT are related by weapon identity. If a new LIST row changes ordering, a TXT or image archive may need corresponding updates: a syntactically valid CONFIG.SGO alone does not establish a coherent game menu.

Do not use guessed positional merges to hide missing keys. Cache the merged derived file with a key incorporating the vanilla baseline, ordered provider hashes, merger/schema versions and conflict policy. Keep original mod archives untouched, report the exact winning source for every semantic change, and support rollback.

See legacy MissionPack namespace tests, RAB/MRAB named entries and resource identity.

Evidence boundary: September 1, 2026 PoC and exact CONFIG audit. An arbitrary schema-unspecified variable-length table, a game binary, or the entire module graph cannot be declared mergeable from these results alone.
