NVMD / DMVN — binary format v0x120/v0x130

ConversionMaps & NavigationNavigationEDF 5EDF 6
Technical reference · Reconciled: source-owned codec + paired native controls

Scope: The measured NVMD navigation metadata used by EDF5 and EDF6. This is a format specification derived from paired samples and the retained source-only converter, not a claim that every converted file reproduces the game's native navmesh bake.

File header

An NVMD uses a fixed header of eleven 32-bit words in total, whose first four bytes spell the magic DMVN; the remaining words are little-endian numeric fields. The fixed header occupies 0x2C (44) bytes. The measured variants use version 0x120 (EDF5) and 0x130 (EDF6).

Offset Type Field in the audited converter
+0x00 Four bytes Magic DMVN
+0x04 u32 LE Version: 0x120 / 0x130
+0x08 u32 LE Section A count
+0x0C u32 LE Companion A count; target normalized to max(0, A_count − 1)
+0x10 u32 LE Section A offset, normally 0x2C
+0x14 u32 LE Section B count
+0x18 u32 LE Section B offset
+0x1C u32 LE Section C count
+0x20 u32 LE Section C offset
+0x24 u32 LE Section D offset
+0x28 u32 LE Section D count

The four section offsets are absolute offsets from the file start.

Section records

Section Contents EDF5 width EDF6 width Conversion policy
A uint16 2 B 2 B Preserve
B uint32 state (EDF5), uint32 state + float32 parameter (EDF6) 4 B 8 B Preserve state and add float
C Three uint16 values 6 B 6 B Preserve multiset; canonicalize ordering
D uint32 4 B 4 B Preserve

The added B float is not fully understood. Some native EDF6 rebakes contain nonzero values; the compatibility converter emits 0.0 because there is no verified derivation from the EDF5 source record. This produces a well-formed target-compatible structure, not guaranteed native fidelity.

The retained converter sorts C records in descending lexicographic order by (third u16, second u16, first u16). The multiset is preserved even when the raw record order changes.

Layout equations

A_offset = 0x2C
B_offset = A_offset + A_count * 2
C_offset = B_offset + B_count * (4 for 0x120; 8 for 0x130)
D_offset = C_offset + C_count * 6
file_size = D_offset + D_count * 4

A reader should validate every range and final length, not just the version bytes. A writer should update offsets when changing B stride, normalize the target companion-A field only within the studied profile, and test C record preservation independently of ordering.

What did the paired-map research prove?

  • Minimal CAVE low/high pairs were byte-identical after conversion in the compared native target files; CAVE503 low/high is an explicitly recorded case.
  • The same 0x120 → 0x130 rule did not reconstruct native NVMD exactly for larger BASE502, HEIGEN507 and KAIGAN502 controls. In particular, the semantics of the extra B float remain open.
  • Structural conversion success for additional EDFROOM pairs did not establish exact HKT graph parity or in-game AI behavior.

HKT is separate. Its Havok tagfile architecture, graph and tile connectivity are not automatically converted by modifying NVMD metadata. Correct counts and offsets are necessary but do not prove the target game will navigate correctly.
