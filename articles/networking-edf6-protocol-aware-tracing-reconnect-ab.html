EDF6 protocol-aware desync tracing and isolated reconnect A/B

EDF 6Engine RE & NetworkingNetworking
Technical reference · R7 two-PC capture; R8/R9 static exact-build analysis only; no R9 runtime verification

A visible multiplayer desync is not one failure type. The important distinctions are (a) whether bytes reach the recipient at all, (b) whether a received SceneObject update survives staging and reaches the Soldier instance, (c) whether Sandlot's retained-message layer is pending, retrying or faulted, and (d) whether the serialized projectile data can reconstruct the initial class-specific state.

Evidence boundary: A two-computer capture established a live player-position divergence and narrowed the subsequent investigation toward SceneObject receive/staging. The protocol-aware R9 instrument is a statically qualified source candidate for that exact binary; its MSVC DLL build and two-computer runtime qualification were not completed in the source record. Do not treat a proposed hook or predicted event as an observed gameplay repair.

First classify the traffic lane

On-wire family Retention/ownership in the audited shipping path What can still go wrong
Class 3, 0x3300 ordinary SceneObject movement Mode1/non-retained; receiver-side parse, per-index/type staging and later Soldier apply A fresh position payload may be overwritten, coalesced or never applied despite successful EOS receipt
Class 4, 0x3400 events/actions Sandlot application-level mode0 retained records for qualified paths; includes EventController An ACKed event can still be misrouted or applied incorrectly; reliability does not validate gameplay result
Class 5, 0x3500 normal NetworkBullet selector0/1/2 Mode0 retained 0x1200 DATA; 0x1300 ACK; sender retry and receiver dedupe Delivered selectors cannot restore omitted Flame/Lightning/SolidExp constructor state
Physical EOS P2P send UnreliableUnordered is used even for Sandlot's application-reliable records Lower-layer delivery alone says nothing about later decode/stage/apply success

This is a scoped native-path matrix, not proof that every modded or alternate writer selects the same mode.

What a protocol-aware trace needs to record

Correlate records by build, peer, session, object/receiver key, monotonic time and event/sequence ID. Separate these boundaries rather than logging only a final position: sender creation → enqueue → EOS TX → EOS RX → logical decode → 0x3300 parser → SceneObject type-node stage → concrete Soldier dispatch → actual transform/HP result.

For class 3, retain receiver generation, object index, type, 16-bit sequence and whether the staged payload contains position; distinguish FORWARD, EQUAL, STALE and WRAP. The R8/R9 experiment permits strict-stale suppression only after the (generation,index,type) key is mapped at runtime to a Soldier. Equal sequence numbers must not be discarded globally: one batch sequence can legitimately cover multiple fragments/types.

For Sandlot reliability, retain these distinct facts:

Observation Source-backed read point / interpretation
Maintenance 0x12CEE60 (ReliableMgr scheduler)
Sender pending count ReliableMgr+0x10
Receiver dedupe count ReliableMgr+0x50
Sticky fault ReliableMgr+0x98 (a later ACK does not clear it)
Per-pending record sequence, sent-once, current retry interval, last-send QPC, retained buffer identity
Duplicate receive 0x12CFCD0 returns new-vs-duplicate handling while ACK can still be emitted
Control records 0x1200 retained DATA, 0x1300 ACK, 0x1400 dedupe-marker retirement

The R9 source adds two hook sites to the 29 inherited R8 inline detours (31 in total). The original static audit reports 31/31 exact signatures and 29/29 inherited-contract preservation, with the RUDP scheduler 20-byte stolen-instruction region and DATA handler 15-byte region checked on instruction boundaries. These are static gates, not independent runtime evidence.

Controlled diagnosis of player-position divergence

Use identical verified EDF.dll builds on both machines (canonical source SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916). Do not load transport-mutating plugins during the root-cause capture: an external UnreliableUnordered → ReliableUnordered rewrite, Direct UDP path, queue resize or 30-second disconnect hold would change the experiment.

Start with the instrument's read-only observation interval. The inherited R8 policy uses 90 seconds of OBSERVE, then a separately distinguishable conservative ENFORCE phase for proven Soldier-key strict-stale events. Analyze the two phases separately; do not call the entire recording behaviorally passive.

A causal SceneObject stale replacement needs the complete chain:

  1. A fresh position-bearing update reaches the stage boundary.
  2. That update remains pending/unapplied.
  3. An older strictly stale update for the same qualified Soldier key replaces it.
  4. Concrete Soldier dispatch no longer receives the expected position-bearing update.

Without this chain, do not claim the R8 stale filter fixes the root cause; inspect the first point at which sender and receiver timelines diverge.

Separate physical reconnect from logical peer removal

For reconnection, use a different A/B. Sandlot's packet Controller and its UserSession/ReliableMgr survive a transient p2p::Link replacement, preserving outstanding DATA, sequences and receiver dedupe. Actual logical peer removal destroys that state.

The statically supported reconnect candidate is to clear READY bit0 on RemoteConnectionClosed before the vanilla replacement-Link INITIAL recovery; leave retained reliable state intact. The R9 switch ReadyResetOnRemoteClose is 0 by default. A later isolated run may set it to 1. Do not combine that switch with the separate EDF6_SANDLOT_RUDP_READY_RESET_ONLY.txt patch: they target the same repair surface.

The desired evidence is a Link entering INITIAL with READY clear, performing its normal recovery, establishing fresh READY and ACK-retiring pending messages without a reliable-manager fault. EDF6's RUDP fault threshold is an interval limit of 7000 ms, not a seven-second clock; repeated 700,+1000 ms backoff yields roughly 25.9 seconds cumulative no-ACK history. Extending the threshold to 20000 ms is a separate experiment that stretches the window to about 204 seconds and can obscure the actual reconnect bug.

Diagnostic outcomes that must remain separate

  • Physical delivery failure: sender record is absent at recipient; diagnose EOS/link first.
  • SceneObject staging/application loss: matching physical receipt but position state lost before Soldier apply; focus class-3 staging, pending replacement and sequence history.
  • Reliable-session trouble: class-4/5 pending/retry grows or fault sets; correlate ACK and Link recovery instead of assuming ordinary packet loss.
  • Projectile-internal divergence: selectors delivered and ACKed, yet FlameBullet02, LightningBullet01 or SolidExpBullet01 has unmatched seed/motion/countdown; solve creation-state parity, not transport.

Source qualification status: R9 source passed static Clang checks, its canonical signature audit and synthetic decoder test, but Windows MSVC build and two-PC testing remain pending in the reviewed package. The earlier two-PC R7 evidence does not retroactively qualify the R9 probe.
