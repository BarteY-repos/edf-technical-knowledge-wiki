EDF4.1 vehicles on EDF6 — why tank, motorcycle and Begaruta need distinct class adapters

ConversionCross-game ConversionGameplay & AIEDF 4.1EDF 6
Technical reference · Exact-build actor-class research and bounded source-only compatibility; not new runtime

At a glance

What this page answers: EDF4.1 tank, motorcycle and Begaruta ports illustrate three different EDF6 vehicle runtime contracts despite superficially compatible assets.

How to read it: Separate skeletons, seats, wheel physics, animation and weapon mount ownership for each vehicle family; one shared adapter cannot cover them all.

Evidence boundary: These case studies are scoped to the cited vehicles and builds. They do not establish a general automatic importer.

Asset compatibility and class compatibility are different questions

The EDF4.1→EDF6 source research contains three particularly revealing vehicle ports: VehicleTank301 (V301 tank), Vehicle408_Motorbike (V408 SDL1 sidecar) and Vehicle406_Begaruta (V406 mech). Each keeps source-facing models/animations/physics where possible, but their EDF6 runtime classes impose different seat, wheel, IK, collision and named-animation requirements. A source asset can pass binary format validation and still fail catastrophically when its native class uses it.

These are specific class and sample contracts, not a universal EDF5→6 vehicle importer; no fresh game runtime test was conducted while writing this guide.

Case A: V301 tank — an accumulating barrel rotation can hide the world

The EDF4.1 VehicleTank301 class no longer exists in the studied EDF6 target. The port uses Vehicle601_Tank rather than a superficially similar class that assumes extra mudguard and antenna parts. The original tank keeps seven wheel pairs and its source mesh, wheel bindings and collision bodies.

The target class's animation pose callback rotates the cannon bone's local transform in place every frame according to seat-0 aim pitch. The donor V601_TANK.CAS has a static rest-pose track for every class-posed bone, so a fresh animation update writes the original local transform before each frame's rotation. If the imported V301 CAS lacks the equivalent cannon rest track, the next frame rotates yesterday's already-rotated transform. Under the studied failure, repeated turns made the matrix enormous (historically reported above 1e20 within about a second); Umbra subsequently received that impossible object-to-cell matrix and culled the visible scene, leaving only sky/grey. The scene-culling symptom was not proof that terrain geometry or textures were corrupt.

There is an additional recoil ownership issue. Physics writes a ragdoll body through animation_from_ragdoll while CAS controls the visible barrel cannon_slide. The bounded fix adds a meshless hidden binding leaf (edf6vc_cannon_slide_physics) with exactly the source barrel's bind frame. Physics writes that sibling leaf, while the visible barrel continues its animation. It preserves both directions of the ragdoll/animation relationship rather than letting two systems overwrite one bone.

Check before attributing the symptom to the map: per-bone rest tracks, wheel count and drawing indices, every ragdoll body-to-bone link, unchanged bind-frame relationships and whether the class modifies local transforms cumulatively.

Case B: V408 motorcycle — drive parameter layout, rider pose and hand IK

The EDF4.1 sidecar has three physical wheels and one independent gunner. Its native VehicleBike class is absent in EDF6; the examined bridge uses a Vehicle_Car chassis, but this is not the same as the donor's complete vehicle semantics.

The original V408 vehicle_setup drivetrain segment has four numbers: grip, slip angle, top speed, max torque. EDF6's Vehicle_Car expects seven numbers in a different meaning/order: friction/brake scale, gear-speed scale, gear-drive scale, steering rate factors and traction parameters. Passing the old four numbers directly yields nonsensical steering and zeroed traction fields rather than “similar driving.”

The validated narrow mapping for the studied SDL1 families scales three target fields relative to a known base:

source base [grip=2.0, slip=0.9, speed=30, torque=100]
EDF6 base drive [0.8, 30, 0.0075, 0.7, 0.075, 0.3, 0.6]
target[0] = 0.8 * grip / 2.0
target[1] = 30 * speed / 30
target[2] = 0.0075 * (torque / 100) * (30 / speed)
target[3..6] = base steering/traction values

The old slip-angle field has no verified direct Vehicle_Car equivalent and is not guessed. This mapping was constructed from five original SDL1 request profiles, including WEAPON688, 700, 721, 739 and 753; it is not a universal conversion for all wheel-based vehicles.

The original rider states differ too. vehicle503_bike_driver is a real EDF6 driver pose, while vehicle_striker_rear is a sidecar/bench pose; a class missing the bike driver clip falls back rather than borrowing motion from an unrelated skeleton. The donor bike class populates two seat hand-IK grip matrices, but generic Vehicle_Car does not. The result is a driver's hands reaching toward identity/world-origin transforms rather than the handlebar. The bounded bridge adds named te_ik_l / te_ik_r locator bones under the steering handle and updates the seat matrices in the same role as the native bike.

Lesson: model/physics correctness does not establish vehicle drivability or rider fidelity. Validate each class's parameter schema, pose-state names and live per-frame IK producers.

Case C: V406 Begaruta — preserved six mounts versus remake's eight

The source EDF4.1 V406 has six weapon mounts. EDF6's redesigned V504 has eight. The studied bridge retains the EDF6 VehicleBegaruta class path that can consume V406's actual original geometry; it does not retarget the old gun list onto V504's unrelated skeleton and does not silently add missing mounts.

A later engine foot lookup requires a named begaruta_foot_node list (ashi_l, ashi_r) not supplied by EDF4.1's original SGO. The source-only writer adds that target field while retaining source weapon mounts, three source seat/sight locators, collision and animation events. The pilot may inherit EDF6 pilot animation where compatible, but its old rig is not replaced wholesale.

Same-named weapon archives are isolated under a private resource namespace so a V406 MAB muzzle cannot be accidentally resolved against the redesigned V504 model. Every locator node, ragdoll proxy, player group (main / AddAim) and MAB event track must still resolve after conversion.

General principles supported by these cases

  1. Model, CAS, MAB, SGO, Havok and native class are a single runtime contract, even if all files parse independently.
  2. When a native class writes a bone's current transform in place, provide an authored rest track or prove a reset before repeated updates.
  3. Physics and animation cannot both own the same transform without a deliberate and measured mediation layer.
  4. A class name or apparently related vehicle model does not establish wheel setup, control-parameter schema, seat pose or IK compatibility.
  5. Remake weapon and mount counts are not interchangeable with source-era vehicle geometry; keep identity and names coherent.
  6. Validate separately: structurally parsed data, source meaning, actual runtime class consumption, correct NPC/player controls and multiplayer behavior.

Sources: retained edf41tank.py, edf41bike.py and edf41mech.py from the EDF4.1→EDF6 R10 HF4 R9 source package. Their comments cite historical exact-build binary and in-game debugging; this article reports those findings but does not rerun the original game.

A fourth independent vehicle ABI: V302 Nereid helicopter

The source V302 VehicleHelicopter302 can use an EDF6 Vehicle506_Helicopter runtime contract only while preserving its original MDB/CAS/Havok rig, converting MAB locator names, validating real rotor/wheel/seat/muzzle bone references, and retaining the target-added fuel block and final fuel-weapon record. It is not equivalent to replacing a V506 model field. The R9 adapter source is inspected, but no new helicopter gameplay PASS is claimed. See the Nereid V302 compatibility guide.

Physics skeleton consistency with moved donor bones

Moving a turret or suspension bone in the MDB without also moving the corresponding SHKT proxy/joint and both SGO ragdoll mapping offsets creates competing rest frames for a single part. The retained source includes a bounded vehicle-ragdoll re-fit algorithm that moves proxies without changing their orientation, recalculates parent joint pivots and reference poses, then validates the result. Its companion CAS code rebases absolute local animation translations when a bone bind position changes.
