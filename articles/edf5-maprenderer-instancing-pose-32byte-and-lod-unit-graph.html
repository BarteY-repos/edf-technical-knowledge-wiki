EDF5 MapRenderer: 32-byte instanced poses, draw groups and LOD selection

EDF 5Game technical referencesRendering / maps
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R133 test

Map props are not all drawn through the same AnimationModel or character-renderer callbacks. The EDF5 MapObject_* family contributes to a MapRenderer::ModelRenderer path which collects groups of models, LOD units and per-instance poses before issuing instanced indexed draws.

What one pose stores

The author observed a CPU pose array with 32-byte entries:

Part Type Meaning
Entry bytes 0–15 float4 Rotation quaternion X/Y/Z/W
Entry bytes 16–31 float4 Translation XYZ and uniform scale W

The entry array has a bounded capacity noted as 0x1770 in the studied implementation, is uploaded to a GPU buffer, then sampled by shaders through g_instancing_array. The shader's instance index includes the draw's InstanceID and a blend-index input; the separate g_instancing_inv_array supplies an inverse-node transform. This does not imply every MAPB placement record itself has a scale field: the render-instance pose and the map-file placement are different layers of data.

Draw-group organization

RenderGroup points at a model and a linked list of RenderUnit objects, including an LOD-linked next group. Each unit has its placement and fade value. Per-frame code chooses a model group according to distance, then creates draw batches in several phases. The source identified three MapRenderer render-phase entry points, but did not establish an exhaustive correspondence to all Commander phases.

For an EDF5 object that seems to disappear at distance, possible causes include the MAPB/MAPO distance rule, LOD choice and shader fade; a simple character draw hook may never see this map object at all.

Evidence: static render-call disassembly in steam-5d11de53; source edf5/map-objects.md, facts map-objects-renderer, map-instanced-draw plus mapobject-primary-vtables. No new graphics capture.
