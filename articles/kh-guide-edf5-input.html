EDF5 Input, Keyboard Snapshot and IME Integration

EDF 5Community Knowledge HubNative UI & Input
Technical reference · Editorial synthesis of contributor static/game observations; per-claim grades below

R86 qualification: Internal locking does not independently establish arbitrary external thread coherent/atomic snapshot reads. Input reconciliation.

Overview

EDF5 has a game-owned keyboard snapshot, dynamically loaded controller input, and special handling of Windows IME composition. Reading keyboard state from a hook on another thread is not equivalent to reading the game input frame.

Format, API or behavior

The message pump fills a 256-byte GetKeyboardState snapshot at RVA 0x1253600. The game does not statically import GetAsyncKeyState or XInput in the form an external patch might expect. For Japanese text, EDF5 temporarily detaches the native IME from its window and renders its own composition/candidates while the game text UI is active.

Keyboard snapshot — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (501 characters)

The game keeps a keyboard snapshot: a 256-byte GetKeyboardState table at 1253600. The message loop 60BC90 (PeekMessage pump) fills it when flag 12535DB is 0 and sets the flag; the input reader (60E04E in the source; input-pump-focus starts it at 60DF50) copies the table under a critical section (lea rcx,[0x1253600] at 60E184, anchor KeyRef) and clears the flag, so it is refreshed once per input cycle on the pump thread and is safe to read from any thread. It can be read instead of calling an API.

The game loads XInput dynamically: the UTF-16 string xinput9_1_0.dll is at RVA EDFFA0 (EDE7A0 is its file offset, which an earlier version of this line gave as the address; checked in EDF5.exe 2026-10-19), so XInputGetState can be resolved the same way for controller combos.

GetKeyState would only be correct on the pump thread (the game's own UI calls it at 49324F, 5A25E9, ...); the keyboard snapshot avoids that question. The GetKeyState slot C977A0 has five callers: 49324F, 493F97, 5A25E9, 5A28DA, 5A471B.

Input not imported — static

GetAsyncKeyState, XInput and DirectInput are not imported; a patch resolves them at runtime, for example GetProcAddress(GetModuleHandleW(L"user32.dll"), "GetAsyncKeyState").

Input ime detach — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (1,543 characters)

EDF5 detaches the IME from its window right after creating it and re-attaches it only while its own text input is active, through a window-procedure hook that swallows the composition messages and draws its own composition and candidate list; so by default no Windows IME window can appear over the game. IME imports (IAT slots): ImmGetCompositionStringW C97060, ImmReleaseContext C97068, ImmSetOpenStatus C97070, ImmGetContext C97078, ImmAssociateContext C97080, ImmGetCandidateListW C97088 (also DefWindowProcW C97770, SendMessageW C97768). Window creation: CreateWindowExW at 60BBA3 stores the window at [125A9C8]; ImmGetContext at 60BC06 saves the context at [12535E8]; ImmAssociateContext(hwnd, NULL) at 60BC1C; flag [12535FC] = 0. Window procedure 60AE90: unhandled messages go to a hook pointer [12535F0] if set (60B2B8), else DefWindowProcW (60B2F6); on WM_CLOSE (60AF7A) it re-attaches the saved context (60AFBF), releases it and destroys the window. The game's text input: setup near 491856 installs the hook 491EB0 (at 49188A) and sends custom message 0x1000, on which the hook re-attaches the saved context (491F58) and sets the flag to 1; message 0x1001 (sent at 492EC9) detaches again (491F11); 4918C0 removes the hook. The hook swallows WM_IME_STARTCOMPOSITION / ENDCOMPOSITION / COMPOSITION and passes WM_IME_SETCONTEXT on with lParam 0 (hides the system IME windows); its own drawing is in 493040 (via 491E10), which also detaches at 4930A5 when bytes +0x109 and +0x10C of its object are set. No per-frame re-detach was found.

Input ime no candidates in game — verified

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (287 characters)

In game, the Windows IME candidate window does not appear over EDF5 while an overlay's text field has keyboard focus: the IME switched to hiragana but no candidate window appeared and no Japanese text reached the field; the same IME works in other windows. The cause is input-ime-detach.

Version notes and limitations

The IME failure is a reported in-game test with an overlay text field, not proof that every IME composition problem shares one cause. Input readings are thread- and build-sensitive.
