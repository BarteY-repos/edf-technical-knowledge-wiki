Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Facts

EDF6 plugin DLLs export EML6_Load (the EDF5 equivalent is EML5_Load)

Evidence: static · Build: steam-678ccb46 · Fact ID: plugin-entry-eml6

EDF6 plugin DLLs export EML6_Load (the EDF5 equivalent is EML5_Load). Both ParameterHUD and the project's HectorBridge plugins use it.

Basis: PE export audit of ParameterHUD.dll; HectorBridge source

Attribution: EDF41-to-EDF6 handoff (Bartey), R3A offline closeout, carrier audit section 13 · 2026-09-29

PluginInfo ABI from loader PluginAPI.h

Evidence: static · Build: steam-678ccb46 · Fact ID: plugin-info-layout

PluginInfo as the loader's PluginAPI.h (FevGrave's copy, MovingPlatformFix folder) defines it: infoVersion u32 at +0 (max 1), name char pointer at +8, version u64 at +0x10 with build, patch, minor, major as four u16 from the low end (PLUG_VER(a,b,c,d) = major a). EML6_Load(PluginInfo*) fills it; the three round-14 plugins return 0 when the pointer is null and otherwise 1, except that SwarmPerf and CorpseCleanup pass on the result of their install step (0 on a failed check); what the loader does with the return value is not read. The three plugins of round 14 all write infoVersion 1, a name and the same version bytes (+0x10 = 0x10000, +0x14 = 1, i.e. 0.1.1.0), which looks like a template value.

Basis: PluginAPI.h; the first instructions of EML6_Load in EDF6SwarmPerf, EDF6CorpseCleanup and EDF6GeneratorBodyBudget

Attribution: FevGrave (MovingPlatformFix), the round-14 plugins, novae (ajane) · 2026-10-22

Build-guarded plugin hooks and fixed RVAs

Evidence: static · Build: steam-678ccb46 · Fact ID: plugin-safety-patterns

How the round-14 plugins stay safe on another game build (a pattern for our own plugins): fixed RVAs with the expected opening bytes compared before anything is written, a log line with the first mismatching byte, and nothing patched on mismatch; one of them also hashes the EDF.dll file with SHA-256 (BCrypt). Hooks are either MinHook detours (the GeneratorBodyBudget plugin, MinGW) or a rel32 retarget of one known call into a block VirtualAlloced within rel32 range of the site, with an absolute jmp [rip] to the plugin's own function (SwarmPerf, CorpseCleanup, MSVC). Per-frame work is wrapped in a structured-exception guard that switches the plugin's features off.

Basis: the three DLLs read (rizin, capstone, one stub assembler emulated); cards mods/corpse-optimization.md, mods/swarm-performance-pack.md

Attribution: EDF6SwarmPerf, EDF6CorpseCleanup, EDF6GeneratorBodyBudget · 2026-10-22

EDF6ML HF5.48 three-DLL installation

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6ml-topology-hf548

EDF6ML HF5.48 installs exactly three DLLs: game-root winmm.dll, Mods/Plugins/Patcher.dll, Mods/.edf6ml/EDF6MLCore.dll. A game-local winmm_real.dll is no longer part of it: the proxy resolves the real WinMM from %SystemRoot%\System32\winmm.dll. It hosts legacy EML6_Load plugins, supported ASI files and Patcher .txt files as separate compatibility paths; it is its own implementation, not BlueAmulet's loader.

Basis: CONTINUATION_GUIDE.md section 2, the release's file list

Attribution: EDF6 Mod Platform HF5.48 · 2026-11-01

11947EC is the engine's deliberate fatal trap after a failed resource read: mov 1, r12d, gated by bl

Evidence: static · Build: steam-678ccb46 · Fact ID: fatal-trap-open-error

11947EC is the engine's deliberate fatal trap after a failed resource read: mov [1], r12d, gated by bl. A write fault at an address below 0x10 therefore means a missing or unreadable file, not a code bug: look for open error in game.log.

Basis: CrashTrace's README and source; the instruction read here

Addresses (build-specific RVAs unless indicated): 11947EC

Attribution: FevGrave (CrashTrace 1.3) · 2026-11-01

Mod platform content override paths

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-mod-paths

Mod content paths used under that platform: mission slots Mods/MISSION/MissionPackNN/Mxxx (for example Mods\MISSION\MissionPack05\M000), objects Mods/OBJECT/<name> (for example Mods/OBJECT/EarthEater), and a game-root KCPluginCFG.cfg read by ParameterHUD.

Basis: R3A installer contract

MissionMgr+0x14FD0 holds the active physical MissionPack

Evidence: static · Build: steam-678ccb46 · Fact ID: missionmgr-active-pack

MissionMgr+0x14FD0 holds the active physical MissionPack; MissionMgr+0x14FC8 is where a Coop8 (5-8 player) parser snapshots/restores its player-4+ spill, so an uncorrected Coop8 restore can overwrite the active pack.

Basis: static analysis by the Network/Desync and platform projects

Attribution: EDF41-to-EDF6 handoff (Bartey), EDF6_CROSS_PROJECT_SCOPE_RECONCILE, archive/online.md (netcode.md#net-join-shell-path) · 2026-10-08

Loose-file overrides from Mods directory

Evidence: verified · Build: steam-678ccb46 · Fact ID: mods-redirect-edf6

In EDF6, BlueAmulet's EDFModLoader serves loose files in Mods\<path> in place of the packed vanilla files, as in EDF5 (../edf5/mod-loading.md#mods-redirect); mods that replace sounds work this way too. A loose layout (Mods/UI/LYT_HUIHQWEAPONSELECT.SGO) was loaded in a test (ui-weapon-select.md#ui-weaponselect-layout-edit).

Basis: novae (ajane)'s long-standing use of EDF6 mods; a layout-replacement test

Attribution: novae (ajane) · 2026-10-26

EDF6 file loading through IoBase::Open

Evidence: static · Build: steam-678ccb46 · Fact ID: io-funnel

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Request and virtual path
  2. Mount and archive lookup
  3. Read-time context
EDF Knowledge Hub record — original wording — expand (2,027 characters)

EDF6's per-file reads go through one funnel, sgs::fs::IoBase::Open (3BC50), which rewrites the virtual path with IoPathConverter (app:/ to /cri_bind/, the EDF5 redirect's path shape) and calls the CRI backend's Open (741C0), which reads from the binder that holds the path or else opens a loose file (the loose-file fallback is read in the code, not tested). File-system init 6FEE80 creates the converter singleton (global 21468C0, constructor 3BDE0, vtable 1C2BC20) and registers mappings with 3C2C0(conv, from, to): app:/ and APP:/ to /cri_bind/ (wide string 17E84D8; 6FF2D7, 6FF3A6..6FF3DE), app:/sound/adx to ./sound/pc, APP:/SOUND/ADX to ./SOUND/PC (direction corrected 2026-11-07, KH chat 55: 6FF0C8..6FF0EA passes APP:/SOUND/ADX (17E8480) as from and ./SOUND/PC (17E8468) as to; the line said the reverse; All Forces' in-game runs agree, #sound-bank-paths-mods). So the stock sound banks open as plain ./sound/pc/<name> files in the game folder, never as /cri_bind/ paths. 3BC50(this, path, &flags): if the converter exists, 3C640 replaces the prefix (mapping list at conv+0x18), then calls this->impl->vfunc[1]. The IoBase is made by 3BB60 from the factory pointer [1FFF3C0]: default 3E8B0 WinIoImplement (slot 1 3E8F0, CreateFileW); CriFs init 73D10 sets 73C60 (setter 3BC40) = CriFsIoImplemnt (vtable 175F0F0, Open 741C0). In 741C0: binder manager [20B2880], 752E0 finds the binder holding the path (result at this+0x98); found, binder read (1094664); not found, plain file open (109B3F8). Callers of 3BC50: exists 50E20 (22 call sites, including the layout and model loaders 7F6190, 7F63E0, 836B20, 10BBFE0), size 50E70, 42DD0, 6AF50, 74750, mount 703540 (703C0E), 7AB220. RTTI on this layer: sgs::fs::FileReader<Buffer>, CpkContentFileReader, StreamArchiveReader. The OS-level open below it (archives and loose files): Windows IO interface table 1FC4C70, Open slot 10A31E8 to 10A37F4 (CreateFileW at 10A388B). The EDF5 redirect's byte pattern (../edf5/mod-loading.md#mods-redirect-pattern) has 0 matches in EDF.dll.

Basis: disassembly of EDF.dll; not run in game; the sound mapping's direction re-read with fn.py (KH chat 55)

Addresses (build-specific RVAs unless indicated): 3BC50, 741C0, 3C640, 3C2C0, 3BDE0, 6FEE80, 21468C0, 1C2BC20, 17E84D8, 6FF2D7, 6FF3A6, 6FF3DE, 3BB60, 1FFF3C0, 3E8B0, 3E8F0, 73D10, 73C60, 3BC40, 175F0F0, 20B2880, 752E0, 1094664, 109B3F8, 50E20, 50E70, 42DD0, 6AF50, 74750, 703540, 703C0E, 7AB220, 7F6190, 7F63E0, 836B20, 10BBFE0, 1FC4C70, 10A31E8, 10A37F4, 10A388B, 6FF0C8, 6FF0EA, 17E8480, 17E8468

CRI File System loader pools

Evidence: static · Build: steam-678ccb46 · Fact ID: crifs-pools-loader-crash

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Initialization and pool counts
  2. Resource loader demand
  3. Reported failure when exhausted
EDF Knowledge Hub record — original wording — expand (2,435 characters)

CRI File System pools, and a crash when the loaders run out: the CriFs init 73D10 (a twin 73EE0 has no caller) builds a CriFsConfig on the stack (rsp+0x20: thread_model 0, num_binders 1, num_loaders 0x60, num_group_loaders 0, num_stdio_handles 0x60, num_installers 0, max_binds 0x60, max_files 0x60, max_path 0x100, version -1) and adds its only caller's values (703588, a struct 7AED20 has just filled: num_binders +0xB (+1 more), num_loaders +0x22, stdio +0, max_binds +0xB, max_files +0xB), so the game runs with 130 loaders, 12 binders, 96 stdio handles, 107 binds and 107 files; then criFs_InitializeLibrary 1092990(cfg, NULL, 0) (config checked by 109317C, work memory sized from it), called at 73E8E / 73FCD; num_loaders is config +0x08. Who holds what: every file opened for reading (741C0, #io-funnel) creates a loader at 742BA (criFsLoader_Create 1099184) and holds it as long as the file object lives, and model archives with HD textures stay open to stream them, so the loaders grow with resident archives; binds only in the mount function 74C70 (bind calls 1093F68, 1093F94, 1093D50, 1093E08 -> 1096D34, "No more resources for binding"); stdio handles (109B1F0, "Can not allocate Stdio handle", reached only through 109B3F8) only in 741C0, for an existence check of an unbound path (opened at 74284, closed at 74298) and for write mode (74345, saves); file handles (10A29C8, "Can not allocate file handle", from the IO opens 10A31E8 / 10A9CB4, listed only in the IO interface tables 1FC4C88 / 1FC4D48) only for reads in progress (inferred; the loader state machine 10A1AF4 not read through). When the loaders are out, CRI reports E2008070931: Can not allocate loader handle. (Increase num_loaders of CriFsConfig.) through its error notice 10826B0, which the game's registered callback 75140 (empty) never shows; the open returns at 3BCA7 with LastError 2 and the game logs RandomAccessArchive::Open( error : ... ) though the file exists. A .lod. texture member is dispatched with its archive's path ([r13+0xA8]; 110B182..110B232) to the sgm::res::TextureResource load 1110E80 (vtable 1A3B0E8), which takes the archive's HD streaming record with 1133C50(mgr, &rec, path) (creating it and calling RandomAccessArchive::Open 6AF50 when missing) and hands it to 1134B10, which reads rec+0x58 (the HD sort index, searched by 71230) at 1134CC4..1134CCB without a null check: a failed open crashes there, EDF+1134CCB reading 0x58.

Basis: the author's static reading and its in-game traces of 2026-10-18 (cdb, ModLoader GameLog=True: three crashes at 1134CCB with 130 loaders in use after preloading 40 vehicles and 51 enemies on the test range; with 512 loaders 123 archive opens and no failure); 1134CC4..1134CCB re-read with fn.py (mov rax,[r15+8]; ...; mov rcx,[rax+0x58])

BlueAmulet loader version and file hash

Evidence: static · Build: steam-678ccb46 · Fact ID: loader-proxy-race

BlueAmulet's EDFModLoader winmm.dll v1.0.10 (official file, SHA-256 B80E4DA6AE7264F0E9774C992DE3C5F9B6E9BC9422146ADEEB5BB2BD681E112E) forwards its 180 WinMM exports through stubs that share one call-target variable, so two threads calling different forwarded functions at once can land in the wrong function (EOS calling timeEndPeriod(1) is one such caller). hajisensai's fixed build (SHA-256 BE94E1FAC0CA12C41B6924E2EB168851641C999CE951D2A5A9FAEA5161B0F9A3, bundled with EDF6Coop and EDF6VR) gives each stub its own target; the two files differ only in those stubs (2,160 bytes).

Basis: the fixer's report (LOADER_FIX_JA.md, change record loader-fix.json): the faulty interleaving reproduced in a test, the fix checked on 180 targets and 800,000 calls over 8 threads; whether it caused the reported crashes is not proven; hashes of the two files in the drops match the report

Attribution: hajisensai (EDF6MultiSlot 1.5.5 / EDF6Coop 2.7.2), the original file in EPIC1DEFENSEF1ORCE's First-Person Mod 1.60 zip · 2026-11-06

Loader and patcher order

EDFModLoader plugin sort and same-start patch changes

Evidence: verified (source-reported) · Build: EDFModLoader v1.0.10 / EDF6 steam-678ccb46 · Fact ID: edf6-patcher-loads-after-plugins

In this loader version, Mods/Plugins DLLs load by case-insensitive filename order, with each EML6_Load callback run immediately. A plugin sorted before Patcher.dll can add, move or remove files in Mods/Patches during its own callback, and the same startup's Patcher then applies the changed list. Patcher unloads itself afterward. A plugin DLL already loaded before that modification cannot be reloaded in that pass; whether brand-new files created during plugin enumeration are picked up remains untested.

Basis: source-reported plugin-order test from the source, restricted to loader v1.0.10.

EDF6 crash-filter ownership and diagnostic blind spots

Scope: seven new source anchors from EDF6 mod-loading.md. The eighth source record, edf6-patcher-loads-after-plugins, already has its canonical anchor here; its verified loader-order result is not duplicated. Crash observations below combine static module scans with specific contributor tests on one machine.

EDF.dll filter scan: contributor's PE/Capstone audit found no game-installed SetUnhandledExceptionFilter handler in EDF.dll. The identified calls were CRT security-failure/fastfail paths, which pass a null filter and then invoke UnhandledExceptionFilter; helper __scrt_set_unhandled_exception_filter at 12D9DA4 had no references. This establishes the scanned native module's usual filter setup, not that every exception can reach an add-on handler.

Launcher and other DLLs: EDF6.exe installs its CRT __scrt_unhandled_exception_filter during startup (launcher offsets 0x10E0 → 0x17DC), before plugins load. A plugin installing its own process filter may therefore receive that CRT handler as the previous filter and choose to chain it. Scans of EDF6Coop, Patcher, Steam/EOS/Umbra and overlay modules found only CRT null-filter paths. tier0_s64.dll exports EnableCrashingOnCrashes, but the contributor found no game module referencing it. This static list cannot exclude later injected or unexamined modules.

Contributor-tested access violation: on RM015, the author deliberately wrote to address 0x10 in a plugin hook around GetKeyboardState. The plugin's top-level filter received exception code C0000005 on the game thread; a cdb dump showed the plugin, EOS overlay, EDF and thread-start frames. Thus the specific exception was not swallowed by a global game __try handler. This deliberately crashed test is not evidence that crash reporting captures all other termination mechanisms, and is not a change introduced by this wiki branch.

One-run replacement check: in the author's 18-Oct-2026 RM015 run, no module called SetUnhandledExceptionFilter after the plugin registered its filter and before mission start. Steam, tier0, EOS overlay and NVIDIA DLLs loaded later; the installed SIGABRT and invalid-argument handlers also stayed active. Neither ReShade nor a dxgi proxy was present, so their filter interactions and long-session changes were not tested. This does not authorize a general statement that the process filter is never replaced.

Unreportable exits: an ordinary unhandled-exception filter misses __fastfail paths (including /GS and some CFG or heap-corruption failures), external process kills, out-of-memory termination without a dispatched exception and hangs. A game routine that locally catches an exception then exits via ExitProcess would also bypass a top-level filter, though the contributor did not identify such a route in the examined game code. The Windows exception-model limit matters even when one access violation was captured successfully.

EDF6 Patcher logs and plain relative SGO paths

Host module in diagnostic logs: BlueAmulet Patcher v1.1.2 EML6_Load obtains EDF.dll via GetModuleHandleW(L"EDF.dll"); EDF5/4.1 patch their executable module with GetModuleHandleW(NULL). EDF6 writes paths such as Patching <n> bytes at EDF.dll+<RVA> (uppercase hexadecimal for image-relative offsets, absolute pointer for writes beyond the image), whereas EDF5/4.1 use EDF5.exe+ / EDF41.exe+. The mod loader's own redirector lines use lowercase hexadecimal, e.g. Hooking EDF.dll+741c0. ModLoader.log and game.log are shared naming conventions; BarteY's separate EDF6ML uses EDF6ModLoader.log. These distinctions matter when correlating patch reports with module-relative addresses.

Unverified relative-resource interpretation: the contributor infers that an SGO path without the app:/ prefix bypasses the archive-to-/cri_bind/ converter and is opened as a filesystem-relative path, as in stock ./sound/pc examples. KittopiaCreator's x40 vehicle EFS bullet SGOs name ./mods/weapon/effect/TonitrusSpear.efarc and ./mods/weapon/vehicle/effect/x40Railgun.efarc. This would let mods carry files outside the normal Mods/<path> override tree, but no independent path-resolution runtime test was performed and platform/case rules remain open.
