MRAB — named resource archive and studied SSA structure

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: An MRAB is another archive of named game resources. In the examined samples, it uses the same basic SSA archive structure as RAB.

Where it fits: Each directory entry identifies a resource name, a type and a byte range. The payload inside can have its own format and compression.

Important distinction: Sharing an archive layout does not prove that RAB and MRAB have identical purposes in every EDF version.

Worked example: two different offset bases

Suppose a made-up SSA entry begins at file offset 0x100. Its signed name displacement is +0x40, while its absolute payload offset is 0x800 and stored size is 0x20. The same rules apply in the inspected MRAB/RAB family:

QuestionCalculationResult
Where does its name begin?0x100 + 0x400x140
Which bytes hold its stored payload?0x800 through 0x800 + 0x20 (end exclusive)[0x800, 0x820)

These numbers are for teaching only, not an extracted native entry. Do not add the entry address to the payload offset: the name displacement is entry-relative, but the payload address is absolute. Resolve the type index against this archive's own type table; then check the payload's actual signature and possible CMPL wrapper before calling it a model, animation or another resource.

What an MRAB archive represents

The measured MRAB container holds individually named resource entries. Each entry identifies its name, resource type and byte payload through the container's entry table and associated name/type lookup structures.

This is an archive format, not an animation clip, scene object or model format in itself. Its payloads must be interpreted according to their individual type and consuming subsystem.

Header and entries in the inspected family

The shared measured SSA\0 grammar has:

  • A 0x28-byte little-endian header with entry count and directory offsets.
  • A 0x20-byte entry record containing name-relative and payload-absolute offsets.
  • UTF-16LE resource names and type-string lookup structures.
  • An archive-local type index that must be resolved through that archive's type table.

The source record defines name_address = entry_address + signed_relative_name_offset. Payload addressing uses a separate absolute file offset and the stored csize field. These distinctions are the same measured parsing rules documented for the sampled RAB family; the RAB article contains an introductory field table.

Compact binary field map

The independent RAB/MRAB round-trip record and the earlier RAB guide agree on the following observed header organization:

Header offset Data
+0x00 / +0x04 SSA\0 signature and studied version word
+0x08 Start of resource data in the inspected serializer
+0x0C / +0x10 Maximum stored and maximum decompressed member sizes
+0x14 / +0x18 Entry count and entry-table position
+0x1C Name-index table position
+0x20 / +0x24 Number of resource types and type-string table position

Each 0x20-byte entry contains a relative name offset (+0x00), stored byte count (+0x04), archive-local type index (+0x08), a fourth attribute word (+0x0C), eight further bytes (+0x10) and an absolute payload offset at +0x18 (treated as a 64-bit field by the examined round-trip reader). The later reader observed zeros in the +0x10 region of the stock archives it reproduced; that observation does not establish a universal rule for other files.

This table is intentionally bounded to the SSA layout actually researched. Do not identify a different archive family solely because its filename ends in .mrab, or assume that a matching signature guarantees identical resource-type semantics.

Resource semantics and limitations

Correctly reading MRAB's outer structure does not identify every embedded resource schema. Keep the archive's entry metadata separate from the interpretation of an embedded MDB, DDS, effect or animation-related payload.

The studied merge rules operate at entry identity, not by concatenating two binary archives. They do not justify arbitrary last-writer-wins changes inside a same-named resource.
