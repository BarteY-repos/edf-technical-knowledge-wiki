EDF6 map Havok materials: collision.hkt, hkConfig and impact surfaces

EDF 6Game technical referencesMaps and collision
Technical reference · Static source and contributor checks, with build and open questions noted; no new R131 EDF runtime

EDF6's visual map geometry and its solid physical collision are separate resources. In the examined corpus each map's MAD contains a collision.hkt Havok payload; the map loader resolves that entry by its name's CRC32, loads its physics-scene data and associates named physical bodies with their map models. The source counted 50 maps with collision resources in three CPK groups; that count belongs to the examined install snapshot, not all conceivable DLC or mod maps.

How a map collision body identifies a model

A body name can combine an MDB model name, a collision node and an optional render node. For example:

com_ym_jihanki_panel1.com_ym_Jihanki_Panel1_Colli|ym_Jihanki_Panel1

The native reader splits on . and |, reconstructs the asset identity and matches the named bodies with models from the map's RAB. The body and the visible mesh are therefore not interchangeable, even if their names resemble one another.

Compact per-surface information

Some Havok material names contain JSON under the source key 0xF201, for example:

{"hkConfig":"p_material=2;p_penetration=0;ai_cost=0;","name":"AAA_Panel01"}

map::havok_FixupShape packs the three values into shape userData:

Property Packed portion Source meaning or limitation
p_material bits 0–7 Surface material; 0 default, 1 glass, 2 metal in the studied configurations
p_penetration bits 8–15 Separate penetration/contact classification
ai_cost bits 16–23 Possible navigation cost input; the native consumer is not established

The low byte is read on a hit by the game's material lookup. That routine descends compound shapes through shape keys and reads the leaf userData (or a material field for a type-8 leaf). It is not simply reading the original JSON string again. Source code for the hit lookup, including +0x1082E0 and +0x11A9B60, was traced on one EDF6 Steam binary.

p_material=1 correlates with window/glass pieces and 2 with metallic panel/vending-machine components; collision-layer and effect-sound tests supported the mapping. The underlying hknpMaterial friction and restitution fields can be overwritten by global map settings during load, so a raw material's half-float values are not necessarily final runtime parameters.

Evidence boundaries

The source reports a contributor-tested hkConfig reading, static code mapping for packed userData, and many observed materials. It does not demonstrate a global use for every ai_cost, or that water on any arbitrary map is implemented as a special penetrable solid. Do not generalize any function address to another binary build.
