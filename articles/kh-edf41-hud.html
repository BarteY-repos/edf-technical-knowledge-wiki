EDF 4.1 — Hud (community source notes)

EDF 4.1Community Knowledge HubGameplay & AI
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Armor gauge (HUiHudPowerGuage, FevGrave: HudPlayer_DurabilityGauge)

EDF4.1 armor gauge number conversion

Evidence: static · Build: steam-57aab039 · Fact ID: armor-gauge-cap

The gauge's update 3FB1E0 gets armor current and max as floats (through 3F5690), truncates them (cvttss2si at 3FC03A cur, 3FC03E max from [rax+0x168]), caps both at 999999 (mov eax,0xF423F at 3FC046, then two cmp/cmovg on the same eax, so one imm32 at 3FC047 raises both), and formats each with 3FC2D0 (calls after 3FC055 and at 3FC0B2). The same bytes B8 3F 42 0F 00 3B D0 as in EDF5 and EDF6.

Basis: FevGrave's notes; anchor unique (also checked by FevGrave in three copies of the exe)

Addresses (build-specific RVAs unless indicated): 3FB1E0, 3F5690, 3FC03A, 3FC03E, 3FC046, 3FC2D0, 3FC0B2

Attribution: FevGrave (ArmorDisplayCap), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

Long power-gauge text clipping report

Evidence: static · Build: steam-57aab039 · Fact ID: armor-gauge-textbox

The text box that may clip long numbers: per FevGrave's PourGaugeUIBox_EDF41.txt (not supplied), the Text_Pow / TText_Pow box fields at gauge +0x4A8 / +0x4B8 (72.0 / 22.4); the render side is PourGauge.sgo in Root.cpk. The code cap must be raised too, or the display stays at 999999 / 999999 whatever the SGO says.

Basis: FevGrave's notes

Attribution: FevGrave (ArmorDisplayCap), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

Executable text RVA to file-offset mapping

Evidence: static · Build: steam-57aab039 · Fact ID: text-file-offset

EDF41.exe file offsets in .text: file offset = RVA - 0xC00 (image base 140000000, .text at RVA 0x1000, raw 0x400).

Basis: FevGrave's note (RVA 3FC046 = file 3FB446)

Attribution: FevGrave (ArmorDisplayCap) · 2026-10-16

Vehicle aim line and crosshair colors

Vehicle weapon aim line: cmp dword rbx+0xAB0,0 / jg at 3200DA (above 0 = cooling down)

Evidence: static · Build: steam-57aab039 · Fact ID: aim-line-cooldown

Vehicle weapon aim line: cmp dword [rbx+0xAB0],0 / jg at 3200DA (above 0 = cooling down); the line color is four floats at [rcx+0x104], +0x108, +0x114, +0x118 (ready = the patch's vanilla red: 0, 0, 0.5, 0.5). metoxys's WeaponAimLineContextual keeps the line during cooldown in yellow (white as an option).

Basis: the patch's anchor and code

Addresses (build-specific RVAs unless indicated): 3200DA

Attribution: metoxys (WeaponAimLineContextual), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

LaserSight mod weapon crosshair backport

Evidence: static · Build: steam-57aab039 · Fact ID: lasersight-hooks

metoxys's LaserSight ("an augmented backport" of EDF5's dynamic crosshair color, for about 290 weapons: gray out of range, white on terrain, red on an enemy in range, blue on an ally) hooks: the XGL system constant writer 5363DA, the crosshair sight state 3F9C90 (original call 3F5410), its clear 3F9DBE, a per-frame update 2B242B (cmp byte [rdi+0x99B],0), the ray range load 2AF276 (constant AB6A10 = 1000.0) and the target hit 2AF580. It casts its own ray with 2AEEF0 and 2AF1D0, takes the weapon range from the weapon's float +0x1A8, and swaps the crosshair pixel shader (0xA70 bytes, DXBC with 7F1738A9 at +4) for its own as the shader is created at 54F91A.

Basis: the patch's 7 anchors (all unique) and code

Addresses (build-specific RVAs unless indicated): 5363DA, 3F9C90, 3F5410, 3F9DBE, 2B242B, 2AF276, AB6A10, 2AF580, 2AEEF0, 2AF1D0, 54F91A

Attribution: metoxys (LaserSight), novae (ajane)'s EDF 4.1 outside set (ExtraPatches) · 2026-10-16

What LaserSight's code reads (offsets as used by the patch): the target's type target+0x180, 1 enemy and 2 ally

Evidence: static · Build: steam-57aab039 · Fact ID: lasersight-fields

What LaserSight's code reads (offsets as used by the patch): the target's type [target+0x180], 1 enemy and 2 ally; the crosshair object's player [+0x4A8] and slot indexes [+0x4B0] / [+0x4B4] into the player's table [+0x12B0] (0xA0-byte entries), the player's weapon array [+0x1290], and a class test [+0x12A0] == 4 before checking a second held weapon (Fencer, per the patch's 2026-05-27 note); eligible weapons by vtable (AA2C78, AA2760, AA2E20, or [w+0x500] and [w+0x690] zero with a sub-object at [w+0x5E0] of vtable AA7F48, AA7FE8 or AA7928).

Basis: decoded from the patch's machine code; meanings from the patch's comments and labels

Addresses (build-specific RVAs unless indicated): AA2C78, AA2760, AA2E20, AA7F48, AA7FE8, AA7928

Attribution: metoxys (LaserSight), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

Vanilla soldier laser-sight raycast trigger

Evidence: static · Build: steam-57aab039 · Fact ID: laser-raycast-vanilla

The game's own laser-sight raycast: the player soldier update tests [rdi+0x99B] at 2B242B and only then calls 2AEEF0 (ray start and direction from [rdi+0xF58] / [rdi+0xF60], else the object's +0x90 / +0x80) and 2AF1D0 (the raycast: range constant AB6A10 = 1000.0, physics world from [CC8528]+0x18 -> +0x88, its virtual +0xF0; each hit goes to 2AF690 at 2AF588). 2AF1D0 and 2AEEF0 have no other callers.

Basis: rizin disassembly; call sites found by scanning .text for E8 rel32

Addresses (build-specific RVAs unless indicated): 2B242B, 2AEEF0, 2AF1D0, AB6A10, CC8528, 2AF690, 2AF588

Attribution: novae (ajane), 2026-10-16 (while reviewing metoxys's LaserSight) · 2026-10-16

LaserSight extra per-frame raycast cost

Evidence: static · Build: steam-57aab039 · Fact ID: lasersight-review

LaserSight runs that raycast a second time every frame for every soldier passing 2B242B, whether or not a laser-sight weapon is held (vanilla never does), into global buffers, with the range taken from the last eligible weapon's +0x1A8; in that private pass the hit handler 2AF690 is skipped. The patch's code fits its allocations exactly (1016, 58 and 3108 bytes), its seven hooks leave no live register clobbered (checked at each return site), and the reconstructed call to 3F5410 passes the original three arguments. Not found: a definite crash bug. The unconditional raycast (states vanilla never raycasts in: no laser weapon, vehicle, dying, mission end) and the unchecked weapon index into [player+0x1290] are the risky parts.

Basis: the patch laid out with its labels and disassembled; game code at every hook read

Addresses (build-specific RVAs unless indicated): 2B242B, 2AF690, 3F5410

Attribution: novae (ajane), 2026-10-16 (novae (ajane) suspects it of occasional crashes) · 2026-10-16

Chat limits: the character limit mov qword [rbp+0xF],0x20 at 4DDD67 (default 32); the text box width mov ebx,400 / cmp ecx,ebx / cmovg ebx,ecx at 413E14 (metoxys's IncreaseChatLimit uses 90 and 1200 with cmovl; "decent values at 1080p").

Basis: the patch's anchors, decoded

Attribution: metoxys (IncreaseChatLimit), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

Single-line chat text width and performance

Evidence: static · Build: steam-57aab039 · Fact ID: chat-measure-cost

Chat performance: the text chat fits every line into one single-line box, measuring its width (UTF-16 wcslen several times per frame for every string in the history; flag value 4 written at 4BF176, imm32 at 4BF17A); the equipment screen measures the chat history again although it does not show it (call 52BD10 at 4BEEB6, the text measure). metoxys's ImprovePerformance clears the flag and makes the equipment screen measure an empty string. Later games use line breaks instead.

Basis: the patch's anchors and notes

Addresses (build-specific RVAs unless indicated): 4BF176, 52BD10, 4BEEB6

Attribution: metoxys (ImprovePerformance), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

EDF4.1 HUD mechanics

HUD dispatch through four view slots

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-hud-frame-path.

5681E0(system) (called from 343370 at 3435B0) walks four camera-view slots at system +0x1D8 with stride 0x258, locks each camera through B29D0 and queues 571850 → render job 571780. The render-thread path 5714D0(camera, ctx) skips a camera whose byte +0x150 is zero, sets a viewport from camera +0xE0–+0xEC via 532D70, invokes camera slot 5 and then each linked HUD's slot 3 through its list at camera +0x158. It restores the viewport at 5716B8. The analogous HUD-visibility bytes for EDF5 and EDF6 are +0x180 and +0x200; do not reuse them in 4.1.

Basis: static call graph in the Knowledge Hub; no newly performed in-game hook test.

Split-screen HUD uses deeper layer offsets

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-hud-split-depth.

Four HUD constructors inspect the local-player count at [[CC84A0]+0xA800]. With two or more players they write greater depth at part +0x60: armor gauge (PourGauge.sgo, 3F9F4D), radar (Radar.sgo, 3FFC4F) and vehicle gauge (VehicleGuage_L_B.sgo, 403849) use −600 → −800; energy gauge (EnergyGuage_R_P.sgo, 4044BF) uses −700 → −900. Smaller apparent size is an inference from depth, not a literal EDF5/6-style 0.7 scale assignment. The source found no matching 48 px HUD inner shift in 4.1.

Basis: constructor-disassembly scan in the source; visual size ratio remains inferred.

Native HUD detail: radar, nameplates and text

Source scope: EDF Knowledge Hub revision 5b589ca, build steam-57aab039. These are contributor static reverse-engineering observations, not new in-game tests. Two preceding records—HUD frame dispatch and split-depth rules—are already anchored in the prior section above; the following adds the remaining source routes without repeating their IDs.

Camera HUD objects, view rectangles and model gauge assets

HudBase construction (static): ten HudPlayer_* classes for radar, armor, reload, vehicle, weapon, crosshair, followers, other players, chat and rescue append counted engine-owned objects to camera list +0x158. EDF4.1 constructs them from app:/Hud/*.sgo rather than the lyt_Hud*.sgo layout framework used later.

Gauge parts (static): Root.cpk's hud/ has model-backed PourGauge.sgo, Radar.sgo, ReloadGuage.sgo, VehicleGuage_L_B.sgo and energy gauge variants, with their RAB/MDB animation resources. Crosshair archives are sight01..18.rab excluding 03, 04 and 16. Other gauges' exact screen placements were not traced.

Per-frame camera rectangle (static): system update 566B80 copies view-slot {x,y,w,h} through 56F530 to camera +0xE0, and rebuilds its projection from w/h; the HUD frame route above reads this same viewport. Console command screen_rect can change the slot rectangle.

Side-by-side views (static): the mission spawn path 14FE30 assigns local player p rectangle (p×W/n,0,W/n,H) for n>1, or the full screen for one player. It refreshes target buffers, initializes the camera and attaches the ten HUD classes. The older note's split-depth change applies within those columns; EDF4.1 does not use EDF5/6's inner-gauge 48 px shifts.

Armor position (static): draw slot 3FB1E0 passes (W/1920×96,H/1080×80,1.333,1) through 3F5690, so its nominal origin is (96,80) and x/y respond separately to screen size. Distortion outside 16:9 is an inference, and the helper's exact projection semantics were not fully decoded.

Radar world mapping, colors, clipping and placement

Radar instance (static): HudPlayer_Rader is built by 3FFAB0 from Radar.sgo and three effect textures Radar_item.dds, HudRaderPoint.dds, HudRaderArea.dds. It holds the local soldier, objective/area lists and positional scale +0x5B0=0.4; dot size is an instruction immediate, not a field.

HUD corner and versus mode (static): draw 4002C0 respects a per-player radar-enable byte linked to versus settings. It positions the radar 50 design units from the viewport's upper right and chooses depth by UI-size option; farther depth draws smaller (inferred). Unlike the armor gauge, its origin is computed from the right edge.

Heading (static): radar rotation uses local soldier basis rows or the ridden vehicle bone matrix; extreme camera pitch beyond ±0.75 changes which basis row is used. The radar center comes from the soldier's world position row +0x90.

World-to-radar point (static): helper 400EB0 clamps eligible distant objects to a 200 m world-radius rim, then applies scale 0.4 (an 80-unit radar radius). It separately treats height displacement, clipping it to ±80; a rim flag distinguishes arrow versus dot.

Color table (static): float4 globals CC9180..CC91D0 are filled once from constants: white, cyan (0,0.75,1,1), green, red, yellow. Patching the table after initialization differs from modifying its source constants, which other UI code may share.

Marker passes (static): 401010 draws white team 4, crates green, cyan team 2, red hostiles, yellow team 5, teammate icons, objective points, stencil disc, area circles and mission boundary. Versus mode limits team passes. Some objective-vs-area interpretation was inferred from EDF5 code and the assigned textures.

Dot and arrow geometry (static): marker quads use immediate ±5-coordinate stores at 401291..4012DF, tile U range 0–0.25 for dots and 0.25–0.5 for rim arrows, plus a height stem. Teammate icon quads use ±7.5 immediates. Changing dot size requires instruction edits rather than a runtime field patch.

Stencil and mission border (static): 4019C0 writes a 32-triangle 72.5-radius stencil disc, switches to EQUAL and clips area circles and boundary. 402780 draws MoveAreaManager min/max bounds in red using the same radar projection helper.

Multiplayer nameplates and player identity links

Player identity (static): 3F7250 locks/casts a weak object to SoldierBase; 1AD660 retrieves its player weak link at soldier +0x1620 (empty for NPCs). Link +0xF8 carries player number and class is resolved through the player table.

Other-player status (static): HudPlayer_MultiPlayStatus projects an anchor 2 m above another soldier, assigns dead/captured states, resolves overlaps and draws inside the current camera rectangle. Teammates in the same vehicle use a fixed column at x 300×W/1920, y (320+110n)×H/1080.

Edge box (static): EDF4.1 nameplate anchors clamp to the central 20–80% on both axes (0.5 of a 0.6-size inner rectangle); EDF5's related box is approximately 17–83%. Increasing the EDF4.1 margin requires changing a shared calculation, not just one constant.

Status sprites (static): the indicator combines an off-screen arrow, armor and vehicle bars, player-color slot icon, class, name, and dead/captured state indicators, with timed alpha for captured status. EDF4.1 omits the later game's special icon over a downed body.

Nameplate textures (static): 3FECA0 opens app:/Hud/OnlineHudTexture.rab and binds named textures such as outcursor01.dds, gauge_frame01.dds, gauge_01.dds, icon_Dead01.dds and icon_Pinch01.dds, then issues HUD quads through DDD20/E4C90.

Text line fitting, wrapping and menu glyph pictures

Direct text calls (static): 52BD10 measures explicit \n line breaks; the glyph draw loop stops after 512 UTF-16 units and has no width parameter. Automatic word wrapping happens in separate text helper functions, not these raw measure/draw calls.

Single-line fitting (static): 4EDE90 can shrink to box width/height and center lines according to low flag bits. Chat history uses width-fit flag 4, shrinking long lines horizontally instead of wrapping; an earlier performance mod clearing that flag changes the result (source inference).

Wrapped UI strings (static): 4ED310 and measure twin 4ECDB0 parse inline color tags, wrap at box width with rules for punctuation and forbidden starts, and keep alphanumeric runs intact; these are used by chat bubbles and weapon selection, without EDF5's ui::TextField layout architecture.

Menu gamepad glyphs (static): EDF4.1 menus load PS4Buttons.dds (260×52, five UV cells) and LRButtons.dds (216×37). The surveyed route uses PlayStation-oriented pictures, not EDF6's controller-type-selecting HuiTextureButtonTextField.

EDF4.1 player chat bubbles and HUD projection

Source: edf41/talk-subtitles.md, Steam build 57aab039. These are native static observations about online chat and coordinate transforms; they should not be confused with mission dialogue subtitles.

HudPlayer_Chat texture, world anchor and local placement

Evidence: static · Fact ID: edf41-chat-bubble

HudPlayer_Chat (vtable AA8D10, constructor path 3F75C0) draws one bubble per list entry +0x90, using chat_Red/Blue/Green/Yellow.dds from app:/Hud/OnlineHudTexture.rab. Its draw path 3F7900 → 3F83B0 projects another player's position +0x90 raised by 1.9 m through 3F6CC0, clamps bubble rectangles to the screen, stores drawn rects to avoid overlaps, and scales against a 1920 × 1080 reference. For a dead sender a second projection without the rise is also computed, but its use was not decoded. The local player's bubble is positioned at a fixed x/y offset around (300, 320) plus 110 per successive line; the message-type interpretation is inferred.

Reusable font and bubble-frame render calls

Evidence: static · Fact ID: edf41-chat-text-draw

Chat bubbles pick a font from the array at [CC8A60 + (GameDataMgr+0x60+1) × 16] (interpretation as a per-language font index is inferred). They begin font rendering with 52BF30, set horizontal/vertical scales at font+0x320/+0x324 to 0.65, draw wide text with 4ED310 using a {0,0,400,0} box, and finish with 52C100. Bubble frame draws use 3F80D0 and 3F7AE0, with texture set at hud+0xA8.

World-to-viewport matrix and behind-camera handling

Evidence: static · Fact ID: edf41-world-to-screen

3F6CC0(out, worldPoint, camera, viewport) combines camera view matrix from rows +0x170..+0x1A0, a perspective built from FOV +0x14, near/far +0x18/+0x1C, aspect from camera rectangle +0xE8/+0xEC, and a viewport matrix scaling x by width/2 and y by -height/2 with center offset. It divides projected x/y by w and negates x/y/z when w is negative (behind camera). Output holds pixel x/y with y downward, z and w relative to the supplied viewport, not necessarily the final letterboxed window.

HUD viewport to letterboxed window mapping

Evidence: static for transform, inferred for switch meaning · Fact ID: edf41-hud-viewport-to-window

Camera HUD draw 5714D0 adjusts rectangle +0xE0..+0xEC using fitted dimensions [CC8374]/[CC8378], full window dimensions [CC827C]/[CC8368], and offsets [CC836C]/[CC8370] conditional on byte [C3F28F]. The structure resembles an EDF5-style 16:9 fitted area with a letterbox switch, but that byte's setter was not decoded in EDF4.1. A point from 3F6CC0 in the unscaled camera viewport needs the same mapping to be placed accurately over the final window.
