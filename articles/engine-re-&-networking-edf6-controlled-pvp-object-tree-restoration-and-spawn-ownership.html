Controlled EDF6 PvP actors — propagate teams through actual emitters and restore every native baseline

EDF 6Engine RE & NetworkingNetworking
Technical reference · Source-reviewed custom PvP rollback/typed-emitter transaction design, not a stock EDF6 feature

One actor is not one team field

A custom-controlled enemy or multipart boss is usually a GameObject tree, not a single root object. Weapon controllers, gun batteries, child parts, live owner-team lookups and cached damage emitters can each read team data. Changing only the root object's current team can give a friendly-looking actor whose rockets still target its old faction, or whose newly created child remains permanently flagged as a PvP faction after control ends.

The retained controlled-PvP implementation is an explicitly designed extension, not proof that stock EDF6 includes a player possession system. Its reusable reverse-engineering lesson is that actual native emitter ownership and lifetime must be part of a team-switch transaction.

Enumerate typed objects and real emission points

The source requires a read-only enumeration of the entire supported native child tree and all emission paths. It distinguishes typed emitters such as weapon bases, indirect-fire controllers, gun batteries, owner-team mirrors and cached fields. The example bounds are up to 256 GameObject members and 512 emitter records per controlled root; these are adapter safety limits, not game-engine universal maxima.

A real emitter is not necessarily a GameObject; blindly casting its address to one and writing an object-team offset is unsafe. The adapter validates the emitter's actual typed container, owning member and current lifetime before modifying or reading it. Some emission paths derive team live from their owner and need no cache write at all. Some cached fields survive the parent object and need independent storage identity.

Full identity and rollback

The controller cannot key only on a raw pointer: native addresses may be recycled. It associates each member with its exact object/control-block identity, tracks emitter incarnation and may preserve a separate live storage identity. A temporary team change is accompanied by an owned restoration lease:

  1. Probe, read-only, validates the tree and whether every firing path can be represented.
  2. Acquire captures the real native current and last team plus typed emitter baselines before making team changes.
  3. Frame maintains the temporary faction only while authenticated control remains stable; a pending/unknown owner fails closed.
  4. Restore writes back all surviving original values and retains a pending lease if any restoration step fails.

A failure during acquisition, object deletion, mode exit or network disconnect must not release the lease prematurely. The ability to restore the exact native team depends on keeping original baseline identity, including the SetTeam(-1) closing state. -1 must not be rewritten to an arbitrary active faction just because a controlled actor has died.

Spawns must be reserved before publication

Multipart bosses may spawn children during a controlled wave. A newly created part can inherit the temporary PvP team, so saving its current value as a “native baseline” would permanently contaminate it. The source uses a bounded prepare → construct/initialize → adopt → publish → finish protocol: reserve the anticipated children, prove each source's real baseline and exact parent identity, adopt the child before network publication, then release unused reservations. Unexpected children, overlapping ownership or an unknown baseline fail closed.

A mother/boss adapter uses this protocol through SpawnWave and the MotherSpawnOwnership hooks. That is a custom transaction model for safe modding, not a claim about native EDF6's default spawn implementation.

Network identity is a separate surface

The controller accepts a source player identity only after an external authenticated Core/Coop decision. It never manufactures, rewrites or trusts a requested user identity from arbitrary SGO resource strings. Even a valid local ownership transaction does not itself guarantee the correct host/client damage attribution; the actual native network authority of root, child and projectile remains a separate requirement.

What the source establishes: a rigorous, testable bounded design for team propagation and rollback, based on real native object/emitter lifetimes and team fields. What it does not establish: 16 native EDF6 teams by default, universal support for every enemy class, or newly verified multiplayer runtime behaviour.

Sources: components/compatibility/src/pvp_controlled.h, enemy_control_legacy_mother.h, team_native_logic.h and online_authority.h in EDF4.1 R10 HF4 R9.
