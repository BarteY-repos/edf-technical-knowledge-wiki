Facts

Menu scripting and key configuration symbols

Evidence: static · Build: unknown · Fact ID: settings-framework-differs

EDF41.exe has MainScript.as, COMMON.CFG, UiCommon_KeyConfigUtil and the OptionPlayer_RotateSpeed text key, but none of EDF5's HUiHQ* settings classes or HUiLayout, so its settings menus use a different framework than EDF5 and EDF6.

Basis: byte search of EDF41.exe (13,896,192 bytes) for ASCII RTTI names and UTF-16 strings; counts only, no disassembly; build id not taken. Searched and absent: HUiHQGameSetting, HUiHQKeyConfig, HUiHQSystemSetting, HUiLayout@ui; present: UiCommon_KeyConfigUtil, COMMON.CFG, MainScript.as, OptionPlayer_RotateSpeed

Attribution: novae (ajane) · 2026-10-14

Limited mouse support in headquarters menus

Evidence: verified · Build: steam-57aab039 · Fact ID: menu-mouse-basic

EDF 4.1's between-mission menus have only basic mouse support: moving the mouse moves the current selection as if an arrow key or d-pad direction were pressed; there is no free pointer like EDF5's and EDF6's menus have.

Basis: novae (ajane)'s play experience, reported 2026-10-26; not looked at in EDF41.exe; consistent with settings-framework-differs (a different framework from HUiLayout)

Attribution: novae (ajane) · 2026-10-26

Headquarters UiBG perspective projection

Evidence: static · Build: steam-57aab039 · Fact ID: uibg-camera-edf41

The HQ background (UiBG) camera: its projection 419A70 -> 51B230 is a right-handed perspective (near 0.01, far 4000) with the vertical field of view from [this+0x90]; the UiBG setup writes 0.96 rad (0x3F75C28F) to +0x540 at 40918F and the position +0x530 defaults to (0, 0, 0, 1) (409199..4091A7), replaced by the SGO's position when present (4091B1..4091E7; Menu_BG01.sgo has none). The geometry fits: the farthest BG_Stripe at z = -31.03, 58.04 x 32.66, exactly fills that frustum. Unlike EDF6's flat UI models (edf6/ui.md#ui-skin-model-transform). EDF 4.1's main game HQ music is BGM_E4S02_EDFHonbu (its default too, 3475F0), pack 1 BGM_Sinkou_intermission, pack 2 BGM_Sinkou_taisenmenu (ModeList item 3 of each package.sgo).

Basis: the author's reading against EDF41.exe; the +0x540 / +0x530 writes re-read with fn.py here (KH chat 47; the author cites 409190, one byte into the 0.96 store)

Addresses (build-specific RVAs unless indicated): 419A70, 51B230, 40918F, 409199, 4091A7, 4091B1, 4091E7, 3475F0

Why EDF4.1 menus do not follow the pointer

Mouse click is virtual-pad confirmation, not a position hit test

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-menu-no-pointer.

EDF4.1 menu input treats the mouse as virtual-pad bits: horizontal/vertical movement becomes thresholded direction steps, left click confirms the currently selected item and right click cancels, regardless of the pointer's screen coordinates. The mouse is recentered and hidden every frame, and the source found no menu read of pointer position. Screens are ui::FrameBase with separate ui::CursorBase highlight variants (UiCursor_Model, UiCursor_PanelCursor, UiCursor_SimpleBox, UiCursor_SlidePanelCursor); selection travels through 4E7E90. A proposed free-pointer mod therefore requires stopping recentering in 561740, drawing a cursor, hit-testing the item rectangle and updating the selection mover. The last four operations are a route, not a tested implementation.

Basis: static input/UI route from the source, preserving the untested mod boundary.

Input mapping: keyboard, mouse, controller, bindings and menus

Provenance: EDF Knowledge Hub revision 5b589ca, novae (ajane), EDF4.1 steam-57aab039. The findings below are static reverse-engineering observations unless explicitly labeled unverified. Addresses and offsets are build-specific, and these routes have not been independently run or confirmed for this wiki.

Window, keyboard snapshot and focus

Window and IME (static): 5613B0 registers and creates the game window, keeps its handle, saves/detaches the IME context, and handles close/window messages; the input pump is separate from the rendering loop.

Keyboard acquisition (static): a thread running 561740 processes window messages, snapshots 256 virtual-key states through GetKeyboardState into CC3040 under lock CC39C0, and marks a fresh sample with CC3027. The frame reader 5630E0 consumes and clears that flag; a reader refresh need not represent a new keyboard sample.

Focus (static): GetForegroundWindow is compared with the window stored at CC8318, with state at system object +0x30. A second activation/click gate at +0x32 delays accepting input after refocus by about half a second.

Imports (static): the traced path uses Win32 keyboard and cursor APIs, not a DirectInput/raw-input acquisition pipeline. GetKeyState has five identified call sites, including chat-wheel code; a call site is not itself proof of why a click fails.

Key filter (static): the 256-byte per-virtual-key table at CC8380 can cause selected keys or mouse buttons to read as released; this is not a general mouse-delta filter.

Mouse accumulation, element layout and directional steps

Cursor-relative movement (static): while focused, 561740 compares GetCursorPos with the window center, accumulates horizontal/vertical differences at C64900/C64904 under a lock, then recenters with SetCursorPos and hides the pointer. This describes the observed pump, not every possible later repositioning call.

Reader timing (static): the pump runs on its own thread (5612F0); 5630E0 takes and resets accumulated mouse deltas and the wheel before deciding whether a new keyboard snapshot exists. A no-snapshot refresh can therefore discard movement.

Player devices (static): elements are in per-player blocks starting CC3D20, stride 0x490 versus EDF5's 0x4A0; floating value is at element +0x48 and pressed flag at +0x4C. Pad slots precede mouse +0xD0..+0x128, then 103 keyboard elements from +0x130. Mouse setup orders MouseL, MouseM, MouseR, raw X/Y, wheel and reversed wheel, directional X/Y steps and reverses, plus MouseWheel. EDF4.1 lacks side-button elements; the earlier broad L/R/M description was corrected by the later exact layout.

Mouse-to-direction conversion (static): system setting C50FC4 is clamped to 0..1 (default 0.5). Reader 5630E0 turns accumulated deltas into discrete steps at thresholds X=(1.2-s)×512 and Y=(1.2-s)×360 pixels (default approximately 358 and 252). X takes priority; separate axis-lock states and a roughly 0.2-second idle release prevent simultaneous free-axis selection.

Soldier view (static): 2A3A80 consumes the selected mouse look bindings (divides by 24, clamps each axis to −16..16) or the right stick, depending on device and state. Mounted look has additional per-human accumulators that produce at most a ±1 step and cap retained movement at 32 (EDF5/6 use 26).

Unverified — mouse-look gaps: the meaning of C3F28D and whether any game-thread SetCursorPos route exists remain untraced. Only the pump recenter path above is identified.

XInput, key indices and COMMON.CFG binding rules

Controller API (static): 561AC0 loads xinput9_1_0.dll dynamically; its GetState, SetState and GetCapabilities pointers are stored at CC3D00, CC3D08 and CC3D10. The read path applies stick dead zones 7849 and 8689.

Keyboard element ordering (static): 563DB0 maps 103 indices to virtual keys: A–Z, digits, numpad digits, F1–F12, OEM keys, modifiers, arrows, editing/navigation keys and others including Kana. W/A/S/D have indices 22/0/18/3. Each keyboard binding takes a 0x18-byte slot.

Binding codes and offsets (static): in EDF4.1, 0 means none, 1–10 are A/B/X/Y/LT/RT/LB/RB/L3/R3, 11–14 are mouse L/M/R/wheel, and keyboard index i becomes code i+0xF (three below EDF5). COMMON.CFG soldier/Fencer pad blocks begin at 0x34/0x80 (player two at 0x48C/0x4D8); player-one keyboard Common starts 0xA8, class/vehicle pages span 0xD4..0x150. Player-two keyboard offsets were not mapped.

Rebind conflict guard (static): dialog 43F5F0 checks conflicts between Common page kind 3 and page kinds 4–10, displays OptionPlayer_KeyCantChange/OptionPlayer_KeyAlreadyChosen, and has action/code exceptions. It does not establish checks for all pages or an EDF5-style Drive W/S exception; some key-code interpretations in the original guard investigation remained unresolved.

Binding labels (static): D7DC0 reads the action's binding at store+0x1C+(player×0x116+action)×4 and constructs an OptionPlayer_Key%s lookup key. 3DFD00 resolves the resulting text through the ResourceManager; an unknown key can yield an empty string.

Unverified — vehicle throttle: the vehicle configuration page visibly names Attack1, Attack2 and Brake; the proposed explanation that throttle must therefore come from Common movement bindings is an inference, not a traced vehicle input path.

Unverified — remaining input mapping: exact player-one pad selection involving C3F28D/CC3150, and the purposes of some GetKeyState callers, remain open. Later binding-code mapping resolves only part of this earlier open record.

Menu virtual-pad masks and selection

Virtual controller (static): ControllerManager at CC84B0 binds pad, mouse and keyboard elements for four devices; update B0ED0 stores held, newly pressed, repeated and released 16-bit masks at offsets +0xD88, +0xD8C, +0xD90, +0xD94. Repetition starts after 16 frames and recurs every two frames; combined no-player masks live at +0x4408..+0x4414.

Fixed menu controls (static): bits 1/2/4/8 encode directions from W/S/A/D, thresholded mouse steps, sticks and sometimes arrow/D-pad states; 0x40 confirms using Space/Return/MouseL/pad A and 0x80 cancels using Backspace/Escape/MouseR/pad B. The menu W/A/S/D route is hard-coded and bypasses gameplay key configuration; this does not mean gameplay binds are fixed. Held confirm/cancel bits suppress some competing bits.

Menu consumer (static): screens read the selected player's virtual pad (or merged masks for player −1). Shared mover 4E7E90 advances selected list or grid items with direction/repeat flags, wrapping where configured. The item under a physical pointer coordinate is not selected by hit test; the previous Why EDF4.1 menus do not follow the pointer is retained above.

Chat shortcut wheel: pick logic and outstanding click hypothesis

Wheel update (static): UiChat_ShortCut updates at 4E1DB0 and draws at 4E26A0; it uses a pointer-like on-screen position for choosing a shortcut while the wheel is open, unlike ordinary HQ list navigation.

Sector selection (static): a selection is valid inside an annulus scaled from radii 100..750. The normalized cursor angle atan2(x,-y), offset by π/8, resolves one of eight 45° sectors (zero points up); closing/clicking sends a valid sector via 4E2460. The rendered wheel cursor uses the same stored position as the picking logic.

Unverified — intermittent wheel clicks: the proposed race between the threaded keyboard snapshot and the game-thread GetKeyState(1) call might explain missed clicks. This is a contributor hypothesis, not a demonstrated cause or a tested fix.

UI frame, cursor and options

These EDF4.1 observations are source-attributed to novae (ajane), build steam-57aab039; all are static except the explicitly unverified option-extension question. The existing menu pointer/virtual-pad account remains the canonical record, without a duplicate source anchor.

Screen lifecycle, hierarchy and input arbitration

Static: 565270 constructs xgs::ui::SystemCore; global [CC8520] points to the outer object's +0x78, so the core starts at [CC8520]-0x78. Core lists: pending inserts +0x18, live screens +0x28/count +0x30, operations +0x38/count +0x40, group +0x48. EDF4.1 list nodes hold the object at +0x18, not the EDF5/6 node offset. Broadcast 56E740 sends messages to both pending and live lists.

Static: base xgs::ui::Object has state bits +8 (1 release, 4 covers, 8 covered), a controller layer from +0xC with group, mask, rank, active, registration and mode, screen group +0x20, channel +0x24, self reference +0x28 and parent reference +0x30/+0x38. Concrete RTTI identifies a screen but does not make mutating it on an arbitrary thread safe.

Static: constructor group census: 2 mission-end jingle, 3 usual HQ/pause/lobby/dialog menus, 4 fade or room-description, 5 loading/save, 6 chat/soft keyboard, 7 notifications and exit. Dialog types 1–6 map to groups 5, 3, 4, 2, 6, 7. These groups are encoded in constructor paths, not a generic layout configuration.

Static: controller [CC84A8] owns a locked layer list; 5604B0 orders it by highest group, assigning active rank. Modes 0/1 claim channel-mask bits, 2 always active, 3 never. Screens register through 575D10. Soldier input uses group 0 and one player's mask; a group-3 modal screen with that bit can take focus (inferred from arbitration, not observed as a user test).

Static: 56DF30 runs each frame after HUD and virtual-pad update. It inserts pending screens, applies queued operations, re-ranks their controller layers, sorts by root rank plus child order, and computes per-channel covers and covered bits. This processing is shared by HQ, pause, online and system overlays.

Static: the pass then releases bit-1 screens, calls remaining slot-0 updates with context (input, active-only input, delta time) and queues their slot-1 draws onto the rendering thread. When active byte +0x18 is zero, updates continue with a null active input pointer; this is not a destruction signal.

Static: ui::FrameBase stores x/y/w/h at +0x48..0x54, 4×4 transform +0x60..0x9F, probable scroll offsets +0xA0/+0xA4 and optional animation scale +0xA8. Slot 7 translates, animates and normally maps pixels onto 3D coordinates with diag(0.01,-0.01,0.01). A free-pointer hit test needs a ray projected into the panel's local plane, not raw screen pixels.

Selection, highlight geometry and pause screen

Static: each ui::CursorBase keeps its frame at +0x28 and selected-item shared reference at +0x40/+0x48. 4E7C70 appends a 0x20-byte selectable element: int rectangle x/y/w/h +0..+0xC, opaque caller value +0x10, enabled byte +0x18; first insertion selects the item. Cursor slot 2 plays the selection-move sound.

Static: UiCursor_SimpleBox uses float rectangle +0x78..0x84 (PanelCursor +0xB8..0xC4). Slot 1 copies the selected item's first four ints; slot 4 eases, and slot 5 draws a quad with frame offsets subtracted. These item rectangles are the local coordinates needed by a pointer-selection adapter.

Static: weapon select registers 300×42 rectangles at x=300×column, y=42×row, each with a 0x40-byte weapon entry as caller data, records row indices in column arrays and selects the current weapon with 4E8310. Ui3DTest demonstrates five 400×32 selectable items.

Static: UiPause_Base with offline and online leader/member subclasses is a model frame; update slot 4CE500 calls the same 4E7E90 selection mover as HQ lists and grids. A cursor integration can share navigation machinery across these screens.

Static/inferred focus: pause constructor 4CDE80 registers group 3, dialog type 2, the pausing player's channel/mask and apparently mode 0. Its layer would outrank the soldier's group-0 input for that player; exact focus behavior follows from code rather than a new in-game test.

Mission-select state, briefing and results

Static: UiHQ_MissionSelect (vtable AAB9D8, constructor 482A10) is a transparent frame with UiHQ_MissionDescription and UiHQ_MissionMedal children. Mission buttons are 3D panels from app:/Menu/Button01.sgo; descriptions use Window03.sgo, and the difficulty is a separate UiHQ_MissionDifficulty screen.

Static: GameDataMgr [CC84A0] supplies clear bytes +0xEE8 + class*0x200 + row, mission list +0x110, class table +0xC8 and active row +0x40. Screen row states in its vector at +0xC8 are 0 cleared, 1 open, 2 shown locked and 4 beyond, including special handling for the all-cleared extra row; the logic parallels EDF5.

Static: labels combine row+1, period and localized missiontext.sgo title columns 0/2/4; state 2 shows N.??? and disables the row. The briefing panel uses language columns 1/3/5 and a texture from the row's Texture set; locked state uses MissionSelect_NotOpenMissionDesc and UnlockedMissionThumb.dds. No EDF5/6-style %dq% substitution was found.

Static plus untested detection idea: UiMissionResult_Main (vtable AAC0E8) is a UiFrame_Model descendant shown after a mission clear. Finding this concrete type in the live list could flag result-screen state, analogous to later games; no plugin test established that contract.

Fixed options rows and save fields

Static: pad options class UiHQ_Option builds 3D panels from app:/Menu/*.sgo in native setup 4854D0, not a single layout manifest. Keyboard, additional, language, window-mode and key-config screens are separate classes.

Static: 4887F0 hardcodes 16 rows: twelve numeric/toggle options (three volumes, shake, rotation, view UD/LR, vibration, camera effect, demo skip, ID tags and UI size) and four actions (Default, two KeyConfig choices, ChatCustomize). Left/right 489680 switches directly on row 0–11 and writes GameDataMgr fields. Adding a row needs native panel, label and switch changes; there is no generic option-ID data table.

Static: GameDataMgr's SYSTEM.CFG block holds three float volumes at +0x158/+0x15C/+0x160 (which volume each corresponds to is inferred from label order). Per-player stride 0x458 in COMMON.CFG includes UI size +0x168, horizontal/vertical inversion +0x16C/+0x170, vibration/shake/camera effect +0x174..0x176, rotate speed float +0x178; demo skip and ID tags near +0xE9C/+0xE9D. No distinct rotate-lerp, dead-zone, camera-type or damage-display setting was found.

Unverified: detailed keyboard-option rows, action destinations and whether an extra 3D panel row can be introduced without editing model assets remain open. Reusing an action row or a hotkey is a proposal, not demonstrated functionality.

Provenance: novae (ajane), steam-57aab039. The separate earlier mouse-as-virtual-pad fact remains intact; no new cursor, hook, menu row or runtime test was implemented in this editorial reconciliation.

EDF4.1 HQ weapon selection native UI

Source edf41/ui-weapon-select.md, Steam build 57aab039. These are static UI-layout/native-call observations; viewport row count and resting scroll edges are inferred.

UiHQEquipment frame family and weak partner panes

Evidence: static · Fact ID: edf41-weaponselect-classes

UiHQEquipment_SelectWeapon (vtable AAABD8, constructor 4384E0, size 0x1430) inherits UiFrame_Model; update/draw callbacks are 43A1B0/43A5D0. It holds weak partners UiHQEquipment_SelectWeaponCategory (vtable AAAC58, category header) and UiHQEquipment_WeaponDescription (vtable AAACD8, stat pane) at screen +0x1980/+0x1988. SGO assets loaded include Window06.sgo, PanelButton01.sgo and WeaponNew.sgo; the “New!” node is actually spelled WeapnNew.

1000×252 viewport and 300×42 cell grid

Evidence: static; visible six-row inference · Fact ID: edf41-weaponselect-view

The weapon-list frame starts at (-500,-126) with size 1000×252. Columns are 300 px apart and rows 42 px tall; thus six full rows and about 3.33 columns fit geometrically. Column records of size 0x20 track cell counts and 0x40-byte cells, with longest row count in screen+0x191C. Draw callback 43A5D0 culls columns outside x range -300..width and rows outside y range -42..height after scroll. It paints per-row colored quads, a white strip at x+251 for each column, then texts (including red cap-refusal states). This is a native 4.1 layout, not EDF5's grid geometry.

Focus-driven smooth scrolling and category-strip sync

Evidence: static; rested-row inference · Fact ID: edf41-weaponselect-scroll

Update 43B150 eases scroll toward the selected item's rectangle: vertically until top and bottom fit in the 252-pixel view (no margin), horizontally with a 100-pixel side margin and clamped to the total column width. Each frame it moves scroll floats at screen+0x1960/+0x1964 halfway toward target, copies integer scroll positions into frame fields +0xA0/+0xA4, and synchronizes the category header. Because height is exactly 6×42, target positions tend to align on row edges at rest; absence of half rows is an inference, not a screenshot audit.

Description pane gets authored text and level

Evidence: static · Fact ID: edf41-weaponselect-desc-pane

On selection change, 43B3B0 copies two preauthored localized weapon strings from the screen's text table into description-frame fields +0x670/+0x690 and writes item level around +0x6B0..+0x6BC. Draw callback 43D120 measures and lays out the text using the EquipSel_WeaponLevel label. Unlike EDF5's twelve numeric stat slots, EDF4.1's description is text prepared per weapon. Wrapping, clipping and long-description scrolling were not decoded in this source pass.
