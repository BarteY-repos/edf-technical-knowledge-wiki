EDF6 MDB material ABI: why shader reflection differs from native records

UniversalModels & MDBModelsEDF 5EDF 6
Source-backed research / case study · Reconciled

Direct shader reflection describes fields that may be consumed; a native MDB material records the fields actually serialized, with their own ordering, type, size and sampler list. The two representations demonstrably differ in several EDF6 material families.

Reflected fields absent from a concrete material

The m_instancing_array_stride UInt scalar appears in the reflected shader metadata for SND_BRDF_MAP_COMMON, COMMON_CLIP, BUILD_WINDOW, BUILD_PARA_NC, SIGNBOARD_PATTERN and certain legacy Build shaders. In the matched MDB material instances from the studied native corpus, that field did not occur in the per-material parameter lists. This establishes a capability-versus-instance distinction; it does not prove every reflected field is forbidden in material serialization.

Some snd_Map_Build_Simple_Clip, snd_Map_Object_NoAO_Light and snd_Map_Build_Basic_NC native instances also omit metallic or roughness despite those fields being reflected by the shader catalog.

Parameter order and TypeByte/SizeByte

For SND_BRDF_MAP_COMMON, the examined reflection order is approximately:

diffuse, specular_diffuse_blend, specular_color, normal_amount, metallic, roughness

The observed native MDB instance order is:

diffuse, metallic, normal_amount, roughness, specular_color, specular_diffuse_blend

Several reflected Float3 variables are serialized as type 2 / size 3, not size 4. Bounded native examples include Common.diffuse, Common.specular_color, Common_Light.light_color, Build_Window.diffuse/interior/specular_color, and the Signboard Pattern counterparts. A reflected vector dimension alone does not fix the per-instance stored SizeByte.

Sampler order differs from shader-register order

Shader Reflected / register order Native MDB material order
snd_BRDF_Map_Build_Basic_NC albedo, normal, dirt, param_r_m_xxx_hr, param_occlusion param_occlusion, dirt, albedo, normal, param_r_m_xxx_hr
snd_BRDF_Map_Build_Window window_frame_texture, interior_texture, normal, window_normal, param_r_m_xxx_hr interior_texture, normal, param_r_m_xxx_hr, window_frame_texture, window_normal
snd_BRDF_Map_Build_Para_NC albedo, normal, dirt, param_r_m_h, param_occlusion param_r_m_h, param_occlusion, dirt, albedo, normal
snd_BRDF_Map_Build_DirtScroll albedo, normal, dirt, param_r_m_cm0_hr, param_occlusion param_occlusion, dirt, albedo, normal, param_r_m_cm0_hr
snd_BRDF_Map_Signboard_Pattern albedo, normal, param_r_m_occ_light, switching_mask switching_mask, param_r_m_occ_light, albedo, normal

These are measured ordering differences, not a blanket claim that every different ordering is rejected by EDF6 at runtime.

Observed value and transparency distinctions

  • Among 44 examined Common_Clip materials, alpha_clip was 0.5 in 42, and 0.3435 in 2.
  • Signboard image_split was a raw type-4 u32 = 2 in its studied native instance.
  • Build_Window.interior_wrap_count was raw type-4 u32 = 4 in the example.
  • Common_Light.light_color used HDR-intended values above one, with non-uniform values across samples.
  • snd_Map_Object_Glass can have transparency flags/priority/layer profiles without containing _Alpha or _Clip in its name.

A reflected shader list is not a universal recipe for initializing every MDB material field to float 1.0 or for classifying all transparency solely from a filename suffix. For raw type-4 encoding see u32 material lanes; for exact profiles see the native profile table.

Color customization and known limits

The documented two-mask param_cm0_cm1 path interpolates diffuse → change_color0 → change_color1 using masks R/G before multiplication by albedo. It is distinct from a generic albedo tint, and some observed materials use packed names such as param_r_m_cm0_hr.

These measurements concern native resource structure and shader-data descriptions. Without an actual matched final-frame draw capture, they cannot alone prove that arbitrary profile modifications retain visually correct compositing.
