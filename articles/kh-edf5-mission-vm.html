Event model

Reachable event registration counts across exact44

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-event-reachability

Count event registrations over the reachable source graph only: across exact44 there are 2233 raw source RegisterEvent calls, 2214 reachable ones and 2214 official internal_CreateEvent calls; the 19 extras sit in unreachable compiler-generated Func_N regions (e.g. M000 dead Func_27: 1×9000; M029 dead Func_42: 5×9051; M032_5 dead Func_43: 1×9000 + 1×9200; M035 dead Func_9: 1×9000). Reachability starts at Main and follows direct wrapper/helper calls and RegisterEvent target edges; named helpers that are not Func_N are kept even when nothing calls them, because the official ports keep export-like helpers such as FadeMainLight (M001, M020_5). Do not whitelist per-mission counts instead.

Basis: exact44 comparison; the old engine scanned all decompiled function regions and registered the dead branches

Attribution: EDF5-to-EDF6 mission transpiler R37 (Bartey drop), section 6.1 · 2026-08-26

Event-slot identity: one unique target handler per slot

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-event-slot-per-handler

One event slot per unique source target handler, not per registration: a Func_N armed several times with different factor sets is one target event. Exact44: 2214 reachable registrations, 2106 unique reachable target handlers = the sum of the official MAX_EVENT_IDs (2106), and this holds mission by mission for all 44 pairs. R37 assigns one event id per unique target, in first-registration order, reused by every registration of that target; this removed duplicate handler bodies and many false API count mismatches.

Basis: exact44 comparison

Attribution: EDF5-to-EDF6 mission transpiler R37 (Bartey drop), section 6.2 · 2026-08-26

Scheduler: the multi flag

BVM scheduler behavior for ready registrations

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-multi-flag

The BVM scheduler (EDF5, kept in EDF6's BVM runtime): when registration record +0x20 == 1, all ready registrations are appended for execution; otherwise the one ready registration with the greatest delay (record +0x18) runs. So RegisterEvent's third argument is a "multiple eligible event executions" flag (the old decompiler name multiple_functions_per_event(?) was directionally right), and the runtime tests equality with 1: R37 changed multi != 0 to exactly multi == 1.

Basis: binary RE; /mnt/data/edf_transpiler/R37_BINARY_MISSION_RUNTIME_CONTRACT_2026-08-26.txt and .json, r37_event_type_binary_contract_gate.txt

Attribution: EDF5-to-EDF6 mission transpiler R37 (Bartey drop), section 7.1 · 2026-08-26

Translation to EDF6: source multi == 1 - EVENT_TYPE_ASYNC, otherwise EVENT_TYPE_SYNC

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-multi-to-event-type

Translation to EDF6: source multi == 1 -> EVENT_TYPE_ASYNC, otherwise EVENT_TYPE_SYNC. EDF6's AngelScript scheduler is isomorphic to the BVM one (events sorted by delay, descending; ASYNC(1) appends all ready events, SYNC(0) keeps the first ready one, the greatest delay; delay at event +0x58, EventType at +0x5C): ../edf6/missions.md#as-event-type.

Basis: binary RE of both games; regression test_mission_event_multi_exact.py

Attribution: EDF5-to-EDF6 mission transpiler R37 (Bartey drop), section 7.2 · 2026-08-26

Difficulty branching via custom call 21

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-getdifficulty-21

Mission scripts read the difficulty with custom call 21 (int GetDifficulty() in mp-s's edftools) and branch on it with push N; testg; jmpf chains (in M003: < 2, then < 3, setting a local scale 1.0 / 1.5 / ... and event waits 14 / 11 / 8 s): 111 of the 141 shipping scripts call it, 324 times in all. The spawn calls carry the SGO and count as arguments: 1010 CreateFriend, 1011 CreateFriendSquad, 1012 CreateFriendGroup, 2000-2011, 2023 and 2030 the CreateEnemy family (group calls: spawn point or area, radius, SGO, count, health scale, active). So per-difficulty enemy lists and counts can be read from the scripts by evaluating each branch per difficulty value; done 2026-11-08 (#bvm-per-difficulty-eval). Every one of the 324 reads has the shape cuscall0 21; push N; testle|testg|testl; jmpf (difficulty >= N, < N or > N, N mostly 3 or 4).

Basis: all 141 shipping scripts disassembled with mp-s's mission_util.bvm_decompiler (scratch driver File_Storage/Logs/catalog/bvm_dis.py), call names from its bvm_model.py; M003 read around the calls; the difficulty values 0-4 (Easy..Inferno) are assumed, not read

Attribution: KH chat 65 (EDF5 catalog), mp-s (edftools) · 2026-11-08

Per-difficulty spawn counts through abstract execution

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-per-difficulty-eval

Per-difficulty spawns of all 141 shipping scripts are read by abstract execution of their disassembly: no operand stack, each statement end (spawn call, store, branch, call) parses its operands backward from the instruction before it; GetDifficulty returns 0-4 (Easy..Inferno); a branch on a value that is not known (other calls' results) takes both sides; the constructor, Main, then every RegisterEvent target run in registration order, globals carried over. Result: every spawn record resolves to an .sgo and a number; 92 of the 141 scripts change their enemy list or counts with difficulty. Against the wiki's tables (counts like 60×2 and HARD以下:黒22 / HARDEST以上:金22 parsed), totals agree on all difficulties for 23 missions (offline 2, 3, 10, 17 and 70 among them, also by wave) and at Inferno only for 21 more: the wiki often records the top difficulty's counts. Most other gaps involve generator spawns (#bvm-generator-calls-2100-2101), which the wiki counts its own way.

Basis: scratch File_Storage/Logs/catalog/bvm_eval.py all (output bvm_eval.json, bvm_eval_all.txt), compared by bvm_vs_wiki.py with the wiki's extract/missions.json; promoted 2026-11-08 (KH chat 68) to _tools/bvm_eval.py, same counts on all 141 scripts, which catalog.py uses for catalog/missions-enemies.md

Attribution: KH chat 67 (EDF5 catalog), edftools (mp-s) for the disassembly · 2026-11-08

Event handler run counters and their guards

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-handler-counter-guard

Event handlers count their runs: each Func_N body starts Func_N___Counter++ and exits unless the counter equals N's own constant, usually 1 but 2 when the handler is armed twice and only the second arming should act (M018 Func_3: its second wave of 60 Red Ants spawns on the second run). Generator dispatch and low-byte call IDs

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-setgenerator-native

The generator calls in EDF5.exe: custom calls dispatch on the id's low byte like opcodes (mission-flow.md#bvm-interpreter-dispatch; ids sharing a low byte share a case that compares the full id, e.g. 2000 and 3024 at 116AF3). 2100 (low byte 0x34, case 115BB4, which first handles call 52) calls 124950(script, object id, hatch, sgo, amount, hp, rate, interval, bool), which resolves the object (12CA60) and sends it message 0x20100 {rate x 60 and interval x 60 as whole frames, amount, hp x the script's +0x414 factor, the bool, the sgo path, the hatch} through its virtual slots +0x38, +0x30, +0x40; 2101 (case 115C1E) calls 124AB0, which sends the same message id. Eight object classes compare for 0x20100 (1F8A17, 2543CF, 27A581, 297F54, 29AD47, 2A09A4, 2A79B1, 2C43A6); the one at 2A09A0 hands it to a generator component at object +0xA30 (3C4840, which loads the sgo) and takes 0x20101 as a flag at +0xB01. The message layout: #generator-message-0x20100; the amount is a wave size and live cap, repeated while the owner lives: #generator-waves-repeat.

Basis: disassembly (index byte table 117968, jump table 1176E8 read with scratch File_Storage/Logs/catalog/rva_find.py; EE66A8 = 60.0)

Addresses (build-specific RVAs unless indicated): 115BB4, 115C1E, 124950, 124AB0, 2A09A0, 3C4840

Generator component message 0x20100

Evidence: static · Build: steam-5d11de53 · Fact ID: generator-message-0x20100

The generator component's message 0x20100 (built by 124950 for 2100, 124AB0 for 2101): +0x0 mode (0 = 2100 SetGenerator, 1 = 2101 one batch), +0x4 wave interval in frames (2100's 8th script argument x 60; 0 for 2101), +0x8 amount, +0xC gap between single spawns in frames (2100's 7th argument, 2101's 6th, x 60), +0x10 hp factor (x the script's +0x414), +0x14 the bool, +0x18 the sgo path, +0x38 1, +0x40 hatch (the owners with several generators pick the component by it). 3C4840 stores a mode-0 message as the standing setup at component +0x20 (amount at +0x28, and grows the spawn-slot pool to amount) and loads the active setup at +0x70 (remaining count +0x78, gap +0x7C, wave delay +0x74, gap timer +0xC0) unless a 2101 batch is still running there.

Generator wave size, live-spawn cap and lifecycle

Evidence: static · Build: steam-5d11de53 · Fact ID: generator-waves-repeat

A 2100 generator releases waves until it dies: the amount is the size of a wave and a cap on its live spawns, not a total. Per frame (3C4D40) the active setup counts down the wave delay +0x74, then the gap +0xC0, then spawns one (3C4E90) and decrements +0x78; a 2100 spawn goes into pool slot +0x78 and is skipped while that slot's earlier spawn is still alive. When +0x78 reaches 0 the standing setup is copied back (3C4CC0: full amount again, wave delay = the interval), so waves repeat for as long as the owner lives. A 2101 batch spawns without slots and then hands back to the standing setup. If the flag +0xD0 is set, each wave also waits for +0xD1 (set by message 0x20101, cleared after the wave).

Basis: disassembly (fn.py) of the update and the copy; owner classes named from their vtables (scratch File_Storage/Logs/catalog/vtable_class.py)

Addresses (build-specific RVAs unless indicated): 3C4D40, 3C4DF3, 3C4E62, 3C4CC0

Attribution: KH chat 75 (curator) · 2026-11-09

Object health percentage via custom call 3019

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-call-3019-durability

Custom call 3019 (object, percent) multiplies an object's max HP +0x1F8 by percent / 100 (EE66D0 = 100.0) and sets current HP +0x1FC = min(current x percent / 100, the new max): a per-object durability factor applied after the spawn, not a "remaining HP percent" as mp-s's edftools labels it (set_HP_remain_percent??). Case 1169EE (switch on the id's low byte: byte table 117968, RVA table 1176E8) calls 1254C0(script, handle, percent). Scripts apply it to the handle a single spawn returned (CreateEnemy ...; store), so its factor multiplies that spawn's hp argument: 54 calls in 14 of 141 scripts, some on friendly vehicles (m041's combat frames and railguns at 10 %). EDF 4.1 and EDF6 the same (../edf41/missions.md#edf41-call-3019-durability, ../edf6/damage-model.md#level-durability-natives).

Script compilers emit switch as value

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-switch-form

Script compilers emit switch as <value>; jmp table and, at the table, one test per case: pushtop; push k; jmpne next; pop; jmp case, each failed test leaving the value on the stack for the next. M065 sets its call-20 factor this way (GetDifficulty 2 / 3 / 4: 0.9 / 0.8 / 0.75). A backward expression parser must take a pushtop that follows a jump from the jumps into it, not from the instruction above it; _tools/bvm_eval.py did not until 2026-11-09 and so ran every case on every difficulty: with the fix, three EDF5 missions' counts changed (m015, m059, m082: e.g. m059's Blue Tadpoles 2 / 4 / 6 / 8 by difficulty, not 8 on all) and nine EDF 4.1 missions'.

Basis: m065's disassembly read (edftools); catalog diffs before and after the fix
