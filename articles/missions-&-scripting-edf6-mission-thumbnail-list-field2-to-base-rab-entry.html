EDF6 mission thumbnails: LIST field2 → base IMAGE.RAB named DDS entry

ConversionMissions & ScriptingMissionsEDF 6EDF 4.1
Technical reference · Prior Procmon/runtime-positive archive routing + R29 named-entry source contract; R29 authored deploy offline-only

The September 2026 uncertainty over whether mission preview images were selected by name or a row ordinal was resolved for the studied EDF6 mission LIST/RAB format. Later R29 source authority and prior runtime file-access evidence establish a named DDS entry derived from LIST field2, rather than an anonymous image_at_row_index relationship.

The actual runtime archive path

The observed target game requests these base-level archives:

Mods/MISSION/MISSIONLIST.OFFLINE.IMAGE.RAB
Mods/MISSION/MISSIONLIST.ONLINE.IMAGE.RAB

A custom MISSIONLIST_MISSIONPACKNN.IMAGE.RAB can be well-formed and still not be the archive the observed loader requests. This is why earlier custom packs with correct local images showed missing or repeated previews. The base-archive lookup is backed by retained file-access / prior mission-port runtime evidence; the September 18 R29 editor authoring build itself was not yet game-runtime qualified.

Stable entry identity

For the studied mission-LIST profile, the entry name is derived from the exact field2 display key, using the path-token normalization:

entry_name = LIST_field2.strip().replace('\\','/').replace('/','_') + '.dds'

For example, MISSION/EXAMPLE_A becomes MISSION_EXAMPLE_A.dds. This is an illustrative synthetic key, not a claim about a shipping mission's literal name. The maintained writer rejects empty keys, absolute paths, path traversal .., an already-suffixed .dds, and trailing separators. It also case-fold-checks duplicate archive entry names.

Consequences: reordering LIST rows does not in itself change the key for an unchanged field2. Conversely, copying one donor row into every new slot without updating field2 makes distinct missions resolve to the same donor preview identity. A converter must populate field2 consistently with its own thumbnails and verify ONLINE and OFFLINE references rather than assuming correct images will follow from row ordering.

Exact archive and payload contract

The retained R29 serializer accepts a raw DDS, not a PNG or a filename disguised as DDS:

  • bytes DDS at offset 0;
  • DDS header size 124 at +0x04;
  • validated width and height (source validator bounds 1–16,384);
  • deterministic literal CMPL wrapper and independent decompress-to-original round-trip;
  • SSA image RAB version 0x110 with exactly one TEXTURE type family;
  • existing named entry replaced in place, otherwise appended;
  • all non-target compressed payload bytes preserved exactly.

The source stores per-slot thumbnail DDS/hash/dimensions in a portable workspace. It requires an existing legitimate EDF6 base image archive; it does not build an empty alternate image namespace and pretend the runtime will load it.
