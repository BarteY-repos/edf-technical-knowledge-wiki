EDF4.1 Earth Eater (UfoMother401) on EDF6 — hex-grid parts and multiplayer identity

ConversionCross-game ConversionNetworkingEDF 4.1EDF 6
Technical reference · Source/exact-build RE of panel grid and target-native multiplayer identity, no new two-peer test

The “mothership” is really a controller for many panel objects

In the studied EDF4.1 UfoMother401 encounter, the hull is a logic controller, not a giant render/collision/HP body. Its source 19 × 19 staggered hex-layout rules instantiate panels as real scene objects. The placement formula identified from the source for row i, column j is:

x = 172.5 * j + (i odd ? 86.25 : 0)
z = 150 * i

Coordinates are then centered within the map/layout, and newly spawned panels begin about 1000 units above their intended cells, awaiting fly-in or immediate-placement actions. Do not assume all 361 cells necessarily produce the same part type or that a 19 × 19 controller is one huge model.

The original hull SGO's action_list contains a small instruction language. The examined eight action kinds cover: constructing a layout, flying waiting panels down in batches, placing them immediately, vanishing panels, starting a slow rotation, enabling/disabling attacks, and flying the core away. A mission ObjectAction(n) selects an entry in that table. A direct pass-through of n into a different EDF6 native actor action table is not semantically valid.

Different panel roles and lifecycle

The reconstructed native contracts distinguish at least these roles:

  • Panel01: armour panel with mounted gun batteries at named locators.
  • WeakPanel: damage triggers a local destruction cascade within approximately 200 m in XZ, including nearby panels / core under the source rules.
  • Core: the hull's apparent HP reflects core status; its destruction drives a long boss-death sequence (about 50 s in the described source).
  • BigCannon01: opens, charges about 5 s, and fires a downward beam for about 10 s.
  • Generator / FinalGenerator: forward SetEnemyGenerator and SetInstantEnemyGenerator calls through the hull to the correct indexed child.
  • FinalCannon01: has a genocide-beam or five aimed lightning-bolt attack path.
  • SmallLaser / Sniper / Plasma / Rapid batteries: independent range-limited targeting behaviour attached to panel locators.

The common PanelBase manages flying in/out, destruction, burn/fall phases and weak-body damage filtering. Only hits on the SGO-defined weakpoint body count for the relevant target, and objects without such a body are not universal damage recipients. Conflating panel visibility with panel HP/damage ownership is a common failure mode.

How EDF6 parts can represent the source object tree

The studied compatibility code makes each visible panel an actual target-side EventAnimationObject, with a model, CAS main player, ragdoll and durability, then attaches class-specific state via a controlled runtime record. The invisible hull uses a very small drawn donor rather than gaining new collision/durability behaviour. Part locator transforms for mounts, muzzles and spawns originate from source MAB locator data, preserved in named SGO fields. The original sound cue names are resolved from corresponding available audio-bank resources instead of inventing new identities.

This representation can be structurally valid while still failing if scripts act on a single parent only, weak bodies aren't attached to their panel objects, or a generator drops from a panel with the wrong identity.

Network copies and ownership

The retained implementation has each peer run the layout controller and its local panel tree. Corresponding parts and spawned enemies receive game-native child identity so that durability, damage and target state can be synchronized. Randomized attack starts are driven by the host, rather than each peer picking different times. It does not replay EDF4.1's wire-level sync records unchanged; it reconstructs target-native identity and authority at the object boundary.

This is a concrete example of why “spawn it on every peer” and “network it correctly” are not the same requirement. For the general authority distinction, see registered objects and local copies.

Evidence: source-side exact-build reverse engineering and design in edf41mother401.cpp (EDF4.1 R10 HF4 R9). No fresh two-peer game runtime or full encounter parity test was carried out for this documentation. The hex spacing and state durations belong to the examined source encounter, not a universal EDF6 map scale.

Source ragdoll filter is not identical to the target EAO default

The recovered EDF4.1 PanelBase uses two source ragdoll layer states: ordinary panels retain SHKT-authored layer 0; only COREPANEL is keyframed and receives layer 7. Layer 13 applies to a separate panel component, not the ragdoll. The studied EDF6 EventAnimationObject instead initially assigns its ragdoll layer 17. This is a distinct collision-model issue from the panel grid's online identity and from its trigger/delay lifecycle. See full Earth Eater panel layer comparison. Direct EDF6 gameplay validation of the source-aligned candidate remains pending.
