M035 / displayed Mission 41 — Titans navigation and airstrike boundary

UniversalMissions & ScriptingNavigationEDF 5EDF 6
Source-backed research / case study · Progression runtime-positive; navigation still open; R157 original runtime report cross-check (source file)

M035 contains two distinct problems that must not be merged into one status:

  1. the airstrike/progression counter defect was repaired and runtime-positive;
  2. Titan physical navigation through target geometry remains not fully runtime-closed.

Airstrike/progression repair — runtime-positive

The source-faithful counter root cause was:

  • shared wrapper __0014 allowed the first invocation into the body with threshold 1;
  • a local Func_55___Counter != 2 check then returned;
  • the second invocation was blocked permanently by the wrapper.

Correct source parity:

  • wrapper threshold becomes 2;
  • remove the redundant local Func_55 counter scaffold;
  • keep Func_62 at threshold 1.

R2 runtime artifact:

SHA-256 5f380c1542e8a102af73ca444cc5cd1e115f94f3d1703dc44ab471045cb7bc20

User runtime: the mission completed, so the progression blocker was fixed.

Titan navigation — separate unresolved layer

EDF5 source applies:

SetAiNavMesh_StraightMode(..., true)

to all three Titans. Source/target RMPA coordinates were already exact, yet on EDF6 target geometry the Titans could hit debris, block, jump or be launched.

R3A

The discriminator changed only initial navigation mode to StraightMode(false) for all three Titans, with no RMPA, route or factor changes.

Runtime result:

  • the approach route became good;
  • the following route4/circling phase still broke.

R3B and later route work

R3B attempted to reapply StraightMode(false) after each route4 assignment. It remained runtime-pending in the September handoff.

Later experiments established a more nuanced history:

  • one route2 configuration achieved PASS 3/3 Titans;
  • an older route3 variant failed 2/3;
  • the later intended R6 path using P001 -> P002 -> P003 and then returning to navmesh has no complete runtime PASS.

The exact M035 AC inherited into 1.0.6 comes from 1.0.5 and has SHA-256:

fc88b3ef6afb160e729b6edddefe1125da55b185925aa70490cb3238f7f9b2eb

Why 1.0.6 does not close M035

M035 was deliberately not overwritten by the 1.0.6 overlay. The BVM-parity work did not qualify the experimental Titan route, so the existing 1.0.5 file was preserved rather than regenerated. Preservation is not a PASS claim.

The exact-release ledger therefore records:

runtime_inherited = PARTIAL_PASS_ROUTE2_AND_FAIL_ROUTE3
runtime_exact_release = PENDING

Correct current status

  • airstrike/progression logic: runtime-positive / closed;
  • Titan route approach: partial positive evidence exists;
  • final route/circling behavior: still open;
  • exact finalized 1.0.6 M035: not runtime-qualified.

Do not describe M035 simply as "broken" or "fixed." Its control-flow blocker and its target-geometry/navigation problem have different evidence states.

4 October 2026 runtime clarification — rejected route4-only theory

The later retained observation narrowed the actual compatibility frontier: the R4 variant, with source-authored StraightMode(true) and an unchanged source-exact RMPA, could already fail at the first approach toward the base/mothership. The problem was therefore not limited to route4/circling.

The historical R3A candidate used StraightMode(false) for heavytank11/12/13 on initial approach; that phase was runtime-positive, while the later route4/circling segment still failed. The R3B follow-up reapplied false immediately after assigning route4 to all three Titans but never received a recorded runtime result. A proposed R5 route4 outer-arc-only RMPA edit was explicitly withdrawn, not validated.

This chronology strengthens the distinction between source-parity and target-engine pathfinding compatibility. The Func_55 count-to-two airstrike fix and the Func_62/Factor_AiMoveEndOrDie state must not be conflated with Titan geometry. No whole-mission Titan route PASS is established by these records.
