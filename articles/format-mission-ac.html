MISSION.AC — EDF6 mission AngelScript and runtime relationships

File FormatsSource-scoped referenceEDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

MISSION.AC is the documented EDF6 mission-script resource in the existing EDF mission corpus. It works alongside mission RMPA, mission-list data, localization, progression state and referenced assets. This page distinguishes its script role from the BVM bytecode used in the examined older mission sources.

What the resource controls

The source research treats EDF6 mission .AC as AngelScript-facing mission logic: event registration, engine calls and references to enemies, objects, groups and route/spawn resources. A mission is more than this one file. The owning mission's RMPA, resource lists and game state are separate dependencies.

The original EDF5/EDF4.1 MISSION.BVM sources encode compact VM instructions and custom-call identifiers. EDF6 native script APIs can express analogous behavior through methods, global functions or provided helpers, but not every BVM operation has a proven exposed AngelScript counterpart.

File identity and encoding in the studied EDF6 build

The shipped MISSION.AC resources examined in the EDF6 mission-source corpus are UTF-8 AngelScript source text with a BOM, rather than the EDF5/EDF4.1 MISSION.BVM compiled-VM format. Those files include the common header app:/Mission/AsCommon.h (stored as MISSION/ASCOMMON.H in the researched archive namespace).

This distinction affects how the game selects its executor. The native-loader research reports that the mission-script selector tests for an openable .ac file first and constructs an AngelScript executor if it finds one. It checks .bvm and constructs the older BVM executor only when opening the AC file fails. Once the AngelScript path is selected, a subsequent script-load failure does not trigger a second automatic BVM fallback in the examined call path.

These are observations from a particular EDF6 binary and source corpus, not a guarantee about every game build or external loader. The source also documents a separate special-case opening-script path, so the main mission selector should not be described as a universal rule for every script resource.

BVM custom calls are not AngelScript identifiers

The researched BVM byte 0xAC is the cuscall0 instruction; the following bytes may encode a little-endian custom-call number, such as 0x07D0 (2000). The numeric ID is an operand, not another bytecode opcode.

The corresponding EDF6 scripting interface must be checked semantically: argument types/order, target object, event timing and preconditions matter. A string-replacement table is not sufficient to establish parity.

For example, the audited BVM custom call 3450 has a native effect, but the reviewed EDF6 AngelScript interface did not expose an equivalent binding. The retained compatibility decision documents a specific accepted fidelity loss rather than silently pretending a different method is equivalent.

Event registration and external dependencies

An authored function body is not evidence that the mission actually registers or executes it. Existing source research distinguishes callback definitions, registration sites, scheduling conditions and runtime execution.

MISSION.RMPA keeps routes, shapes and spawn references; links to these resources must remain consistent with the script. Source-level closure or static translation can be complete while particular gameplay interactions remain unqualified.

Evidence boundaries

  • MISSION.AC here means the documented EDF6 mission script resource, not a general description of the AngelScript language or arbitrary user-created .ac files.
  • The game-engine API/call mapping is scoped to tested or statically inspected signatures.
  • Source compilation, file loading, event registration and mission-playthrough success are different validation stages.
