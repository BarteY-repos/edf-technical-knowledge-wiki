Vehicle boarding in EDF4.1, 5 and 6: seats, class masks and team gates

ConversionGame technical referencesGameplay & AIEDF 4.1EDF 5EDF 6
Technical reference · Static/source-backed community evidence; verified test results identified separately; no R117 native runtime tests

Evidence: Native VehicleBase/soldier analysis in the EDF Knowledge Hub, with build-scoped observations for EDF4.1 (steam-57aab039), EDF5 (steam-5d11de53) and EDF6 (steam-678ccb46). This is a comparative game-mechanics reference, not a guide to any custom vehicle plugin.

The same SGO concepts do not imply identical runtime structures

All three games recognize source concepts such as vehicle_riding_position, vehicle_weapon_setting, animation_model, ragdoll and vehicle_damage_effect. However, the in-memory structures and native seat authorization changed:

Seat table within VehicleBase data/count at +0x328/+0x338 data/count at +0x418/+0x428 seats at +0x608; count +0x618

These are memory-layout observations, not offsets to use indiscriminately in a different game version.

EDF4.1: a comparatively simple class-mask and distance test

CanRide checks that the human's game_object_vehicle_mask intersects the seat mask, that the seat has no rider, and that the human is close enough to the MAB-derived riding point. In the examined build the point-radius threshold includes an additional 0.5. Unlike EDF5/6, this particular CanRide path has no team gate and no second seat mask.

A separate FindSeat route chooses the first eligible seat and updates a per-seat change-bit field. The vehicle's team may follow the highest-numbered live occupied rider in the audited update loop. This is relevant to native AI/vehicle relation changes, not evidence of a universal player-vehicle command system.

EDF6: masks are class identities, not seat numbers

The inspected EDF6 game_object_vehicle_mask values use one bit for each infantry class:

Class Source mask bit
Ranger 1
Wing Diver 2
Fencer 4
Air Raider 8

A seat is eligible only if the intersection of all three masks is nonzero (human class mask, seat class mask and seat access mask). Occupancy is checked through the native weak rider control. Vehicles in team 5 have a special eligibility path; for a different team, an additional seat bit-7 permission can apply. The precise checks are in the source appendix; the team relationship is not equivalent to a bare “vehicle friendly/hostile” bool.

The EDF6 vehicle stores the rider at seat+0x260. Seat change bits are separate from occupancy and allow the native code to select boarding versus leaving sounds; hearing a boarding sound on a non-boarding action may therefore indicate a stale or misapplied seat-change state rather than an audio resource problem.

Displayed seat name and rider animation are different resources

In the audited EDF6 seat configuration, vehicle_riding_position[i][3] is a text-table key such as “Pilot Seat” or “Machine Gun - Left”. It is not the animation name. The rider's visual pose is selected using the seat locator's MAB parameters (Animation, DispCharacter) and the rider's CAS animation state.

This distinction matters when an imported vehicle shows the right seat label but the wrong character pose, or plays a boarding sound despite no actual rider transition.

Network ride events are distinct from physics ownership

EDF4.1 has explicit online vehicle ride/leave events with a seat index and sequence/counter; EDF5 likewise has online ride events. EDF6 retains event-driven ride state with its own native fields. A visible vehicle in the scene does not prove that a remote player has the same seat assignment or weapon-input authority. Cross-generation multiplayer parity therefore requires a seat-event and entity-owner check, not just geometry.
