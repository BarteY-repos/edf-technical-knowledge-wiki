EDF4.1 DLC CPK mounts: why identical object names require source-aware namespaces

ConversionFormats & ContainersCollision & PhysicsEDF 4.1EDF 6
Technical reference · Retained R9 source path rewriting and CPK mount identification; no new runtime compatibility test

EDF4.1's two DLC packs are independently mounted CRI CPK archives. Their object-resource namespace can contain the same filename with different contents, and EDF6 can already ship yet another resource under that name. Porting a DLC is therefore not merely copying a folder into Mods: every original reference in its missions and nested SGOs must resolve to the matching source pack's resource identity.

Native mounts and identification

The retained EDF4.1 source reader identifies the two original DLC products by their CPK-internal Steam application IDs, not by the arbitrary on-disk hash folder:

Original DLC mount CPK-internal app ID Dedicated port resource namespace
mp01:/ 410780 EDF41MP01
mp02:/ 411380 EDF41MP02

An EDF4.1 installation stores each as <EDF4.1>/DLC/<hash>/dlc.cpk. Since the hash is not the mount identity, the converter scans the CPK index for its app-ID directory. Within the archive the relative path is taken from the app-ID prefix; entries are looked up case-insensitively. If ExtractSize != FileSize, the retained reader decompresses that entry through CriLAYLA. This does not imply the complete CPK file is raw CriLAYLA.

One path in the DLC becomes two coordinated paths in EDF6

For an original reference:

mp01:/Object/GiantAnt04.sgo

the source-aware conversion uses:

runtime reference:  app:/Object/EDF41MP01/GiantAnt04.sgo
Mods file path:     OBJECT/EDF41MP01/GIANTANT04.SGO

For mp02: the namespace is EDF41MP02. The original spellings inside a runtime script/string are retained where semantic resolution uses them; the on-disk Mods destination is normalized to the loader's uppercase target convention. The rewrite() function also converts semicolon-delimited resource lists entry by entry; bulk string replacement would miss multi-resource fields.

Collisions are not theoretical. The source describes GiantAnt04.sgo, GiantBeeQueen02.sgo and DragonSmall401_HS.sgo as names overlapping with EDF6; AntHill301Large.sgo, GiantAnt04SB.sgo and ari_half.rab may also differ between the two EDF4.1 DLCs. Putting everything directly under app:/Object/ would silently select the wrong object for some mission paths.

Campaign shadow objects need their own identity

EDF6 already reuses several EDF4.1 story filenames for EDF5-descended variants. In particular the campaign's small-dragon SGO names DragonSmall401.sgo, RedSmallDragon.sgo, and YerrowSmallDragon.sgo must not overwrite native EDF6 equivalents. The source maps the original story object roots to private EDF41_ names (e.g. app:/Object/EDF41_DRAGONSMALL401.SGO), while related models, animations and source soldiers remain under the independent campaign source folder. Previously generated app:/Object/EDF41/<dragon>.sgo aliases are canonicalized to the same EDF41_ root target.

The mount rewrite must be shared by the object converter and the mission/BVM converter; otherwise the new object is deployed correctly but a mission script still asks for the original mount or a stock EDF6 object with the colliding name.

Boundaries

The implementation proves a coherent naming and extraction policy for the studied DLCs, not that every DLC mission, physics rig or weapon effect runs unchanged in EDF6. Do not infer a universal rule from the example GiantAnt04 for all unknown native packs; inspect the exact original CPK index, mount ID and resource consumers. See EDF4.1 BVM source conversion, resource identity and virtual paths and mod composition.
