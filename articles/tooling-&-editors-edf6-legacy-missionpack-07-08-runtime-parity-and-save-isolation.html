EDF6 MP07/MP08 mission loading, progression isolation and online-host evidence

EDF 6Missions & ScriptingMissions
Technical reference · September 3, 2026 user runtime observations + isolated offline parity-flip candidate; peer join not qualified

The core EDF6 ModeList loader is not demonstrated to have a hard five-pack limit. Legacy custom packs still depend on coherent namespace ownership, matching LIST/TXT resources, save namespaces, and historical mppp DLC-validation parity. The strongest retained direct game evidence tests MissionPack07 and MissionPack08 — not an arbitrary pack number.

Why physical pack parity mattered in the old plugin

The public historical mppp contract uses odd custom MissionPack IDs to validate against official MP01 and even custom IDs against MP02. Thus a safe legacy/import rebase shifts an entire provider by the same even delta rather than mixing identities:

Existing port:       MP03 MP04 MP05
Second provider:     MP03 MP04
Rebased provider:    MP07 MP08

It must rewrite more than filenames: ModeList game-mode names, MissionPackNN.MST save identities, pack ID field 9, LIST/TXT references, physical mission content roots and all embedded LIST row paths. Preserve unrelated display/icon identifiers unless an exact rule justifies changing them.

A newer authored BASE_OWNED MissionBundle uses a different ownership model. Do not claim all contemporary custom bundles require the historic parity/DLC donor scheme.

Later runtime evidence supersedes the early MP07 failure

An early MP07 black screen came from a confounded test fixture that copied only MISSION.AC, omitting the rest of the required mission subtree. The later R11/R12 tests copied the complete provider-owned subtree instead. The measured chronology is:

Runtime or structural test Retained result What it proves
MP03 control versus rebased MP07, same mission Both offline PASS Odd parity rebase can load real gameplay on the tested build
MP04 control versus rebased MP08 Both offline PASS Even parity rebase can also load gameplay
Progress recorded in MP08 vs MP04 Isolation PASS Save/progression namespaces did not alias in the tested case
Create online host/room for MP08 PASS Host-creation path accepted this pack ID
Two machines joining and starting rebased MP07/08 Not directly tested No multiplayer interop claim is warranted

Separate earlier two-player reports for MP03/04/05 do not supply missing MP07/08 peer proof. A successful host-creation UI step is not a peer-join test.

Do we need to modify mppp to add more packs?

The investigated public mppp v1.0.2 release advertises support for a third custom pack “or more.” The original ModeList loader also reads its row count dynamically. R13 runtime evidence further disproved a hard MP05 cutoff on the qualified environment. Neither fact proves arbitrary parity flips, save-key migration safety, public-room compatibility, or nonidentical mod compositions between peers.

The MP03 → MP06 parity-flip experiment remained pending

R17 built a tightly controlled candidate: clone a working full MP03 tree and all LIST/TXT companions to MP06, clone corresponding ModeList rows and MST namespace, and do not alter mppp.dll. It passed nine offline/integration gates including exact restore. No retained runtime PASS exists for this parity flip. The safe production policy therefore remained even-delta allocation (R16), despite the possibility that both-DLC ownership could make dense allocation workable.

Never silently renumber an already-published pack because saved progress is keyed to its physical namespace. A composer must preserve a persistent namespace lock and provide an explicit migration process if a policy ever changes.

Practical compatibility and deployment test order

For a legacy provider, establish in order: (1) original pack as control; (2) rebased pack with complete mission subtree, not just AC; (3) LIST/TXT/image and ModeList integrity; (4) save isolation; (5) online host creation; (6) actual second-peer join/start with identical generated composition. Stop after a failed gate rather than editing unrelated mission script logic.

The historical mppp deliberately limited public-room usage; custom peers should not be assumed to have compatible mods simply because a lobby is visible. Reusing a room-creation success to claim multiplayer interoperability would overstate the evidence.

See legacy namespace rebase contract, CONFIG three-way merge and current donor-free authored bundles.

Evidence boundary: R12/R13 historical user game runs, R17 static parity candidate. All such tests are version/environment-scoped and were not rerun for this wiki release.

Later authored-A2Z MP06 negative and MP07 complete offline PASS

A separate September 29–30 authored MissionBundle / A-to-Z lineage (not the historical R17 legacy-composer parity-flip fixture) actually observed 0xC0000094 at EDF.dll+0xDD2A9 when selecting physical MP06. The on-disk pack contained a valid one-mission LIST, but its resource request arrived before MissionMgr+0x14FD0 had a valid active-slot value. The loader therefore missed the exact requested LIST provider. The authored content additionally inherited odd MP03 source-mode semantics while physical MP06 was even. A request-identity routing fix plus transactional migration to physical MP07 closed both separate issues; the MP07 list then appeared in real EDF6 runtime. See the MP06 root-cause case study.

A further alias-free VFS revision initially reached the LIST but could not launch its mission due to a stale ./mods/MISSION/... row path. After correcting that path to ./Mods/.edf6ml/providers/p/..., a retained user-observed offline test completed the custom Golden-map mission with 10 GiantAnt01, reached Mission Cleared, and restored the test payload. This is a bounded runtime end-to-end proof for that authored MP07 setup, not proof of parity-flipped MP06 acceptance, of MP07/08 two-peer compatibility, or of arbitrary later builds. See alias-free LIST path and mission startup.
