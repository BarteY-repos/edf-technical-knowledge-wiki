Map container stack: MAC, MAPB, MAPO, FMB and FMEP

UniversalMaps & NavigationMapsEDF 5EDF 6
Source-backed research / case study · Runtime

At a glance

What it is: The map-container stack tells EDF which files and objects belong to a map and how the separate consumers locate them.

Where it fits: MAC is the envelope; MAPB/MAPO contribute registrations and placements; FMB/FMEP concern a specialized terrain path whose loader and rendering conditions have their own rules.

Important distinction: Offsets and row widths are generation- and profile-specific. A changed version number or an apparently valid table is not a complete conversion.

Cross-generation MAPO relayout: another record family

The EDF4.1 NW_HILLYCITY_LIGHT research additionally found an embedded MAPO layout with a 0x58→0x60 header and 44,213 object rows expanding 0x38→0x3C (+176,860 bytes). This is different from the 0x1C table-item family described below. It closes historical MAPO and outer-MAC byte size, not byte identity. See MAPO object-row relayout and whole-MAC size.

Evidence level: Reconciled binary/runtime evidence. Several rules are profile-specific; do not collapse the stack into a universal offset transform.

Structural conversion, not version patching

Implementation rule: MAC/MAPB/MAPO and terrain/field resources must be converted structurally. A loader-accepting version/header change is diagnostic evidence only.

MAPB

Observed native behavior: The reconciled record strides are:

  • T1: EDF5 56 bytes → EDF6 60 bytes;
  • T2: EDF5 68 bytes → EDF6 72 bytes.

For the current T1 rule, EDF6 inserts a zero dword at entry +0x20; the old source field at +0x20 moves to +0x24. An older note that placed the insertion itself at +0x24 is superseded. T2 grows by four zero bytes at the end of the record; relative parent/T1 references must be rebased to the target stride rather than copied numerically.

The measured Desert profile preserves its source record cardinality while changing the target layout; replacing the table with a donor map's counts is not conversion.

Known exception: These are measured record-layout rules, not permission to shift every subsequent map structure blindly.

MAPB registration strings can reference different resource roles (.mdx, .trb, .mosb, .fmep, etc.). The suffix identifies a role, not a generic byte-conversion recipe.

MAPO

Observed native behavior: The reconciled MAPO object-table element stride at the +0x08 table is 0x1C / 28 bytes. The old 8-byte-stride interpretation is superseded.

Implementation rule: Object identity, placement and collision binding must be kept explicit. Auxiliary-table validity alone is not proof of working floor collision or navigation.

FMB / FieldRender

Observed native behavior: FMB carries terrain/render/spatial data and can be parsed by EDF6 in qualified cases. Runtime hooks showed FieldRender::Initialize receiving decompressed FIELD data.

Known exception: The old statement “FMB is the floor-collision source” is too strong. Cases exist where FMB/FieldRender parses and renders while the collision symptom remains elsewhere.

EDF5 FMB passthrough has worked in specific shared/render-side profiles, but it is not a universal source-only FMB conversion rule.

Later native-variant census evidence also disproves a single fixed FMB config-table model: full HEIGEN uses 27 config rows and a string/resource trailer while directional ENKEI variants use 21 rows and file-local config-index remapping. See Native FMB tree, config variants and authoring boundary.

FMEP / field terrain

Critical boundary: Ordinary MDB models are not FMEP/FieldRender terrain.

FMEP is a map-field/terrain role referenced through the map stack. Model-material rules learned from ordinary static MDB assets must not be projected onto FMEP field chunks or their FieldRender configuration.

Do not assume: An MDB shader/material migration, even if runtime-positive for props or foliage, describes FMEP terrain serialization or field collision.

Resource-role consistency

Implementation rule: Validate the full chain:

MAC → MAPB registrations → MAPO/object placement → resource payload role → render/collision/NAV consumers

Do not fix one table in isolation and infer whole-map parity from successful loading.

Detailed standalone format references

For precise headers, table strides and validation, see MAPB binary record layout, FMB header and terrain tree and MAE weather binding. These cover different resource consumers and should not be mixed with ordinary MDB model shading.

Map RMPA versus mission RMPA: different conversion evidence

The historical CAVE501 map.rmpa cross-game research is a map-contained resource case, not the file layout for mission-owned waypoints, spawns and routes. It identified target-only content deltas and shape-record size/constant fields measured from native EDF6 reference assets. Those target values are not automatically derivable from a source EDF5 RMPA stream; copying them can reconstruct a qualified paired profile, but does not constitute a general source-only map-RMPA conversion law.

The old R6 ledger preserved partial quotations of a paired CAVE501 RMPA table, but the retained maintained rmpa_tool.py has now been recovered. It documents the CAVE501 and CAVE503 target profile constants and the actual writer/validator layout; see Map RMPA: measured binary structure and paired profiles.

This closes the sample-specific source-documentation gap for these two profiles without making up arbitrary-map constants. It does not prove that a generic map's source-only RMPA can be converted without paired target measurements, and it does not give complete standalone native paired files for fresh binary testing. Never substitute mission RMPA or MAE weather RMPA schemas.

FMEP external registration and MARC directory addressing

In the studied EDF6 FieldRender path, MAPB can name a .fmep while the runtime loader derives and looks up the sibling .fmb. The external FMB resource must be registered through the MAC's externals.sgo: having valid FMB bytes available on disk is not sufficient. The native MARC v5 reader uses a signed field-relative rel32 at MAC header +0x14 to the first 24-byte directory entry; each entry's +0x00 is another signed field-relative rel32 to its UTF-16 name. A measured 12-byte directory-base error produced a null name pointer after adding the fourth block. Source: original EDF6 EDF.dll read-site audit and modified-game diagnostic logs, not a runtime-qualified FMEP authoring system. See the native FMEP/DDS and loader evidence.
