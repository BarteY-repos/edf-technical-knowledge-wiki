Health

EDF4.1 enemy HP float32 calculation sequence

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-hp-same-steps

EDF 4.1 computes enemy health in the same steps and float32 order as EDF5 (../edf5/combat.md#hp-formula-modelist, #hp-float32-order): the level function D98E0 (EDF5 8ACC0, the same instruction order; no counterpart of EDF5's save byte +0x44 override) gives f = x x (L + (M - L) x row / (count - 1)) with the difficulty at [save+0x44], the row at [save+0x40] and the list at [save+0x110] (save object [CC84A0], config at [save+0xC0]); a class's activation handler then sets max HP +0x168 = current +0x16C = f / 10.0 (AB6790) x durability +0x160 x ModeList[mode][6][difficulty][3][0] x [1][players - 1], the player count at [save+0xA804] (read in GiantSpider's 215EF0, called from its slot 3 219240 with f from +0x25C). Offline, [3] and [1] are all 1, so offline HP alone = durability x level adjust x (L + (M - L) x t) / 10.

Basis: fn.py, set beside EDF5's code; ModeList from config.sgo (scratch modelist41.py); confirms motherships.md#edf41-difficulty-level (hajisensai) by a second class

Addresses (build-specific RVAs unless indicated): D98E0, 215EF0, 219240, AB6790, CC84A0

Shield Bearer online HP factor exception

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-shield-bearer-online-hp

EDF 4.1's Shield Bearers (AlienTrailer) take another online health factor than every other enemy: their HP setter 1D5010 (called through 1D34B0 from slot 3 1D75A0) multiplies f / 10 x durability by [rax + r10 + 0x38], ModeList[mode][6][difficulty][3][1] (the attack factor), where the other classes read +0x2C, value 3[0] (#edf41-hp-same-steps), then by value 1[players - 1] as usual. Online 3[1] is 1.5 on Easy and 2.4 on Normal and up against 3[0]'s 1.8 and 2.0 (file-formats.md#edf41-modelist-online-hp), so online Shield Bearers have x 1.2 the HP of the common rule from Normal up and x 0.83 on Easy; offline both are 1. The JP wiki's "x 1.2 more online" agrees in kind, but its example (four players 2.4 -> 3.6) adds where the code multiplies: 2.0 x 1.2 x 1.2 = 2.88 (file-formats.md#edf41-hp-formula-wiki).

Basis: fn.py 1D5010; the node offsets read as EDF5's (../edf5/combat.md#hp-formula-per-class: +0x2C = [3][0], +0x38 = [3][1]); online values by scratch File_Storage/Logs/catalog/modeprobe2.py edf41 1

Addresses (build-specific RVAs unless indicated): 1D5010, 1D34B0, 1D75A0, 1D50DC

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-kill-merit-durability

EDF Knowledge Hub record — original wording — expand (1,863 characters)

UfoRobo is born a flying ship and ObjectAction 0 turns it into a giant walking robot, one object with one handle (the scripts register durability events on it before and after). Body state machine (+0x15B0), 12 states: S0 flying idle, S1 small-gun volley, S2 medium gun, S3 the buster cannon (charge 300 frames, a shot every 31 frames for 600), S4 transforming (takes no damage: slot 10 2759F0), S5 falling (switches to robot form), S6 landing, S7 robot main state (choosing steps, turns, attacks; 278810), S8 one step or turn, S9 attacking, S10 dying (8-15 s), S11 wreck (deleted after 10 s). AI, 6 states: A1 flying circles 300-500 m from the target and 250 m above it facing it (yaw at most 0.01 rad per frame, speed command <= 90), then flies straight a while, with side slips; in S0 three timers run only while the target is in their range: small guns 180-720 frames (0-500 m), medium 300/s-480/s (150-800 m), buster 1800/s-3600/s (0-1000 m); A3 robot: in normal mode it turns first, then walks forward (2/3) or back (1/3); in approach mode it steps in or out by radius; turns pick the 45 / 90 / 180° clip by the target's bearing (thresholds 36° / 72° / 126°); an attack timer of 600/s-1800/s sends it to A5, which picks an entry of robo_attack_table whose distance and angle windows fit, all equally likely, and holds until the body is back in S7 (27A770). Motion: flying, the velocity moves 0.25 % a frame toward the command and the roll = clamp(-30 x yaw rate, ±0.9425) approaches it by 10 % a frame; the robot moves by the animation's root motion, rotated by the heading at the step's start, kept on the ground by a map ray, falling with -0.008 per frame when off it. ObjectAction: 0 transform if alive (also replayed when already a robot), 1 robot form at once with stand and approach mode, 2 approach mode only. s = level / 10. Sync state from +0x24F0.

EDF4.1 UfoRobo: attack state timing

Evidence: static · Build: steam-57aab039 · Fact ID: uforobo-attack-rhythm

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Host-side attack selection
  2. State duration and transitions
  3. Shot scheduling
EDF Knowledge Hub record — original wording — expand (1,577 characters)

UfoRobo's attack rhythm in detail: on entering A5 (host branch of 27A770) the AI picks the attack and switches the body straight to S9 (27AAE2 call 27E950(+0x15B0, 278C20, entry)), then each frame (27AB46..27ABD3) returns to A3 only once the body is back in S7; so during an attack A3 does not run, the attack timer does not count down and the legs' phase counters do not drop, and every attack is followed by 4-13 s of A3 (turns, steps, approach) at s = 2.35 (the timer is 600/s-1800/s frames, counted down in A3: 27A3D9 calls 271AB0). Explosion interception remains open

Bullet frame testing, map-stop ray and collision query filters

BulletMtSystem moves without query on skipped frames

Static. Bullet step 1697F0 integrates velocity +0x340 and acceleration +0x350 at 1/60 s from position +0x330. When query-enable byte +0x374 is zero, it only moves. Otherwise it builds swept AABB candidates from +0x360 to new position with extents +0x388 through world slot 0xF0 and calls 16A0B0; candidate filter EC970 splits stop query kind 0xB and hit query kind 0xA. Inactive core flags +0x2D8/+0x390 end the step early.

Stop kind 0xB tests map layers; hit kind 0xA tests actors

Static corrected collider filter. Candidate filter EC970 checks CollisionFilter [CC85A0]+8 via 5E73D0, passes collidables with direct owner, or those with key-1 property and swept AABB intersection. In the EDF4.1 layer matrix, query kind 0xB (layer 11) collides with map layers 13–17, whereas kind 0xA (layer 10) meets layers 5–8 and 12. Thus the former stops the projectile at scenery and the latter collects hit targets; translating these as one undifferentiated query loses the wall-blocking distinction.

Ray batch truncates bullet path at nearest map hit

Static. 16A0B0 prepares path +0x190→+0x1A0, ray result +0x1D8, and kind-0xB candidates. Ray job builder 16D7B0 casts only against those candidates (modes other than zero extend the ray 0.1). Hit before bullet limit +0x1B0 clamps end to hit and sets +0x2DA. Subsequent hit step 16A580 processes targets only before nearest key-2 special body; mode-zero bullet ends on stop or hit flags +0x2DA/+0x2DB through core flags +0x2D8/+0x2D9.

Staggered bullet collision checks sweep from last tested position

Static; scheduling intent inferred. Per-bullet job 169740 sets query byte +0x374: mode +0x200=1 always checks, initial mode-zero state uses frame-info field +4==0, and other mode-zero bullets check normally. Dispatch 16AFA0 updates sweep start +0x360 only on tested frames; skipped frames therefore leave a longer swept segment rather than a collision gap. Frame-info field +8 feeds +0x2D4 and scales mode-one damage. The frame-info producer was not read, so exact staggering assignment remains inferred.

Ten-node Verlet rope and actor-only strand casts

SpiderStringBase moves its head and snaps last node to a hit

Static. Base update slot 2 1A2100 advances frame counter +0x538, dispatches bullet core at web +0xD0 via 16AFA0, mirrors its matrix to web render transform, and checks core hit list +0x138. A collision sticks the last rope node through 1A2C80 and invokes web hit slot 11 with that node. The bullet's normal map query runs in its separate system; this base rope routine does not make strand nodes collide with terrain.

Head is a normal mode-zero bullet stopped by a map ray

Static. The web constructor/updates do not override core bullet mode +0x200, stagger counter +0x370 or query enable +0x374. Therefore its flying head participates in the mode-zero bullet's swept map-stop test and ends when the first scenery hit blocks the head. This head behavior differs from the rope segments, which are tested with a different collision filter.

Verlet rope springs have no terrain-node collision

Static. Ten 0x70-byte rope nodes at web +0x520 (count +0x530) integrate position using prior-position delta times damping +0x20 and gravity +0x420×(1/60)². Neighbor nodes are pulled together by distance-error factors 0.01 or 0.1 under flag +0x3A8, halved; no rest length is enforced. Endpoint zero snaps to owner anchor and endpoint nine to bullet head; stuck nodes use 1A2DE0. No segment-node update queries map geometry, so the strand can straighten through walls even when the head stopped at a wall.

Strand candidate collector filters kind 0xA and excludes friendly team

Static. SpiderStringBase constructor 1A1AD0 creates a hit_query::TargetCollector at +0x4E0 with collision kind 0xA, registers web callback 1A1F80, and keeps only layer-eligible bodies, including key-1 property when needed. The callback excludes the web owner and friendly objects by team relation before testing special key-2 bodies. As kind 0xA does not meet map layers 13/15/17, terrain is absent from the strand's candidate set.

Each rope segment tests actors every fourth frame

Static. For segment index i, base update 1A2100 tests only when (i & 3)==(web+0x538 & 3) and neither endpoint is stuck. It queries an AABB bounding segment i→i+1 through world slot 0xF0 into web candidate list +0x4E0. If candidates exist, a sphere of radius +0x32C is linearly cast with ED2C0 against that list only, producing closest contact. The quarter-rate schedule and actor-only filter explain how the moving strand can damage across an occluding wall without registering that wall as a segment collision.

Strand hit, web reel, captured soldier motion and expiry

Held soldier moves toward web anchor at six times gap per second

Why rope strands can damage behind walls — source inference only

Unverified gameplay conclusion from static collision paths. Sixty-frame staggered retarget to nearest hostile object

Evidence: static · Fact ID: edf41-target-retarget-step

GameObjectBase per-frame route 28D700 increments its step counter +0x2A0 and retargets every 60 updates (cmp ecx, 0x3c at 28D805), rather than reading an editable interval as in EDF5/6. Initial count is rand(60) from object RNG +0x210, staggering different actors. Its inline picker walks TeamManager's hostile team candidates through 2C9920 and GameObjectBase::EnumNearObjectCallback (vtable A9CC00), minimizing distance from FLT_MAX. There is no base range cutoff or line-of-sight test in this callback. Target pointer lives at +0x2A8/+0x2B0; it clears when none is found, then calls object slot 22.

Candidate state exclusion and encounter-dependent weight

Evidence: static · Fact ID: edf41-target-pick-callback

Callback 28F070 skips a candidate when its state byte +0x204 has any bit except bit 1 set. Once the picker has entered encounter state +0x260, it multiplies candidate distance by candidate weight +0x24C. Unlike the EDF5/6 callbacks inspected by the source, this base EDF4.1 picker has no special squad-leader bias. This is a weighted nearest-target routine, not a proof that every enemy subclass delegates to it unchanged.

Encounter notice and teammate report radii

Evidence: static · Fact ID: edf41-encounter-step

If object encounter flag +0x260 is zero, a target exists, and local notice radius +0x240 exceeds 0.01, native proximity check 28D910 may invoke SetEncount 28EEC0 (sets flag to 1 and calls slot 15). Under object flag +0x1E8 bit 0x400, 28EE60 also notifies same-team objects within report radius +0x244. game_object_encount initializes radii at +0x240/+0x244, or zero when the setting is absent; weight/divisor fields +0x248/+0x24C start at 1.0. Hence mission native SetEncountReportRadius changes encounter-notice distance and notification radius, not the base picker's global search reach.
