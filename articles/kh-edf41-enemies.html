Health

EDF4.1 enemy HP float32 calculation sequence

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-hp-same-steps

EDF 4.1 computes enemy health in the same steps and float32 order as EDF5 (../edf5/combat.md#hp-formula-modelist, #hp-float32-order): the level function D98E0 (EDF5 8ACC0, the same instruction order; no counterpart of EDF5's save byte +0x44 override) gives f = x x (L + (M - L) x row / (count - 1)) with the difficulty at [save+0x44], the row at [save+0x40] and the list at [save+0x110] (save object [CC84A0], config at [save+0xC0]); a class's activation handler then sets max HP +0x168 = current +0x16C = f / 10.0 (AB6790) x durability +0x160 x ModeList[mode][6][difficulty][3][0] x [1][players - 1], the player count at [save+0xA804] (read in GiantSpider's 215EF0, called from its slot 3 219240 with f from +0x25C). Offline, [3] and [1] are all 1, so offline HP alone = durability x level adjust x (L + (M - L) x t) / 10.

Basis: fn.py, set beside EDF5's code; ModeList from config.sgo (scratch modelist41.py); confirms motherships.md#edf41-difficulty-level (hajisensai) by a second class

Addresses (build-specific RVAs unless indicated): D98E0, 215EF0, 219240, AB6790, CC84A0

Shield Bearer online HP factor exception

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-shield-bearer-online-hp

EDF 4.1's Shield Bearers (AlienTrailer) take another online health factor than every other enemy: their HP setter 1D5010 (called through 1D34B0 from slot 3 1D75A0) multiplies f / 10 x durability by [rax + r10 + 0x38], ModeList[mode][6][difficulty][3][1] (the attack factor), where the other classes read +0x2C, value 3[0] (#edf41-hp-same-steps), then by value 1[players - 1] as usual. Online 3[1] is 1.5 on Easy and 2.4 on Normal and up against 3[0]'s 1.8 and 2.0 (file-formats.md#edf41-modelist-online-hp), so online Shield Bearers have x 1.2 the HP of the common rule from Normal up and x 0.83 on Easy; offline both are 1. The JP wiki's "x 1.2 more online" agrees in kind, but its example (four players 2.4 -> 3.6) adds where the code multiplies: 2.0 x 1.2 x 1.2 = 2.88 (file-formats.md#edf41-hp-formula-wiki).

Basis: fn.py 1D5010; the node offsets read as EDF5's (../edf5/combat.md#hp-formula-per-class: +0x2C = [3][0], +0x38 = [3][1]); online values by scratch File_Storage/Logs/catalog/modeprobe2.py edf41 1

Addresses (build-specific RVAs unless indicated): 1D5010, 1D34B0, 1D75A0, 1D50DC

EDF4.1 kill merit equals object durability

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-kill-merit-durability

A kill's merit in EDF 4.1 is the object's game_object_durability alone: in the damage and death function 28E1F0, the object's +0x160 (that value, read by the GameObjectBase constructor 28CBD0 at 28CEFC, stored at 28CFCA, 100.0 when the SGO lacks it) is added (28E72D-28E73C) to the merit total +0x30 of every team whose relation to the object's team (+0x180; -1 credits nobody) is 2, the teams read through the global CC8510 (stride 0x38, count +0x48): EDF5's loop (../edf5/combat.md#kill-merit-team-credit) inlined, without its multiplier. EDF41.exe holds no game_object_destroy_score_adjust key at all (its game_object_* keys: drop_item, level_adjust, camera_setting, vehicle_mask, formation, talk_setting, encount, durability, ai_route_update_distance, kill_counter), so the value 1 every EDF 4.1 SGO carries is unread. No integer 1500 compare as EDF5's merit cut (../edf5/combat.md#credit-reload-merit-compression) was found; the one float 1500 is used in 652870; the call-in reload itself was not read.

Basis: EDF5's hostile-team test bytes (83 3C 91 02) found once in EDF41.exe; fn.py reads; the module's UTF-16 keys listed (scratch File_Storage/Logs/catalog/exe_find.py u16 game_object_)

Unexplained Japanese wiki Deroy HP bases

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-deroy-no-hp-factor

No factor in EDF41.exe explains the JP wiki's Deroy HP bases (medium 1200 and large 2000 against deiroi401 900 and deiroi401l 1500, both x 4/3; #edf41-wiki-merit-table): the module holds no float 4/3 (1.3333334); the Deiroi constructor 1DCB80 (RTTI .?AVDeiroi@@, vtable A972C0, NetworkObject vtable A97230 at +0xB0) sets no durability factor; the only 0.75 in the Deroy code is in the leg setup 1E4B60, which sums its parts' durabilities (each part's +0x390) into the leg's +0x58 and stores 0.75 at +0x80 (meaning not read; the parts are 70 + 260 + joints of 1, nowhere near 300 or 500). So the wiki's figure is a measurement or an error; an in-game count of hits would settle it.

EDF4.1 UfoRobo: flying-to-walking state change

Evidence: static · Build: steam-57aab039 · Fact ID: uforobo-states-ai

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Initial ship and ObjectAction states
  2. Transformation to walking robot
  3. AI movement and action dispatch
Complete original research record — expand (1,863 characters)

UfoRobo is born a flying ship and ObjectAction 0 turns it into a giant walking robot, one object with one handle (the scripts register durability events on it before and after). Body state machine (+0x15B0), 12 states: S0 flying idle, S1 small-gun volley, S2 medium gun, S3 the buster cannon (charge 300 frames, a shot every 31 frames for 600), S4 transforming (takes no damage: slot 10 2759F0), S5 falling (switches to robot form), S6 landing, S7 robot main state (choosing steps, turns, attacks; 278810), S8 one step or turn, S9 attacking, S10 dying (8-15 s), S11 wreck (deleted after 10 s). AI, 6 states: A1 flying circles 300-500 m from the target and 250 m above it facing it (yaw at most 0.01 rad per frame, speed command <= 90), then flies straight a while, with side slips; in S0 three timers run only while the target is in their range: small guns 180-720 frames (0-500 m), medium 300/s-480/s (150-800 m), buster 1800/s-3600/s (0-1000 m); A3 robot: in normal mode it turns first, then walks forward (2/3) or back (1/3); in approach mode it steps in or out by radius; turns pick the 45 / 90 / 180° clip by the target's bearing (thresholds 36° / 72° / 126°); an attack timer of 600/s-1800/s sends it to A5, which picks an entry of robo_attack_table whose distance and angle windows fit, all equally likely, and holds until the body is back in S7 (27A770). Motion: flying, the velocity moves 0.25 % a frame toward the command and the roll = clamp(-30 x yaw rate, ±0.9425) approaches it by 10 % a frame; the robot moves by the animation's root motion, rotated by the heading at the step's start, kept on the ground by a map ray, falling with -0.008 per frame when off it. ObjectAction: 0 transform if alive (also replayed when already a robot), 1 robot form at once with stand and approach mode, 2 approach mode only. s = level / 10. Sync state from +0x24F0.

EDF4.1 UfoRobo: attack state timing

Evidence: static · Build: steam-57aab039 · Fact ID: uforobo-attack-rhythm

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Host-side attack selection
  2. State duration and transitions
  3. Shot scheduling
Complete original research record — expand (1,577 characters)

UfoRobo's attack rhythm in detail: on entering A5 (host branch of 27A770) the AI picks the attack and switches the body straight to S9 (27AAE2 call 27E950(+0x15B0, 278C20, entry)), then each frame (27AB46..27ABD3) returns to A3 only once the body is back in S7; so during an attack A3 does not run, the attack timer does not count down and the legs' phase counters do not drop, and every attack is followed by 4-13 s of A3 (turns, steps, approach) at s = 2.35 (the timer is 600/s-1800/s frames, counted down in A3: 27A3D9 calls 271AB0). The timer 271AB0 fires when the value before the decrement is <= 0, and always checks its distance window (the attack timer passes the window 0-1000 and 0). In approach mode (+0x1538) the sideways move runs only once phases 1 and 2 are used up, and when used up with its interval <= 0 the side move and the parameters are rerolled together (27A2DF..27A325); the legs are 27A180's host branch (approach and normal paths). Commands keep their raw values (cruise ±90, side ±22.5, approach ±1).
