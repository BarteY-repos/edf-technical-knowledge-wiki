Five effect texture archive families

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-effect-textures

Effect textures come from five .rab archives: basic.rab and light.rab (EffectGenUtil), app:/Effect/Decal.rab (the decal manager, read in 3D7680), app:/Effect/spider.rab (read by 292740, the web code that also reads spider_net_* keys) and app:/Effect/Hud.rab. Code names textures by file name, e.g. 火炎_01.dds (flame), 煙_01.dds (smoke), spark_01.dds, ParticleAlpha_1-6.dds, Particle1_k.dds, 稲妻_01.dds (lightning), 噴射煙_01.dds (exhaust), マズルフラッシュ01.dds (muzzle flash); a few use a full path such as APP:\EFFECT\BASIC.RAB@煙_01.DDS. So replacing a texture inside basic.rab changes every effect that names it; shapes, counts and colors stay in code.

Basis: exe_strfind on Effect/ and .dds; the loaders' references read with fn.py

Addresses (build-specific RVAs unless indicated): 3D7680, 292740

EDF5 generated effects, limiter table and pool caps

These observations come from source-contributor native reads and class census, not a fresh particle stress test. Unlike EDF6 EFS, the examined EDF5 system constructs effect InitParams in code.

Effects initialized by classes, not EDF6 EFS files

Static. EDF5's EffectGenUtil members and individual effect classes populate ParticleObject/LineParticleObject InitParam fields in native code. Textures reside in .rab archives and SGO keys name effect classes, but the inspected EDF5.exe RTTI census found no efs or atf class namespace corresponding to EDF6's effect runtime. This resolves the source's earlier ESB-format uncertainty for the audited EDF5 effect path; absence of those RTTI symbols is not proof that arbitrary external mods cannot add a different system.

EffectLimitter shared count table and non-evicting admission

Static constructors and destructors. EffectLimitter<T> is an 8-byte embedded base (kind int, weight int) used by ModelDebris, HumanoidPartsBreak, ParticleObject, LineParticleObject, GlassClashEffect and StencilLight, without a separate vtable or method body. All kinds share integer counts at 124DD78; kind 0 is uncounted. A constructor adds its weight only if the resulting count remains within cap; otherwise it clears the new instance's weight and destroys that new effect immediately (617B30). On normal destruction weight is subtracted. Full pools refuse incoming instances rather than recycling an older live effect.

Effect pool kinds and counted weights

Static. Kind 1 counts ParticleObject and LineParticleObject together by emitted particle count (InitParam +0x30 or line +0x34, possibly extra randomized count with flag +0x80). Their InitParams set kind/cap at +0x1B0/+0x1B4 or line +0x160/+0x164, defaulting to kind 1 and cap 65535; one line hit effect limits its own spawn to 256. Kind 2 had no fixed user identified in the bounded search. Kind 3 StencilLight cap 2048; 4 GlassClashEffect cap 100; 5 ModelDebris cap 400; 6 HumanoidPartsBreak cap 50 or 10 when [125AB30]+0x40 is set. Kinds 3–6 normally weigh 1. A part-break InitParam option can count a break without running the usual cap check, so apparent count limits are not all enforced at one universal callsite.

ModelDebris 400-piece cap at callers and constructor

Static. Spawner 1C1650 clips a requested piece count to the remaining room below 400 before creating bodies; 1C1EB0 also reads the count and 23E370 skips spawning at 400. Native immediate 0x190 appears at 1C0502, 1C16D9, 1C16E0, 23F4C1; adjusting only the constructor would leave other guards. The constructor has an additional rejection when helper 614CE0 returns above 300.0 with camera and 50.0 as inputs, possibly a distance cutoff (unverified). This source map is not a tested safe procedure for raising caps.

Humanoid limb regrowth and visible particle shell

Colonist SGO part delay and splash descriptor

Static sample OBJECT/E503_FROG_SG.SGO. humanoid_base_parts_config contains part name/parent plus values; in the cited Colonist the third value is 50 for limbs and 300 for head (interpreted as probable HP), and the eighth is regrowth delay: 900 frames (15 seconds at 60 FPS) for eight limb parts, −1 for body/head (never regrow). body_revive_effect names HumanoidPartsReviveEffect_Splash with texture APP:/EFFECT/BASIC.RAB@再生01.dds and color [1,2,1.5,1]; body_break_effect names HumanoidPartsBreakEffect_Blood. These row positions are from that SGO, not a census proving identical per-part values for every humanoid.

Broken-state delay, living owner and intact parent gates

Static. Broken state update 245150 switches part +0x118's state machine to regrowth 245220 only when delay +0xA4 is positive and elapsed state frames meet it, the humanoid owner remains alive (HP field in the owner chain above 0), and parent part 2411D0 is not broken (parent +0xB8 lacks bit 0x1000000). A dead Colonist does not regrow limbs; a broken forearm waits for the upper arm. Delay is based on the state's frame counter, not a general wall-clock timer shared by every body part.

Regrowth state 245220, scale and HP restoration

Static state logic. At entry, part scale +0xC0=1 and revival spray begins. Over state-time t (probably seconds; exact clock mapping inferred), for t<0.5 scale is 1−2t while hidden; for 0.5≤t<1.5 shown-while-broken bit 0x8000000 is set and scale grows as t−0.5 from 0 to 1. At t≥1.5, current HP +0x98 restores to max +0x9C, broken bit 0x1000000 clears, limb ragdoll bodies re-enable, and state returns to normal 245140. Scale is clamped above 0.001; exit clears show bit and sends stop byte +0xC8 to the spray.

Part bone-matrix scale pass before model update

Static. 2440C0, called by parts-manager step 242BF0 before model matrix refresh, iterates 16-byte part entries in [manager+8]+0x488 (count +0x498). If part +0xC0<0.999, it scales the three axis rows of bone matrix [part+0xD0] by that factor. This makes a limb grow from its joint during the visible one-second regrowth, while child-bone follow-through is inferred. The pass can be skipped under manager +0x24C and step mode conditions tied to [125AB30]+0x40.

Broken/hidden/regrowing mesh bits

Static. A limb part renders when status +0xB8 contains neither broken 0x1000000 nor hidden 0x4000000, or explicitly contains regrowing-show 0x8000000. Bit 0x2000000 caches the last shown state. On change, 2429B0 iterates named meshes in the part's 32-byte array at +0x60 (end +0x70), calling 3AF5D0 to queue each mesh visibility change. This decouples visible regrowth from the still-broken collision state.

HumanoidPartsReviveEffect_Splash particle emitter and shape placement

Static class/factory read. HumanoidPartsReviveEffect_Splash (vtable EA3DE8, base HumanoidPartsAttachEffectBase, factory EA3EB8, constructor 23FCB0) is a 0x400-byte particle-emitter object, not a replacement limb model. Its emitter is at +0xE0 and uses SGO texture 再生01, starting color [1,2,1.5,1] and ending at the same RGB with alpha zero (values over 1 create a bright green-cyan effect). Placement helper 23E160 uses bone and collision shape: shape type 4 produces a segment between points, 1/2 an axis-times-length, and 0 a point. Remaining constant effects were not decoded.

Splash particle count, timer and cleanup

Static. Update 23FFE0 follows the limb each frame and sets emission to min(180,64×k), where k combines +0x3F8 scaling (default 1) and a 300-frame lifetime fade (+0x3F0/+0x3F4). When its timer expires or regrowth exit sets stop byte +0xC8, it clears emission +0x190 but remains until live particle count +0x2E0 reaches zero; then 617B30 removes it. Thus the glowing regeneration “shell” is a temporary cloud around the independently scaling bone, not a mesh grown by the particle factory.

Weather effect script natives and mission census

BVM weather calls 5100–5103 and fade call 5150

Static BVM native dispatcher tracing. EDF5 mission scripts invoke custom calls 5100 SetEffectSnow (129BB0→12DA70→1AA9F0), 5101 SetEffectRain (129D40→12DCD0→1A73A0), 5102 SetEffectDust (129EA0→12DF30→1A61D0) and 5103 SetEffectFog (129FC0→12E190→1A4C30, known fullscreen fog class); script wrappers include SceneEffect_Snow/Rain/RainEx/FugitiveDust/Fog. As one-at-a-time decal-style effects, a later instance replaces an earlier one. Call 5150 (12A0E0) sends message 0x3000 containing value and seconds to objects in the manager's two lists, providing effect fade. Most callee class names are inferred by call order; only the specific fog constructor was identified.

Fifteen EDF5 mission scripts with weather effects

Static disassembled BVM census. Fifteen examined mission scripts begin a weather effect: ten start rain (eleven calls, usually cloudy2 except one sunset), three snow (two cloudy2, one cloudy), one dust (evening), and two fog (cloudy). Counts of scripts differ from number of weather calls because a mission can change effects. In M026, a later event fades rain to zero over 120 seconds via call 5150, waits 120 seconds, starts snow and fades it to 0.51 over 120 seconds. The mission-wide scan is source-corpus analysis, not a runtime weather transition test; backdrop/weather profile and spawned effect are separate systems.

Xgl graphics resource ownership versus EDF6

Engine SmartPtr is not EDF6 std::shared_ptr

Static RTTI. EDF5 uses the xgl::gs Direct3D 11 layer (including xgl::gs::Device vtable EDE798 and shader templates for ID3D11 pixel/vertex shaders at E97058/E97078), with similar class names to EDF6. But EDF5 stores resources in custom sgs::ut::SmartPtr<T,DefaultDeleter<T>>, while EDF6 uses std::shared_ptr (visible in resource-destruction RTTI). Therefore matching class names do not make resource-pointer ABI layouts or calls interchangeable across games; EDF4.1 follows EDF5's ownership convention in this comparison.
