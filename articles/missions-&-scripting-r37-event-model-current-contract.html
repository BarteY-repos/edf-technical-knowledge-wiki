Mission event model: exact registration and scheduler observations

UniversalMissions & ScriptingScriptingEDF 5EDF 6
Source-backed research / case study · Reference

Evidence level: Historical reconciled source; not automatically current authority. Check newer domain-specific findings.

Reachability first

Old engines scanned every decompiled function region and counted dead compiler-generated Func_N registration branches. Exact44 proves the correction: 2233 raw source RegisterEvent calls → 2214 reachable source registrations = 2214 official internal_CreateEvent calls. Reachability starts at Main and follows helper/wrapper calls plus RegisterEvent target edges. Ordinary named/export-like helpers must still be preserved even when not internally called.

One event state per unique target handler

A source target may be registered repeatedly with different factors. All such registrations share one target event state/wrapper. Across exact44: 2214 reachable registrations, 2106 unique reachable targets, official MAX_EVENT_ID sum 2106. R37 allocates IDs once per unique target in first-registration order. Sparse Func_N numbers are not event IDs.

multi → EVENT_TYPE is binary-confirmed

EDF5 and EDF6 BVM schedulers treat registration field multi == 1 as “append every ready registration”; otherwise they select one ready registration with greatest delay. EDF6 AngelScript uses EVENT_TYPE_SYNC=0, EVENT_TYPE_ASYNC=1; its scheduler sorts by delay and ASYNC appends all ready events while SYNC keeps one greatest-delay ready event. Therefore the source-faithful translation is multi == 1 → EVENT_TYPE_ASYNC, otherwise EVENT_TYPE_SYNC. Do not use multi != 0; runtime tests equality to 1.

Shipping raw census: 5193 registrations = 4619 multi0 + 574 multi1. Reachable shipping graph: 5112 = 4540 multi0 + 572 multi1. Exact44 reachable: 2214 = 1993 SYNC + 221 ASYNC. Official ports M015/M016/M024/M035 intentionally differ in EventType totals; after binary proof these are port-level authoring deviations, not a reason to alter source semantics.

Event/factor corrections

The former M041 “factor before RegisterEvent” blocker is resolved as a narrow compiler idiom: an exact pre-registration 9000 pattern belongs to the body as Wait, not to the child factor set. M029 remains a high-level normalization case involving empty relay handlers; treat it as equivalent graph normalization, not gameplay loss.

Current factor meanings include: 9201 Factor_ObjectDestroy, 9202 Factor_ObjectEncount, 9300 Factor_AiMoveEnd, 9301 Factor_AiMoveEndOrDie, 9116 Factor_GroupObjectCount, 9117 Factor_GroupObjectEncount, 9205 Factor_RideVehicle. Never re-merge 9201/9202.

Invocation policy, re-arm cycles and counters

Later native/source event reconciliation makes the re-arm/counter model explicit without replacing the recovered R37 target-state identity:

  • once — ordinary single-invocation policy;
  • repeat — re-armable; no counter-threshold guard, matching recovered ENABLED=0 repeat handlers;
  • nth — shared target counter with an exact m_counter != N guard before invocation.

One generated target Event still owns one stable event state/counter even when several registrations point at it. This preserves the recovered native/source rule that repeated registrations share target state rather than creating independent hidden event states.

Reachable cycles such as Start -> A -> B -> A are representable when the involved events use an explicit re-arm policy. Direct self-registration and Start/Main re-entry remain fail-closed rather than being silently normalized into loops.

ASYNC wrapper boundary: a generated ASYNC event does not execute the SYNC WaitVoice / GetTalkers / game-thread↔voice-thread handshake. Do not copy the SYNC wrapper shell merely because the event body is otherwise similar.

Registration-owned factors and join semantics

R36R39 promotes incoming edges to first-class Event Registrations. The target Event still owns the handler/state/counter, while each Registration owns its own Factor set, delay and check mode.

This closes the common fan-in cases without inventing a second event system:

  • multiple once registrations are source-backed OR fan-in;
  • repeat executes on every qualifying invocation;
  • nth is a shared-counter join over the target event state;
  • Factor AND/OR applies inside one Registration.

Do not assume: factors on separate Registrations form one cross-edge AND expression. Arbitrary cross-registration Factor AND is not established by the retained evidence and remains fail-closed.

The older R36R38 note that factors were target-owned is therefore historical only; R36R39 supersedes that temporary limitation with edge-owned registrations while preserving one target handler/state/counter.
