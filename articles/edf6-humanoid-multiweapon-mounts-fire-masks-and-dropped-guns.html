EDF6 humanoids: weapon slots, fire-mask messages and dropped guns

EDF 6Game technical referencesGameplay & AI
Technical reference · Native-data and static code observations; no new in-game runtime test

Colonists, Martians, Venus variants and other humanoid-like enemies do not necessarily carry a single hard-wired gun. In the analyzed EDF6 data and runtime, weapons can be independent scene objects and, for newer families, independent child slots under the owning humanoid.

Weapon ownership: single-gun example

The Humanoid_Basic (Colonist/Frog) constructor reads weapon from its object SGO, creates a separate gun object and attaches it to a weapon_node such as arms_r. The part named by weapon_constraint_parts is looked up in the owner's body/part table. The owning humanoid's +0x1120 list contains weapon weak-reference rows and +0x1130 is its count in the scoped build.

The identified gun-family types include HumanoidWeaponBase, HumanoidWeapon_Basic and HumanoidWeapon_Heavy. Their own SGO settings and bullet factory determine firing; the object is not simply a muzzle mesh on the humanoid.

Multiweapon SGO records

The humanoid_base_weapon_ex.list field contains independently configured child entries with:

Field Role in the examined object model
object Child weapon/shield object
node Model attachment / bone node
constraint_parts Logical body-part binding resolved against humanoid_base_parts_config
Rotation data Attachment orientation

Observed stock families include E616_VENUS*, E664_ARMOR_VENUS*, E601_MARTIAN*, E661_MARTIAN_LEADER* and E602_BERSERKER*. A Venus variant can mix two weapon children with two shield children. The important distinction: constraint_parts is a logical body-part reference, not automatically the name of an Havok constraint or a SoftBody-only special field.

Which child actually fires?

A native per-slot fire mask is sent through object message type 0x11 in the examined parent humanoid logic. The receiving dispatch fires the child slots indicated by the mask. Thus a two-gun humanoid can fire left, right or both children without changing the weapon classes. Relevant read sites in the one surveyed binary: message construction near RVA 0x4716BF / 0x4716D6 and reception near 0x4740B0.

This is a static message-path observation, not a completed online replay test. Do not claim that arbitrary simultaneous firing across peer clients was proven by this disassembly alone.

Why weapons fall off

The gun's enabled state is updated from its associated body part. On a transition to disabled, the original object code hides the in-hand weapon and can create a separate dropped gun scene object with its own model and ragdoll. In an online session the owning side also sends a drop counter/event; other peers can create their own drop using that sequence. The inspected HumanoidWeaponBase::Drop object survives 600 frames (10 s at 60 Hz), with physics/presentation; it has no recorded player pickup behavior.

An isolated source investigation found no universal "enemy dies, always drop gun" shortcut: the observed event originates from the relevant part's loss of the enabled condition. Therefore don't treat a dropped model, a recoverable player weapon item and a mission ItemDrop packet as equivalent things.

Evidence boundaries

fire_setting indices and several body-part byte interpretations were partly inferred from observed stock values and instructions. The source has stronger confirmation for the child-object ownership, 0x11 dispatch, weak-reference handling and drop creation. These offsets are not stable cross-build public API addresses.
