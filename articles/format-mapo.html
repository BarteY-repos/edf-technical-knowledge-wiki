MAPO — map-object records, placements and collision references

File FormatsSource-scoped referenceEDF 4.1EDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: MAPO contains map-related object records. It is one part of a larger map system, not a complete standalone scene or a mesh format.

Where it fits: MAPB registrations, MAPO object data, rendered models, collision and navigation are related but distinct pieces of a map.

Important distinction: Different examined MAPO profiles have different record widths; do not reuse one layout for every game and map.

MAPO's role in a map

The reconciled map hierarchy includes MAC resources, MAPB registration records, MAPO-related object data, and separately loaded object/terrain/collision assets. A MAPO row must be interpreted as part of this resource and placement graph, not simply as a standalone mesh record.

The measured record families are not interchangeable

  • A reconciled MAPO auxiliary object-table element stride at the +0x08 table is 0x1C (28 bytes). An older 8-byte interpretation was superseded.
  • Separate original EDF4.1 NW_HILLYCITY_LIGHT research identified an embedded MAPO profile with a header growing from 0x58 to 0x60 and 44,213 object rows growing from 0x38 to 0x3C in a studied cross-generation relayout.

These refer to different record families. The 44,213-row result closed a measured byte-size difference; it did not establish byte identity or a universal MAPO transform.

EDF6 map.mapo: measured header tables

The native EDF6 map-loader source describes a map.mapo profile whose header offsets are relative to the beginning of MAPO, while offsets within an entry are relative to that entry. The following fields come from the source's mapb-mapo-layout record and its reported fixup at 11FE90 for the studied game build:

MAPO header offsets Referenced structure
+0x08 / +0x0C Per-placement entries, 0x1C bytes each, with count matching placement records
+0x10 / +0x14 (int, int, float) record array
+0x20 / +0x24 0x3C-byte object structures for non-.fmep entries
+0x28 / +0x2C Self-relative 32-bit pointers into those object structures
+0x30 through +0x44 Vector arrays, including a reported color-palette role
+0x48 / +0x4C UTF-16 string pool, sorted and deduplicated in the observed maps
+0x50 / +0x54 Named entries of 0x0C bytes
+0x58 / +0x5C 0x0C-byte records containing nested lists

Placement-linked entry (0x1C bytes)

Entry offset Source-observed interpretation
+0x00 Reference to an {int, int} pair for .fmep terrain pieces
+0x04 / +0x08 Offset into the +0x28 header array and count 1
+0x0C Float field (reported value 1000 on rock entries; not a universal default)
+0x10 / +0x14 Model and collision resource-name references
+0x18 Reference into the +0x58 header array

These tables describe the measured EDF6 map.mapo loader profile, not the distinct EDF4.1 relayout case above. In the linked source, the map loader associates each placement with its corresponding MAPO entry and record index; collision bodies are resolved through resource names, not by assuming the placement GUID appears in every collision container. The source reports static reading and corpus checks, not an in-game qualification of arbitrary edited maps.

Relationships with models and physics

Map-object records can refer to visual and collision resources separately. Existing original EDF4.1 research found collision names represented by compact fixed bodies, not necessarily by a triangle-mesh object in the associated MAD. This corrected an earlier mesh-only census overstatement; it did not by itself prove EDF6 runtime collision parity.

Other source studies cover EDF5 structure/LOD and rubble pairs, duplicate placements, child closure and collision-reference identities. Their limits are map/profile specific.

Reading and validation

  1. Establish the MAPO variant and its owning map-generation profile.
  2. Validate the relevant header and table stride before interpreting rows.
  3. Preserve object/parent/child placement identity and referenced resource roles.
  4. Resolve visual and collision asset references separately.
  5. Do not infer successful floor collision or navigation from a parseable MAPO alone.
