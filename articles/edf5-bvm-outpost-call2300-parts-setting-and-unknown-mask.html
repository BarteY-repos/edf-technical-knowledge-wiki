EDF5 Outpost part control: BVM call 2300, message 0x8000002B and tentative group-mask mapping

EDF 5Game technical referencesMissions / multipart objects
Technical reference · Source static analysis; explicitly identified source hypotheses retained

The original EDF5 BVM call 2300 takes an object, a group argument, an index and a byte-like flag. The native dispatcher sends message 0x8000002B with these fields via the target object's message route. Unlike enemy spawn calls it does not create a new enemy. The receiving class implementation was not conclusively identified in the source reverse engineering; therefore the precise flag meaning remains unresolved.

The script supplies group values 1, 2, 4, 8, 16 and 32. The Outpost SGO's parts_setting contains a third integer field in the range 0–5, with six corresponding groups. A proposed mapping is group mask = 1 shifted left by that third field. It is supported by a specific mission count cross-check but remains a hypothesis, not a native binary handler proof.

Proposed mask Observed SGO part category Count in the studied Outpost configuration
1 Large cannons 3
2 Medium cannons 9
4 smallcannon1 42
8 smallcannon2 52
16 smallcannon3 13
32 smallcannon1_g 6

For M021, the script activates masks 8 and later 4; 52 + 42 = 94 matches the Japanese wiki's Outpost turret tally in that mission. Counting these 94 SGO components as ordinary scripted BVM enemy spawns would misrepresent the source: the whole Outpost and its turrets can be one object hierarchy.

This page distinguishes three facts: the actual 2300 message is statically established, the SGO parts grouping is observed, and the bitmask interpretation of that message's group field is unverified.

Evidence: bvm-calls-1141-2300, bvm-call-2300-native, outpost-part-group-mask (unverified), outpost-2300-calls-per-mission, bvm-wiki-gaps-explained. Investigated EDF5.exe build only.

E510 fortress part resources: design differences rather than one interchangeable object

The examined EDF5 standard E510 composition and its EDF5 DLC variant both contain 125 parts_setting entries. Their top-level part order, numeric part configuration and embedded blobs are identical; 125 resource path references and 10 resource-list entries differ. This indicates that the EDF5 DLC difference in the top-level asset is predominantly a resource-selection difference, while its child SGO components can encode substantially different durability and loot values.

When comparing EDF5 standard with EDF6 standard, three small-cannon resource bindings switch from the green variant E510_FORTRESS_PARTS_SMALLCANNON1_G.SGO to the purple ...SMALLCANNON1_P.SGO, at part indices 99, 105 and 111. These are not color-only aliases: the native green small cannon uses bullet_small_1_green / LaserBullet02, while the purple version uses bullet_small_1_purple / PulseBullet01. The examined EDF6 M055 fort composition differs again: six medium-cannon slots use MEDIUMCANNON_2, so it is not a safe stand-in for original EDF5 DLC behavior.

The inspected source DLC large/medium cannon drop_item_2 values differ too: 3.29 / 2.29 versus EDF6 standard 0.29 / 0.29. Exact SGO child references, weapon parameters, durability and resource availability must be assessed together, not guessed from an E510 basename. An observed 141-mission app:/object/*.sgo inventory contained 183 unique referenced object basenames and five missing from the EDF6 native resource tree: four belonged to synthetic DM006_2 frog search-radius variants, and one was the original EDF5 DLC e510_dlc_fortress.sgo resource. A source-only port must address their identities without falsely calling generated compatibility SGOs native assets.

This resource and script-mask comparison is binary/source evidence, not proof that the unlocated BVM 2300 message receiver implements every hypothesized bitmask rule. It also does not make EDF5 DLC object data freely redistributable.
