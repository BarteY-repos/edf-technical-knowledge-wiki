EDF6 map MAD: MARC v5 wrapper around native collision.hkt

EDF 6Game technical referencesMap / file format
Technical reference · Source analysis only (unless a source fact is contributor-verified); no new EDF runtime test

The examined map .MAD files use a MARC version-5 wrapper, not a raw Havok file at byte zero. In the source corpus, each of the 50 map MADs contains exactly one collision.hkt entry. The payload starts at byte 0x24 and is a native TAG0 Havok tagfile. The name block is UTF-16LE, stored after the payload aligned to a 16-byte boundary.

MAD field Meaning in the observed 50 native examples
+0x00 ASCII MARC
+0x04 Version 5
+0x08 Payload offset 0x24
+0x0C Name-block offset relative to +0x24
+0x10 Payload byte size
+0x14 File-entry table offset relative to its own field
+0x18 File count 1
+0x1C Absolute name-block offset
+0x20 UTF-16 name length including terminator (14 code units)
+0x24 collision.hkt TAG0 payload, padded to 16 bytes

The trailing name text is collision.hkt\0 in UTF-16LE. The entry record holds a signed relative name offset, payload offset and length, then reserved zero fields. The native rule set reproduces the 50 scanned wrappers byte for byte. That establishes the wrapper format for this corpus; it does not prove every unknown modded or future MAD has exactly one member.

The HKT payload itself still has to be interpreted as Havok Physics data: understanding MARC offsets alone says nothing about whether a body's collision layer, mesh BVH, mass or joint setup is accepted at runtime.

Source: edf6/havok-format.md, fact mad-marc-layout. Static byte-level audit of 50 map archives.
