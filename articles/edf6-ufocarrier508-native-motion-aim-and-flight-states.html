EDF6 UfoCarrier508: native movement, flight states and route transitions

EDF 6Game technical referencesGameplay & AI
Technical reference · Native-data and static code observations; no new in-game runtime test

The surveyed UfoCarrier508 is a separately configured dropship object, loading app:/object/e508_carrier.sgo, and inheriting parts of the UfoCarrier flight/AI machinery. Understanding its position, target and velocity fields is more useful than interpreting it as a model translated directly to a coordinate every frame.

Flight is eased toward a requested velocity

In the examined object update (reported RVA 0x4F74D0), the active flight mode uses an approximate per-frame easing operation:

velocity += (requested_velocity - velocity) * 0.01
position += velocity

The named fields are +0xB40 (requested direction/velocity command), +0x5C0 (current velocity) and +0x90 (position), with heading adjustment through +0x600. This is the source's static reading of the normal active flight branch; not every state necessarily runs that branch. The unit and update cadence should not be generalized outside this code path.

The parent AI slot can compute +0xB40 from a target/explorer direction, turn rate and speed. The ship itself performs the easing, which explains why forcing position directly would bypass its native flight model.

Named state-machine families

The source identifies a state value at +0x16F0 and these handler functions in the examined build:

State Reported role
0 Idle
1 Follow route at +0x1728
2 Follow route at +0x1740, then delete
3 Fly to target at +0x1760, with radius +0x1780, then state 5
4 Fly to +0x1770, then delete
5 Additional state (function identified, exact gameplay label unresolved)
6 Additional state (function identified, exact gameplay label unresolved)

The inferred meanings of states 0–4 come from code and script usage; the exact caller that advances the state machine during every frame was not fully closed. Specifically, a prior source note misidentified the damage-flame burst update as the state-machine tick. This later interpretation supersedes that mistake.

The fly-to helper chooses a point on a horizontal circle about the target (radius 0 means the target itself), creates a desired 3D direction, adds a turn penalty and multiplies by its speed. The surveyed code did not implement a general smooth slowdown near the target point in that helper.

Model, bounding box and damage context

In the analyzed model, catapult_A (the core) is approximately at local (0,-5,0), a hatch ring of eight hatch_A through hatch_H nodes is around local Y -16.814, and its model collision box has approximate half-extent (47,43.5,75.9) with a small negative Y centre offset. These are model-space measurements, not a universal collision radius for every carrier variant.

The carrier's HP is maintained independently of its movement state. Additional fire/damage effects are handled around an update separate from the flight-state logic. The model's physical shape, scripted spawn event and generated enemy occupancy belong to other subsystems.
