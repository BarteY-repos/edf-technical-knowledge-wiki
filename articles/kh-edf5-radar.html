The radar HUD object

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-hud-class

Radar dispatcher and marker list creation

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-dispatcher

Dispatcher 4CD7D0 (vtable slot 2) builds one list of positions per kind each frame and calls the marker drawer 4CE730 eight times. Normal-mode draw order: team 4 (color 125B410, white), crates (125B430, green), team 2 (125B420, cyan), hostile (125B440, red), team 5 (125B450, yellow), teammate icons (4CED00), team-0 others (125B400, white), objective points (4CF560), area circles (4CF8E0). Versus mode (a mode dword equal to 2) draws only hostile and team 5. No sorting and no depth test: later draws paint over earlier ones.

4CE5C0 returns radar-plane x, y, a height term and a flag at rbp-0x14 (1 = inside range, 0 = clamped to the rim)

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-position-helper

4CE5C0 returns radar-plane x, y, a height term and a flag at [rbp-0x14] (1 = inside range, 0 = clamped to the rim). The 2D distance is compared with 200.0 m (constant EE66FC, loaded at 4CE64E); positions are scaled by 0.6, so the rim radius is 120 radar units. Height term = scale^2 x 2.25 x dy, clamped to +-80. The radar rotates with the player's heading (object [this+0x768], rows at +0x80 / +0x90; the source called it the camera object, but it is the player soldier: #radar-own-player-object, settled 2026-11-08).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 4CE5C0, 4CE64E

Attribution: novae (ajane), GAME_KNOWLEDGE 1 · 2026-10-14

HUD renderer draw-call arguments

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-draw-call-v2

The draw call at 4CEB2C calls A4E00 (rcx = global renderer manager 1259640, rdx = draw context, r8 = a 16-float matrix at [rbp-0x70], r9 = color pointer); the four vertices (x, y, z, u, v, stride 0x14) are at the drawer's [rsp+0x40], strip order (+x,-y), (-x,-y), (+x,+y), (-x,+y) (stores 4CEA35..4CEB24; dot tile UVs v0 (0.25, 0), v1 (0, 0), v2 (0.25, 0.25), v3 (0, 0.25)). A4E00 calls the matrix upload 97B30 (at A4E7A), which copies the 16 floats transposed to its stack, calls the device context's vtable +0x180 (UpdateSubresource) on the buffer at [rdi+0x538], then vtable +0x38 (VSSetConstantBuffers, slot 1, count 1); A4E00 then sets the color (9D7F0, call at A4ED3) and draws (5EFF80; the final draw call was not re-read in the 2026-10-15 session, listing stopped at A4F17). After the call the drawer draws the dot's height line (4CEBA5..4CEC5B): global identity matrix 118C710, line list (topology 2) from [rbp-0x10].

Marker coordinates outside clip-space transforms

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-matrix-hud-space

The marker drawer's per-dot matrix is not a clip-space transform: with an identity matrix, vertices are in the radar's own HUD space (radar center at (150, 150), one unit = one dot-size unit); the step to the screen happens on the GPU, not in the CPU code. The dispatcher 4CD7D0 builds [rsp+0x60] as a pure rotation (cos/sin of the heading at 4CDA0C..4CDA43, rows 2 and 3 identity); the drawer 4CE730 multiplies the dot's rotation and position by it (loop 4CE920), then by a matrix that is identity except row 3 = (150, 150, 0, 1), from EE75F0 (xmm13, loop 4CE994); the height line right after each dot uses the identity matrix 118C710 (lea at 4CEBAC, upload 97B30) with the dot's final translation ([rbp+0x90] -> [rbp-0x10]), the same space. A test drawing with an identity matrix and vertices -1..1 showed nothing in game, which fits a 2-unit speck at that space's origin (but the test may not have loaded: its SiteT0 anchor fails when another radar patch is present). The screen mapping is measured in radar-hud-space-mapping.

Basis: disassembly; novae (ajane)

Addresses (build-specific RVAs unless indicated): 4CD7D0, 4CDA0C, 4CDA43, 4CE730, 4CE920, EE75F0, 4CE994, 118C710, 4CEBAC, 97B30

Identity-matrix test for screen positions

Evidence: verified · Build: steam-5d11de53 · Fact ID: radar-hud-space-mapping

With the identity matrix, the marker drawer's vertices land at screen position = vertex + (1509, 51) in a 1920 x 1080 virtual HUD, y down, 1.333 px per unit at 2560 x 1440 (16:9, novae (ajane)'s normal HUD); the radar center (150, 150) is at virtual (1659, 201). This confirms the 1920 x 1080 virtual size of the older line and adds that the radar's draw space is offset by the widget position. A test drew, through 4CEB2C with the identity matrix and the stencil clip off, a 260-unit cyan frame around HUD point (150, 150) and a 4-unit white line at HUD y 540 from x 192; in novae (ajane)'s 2560 x 1440 screenshot the frame bars are at x 2039..2042 and 2381..2384, top at y 95 (346 px = 260 x 1.333), the line rows 785..790 from x 2268: center (2212, 268) px = (1659.0, 201.0) units, origin (1509.0, 51.0); line 788 px = 591 = 540 + 51, start 1701 = 192 + 1509. Shapes placed beyond those numbers were off screen, as predicted. Not checked: other resolutions, aspect ratios or HUD layout options (a right-anchored radar would move the origin on other aspect ratios).

Basis: novae (ajane)

Addresses (build-specific RVAs unless indicated): 4CEB2C, EE75F0, 118C710

North-up radar coordinate projection

Evidence: static · Build: steam-5d11de53 · Fact ID: radar-north-up

North-up radar coordinates: the position helper 4CE5C0 gives un-rotated radar x = -(dx) x 0.6, y = -(dz) x 0.6 (constant EE80D0 = -1 in all lanes), so a north-up view (world +z up, world +x to the left on screen, the game's own handedness) is the helper's formula without the heading rotation.

EDF Knowledge Hub record — original wording — expand (1,239 characters)

The radar clips its area circles to the radar disc with the stencil buffer. 4D0290(rdx = draw context), called at 4CDE9D, sets [ctx+0x1A4] (stencil enable) = 1, [ctx+0x1A8] / +0x1A9 (read / write mask) = 0xFF, [ctx+0x1CC] (reference) = a counter at 12535C8 incremented per call and wrapped 255 -> 1, front and back ops (+0x1AC fail, +0x1B0 depth-fail, +0x1B4 pass, +0x1B8 func; back +0x1BC..+0x1C8) = 1, 3, 3, 8 (KEEP, REPLACE, REPLACE, ALWAYS; D3D11 enum values), each change ORing dirty bit 4 into [ctx+0x78]; it draws the disc (5EFF80), then sets the ops to KEEP and func 3 = EQUAL (4D062A..4D06BC). 4CF8E0 (area circles) and 4D0720 leave these fields alone; at 4CDF0F the dispatcher switches the test off (cmp [rsi+0x1A4],0; je; mov [rsi+0x1A4],r12d (0); or [rsi+0x78],4). So anything drawn through the HUD draw context between 4CDE9D and 4CDF0F shows only inside the disc. Dirty bits are applied by 5F0C40(ctx+0x20, [ctx+8]) when [ctx+0x78] != 0, called from A4E00 and from the drawers. In game, a test drawing 11 shapes from a hook at 4CDF0A (inside the window), all outside the disc, showed none of them while its message line appeared; with the enable cleared and the dirty bit set first, they were drawn (radar-hud-space-mapping).

Basis: disassembly; novae (ajane)

At run time the vtable (class) is the stable handle for an entity

Evidence: static · Build: steam-5d11de53 · Fact ID: entity-identification

At run time the vtable (class) is the stable handle for an entity; the SGO file name is not stored readably. The class name comes from MSVC RTTI: vtable[-1] = complete object locator, its pSelf field gives the image base, its type descriptor holds .?AVName@@.
