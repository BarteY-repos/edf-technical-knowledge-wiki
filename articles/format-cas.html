CAS — animation players, controllers and embedded clips

File FormatsSource-scoped referenceEDF 4.1EDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: CAS organizes animation playback: players, controller groups, state and references to animation data.

Where it fits: CANM describes the keyed motion, and MAB can supply event-related data. The researched CAS wrapper has its own version and record layout.

Important distinction: A valid animation clip is not enough if its controller expects named variables that are missing.

Worked example: three levels of animation compatibility

Imagine moving a CAS-driven animation between the studied EDF5 and EDF6 profiles. A quick check that its embedded CANM keys decode is only the middle of the investigation. The example is a verification checklist, not a claimed successful game conversion:

  1. Outer wrapper: identify the CAS version, offsets and 16-byte-aligned embedded CANM position. Replacing the version word alone does not relocate records or fix pointers.
  2. Animation data: parse the embedded CANM using its own generation's channel widths and rotation representation. In the examined EDF6 implementation, the CANM channel table must also be 16-byte aligned; aligning only the start of the embedded file is insufficient. A valid wrapper does not guarantee valid target tracks.
  3. Controller contract: resolve the expected player names, tcontrol/vcontrol variables, groups and skeleton references. A clip can look mathematically correct yet still lack the controller state needed by the target class.

Keep the three outcomes separate: parses as CAS, decodes as CANM, and works in the game are not equivalent statements.

Role of the container

The studied CAS resources organize named players and controls around animation data. A target game class can depend on controller variables by name. A missing controller is not necessarily a harmless default: the existing EDF6 case studies include target classes that fail when expected named variables are absent.

The measured cross-generation format work identifies a 0x30-byte CAS header in its examined family. It also contains references into associated channels, tracks and string data. These are sample-scoped structural findings, not a universal promise for every historical CAS variant.

What the measured CAS wrapper points to

The studied 0x30-byte header references several related structures:

Header offsetStored fieldStudied interpretation
+0x00char[4]CAS\0 signature
+0x04u32CAS wrapper version; independent of the embedded CANM version
+0x08i32Embedded CANM data position
+0x0C / +0x10i32 × 2TControl count / table position
+0x14 / +0x18i32 × 2VControl count / table position
+0x1C / +0x20i32 × 2Animation-group count / table position
+0x24 / +0x28i32 × 2Bone count / table position
+0x2Ci32Global controller program offset in the examined EDF6 CAS; called UnnamedC / CasDataGroup in the older guide

The four count/offset pairs and the embedded-CANM location in the EDF6 header are file-absolute offsets; most nested record references in that examined build are signed offsets from the start of their containing record. These are different bases. A zero or negative nested name/reference offset is a missing-reference sentinel in the examined native parser, not a file-absolute address. The original community guide also notes that CAS string data can follow the embedded CANM strings, so a parser must not assume that the CAS names all precede the animation payload.

Structure Recorded relationship
Embedded CANM Offset at CAS header +0x08; CANM begins at a 16-byte-aligned position
tcontrol and vcontrol Control records used by the animation-state graph
Animation groups Named groups and their associated state/clip references
Bone references Names and relationships needed to address the owning skeleton
String references Signed relative pointers to UTF-16LE names in the measured layout

The header and the embedded animation bytes are two layers. Repositioning records or inserting controller data requires recalculating the relevant relative pointers; a version word alone does not repair them.

Nested EDF6 controller records and their field offsets

The following is the CAS 0x204 / steam-678ccb46 static parser-and-engine profile, cross-checked against the older CAS guide. Offsets are local to each record; a relative pointer is added to the record's start, not automatically to the file's start.

Record / sizeLocal fieldsBehavior and boundary
TControl, 0x0C+00 relative UTF-16LE name; +04 i32 clip-index count; +08 relative array offset (each entry i32).Indices address CANM animation-name order. Clips form a sequence whose durations are summed; zero entries are valid.
VControl, 0x14+00 relative name; +04 i32 type (0 float, 1 int, 2 4×4 matrix); +08 i32 role/tag; +0C f32 initial float; +10 i32 initial int.Game code resolves variables by name. Role/tag 0..3 was classified by source-name patterns, not by a demonstrated engine switch; matrix inputs stay unset until supplied.
AnmGroup, 0x0C+00 relative group name; +04 i32 state count; +08 relative state-array offset.Each group is its own state machine; names such as main and weapon are lookup identities.
MCAnm state node, 0x24+00 relative name; +04 default transition; +08/+0C transition count/array offset; +10/+14/+18 program references; +1C end-kind; +20 end-time float or TControl index.End-kind 0 loops, 1 uses a float end time, 2 uses a TControl's summed duration. In kind 2, +20 does not index a CANM clip directly.
BoneList entry, 0x04+00 relative UTF-16LE bone-name offset.CAS node mapping is independent of the CANM BoneList; interchangeability is unproven.
Program header, 0x08+00 i32 instruction count; +04 relative instruction-array offset.EDF6 instructions are 13 × u32 = 0x34 bytes; the older CAS 0x200 command form is 9 × u32 = 0x24 bytes.

Important source disagreement: the retained source-only cas_graft.py comments call VControl +0x04 = 1 “following a TControl”. The independent EDF6 native-controller analysis instead identifies +0x04 as the variable type and +0x10 as an initial integer. The graft implementation is intentionally restricted to +0x04 = 0 records; that restriction must not be mistaken for proof that all type-1 VControls contain TControl pointers. See graft compatibility boundary and EDF6 controller execution.

The CAS command/data generation difference

EDF4.1 0x24 bytes
EDF5 0x34 bytes
EDF6 0x34 bytes

The original paired-file research found that command identities changed across generations. Its measured crosswalk relied on same-named controls, states and corresponding slots in paired resources, not on a universal numeric increment. It also rejected unmapped commands rather than silently substituting a nearby ID. These are evidence-bounded conversion observations, not a license to remap unknown opcodes.

Relationship to CANM

An outer CAS wrapper can contain or refer to animation data governed by its own CANM layout. In the studied EDF5/EDF6 profiles, CANM changes its channel record width and rotation representation. Therefore:

  • Reading the CAS wrapper does not prove that trailing CANM bytes have been decoded correctly.
  • Converting the CAS version word does not convert Euler-based animated rotations into the measured target quaternion form.
  • A syntactically valid resource must still satisfy named-player/controller and owning-skeleton expectations.

See CANM — clip and channel encoding for the dedicated channel reference.

Validation and limits

The existing measured conversion recorded an 836-file CAS round-trip and a 230-pair EDF5/EDF6 corpus. Those counts describe a bounded validation set. They are not an unconditional successful-animation guarantee for every resource, nor proof of a universal conversion schema.

Within that 230-pair study, 66 converted files matched the target bytes exactly, 21 were classified as substantially re-authored target resources, and the other 143 differed only in reported quaternion floating-point values and, in 69 of those cases, key-block ordering. For EDF4.1 CAS input, the same study accepted 204 of 205 examined assets and rejected an uncommon unmapped command case. These are specific source-reported results; no new test has been performed for this page.

The EDF6 source cases support retaining required named controller placeholders where appropriate, rather than blindly copying donor-bone animations. These are controller-compatibility findings, not a generic CAS layout rule.
