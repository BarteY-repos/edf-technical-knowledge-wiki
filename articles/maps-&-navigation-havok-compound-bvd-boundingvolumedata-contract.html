Havok compound BVD / `boundingVolumeData` contract

UniversalMaps & NavigationCollision & PhysicsEDF 5EDF 6
Source-backed research / case study · Reconciled

BVD in this corpus means the compound-shape boundingVolumeData substructure inside MAD/Havok data, not a standalone map file.

Current structural measurement

The reconciled compound record places boundingVolumeData at compound +0x5C. The BVD slice is 32 bytes. An older 36-byte slice interpretation is superseded.

The retained compound layout around it is:

  • instance/free-list state before the AABB;
  • aabb at +0x30;
  • boundingRadius at +0x50;
  • isMutable at +0x54;
  • estimatedNumShapeKeys at +0x58;
  • boundingVolumeData at +0x5C;
  • BVD type field observed at +0x78.

For native compound examples used by the map research, the BVD is not NONE: it uses SIMD_TREE / type 2 with a real tree. The retained runtime analysis describes a four-way SIMD tree, a dummy node 0 and ray traversal beginning from node 1. A compact native-style state is represented as an empty/zero AABB-tree reference plus a real SIMD-tree node reference, compact flag, and type 2.

Rebuild rule

The runtime consumes the compound BVD as serialized data for this path; it is therefore not safe to preserve a stale tree after changing compound children. Rebuild BVD/tree data whenever child topology changes.

Important negative evidence

Correct BVD structure is necessary structural work but not a sufficient explanation for every collision failure. The 2026-08-17 line fixed the old BVD-size/tree problem and still did not recover the Desert floor collision. Later investigation moved on to section-tree, slot, resource and other map/Havok factors.

Do not resurrect the old causal claim “bad BVD is the entire Desert floor bug.” The current rule is narrower: malformed or absent compound BVD can make broad-phase/raycast candidates disappear, but a structurally correct BVD does not prove the rest of the collision pipeline is correct.

Conversion boundary

This evidence is tied to the audited compound/Havok family. Do not use the 32-byte BVD record as a substitute for understanding unrelated SHKT/HKT, NAVMESH.HKT or ordinary MDB collision resources. Havok generation and owning structure still matter.

Compound free-list field offsets in the audited record

The retained Havok compound record shows instance-list/free-list metadata leading into the BVD region:

Compound-relative offset Field
+0x14 instance list m_data
+0x18 instance list m_size
+0x1C instance list m_capacity
+0x20 m_firstFree
+0x24 m_numAllocated
+0x30 AABB
+0x50 bounding radius
+0x54 mutable flag
+0x58 estimated shape-key count
+0x5C 32-byte bounding-volume data
+0x78 type field inside BVD

These offsets are for the measured compound ABI; they must not be treated as a generic stand-alone SHKT/mesh layout. The BVD contains tree references, not merely the axis-aligned bounds.
