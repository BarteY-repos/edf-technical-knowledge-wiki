EDF 4.1 / EDF 5 / EDF 6 CAS and CANM: actual record layouts and key conversion

ConversionAnimationEDF 4.1EDF 5EDF 6
Technical reference · Native format source research and bounded pairwise corpus; not new runtime

At a glance

What this page answers: CAS controllers and CANM channels differ across EDF4.1, EDF5 and EDF6; changing the version number is not a reliable conversion.

How to read it: Compare each game's record layout, rotations and command semantics before attempting retargeting or bind-pose changes.

Evidence boundary: Paired-file and exact-binary studies support the stated mappings, but not every modded skeleton or animation is covered.

The games have different CAS state-controller layouts and CANM key encodings. A version-word edit can make a file look plausible to a parser while still mapping the wrong commands or rotations. This guide describes the measured 2026 paired-file and exact-binary research, not an independently established universal conversion law for every modded asset.

A studied CAS header uses 0x30 bytes, with its embedded-CANM offset at CAS +0x08, followed by the counts and offsets for tcontrol, vcontrol, animation groups and bones. The embedded CANM begins on a 16-byte boundary. CAS string references include signed relative offsets to UTF-16LE names. Do not transplant offsets from the old layout after inserting new records.

A CANM has a 0x20-byte header, 28-byte clip records and 8-byte track records. Each track contains a uint16 bone index and three signed 16-bit indices for translation, rotation and scale (-1 = no channel). Clip records hold a name pointer, duration, step/frame interval, frame count, and track count/location.

EDF5/4.1 CANM 0x200 channels

The measured 0x20-byte channel stores a keyed/static flag, count, three float32 base values, three float32 scale/step values, and an offset to key data. Animated XYZ keys are stored as three uint16 integers per key. For each component:

v_i(k) = float32(base_i + float32(uint16_key_i(k) * step_i))

In the studied rotation lane, the resulting XYZ values are Euler angles in radians, applied in source rotation order Rz · Ry · Rx. Floating-point evaluation order matters when comparing exact converted bytes.

Profile limit: a separate EDF_Tools-derived CANM v512 note describes legacy channel tag 625 with uncompressed 4 × float32 keys. The measured cas_legacy.py converter accepts source channel flags 0 and 1 only; its successful bounded corpus counts do not establish a conversion path for tag 625. Treat it as a source-guide variant until separately decoded and qualified. See legacy CANM field reference.

EDF6 CANM 0x300 channel kinds

The channel expands to 0x30 bytes: eight float32 values (base XYZW and multiplier XYZW), then four signed 32-bit values (key offset, kind, count, reserved). In the analyzed native channels:

Kind Role Stored values
0 Static vector Base XYZ (W and steps set appropriately)
1 Animated quantized vector Base + uint16 XYZ key × multiplier
2 Static quaternion Base float32 XYZW
3 Animated quaternion One float32 XYZW quadruplet per key

The target engine reads quaternion vector data with aligned vector loads. The native writer therefore places quaternion key blocks on 16-byte boundaries. For every reused source channel, a converter must separate vector and quaternion roles, because EDF5 can reuse a zero-valued channel for translation and Euler rotation, while EDF6 needs different representations.

Euler → quaternion: not merely degree conversion

The examined EDF6 path converts source Euler radians to an XYZW quaternion through an explicit sequence of X, Y and Z rotations, applying float32 rounding and the target runtime's sinf/cosf behavior. If the source has quantized keys, the exact original unquantized authoring angles may already be lost. Producing a geometrically equivalent rotation does not guarantee byte-exact target quaternions.

Measured evidence from retained matched-file tests:

  • All 836 analyzed CAS files across the three Root.cpk corpora could be parsed and round-tripped under the retained model.
  • Among 230 same-name EDF5/EDF6 pairs, 66 matched byte-for-byte after conversion; 21 target files were substantively re-authored.
  • The other 143 paired conversions were byte-identical apart from quaternion float differences and, in 69 cases, quaternion key-block ordering.
  • 1,487/1,487 measured static quaternions matched bitwise; among 1,958,796 animated quaternion keys, 88,038 matched bitwise, with the others differing within the source quantization/float rounding envelope reported by the original analysis.
  • 204/205 tested EDF4.1 CAS assets converted under the bounded implementation. GIANTANT_HOKAO contained uncommon source command IDs 2/3 without demonstrated mappings and was intentionally rejected.

These numbers are corpus results, not proof that arbitrary custom CAS variants or future game builds have the same command set.

CAS commands also need semantic remapping

Command IDs changed between generations; the observed converter mapped known commands by same-named control/state/slot position in paired assets, not by blindly adding a constant to every opcode. EDF4.1's 0x24-byte data structs expand to 0x34 and inherited pointers/unused words require clearing where the destination native representation does. Unknown command identities must fail closed rather than adopting the nearest numeric opcode.

Retargeting after a skeleton/bind-pose change

If an MDB bone's bind translation changes, absolute CANM animation translations can pull it back to its original location. The qualified source procedure computes a per-bone local translation delta, applies it only to explicitly named absolute clips and modifies the base XYZ of a channel, leaving quantized keys and time steps intact. Additive/recoil clips should not automatically receive this offset.

A channel shared by two tracks needing different translation adjustments cannot be patched unambiguously and must be rejected. Removing a runtime-plugin-owned bone track also differs from changing its key values. Quaternion rotation poses follow EDF's row-vector matrix convention; directly substituting the more common column-vector matrix will produce a wrong world-space result.

What CAS/CANM changes before an EDF6 model is drawn

The EDF6 native model path distinguishes clip channels, local bone poses, world bone poses and GPU draw poses. CAS binds a controller to model bones by name at initialization; channel evaluation updates local transforms, with translation, rotation and scale represented by separate channel-presence bits. A channel absent from a clip does not necessarily reset that bone's code-owned local value. That preservation behavior is an inference from the observed writes, not a complete evaluation of every sampler branch.

The AnimationModel synchronization path gates this copy via a model flag (+0x31C & 1). In the studied vehicle initialization the flag is explicitly enabled, so that vehicle model follows the ordinary draw-pose route. Separately measured multi-thread draw timing means a submitted pose may lag a game-thread update by a small number of steps; it does not imply that CANM key timestamps are globally delayed.

These relationships explain why editing a skeleton, repairing a CANM translation track and changing an attachment transform are distinct problems. The MDB/AnimationModel reference gives the runtime LOD and draw-pass context. The source combines static EDF6 disassembly with limited contributor probes, not an exhaustive per-character animation validation.
