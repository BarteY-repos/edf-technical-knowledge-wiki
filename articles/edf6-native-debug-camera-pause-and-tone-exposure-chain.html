Documentation / EDF 6 / Camera and rendering

EDF6 embedded free camera, online pause masks and bloom/exposure pipeline

EDF 6Game technical referencesCamera and rendering
Technical reference · Source-backed static analysis with explicitly scoped contributor tests; no new R125 runtime

Not a user-facing photo mode: The source research uses “photo mode” as a section label. Evidence here establishes internal debug code and post-processing behavior in the inspected binary, not an ordinary retail feature or publicly reachable menu.

The investigated retail EDF.dll has a FreeViewCamera implementation with analog control, collision handling and a field-of-view value. It is an internal debug system, not evidence of an ordinary user-selectable photo mode. EDF6's post-processing chain also has tone and bloom operations, but does not automatically provide photographic depth of field or an adjustable vignette.

Pause is mode-gated

The game system stores both requested pause flags (+0xCD8) and an allowed mask (+0xCDC). MissionMgr::SetMode changes whether bits 2, 4 and 8 can pause simulation: they are excluded in the examined online mode and allowed offline. A pause request may therefore set its bit without stopping the game. Listeners are notified when the effective paused state changes. Build offsets refer only to steam-678ccb46.

Camera update and FOV

The class reads the left stick, triggers and right stick; yaw and pitch apply a FOV-scaled rotational sensitivity, with pitch limited to ±π/2. Depending on whether the game is paused, movement either changes the stored point directly or uses the debug camera's own collision-controller velocity. Start toggles the class's pause bit, Back advances one step, and the code retains debug hit/projection actions. FOV adjustment uses a factor involving tan(FOV/2) and the shoulder-button difference.

These are structural code observations. They neither prove the controls can be used from a retail menu nor authorize changing a live game installation.

Bloom and exposure order

The 490 examined DXBC blobs contain resize, high-pass, blur, tone-lerp, final combine, depth and ambient-occlusion shader paths. The inspected final combine computes roughly:

result.rgb = scene * tone + bloom0 * strength0 + bloom1 * strength1

The tone value is a single scalar and bright-pass uses that tone before thresholding. The LightEnv parser provides tone and bloom keys, and scene linear/view-space depth exists for ambient occlusion. The surveyed DLL shader set did not reveal a native bokeh or depth-of-field pass; the study did not exhaust every external shader resource.
