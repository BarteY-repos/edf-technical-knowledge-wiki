EDF5 / EDF6 Input Acquisition: Snapshot, Overlay and Raw Input Boundaries

Technical reference · Cross-source editorial reconciliation; no new runtime tests

Three distinct interfaces

A game's message-pump snapshot, a Windows API's key state, and the game's downstream action/aim model are not interchangeable. Both games use their own input-side state, but the supplied snapshots belong to different exact binaries. A raw-mouse plugin changes a narrowly identified relative-motion acquisition point; it does not validate replacing the entire action system.

Do not copy EDF5 0x1253600 into an EDF6 mod. The 0x1253600 address is reported as array storage, not a pointer to a heap buffer. The 0x21360E0 location is similarly build-specific; verify both anchors again for patched executables. See EDF5 source notes, EDF5 global, EDF6 global.

Threading: what is known and what is not

The contributor reports that EDF5 fills its array from the message pump and copies it under a critical section before clearing the refresh flag. This establishes an internal producer/consumer synchronization path, not automatically a guarantee that arbitrary external readers can safely read all 256 bytes lock-free at any moment. The claim "safe to read from any thread" in the source appendix is preserved as contributor-reported, but has not been independently race-qualified by this wiki. A robust external hook should sample at a defined frame boundary or arrange appropriate synchronization if consistency matters.

Windows GetKeyState semantics are thread/message-queue sensitive, and cannot simply be substituted for the game's frame snapshot. GetAsyncKeyState not appearing in an import table is only a statement about static imports, not proof that no dynamic call can occur. EDF5's IME association and candidate rendering are a separate UI text input pipeline; do not rewrite them as if they were gameplay key polling. See input and IME source.

EDF6 overlay can replace import hooks

The community source describes EOSOVH-Win64-Shipping.dll rewriting several EDF.dll import slots after launch and periodically afterward. If reproduced in the selected build, this explains why an import-address-table hook installed early can appear to work and later disappear. The source also describes a crash caused by overriding the entire USER32 GetKeyState export; do not interpret that as a blanket recommendation to patch USER32. Prefer minimally invasive, build-checked hook points, proper chaining and an explicit coexistence policy. Contributor source.

Raw Input does not mean unbounded aim rewrites

The separate native Modernization Raw Input contract replaces EDF6 relative delta acquisition (WM_INPUT counts), leaving menus and downstream Sandlot aim shaping intact: /24 scaling, saturation/carry, class-specific response and turret inertia where applicable. Do not equate acquisition quantization with downstream intentional mechanics, nor turn an input hook into an implicit Safe120 simulation-rate patch.

Suggested tests

  • Under the same build, compare foreground/focus state, keyboard snapshot and action event in the same frame; test UI typing/IME separately.
  • For hooks, test cold launch and several seconds after EOS overlay initialization; trace who owns the import slot.
  • For Raw Input, test absolute cursor UI and relative gameplay paths separately, and check menu-to-game transitions for stale deltas.
  • Confirm two independent axes: key correctness and frame coherence. Correct individual bytes do not prove one coherent snapshot if observed asynchronously.
