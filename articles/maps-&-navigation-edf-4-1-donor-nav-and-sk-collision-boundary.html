EDF 4.1 donor NAV mismatch and SK collision boundary

UniversalMaps & NavigationNavigationEDF 4.1EDF 5EDF 6
Source-backed research / case study · Runtime-root-cause evidence + offline collision qualification

Donor NAV is a known fidelity limitation

Runtime reports showed friendly Rangers, Fencers and Hectors detouring, stopping, snagging, walking toward geometry and behaving especially badly in underground follow sections.

The historical baseline copied native EDF6 donor navigation for all 16 EDF4.1 map families, despite geometric mismatch with ported EDF4.1 terrain. The later R13 functionality candidate changes exactly one map family, NW_HILLYCITY_LIGHT, to a source-derived NAV pilot when the expected source MAD identity is present. The other 15 maps remain outside that pilot. This is not a claim that the pilot has a gameplay PASS.

This makes donor-NAV mismatch a strong, evidence-backed root-cause class. It is not necessary to import AllForces gameplay/command redesign to explain these symptoms.

Product rule

Source-derived navigation is a gameplay requirement, not optional fidelity polish.

Do not classify a map as gameplay-faithful merely because:

  • it renders;
  • collision loads;
  • an EDF6 donor HKT/NVMD is structurally valid;
  • actors can move somewhere on the map.

Navigation must correspond to the actual ported terrain and obstruction topology.

Scope of the R1C/R1D branch

The exact HillyCity work proves the source-derived approach is viable:

  • R1C is byte-exact closed;
  • historical R1D is known by exact oracle hashes;
  • current R1D reconstruction is close but still non-exact.

That branch provides source-derived geometry and an offline pilot for exactly HillyCity, not proof that all 16 maps have source-faithful NAV or even that the pilot behaves correctly during gameplay. Each map family still needs appropriate source-derived geometry and runtime qualification. R1D historical byte-exactness and a functional candidate are different evidence categories.

See the dedicated R1C/R1D article for the exact 1562/2928 R1C and 1562/2651 R1D contracts.

Seven SK maps — conservative collision rule

The R13 reconciliation also carries a separate collision repair for seven SK maps. It reuses the EDF5→EDF6 runtime-proven runtime-safe-conservative-unflatten-v1 semantics:

  • only final-geometry flat -> split is allowed;
  • never convert split -> flat;
  • do not change material;
  • do not change triangle winding;
  • do not change triangleIsInterior.

A 10,000-case helper-equivalence audit passes.

Evidence boundary

The SK rule is strongly qualified as a transformation rule, but EDF6 runtime on an EDF4.1 SK mission remains pending in this branch.

Similarly, HillyCity exact/reconstructed NAV evidence must not be generalized into “all 16 maps are fixed”.

Practical diagnosis order

When friendly or vehicle AI behaves incorrectly on a ported EDF4.1 map:

  1. verify the map uses navigation derived from matching source geometry;
  2. verify collision/terrain correspondence;
  3. inspect route/RMPA semantics;
  4. only then blame actor-specific AI code or import broader behavior redesign.

This order avoids compensating for a geometric navigation mismatch with mission- or actor-specific hacks.

Measured legacy MAD collision conversion scale

The EDF4.1 mission-map corpus contains 16 map families. In an examined source-only conversion plan, seven SK_* maps used a specialized terrain/collision route and nine non-SK maps used a strict Havok-2014 → Havok-2020 MAD conversion. A converter was instructed to reject an unrepresentable body or shape, rather than silently carrying an unconverted legacy asset under a target-format name.

The exact retail source-derived collision outputs retained for three non-SK sample maps were:

NW_UNDERGROUND01 386 Source-only output with deterministic SHA validation

These cases demonstrate that the serializer operates at very different map scales, from a few bodies to thousands. The three samples are not proof that all nine non-SK maps, all collision shapes or all sixteen map families have EDF6 runtime parity. A permissive runtime fallback to Havok 2014 was retained as a diagnostic path in the earlier workflow, not a source-only conversion success.

Heightfield rendering is not navigation fidelity

The seven SK map families use the EDF4.1 .shfb heightfield, whereas the examined EDF6 target consumes FMB render mesh and hknp MAD collision. The source-field conversion guide explains how the two are reconstructed from the same height lattice. The vegetation and wire guide covers extra FMB/MAPO resource dependencies. These reconstruction steps do not change the separate donor-HKT/NVMD mismatch discussed above.

What seven-map contact analysis adds

A later R24–R28 original-source survey inspected SHFB terrain contacts for seven SK maps (505,633 transformed static-mesh triangles in the R27 restricted-scope pass). The two concepts remain different: matching terrain to object collision does not recover route HKT/NVMD, guarantee agent clearance or remedy donor-NAV movement. No user gameplay test was performed in those passes.

Source-only nine-map collision ownership: why geometry does not yet solve NPC navigation

The later original-source non-SK investigations distinguish several layers that may look identical on a rendered map:

  1. The MAD motionState determines coordinates and orientation of decoded source rigid-body geometry. Its source-body bounding box is not necessarily its final world-space position.
  2. MAPB record XYZ/Euler provides the actor placement. Later R58/R59 native EDF41.exe and EDF.dll witnesses confirmed the per-record base actor matrix and algebraically matched row-vector Rx*Ry*Rz (column-vector Rz*Ry*Rx), superseding this older uncertainty about the base matrix. Bit-exact float32 rounding, later group attachments and Havok body activation are still unproven.
  3. MAPO +0x14 can name an explicit collision .hkt resource different from the MAPB definition model. Matching that name against a MAD body establishes a source-reference candidate, not which actual physics bodies are enabled in the engine.
  4. MAPB +0x2C group children are linked by record indices. Do not inherit parent transforms or collision bodies without native parent/child matrix evidence.
  5. Havok collision activation, material filters, NPC agent radius/height, floor/ceiling disambiguation, navigation links, and final HKT/NVMD behavior are separate questions.

Across nine non-SK maps, the strict stored-pose branch yielded 11,286 conditional collision AABB candidates. Another 220 MAPB records have finite XYZ/Euler but nonzero, semantically unresolved auxiliary integer fields; including them diagnostically yields 11,506 candidate body-instance AABBs, not 11,506 verified collision bodies. Four exact placed-source mesh witnesses (including a grouped owner and child) produced 1,302 decoded triangles and 911 fragments within bounded 4 m columns. Their AABBs fit the conditional broadphase, but no native actor/child transform parity or real NPC route is proven.

The accompanying six city-map source audit covered 768/8,402 planned spatial 64 m windows. This coverage figure is neither the proportion of verified NPC routes nor the percentage of active game collision. All work remains offline: no installable NAV HKT/NVMD and no EDF6 gameplay PASS. A structurally valid HKT or matching NVMD still needs real mission tests against Ranger, Fencer, Hector, vehicles and underground routes.

The newer MAPB/MAPO source ownership audit also resolves 145 previously unmatched explicit HKT references to real compact source MAD rigid-body geometry. That prevents falsely labelling them “missing resources”, but does not convert candidate geometry into proven NAV clearance.

November 17 native correction: matrix and Havok filters

The original EDF4.1 MAPB actor-matrix and Havok-filter census supersedes the older R41–R57 assertion that even the base actor rotation convention had no native witness. Across 18 original MACs, 42,388/42,388 stored position/Euler sextets survive the EDF4.1 0x44 → EDF6 0x48 record conversion byte-exactly. Read-only pinned native code supports the base actor row-vector Rx*Ry*Rz / column-vector Rz*Ry*Rx equivalence.

A separate 18,520-body, 18-MAD original Havok 2014 census found that the declared collisionFilterInfo field was absent from every serialized body instance; this is not proof that the engine uses zero or that every source body participates in NPC collision. R58/R59 do not establish the native contact filter pair matrix, convert any new game-ready NAV, or provide an EDF6 NPC runtime PASS. The unresolved child/attachment and collision-activation gates above remain valid.

Original-source collision cohorts are not NPC filter decisions

The November 17 R60 cohort census reconciles all 18,520 original EDF4.1 MAD rigid bodies into 15 observed combinations of serialized motion type, root shape class and field-presence state. It also identifies native EDF6 hknp* group/pair/query filter type names. These two source surfaces are not a measured contact-pair matrix: the original bodies omit the collisionFilterInfo value and reflected target type names do not establish active NPC query masks. Without a runtime Ranger/Fencer/Hector query-and-contact witness, no additional NAV edge can be declared traversable or blocked from R60 alone. See the joint original Havok census and native type evidence.
