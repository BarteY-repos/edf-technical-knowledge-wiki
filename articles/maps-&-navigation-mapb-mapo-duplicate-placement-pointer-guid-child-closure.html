EDF6 map placement cloning: MAPB/MAPO relative pointers, GUIDs and child references

EDF 6Maps & NavigationMaps
Technical reference · Source-code algorithm cross-checked with retained build-specific fixup routines; no new in-game validation

A new MAPB placement is not only another (x,y,z) triplet. The studied EDF6 map.mapb and map.mapo represent the same ordered placement set through parallel indexed tables, relative references, stable/unique identifiers and parent-child relationships. A retained map-tile duplication utility demonstrates the minimum identity work needed when a placement is cloned or relocated.

Parallel placement tables

The studied MAPB v2 format has a 0x48-byte placement record and 0x3C-byte definition row; the MAPO profile has a 0x1C-byte placement-linked entry and a 0x0C-byte named placement row. For the implemented profile, the three counts must agree:

MAPB +0x24 placement count
MAPO +0x0C per-placement entry count
MAPO +0x54 named-object row count

A record's definition reference at MAPB record +0x00 is signed and relative to the record base. Its position starts at record +0x04. The record's child-list reference is at +0x2C and likewise uses the record's base. The 16-byte GUID occupies +0x34..+0x43.

The MAPO entry array uses record-relative offsets at +0x00, +0x04, +0x10, +0x14, +0x18; named rows use +0x00 (name) and +0x04 (sub-list). Copying a raw record without correcting these offsets moves its targets, often pointing at the wrong model/strings or outside the file.

The studied duplication algorithm

  1. Select (source_record_index, dx, dy, dz) placements; optionally traverse all children recursively using the +0x2C child-list relation, preventing duplicate (index,offset) copies.
  2. Rebuild/relocate the entire MAPB placement-record array and rebase the old references so originals continue pointing to exactly the same definitions and child lists.
  3. Append cloned records with offset positions and fresh GUIDs, then rewrite cloned child indices to refer to the matching cloned children at the same offset.
  4. Add corresponding MAPO entries and named rows; the studied profile names each row by its decimal placement index. Rebase all MAPO relative references and update both placement-table header offsets and counts.
  5. Rebuild the outer MARC archive, changing map.mapb and map.mapo while preserving every unrelated member payload.
  6. Reparse the output and check bounds, references, counts, preexisting semantics, no unintentionally modified archived members, and no new GUID collision.

The utility generates a reproducible UUIDv5-style identifier from the source GUID, new index, displacement and a collision salt. That generation formula is a tool-side identity policy, not proof that the EDF6 engine itself creates GUIDs this way. It deliberately does not require that all original native placements have unique GUIDs: one retained native map (NW_DLCMAP601) reportedly contains duplicates. New duplicated placements must not add collisions.

Child references are the subtle trap

The +0x2C list points to {relative index-array offset, count}, then to placement indices. When cloning a parent and children together, parent references should point at the new child records. If only the parent is copied, the retained tool preserves references to the original children and emits a warning; this may be structurally parseable but semantically wrong for a coherent relocated assembly. It should not be silently treated as a valid object hierarchy.

Likewise, if the source MAPO string pool is not the last block, new names cannot simply be counted as an extension of that pool. The retained utility warns rather than inventing a global pool rewrite.

Format correctness does not complete the map

This tool proves a bounded MAC/MAPB/MAPO placement-copy approach. It does not independently rebake an object's collision body in MAD, native navmesh HKT/NVMD, terrain FMB, occlusion or any dependency introduced by a new placement. A map can have perfectly valid pointers and still produce missing physical collision or bad AI routes. Those systems have their own authorities and runtime qualifications.

Evidence boundary: bigmap.py names the observed EDF6 MAPB/MAPO endian/fixup functions and reconstructs the record fields in Python. This description derives from that retained implementation. It is not evidence that a new large map generated by this tool was accepted in the target game's runtime in this release.

Original EDF4.1 linked-group census

The seven-map contact and placement analysis reports 193 child references across 18 linked groups in a 16-map original EDF4.1 source group list. A correctly linked child placement may be rejected by a flat walker and accepted when its parentage is recognized (R26 → R27 valley case). The count is of source references, not an inventory of independently simulated bodies; no runtime proof follows.

Exact source MAPB group records versus actual transform inheritance

The later nine-map non-SK original EDF4.1 census contains 39,252 MAPB records, 17 group owners and 169 child-index references. There are 169 unique referenced children, no child owned by multiple groups and no nested group owner in this sampled scope. The grouping is concentrated in NW_HILLYCITY_LIGHT (5 owners / 40 children), NW_KASENJIKI01 (2 / 3) and NW_KOUSOUBLD01 (10 / 126). Of these, 7 group owners and 16 child records have matching static-mesh collision candidates.

This is a different denominator from the earlier 18 groups / 193 references across a 16-map source scope described above. Those results must not be added together or described as contradictory. In the studied EDF4.1 MAPB records, the +0x2C link acts as a record-index relation. It does not, by itself, establish child collision activation, parent_matrix × child_matrix composition or native EDF4.1 actor transform behavior. Unknown auxiliary integer fields are likewise not automatically scale or collision flags.

MAPO visual model, explicit .hkt resource and MAD body are different identities

For the same nine original maps, the source collision-routing audit partitions the 39,252 MAPB records into these record-level categories:

Source association MAPB records What it means
Explicit MAPO .hkt name matched a decoded mesh MAD body 5,944 A named candidate, not confirmed active Havok collision
Definition model matched a source MAD body without an explicit MAPO HKT route 5,469 A fallback candidate, not a verified game lookup
Explicit .hkt reference outside the mesh-only MAD census 145 Later resolved as compact-shape MAD bodies, not absent game files
No directly matched MAD collision binding in this limited census 27,694 Does not prove an object is non-colliding

The 145 cases were subsequently traced to five original fixed MAD rigid bodies across four maps, using just three distinct model names. They were missed because the earlier source census restricted itself to mesh geometry and excluded hkpBoxShape and hkpListShape. Thus “145 missing HKT files” is incorrect; the accurate statement is “145 originally unmatched mesh-route associations, now reconciled to compact MAD collision shapes”.

These synthetic hull faces are not automatically another active collision copy, not authored NAV walkability, and not proof of an EDF6 HKT loader dispatch.
