EDF4.1 native MAPB actor transforms and Havok 2014 body/filter evidence

ConversionMaps & NavigationCollision & NAVEDF 4.1EDF 6
Source-backed research / case study · Original EDF4.1/EDF6 static R58-R62; 18520 source bodies, 15 source cohorts, native target RTTI/vtables and group32 code; live NPC filter matrix UNKNOWN

Evidence: November 17, 2026, read-only original EDF4.1/EDF6 binary checks and an 18-map original EDF4.1 MAD corpus. Native parsing and algebraic verification are not evidence of successful EDF6 NPC navigation. The original game executables and private physics payloads are not included in this reference.

Two separate systems: placed actors and registered collision bodies

A map object's placement is not synonymous with a Havok body being active or blocking an NPC. The original map.mapb T2 placement record supplies a position and Euler rotation; the native actor loader constructs a base world matrix for that placement. The physics scene and collision/query filters then determine which serialized shapes actually participate in movement and hits. Navigation HKT/NVMD is yet another representation. A geometrically correct box or mesh does not automatically qualify as a pathfinding obstacle.

Native MAPB matrix construction: EDF4.1 and EDF6

A read-only comparison of the original game routines established the per-record base actor matrix in both pinned executables:

Attribute EDF4.1 original EDF6 target
T2 record stride 0x44 (68 bytes) 0x48 (72 bytes)
Translation three floats at record +0x04/+0x08/+0x0C same offsets
Euler angles, degrees three floats at +0x10/+0x14/+0x18 same offsets
Base actor matrix construction uses the record's own pose uses the record's own pose
Canonical routine RVA 0xFF420 0x1169B0

The independent relayout audit compared 42,388 / 42,388 placements across 18 original MAC files and found all six source translation/rotation floats byte-identical after the 0x44 → 0x48 relayout (the extra four bytes are appended). This confirms preservation of the stored pose, not proof that every physics body ultimately uses that pose unchanged.

The native routine arithmetic supports row-vector Rx × Ry × Rz rotation order, whose transposed column-vector convention is Rz × Ry × Rx. The conventional R23 column-vector placement formula is thus algebraically consistent with the two observed native routines. Both use degree-to-radian conversion. These are static instruction and mathematical equivalence results, not bit-exact SSE/libm float32 output comparisons. Differences in operation order and rounding can remain important to exact contact geometry.

Correction to older NAV research: An R57 experiment applying a parent's transform to an indexed child was only a sensitivity hypothesis. The base actor matrix itself is computed from each actor's own T2 record in the verified routines. This does not rule out later group attachment transformations, MAPB +0x2C child handling, Havok body-local motionState transforms, or alternative engine consumers. See EDF4.1 donor NAV and collision boundaries and MAPB cross-generation layout.

Original Havok 2014 map collision corpus: 18 MAD files

A separate read-only Binary Tagfile census of 18 original EDF4.1 .MAD files found exactly 18,520 serialized hkpRigidBody objects and one examined hkpPhysicsSystem per map. All 18 systems serialized active=1, but this is a source-file field; it is not a gameplay observation that every body was registered in the running Havok world.

Motion types are not automatic NAV eligibility

The hkpMotion.type values actually serialized in these 18,520 bodies were:

Serialized hkpMotion.type value Bodies
5 17,660
3 849
2 11

The counts total 18,520. The audit deliberately does not assign undocumented names such as “static NAV blocker” or “dynamic obstacle” to these raw values. In particular, all 860 records with type 2 or 3 require separate eligibility/activation treatment before their geometry is baked as an impassable NPC obstacle.

The omitted collisionFilterInfo field

The original Havok type registry declares hkpTypedBroadPhaseHandle.collisionFilterInfo, yet none of the 18,520 serialized rigid-body instances contains the field as an explicit value. The audit distinguishes a field's absence from an actual serialized zero. Similarly, broadPhaseHandle.type=1 on these objects is a handle-type observation, not a demonstrated collision-layer number.

It follows that a file reader cannot recover the original runtime NPC-contact layer matrix simply by using zero as the missing value, by treating every shape as collidable, or by transplanting EDF5's inferred layer table into EDF4.1 or EDF6. EDF6's later hknp collision filters and NPC query layers have to be established independently.

The table reconciles exactly to the earlier marginal totals: motion types 2 / 3 / 5 have 11 / 849 / 17,660 bodies respectively, and the shape-class sums match the original 18,520-body table above. A member's group label is not an NPC blocking rule. In particular, it cannot establish that any given Ranger/Fencer/Hector capsule should collide, that motion.type=5 always means an active static obstacle, or that an absent filter field defaults to any particular bit mask. Motion enum names, activation, query filter masks and later child/compound ownership remain separate unknowns.

The registry demonstrates that these interfaces/structures are represented in the target binary, including the group/pair/disable filter family and a character rigid-body configuration type. EDF6 Havok 2020 collision-filter dispatch: executable evidence beyond the type registry

Two later bounded examinations of the same pinned EDF6 DLL establish a stronger chain than type-name reflection alone. They found executable references and C++ virtual-method tables, and inspected a candidate group-filter decision function. This still concerns static binary behavior: no unmodified or modded EDF6 runtime call, in-world filter assignment or NPC collision result was observed.

What is directly present in the target binary

An x64 .text scan found three guarded references to native filter metadata: 0x135D34E and 0x135D402 refer to hknpGroupCollisionFilter; 0x1394F98 refers to hknpSetBodyCollisionFilterInfoCommand. The surrounding code resembles repeated type-descriptor registration and dispatch, so these references do not establish that the running game assigns any collision mask to an NPC or obstacle.

A separate native Microsoft x64 RTTI walk follows the verified TypeDescriptor → CompleteObjectLocator → vftable → executable code chain. The exact-build virtual tables resolved include:

Target native class Virtual-method table RVA Bounded executable entries
hknpCollisionFilter 0x1761B58 9
hknpGroupCollisionFilter 0x18BBFC0 9
hknpPairCollisionFilter 0x18BBAB0 9
hknpDisableCollisionFilter 0x18B0A90 9
hkaiNavigator 0x187B548 3
hkaiNavMeshInstance 0x187B4E8 3

The last two classes belong to the navigation side of Havok AI. Their coexistence with hknp* physics filter classes does not prove that a physics filter decides path graph connectivity; these remain different stages of movement.

Observed group-filter code branch

For the registered hknpGroupCollisionFilter table, zero-based virtual slot 6 points to executable RVA 0xD93700 in the exact DLL. This native method reads 32-bit values at [r9+0x8c] and [r8+4]. The examined instructions have a special comparison branch involving mask 0x7fff8000 and otherwise consult a 32-row table of 32-bit group masks at this+0x24. In that ordinary table path, one low-five-bit group value selects the row and another low-five-bit value selects its bit. The result is a candidate low-level allow/deny predicate for the examined branch, not a measured gameplay policy.

A second executable witness at 0xD93800 contains a 64-row, 64-bit branch. Its specific active world owner is unverified; the presence of that code is not evidence that EDF6 uses 64 groups for Rangers or any other actor. Neither function reveals the actual matrix contents in the running game. An absent native matrix row must be recorded as unknown, never synthesized as zero or treated as a rejected contact.

What an NPC-contact assertion would additionally require

An individual engine decision would need its real instantiated filter object, actual filterInfo pair, callback entry/return, actor identity, query context, map and a defensible MAPB/MAD body-to-source-cohort relationship. The source research's 15 cohorts across 18,520 original EDF4.1 rigid bodies can make this qualification class-based; it cannot supply the missing runtime values. The first evidence-gate inventory contained zero native callback events and thus 45/45 actor/cohort combinations (15 cohorts × three provisional actor profiles) remained UNKNOWN. None was accepted as a verified in-game collision pair.

Most importantly, a collision-filter return does not itself establish an NPC route: bad NAV connectivity, absent HKT polygons, low/high agent-profile mismatch, local avoidance, physical clearance and actual contact responses can each stop movement separately. The retained evidence therefore does not fix or validate Ranger, Fencer or Hector pathfinding on original EDF4.1 maps in EDF6.

What this resolves and what stays open

Resolved by read-only evidence: the original MAPB and EDF6 target record strides and pose-field offsets, original source-pose byte preservation in 42,388 placements, per-record base actor-matrix construction in both pinned native binaries, algebraic rotation order, original 18-map root-shape/motion-type counts, 15 observed joint cohorts and explicit-versus-absent filter-field status, target-filter reflection type presence, six bounded C++ vtables, and a verified native 32-group filter-code branch.

Not resolved: bit-exact runtime matrix rounding, secondary group/child transforms, original-world contact activation, Havok 2014-to-2020 filter mapping, actual instantiated group/pair filter and its matrix values, NPC controller query pair rules, native LOW/HIGH agent profiles, or improved EDF6 Ranger/Fencer/Hector navigation. No new HKT/NVMD was installed or gameplay-tested by R58–R62. These are constraints on future NAV analysis, not a declaration that the AI problem has been fixed.
