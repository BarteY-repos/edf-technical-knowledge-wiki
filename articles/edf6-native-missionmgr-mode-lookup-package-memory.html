Documentation / EDF 6 / Mission mode and save

EDF6 native ModeList lookup, SetGameMode and active Package

EDF 6Missions & ScriptingMission mode and save
Technical reference · EDF6 build-specific static disassembly; one separate bounded negative modified-runtime observation

This reference separates three different native operations in a studied EDF6 executable: loading the game-mode definitions, choosing an active mode, and materializing the package that supplies mission/character/weapon resources. Treating these as one interchangeable setter is unsafe, particularly in reverse-engineered compatibility work.

Binary/build scope

The specific EDF.dll used for this study had SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916, image timestamp 0x678CCB46, and PE SizeOfImage=0x022CE000. All addresses below are offsets relative to this EDF.dll image, not portable signatures, game-version-independent API declarations or absolute addresses.

Two research names, MissionMgr and GameDataMgr, are sometimes applied to the same central manager. This article therefore uses the neutral term manager where the exact RTTI class name is not independently proven.

Lookup layout — source-backed offsets

FindOuterMode was reconstructed with the following logical signature:

int FindOuterMode(Manager* manager, int modeType, int missionPack);

Its observed traversal is:

  1. Read the outer collection from manager+0x20 and its count from manager+0x30.
  2. For each outer item, follow its +0x10 ModeList-like pointer.
  3. Read the selected row offset/index from that ModeList-like object at +0x08.
  4. Compare the selected row's MissionPack at +0x74 and mode type at +0x80 against the requested pair.
  5. Return the matching outer index, or -1 when there is no match.

The native direct-call census for the lookup named four call sites: EDF+0x70E704, +0x70E74C, +0x8EFEF1, and +0x954333. This is a build-local call census, not a promise that indirect calls or later builds cannot introduce other paths.

The outer index returned by this function, the MissionPack numeric ID stored in a selected record, and the active physical MissionPack are distinct fields. A value read from one cannot be substituted for another without a lookup.

Active-mode transition

The native transition at EDF+0xDC460 expects RCX=manager and EDX=requested outer-mode index at the observed entry point. In the examined control flow it selects the outer record and invokes the package-building path at EDF+0xE2AD0 (call observed around +0xDC4B3). Later, it publishes the selected outer index to manager+0x38 (around +0xDC4C5) and emits an event identified as 0xE in the retained reconstruction.

The direct native call-site census for this transition found +0xAC21A, +0xD6722, +0xDB6BF and +0x70FAC9 in the audited .text. A function that changes the active mode is consequently not equivalent to setting a menu selection integer or appending an extra ModeList row.

Active Package and mission/save resources

The LoadPackage path materializes the active Package at manager +0x130. The following child fields were identified in the studied layout:

Active Package field Supported interpretation
+0x20 SoldierInit-related node
+0x28 Weapon-category/map-related data
+0x68 MSVC std::wstring-style package / MissionPack MST namespace
+0xF0 DSGO/node reference to the mission table

This explains why a valid ModeList row alone is not sufficient to establish a playable/complete game mode: later package materialization can still require related PackageName, SoldierInit, SoldierWeaponCategory, WeaponTable and WeaponText roots from the selected config source. These are observations from a tested extension/reconstruction context, not a claim that every native official pack loads from separate CONFIG files.

For the on-disk MST layout and class difficulty bits, see GST/MST save and progress tables. For the cross-file LIST/TXT/image requirements, see EDF5-derived MissionPack metadata.

Why save safety matters

One historical modified-runtime test inserted an extra SetGameMode invocation in a user-interface callback where the original game would not have made that call. The user observed armor and collected weapons reset, and the damaged state was written on game exit. Later analysis found the high-level call also enters LoadPackage and rebuilds the active package. The exact downstream instruction chain from this call to the save writer was not completely demonstrated. Therefore this is direct evidence that that injected transition can be destructive in the tested modded configuration, not evidence of spontaneous save loss in unmodified EDF6.

The native takeaway is narrow but important: configuration registration, mode selection, package rebuilding and persistent progress are related, but distinct state transitions. For delayed pack-ID publication, see asynchronous lobby/mode lifecycle.
