SGO — file structure, typed nodes and resource usage

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: An SGO stores structured game data as named values and nested arrays. It is closer to a configuration/data tree than to a mesh, texture or animation clip.

Where it fits: The documented values include integers, floating-point numbers, strings, raw bytes and arrays; different resources give those values different meanings.

Important distinction: Do not choose an SGO decoder solely from the file extension: some EDF6 resources named .SGO actually use DSGO encoding.

Identifying an SGO file

  • In the documented EDF5/EDF6 little-endian profile, the signature is SGO\0, with version 0x102 (decimal 258).
  • Some documented SGO resources are big-endian and use the reversed signature \0OGS; their header, variable and name-table fields also follow the big-endian layout.
  • A filename ending in .SGO is not sufficient to choose the decoder. EDF6 also has DSGO-encoded resources whose names end in .SGO.

These are observed profiles, not a claim that every EDF generation or every resource uses an identical layout.

The conventional SGO header exposed by the community format reference has the following six 32-bit words (0x18 bytes). Read integer fields using the byte order established from the signature:

OffsetFieldMeaning
+0x00char[4]SGO\0 (little-endian profile) or reversed signature in the documented big-endian profile
+0x04u32Version (observed 0x102 in the EDF5/EDF6 classic profile)
+0x08 / +0x0Cu32 × 2Top-level variable count / variable-table position
+0x10 / +0x14u32 × 2Named-variable count / name-table position

The separate name lookup has 8-byte entries: a string reference at +0x00 (relative to that entry in the examined layout) and a top-level variable index at +0x04. Validate that the index and decoded UTF-16 name stay within the file; the name-table count need not be silently substituted for the value count. The older source notes possible differences in EDF 2017, so this table is not a claim about that earlier generation.

The basic node model

The documented little-endian SGO format uses a 12-byte node containing three fields: int type, int a, and uint b. The interpretation of a and b depends on type.

Node type Meaning Stored interpretation
0 Array a is the element count; b is the child offset relative to this node
1 Integer Integer value stored in the node
2 Float Floating-point value stored as its bits
3 String a is length; b points relatively to UTF-16 string data
4 Raw data a is byte size; b is a relative data offset

In the documented EDF6 layout, the top-level values are sorted by name using ordinal ordering. The name table references values by index and stores offsets relative to its own entries. Child blocks follow the top-level table in depth-first order; the name table and pooled names/string values follow later. The cited byte-for-byte round-trip result applies to the examined layout, not arbitrary unknown variants.

Worked example: a small typed data tree

Imagine a fictional configuration with three named values. These names are for teaching the data model, not actual EDF field names:

NameSGO node typeDecoded value
Count1 — integer10
Scale2 — float1.5
Label3 — string"Sample"

These values can be nested under a type-0 array node. The parser learns how to read each value from its node type; the game decides what a name like Scale means through the resource-specific schema. The binary file stores a node table, relative offsets and name strings, not this illustrative table or JSON text.

What SGO files contain

SGO is a container for resource-specific data. The research corpus includes configuration, layout/UI and object/weapon resource examples. A field that is meaningful in one resource's schema cannot be assumed to have the same meaning in another.

For a concrete mission example, the studied MISSIONLIST.OFFLINE.TXT.EN.SGO-style name/description tables use classic SGO version 258. The associated ...LIST.SGO resource uses DSGO instead. The resource name, binary signature and known schema must all be considered.

Reading or converting an SGO safely

  1. Inspect the actual signature and byte order.
  2. Validate the version, node ranges, counts and relative offsets.
  3. Decode the typed tree and its names without silently discarding unknown values.
  4. Determine the specific resource schema before interpreting or changing field semantics.
  5. Keep byte-level round-trip, structural validity and successful in-game loading as separate claims.

The original research distinguishes semantic merging from byte concatenation. A baseline-relative merge can use stable names or schema-defined record keys, but an ambiguous variable-length array must not be merged using guessed identity.

Relationship to DSGO

DSGO is a separate serialization family with a different signature, 16-byte nodes and additional node semantics, including embedded resources and expressions. See DSGO — structure and expression nodes for its measured layout.
