BVM bytecode and custom calls

UniversalMissions & ScriptingScriptingEDF 5EDF 6
Technical reference · Exact native / Reconciled with scoped runtime evidence

A custom-call number is an operand, not a new bytecode instruction. That distinction is important when reading EDF mission scripts. The EDF5/EDF6 MISSION.BVM frontend uses compact VM instructions and encoded operands, while the actual engine action is selected by a custom-call identifier. The target AngelScript API may express the same action as a method, a global function, or—occasionally—have no exposed binding at all.

Source-identity caution: The inspected clean EDF5 shipping BVM corpus is not byte-identical to the EDF5_OLD_SCRIPT files stored on the EDF6 side (0/141 exact pairs in the audited set). See the source-identity comparison. This matters when attributing an opcode or custom call to original EDF5 behavior.

Reading an instruction correctly

In the researched BVM stream, byte 0xAC represents the cuscall0 opcode. If the following argument bytes are D0 07, their little-endian value is 0x07D0 = 2000, which identifies an engine custom call. Neither D0 nor 07 should be interpreted as a second BVM opcode.

AC D0 07
│  └─┬─┘
│    └── u16 LE custom-call ID = 2000 (0x07D0)
└────── cuscall0 opcode

The example establishes the operand/dispatch distinction; a full decoder must still honor each instruction's actual arity, stack convention and length. The observed invalid/crashing BVM instruction opcode range is 0x39–0x3F, not merely 0x3A–0x3F. This bytecode range is unrelated to custom-call identifiers such as 2000 or 3450.

Engine-call identity and port mappings

The following mappings are drawn from paired EDF5 scripts, native EDF6 AngelScript material and binary-backed translation work. They apply to the inspected call signatures and contexts; they do not imply that arbitrary object types support every method.

Source custom call Studied effect Target-side expression / constraint
2000 Create enemy CreateEnemy semantics; not a misread opcode
2001 Alternate enemy creation CreateEnemy2, independently distinguished from 2000
2008 Area enemy-group creation CreateEnemyGroup_Area; not inherently flying-only. Separate spawn steps may be required
3100 AI route/movement speed SetAiMoveSpeed(...); an older SetAiRouteSpeed name is superseded
3101 Assign AI route SetAiRoute(...) in the paired context
3102 Assign AI path SetAiPath(...), independently distinguished from route assignment
4004 / 4005 Random AI conversation EnableAiRandomTalk() / DisableAiRandomTalk() rather than a forced constant
3450 Search/encounter radius Runtime effect known, but no exposed AngelScript binding established for the audited build

These are examples of semantic translation, not literal replacement of numeric IDs with arbitrary text. A translator must preserve source argument order and types, ownership of the target object, execution timing and preconditions. The retained ASCOMMON.H reference defines RadioBegin and RadioEnd as provided helpers; earlier notes inferring they must be engine built-ins from a native script's direct RadioVoice() usage were superseded. Their definition does not imply every source mission calls them: preserve direct Voice calls, higher-level radio wrappers and their distinct source control flow rather than swapping them by name.

Why call 3450 cannot simply be renamed

Exact-binary analysis identifies 3450 as an object + float operation. The EDF5 BVM handler stores the value at Object + 0x2E0; the EDF6 BVM equivalent stores it at Object + 0x470. A separate EDF6 native helper performs that target write, but the reviewed AngelScript interface did not expose a matching binding.

It is not safe to substitute the similarly named SetEncountReportRadius (3024) or SetAiFormationRadius (3150): they access different object fields and have different effects. In the examined shipping set, 3450 occurred six times in DLC/DM006_2. The later user-accepted compatibility policy deliberately omitted these specific writes after a 3450-OFF runtime test loaded, spawned the frogs and reached mission completion. Emit an explicit accepted-fidelity-loss warning, not a silent drop. Exact semantic parity remains unproven, but this is no longer a blocker for documentation or the playable port.

Six independently reconstructed object/vehicle stack contracts

Beyond the enemy/AI table above, the paired source BVM stack and EDF6 target signatures were independently checked for cuscall0 52 (SetEnablePause(bool)), cuscall0 910 (DeleteMob()), cuscall3 1000 (SetMoveArea(string)), cuscall0 1024 (RideVehicle(Object)), cuscall0 1027 (SetupVehicle(Object)), and cuscall0 1028 (Object.Vehicle_SetRideEnable(bool)). In the last case the BVM stack contains object receiver below boolean, while the AngelScript method takes only the boolean explicit parameter.

This is why decoding a method call as a global function, or flattening all call banks into one numeric namespace, can change game behavior even when the visible API name looks appropriate. The complete small table is in BVM custom-call reference. The reconstructed source/API mapping is statically verified, not a fresh EDF6 in-game test.

Registering and scheduling events

Event registration is a separate layer from the VM custom-call opcode grammar. In the audited BVM scheduler, multi == 1 processes all ready registrations; otherwise it selects the highest-delay ready registration. The target EDF6 AngelScript event types are equivalent in scheduling behavior:

BVM multi == 1  → EVENT_TYPE_ASYNC (1)
BVM multi != 1  → EVENT_TYPE_SYNC  (0)

This is based on the compared EDF5 and EDF6 native schedulers, not just names. In the measured 141-mission corpus, 5,193 raw registrations reduced to 5,112 reachable registrations (4,540 with multi=0, 572 with multi=1). The other 81 were unreachable scaffolding; do not publish them as active mission events. The source multi and target EventType are different physical fields: equivalent behavior does not mean identical ABI layout.

What an implementer should do

  1. Decode the VM stream and operand widths before interpreting call IDs.
  2. Reconstruct the stack values, object identity and actual argument order at the call site.
  3. Compare source effects against paired native target scripts or binary consumers.
  4. Keep mission registration/factor/handler topology separate from the textual order of decompiled methods.
  5. Preserve unknown calls and fail explicitly; don't invent a convenient replacement.
  6. Verify the output through source/compile and, when claiming gameplay parity, actual runtime evidence.

Evidence: exact EDF5/EDF6 BVM scheduler and 3450 binary contract (studied 2026 builds); paired mission scripts and the R37 transpiler research. No general claim of runtime parity for every EDF5 mission API. For related information see event registration and re-arming, accepted 3450 fidelity waiver and mission RMPA.

VM stack and side effects: avoid silent event changes

Not all target AngelScript helpers return the same kind of value that the source VM expects. A particularly important group of source BVM calls is side-effect-only:

2002 2003 2004 2005 2006 2007 2008 2009
2010 2020 2021 2022
902  (CreateMob_Path)

In the studied 145-mission source set, the group transaction family above had no immediate result consumer (store, storeabs, storerel, cvtstore, pop) and had to be emitted immediately as statements. Retaining a target helper's return expression on the simulated VM stack caused later calls to consume or reorder it, which had caused missing UFO group creation in M020/M080. For opcode 902, delayed emission also moved CreateMob_Path calls after SendTeamEncount in M008, changing gameplay order.

The same exact-pair analysis establishes that direct cuscall0 4000 with a voice string is Voice(string), not PlaySe. It must also be distinguished from higher-level RadioVoice wrappers whose implementation might contain the same low-level custom call.

The general rule is: reconstruct source stack effect and source side-effect ordering, then map the target API; do not infer source return semantics from the target function's signature. These are exact-corpus findings, not a declaration that every custom-call ID has been reverse engineered.

EDF4.1 native IDs are not EDF5 custom-call IDs

See the EDF4.1 BVM→EDF5 exact recompile guide. It distinguishes EDF4.1 table-1 native 3000 SetEncountReportRadius (requiring a custom plugin table-1 3003 in the studied compatibility path) from EDF5 cuscall0 3450 SetAiSearchRadius (a separate, consciously omitted six-call effect). Native IDs must be interpreted with their table and generation, not mapped by similar human names.

EDF4.1 example: CreateEnemy2 is observable as distinct call sites

The original EDF4.1 M014 decompiled BVM uses 20 calls to cuscall0 2001: eleven source Nephila and nine SpiderNet20/40/80 resources, some referencing the same named map spawnpoint. By contrast, original EDF4.1 M002 uses ten cuscall0 2000 sites for single enemies, and M001/M003 use the 2002 group-creation form. This is a bounded six-mission illustration of different custom-call operands, argument lists and resource classes, not evidence that 2000/2001/2002 can be substituted at runtime.

The two CreateMob_Path (902) calls and seven CreateFriend (1010) calls in original EDF4.1 M014 likewise show that crowd/path, allied and hostile creations share a mission graph without sharing one interchangeable API. Do not conflate this EDF4.1 M014 city-script example with EDF5 M014 “Secret of the Cave” and its three-source-call reinforcement fix. See the EDF4.1 six-mission native BVM comparison; this edition inspected the decompiled source statically and ran no gameplay parity test.

R173 registration graph caution: a callback body is not itself an event

A static function list can overstate the events a mission has actually wired. In the original EDF4.1 BVM subset M001–M004, M012, M014, R173 followed RegisterEvent (cuscall0 2) callback names starting from Main and derived a bounded registration-closure graph. A procedure may exist without being registered anywhere in that graph (e.g. EDF4.1 M002's Func1709960674); another procedure may contain a registration that never enters the Main-rooted closure (EDF4.1 M012's Func1974397686 registering Func801877805).

For M012, immediate factor calls such as 9000 wait, 9100 all-enemy-destroy, 9201 object-destroy and 9300 AI-movement-end are distinct conditions attached to registration sites. In one case, the native source registers Func508242891 and then lists six 9300 sites corresponding to six carrier references. This is not license to assume they behave as a simple simultaneous AND, a linear wait, or a fixed time delay: exact factor grouping and runtime scheduling require independent engine-level evidence. RegisterEvent source presence alone establishes authored registration, not event execution.

Evidence and limitation: static six-file EDF4.1 decompiled BVM graph, data/R173_EDF41_BVM_EVENT_REGISTER_GRAPH_EDGES.csv and data/R173_EDF41_BVM_EVENT_CALLBACK_CLOSURE.csv. It is not the 44-pair native EDF5 scheduler study and does not override its separate confirmed EVENT_TYPE_SYNC/EVENT_TYPE_ASYNC findings. No EDF4.1 or EDF6 gameplay was replayed for R173.
