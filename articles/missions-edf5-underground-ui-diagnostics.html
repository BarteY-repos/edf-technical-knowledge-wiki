EDF5 underground mission ports: historical UI and host-mode diagnostics

ConversionMissions & ScriptingMissionsEDF 5EDF 6
Technical reference · Historical exact source and offline static audit; runtime correction specifically noted

Scope: a historical, source-scoped diagnostic sequence, not a recommended current patch. Later direct runtime tests of custom M000, M001 and DM019 confirmed the native-like flags=40 restriction. Read the current underground flag/runtime rule before applying any older hypothesis.

Why the first diagnosis was misleading

The early MP03 M001 investigation observed Air Raider equipment restriction offline but apparent online permission, even with mission-list flags=40 (0x08 | 0x20). The initial interpretation treated red menu presentation and real weapon/support activation as if they had the same semantics; later in-game checks refuted that blanket conclusion.

Two independently plausible interference paths were examined. Both remain useful diagnostic examples, not confirmed fixes for a newly observed issue.

1. Global OnlineLimitsDisabled UI setter

The inspected mod patch replaced a shared native UI setter (the studied binary's mov byte ptr [rcx+0x71], dl; ret) with an unconditional 1 write. Twenty-three call sites use that setter, including unrelated item, cursor, room, mission and difficulty controls. Consequently, removing the disabled appearance for online armor/weapon-limit buttons could also re-enable unrelated UI states.

A proposed narrower alternative targeted only the two identified room-setting calls for Button_ArmorLimit and Button_WeaponLimit, without changing the common setter. Its exact match positions were binary-build-specific (0x91C8BF and 0x91C9AB file offsets in the studied DLL); these addresses are not portable across versions. That proposal had STATIC PASS / RUNTIME PENDING status and was conditional on an A/B test proving this hook caused the actual symptom.

Rule: never modify a shared UI setter globally when only two specific room controls are intended, and never infer in-mission weapon authorization from a red/disabled equipment entry.

2. Host-side mode refresh

The compared source flow was:

  • EDF5 PlayMission_Common: called ApplyModeNo(new_mode_index) for host and client before SetUsedWeapon.
  • Studied EDF6 PlayMission_Common: called ApplyModeNo(sync.GetNewMode()) inside !IsGameHost(), relying on earlier lobby selection for the host.
  • The R5 candidate made ONLINE call the common routine with a refresh flag and preserved the native client-only rule for OFFLINE.

This was an intentionally isolated MainScript-only STATIC PASS / RUNTIME PENDING candidate. The later R6 diagnostic explicitly labeled that R5 MainScript as runtime-negative for the symptom and proposed removing it after the A/B unless new evidence justified it. Neither R5 nor the subsequent per-mission R7 SetWeaponCondition(NO_SUPPORT) experiment may be promoted to a mandatory authoring rule.

What later evidence actually settled

The actual in-mission support-request test, not loadout selection color, confirmed native-style flags=40 enforcement for M000, M001 and DM019 in the tested deployments. Maintain the established metadata 0x20 path; do not globally rewrite it to 0x200, inject forced condition calls into all missions, or deploy an untested MainScript override based on the early symptom report.

For a fresh regression, isolate variables: record the actual selected pack and mission, host/client and OFFLINE/ONLINE modes, deployed LIST flags, custom patch state, plus whether a conventional air raid/vehicle request succeeds in mission. Distinguish a menu-only discrepancy from a state/write discrepancy before modifying game code.
