EDF 5Community Knowledge HubGameplay & AI
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested
Evidence and uncertainty: “Source: unverified” labels reproduce the contributed research’s own evidence grade. These entries may be hypotheses, untested approaches or community reports; they are not independent runtime verification. Original wording, build identifiers and fact IDs remain available below.

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Scene camera and projection

SceneCamera (xgs::game) fields: +0x24 vertical FOV (radians), +0x28 near, +0x2C far

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-scenecamera-fields

SceneCamera (xgs::game) fields: +0x24 vertical FOV (radians), +0x28 near, +0x2C far. The constructor 622290 sets 0.785 / 0.1 / 1000 (mov [rsi+0x28],0x3DCCCCCD at 6223EC).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 622290, 6223EC

The camera's forward direction is the snapshot view matrix's row 2 times sign(P14)

Evidence: verified · Build: steam-5d11de53 · Fact ID: camera-view-forward-from-snapshot

The camera's forward direction is the snapshot view matrix's row 2 times sign(P14); its y component gives the aim pitch (an arcsine series is within about 1 degree up to 55 degrees).

Basis: novae (ajane)

Player camera update

CharacterGhostCamera target pointer and update

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-update-target-and-look-block

CharacterGhostCamera::Update 9F260 (vtable E93548 slot 4) locks the target weak pointer at camera+0x290 (raw object at +0x2A0, control block +0x298) into its local [rsp+0x20]/[rsp+0x28] (lock call 741C0 at 9F2A0; null when there is no target, path 9F3EE; released at 9F3F7, but the local pointer is not cleared, so the target is a live object during the tail). It copies the target matrix rows target+0x70..+0xA0 to camera+0x2B0..+0x2E0 and the look state from target+0x100 (or target+0x180 when byte target+0x170 != 0) into camera+0x2F0..+0x350: +0x300 local camera offset, +0x310 lerp factor, +0x350 zoom. Time accumulator +0x428.

Basis: disassembly of 9F260-9F4FF; novae (ajane)

Addresses (build-specific RVAs unless indicated): 9F260, 9F2A0, 741C0, 9F302, 9F3EE, 9F3F7, 9F3D7

Attribution: novae (ajane) · 2026-10-07

Per-frame camera update hook site

Evidence: verified · Build: steam-5d11de53 · Fact ID: camera-tail-hook-site

The end of Update, inc dword ptr [rdi+0x424] at 9F4F3 (6 bytes, rdi = camera), is a working per-frame hook site: the target is still locked in the local [rsp+0x20] and the camera fields are final for the frame. Hook: E9 to own code, replay the inc, jump back to +6. Only one patch can own the site.

Basis: novae (ajane)

Addresses (build-specific RVAs unless indicated): 9F4F3, 9F260

Attribution: novae (ajane) · 2026-10-07

Camera follows soldier while riding vehicles

Evidence: verified · Build: steam-5d11de53 · Fact ID: camera-target-stays-soldier

While the player rides a vehicle the camera target is still the soldier, and the soldier has no scene parent (the vehicle is not its parent in the scene tree); find the vehicle through the ride link (player.md#ride-link-fields).

Two modes of player-camera update

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-mode-state-machine

The player camera runs one of two modes: Update calls the mode object at camera+0xAE0 (call [vtable+8], edx = 1, at 9F45F); follow mode 9F590 switches to ride mode A0130 when the target's ride control block [target+0x1170] has users (9FFDC-9FFEE: lea of A0130, state installed through camera+0xAE8, old state called with edx = 2), and ride mode switches back when it has none (A033C-A034E). Member-function-pointer state at camera+0xAE8 (state object [+0x10]). Ride mode reads the seat record [target+0x1160]: [seat+0x200] == 1 builds the camera from the bone matrices at seat+0x208 / +0x218 (A01A2); the ride update switches on [seat+0x200] at A03B4.

Basis: disassembly, re-read 2026-10-24 for the EDF6 comparison

Addresses (build-specific RVAs unless indicated): 9F45F, 9F590, A0130, 9FFDC, A033C, A01A2, A03B4

Attribution: novae (ajane) · 2026-10-24

The final world matrix is camera+0x1A0 / +0x1B0 / +0x1C0 (rotation rows) and +0x1D0 (eye position, w = 1)

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-final-matrix

The final world matrix is camera+0x1A0 / +0x1B0 / +0x1C0 (rotation rows) and +0x1D0 (eye position, w = 1). Follow mode writes +0x1D0 at 9F7E4, 9FB03, 9FF9C and the rows at 9FFAD-9FFBC; ride mode writes them at A077D-A07A8; the optional shake A5900 (called at 9F49D) multiplies the rows by +0x200; nothing writes them after the tail. The render submit (vtable slot 5, A0E00) copies them into the render record at A1068; slot 3 9EB50 copies them to +0xA90..+0xAC0 (probably the previous-frame copy, unverified). Systems that find the camera through the per-view table [125AB68] (0x188 bytes per entry, camera weak pointer at +0x238) read +0x1A0..+0x1D0 directly (e.g. 302760, 47A670).

Basis: disassembly (2026-10-07, first-person feasibility check)

Addresses (build-specific RVAs unless indicated): 9F7E4, 9FB03, 9FF9C, 9FFAD, A077D, A07A8, A5900, 9F49D, A0E00, A1068, 9EB50, 125AB68, 302760, 47A670

Attribution: novae (ajane) · 2026-10-07

The eye +0x1D0 is lerped from its own stored value each frame (9F7D4: pos = old + (desired - old) +0x310

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-eye-lerp-and-view-source

The eye +0x1D0 is lerped from its own stored value each frame (9F7D4: pos = old + (desired - old) * [+0x310]; 9FAEC: toward +0x440 by +0x430), and the view rotation is built from the soldier's look block (5BE8F0 from +0x2F0 - +0x300 at 9FB7F / 9FBBC), not from the eye. So moving +0x1D0 at the tail only translates the eye (the aim is unchanged), but the value becomes next frame's lerp base and the collision sweep's start: save the game's value and restore it before the next Update. Where the crosshair hit point is computed was not found (eye-to-muzzle parallax untested).

Basis: disassembly; not run in game

Addresses (build-specific RVAs unless indicated): 9F7D4, 9FAEC, 5BE8F0, 9FB7F, 9FBBC

Attribution: novae (ajane) · 2026-10-07

Camera collision and push-in

Havok phantom sweeps controlling camera push-in

Evidence: verified · Build: steam-5d11de53 · Fact ID: camera-push-in-phantom-sweep

The push-in (the camera snaps toward you when something is between you and its spot) is a Havok shape phantom at camera+0x418, created at 9E55E by 752860(shape [camera+0x410], info, filter 0x16) (collision layer 22) and swept with the phantom's vtable +0x78 (setPositionAndLinearCast: rdx position = target+0x2E0 with a height offset, r8 cast input with the end point, r9 collector, [rsp+0x20] start collector) into an hkpSimpleClosestContactCollector on the stack (vtable D9D420; addCdPoint 713CF0 keeps the closest contact: hasHit +0x10, contact +0x20 / +0x30, early-out +8; reset A58D0). Four call sites: 9FDAF and 9FECE in follow mode 9F590, A4478 and A456D in A4380. Contact layout: physics-havok.md#cdpoint-cdbody-layout.

Basis: static; novae (ajane)

Addresses (build-specific RVAs unless indicated): 9E55E, 752860, D9D420, 713CF0, A58D0, 9FDAF, 9FECE, A4478, A456D, A4380

Attribution: novae (ajane) · 2026-10-07

Camera sweep early-stop flags

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-pushed-in-flag

After each of the four casts the game's own collector says whether the sweep was cut short: byte collector+0x10 (hasHit) is nonzero exactly when something that still counts stopped the camera this frame. The contact distance (normal.w at collector+0x3C) is probably the fraction along the cast (Havok linear-cast semantics, unverified).

Basis: follows from addCdPoint 713CF0; novae (ajane)

Addresses (build-specific RVAs unless indicated): 713CF0, 9FDAF, 9FECE, A4478, A456D

Thin-prop contact filtering tradeoffs

Evidence: verified · Build: steam-5d11de53 · Fact ID: camera-prop-pass-behavior

Dropping a map object's contacts from the sweep works well for thin props (lamp poles, forklifts) but makes bulky or double-sided props worse: the camera ends up inside a tent or crate stack whose inner faces fill the view, and passing large level pieces puts the camera outside the level or under the ground. Which classes are what: map-objects.md. A size limit from the collision shape's AABB (10 m, physics-havok.md#shape-getaabb-slot) is untested.

Basis: novae (ajane)

Attribution: novae (ajane) · 2026-10-07

TargetCollector Havok group-filter check

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-targetcollector-addhit

The TargetCollector's add-hit AB890 (vtable slot 1) applies the Havok group filter first (7155F0, filterInfo collector+0x10 vs collidable+0x2C); the hit body is rdx + (signed byte [rdx+5]); for a collidable whose type byte (+0x28) is not 2 (2 = accepted only with a key-1 property) and when collector+0x38 is set, it looks up the attached SceneObject (property list at body + (signed byte +0x20) + 0xB8 pointer / + 0xC0 count, 16-byte {key u32, value u64}; key 1 here, key 0 holds the SceneObject), dynamic_casts it to MapObject_Base (source TD 11A49C0 SceneObject, target TD 11A4830) and skips the hit if its virtual +0x78 returns true; an optional filter callback at collector+0x28 (argument +0x30) can veto hits too. It returns 1.0 (constant EE6430) on every path.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): AB890, 7155F0, 11A49C0, 11A4830, EE6430

Attribution: novae (ajane) · 2026-10-07

Camera weak reference and pose history

Weak pointer lock and GameObjectBase target cast

Static, steam-5d11de53. Update 9F260 calls 741C0 to lock the MSVC weak_ptr at camera +0x290/+0x298, then 73EA0 to __RTDynamicCast the object from xgs::game::SceneObject to GameObjectBase. The camera object is held by view slot zero's weak pointer at [125AB68]+0x238 (control block +0x240). A proposed followed-character chain is [[[125AB68]+0x238]+0x290] only if the RTTI cast leaves pointer address unchanged; Eiton's player chain dereferences a further +0x10. Neither chain was confirmed by simultaneous live memory inspection, and target vs player must not be assumed identical.

Slot-3 snapshot and slot-5 view projection matrices

Static. CharacterGhostCamera (vtable E93548) slot 3 9EB50 copies current matrix +0x1A0..+0x1D0 to +0xA90..+0xAC0 and float +0x428 to +0xAD0 before its own work; slot 4 9F260 rebuilds pose. Render slot 5 A0E00 makes a view matrix from that saved transform, multiplies it by perspective 5BE600 and writes product +0x390..+0x3C0; live matrix is separately copied to +0x3D0..+0x400. Thus +0x390 is a pre-last-step projection and would represent the previous frame if slots 3 and 4 run in that order each frame. Call ordering and the actual on-screen pose were not traced.

Scripted camera look state and HUD interplay

BVM calls 420/421 send finite-duration camera messages

Static. EDF5 cuscall0 420 invokes 11C290(script,object_id, five_floats) and sends camera message 0x80000020 to all views via game-system 613CB0; payload includes target, point (x,y,z,1), priority 1.0, fourth float and fifth float times 60 frames. Call 421 invokes area form 11C3F0 (area argument inferred from EDF6) and sends the same message. Low-byte dispatcher cases are shared with talk commands 4004/4005, not proof of identical behavior. Source found only these two camera-message senders; no explicit stop or endless-look native. The finite frame countdown controls termination.

Message handling, priority and active look byte

Static. Camera vtable slot 8 AA2D0 receives 0x8000001F shake (max kept at +0x1F0), 0x80000020 look start (accepted at sufficient priority relative to +0x260, state copied to +0x240, target-live +0x280) and 0x80000021 HUD-list forwarding. Each tick AA150..AA1D8 sets active +0x281 while finite +0x268 frames remain, except paused frames, and clears it when target dies or timer expires. HUD byte +0x180 is hidden only when look block +0x330 is set and active byte +0x281 is zero; unlike EDF6, the scripted look does not uniformly hide EDF5 HUD.

Character weak-reference override is an open lead

Static candidate, not a completed dataflow. In A2C10 a live character-target weak reference at character +0x970 is locked, and owner +0x140 set to 1 with +0x150 copying target position +0x10; absent target clears it. It is not yet established that +0x140 is the state copied into camera update 9F260, or who populates character +0x970. Treat this as a candidate for HUD-hiding scripted look behavior, not a validated memory chain.
