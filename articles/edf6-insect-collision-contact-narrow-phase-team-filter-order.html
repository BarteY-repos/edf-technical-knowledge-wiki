EDF6 insect contact queries: candidate filtering, team relations and narrow-phase cost

EDF 6Game technical referencesPhysics and AI
Technical reference · Source-derived; evidence grades and build restrictions described in article; no new EDF runtime

In the examined EDF6 Steam binary, a particular insect-related contact check performs a full world collision query before discarding many non-hostile results. This is important for understanding the cost of a crowded scene, but it does not establish that the same call path is used by every insect attack or every swarm.

Observed query chain

The study identified a candidate contact routine at EDF.dll+0x429B00, called from +0x431B80 at +0x4322AC. It reads a collision filter, builds a list of 0xA0-byte hit entries and calls the common world-query routine +0x542860. The latter has five known direct callers; only one was associated with this insect-related site.

The broad world query visits body IDs, resolves a body and its owner, skips null owners and the querying object itself, invokes the narrow collision phase (+0x11AA270) and appends contacts that pass. These operations happen before the caller makes its later hostility decision.

The function lies near RTTI/vtables for GiantDango, but the source did not confirm the exact in-game creature that owns this call site. The adjacency must not be promoted to a resolved class identity.

Post-query team filtering

Back in +0x431B80, the caller locks weak references for the recorded hit entries and reads team IDs at object +0x314. If both IDs are valid (not -1), it retains a hit only when the querying team's relation table says the target is hostile (2). Otherwise the contact can be discarded after the more expensive collision work has run.

This means that in a same-team swarm some narrow-phase intersections can be computed only to be thrown away. It does not imply friendly units collide or attack one another in the final gameplay result.

Where performance claims stop

A separate contributor explored moving that hostility predicate to the candidate loop before narrow-phase testing. That explains a potential optimization principle, not a measured speedup: the original hub explicitly marked the claimed large FPS gain unverified. Counts of candidates and excluded non-hostiles would be needed to quantify it. Moving the check can also change behavior if team IDs are missing or relationship tables are inconsistent, so source equivalence alone is not gameplay parity.

Evidence level: static disassembly / known caller mapping for steam-678ccb46; no new profiling or runtime performance measurement in this wiki revision.
