EDF4.1 SK heightfields — converting SHFB terrain into EDF6 FMB and MAD

ConversionMaps & NavigationMapsEDF 4.1EDF 6
Technical reference · Exact-source SHFB/FMB/MAD reverse engineering, real-source offline tests; no fresh game runtime

What actually differs between these map generations

Seven examined EDF4.1 map families — SK_HEIGEN02, SK_VALLEY01, SK_KAIGAN01, SK_SANGAKU01, SK_SANGAKU02, SK_STEPMOUNTAIN01 and SK_CRATER01 — use a terrain asset named <model>_fld2mgrid.shfb. The examined EDF6 engine uses mesh-based FMB terrain, an associated FieldRender texture-array contract and hknp compressed-mesh collision. In that target build, rewrapping the EDF4.1 SHFB header or relying on Havok's old heightfield migration does not supply equivalent terrain.

The studied source-only converter reconstructs both rendered and collided terrain from SHFB. Its successful real-source offline tests are not a gameplay/runtime PASS. The later EDF4.1 SK collision lineage also has its own conservative mesh-shape policies; this article describes the earlier source heightfield generation and its constraints, not a replacement for those later policies.

SHFB sample, coordinate and layer layout

The reverse-engineered SHFB reader identified these header fields in the seven sampled maps:

Offset Interpretation in the examined profile
0x08, 0x0C Sample width and height: 1001 × 1001
0x18, 0x1C Horizontal cell dimensions: 2.0 m × 2.0 m
0x20 Block structure: 33 blocks of 32 cells
0x30, 0x34 Stated lowest and highest elevation
0x38 Per-block tables
0x3C, 0x40 Layer metadata / references
0x44, 0x48 Material-name index and related table
0x50 Packed height/material field
0x54, 0x58 Per-vertex blend-weight runs
0x5C, 0x60 UTF-16 name storage

Each height sample occupies two unsigned 16-bit words. The low word is the bit representation of an IEEE-754 half-float height in metres. The high word identifies its strongest material layer. This is a decoded shader and source-data observation, not an integer-centimetre height. The observed SK_HEIGEN02 decoded height range was about −10.2266 to 47.25 m.

The map's placed SHFB object supplies the world origin. A sample (row, col) becomes approximately:

world.x = origin.x + col * 2 metres
world.z = origin.z + row * 2 metres
world.y = decoded_half_float_height

Rows follow Z and columns follow X. A transpose produces misplaced ground and vegetation. As a cross-check, several maps' pre-existing objects were compared against the decoded field; median vertical differences ranged from 0.000 m to 0.29 m depending on map. This corroborates placement, not collision or navigation equivalence.

The field also carries layer names, per-layer colour/multiplier tiling and runs of half-float blending weights. An important special case: a source layer with one colour texture has no multiplier; it does not mean “sample index −1” in EDF6's unconditional multiplier path.

FMB rendering reconstruction

For this particular converter the source 1001 × 1001 at 2 m was sampled at every second source point: 501 × 501 render vertices spaced 4 m. Render and collision use the same lattice to reduce visible ground/physics divergence. This is a chosen conversion resolution, not an inherent EDF6 limit.

The resulting field FMB uses 625 leaves of 20 × 20 cells: 21×21 vertices and 800 triangles per leaf. It builds the stock-style spatial AABB tree, mesh records, layer lists and four-corner splat grids. A 0x50 splat-grid record per 4 m cell stores the four corners' weights, normalized to 255 per corner. In examined EDF6 FieldRender assets the shader tables cover 1–15 layers and passes 0–2; source leaves needing more than 15 are rejected rather than silently dropping a painted layer.

A critical native-profile correction concerns the FMB mesh-record field at +0x28: it is an index into that FMB's shader-record table, not the texture-slice count. Across 46 inspected stock EDF6 FMB files and 9753 meshes, the index selected a row matching (layer_count, mode=1, pass=0, flag=0). An older writer treated it as a slice count and selected rows with flag=6 or the wrong layer count; this produced the historical black terrain blocks. A renderer seeing black blocks should inspect this relation before assuming missing DDS or shader code.

The source colour DDS array is mapped to EDF6's <map>_color.dds; an existing EDF6 flat normal map is used for <map>_normal.dds in the examined converter. To preserve a layer whose source had no multiplier, the builder appends an opaque white BC1 identity slice at every mip rather than writing an invalid negative sample index. The original colour slices and mips remain unchanged. In a D3D11 WARP test, multiplying source colour by that identity slice preserved the sampled RGB.

MAD collision reconstruction

The examined terrain collision builder creates one target map body named <piece>.<piece> with 2500 compressed-mesh tiles, each a 10×10-cell tile of the same 4 m lattice (100 quads / 200 triangles per tile). The output is encoded using an EDF6 donor's Havok-2020 structural schema rather than copying EDF4.1's heightfield shape. Additional placed objects are represented by named collision bodies when corresponding source model collision triangles are available.

Offline checks decoded the generated triangles back to the lattice within approximately 1e−5 m, compared bounds and used independent compressed-mesh readers. The old output still had open questions about triangleIsInterior, material palette and object models missing from a map's RAB. Later SK collision work should be consulted before treating this historical builder as the final target.

Map-level resource wiring

A successful export has to update all linked resources, not just FMB and MAD:

  • MAC: replace the SHFB's definition with an FMEP definition, update the map object / MAPO height linkage, write externals.sgo for the new FMB and remove obsolete source field members.
  • RAB: expose the colour array under the expected EDF6 name and supply a normal array and valid multiplier slices.
  • MAD: supply target-format named collision bodies for terrain and included map objects.
  • Plants: reconstruct FMB table 2/3 and MAPO height data rather than inheriting an empty grass placeholder; see the dedicated vegetation guide.
  • Navigation: donor HKT/NVMD remains geometrically mismatched unless explicitly rebuilt against this terrain.

What was and was not demonstrated

The historical report records extensive real-source offline tests, serializer round-trips, source-object-to-ground comparisons and a GPU WARP texture test. It explicitly lists map load, black-block rendering, driveability and real AI pathing as still requiring game tests in that branch. Do not turn those offline checks into blanket game-runtime claims.

Subsequent source contact measurements

The newer seven-map terrain–object contact census follows the native SHFB, MAPB and MAD geometry relationships beyond bare terrain generation. R24–R28 examine 81 sampled placements and then 1,770 matched static-mesh placements. This demonstrates a source-geometry contact boundary, not native collision acceptance, full map coverage or pathfinding parity.

Cross-check: field lattice is not a navigation tile set (16 November source evidence)

The seven original SHFB fields also support a 4 m terrain lattice plan of 250,000 cells/500,000 triangles per map; this coincides in spatial sample spacing with the earlier 501×501 FMB render lattice, but neither the historical 625 FMB render leaves nor the 2,500 MAD collision tiles is the same as the later 256 planned HKT navigation tiles. The HKT tile grid belongs to a separate streaming/agent representation. Structural HKT/NVMD samples at 4 m have only been generated for bounded windows, while 32/64 m samples span the terrain domain. Read the 4 m source-grid/HKT/NVMD evidence atlas before interpreting any of these numbers as gameplay-equivalent navmesh coverage.
