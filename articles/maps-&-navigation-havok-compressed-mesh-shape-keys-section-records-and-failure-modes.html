Havok compressed-mesh primitives: shape keys, section records and failure modes

Technical reference · Scoped: binary decoder, section ABI and runtime case

Native broadphase checker: inactive keys and rounding

Do not treat every 4-byte primitive row as a live shape key: the examined native NW map uses DE AD DE AD tombstones. A faulty validator counted ten false missing keys until those inactive slots were excluded. The same checker formerly used a fixed 1e-4 world-bound tolerance, which was too strict for float32 at this map's scale. See Havok broadphase validation for the exact ULP-based budget and a deliberate +0.01 negative test. These tombstones are distinct from 0xFFFFFFFF encoded invalid key sentinels discussed above.

A collision mesh in EDF6 is not simply an array of triangles. The examined Havok 2020 compressed-mesh representation carries packed/shared vertices, primitives, per-section prefixes and a hierarchy of keys used by runtime collision queries. A generated mesh can render or even parse correctly while producing invalid contacts when one of these structures is inconsistent.

This article describes fields independently identified in the inspected EDF6/Havok-2020 wire representation and their observed consequences. Offsets below are specific to that inspected hkcdStaticMeshTree::Section layout; they are not interchangeable with generic HKX/MAD file offsets.

Primitive storage: triangles, quads and keys

The examined four-index primitive representation distinguishes two cases:

Primitive index relation Meaning in the measured writer Physical primitive keys
c == d Degenerate fourth corner: one triangle 1
c != d Four-corner quad, expanded as two triangles 2

A scene may therefore have many more expanded triangles than primitive records. The conversion must count expanded primitive keys, not merely quad records or source triangles, when computing the next section's prefix.

The firstPrimitiveIndex in a section is a mesh-global accumulated prefix for previous sections. It is not a per-section zero-based count. The accepted Desert sample's independent audit checked 11,873 sections in 387 section arrays with zero prefix mismatches. These counts describe that sample, not universal file constraints.

Measured section record ABI

A target section occupies 0x60 bytes (96 B) in the audited structure. Selected member offsets are:

Section-relative offset Member Implementation consequence
+0x48 firstPackedVertexIndex Start index into the section's packed-vertex data
+0x4C firstSharedVertexIndex Start index for shared vertices
+0x50 firstPrimitiveIndex Primitive-prefix index across preceding sections

A reader should first determine the exact version/schema that owns these fields, validate section indices and array bounds, then resolve the section's primitive and vertex references. Do not treat bytes that happen to resemble these offsets in an older Havok generation as compatible.

Why an invalid key can crash long after loading

One investigated EDF6 crash had an exact decoder-side failure path:

invalid compressed-mesh shape key = 0xFFFFFFFF
       -> decoded section index = 0xFFFFFF
       -> section address = base + 0x80 + 0xFFFFFF * 0x60
       -> attempted read of Section.firstPackedVertexIndex at +0x48
       -> out-of-bounds memory access

The failing instruction, constructed address and recorded access violation matched in that audited build. This establishes how the invalid key causes the observed failure, not necessarily where the invalid key came from.

In the same investigation a source-built compressed-mesh representation had a separately proven defect involving inactive SIMD lanes. The causal link from that defect to the exact 0xFFFFFFFF key was not closed. Do not present the candidate as a proven universal root cause. Both are useful independent checks: initialize inactive vector lanes correctly and reject invalid section/shape keys before dereferencing them.

Sparse triangleIsInterior indexing

The interior-edge/triangle bitfield is indexed by shape-key space. For the measured compact-mesh path, the span is driven by maxShapeKey + 1, not directly by the number of source input triangles. Sparse keys and two-key quad expansion can make those quantities different.

A correct triangleIsInterior bitfield does not automatically make triangle winding, primitive shape type or section prefix correct. Likewise, zero-valued interior bits are not a guarantee of contact parity. The bitfield, topology and key mapping should be validated independently.

The flat/convex conversion trap

In one runtime-qualified Desert compatibility branch, geometric reclassification that freely converted both flat→split and split→flat improved floor appearance/collision but crashed in the compressed-mesh primitive decode path. A control with zero interior bits and the same unsafe topology also crashed. That observation falsified the claim that the crash required triangleIsInterior to be nonzero.

The stable local profile preserved deterministic source-backed primitive order and permitted only geometry-justified flat→split, never an unproven reverse synthesis. This is an observed safe conversion policy for the investigated family, not proof that every EDF6 mesh can or should use all-zero interior bits.

Shape type, dispatch type and body motion are different domains

Do not confuse a model's shape-type identity, the collision dispatch enum, and the body's motion type. The measured target shape taxonomy includes convex (0), cylinder (3), box (5), compressed mesh (8) and compound (11); one working compressed-mesh profile separately required numShapeKeyBits=14 at +0x04, while retaining dispatchType=3 at +0x01. An old crash report incorrectly called the +0x04 value "dispatchType=14". Those numerals are not the same enum or field. Do not put a bit-count in a dispatch-type field and do not force shape-key bit-count 14 on all meshes.

The original EDF5→EDF6 research also caught a lossy motion-type mapping of source values {5:0, 2:2, 3:2}. Any unknown source value silently defaulted to target static 0. This is not a safe universal translation: preserve the source meaning, reject unrecognized types, and require target-class evidence before mapping.

Useful validation checks

  1. Reparse the generated target TYPE/ITEM/DATA graph, but don't stop at successful parsing.
  2. Verify each section's packed/shared-vertex and primitive spans and all mesh-global prefixes.
  3. Verify the true quad expansion: c == d versus c != d, and each resulting shape key.
  4. Validate sparse-key-dependent bitfields against actual key maxima, not input-triangle counts.
  5. Reject the 0xFFFFFFFF sentinel when it is not a valid key and verify section-index bounds before access.
  6. Check dispatch/shape/motion enums as separate fields, never by matching numeric values by coincidence.
  7. Separate game-runtime collision and AI contact results from byte-structural writer validation.

See MAD wire ABI and primitive indexing, Havok collision architecture and physical walls versus AI target selection.

The native interior-bit evidence is substantial, not decorative

The retained native EDF6 collision analysis reported:

Native map family Compressed meshes with nonzero interior data Approximate set bits
CAVE 102 / 102 320,000
HEIGEN 415 / 767 1,090,000
EUROPE 83 / 102 33,000
Historical working Desert control reported nonzero 5,290,000
Source-built Desert R5 0 / 387 0

These are reported counts from a historical paired-file audit, not new runtime measurements. The zero-filled compatibility path was successful under a particular conservative topology; it is not exact native interior-edge semantics. Suppressing interior-edge contacts affects collision response and may alter seams or edge behavior.

The classifier work identified vertex identity rather than just floating-point position as important. Per-section packed vertices must be decoded with section-local codecParms; using a section AABB as the codec or welding coincident coordinates across deliberate seams corrupts adjacency. Classification is related to local edge adjacency/concavity and exterior boundary status, rather than a direct copy of EDF5 weldingType (the sampled EDF5 maps reported WELDING_TYPE_NONE). A reference-aware method reached approximately 98% F1 on one CAVE sample when it was allowed to consult target-neighbor information. This is promising evidence for the mechanism but does not constitute a source-only exact-bit generator.

The related numShapeKeyBits is a per-shape key-space budget, not a universal 14: the historical census observed CAVE 11–14, HEIGEN 1–14, and some EUROPE values up to about 18. Allocate against actual maximum encoded keys and keep it distinct from the size of the triangleIsInterior sparse bitfield.

Current state: native semantics strongly indicated; exact source-only reconstruction for every map still open. Keep zero-policy acceptance and native-bit parity as different statements. The source paper trail is the 2026-08-22/23 MAD research material retained in R6_ALL_HANDOFFS_CHRONOLOGICAL_FULLTEXT.md (detailed hknpCompressedMeshShape member table, interior audit and shape-key audit).

A derived bit-width rule that reserves the all-ones sentinel

For the independently audited EDF5→EDF6 MAD compressed-mesh R12 serializer profile, the correct field width is:

numShapeKeyBits = (maxShapeKey + 1).bit_length()

This is not the same as maxShapeKey.bit_length() when maxShapeKey ends an all-ones binary range. The old expression could encode a valid largest shape key as all ones, colliding with the representation's reserved invalid/sentinel key pattern. Sample values from the audited corpus:

Maximum legitimate shape key Old width Correct R12 width
0 0 1
1 1 2
3 2 3
7 3 4

The retained R12 audit records 61 compressed-mesh instances with this collision, and 122 mirrored field updates (122 changed bytes in the studied file delta). After applying the corrected rule, its recorded all-ones collisions dropped from 61 to 0. A separate validation entry reports 1,628/1,628 native compressed meshes across BASE502, HEIGEN507, CAVE503 and NW_EUROPE01 for that investigated rule.

Implementation rule: derive bit width from the actual maximum encoded source shape key and its reserved invalid-pattern convention, not from source triangle count, an assumed universal 14, or only the number of mesh sections. This audit is specific to the studied Havok/MAD variant; it does not prove a version-independent law for every hknpCompressedMeshShape producer. The structural key-width fix is source/byte audited, not a claim of newly observed game collision runtime.
