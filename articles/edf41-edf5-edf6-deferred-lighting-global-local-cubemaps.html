EDF4.1 to EDF6 deferred lighting: from global reflections to local cubemap grids

ConversionGame technical referencesRenderingEDF 4.1EDF 5EDF 6
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R132 test

At a glance

What it is: The examined EDF games all use a deferred-lighting path, but their environment reflections and supporting G-buffer resources differ.

Where it fits: EDF4.1 uses a global cubemap in the audited path; EDF5 and EDF6 use local-cubemap grids with distinct shader contracts.

Important distinction: Cross-generation reflection shaders are not drop-in swaps, and forward-rendered water/glass may bypass the deferred reflection route discussed here.

All three EDF releases ship precompiled DXBC shaders and a deferred lighting path. But where an object reflection comes from changed substantially. The same-looking model shader name can give a different result after a cross-generation port.

The EDF4.1 deferred pass additionally produces a view-Z component. EDF5 adds a g_smooth_reflection_specpow G-buffer binding which is missing from the EDF6 list; EDF6 introduces brightness-fog parameters inside xgl_system. Names and resource bindings were read from disassembled DXBC shader data, not guessed from screenshots.

EDF5's local cubemap path binds g_local_cubemap_array and g_local_cubemap_grid, with parameters such as the world AABB and grid cell size. EDF6 retains the same concept but not the exact G-buffer or per-shader register contract. Copying one game's reflection shader wholesale into another is therefore not a lossless swap.

EDF6 deferred combine: concrete resource contract

The 7 November static study identified three EDF6 compute variants in EDF.dll: 0x1FCB890 (main), 0x1FCF2B0 (sun-shadow variant) and 0x1FD3340 (variant with different fog handling). These are build-scoped binary addresses for steam-678ccb46, not universal function IDs or demonstrated live dispatch points. Their reflected inputs include:

The reflected constant buffers include xgl_system (608 bytes, including brightness-fog fields), xgl_additional_light_setting and xgl_localcubemap at b10. The EDF5-only g_smooth_reflection_specpow does not appear in this EDF6 compute input list. Resource-slot reflection specifies possible shader inputs; it does not by itself show which resources are bound for a particular frame.

In the main and sun-shadow EDF6 compute variants, the source's static arithmetic gives m = saturate(g_metallic_roughness.x), r = g_metallic_roughness.y and a directional Fresnel base F0 = g_specularRGB * (0.04 + 0.96*m); its directional diffuse term has a (1-m) factor. The documented ambient-path core has the form (1-q)*D + E*(q*AO*A + 0.2*(1-r)*(1-q)), where q is a squared metallic-channel term and A, D, E are the source's intermediate albedo, diffuse and environment terms. This is a bounded shader-expression excerpt, not a complete independently executable compositor: the excerpt does not identify every intermediate lane, output format, dispatch state or postprocess. It nevertheless establishes why changing a specular color alone cannot reverse an albedo tint, and why metallic affects both directional diffuse and ambient/reflection routing.

Same legacy shader name, different base color

In the examined SND_MECH.SGO and SND_CHARA_2COLORCHANGE.SGO Deferred programs, EDF4.1 and EDF5 write the ordinary base color b directly to o0.rgb. The EDF6 program of the same-named family instead writes:

b = albedo.rgb * diffuse
f = reflect.R * saturate(
      (1 - pow(saturate(dot(-view, N)), max(fall_off_amount, 0.01)))
      * fall_off_scale + fall_off_offset)
o0.rgb = b + f * (1 - b)

Character color-change masks modify b before this expression. As f increases, the EDF6 G-buffer albedo moves toward white even when the texture's base pigment is dark. The source reports four outputs in EDF4.1, six in EDF5 and five in EDF6 for these specific compiled variants; EDF6 additionally routes sqrt(f) to o3.x and a value derived from legacy specular power to o3.y. These lanes are not a cross-generation identical ABI.

Concrete source-corpus contrast: EDF6 VEHICLE502_GROUNDROBOGOLD.MRAB retains snd_Mech; its reported reflect-R around 0.63 and fall-off parameters 50 / 2 / 0.5 can lift an approximate base (0.25, 0.13, 0) to (0.72, 0.68, 0.63) in the static source analysis. The native EDF6 V504_BEGARUTA_GOLD.MRAB example instead uses snd_BRDF_Common_Basic with a brown/gold base (123,93,57) (8-bit color), metallic 0.9, roughness 0.1, specular color 0.4 and blend 0.5. It therefore follows a different G-buffer/compositor contract; its color cannot be reproduced by relabeling the older shader.

The researcher's shader extraction and WARP acceptance tests support the static shader arithmetic; the cited vehicle colors were not independently matched against an in-game image in this pass. This explains a plausible whitening mechanism, not a universal repair or proof that any particular port will render identically after substituting BRDF parameters.

Deferred versus forward reflective surfaces

A deferred-combine change does not necessarily affect EDF5 water or glass objects: their source shaders use a forward pass, read g_xgl_environment_map, and do not themselves sample the local cubemap grid. By contrast, building windows use an interior-mapped G-buffer shader and acquire environment lighting downstream in the deferred pass.

EDF5 water, object glass and windows: three different pass contracts

Static DXBC analysis of EDF5 build steam-5d11de53 shows that these superficially similar surfaces do not share one reflection path:

Material shaderObserved program/passNative texture and output roles
SND_MAP_WATER_TRANSPARENTForward* and ZPass*; one color outputThree scrolling normal maps, three parallax maps, bubble albedo; t9 global g_xgl_environment_map, t10 scene g_xgl_viewXYZ_id_texture, t11 shadow depth. Material cbuffer xgl_user_param = 176 bytes.
SND_MAP_OBJECT_GLASSForward and depth passes; one color outputalbedo, normal, packed reflect/spec texture and t5 global cubemap, plus lighting/shadow resources; xgl_user_param = 96 bytes, with translucent fall-off values at offsets +84..+92.
SND_MAP_BUILD_WINDOWDeferred* and ZPass*; six G-buffer targetswindow_frame_texture at t2, interior at t3, normals at t4/t5, packed reflect/spec at t6. The window shader itself has no cubemap sampler; its material cbuffer is 80 bytes.

For the studied EDF5 water pixel shader, its environment term is mixed at a material-controlled strength without a conventional Fresnel factor. Its alpha is based on the separation between the water surface's view-Z and the opaque scene view-Z read from t10, modified by viewing angle, near fade and fog fade. The source-reconstructed color and alpha shapes are:

waterRGB = lerp(albedo * diffuse,
                env * lerp(1, albedo, metallic),
                environment_reflection * (1 - bubble))
           + directSpecular * specular_color

alpha = water_color.a * sqrt(min(depthDifference / angleTerm, 1))
        * nearFade * FOG_FADE.y

The source gives angleTerm = 1 - 0.75 * (1 - dot(normal, view)), with the view term determined from its vertex-to-camera direction; the exact source also applies fog to RGB after lighting. A disassembled pixel shader and compiled HLSL transcription matched the reflected layout and source-controlled D3D11 WARP output across 65,536 generated pixels, with a reported worst relative difference of 5.4×10−4. This is strong EDF5 static/WARP qualification, not a native EDF5 frame capture, and emphatically not an EDF6 water formula. EDF6 has its own observed BRDF Water material and later, separately qualified water-shader interpretation.

Building windows instead project an interior_texture behind the pane with a view-dependent offset (and an instanced random-seed variant); reflected surroundings are assembled by the later deferred local-cubemap pass. Object Glass's forward global-cubemap path must not be substituted for that mechanism. The EDF5 source method is static DXBC reflection/inspection from 3–4 November 2026; these descriptions do not establish equivalent shader names, output layouts or screen behavior for EDF6.

Evidence and uncertainty

The three shader families were identified by resource bindings across the executables. One EDF5 creation/dispatch chain was also traced; corresponding code paths were not traced to equal depth in EDF4.1/EDF6. The absence of a discovered SSR shader set is not proof that all forms of screen-space approximation are impossible; it is a bounded binary search result. No new picture-level comparison was performed.
