EDF6 SceneObject desync: two-PC evidence and later protocol-aware probe

EDF 6Engine RE & NetworkingNetworking
Source-backed research / case study · R7 two-PC runtime capture, R8/R9 exact static diagnostic candidates; no R9 runtime PASS

Evidence level: Direct two-PC runtime capture plus static/native reverse engineering.

Observed native behavior

The two-PC R7 capture did not support a simple physical EOS packet-loss explanation. Directional physical packet hashes matched, no SendPacket failure explained the divergence, and sender-side ordinary state continued to be produced while the remote player became sparse in position-bearing receive/application behavior. The observed divergence reached roughly 183 world units.

The position snapshot reaching the concrete parser was fresh rather than an obviously stale physical backlog. This moves the main frontier above EOS transport and below/around concrete player-state application: SceneObject receive parsing/staging and freshness handling are the critical boundary.

EDF5 contains explicit wrap-aware freshness behavior: accept a newer sequence normally, or accept a wrapped sequence when the previous value is high and the incoming value is low. The corresponding EDF6 staging path passes a 16-bit sequence onward but did not yield an equivalent generic wrap-aware gate during the audited static path.

Implementation rule

R8 MAXCAP is an instrumentation/diagnostic candidate, not a blanket sequence filter. It records outer sequence state and receiver-generation/index/type context, then allows strict stale suppression only for runtime-confirmed Soldier-type keys. Equal sequence values are not dropped. Generation changes reset the tracked comparison state.

The decisive proof chain is narrower than “desync happened”:

  1. a fresh position-bearing state is staged;
  2. it remains unapplied;
  3. an older strict-stale state for the same confirmed player/type arrives and replaces the pending state;
  4. the next concrete player dispatch lacks the expected position update.

Without that chain, collected sidecars should be re-parsed before adding another behavioral patch.

Relationship to Sandlot RUDP

Later Engine RE establishes retained Sandlot reliability above EOS for selected traffic. That does not invalidate the R8 staging frontier. It means transport reliability and SceneObject state freshness are different layers: a reliably delivered packet can still be staged, superseded or applied incorrectly. RUDP telemetry should therefore extend the diagnosis, not replace the R8 evidence model.

Do not assume

  • Matching EOS send/receive packets prove gameplay-state application.
  • A 16-bit sequence field can be globally filtered with one rule across every receiver/type.
  • A stale-looking packet is causal unless it is shown to replace a fresher pending state before concrete dispatch.
  • R8 static qualification is a two-PC runtime fix qualification; it is not.

Unresolved

The exact SceneObject staging/apply condition that produces the live divergence remains unresolved. R8 defines the discriminating telemetry surface; it does not close the root cause by itself.

Protocol-aware continuation: later static candidate, earlier two-PC evidence

The first later protocol-aware probe retains the same SceneObject evidence frontier but extends instrumentation from 29 to 31 exact-build inline hooks. The two extra sites observe Sandlot RUDP maintenance (0x12CEE60) and DATA deduplication (0x12CFCD0) and log pending count (ReliableMgr+0x10), dedupe count (+0x50) and sticky fault (+0x98). R9 also classifies 0x1200/0x1300/0x1400 control records and offers a default-off READY reset for a separate reconnect A/B. Its static source audit passed 31/31 canonical signatures; Windows MSVC build and two-PC R9 execution were not yet qualified.

Therefore R8 remains the scope of the existing captured player-position divergence; the newer R9 is a broader diagnostic candidate, not evidence of a live repair or a reason to abandon the SceneObject staging hypothesis. Keep RUDP/Link faults separate from ordinary class3 position staging and from omitted projectile constructor state. Use protocol-aware tracing and reconnect A/B for an actionable decision matrix.

Earlier two-PC R6 matrix: delivery was not enough

The 7 September V/A/B/C matrix observed exact pairwise equality for all eight physical ordinary 0x3300 TX→RX enqueue directions, and the parse counts also matched; the host's dominant remote Soldier apply cadence was approximately 100 ms in every run. This does not contradict the later R7/R8 position-bearing staging frontier: an apply call can occur without correctly applying a new position to the concrete Soldier world state. A delayed-delivery option was proven active but had no packet loss to repair in that matrix. Stale READY reconnect and 0x3500 bullet paths were not exercised.

R7 two-PC capture: exact delivery counts and a non-transport divergence

The retained R7 comparison matched 19,252 of 19,252 physical EOS records from PC-A to PC-B and 17,141 of 17,141 in the reverse direction, by the paired capture's physical payload hashes. No EOS SendPacket errors were observed in that run. Ordinary outgoing Soldier state remained active; meanwhile the remote side received few position-bearing concrete Soldier updates even as aim/state traffic continued. In one representative sample the apparent remote divergence reached approximately 183 world units, while the Soldier root and physical controller stayed relatively close together. The checker+0x22 flag was not permanently stuck. When a position-bearing update finally reached the concrete parser, it was fresh, not an obviously ancient pending update.

These facts exclude simple physical packet absence as a sufficient explanation for that recorded run, not every physical transport bug in every build or session. They do not prove the proposed specific stale-pending replacement chain. A later successful physical receive is distinct from a position-bearing update being applied to the right object.

Native sequence handling: an interleaved-batch trap

In the analyzed EDF6 build, the SceneObject parser hands a 16-bit sequence to native staging at EDF+0x757EC0. The EDF5 homolog uses a wrap-aware freshness rule, accepting a strictly higher sequence or a wrap when the old value is above 50,000 and the incoming value below 10,000. No matching generic wrap-aware freshness check was established in the inspected EDF6 staging path.

This does not authorize blindly inserting the EDF5 check at the outer object boundary: the EDF6 sender batch counter (manager+0xB8) can legitimately use one sequence for several fragments and type nodes before incrementing. Equal sequences on distinct fragments are therefore not inherently stale. The R8/R9 experimental strict-stale rule is scoped to a receiver-generation/object-index/type key first mapped at runtime to Soldier state, never to all class-3 records.
