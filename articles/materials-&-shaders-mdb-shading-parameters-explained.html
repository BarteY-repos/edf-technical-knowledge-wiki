MDB material parameters — roughness, metallic and normals

EDF 6Materials & ShadersShaders
Technical reference · Mixed: native, corroborated and reference-derived

At a glance

What this page answers: Roughness, metallic, normal and color-change fields have meanings within specific EDF6 MDB shader families, not a universal PBR material schema.

How to read it: Separate serialized MDB parameter order from shader reflection order, then follow each sampled texture channel and fallback value.

Evidence boundary: The equations describe bounded Common/BRDF paths. Special-purpose maps, terrain and transparent materials may use different contracts.

How these values are actually stored in MDB

The equations below describe shader semantics. A native MDB also has its own typed parameter and sampler record order. For example, snd_BRDF_Map_Common parameters are stored as diffuse, metallic, normal_amount, roughness, specular_color, specular_diffuse_blend, which differs from the reflected shader-variable order. Read How to read and write native MDB materials before creating a fresh material; it includes the type/size records, observed defaults, texture slot order and raw integer exceptions.

EDF6 MDB materials combine an exact shader family, parameters and textures. Their values should be interpreted according to that family, not according to a universal PBR importer. The equations below describe the studied ordinary MDB Common/BRDF-style material path, with provenance and exceptions stated explicitly. They do not apply wholesale to legacy character shaders or FieldRender terrain.

Native vector widths: do not infer them from parameter names

Several EDF6-native snd_Map_* materials are not serialized like the common BRDF scalar/RGB pattern. In the retained NW_EUROPE01 sample:

  • normal_amount is type=1, size=2 in legacy Build Parallax, Field Parallax, Build DirtScroll and snd_FarMap_Simple. The comparable studied BRDF Build Parallax and DirtScroll fields are type=0, size=1. The serialized width is known; whether each vector component maps to a particular tangent axis is not established by this MDB record alone.
  • diffuse and specular_color are type=2, size=4 in sampled legacy Build Parallax, Build DirtScroll and Map LOD materials, but type=2, size=3 in their sampled BRDF counterparts. Never discard the fourth stored component in the legacy material just because a preview shader consumes RGB.
  • Water normal1/2/3_scroll_speed and bubble1/2_scroll_speed are five two-component 1/2 vectors, while water_color is an RGB 2/3 value. These are material types, not direct proof of scrolling equations or output alpha.

See the ordered specialized-map ABI tables and the 26-field Water record for exact variants. This matters even to a read-only reference: the same visible label can have different binary structure in different shader families.

Albedo and diffuse

For the described Common-family material path, the simple base color is approximately:

float3 baseColor = albedoTexture.rgb * diffuse.rgb;

diffuse is a material color factor. The albedo sampler supplies texture color. Depending on the family, other masks can modify the color before it reaches the compositor.

Metallic: which texture channel matters?

For observed param_r_m_* packed-texture families, the material's metallic scalar is modulated by the green (G) channel:

metallicValue = saturate(packedTexture.g * material.metallic);

Thus neither metallic=1 nor a white albedo guarantees a metallic surface; the packed texture can reduce the effective value. Treat the stored texture's semantic family as part of the rule. Older reflect/spec masks are not automatically the same thing as this packed metallic channel.

In Hajisensai's separate param_r_m_occ_hr vehicle-material source read, R/G/B carry linear roughness/metallic/occlusion bytes. The described deferred combine uses the metallic value m to compute the dielectric-to-metal Fresnel base 0.04 + 0.96m and attenuates diffuse with 1-m. This reinforces the R/G lane mapping in that model family; it does not override the Common_Light_NoOcc exception below or prescribe a global glTF-to-EDF channel repack.

Roughness, including _hr

For the same Common/BRDF param_r_m_* family, the red (R) channel modulates the material roughness scalar:

roughnessValue = saturate(packedTexture.r * material.roughness);

For the sampled _hr variant, alpha (A) is an additional roughness multiplier:

roughnessValue = saturate(packedTexture.r * packedTexture.a * material.roughness);

This explains a common Blender/Helix/glTF preview mismatch: connecting only roughness to a PBR shader ignores the red/alpha texture contribution. roughness is not a synonym for older specular_pow values.

Normal maps and normal_amount

In the described ordinary Common/model-style path, the normal texture uses a nonstandard R×A / G decode:

float x = texture.r * texture.a * 2.0 - 1.0;
float y = texture.g * 2.0 - 1.0;
float z = sqrt(max(0.00001, 1.0 - x*x - y*y));
x *= normal_amount;
y *= normal_amount;
// Transform (x,y,z) with tangent, binormal and geometric-normal basis,
// then normalize for the relevant material path.

A conventional RGB or RG normal-map import can therefore be visibly wrong. normal_amount=0 disables the tangent-plane perturbation; values greater than one exaggerate it and negative values reverse its X/Y direction. The convention is supported by the supplied rendering description and corroborated in the analyzed Water shader, but not every EDF shader family has been proven to use it.

FieldRender exception: the studied terrain normal path reconstructs X from R×B, and Y has an inverted sign; see FieldRender textures and normals. Do not reuse the MDB decoder blindly for terrain.

Color-change masks

For two-channel param_cm0_cm1, the supplied rendering description uses sequential interpolation, not one combined tint multiply:

float3 c = lerp(diffuse, change_color0, colorMask.r);
c = lerp(c, change_color1, colorMask.g);
float3 result = albedo.rgb * c;

The second interpolation sees the result of the first. Channel order and family-specific UV routing matter.

Cross-generation source test: Hajisensai's two-color character-shader comparison found change_color0 and change_color1 as float3 at cb2 offsets 16 and 32 in EDF4.1 and EDF6, with sampler t2 (param_cm0_cm1_occ) supplying R/G color masks and B occlusion. The source's offline pixel-shader replay produced identical RGB values in 1,130,496 comparisons on sampled stock four-class models, while changing either color slot affected the expected RGB without changing alpha. This is a bounded shader-replay result, not an EDF4.1-to-EDF6 full model/animation parity test.

Native upload detail: EDF6 material-parameter upload 6C32B3..6C32F9 walks 24-byte parameter records; their size is at +0x10 and constant-buffer offset at +0x08. The code copies at most 16 bytes per record into the buffer's base [buf+0x30] plus that offset, then sets the dirty byte [buf+0x48]. A float3 therefore copies only 12 bytes; the fourth 4-byte lane is not implicitly cleared. An authoring tool must preserve declared vector width and explicitly handle padding rather than assume every color is float4.

Conversion-specific parameter type: the source's EDF4.1-to-EDF6 player-outfit comparison changed a color parameter's serialized type from 0x302 to 0x402 while retaining its numeric values and texture-mask bindings; 344 checked BC1/BC3 texture payload comparisons were byte-identical. This isolates a material ABI adjustment in those outfits, not evidence that all EDF4.1 materials or their complete rigs can be ported by one type-word rewrite. Source: Hajisensai, All Forces docs/outfit-color.md, steam-678ccb46, static/offline.

Cutout/alpha clip

In snd_BRDF_Map_Common_Clip, pixels below the alpha_clip threshold are discarded:

if (albedoAlpha < alpha_clip) discard;

In a 44-material native sample, 42 used alpha_clip=0.5 and two used 0.3435. Those counts are sample results, not universal defaults. Native BC1/DXT1 textures with one-bit transparency have been observed in foliage using this path.

EDF6 model Clip family: alpha and depth passes

Source-reported static disassembly (Steam 678ccb46): snd_BRDF_Chara_2ColorChange_Clip and snd_BRDF_Mech_Catapillar discard when albedo.a < alpha_clip, without multiplying that alpha by diffuse. The parameter sits at pixel constant-buffer offset 60 in the former and offset 56 (cb2[3].z) in the latter's deferred, forward and depth variants. Stock V603/V601/V505 tracks use alpha_clip=0, meaning their shader does not actually cut those samples. This is a different source family from the snd_BRDF_Map_Common_Clip 44-material sample above. snd_BRDF_Common_Simple_Clip instead uses a fixed albedo.a × fall-off - 0.5 condition and has no alpha_clip parameter.

The source also inspected ZPass pixel shaders a5e9e544753e (2ColorChange_Clip) and a3863b7d2f9f (Mech_Catapillar): both read albedo alpha and discard under the same threshold, with Catapillar carrying scrolled UVs into the pass. In contrast, the sampled Common_Basic and Common_Alpha ZPass pixel shaders emit a constant. Thus a cutout also leaves a hole in any depth/shadow draw that invokes this ZPass; the source did not trace EDF.dll sufficiently to prove which native shadow passes invoke it.

Stock examples: VEHICLE403_TANK track has alpha_clip=0.2 and DXT5 alpha, while the source found P601_PROTO_RANGER and wing-suit hair examples of 2ColorChange_Clip with 0.2356 and 0.55 thresholds. Sampled transparent glass includes V613_BIKE (diffuse.w=0.5, texture alpha fully opaque) and V512_KEITRUCK (fall-off toward grazing angles). The audited stock Alpha/Clip albedos used classic DXT formats, not DX10/BC7; this is a corpus finding, not a decoder restriction.

EDF6 Common_Alpha: model transparency is not cutout

The separate snd_BRDF_Common_Alpha family uses a source-disassembled formula saturate(albedo.a × diffuse.w × saturate((1 - (N·V)^max(amount, 0.01)) × scale + offset)). Its deferred pixel shader writes this alpha into all five G-buffer output alpha components, and the forward pixel shader combines it with fog attenuation. The source observed shared vertex shader binaries/layout compatibility with Common_Basic, but sharing a vertex format does not make the pixel alpha rules interchangeable. In the source's stock material scan, 55 entries used snd_BRDF_Common_Alpha; this is not a universal material count. The suggested 0.842/0.164 color factors copied from v603_body do not prove a separate Common_Basic diffuse-dimming equation.

specular_color and specular_diffuse_blend

The supplied compositor description gives the following BRDF-family logical mixing rule:

float blend = metallicValue * specular_diffuse_blend;
float3 specularRGB = lerp(specular_color,
                           preEmissionAlbedo * specular_color,
                           blend);
float3 F0 = specularRGB * (0.04 + 0.96 * metallicValue);

This is a guide-derived model of the general path, not a claim of native-byte verification for every shader. specular_color participates in specular/Fresnel computation; it is not simply an albedo tint. The described direct-specular term is GGX/Schlick-like, subject to family-specific differences.

Emission and light masks

Emission is not universal across EDF6 shader families. For the studied snd_BRDF_Map_Common_Light shader, native shader analysis supports an accumulation term equivalent to:

emissionAccum.rgb = packedLightMask.b * light_color.rgb;

A mandatory extra multiplication by albedo has not been established for that exact write. Do not force one generic albedo × light_color × mask formula onto all families.

EDF6 model Light_NoOcc is a separate emissive contract

Hajisensai's static DXBC read of snd_BRDF_Common_Light_NoOcc (EDF6 Steam 678ccb46) instead uses param_r_m_light_hr with B as an emissive mask m=saturate(B). For a=albedo.rgb × diffuse, it writes G-buffer target 0 RGB as (1-m) × a and target 6 RGB as m × a × light_color. The G channel still modulates metallic and R×A modulates roughness; the specular base is also suppressed by (1-m). At full mask, diffuse/specular are removed in favor of emission. This does include albedo, unlike the distinct snd_BRDF_Map_Common_Light source observation above.

The NoOcc part of the model shader name matters: ordinary snd_BRDF_Common_Basic uses the sampled B channel as normal/occlusion modulation, whereas Common_Light_NoOcc uses it for light and omits that occlusion term. A single unchanged stock shader instance therefore cannot simultaneously interpret B as both the ordinary occlusion lane and the full emission mask.

Source boundary: Hajisensai, All Forces docs/model-quality-1121-alpha.md, docs/model-quality-1110.md and docs/xmorph-redo-1121.md; static shader/file reads on steam-678ccb46. These results supplement, rather than independently validate in-game, the older shader-family guide.

Occlusion and why a standard PBR preview differs

The supplied rendering model describes an unusual intermediate where the length of the stored surface normal carries occlusion information:

normalXYZ = normalizedSurfaceNormal * occlusion;

For the described composition, ambient diffuse can scale approximately with squared normal length, while several directional/specular/environment terms scale with length. This is not the same as applying a conventional ambient-occlusion texture only to base-color darkening. The system also includes distinct environment weighting, fog and HDR/exposure/bloom behavior. A Principled BSDF or generic glTF preview is therefore only a useful approximation.

Shader names do not imply interchangeable data

Older snd_Map_*, SND_CHARA_BASIC and specialized Window/Glass/Parallax/DirtScroll/Signboard materials can use different parameter and sampler ABIs. specular_pow must not be silently renamed roughness. Raw integer type=4 parameters must retain their u32 bits, not float32 numeric values (for example raw integer 2 is 02 00 00 00, whereas float 2.0 is 00 00 00 40).

For material-by-material tables and typed parameter order, see native shader profiles, specialized shader families and raw type-4 values.

For sampled shader-family counts, ordered sampler layouts and the type=4 raw-u32 exception, see the native MDB shader family field guide.

EDF6 visual damage map: grid and shader-family rules

This is visual/material damage, not the gameplay HP, armor or bullet-hit calculation in the damage model source notes. The following six IDs come from ktaro's EDF6 model-material shader work in the Knowledge Hub, scoped to Steam build 678ccb46. Static disassembly is distinguished below from the separately reported in-game visual check.

DamageMap storage: DamageMap (6CAD20, 6CC760) uses an SGO's three division counts as grid points, not cells. With nx,ny,nz points, spacing is (maxCorner-minCorner)/(divisions-1), point index x + y*nx + z*nx*ny, and each point stores one of four damage levels in two bits (16 points per 32-bit word; word count (points+15)/16). The SGO declares the shape only, not the damage-bit values; source-reported runtime initialization sets the bitfield to zero and hits raise levels. Shader constants include m_org, m_line_pitch, m_inv_grid_size and m_slice_pitch.

Shader sampling: before skinning, the local vertex LOCAL_POSITION is converted to grid coordinates by subtracting origin and dividing by spacing. The shader tri-linearly interpolates the eight surrounding two-bit point values (each normalized by 3) into d0. Then d=d0-damage_dist.r sampled at UV0 × damage_mask_uv_mul; a pixel is in the damaged region when d>0. Its damage color interpolates between damage_diffuse sampled with damage_uv_mul and damage_max_color. Because lookup starts in local/pre-skinning space, the painted damage follows an animated mesh instead of staying fixed in world coordinates.

BRDF damage variants: the BASIC, LIGHT, SEPARATEOCC, LIGHT_SEPARATEOCC, LIGHT_NOOCC, RADON and LIGHTSCROLL(2) variants ordinarily replace damaged albedo, specular, metallic, roughness and normal with their damage_* counterparts while retaining their original occlusion. For selected LIGHT/RADON variants lightCoefficient × damage_light_mask reduces the damage value. At a damage-edge interval d<0.1 only albedo becomes damage_edge_color; otherwise the damage color/parameter replacements apply. Emission is usually zero within the damaged region, with specific exceptions below.

_DAMAGE2 is different: in BASIC/LIGHT variants, packed damage_param_r_m_occ_light contributes R×damage roughness, G×damage metallic, B as either replacement occlusion or a multiplier according to is_damage_occlusion_mul, and A as the light mask. Away from the edge, emission is damage color × damage_light_color × A, while damaged diffuse/specular are suppressed by 1-A. BASIC can additionally multiply the maximum damage color when use_damage_max_color_mul is active. A generic `_DAMAGE` material rewrite must not silently substitute the `_DAMAGE2` channel equations.

Other branches: DECOY_DAMAGE substitutes damaged albedo, normal and R/M/O textures without an edge treatment. _CLIP discards where d>0; _CLIPR uses a different d0 - max(dist,0.01) test and can draw nothing at zero damage (intended for revealing contents beneath torn clothing). Legacy CHARA/MECH/DINO damage families convert replacement color, specular exponent and reflectivity through their legacy shader path, rather than reusing BRDF roughness. Forward BRDF_CHARA_LIGHTSCROLL2_ALPHA_DAMAGE has its own alpha and no edge/max-color mix. The family must be identified before editing.

Reported game test versus disassembly: the source found four of 18 damage pixel-shader families that compute emission before the damage branch and retain it in damaged regions: BRDF_CHARA_LIGHTSCROLL_DAMAGE, LIGHTSCROLL2_DAMAGE, BRDF_COMMON_LIGHT_SEPARATEOCC_DAMAGE and DINO_LIGHTSCROLL_DAMAGE. In novae (ajane)'s source-reported in-game check of ktaro's findings (16-Nov-2026), MONSTER501, E616 and E509 continued glowing after visual damage. The E609 LIGHTSCROLL2 cannons instead went dark after destruction/falling, potentially due to another state change; do not generalize the shader branch alone to all complete game-object lifecycles. The suggestion that MONSTER501's initially zero light fields are later changed by MTAB is inferred, not a traced native assignment.

Evidence and limits

  • Native observations: sampled MDB material schemas and texture binding; exact Common_Clip/Light family behavior where audited; native texture/channel and source paired-asset findings.
  • Corroborated but not universal: Common/Water-style normal decoding, selected packed R/M rules.
  • External descriptive guide: parts of the high-level specular, occlusion and scene compositor equations above. Treat these as useful qualified descriptions, not proof for every shader binary.
  • Still unknown: universal behavior of legacy SND_CHARA_BASIC/non-BRDF scene composition, and a universally faithful stock Blender/glTF preview.

Evidence below comes from hajisensai's All Forces notes for steam-678ccb46 and is static source reading, not an independent shader capture or draw-order test.

Material header b3=2 routes into a distinct translucent list

Static. Material ctor 110F110 copies MDB b3 into runtime material +0x13 (110F1FF) and b2 into +0x12. Submission at 11034DF sends b3=2 to model list +0xC8 and all other b3 values to +0xA8; 10FEF88 also separates them. Setup 6BDC82/6BDCA2 tests both: nonempty opaque list raises render flags bit28 and bit30, nonempty translucent list raises bit29 only. b3=2 therefore skips two opaque passes, but identifying bit30 as shadow is still medium-confidence inference. This does not prove a forward-versus-deferred technique, nor sorting inside the translucent list.

Stock material header byte census

Static, 2,097 OBJECT/WEAPON archive materials. b3=0 in 1,917, =2 in 174, =1 in 6. All b3=2 were *_Alpha, shield or BeamShield families; all surveyed Clip variants (2ColorChange_Clip, hair_Clip, Simple_Clip, Decoy_damage_clip) used b3=0. Six b3=1 were Catapillar cutout tracks (alpha_clip 0.2/0.5 with DXT5 albedo) on three EDF4.1-origin vehicle resources, but EDF.dll does not branch on b3=1; it only hashes the byte at 1118AF0, so b3=1 is not a required cutout selector. b2 values observed were 0,1,2,3,5,6,7,10,20 (often translucent). b2 was copied at 1110870/111D04A and hashed without comparison; draw-order bias is merely a hypothesis.

Native Light material values are not one universal preset

Static Root.cpk examples. Retro Balam V515_RETROBALAM.MRAB material light: metallic=roughness=normal_amount=1, specular_diffuse_blend=0.5, light_color=(0,5,0.1). Vehicle603_Flak uses its own v603_light (same shader) with light_color=(0.43,0.42,0.47) and specular_color=0.137. Reported stock light_color components range about 0.43–30. On V613, v613_bikeGlassmat uses snd_BRDF_Common_Alpha, b3=2 translucent bucket; Common_Alpha shares Common_Basic vertex shader. Do not replace these source-owned values with generic emission assumptions.

Mech_Catapillar swaps color green and blue in shader

Static. Deferred and forward snd_BRDF_Mech_Catapillar pixel programs end with mul r0.xyz,r0.xzyx,cb2[0].xyzx, yielding (albedo.r, albedo.b, albedo.g)×diffuse. Stock tracks are nearly gray (V603 source sample 26.8/25.0/24.4), hiding the swap; a brown-colored replacement can turn visibly magenta. Do not treat RGB sampling order as unchanged solely from observing stock thumbnails.

Native roughness/metallic maps vary spatially

Static stock texture statistics. Parameter-map roughness R standard deviation for vehicle bodies: V603=12, V601=19, V505=48; metallic G deviations 37,26,52. The source's ordinary painted vehicle reference averaged roughness ≈140 and metallic ≈90 in byte space. A single constant roughness/metallic scalar may match the average but loses deliberate pixel-level variation, particularly on the older V505 material.

Native Water is a separate MDB shader family

One retained native MDB, eu1_nw_field01_water.mdb, uses snd_BRDF_Map_Water and has associated water-shore and normal texture resources. The wider four-map retained census does not establish separate River/Ocean shader families. See native static-water shader evidence. The existence of this specialized family does not change how unrelated BRDF or legacy MDB shaders should be interpreted.
