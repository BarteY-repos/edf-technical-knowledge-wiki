MDB material parameters — roughness, metallic and normals

EDF 6Materials & ShadersShaders
Technical reference · Mixed: native, corroborated and reference-derived

At a glance

What this page answers: Roughness, metallic, normal and color-change fields have meanings within specific EDF6 MDB shader families, not a universal PBR material schema.

How to read it: Separate serialized MDB parameter order from shader reflection order, then follow each sampled texture channel and fallback value.

Evidence boundary: The equations describe bounded Common/BRDF paths. Special-purpose maps, terrain and transparent materials may use different contracts.

How these values are actually stored in MDB

The equations below describe shader semantics. A native MDB also has its own typed parameter and sampler record order. For example, snd_BRDF_Map_Common parameters are stored as diffuse, metallic, normal_amount, roughness, specular_color, specular_diffuse_blend, which differs from the reflected shader-variable order. Read How to read and write native MDB materials before creating a fresh material; it includes the type/size records, observed defaults, texture slot order and raw integer exceptions.

EDF6 MDB materials combine an exact shader family, parameters and textures. Their values should be interpreted according to that family, not according to a universal PBR importer. The equations below describe the studied ordinary MDB Common/BRDF-style material path, with provenance and exceptions stated explicitly. They do not apply wholesale to legacy character shaders or FieldRender terrain.

Native vector widths: do not infer them from parameter names

Several EDF6-native snd_Map_* materials are not serialized like the common BRDF scalar/RGB pattern. In the retained NW_EUROPE01 sample:

  • normal_amount is type=1, size=2 in legacy Build Parallax, Field Parallax, Build DirtScroll and snd_FarMap_Simple. The comparable studied BRDF Build Parallax and DirtScroll fields are type=0, size=1. The serialized width is known; whether each vector component maps to a particular tangent axis is not established by this MDB record alone.
  • diffuse and specular_color are type=2, size=4 in sampled legacy Build Parallax, Build DirtScroll and Map LOD materials, but type=2, size=3 in their sampled BRDF counterparts. Never discard the fourth stored component in the legacy material just because a preview shader consumes RGB.
  • Water normal1/2/3_scroll_speed and bubble1/2_scroll_speed are five two-component 1/2 vectors, while water_color is an RGB 2/3 value. These are material types, not direct proof of scrolling equations or output alpha.

See the ordered specialized-map ABI tables and the 26-field Water record for exact variants. This matters even to a read-only reference: the same visible label can have different binary structure in different shader families.

Albedo and diffuse

For the described Common-family material path, the simple base color is approximately:

float3 baseColor = albedoTexture.rgb * diffuse.rgb;

diffuse is a material color factor. The albedo sampler supplies texture color. Depending on the family, other masks can modify the color before it reaches the compositor.

Metallic: which texture channel matters?

For observed param_r_m_* packed-texture families, the material's metallic scalar is modulated by the green (G) channel:

metallicValue = saturate(packedTexture.g * material.metallic);

Thus neither metallic=1 nor a white albedo guarantees a metallic surface; the packed texture can reduce the effective value. Treat the stored texture's semantic family as part of the rule. Older reflect/spec masks are not automatically the same thing as this packed metallic channel.

Roughness, including _hr

For the same Common/BRDF param_r_m_* family, the red (R) channel modulates the material roughness scalar:

roughnessValue = saturate(packedTexture.r * material.roughness);

For the sampled _hr variant, alpha (A) is an additional roughness multiplier:

roughnessValue = saturate(packedTexture.r * packedTexture.a * material.roughness);

This explains a common Blender/Helix/glTF preview mismatch: connecting only roughness to a PBR shader ignores the red/alpha texture contribution. roughness is not a synonym for older specular_pow values.

Normal maps and normal_amount

In the described ordinary Common/model-style path, the normal texture uses a nonstandard R×A / G decode:

float x = texture.r * texture.a * 2.0 - 1.0;
float y = texture.g * 2.0 - 1.0;
float z = sqrt(max(0.00001, 1.0 - x*x - y*y));
x *= normal_amount;
y *= normal_amount;
// Transform (x,y,z) with tangent, binormal and geometric-normal basis,
// then normalize for the relevant material path.

A conventional RGB or RG normal-map import can therefore be visibly wrong. normal_amount=0 disables the tangent-plane perturbation; values greater than one exaggerate it and negative values reverse its X/Y direction. The convention is supported by the supplied rendering description and corroborated in the analyzed Water shader, but not every EDF shader family has been proven to use it.

FieldRender exception: the studied terrain normal path reconstructs X from R×B, and Y has an inverted sign; see FieldRender textures and normals. Do not reuse the MDB decoder blindly for terrain.

Color-change masks

For two-channel param_cm0_cm1, the supplied rendering description uses sequential interpolation, not one combined tint multiply:

float3 c = lerp(diffuse, change_color0, colorMask.r);
c = lerp(c, change_color1, colorMask.g);
float3 result = albedo.rgb * c;

The second interpolation sees the result of the first. Channel order and family-specific UV routing matter.

Cutout/alpha clip

In snd_BRDF_Map_Common_Clip, pixels below the alpha_clip threshold are discarded:

if (albedoAlpha < alpha_clip) discard;

In a 44-material native sample, 42 used alpha_clip=0.5 and two used 0.3435. Those counts are sample results, not universal defaults. Native BC1/DXT1 textures with one-bit transparency have been observed in foliage using this path.

specular_color and specular_diffuse_blend

The supplied compositor description gives the following BRDF-family logical mixing rule:

float blend = metallicValue * specular_diffuse_blend;
float3 specularRGB = lerp(specular_color,
                           preEmissionAlbedo * specular_color,
                           blend);
float3 F0 = specularRGB * (0.04 + 0.96 * metallicValue);

This is a guide-derived model of the general path, not a claim of native-byte verification for every shader. specular_color participates in specular/Fresnel computation; it is not simply an albedo tint. The described direct-specular term is GGX/Schlick-like, subject to family-specific differences.

Emission and light masks

Emission is not universal across EDF6 shader families. For the studied snd_BRDF_Map_Common_Light shader, native shader analysis supports an accumulation term equivalent to:

emissionAccum.rgb = packedLightMask.b * light_color.rgb;

A mandatory extra multiplication by albedo has not been established for that exact write. Do not force one generic albedo × light_color × mask formula onto all families.

Occlusion and why a standard PBR preview differs

The supplied rendering model describes an unusual intermediate where the length of the stored surface normal carries occlusion information:

normalXYZ = normalizedSurfaceNormal * occlusion;

For the described composition, ambient diffuse can scale approximately with squared normal length, while several directional/specular/environment terms scale with length. This is not the same as applying a conventional ambient-occlusion texture only to base-color darkening. The system also includes distinct environment weighting, fog and HDR/exposure/bloom behavior. A Principled BSDF or generic glTF preview is therefore only a useful approximation.

Shader names do not imply interchangeable data

Older snd_Map_*, SND_CHARA_BASIC and specialized Window/Glass/Parallax/DirtScroll/Signboard materials can use different parameter and sampler ABIs. specular_pow must not be silently renamed roughness. Raw integer type=4 parameters must retain their u32 bits, not float32 numeric values (for example raw integer 2 is 02 00 00 00, whereas float 2.0 is 00 00 00 40).

For material-by-material tables and typed parameter order, see native shader profiles, specialized shader families and raw type-4 values.

For sampled shader-family counts, ordered sampler layouts and the type=4 raw-u32 exception, see the native MDB shader family field guide.

Evidence and limits

  • Native observations: sampled MDB material schemas and texture binding; exact Common_Clip/Light family behavior where audited; native texture/channel and source paired-asset findings.
  • Corroborated but not universal: Common/Water-style normal decoding, selected packed R/M rules.
  • External descriptive guide: parts of the high-level specular, occlusion and scene compositor equations above. Treat these as useful qualified descriptions, not proof for every shader binary.
  • Still unknown: universal behavior of legacy SND_CHARA_BASIC/non-BRDF scene composition, and a universally faithful stock Blender/glTF preview.

Native Water is a separate MDB shader family

One retained native MDB, eu1_nw_field01_water.mdb, uses snd_BRDF_Map_Water and has associated water-shore and normal texture resources. The wider four-map retained census does not establish separate River/Ocean shader families. See native static-water shader evidence. The existence of this specialized family does not change how unrelated BRDF or legacy MDB shaders should be interpreted.
