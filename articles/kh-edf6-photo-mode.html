This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Terminology and availability: The upstream EDF Knowledge Hub organized this source page under the historical label "Photo Mode". In this wiki it means internal debug free-camera and pause/post-process code observed by static inspection of a specified retail executable, not an established player-accessible photo mode. The identified class and controls do not by themselves prove a retail menu entry, supported activation sequence or in-game usage. Keep the original fact IDs and build-specific RVAs for source traceability. No new live-game test was performed.

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

The pause bits (the world freeze)

Game pause-bit ownership by subsystem

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-pause-bit-users

Who sets which pause bit of the game system (1196FC0(system, bits, set), system.md#system-pause-bits), by value: 1 the debug free camera (on in its constructor at 100151, toggled in its update at 102385, off at 1019DB); 2 the pause menu (934A55, 934D3A, 934EE1); 0x10 four debug and map-preview handlers (95BA1, 9DAD8, BB462, BB582); -1 (all off) 70527B and 705386. Value 8 has no setter. 1195E70(system) is the is-paused test ([+0xCD8] & [+0xCDC] non-zero).

Basis: fn.py --xref 1196FC0 (12 calls) and the edx set before each

Addresses (build-specific RVAs unless indicated): 1196FC0, 100151, 102385, 1019DB, 934A55, 934D3A, 934EE1, 95BA1, 9DAD8, BB462, BB582, 70527B, 705386, 1195E70

Per-mode pause permission mask

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-pause-mask-offline

Which bits may pause is decided per mode: the system constructor sets the mask system+0xCDC = 0xFFFFFFFF and the bits +0xCD8 = 0 (119180A, 1191804); after that the mask is written only by 1195630(system, bits, set), whose only caller is MissionMgr::SetMode (DC460, tail jump at DC512) with bits 0xE (values 2, 4 and 8), set = true when the mode is -1 or the mode row's online flag +0x68 is 0 (mission-packs.md#mode-row-online-flag), false otherwise. So in an online mode the pause menu (2) and the unused value 8 change +0xCD8 but stop nothing, while values 1 (the debug free camera) and 0x10 still freeze the local game. 1195630 and 1196FC0 call every pause listener's slot 11 when the paused state flips.

Basis: fn.py reads of 1195630 and DC460; a .text scan for +0xCDC (writers: 119180A, 119565A only)

Addresses (build-specific RVAs unless indicated): 119180A, 1191804, 1195630, DC460, DC512, 1196FC0

The built-in debug free camera (FreeViewCamera)

Retail FreeViewCamera debug class

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-free-view-camera

The retail EDF.dll keeps a debug free camera, FreeViewCamera (vtable 1768FA8, size 0x690): constructor FF580 (base 103740, as the player camera), update slot 4 101BA0, slot 7 1019C0 (calls 104250, then clears pause bit value 1). The constructor binds 19 controller inputs by name, copies the start pose (eye +0x250 to +0x520, angles from the forward row to +0x530), sets +0x54A = 1 and turns pause bit 1 on (100151), so the world is frozen from the first frame; FOV +0x24 = π/4 and +0x38 = 1. A second vtable at 17631E8 shares the update and slot 7 (1763208, 1763220; its class not read).

Basis: fn.py reads of FF580 and 101BA0; --xref of both functions (vtable pointers only)

Addresses (build-specific RVAs unless indicated): 1768FA8, FF580, 103740, 101BA0, 1019C0, 104250, 100151, 17631E8, 1763208, 1763220

Free-camera input binding lookup

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-free-camera-bindings

Its inputs: 11825D0(input manager [20B2888], binding, device, name) looks the name up in the manager's list +0x28 (node +0x10 name, +0x50 type, +0x54 device index); the device is the creator's argument. Bindings (0x18 bytes each; updated by 1182BC0(binding, frames): +0 source node, +8 repeat counter, +0xC analog value from node +0x48, +0x10 held, +0x11 pressed this frame, +0x12 released, +0x13 repeat pulse, on press and then every 2 frames after 16): +0x350 LeftStickX, +0x368 LeftStickY, +0x380 RightStickX, +0x398 RightStickY, +0x3B0 RightTrigger, +0x3C8 LeftTrigger, +0x3E0 RightThumb, +0x3F8 LeftThumb, +0x410 RB, +0x428 LB, +0x440 Up, +0x458 B, +0x470 Down, +0x488 Right, +0x4A0 Start, +0x4B8 Back, +0x4D0 A, +0x4E8 X, +0x500 Y. Whether a keyboard and mouse device carries these names was not read.

Basis: fn.py reads; the names are UTF-16 strings at 175F340..175F470 (fn.py --str)

Addresses (build-specific RVAs unless indicated): 11825D0, 20B2888, 1182BC0, FF580

What the free camera's update 101BA0 does each step: sets byte 20B2958+0xAF0 = 1

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-free-camera-update

What the free camera's update 101BA0 does each step: sets byte [20B2958]+0xAF0 = 1; the left stick moves (dead zone 0.08 1765A08, rescaled by 1.08696), the triggers move up and down (RT minus LT), speed x0.25 or x1.5 while X is held (1768820 / 1769140); while paused (1195E70) the point moves directly, otherwise through its own character controller at +0x550 (velocity x60, 11AFA70 / 11AF720), whose map collision A toggles (+0x548, 106100 / 106150); the right stick turns: yaw +0x530, pitch +0x534 clamped to ±π/2, both slowed by tan(FOV/2) / tan(+0x20/2) x 0.1; roll +0x538; rows built by 102CA0 and 4CD10 into +0x220..+0x240, eye +0x250, then multiplied by the 3x3 at +0x280..+0x2A8. Start toggles the pause (+0x54A, bit 1); Back's repeat pulse steps one frame (+0x549); both thumb buttons reset the pose and FOV; Y (without B) fires a RocketBullet01 from the camera (101800); +0x54B turns on a ray from the eye that prints the hit's material (74960).

Basis: fn.py read of 101BA0 (860 lines, t7_101BA0.txt); constants with flt.py

Addresses (build-specific RVAs unless indicated): 101BA0, 20B2958, 1765A08, 1768820, 1769140, 1195E70, 11AFA70, 11AF720, 106100, 106150, 102CA0, 4CD10, 101800, 74960

The free camera's zoom: each step +0x24 += tan(+0x24/2) x (LB value - RB value) x 0.02 (17690F8)

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-free-camera-zoom

The free camera's zoom: each step +0x24 += tan(+0x24/2) x (LB value - RB value) x 0.02 (17690F8); LB and RB held together reset it to π/4 (1765A20); it is clamped to 0.001..2.0 rad (1768808, 1C369B8; about 0.06 to 115 degrees vertical) at 101E90.

Basis: fn.py read of 101E27..101E90; flt.py

Addresses (build-specific RVAs unless indicated): 17690F8, 1765A20, 1768808, 1C369B8, 101E90

Debug command creating FreeViewCamera

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-free-camera-create

How the free camera is made: the debug command table (A1F90, registered on [20B2968] by 11A0900, UTF-16 names) holds free_camera (9BA90, string 1763E48), next_camera (9F5B0, 1763E60), Map / map (9E4A0), MapPreview (9E720), MapPreview_NoCollision (9E970) and stereo_camera. free_camera takes two ints below 4 (view slot, input device) and calls 1016C0(&pose, slot, device, 1) with the pose copied from view slot 0's camera rows +0x220..+0x250, then 11959E0(system, 1); next_camera makes one on device 1 with flag 0, then picks a slot's camera through 1196850. 1016C0 first walks the views (11988D0, visitor vtable 17690C8) and stops if one already has a free camera, then FF090 allocates 0x690 bytes, runs FF580 and queues the camera at system+0x4C0 (1195990, lock +0x308). How a view slot then switches to it was not traced.

Basis: fn.py reads; --str of the names; --xref of 1016C0 (5 calls, all in debug handlers)

Addresses (build-specific RVAs unless indicated): A1F90, 20B2968, 11A0900, 9BA90, 1763E48, 9F5B0, 1763E60, 9E4A0, 9E720, 9E970, 1016C0, 11959E0, 1196850, 11988D0, 17690C8, FF090, FF580, 1195990

Post effects: what exists (bloom, auto exposure, AO) and what does not (depth of field)

No identified depth-of-field or bokeh shaders

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-post-chain-shaders

EDF.dll's 490 DXBC blobs hold no depth-of-field, bokeh, motion-blur or vignette shader (no such resource or constant name). The post chain is compute shaders: resize 1FE0880 / 1FE0E50 (ComputeResizeSetting), bright pass 1FE1630 (ComputeHighPassSetting), blur 1FE1D20 (ComputeGaussBlurSetting, 288-byte weights), exposure 1FE36B0 (ComputeToneLerpSetting), combine 1FD6D30 (ComputePostCombineSetting), plus depth helpers (ComputeDepthToViewZ 1FE3CE0, CalLinearDepth 1FEBAB0) and Alchemy AO (1FE57E0, 1FE7060, blurs 1FE8A40 / 1FE9F40, composite 1FEB450). A linear or view-space depth therefore exists on the GPU already (for AO).

Basis: RDEF of every blob (t7_dxbc_all.py); RVA = file offset + 0x1E00 in this range

Addresses (build-specific RVAs unless indicated): 1FE0880, 1FE0E50, 1FE1630, 1FE1D20, 1FE36B0, 1FD6D30, 1FE3CE0, 1FEBAB0, 1FE57E0, 1FE7060, 1FE8A40, 1FE9F40, 1FEB450

Final scene combine tone and bloom

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-post-combine-formula

The final combine 1FD6D30 (16x16 threads): out.rgb = scene (t0, loaded per pixel) x tone + blur0 (t1) x cb2[1].x + blur1 (t2) x cb2[3].x, alpha 1; tone is the single float of the structured buffer t3 (g_tone_data), the blurs are sampled at uv x cb2[0].zw / cb2[2].zw clamped to cb2[0].xy / cb2[2].xy (the 64-byte g_post_combine_bloom). The bright pass 1FE1630 scales the source by the same tone, takes Y = 0.298912 R + 0.586611 G + 0.114478 B, multiplies by saturate(Y x +0xC + +0x10) (cut-off fade) and limits Y to +0x14 (maximum). So exposure is one multiplier on the whole scene before bloom is added.

Basis: D3DDisassemble of both blobs (t7_post_dis.txt)

Addresses (build-specific RVAs unless indicated): 1FD6D30, 1FE1630

EDF6 automatic exposure compute stage

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-auto-exposure-formula

Auto exposure 1FE36B0 (one thread, run per frame, inferred): reads texel (0,0) of t0 (the scene shrunk to its average, inferred from the resize chain), L = max(Y, 0.0001); with c = g_tone_lerp_brightness_center, t = ..._brightness_target, k = ..._brightness_lerp, p = saturate(g_tone_power): goal = t / (p x L + (1 - p) x 2ct), then tone += k x (goal - tone), stored back to the one-float buffer u0. So p = 1 maps the scene average to t, p = 0 gives a fixed tone 1 / (2c), and k = 0 freezes the tone where it is.

Basis: D3DDisassemble (t7_post_dis.txt)

Addresses (build-specific RVAs unless indicated): 1FE36B0

Render-system bloom and exposure fields

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-bloom-tone-settings

Bloom and exposure settings live in the render system ([20B2958]) at +0x280..+0x2C8, defaults at 11913F0..1191466: +0x280 HighBloomCutOff 0.5, +0x284 its fade 0.4, +0x288 HighBloomBrightnessMax 1000, +0x28C HighBloomBrightness 0.2, +0x290 LowBloomCutOff 0, +0x294 fade 0.2, +0x298 max 1000, +0x29C LowBloomBrightness 0.2, +0x2A8 v3_brightness_max 10, +0x2AC v3_center_brightness 0.5, +0x2B0 v3_brightness 0.5, +0x2B4 v3_lerp 0.2, +0x2B8 v3_intensity 0.9. Names from the LightEnv keys that fill the same block (#edf6-lightenv-tone-keys); that +0x2AC..+0x2B8 feed the exposure shader as center, target, lerp, power is inferred from the key order and the shader's cbuffer order; the upload was not found.

Basis: fn.py read of the defaults; a .text scan for +0x2AC / +0x2A8 found no other float reader

Addresses (build-specific RVAs unless indicated): 20B2958, 11913F0, 1191466

LightEnv tone and bloom key parser

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-lightenv-tone-keys

The LightEnv's key-value parser 15FE20 reads the tone and bloom keys (v2_HighBloomCutOff, ...CutOffFade, ...Brightness, ...BrightnessMax, the same for v2_LowBloom, v3_brightness_max, v3_center_brightness, v3_brightness, v3_lerp, v3_intensity; at 16117F..161303) into env +0x2E0..+0x318 and sets the word +0x2D8 = 0x101; the DSGO parser 161830 has _tone, _lowBloom, _highBloom (1621B1, 162250, 1622A2). The env apply 1230A0 then copies env +0x2E0..+0x328 to system +0x280..+0x2C8 (123380..1233C0; the block rendering.md#view-distance-details left unread) and, when +0x2D9 is set, snaps every view's tone to v3_brightness with 119AD80(system, 2136FF0, value) -> 1175870 on each view's buffer (system+0x620 + i*0x188) -> 113F7C0 (a render-queue buffer write); then clears +0x2D8. Mission scripts fade them by EVENT_LIGHT_ENV_FADE_TONE_CENTER_BRIGHTNESS, ..._TONE_BRIGHTNESS, ..._TONE_BRIGHTNESS_LERP, ..._TONE_POWER (not followed).

Basis: fn.py reads; key strings at 178C9F0..178CBF8 and 178CCF8..178CD30 (findstr.py)

Addresses (build-specific RVAs unless indicated): 15FE20, 16117F, 161303, 161830, 1621B1, 162250, 1622A2, 1230A0, 123380, 1233C0, 119AD80, 2136FF0, 1175870, 113F7C0

Complete original research record — expand (1,382 characters)

Photo-mode route (untested): (1) freeze: 1196FC0([20B2958], 8, true) from code on the game thread (inside a hook on the camera step, as the free camera does), value 8 being unused and masked out online, so it cannot stall an online game (#edf6-pause-mask-offline; the free camera's own value 1 would); the scene update stops while cameras step and the frame renders (system.md#system-pause-bits); clear it to resume. (2) camera: either make the stock free camera with 1016C0(&pose, 0, device, 1) (it pauses by itself, flies, zooms and steps frames, but reads named controller inputs, #edf6-free-camera-bindings), or keep the player camera and overwrite its rows +0x220..+0x250 and FOV +0x24 after F86A0 returns (camera.md#ghost-camera-target-fixed; the next frame eases from +0x250). (3) HUD: 118DF30(camera, 0) per view (hud.md#player-hud-switch). (4) focal length: +0x24 is the vertical FOV in radians, f = 12 mm / tan(FOV/2) on a 24 mm-high frame (π/4 is about 29 mm); the free camera allows 0.001..2.0. (5) exposure: tone multiplies the scene (#edf6-post-combine-formula): set system +0x2B4 (lerp) to 0 and write the tone through 119AD80, or set power +0x2B8 to 0 and drive the center (tone = 1 / (2c)). (6) depth of field: none in the game; needs a new compute pass between the scene and the combine (1FD6D30), fed by the depth the AO already builds (#edf6-post-chain-shaders).

Basis: assembled from the lines above; nothing run
