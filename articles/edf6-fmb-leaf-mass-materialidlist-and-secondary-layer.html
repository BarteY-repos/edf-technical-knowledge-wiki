EDF6 FieldRender FMB: leaf anatomy, mass cells and secondary-layer uncertainty

EDF 6Maps & NavigationFMB terrain binary structure
Technical reference · Native source-corpus/static binary evidence, runtime limitations stated explicitly

At a glance

What this page answers: EDF6 FMB terrain leaves combine geometry, mass-cell material weights and local identifiers; they are not conventional MDB mesh entries.

How to read it: Start with the native six-file leaf census, then read primary material lists separately from the secondary-layer uncertainty.

Evidence boundary: A decoded and structurally valid leaf does not establish the shader's final colors. The '_2' resource behavior remains a distinct open question.

The .FMB terrain resource is not an ordinary .MDB model. In the examined EDF6 source corpus it contains a spatial directory of tree records and compressed leaf payloads. A leaf combines triangle/vertex geometry, a mass cell grid, local material identifiers, shader selectors and material weights. The correct interpretation depends on each leaf's own descriptor and reference bases; merely unpacking the CMPL wrapper or displaying the triangle mesh does not establish semantic correctness.

Full native control corpus

An exhaustive read-only census of the six retained IG_HEIGEN507*.FMB files decoded and structurally validated all 1,200 leaf records. The combined directory contained 2,394 records: 1,194 internal/tree records and 1,200 leaves. The scan evaluated 1,045,523,544 decoded bytes, 2,058,350 triangles, 1,085,605 vertices and 12,582,869 mass cells. All listed semantic error classes were zero in this bounded corpus. A separately inspected IG_CAVE503.FMB added 102/102 passing leaf controls.

This does not mean all FMB assets in every EDF6 build have identical flags, counts or selector assignments.

Leaf sizes, geometry counts and mass-cell layouts vary within these ranges. A decoder should verify each leaf rather than using main-file averages as constants.

Checks that distinguish a correct decoder from a plausible-looking preview

For each leaf, the recovered structural relations include:

  1. Exact CMPL decompression and agreement of wrapper versus decoded bounding boxes.
  2. The index array and triangle count must agree: index_count == triangle_count * 3.
  3. Index storage must be followed by the properly aligned mass-cell region; mass_count == divideX * divideZ.
  4. The decoded vertex tail occupies vertex_count * 24 bytes in the audited native layout.
  5. The material list is a fixed-size sparse list; active material IDs must resolve within native material tables.
  6. Material weights may reference only active local slots, with valid selector/config-row bounds.
  7. Reserved fields and weight padding must satisfy observed zeros. A successful render does not excuse inconsistent reserved data.

The 16-byte MaterialIDList is sparse. The byte value 0xFF means this slot is empty, not stop parsing now. Its actual arity is the count of non-0xFF slots, not the index of the first hole. A capacity-like word in the leaf descriptor is a separate field; it is not universally identical to the local material-list arity. Merging those concepts would misdecode valid native leaves.

Native shader layer count versus local mapping width

The November EDF6 loader and shader study exposes three different counts, each with a different purpose:

ValueWhere it belongsInterpretation
0x10 bytes = 16 entriesDecoded FMB mesh local MaterialIDList, referenced by mesh +0x38Storage for up to 16 one-byte indices, with sparse 0xFF holes. This is not proof that all 16 are simultaneously active.
n = 1..15MAP_FIELD_RENDER<n>_1_14_<pass>.SGONative compiled shader family selected by layer count. Fifteen n values times three passes (0/1/2) give 45 identified shader assets.
12 slotsStudied R4/R6 non-native local RGBA preview/bridge transportOne renderer-translation capacity; not the native FMB format or SGO catalog maximum.

Inside a decoded 0x3C-byte mesh record, the shader selector at +0x24 encodes (layers << 8) | slots; +0x28 indexes the FMB shader-config table, and +0x38 points to the 16-byte mapping. The cited source checked all 9,753 meshes in 46 EDF6 FMBs: each selected shader-table row declared the same layer count as the selector's high byte; the surveyed pass/flag values were zero. The config table contains 7-dword rows and is a different table from the per-mesh 16-byte material mapping. An earlier main-file report of 27 configuration rows and a separate 21-row 0x15 header profile must not be equated without checking file identity and table role.

The EDF6 loader creates per-leaf 0x50-byte weight records and 0x10-byte mapping records at their actual counts, and formats the SGO name from the selected layer count. The reported fifteen-layer, pass-0 pixel shader uses 156 structured loads and 45 array texture samples: that is a property of that specific compiled variant, not of every terrain draw. Pass 2 omits a normal resource and its registers shift, so register numbers should not be reused blindly between passes. All these statements come from static loader/shader inspection for build steam-678ccb46, not a frame-level capture.

Color-slice edge case: in a pinned one-layer EDF6 pixel shader, the material color-array slice multiplier is loaded as an unsigned integer from the material buffer (g_materials + 48) and converted with utof; the source found no branch for a missing -1/0xFF value on that path, unlike its cited EDF4.1 counterpart. A D3D11 WARP probe sampled slice 0 for uint(-1), but that result must not be promoted to a guaranteed native EDF6 GPU behavior. Preserve valid native slice indices rather than relying on the probe's fallback.

Shader selectors are not proof of finished rendering

One flat, experimental FMB record used two triangles, four vertices, two local materials, config index 4 and the shader config row (2,1,0,0,0,0,0). The associated selector/capacity pair 0x0202 + cfg4 also occurred in 80 of 118 inspected native HEIGEN ENKEIRIGHT leaves, supporting the established filename resolution MAP_FIELD_RENDER2_1_14_0.SGO for that particular selector.

That selector match is structural evidence. It cannot prove that non-native material/orientation records render correctly. The experimental record's two 80-byte material records did not match any of the retained HEIGEN/CAVE native material records exactly. Orientation and texture-slice bindings also differed. A black terrain surface therefore cannot be diagnosed solely from filename selection without direct rendering evidence.

For source texture-array and preview-attribution boundaries, see FieldRender/FMEP records.

Planar material orientation is a separate native byte contract

The native IG_HEIGEN507_ENKEIRIGHT.FMB planar material and orientation records survived an exact parse/re-serialize round-trip: material 0 and both orientation records were byte-identical. Comparing the retained experimental FMB with native ENKEIRIGHT material 0 gives a narrower, unproven rendering discriminator:

Semantic field Native ENKEIRIGHT material 0 Experimental flat record
Planar paint mode / correction 0 / 6.0 0 / 6.0
Base/color and normal slices 0, 0 0, 0
Base/detail orientation pair (0,1) (0,0)
Detail/multiplier texture slice 1 0
Euler orientation (90°,0°,0°) for both native orientations (0°,0°,0°)
Projection scales (7,7,7) and (100,100,100) (20,20,20)

The exact shader specialization already matched a native-observed selector; these remaining byte/semantic differences are why matching an FMB shader filename alone does not validate planar terrain rendering. No direct in-game experiment in the inspected source establishes the root cause of a black surface or grants a universal material conversion rule. The separate auxiliary floats were deliberately not assigned a guessed native role.

Why IG_HEIGEN507_2.FMB should remain a distinct unknown

The retained _2 file is not corrupt. It passes the same structural checks with 468 leaves, a 1-metre mass-cell grid, sparse geometry of roughly 1–61 triangles and 3–46 vertices per leaf, and central coverage around 2500 × 2500 metres. It shares the main map's six-material/two-orientation structure and material lookup table, although its 27 config rows appear in a different order.

However, the examined IG_HEIGEN507.MAC explicitly names the main and four ENKEI FMBs but does not name _2; the retained RAB also provides no _2 name link. The sources did not establish an implicit *_2.FMB loader rule. The only defensible classification is structurally valid secondary FMB with an unresolved native loading role. Its presence is not permission to assume all secondary FMBs load automatically.
