EDF6 Common Clip and Common Light: exact native MDB material profiles

EDF 6Game technical referencesShaders
Technical reference · Native-data and static code observations; no new in-game runtime test

Two ordinary map-model shader families in the examined EDF6 MDB corpus are especially easy to oversimplify: snd_BRDF_Map_Common_Clip for alpha-cutout surfaces and snd_BRDF_Map_Common_Light for the basic illuminated/emissive path. Both use a 60-byte, one-UV native mesh declaration in the bounded source examples, but they have different material contracts and texture slots.

Family Native shader Observed slots in the qualified reference Mesh stride / UV
Common Clip snd_BRDF_Map_Common_Clip albedo, normal, param_r_m_xxx_hr 60 B, one UV set
Common Light snd_BRDF_Map_Common_Light albedo, normal, param_r_m_light_hr 60 B, one UV set

The material includes its own ordered parameter records, exact type/size values, flags, layer, priority and native default values. A shader name and vertex stride alone do not supply that information. In the studied Common_Light family, light_color can be HDR (components above 1); clamping to a normalized editor color can alter the appearance.

Cutout is not generic transparency

A 44-material sample of native Common Clip configurations had alpha_clip=0.5 for 42 instances and 0.3435 for 2 instances. This is an observed distribution, not a universal engine default. A sk_pShrub003-df.dds asset provides a concrete BC1/DXT1 one-bit-alpha example. Other cutout and glass families use different render states; a cutout material is not equivalent to snd_Map_Object_Glass or BRDF Window.

Known valid format versus observed in-game image

The source qualified complete MDB geometry/material profiles structurally and reproduced the native-observed parameter ABI in offline tests. It did not verify in-game rendering for a newly generated model. Therefore native-like record ordering and exact values are stronger evidence for correct serialization than a generic PBR viewer, but not themselves proof of the final pixel appearance, clipping threshold interaction or glow intensity.

For other profiles see native Windows/Glass/Parallax family contracts and typed MDB material serialization.

What the exact pixel shaders establish beyond the MDB records

Native material serialization and the shader's arithmetic are distinct evidence. Two pinned Common_Clip pixel-shader paths have the static alpha test equivalent to:

if sampled_albedo_alpha < alpha_clip: discard

This strengthens the interpretation of the named alpha_clip parameter for those compiled paths. It does not imply that all native clip materials use one threshold, nor that cutout is blended translucency. The material-level distribution above (42 of 44 at 0.5, two at 0.3435) is a bounded census, not a global default.

For one exact Common_Light pixel shader, the recovered MRT write has the shape:

SV_TARGET6.rgb = sampled(param_r_m_light_hr).b * light_color.rgb

Crucially, the pinned write does not contain an extra multiplication by diffuse/albedo. A broader contributed renderer guide describes emission as depending on pre-emission color; that more general account must not override this specific compiled program. The scene compositor may combine other colors later, but the recovered target write alone cannot establish that later behavior.

Both shader families remain distinct from legacy SND_CHARA_BASIC, glass/window translucency and the separate terrain/FieldRender path. Identical mesh strides do not imply identical GPU outputs. For the broader static-vs-frame evidence matrix see EDF6 rendering and shader evidence.
