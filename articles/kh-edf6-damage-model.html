Which hits reach the damage function

GameObjectBase hit-message dispatch across object classes

Evidence: static · Build: steam-678ccb46 · Fact ID: hit-handler-coverage

Every one of the 150 game-object classes (anything derived from GameObjectBase) routes the hit message 0x10000000 to the base handler 54A530, and that handler is the only caller of the damage function 547C30: no class applies hit damage by itself. So every living game object the player hits goes through 547C30 and produces the damage event (damage-numbers.md#damage-event-payload).

Basis: the chat's message-handler audit (msgaudit.py) over every class's vtable

Addresses (build-specific RVAs unless indicated): 54A530, 547C30

Attribution: novae (ajane) · 2026-10-11

Hit record and message plumbing

Hit record fields and message creation

Evidence: static · Build: steam-678ccb46 · Fact ID: hit-record-layout

Hit record fields (set up by 5CBDA0(_, record, &y, &position, damage (doubled), attacker), combat.md#hit-message): +0x10 / +0x18 attacker handle, +0x20 type (type 4 forces part rate 1.0, so it ignores armor), +0x24 team (-1 = no team rules), +0x30 position, +0x50 base damage (negative = heal), +0x58 blast value (> 1e-6 = a blast hit), +0x60 flags (0x40 forced, 0x200 skip, 0x400 rate 1.0, 0x1000 see flag-1000-zero-hits), +0x68 shield multiplier, +0x70 hit-point vector (data +0x78, capacity +0x80, count +0x88, 0x30 bytes per point; reserve 124190). Example sender: the vehicle self-destruct 673850.

Basis: disassembly; +0x68 agrees with weapons.md#shield-attribute-resists (KittopiaCreator: the shield-damage attribute at +0x68); that it is a per-bullet shield multiplier is the source's inference

Addresses (build-specific RVAs unless indicated): 5CBDA0, 124190, 673850

Hit record lifecycle and initialization

Evidence: static · Build: steam-678ccb46 · Fact ID: hit-record-life

Hit record life: the constructor (22FDF0..22FE27) zeroes the record, sets +0x68 = 1.0 and reserves 4 hit points (124190(+0x70, 4)); the point vector is freed with 11E9D0(+0x70). Attackers cross the network as object reference ids (785050, the same ids the kill message uses; resolved with 784C60). Hit-point vector: collision body references

Evidence: static · Build: steam-678ccb46 · Fact ID: hit-points-bodies

Hit points name the bodies hit: each entry of the hit record's point vector (+0x70, 0x30 bytes) holds the world point (float[4]) at +0x00 and the Havok rigid body id at +0x20. Classes hurt on one body only check them: UfoCarrier508's slot 16 4F7190 (hatch flag +0xD85) takes the point nearest the hit, maps its body id to a ragdoll body index with 6EA430(this+0xB60, id) and accepts the hit only when that index equals the core's (+0xD8C); MovingFortress 4C6650 does the same with +0xB00 / +0xE64; a hit without points is refused. A ragdoll component (built in place by 6E3B10, no vtable) has its body array at +0x78 and count at +0x88; a body's id is [[b+0x50]+0xF0], or [[[b+0xB0]+0x10]+0xF0] when b+0xB8 is set (6EA46C). Ragdolls sit in objects at +0x400, +0x420, +0x4E0, +0x4F0, +0x500, +0x520, +0x5E0, +0x650, +0x6F0, +0xAA0, +0xAC0, +0xAF0, +0xB00, +0xB10, +0xB40, +0xB60, +0xCC0, +0xCD0, +0xD80, +0xD90, +0xDA0, +0xE00, +0x10F0, +0x1320 (every lea rcx, [obj+X] before 6E3B10 or 6EA430). Body ids belong to each machine's own physics world.

Basis: the authors' static reading and their test, which calls the game's 4F7190 on a stand-in object (core index 2 accepted, 1 refused, no points refused); 6EA430 is the is-part check of objects.md#havok-helpers

Addresses (build-specific RVAs unless indicated): 4F7190, 6EA430, 4C6650, 6E3B10, 6EA46C

EDF Knowledge Hub record — original wording — expand (1,238 characters)

A bullet's hit record is bullet+0x870 (= core +0x730, core = bullet+0x140); its direct-hit queue is core +0x6E0 (bullet+0x820), one per bullet, filled at 230EA6 in 230CA0. Queue: entry array +8, capacity +0x10, count +0x18, mutex +0x20; a second hit on a target already queued merges its hit points into the old entry and drops its +0x50 damage, so a settle applies at most one entry per target. Settling is synchronous inside the caller: direct hits at 232702 (in 2321B0) and 23426F (in 233CB0), blasts at 54301D (in 542860, which copies the record to the stack at 5429B9 and queues per target on a local queue at 542FD4); 543920 clears the queue at 543BC4. Bullets with flag 0x10 clear the direct-hit queue (231490 at 23268E / 2326E2) and do only blast damage. Blast callers pass the bullet's record in rcx (232507, 232682, 2326CE, 23645D, 236978); 542490 / 542670 pass rcx through to 542860(record, flag*, hitSet*, xmm3 radius, [rsp+0x20] collision filter info, [rsp+0x28] ignored object, [rsp+0x30]) (corrected 2026-11-07: the note first called [rsp+0x20] a frame; 542670 passes the result of the layer-13 getter 106070 there, 5426B5 -> 5426BA -> 5427AE, #area-damage-call). The record copy 114210 keeps no pointer back to its source.

Bullets reference owners rather than weapon objects

Evidence: static · Build: steam-678ccb46 · Fact ID: bullet-to-weapon

A bullet does not know its weapon, only its owner: the parameter block's +0x08, copied to core +0x9A8 (= bullet+0xAE8, control block bullet+0xAF0) and to record +0x10. The owner comes from weapon +0x838, written once in the weapon init (68D5AD). Every player weapon class (33 Weapon*) fires through 696FD0(weapon, muzzle, overrideParam, counter, replay) (network replay 692540 too): bullet factory weapon+0x7F8, InitParam weapon+0x800 (+0x9E0 with an override); each bullet, shotgun pellets included, is created synchronously at 69799F (call 1194280(manager [20B2958], &matrix, factory, InitParam)), so a hook there can map the new bullet to weapon = InitParam - 0x800 or - 0x9E0. Not through it: the EMC maser (Weapon_VehicleMaser: 6B27B6 -> 2B3340 -> 2B2A10, a DummyBullet built at 2B2BAD), bullets spawned by bullets (the generic fire unit 2B95A0 at 2B9F68: NapalmBullet01, MissileBullet02, ClusterBullet01, DemoIndirectFire), sentry guns (2A4291 / 2A42F2), and enemies (their own weapon paths, owner = the enemy).

Evidence: static · Build: steam-678ccb46 · Fact ID: direct-hit-to-damage-path

EDF Knowledge Hub record — original wording — expand (1,524 characters)

A direct hit from shape cast to damage: 232359..23238F clamps the shape cast's hit fraction and passes the hit's body id (hit+0x48), position and normal to 230CA0; there 230CD3..230CDB turns the body id (*r9) into the hit object with 108260 (into r14); 230E34..230E6C fills the hit record that core+0x7A8 points to (+0 the real contact point, +0x20 the body id); 230E70 sets rcx = core+0x6E0 (so a hook can recover the core); 230E80..230E96 builds a weak reference to the target from the object's self weak +0x28 / +0x30 (adding a weak count); 230E9A..230EA6 sets r8 = core+0x730 and rdx = &that weak reference and calls 541FF0 (three arguments, the result unused). Redirecting only that call (as All Forces does to turn a hit into boarding) leaves the native collision, hit event and bullet stop or pierce untouched; the broadphase candidates (addBody) come before the layer filter, the nearest map hit and the object shape cast (bullet-collision.md), so they are not hits. Self-damage from player vehicle explosions

Evidence: static · Build: steam-678ccb46 · Fact ID: vehicle-self-blast

A vehicle's own blast hurts it: a player-driven vehicle's weapon rounds carry core+0x790 = 0x23 (0x20 = no team filter, #bullet-damage-record-flags), and the blast 542670 queries a box of radius AmmoExplosion around the burst, which meets the vehicle's body bounding boxes, not its origin; in the author's runs a 700-damage, 12 m missile bursting 6.8 m and 13.7 m from the launching tank's origin took 175 from it each time (700 x 0.25, the friendly-damage factor on Normal), at 22 m nothing; a Tunguska-type launcher lost 125 to a 500-damage burst. A round's own direct hit never strikes its owner: offline a vehicle weapon's owner is the vehicle, and the collector 232AA0 skips bodies whose key-0 object is the owner unless core+0xAF4 bit 0x80 is set, which a missile never sets (bullet-collision.md#bullet-collector-addbody).

Dead-character state and object identity

Evidence: static · Build: steam-678ccb46 · Fact ID: death-same-object

A dead character is the same game object: 547C30 sets +0x2E8 = 1 at the first HP <= 0, and no EventAnimationObject replaces it. InsectBase: OnDamaged 4A8DA0 sees +0x2E8 and removes the cling body (6DAE80(obj+0xE00) at 4A8E4D); the death state (for example 422C70) activates the ragdoll (4A8570 -> 6E4160) and hands it the cling body's last velocity (6ECF20(obj+0xB10, 11B1300([obj+0xE10])), 4230B0..4230D2); between the two there is neither a movable body nor a movable ragdoll. HumanoidBase: slot 60 479640 activates the ragdoll 6E40B0([obj+0xA78]) and registers it with the ragdoll manager (6EED10([20B30E0], ragdoll, weak self), corpses.md#ragdoll-register). HumanBase's ragdoll is obj+0xD90 with +0x1180 the ragdoll state (inferred); a blast knocks a soldier into it without death. Native damage message, friendly-fire flag and synthesized death record

Scope: five previously unanchored EDF6 damage-model.md facts. The already reconciled owner-hp-change-factors-2 successor remains at its existing anchor. These are contributor static readings; the synthesized kill case was not executed in this wiki session.

Messages and writable damage records: SendMessage 1DA480(obj,u32,data) calls object slots 10, 9 and 11. Queued hit delivery at 543AB9 uses message 0x10000000; GameObjectBase slot 9 54A530 converts the ID to a switch index by subtracting 0x10000000 and accepts only 0x10000000..0x1000000F, with case 0 dispatching ApplyDamage 547C30. Arbitrary high IDs such as 0xF0000000 are not equivalent. Soldier handlers (Ranger/Wing Diver/Air Raider 598FD0, HeavyArmor 567250) pass through HumanBase 572810 to the base handler. When a death edge occurs, the handler emits PlayerDown and writes data+3, so the passed damage record must be writable, not read-only memory.

Friendly-fire evaluation: local byte [rsp+0x20] starts clear at 547DA6 and becomes 1 at 547DE6 when the hit team's +0x24 and target's +0x314 are known (not -1) and their relationship is friendly. Self-hits meet the same-team condition. At 547DEB, ordinary friendly damage is rejected without hit flag 0x20 or target exemption +0x380 & 0x100000; otherwise D8110 supplies difficulty's friendly multiplier in xmm8. 5483CD reads the byte again to suppress activation by friendly hits. Both [rsp+0x20] and part factor [rsp+0x44] remain accessible in 547C30's fixed stack frame at 54820F for an appropriately bounded static hook.

Contributor's proposed forced player down, untested: a 0x90-byte writable hit record can use team +0x24=-1, null attacker fields +0x10/+0x18, target position at +0x30, finite high damage at +0x50, forced flag +0x60=0x40, one valid 0x30-byte hit-point structure referenced by +0x78, and +0x88=0. A null hit-point pointer is unsafe because native readers 54E400/5987DB dereference it regardless of count. Avoid FLT_MAX: a downstream inf×0 may become NaN and clamp back to full HP. Since hit settlement is local to the executing machine, source advises operating on that machine's own controlled soldier (player input pointer +0x340, control bit +0x128) and then allowing normal soldier down message 0x11 and slot 41 577020. It does not invent a new MissionResult failure enum: an all-dead fail is script-driven by MissionGameOverEvent. This paragraph records a theoretical data contract, not a tested kill implementation.

Weak-part multipliers and slot-17 overrides

Part factor output: target vtable slot 17 (+0x88) accepts a two-float output at rdx=rsp+0x40. Its second float [rsp+0x44] starts at 1.0 (54806D), may be overwritten by the slot, resets to 1.0 when hit flag 0x400 is set (5480EC), then multiplies damage at 548148. Values above one are plausibly more vulnerable hit parts, below one armor, but the author did not measure per-body values in-game. This is one contribution to the already documented chain of target/ModeList and friendly-fire factors.

Class-specific slot-17 implementation census: HumanoidBase variants, BigGreyBoss, Martian and Venus share 4704B0, deriving out[1] from a hit part via 4915D0(this+0x6C0,record) and forcing 1.0 for hit kind 4.
