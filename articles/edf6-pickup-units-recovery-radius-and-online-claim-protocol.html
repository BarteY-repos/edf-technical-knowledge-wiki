EDF6 pickup manager: health recovery, physical boxes and host arbitration online

EDF 6Game technical referencesPickups and rewards
Technical reference · Source-declared grades; this edition does not add native game runtime testing

An EDF6 pickup box is a DropItemManager::Unit stored in a manager-owned linked list, not a general enemy GameObjectBase and not a hidden extra kind of hostile object. The manager owns the physical box instances, their category, their online IDs, pickup counters and the running drop accumulator.

Four item models and their behavior

Type Native model from app:/object/ItemModel.mrab When effect is applied
0 Weapon.mdb Counts a weapon crate for end-of-mission result
1 Armor.mdb Counts an armor crate for end-of-mission result
2 Healingsmall.mdb Immediately heals the picker: 15% max HP
3 Healingbig.mdb Immediately heals the picker: 30% max HP

The item manager in the studied EDF6 build has a list head at +0xDE0, item count at +0xDE8, a drop accumulator at +0xDF0 and a next-box ID at +0xE00. Individual Unit objects hold category at +0xC0, picked flag at +0xC4, box ID at +0xC8 and a physical transform. These are version-specific field locations, not a general EDF engine ABI.

Who can collect?

The soldier update calls the pickup manager once per update for an eligible local player. The pickup is tested against a point roughly one metre above the soldier position, using squared distance and a radius assembled from the soldier's class/state, certain accessories and the vehicle seat while mounted. A default base radius of 3.0 metres appears in the examined constructor; other states can increase it.

The actor must be alive and have the local player-controller field set. NPC allies walking through a pickup do not collect it. Recovery items can propagate healing to living recruited followers using a separate recursion and ratio rule. In the source's ordinary player configuration that follower ratio is 0.35; an equipment-derived factor may alter it. This does not imply an identical ally-healing rule for EDF4.1 or EDF5.

Pickups persist until a cleanup condition

DropItemManager maintains a physical box list, clamps horizontal positions into the map area, removes boxes after pickup or when their height falls below −1000, and clears the list on mission change. The source did not find a universal short crate timeout or an automatic map-wide magnet in the ordinary native path. The on-field limit is 128 crates and the collected-crate limit is 1024 for this build.

Online protocol and ownership

The source distinguishes four message kinds:

Message Native meaning
0 Replicate a newly spawned crate, using an agreed seed/ID
1 Guest requests the host to claim a particular box
2 Host publishes the confirmed pickup to participants
3 Request that an enemy death create dropped items

The picker applies the pickup locally, then communicates with the host. The host arbitrates which player first claims an unpicked ID and prevents duplicated weapon/armor counts. The source has no rollback if a guest applied an immediate local pickup that the host rejects. Box IDs can be negative; they are not equivalent to an enemy owner ID.

Evidence boundary: The state and message flow are static analysis of steam-678ccb46. An offline invocation of the game's own functions (83 checks) confirmed some radius and serialization behavior, but that is not a live multiplayer or complete game-run test. The original appendix labels those facts accordingly.
