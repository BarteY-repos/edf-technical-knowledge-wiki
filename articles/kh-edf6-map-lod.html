Tree LOD distances in .trb rules

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-trb-distance-fields

The .trb reader 14BA70 takes the tree's distances from rule 0: child 5 [near, far] -> out +0x14 / +0x18 (absent: -1.0 and -1.0, 1C369CC), child 4 [n] -> out +0x1C (absent: -1.0); the yaw is out +0x10 (rand(0..9999) from EDF5's LCG, 14BCB8). It also builds +0x28, the billboard texture (a name at out +0x20 plus .dds, 1768348, looked up with 18DD30 at 178C96; null when missing).

Tree mesh-to-billboard distance test

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-tree-billboard-switch

The mesh-to-billboard switch: a tree model's draw 17A020 takes x = |tree position - camera position|² x view+0x18 (17A0B2; the view factor's writer not traced) and compares it with the squared fields of #edf6-trb-distance-fields: above +0x20 the tree is not drawn at all (17A0BC); with near² +0x18 <= 0 or x <= near² it draws the full mesh; between near² and far² +0x1C both, crossfading (177C00 returns 1 - (x - near²) / (far² - near²)); beyond far² only the billboard card, and only in pass 0 and when the texture +0x28 exists (17A0DA..17A0E9, model slot 6), else nothing. 177C70 returns the same state as a number: 0 mesh, 1 crossfade, 2 billboard, 3 none. So billboard cards draw in no pass but 0 (inferred: no shadow from a card).

Basis: fn.py 17A020, 177C00, 177C70; the blend formula read from 177C46..177C63; pass meaning inferred

Addresses (build-specific RVAs unless indicated): 17A020, 17A0B2, 17A0BC, 177C00, 17A0DA, 17A0E9, 177C70

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-building-lod-pop

Buildings switch level of detail with a hard pop, not a crossfade: in a city map with tram tracks, a small step forward switched the building across the square (and the facades down the street) from a lower-detail model (flat facade, balconies and bay windows without relief) to the full one in one frame; novae (ajane) finds it jarring in motion. MapRenderer per-frame building LOD selection

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-building-lod-pick

The per-frame pick, a hard switch: the map render node (MapRenderer::ModelRenderer::RenderObject_Nodes, vtable 178FCD8; built from the LOD table by 16EE60, which makes one 0x38-byte unit per LOD, vtable 178FCC0, the distance at unit +0x30) gets slot 1 171360 from the Umbra collect: d = the node's distance term +0x24 (byte +0x45 stays 0 for map nodes, so the distance to the object's center) times the camera's zoom ratio (11E3EFA -> 11B28C0, camera.md#camera-projection-fields), squared. 171AD0 skips the node when its cull value (node +0x70) is positive and not above d², else picks the last unit whose distance is below d² (unit 0 always qualifies) into +0x98 (word) and queues only that unit (slot 2 171D20). One LOD is drawn per node per frame, no blend; zooming in brings full detail nearer.

Basis: fn.py 171360, 171AD0, 16EE60, 11B28C0, 11B2400; +0x45 writers grepped in 11DA60..17B023 (only copies and the tree class)

Addresses (build-specific RVAs unless indicated): 178FCD8, 16EE60, 178FCC0, 171360, 11E3EFA, 11B28C0, 171AD0, 171D20

Building and LOD material shader families

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-lod-fade-shaders

Shaders for a fade: building parts use shader/dx11/snd_map_build_*.sgo and their LODs snd_map_lod*.sgo (DX11.cpk), instanced (g_instancing_array, g_instancing_inv_array), with per-material xgl_user_param only (diffuse, specular, roughness, fall-off, dirt): no per-object fade, alpha or dither input, and snd_map_build_basic has no clip. g_xgl_fade_mul / g_xgl_fade_add sit in the per-view xgl_system cbuffer beside the fog terms (+0x238 / +0x23C; read by 84 of 349 shaders embedded in EDF.dll), not per object. Only three wind vertex shaders in EDF.dll (grass, inferred) fade by distance (xgl_user_param g_culling_distance +0x20, g_fadeout_distance +0x24). The tree band value of #edf6-tree-billboard-switch goes to 178010, which scales the number and size of leaf cards drawn (inferred from the arithmetic), not an alpha blend.

Tree and far-view rules

Standing trees include a stump-and-body pair

Evidence: static (gameplay observation and model analysis combined) · Build: not stated · Fact ID: map-tree-stump-drawn.

The source corrects an earlier “stump appears only after falling” assertion: the tree's main model and stump are a paired construct even while upright. Twenty-one _kabu stump models each pair with a main model; the main mesh has a cut face with pTreeKirikabu and the roots live in the stump. The large sk_ptree010_25m_kusu main begins about 1.17 m above ground while its stump spans −3.3 to +2.2 m. In the author's game check a hit toppled the main model while the stump remained; the exact draw-enable branch was not traced. Census examples: NW_TRAINCITY 439 trees/180 stumps, IG_MOUNTAINVILLAGE 4,087 trees/2,876 stumps. These counts refer to surveyed placement populations, not a universal stump-per-tree invariant.

Basis: ktaro's asset inspection and novae (ajane)'s source-reported fall observation, source.

Leaf-particle rule data exists but the shipped trees do not use it

Evidence: static · Build: not stated · Fact ID: map-tree-leaf-particles-unused.

The leaf-particle emitter route requires a TreeModel without skin meshes: the isSkinMesh byte at ObjectInfo +0x01 must be zero for every mesh (FUN_180187000 → FUN_181106C90). In a census of 410 .trb uses on 35 maps (75 unique names), every resolved main model had skinned meshes and used TreeSkinningModel, so rule 2 leaf data is present but the emitter is inactive in that surveyed stock set. The generation/shader pipeline was not shipped in ktaro's viewer, and the claim is not proof that custom non-skinned models could never activate it.

Basis:native-tree data census and static consumer branch.

Far-view placement bypasses ordinary part distance cutoff

Evidence: static · Build: not stated · Fact ID: map-far-view-flag.

A placement is treated as far-view when its MAPB definition +0x20 or placement +0x44 is nonzero. Such parts submit in the far pass and do not use the usual group cutoff or part slot 7. Conversely a FarMap-family material on a non-far-view group is not submitted by either pass. This is a placement/classification rule, not a general prescription to remove distance limits from all map objects.

Basis: ktaro's static map-placement and render-path reading, source.

Tree and small-object weighted selection: type mismatch trap

Evidence: static · Build: not stated · Fact ID: map-weighted-lottery.

FUN_180149C20 selects from rule groups shaped [weight, [items...]] with a total of sum(weight × item count), then advances the source RNG and subtracts each item's weight until the draw reaches zero. The .trb reader accepts integer or floating-point weights; the .mlb small-object reader at 149A00 reads only float. An integer-stored weight in an MLB will be interpreted as its float bit pattern (often effectively zero), not converted numerically. Preserve the native SGO value type when authoring weighted vegetation lists.

Basis: source, static rule-reader inspection and RNG interpretation; not newly tested in the Megawiki.

Map caster shadow setting

Source record: map-caster-shadow-setting · Source evidence: static

Which placed objects cast shadows: the game removes map objects whose embedded SGO says CasterShadow_Enable = 0 from the shadow casters (the Umbra bit 0x40000000); characters and vehicles always cast. The same SGO also has Shadow_Enable, Durability, CrashType, xgs_scene_object_class (always MapObject_***) and Action_* keys. In EDFROOM601 (mission 116) 1,767 of 1,872 placements are 0 (railings, pillars, room floors and walls, ceiling structures, containers); novae (ajane) checked in game that characters and tanks have shadows there while railings and ceiling structures do not. On outdoor maps the 0 objects are few, such as the distant-view boards (11 placements in IG_CRATER601).

Map def SGO settings

Source record: map-def-sgo-settings · Source evidence: static

The embedded SGO of a MAPB def (offset at def +4, relative to the field) carries settings the renderer reads: Type (a string; stock values include 地形パーツ terrain part, ビル building, 木 tree, 小物（棒） small object (pole), 小物（その他） small object (other) and 民家 house), CasterShadow_Enable (0 = the object casts no shadow; absent = it does) and Collision_Enable (absent = it has collision).

Map FMB cmpl start

Source record: map-fmb-cmpl-start · Source evidence: static

In all 46 FMB files the compressed (kind 2) leaf's CMPL block starts at element +0x24 (the stored offset at +0x1C points to the same place, counted from the element), and a kind 1 leaf is used in place; the viewer takes the file's bounds as the union of the leaves' boxes (center, half size). The CMPL LZSS routine ktaro wrote from the algorithm matches file-formats.md#cmpl-lzss (4096-byte window starting at 4078, flag 1 = literal, 2-byte token v >> 4 position and (v & 15) + 3 length, big-endian).

Map FMB grass

Source record: map-fmb-grass · Source evidence: static

Grass from the FMB (category 0 plant types; FUN_1801400b0): the grass registry grass.merge.sgo in the MAC maps a species name (the type file's stem) to a layer of the grass.merge.dds array; a type is skipped when its species is not in it. Per cell: the size = lerp(type min size [9..11], max size [12..14], the jitter's size factor), the half width = size x / 2, the height = size y, the yaw = -jitter angle, the color = one of the type's colors (parameter SGO, RGB / 255) picked by ((next(seed) >> 32) x count) >> 32 with seed = columns x row + column; the type's uv (u0, v0, u1, v1; default the whole image) and a scale 1 select the card. Identical (layer, uv, scale) sets share one entry (FUN_1801689e0); the blade color is multiplied by (0.75, 0.75, 0.75, 1) when drawn.

Map FMB material GPU

Source record: map-fmb-material-gpu · Source evidence: static

An FMB material (file section header +0x10: {material count, offset, projection count, offset}, offsets from the section): 0x50 bytes = 20 ints: [0..5] three pairs of ints (one pair per set, carried to the GPU as is; ktaro does not name their members), [6] the painting mode, [7..9] the color array index of set 0 / 1 / 2, [10..12] the multiplier index, [13..15] the normal index, [16] m_correction (a float), the rest unread. The GPU struct (FUN_18010ce70) is 80 bytes: three (projection, ?) pairs, the painting mode (3 is written as 2), three color, three multiplier and three normal indices and m_correction; set 1 and set 2 copy set 0's color, multiplier, normal and projection when their color index is -1. A projection (8 floats: rotation x, y, z in degrees, scale x, y, z, offset u, v) becomes a 64-byte matrix: rows i = (R[0][i], -R[1][i], R[2][i], offset_i) / scale_i with R = Rx x Ry x Rz, the Z offset 0.

Map FMB plant cell position

Source record: map-fmb-plant-cell-position · Source evidence: static

The cell position of every FMB plant (FUN_180140570, MapObject_Fmex_GrowGrasses's visitor): groups in file order, cells row-major; fx = (column + jitter x) x cell size + origin x, fz = (row + jitter z) x cell size + origin z, then x = fx x M11 + fz x M31 + M41 and z = fx x M13 + fz x M33 + M43 of the terrain placement matrix, y = the cell's ground height from the MAPO row's table (the placement's y is not added); the height index advances for every occupied cell, also those of other types or categories, and the jitter row is the cell's jitter-grid byte modulo the table's count.

Map FMB submesh slots

Source record: map-fmb-submesh-slots · Source evidence: static

A terrain sub-mesh (0x3C bytes in a leaf; layout in file-formats.md#fmb-layout): word [9] low byte = the number of slots that carry weights (the highest used slot + 1; held in 276 of 276 sub-meshes of the first chunks of all 46 FMBs), second byte = the shader's slot count; word [0] is not a shader index (first read as one; purpose unknown); word [10] indexes the shader list, whose row has material count >= the slots used and a painting-mode mix equal to that of the materials in use (no exceptions in the 276). The slot count the viewer uses = max(shader row [0], slots used) clamped to 1..16; one cell mixes that many materials. The weights array is 80 bytes x divide x x divide z (g_mass), the layer list 16 bytes each.

Map FMB tree placement

Source record: map-fmb-tree-placement · Source evidence: static

Trees that grow on terrain: FMB plant types of category 1 with a file ending .tree become the .trb of the same name (lowercased) in the MAC; the position is the cell's (x, y + the type's height offset +0xC, z), the seed is columns x row + column of the cell in its group, and the rotation is Ry(the jitter angle of table 3), kept only when rule 0 child 7 is not 0; the jitter's size factor is not used for trees.

Map grass counts

Source record: map-grass-counts · Source evidence: static

Grass counts and ground-drop checks (ktaro's viewer, off screen): IG_MOUNTAINVILLAGE 282,909 blades from the FMB (about 1,700 within 75 m of the camera; 282,330 find ground, the rest have none below), NW_SEIYU 17,699 (.grb only, dry grass on gravel lots), IG_BASE502 143,967 (FMB and .grb), IG_CRATER601 65,684 (all hit the ground; its .grb blades all sit at y0 = 10.0 before the drop and end at -0.1 to 0.0) and IG_HAIKYO603 32,256 (all hit; the .grb y0 of about 50 drops to -0.1 to 1.5, with tilts up to 47 degrees on rubble). A .grb area's y is uniform per area, so without the ray the grass floats.

Map GRB areas

Source record: map-grb-areas · Source evidence: static

Grass areas from MAPB (header +0x78; FUN_1801658a0 -> FUN_180166550): a block {vertex array offset, vertex count, area-row offset, area-row count} (offsets from the block's start, negative, confirmed on all 8 maps with grass .grb); vertices are 3 floats; an area row is 12 bytes {name offset, triangle-list offset (both relative to the row), triangle count}, the name being a .grb in the MAC (without extension), and each triangle 8 bytes {u16 a, b, c, u16 mark}. A row starts its random state at 0x796. The same block is described in file-formats.md#mapb-header-layout as a point or route block (0x78, inferred there): see the conflict listed in STATUS.

Map GRB rules subdivide

Source record: map-grb-rules-subdivide · Source evidence: static

The .grb rules (an SGO in the MAC): rules[0] = [[weight, [[species string index, uv, scale], ...]], ...] (weights are not read: every item is equally likely), rules[1] = [[width base, range], [height base, range]], rules[2] = [[weight, [RGB, ...]], ...] (a weight per color group), rules[3][0] = the spacing (at least 0.1). A triangle is split at the midpoint of its longest edge (the longest by squared length: a-b only if strictly longest, else b-c if it exceeds c-a, else c-a) until its area (Heron's formula; a NaN splits) is below spacing^2 / 2 or the depth is 40; the split carries a 3-bit mark of which edges lie on the original outline, and only a leaf with mark 0 (an inner triangle) grows one blade.

Map group cutoff

Source record: map-group-cutoff · Source evidence: static

The cut-off of a placed part: it is drawn only while the squared distance d^2 is below slot 7, with no extra 5 m (a first reading had one; ktaro's note says it was settled in EDF.dll). The distance base of a placement ("the group") is min(def +0x1C, MAPO row +0xC), a plain min (FUN_180173450); the group's cut-off is sqrt(max(that distance^2, the largest slot 7 among its parts)) plus the |X| and |Z| half sizes of the group's box (the union of its parts' main-model boxes in world space), with 1000 m used when the first term is 0. Distances are measured from the box center.

Map group distance rules

Source record: map-group-distance-rules · Source evidence: static

Of the 39 maps the missions use, 21 have no terrain FMB (the city nw_* maps and interiors, where the ground is placed objects), and a map's .rab sits in the same folder as its .mac. The game's per-group distance for part LOD and cut-off tests (the P1 stage of ktaro's viewer): the distance d is measured per group (one MAPB placement = one Umbra object), from the center of the group's box to the camera, and every part of the group is tested with that same d. The LOD level boundary is not smoothed: the main model while d <= sqrt(LOD 1), LOD 1 up to sqrt(LOD 2), LOD 2 beyond, the nearer level at equality, no hysteresis; a part with slot 7 above 0 is drawn only while d < sqrt(slot 7). The distance factor 1.0 was confirmed with Cheat Engine (verified). The game takes the half sizes from the group's box rotated by the placement matrix, ktaro from the world axis-aligned box (the difference inferred small), and the group box function FUN_180172630 is unread.

Map instance color seed

Source record: map-instance-color-seed · Source evidence: static

The per-instance color and seed the map shaders get (INSTANCING_change_color, INSTANCING_interior_random_seed; FUN_180156e40, FUN_180158d40): the color is the part's slot 4 RGB (none: the material's change_color is used); the seed is 1 / (|p|^2 + 1) + p.y + S / 300 with p the part's local position (slot 3) and S the sum of the low 16 bits of the four dwords at placement +0x34, +0x38, +0x3C, +0x40 (the GUID); a .mdx object uses 1 + S / 300. The EDF5 side of the same input: ../edf5/map-objects.md#edf5-map-instance-seed.

Map MAPO part slots

Source record: map-mapo-part-slots · Source evidence: static

A MAPO part (0x3C bytes; every offset below counts from the part's start, the slots are 4 bytes): slot 0 the kind (the stock values are 0, 1, 2, 4 and 770), slot 2 an offset to a quaternion (x, y, z, w; absent = identity), slot 3 an offset to the local position, slot 4 an offset to a color (RGB floats; absent = none), slot 7 the squared cut-off distance, slot 8 the main model name, slot 9 the squared LOD 1 distance (-1 = none), slot 10 the LOD 1 model (_lod), slot 11 the squared LOD 2 distance, slot 12 the LOD 2 model (_lod2). A part whose slot 8 is 0 draws nothing. The slots agree with map-lod.md#edf6-structure-lod-data (+0x1C is slot 7, +0x20 slot 8, +0x24 / +0x28 slots 9 / 10, +0x2C / +0x30 slots 11 / 12).

Map MAPO row parts

Source record: map-mapo-row-parts · Source evidence: static

A MAPO row's part list: row +4 is the offset (from the row) of an array of 4-byte offsets (each relative to its own slot) to the parts, row +8 the part count, row +0xC a float draw distance. A row with a count of 0 or less has no parts (a placement without parts, such as a terrain piece).

Map MDX object rules

Source record: map-mdx-object-rules · Source evidence: static

A placement whose def name ends in .mdx does not use its MAPO parts (Preload_Model, 1555A0): the model is the name with .mdb, the local matrix is the identity, slot 7 counts as 0, the color comes from the first part's color slot, and the LOD models are the names at def +0x24 and +0x2C (offsets relative to the field) with the squared distances at def +0x28 and +0x30 (LOD 2 only when its distance is above LOD 1's). Its group distance is def +0x1C when above 0.01, else 0. A def whose embedded SGO contains the name HAS_ANIMATION is an animated object, which ktaro's viewer skips.

Map MLB matrix

Source record: map-mlb-matrix · Source evidence: static

A small object's matrix: the rotation is (base + random) x 57.32484, a constant the game multiplies by directly (it is close to 180 / pi = 57.2958, the number a degree-to-radian conversion would divide by, but not equal; ktaro keeps the game's product and gives no explanation, so what the angle means in the game is unverified), built as the quaternion Rz x Ry x Rx, scale always 1; the position is the cell position + the type's height offset + (position base + random) turned by Ry(the jitter angle). The jitter angle does not remain in the orientation. The viewer treats the small object as an ordinary part: group cut-off = (slot 8, or 1000 when none) + the |X| and |Z| half sizes of the model's world box, distance measured from the box center, with _lod / _lod2 models only when the RAB has them (FUN_180126ba0).

Map MLB rules

Source record: map-mlb-rules · Source evidence: static

A terrain-grown small object (FMB category 1, file .mls, the MAC's .mlb of the same name): FUN_180145060 rules (the .mlb reader FUN_18014b5b0; each rules slot is wrapped in one list): slot 0 the model lottery, slot 2 a random rotation range (degrees), slot 3 a random position range, slot 5 a rotation base (degrees), slot 6 a position base, slot 8 the cut-off (0.01 or less = none), slot 9 [LOD 1, LOD 2] (compared with d^2 unsquared, so the distances are their square roots; 0 or less = no level), slot 10 the color candidates (RGB 0 to 255). The draw order from the seed (the cell's seed as a signed 32-bit value): the model pick, one idle step, the position offset x, y, z, the rotation x, y, z, then the color (index = ((s >> 32) x count) >> 32). Each random value is f x 2v - v (a step each).

Map part lod levels

Source record: map-part-lod-levels · Source evidence: static

The LOD distances of a placed part: LOD 1 is sqrt(max(def +0x28, slot 9)) and LOD 2 sqrt(max(def +0x30, slot 11)), used only when the part has the _lod / _lod2 model and the LOD 1 value is above 0, and LOD 2 only when it is larger than LOD 1. The main model draws from 0 to LOD 1, _lod to LOD 2 and _lod2 beyond; the part's cut-off and the group's apply to every level. ktaro marks the LOD 1 switch distance itself as inferred (the cut-off is confirmed), so it is unverified against map-lod.md#edf6-structure-lod-distances, which reads the same max from 158D40.

Map placement matrix

Source record: map-placement-matrix · Source evidence: static

A MAPB placement (0x48 bytes) is drawn from the MAPO row of the same index (0x1C bytes): the counts must agree (ktaro's reader throws otherwise). The placement matrix is the row-vector product Rx(pitch) x Ry(yaw) x Rz(roll), then the translation, with the angles in degrees from placement +0x10, +0x14, +0x18 and the position from +4, +8, +0xC (MapSyncObjInit); a part's world matrix is its local matrix x the placement matrix.

Map plant RNG

Source record: map-plant-rng · Source evidence: static

The game's random generator for map plants, one step: s = s x 0x5D588B656C078965 + 0x269EC3 (64 bits); R31(s) = ((s >> 32) x 0x7FFFFFFF) >> 32; the float draw F(s) = ((s >> 32) x 10000 >> 32) x 1.0001e-4, so a draw takes one of 10,000 values from 0 up to 9999 x 1.0001e-4 (about 1.0). The same generator as edf6/objects.md#object-rng; 149C20 loads the constants 0x2710, 0x269EC3, 0x5D588B656C078965 and 0.00010001.

Map terrain placements

Source record: map-terrain-placements · Source evidence: static

Terrain placements: the .fmep defs name the terrain FMB (name without extension) and carry a placement position and rotation like any object. Over the 45 maps, 42 terrain placements: most are translated, one is turned Y -180 degrees (for example IG_PLATEAU is raised by 80 and the park ig_2000mpark1 of IG_2000MCITY sits at (250, 0, -400)). A map can place the same FMB twice, and the terrain texture arrays are named after the MAC, not the FMB, and live in the RAB of the same name as the MAC (<map>_color.dds, <map>_normal.dds; confirmed on all 23 maps with terrain, for example IG_HEIGEN601 draws ig_heigen507_2 with ig_heigen601_color.dds). City nw_* maps and interiors have no terrain FMB: their ground is placed objects.

Map tree resolve

Source record: map-tree-resolve · Source evidence: static

A placed tree (a def named .trb; the rules are the SGO of the same name in the MAC): its seed is placement +0x1C, or when that is 0 the plain integer sum of the four dwords at +0x34 .. +0x40. From the seed s0 the game derives separate streams (FUN_18014ba70, FUN_180145ad0): A = R31(next(s0)) for the body and stump picks, B = R31 of the next step for the billboard picks, a third step for the leaf stream; the body is rule 0 child 0's lottery, the stump (a list in child 3) a second draw from A, the yaw = F(next(A)) x 2 pi without advancing A. The tree's matrix is Ry(yaw), times the placement rotation only when rule 0 child 7 is not 0, then the placement position. A tree whose body pick fails is not made.

Map tree sway quaternions

Source record: map-tree-sway-quaternions · Source evidence: static

The tree bone sway as quaternions: the game's quaternions follow the System.Numerics convention (matrix M(a x b) = M(b) . M(a)); the bone's new local rotation is q' = D x Rx x q with D = (B x Q_tree)* x Rz(angle) x (B x Q_tree), B the bone's bind rotation in model space and Q_tree the tree's rotation; the position is unchanged. The signs were fixed by comparing the street trees of NW_DANTI01 with the game (sign - in the bone's own axes forked the trunk low; sign + in the parent's axes matches), so the convention is unverified. The sway angle is at most about 2 degrees (weight 0.7, wind 0.3).
