EDF 6 — Map Lod (community source notes)

EDF 6Community Knowledge HubMaps
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Tree classes: MapObject_Tree (vtable 176BA90, 0x1F0 bytes, constructor 145AD0, made per .trb record by pass 2 11A3F0 at 11B303) reads its .trb with 14BA70 and registers its render model with MapTreeMgr ([20B2990]+0x278, vtable 178FEE8) through 176F90, which files it into a grid cell (17B030) of MapTreeMgr::TreeBlock render nodes (vtable 178FEC8, constructor 176EC0, an Umbra node built by 11B2400, tree list at +0x80). TreeBlock slot 1 177100 draws a block: 176720 walks the list and calls each model's slot 4 17A020.

Basis: RTTI names and vtables (scratch rtti.py), fn.py --xref on each vtable and reads of 145AD0, 176F90, 177100, 176EC0

The .trb reader 14BA70 takes the tree's distances from rule 0: child 5 near, far - out +0x14 / +0x18 (absent:…

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-trb-distance-fields

The .trb reader 14BA70 takes the tree's distances from rule 0: child 5 [near, far] -> out +0x14 / +0x18 (absent: -1.0 and -1.0, 1C369CC), child 4 [n] -> out +0x1C (absent: -1.0); the yaw is out +0x10 (rand(0..9999) from EDF5's LCG, 14BCB8). TreeRenderer_Billboard's init 178BE0 squares them into the model: +0x18 = near² and +0x1C = far² when positive (178D53..178D7F), +0x20 = cut-off² from child 4, 500 m (1765A7C) when negative (178D46, 178D84). It also builds +0x28, the billboard texture (a name at out +0x20 plus .dds, 1768348, looked up with 18DD30 at 178C96; null when missing).

Basis: fn.py 14BA70 (rule node offsets: child 4 at +0x30, child 5 at +0x3C) and 178BE0; constants read from the file

Addresses (build-specific RVAs unless indicated): 14BA70, 1C369CC, 14BCB8, 178BE0, 178D53, 178D7F, 1765A7C, 178D46, 178D84, 1768348, 18DD30, 178C96

The mesh-to-billboard switch: a tree model's draw 17A020 takes x = |tree position - camera position|² x view+…

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-tree-billboard-switch

The mesh-to-billboard switch: a tree model's draw 17A020 takes x = |tree position - camera position|² x view+0x18 (17A0B2; the view factor's writer not traced) and compares it with the squared fields of #edf6-trb-distance-fields: above +0x20 the tree is not drawn at all (17A0BC); with near² +0x18 <= 0 or x <= near² it draws the full mesh; between near² and far² +0x1C both, crossfading (177C00 returns 1 - (x - near²) / (far² - near²)); beyond far² only the billboard card, and only in pass 0 and when the texture +0x28 exists (17A0DA..17A0E9, model slot 6), else nothing. 177C70 returns the same state as a number: 0 mesh, 1 crossfade, 2 billboard, 3 none. So billboard cards draw in no pass but 0 (inferred: no shadow from a card).

Basis: fn.py 17A020, 177C00, 177C70; the blend formula read from 177C46..177C63; pass meaning inferred

Addresses (build-specific RVAs unless indicated): 17A020, 17A0B2, 17A0BC, 177C00, 17A0DA, 17A0E9, 177C70

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-anyobject-lod

MapObject_AnyObject (constructor 145060, for .mlb grown objects from 140230 at 1404A0 and placed ones from 11A3F0 at 11B4EB) reads its rules with 14B5B0: child 9 (up to four floats) -> out +0x48.. and child 8 -> out +0x44. It loads the models <name>_lod and <name>_lod2 (name builder 126BA0, and its twin 151240: kind 1 _lod, 2 _lod2, 3 _lod3, 4 _hk, 5 _gr) and adds each with out +0x48 / +0x4C as its distance, unsquared, to a LOD table of {model, float} pairs (171E10, table at +0x80); out +0x44 squared (or -1.0 when not above 0.01, 1765A00) goes to the render-object build 16E0B0 (a cull distance, inferred from the square and #view-distance-details' 16EE60). ig_heigen507's small-object .mlb: child 8 [100], child 9 [100, 200]. The draw that picks among the LODs was not read.

Basis: fn.py 145060, 14B5B0, 126BA0, 151240, 171E10; trb_dump.py

Buildings

Buildings switch level of detail with a hard pop, not a crossfade: in a city map with tram tracks, a small st…

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-building-lod-pop

Buildings switch level of detail with a hard pop, not a crossfade: in a city map with tram tracks, a small step forward switched the building across the square (and the facades down the street) from a lower-detail model (flat facade, balconies and bay windows without relief) to the full one in one frame; novae (ajane) finds it jarring in motion. The switch distance, the building's model names and the code that picks the LOD were not read (now read: #edf6-structure-lod-distances, #edf6-building-lod-pick, route #edf6-building-lod-route).

Basis: two screenshots by novae (ajane) before and after the step (2026-11-14; the game taken as EDF6 from the 00v context and the HUD, the map not named)

The LOD distance per part (158D40, loop 158E40..158F04, i = 1, 2): max(def +0x28 / +0x30, part +0x24 / +0x2C)…

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-structure-lod-distances

The LOD distance per part (158D40, loop 158E40..158F04, i = 1, 2): max(def +0x28 / +0x30, part +0x24 / +0x2C), then 151310 multiplies it by [17698D0] for def types 2, 4, 5, 6 (mask 0x74) or by [17698D8] for the others (both 1.0), and 171E10 stores {model, distance} in the build's LOD table (1705A0 makes the 3 slots; slot 0, the full model, gets 0). The values are squared meters: nw_europe01's type-1 building defs (748 placements: eu1_nw_classicbld*, eu1_nw_bd4030_01) hold 10000 and 40000, LOD 1 at 100 m and LOD 2 at 200 m; type-6 props 2025 / 10000 (45 / 100 m) or 2500 / -1; type-5 fences 1600 / 10000; trees (type 2) and far buildings (type 3) -1. Preload_Model (1555A0, .mdx) uses the same helpers, and FixedCrashModel's 13ECE0 the twin 126C70 with the same two constants.

Basis: fn.py; constants read with scratch flt.py; def floats tallied with mapbdefs.py on nw_europe01 only

Addresses (build-specific RVAs unless indicated): 158D40, 158E40, 158F04, 151310, 17698D0, 17698D8, 171E10, 1705A0, 1555A0, 13ECE0, 126C70

Type-1 .mosb building defs across all EDF6 maps (map.mapb +0x28 / +0x30, squared, weighted by placements): most common [22500, -1] (150 m, no LOD 2; 3,901 placements, 17 maps), [40000, 90000] (200 / 300 m; 2,766), [10000, 90000] (100 / 300 m; 2,040), [10000, 62500] (100 / 250 m; 1,876), [22500, 40000] (150 / 200 m; 1,697), [10000, 40000] (100 / 200 m; 1,098); rural maps lower ([6400, 22500], 80 / 150 m, on nw_henden, nw_suiden, ig_mountainvillage), the largest [160000, 250000] (400 / 500 m, nw_dlcmap601 / 602); 356 placements carry no LOD ([-1, -1]). So most city buildings switch at 100 to 150 m.

Basis: one Python pass over every map/*.mac's map.mapb (scratch, KH chat 164)

The per-frame pick, a hard switch: the map render node (MapRenderer::ModelRenderer::RenderObject_Nodes, vtabl…

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-building-lod-pick

The per-frame pick, a hard switch: the map render node (MapRenderer::ModelRenderer::RenderObject_Nodes, vtable 178FCD8; built from the LOD table by 16EE60, which makes one 0x38-byte unit per LOD, vtable 178FCC0, the distance at unit +0x30) gets slot 1 171360 from the Umbra collect: d = the node's distance term +0x24 (byte +0x45 stays 0 for map nodes, so the distance to the object's center) times the camera's zoom ratio (11E3EFA -> 11B28C0, camera.md#camera-projection-fields), squared. 171AD0 skips the node when its cull value (node +0x70) is positive and not above d², else picks the last unit whose distance is below d² (unit 0 always qualifies) into +0x98 (word) and queues only that unit (slot 2 171D20). One LOD is drawn per node per frame, no blend; zooming in brings full detail nearer.

Basis: fn.py 171360, 171AD0, 16EE60, 11B28C0, 11B2400; +0x45 writers grepped in 11DA60..17B023 (only copies and the tree class)

Addresses (build-specific RVAs unless indicated): 178FCD8, 16EE60, 178FCC0, 171360, 11E3EFA, 11B28C0, 171AD0, 171D20

Shaders for a fade: building parts use shader/dx11/snd_map_build_.sgo and their LODs snd_map_lod.sgo (DX11.cp…

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-lod-fade-shaders

Shaders for a fade: building parts use shader/dx11/snd_map_build_*.sgo and their LODs snd_map_lod*.sgo (DX11.cpk), instanced (g_instancing_array, g_instancing_inv_array), with per-material xgl_user_param only (diffuse, specular, roughness, fall-off, dirt): no per-object fade, alpha or dither input, and snd_map_build_basic has no clip. g_xgl_fade_mul / g_xgl_fade_add sit in the per-view xgl_system cbuffer beside the fog terms (+0x238 / +0x23C; read by 84 of 349 shaders embedded in EDF.dll), not per object. Only three wind vertex shaders in EDF.dll (grass, inferred) fade by distance (xgl_user_param g_culling_distance +0x20, g_fadeout_distance +0x24). The tree band value of #edf6-tree-billboard-switch goes to 178010, which scales the number and size of leaf cards drawn (inferred from the arithmetic), not an alpha blend.

Basis: DXBC RDEF chunks parsed (scratch dxbc_rdef.py on EDF.dll, sgo_cb.py on snd_map_build_basic.sgo and snd_map_lod.sgo); fn.py 17A020, 178010

Addresses (build-specific RVAs unless indicated): 178010

Route and open questions

Route for "keep distant trees as full meshes" (00v topic 1): data, set each .trb's rule 0 child 5 near to 0 o…

Evidence: unverified · Build: steam-678ccb46 · Fact ID: edf6-tree-lod-route

Route for "keep distant trees as full meshes" (00v topic 1): data, set each .trb's rule 0 child 5 near to 0 or below (state 0 to the cut-off) and raise child 4 for a longer cut-off (the .trb files sit in each map's MAC); or code, one 5-byte patch at 178D64 F3 0F 11 4B 18 (movss [rbx+0x18], xmm1) -> F3 0F 11 5B 18 (store xmm3, zeroed at 178D3E), which makes near² 0 for every tree; a longer cut-off in code needs a cave at 178D84. Risks: draw cost (thousands of leaf meshes to 1000 m), the env FarClipZ (1000 m, rendering.md#view-distance-passes), TreeBlock culling. Open: the writer of view+0x18 (a zoom factor would move the switch), TreeBlock's own Umbra cull distance, the AnyObject LOD pick, and LODs of placed .mdx / .mosb props (not read). Nothing here was run in game.

Basis: novae (ajane); the route inferred from #edf6-trb-distance-fields and #edf6-tree-billboard-switch

Addresses (build-specific RVAs unless indicated): 178D64, 178D3E, 178D84

Route for buildings' LOD (00v topic 1b): (a) push the switch out, globally with one float, 17698D8 (buildings…

Evidence: unverified · Build: steam-678ccb46 · Fact ID: edf6-building-lod-route

Route for buildings' LOD (00v topic 1b): (a) push the switch out, globally with one float, [17698D8] (buildings and the other def types 0, 1, 3, 7+) or [17698D0] (types 2, 4, 5, 6), both read only by 151310 and 126C70 at load: the distances are squared, so 4.0 doubles the switch distance and 9.0 triples it; or per map in data, each map.mapb def's +0x28 / +0x30 (squared meters); (b) a gradual fade, the middle ground novae (ajane) asked about, needs three parts: in 171AD0 queue both neighboring units inside a band below each switch distance, a per-instance factor in the instance data, and modified snd_map_build_* / snd_map_lod* pixel shaders that discard pixels by a screen-space dither pattern against that factor (the deferred path has no alpha blend, inferred); a time-based fade (both LODs for a few frames after a switch) needs the same shader part. The same pick serves every map node built through 1705A0 (props, .mdx models), so the fade would cover them too; trees have their own path (#edf6-tree-lod-route). Risks: draw cost of the doubled band, shadows (whether the shadow pass picks with the same d, not read). Open: def +0x18 (300 / 400 on buildings), LODModelObject / BuildingObject / LODCaptureCamera and lod_capture (an impostor capture path, not read), and whether view+0x18 in #edf6-tree-billboard-switch is the same zoom ratio (likely). Nothing here was run in game.

Basis: inferred from #edf6-structure-lod-distances, #edf6-building-lod-pick and #edf6-lod-fade-shaders

Addresses (build-specific RVAs unless indicated): 17698D8, 17698D0, 151310, 126C70, 171AD0, 1705A0
