Facts

Havok Walk_Step velocity update each physics tick

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-step-velocity-sum

xgs::havok::CharacterControl_Walk_Step (11B9890) sets the soldier's Havok body velocity every physics step to the sum of four terms: own velocity (Walk+0x30; +0x34 is the vertical part, a jump sets it above 0), move input (Walk+0x20), external slot A (Walk+0x60) and external slot B (Walk+0x1C0); the sum is built at 11B9A92, and Walk+0x60 is cleared at 11B9CB7 at the end of every step. Because the velocity is set, not integrated, Havok friction cannot drag a soldier along with the ground.

Basis: the plugin's header comment and README; opening bytes matched uniquely

Addresses (build-specific RVAs unless indicated): 11B9890, 11B9A92, 11B9CB7

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

Walk+0x60 is the game's own per-step external-velocity slot

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-external-velocity-slot

Walk+0x60 is the game's own per-step external-velocity slot; HumanBase::OnMessage (572810) feeds it too (add-velocity messages). Adding a vector there for one step moves the character without any other state change.

Basis: the plugin writes it every step and reports it works (jumping off keeps speed, riding tanks); the hub did not run it

Addresses (build-specific RVAs unless indicated): 11B9A92, 11B9CB7, 572810

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

Walk_CheckSupport Havok ground query

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-support-info

The ground query runs in Walk_CheckSupport (11AF750, its only caller is Walk_Step at 11B98C8): Havok hknpCharacterRigidBody::checkSupport (vtable slot +0x20 = 11DE1C0) calls getSupportInfo (11DF0A0), which fills an hknpCharacterSurfaceInfo at Walk+0x90: +0x00 u8 isSurfaceDynamic, +0x01 u8 supportedState (0 unsupported, 1 sliding, 2 supported), +0x10 float4 surfaceNormal, +0x20 float4 surfaceVelocity, +0x30 float4 surfaceAngularVelocity (world space). The physics step is read from the instruction at Walk_CheckSupport+0x2C (movss xmm0,[rip+dt]): 1/60 s.

Basis: the plugin's header comment and its patterns (unique); dt read by the plugin at load and logged

Addresses (build-specific RVAs unless indicated): 11AF750, 11B98C8, 11DE1C0, 11DF0A0

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

Observed zero surface velocity on EDF vehicles

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-support-body

Havok's surfaceVelocity came out 0 for EDF vehicles (the author: it is weighted by the contact's +0x2C), so the plugin finds the supporting body itself: the contact array is at hknpCharacterRigidBody+0x78 (stride 0x40, count at list +0x08, indices at [list+0]), each contact holds the body id at +0x20 (& 0xFFFFFF, 0xFFFFFF = none); the world interface is at +0x28 (vtable +0x80 getBody, +0xF8 getMotion); body flags at +0x54 (bit 0 = static), motion id at +0x80; motion orientation quaternion at +0x00, local angular velocity at +0x70. The platform's velocity at the soldier comes from hknpMotion_GetPointVelocity (DF6A50).

Basis: the plugin's offsets table and v1.4 note ("1.3 log/test: vehicles reverted = no carry"); the README (v1.3 text) still describes the earlier method

Addresses (build-specific RVAs unless indicated): 11DF0A0, DF6A50

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

Walk+0x70 is the measured body velocity, written only on airborne steps (by the function at 11AF7E0)

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-measured-velocity

Walk+0x70 is the measured body velocity, written only on airborne steps (by the function at 11AF7E0). HumanBase (the function at 572DF0, instruction 573F7C) seeds its landing slide from it: when supported and the airborne frame count (HumanBase+0x1264) exceeds 16, HumanBase+0x1210 = Walk+0x70 * k. A mod that adds platform velocity to the body would be counted twice on landing unless it subtracts its carry from Walk+0x70 afterwards.

Basis: the plugin's v1.5 note and its fix (landing_relative)

Addresses (build-specific RVAs unless indicated): 11AF7E0, 572DF0, 573F7C

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

HumanBase embedded walk-controller offset

Evidence: static · Build: steam-678ccb46 · Fact ID: humanbase-aim-yaw

HumanBase (soldiers and civilians) embeds the walk controller at +0x680 (HumanBase::SetTransform 574D90, OnMessage 572810) and calls Walk_Step from HumanBase::Update at 575BB7 (virtual call +0x1B8, then lea rcx,[rsi+680h], call Walk_Step; return address 575BCF). Aim angles: a (pitch, yaw, ..) vector at +0x1230 (yaw +0x1234) that look input is added to at 573BB7, and a reference vector at +0x1240 (yaw +0x1244) that recoil moves (SoldierBase::OnUpdate, 59B0AB and 59B0F1). Adding the same yaw delta to both turns the view with a platform while look input keeps working.

Basis: the plugin's offsets table; the call-site pattern is unique and its call operand targets Walk_Step, as the plugin checks

Addresses (build-specific RVAs unless indicated): 575BB7, 573BB7, 59B0AB, 59B0F1

Attribution: FevGrave (MovingPlatformFix 1.6) · 2026-10-21

Walk_Step gravity and sliding state

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-step-states

What Walk_Step 11B9890 does with +0x30 (g = +0x80 / 60): in the air or sliding (state 0 / 1) +0x34 += g and +0x30 is kept, except that one step after standing (state 2) without a launch it gets -6 m/s to hug a slope; standing with +0xD0 == 0 it projects the wanted velocity onto the ground and clears +0x30 (an external velocity is dropped); standing with +0xD0 set it skips that, and when +0x30 points away from the ground normal it adds g and sets the state to 0 (lift-off); it then sends +0x40; a body not in the world or not dynamic clears +0x30; +0xD0 is cleared once +0x34 < 0 (11B9BC3..11B9BC9). Callers: Humanoid slot 5 470D10 (at 472862), MonsterBase slot 5 4BD100 (at 4BD2A7), HumanBase 5750E0 (at 575BCA), Merman, FlyingDyno, SquidSmall, GiantDangoLarge, AlienTrailer, Vehicle501. First bytes 48 8b c4 48 89 58 10 48 89 78 18 4c 89 70 20 55.

Basis: the author's static reading ("H"); the HumanBase call site agrees with #humanbase-aim-yaw (return address 575BCF)

Addresses (build-specific RVAs unless indicated): 11B9890, 11B9BC3, 11B9BC9, 470D10, 472862, 4BD100, 4BD2A7, 5750E0, 575BCA

Launching a walking actor with Walk_Detach

Evidence: static · Build: steam-678ccb46 · Fact ID: walk-launch

The game's way to launch a walking character: write the velocity to walk +0x30, then Walk_Detach 11B9880 (+0x91 = 0, +0xD0 = 1, ret; three instructions). HumanBase's jump writes (0, 10, 0) (5669A8..5669C4); Humanoid slot 65 47A890 detaches and writes +0x30 too. Writers of +0x30: the step, Humanoid slot 65 only (+0xB70), MonsterBase only its constructor, HumanBase a dozen (jump, boarding, the Wing Diver's flight states 583240 / 583820), so a soldier's state code may overwrite an outside push every frame. The AI's +0x20 is added on top every frame. Other functions: 11B8D90(walk, dv) adds to +0x60 for one step; 11B9470(walk, n) removes the part of +0x30 that points into n (stopping at a wall, inferred).

Basis: 11B9880 re-read with fn.py (mov byte [rcx+0x91],0; mov byte [rcx+0xd0],1; ret); the rest the author's reading ("H" for the writers, "L" for how often HumanBase's run)

Addresses (build-specific RVAs unless indicated): 11B9880, 5669A8, 5669C4, 47A890, 583240, 583820, 11B8D90, 11B9470

Cling Launch velocity and landing cooldown

Evidence: static · Build: steam-678ccb46 · Fact ID: cling-launch

Cling Launch 6DAA10(ctrl, const float vel[4], int noLandFrames): +0x70 = 0, +0xB8 = frames, +0x80 = vel (four instructions). It sets a velocity (m/s, w 1), not a force; the update keeps +0x70 at 0 and counts +0xB8 down while it is nonzero (6DB5F6), so without frames the body, still touching the ground, lands again at once. The game passes 2 for a blast knockback (GiantAnt 40ABF1), 0 for a jump (a constant velocity on the ground, 409E28 and others), 4 and 8 for the robots (540997, 35D524). Launch changes no animation state. It has no effect while +0x00 is nonzero (a flying GiantBee, slot 5 420180; the update's cmp [rbx],0; jne at 6DB309); there only the body's velocity (11B18F0([obj+0xE10], v)) moves it, against the bee's own flight code. Related: 6DAE50(ctrl, dv) adds to +0x120 for one step (only when not attached); 6DAB90(ctrl, pos, n) teleports to pos + n x R and sets the attach normal; 6DAE80(ctrl) deactivates (body removed with 11B1710, +0x70 / +0x73 / +0x90 cleared; called on death at 4A8E4D). Reading: grounded = [ctrl+0x70], ballistic velocity ctrl+0x80, true velocity 11B1300([ctrl+0x10]).

Basis: 6DAA10 re-read with fn.py (mov byte [rcx+0x70],0; mov [rcx+0xb8],r8d; movups [rcx+0x80],[rdx]; ret); the rest the author's reading ("H"); All Forces' gravity gun launched ants with it in the author's autopilot run (run 11, 2026-10-20)

Moving ground (00v topic 4, KH chat 166)

Stock walk ignores movement of support bodies

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-moving-ground-stock

The stock walk step ignores the support's motion: Walk_Step (11B9890) reads from the support info only the state (+0x91, 11B98DB) and the ground normal (+0xA0, 11B98CD), never the surface velocity +0xB0 or angular velocity +0xC0 that Walk_CheckSupport (11AF750) has Havok fill (the unsupported path zeroes them, 11AF7AC..11AF7C7); the HumanBase code (560000..5B0000) reads only the state byte, at HumanBase+0x711 (walk +0x680 + +0x91, about 20 sites).

Basis: fn.py reads of 11B9890 and 11AF750; fn.py --grep over 560000..5B0000 for +0x710 / +0x711 / +0x730 / +0x740 found only +0x711 reads (57798F's lea +0x740 and 5708C4's indexed read belong to other structures, inferred)

Addresses (build-specific RVAs unless indicated): 11B9890, 11B98DB, 11B98CD, 11AF750, 11AF7AC, 11AF7C7

Effective walking velocity components

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-moving-ground-effect

What that means in play: the velocity sent is +0x30 + the projected +0x20 + +0x60 + +0x1C0 (11B9A92..11B9B29, stored at +0x40, sent by 11AFA70 at 11B9BB3; agrees with #walk-step-velocity-sum), so a soldier on a moving body keeps its own world velocity: the platform slides away under it, only the solver's contacts push it (a rising floor lifts it, a wall of the platform shoves it), its view never turns with the platform, and a jump off keeps none of the platform's speed.

Ragdoll update and moving part velocities

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-keyframed-ragdoll-drive

How living actors' parts move: ragdoll update 1 (6ED800, corpses.md#ragdoll-updates) walks the records (corpses.md#ragdoll-component-records) under the world lock (DAC5B0 .. DB04B0); for an enabled record (+0xA4) in mode 2 it builds the bone's world matrix and, unless the body's linear and angular velocity are both about 0 and 11BAD40 finds it already at that pose (position and three rotation rows within an epsilon), calls 11B0AB0 (matrix to quaternion 98BDB0, then MoveTo 11B0B20 with dt 1/60 from 179F358), which sets the velocities that reach the pose in one step (havok-runtime.md#body-wrapper-functions). MovingPlatformFix route for mobile supportSource: unverified

Evidence: unverified · Build: steam-678ccb46 · Fact ID: edf6-moving-ground-route

Route for standing on moving objects (00v topic 4): FevGrave's MovingPlatformFix 1.6 does the work (hooks 11DF0A0, 11AF750, 11B9890; #walk-support-body), and its method is the route: after Walk_CheckSupport, when +0x91 == 2, take the support body from the contact list (Havok's own +0xB0 came out 0 for EDF vehicles), add 11B1520's point velocity at the feet to the one-step slot +0x60 (#walk-external-velocity-slot), turn the aim and reference yaw by the support's yaw rate x 1/60 (#humanbase-aim-yaw), keep the carry while airborne and subtract it from +0x70 on landing (#walk-measured-velocity). Soldier move-stick scaling and limitations

Per-soldier movement speed and analog stick magnitude

Static native reads; stock NPC timing cited by the contributor. Soldier slot 4 calls 56D350 at 573B72, which computes desired movement +0x11E0 = input(+0xD50) × speed(+0x11C4) × factor(+0x126C). Then 23F4E0 caps vector length at +0x11C0. Constructor initializes the cap to FLT_MAX, speed to 0.1 m/frame (approximately 6 m/s at 60 FPS) and factor to 1.0; hence this default path adds no lower-speed floor and effectively no finite cap. Fencer heavy-armor code can assign different speed constants 0.12/0.07, but the exact states were not examined. A plugin steering via a half-deflected stick obtains roughly half movement speed. The contributor's separate stock NPC timing of 95 m in 48 s (approximately 2.0 m/s) is not a proof that every NPC always uses the same analog magnitude.

Move-stick-only plugin cannot reproduce stock climb or jump

Static plugin-versus-stock control-path comparison. The source plugin writes only the Soldier move stick, so it does not issue the separate stock climb/jump actions. Stock soldiers use common_elude_*_up climb animations and jump path 58F7E0; merely setting movement direction supplies neither. The author's Wing Diver squad members fly and did not exhibit that same climb obstacle. Source-specific slope sampling/step-height mod settings belong to the separate mod card, not to the stock soldier movement ABI. See native squad navigation/jump for a stock state path that can call 58F7E0.
