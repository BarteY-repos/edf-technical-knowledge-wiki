Facts

EDF6 keeps EDF5's player camera design: CharacterGhostCamera (vtable 1768C10) Update is slot 4 F86A0

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-update-fields

EDF6 keeps EDF5's player camera design: CharacterGhostCamera (vtable 1768C10) Update is slot 4 F86A0. It locks the target weak pointer at camera+0x350 (control block +0x358, raw object +0x360), copies target+0x60..+0x90 to camera+0x370..+0x3A0, and copies the look block from target+0x170 (or target+0x230 when byte target+0x224 != 0) into camera+0x3B0..+0x450.

Basis: novae (ajane)

Addresses (build-specific RVAs unless indicated): 1768C10, F86A0, F8985, F87DD

Attribution: novae (ajane) · 2026-10-24

Follow mode is FAF20 and ride (vehicle) mode is FB9F0

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-follow-ride-modes

Follow mode is FAF20 and ride (vehicle) mode is FB9F0. Follow switches to ride at FB93E-FB97C when the target's ride control block [target+0x1550] has users; ride switches back at FBBF3-FBC33. The mode state slot is camera+0xBF0, set by FADF0. The riding predicate F7210(camera) -> bool (camera+0x358 users, +0x360 non-null, [[+0x360]+0x1550] users) has no direct callers; the same test is inside vtable slot 9 F7500.

Basis: found by searching for EDF5's follow-mode ride test pattern (mov reg,[camera+raw target]; mov reg,[target+X]; cmp dword [reg+8],0), confirmed by the lea of each mode inside the other. EDF5: follow 9F590, ride A0130, state camera+0xAE8 (edf5/camera.md#camera-mode-state-machine)

Addresses (build-specific RVAs unless indicated): FAF20, FB9F0, FB93E, FBBF3, FADF0, F7210, F7500

Attribution: novae (ajane) · 2026-10-24

The final camera matrix is camera+0x220 / +0x230 / +0x240 (rotation rows) and +0x250 (eye)

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-final-matrix

The final camera matrix is camera+0x220 / +0x230 / +0x240 (rotation rows) and +0x250 (eye). The ride mode writes it at FC0DB-FC106 and the follow mode writes the rows at FB907-FB919. After the mode call, Update multiplies the rows by the shake matrix +0x280..+0x2A8 when shake is on.

Basis: disassembly; the offsets are EDF5's +0x1A0..+0x1D0 plus 0x80. EDF5 ride-mode writes: A077D-A07A8 (edf5/camera.md#camera-final-matrix)

Addresses (build-specific RVAs unless indicated): FC0DB, FC106, FB907, FB919

Attribution: novae (ajane) · 2026-10-24

Vehicle ride-camera seat-based configuration

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-ride-seat-camera

The ride mode builds the vehicle camera from the seat record, not from the look block: [seat+0x200] == 1 -> bone matrices at seat+0x208 / +0x218 (FBA3A), plus two values from the SGO data node at seat+0x228 -> camera+0x650 / +0x654 and seat+0x230 -> camera+0x658; it never reads camera+0x3B0..+0x450. A camera-distance hook in Update's look-block copy therefore cannot reach vehicles; candidates are scaling the eye at the ride-mode writes FC0DB-FC106, or the seat parameters copied at FBA7A-FBAAB. The meaning of seat+0x228 / +0x230 (likely per-vehicle camera distance or offset parameters) is unverified, as is the guess that RideInfo@VehicleBase (vtable 17D9868) is the seat record type.

Basis: disassembly of FB9F0-FC200 with a register-offset scan

Addresses (build-specific RVAs unless indicated): FB9F0, FBA3A, FBA7A, FBAAB, FC0DB, 17D9868

Attribution: novae (ajane) · 2026-10-24

Soldier ride seat and vehicle object fields

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-ride-link

An EDF6 soldier keeps the vehicle it rides at +0x1540 (seat record), +0x1548 (vehicle object) and +0x1550 (weak-pointer control block; riding while [ctrl+8] != 0); the three are cleared together at 57C2D6-57C300. EDF6 soldier offsets are EDF5's + 0x3E0 here, but the class layout grew (secondary NetworkObject vtable at +0x120 instead of +0xC0; soldier third base at +0x1940 instead of +0x1580). Reverse-engineering notes on the damage-number HUD read the same three fields (+0x1548 vehicle, a SceneObject at offset 0; +0x1540 seat; count block +0x1550, [+8] != 0 while riding) and name the get-off code at 56FF1A as the place that clears them, after it calls the vehicle's 62E1A0(vehicle, seat); whether that is a second clearing site besides 57C2D6 was not compared. The damage-number HUD's in-vehicle flag comes from +0x1550 (damage-numbers.md#damage-layout-styles).

Basis: disassembly; the clear sequence matches EDF5 2EFCEA (+0x1160 / +0x1168 / +0x1170); the camera tests +0x1550 (ghost-camera-follow-ride-modes)

Addresses (build-specific RVAs unless indicated): 57C2D6, 57C300, 56FF1A, 62E1A0

CharacterGhostCamera constructor and vtables

Camera mode field and setter values

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-mode-values

[camera+0xC08] holds only two values in this build: the mode setter FADF0(state = camera+0xBF0, &mode, arg) (calls the old mode with edx = 2, stores the 16-byte member-function pointer at state +0x18, calls the new one with edx = 0) is called only at FB97C (follow -> ride, lea FB9F0 at FB950) and FBC33 (ride -> follow, lea FAF20 at FBC05), and the constructor installs follow at F5091. SpectateCam's names fit after a shift: FAC90 "normal" and FB760 "vehicle" are each exactly 0x290 below FAF20 (follow) and FB9F0 (ride), so the plugin's StateName table was written for another EDF.dll build (its hooks find their sites by signature, so only this label table is build-bound; inferred).

Basis: FADF0 read with fn.py; its callers and every lea of a mode address found by a scan of F4000..106000; settles the conflict of #ghost-camera-mode-names-spectatecam

Addresses (build-specific RVAs unless indicated): FADF0, FB97C, FB950, FBC33, FBC05, F5091, FAF20, FB9F0, FAC90, FB760

Camera retarget to a different character

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-retarget

Pointing the camera at another character: store {character, its control block [character+0x30]} into the target weak pointer camera +0x350 / +0x358 (MSVC control block: users +8, weak count +0xC, raised for the new block; the old block's weak count dropped and the block freed through its vtable slot 1 at zero). SpectateCam does this from its hook on Update F86A0, before calling the original. While it spectates it also puts the target into the raw-object slot +0x360 for the duration of the original Update when that slot still holds the camera's own character, and restores it afterwards. When the game itself changes +0x350 meanwhile (respawn, vehicle), the plugin keeps the game's pair and re-applies its own target; going back, it restores the game's pair if its users count [ctrl+8] is still above 0. Its check log compares camera +0x3A0..+0x3A8 with the target's position +0x90..+0x98 (the copy of ghost-camera-update-fields).

Basis: the plugin's Spectate and Update hook disassembled (it keeps its symbols); not run by us

Addresses (build-specific RVAs unless indicated): F86A0

Attribution: SpectateCam 0.4 (DonPardon42) · 2026-10-28

Free-camera control while spectating

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-borrow-controls

Free camera around another character (SpectateCam's FreeCamera=1, "borrows your controller during the camera update"): for the length of the original Update F86A0 the plugin copies the local soldier's controls pointer +0x340, pad index +0x338, byte +0x354 and floats +0x320 and +0x32C into the spectated soldier, adds ExtraHeight to its +0x174 and +0x184 (the Y of the camera facing +0x170 and position +0x180 vectors, objects.md#gameobjectbase-layout), then restores all seven. So the camera's mouse look reads +0x340's input and the target's +0x320 / +0x32C (likely the aim angles) and +0x354; their meanings are unverified.

Basis: the plugin's Update hook disassembled; the ini comment; not run by us

Addresses (build-specific RVAs unless indicated): F86A0

Projection, draw distance and sight slots (round 23, EDF6VR source)

Stored vertical FOV and projection fields

Evidence: static · Build: steam-678ccb46 · Fact ID: camera-projection-fields

The camera keeps its projection together: +0x20 the reference vertical field of view, +0x24 the live one (radians; rebuilt every update as [1765A20] / [camera+0x410], F8906..F8916, rendering.md#vertical-fov), +0x28 the near and +0x2C the far clip plane; the projection builder 4DD70 turns +0x24 into cot(fov/2). Draw distance follows the zoom: 118DCD0 returns tan(+0x24 / 2) / tan(+0x20 / 2), or [1C36994] when byte +0x39 is 0; 1197F31 (far view) and 1197FBD (main view) store it at +0x18 of the view's submission, and 11E3EFA -> 11B28C0 scales distances with it before the squared-distance cutoff at model +0x60. The camera's depth buffer is ordinary normalized depth (near 0, far 1).

Basis: 118DCD0 decoded with fn.py (2026-11-07; tanf 12DA8C4 of each angle times [1C36990]); the rest from the EDF6VR source's comments

Addresses (build-specific RVAs unless indicated): F8906, F8916, 4DD70, 118DCD0, 1C36994, 1197F31, 1197FBD, 11E3EFA, 11B28C0

Attribution: EDF6VR source (momotori01, Unlicense; round 23), novae (ajane) · 2026-11-07

Where the zoom in [camera+0x410] comes from: the weapon loader 68A920 reads SecondaryFire_Type (string 17E2B88, 68D068) into weapon +0x690 (68D0A4) and SecondaryFire_Parameter (17E2BB0, 68D0B7) as a 16-byte variant into +0x698; initially +0x780 (scoped, byte) = 0 and +0x784 (zoom) = 1.0 (68EBB9 / 68EBBF; 690060 resets the same). The weapon tick 6934F0 calls the secondary-fire dispatch 698570 (jump table on +0x690, 0..6) when +0x13B (the secondary key's edge, written only by soldier code: 59AEF1 in 59ABB0, 5A2094 in 5A1D70) is 1 (693939); type 1 goes to the scope toggle 696310 (6985C7), which flips +0x780 and sets +0x784 = the parameter (69636B) or 1.0 (696385) with a sound each way (7B2A80); 695F10 closes an open scope (called by soldiers, 59AECA, 5A1733; SoldierBase slots 73 / 79). The SoldierBase update 59ABB0 writes the maximum +0x784 over its WeaponSet +0x1970 (stride 0x150, weapon at +0x40 through two pointers; 59AD30) to human+0x1D0 unconditionally (59B209); the camera update F86A0 copies the target's +0x170..+0x21F to camera+0x3B0 (or +0x230.. when target +0x224 != 0, zoom then at +0x290; set by class slot 5s and 5790E9 / 579776 for class gadget views), so camera+0x410 = human+0x1D0; without a target the FOV write is skipped (F870F -> F891D). The state function runs after the FOV write (F8985); the ride state does not write +0x24; a state-1 sub-mode eases +0x24 toward +0x560 by +0x540 (FB4C8, target from atan at FB3A3). Infantry aim input is divided by human+0x1D0 (570780, over +0xD60..); the ride input 572DF0 (writing seat+0x2D0) is not. Vehicles have no zoom: only four vehicle weapon SGOs have type 1 (zoom 4.0: V_504BEGARUTA_DLC_LONGCANNON015_L/_R, V_504BEGARUTA_DLC2_LONGCANNON015_L, V_612_LASER_CANNON01_R), and no vehicle or seat code writes +0x13B. Constructor chain F4860 -> 103740 (writes +0x24 = π/4 at 103898) -> 118AFC0 (xgs::game::SceneCamera, vtable 1AE1F68; +0x20 = +0x24 = π/4 at 118B0A7 / 118B0AF); the Umbra frustum builder (vtable +0x50 = 118DD30) reads +0x24 too (118DD3F); other +0x24 writers are the debug FreeViewCamera (101BA0, clamped by 101E90), FE210, FEF54.

Basis: F8906..F891B re-read with fn.py; the rest the author's reading ("H"; that vehicles never zoom "M", from a full scan)

Complete original research record — expand (1,290 characters)

game_object_camera_setting = [vector 0, vector 1, (not read), factor]: vector 0 is the look point and vector 1 the eye, both points in the object's own frame (x right, y up, z forward; vector 1 is not an offset from vector 0), the fourth item the eye's easing factor; it acts only while the camera's target is the object itself (state 1). Its only reader is 54DDF0 (GameObject common; string 17CDBB8): +0x170 item 0 (xyzw, default (0,0,0,1) from 1765B30), +0x180 item 1, +0x190 1.0 or item 3 when the list has more than 3 items (54E227..54E2A1), +0x194 / +0x1B0 / +0x224 cleared, +0x1A0 / +0x1C0 (0,0,0,1), +0x1D0 = 1.0, +0x1D4 = 0, +0x1E0..+0x21F identity; when item 0 is itself a list (type 3), the set is picked by +0x220 (the player's camera-distance option index; soldiers use this). Called by the GameObject constructor 545670 (every object, once) and by the soldier classes; no vehicle class writes +0x170 / +0x180 again. A vehicle's setting is therefore never used while someone rides it (the camera's target stays the soldier, #ghost-camera-target-fixed); vanilla values as the author sums them up (two numbers each, the frame's size; their exact meaning not stated): Blacker 4 / 15.5, Titan 8 / 25.5; the Grape's (VEHICLE401_STRIKER) eye is 4 m above and 10.5 m behind the origin.

Basis: the author's static reading ("H") and its read of the SGOs

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Initial target weak reference
  2. Follow-camera update

Complete original research record — expand (1,452 characters)

The player camera's target is set only at construction: F4860 stores the weak target at +0x350 / +0x358 and +0x360 = dynamic_cast<SoldierBase*>(target), and no other code writes those three fields except the constructors of two other camera classes (FE210, 1051F0); so boarding never retargets the camera to the vehicle. The update F86A0 (referenced only by CharacterGhostCamera's vtable) copies the target's world matrix +0x60..+0x9F to cam+0x370 and the look block (#ghost-camera-update-fields); with target +0x1D4 > 0 it blends the frame toward the matrix at +0x1E0 by that share (F87EB..F888F, a quaternion slerp); then calls the state (cam+0xB58). State 1 FAF20 (third person, the target's +0x170 / +0x180) uses the target's world matrix as the frame (511C0 only orthonormalizes), or, with cam+0x3F0 = 1, a rotation from the two angles cam+0x400 / +0x404 (4CD10); it eases the eye from last frame's +0x250 (FB03E..FB101), so anything written there becomes the next frame's start. Slot 9 (1768C58) -> F7500 is the HUD-visible test: !cam+0x3F0 && (!cam+0x301 || target +0x1550 live) (#hud-gate). The ride camera (state 2 FB9F0) places itself by the seat's MAB locators: the seat constructor 62B430 fills the seat's camera fields from vehicle_riding_position item 3 (a MAB locator name such as カメラ１; 6BADD0 finds the locator and its parent bone; the locator record's +0x1C is its own small SGO): seat +0x200 Type (0 when missing), +0x208 / +0x210 the eye locator record / parent bone, +0x218 / +0x220 the LookTarget locator / parent bone, +0x228 the Param node [eye easing, look easing] (copied to cam+0x650 / +0x654 on entering state 2), +0x230 XAngleAdjust (default 1.0; below 1 the eye is recomputed with that share of the parent bone's pitch, FBCB1..FC00F): this names the fields #ghost-camera-ride-seat-camera left open. 6BB5A0 (locator to matrix): the locator record's +8 type sets the local matrix (0 / 1 translation only, 2 adds three angles at +0x14), times the parent bone's world matrix (bone record +0xB0..+0xEF, translation +0xE0); the result's fourth row is the point. Each frame by Type: 1: eye target 6BB5A0(seat+0x208) (at rbp+0x30), look target 6BB5A0(seat+0x218) (call FC01B: lea rcx,[rbx+0x18]; lea rdx,[rbp-0x40], result at rbp-0x10, camera in rsi; the 39 bytes from FC013 also hold the cam+0x630 / +0x650 / +0x640 offsets), then cam+0x630 (eye) and cam+0x640 (look) ease toward them by +0x650 / +0x654, F6760 does the map collision and the matrix looks from the eye to the look point; 0: the soldier's own view angles (human+0x1240) times the eye locator's matrix (the Balam's seat has no Type); other values write no camera. Uneven offline mouse look with even frames

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-mouse-look-uneven

Offline, mouse look turns the camera unevenly from step to step while the frames are even: in a steady hand turn about every 11th step (about 5.5 a second) turns 1.3-1.6x as far as its neighbors, and the turn per step comes in whole cursor pixels (about 0.06 deg each at novae (ajane)'s setting); the right stick turns exactly the same angle every step (0.4578 deg at half deflection, 27.5 deg/s). Yaw read as atan2(z, x) of the final matrix's row +0x220 (#ghost-camera-final-matrix); the soldier's +0x320 / +0x32C stayed 0.0 while turning, so they are not the yaw (#ghost-camera-borrow-controls).

Basis: novae (ajane); mouse 1797 steps, 142 of 1407 turning steps above 1.3x their 9-step median, spacing median 11; loop interval at the spikes the same as elsewhere; novae (ajane): "as choppy as typical"

Addresses (build-specific RVAs unless indicated): 20B2958

Mouse report aliasing at 60 Hz input sampling

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-mouse-125hz-aliasing

The cause is report aliasing: the summed cursor offset is taken once per 60 Hz step (system.md#edf6-mouse-total-take), so a 125 Hz mouse gives 2 reports on most steps and 3 on about every 12th (125 / 60 = 2.083). Replacing the take with Raw Input counts spread over time and sampled at the step clock (the limiter base [2139D18], 10 ms behind) halves the unevenness.

Basis: one user run in M002 (125 Hz mouse): step / mean of its 8 neighbors, game's mouse median 0.960 (= 2 / 2.083), p95 1.51-1.58, 11-14 % of steps above 1.25x; the Raw Input test plugin's mode 3 median 1.003, p95 1.21-1.24, 4-5 %, sd 0.21 -> 0.12; novae (ajane): "somehow felt nicer", far scenery still jumps

Addresses (build-specific RVAs unless indicated): 1188479, 11831F0, 2139D18

Attribution: novae (ajane) · 2026-11-14

Uniform cursor input yields uniform camera turn

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-mouse-choppiness-input-side

Nothing after the take adds unevenness: handing exactly 10 cursor px to every take turns the camera exactly 10 px every step and looks "as good as can be expected at 60Hz" (novae (ajane)); so the choppiness is input-side. Spread of the step ratio (sd; share above 1.25x): even input 0.000, 0 %; smoothed by real time with a delay 0.043, 0 %; smoothed by the sim clock 0.045, 0 %; the game's own path with 125 Hz moves 0.175, 8.1 %; raw counts summed per take 0.161, 9.0 %; the game's path fed at 1000 Hz still 0.152, 2.9 % (one run).

Basis: novae (ajane); re-scored after a first scoring used mislabeled recordings; faster turns not tested
