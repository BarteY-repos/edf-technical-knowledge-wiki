Facts

EDF6 keeps EDF5's player camera design: CharacterGhostCamera (vtable 1768C10) Update is slot 4 F86A0

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-update-fields

EDF6 keeps EDF5's player camera design: CharacterGhostCamera (vtable 1768C10) Update is slot 4 F86A0. It locks the target weak pointer at camera+0x350 (control block +0x358, raw object +0x360), copies target+0x60..+0x90 to camera+0x370..+0x3A0, and copies the look block from target+0x170 (or target+0x230 when byte target+0x224 != 0) into camera+0x3B0..+0x450.

Basis: novae (ajane)

Addresses (build-specific RVAs unless indicated): 1768C10, F86A0, F8985, F87DD

Attribution: novae (ajane) · 2026-10-24

Follow mode is FAF20 and ride (vehicle) mode is FB9F0

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-follow-ride-modes

Follow mode is FAF20 and ride (vehicle) mode is FB9F0. Follow switches to ride at FB93E-FB97C when the target's ride control block [target+0x1550] has users; ride switches back at FBBF3-FBC33. The mode state slot is camera+0xBF0, set by FADF0. The riding predicate F7210(camera) -> bool (camera+0x358 users, +0x360 non-null, [[+0x360]+0x1550] users) has no direct callers; the same test is inside vtable slot 9 F7500.

Basis: found by searching for EDF5's follow-mode ride test pattern (mov reg,[camera+raw target]; mov reg,[target+X]; cmp dword [reg+8],0), confirmed by the lea of each mode inside the other. EDF5: follow 9F590, ride A0130, state camera+0xAE8 (edf5/camera.md#camera-mode-state-machine)

Addresses (build-specific RVAs unless indicated): FAF20, FB9F0, FB93E, FBBF3, FADF0, F7210, F7500

Attribution: novae (ajane) · 2026-10-24

The final camera matrix is camera+0x220 / +0x230 / +0x240 (rotation rows) and +0x250 (eye)

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-final-matrix

The final camera matrix is camera+0x220 / +0x230 / +0x240 (rotation rows) and +0x250 (eye). The ride mode writes it at FC0DB-FC106 and the follow mode writes the rows at FB907-FB919. After the mode call, Update multiplies the rows by the shake matrix +0x280..+0x2A8 when shake is on.

Basis: disassembly; the offsets are EDF5's +0x1A0..+0x1D0 plus 0x80. EDF5 ride-mode writes: A077D-A07A8 (edf5/camera.md#camera-final-matrix)

Addresses (build-specific RVAs unless indicated): FC0DB, FC106, FB907, FB919

Attribution: novae (ajane) · 2026-10-24

Vehicle ride-camera seat-based configuration

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-ride-seat-camera

The ride mode builds the vehicle camera from the seat record, not from the look block: [seat+0x200] == 1 -> bone matrices at seat+0x208 / +0x218 (FBA3A), plus two values from the SGO data node at seat+0x228 -> camera+0x650 / +0x654 and seat+0x230 -> camera+0x658; it never reads camera+0x3B0..+0x450. A camera-distance hook in Update's look-block copy therefore cannot reach vehicles; candidates are scaling the eye at the ride-mode writes FC0DB-FC106, or the seat parameters copied at FBA7A-FBAAB. The meaning of seat+0x228 / +0x230 (likely per-vehicle camera distance or offset parameters) is unverified, as is the guess that RideInfo@VehicleBase (vtable 17D9868) is the seat record type.

Basis: disassembly of FB9F0-FC200 with a register-offset scan

Addresses (build-specific RVAs unless indicated): FB9F0, FBA3A, FBA7A, FBAAB, FC0DB, 17D9868

Attribution: novae (ajane) · 2026-10-24

Soldier ride seat and vehicle object fields

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-ride-link

An EDF6 soldier keeps the vehicle it rides at +0x1540 (seat record), +0x1548 (vehicle object) and +0x1550 (weak-pointer control block; riding while [ctrl+8] != 0); the three are cleared together at 57C2D6-57C300. EDF6 soldier offsets are EDF5's + 0x3E0 here, but the class layout grew (secondary NetworkObject vtable at +0x120 instead of +0xC0; soldier third base at +0x1940 instead of +0x1580). Reverse-engineering notes on the damage-number HUD read the same three fields (+0x1548 vehicle, a SceneObject at offset 0; +0x1540 seat; count block +0x1550, [+8] != 0 while riding) and name the get-off code at 56FF1A as the place that clears them, after it calls the vehicle's 62E1A0(vehicle, seat); whether that is a second clearing site besides 57C2D6 was not compared. The damage-number HUD's in-vehicle flag comes from +0x1550 (damage-numbers.md#damage-layout-styles).

Basis: disassembly; the clear sequence matches EDF5 2EFCEA (+0x1160 / +0x1168 / +0x1170); the camera tests +0x1550 (ghost-camera-follow-ride-modes)

Addresses (build-specific RVAs unless indicated): 57C2D6, 57C300, 56FF1A, 62E1A0

CharacterGhostCamera constructor and vtables

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-ctor-dtor

CharacterGhostCamera constructor F4860 (calls 103740 first, then writes vtable 1768C10 at +0, 1768C78 at +8, and clears the target pair +0x350 / +0x358) and deleting destructor F6030(camera, flags) (writes the same two vtables and 1768BB0 at +0xBF0, the embedded mode-state object of ghost-camera-follow-ride-modes). Camera mode field and setter values

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-mode-values

[camera+0xC08] holds only two values in this build: the mode setter FADF0(state = camera+0xBF0, &mode, arg) (calls the old mode with edx = 2, stores the 16-byte member-function pointer at state +0x18, calls the new one with edx = 0) is called only at FB97C (follow -> ride, lea FB9F0 at FB950) and FBC33 (ride -> follow, lea FAF20 at FBC05), and the constructor installs follow at F5091. SpectateCam's names fit after a shift: FAC90 "normal" and FB760 "vehicle" are each exactly 0x290 below FAF20 (follow) and FB9F0 (ride), so the plugin's StateName table was written for another EDF.dll build (its hooks find their sites by signature, so only this label table is build-bound; inferred).

Basis: FADF0 read with fn.py; its callers and every lea of a mode address found by a scan of F4000..106000; settles the conflict of #ghost-camera-mode-names-spectatecam

Addresses (build-specific RVAs unless indicated): FADF0, FB97C, FB950, FBC33, FBC05, F5091, FAF20, FB9F0, FAC90, FB760

Camera retarget to a different character

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-retarget

Pointing the camera at another character: store {character, its control block [character+0x30]} into the target weak pointer camera +0x350 / +0x358 (MSVC control block: users +8, weak count +0xC, raised for the new block; the old block's weak count dropped and the block freed through its vtable slot 1 at zero). SpectateCam does this from its hook on Update F86A0, before calling the original. While it spectates it also puts the target into the raw-object slot +0x360 for the duration of the original Update when that slot still holds the camera's own character, and restores it afterwards. When the game itself changes +0x350 meanwhile (respawn, vehicle), the plugin keeps the game's pair and re-applies its own target; going back, it restores the game's pair if its users count [ctrl+8] is still above 0. Its check log compares camera +0x3A0..+0x3A8 with the target's position +0x90..+0x98 (the copy of ghost-camera-update-fields).

Basis: the plugin's Spectate and Update hook disassembled (it keeps its symbols); not run by us

Addresses (build-specific RVAs unless indicated): F86A0

Attribution: SpectateCam 0.4 (DonPardon42) · 2026-10-28

Free-camera control while spectating

Evidence: static · Build: steam-678ccb46 · Fact ID: ghost-camera-borrow-controls

Free camera around another character (SpectateCam's FreeCamera=1, "borrows your controller during the camera update"): for the length of the original Update F86A0 the plugin copies the local soldier's controls pointer +0x340, pad index +0x338, byte +0x354 and floats +0x320 and +0x32C into the spectated soldier, adds ExtraHeight to its +0x174 and +0x184 (the Y of the camera facing +0x170 and position +0x180 vectors, objects.md#gameobjectbase-layout), then restores all seven. So the camera's mouse look reads +0x340's input and the target's +0x320 / +0x32C (likely the aim angles) and +0x354; their meanings are unverified.

Basis: the plugin's Update hook disassembled; the ini comment; not run by us

Addresses (build-specific RVAs unless indicated): F86A0

Projection, draw distance and sight slots (round 23, EDF6VR source)

Stored vertical FOV and projection fields

Evidence: static · Build: steam-678ccb46 · Fact ID: camera-projection-fields

The camera keeps its projection together: +0x20 the reference vertical field of view, +0x24 the live one (radians; rebuilt every update as [1765A20] / [camera+0x410], F8906..F8916, rendering.md#vertical-fov), +0x28 the near and +0x2C the far clip plane; the projection builder 4DD70 turns +0x24 into cot(fov/2). Draw distance follows the zoom: 118DCD0 returns tan(+0x24 / 2) / tan(+0x20 / 2), or [1C36994] when byte +0x39 is 0; 1197F31 (far view) and 1197FBD (main view) store it at +0x18 of the view's submission, and 11E3EFA -> 11B28C0 scales distances with it before the squared-distance cutoff at model +0x60. The camera's depth buffer is ordinary normalized depth (near 0, far 1).

Basis: 118DCD0 decoded with fn.py (2026-11-07; tanf 12DA8C4 of each angle times [1C36990]); the rest from the EDF6VR source's comments

Addresses (build-specific RVAs unless indicated): F8906, F8916, 4DD70, 118DCD0, 1C36994, 1197F31, 1197FBD, 11E3EFA, 11B28C0

Attribution: EDF6VR source (momotori01, Unlicense; round 23), novae (ajane) · 2026-11-07

Where the zoom in [camera+0x410] comes from: the weapon loader 68A920 reads SecondaryFire_Type (string 17E2B88, 68D068) into weapon +0x690 (68D0A4) and SecondaryFire_Parameter (17E2BB0, 68D0B7) as a 16-byte variant into +0x698; initially +0x780 (scoped, byte) = 0 and +0x784 (zoom) = 1.0 (68EBB9 / 68EBBF; 690060 resets the same). The weapon tick 6934F0 calls the secondary-fire dispatch 698570 (jump table on +0x690, 0..6) when +0x13B (the secondary key's edge, written only by soldier code: 59AEF1 in 59ABB0, 5A2094 in 5A1D70) is 1 (693939); type 1 goes to the scope toggle 696310 (6985C7), which flips +0x780 and sets +0x784 = the parameter (69636B) or 1.0 (696385) with a sound each way (7B2A80); 695F10 closes an open scope (called by soldiers, 59AECA, 5A1733; SoldierBase slots 73 / 79). The SoldierBase update 59ABB0 writes the maximum +0x784 over its WeaponSet +0x1970 (stride 0x150, weapon at +0x40 through two pointers; 59AD30) to human+0x1D0 unconditionally (59B209); the camera update F86A0 copies the target's +0x170..+0x21F to camera+0x3B0 (or +0x230.. when target +0x224 != 0, zoom then at +0x290; set by class slot 5s and 5790E9 / 579776 for class gadget views), so camera+0x410 = human+0x1D0; without a target the FOV write is skipped (F870F -> F891D). The state function runs after the FOV write (F8985); the ride state does not write +0x24; a state-1 sub-mode eases +0x24 toward +0x560 by +0x540 (FB4C8, target from atan at FB3A3). Infantry aim input is divided by human+0x1D0 (570780, over +0xD60..); the ride input 572DF0 (writing seat+0x2D0) is not. Vehicles have no zoom: only four vehicle weapon SGOs have type 1 (zoom 4.0: V_504BEGARUTA_DLC_LONGCANNON015_L/_R, V_504BEGARUTA_DLC2_LONGCANNON015_L, V_612_LASER_CANNON01_R), and no vehicle or seat code writes +0x13B. Constructor chain F4860 -> 103740 (writes +0x24 = π/4 at 103898) -> 118AFC0 (xgs::game::SceneCamera, vtable 1AE1F68; +0x20 = +0x24 = π/4 at 118B0A7 / 118B0AF); the Umbra frustum builder (vtable +0x50 = 118DD30) reads +0x24 too (118DD3F); other +0x24 writers are the debug FreeViewCamera (101BA0, clamped by 101E90), FE210, FEF54.

Basis: F8906..F891B re-read with fn.py; the rest the author's reading ("H"; that vehicles never zoom "M", from a full scan)

EDF Knowledge Hub record — original wording — expand (1,290 characters)

game_object_camera_setting = [vector 0, vector 1, (not read), factor]: vector 0 is the look point and vector 1 the eye, both points in the object's own frame (x right, y up, z forward; vector 1 is not an offset from vector 0), the fourth item the eye's easing factor; it acts only while the camera's target is the object itself (state 1). Its only reader is 54DDF0 (GameObject common; string 17CDBB8): +0x170 item 0 (xyzw, default (0,0,0,1) from 1765B30), +0x180 item 1, +0x190 1.0 or item 3 when the list has more than 3 items (54E227..54E2A1), +0x194 / +0x1B0 / +0x224 cleared, +0x1A0 / +0x1C0 (0,0,0,1), +0x1D0 = 1.0, +0x1D4 = 0, +0x1E0..+0x21F identity; when item 0 is itself a list (type 3), the set is picked by +0x220 (the player's camera-distance option index; soldiers use this). Called by the GameObject constructor 545670 (every object, once) and by the soldier classes; no vehicle class writes +0x170 / +0x180 again. A vehicle's setting is therefore never used while someone rides it (the camera's target stays the soldier, #ghost-camera-target-fixed); vanilla values as the author sums them up (two numbers each, the frame's size; their exact meaning not stated): Blacker 4 / 15.5, Titan 8 / 25.5; the Grape's (VEHICLE401_STRIKER) eye is 4 m above and 10.5 m behind the origin.

Basis: the author's static reading ("H") and its read of the SGOs

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Initial target weak reference
  2. Follow-camera update
  3. Why the target does not change afterward
EDF Knowledge Hub record — original wording — expand (1,452 characters)

The player camera's target is set only at construction: F4860 stores the weak target at +0x350 / +0x358 and +0x360 = dynamic_cast<SoldierBase*>(target), and no other code writes those three fields except the constructors of two other camera classes (FE210, 1051F0); so boarding never retargets the camera to the vehicle. The update F86A0 (referenced only by CharacterGhostCamera's vtable) copies the target's world matrix +0x60..+0x9F to cam+0x370 and the look block (#ghost-camera-update-fields); with target +0x1D4 > 0 it blends the frame toward the matrix at +0x1E0 by that share (F87EB..F888F, a quaternion slerp); then calls the state (cam+0xB58). State 1 FAF20 (third person, the target's +0x170 / +0x180) uses the target's world matrix as the frame (511C0 only orthonormalizes), or, with cam+0x3F0 = 1, a rotation from the two angles cam+0x400 / +0x404 (4CD10); it eases the eye from last frame's +0x250 (FB03E..FB101), so anything written there becomes the next frame's start. Slot 9 (1768C58) -> F7500 is the HUD-visible test: !cam+0x3F0 && (!cam+0x301 || target +0x1550 live) (#hud-gate). Mouse report aliasing at 60 Hz input sampling

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-mouse-125hz-aliasing

The cause is report aliasing: the summed cursor offset is taken once per 60 Hz step (system.md#edf6-mouse-total-take), so a 125 Hz mouse gives 2 reports on most steps and 3 on about every 12th (125 / 60 = 2.083). November 2026: extra world view, scene cameras and render-slot contracts

These are source-attributed records from hajisensai's view-slots-and-extra-camera-view.md, reconciling the camera-owner and renderer paths of EDF6. The underlying static EDF.dll reading is distinguished from the contributor's offline checks, in-game failure report and still-unverified display behavior. Relative addresses apply to the source author's build and should not be transplanted unchanged to another edition.

Four view slots, camera ownership and target construction

0x188-byte view slot and per-slot render resources

Static. xgs::game::System is [EDF+20B2958]; its four 0x188-byte view slots begin at system+0x4D0, slot i at +0x4D0+i×0x188. 1195BE0(system,i) returns the slot's current-camera field at system+0x4D8+i×0x188. Relative fields: +0 view mode (0–3 observed, no writer proven); +8/+0x10 current-camera weak pointer; +0x18/+0x20 owned-camera list and count; +0x34…+0x40 integer rectangle x/y/w/h; +0x44/+0x48 target dimensions; +0x68/+0x88/+0xA8 G-buffer targets; +0xD0/+0xF0 color targets (first conditional on byte +0xC8); +0x110/+0x130 depth with formats 0x27/0x28/0x29 for R32_TYPELESS/D32/R32_FLOAT; +0x178/+0x180 a slot-owned 0x128-byte object with eight subitems including shadow/render parameters, sized by 11295E0.

Per-rectangle targets and paused redraw requests

Static with multiplayer scope open. Split-screen local players render into separate slot-sized off-screen targets and are composited afterward. This supports the "four local render views" interpretation over a universal online-player ownership scheme; the online case was not established. 1198C40(system,i,rect[4]) writes slot rectangle and size then calls 11997A0: with camera count zero it creates nothing, while a changed rectangle/size with a camera rebuilds targets through the game-thread texture-creation record (five matching textures from 1121F70). Rebuild sets system+0xAF0, forcing a draw even in pause.

Camera queue to owned list and current-camera attachment

Static. 1195990(system,const shared_ptr&) locks critical section system+0x308 (via reentrant EnterCriticalSection 50BC0) and queues a strongly held camera at system+0x4C0. Before drawing, System::update 1198DA0 drains it (1198F61→1195A80), inserts each camera into the list of slot camera+0x60 through 119B410, calls 1193FA0 to make it current and builds targets with 11997A0. 1193FA0(slot,weak_ptr) detaches previous camera (vtable slot7) and attaches new camera (slot6), then destroys its by-value weak pointer. Queue insertion alone does not make the camera current until the next system update.

Mission-end cleanup frees views before Umbra world

Static. Scene cleanup 11956C0 empties the pending add-camera queue, then for each of four slots clears the current weak camera, releases the owned list's shared pointers, zeros its count and destroys render targets via 11974C0. It does not clear the saved rectangle. Only afterward is the Umbra world at system+0x260 released. A mod-created camera successfully queued into a free view slot dies at mission end along with game cameras; stale plugin pointers must not survive it.

GameCameraBase derived camera types

Static RTTI. GameCameraBase constructor 103740 (vtable 1769178) calls SceneCamera 118AFC0, then sets +0x38=1 to enable shadow cascades. Derived types identified are CharacterGhostCamera (player), DemoAnimationCamera, FreeViewCamera, TraceCamera and LODCaptureCamera; prior source supplied vtables for the first, third and fourth but not every subclass.

SceneCamera descriptor and projection defaults

Static. SceneCamera::SceneCamera 118AFC0(this,desc) reads a 4×4 world matrix at desc+0x10…+0x4F to this+0x220, Umbra world at desc+0x50 (system +0x260) to build wrappers at this+0x70 main and +0xF0 far, view number at desc+0x58→this+0x60, rectangle at desc+0x5C→this+0x190, and output shared pointer at desc+0x70. It creates shadow-cascade vector at this+0x170 (0x150-byte items, mask 0x40000000) and a 0x18-byte shared-pointer control block enabling shared_from_this at +0x10/+0x18. Defaults are vertical FOV fields +0x20/+0x24=π/4, near +0x28=0.1, far +0x2C=1000.

TraceCamera follows another camera with stereo offset

Static. TraceCamera is 0x360 bytes (vtable 1769218); constructor 1051F0 calls base, then copies followed-camera weak pointer from desc+0x80/+0x88 into this+0x350/+0x358. Every step vtable slot4 1052F0 locks it, copies camera world matrix +0x220…+0x25F after a 0.2 m offset along the right axis ([1F56234]), plus FOV and near/far fields +0x20/+0x24/+0x28/+0x2C. It reads no player input and owns no HUD. Attach/detach slots6/7 (1041F0/104250) only inspect zero field +0x268 and effectively do nothing; slots3/5 return immediately.

Existing stereo_camera debug path is a TraceCamera factory example

Static. Factory 82F60(system,shared_ptr* out,viewNo,aligned float matrix[16],desc*) fills desc+0x10…+0x70, allocates and constructs a 0x360-byte TraceCamera, queues it through 1195990 and casts it into out. Built-in debug command stereo_camera (string 1763E28, registration A3C9A, handler ACC80) takes view0's current camera, doubles its +0x20, and invokes 82F60 with a requested view number, identity matrix and weak pointer to view0. View loop, post-chain state and render-command ring

Camera view loop and per-slot draw/finish sequence

Static. 11978D0 (called from 1198FA4; dl=system+0xCE9, r8b=1) processes slots0–3 in order, skipping a slot if its current-camera weak pointer cannot be locked. Each active slot calls 1197B50→118DFF0 to build projection from its rectangle aspect, vertical FOV +0x24 and near/far, and 118E10A to hand matrix +0x220 to Umbra. Then it records shadow-cascade queries, far-view query, G-buffer setup, main-view query 1198656→11B6AA0 (Umbra and Commander callbacks), followed by that slot's own finish records. The view loop ends with 119889B→111B410, an immediate command-stream publication after the four slots.

Five conditional finish commands

Static. Finish calls take rdx=cmdctx=[EDF+2136FF0]: 1198742→112C230 when dl, recording full post chain 1131660 with slot color target +0xD0/+0xF0 and a copied 0x48-byte parameter block from system+0x280 (whose +0x2A0 was slot-linked); 1198753→112C460 when not dl, simple 1175A50 path; 1198777→11B6E20 always, byte argument 1; 119879F→112C5A0 when dl and slot byte +0xC8, with two color targets, tentatively identified as temporal anti-aliasing; 11987BF→112A7F0 only in mode3. The post-chain command matches the pause-free-camera render dispatch reference.

Finish arguments are copied on record, but order is still semantic

Static. All five finish command recorders copy their arguments, including TextureBase shared pointers and the 0x48-byte parameter block; the executing commands do not reread the record caller's original pointers. This makes it memory-safe for argument lifetime to re-record the same finish call later. It does not prove render-state equivalence after a different slot's world pass: the source's failed extra-view experiment demonstrates that finish/world ordering changes renderer state. Screen HUD is outside this slot loop: main flow 7058B7→11977F0 calls 118E500 for each slot later.

DeferredRenderSystem view descriptor and unresolved slot propagation

Static, final propagation inferred. The Commander's view block is at DeferredRenderSystem+0xE0, copied from each query descriptor by 11E1BC0; fields are view number +0, query type +4 (0 main, 1 far, 2 shadow), view matrix +0x20 and projection +0x60 (element5 vertical scale). View loop writes slot index to query descriptor +0 at 1197D2A. Main query 11B6AA0 copies this value at 11B6B85…11B6B8B into a block with query type0, and 11B41F0 writes it to a ring payload block +0x20 in 0x3C-unit records. The execution path 11B5A70→11E1BC0 was not read completely; view+0 as slot number at the world-end hook is a strong but unproven interpretation, not necessarily a viewport ordinal on every call.

Command recording, publication and render-thread execution

Static with contributor-measured lag reported separately. The command ring is cmdctx+0x28A8 with cmdctx=EDF+2136FF0. 51D00(ring,n) reserves n 16-byte units, 51D60 publishes and signals SetEvent when a 0x100-unit batch fills; 111B410(cmdctx) publishes immediately. The first command unit contains a function pointer; executor 111B8E0 reads units until null, then calls fn(nativeCtx=cmdctx+0x140,reader=cmdctx+0x2908). nativeCtx+8 is ID3D11DeviceContext*; 111D810 enqueues 1118AC0 for ctx→Flush. Therefore a callback-only command inserted at a known record position runs after earlier and before later render commands. The contributor's separate frame-pacing notes measured 0–3 game-thread steps of render-thread lag; do not assume synchronous execution.

Post chain may depend on untraced per-view renderer state

Partial static reading; dependency open. 1126AE0→1131660(R=renderer+8,native,texture,block) accesses R+0x598/+0x698/+0x6A8/+0x960/+0xB98/+0xBB0…+0xC48. View setup recorders such as 1127000 write native+0x698/+0x6B8, a distinct object; G-buffer setup writes R+0xF98/+0xFB8/+0xFD8, also non-overlapping with those direct accesses. Callees inside 1131660 (1134780, 11325D0 etc.) were not traced, so their dependency on per-slot state is unresolved. The actual failed slot3 run shows that some state leaks despite the initial non-overlapping fields.

Scope zoom and slot-three extra-view experiment

Undoing visual scope zoom after CharacterGhostCamera update

CharacterGhostCamera vtable slot4 at F86A0 writes camera+0x24=π/4/camera+0x410 every scoped-target step (F8906…F8916); projection 118DFF0 and Umbra 118DD30 consume +0x24 afterward. Slot-three lens view: proposed native route and offline guard tests

Static design and offline checks, not a proven successful in-game implementation. The author's route C uses spare view slot3 rather than a manual D3D scene renderer. At slot0 projection hook 1197B50→118DFF0, set slot3 rectangle {0,0,S,S} by 1198C40; create TraceCamera through 82F60 to follow slot0 and wait for the engine's next queue-drain update to populate slot3's owned list and targets. Conditions in which the extra camera must decline to run

Source-defined design guards. Reject split screen if slot1 or2 already has a camera; reject a nonempty camera list, existing current camera or nonzero view mode in slot3; give up if new camera does not reach slot3 within three seconds or the factory returns null. Also reject an unsupported main-view surface, including multisampling, a partial viewport, an unknown format or device-resource failure. These rules protect the user's active view; the source did not establish support for an arbitrary second mod concurrently occupying slot3.

Failed first live run exposed state-leak ordering bug

Contributor-reported live evidence (13 November log, 21 November screenshot), interpreted with static traces. The initial plugin postponed slot0's finish commands until after slot3's world, replaying only G-buffer setup 112B230. Yet slot3's world had also recorded three shadow cascades 112AA90, 112B550, 112AD40 and conditional 112A350 when system+0xCE8 was set. Slot0's post chain 1131660 then inherited slot3 state. Reported result: picture freeze, return to full-screen scope, and a black top-left square the size of inset (1296×1296 at 4K), the only written region. The source's correction is to keep each slot's own world and finish records adjacent in engine order (slot0 finish before slot3 world). This is a diagnosis and intended fix, not evidence of a successful later game run.

Unmeasured cost, post-processing and mission-lifecycle risks

Open; requires real-game qualification. Slot3 performs a full extra world draw, including three shadow cascades, Umbra and CPU scene walk. At inset side length roughly 0.6×short screen dimension, its pixel ratio is (0.6×shortSide)^2/(width×height), approximately 20% for 16:9, but that is pixel-area arithmetic, not measured GPU or CPU cost; narrow FOV can affect culling. The main-view temporal resolve 112C5A0 or depth-of-field uses main depth/motion and could smear the inset. A separate first-person mod matching players by view matrix could mistake an identically oriented extra view for that player's primary view. Clean recovery across mission change/reload/restart and world-end hook's view+0==3 slot interpretation remain unverified.

Camera pose, frame ordering and screen coordinates

Evidence scope: static native reads and one bounded render-timing study from the Knowledge Hub camera.md, pinned to steam-678ccb46. Frame-pose effects are code-order inferences unless separately measured; no new two-thread instrumentation was performed for this reconciliation.

Previous camera pose: CharacterGhostCamera slot 3 F8210 copies its 64-byte live matrix at +0x220..+0x25F into +0xB00..+0xB3F and float +0x530 to +0xB40 before the simulation camera step. Render slot 5 F7B80 reads both the copy and live rows and calls matrix uploader 112F590, shaped like EDF5's view/projection and inverses writer. The audit did not establish exactly where every matrix built from the copy is stored; do not equate a saved previous pose with a demonstrated interpolation implementation.

Per-frame slot rectangle: view setup 118DFF0 copies view slot +0x34 rectangle {x,y,w,h} to camera +0x190..+0x19C and derives the projection aspect from it. Player construction 22AB90 assigns each local player a side-by-side column of target width W/n and height H when n > 1, or full W×H for one player; the source reads W/H from renderer target [[2137090]+0x10]+0x20/+0x24. This pins a camera/slot relation; other slot setters were not exhaustively reviewed.

World and HUD pose timing: on game thread Application::Update 705530 first submits world-view work through 1198DA0, using the camera rows handed to Umbra near 118E10A. It then advances fixed simulation/camera steps and later queues HUD work through 11977F0; the render-thread HUD projection uses later live rows via 81EC50/118DA40. The contributor infers a one-step-like potential world/HUD overlay mismatch while turning, possibly larger with render lag, but did not measure its actual visible size in gameplay.

HUD viewport translation: 118D810 first sets the camera rectangle, then a window-scaled rectangle taking letterbox/pillar offsets from 1183250/1183290. HUD world-to-screen still receives the unscaled camera rectangle. Without letterbox the source transforms X by actual window width / fitted target width and Y by actual height / fitted target height; with letterbox it adds the fitted image's X/Y offsets. The assertion that the slot rectangle is always defined in the 16:9 fitted coordinate system is a scaling-based inference, not a checked alternative aspect-ratio runtime sample.

World-to-screen helper: 81EC50(out, point, camera, viewport) multiplies a vec4 point through the live view, camera projection and viewport scale/flip. For nonzero clip w it divides X/Y by w (not Z), negates XYZ if w is negative, and uniquely versus the EDF5 reader adds the viewport's own X/Y origin before returning {screen X, screen Y, clip Z, clip W}. Points in front have positive W. This output is in the camera rectangle's coordinate space, not just relative to its upper-left corner; window-pixel conversion is a separate step.

Presentation-only interpolation study: normal CharacterGhost solver FAF20 was left intact; the study used generation marker CharacterGhost+0x52C, QPC phase from 66CD0 / boundary 2139D18, temporarily blended rigid SceneCamera rows +0x220..+0x250 for render setup 118DFF0, then restored them. Its bounded moving-camera measurement counted approximately 90.306 unique camera states/s, 89.728 Presents/s and 59.922 fixed steps/s, yet other actor/VFX jitter remained. This is a contributor runtime sample of camera presentation, not a claim of full world interpolation or engine-native 90 Hz simulation.

Ride-camera horizon: type-1 ride camera uses look-to function 4E220 based on eye-to-look direction, with no separate vehicle up vector. The contributor concludes the view remains horizon-level when a banking jet rotates, even when camera and look locators both follow the root bone. Its custom chase-camera roll adjustment is a mod workaround; the exact absence of roll was inferred from the code path, not newly compared in-game across all vehicles.

Radar-warning camera message and patch

RadarWarning payload · static reference: System::SendMessageToCamera 11989F0 accepts camera message 0x10000023 with a 16-byte-aligned block: int type at +0x00, start vec4 +0x10, end vec4 +0x20, float radius +0x30, int lifetime +0x34, color vec4 +0x40. Gaps are padding. The field meanings come from KittopiaCreator's RE note; a successful general camera-message call does not independently test this specific RadarWarning message.

Lingering EfsBullet warning overlay · source unverified: KittopiaCreator's patch hooks hit-area spawn at 23D25D, then sends message 0x10000023 with same start/end at hit translation, radius bullet+0x8C8 × 1.5, reported lifetime from the area object, red color (1,0,0,0.8) and type 0. The patch's coexistence checker reported no known overlap, but the source contains no in-game warning result; lifetime/radius units and missing team filtering are outstanding issues. Enemy and friendly lingering areas would both be marked by that implementation.
