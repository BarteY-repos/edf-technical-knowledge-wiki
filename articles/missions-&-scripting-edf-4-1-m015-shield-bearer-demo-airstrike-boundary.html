EDF 4.1 M015 Shield Bearer demo-airstrike boundary

UniversalMissions & ScriptingMissionsEDF 4.1EDF 6
Source-backed research / case study · Source behavior established; target runtime pending

Source behavior

The scripted “Breaking Through” demonstration establishes a real gameplay invariant: the demonstration airstrikes fail against the defensive screen and the Shield Bearer remains alive/unharmed afterward.

A port in which that scripted airstrike kills the Shield Bearer is therefore a fidelity failure, not harmless target variation.

Why the fix is not “give it more HP”

The old bridge relied heavily on stock EDF6 Shield Bearer behavior. R12 improved the physical collision side by pairing EDF4.1 AlienTrailer401 variants with corresponding native EDF6 E513 shield SHKT geometry.

That does not prove identical damage semantics for:

  • area damage;
  • scripted/demo airstrike damage;
  • forced-damage flags;
  • shield/body acceptance routing.

No evidence supports blanket invulnerability or a generic HP increase.

Current R12 collision bridge

The collision mapping is:

  • S → e513_Barrier_S.shkt;
  • L → e513_Barrier_L.shkt;
  • LL → e513_Barrier_LL.shkt;
  • XL → e513_Barrier_XL.shkt.

The geometry match is strong and the target SHKT uses EDF6-native hknp representation. This is a collision-format compatibility decision, not a damage-policy claim.

Runtime gate

The required test is mission-specific:

  1. run the M015 scripted demonstration;
  2. verify the airstrike hits the intended shield interaction;
  3. verify the defensive screen behaves as in EDF4.1;
  4. verify the Shield Bearer remains alive/unharmed after the demonstration;
  5. ensure ordinary later combat/damage remains functional.

If the demonstration still fails, inspect the exact scripted-airstrike/shield damage path before changing the object globally.

Rule

Preserve the source interaction, not a guessed immunity property. A scripted demonstration can depend on damage type, shield query, forced-damage semantics or routing that a generic stock target object does not expose identically.

R175 original script-object and collision evidence: do not infer immunity

The original EDF4.1 and EDF6 DEMOAIRSTRIKEE50_10.SGO files are byte-identical in the inspected source corpus (SHA-256 b186d3f74d4ee4d77f222087a15d26d6cc01c96d04eaff36dc0ad3d23dd08dad). Their source-controlled DemoAirStrike uses a BombingPlane (Bomber401) with damage 1000, height 250, speed 3, spread 10, target adjustment 0.5 and target distance 100. These are original object fields, not evidence that a target-side animation, physics query or damage result must match automatically.

Exact EDF41.exe source analysis identifies the DemoAirStrike event handler at RVA 0x2BD560. It accepts event 0x80000004, resolves its BombingPlane and assigns a scaled bombing-damage value to the plane; the identified seam is not a direct forced-damage bypass into the Shield Bearer's HP. Independently, EDF4.1 AlienTrailer barrier construction attaches body metadata key 2 (around 0x1DC2F4 → 0x606B30). EDF6 native E513's AlienTrailer_Barrier also uses body key 2 to reach BarrierInfo, which participates in hostile-projectile stopping. This correspondence makes the stock-native barrier route plausible, not proof of all kinds of scripted bombing protection.

An earlier source-to-target SHKT census establishes four bounded geometry pairs, not equal Havok files: EDF4.1 RAGDOLL_ALIENTRAILER401_BARRIER_{S,L,LL,XL}.SHKT (Havok 2014) and EDF6 E513_BARRIER_{S,L,LL,XL}.SHKT (Havok 2020). Their observed half-extents are close to 50, 100, 200 and 470 respectively, but even closely matching AABBs do not prove identical layer filters, projectile interception, explosion damage or runtime state. The exact component bounds and SHA-256 values are in data/R175_EDF41_EDF6_SHIELDBEARER_FOUR_SHKT_AABB_PAIRS.csv.

These results refine the older statement that an unknown generic source/target damage-scalar mismatch was the obvious cause: no relevant divergence was established at the compared DemoAirStrike or Bomber401 SGO scalar level. The real M015 demonstration remains an unresolved runtime fidelity test, not an authorization to grant blanket invulnerability.
