Player-state networking: periodic transforms, jumps, EOS and RUDP

UniversalEngine RE & NetworkingNetworkingEDF 5EDF 6
Technical reference · Native binary confirmed packet routing; observed directional desync; repair candidates runtime-unproven

A player's walking position, a class-specific jump action, and a projectile collision event are not equivalent kinds of network messages. EDF has separate gameplay packet classes, ownership and delivery rules. Understanding these explains how a jumping player can briefly appear to snap into the correct position while ordinary walking state remains stale for other peers.

Three gameplay traffic classes

The audited EDF6 implementation separates the following paths:

Gameplay path Packet / receive route Application delivery What it is used for
Ordinary scene/player state Class 3 / 0x3300, SceneObjectReceiver Mode 1, no retained sequence/ACK/retry Periodic actor snapshots and ordinary transforms
Immediate gameplay events Class 4 / 0x3400, EventController Mode 0, Sandlot RUDP retained reliability Actions and class-specific state changes, including jump transforms
Projectile-state publication Class 5 / 0x3500, NetworkBullet/BulletManager Mode 0, Sandlot RUDP retained reliability Later projectile and contact state, according to selector

All three can eventually use the same physical ordinary gameplay transport. Reliable class 4/5 messages are wrapped in the game's own RUDP records before that lower transport. Therefore an underlying EOS UnreliableUnordered call does not mean class 4/5 traffic lacks application-layer retransmission.

Periodic walking transforms (0x3300)

The measured Soldier state is an absolute current transform/state, not a delta that mathematically requires the previous packet. One inspected wire path compresses XYZ to approximately six bytes. Transforms are generated on a cadence (approximately one transform bit every six network updates), rather than only when a dirty baseline changes.

The class-3 record is fire-and-forget: no pending reliable record or ACK is retained after the physical send. If a packet is lost, a later successfully delivered and applied snapshot should correct position. Persistent drift therefore demands something beyond one isolated loss: repeated failure/suppression, stale receive queues, a gate that discards decoded updates, or another ongoing defect.

The receive path is staged. 0x3300 payloads are copied into a pending queue, later parsed, and then offered to a target NetworkObject through an apply gate. The pending flag can be cleared before the target gate is evaluated, so a false gate can discard that particular decoded batch. However, the basic Soldier gate was found structurally homologous to EDF5; treating its mere existence as an EDF6-specific regression was a rejected hypothesis.

Why a jump can temporarily correct a position

For Fencer/HeavyArmor, the audited path is:

base_high_jump_start
  -> immediate Soldier message 0x15
  -> transform mask = 1
  -> class 4 / 0x3400
  -> retained RUDP delivery

Ranger/AssaultSoldier has transform-bearing 0x14-family messages, and Wing Diver has 0x16/0x17-family messages. The common result is that a class-specific action can publish a strong transform through a lane different from ordinary walking snapshots.

In observed multiplayer desync, the jumping player's outward position corrected on other peers, but the jumper's view of the other players did not globally recover. Desync could then return. This is a directional/per-sender event, not evidence that jumping resets the whole connection.

Important correction: a jump transform should not be generically called “message type 5” or “message 19.” Those strong correction paths also exist but are not the identified class-specific jump route.

EDF5 Steam versus EDF6 EOS physical delivery

The audited EDF5 physical interface distinguishes Steam Unreliable from UnreliableNoDelay. The shipping EDF6 ordinary gameplay path uses the EOS adapter's ordinary slot and ultimately EOS UnreliableUnordered. In the inspected EOS wrapper, the two logical unreliable methods had effectively converged on sends with bAllowDelayedDelivery = false.

This difference is a candidate loss/reconnect mechanism, not a runtime-proven universal cause. It may remove establishment/delayed-delivery behavior expected by the original ordinary path. In another observed code branch, EOS_NoConnection prompts connection acceptance but does not resend the failed original packet inside that wrapper.

EDF6 also adds a per-peer physical aggregation buffer that normally flushes on roughly 90 ms, or earlier when size requires. One physical loss can therefore discard several bundled lower-layer records. The buffering interval alone is much too short to explain sustained positional drift; its significance is the common loss domain beneath the gameplay lanes.

Normal class-3 payloads are not plausible 1400-byte limit overflow by themselves: the audited scratch record is 0x484 (1156 bytes) at maximum, and an ordinary walking XYZ field is much smaller. The historical idea that legitimate RUDP records routinely exceed the EOS maximum was also rejected after checking the actual builder/aggregate envelope. The legitimate shipping class 4/5 retained record is bounded to 1156 bytes, first physical aggregate to 1164 bytes, against the audited 1170-byte EOS path limit.

RUDP recovery and peer READY state

For class 4/5 and normal NetworkBullet selectors 0/1/2, Sandlot RUDP retains sequence-tagged data until an ACK. In the researched framing:

  • 0x1200 — retained DATA;
  • 0x1300 — ACK for a matching pending record;
  • duplicate received DATA is acknowledged again but not reapplied;
  • 0x1400 — removes a receiver deduplication marker; its general role remains unresolved.

Retries start after 700 ms and add 1000 ms per retry. The EDF6 fault interval threshold is 7000 ms, yielding about 25.9 seconds cumulative no-ACK history in that failure chain; the directly compared EDF5 threshold is 20000 ms, approximately 204 seconds cumulative. Neither figure is simply a single 7-second/20-second timeout.

The physical p2p::Link object is replaceable while the higher-layer UserSession, sender and ReliableMgr persist. A transient RemoteConnectionClosed can replace the Link without discarding outstanding reliable messages. But the studied EDF6 path can retain READY=1 during this replacement, causing the newly created Link to bypass its normal INITIAL recovery flow. This is a concrete binary-supported reconnect defect candidate; runtime repair qualification remains separate.

What is confirmed, and what is not

Exact-binary findings: the three packet routes; non-retained class-3 snapshots versus retained RUDP class-4/5; class-specific jump messages; 90-ms physical aggregation; the inspected READY/Link behavior; and the compared retry thresholds.

Observed gameplay symptom: jumping briefly corrects the jumper's position outward, not every direction or peer. Aim/firing state and HP can also diverge, so not all symptoms are transform-only.

Not established: that the delayed-delivery difference or stale READY individually explains every real-world desync; that restoring either is universally safe; or that eight-player multiplayer is already qualified. Runtime traces must correlate physical sends, per-lane enqueue/drain/apply and RUDP ACKs before assigning a singular root cause.

For deeper bullet-specific behavior see NetworkBullet selector/contact semantics and RUDP ownership and retransmission.

Event protocol registry and evidence-based diagnosis

Outer class 0x3400 is not an event protocol ID. In the audited EDF6 registry, DamageObject=1, Generator=2, Mission=3, SynchronizeGate=4, SceneObject=6, NoteEventSceneObject=7, ItemDrop=8, System=9, TalkManager=10, and Debug=100. Protocol DamageObject belongs to the retained class-4 EventController path; it should not be conflated with fire-and-forget class-3 position snapshots. The literal 0x2B observed later in the DamageObject handler is an internal event/job code. See full event registry.

The comparative investigation also explicitly rejected the inherited bandwidth scheduler, inherited LightSync, a supposed NetworkBullet reliability downgrade, Watchdog_Session as a proven PC keepalive, and legitimate oversized ~1400-byte RUDP traffic as stand-alone causes. See cross-version desync evidence table.
