MDB model format

UniversalModels & MDBModelsEDF 5EDF 6
Technical reference · Reconciled native/source research

At a glance

What it is: An MDB describes a 3D model: its mesh geometry, vertex layout, materials, texture bindings and, where applicable, bones.

Where it fits: It provides the data needed to draw a model, but rendering also depends on the correct shaders and resources. Animation and collision impose additional requirements.

Important distinction: This article separates model-file structure from the separate questions of runtime compatibility and physics.

Worked example: calculate a vertex stride

A vertex declaration tells the reader how many bytes to advance between vertices. For an illustrative combination of declaration types from the measured table below, the stride is the sum of the element widths:

Declaration typeLane representationBytes per vertex
4float32 × 3 (three-component lane)12
12float32 × 2 (texture coordinate lane)8
21uint8 × 4 (four indices)4
TotalHypothetical packed declaration24

With that hypothetical packed layout, vertex 1 begins 24 bytes after vertex 0. This is arithmetic, not a claim that every native MDB uses this combination or has no padding. For a real mesh, follow its actual declaration, stream and alignment. In particular, measured type 1 is float32 × 4 (16 bytes), not a four-byte field: misreading it shifts every following attribute.

Overview

MDB is a model resource containing structural metadata, geometry streams and material relationships. The bytes must agree with the mesh's vertex declaration; animation and object collision add further bone and physics constraints.

Native material schema versus shader reflection

How to read and write native MDB materials explains the exact parameter sequence, sampler order, integer-bit parameter exceptions and why a reflected shader catalog must not be serialized directly as a material. For roughness and metallic formulas, see MDB shading parameters.

An MDB is a model resource used by Earth Defense Force. Its observable data can include name/bone/object relationships, meshes, vertex declarations and buffers, material records, shader identifiers and texture references. Those parts have to agree: a model is not just vertex positions with a shader name attached. We have strongest detailed structural examples from EDF5/EDF6 ordinary model assets, including buildings and props used in maps. These are not FieldRender/FMEP terrain formats.

Geometry and vertex declarations

Each mesh describes how the bytes in its vertex stream should be interpreted. The declaration supplies a semantic (such as POSITION, TEXCOORD or BLENDINDICES), a stored element type and a per-vertex layout. Do not infer a universal stride from the game version alone.

Observed declaration encodings in paired EDF5/EDF6 research:

Type Observed lane shape Bytes Common use
1 float32 × 4 16 BLENDWEIGHT and four-component lanes
4 float32 × 3 12 Three-component float lanes
7 float16 × 4 8 POSITION/NORMAL/TANGENT/BINORMAL profiles
12 float32 × 2 8 TEXCOORD
21 uint8 × 4 4 BLENDINDICES

Important correction: declaration type 1 is 16 bytes, not four. A parser using four bytes shifts all later elements and silently damages its view of the vertex buffer.

Meshes can carry multiple UV streams, including repeated TEXCOORD semantics in non-obvious order. Vertices may need to be duplicated at UV, tangent and normal seams when constructing a target mesh. In observed static EDF6 map-model profiles, 60-, 68- and 76-byte strides occur, sometimes including rigid blend weight/index channels for visually static assets. Those are observed profiles, not universal MDB requirements.

Large-model precision caveat (source-reported offline conversion): stock EDF6 v505, v515 and v603 templates encode positions as half4 (vertex declaration format 7). The source estimates position quantization up to roughly 7.8 mm at 8–16 m from model origin, increasing with coordinate magnitude. On an unusually large, centered 228 × 110 × 500 m authored battleship, the measured mean position error was 29.1 mm (99th percentile 65.1 mm), with 343/71,669 triangles collapsing and 12.4% of face normals turning more than 5°. Changing position to float4 (format 1) expanded its particular vertex stride from 60 to 68 bytes and reduced the reported position error to 0.01 mm. This is one source-authored asset comparison, not proof that every large MDB can be re-encoded without also checking the runtime vertex declaration, material and skinning path. Source: Hajisensai, All Forces docs/model-quality-1110.md, EDF6 Steam 678ccb46.

The studied exporter path uses 16-bit mesh indices. A mesh that exceeds that range needs rejection or a deliberate triangle-boundary split, rather than index truncation or an invented 32-bit variant. Sampled native EDF6 multi-mesh resources align each mesh vertex-buffer start to 16 bytes; this is a strong native-conformance practice, not proof that every misaligned MDB crashes.

Object names, bones and mesh relationships

Name, Bone, Object and Mesh records are connected rather than freely interchangeable. A source-to-source writer should preserve shared name identity, relative-offset conventions, object-to-bone links, bounds and skinning metadata. Some games or authoring utilities support ordinary static geometry without a visible character rig, but that does not justify discarding blend channels from every native static-model profile.

A reliable importer/exporter should parse the declaration and semantic relationships, preserve unknown records and shader ABI metadata where possible, and only regenerate fields it has a defensible interpretation for.

How EDF6 selects an MDB LOD and draws the model

The 7 November 2026 EDF6 native model-draw study (build steam-678ccb46) traces the link between model data and the renderer. An animation_model SGO may contain a list of MDB resource name + distance threshold pairs at animation_model[0][2]. The loader resolves each MDB in the same archive and stores an LOD entry at model +0x250 + i*0xF0, with a squared distance threshold at entry +0xE8 and an entry count at model +0x260.

The sampled AnimationModel draw (6BF9F0) starts with the base mesh at +0x160 and walks the LOD entries in their source order, selecting each entry while its threshold is no greater than the computed distance squared. Thresholds must therefore be ordered ascending in the studied loader/draw contract. The source interprets the selected distance as approximately max(camera distance - bounding radius, 0), i.e. distance to the bounding sphere's surface; that part is an inferred field meaning, not a separately measured distance formula.

Observed passAnimationModel behavior
0, 3Selected LOD's depth/shadow draw path; the mesh loader can suppress a shadow pass for a given LOD.
1Selected LOD's opaque mesh table for the main G-buffer pass.
2Transparent mesh handling through a separate draw slot and distance sorting.
5Distant-view submission of selected LOD's opaque and transparent mesh tables.
4 or 6+No mesh draw in the studied AnimationModel draw switch; pass 4 can still be used by other renderer objects.

The same selected LOD is used across these studied passes, including shadows; an LOD material does not independently choose another geometry distance. In a finite stock census, 45 HD/LOD pairs across 30 archives shared matching bone counts and order, and LODs reused the base model's skeleton instance as well as its material and texture tables. These are observed stock relationships, not proof that arbitrary custom LODs can omit bone compatibility checks. The same loader exists for vehicles, but the surveyed 155 Root.cpk SGOs with LOD tables were soldiers, insects and UFOs, not stock vehicles.

Do not confuse this runtime geometry selection with the native map LOD/FarMap shader profiles: an _lod.mdb name, a particular 44-byte material declaration and an SGO switching threshold are three separate facts.

Draw pose versus bones and GPU skinning

For a skinned model, the submitted pose is not sampled directly from CANM at draw time. The recorded native path is:

  1. CAS/CANM updates the bone's local transform fields (record +0x70); the skeleton computes world transforms into per-bone record +0xB0.
  2. Model synchronization (1100F10) copies each world matrix into a separate draw-pose array at skeleton-instance +0x30, with a 0x40-byte matrix per bone.
  3. The draw path (11009A0) multiplies inverse bind × draw pose for each bone, packs 3×4 rows, and uploads a skinning palette to the vertex stage. The studied GPU binding is vertex constant-buffer slot 1.
  4. Rigid meshes instead use their selected bone pose in the rigid-mesh draw constant buffer.

The source's ordinary vertex paths include 16-bit indices and uint8×4 BLENDINDICES, so a mesh's bone-index lane cannot name an arbitrary index over 255. In the 738 sampled stock OBJECT MDBs, none used 32-bit mesh indices; this does not establish a universal maximum for every future model version.

The draw pose can lag the game-thread skeleton pose because draw submission and object update cross threads. Thus the CAS controller, bone world matrix, draw-pose copy and GPU skinning buffer are different state. This page explains the observed engine route, not a requirement that every parser or game version use the same memory offsets. See the CAS-to-draw-pose distinction and render pass meanings.

Visibility can also gate secondary model physics

The same EDF6 AnimationModel study found that a color-pass draw marks the model's +0x4D0 flag and keeps the smallest drawn distance squared at +0x4D4. During synchronization, these values are copied into “drawn last frame” state (+0x4D1, +0x4D8), and the current-frame values reset. This is a visibility bookkeeping channel, separate from the model's CAS animation time or bone data.

The sampled secondary-physics controller at model +0x298 uses that prior draw flag and the square root of the saved distance. Its reported active state requires the model to have been drawn in a color pass and to remain inside the controller's distance bound (controller +0x200). When those conditions fail, it sleeps. This gives a concrete engine-level reason why a distant or non-rendered character's cloth, skirts, hair or chains may stop updating while ordinary skeleton animation continues. The interpretation is from static code plus finite model probes; it is not a universal statement about all Havok bodies or mission physics.

Materials: what is actually stored

A material is not fully described by a familiar PBR tuple of color/roughness/metallic. Native MDB material profiles can include:

  • An exact shader family, for example snd_BRDF_Map_Common, snd_BRDF_Map_Common_Clip, snd_BRDF_Map_Build_Basic_NC or older snd_Map_* families.
  • An ordered parameter list, where each entry has a name, type/size encoding and stored value bytes.
  • An ordered sampler list, with texture resource identities and filtering/addressing/LOD metadata.
  • Render metadata and a corresponding vertex/UV/tangent contract.

For example, observed EDF6 snd_BRDF_Map_Common material records use parameters diffuse, metallic, normal_amount, roughness, specular_color and specular_diffuse_blend, with sampler order albedo, normal, param_r_m_xxx_hr. Common_Clip adds alpha_clip. These are observations for named families, not a schema for all MDB shaders.

How do roughness and metallic work in MDB materials?

For the studied EDF6 snd_BRDF_Map_Common / param_r_m_* ordinary-model path, the packed texture modifies the scalar material parameters. In the observed family, G controls metallic and R controls roughness; an _hr packed texture also uses A to scale roughness:

float metallicValue = saturate(packed.g * material.metallic);
float roughnessValue = saturate(packed.r * material.roughness);
// If this is the _hr family:
roughnessValue = saturate(packed.r * packed.a * material.roughness);

For the studied Common/Water-like normal-map convention, X is reconstructed from R×A, Y from G, and Z from the remaining unit-normal length. This is why a standard RGB normal map or a plain Principled BSDF can disagree with the EDF material. These formulas are specific to the identified shader family: legacy reflect/spec materials, some character shaders and FieldRender terrain use different or incompletely recovered semantics.

See MDB shader parameters explained for normal decoding, specular_color, cutouts, light masks and the broader shader family caveats. The exact native profile tables give family-specific parameter order and type/size values.

Texture data and resource identity

An MDB can refer to logical texture identities, while texture payloads live in separate resource packaging such as RAB/DDS. The resource name, payload, filtering rules, sampler order and shader expectation have to agree. A working model may have editable MDB material bindings without forcing a rewrite of its geometry or collision.

What changes between EDF5 and EDF6?

Paired models show changes beyond a header version: tangent/binormal streams may be added, vertices split at seams, materials reauthored, samplers reordered, texture channels changed, and object/name responsibilities altered. There is no universal conversion rule of “write EDF6 version, rename the shader, keep everything else.” Nor is there one mandatory EDF6 vertex declaration order for every material.

A conversion tool must recognize supported source/target profiles, preserve semantic identities, and validate material ABI, shader, texture packing and required vertex lanes together. Native observations are stronger than plausible-looking imported previews.

Float4 vehicle body-shell positions remain untested in native passes

Static, hajisensai All Forces model-quality notes, EDF6 steam-678ccb46. A float4 POSITION declaration works for a vehicle's stock cockpit meshes, which already render this way, but the source has no in-game run of a float4 body shell; depth and shadow submissions remain unchecked. All materials sharing one model's vertices must use a consistent position format. Mixing half4 and float4 quantizes the same vertex differently and produces seams: in the author's C-130 sample, 53 of 171 shared vertices disagreed by over 1 mm, with maximum discrepancy about 3.9 mm. This is an authoring precision boundary, not proof that switching the shell to float4 fixes model parity.

Important boundaries

  • Ordinary MDB mesh materials are not FMEP/FieldRender terrain. The latter uses a different terrain-material and texture-array path.
  • _lod.mdb does not guarantee a specific LOD shader; some native LOD companions reuse normal material families.
  • A preserved unknown material can round-trip correctly even when a Blender/glTF-style preview is approximate.
  • A shader's register-level texture binding order need not equal its MDB material sampler-list order.

For deeper reading: MDB migration profiles, vertex layouts and skinning, type-4 parameter encodings and map render/collision separation.

Source-tree cases and version rewrites are not full model parity

A historical paired-tree resource comparison reported 218 position-only placement records (T2) that were byte-identical in its EDF5/EDF6 samples, while the displayed tree size remained a separate open question in that test. That finite record equivalence cannot establish general MDB mesh/material parity or native render-size rules. Likewise, an older converter upgrading a measured MDB version and rewriting fields was a conversion attempt, not proof that every model, skeleton and material family is equivalent across the games.

When debugging a correct MDB that still crashes, check the resource type registration first: an earlier byte-exact in-memory MDB was fed into the wrong .trb handler. See typed-dispatch failure analysis.

EDF6 native MDB 1,176-file census and field conflicts

Source: edf6/mdb-format-census.md, 21 canonical ktaro records, compared with the older Knowledge Hub MDB layout study. All counts refer to the inspected OBJECT/WEAPON stock files. Apparent conflicts between source corpora and uncertain use of unknown fields are preserved, not silently normalized.

1,176 MDB v0x20 files and inconsistent source subtotals

The parser successfully read 1,176 EDF6 MDBs—804 under OBJECT, 372 under WEAPON—with no recorded parse/structural anomaly and every file version 0x20. The corpus totals 13,035,887 vertices and 9,034,557 triangles over 3,153 submeshes; a different MeshIndex table in the same source reports 3,183, an unresolved count mismatch. The summary records 19,594 bones while a separate hierarchy paragraph gives 19,469; do not combine them as if equal. Per-file maxima include 126 bones, 26 objects, 14 materials and 49 textures.

Large stock models and vertex-count scale

Largest sampled model ev607_jormungand.mdb has 1,238,222 vertices in an approximately 77 MB file (distant scripted prop). Next are e609_jormungand_face 145,904 (Primer's head), e604_radon 142,610 (Siren/Glaukos), p606_wingDiver 133,219 and p608_airRader 109,901. Major character models commonly occupy 90,000–150,000 vertices, but this list only ranks the sampled files by vertex count, not draw-call performance or memory residency.

Record-size agreement with older format layout

ktaro's header/name-table/bone/object/mesh/layout/material/parameter/texture-reference/texture tables agree with the earlier native MDB layout on field offsets and sizes: 4-byte name-table entries (nonpositive offset means no name), bone 0xC0, object 0x10, mesh header 0x28, layout element 0x10, material 0x20, parameter 0x20, texture reference 0x1C and texture 0x10. Most relative offsets are based at their containing record; ObjectInfo.matid and Material.materialname are direct array indices. Agreement on layout does not by itself settle disputed field semantics.

Object record's first two dwords have rival labels

For each 0x10-byte Object record, ktaro labels dword 0 as ID and dword 1 as Nameid, followed by mesh count and record-relative offset to a 0x28-stride header array. The older file-format/authoring study instead reads the first as object name reference and second as the bone the object attaches to. Both sides agree on physical locations, so the naming/meaning disagreement must remain open until cross-checked with engine consumers.

Sixty-five shader names in OBJECT/WEAPON materials

The 1,176-file material census contains 65 distinct shader names. Most common are snd_BRDF_Common_Basic (701 materials), snd_BRDF_Common_Light (294) and snd_BRDF_Common_Basic_Damage (157). Because this census covers OBJECT and WEAPON only, snd_Chara_* usage is undercounted, and a shader omitted from this list is not necessarily absent from the entire game.

Material ID, priority and layer byte distributions

Every observed material's uint16 id equals its array index. Priority byte takes 0 (dominant), 1, 2, 3, 5, 6, 7, 10 and 20; layer byte takes 0 (dominant), 2 (185 materials) and 1 (8 materials). ktaro suggests priority sorts overlapping transparent meshes and layers distinguish opaque from transparent/UI, but those runtime meanings, especially layer 1, are unverified. A raw serializer should preserve both bytes regardless of the preview's sorting convention.

Render type 2 appears in enlarged census

Material +0x1C (render type) is 3 in 2,293 observed material records and 2 in 11, no other value. The earlier 738-MDB corpus reported only 3; the larger corpus includes WEAPON files, so the earlier universal statement needs narrowing. The source's explanation of type 2 as a force-field/shield whose texture updates during rendering is hearsay and remains unverified.

20-byte value body and type/size census

Each 0x20-byte material parameter record has four value dwords, two following dwords dat5/dat6 that were zero throughout the sampled corpus, and a final dword packing type byte, size byte and zero uint16. Counts of type/size: 0/1 12,102, 1/2 1,421, 2/3 3,499, 2/4 3,398, 3/4 159, 4/1 74 and 255/1 160. Type 4/size 1 is the raw-uint32 interpretation from authoring research, not an ordinary float. Other type-to-float-width readings are ktaro's provisional inference, and additional packed words such as 0x0402 should not be treated as a general validated typing rule.

Forty-five texture slot names in stock MDBs

Sampled texture references use 45 distinct ASCII slot names. Frequent kinds: albedo 2,276, normal 2,271, param_r_m_occ_hr 1,106, param_r_m_occ_light 415, damage_dist 409, damage_normal 404, damage_diffuse 401, param_occ 256, param_r_m_xxx 169 and param_cm0_cm1 162. The family suggests roughness/metallic/occlusion and damage maps, but unnamed trailing bytes of texture-reference records remain open in this source.

Texture-table fourth dword and runtime suffix branch

The fourth dword of every texture-table entry in the 1,176-file corpus is zero. On resolving a v0x20 material texture, the native code checks whether its mapping string ends with _dds using a 64-bit literal comparison; if not, it extracts a mip-level suffix. This identifies a loader branch, not a license to assume all resource strings are filesystem DDS paths.

Vertex attribute name casing differs between reported corpora

ktaro reports v0x20 vertex attribute names as lowercase except BLENDWEIGHT/BLENDINDICES, while the older 738-MDB source survey saw both upper- and lowercase naming variants. Preserve exact name bytes in import/export; do not force a lowercase rewrite based only on the larger summary. The difference remains a source-sample or interpretation discrepancy.

Mesh header flags track skinning declaration

Across the source's 3,153 submeshes, flag bytes 0 and 3 and field +0x08 were zero. Header byte 1 is 1 precisely when the vertex declaration includes BLENDWEIGHT; byte 2 stores the number of influences, 0–4. These are observed format correlations, not proof that a newly authored mesh with inconsistent fields is accepted by the game.

MeshIndex is bounded but has no identified drawing reader

Mesh header +0x18 MeshIndex is always below the number of meshes in its object, yet does not equal mesh order, object index or material ID. Native load copies it to memory, but ktaro found no drawing or sorting reader in the Ghidra search. This is a bounded negative read; indirect consumers could still exist, and an exporter should retain the value until semantics are confirmed.

Four bone kind codes with conflicting class names

All 19,594 counted bones have kind byte +0x18 among 0/1/2/3, at 14.4%/3.2%/5.9%/76.5%. ktaro calls kind 1 unknown and kind 2 empty (a wiki-derived, unverified interpretation); the other format study reads 1 as rigid-mesh attachment bone and 2 as skinned-object attachment bone based on 738 MDB relationships. Both interpretations are retained because they classify the same byte differently. Kind 3 is the dominant weighted/skinned case in the surveyed files.

Bone bounded flag and consistently empty padding

Bone +0x1A is binary (0/1): kind 0 always 0, kind 1 always 1, kind 2 always 0 and kind 3 has 1 in 99.5% (71 zero exceptions). Byte +0x1B and four bytes +0x1C..+0x1F are zero for every one of the 19,594 sampled bones. The source associates +0x1A with whether the bone's bounding box is used; the exact engine culling predicate was not traced.

Bone hierarchy depth-change byte and sentinel hypothesis

Bone byte +0x19 takes 0–14 or 243–255 (signed −13..−1). Values 1 and 0 occur in 57.8% and 23.5% of entries; 250–255 account for another 16%. ktaro left it unnamed and suggested sentinel behavior, while the prior format study interpreted it as a signed depth delta to the next bone (+ when descending, − when returning up the tree). Range compatibility is supporting evidence, not an independent verification of every malformed hierarchy case.

Bone parent-local transform and world inverse bind

Bone matrix +0x20 is local-to-parent (root: world bind), while +0x60 stores inverse world bind. Translation occupies the fourth row in row-vector convention; transpose for column-vector tools. On a 19-bone example, inverseBind[i]×mainTM[i]=inverseBind[parent] (root identity) within 5×10⁻⁶. The older 738-MDB census also has locator, rigid-object and 239 skinning bones whose inverse bind differs from simple chained locals; these are exceptions requiring preservation, not proof the matrix order is wrong.

Inverse-bind-space bone bounding box formula

Bone box at +0xA0 half-size and +0xB0 center (w=1) encloses owned vertices after inverse-bind transform into that bone's space. For kind 3, include any model vertex with nonzero weight on the bone. For kind 1/2, use the mesh object having exactly the same bone name; when duplicated, choose whose vertex centroid is closest to the bind position. An unowned bone stores (0,0,0,1); kind 0 has no meaningful box. These construction rules are useful for exporters but require consistent bone/object name resolution.

Recomputed bone boxes match most stock values

Applying that box formula across the 804 OBJECT MDBs matched stored boxes in 98.6–100% of bones depending on kind. ktaro attributed residual discrepancies possibly to manually edited vertex data and proposed recomputing after geometry edits. This is a source-file match test, not proof that runtime frustum culling reads these boxes; the bounded flag +0x1A would be a relevant predicate to test.

Practical 256-bone claim is not an MDB format limit

A cited Ghidra estimate suggests roughly 256 bones in one draw/submesh due to GPU constant-buffer capacity, alongside an engine-side six-UV-channel limit. Stock surveyed maximum is 126 bones per model. Neither estimated cap is encoded as an MDB header maximum, and the source supplies no address or tested 256-bone case; classify it as unverified engine guidance, not a writer's strict format constraint.

Observed native vertex format codes and four influences

Parser codes: 1 = float4, 4 = float3, 7 = half4, 12 = float2, 21 = ubyte4, 919 = int4 (16 bytes; never seen in this corpus). Position/normal/binormal/tangent use float3 instead of half4 in 138 sampled files, so each file's declaration must drive decoding. TEXCOORD uses channels 0–3 here; BLENDWEIGHT float4 and BLENDINDICES ubyte4 appear only on channel 0, limiting the sampled skinning format to four influences. This is corpus evidence, not a universal engine prohibition on other attribute types.
