Overview

MDB is a model resource containing structural metadata, geometry streams and material relationships. The bytes must agree with the mesh's vertex declaration; animation and object collision add further bone and physics constraints.

Model part What it controls
Vertex declaration Attribute types, sizes and stride for every mesh buffer
Mesh indices and weights Geometry topology and skin binding
Material and sampler records Shader family, parameters and texture slots
Bones, bind pose and sockets Animation, attachments and related SHKT physics

Start at Models for the subject index. Use the detailed sections below for exact source-backed findings and generation differences.

Native material schema versus shader reflection

How to read and write native MDB materials explains the exact parameter sequence, sampler order, integer-bit parameter exceptions and why a reflected shader catalog must not be serialized directly as a material. For roughness and metallic formulas, see MDB shading parameters.

An MDB is a model resource used by Earth Defense Force. Its observable data can include name/bone/object relationships, meshes, vertex declarations and buffers, material records, shader identifiers and texture references. Those parts have to agree: a model is not just vertex positions with a shader name attached. We have strongest detailed structural examples from EDF5/EDF6 ordinary model assets, including buildings and props used in maps. These are not FieldRender/FMEP terrain formats.

Geometry and vertex declarations

Each mesh describes how the bytes in its vertex stream should be interpreted. The declaration supplies a semantic (such as POSITION, TEXCOORD or BLENDINDICES), a stored element type and a per-vertex layout. Do not infer a universal stride from the game version alone.

Observed declaration encodings in paired EDF5/EDF6 research:

Type Observed lane shape Bytes Common use
1 float32 × 4 16 BLENDWEIGHT and four-component lanes
4 float32 × 3 12 Three-component float lanes
7 float16 × 4 8 POSITION/NORMAL/TANGENT/BINORMAL profiles
12 float32 × 2 8 TEXCOORD
21 uint8 × 4 4 BLENDINDICES

Important correction: declaration type 1 is 16 bytes, not four. A parser using four bytes shifts all later elements and silently damages its view of the vertex buffer.

Meshes can carry multiple UV streams, including repeated TEXCOORD semantics in non-obvious order. Vertices may need to be duplicated at UV, tangent and normal seams when constructing a target mesh. In observed static EDF6 map-model profiles, 60-, 68- and 76-byte strides occur, sometimes including rigid blend weight/index channels for visually static assets. Those are observed profiles, not universal MDB requirements.

The studied exporter path uses 16-bit mesh indices. A mesh that exceeds that range needs rejection or a deliberate triangle-boundary split, rather than index truncation or an invented 32-bit variant. Sampled native EDF6 multi-mesh resources align each mesh vertex-buffer start to 16 bytes; this is a strong native-conformance practice, not proof that every misaligned MDB crashes.

Object names, bones and mesh relationships

Name, Bone, Object and Mesh records are connected rather than freely interchangeable. A source-to-source writer should preserve shared name identity, relative-offset conventions, object-to-bone links, bounds and skinning metadata. Some games or authoring utilities support ordinary static geometry without a visible character rig, but that does not justify discarding blend channels from every native static-model profile.

A reliable importer/exporter should parse the declaration and semantic relationships, preserve unknown records and shader ABI metadata where possible, and only regenerate fields it has a defensible interpretation for.

Materials: what is actually stored

A material is not fully described by a familiar PBR tuple of color/roughness/metallic. Native MDB material profiles can include:

  • An exact shader family, for example snd_BRDF_Map_Common, snd_BRDF_Map_Common_Clip, snd_BRDF_Map_Build_Basic_NC or older snd_Map_* families.
  • An ordered parameter list, where each entry has a name, type/size encoding and stored value bytes.
  • An ordered sampler list, with texture resource identities and filtering/addressing/LOD metadata.
  • Render metadata and a corresponding vertex/UV/tangent contract.

For example, observed EDF6 snd_BRDF_Map_Common material records use parameters diffuse, metallic, normal_amount, roughness, specular_color and specular_diffuse_blend, with sampler order albedo, normal, param_r_m_xxx_hr. Common_Clip adds alpha_clip. These are observations for named families, not a schema for all MDB shaders.

How do roughness and metallic work in MDB materials?

For the studied EDF6 snd_BRDF_Map_Common / param_r_m_* ordinary-model path, the packed texture modifies the scalar material parameters. In the observed family, G controls metallic and R controls roughness; an _hr packed texture also uses A to scale roughness:

float metallicValue = saturate(packed.g * material.metallic);
float roughnessValue = saturate(packed.r * material.roughness);
// If this is the _hr family:
roughnessValue = saturate(packed.r * packed.a * material.roughness);

For the studied Common/Water-like normal-map convention, X is reconstructed from R×A, Y from G, and Z from the remaining unit-normal length. This is why a standard RGB normal map or a plain Principled BSDF can disagree with the EDF material. These formulas are specific to the identified shader family: legacy reflect/spec materials, some character shaders and FieldRender terrain use different or incompletely recovered semantics.

See MDB shader parameters explained for normal decoding, specular_color, cutouts, light masks and the broader shader family caveats. The exact native profile tables give family-specific parameter order and type/size values.

Texture data and resource identity

An MDB can refer to logical texture identities, while texture payloads live in separate resource packaging such as RAB/DDS. The resource name, payload, filtering rules, sampler order and shader expectation have to agree. A working model may have editable MDB material bindings without forcing a rewrite of its geometry or collision.

What changes between EDF5 and EDF6?

Paired models show changes beyond a header version: tangent/binormal streams may be added, vertices split at seams, materials reauthored, samplers reordered, texture channels changed, and object/name responsibilities altered. There is no universal conversion rule of “write EDF6 version, rename the shader, keep everything else.” Nor is there one mandatory EDF6 vertex declaration order for every material.

A conversion tool must recognize supported source/target profiles, preserve semantic identities, and validate material ABI, shader, texture packing and required vertex lanes together. Native observations are stronger than plausible-looking imported previews.

Important boundaries

  • Ordinary MDB mesh materials are not FMEP/FieldRender terrain. The latter uses a different terrain-material and texture-array path.
  • _lod.mdb does not guarantee a specific LOD shader; some native LOD companions reuse normal material families.
  • A preserved unknown material can round-trip correctly even when a Blender/glTF-style preview is approximate.
  • A shader's register-level texture binding order need not equal its MDB material sampler-list order.

Source-tree cases and version rewrites are not full model parity

A historical paired-tree resource comparison reported 218 position-only placement records (T2) that were byte-identical in its EDF5/EDF6 samples, while the displayed tree size remained a separate open question in that test. That finite record equivalence cannot establish general MDB mesh/material parity or native render-size rules. Likewise, an older converter upgrading a measured MDB version and rewriting fields was a conversion attempt, not proof that every model, skeleton and material family is equivalent across the games.

When debugging a correct MDB that still crashes, check the resource type registration first: an earlier byte-exact in-memory MDB was fed into the wrong .trb handler. See typed-dispatch failure analysis.
