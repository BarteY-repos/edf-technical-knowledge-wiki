BVM custom-call and factor reference: decoded engine actions

UniversalMissions & ScriptingScriptingEDF 5EDF 6
Technical reference · Scoped: native source/target exact-pair semantic mapping

At a glance

What this page answers: Numeric BVM custom-call IDs are not VM opcodes, and a named EDF6 AngelScript action is not automatically a safe replacement for every original call.

How to read it: Use this table to decode the intended engine effect while reconstructing stack arguments, factor conditions, object ownership and timing.

Evidence boundary: Mappings come from an examined shipping corpus and can be build- or class-specific. An uncertain binding stays uncertain even when its target field looks similar.

The EDF5 mission VM stores numeric custom-call identifiers; EDF6 mission authoring exposes many of the same effects as named AngelScript operations. The tables below are a reverse-engineered reference for the inspected EDF5 shipping mission corpus, not a guarantee that every name can be called on every object type or that each conversion has been runtime-certified.

An instruction such as AC D0 07 means the cuscall0 instruction with a little-endian custom-call ID 0x07D0 (2000). The call ID does not change the VM opcode or its operand width. A correct converter must reconstruct stack ownership, arguments, control flow and timing before mapping an API.

Source VM: pause, object removal and vehicle setup

These six entries have source-stack arity and target API signature independently checked for the inspected EDF5 BVM corpus. Call bank and receiver ownership matter, rather than just the numeric ID:

Source BVM call Source-stack arguments Verified target-side signature Important constraint
cuscall0 52 1 void SetEnablePause(bool) Use source boolean value, not forced true
cuscall0 910 0 void DeleteMob() No invented object argument
cuscall3 1000 1 void SetMoveArea(string) Different call bank; one area string
cuscall0 1024 1 void RideVehicle(Object) Vehicle argument is an object
cuscall0 1027 1 void SetupVehicle(Object) Setup is distinct from RideVehicle
cuscall0 1028 2 Object& Vehicle_SetRideEnable(bool) Object receiver is below the bool on the source VM stack; target is a method, not a global function

These are source/API signature and stack-contract observations, not proof that every gameplay path using each call has been separately tested in EDF6. They do not justify changing mappings for unrelated call IDs 5020, 5150, 1301 or 1100.

Scalar group tokens are not object references

AddGroupObjectBegin, GetGroupObjectCount and the group-count/encounter factors work with integer group IDs or counts, not automatically with AngelScript Object handles. An exact 141-mission source audit corrected 22 declarations in 12 scripts plus one IsAiMoveEnd(...) == 1 comparison in M004, giving 13 affected scripts. See group IDs, counts and bool domains for examples and the verified limits of this inference.

VM scaffolding is not gameplay scripting

The inspected BVM stream also uses cuscall0 9 and cuscall1 1/2 for VM progress/resume or coroutine framing. The former is not Wait(seconds) in this source context. Treat them as control-flow scaffolding, not invented gameplay calls. A separate, narrowly verified pattern containing 9000 before an event registration can represent an in-body wait; the context determines which rule applies.

Important: Group creation operations that consume arguments and have side effects must be emitted in their original order even if an AngelScript helper returns an object. Retaining the target's return expression on the reconstructed source VM stack caused out-of-order enemy groups in the inspected port. Reconstructing the source stack effect and side-effect timing is essential.

How far has this mapping been verified?

The R37 inspected source corpus comprised 141 shipping missions with an additional four-mission stress set. Its source/target correspondence gates are static or exact-pair comparisons, not automatically fresh gameplay tests. A subset of mappings such as the wall-spawner 2001 has direct runtime-positive evidence. 3450 is specifically not safe for generic AngelScript emission: it writes to Object +0x2E0 (EDF5) or +0x470 (EDF6), but the equivalent callable target setter was not demonstrated. Do not substitute 3024 or 3150. The accepted 3450-OFF route is a documented, mission-specific fidelity waiver, not proof the radius write was reproduced or an active blocker to publication.

Use this table alongside BVM bytecode and operands and event registration/scheduling. The IDs are grounded in inspected game builds and paired scripts, not a complete registry of every possible native call.
