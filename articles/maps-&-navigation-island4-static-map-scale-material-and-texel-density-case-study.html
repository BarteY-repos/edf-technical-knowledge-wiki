Island4 static-map scale, material and texel-density case study

EDF 6Maps & NavigationMaps
Source-backed research / case study · Runtime-positive / Reconciled

Evidence level: Runtime-positive control lineage + exact byte-identity editor reproduction + offline asset/texel-density audits. This is a case study, not a universal terrain scaling law.

What made Island4 a map

The source visual asset Island4(2).fbx is one FBX mesh object with 10 connected closed components and 109,658 triangles. Its original bounds are only about 10.33 × 5.86 × 11.75 m. A separate physics FBX is about 9.72 × 5.14 × 11.19 m.

This proves an important authoring distinction: object count does not decide whether something can be the primary playable map geometry. A complete custom map may technically use one root static render resource. Map semantics come from the whole world contract — geometry, placement, collision, environment/weather, spawn integration, navigation and mission usage — not from having a large number of scene objects.

The native FieldRender/FMB route is a different terrain backend, not a prerequisite for treating a root static MDB as playable world geometry.

Scale is an explicit authoring decision

The small source asset was not silently interpreted as EDF-scale terrain. The runtime-positive R4C control freezes:

scale       = [20,20,20]
bake anchor = top_center_aabb
position    = [400.0, 108.35, -134.2688751220703]
rotation    = [0,0,0]
UV mode     = preserve_obj

At x20 the runtime MDB bounds are about 206.6 × 117.1 × 234.9 m.

Implementation rule: treat map extent/scale as project semantics. Do not infer intended final world size from the source file alone, and do not change scale while debugging unrelated material/collision issues.

Strongest editor-path proof: byte-identical R4C family

The v0.3 editor/frontend assembled a fresh semantic Island4 project from the authoritative FBX/DDS inputs and reproduced the complete directly runtime-positive R4C five-file family byte-for-byte.

Therefore the static editor path itself does not introduce a new runtime variable for that exact project shape. Another runtime test is only meaningful when a new semantic delta is introduced, such as material ABI, collision source or another backend.

This is a stronger statement than “the editor builds files”: it is byte identity to the already runtime-positive map package.

Material response and texture density are different problems

R4C was playable/textured but looked too shiny/chrome-like. The source packed texture is artist-defined:

R = roughness
G = metallic
B = AO

The old control material interpreted the packed channels through a reflect/spec-style contract. That makes the shiny response a material-ABI mismatch, not evidence that the DDS is missing.

Separately, the source uses one 4096² baked atlas whose UVs are preserved after x20 scaling. The R7 runtime-MDB audit measured:

  • area-weighted mean density ≈ 9.25 px/m;
  • unweighted median ≈ 18.44 px/m;
  • over 52.9% of surface area below 5 px/m;
  • strong directional anisotropy on substantial parts of the mesh.

So even a corrected R/M/O shader cannot by itself restore close-range texture sharpness. The likely production direction is a macro/base atlas plus tiled/world-space detail (or another multi-scale material), not blind global UV multiplication.

Why blind UV scaling is unsafe

The texel-density audit shows extreme anisotropy in some triangles and meshes. Some areas are pinched or intentionally stretched. Multiplying all UVs would:

  • change authored seams/atlas layout;
  • repeat non-seamless baked regions;
  • hide the distinction between genuine low density and bad directional UVs;
  • mix a texture-detail fix into the material-response experiment.

Keep the fixed R4C geometry/scale/placement as the control when testing shader ABI changes.

Collision is a third independent axis

Early runtime observations included partial sinking on side surfaces. Later R4C/static-map work established a runtime-positive control, while dedicated simplified physics remained a separate authoring option.

Do not use material or texel-density changes to diagnose collision, and do not infer that one render-mesh collision result is the general production simplification strategy.

FMEP remains a separate terrain backend

The later product interpretation is:

static MDB backend = qualified/current path for textured authored terrain/objects
FMEP/FieldRender   = separate native-terrain/streaming/material-layer branch

FMEP research is valuable for native terrain semantics, spatial partitioning and future layered/scatter systems, but it is not required before an authored static-MDB map can be playable.

Source authority boundaries

Authoritative visual source for this case: Island4(2).fbx; the earlier Island4.fbx had artist-reported backward normals and is not the source authority. The exact x20 R4C project freezes geometry, placement, scale and texture identities while material work proceeds.

This case study should therefore be used as a regression/control model for separating map scale, material ABI, texture density, collision and backend choice, not as a universal recommendation to scale every imported map by 20.

The distinct experimental FieldRender branch

The runtime-positive x20 R4C Island4 control used the static MDB route. A separate custom FMEP branch later reached an EDF+0x1170B7 missing-external-FMB lookup and then, after resource registration, a distinct EDF+0x19026A MAC directory-name fault. A field-relative MARC v5 pointer defect was corrected offline, with subsequent FMEP gameplay still unqualified. No result here upgrades the experimental FMEP path to the runtime-positive status of the static map. See native FMEP DDS, leaves and registration.

Pixel-shader cross-check against the shiny static-MDB control

The bounded RenderDoc comparison provides exact compiled pixel-shader resource strings and hashes for the ordinary static-MDB control versus R/M/O sample shader lanes. Its modified-runtime R6B MDB0 2,048-byte prefix matches the expected model byte-for-byte, excluding a stale early model payload as the explanation for that run. R5B/R5C reduced shine but were not faithful, R6A/R6B did not fix it, and the proposed artist-side snd_BRDF_Common_Basic path remained runtime pending. Do not infer that FMEP uses the same shader ABI.
