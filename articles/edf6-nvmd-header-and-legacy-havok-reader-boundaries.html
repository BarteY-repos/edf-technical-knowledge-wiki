EDF6 NVMD header and legacy Havok reader: confirmed formats and open boundaries

EDF 6Game technical referencesNavigation / compatibility
Technical reference · Source analysis only (unless a source fact is contributor-verified); no new EDF runtime test

For EDF6, source navigation companions *.NAVMESH.NVMD and *.NAVMESH_H.NVMD begin with bytes 44 4D 56 4E, the little-endian representation of the four-character value NVMD, followed by version 0x130. The native code checks the identifier and version. The remaining NVMD structure was not analyzed in the source chapter; treating its later bytes as decoded path polygons or point indices would be unsupported.

The game's DLL also contains a legacy Havok binary tagfile reader named hkSerialize::TagfileReadFormat2014 and many old hkp* classes alongside the modern hknp* system. This is valuable compatibility evidence, but recognition of the old serialization is not proof that every old HKT or SHKT is usable by every EDF6 subsystem. A map collision loader and a character ragdoll path can enforce different root-type, conversion and solver requirements.

This particularly matters for EDF4.1/EDF5 assets retained within later archives. A file's extension, a successful read of its old tagfile header and an actual functioning Havok body in-game are three distinct gates. The source's older experiment with RAGDOLL_TESTVEHICLE401.HKT is explicitly documented as unresolved for that isolated reader test. Later subsystem-specific evidence must be consulted instead of extrapolating.

Source: edf6/havok-format.md, nvmd-header, legacy-tagfile-reader. Unresolved NVMD fields remain marked unknown.
