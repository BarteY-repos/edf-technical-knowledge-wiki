EDF6 Packet Size, EOS Transport and Native RUDP: Scope Reconciliation

EDF 6Cross-source ReconciliationNetworking
Technical reference · Cross-source editorial reconciliation; no new runtime tests

Current conclusion

The EOS P2P datagram limit, a packet-controller defensive size check, and the actual maximum built by a particular shipping sender are three different quantities. They must not be used interchangeably. In the qualified native class-4/class-5 application-reliable sender, the original research bounded the reachable physical aggregate to 1164 bytes, below the reported 1170-byte EOS limit. A separate community analysis identifies a 1400-byte rejection check. That check does not establish that ordinary, legitimate native traffic reaches 1400 bytes.

This is a reconciliation of separately contributed, build-scoped static/native analyses, not a new live packet capture. Third-party mods may build larger packets or alter flush/fragmentation behavior; claims about those paths must be tested in those paths.

The three size layers

Layer Reported size Meaning and applicability
Physical EOS P2P packet 1170 B Reported EOS transmission cap in the Knowledge Hub; see community claim
Native application's defensive check 1400 B Guard cited at 12D0BE6 in the contributed analysis. A higher guard is not an observed payload size; see source claim
Qualified native source payload 1144 B Builder limit in the previous native RUDP analysis
Qualified native retained record 1156 B Application-layer reliable wrapping, same audited path
Qualified first physical aggregate 1164 B Transport envelope in the audited native path, 6 B below reported EOS cap
Community per-peer builder flush trigger 1100 B Datagram builder flush threshold; not maximum total datagram size; community record description

Implementation rule: do not apply the general statement "records between 1170 and 1400 are routinely resent to disconnection" to unmodified class-4/class-5 shipping sends. It is a plausible out-of-envelope scenario, e.g. if another builder, injected plugin, oversized extension or altered call path can actually produce such a record. Prove reachability and exact build before treating it as a cause.

Physical transport is not application reliability

The Knowledge Hub's datagram description says the controller calls EOS with EOS_PR_UnreliableUnordered. This is compatible with native class-4/class-5 application-layer retained RUDP. SendReliable adds a record with 0x1200 envelope and sequence; acknowledgements (0x1300) retire pending records, with duplicate suppression at receiver. It does not turn physical EOS delivery into a reliable mode.

The routes have separate semantics:

Game route Outer class Delivery at application level
Ordinary player/scene state 0x3300 class 3 Mode 1: latest snapshot, no retained reliable message
Immediate gameplay events, DamageObject 0x3400 class 4 Mode 0: retained Sandlot RUDP
Normal NetworkBullet selectors 0/1/2 0x3500 class 5 Mode 0: retained Sandlot RUDP in audited native senders

See player-state lanes and native event registry. Event protocol ID 1 (DamageObject) is inside class 4; it is not a substitute for its outer 0x3400 class identity. Retrying packets can only recover data actually serialized, not missing projectile RNG, movement or detonation state.

Retry counts and disconnect

The community note describes six tries for a reliable record, whereas a third-party source refers to eight over roughly 26 seconds. The supplied records did not reconcile those counts. The earlier native analysis independently derives about 25.9 s cumulative no-ACK for its measured EDF6 retry/fault progression (700 ms, then +1000 ms after each resend, final interval guard 7000 ms). These statements cannot be normalized to an unqualified "six" or "eight" send-count policy: attempts, resends, retry interval checks and higher-level peer faults may count different events.

Current rule: use the native qualified state-machine and cumulative timing for that exact sender/build, but retain the contributor's count discrepancy as unresolved pending an instrumented per-peer trace. RemoteConnectionClosed replacing a physical Link does not destroy the logical ReliableMgr; a stale READY bit can obstruct INITIAL recovery. See reconnect lifecycle.

Timing: 90 ms is not proof of a permanent phase lock

The contributor locates a 90 ms controller flush timer (source) and separately proposes that a six-frame transform rhythm can phase-lock with flushes at 60 FPS (unverified claim). The previously audited player-state reconstruction describes a transform bit approximately every six network updates and a staged receive/apply path. The unit of cadence matters.

A period similarity alone does not demonstrate indefinite starvation; the observed remote-player drift and phase-lock mechanism remain contributor-reported and unverified for the qualified native path. Verify the exact update counters, flush timebase, queued state overwrite, send events and receiver apply gate before making a root-cause claim.

Practical investigation

  1. Record build hashes and whether the reproducer uses stock game, EDF6Coop, MultiSlot or other hooks.
  2. Log actual built physical datagram lengths, reliable record types and the sending source path, not just the defensive guard's constant.
  3. Separate EOS transport failures, reliable records pending ACK and class-3 periodic state.
  4. Capture the same actor/object across send, wire/receive, pending queue and apply gate; correlate with time and peer ID.
  5. For oversized candidates, prove that normal shipping producer can reach the candidate byte count. For persistent drift, distinguish lost snapshots from repeat suppression or never-applied batches.
