Mission LIST — previews and resource identity

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Technical reference · Runtime-observed and case-scoped

Reference overview

An EDF6 mission preview has three separate identities: the mission LIST.SGO row, its localized title/brief, and the named DDS selected from the correct runtime image archive. Correcting one does not automatically correct the others.

Contract Studied EDF6 target profile
Mission rows OFFLINE/ONLINE target order must remain compatible with save/progression identity
Thumbnail key LIST field 2; replace / with _, append .dds
Runtime images Base MISSIONLIST.OFFLINE.IMAGE.RAB and MISSIONLIST.ONLINE.IMAGE.RAB
Pack-local IMAGE.RAB Not authoritative for the audited runtime loader

See Missions and Mission thumbnails. The historical mismatch below is a case study, not the current desired metadata arrangement.

Historical OFFLINE/ONLINE list mismatches

The 139-unique-mission OFFLINE/ONLINE mismatch above is a historical deployment observation, not the corrected target schema. The later maintained MissionPack03 resource has 112 rows on both OFFLINE and ONLINE, with a shared ordinal sequence and matching companion TXT/image resources. For the ordinary underground flags=40 behavior and the different special 0x200 condition bit, see Underground mission flags and WeaponCondition.

A custom MissionPack may contain a valid LIST.SGO and still show missing thumbnails or incorrect localized titles. Mission ordering, images, text, and gameplay logic are separate resources that must agree.

A shared-name image archive can be authoritative

In one runtime-traced EDF5-content deployment on EDF6, the game requested MISSIONLIST.OFFLINE.IMAGE.RAB, not each pack's separately named IMAGE.RAB. Correct per-pack image payloads alone did not supply the resource the game requested.

The successful historical override used the shared-name path:

Mods/MISSION/MISSIONLIST.OFFLINE.IMAGE.RAB

The tested additive archive retained 147 native entries and added 139 EDF5-related entries, with a corresponding ONLINE resource. That is one observed loader/configuration; it is not proof that every mod loader or game revision uses the same lookup precedence.

Three linked tables, three different concerns

Resource What it provides Why archive integrity is not enough
LIST.SGO Order, progression and metadata for missions An inserted/reordered row can change display associations
Localized TXT (SGO or DSGO by profile) Titles and descriptions TXT's serialized form is not universal across deployment roles
MISSIONLIST.*.IMAGE.RAB Preview-image payloads The loader may request a shared name rather than a pack-local one
MISSION.AC / BVM Mission actions and events Menu success does not imply the script will execute
CONFIG / pack registration Namespacing and selection An archive can exist yet never be selected

Later R29 evidence settles the studied EDF6 mission-list association: derive the named archive entry from LIST field2, replacing / with _ and appending .dds. This supersedes the older unresolved name-versus-ordinal hypothesis for that profile. It remains necessary to update field2 when constructing new missions and to audit actual ONLINE/OFFLINE base IMAGE.RAB lookup; see the exact format and tested scope.

Historical 112/111 list ordering is not the later 112/112 save contract

An exact R41 audit of an EDF5-content converted MissionPack03 recorded 112 OFFLINE rows (M000 plus the studied ONLINE sequence) and 111 ONLINE rows (M000 omitted, M082/M083 retained). That describes the audited converted LISTs, not an independently proven native EDF5 OFFLINE binary layout. A later EDF6-compatible metadata scheme deliberately uses 112/112 shared ordinal rows to keep progress/save identity consistent. See source-vs-converted list contract.

Online and offline lists are not interchangeable

A separate observed deployment had the MISSIONPACK03 ONLINE LIST.SGO byte-identical to its OFFLINE version. This exposed only 139 unique shipping missions, omitted M082 and M083 from the online list and exposed tutorial M000 online. The mistake was in list generation/deployment, not in what the mission transpiler should support. Companion JSON lists were stale; the loaded binary LIST was the evidence.

How to diagnose a missing or wrong image

  1. Identify the actual archive filename opened by the running game using file-access evidence where needed.
  2. Verify the selected archive has the right named entry and decoded image payload.
  3. Check LIST order, TXT titles/descriptions and thumbnail relationship together.
  4. Compare ONLINE and OFFLINE binary LISTs intentionally rather than assuming they match.
  5. Check script/mission startup separately from menu display.

Related: RAB/MRAB named-entry layout, mission metadata and shared progress.

Evidence: recorded runtime file-access observation and subsequent mission-list binary comparison in the retained R6 corpus. Statements are case-scoped, not general assertions about all installations.

For the distinction between mission-list row visibility and saved progress, and between weapon ownership and star bytes, see mission selection and weapon-record states.

When two mods change the same mission-image archive, entry-wise SSA merging can retain both named payloads. LIST-to-image association is cross-file-coupled, but the R29-supported profile now has an explicit field2 name rule; archive-level merging must check that each changed LIST field2 resolves to the correct named entry. See RAB/MRAB entry merging.
