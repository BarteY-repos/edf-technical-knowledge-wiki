Cross-game conversion and compatibility

ConversionDocumentationStartEDF 4.1EDF 5EDF 6
Reference index · Navigation index; linked articles carry technical evidence

Cross-generation compatibility is a matter of matching runtime semantics, not just rewriting headers. An old resource may parse correctly while having different collision, shader, animation, script or asset-ownership behavior in the target engine.

Start with the boundaries

  • Three-generation format/version matrix and what actually changes between EDF5 and EDF6.
  • Format contracts and non-rules, MDB native conversion evidence, and CAS/CANM animation differences.
  • EDF5 BVM → EDF6 AngelScript translation and full 141-mission static value-flow audit.

Native world and gameplay are separate tests

  • Source EDF4.1 navigation versus target EDF6; EDFROOM collision solid wall versus NPC targeting.
  • EDF4.1 mission objects and mapped target classes, EDF4.1 vehicle role/asset differences and EDF4.1 Earth Eater layered bodies.
  • ED5/6 DLC1/DLC2 29-mission compatibility matrix and EDF5 source BVM versus EDF6-side legacy BVM identity.

Evidence strength

  • Game runtime, same exact context: strongest evidence for actual behavior.
  • Exact source-file/binary comparison: strongest evidence for retained bytes, structures, names and parameters; not a gameplay pass.
  • Static source compiler or offline tests: can prove a reproducible representation and build but not that the target game accepts its intended behavior.
  • Community technical notes: useful references with original author/source attribution, requiring build/context boundaries.

Where evidence stops, retain the uncertainty instead of inventing translation rules. The unresolved game questions are listed in OPEN_QUESTIONS.md in the archive.
