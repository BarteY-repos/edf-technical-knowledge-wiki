EDF6 renderer presentation versus fixed gameplay updates

EDF 6Performance & 120 FPSPerformance
Technical reference · Exact-build binary analysis plus bounded runtime camera measurements; full 120 FPS not established

EDF6 has a fixed gameplay-update clock, a main-loop/render-submission cadence and a DXGI presentation clock. Removing the wait in the stock 60 FPS limiter can increase loop and Present frequency without producing a new world pose on every display frame. A correct high-FPS presentation path must preserve authoritative gameplay timing while publishing fresh visual state from known, correctly owned simulation snapshots.

Build scope: the addresses below are module-relative RVAs in the studied Windows EDF.dll, PE timestamp 0x678CCB46, SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916. They are not universal offsets for other game builds. Labels such as “render-only candidate” describe analyzed data flow, not a proven complete mod.

Game loop and native limiter

EDF.dll RVA / fieldObserved role
0x11A2E90Main loop containing the fixed-step count and presentation work.
0x11DAE60Period counter: whole 1/60-second intervals elapsed since the stored QPC boundary; advances that boundary by consumed periods.
0x2139D10, 0x2139D18Related QPC timing state; 0x2139D18 is the fixed-period boundary used by the counter.
0x11A2F4F, 0x11A2F6BTwo calls to the period counter, before and inside the wait/poll loop.
0x11A2F65, 0x11A2F74Sleep call and conditional backward branch in the limiter. Existing FPSUnlimiter approaches remove these waits; this alone does not interpolate animation.
0x11A2F76, 0x11A2F80Clamp the number of catch-up update steps to at most three; excess elapsed periods are not simulated indefinitely.
0x11A3006Scene virtual +8 update dispatch receives the selected fixed-step count.

A loop that wakes early can therefore issue a new Present with zero new fixed updates. Repeated renders, fixed-cadence character poses and presentation stalls must be measured separately. Changing the counter to run physics/AI twice as often would also affect reloads, collision, weapon cadence, missions and online semantics; that is not a render-only FPS unlock.

Camera presentation path

RVA / object fieldTechnical role
0xFAF20Studied normal CharacterGhost camera solver. 0xFB9F0 and unidentified or special camera paths are separate and were left native.
CharacterGhost+0x52CGeneration/iteration marker used to identify fixed-simulation camera endpoints, not itself a presentation-time clock.
0x66CD0, 0x2139D18Elapsed-QPC helper and fixed boundary in the same clock domain; support a fractional presentation phase between fixed endpoints.
SceneCamera+0x220..+0x250Rigid affine camera matrix data temporarily replaced for synchronous render preparation, then restored; rotation uses shortest-path quaternion interpolation and translation linear interpolation.
0x118DFF0Synchronous camera/render-preparation consumer that reads the temporary presentation matrix.
0x11E3692 → 0x112F590Traced downstream type-0 view/world-matrix binding, leading into world renderer traversal.

Runtime observation: during a moving normal type-0 camera test, telemetry recorded 90.306 unique camera states/s, 89.728 Presents/s and 59.922 fixed updates/s. This proves a distinct high-rate camera presentation stream on the tested setup. It does not establish smooth 120-Hz actors or VFX; visible stutter remained.

World visibility and graphics-fence ownership

RVA / recordObserved role or constraint
0x11B6AA0Main world/type-0 visibility packet producer (tag 0).
0x11B6F90Auxiliary type-2 visibility packet producer (tag 2), within two persistent entries of stride 0x150, total 0x2A0; studied special mask 0x40000000.
0x11B5A70, 0x11B5B30Large graphics-worker state/visibility callback families. The first maps to measured Umbra Camera::processVisibility work in the profiler study.
0x1120B90, 0x1127000Deferred resource release/destruction and multi-resource/state-update callback families; their pending counts alone are not execution cost.
0x11A305A → 0x111CC20Active main-loop graphics-worker completion fence/drain.
0x11A305F → 0x119FB40Immediately subsequent release of list-owned objects/nodes; this lifetime dependency forbids assuming the fence can simply be removed.

A reduced-cadence type-2 auxiliary-visibility treatment caused black-surface flicker and delayed/coarse shadows in the tested composition. A separate skip-resolve path could freeze level loading. Neither is a safe generic speedup. A graphics worker processing a queued job must use that job's captured presentation generation; a global g_currentSimulationTicks sampled later by an asynchronous worker can refer to a different frame. A shared PresentationEpoch remains a design hypothesis, not completed runtime evidence. See Umbra measurements and the rejected occlusion-disable result.

Actors, animation and other visual clocks

RVA / fieldSource-verified data flow
HumanBase+0x860Embedded AnimationModel in the examined human actor path.
AnimationModel+0x482Mode branch at 0x6C2C44: zero selects the normal skin helper; nonzero selects a separate native path. No direct nonzero initializer was found, but reachability is not disproved.
0x1100F10, 0x11009A0Draw-pose matrix publication and primary skin-palette construction; the skin call is reachable from 0x6C2C8A with other auxiliary callsites.
0x1103EC2 → 0x113F860 → 0x113D240Normal actor-root matrix selection, 64-byte constant-buffer source and D3D11 UpdateSubresource dispatch (device-context vtable +0x180).
0x1103DA0CPU→GPU path binds the selected actor constant buffer to VS slot 1 (device-context vtable +0x38), followed by the normal indexed-draw path.
0x16CC2ELeafRenderer wind-time parameter publication; a possible render-phase output independent of fixed foliage simulation.
0x1198E33Queued standard XGL g_xgl_time publication; the authoritative game::xgs::System shader clock remains fixed-tick based.
0x2D7150, 0x2D8A80, 0x2DB170, 0x2DE1C0Identified secondary Fog/Dust/Rain/Snow render-vtable family, separate from fixed weather simulation.
0x287B70, 0x26A570Studied projectile visual-render vtable consumers. In a separate Rocket/Missile core the visual interface at +0xE90 reads prior positions +0x1340/+0x1350; the authoritative current position remains +0x90.

The normal AnimationModel CPU path was traced from its selected descriptor through buffer upload and draw, without finding another downstream CPU-side fixed-root latch. This is an exact-binary static finding, not a runtime demonstration of smooth character movement. Particle, trail, ribbon, weather, projectile, foliage and shader-time interpolation candidates similarly have source/binary boundaries, but do not inherit the camera's successful runtime qualification. Do not advance projectile trajectories, AI, physics or collision to achieve visual interpolation.

Evidence and open boundaries

SystemCurrent supported conclusion
Native 60-Hz step/wait logicExact-build static analysis; limiter wait removal alone is insufficient.
Normal type-0 cameraMeasured greater-than-60 unique state cadence with approximately 60-Hz fixed gameplay; subjective stutter not eliminated.
Actor root/skin/constant-buffer pathCPU/GPU submission chain mapped offline; integrated high-rate visible actor animation not runtime-confirmed.
Foliage, shader time, VFX and projectile visualsSeparate exact-build candidates; no general all-domain runtime pass.
Umbra/graphics-worker throughputMeasured scene-specific cost and negative shortcuts; not a universal graphics-fence or occlusion fix.
Multiplayer and other buildsNo demonstrated online-safe full 120-unique-FPS mode; native DXGI measurements must not be substituted for DXVK behavior.

More Presents do not prove more distinct poses. Meaningful high-FPS measurements separately count fixed updates, Present calls, unique camera and actor matrices, visibility submissions, skin builds and fence stalls. Input fixes must also preserve the native Fencer, vehicle, Air Raider, weapon, zoom and network semantics instead of treating their deliberate response curves as sampling bugs.
