EDF4.1 Deiroi landing in EDF6 — null-world raycasts and state transitions

ConversionCross-game ConversionCollision & PhysicsEDF 4.1EDF 6
Technical reference · Exact-build source/engine-static cause and historical M412 crash, no fresh game test

The symptom depends on how the mission spawns the enemy

The studied EDF4.1 mission M412 creates Deiroi units in the air using generators on the UfoMother401 carrier. When those source actors are passed to the examined EDF6 Deiroi class, they can reach an airborne/falling state that native EDF6 missions in this study did not exercise. The retained exact-build analysis identified a crash in that state even without the EDF4.1 compatibility plugin.

The crashing call constructs a ray from the unit's previous position to its current position, then invokes an older Havok-world raycast routine with a null world pointer (xor ecx, ecx at the studied call site). The callee assumes the world exists and dereferences world + 0xC0; the program faults before the enemy can transition to standing.

What the caller actually expects back

The falling-state caller examines a ray result structure. The important fields in this studied ABI are:

Field Meaning for the falling-state caller
result + 0x10 Float hit fraction along previous→current ray
result + 0x50 Non-null hit marker / hit object, checked before landing transition

The source-only bridge checks whether a valid old-world object was actually supplied. When present, it preserves the original raycast. Only when the world pointer is null does it call the EDF6 map-ground ray routine with the same endpoints. If a hit is found, it computes a fraction clamped to [0,1], writes the expected fields and permits the native caller to enter its landing state. If no hit is found, it leaves the caller's initialized “no hit” state alone.

This is not a general Havok raycast replacement, and it is not a new collision mesh or navigation repair. It is an exact call-site compatibility adaptation for a state that older mission scripts expose in a newer engine. The code refuses to patch when exact instruction bytes differ from those expected for the studied DLL.

Lessons for porting enemy state machines

  1. A native-class update may contain a broken or unexercised substate; matching the class is not proof that an imported spawn path is safe.
  2. Reproduce the state transition (airborne→falling→grounded), not merely the enemy's initial position.
  3. Use the same ray endpoints and reproduce the exact result contract expected by the caller; a boolean hit alone may not suffice.
  4. Verify the target object's pointer/ABI and keep the replacement scoped to the failing state and build.
  5. Distinguish historical observed game crash, exact-build code analysis, a source-level corrective implementation, and a subsequent in-game confirmation. The last is not supplied by this wiki release.

Sources: EDF4.1 R10 HF4 R9 components/compatibility/src/edf41deiroi.cpp and its referenced M412/UfoMother401 investigation. The cited addresses belong only to the investigated EDF6.dll build.
