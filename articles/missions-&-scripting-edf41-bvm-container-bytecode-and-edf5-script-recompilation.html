EDF4.1 BVM: binary instruction grammar and exact EDF5-script recompilation

ConversionMissions & ScriptingScriptingEDF 4.1EDF 5EDF 6
Technical reference · Retained R9 converter implementation and historic paired-corpus assertions; no new native round-trip test

The EDF4.1 MISSION.BVM / BEFORE.BVM container includes globals, a typed-function table, executable bytecode and UTF-16LE strings. A retained, source-backed converter can rebuild these scripts into the form used by the EDF5 EDF4.1 mission archive and ultimately by an EDF6 compatibility runtime. This is a separate EDF4.1→EDF5 BVM stage from the EDF5→EDF6 BVM→AngelScript transpiler; do not conflate the two sets of calls or source authorities.

Exact BVM envelope

The examined files use little-endian words and this layout:

Offset Field Known contract
0x00 Magic BVM (including trailing space)
0x04 Header bytes 0x50
0x10 Version 0x01150138
0x18 / 0x1C Global count / global-name table 4-byte name pointer per global
0x20 / 0x24 Function count / table 16-byte rows; call-stub offset, name offset, parameter-type offset and packed signature
0x28 / 0x2C VM stack capacities Both 0x200 in the studied profile
0x30 Initializer entry After the function table
0x34 Function-code base Offsets for call stubs are relative to this base
0x38 String-pool start Immediately after code
0x3C Script name offset String name such as Mission or Before
0x4C File size Header-asserted 16-aligned total; padding 0xBA

Strings are UTF-16LE, null-terminated, with literal occurrences deduplicated in the source compiler's first-use order before global and function names. The parameter type codes in the measured table include 0x01 int, 0x02 float and 0x03 string. The observed high signature flag 0x100 indicates a returned value left below the return address for two shipped helper patterns; unknown flags are rejected rather than guessed.

VM instruction encoding and branch sizes

The low six bits of each first byte are the opcode. The top two bits select the operand width: 0, 1, 2 or 4 bytes. Certain typed opcodes have one additional trailing type byte. Signed operand interpretation applies to the studied push, relative branch and call opcodes; other immediates are unsigned. Four native opcode families 0x2C..0x2F use IDs local to each native table — a raw ID is not an API identity without its table.

Function rows point to call/end stubs at the end of executable code; the bodies appear in table order and begin after a three-instruction epilogue (pushl 0; fp+ N; ret). A parser must resolve branch and call targets against real instruction boundaries and reject a jump outside its own function. The retained generator reproduces the historical compiler's variable branch sizing: it first reserves four bytes for every branch/call, then resolves smaller operands forward rather than running an ordinary repeated relaxation pass. That distinction matters for byte-exact output even when both generated programs behave the same.

The source documents parse/build byte identity over 270 EDF4.1 base and 55 DLC BVM files. It separately reports that the EDF5 compiler's transformation of 135 paired EDF4.1 base scripts reproduced EDF5 bytes. These are retained corpus assertions; this release did not obtain/re-run the original game archive comparisons.

EDF4.1 → EDF5 source recompile is a semantic transformation

Beyond opcode renumbering, the paired source compiler has rules affecting mission behavior:

  • EDF5's common helper functions replace the EDF4.1 library before Main; numbered FuncNNN event handlers become sequential Func_1, Func_2, etc., including their counter names.
  • Four EDF5 g_sergent slots (main plus three followers) are inserted after the handler counters and initialized to -1. The converter rebases all referenced user globals, including values passed through the VM's indirect global-store pattern.
  • RegisterEvent receives an extra argument; for the clearing handler the extra value is 100 rather than the usual 0. Handlers that have the original run-once guard gain a progress update and an additional mission still running / clear-state gate.
  • Main preloads three EDF5 result screens following the original setup native, and unconditional jump-to-jump chains are threaded.
  • Native opcodes are mapped using an explicit table; a script-native from EDF4.1 that has no compatible EDF5/EDF6 binding is rejected rather than emitted as a wrong call.

For DLC calls absent from the base-game pairs, the source also records engine-dispatcher mappings. The EDF4.1 table-1 3000 SetEncountReportRadius has no native EDF5/EDF6 script binding in this path; the studied compatibility plugin supplies a distinct table-1 ID 3003. This is not EDF5's separately documented cuscall0 3450 SetAiSearchRadius, whose omission from the EDF5 port was consciously accepted. Identical English ideas about a “radius” do not make those two ABI calls interchangeable.

What authors should check

Validate the header, every indirect offset, each string, all function stubs, function-level branch targets and type bytes. Compare raw BVM and EDF5-recompiled BVM separately from later AngelScript AC. Preserve the original event graph and source resource-path rewrite policy. Do not infer that a successful static source conversion proves mission completion under an EDF6 runtime.

Six original EDF4.1 BVM missions: native event and creation-call census

A separately retained set of six decompiled original EDF4.1 MISSION.BVM scripts (M001–M004, M012, M014) allows a bounded source-level comparison of mission structure. This is not the EDF5 M014 cave case or the EDF5/EDF6 EDF5_OLD_SCRIPT 141-mission corpus; equal numeric mission IDs from different games are not interchangeable. M002 caveat. The original nw_testmap.mac scene creates 10 individual enemies (three ants, two bees, three Nephila, two Ufo10) by cuscall0 2000. Its decompiled program still includes a generated Func1709960674 clear-handler body, but no textual call to RegisterEvent (cuscall0 2) or CreateEventFactorAllEnemyDestroy (9100). The mere presence of that handler is not proof it is registered or reachable, nor proof that the map is impossible to complete; other engine/mission pathways were not runtime-tested. By contrast, M001 and M003 create 40-member ant groups via 2002, while M004 creates one deiroi401 using 2000; those three include a textual all-enemies-destroy registration.

M012 staged mothership and carrier example. The source sk_Sangaku02.mac mission constructs a neutral UfoMother401M012, two UfoCarrier301 enemies and a later sequence of carrier-related spawns/actions. Its source contains 7 CreateNeutral (1020), 13 SetObjectAction (3200), 2 SetGenerator (2100), 9 additional generator call sites (2101), 11 wait-factor (9000), 4 all-enemies-destroy-factor (9100), 1 object-destroy-factor (9201), and 6 AiMoveEnd-factor (9300) instructions. For example, a Func455038071 registration follows SetGenerator and Factor_ObjectDestroy attached to the first carrier; other branches first schedule by delay and then advance mothership actions. The source is demonstrably more than one linear spawn list. The count does not prove that every stage executes on every playthrough, or that a later target-port runtime reproduces it.

M014 spider/web and civilians example. In original EDF4.1 nw_KousouBld01.mac, the 20 CreateEnemy2 call sites comprise 11 Nephila.sgo spiders and 9 web resources (SpiderNet20: 3, SpiderNet40: 5, SpiderNet80: 1). They reference 10 named 蜘蛛01–蜘蛛10 spawnpoint labels; label 蜘蛛04 is used for two spiders and one web, while 蜘蛛10 has a spider without a web site in this set. Sharing a label shows a common spawnpoint reference, not a proven attachment/ownership relationship. The same source contains 7 CreateFriend (1010) and 2 CreateMob_Path (902) calls, distinguishing allied unit and civilian-path staging from hostile spawning. CreateEnemy2 is a distinct native call ID from CreateEnemy; their exact effects must not be merged just because both can produce an enemy object.

R173 registration-closure study: authored callbacks versus possible event paths

The same six original EDF4.1 decompiled BVM scripts were re-read as a function/event-registration graph, rather than counting cuscall0 occurrences again. For each public function stub (Main, Func...), the analysis locates its decompiler location_N body. A textual RegisterEvent (cuscall0 2) with a named callback gives a possible event edge from the containing procedure to that callback. The table starts at Main and repeatedly follows only those registration edges; it does not assume that a registered event's factor becomes true or that the game invokes it.

M002 is an existence/registration distinction, not a demonstrated gameplay deadlock. Its named clear handler is present but no RegisterEvent edge connects it to Main in the decompiled source. M001, M003 and M004 use the same-named handler with one explicit registration. Other engine dispatch paths have not been excluded.

M012 has two visible entry branches from Main. One registers Func1440396720 behind a 9000 wait factor with source operand 2.0, the other Func1949816122 with 25.0. The subsequent possible registration graph includes Func1440396720 → Func455038071 with 9201 object-destroy factor for the first carrier; the other branch goes through Func1949816122 → Func84848491 → Func48514845 → Func602383665 → Func1217631729 → Func597953820 → Func388411059. These branches later connect through Func937203595, before further mother-ship and transport-stage registrations. This is a dependency/registration sequence, not a timed playback trace: whether the engine processes each event is conditioned by the real objects and factors.

Func1974397686 is declared but receives no direct registration in the studied source; its own body nevertheless registers Func801877805 after an enemy-clear factor. Consequently one of M012's 19 registration sites is inside a procedure that is itself outside the Main-rooted registration closure. Func273691782 is likewise unregistered in this graph. This does not establish impossible runtime reachability because native callbacks, alternative registration paths or other VM dispatch semantics might exist outside the examined textual registration edges. It is specifically a result about this bounded source graph.

M014 provides the opposite contrast: all 14 event-registration sites belong to procedures in the Main-rooted registration closure, although Func979272483 is declared without a path in that graph. This does not mean all 14 conditions activate during a real run; it means their registration-owner procedures are structurally reachable if upstream event dispatches occur.

The R173 CSVs preserve all 36 registration edges, 45 declared public function nodes, source-line references, factor-call IDs found in immediately following source statements, and six separate source SHA-256 hashes. The graph intentionally omits claims about call probability, event ordering across asynchronous branches, runtime race conditions or game-ported parity. Original game ASM is not republished.
