EDF5 map HKT: model-name collision lookup, rigid-body pose and layer categories

EDF 5Game technical referencesMaps / collision
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R132 test

EDF5 looks up many placed prop collision resources using the model or structure name, with a .hkt suffix. A map also has its own collision.hkt, but a placed model's resource path and its world transform have to be handled separately.

Two independent conditions: source resource and a collision role

Preload_Model reads the object-definition name, derives its stem, and conditionally requests <stem>.hkt when a definition field at +0x10 indicates a collision asset. The same suffix is used by the FMEX, animated-model and structure preload paths. The source counted 1,309/1,317 inspected definition rows with value -1 and eight with 0; interpreting this as a collision-presence switch is an inference, not an officially named file field.

For a qualifying HKT, the engine builds Havok rigid-body information, assigns a collision filter, poses the body from the MAPB world matrix, and associates it with the object's placement index. Recorded default physics data include friction-like values 0.8 and 0.5; the researcher inferred the fixed-body motion type from the stored enum. No universal collision-shape identity can be inferred from a matching MDB file name alone.

Observed layer selection by definition category

Object definition category Observed collision layer
3 17 (0x11)
2, 4, 5, 6 20 (0x14)
10 Water path, no ordinary body built here
Other categories 15 (0x0F)

For composite .mosb structures, the native code merges multiple .hkt parts into a fixed body with local part transforms. Generated trees use their own capsule collision, often on layer 20. The numeric layer does not alone establish every permitted pairwise collision: the filter matrix is a separate piece of Havok state.

Limits of the evidence

These findings come from EDF5's object-preload functions and a 24-map tally. The source did not read all layer-to-layer pair rules in the same pass. Do not substitute EDF6's hknp material/layer semantics into EDF5's hkp bodies simply because the class or object name is familiar.
