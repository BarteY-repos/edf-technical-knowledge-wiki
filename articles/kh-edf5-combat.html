Teams and the TeamManager

Evidence: static · Build: steam-5d11de53 · Fact ID: team-id-field

The team id is the dword at player +0x218, read as the team by the generic damage function 2DB370 (e.g. at 2DB7B3); -1 = none (also the value when dead). Writing only this field (as the Cheat Engine table does) leaves the player in team 0's member list, so a player search over team 0 keeps working. 3094EC in the per-player update (local players only) is a hook site.

Basis: disassembly; novae (ajane); the key is polled by the pad-0 player

Addresses (build-specific RVAs unless indicated): 2DB370, 2DB7B3, 3094EC

Attribution: novae (ajane) · 2026-10-07

Evidence: verified · Build: steam-5d11de53 · Fact ID: team-switch-restart-crash

Changing a player's team id (+0x218, dword) by direct write (0 -> 1, the Kemui52/BlueAmulet CT "Team Damage Byte") lets enemy attacks pass, but the game crashes on Mission Restart unless the original team is restored before TeamManager's remove 32C1E0 runs: remove looks the object up under its current team, so the object stays in team 0's member set as a dangling pointer. Side effects while switched: enemies vanish from the radar, friendly NPCs show red, Wing Diver lock-on weapons stop locking onto enemies, the player's shots still kill. The debug command player (handler 55E00) changes the team properly through the TeamManager.

Basis: novae (ajane); cause static

Addresses (build-specific RVAs unless indicated): 32C1E0, 55E00, 3094EC

Evidence: static · Build: steam-5d11de53 · Fact ID: combat-teammanager-walk

TeamManager [125AB80]: lock (CRITICAL_SECTION) at +8, team array data [+0x38], 0x38 bytes per team, count [+0x48]; each team begins with an MSVC std::set<GameObjectBase*> (head pointer; node left +0, parent +8, right +0x10, isnil +0x19, value +0x20); the team record's +0x30 is the team's merit total (weapon-credit-reload-fields, kill-merit-team-credit; corrected 2026-11-09, KH chat 71, from "damage total" by a read of its writer 32BDD0) and +0x18 points to its relation dwords, one per team (2 = hostile). Damage, invincibility and kills

The developer command set_invincible (592F0) sets player+0x280 |= 1

Evidence: verified · Build: steam-5d11de53 · Fact ID: set-invincible-bit

The developer command set_invincible (592F0) sets [player+0x280] |= 1; with that bit set attacks still hit and can knock you down but do no damage, and the team is unchanged. The generic damage function skips the HP change at 2DB608 when bit 1 is set and the damage record's flag 0x40 is clear. The command table registrar 618340 registers 240 commands; there is no kill-all.

Basis: novae (ajane); static for the damage path

Addresses (build-specific RVAs unless indicated): 592F0, 2DB608, 618340

Attribution: novae (ajane) · 2026-10-04

Evidence: static · Build: steam-5d11de53 · Fact ID: combat-dead-flag

player+0x280 bit 0x10 is the DEAD flag (set at 2DB7F0 when HP <= 0; it skips HP changes), not an invulnerability bit: do not set it.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 2DB7F0

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-29c-constructor-subobject

The byte write at 2D269D (mov b[r9+0x29c],1) is not to an object's +0x29C: its function 2D2600 is called once, from the constructor 2D15A0 at 2D18A0, with rcx = this + 0xEF0, so it sets this + 0x118C. An object's own +0x29C is a dword, the captured-by kind (stingers-webs.md#edf5-capture-state-29c): 0 free, 1 jaws, 2 web, 3 grab.

Basis: fn.py reads (the function bounds from .pdata)

Addresses (build-specific RVAs unless indicated): 2D269D, 2D2600, 2D15A0, 2D18A0

A patch can kill any object the way the game's own instant kills do (model: vehicle handler 360A50): build a…

Evidence: verified · Build: steam-5d11de53 · Fact ID: lethal-damage-message

A patch can kill any object the way the game's own instant kills do (model: vehicle handler 360A50): build a damage record with 323CD0 (rdx record 0x90 bytes, r8 -> y, r9 -> position, [rsp+0x20] damage (doubled), [rsp+0x28] attacker), reserve its vector at +0x70 with 6FD80(..., 4), send it as message 0x80000000 with 4FCE0 (target vtable +0x38 / +0x30 / +0x40) -> handler 2DAC60 -> damage function 2DB370 -> death path 2DB7F0, then free the vector with 6FC20; deaths, ragdolls and kill counts behave normally. Record fields: +0x10/+0x18 attacker handle {ptr, ctrl}, +0x24 attacker team (-1 = no team rules), +0x30 position, +0x50 damage, +0x5C flags (0x40 = ignore invincible and hit-zone checks, 0x200 = no damage, 0x400 = multiplier 1), +0x78 -> hit-point vector data. Also HP min +0x1F4 and damage multiplier +0x294 on the object.

Basis: novae (ajane); static path

Addresses (build-specific RVAs unless indicated): 323CD0, 6FD80, 6FC20, 4FCE0, 2DAC60, 2DB370, 2DB7F0, 360A50

Evidence: static · Build: steam-5d11de53 · Fact ID: kill-team-members-sequence

Killing a team's members outright works like this: they are collected from the TeamManager under its lock, then each is looked up again before it is hit; the record from 323CD0 carries damage 2 x 1e9, attacker = you, team -1 (no team rules), position = target +0xA0, and goes out as message 0x80000000 by 4FCE0 -> damage function 2DB370 -> the normal death path. Afterwards the record vector is freed with 6FC20 and the attacker handle released, as the game does after its own instant kills (360BF4).

Health per mission, difficulty and player count

An object's max HP (+0x1F8, current +0x1FC set equal

Evidence: static · Build: steam-5d11de53 · Fact ID: hp-formula-modelist

An object's max HP (+0x1F8, current +0x1FC set equal; radar.md#gameobjectbase-fields) = game_object_durability (+0x1F0, loaded at 2D9EE5, name lookup 2D9E12, default 100) x f / 10 x ModeList[mode][6][difficulty][3][0] x ModeList[mode][6][difficulty][1][players - 1] (2D49D0, the product at 2D4B63-2D4B85). f (+0x2FC, default 10.0) is set by 2DBCC0(obj, x): x x the SGO's game_object_level_adjust (default 1.0) goes to +0x2F8, and f = that x (L + (M - L) x t) (8ACC0), where [L, M] = ModeList[mode][6][difficulty][0] and t = the mission's row index [save+0x48] / (row count - 1) of the current list (as the loot roll, drop-items.md#loot-roll-level-window); when the save-object byte +0x44 is set, f = x x 10 instead (set by BVM call 22, the tutorial's fixed level: #bvm-call-22-level-fix). x is the spawn's own hp factor: 1.0 for a plain spawn, the script's hp argument x its whole-mission factor (+0x414, mission-vm.md#bvm-call-20-hp-factor) for scripted ones (generators: message +0x10, used at 3C5FC5). 2DBCC0 has 36 callers (enemy, NPC and vehicle spawns); every enemy class computes the product in its own copy, none with a factor of its own (#hp-formula-per-class; the Teleport Anchor: #generatorpoll-hp-same-formula).

Basis: disassembly (fn.py); config.sgo decoded (scratch File_Storage/Logs/catalog/modelist_hp.py); checked against the JP wiki in #hp-formula-wiki-check

Addresses (build-specific RVAs unless indicated): 2D49D0, 2D4B63, 2DBCC0, 8ACC0, 2D9EE5

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-call-22-level-fix

BVM custom call 22 (no arguments) fixes the mission level: it sets save-object byte +0x44 = 1 (115481, mov b[rax + 0x44], 1; jump-table slot 117740, after call 20's at 117738 and call 21's at 11773C), so for every later spawn 8ACC0 returns f = (hp factor x level adjust) x 10.0 (8ACCC, constant EE65F4) and its max HP is durability x adjust x factor, times the online multipliers, with no difficulty curve (#hp-formula-modelist). Evidence: static · Build: steam-5d11de53 · Fact ID: hp-formula-wiki-check

The EDF5 JP wiki's enemy health rule (page 15, "HP = K{L+(M-L)(n-1)/(N-1)} x p x K2") is the game's formula (#hp-formula-modelist): its L and M for the main game and both packs are value 0 / 10 exactly; its online multipliers p for HP (1-4 players, every difficulty: e.g. Easy 2.16 / 1.44 / 1.8 / 2.16, Hard 2.76 / 2.07 / 2.415 / 2.76, Inferno 2.64 / 2.42 / 2.53 / 2.64) are value 3[0] x value 1[players - 1], and for attack value 3[1] x the same (Inferno 2.4 / 2.2 / 2.3 / 2.4); its K (base durability) is durability x level adjust (object-classes.md#atwiki-enemy-durability-level-adjust); its K2 (per-mission factor) is the script's factors (x). Page 310's "Inferno, 4 players: health x 2.64, attack x 2.4" agrees. Example (the wiki's): Black Ant (60), offline Inferno: 960 at the first mission, 1680 at the last.

Basis: the wiki's two tables compared value by value with modelist_hp.py's output

Max HP is a float32 the game never rounds: every step of hp-formula-modelist is a single-precision mulss / di…

Evidence: static · Build: steam-5d11de53 · Fact ID: hp-float32-order

Max HP is a float32 the game never rounds: every step of #hp-formula-modelist is a single-precision mulss / divss / addss, in this order: s = x x level adjust (2DBD17; level adjust default 1.0 from EE6430), t = float(row) / float(rows - 1) (8AD43-8AD4D), f = ((M - L) x t + L) x s (8AD37-8AD59), then f / 10 (EE65F4 = 10.0, 2D4B66), x durability, x value 3[0], x value 1[players - 1] (2D4B71-2D4B7E), stored to +0x1F8 and +0x1FC. Hits subtract float damage from +0x1FC (#damage-hp-apply) and the object dies when HP <= 0 (comiss against 0.0 at 2DB7E3, xmm6 zeroed at 2DB605), so the least whole damage that kills is the max HP rounded up. Because t steps by 1/109 in the 110-mission offline list, most per-mission HPs are fractional (7813 of 8612 cells of enemy, mission, difficulty and spawn factor over the six mission lists, offline factors): Black Ant, offline mission 2, Inferno = 966.6055 (kills at 967 damage). A double-precision calculation can differ in the last digits; reproduce the float32 order to match the game. The spawn natives multiply the script's hp argument by the call-20 factor in float32 too (12498A, mission-vm.md#bvm-call-20-hp-factor).

Basis: disassembly (fn.py); constants read with scratch File_Storage/Logs/catalog/exe_floats.py; cell count by scratch hp_survey.py

Addresses (build-specific RVAs unless indicated): 2DBD17, 8AD43, 8AD59, 2D4B66, 2D4B7E, 2DB7E3, 2DB605, 12498A, EE65F4, EE6430

Attribution: KH chat 76 (curator), on novae (ajane)'s question whether the game rounds HP · 2026-11-09
