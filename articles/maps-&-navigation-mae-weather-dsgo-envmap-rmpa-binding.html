MAE weather: DSGO profiles, _envMap and RMPA references

UniversalMaps & NavigationMapsEDF 4.1EDF 5EDF 6
Technical reference · Maintained binding parser + scoped Desert508 runtime

At a glance

What it is: An EDF6 MAE weather resource is a container whose DSGO weather profiles must refer to the correct embedded area RMPA identity.

Where it fits: The qualified MARC profile packages a weather DSGO alongside a separately named area RMPA; the DSGO _envMap name is an actual lookup dependency.

Important distinction: Two individually parseable blocks can still be semantically disconnected by a mismatched name. Weather schema, environment textures and runtime acceptance require separate checks.

EDF6 MAE is an environment/atmosphere resource carried in a MARC envelope. A MAE file may be structurally valid and still fail to supply the resource that its weather profile requests. The important relationship is not merely the MAE filename, but the identity of the RMPA block referenced by the weather DSGO.

The two embedded resources

The measured builder creates a MARC container with two named blocks:

MAE (MARC archive)
  <environment-area>.rmpa  -> weather-area data
  weathers.dsgo           -> weather profiles and shader/environment parameters

Do not confuse the embedded weather RMPA with mission RMPA or assume its area name must equal the main map's base name.

The weathers.dsgo payload is parsed as a DSGO tree. Each relevant extra profile may contain an _envMap pointer-like node. In the examined format, its first two typed values must be strings:

_envMap[0] = "<environment-area>.rmpa"
_envMap[1] = "<environment-texture-identity>"

The first string must match an actual embedded MAE RMPA block name (comparison is case-insensitive in the qualified validator). The second is the texture identity; matching it to the RMPA name is not a valid shortcut.

Why a plausible MAE can have a broken binding

Suppose a port creates an MAE for ig_desert508 and automatically names the embedded resource ig_desert508.rmpa, but the source-authored weather DSGO actually says _envMap[0] = "ig_base502.rmpa". Then the weather profile's lookup points to a different resource name from the block that was packaged. The two pieces are both parseable but semantically disconnected.

The retained builder refuses this mismatch unless the appropriate explicit RMPA identity is selected. The corresponding validator requires exactly one weathers.dsgo in the tested profile, parses each weather profile and checks that every _envMap[0] resolves to an embedded RMPA. A repair can rename a single RMPA block when every profile shares exactly one target identity and the rebuilt MARC passes validation. This is an identity fix — not reconstruction of weather visuals.

Weather is more than a resource header

Within the observed EDF6 weather DSGO profile, named fields also include:

_lights   _ambient   _sky      _envMap
_tone     _sun       _lowBloom _highBloom
_fog      _brightnessFog _farClipZ _shadowOffset
_wind

An EDF4.1→EDF6 validation path found that a missing _brightnessFog was sufficient to violate its target resource contract. This list is the measured validation envelope of that pathway, not a claim that all native files must contain precisely the same global set.

EDF5 did not supply one native MAE counterpart for every EDF6 map. Earlier paired comparisons showed map-specific weather-DSGO parameter differences that are not derivable from the EDF5 name alone. Using an EDF6 reference can help a compatibility build load; copying one donor's parameters does not prove the authored environment matches the EDF5 original.

EDF6 camera ranges: weather far clip versus distant visibility

The 7 November 2026 EDF6 render-loop disassembly for build steam-678ccb46 traces an important connection between weather/LightEnv values and visibility. EDF6 uses a near/main camera range and a separate distant camera range; a single “render distance” number does not explain whether an object actually appears.

LightEnv fieldNative offsetReported defaultObserved use
FarClipZ+0x1A01000Main camera far plane (camera +0x2C).
DistantViewNearClipZ+0x1A4500Distant camera near plane (camera +0x30).
DistantViewFarClipZ+0x1A820000Distant camera far plane (camera +0x34); source MAEs also show 35000.
FogBegin+0x150300Fog configuration, separate from culling.
FogEnd+0x1548000Fog endpoint; studied MAEs range from 5000 to 25000.

The weather DSGO parser recognizes names including _farClipZ, _distantNearClipZ and _distantFarClipZ. The traced LightEnv apply path (1230A0) copies the three clip fields into the renderer's four camera instances; the frustum builder (118DFF0) produces the separate near and distant frusta. The ranges overlap by default: main 0.1–1000 and distant 500–20000. The native far-plane values are source observations, not a guarantee of visibility at every distance.

The second gate is the render-node mask. The reported main view selects masks containing bits 25/27 (0x0A000000), while the distant view selects bit 26 (0x04000000); shadows use bit 30. The native setFarRender route (11B3020) sets/clears bit 26, and some character render options and effects route through it. Thus an object with no distant-render bit can disappear beyond FarClipZ even when the environment's distant far plane is 20 km. An object's own cull-distance threshold is a third, separate limit.

Important: these are build-scoped static engine-code findings and the source author's interpretation of the pass split. They do not establish a universal global-distance tweak or in-game appearance for every weather profile. The render-pass article explains which near/far/shadow submissions use those visibility results.

EDF6 MAE scene type controls shadow-pass submission

Evidence: verified (source-reported Cheat Engine reads and mission tests) · Fact ID: ktaro-scene-type-shadows · EDF6 Knowledge Hub, source revision.

The weather root weathers.dsgo field _sceneType, observed at System+0xB00, gates the shadow-depth pass: 0 draws it, 1 suppresses it. Source in-game checks found 1 and no character shadows in missions 42 and 111 (nw_TikaKyoju01) and 100 (nw_Seiyu_night); M31 (nw_Seiyu) and the EDFROOM601 test map in mission 116 had 0 and submitted the shadow pass. A purpose-written parser read all 303 MAE files without failures: value 1.0 in 19 weather records (16 cave profiles, two NW_TIKAKYOJU01 variants and NW_SEIYU_NIGHT_NIGHT), zero in the remainder. Do not assume that enabling the distant view or adjusting shadow shaders overrides this scene-level gate.

This is the source's measured configuration and pass behavior, not an independently reproduced game test for the wiki.

What was actually runtime-qualified

A later source-derived Desert508 workflow addressed the two retained shipping consumers: DM018 selects EVENING and DM020 selects SUNSET. Both presets were tested successfully in game. In that specific branch the source weather texture/RAB payloads were retained and MAE/DSGO components constructed for the required profiles; the result should not be confused with the earlier reference-assisted experiments. The four additional Desert presets remained offline/source-qualified but lacked a retained mission BVM consumer.

Checklist for authors and parsers

  1. Inspect the outer MARC entry table. Check that the MAE contains the expected named RMPA and weathers.dsgo blocks.
  2. Parse weather DSGO structurally and verify every relevant _envMap pointer has the expected string fields.
  3. Resolve _envMap[0] to the embedded RMPA name, not to an assumed map-base name.
  4. Validate weather RMPA content and the referenced textures/RAB resources separately.
  5. Distinguish a source-authored weather profile from an EDF6-reference-derived donor profile.
  6. Confirm actual use in the relevant mission and scene before claiming visual/runtime parity.

Evidence: maintained converter/weather/mae_tool.py and weather_mae_binding.py plus the qualified Desert508 runtime evidence. This is a source/target binding rule, not a universal weather profile conversion algorithm.

Why an EDF5 weather source may not exist to copy

In the historically audited shared-map EDF5 → EDF6 set, EDF5 did not supply MAE files of the target kind; EDF6 native profiles were used as observational references. A CAVE501-versus-CAVE503 comparison found roughly 308 bytes of differing weathers.dsgo parameter data even where the profile did not spell out the map name. This is a measured difference in two native examples, not a fixed per-map header segment or a magic 308-byte patch rule. It demonstrates why a new weather profile cannot be obtained by renaming one MAE file or mechanically generating parameter bytes from an EDF5 source that contains no equivalent MAE resource.

Native named-record lookup: the Desert508 mismatch

A bounded EDF6 EDF.dll analysis traced _envMap[0] as an actual lookup key in the currently loaded MAE descriptor, not display-only metadata. Around EDF+0x162FC2..0x163054, the weather reader extracts _envMap[1] as a texture string and _envMap[0] as the area-resource string; a later call near EDF+0x164B80 resolves the area name through the resource lookup route near EDF+0x1198D0. Offsets apply to the specified binary, not every EDF6 build.

The original EDF5 IG_DESERT508.MAC and its six authored weather profiles refer to ig_base502.rmpa. Two effective EDF6-compatible MAEs, IG_DESERT508_EVENING.MAE and IG_DESERT508_SUNSET.MAE, retained _envMap[0] = ig_base502.rmpa but packaged the weather RMPA record under ig_desert508.rmpa. That name mismatch can leave the local environment-area binding unresolved, even though MARC and DSGO both parse. A source-faithful identity correction changes the embedded RMPA entry name to ig_base502.rmpa, preserving weathers.dsgo, RMPA payload and _envMap strings. The audited effective five-MAE set contained exactly these two failed names before correction, zero afterward. The additional four Desert weather profiles were source-checked research variants, not additional released mission consumers.

Do not generalize an _envMap rewrite to the map filename or copy an assumed _sub_spec_factor_max from a donor MAE. Native EDF6 examples vary in that optional field. This specific named-record correction has structural evidence; its weather appearance must be judged independently in a relevant scene. Primary evidence: EDF5_EDF6_TESTER_FEEDBACK_R5_OFFLINE_CHECKPOINT_2026-09-27.md and its native binary-lookup notes.

Weather RMPA IDs have their own namespace

For the examined IG_2000MCITY / Evening profile, original EDF5 embedded weather-area ig_2000mcity.rmpa measures 2,062 bytes, while the native same-map EDF6 counterpart is 2,080 bytes; the separate IG_2000MCITY601 counterpart is 1,412 bytes. Their measured shape IDs are local to the weather RMPA, not offset by the main map's MAPB actor count. Therefore the formula gid_base = final MAPB T2 count + 3, which is useful only in certain map-RMPA contexts, is invalid as a global weather-RMPA rule. Do not confuse either with mission RMPA identity.

The same-source IG_2000MCITY weather RAB and the exact native same-map RAB contain the same five logical resource names modulo case in the sampled comparison; one examined sky cubemap was byte-identical. This is not permission to substitute IG_2000MCITY601 as a donor. Its MAE was only 5,712 bytes versus 25,984 for the native exact-name IG_2000MCITY_EVENING.MAE; they are materially different weather profiles, despite overlapping map nomenclature.

A later five-file release set passed its specific effective-MAE _envMap/embedded-RMPA binding audit 5/5, including IG_2000MCITY_E5EVENING, Desert EVENING/SUNSET, and two E5CLOUDY city profiles. This is structural source-binding confirmation only; it does not certify full image fidelity or all six optional Desert presets. The source audit and five-path list remain identified in EDF5_EDF6_IG2000MCITY_WEATHER_RMPA_BRIDGE_R68_OFFLINE_AUDIT_2026-09-05.md and EDF5_EDF6_RELEASE_PLUS_R5_MAE_BINDING_GATE_2026-09-27.json.

Recovering the six original EDF5 weather SGOs from MAPB

The tested EDF5 MAC/MAPB source layout stores six classic weather SGO objects inside map.mapb; they are not six top-level MAE/MARC members. MAPB has six signed little-endian self-relative 32-bit pointer fields at offsets:

0x28   0x30   0x38   0x40   0x48   0x50

Decode each pointer with target_offset = pointer_field_offset + int32_le(mapb[pointer_field_offset]). The immediately adjacent +4 word was zero/reserved in both examined source maps. All 12 decoded targets in the IG_HEIGEN507 and IG_DESERT508 cases landed on SGO\0 magic; the six source object names in both maps were fine, sunset, cloudy, Evening, FineCloud, cloudy2 in the measured slot order. Use the SGO's Name field for identity, not its pointer index. The underlying source MAC sizes were 794,906 and 329,052 bytes respectively.

Every sampled source SGO exposed 116 variables; 80 matched the examined EDF6 legacy weather reader's named-field contract. From these originals one source-only translation produced weathers.dsgo of 18,688 bytes for HEIGEN507 and 18,660 bytes for DESERT508. Both compiled/re-decompiled and reproduced byte-identically on a second generation. An independent minimal DSGO writer also reproduced the exact same bytes: the two header pointers at DSGO +0x04 and +0x0C are expressed relative to the header base (0), not relative to their individual pointer-field locations. That is a measured format rule of the tested weather subset, not a guarantee of a complete generic DSGO serializer.

The classic fields include the four light groups, sky/ambient, EnvmapArea/EnvmapTexture, sun, bloom, fog, brightness fog, clipping, shadow offset and wind. Constructor completion is used only where the tested target reader would leave an omitted legacy member at its canonical initial value. For the measured maps a missing SunMaskTexture maps to the empty string by exact target reader behavior; do not invent a texture name. Importantly, some old source members not consumed by this specific native reader (such as legacy36 names) remain unresolved rather than automatically obsolete.

The source-owned IG_2000MCITY / Evening profile independently confirmed EnvmapArea = ig_2000mcity.rmpa, FogBegin = 300, FogEnd = 800, FarClipZ = 1000 and Wind = 3 in that original profile. These are source-authored numbers, not visual evidence that EDF6 interprets the final composed image identically. The exact two-map pointer/SGO observations are tabulated in data/R164_EDF5_MAPB_EMBEDDED_WEATHER_SGO_12_POINTERS.csv.

Evidence: source MAC/MAPB extraction and byte-exact reserialization: EDF5_EDF6_SOURCE_WEATHER_MAPB_BRIDGE_R67_OFFLINE_AUDIT_2026-09-05.md and EDF5_EDF6_WEATHER_DSGO_PYTHON_BACKEND_R72_OFFLINE_AUDIT_2026-09-05.md; exact later IG_2000MCITY source profile: EDF5_EDF6_IG2000MCITY_WEATHER_RMPA_BRIDGE_R68_OFFLINE_AUDIT_2026-09-05.md. These are static/source and offline construction findings, not new in-game validation.

Modern weather nodes: a missing-field crash is not fog tuning

The source-derived IG_2000MCITY / e5evening candidate exposed a separate target-format hazard. In an earlier runtime test, EDF6.dll raised 0xC0000005 at the examined build's EDF+0x52E44 data-accessor dereference. The fault registers matched a missing named-node lookup returning -1, subsequently scaled into an invalid indexed access. The source profile had omitted the modern _brightnessFog DSGO node, but the relevant EDF6 weather reader accessed it without a guard.

The exact target-reader audit identified 13 required, unguarded nodes:

_lights, _ambient, _sky, _envMap, _tone, _sun,
_lowBloom, _highBloom, _fog, _brightnessFog,
_farClipZ, _shadowOffset, _wind

The three recovered guarded/optional names were _sub_spec_factor_max, _distantFarClipZ and _distantNearClipZ. The repair candidate used the measured EDF6 constructor defaults for absent EDF5 _brightnessFog: begin 100.0, RGBA (0,0,0,1), curve 0.5, end 3000.0. The 24/24 static verification gates passed and a byte-identical DSGO roundtrip was obtained, with no unrelated weather-profile field changes. This proves a structurally qualified candidate and an exact crash-mechanism explanation; the immediate repair candidate was still marked runtime pending. Do not infer that the repaired weather looked correct merely because the missing node was supplied.

This is a different kind of issue from the later Desert508 _envMap name-reference mismatch: one is a required target DSGO node causing an invalid -1 dereference; the other is referential integrity between separately contained MAE resources. Both must be checked, and neither is a substitute for visual runtime evidence. Sources: EDF5_EDF6_M020_5_R73_E5EVENING_ISOLATED_WEATHER_OFFLINE_AUDIT_2026-09-05.json, EDF5_EDF6_M020_5_R74_BRIGHTNESSFOG_ABI_OFFLINE_AUDIT_2026-09-05.md and R74_MODERN_REQUIRED_FIELDS_GATE_2026-09-05.json. The RVA is exact-build-specific.

A native target weather-RMPA discrepancy that is not a general conversion law

The original IG_2000MCITY evening environment-area RMPA parsed with 10 shape records and 10 spawn records and reserialized into the target's structurally valid 2,080-byte weather-RMPA envelope. Its source payload was 2,062 bytes. Comparison with the exact same-map native EDF6 environment asset found a deliberately small game-content value difference, not a broken codec: two target float bytes/fields at file offsets 0x5EE and 0x5FE represent p1.x and p2.x of the local spawn 公園1, adjusted from 281.718719 (EDF5 source) to 281.218719 (native EDF6), a delta of −0.5 in each field. The weather RMPA's local record-identity namespace is not the map's general MAPB T2 node numbering.

This exact map-local reauthoring refutes an algorithm that blindly applies a global −0.5 offset or assumes source→target weather RMPA is byte-identical. An independent 18-profile comparison across IG_2000MCITY, NW_JYOUSUICITY and NW_KITAGUNICITY likewise found no single global source-to-native numerical transform. It was a source/target asset comparison and serializer test, not a visual runtime pass for all 18 profiles. Source: EDF5_EDF6_IG2000MCITY_WEATHER_RMPA_BRIDGE_R68_OFFLINE_AUDIT_2026-09-05.json and EDF5_EDF6_WEATHER_PROFILE_3FAMILY_PAIR_EVIDENCE_R68_2026-09-05.json.

Two similarly described relative-offset mechanisms must not be mixed: the six EDF5 map.mapb weather pointers are signed rel32 offsets relative to each pointer field (0x28, 0x30, 0x38, 0x40, 0x48, 0x50), whereas the audited DSGO header references at +0x04/+0x0C use the header base/address 0. The independent backend reproduced original weather DSGOs byte-for-byte for IG_HEIGEN507 (18,688 bytes) and IG_DESERT508 (18,660 bytes); this verifies the binary interpretation of those samples, not any future reader's behavior or on-screen appearance. Sources: EDF5_EDF6_SOURCE_WEATHER_MAPB_BRIDGE_R67_OFFLINE_AUDIT_2026-09-05.json and EDF5_EDF6_WEATHER_DSGO_PYTHON_BACKEND_R72_OFFLINE_AUDIT_2026-09-05.json.

Native weather pair audit: why same profile names are not same parameter layouts

The R68 evidence compares 18 identically named weather profiles, six each for the source families IG_2000MCITY, NW_JYOUSUICITY and NW_KITAGUNICITY. Every sampled EDF5 profile has 116 flat source variables; native EDF6 comparison values are nested, differently named _fog, _brightnessFog, _lights, _tone and other nodes (16 nodes in the 2000 family, 18 in JYOUSUI, 17 in KITAGUNI for the sampled FINE profiles). Do not compare FogBegin with _fog[0] or FogEnd with _fog[3] as if these were automatically the same unit/semantic contract. For instance source 2000/FINE stores FogBegin=300, FogEnd=1200, whereas native target _fog holds [2500, [color RGBA], 0.23353..., 10000]. The separate target-native JYOUSUI sample has 12 profile names versus the six original EDF5 names; its six additional native presets are not proof of missing original EDF5 profiles.

The record-level matrix is data/R167_WEATHER_18_NATIVE_PAIR_PROFILE_MATRIX.csv. R73 is a hash/provenance manifest for the initial M020_5 E5EVENING candidate, not a gameplay trial. R74 rebuilt all six IG_2000MCITY source profiles with field-relative MAPB pointers and an explicit _brightnessFog completion after the crash. Its own final status still said RUNTIME_PENDING; later M020_5 source-weather acceptance is a different subsequent runtime observation, not a retroactive R74 test. This cross-check prevents interpreting either a same-named source/target profile or an offline bridge PASS as pixel parity. Sources: EDF5_EDF6_WEATHER_PROFILE_3FAMILY_PAIR_EVIDENCE_R68_2026-09-05.json, R73_RESEARCH_CHECKPOINT_MANIFEST_2026-09-05.json, R74_IG_2000MCITY_SOURCE_BRIDGE_REPORT_2026-09-05.json.
