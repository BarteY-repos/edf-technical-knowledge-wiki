EDF 6 — Effects (community source notes)

EDF 6Community Knowledge HubFile Formats
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Structure

EFS is the particle system new in EDF6

Evidence: static · Build: not stated (game data) · Fact ID: efs-overview

EFS is the particle system new in EDF6. Effects are .esb files inside an .efarc (RAB-format) archive, alongside .ssb sprite settings; hash keys in the data choose which EFS component is created. Editing: KittopiaCreator's EFS Tool (Discord only).

Basis: the wiki's EFS category page and Getting Started guide

Attribution: EDF Modding Wiki, Category:EFS (KittopiaCreator, rev 2025-08-26), Guides:GettingStarted/EDF6/EN (ktaro) · 2026-10-29

StencilLight: its InitParam (vtable 1762108

Evidence: static · Build: steam-678ccb46 · Fact ID: stencil-light-emitter-jobs

StencilLight: its InitParam (vtable 1762108; +0x30 position, +0x40 / +0x50 colors, +0x60 radius, +0x64 frames, EDF 4.1's layout) is made by 84880 with the values as given, while EffectGenUtil's 2EBC00 first scales the color x 2.5 and the radius x 5. Emitter effects (ChargeEffect_StdParticle and the like): the update job is queued from the update and the render job (vtable slot 0) from the sync-render phase; queued together from the update they run concurrently and the render job throws bad_alloc (30316D); after each job the game sets [fx+8] = [fx+0xC] and [fx+0x10] = 0 (MovingFortress_Battery, 4D1B96); an emitter's deleting destructor is 301460.

Charge glows (gunbattery::ChargeEffect_StdParticle): the factory 6D92D0 (MovingFortress_Battery calls it at 4D3F22); +0xC = 0 shown, 1 hidden (the wanted state: slot 1 6D9910 turns the emitter's +0xE0 on or off when it differs from +8; vtable 17E7220); each frame its slot 1 (with the UpdateContext and the muzzle matrix) and slot 0 queue the update and render jobs in the scene's job table (manager +0x358), the render job belonging in the sync-render phase (#stencil-light-emitter-jobs; EventAnimationObject's slot 3 5B6D10 = the model's 6C06A0, MovingFortress_Battery's same slot 4D1900): queued next to the update job, the two ran at once on the job threads, the render side reading the particle ring while the update side popped it, until the render's vector threw bad_alloc (30316D from 302D10; the author's runs on M809 / M018, 2026-10-16). The SGO form is E510's charge_effect_std: [[], ['ChargeEffect_StdParticle', [[key, value, ...], [se]]]]; its parser tables 303710 / 3039B0 write the same offsets as EDF 4.1's particle block (key 12 -> +0xC4 / +0xC8 / +0xCC, key 13 -> the colors +0xE0 and +0x100, key 8 -> +0x50, key 11 -> +0xB8 / +0xBC, key 15 -> the texture), and EDF6's own glows use the integer triple 30 / 30 / 2 where EDF 4.1's use 4 / 4 / 2 (which of 4.1's +8 / +0xC / +0x10 maps to EDF6's +8 / +0xC / +0x14 is taken from that shape, "M"). Spawned enemies are told their start by message 0x20102 whose data is the spawn node matrix's row 1 (EDF6's generator 6E2170 sends it; the SpawnerObject's delivery at 6E33C3): UfoSmall507 takes it x 60 as its initial velocity (52EDE0), Deiroi (31ED40) and DragonSmall (335110) enter a falling state. A material-animation component of the 309CC0 kind binds at +0x720 like an EAO. UfoRoboCanonChargeEffect survives in EDF6 (constructor 306B60, 0x590 bytes) without a factory name (EDF.dll holds no such string): created directly by 84A60(manager, out weak, matrix, params) with an InitParamBase (vtable 1762068, 0x30) followed by EDF 4.1's template moved up by 8 (4.1 +0x28..+0x48 -> +0x30..+0x50, colors +0x50 / +0x60 / +0x70 -> +0x60 / +0x70 / +0x80), stepped each frame by 307C40(effect, muzzle matrix, dt) (its slot 5 is empty; it copies the matrix to +0x4F0 and steps the particles with 2F3B60(effect+0x190, dt) as HomingLaserHit01's update does), vtable 17A9338; 84A60 hands the caller one weak count (84B8B..84B92) and puts the object in the scene itself (1195A20 / 1197050); strength at +0x4E4 (EDF 4.1 +0x494); its constructor takes its texture by name at 306D4B. ParticleObject: 844C0(manager, out weak, matrix, params) with the parameter vtable 17620E8 (0x1D0 bytes; the emitter part built by 300C80(params + 0x30), destructor 8FDF0); the fields EffectGenUtil's Explosion (2E5ED0) fills by hand: +0x1A0 = 1, +0x1A4 = 0xFFFF, +0x1A8 / +0x1B0 / +0x1B8 = the addresses of +0x90 (position), +0xA0 ((0,0,0,1)) and +0x30, +0x38 / +0x3C life, +0x50 0.98, +0xC8 0.1, +0xF4 / +0xF8 size, +0xFC -size / life, +0x110 color, +0x130 the color's rgb with alpha 0, +0x158 a TextureRef taken by name from EffectGenUtil (2E8510) and assigned with F5E10 (ParticleAlpha_6.dds for a muzzle flash). Metal hit sparks: EffectGenUtil MetalHit 2E8F20(egu, position, normal, color, size, bool) (bullets give it sizes of about 1-20; a bullet hit calls it at 23C5C1; the debug effect table's MetalHit entry is the lambda B3280).

LineStripObject trail draw transform

Evidence: static · Build: steam-678ccb46 · Fact ID: linestrip-trail-matrix

LineStripObject smoke trails are drawn through the matrix they were created with: the factory 842E0(mgr, out, matrix, InitParam) builds the object, whose base constructor 1189C00 copies the matrix at InitParam+0x08 to obj+0x60 and nothing changes it later; the render task 2F6310 copies obj+0x60 to the renderer's +0x260 each frame and the draw (2F583A) passes it as the world matrix to 11544F0; the vertices (2F5AC0) take each node's +0x00 as is, and nodes are placed (2F6110 -> 2F4C10) at the emitter's core+0x50 in world coordinates. So a trail must be created with the identity matrix, as the game's own world-space trails are (the inline trail at 24B8EC passes the identity at 1FFF3D0; the factory's only stock caller A01A0 passes an unrotated matrix); a nozzle matrix moves and turns every node (the author measured 5785 m off before, 3.16 m after the fix, one frame of flight).

Basis: the author's static reading and their in-game runs with a debug log (static for the hub)

Addresses (build-specific RVAs unless indicated): 842E0, 1189C00, 2F6310, 2F583A, 11544F0, 2F5AC0, 2F6110, 2F4C10, 24B8EC, 1FFF3D0, A01A0

Attribution: hajisensai, All Forces source docs/feedback-2026-10-21-jet-trail.md (round 24) · 2026-11-07

LineStripObject lifecycle and removal

Evidence: static · Build: steam-678ccb46 · Fact ID: linestrip-object-lifecycle

LineStripObject's life cycle: the factory 842E0(mgr, out[2], matrix16, InitParam*) news it, constructs it (2F47F0, object vtable 17A8930 loaded at 2F4810), registers it and returns a weak reference {obj, ctrl} (84412 lock inc [ctrl+0xC]). InitParam (vtable 1762138, InitParam@LineStripObject): the emitter's parameters at +0x30 (defaults filled by 2F4490), +0x150..+0x160 a warm-up (count 0: none). The object's emitter is at +0x190 (+0x40 emitting, +0x50 where, +0x60 which way); its update task 2F64F0 runs the emitter (2F6110) and deletes the object once it is off with no node left alive (+0x2D0), so a stopped trail fades over its nodes' life and goes by itself. The missiles' smoke texture is L"噴射煙_01.dds" (17A1CC8), got from EffectGenUtil ([20B2980]) with 2E8510, copied with F5E10 and the temporary freed with 1120820 (the stock does the same at 268EFC); 2E8510 dereferences null for a name it cannot find.

Basis: the author's static reading ("H"); the vtable load at 2F4810 re-read with fn.py
