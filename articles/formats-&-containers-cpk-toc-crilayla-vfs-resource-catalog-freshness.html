EDF6 CPK archives: TOC, CriLAYLA and resource identity evidence

EDF 6Formats & ContainersFile Formats
Source-backed research / case study · Reconciled

Evidence scope: an observed EDF6 Windows installation and separate read-only reverse-engineering of its resource archive formats. Do not confuse a tool's ability to index, preview or cache an asset with a native game loader guarantee.

Audited installation and archive index

In one retained Windows EDF6 installation, four game archives were enumerated:

  • Root.cpk
  • Chunk01.cpk
  • Chunk02.cpk
  • DX11.cpk

Their parsed TOC records produced 9,717 indexed virtual resource paths. This number is the measured inventory of one installation, not a constant of every patch, storefront or region. Other loose/custom paths and later resource overrides are separate namespaces.

Container grammar and compressed entries

The investigated read-only parsing path had this source layout:

CPK header/TOC -> CRI @UTF table -> file offset + packed length
                -> plain entry OR CriLAYLA decompression
                -> native RAB/MAC/MDB/FMB/RMPA reader

Both unencrypted and standard encrypted @UTF table forms were represented in the research reader. CriLAYLA literal, backreference and variable-length decoding were checked in synthetic offline fixtures; this does not establish complete runtime fidelity against every original compressed CPK entry. A research decoder's 1 GiB safety cap is not a native EDF6 resource-size limit.

The four sampled archives were TOC-backed; an ITOC-only fallback was not needed for that narrow inventory. This does not mean the ITOC family is universally absent, unnecessary or unsupported across CRI archives.

Resource path and archive identity must be distinguished

A virtual resource path is not enough to establish a unique source when two indexed archives or overrides contain a path with the same normalized spelling. The historical research index treated case-insensitive duplicates as ambiguous archive-origin candidates rather than arbitrarily choosing the first. This is a conservative research identification policy, not independent proof of the game's exact case-folding, search precedence or override resolution.

Resource-family readers were checked at different levels: MARC/MAC section headers, MAPB type/placement tables, SSA/RAB and CMPL envelopes, MDB position/index data, and mission-specific RMPA summaries. Native model identity and correct rendering/material bindings require further evidence than a successful CPK TOC decode.

For a concrete negative CPK lookup, the source-derived Desert508 FINE weather RAB had four known DDS dependencies absent from the particular vanilla CPK set searched on one Windows host. That result is not equivalent to a claim that those textures or FINE weather do not exist in EDF6 generally. See FINE MAE/RAB resource closure.

Evidence and failure boundaries

  • A readable TOC and entry offset do not by themselves prove the entry's CriLAYLA decode or downstream format parse.
  • Identical normalized filenames from different CPK origins do not prove identical bytes or that the game chooses the same entry as a research tool.
  • The 9,717-path count is installation-specific; inventory changes may be version changes rather than corruption.
  • Neither cache metadata nor a generated preview is part of the native CPK file specification. Their implementation, UI behavior and performance are outside this wiki's subject.
  • This research did not establish a general CPK writer or byte-identical repacker. The public wiki contains no native game archive payloads.

Source family: EDF5_EDF6_RESEARCH/research/active/MAP_AUTHORING read-only CPK indexing and resource-reader evidence, plus the source-specific Desert FINE negative control. Archive source identity is distinct from a product's asset-browser lifecycle.

A separate read-only three-archive unpacked-file census (September 2026)

Another measured EDF6 Windows baseline, recorded on 2 September 2026, indexed a complete local extraction of three of the game's archives, not the four-archive TOC census above. This source independently counted:

Archive extracted Files Aggregate decompressed-file bytes
Root.cpk 8,300 8,635,277,053
Chunk01.cpk 11 468,567,682
Chunk02.cpk 921 24,155,715,208
These three combined 9,232 33,259,559,943 (~30.98 GiB)

The three extracted archive namespaces contained no duplicate virtual paths in the measured baseline. The separately retained tree_edf6.txt catalog had the same per-archive counts. The recorded 86 apparent source-tree spelling disagreements were restricted to non-ASCII mission-path names affected by an older Windows console/codepage text representation, not a measured loss of 86 game resources. The observation comes from a real read-only extraction/inventory, not a synthetic file list.

The earlier 9,717 virtual paths figure covers four CPK archives, including DX11.cpk, and came from a different inventory procedure. Do not subtract 9,232 from 9,717 to infer a DX11 file count, patch delta, duplicate count, missing files or changes in the game. The compared inventories do not share a demonstrated identical build, inclusion policy, archive-entry normalization or effective resource namespace. In particular the second inventory counts extracted files, whereas the first counts indexed TOC paths. Both measurements are valid within their original scopes; neither is a universal EDF6 asset total.
