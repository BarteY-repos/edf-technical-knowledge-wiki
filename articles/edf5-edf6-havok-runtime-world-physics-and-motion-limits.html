EDF5 vs EDF6 Havok: world, motion properties and physical limits

ConversionGame technical referencesCollision & PhysicsEDF 5EDF 6
Technical reference · Static/source-backed community evidence; verified test results identified separately; no R117 native runtime tests

Evidence: Exact binary-level inspection reported by the EDF Knowledge Hub (EDF5 steam-5d11de53, EDF6 steam-678ccb46, 2026-11-14 snapshot) plus existing native MAD/SHKT research. This page compares observed game behavior and memory structures, not SDK headers. No new physics runtime trial was performed.

A real engine transition, not just a file extension change

Feature EDF5 inspected engine EDF6 inspected engine
Havok family Older hkp rigid-body architecture; reported version string hk_2015.1.0-r1 Havok 2020-era hknp bodies and world
Per-body main object hkpEntity with embedded motion; 0x2C0-byte wrapper in the audited class xgs::havok::Body wrapper 0x110 bytes plus separate hknpBody 0xB0 bytes
Motion representation hkpMotion embedded at body+0x150 in the studied instance hknpMotion 0x80 bytes, with IDs into a shared hknpMotionProperties library
Material/shape data Older hkp layout hknp shapes, materials and collision filters requiring re-encoding

This is why a model with a correct visible mesh can still have nonfunctional collision when its SHKT/MAD data are migrated incorrectly. Renaming a Havok class or editing a version string is not a valid conversion.

EDF5: measured world and body characteristics

  • Gravity in the analyzed world constructor: (0, −14.7, 0).
  • World broadphase AABB: approximately −1000 m to +1000 m; border behavior DO_NOTHING rather than automatic body removal.
  • A native game tick is reported at 60 updates per second for the inspected game logic.
  • The original body stores linear and angular damping as half-precision values and velocity limits as hkUFloat8 bytes at motion offsets +0xCA/+0xCB.
  • In a crate example, the recorded 60 m/s nominal linear limit encodes to approximately 57.4 m/s. An attempted 80 m/s launch can be clipped by the physics solver.

These are EDF5 source measurements. It would be incorrect to copy its gravity and speed-limit numbers into an EDF6 physics specification without examining the EDF6 world independently.

EDF6: motion-properties library, not arbitrary per-body floats

The recovered hknpMotionProperties entries are 0x70 bytes in the studied live library; a separate 104-byte serialized motion-properties record is documented for the compatible MAD file profile. These should not be conflated as if they were the same structure or storage location.

The default runtime library contains five named presets: STATIC, DYNAMIC, KEYFRAMED, FROZEN and DEBRIS. Observed properties include:

Preset Measured property
DYNAMIC Max linear speed 200, max angular speed 100, gravity factor 1
KEYFRAMED Gravity factor 0
DEBRIS Max linear speed 100, angular speed 10, linear/angular damping 0.01 / 0.5
All default entries Time factor 1.0

The source's runtime field offsets within a motion-properties entry include gravity factor at +0x08, time factor at +0x0C, max linear/angular speed at +0x10/+0x14, and linear/angular damping at +0x18/+0x1C. These addresses are build/structure-specific, not a universal external file format.

A body can be assigned a different properties-library entry, but the analysis warns that a shared motion can make a nominally “per-body” change affect more than expected. A method being registered does not prove it is used by the original game.

Body lifecycle and gameplay contact are separate

EDF6 has distinct object-body paths: many vehicles retain a ragdoll component, EventAnimationObject has its own ragdoll, buildings and breakable map objects keep their own body ownership, and visual ModelDebris can use a layer that ordinary bullets never hit. The native game also exposes contact-signal callbacks for map objects and helicopter landing interactions.

Do not assume every collision or falling body produces character HP damage. The source analysis found no general native fall-damage rule in the investigated walking/cling paths, while contact handling of map props has its own ownership and event semantics. This is a scoped finding, not a proof that no conceivable script can damage an object on impact.

The practical cross-generation rule

When comparing EDF5 and EDF6 collision:

  1. Confirm the game-owned body shape and world membership separately from the rendered model.
  2. Distinguish source hkp collision filters from target hknp filters and target motion-properties IDs.
  3. Keep runtime memory offsets apart from file serializer offsets.
  4. Interpret speed caps and gravity against the correct game's native world, not an inherited constant.
  5. Test contact, damage and animation lifecycle separately from whether a body appears in the Havok world.
