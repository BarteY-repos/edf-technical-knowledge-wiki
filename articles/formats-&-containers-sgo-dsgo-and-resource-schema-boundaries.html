SGO, DSGO and resource-schema boundaries

UniversalFormats & ContainersFile FormatsEDF 5EDF 6
Source-backed research / case study · Reconciled

Evidence level: Reconciled binary/corpus rules from the unified assertion ledger and later mission/resource evidence.

Container grammar is not resource semantics

Implementation rule: Treat SGO/DSGO as container/serialization families. Shared container grammar does not imply that fields, versions, enums or object schemas are interchangeable between resources.

A converter must know both:

  1. how to losslessly parse/write the container; and
  2. the schema of the specific resource carried inside it.

Do not derive a resource conversion law from a version number alone.

Mission LIST resources

Observed native behavior: EDF6 mission LIST resources use DSGO in the qualified mission pipeline. The retained lossless path is block-oriented and should preserve unknown data rather than rebuilding it from guessed semantics.

Implementation rule: Deployment truth comes from the actual binary LIST.SGO/DSGO payload. Companion JSON, editor exports or stale manifests are secondary if they disagree with the deployed binary.

Text/name resources: the same .SGO suffix does not mean the same binary

The resource name tells you its purpose; the file header tells you which serialization family to decode. In the measured mission-pack profiles, ordinary language/name-description tables such as MISSIONLIST.OFFLINE.TXT.EN.SGO use classic SGO version 258, while the corresponding mission-list ...LIST.SGO is DSGO. Treating every file with an .SGO suffix as the same serializer can produce a parseable-looking JSON conversion but an invalid game resource.

Resource role Observed binary format Confidence / constraint
Normal mission-pack ...TXT.<LANG>.SGO Classic SGO, version 258 Verified for the studied pack grammar
Normal mission-pack ...LIST.SGO DSGO Verified for the studied mission list format
Deployed E2_BASE_OVERRIDE/...TXT.*.SGO DSGO in observed files File magic confirmed; whether all such overrides are actually loaded is untested
Other configuration *.SGO files Resource-specific SGO or DSGO grammar Inspect actual magic and schema; extension alone is insufficient

Practical rule: identify the magic and resource schema first; then apply the correct version/serializer and inspect the round-trip data. This is a profile-specific finding, not a claim that a universal TXT = SGO-258 law applies to every EDF mission deployment.

Schema-specific conversions

Do not assume: Numeric field similarity means semantic identity. Examples across the corpus include resource-specific enum/value translations, different embedded object types and target-only fields.

Weather DSGO values are particularly profile-specific; there is no accepted blind copy or scale rule.

Desert destruction-prop template case

One late clean Desert conversion line observes an EDF5 destruction/collision prop template with 33 variables and an EDF6 target form with 34 variables, inserting a target record (0x682, 1, 4, 0xFFFFFFFF) at index 17. The paired MAPO/destruction-group work uses this as a resource-family conversion.

This is not a global SGO 33 → 34 law. Shared props may use target-native templates while source-unique Desert props require the measured upgrade; unrelated SGO resources must be treated by their own schema.

Provenance and source-only output

A source-only converter may reconstruct a valid target resource using independently derived schema knowledge. Using native EDF6 resources as research oracles does not permit shipping them as production donors/templates.

Implementation rule: Preserve unknown fields losslessly when possible, document target-only synthesis explicitly and fail closed where a semantic field cannot be justified.

Baseline-relative semantic merging for legacy SGO/DSGO overrides

Two mods can supply whole-file replacements for one CONFIG.SGO even when they change different logical fields. Overriding one file with the other loses data. Conversely, blindly appending or byte-merging arrays can corrupt ordered or coupled resource semantics.

A researched offline merge approach is:

vanilla SGO/DSGO V ----\
mod A replacement MA ----> semantic parse -> diff against V -> merge -> serialize
mod B replacement MB ---/

The parser/serializer must preserve the specific SGO or DSGO format; these are not automatically interchangeable. In the demonstrated workflow, a common sgott semantic JSON representation provides the merge view, with binary serialization delegated back to the corresponding existing formatter.

Identity precedence for independently edited records:

  1. Top-level named variables: match by semantic name, not physical slot. Real paired EDF files may reorder these variables without changing their names.
  2. Known tables (e.g. mission ModeList or CONFIG weapon tables): use a schema-defined stable key whenever established.
  3. Record arrays: infer a unique stable identifier only if baseline overlap makes it unambiguous.
  4. Fixed-shape unnamed tuples: index merging is acceptable when tuple sizes are equal.
  5. Variable-length arrays without stable identity: fail closed rather than guessing what a moved row means.
Changes relative to baseline Treatment
Different fields/records Merge
Same field, same resulting value Deduplicate
Same field, differing resulting values Conflict
Delete versus update of the same item Conflict
Different newly keyed records Merge, provided keys are stable
Ambiguous variable-length insertions Manual/schema-level reconciliation

The six initial semantic-merge PoC scenarios passed offline, including reordered top-level names, independent fields, disjoint record insertions and true conflicts. A later exact Air Raider + EDF5-port CONFIG case also showed a zero-conflict 112-byte Air Raider-owned delta composed with MissionPack ModeList additions, without rewriting unrelated scopes (see the concrete CONFIG example).

Do not assume: a generic last-writer-wins preview is a valid production conflict policy. A deterministic output can still be semantically wrong. The initial algorithm PoC was not itself a successful in-game qualification.

For a reader-oriented worked example of baseline-relative semantic three-way merging and failure cases, see SGO/DSGO merging by semantic identity. The exact Air Raider plus EDF5 mission-port CONFIG.SGO proof is offline and profile-scoped, not an automatic arbitrary-resource promise.
