EDF 4.1 M210 Starship object-action boundary

UniversalMissions & ScriptingMissionsEDF 4.1EDF 6
Source-backed research / case study · Static source/object contract; runtime progression pending

Exact failure mode in the weak-point collision gate

The later R8 static audit establishes the required UfoMother301::HullAccept sequence:

  1. While the live BigCannon part exists, hull damage is disallowed.
  2. After that gate, resolve the canonical EDF6 rigid-body name RagDollProxys.weak.
  3. If lazy lookup fails, reject the current hit, clear the failed-lookup sentinel and allow a later hit to retry resolution.
  4. Only exact identity with the weak rigid body permits post-gate hull damage. A generic hit on the visually exposed hull is not equivalent.

The former fail-open behavior accepted arbitrary shell hits after an unsuccessful weak-body lookup, potentially reducing hull HP and advancing the mission's scripted phases prematurely. The source-level fix was subjected to nine focused static checks, not an EDF6 runtime retest. This mechanism is a useful general lesson for ported multipart bosses: a missing collision-body reference must not turn a source weak-point requirement into global vulnerability.

Identity must be established before debugging

A tester's visible “Mission 40” label must not be mapped to an internal EDF4.1 mission ID by position alone. The pinned campaign source order's slot 40 is M501, not the Mothership/Starship case under investigation.

The later audit identified the relevant internal Starship mission as M210.

This is an important conversion rule: use the built MissionPack metadata/output identity, not displayed numbering assumptions, before patching a mission state machine.

Two historical failure candidates already addressed

Parts availability on creation frame

CreateHull() calls SpawnParts() before returning from the factory because source mission logic can issue creation-frame ObjectAction / GetPartsObject operations.

A bridge that deferred parts creation would change the mission's state-machine semantics even if all parts appeared one frame later.

Hull damage acceptance

HullAccept() is fail-closed while RagDollProxys.weak cannot be resolved. It retries later rather than accepting arbitrary hits during incomplete object setup.

This prevents initialization timing from silently turning into a damage-state change.

Current conclusion

There is no current source/static evidence for another M210 transpiler patch.

The previously reported skipped turret-activation / directly destructible cannon/weakpoint behavior is still a runtime progression gate. If it reproduces, the correct next step is a source-BVM versus generated-AC event/factor/object-state trace using the confirmed M210 identity.

Do not do

  • do not assume visible mission number equals internal mission ID;
  • do not patch generic ObjectAction numbering without a source mismatch;
  • do not defer SpawnParts() past creation-frame source calls;
  • do not make HullAccept() permissive to hide incomplete initialization;
  • do not call a static action-table match a runtime progression PASS.
