The two flags

A bullet carries two collision filter values

Evidence: verified · Build: steam-678ccb46 · Fact ID: bullet-flag-roles

A bullet carries two collision filter values. Flag 1 (m_iCollisionFlag1, BulletControl +0x890, bullet +0x9D0, default layer 12) says what STOPS the bullet: a zero-thickness ray along its path; when it hits, the path end is moved to the hit point and the bullet stops. Flag 2 (m_iCollisionFlag2, +0x894 / +0x9D4, default layer 11) says what the bullet HITS: a sphere shape-cast of the bullet's size along the (already shortened) path; a hit does damage, and a penetrating bullet passes through. A target hit by neither is passed through. Shields are the exception: a Flag 2 hit on a shield stops the bullet.

Basis: ktaro's 2,800-cell test; the model of REPORT.md §4.1 explains 2,738 cells (97.8%); code read in the next lines

Addresses (build-specific RVAs unless indicated): 22FD80

EfsBulletExpansion collision flag writes

Evidence: static · Build: steam-678ccb46 · Fact ID: efsbullet-flags-reading

EfsBulletExpansion writes both flags in EfsBullet::EfsBullet (239210) at 23A7C0 (mov [rsi+8D0],ax, RSI = the bullet). It reads each node as a double and converts with cvttsd2si. If collision_flags is absent the code leaves without reading collision_flags2 (the first je goes to the exit), so to change only Flag 2 the file must also give collision_flags (12 for the default).

Basis: Ghidra read of the patch's target, REPORT.md §1.1

Addresses (build-specific RVAs unless indicated): 239210, 23A7C0

A value counts by its low 5 bits (the layer, 0 to 31) while the system-group bits (15 to 30) are zero

Evidence: verified · Build: steam-678ccb46 · Fact ID: bullet-flag-value-bits

A value counts by its low 5 bits (the layer, 0 to 31) while the system-group bits (15 to 30) are zero. So 32, 64 and 128 act as 0, and 255, 32767 and 4294967295 act as 31; ktaro's test results show exactly this.

Basis: filter function read (next line) and ktaro's cells for 32, 47, 64, 128, 255, 32767, 4294967295

Addresses (build-specific RVAs unless indicated): D93700

Havok group-collision filter test

Evidence: static · Build: steam-678ccb46 · Fact ID: bullet-filter-test

The filter test (hknpGroupCollisionFilter, vtable 18BBFC0 slot +0x30 = D93700): with query = the bullet's flag and body = the body's filter info (+0x8C): if (query ^ body) & 0x7FFF8000 is 0 and query & 0x7FFF8000 is non-zero (same non-zero system group) the subsystem ID (bits 5 to 9) and "don't collide with" (bits 10 to 14) decide; otherwise the table bit table[query & 31], bit body & 31, decides. The layout matches physics-shkt.md#collision-filter-info-bits and GetCollisionGroup? D929F0 (((system<<5 | dontCollide)<<5 | subId)<<5 | layer). The game's own values have system group 0.

Basis: Ghidra read, REPORT.md §1.3

Addresses (build-specific RVAs unless indicated): D93700, 18BBFC0, D929F0

One frame of a bullet's collision

BulletMtSystem collision-update execution order

Evidence: static · Build: steam-678ccb46 · Fact ID: bullet-hit-flow

Order, from BulletMtSystem 237CF0 (all bullets through steps 3 and 4 first, then 5, then 6): (1) BulletInfo::MovementUpdate? 233BD0 runs a broad phase over the bullet's path AABB (HavokHitFn1); CustomCollector 232AA0 drops candidates for the shooter, friendly fire and so on. (2) Bullet_Collsion_Fn1 2359C0 (second caller 2349D0) splits the candidates in two lists; Bullet_Collsion_Fn2 1079D0 asks the filter (slot +0x30) per body: passes Flag 1 go to list 1 (BulletControl +0x8C8), passes Flag 2 to list 2 (+0x8D8). (3) 231840 then 11AA620 casts a ray over list 1 along path +0x8A0 to +0x8B0 with filter +0x890. (4) 234D20 replaces the path end +0x8B0 with the hit point and sets bit 4 (value 4) in the ammo state +0xAF4. (5) 231720 then 11AA620 shape-casts a sphere of m_flBulletShapeSize over list 2 on the shortened path. (6) 2321B0 handles the shape-cast result (damage, penetration). Because a Flag 1 and a Flag 2 hit can both happen, the bullet can damage and then stop.

Basis: Ghidra read, call order checked in 237CF0; the "damage then stop" part matches novae (ajane)'s memory of the test (REPORT.md §6)

Addresses (build-specific RVAs unless indicated): 237CF0, 233BD0, 232AA0, 2359C0, 2349D0, 1079D0, 231840, 11AA620, 234D20, 231720, 2321B0

Candidate collector: body selection and exclusion rules

Evidence: static · Build: steam-678ccb46 · Fact ID: bullet-collector-addbody

Reading guide: candidate collision bodies

This collector selects candidate collision bodies for each bullet. The source distinguishes the collection stage from the subsequent shape cast and damage processing.

  1. Look up a Havok body ID and resolve its associated game object.
  2. Apply the owner, death-state, prior-hit and team/friend checks when their documented flags require them.
  3. Apply the remaining class- and body-property exclusions.
  4. Add the permitted body to the collector; excluded bodies do not reach the later object hit pass.

Exact offsets, flag interactions, exceptions and function addresses are retained below in the original source trace.

How well the model fits, and how to use it

The model (stop if Flag 1 collides with the target's layer

Evidence: static · Build: steam-678ccb46 · Fact ID: map-raycast

Reading guide: map raycast sequence

The documented wrapper constructs a ray query in the Havok world and returns the nearest map hit under its filter.

  1. Read the input endpoints and derive a direction and length.
  2. Construct the layer-22 collision query, then invoke the native world cast.
  3. Collect the nearest result and its hit fraction, position, normal and body-related metadata.
  4. Distinguish this map ray from object shape casts and helicopter-specific ground checks; the native call paths are not interchangeable.

The full structure offsets, caller lists, special flags and source checksums remain in the original trace below.
