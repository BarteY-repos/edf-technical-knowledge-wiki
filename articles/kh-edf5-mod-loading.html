EDF 5 — Mod Loading (community source notes)

EDF 5Community Knowledge HubMod Platform
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Facts

Patcher.log order and AOB scan matches

Evidence: verified · Build: steam-5d11de53 · Fact ID: patcher-log

Patcher (v1.1.2) rewrites Patcher.log every run with, per patch file in load order, each AOB hit (label and RVA), each alloc address and each write, so another plugin loaded after Patcher.dll can map every patch's alloc blocks to live addresses. Log lines: Loading patch: <file>, AOB scan found <label> at <rva>, Allocated <n> bytes at <address> (size printed exactly as the .txt writes it), Patching <n> bytes at EDF5.exe+<rva> (or at an absolute address inside an alloc); skipped files log "AOB scan failed" / "Ignoring patch".

Basis: novae (ajane); pairing the 11 alloc lines in novae (ajane)'s 22 patch files with the log by order and size matched all 11; Patcher source (ltprintf("Allocated %s bytes at %p", sizeStr, …))

Attribution: novae (ajane), Patcher by BlueAmulet · 2026-10-14

EDFModLoader loads plugins in name order (EDF5_damage_number_display.dll, then Patcher.dll)

Evidence: verified · Build: steam-5d11de53 · Fact ID: plugin-load-order

EDFModLoader loads plugins in name order (EDF5_damage_number_display.dll, then Patcher.dll); Patcher.dll unloads itself after applying the patches ("Unloading plugin").

Basis: novae (ajane)'s ModLoader.log of 2026-10-14; the loader source shows why: the Patcher's EML5_Load returns false ("Patcher does not need to remain loaded"), see #plugin-keep-rules

Attribution: novae (ajane), EDFModLoader by BlueAmulet · 2026-10-17

EDFModLoader plugin acceptance conditions

Evidence: static · Build: steam-5d11de53 · Fact ID: plugin-keep-rules

EDFModLoader keeps a plugin loaded only if EML5_Load returns true AND PluginInfo.infoVersion is 1 (PluginInfo::MaxInfoVer) AND PluginInfo.name is non-null; any other outcome makes it call FreeLibrary (a DLL without the EML5_Load export is unloaded with a warning). PluginInfo { unsigned long infoVersion; const char* name; PluginVersion version; } is 24 bytes; PLUG_VER(a,b,c,d) fills the version.

Basis: loader source LoadPluginsFromPath (about lines 130-210): infoVersion = 0 before the call; loadfunc false logs "Unloading plugin"; novae (ajane); not run under the real loader

Attribution: novae (ajane), EDFModLoader by BlueAmulet · 2026-10-17

Non-recursive plugin DLL discovery

Evidence: static · Build: steam-5d11de53 · Fact ID: plugin-search-order

The loader finds plugins with one non-recursive FindFirstFileW(L"Mods\\Plugins\\*.dll") and skips directories, so a DLL in a subfolder of Mods\Plugins is never loaded and other files there (config, notes) are ignored (*.asi is searched too only when the loader's LoadASI option is on). EML5_Load runs immediately after each LoadLibraryW, in enumeration (file-name) order, so a plugin named to sort after Patcher.dll (for example zOMG.dll) runs after the Patcher has applied every patch.

Basis: loader source LoadPluginsFromPath; not run under the real loader

Attribution: novae (ajane), EDFModLoader by BlueAmulet · 2026-10-17

The Patcher clears its label table at the start of every .txt file (labels.clear()

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-labels-per-file

The Patcher clears its label table at the start of every .txt file (labels.clear(); patches.clear(); at dllmain.cpp lines 296-298 and again at 704-705; labels is a std::unordered_map<std::string, uintptr_t>), so one patch cannot refer to another patch's labels or alloc blocks by name. Its alloc blocks are committed PAGE_EXECUTE_READWRITE (VirtualAlloc, line 456) and nothing guards any memory after patching (writes to the module use VirtualProtect(PAGE_EXECUTE_READWRITE) and restore the old protection), so a plugin DLL can read and write every patch's block using the addresses in Patcher.log. A mod-control plugin must therefore be a DLL: a .txt cannot locate other patches.

Basis: Patcher source only; whether novae (ajane)'s Patcher v1.1.2 binary matches this copy is not checked; not run in game

Attribution: novae (ajane), Patcher by BlueAmulet (modding archive copy, Patcher/dllmain.cpp) · 2026-10-17

Patcher line parsing and semicolon comments

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-grammar-basics

Patcher grammar basics: on each line everything from the first ; is removed, then the line is trimmed (leading and trailing whitespace) and empty lines are skipped, so indented comment-only lines are fine. Addr: with nothing after it still sets the current offset; label Name stores the current offset under Name (letters / digits). ParseAddress accepts label+hex and label-hex. aob uses LightningScanner and takes the first match (no uniqueness check). No line-length limit.

Basis: novae (ajane); moved here from section 11 of the internals reference in the online.md conversion (archive/online.md)

Attribution: novae (ajane), Patcher by BlueAmulet · 2026-10-12

EDF5 patcher grammar edge cases

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-grammar-traps

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Parsing of lines and comments
  2. Cases that skip a file
  3. Case-specific input rules
EDF Knowledge Hub record — original wording — expand (1,245 characters)

Five details of the Patcher's grammar that discard a whole file or read a line differently than a human does: (1) an address takes ONE + or - offset (Label+3); Label+4-1 fails with "Invalid address offset" (4-1 is not entirely hex); ParseAddress tries the first +, else the first -, then needs the base to contain no whitespace. (2) Whitespace in the address part of Addr: data turns the whole line into data: T + 10: u32! 1 fails as "Unknown patch type: T + 10: u32". (3) Typed floats go through strtof and must consume the whole text, so 1.5f fails; integers use strtoull base 0, so 060 is octal 48 and 08 fails; an unsigned value with a leading - fails; the limit message is "Value limits exceeded: (min, max)". (4) In raw hex lines the characters [ and ] are dropped along with whitespace (patchfilter; the source comment calls them a "configurable data indicator"), a free marker that no installed patch checked so far uses. (5) Comments are removed first, from the first ; on, so a ;@ tag line is invisible to the Patcher; a UTF-8 byte-order mark before the first command would become part of line 1. Relative values are Addr - (here + 4), hence rel32! Target-1 before a trailing imm8 (RangerToggleSprint: 80 3D, rel32! toggleState-1, 00).

Basis: novae (ajane); its results on a file with each trap matched the messages the source would log. Not run through the real Patcher

Attribution: novae (ajane), Patcher by BlueAmulet · 2026-10-17

Patcher encoding behavior with non-ASCII text

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-utf8-comments-inert

The Patcher ignores UTF-8 non-ASCII text (Japanese, Chinese, accented letters) in .txt comments: it opens the file in text mode with no decoding and cuts each line at the first ; byte before parsing, and no byte of a UTF-8 multi-byte character is ; (0x3B: lead and continuation bytes are all 0x80 or above). The one encoding trap is a UTF-8 byte-order mark: its three bytes sit before the first ; on line 1 and stay as code. Legacy code pages (Shift-JIS, GBK) would be accepted too (their second bytes start at 0x40), but a tool that reads patches as UTF-8 shows them as replacement characters; save localized patch files as UTF-8 without a BOM. Checked for the EDF5 Patcher only; whether EDF6's Patcher build has the same reader is not checked.

Basis: BlueAmulet's Patcher source read (Patcher/dllmain.cpp lines 301-320: std::fstream(filename, std::ios::in), getline, find(';') / substr(0, scpos), trim, skip empty lines; modding archive copy); not run in game; confirms patcher-grammar-traps (5)

Attribution: novae (ajane), Patcher by BlueAmulet · 2026-10-29

Resolving live patch addresses from Patcher.log

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-log-format

Patcher.log is enough to find every patch's live addresses: per file it logs AOB scan found NAME at RVA for each aob, Allocated N bytes at ADDR for each alloc in file order (the label name is not logged: pair by order), then one Patching N bytes at ADDR or at EDF5.exe+RVA line per merged write run, or Ignoring patch when any line failed (then nothing of that file is written). AddPatch merges a write only with the last record when it is contained in or extends it; Apply logs and writes the records at the end of the file, only if the whole file parsed; alloc labels are stored as alloc - module base. A line Loading patch: starts a record, a blank line ends it; LF line ends.

Basis: Patcher v1.1.2 source and novae (ajane)'s Patcher.log of 2026-10-19; novae (ajane)

Attribution: novae (ajane) · 2026-10-20

Plugin unload log and failed EML5_Load

Evidence: static · Build: steam-5d11de53 · Fact ID: modloader-log-unloading

In ModLoader.log an Unloading plugin line right after Loading Plugin: X means X returned false from its load function (Patcher.dll does this on purpose). A plugin that sorts after Patcher.dll can read the finished Patcher.log inside its own EML5_Load; to tell that the Patcher ran in this process, compare the log's last-write time with the process creation time.

Basis: loader source and novae (ajane)'s logs of 2026-10-19

Plugin INI initialization paths

Evidence: static · Build: steam-5d11de53 · Fact ID: plugin-ini-locations

EDF5 plugins read their .ini once at startup, from different places: Eiton's Damage Number Display reads EDF5-Damage-Number-Display.ini from the working folder (the game folder; relative path in mINI::INIFile), a plugin can read its .ini beside its DLL in Mods\Plugins\ (path built from the DLL's folder, GetPrivateProfileStringW, writes a default file when missing). Neither re-reads it while the game runs. Eiton's sections: [FIXED_POSITION_DISPLAY] (Enabled, Change_Time, Display_Time, Font_Size, Pos_X, Pos_Y, Vehicle_Font_Size, Vehicle_Pos_X, Vehicle_Pos_Y) and [WORLD_POSITION_DISPLAY] (Enabled, Mode 1-3, Display_Time, Font_Size); some comments are Japanese. Source quirk: the WORLD section's Display_Time and Font_Size are read only if the FIXED section has those keys (has() checks the wrong section). A plain relative ini name passed to the GetPrivateProfile* API would resolve to the Windows folder (ops/build-tools.md#ini-relative-path).

Basis: novae (ajane)

Attribution: novae (ajane), Eiton (EDF5 Damage Number Display, MIT) · 2026-10-20

Win32 file API imports usable by memory patches

Evidence: static · Build: steam-5d11de53 · Fact ID: file-io-imports

EDF5.exe imports the Win32 file API, so a text patch can read and write its own file by calling the IAT slots (FF 15 rel32! <iat>) without a DLL. IAT RVAs: CreateFileW C97118, ReadFile C970F8, WriteFile C97110, CloseHandle C971B0, SetFilePointer C972C0, FlushFileBuffers C972C8, CreateDirectoryW C971A8, GetFileAttributesW C97148, DeleteFileW C970F0, GetModuleHandleW C97170, GetProcAddress C97350, LoadLibraryW C97200. Not imported: GetPrivateProfileString/WritePrivateProfileString, VirtualAlloc/VirtualQuery/VirtualProtect. A patch can already write a file this way (a debug log, through anchored game call sites ApiCreate/ApiWrite/ApiClose; radar.md).

Basis: import table read with LIEF; novae (ajane); the source finding said no patch did it yet

Addresses (build-specific RVAs unless indicated): C97118, C970F8, C97110, C971B0, C972C0, C972C8, C971A8, C97148, C970F0, C97170, C97350, C97200

Attribution: novae (ajane) · 2026-10-14

AngelScript sources shipped inside Root.cpk

Evidence: static · Build: steam-5d11de53 · Fact ID: rootcpk-script-files

Root.cpk holds two AngelScript source files the game compiles, mainscript/mainscript.as (packed 11376 / unpacked 36790 bytes) and network/network.as (4844 / 16102), plus an unused-looking mainscript/old/mainscript.as (10724 / 37317). Through the redirect, a mod file at Mods\MainScript\MainScript.as or Mods\Network\Network.as replaces the game's own script, so mod-owned script or config files must live in folders that mirror no Root.cpk directory. Root.cpk top-level folders: weapon, object, mission, ui, bat, network, sound, etc, map, hud, menu, menuobject, mainscript, defaultpackage, effect, debug, addon. Folder names free of collisions today: Mods\Patches, Mods\Plugins, Mods\Config, Mods\Scripts.

Basis: novae (ajane); not run in game (the redirect itself: #mods-redirect)

Attribution: novae (ajane) · 2026-10-14

Shared settings block initialized by first hook

Evidence: verified · Build: steam-5d11de53 · Fact ID: patch-settings-copied-once

A memory patch whose hooks read their settings from a working copy that the first hook to run fills once per game run (the preset-loader pattern, methods/lessons-blood-decals.md) ignores every later write to its setting lines: changing a setting in game (an overlay menu, Cheat Engine, any memory editor) takes effect only after the game restarts, while values written before that first hook runs (a plugin writing saved values at start-up) do take effect. A patch meant to be configured in game must read its setting lines live, re-copy the chosen row each frame or when the selector or a custom value changes (0x60 bytes per frame costs nothing), or say that a change applies at the next start.

Basis: novae (ajane)'s in-game test (2026-11-06) of an overlay menu changing a decal patch's key settings (custom block +40 / +44) during the run: the plain key never cleared decals, Alt+key (the start-up values) kept working even with the Alt setting at 0 and another key, the same through the menu's Hotkeys tab; novae (ajane)

Attribution: novae (ajane) · 2026-11-06

EDF5 patcher label resolution

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-one-pass-labels

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Top-to-bottom parse order
  2. When labels become available
  3. Effects of forward references
EDF Knowledge Hub record — original wording — expand (1,742 characters)

The Patcher reads a .txt once, top to bottom, and resolves a label when it reads the line that uses it, so a label must be defined (by aob, alloc or label) on an earlier line; only the alloc line that defines a settings block has to come before that block's value lines, and aob anchors the settings do not name can follow them. ParseAddress (about line 222) looks the base name up in labels; not found and not hex gives "Malformed patch input: Undefined label: X" and sets patch = false, so the whole file writes nothing (no second pass, no forward reference). alloc NAME SIZE with two arguments starts its search at target = mModule (near EDF5.exe), independent of any aob; only a three-argument alloc NAME SIZE Label needs that label first. alloc runs only while patch is still true, and a failure later in the file leaves the block allocated but never written (a few KB). Writes are collected (AddPatch) and applied only at the end, and only when nothing failed; aob scans cover the module image (mModule, mScanRange), so they see unpatched code and never the allocated block. A value line with no address before any address line writes at the current offset, which starts at 0 (the module base). The minimum order is therefore: alloc (plus any aob named by an in-code setting such as Label+1: u32! 128, or by the alloc's third argument), then the settings, then every other aob, the code and the hooks; in a patch with 20 anchors and a 10-line banner that moves the first setting from about line 34 to line 14. The grammar table in methods/patch-format.md section 1 agrees (alloc row: an optional third argument asks for memory near that address); its section 3 puts "GAME ANCHORS" before alloc, which is a convention, not a requirement.

Basis: BlueAmulet's Patcher/dllmain.cpp (MemoryPatcher::Apply, MemoryPatcher::ParseAddress) read in the modding archive copy; not load-tested: a reordered patch has not yet been loaded and its Patcher.log compared

Attribution: novae (ajane), Patcher by BlueAmulet · 2026-11-08

Patcher file iteration and patch application order

Evidence: static · Build: steam-5d11de53 · Fact ID: patcher-file-order

The Patcher applies the patch files in the order one FindFirstFileW(L"Mods\\Patches\\*.txt") / FindNextFileW walk returns them (non-recursive; subfolders are skipped), logging Loading patch: <name> before each; it sorts nothing itself, so the order is the file system's: on NTFS, name order (case-insensitive), which is the alphabetical order novae (ajane)'s Patcher.log shows (#patcher-log). A failure inside one file skips only that file (#patcher-log-format).

Basis: Patcher dllmain.cpp lines 737-754 (modding archive copy) read; NTFS name order from Windows' documented directory enumeration, not tested on FAT or exFAT

Attribution: novae (ajane), Patcher by BlueAmulet, KH chat 64 (source read) · 2026-11-08
