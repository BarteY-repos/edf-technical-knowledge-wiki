MDB loader dispatch and CMPL — valid models that still crash

ConversionCross-game ConversionEDF 5EDF 6
Technical reference · Exact inspected crash buffer, verified-offline archive rebuild; historical case studies, not universal format rules

A model can have a valid MDB0 header, survive an elementary parser check, and still crash the target game for two independent reasons: the game selects the wrong resource loader, or the archive decompressor supplies a corrupted model body. Both failures were isolated in an EDF5 → EDF6 desert-map port. They illustrate useful diagnostic methods, not universal conversion rules.

1. Resource registration selects a typed consumer

The map's registration table is not merely a list of filenames. Its resource names and suffixes participate in type selection. In the studied desert map, MAPB/MAC T1 registration indexed one object under .trb, while the actual decompressed resource was an ordinary .mdb model.

The observed chain was:

Map T1 entry 37 → sk_ptree007_11m_shuro.trb
RAB archive payload → sk_ptree007_11m_shuro.mdb
Actual payload → MDB model bytes, 53,806 bytes
Target consumer → TRB/tree header parser, not MDB parser

A crash dump showed the in-memory resource buffer was byte-for-byte identical to the deployed MDB (53,806 bytes). The normal EDF6 model validation path accepted that MDB. The faulty path instead treated base+0x28 as the TRB entry count and base+0x2C as a TRB table offset. In this model the value at +0x28 was 0x300000, which led to nonsensical tree-table traversal.

The useful rule is match the requested resource type to the actual resource; do not conclude that the model payload is malformed merely because the crash occurs during resource loading. A second T1 entry used a .mosb suffix; it too required separate role checking. Other entries used .mdx and .fmep roles. Do not globally rename every .trb to .mdx—this source-specific mismatch is not a generic conversion law, and valid TRB resources must retain their real type.

2. A valid MDB header is not evidence that the whole body survived decompression

A separate error occurred when the historical cmpl_compress_lz encoder in rab_mdb_upgrade2.py rebuilt compressed RAB entries. An independent strict decoder confirmed that 45 of 76 MDBs failed round-trip: their first eight bytes, including the MDB0 version marker, remained readable, but their remaining model bodies were corrupted.

An MDB version/dispatch check could therefore pass while later vertex, mesh, material or offset reads were using garbage. The offending historical encoder was withdrawn; that failure must not be attributed to the MDB ABI itself.

For the checked desert RAB, a literal-only CMPL stream was used as a safety workaround. Each group of up to eight literal bytes was preceded by a flag byte 0xFF, consistent with the decoder's bit-0-as-literal convention. After rebuilding from pristine source, verification reported:

Post-rebuild content Measured result
MDB entries 76/76 recognized as MDB0 version 0x20
MDB bodies Byte-identical to pristine source except the sanctioned version edit
DDS textures 348/348 byte-identical
Reported remaining problems 0 in the offline file audit

The literal-only encoding was a tested historical fallback, not a recommendation that all EDF archives should permanently abandon LZ compression. A correctly specified, separately round-trip-tested exact encoder is preferable when available.

3. A converter's validation checklist

For every transformed archive entry, check each layer independently:

  1. Entry identity: exact resource name, type, expected role, and registration reference.
  2. Decompression correctness: a strict independent decoder must reproduce the full expected payload, not just its magic/version bytes.
  3. Payload ABI: validate every offset, length, record count and expected semantic field after decompression.
  4. Container consistency: rebuild entry tables, offsets and cross-file references without moving unrelated resources unexpectedly.
  5. Runtime scope: a reproducible offline round-trip is stronger than a parser smoke, but cannot by itself prove all rendering or gameplay paths in the game.

The two cases explain why a crash labelled “MDB loading” can have a typed-dispatch cause or a compression-payload cause. They also explain why extension-wide replacement, changing only MDB0 version bytes, or checking only the archive header are unsafe repair strategies.

Evidence boundary

These are recovered observations from one historical EDF5 desert-map port and its archived source handoff. The 45/76 and 76/76 counts refer to that RAB content set, not all MDB assets or all CMPL encoders. Later production versions may use different encoders and resource tables. The general lessons are type-matched dispatch and full-body round-trip verification.
