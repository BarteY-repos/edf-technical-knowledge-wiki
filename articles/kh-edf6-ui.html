UI models have no perspective: Skin_Model (RTTI .?AVSkin_Model@ui@@, vtable 17F6050) transforms by diag(scale…

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-skin-model-transform

UI models have no perspective: Skin_Model (RTTI .?AVSkin_Model@ui@@, vtable 17F6050) transforms by diag(scale.x x 100, scale.y x 100, scale.z) and translates to the layout's center pixel (7F4D30), so one model unit is 1/100 pixel on the 1920 x 1080 UI plane; EDF6's HQ background layers at z 0..1.6 are all 19.2 x 10.8. EDF 4.1's UiBG uses a real perspective instead (edf41/ui.md#uibg-camera-edf41), so its background models need rescaling to port.

Basis: the author's reading ("H"), with model sizes measured from the files

Addresses (build-specific RVAs unless indicated): 17F6050, 7F4D30

Key binding restrictions (round 10, novae (ajane)'s outside set; source: pickups.md header)

Two checks stop a key from being bound: at 89D20B call 7CCD50 / test eax,eax / jz 89D22C / cmp eax,1 / jz 89D…

Evidence: static · Build: steam-678ccb46 · Fact ID: keybind-restriction-checks

Two checks stop a key from being bound: at 89D20B call 7CCD50 / test eax,eax / jz 89D22C / cmp eax,1 / jz 89D222, and in the assignment 7CDAF8 call 7CD9B0 / test al,al / jnz 7CDDF0 (rdi = the binding object, fields +0x04, +0x08, +0x14). TempRemoveBindRestrictions (no author named) retargets the first jz to 89D219 (74 05) and skips the second call. This is the shape of the EDF5 bind-restriction removal, whose comments call its 49005F write "the actual counterpart to EDF6's second patch point" (edf5/input.md#keybind-restriction-removal-writes).

Basis: the patch's fixed addresses decoded with rizin

Addresses (build-specific RVAs unless indicated): 89D20B, 7CCD50, 89D212, 7CDAF8, 7CD9B0

TempRemoveBindRestrictions writes six NOPs at 7CDAF8, but the call there is five bytes: the sixth NOP replace…

Evidence: static · Build: steam-678ccb46 · Fact ID: tempremovebind-overrun

TempRemoveBindRestrictions writes six NOPs at 7CDAF8, but the call there is five bytes: the sixth NOP replaces the first byte of test al,al (84 C0), and the leftover C0 with the following jnz bytes decodes as ror byte [rdi],0x85 then jmp 7CDB05. So in this build every pass rotates the first byte of the binding object ([rdi]) by 5 bits, besides skipping the check. Not tested in game; five NOPs (90 90 90 90 90) would skip only the call (al is already 0 there, since the jnz at 7CDAE1 after the previous test al,al was not taken).

Basis: rizin disassembly of the original bytes and of the patched byte string

Addresses (build-specific RVAs unless indicated): 7CDAF8, 7CDAFE, 7CDB05, 7CDAE1

Key config screen and binding store (round 24, All Forces)

Binding store (in GameDataMgr at +0x318, built by D3F90): per local player 10 sets x 0xFF action slots of int…

Evidence: static · Build: steam-678ccb46 · Fact ID: keybind-store

Binding store (in GameDataMgr at +0x318, built by D3F90): per local player 10 sets x 0xFF action slots of int32, read by D4260(store, player, set, action) = [store + 0x28 + (player*0xA00 + set*0xFF + action)*4]; two players of 0x2800 bytes each (D41F0), initialized flag +0x5488. Sets: 0 Ranger, 1 Wing Diver, 2 Air Raider, 3 Fencer (others unused). Vanilla uses actions up to 0x4D (0x4E ends a group), so slots 0x4F..0xFE are empty; the runtime reads D43C0(store, player, set, action) at 51 call sites, every action an immediate (largest 0x4E, 7A649). The whole 0x548C-byte block is saved and loaded as COMMON.CFG (7C0120, string 17F1498; write 7BBC30, read 7BC9E0 from 7C2AF0, both r9d = 0x548C), empty slots included. Key codes are the game's own: 0 unassigned (OptionPlayer_NoAssign, name table 1F56050; PS4 / Switch tables 1F560E0 / 1F56170), 0x01..0x0B pad A B X Y LT RT LB RB L3 R3 Back, 0x0C..0x11 mouse left, middle, right, wheel, side 1, side 2, 0x12..0x78 keyboard (names 11856F0; 11852C0(i) maps code 0x12 + i to a VK through the jump table 118554C, 0x67 entries); the poll 1188270 reads GetKeyboardState (stored by 1183880 into 21360E0) and mouse VKs 1 / 4 / 2 / 5 / 6 directly; the wheel has no held state. D4290 (key name, 7CD2B0 -> [20B2890]+0x318, "OptionPlayer_Key%s") indexes its table without a range check.

Basis: D4260 re-read with fn.py; the rest the author's reading (their offline audit pins the call count and maximum)

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-input-context

Menu input: the UI runs each frame as 119D270(sys, UiInput*, dt) (called at 7058F7), the input object being *(EDF+0x20B28A0)+0x5AE8; each top-level object gets slot 1 OnUpdate(this, ctx) through 11A45C0. ctx: +0 the raw UiInput, +8 the effective UiInput (filled only when the object's byte +0x28 is nonzero, 11A4540; else null), +0x10 float dt (84B716). Every input reader reads only ctx+8: the room's OnUpdate (8FE5BE), the HUiLayout base 84B490 (focus, cancel, button callbacks; also called by MainFrame 8C12B0), the component tree 7FAE70 and HUiBase::GetInput 8DAD00; the HQ's OnUpdate 89F740 is 84B490 plus a description refresh. So an OnUpdate called with a copy of ctx whose +8 is null is the game's own "not the input owner" state: network keep-alive, the member rebuild (+0x940), state publishing (901100), animation and chat go on, and the mouse is blocked too. GetInput 8DAD00 returns ctx+8, or null during a cutscene (7E4E30), when [this+0xD8]+0x111 == 0, [this+0x184] == 0, the weak pointer at +0x178 is alive (a child window open) or 7EBFD0(this+0x160) is false; the room's buttons respond by the same test. ctx+0 is not always the raw input: the tree dispatch (7FB0DD) gives children {&this+0x170, input or null, dt}. HQ child windows open through CallWindow 84EEA0 (wrapper 89DA40), the weak pointer kept at HUiLayout +0x5E8 / +0x5F0 (written at 84F3B1); the weapon and color selections are grandchildren of the class select ("inferred" in part). Room state +0xAC0: equipment 1, mission 2, room settings 3, options 5, start 6; the history writes 0, so it is no test alone; in the co-op room +0xAF0 / +0xB00 are weak pointers to message dialogs. The room's OnUpdate slot 180AC48 holds 8FDFE0, and EDF6Coop refuses to install unless it does (EDF6MultiSlot's plugin.cpp SlotTargets); EDFModLoader loads plugins in file-name order (its ModLoader.log: EDF6Coop before EDF6VehicleCrew). Inferred: the key that closes a menu must stay blocked until released, or it reads as cancel.

Basis: the author's static reading (the child-window nesting and the key release inferred); 11A4540 re-read with fn.py (movzx eax, b[rcx+0x28]; ret)

Weapon select and layouts: HUiHQWeaponSelect constructor 8B4280 (hook written but commented out), GetWeaponTextFromID D8A90 and GetWeaponListDataFromID E1CF0 (both hooked: the plugin adds its own weapons' texts and list entries), UiGetLayout 8456D0, a copy function 8B6BA0, a button function 8B8260, E23F0 and 839560 (commented out). The radar update 82B4D0 is hooked, and the radar HUD update is found by the pattern 0F 10 86 90 00 00 00 66 0F 7F 44 24 50 and patched with a 7-byte jump. The weapon select, Class Select and layout-loading findings are in ui-weapon-select.md (same constructor 8B4280, button function 8B8260 = the cell's lazy init, 8456D0 = template instantiation; D8A90 is called GetWeaponTextFromID here but read as a weapon-level getter at 8B5116 there: ui-weapon-select.md#ui-weaponselect-colors; both fit, it fills one record with the level and the texts: weapons.md#weapon-info-record).
