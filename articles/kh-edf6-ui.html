UI Skin_Model orthographic transform

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-skin-model-transform

UI models have no perspective: Skin_Model (RTTI .?AVSkin_Model@ui@@, vtable 17F6050) transforms by diag(scale.x x 100, scale.y x 100, scale.z) and translates to the layout's center pixel (7F4D30), so one model unit is 1/100 pixel on the 1920 x 1080 UI plane; EDF6's HQ background layers at z 0..1.6 are all 19.2 x 10.8. EDF 4.1's UiBG uses a real perspective instead (edf41/ui.md#uibg-camera-edf41), so its background models need rescaling to port.

Basis: the author's reading ("H"), with model sizes measured from the files

Addresses (build-specific RVAs unless indicated): 17F6050, 7F4D30

Key binding restriction checks

Evidence: static · Build: steam-678ccb46 · Fact ID: keybind-restriction-checks

Two checks stop a key from being bound: at 89D20B call 7CCD50 / test eax,eax / jz 89D22C / cmp eax,1 / jz 89D222, and in the assignment 7CDAF8 call 7CD9B0 / test al,al / jnz 7CDDF0 (rdi = the binding object, fields +0x04, +0x08, +0x14). TempRemoveBindRestrictions (no author named) retargets the first jz to 89D219 (74 05) and skips the second call. This is the shape of the EDF5 bind-restriction removal, whose comments call its 49005F write "the actual counterpart to EDF6's second patch point" (edf5/input.md#keybind-restriction-removal-writes).

Basis: the patch's fixed addresses decoded with rizin

Addresses (build-specific RVAs unless indicated): 89D20B, 7CCD50, 89D212, 7CDAF8, 7CD9B0

Attribution: TempRemoveBindRestrictions, novae (ajane)'s EDF6 outside set, novae (ajane) · 2026-10-16

TempRemoveBindRestrictions patch byte span

Evidence: static · Build: steam-678ccb46 · Fact ID: tempremovebind-overrun

TempRemoveBindRestrictions writes six NOPs at 7CDAF8, but the call there is five bytes: the sixth NOP replaces the first byte of test al,al (84 C0), and the leftover C0 with the following jnz bytes decodes as ror byte [rdi],0x85 then jmp 7CDB05. So in this build every pass rotates the first byte of the binding object ([rdi]) by 5 bits, besides skipping the check. Not tested in game; five NOPs (90 90 90 90 90) would skip only the call (al is already 0 there, since the jnz at 7CDAE1 after the previous test al,al was not taken).

Basis: rizin disassembly of the original bytes and of the patched byte string

Addresses (build-specific RVAs unless indicated): 7CDAF8, 7CDAFE, 7CDB05, 7CDAE1

EDF Knowledge Hub record — original wording — expand (1,989 characters)

Menu input: the UI runs each frame as 119D270(sys, UiInput*, dt) (called at 7058F7), the input object being *(EDF+0x20B28A0)+0x5AE8; each top-level object gets slot 1 OnUpdate(this, ctx) through 11A45C0. ctx: +0 the raw UiInput, +8 the effective UiInput (filled only when the object's byte +0x28 is nonzero, 11A4540; else null), +0x10 float dt (84B716). Every input reader reads only ctx+8: the room's OnUpdate (8FE5BE), the HUiLayout base 84B490 (focus, cancel, button callbacks; also called by MainFrame 8C12B0), the component tree 7FAE70 and HUiBase::GetInput 8DAD00; the HQ's OnUpdate 89F740 is 84B490 plus a description refresh. So an OnUpdate called with a copy of ctx whose +8 is null is the game's own "not the input owner" state: network keep-alive, the member rebuild (+0x940), state publishing (901100), animation and chat go on, and the mouse is blocked too. GetInput 8DAD00 returns ctx+8, or null during a cutscene (7E4E30), when [this+0xD8]+0x111 == 0, [this+0x184] == 0, the weak pointer at +0x178 is alive (a child window open) or 7EBFD0(this+0x160) is false; the room's buttons respond by the same test. ctx+0 is not always the raw input: the tree dispatch (7FB0DD) gives children {&this+0x170, input or null, dt}. HQ child windows open through CallWindow 84EEA0 (wrapper 89DA40), the weak pointer kept at HUiLayout +0x5E8 / +0x5F0 (written at 84F3B1); the weapon and color selections are grandchildren of the class select ("inferred" in part). Room state +0xAC0: equipment 1, mission 2, room settings 3, options 5, start 6; the history writes 0, so it is no test alone; in the co-op room +0xAF0 / +0xB00 are weak pointers to message dialogs. The room's OnUpdate slot 180AC48 holds 8FDFE0, and EDF6Coop refuses to install unless it does (EDF6MultiSlot's plugin.cpp SlotTargets); EDFModLoader loads plugins in file-name order (its ModLoader.log: EDF6Coop before EDF6VehicleCrew). Two-player input pad channel table

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-pad-table

The pad table EDF+0x2136530: two slots 0x4A0 apart, one channel pointer per button, written by 1182A00 (+0x48 analog value, +0x4C held, +0x4D = 0) from the poll loop 1188270 (base lea r13 at 1188315), which takes the bits from XInput wButtons. Channels: 0x50 / 0x58 / 0x60 / 0x68 up / down / left / right, 0x70 A (bit 0x1000, 1188A4D), 0x78 B (0x2000), 0x80 X, 0x88 Y, 0x90 Back, 0x98 Start, 0xA0 LB, 0xA8 RB, 0xB0 L3, 0xB8 R3, 0x40 / 0x48 the triggers; A is the bottom button (the XInput layout, no A / B swap). +0x4C is rewritten every frame from the current bits; +0x4D nonzero = suppressed (all set to 1 while 1183D60 is false), and readers treat it as not pressed.

ButtonApply does path scoping, not a focus click

Static, corrected by source author on 12 November. At 84EC17–84EC20, 83A0C0(window,button+0x110) resolves the button ID to a name via window +0x470, returning std::wstring* or zero; it is not a focus setter. 84EC32 writes that ID to the button's HuiCallbackInfo at +0x2B0, and 84EC25 passes it as event argument. While firing, "/"+name is temporarily appended to window action path +0x6B0, then restored. Plugin caller validates dynamic cast Component→HUiButton (RTTI 2062F00→2062F50) and HasAction before calling original 84EB40 with a slot0-returning callback; original's null-cast path can crash on HasAction.

Per-object update hook and input-availability gate

Static plugin call-site reading. HUiHQMain::OnUpdate vtable slot 1804DE0 targets 89F740, destructor slot 1804E00 targets 89F480 for detecting new instances even when addresses are reused. HUiBase::GetInput 8DAD00 returns non-null only when the HQ menu itself is reading input, without a covering child/dialog/transition. Layout lookup 839FD0(this,shared_ptr<Component>* out,const wstring* name) can resolve the select button. A safe hook calls original update first and gates its one-shot action by object lifetime and input availability.

Contributor-tested automatic select on HQ entry

Author-reported in-game test, dated 2026-11-12, though classified static in delta ledger. A world-map plugin triggered ButtonApply once per fresh HQMain object after original OnUpdate when GetInput became non-null. It opened select on single-player HQ entry; Back returned to HQ; Deploy opened select normally again; mission, difficulty and deployment worked; after retreat the new HQ opened it once more. Unresolved: whether this can fire during fade-in, how notice overlays inhibit it, whether the plugin's F2 pre-battle menu should close first, and interoperability with another room-slot chaining plugin. Do not claim multiplayer or overlay compatibility from this run.

Layout timeout is continuously invoked after expiry

Static. A layout may carry timeout_action and window_timeout; stock uses them only in LYT_TGSEND.SGO for a five-second ResultCallback(set_close_exit=1). Parser 84A700 stores timer at +0x638 (default −1), action functor +0x640 and arguments +0x650. Base update 84B490 subtracts dt at 84B702–84B742, then invokes action every frame at time ≤0 without resetting the timer. Putting CallWindow there would repeatedly reopen select; it is not a safe one-shot automation.

UI system objects and input-layer arbitration

SystemCore pointer and screen lists

Static RTTI/frame analysis. [EDF+20B2960] points into xgs::ui::System at its +0x88 subobject (vtables 17F85E0/17F85F0); the SystemCore base is [20B2960]-0x88 and is passed to frame update 119D270. Core fields: +0x18 pending inserts, +0x28 live screen list, +0x30 count, +0x38 queued operations, +0x48 input list. The live list is an MSVC std::list of shared screen pointers: node next/previous +0/+8, object +0x10, control block +0x18; pending inserts are moved at frame start. Treating the singleton global as the direct core base would shift all these offsets incorrectly.

xgs::ui::Object flags and embedded layer

Static constructor/list reads. Base screen xgs::ui::Object (vtable 1AE29B8, constructor 11A3EA0, enable_shared_from_this parent) has state bits at +0x18: 1 removed, 0x40 hidden, 0x20 reset on insertion, 4/8 used in cover processing. A live screen's RTTI comes from its vtable metadata; this does not validate every class across builds.

Layout ui_type to screen group mapping

Static layout/dispatcher table. Parser 84A920 uses ui_type=2 when absent; mapping in 7E3220 through jump table 7E328C is 1→5, 2→3, 3→4, 4→2, 5→7, 6→6, 7→2, 8→8. The group reaches screen +0x30 via 11A45B0. Stock HUD (type 7), backgrounds/frames (type 4) use group 2; default menus/pause/results/dialogs group 3; loading/save group 5; chat/soft keyboard group 7; mouse pointer group 8. Group controls input/sort order; it is not merely an SGO child order.

Input layer ranks, channel masks and claim modes

Static. A 0x14-byte layer stores group +0, channel mask +4, rank +8, active byte +0xC, registered byte +0xD, mode +0x10. Registration at 11C1010/11823B0 keeps the list at [20B2888]+0x38 group-sorted (new equals after older); 11C0FB0 reinserts changes. Before screen sort, 1182520 walks highest group first and gives rank zero to the top. Mode 0 activates if no higher mode-0 layer claimed matching bits; mode 1 if no higher mode-0/1 layer claimed them; 2 always activates; 3 never activates. Screen layer at +0x1C exposes active at +0x28, initially registers mask −1/mode 3, and changes mode later (setter not traced). Player layer +0x348 registers group 0/mode 0 with the player's bit. A screen claiming that bit likely takes player input; that handoff remains inferred.

Inferred screen order and covering pass

Source: unverified inference, no in-game check. Sort key high bits use the root screen layer rank at +0x24; lower ranks represent higher-priority input groups, so ascending sort apparently visits top screens first. The cover pass 119D3D0..119D40C lets a screen with state bit 4 claim its channel and marks later same-channel screens with bit 8 unless bit 0x10 exempts them. This is consistent with upper screens covering lower ones but is not independently demonstrated as visible occlusion or exact input flow.
