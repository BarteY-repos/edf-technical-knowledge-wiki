EDF6 EOS Datagram Framing, Reliability and State Flush

EDF 6Community Knowledge HubNetworking
Technical reference · Editorial synthesis of contributor static/game observations; per-claim grades below

R86 scope note: For the ordinary audited shipping class-4/class-5 path, the native builder capped the first physical aggregate at 1164 B; a 1400 B defensive check alone does not prove oversize reachability. Current reconciliation.

Overview

EDF6 uses EOS P2P as a transport while the game’s own controller manages record framing, acknowledgements, replay suppression and periodic state flushes. “EOS unreliable” does not mean every game-level record has no retransmission.

Format, API or behavior

The contributor’s static reading reports an EOS size limit of 1170 bytes against a looser native 1400-byte record rejection threshold. Native outgoing state is flushed around 90 ms. Records use a packed size/type header; reliable records include sequence envelopes and acknowledgements. A hypothesized six-frame state-phase interaction is marked unverified despite reported measurements.

Evidence and exact technical details

The following selected source observations retain their original evidence level and build-specific details. Follow their links for the complete evidence method, addresses and attribution.

Net eos packet cap — static

One EOS P2P packet carries at most 1170 bytes (the EOS SDK's limit); the game neither splits larger data nor reports it, so anything above the limit is lost.

Net size check 1400 — static

The game's own size check is looser than EOS's: the packet controller refuses a record only above 1400 bytes (12D0BE6), so a reliable message between 1170 and 1400 bytes is accepted, refused by EOS on every try and resent until the room drops its members (packetfit.h: eight times over about 26 s; netclass.h gives a reliable record 6 tries, #net-record-format; the two counts were not reconciled).

Exact source: View evidence and source details · build steam-678ccb46

Net flush 90ms — static

The game flushes its outgoing packet queue on a 90 ms timer and sends only the newest state record then, not every frame's. The interval is a float written by the packet controller's constructor 12CB5F0 at 12CB66C (41 C7 46 58 00 00 B4 42, mov dword [r14+0x58], 90.0f), fixed at start; the controller's update is 12CECC0, its flush 12CEA10.

Exact source: View evidence and source details · build steam-678ccb46

Net datagram format — static

A datagram of the packet controller (eos::packet::ControllerImpl, vtable 1AF4FF0): records gather per peer in a buffer (12CFFD0) that is flushed (12CEA10; called from the send path 12CE99A, the acknowledgements 12CEDBB and the per-peer builder 12D0020) when the next record would pass 1100 bytes (0x44C) and on the 90 ms timer. The flush writes an 8-byte header (two random bytes, a 16-bit datagram number, a CRC32C of the plaintext records taken at 12CEA79), encrypts the records with AES-CTR (7B8060, called at 12CEBAA; same length) and hands the datagram to EOS on the same thread (12D0120 -> vtable slot 3 12D2EF0 -> 12C8BC0, always EOS_PR_UnreliableUnordered). The receive 12CDF20 decrypts with D2360 (at 12CE16B), checks the CRC and drops a datagram whose number and CRC it has seen (12CE1F3..12CE1FE).

Net record format — static

Records inside a datagram start with a u32 size << 20 | type and size bytes follow (the receive loop 12CE515 advances by size + 4). SendUnreliable (12D1040) writes the data record alone, lost with its datagram. SendReliable (12D0AC0) first writes an envelope, u32 0x00401200 (type 0x1200, size 4) and a u32 sequence number, and keeps the record until the peer acknowledges it: 6 tries, the first resend after 700 ms (1FEF040), the wait growing by 1FEF048 each try; the receiver acknowledges every envelope (12CE4FF -> 12CFCD0) and drops a record it already has. Types 0x13xx, 0x14xx and 0x18xx are the controller's own (acknowledgements and the like, 12CE2B7..12CE2D7); a data record's type is ((sub & 0xF) | id << 4) << 8 (12C2E59); the event layer's batches are type 0x3000.

Exact source: View evidence and source details · build steam-678ccb46

Net event batch builder — static

Event messages queue in a per-peer builder that sends only once it holds more than 250 bytes (761E60, the 0xFA from 74ED6D), so small messages of one frame share a record; 761E60 sends unreliable when the builder's +0x628 is set. Framing costs at most 26 bytes per message (750380 / 7504A0 at most 12, 74D3E0 at most 14), then 12 for the reliable record and 8 for the datagram header.

Exact source: View evidence and source details · build steam-678ccb46

Net position every 6 frames — unverified

A player's machine puts its own position and facing into its sync record only every 6th frame; with the 90 ms flush (#net-flush-90ms) at 60 fps the two periods lock together, so another machine either gets the position in every packet or in none for seconds: measured, 1.3-5.9% of a remote player's packets held a position and 6% a facing, and remote players were drawn a median 1.57 m (up to 17 m) off and up to 117 degrees turned.

Version notes and limitations

The 1170-byte transport limit and frame synchronization findings derive partly from third-party mod source/readmes; they were not freshly packet-captured in this release. For EDF5 homologs and Sandlot RUDP see the earlier network references.
