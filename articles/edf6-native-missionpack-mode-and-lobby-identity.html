EDF6 MissionPack identification: native verification, ModeList and online room DLC field

EDF 6Missions & ScriptingMissions
Technical reference · Per-build native EDF.dll path tracing plus historical offline custom-pack tests; no new two-peer verification

An EDF6 MissionPack has several distinct identities. The selected numeric MissionPack row, the native validation-name family, the network-room field named DLC, and license/entitlement checks are not interchangeable. The following facts come from a specific studied EDF6 binary and historical custom-pack diagnostics, not from a universal rule across all builds.

Native membership and validation-name paths

The retained binary study identified these build-relative entry points:

Studied native function EDF.dll-relative address Observed role
MissionPack membership/verification lookup +0xD92B0 Resolves the native DLC/pack membership check
MissionPack validation-name mapper +0xE3F80 Uses the MissionPackName1 and MissionPackName2 classes

These offsets are build-specific. Neither implies that every custom MissionPack is natively licensed, or that the correct solution is a global DLC-check bypass. Official MP01 and MP02 follow their native paths.

Historical compatibility extensions used odd/even MissionPackName1/MissionPackName2 classification for higher custom slots. That is an observed extension requirement, not evidence that the unmodified game natively supports arbitrary packs 03–99.

Why the room attribute DLC does not mean entitlement

The native room-attribute table includes SEARCH_TYPE, DLC, MISSION_NO, DIFFICULTY, ARMOR_LIMIT and WEAPON_LIMIT. In the studied path, the published DLC value is the selected ModeList row's MissionPack ID. A room using custom MP03 therefore publishes DLC=3, even when the custom mission is not paid DLC.

The corresponding room lookup compares the requested MissionPack ID and online mode type. No 0–2 clamp was found on this specific path. This proves only how that lobby-field path is interpreted; it does not prove successful two-peer joining or universal native custom-pack entitlement.

Resource path identity can precede active-mode identity

During one MP06 custom-pack selection, the game requested /cri_bind/MISSION/MISSIONLIST_MISSIONPACK06.OFFLINE.LIST.SGO while MissionMgr+0x14FD0 still read -1. A lookup using only the currently active manager slot therefore missed a resource whose exact request path already contained MissionPack06. The resulting UI later tried to divide by an effective mission count of zero and raised 0xC0000094 at EDF.dll+0xDD2A9 in that binary. See the full native failure case.

Reported two-PC incompatibility in a custom extension

The contributor Knowledge Hub records a reported HF5.48 custom-MissionBundle two-computer test in which peers loaded different missions/cutscenes. This is negative evidence for that specific extension and custom mission setup, not proof of a native vanilla EDF6 lobby defect. A local successful offline or host-only launch cannot substitute for a successful remote-peer join and synchronized mission start.

Observed CONFIG ModeList and cross-file reference fields

In the studied EDF5-port / EDF6 custom-MissionPack CONFIG schema, the static research identified:

Field Observed interpretation
0 GameMode_Offline/Online_MissionPackNN class identity
5 MissionPackNN.MST save/progression namespace
6 companion LIST/localized TXT/IMAGE references
8 offline 0, online 1
9 logical MissionPack ID, shared by offline/online pair
12 retained profile shape in official and custom rows; exact meaning is not asserted

The generic CONFIG ModeList loader read the runtime row count dynamically in the studied binary. This observation does not establish that arbitrary custom packs bypass license checks or that any pack number is universally supported. The network-room DLC field and the ModeList pack ID should be compared with actual LIST resource identity rather than inferred from a directory name.

Later tested custom-pack boundaries

In September 2026 modded-game checks, MP03→MP07 and MP04→MP08 custom relocations reached an offline mission. MP08 progression was separate from MP04 and MP08 permitted creating an online host. A real second-peer join/start was not tested. An earlier MP07 black screen was traced to an incomplete AC-only fixture; it was not evidence of a numerical pack-ID ceiling. These findings concern the tested extensions, not stock EDF6.

What cannot be inferred

  • A game lobby field called DLC is not sufficient evidence of paid ownership.
  • A valid on-disk LIST is not sufficient evidence that the selected runtime ModeList references it.
  • An online host creation result does not establish a remote-peer join.
  • One extension's parity rules do not automatically describe stock EDF6.

Source boundary: The native offsets and room-field relationship were audited statically for the retained binary. The custom-slot workaround and later MP07 result belong to separate historical modded runtime tests, not a new validation performed for this wiki.

Native manager versus network-room identity — deeper detail

The studied native FindOuterMode(manager, modeType, MissionPack) lookup uses the selected ModeList row's +0x74 MissionPack and +0x80 mode-type fields and returns an outer mode index. This is distinct from the room attribute named DLC and the currently committed pack stored at manager +0x14FD0. For the exact build-specific offsets and call chain, see native mode selection and Package memory and async response pack publication.
