NetworkBullet selectors — contact geometry and state boundaries

EDF 6Engine RE & NetworkingNetworking
Source-backed research / case study · Exact native binary through Engine RE R17; class-state repair remains open

Why a reliable selector does not guarantee identical construction

A lost batched subtype1 publication has no automatic subtype1 application-layer retry, and later cumulative counters may restore shot quantity without the old random or charge history. This is independent of normal NetworkBullet selector traffic being retained/retried by Sandlot. The complete example is in Weapon RNG and remote projectile reconstruction.

NetworkBullet selectors are later projectile-state publications. They can correct spatial/contact outcomes, but their payloads are narrower than the complete internal state of several projectile classes.

Per-class selector availability in the analyzed Bullet hierarchy

These flags are native Bullet+0xE8C selector gates, not a complete inventory of unrelated SceneObject replication. The common BulletBase constructor initializes the field to 1 (selector1). Later class writers give these three RNG-sensitive families different effective states:

Bullet class Observed selector state Direct consequence
FlameBullet02 0x1: selector1, not selector0 External-object reference/contact context can be sent; class motion scalars +0x11D0/+0x11D8 are not restored
LightningBullet01 0x1: selector1, not selector0 Local path/RNG Bullet+0x130 remains unsynchronized by selector0/1
SolidExpBullet01 0x0: constructor clears inherited selector1 Common selector0/1/2 is unavailable in the audited normal path; random detonation countdown +0xF00 is not recovered

Selector0 (0x2) is the common spatial state path (Bullet+0xCC0/+0xCD0); selector1 (0x1) is an external-object contact/reference context, not another position snapshot. Selector2 (0x4) has collision/contact semantics on the examined missile paths. Static evidence does not imply that a different engine subsystem can never destroy or reposition a projectile; it establishes only that these recurring NetworkBullet messages do not carry the three listed class-state fields.

Selector2: collision/contact record transport

Recovered selector2 contract:

  • Bullet+0xE8C bit 0x4 gates selector2;
  • TX: 0x2330B0;
  • RX: 0x232E80;
  • records live in an 0x50-byte collision/contact vector at replicated projectile state +0x6C0;
  • vector data/capacity/count are at +0x6C8 / +0x6D0 / +0x6D8.

The wire payload carries:

  • external-object identity/context;
  • one auxiliary dword;
  • contact point XYZ;
  • contact normal.

It does not carry the complete pre-contact record. In particular, the qualified payload omits the record's pre-contact position, local query flag and the class-internal RNG/history recovered for other projectile families.

Contact outcome can change trajectory

0x231640 consumes the latest contact-record normal and can update motion state +0xB90 with the canonical reflection operation:

v' = v - 2 * dot(v, n) * n

or route through a class-specific handler.

Selector2 is therefore not cosmetic telemetry: it can alter later projectile trajectory/contact geometry.

Selector2 ownership is narrow in shipped data

The complete direct writer census found selector2 bit 0x4 enabled only in RTTI-owned construction paths for:

  • MissileBullet01;
  • MissileBullet02.

The qualified shipped WEAPONTABLE corpus contains 90 active rows using those classes: 85 MissileBullet01 and 5 MissileBullet02.

Those 90 have zero intersection with the earlier subtype1_batched_receiver_local initial-fire envelope. Do not generalize selector2 missile semantics to every projectile class or to subtype1 creation.

Selector1: contacted-object-local frame

Selector1 fields +0xC20/+0xC30 are recovered as contacted-object-local projectile position and contact normal/direction.

When the contact-frame path is active, the receiver reconstructs/anchors world position +0xB80 from the contacted object's current transform and bypasses ordinary motion/collision integration branches for that state.

Selector1 can therefore change later hit/collision geometry. It is not merely a visual attachment marker.

What selectors 1/2 do not restore

Neither selector1 nor selector2 restores the class-internal state identified by the R14–R16/R17 reconciliation for:

  • FlameBullet02 motion scalars;
  • LightningBullet01 per-projectile RNG/path state;
  • SolidExpBullet01 detonation countdown.

The same limitation applies even when the selector bytes themselves are delivered reliably.

Reliability boundary

R17 proves normal selector0/1/2 traffic uses Sandlot mode0 retained reliability above EOS. A transient physical packet loss can therefore be recovered for the bytes that were serialized, using sequence retention, resend, ACK retirement and receive deduplication.

That mechanism does not invent omitted fields. Consequently there are two distinct failure classes:

  1. delivery failure — serialized selector bytes were not yet successfully delivered/applied;
  2. state-model incompleteness — selector delivery succeeds, but the receiver still lacks class-internal state that was never serialized.

Treating both as generic “packet loss” obscures the actual repair surface.

Repair implication

For Flame/Lightning/SolidExp divergence, the higher-value repair target remains initial projectile seed/state parity before class evolution diverges, not broad duplication of selector1/2 or Soldier orientation forcing.

Unresolved: the minimum sender seed/state and exact receiver injection point for those class-internal states remain runtime/RE frontiers.
