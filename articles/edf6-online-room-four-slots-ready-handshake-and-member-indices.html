EDF6 online rooms: four slots, member indices and READY handshake

EDF 6Game technical referencesNetworking
Technical reference · Source-code/static interpretation with explicitly labelled contributor gameplay observations; no new game runtime

The original EDF6 online room is a four-member system in several separate layers: eos::Users, per-peer packet sessions, the mission context, HUD widgets and loadout tables. The four-player limit is therefore more than one menu setting. The details below refer to the examined steam-678ccb46 build and are not a description of an eight-player modification.

User slots are not always HUD player numbers

The room's eos::Users collection assigns a new member the first available slot (Users::Add, RVA 0x12B7F50). Removing a member empties a slot; it does not compact everyone upward. A later join can reuse the vacancy. The User+0x40 network/member slot, used in packets and initial synchronization, must not be assumed to equal the User+0x48 HUD/loadout player index. The latter is assigned through mission and roster synchronization. A source harness observed a lost start-sync record after different machines saw leave/join slot orders differently; this is not a reported stock-production crash in every session.

Original room construction and UI also use four entries for the voice-talk display, status lamps, packet sessions and other per-member arrays. A larger mod has to reconcile these independent limits; changing a single room-capacity integer is insufficient.

Ready is a state machine, not merely the host pressing Start

The HUiRoom screen exposes Request_ReadyWait. Members enter a ready handshake that tracks the roster count, content entitlement/availability checks and a short start countdown. The examined handshake states are:

State Meaning in the source investigation
0 Idle
1 Start initiated
2 Own ready state submitted
3 Roster locked / counting down
4 Mission-start commit

The exact state-object names are inferred from call sites; their numeric values and branching are from code. A changing member count or incompatible selected content can cancel or block the transition. The source reports a 1000 ms countdown stored when the ready flow starts; it is not a complete guarantee of wall-clock start latency under loading or network delays.

HUiRoom's transition to mission start is a local screen/state commit; it should not be confused with the native MissionMgr::LoadPackage or a fresh SetGameMode call. See MissionMgr package model for those separate responsibilities.

Can someone join during a mission?

In the source contributor's actual online gameplay, players could leave mid-mission, but a newly joined member stayed in the room until the next mission, rather than materializing mid-combat. That observation is contributor-verified gameplay; the separate four-slot limits and UI/state details are static binary research. Do not use a room-entry observation as proof that a live mission supports dynamically rebuilding every player object.

EDF6 EOS lobby limits, slot imports and browser evidence

Source: edf6/lobby-room-cap-sites.md, thirteen canonical records, from static build-specific native analysis and the contributor's recorded lobby tests. A room's EOS capacity, client admission flow, roster arrays, HUD placeholders and local packet contexts are separate constraints; changing one constant does not establish multiplayer compatibility above four players.

EOS startup and Steam external-auth wrapper routes

EosCore_InitializePlatform (12AD070, caller 726830) invokes EOS_Initialize, builds integrated-platform options with a Steam entry and calls EOS_Platform_Create. The native path decodes obfuscated credentials, which this page does not reproduce. EosConnect_LoginExternal (12C2010) calls EOS_Connect_Login; Steam ticket path 73FC60 supplies credential type 0x12. EosAuth_Login (12C24A0, caller 725A80) uses external-auth login type 7. Related wrappers 7CC6B0 open a Steam profile by steamid, and 95B750 reports an invite-dialog error on failure. These are call-site observations, not a successful end-to-end auth replay.

Create flow sets maximum members twice

In RoomCreateFlow_Step (742980), state 0 constructs EOS_Lobby_CreateLobbyOptions API version 9 with MaxLobbyMembers=4, public PermissionLevel=0, local user and bucket EDF6:Region, then invokes EosLobbyCreate_RequestAsync (12B3160) for EOS_Lobby_CreateLobby. Only after successful creation does state 1 invoke BuildCreateLobbyModification (749AD0) and set maximum members to 4 again through 12BFE20. These are distinct paths requiring separate scrutiny.

Join request cap and room-full preflight

RoomJoinFlow_Step (743050) passes local max-members 4 to EosLobbyJoin_RequestAsync (12B39A0), backed by EOS_Lobby_JoinLobby. State 1 polls completion at this+0xA0 (flag +8, result code +0xC). The cap is a qword immediate at 7430C2 (mov [rbp-11h],4). Separate PrepareJoinCurrentLobby (78BB60) treats the room as full if 3 < memberCount, with cmp eax,4 at 78BDE9. The creation, join-request and full-room checks cannot safely be conflated.

Two local cap patches did not locate EOS admission rule

Contributor-verified negative probe. Patching both immediate 7430C2 and comparison 78BDE9 to 2 still caused NetworkInstance_QueueJoinRoomEvent (780730, log OnlineSys_JoinRoom) before recurring 78BB60 calls. Therefore 78BB60's room-full test runs after the request is admitted into this flow; the actual decision is deeper in EOS join handling. This test does not establish that increasing the same constants allows additional members.

Source plugin signatures and fallback fragility

The plugin scans .text and falls back to build-specific RVAs if a signature is missing or non-unique. Reported entry signatures begin: 749AD0 (BuildCreateLobbyModification) 40 55 53 56 57 41 54 41 55 41 56 41 57; 743050 (RoomJoinFlow_Step) 48 89 5C 24 08 4C 89 44 24 18; and 78BB60 (PrepareJoinCurrentLobby) 48 89 5C 24 10 48 89 74 24 18. Join-cap 7430C2 matches 48 C7 45 EF 04 00 00 00 0F 57 C0 F3 0F 7F 45 0B with immediate at match+4; room-full 78BDE9 matches 83 F8 04 0F 93 C0 49 8B with immediate at match+2. These are provenance markers, not stable patch instructions across builds.

Room browser search filters and serialized keys

SerializeLobbySearchQuery (739DE0) submits filters through EosLobbySearch_SetParameter_Wrapper (12AFDC0): SEARCH_TYPE first (one or two calls; comparator opcodes 3/5/0), REGION (key ID 0x14, value 2), then HIDDEN, CREATE_TIME, mission-range fields, DIFFICULTY, ARMOR_LIMIT, WEAPON_LIMIT, chat, UGC and DLC. The trace logs Lobby_CreateQuery :: %ls. These are observed serialized query fields, not proof that disabling one filter reveals every EOS lobby.

A full 4/4 lobby stayed absent after filter suppression

Contributor-verified negative test (26 March 2026): suppressing the SEARCH_TYPE parameter at EOS_LobbySearch_SetParameter did not make full 4/4 rooms appear; each browser run showed exactly 20 results. The author did not see EOS_LobbySearch_SetMaxResults called and suspects the SDK's default EOS_Lobby_CreateLobbySearchOptions.MaxResults, with only medium confidence. The author attributes missing public full rooms to EOS's documented searchable-while-not-full condition for advertised public lobbies (PermissionLevel 0), not a second proven client-side filter. Twenty results is an observation of this test, not a universal hardcoded game-side cap.

Browser row data, paging and X/Y formatter

UpdateLobbyListWidget (8E7F00) copies cached result pairs from HUiLobby+0x7E0 into +0x990 via LobbySearchInfo_CopyResultPairs (73AB20); it skips a row if rowData+0x78 is zero. PopulateLobbyListRowLabels (8E79A0) formats current/max rowData+0x78/+0x7C using L"%d/%d" at 956E50. SearchInfo+0x42 is hasNextPage, +0x50 is the 0x10-byte-pair array, +0x60 its count; 73A6B0 copies source bytes +0x70..+0x118. One log measured 2 current and 4 maximum at the formatter. The browser UI reflects cached EOS results rather than independently determining server capacity.

Compact lobby attributes and remapped IDs

BuildRoomListEntryFromLobbyDetails (744AB0) maps six compact attribute keys w0–w5 into entry offsets +0x38, +0x3C, +0x40, +0x44, +0x48, +0x4C. The inferred association, medium confidence, is SEARCH_TYPE, DLC, MISSION_NO, DIFFICULTY, ARMOR_LIMIT, WEAPON_LIMIT. Source logs returned IDs 717, 823, 824, 772, 911, 873 rather than the raw create-room numbers, implying an intermediate remapping. entry+0x5C is reported as a story-completion float. Do not equate those remapped IDs with the original create-option values.

Online slot stride and overlapping loadout views

The online-player region begins at GameStatus+0x14B80 with nominal stride 0xD4. BuildOnlinePlayerObjectInfo (595960) reads object+0x48, rejects indices ≥4, and addresses +0x14B80+slot*0xD4. Debug loadout dump 59DC90 reads companion fields at +0x14C78+slot*0xD4: class ID, variant and four equipment/weapon IDs. SoldierBase_ApplyLoadoutTree (5914C0) also reads +0x14B80+slot*0xD4+0xFC, and 5A3F90 reads another block at +0x14D1C+slot*0xD4. Since those offsets extend beyond a single 0xD4 record, the source interprets them as companion or overlapping views of a larger structure; treating them as a flat fixed-size record would be incorrect.

Partial slot-less-than-four gate and distinct snapshot counts

ImportOnlinePlayerSlotSnapshot (790600, wrapper 792120) copies its large loadout block into +0x14C78 only for slot indices 0–3, while other fields accept any nonnegative index. It writes the imported active count at +0x14FF8. MatchOnlinePlayerObjectsToImportedSnapshot (790F70, wrapper 793450) matches names, assigns object+0x48 and stores a matched-object count at +0x14FD0; other room-state writers 904B30/70C1C0 also write this latter field. These two counters have different meanings; an attempted capacity extension must not treat one as the other.

Fixed-four member index and HUD placeholders

GameImpl_InitializeSessionControllers (7364A0) stores the local session-member index masked by &3 at [[this+0xE0]+0x10]. UiText_ReplaceRoomPlayerPlaceholders (71F950, caller 720930) handles exactly %PLAYER1% through %PLAYER4% with count 4. These are distinct fixed-four assumptions even if a host's EOS member count changes. The source did not identify a packet message with exactly four records; the absence of such a hit is a search limit, not proof that all network formats are scalable.

Net-send context classes, thresholds and per-tick drain

NetSendContext_Init (761C80) sets class at +0x10, flush threshold +0x18, payload +0x20/+0x28, queue +0x30, reliability byte +0x628 and send counter +0x630. Event constructor 74E9B0 builds two class-4 transmit contexts with threshold 0xFA (250) and unreliable delivery, while factory 753C60 constructs a 0x648-byte reliable variant; 75FF10 sends class 1 with threshold 200; 763F40 uses class 5 with threshold 300 through reliable/unreliable contexts. Drain 762E10 stops when send counter exceeds 2, giving at most three flushes per context per tick and deferring later packets. These are message-queue conditions, not proof of a four-player packet-array limit.
