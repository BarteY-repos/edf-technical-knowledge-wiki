EDF6 object SHKT validation: joint pivots, mass properties, shape bounds and collision filters

UniversalMaps & NavigationCollision & PhysicsEDF 4.1EDF 6
Technical reference · Retained source validator and native object-corpus measurements; new EDF6 runtime testing not performed

An object SHKT does not merely contain a valid collision shape. Its body names, constraint endpoints, mass-property sources, broadphase bounds, filter groups and SGO animation links must agree. A tagfile that parses successfully can still mis-collide, hold a part at two different pivots, or fail while the game constructs the object.

This guide describes bounded checks implemented by a retained EDF4.1→EDF6 source validator. The format observations are also cross-checked against the retained EDF6 SHKT Editor analysis (Ktaro, MIT-licensed project); the counts below are historical measurements from that source, not a fresh native-corpus scan.

Physics body identities and their SGO consumers

For the target hknpPhysicsSystemData, bodyCinfo.name is the semantic link back to an object's SGO animation_from_ragdoll / ragdoll_from_animation mappings and accessory-part references. A mapping pointing at an absent body is not a harmless extra entry: the native code may dereference it during construction. Check all referenced names before loading the mission, and check for duplicate or empty body names.

Each body's materialId and motionPropertiesId are indices into the containing system's arrays; 0xFFFF means no index and is only valid for the studied static-body cases. A dynamic body cannot inherit an absent motion-properties row just because the serialized field is representable.

The older EDF4.1 Havok 2014 tagfiles begin with magic 1E0DB0CA CEFA11D0. The port retains a legacy hkpRigidBody reader for these resources; its body names still bind to SGO names, but its shapes use a different layout from target hknp and were not covered by the target-shape validator. Never claim identical validation breadth for the two versions.

Joint pivots must meet in the same world-space point

A two-body constraint stores a local pivot in body A (transformA) and body B (transformB). Their transformed world points should coincide:

pivot_world_from_A = position_A + rotate(orientation_A, pivot_A)
pivot_world_from_B = position_B + rotate(orientation_B, pivot_B)
error = distance(pivot_world_from_A, pivot_world_from_B)

A stock validation census reported 3,051 joints whose dual pivot points agreed within approximately 0.8 mm. The retained checker uses 1 cm as a warning threshold, matching the referenced editor policy. A moved bone with an unchanged physics joint can make a rotating turret appear welded or resist rotation; both ends and their parent reference pose need a coherent model-space frame. See vehicle ragdoll re-fitting.

Shape-derived data are part of the payload

Several Havok structures contain bounds or mass information derived from the shape geometry rather than from the object's visible MDB mesh:

  • A convex hull's planes must contain its vertices (within the source's bounded approximation tolerances). The retained validator uses 1e-3 m absolute or 2% of the hull extent; an old stock hull could exceed the 1 mm error while staying inside the proportional bound.
  • A compound's AABB and SIMD tree must enclose the transformed child instances; stale trees lead to incorrect broadphase behavior even when all mesh vertices are valid.
  • The shape property key 0xF100 is the retained Havok mass-property record. A body with massDistribution = null relies on its shape's properties instead. Historical source annotations report 11,281 stock object shapes carrying such data. A body that lacks both sources is unlike the measured stock population; the downstream engine outcome was not proven and should be flagged as a warning, not an invented crash certainty.
  • A body with explicit massDistribution need not read the shape's fallback mass record. Replacement hulls and their stand-in proxies can therefore legitimately use different mass-distribution policies.

A zero-error parser, a visually aligned MDB, and a consistent tagfile offset table do not prove these invariants.

Collision-filter bit fields

For the examined collisionFilterInfo uint32 layout, use the following bit ranges:

Bit range Consumer meaning in the retained object validator
0..4 Collision layer; the target game overwrites these bits for the examined runtime path
5..9 Subsystem
10..14 Don't collide with mask/category
15..30 System group; all bodies in one native file shared one group in the retained census

A writer must not flatten the full 32-bit word into a single layer enum. The runtime may replace the low layer while keeping subsystem and group bits.

Practical qualification gates

Validate names → body indices → material/motion IDs → joint frames → reference pose → derived shape bounds and mass in that order. Report any unsupported 2014 shape family or missing tagfile section explicitly. A supported set of structural checks remains different from a Windows EDF6 runtime result (physics creation, movement, collisions, damage and cleanup).
