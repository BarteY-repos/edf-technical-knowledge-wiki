Two script systems

Mission scripts are BVM bytecode (app:/Mission/name/mission.bvm) run by the game's interpreter (around 114F38)

Evidence: static · Build: steam-5d11de53 · Fact ID: mission-script-systems

Mission scripts are BVM bytecode (app:/Mission/<name>/mission.bvm) run by the game's interpreter (around 114F38); their natives are called by opcode number (for example ShowLayout 126EE0 is called only from the interpreter case at 1158CE). Separately, an AngelScript layer drives the menus and the system: 3DCF80..3DE67C registers its natives with their declarations (strings), including bool ApplyResult(bool is_mission_clear), ResolveResult(), ClearResult(), PlayerCount(), Mission(), Save(…), GetStartupRoutine() (103 declarations, all system / menu API: angelscript-natives).

Basis: disassembly and declaration strings; novae (ajane)

Addresses (build-specific RVAs unless indicated): 114F38, 126EE0, 1158CE, 3DCF80, 3DE67C

Attribution: novae (ajane) · 2026-10-12

The BVM interpreter 114F38 dispatches with movzx eax,dl

Evidence: static · Build: steam-5d11de53 · Fact ID: bvm-interpreter-dispatch

The BVM interpreter 114F38 dispatches with movzx eax,dl; movzx eax,[base+0x117968+rax]; jmp [base+0x1176E8+rax*4] (dl = the opcode's low byte; each case re-checks the full opcode).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 114F38, 117968, 1176E8

ShowLayout stack-frame handling

Evidence: static · Build: steam-5d11de53 · Fact ID: showlayout-r11-frame

ShowLayout 126EE0 keeps its entry rsp in r11 (mov r11,rsp at entry) and still addresses its frame through it after 126F0D (+0x2D, mov rbx,rdx; mov rsi,rcx): lea rcx,[r11-0x38] at 126F13. Code run in place of the instructions at 126F0D must leave r11 unchanged.

Basis: disassembly (fn.py, KH chat 63); novae (ajane)

Addresses (build-specific RVAs unless indicated): 126EE0, 126F0D, 126F13

MissionScript state transitions 0 through 3

Evidence: static · Build: steam-5d11de53 · Fact ID: missionscript-state-values

The MissionScript state at [[125AB40]+28]+F8 takes 0 = created, 1 = started (set at 1148F8), 2 = playing (set at 126614 by the native behind interpreter op sub-id 0xB, called at 115261), 3 = ended (EndMission). The 16 timers at MissionScript +36C count only in state 2 (114D16). Whether state 1 covers the loading screen is not settled, so only the transitions to 2 (start) and 3 (end) are certain; a once-per-frame poll of this field answers methods/unexplored.md's "Mission start event".

Basis: disassembly only, not observed in the running game; novae (ajane)

Addresses (build-specific RVAs unless indicated): 1148F8, 126614, 115261, 114D16

Attribution: novae (ajane) · 2026-10-24

Per-player mission-clear markers

Evidence: static · Build: steam-5d11de53 · Fact ID: mission-clear-bits

Mission clear marks inside ApplyResult 3E3160 (FevGrave: "once per player"): r9d = [r8+0x4C] difficulty (r8 = save) at 3E31C0, start = esi (mov edx,esi), but cmp r9d,3 / cmovge edx,r9d at 3E31CE starts Hardest and Inferno at themselves; the loop to 3E3212 sets bits (bts) in the byte [save + 0x566C + class*0x200 + mission] (class [rbp], mission [r8+0x48]): Easy 0x01, Normal 0x02, Hard 0x04, Hardest 0x08, Inferno 0x10. So a vanilla Inferno or Hardest clear marks only itself; Normal and Hard also mark the lower ones (FevGrave: "Vanilla 5/6: 01 03 07 08 10"). The per-player outer loop supports #local-player-count over the "difficulty loop" reading of applyresult-difficulty-loop: the difficulty loop is the inner one.

Basis: FevGrave's disassembly notes; anchor InfClr5 unique; the start and the cmovge decoded with rizin

Addresses (build-specific RVAs unless indicated): 3E3160, 3E31C0, 3E31CE, 3E3212

Attribution: FevGrave (InfernoClearsAll_EDF5; FevGrave reports the patch works in game, 2026-10-06), novae (ajane)'s EDF5 outside set, novae (ajane) · 2026-10-16

EDF5 menu and mission harness

Cold boot: menu sequence and confirm-button path

Evidence: verified (source-reported) · Build: steam-5d11de53 · Fact ID: edf5-cold-start-menu-walk.

The scripts ran in order Boot → StartToTitle → SlotSelect → ModeSelect → HQMain. A source-controlled series of six pad-A confirmations passed the autosave notice, title, default slot (saveslot00) and default Offline mode to reach HQ, where another A starts the highlighted “Start Mission”. At HQ [125AB30]+0x50 read zero, and the game loaded saveslot00/DEFP_M00.MST and MAIN.GST. A source harness that swapped HQMain for PlayMission_Offline on M1 Easy reached state 2 at [[125AB40]+0x28]+0xF8. Timing matters: earlier A presses were consumed before their screen was ready; this is not an unconditional six-frame skip.

Basis: source's cold-boot run and script-state observations.

EDF5 createCoRoutine takes a wide MSVC string object

Evidence: verified (source-reported) · Build: steam-5d11de53 · Fact ID: edf5-createcoroutine-wide-string.

The script dispatcher calls createCoRoutine("string " + name + "") and waits. The coRoutine createCoRoutine(const string &in) entry is 27E00 (registration 29234, declaration E8C0B8); the extra any @+ overload is 27B30 (291FD, E8C080). At the native boundary, the string argument in rdx is an MSVC std::wstring object, not a narrow std::string: 32-byte object, inline buffer or pointer at +0, size at +0x10, capacity at +0x18, inline space for eight wide characters. It presents a candidate hook point for routine substitution analogous to EDF6, but the source had no working EDF5 debug routine to substitute.

Basis: source's ABI observation; avoid exporting the AngelScript declaration as the native string layout.

M1 tutorial restrictions and M3 test mission

Evidence: verified (source-reported) · Build: steam-5d11de53 · Fact ID: edf5-m1-tutorial-not-a-test-mission.

Offline M1 “Today's Schedule” (m000) constrains controls for its tutorial, making it a poor automated movement/combat test. The source test harness instead defaults to M3 “Crisis in Base 228: Part 1” (m003, Black Ants only). The choice is a test-harness convention, not a rule that an EDF5 mission can never start at M1.

Basis: source's in-game mission comparison, source.

Menu-script and mission transitions: native follow-up

Source: EDF Knowledge Hub revision 5b589ca, build steam-5d11de53, novae (ajane). The three previously merged edf5-cold-start-menu-walk, edf5-createcoroutine-wide-string and edf5-m1-tutorial-not-a-test-mission records remain anchored in the earlier section. Below are the 18 other mission-flow.md source records. They are static native or extracted-script observations, with inference and proposed harness changes identified separately.

Script entry, the offline menu route and save-state persistence

Shipped main menu (static): MainScript.as has main, Boot, StartToTitle, SlotSelect, ModeSelect, HQMain, mission and results routines, but no EDF6-like Debug_StartOffline shortcut.

Offline transition (static): normal flow is Boot → StartToTitle → SlotSelect → ModeSelect → HQMain → PlayMission_Offline → PlayMission_Common → Result_Offline. Mode Select sets the mode, loads the associated save state, updates counters and unlocks downloadable content before HQMain. Mission Common retries if the Mission result requests retry.

Event-show branch disabled (static): IsTGSMode at 24980 is a constant-false stub, so the script paths that bypass slot/mode menus or show TSGEnding are not reached through that condition in the shipped build.

Entry override field (static, proposed use untested): GetStartupRoutine 3DEED0 reads wide string mainscript+0xC8; empty falls back to Boot. No normal writer was identified. Pre-setting a custom routine there is a proposed hook for a harness, not a tested patch.

ScriptBuilder sections (static, proposed hook untested): loader 41D4A..41D73 uses CScriptBuilder include tests and ProcessScriptSection before building its AngelScript module. A plugin could inject a supplemental section at the 41D69 call, but successful injection into this build was not demonstrated.

Save/mission fields (static): GameDataMgr 125AB30 stores mission row +0x48, difficulty +0x4C, save slot +0x50; constructor defaults are 0/1/0. Slot Select writes the slot, and the COMMON.CFG save path uses saveslot%02d, so skipping selection without another writer likely targets slot 00.

Mode setter (static): SetMode native 3E1530 validates the requested ModeList entry and passes it to 8ABB0; the offline campaign uses mode 0. Title and mode-load natives also show a loading layout during save operations.

Mission selection restoration (static): RestoreMissionSelect 3E3C00 copies stored mode-save row and difficulty +0x5664/+0x5668 into active +0x48/+0x4C. PlayMission_Common runs the mode application step, so changing only the active pair can be overwritten. For a repeatable harness, the saved pair must also be considered; the HQ writer of that pair was not traced.

Title controller initialization (static, extrapolation untested): HUiTitle code at 547490 adjusts gamepad/keyboard mode flags and reassigns controller slots. A startup skipping the title may preserve different defaults; explicitly forcing keyboard mode is a proposed test setup, not a verified one.

Second local controller and mission player list

Reset to one player (static): ResetControllerAssign 3E4E30 writes local count GameDataMgr+0x2459C=1, resets the ControllerManager and binds player zero to device zero.

Second-device handshake (static, some input bits inferred): 5A11D0 polls menu virtual-pad records for devices 1–3 and, on a suitable press, binds player two's slot via 43270 and stores device index at ControllerManager+0x9944. Device 0, containing keyboard and mouse, is not offered as the second device.

Mode Select joins second player (static): HUiModeSelect update 53F100 responds to that handshake by writing local count two at GameDataMgr+0x2459C. Directly writing the count without a device assignment is an incomplete, untested split-screen harness.

Mission spawn list (static): 11D5E0 builds player/pad slots for local offline players and, in online modes, from session members. The spawn routine 11D860 passes the local count to the view layout. Whether two local players can also participate in an online room was not resolved.

Network location, mission loading and results lifecycle

Mode versus online flag (static): setter 8ABB0 holds mode at GameDataMgr+0x38 and reads ModeList's online property to configure pause behavior. Reading related pause-mask state may indicate online mode, but safety of unsynchronized reads from a plugin was only inferred.

Location state (static): native Network_SetLocation writes a synchronized integer at 125AC08+0x2B8. Enum values 0..5 represent booting, boot complete, lobby, room, playing and loading. Mission Common moves to loading and later back to room even offline; mission script custom call 10000 moves to playing, with online synchronization differences.

BVM load bookends (static): mission interpreter sub-IDs 0xA/0xB start/end loading through 126360/126550, show lyt_Loading.sgo, increment/decrement a shared loading counter and transition MissionScript state from 1 to 2 while resetting timers and sound state. That counter has other consumers, so it is not an exclusive mission signal.

Result screen (static): offline/online results both reach Result_Common, which loads result layouts, calls native ResolveResult for loot, ApplyResult, saves, waits for dismissal and then calls ResetResult. Those native calls bracket the result UI lifecycle.

Residual multiplayer debug scripts (static): Network.as contains DebugStartup and DebugMission routines and registered debug natives for two-machine room/join/sync flows. The source did not establish that a shipped menu or startup path still creates them; they do not replace an offline mission-debug entry.
