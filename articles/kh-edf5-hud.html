EDF 5 — Hud (community source notes)

EDF 5Community Knowledge HubGameplay & AI
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Armor gauge (HUiHudPowerGuage)

Armor gauge current and max integer text

Evidence: static · Build: steam-5d11de53 · Fact ID: armor-gauge-cap

The gauge text is (int)cur " / " (int)max, read from the soldier's floats +0x1FC (current) and +0x1F8 (max) (agrees with radar.md's GameObjectBase HP fields), truncated at 4CC78C / 4CC790, and capped at 999999 by mov eax,0xF423F at 4CC798 and four cmp/cmovg on that eax (cur, max, and the stored copies [rbx+0xAE0] / [rbx+0xAE4]), so one imm32 at 4CC799 raises all four (BlueAmulet's hard-coded method writes the same address). The bar fill is the uncapped float ratio.

Basis: FevGrave's Ghidra notes; anchor unique

Addresses (build-specific RVAs unless indicated): 4CC78C, 4CC790, 4CC798, 4CC799

Attribution: FevGrave (ArmorDisplayCap; offset method credited to BlueAmulet), novae (ajane)'s EDF5 outside set · 2026-10-16

Vehicle weapon aim line

At 3ABDD4 cmp dword rbx+0xB40,0 / jg hides the line while the weapon cools down

Evidence: static · Build: steam-5d11de53 · Fact ID: aim-line-cooldown

At 3ABDD4 cmp dword [rbx+0xB40],0 / jg hides the line while the weapon cools down; the patch also keeps the game's override test test byte [rbx+0x111C],1 (blocked) and the "bad-state" path at 3ABDE6 ([rbx+0x11EC]). Line color floats at [rcx+0x114], +0x118, +0x124, +0x128 (ready = the patch's vanilla red 0, 0, 0.5, 0.5). metoxys's WeaponAimLineContextual keeps the line during cooldown in yellow (white as an option).

Basis: the patch's anchor and code

Addresses (build-specific RVAs unless indicated): 3ABDD4, 3ABDE6

Attribution: metoxys (WeaponAimLineContextual), novae (ajane)'s EDF5 outside set · 2026-10-16

Chat

Chat limits: the character limit is mov dword rbp+0x48,0x20 at 4FCF35 (imm byte at 4FCF38, default 32)

Evidence: static · Build: steam-5d11de53 · Fact ID: chat-limits

Chat limits: the character limit is mov dword [rbp+0x48],0x20 at 4FCF35 (imm byte at 4FCF38, default 32); the text input width is mov r8d,400 at 495468 (imm32 at 49546A), after shl ecx,2 at 495465, which BlueAmulet's IncreaseChatLimit replaces with xor ecx,ecx (width 680, limit 128 in the file).

Basis: the fixed addresses decoded

Addresses (build-specific RVAs unless indicated): 4FCF35, 495465, 495468

Attribution: BlueAmulet (IncreaseChatLimit, inspired by Souzooka's), novae (ajane)'s EDF5 outside set · 2026-10-16

The chat word filter starts with cmp word rbx,0 / jnz at 3EF7A0 (the same bytes as in EDF 4.1)

Evidence: static · Build: steam-5d11de53 · Fact ID: chat-filter

The chat word filter starts with cmp word [rbx],0 / jnz at 3EF7A0 (the same bytes as in EDF 4.1); BlueAmulet's RemoveChatCensor jumps over it (EB 6E).

Basis: the patch's anchor

Addresses (build-specific RVAs unless indicated): 3EF7A0

Attribution: BlueAmulet (RemoveChatCensor), novae (ajane)'s EDF5 outside set · 2026-10-16

EDF5 HUD native machinery

Source: novae (ajane), EDF Knowledge Hub revision 5b589ca, EDF5 Steam build 5d11de53. The forty source IDs below are reconciled by mechanism, rather than copied as forty independent unreviewed source notes. Unless stated otherwise these are source-reported static disassembly findings, not new in-game tests. EDF6 comparisons are version-specific; addresses must not be ported between builds.

Camera ownership and HUD draw jobs

The EDF5 camera's HUD-enable byte is +0x180 (EDF6 uses +0x200). Constructor 622290 enables it; draw 623FB0 returns immediately when it is zero. Unlike the source-observed EDF6 script-only writer, CharacterGhostCamera at 9F75A refreshes it every frame using the target's look-at override state. Whether that state is always intended to suppress the HUD is inferred, not a traced script rule.

Player HUD setup 4B47B0 creates radar, power, weapon, rescue, chat and status objects from named layouts, and appends their shared pointers to the camera's HUD list at +0x188. Frame step 3D7D30 schedules 6133C0 for up to four view slots: a live weak camera handle becomes a ring-queue job 624280, and the render thread dispatches 623FB0. Merely creating a HUD object without camera-list registration does not establish that it will draw.

During 623FB0, the renderer selects a viewport from the camera's +0x110..0x11C, walks the +0x188 list, invokes each object's virtual draw and restores the D3D11 viewport. The end of that walk (6241B8) is a per-view completion point, not a guaranteed safe arbitrary-thread hook. HUD subclasses draw through vtable slot 3 (+0x18), receiving a draw context and viewport; named examples include HudPlayer_RescueMessage, MultiPlayStatus, Chat and FollowerDurability. Crosshair's body was not decoded.

A HUD object's mode +0x60 selects its own view/projection: sampled mode 1 uses identity view and an orthographic pixel rectangle (5BE700), while other modes use a Z-negating view and perspective (5BE600, near 0.01, far 4000 in the inspected code). Which subclasses use each mode was not fully inventoried. Remaining unknowns include resolution-dependent scaling by class, some unnamed HUD creators, crosshair draw behavior, layout-hosted custom images and loader-safe threads. These are open questions, not implementation guarantees.

Projection, fitted viewport and split-screen layout

Umbra camera setup 6226E0 copies each view-slot rectangle into camera +0x110..0x11C and constructs projection from width/height, FOV and clip planes. World-to-screen 4B64F0 applies view, perspective and a viewport matrix, divides X/Y by W when nonzero, and returns a rectangle-local pixel position with Y downward. For behind-camera W, it negates X/Y/Z; it does not add the viewport origin as the EDF6 helper reportedly does.

Aspect helper 60C120 fits a 16:9 rectangle to the screen, tracking fitted width/height and black-bar offsets. Camera HUD draw scales from the fitted rectangle to the window/swap-chain size, with letterbox-specific offsets when flag [115408C] is set. A world anchor's rectangle-local projection must therefore be composed with its view rectangle and this window transform; raw 4B64F0 output is not automatically an absolute desktop pixel.

Mission spawn 11CE60 lays local player viewports out as side-by-side columns: player index p gets (p*W/n, 0, W/n, H), or the whole rectangle for one player; the slot also receives that player's camera, controller and HUD. The debug screen_rect(slot,x,y,w,h) handler 6299F0 can replace any of four slot rectangles and refresh targets; the separate player console path prepares the same column layout. These are specific console/native paths, not a promise of arbitrary supported gameplay layouts.

Gauge layout base 4C9D50 uses scale 0.7 for multiple local players, divides width by player count and applies the recorded ±48-pixel-side offsets. Many EDF5 gauge files match their EDF6 counterparts structurally, but EDF5 has one weapon-gauge TextNumeric where EDF6 splits numerator/denominator, a distinct armor DefText offset and subweapon positioning, and no lyt_HudDamage. Its mission ui_type=7 list lacks EDF6-style mission alert banners; chat-window and mouse-pointer layout families do overlap.

HUD position helper 4B4590 converts pixel coordinates (top-left origin, down-positive Y) to normalized coordinates, then through the inverse of the HUD object's own view/projection; rescue prompts and nameplates use the sampled depth -600. Draw helper 4B4360 submits the resulting model/view/projection and sets family-specific draw-utility states. Its mode handling must be preserved by any replacement HUD renderer.

World/post/HUD render ordering

EDF5's frame step queues scene views before it steps objects and the camera, then queues HUD jobs; those jobs read the camera later on the render thread. The source infers that world-anchored HUD can therefore project from a camera pose one simulation step newer than the underlying world image. This possible offset was not independently seen in-game.

For an active view the renderer queues a post-combine 5DE540 or a no-post copy 5DE700, with conditional intermediate full-screen and slot-3 paths; it always ends with a context job. After scene/post submissions, the frame thread queues a depth clear, the HUD viewport job, state synchronization, utility effect job, and only then 6133C0 HUD jobs. This recorded queue order is stronger evidence than treating HUD as an undifferentiated final draw call.

Texture, sprite and button resources

Nameplate texture setup 4BCA00 constructs a sampler, opens app:/Hud/OnlineHudTexture.rab via cache-aware loader 5AF3A0, and resolves named Texture group members with 4BC880. Sampled slots include arrow outcursor01.dds, gauge frame/fill, dead/pinch icons and the four-cell player_lamp.dds sheet. These are resource identities, not evidence that every new DDS will be admitted to the loader.

Draw utility 9DD10 binds two sprite resources; A4E00 uploads matrix/color/state and emits vertices with (x,y,z,u,v) lanes through 5EFF80. The radar and nameplates use this path. Button-text field HuiTextureButtonTextField references app:/ui/PS4Buttons.dds, a 260×52 uncompressed 32-bit five-cell sheet without mips. No Xbox/Switch sheet was seen in the examined code, which is not a broad hardware-support test.

Unverified modding options: source code suggests archive replacement, cached external RAB loading followed by the native sprite calls, or a plugin-managed D3D11 texture at the list-walk endpoint. None of these three proposed custom-image routes was tested in-game; loader thread safety is unresolved. Do not treat this as a ready-made supported HUD extension API.

Fonts, direct text calls and UI text-field wrapping

Font manager global [125B120] initializes TT_NewCezanne-DB.ttf alongside two AR UDJingXiHei faces; language associations of the latter are inferred from their names. Rescue text and nameplates build a 0x34-byte font descriptor, acquire a locked font handle, begin 5E89C0, measure with 5E7400, draw through 5E8D40 and release the handle. Draw strings are zero-terminated UTF-16; the sampled nameplate can emit several labels from one handle.

Native text draw 5E8D40 has 14 reported call sites, spanning layout/menu text fields, textured button labels, chat bubbles, nameplates, rescue prompt and other UI code. The low-level measure/draw functions break only on explicit newline, and the draw path caps a run at 512 UTF-16 units; that does not mean a higher-level layout text field never wraps.

Text-field layout 4B1220 rebuilds runs when dirty. Flags choose markup parsing, wrapping, no-tags wrapping, or unwrapped shrink/center modes; low-level attribute-to-flag mapping is incompletely traced. Wrapper 600530 measures each character and allows breaks at explicit whitespace/punctuation and broadly between CJK characters, with Japanese line-start restrictions and a suspected unsplit digit-run rule. Slot 8 draw 4B13A0 renders already laid-out runs (text, font descriptor, RGBA and position), optionally clipping to the field. Thus direct world-HUD text calls and layout/menu text use the same glyph primitive but not the same wrapping stage.

Chat, followers and multiplayer nameplates

Chat bubbles project the speaker's position roughly 1.9 m upward, then offset the bubble toward screen center; a second unraised projection is used for selected bubble kinds/health states, but that condition's purpose remains unclear. Follower health bars project roughly 2.0 m above soldiers, draw a 60-pixel-width fill from HP +0x1FC / max +0x1F8, and recurse into subordinate follower lists. Their four color bands and the soldier-config-controlled visibility byte are source observations, not a universal team overlay.

Multiplayer status renderer 4BABF0 builds each frame's player boxes, projects a 2 m-high anchor (0.8 m downed), constrains it to an inner screen region and draws health, vehicle status, text and icons. A same-vehicle case moves the plate to a fixed column; the exact saved-state flag behind special name formatting was not decoded. The inner clipping rectangle spans 60% of the viewport, with an anchor limit at 55% of that inner half extent: final center range 17–83% of W/H, a rectangle, not an elliptical boundary.

Placed plate boxes are checked against prior boxes; collisions move the newer plate by 1.5×box height toward the screen's vertical middle and retry. The measured draw consists of an arrow, frame, cyan HP fill, optional yellow vehicle bar, player/class icon and multiple text fields; the actual scale of those pixel coordinates across all display sizes remains open. Status byte 0/1/2 denotes normal, downed and captured in the sampled update: downed uses red labeling/death icon and a lower anchor; captured uses a blinking pinch icon/name.

The edge arrow appears only when the original anchor lies beyond 1.2× the clamp boundary. Its opacity rises toward full by 2.2× that boundary, and its rotation is derived from the off-screen player's direction relative to the clamped plate. An on-screen plate has no such arrow; being pinned at the box boundary does not itself make one visible.
