Facts

Root.cpk parsing and obfuscated UTF tables

Evidence: static · Build: steam-5d11de53 · Fact ID: cpk-format

Root.cpk can be read in place with a small reader: UTF tables XOR-obfuscated (LCG seed 655F, multiplier 4115), file data offsets relative to 800h, most files CRILAYLA-compressed. Header: CpkMode 3, Tvers "CPKMC2.49.32, DLL3.24.00", Align 4, 4,687 files.

Basis: used throughout the session: all 4,687 entries listed, settings layouts and MainScript.as decoded; novae (ajane)

Attribution: novae (ajane) · 2026-10-14

SGO tree nodes, header and typed values

Evidence: static · Build: steam-5d11de53 · Fact ID: sgo-format

SGO files (layouts and config data) are a tree of 12-byte variables {type, size, value} with a header "SGO ", version 102h, root variable count and offset, name count and offset; type 0 = array of size variables, 1 = int, 2 = float, 3 = UTF-16 string; for types 0 and 3 the value is an offset relative to the variable itself. Name table entries are 8 bytes {string offset relative to the entry, variable index}.

Basis: decoded lyt_HUiHQGameSetting.sgo (33 named roots), the other HQ settings layouts and every ui/lyt_*.sgo without errors (86 files); values match the strings and on-screen geometry; novae (ajane)

Attribution: novae (ajane) · 2026-10-14

Map .rab files are SSA archives of CMPL-compressed entries (MDB0 v20 models and DDS)

Evidence: static · Build: steam-5d11de53 · Fact ID: map-rab-cmpl

Map .rab files are SSA archives of CMPL-compressed entries (MDB0 v20 models and DDS). CMPL: a tag, a big-endian uncompressed size, then an LZSS stream (4 KB ring, initial write position 0xFEE, flag byte read LSB first with 1 = literal, 2-byte token: ring position (b0<<4)|(b1>>4), length (b1&15)+3). .mac and .mad are MARC archives (file table: the last count*0x18 bytes of the file, name offsets signed and relative to each entry): .mad holds only the Havok collision.hkt; .mac holds small .mab model-type stubs (79 in jyousuicity), .trb/.erb/.grb, map.mapb, map.mapo, map.rmpa. map.mapb (jyousuicity): 132 T1 type records of 56 bytes, 7842 T2 records of 68 bytes each pointing back to a T1; T1 names unreliable, none an sk_bd* building module, so building placements probably live in .mosb groups (not in the .rab; not located). Maps live in Chunk01.cpk as map/<name>.rab plus weather variants (_cloudy, _cloudy2, _evening, _fine, _finecloud, _sunset) that hold no .mdb; because entries are compressed, a plain byte search of a .rab/.mac for a shader name finds nothing.

Basis: decoder derived and run over map/nw_jyousuicity in Chunk01.cpk: 1250 files decoded, 0 failures (625 MDB0 v20 models plus DDS); later used over every map archive (shaders.md#water-shader-maps); novae (ajane); MDB parsing with the converter's mdb_tool.py in File_Storage/Reference; not run in game

Attribution: novae (ajane) · 2026-11-04

Big-endian SGO variant and field encoding

Evidence: static · Build: steam-5d11de53 · Fact ID: sgo-big-endian

Some SGO files are big-endian: magic \0OGS instead of SGO\0, every header field, variable and name-table entry big-endian and strings UTF-16BE, otherwise the layout of #sgo-format; defaultpackage/config.sgo is one.

Complete original research record — expand (1,257 characters)

config.sgo's ModeList (#defaultpackage-config) has six modes of 12 values each, in order GameMode_Scenario (offline), GameMode_OnlineScenario, GameMode_Offline_MissionPack01, GameMode_Online_MissionPack01, GameMode_Offline_MissionPack02, GameMode_Online_MissionPack02. Value 5 names the mode's mission list files; value 6 holds five per-difficulty arrays (Easy to Inferno) of eight values each; value 7 is 1 in the online modes; value 8 is the pack number (0, 0, 1, 1, 2, 2) that a weapon's source must be 0 or equal to for it to drop (drop-items.md#loot-roll-candidates); value 11 is [1, 2] offline and [1] online (local player counts, unverified). Per-difficulty value 2 is the drop level [low, high, spread] (#modelist-drop-level-values). The other per-difficulty values (value 0 [5, 15] on offline Easy to [160, 280] on Inferno; online modes fill values 6 and 7, e.g. Inferno [2.4, 3.2, 3.999, 3.999] and [8000, 20000], the online caps: #modelist-online-caps) are not read; EDF 4.1 has the same value 0 arrays, which equal its Japanese wiki's enemy health coefficients x 10 (../edf41/file-formats.md#edf41-modelist-hp-scale). Values 0, 1 and 3 are EDF5's enemy health factors, read in the code since (combat.md#hp-formula-modelist, #hp-modelist-values).

ModeList online weapon and armor caps

Evidence: static · Build: steam-5d11de53 · Fact ID: modelist-online-caps

The online multiplayer caps are ModeList data: in each online mode, per-difficulty value 6 is the weapon-level cap and value 7 the armor cap in armor boxes, each a list of knots spread evenly over the mission's place t = (online list row - 1) / (rows - 1) (as the drop window's, drop-items.md#loot-roll-level-window) and interpolated linearly; -1 means no cap. Shown cap level = floor(cap x 25); armor cap per class = floor(base + per box x floor(boxes)) (player.md#armor-hp-per-box). Main online, Easy / Normal, Hard, Hardest, Inferno: levels [0.1, 1.1], [0.1, 1.1], [0.2, 2.1], [2.1, 3.1], [2.4, 3.2, 3.999, 3.999]; boxes [350, 2000], [350, 2000], [700, 4500], [4500, 8000], [8000, 20000]. Mission Pack 1 levels [0.6, 1.1] twice, [1.1, 1.65], [2.48, 3.1], none; boxes [1100, 2000] twice, [2600, 4500], [6200, 8000], [14000, 20000]. Mission Pack 2 levels [1.1, 1.6] twice, [1.875, 2.6], [3.1, 3.6], none; boxes [2000, 3500] twice, [4500, 7000], [8000, 14000], [20000, 25000].

Basis: config.sgo read from Root.cpk; the JP wiki's caps (atwiki edf5, saved 2026-11-08) reproduced cell for cell (#modelist-online-caps-check)

Native code applying online equipment caps

Evidence: static · Build: steam-5d11de53 · Fact ID: modelist-online-caps-code

The code that applies the online caps (#modelist-online-caps): the save object's 8AFC0 (weapon) and 8AF60 (armor) take t = float32([save+0x48]) / float32([[save+0x178]+4] - 1), as the HP formula does, and call 90F90 / 90E60 with the mode node [save+0xF0] and the difficulty [save+0x4C]. Each reads value 6 / 7 of the difficulty node (not a list: -1, no cap), clamps t to 0..1, x = float32(knots - 1) x t, i = floor(x) (9C8288); past the last segment it takes the last knot, otherwise -1 if either knot of the segment is below 0, else a + (x - i) x (b - a), all float32 (armor knots are ints, converted). Weapon: trunc(v x 0.25 (EE62D4) x 100 (EE66D0)), the shown cap level. Armor: trunc(boxes).

Basis: fn.py from the lobby text keys (Room_Weapon_Level_Limit EDCA50 -> 59E800 <- 568290); constants read with scratch exe_floats.py

Addresses (build-specific RVAs unless indicated): 8AFC0, 8AF60, 90F90, 90E60, 9C8288, EE62D4, EE66D0

Animation (CAS / CANM)

EDF5 CAS animation containers are version 0x203 (common records 13 u32 wide) with embedded CANM version 0x200

Evidence: static · Build: unknown (EDF5 game data examined by the EDF41-to-EDF6 project) · Fact ID: cas-canm-versions

EDF5 CAS animation containers are version 0x203 (common records 13 u32 wide) with embedded CANM version 0x200; standalone CANM files (for example ARMYSOLDIER/APPEAL/AP025.CANM, and the AP025/AP027/AP030/AP037 sets of EDF5_PALEWING, ENGINEER and HEAVYARMOR) are also 0x200. In the seven families shared with EDF 4.1 and EDF6 (GIANTANT01, GIANTANTQUEEN, GIANTSPIDER, GIANTSPIDERQUEEN, MONSTER501, VEHICLE407_BIGBEGARUTA, VEHICLE502_GROUNDROBO) the EDF5 and EDF6 files keep the same T-control, V-control and animation-group counts and offsets and the same CANM bone counts; EDF6 files have exactly one more key each, a different CANM version and are about twice the size.

Basis: header census of native files

  1. Endian and string conventions
  2. Record groups and offsets

Complete original research record — expand (2,392 characters)

RMPA (mission and map coordinates, routes, shapes, cameras) in EDF5 and EDF 4.1, big-endian with UTF-16BE NUL-terminated strings, (n, off) = count and offset: the header is EDF6's (edf6/file-formats.md#rmpa-edf6-layout: \0PMR, version 1, four (n, off) section pairs) with +0x28, +0x2C 0; section headers are 0x20 and empty sections are left out; every named object carries an int "refs" list, empty in every file of both games. Route / shape / point section 0x20: +0 (n, off) sets (0x20 each), +8 (n, off) refs, +0x10 id, +0x14 name length, +0x18 name, +0x1C raw 0x00010000; camera section 0x20: +0 refs, +8 id, +0xC raw, +0x10 / +0x14 name, +0x18 (n, off) camera sets (0x30); a set 0x20: +0 raw flags (0, 0x00010000, 0x01010000), +4 refs, +0xC id, +0x10 / +0x14 name, +0x18 (n, off) items; waypoint 0x3C: +0 index within its route, +4 (n, off) links (indices within the route), +0xC refs, +0x14 id, +0x18 / +0x1C SGO size / offset, +0x20 / +0x24 name, +0x28 vec4 position, +0x38 raw flags; shape 0x30: +0 raw flags, +4 / +8 type, +0xC / +0x10 name, +0x14 refs, +0x1C id, +0x20 (n, off) shape data (0x3C: EDF6's 0x38 plus 4 raw bytes), +0x28 / +0x2C SGO size / offset (little-endian, always 0); point 0x40: +0 refs, +8 id, +0xC vec4 position, +0x1C vec4 facing, +0x2C raw flags, +0x30 / +0x34 name, +0x38 / +0x3C SGO (little-endian, 0); camera set 0x30: +0 refs, +8 id, +0xC raw, +0x10 / +0x14 name, +0x18 (n, off) cameras (0x74), +0x20 int, +0x24 offset to timeline 1, +0x28 int, +0x2C offset to timeline 2; camera 0x74: +0 int, +4 int, +8 refs, +0x10 id, +0x14 / +0x18 floats, +0x1C / +0x2C / +0x3C / +0x4C vec4, +0x5C float, +0x60 raw, +0x64 / +0x68 name, +0x6C / +0x70 SGO size / offset (little-endian; an empty 0x20-byte SGO); timeline as EDF6's; the SGO blobs are little-endian (waypoints carry rmpa_float_WayPointWidth as a float). EDF5.exe's reader: loader 3CEDF0, walkers 3CF170 / 3CFA00 / 3D0360 (routes), 3CF3A0 / 3CFC20 / 3D0650 / 3D0D30 (shapes), 3CF5C0 / 3CFE40 / 3D08E0 / 3D0FE0 / 3D0DE0 (cameras), 3CF7E0 / 3D0140 / 3D0B90 (points), string swap 5BE150. In a MAC's map.rmpa the wire routes' links past a route's own waypoints index the map's wire-point list (the mapb's 0x7C block), not a route (107 such links in 3 EDF 4.1 maps; HILLYCITY 115, SINSUIKOUEN 97 and EDF5's NW_DANTI01 28 below the count). EDF5's MACs also hold a <map>.rmpa member that EDF6's MACs no longer have.

Basis: the author ran the walkers under an emulator over all 567 EDF5 / EDF 4.1 RMPAs and decoded every non-zero byte; 3CEDF0 checked with fn.py edf5

Complete original research record — expand (1,174 characters)

weapon/weapontable.sgo (root table) lists 1187 weapons as 8-value rows [id, weapon file, category, rarity, level, acquisition, stars, source], and weapon/weapontext.<ja|en|cn|kr>.sgo (root text_table) holds [name, description] for the same rows in the same order. The category is class x 100 + kind (0 Ranger, 1 Wing Diver, 2 Fencer, 3 Air Raider; kinds seen 0-10, 100-108, 200-209, 302-320); the id prefix says the class too (a... Ranger, p... Wing Diver, h... Fencer, e... Air Raider). Values 4-8 read by EDF6's meanings (edf6/weapons.md#weapon-table-entry, which has a ninth value): acquisition 1 = owned from the start (PA-11), 3 = DLC (npDecoyLauncher_amane); source 1 / 2 = the two DLC packs (EX_A_..., EX_B_..., 34 and 39 rows); rarity 1.0 (1151 rows) or 2.0 (36 rows, the EX_A ones). Each weapon SGO carries name.ja / name.en / name.cn / name.kr and WeaponIcon (a .dds path). Other per-language lists in the same SGO form: mission/missionlist.offline.txt.<lang>.sgo (110 rows [title, briefing]), missionlist.online..., the dlc1_ / dlc2_ lists, and etc/texttable_xbox.<lang>.txt_sgo (989 named strings; class names Loading_Title_001..004, difficulties LevelSelect_*).

Weapon table level unit versus displayed level

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-level-times-25

The weapon table's fifth value (level, a float, #weapon-table-sgo) is the weapon level the game shows divided by 25: level = floor(float32(value x 25)) (0.04 -> 1, 1.01 -> 25, 2.12 -> 52, 4.3 -> 107). Six-value weapon SGO star-stat arrays

Evidence: static · Build: steam-5d11de53 · Fact ID: weapon-star-arrays

Weapon SGO stats that change with stars are 6-value arrays [v, kind, x, top star, Ra, Mu]: v is the value at ☆5 (not ☆0); kind names the stat (0 AmmoCount, 8 AmmoDamage, 13 FireAccuracy, 16 AmmoSpeed, 21 ReloadTime, 25 FireInterval, the same in every row checked); the fourth value is the stat's top star; Ra (the share lost at ☆0) and Mu (the curve) shape the rest. At star s a stat where more is better is v x ((1 - Ra) + Ra x (s/5)^Mu), one where less is better (reload, fire interval, accuracy spread) v x ((1 + Ra) - Ra x (s/5)^Mu): the JP wiki's formula (page 307), which calls Ra 星0での悪化割合 and Mu 星変動係数. The third value (0-7; 0 in every AmmoCount) is the star slot (read since, KH chat 137: weapons.md#edf5-star-slot). A plain number (AmmoAlive, FireCount here) does not change with stars: the wiki's range is the top-star speed x AmmoAlive. Example: PA-11 LS (aWeapon001) AmmoDamage [16.0, 8, 1, 8, 0.5, 0.5]: 8.0 at ☆0, 16 at ☆5, 18.1 at its top ★8.

Basis: weapon SGOs read with the catalog tool; the formula checked against the wiki's tables (#weapon-star-formula-check); the code that applies it: weapons.md#weapon-star-fields (KH chat 137)

HQ star evaluator and float32 intermediate values

Evidence: static · Build: steam-5d11de53 · Fact ID: hq-star-eval-float32

The HQ star evaluator 8C8C0 (called per $n by 8C280, #hq-number-format) computes in float32: vRa = v x Ra, x0 = (s/5)^Mu x vRa (s = the slot's stars, cut to top; s/5 with 5.0 at EE65A8), then (v - vRa) + x0 (more is better) or (vRa + v) - x0 (less is better), max 0, times the sign (-1 for v < 0, EE68E8). It stores kind >> 2 as the display mode. If the array's first value is an integer in the SGO, the result is stored as an integer, x + 0.5 truncated (8C9E4, 0.5 at EE633C), else as a float; a plain number keeps its type.

HQ number formatting through C runtime

Evidence: static · Build: steam-5d11de53 · Fact ID: hq-printf-runtime

The HQ's numbers are printed by 5BDD30, a wrapper around the system C runtime's __stdio_common_vsnwprintf_s (import slot C97D90), with the printf options at 125AB18, which the startup code 9C8038 sets to 4 (9C8041; EDF6 sets 0x24, ../edf6/weapons.md#edf6-hq-printf-options). AmmoDamageReduce range falloff in weapon SGOs

Evidence: static · Build: steam-5d11de53 · Fact ID: ammo-damage-reduce

Every weapon SGO (1187 of 1187) has AmmoDamageReduce = [m, x], its damage falloff over range: m is the share of damage left at the end of the shot's life, x the exponent, so damage = MIN + (MAX - MIN) x (ls / LS)^x with MIN = m x MAX, ls the frames of life left and LS the full life (AmmoAlive), the JP wiki's formula (page 307; it says the falloff steps once per frame, so a 24-frame shot has 24 steps, and the minimum is never quite reached). [1.0, 1.0] is no falloff. All 24 range coefficients in the wiki's table equal x (M5 Raven [0.3, 2.0], Slaughter EZ [0.1, 2.5], Blazer and Buster Shot [1.0, 1.0]), and every "max～min" damage the wiki's class tables give (91 weapons) has min / max = m. The wiki's falloff by charge (lances, Thunder Bowgun, Plasma Great Cannon) and by ammo left (Mag Blaster, Reflectron, MONSTER GZ) is not in this array (those weapons have [1.0, 1.0] or only their range values); it is in custom_parameter (weapons.md#weapon-falloff-apply, KH chat 137).

Basis: File_Storage/Logs/catalog/falloff_check.py (every weapon SGO; page 307's table and extract/weapons.json); the per-frame stepping is the wiki's, the code was not read
