EDF4.1 Nereid V302 on EDF6 V506: helicopter rig, animation, mounts and fuel

ConversionCross-game ConversionGameplay & AIEDF 4.1EDF 6
Technical reference · Retained EDF4.1 R9 full source adapter with exact class/asset validation; no new helicopter game runtime proof

The EDF4.1 VEHICLE302_HELI Nereid and EDF6's V506_HELI can share a host runtime class contract, but their models, animation controllers, Havok bodies and weapon locators are not interchangeable. A retained source-only adapter preserves the original V302 geometry while using the target EDF6 Vehicle506_Helicopter class. This section describes the adapter's evidenced requirements; it is not a fresh successful helicopter flight test.

Preserve a coherent source rig

The source SGO class is VehicleHelicopter302; EDF6's host template uses Vehicle506_Helicopter. The adapter retains from V302:

  • original converted MDB model and source RAB resource identity;
  • original CAS animation with corresponding rest pose;
  • original ragdoll/SHKT and both animation-to-ragdoll and ragdoll-to-animation bone maps;
  • source durability, helicopter rigid-body data, dead-effect names, and boarding/camera locators;
  • gun mounting coordinates and source-associated MAB locator frames.

Do not graft the V506 CAS or its ragdoll binding blob onto the V302 mesh. The adapter's documentation records that the mixed rig shifts the helicopter body and leaves tail-rotor and wheel bone names unresolved. An MDB that parses fine does not pass a class-level animation/physics contract.

The EDF4.1 object also advertises a second _light LOD archive that was not present in the studied source installation. The bounded converter retains the real primary MDB rather than fabricating an unavailable second LOD path.

What must be adapted to the EDF6 class

The host expects seven-field seat/boarding rows, while source V302 supplies the first three locator roles and EDF6 supplies the remaining riding/animation/input-related fields. The source 302_HELI_DRIVER animation token is absent from the target runtime, so copying it as a required target player state is unsafe; the adapter uses the target-registered rider animation contract.

A source MAB conversion preserves V302's locator node frames while translating the damage-locator names into the target V506 class's expected names. The code checks:

  • every MAB locator references a real source model bone;
  • every required host locator name is present;
  • each seat has exactly seven fields, with real seat/camera locator identities;
  • each weapon holder names a real model bone and an existing seat index (or the studied -1 special holder);
  • death-effect bone references all resolve to source geometry;
  • all target-required animation player states and control variables exist in the resulting V302 CAS;
  • each ragdoll mapping's bone name resolves against the source MDB.

These are explicit checked invariants, not evidence that a conversion succeeds merely because xgs_scene_object_class is renamed.

Weapon and fuel records

The source V302 uses dedicated left/right Gatling and laser-mount resources; missiles and napalm have their own model-local emitters. The target V506 has a different setup shape, including an additional fuel block and final fuel weapon. The adapter carries source durability and flight/gun values where the corresponding shape is proven, but retains the target fuel data instead of trying to treat absent source entries as zero or moving the last list element.

In the studied setup, two left/right Gatling holders map to seat 0, a body missile holder maps to seat 0, and the target's final body/fuel holder carries the profile's -1 seat semantics. The generated weapon resources have private names and cross-check that their MAB muzzle locator bones exist in the target weapon MDBs. The source calls are likewise reshaped to preserve V302's three-part setup while supplying the V506 fourth/fuel-compatible component.

What this does not prove

The retained R9 source only proves the implemented bounded conversion algorithm and its fail-closed checks. It does not independently show that the generated Nereid was flown through a full EDF6 mission, that every weapon fired in-game, or that its multiplayer ownership/network effects are qualified. The historical R9 object reference inventory lists zero mission uses for this root in that census — it does not mean the engine lacks support or that the asset is universally unused.
