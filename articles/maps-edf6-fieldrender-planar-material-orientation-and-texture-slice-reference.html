EDF6 FieldRender: native planar projections, texture slices and orientation records

EDF 6Maps & NavigationMaps
Technical reference · Exact retained native EDF6 ENKEIRIGHT FMB material/orientation bytes with read-only semantic round trip; offline comparison with explicitly non-native FIX3

At a glance

What it is: The measured native ENKEIRIGHT material uses multiple projection/orientation records and distinct texture-array slices, not one universal texture scale.

Where it fits: The paired projection entries describe different scales for the same material's texture roles. The comparison also includes a non-native experimental record.

Important distinction: Do not copy one material's orientation or slice indices to every terrain material; the true output pixel still depends on shader sampling and composition.

Evidence: Exact IG_HEIGEN507_ENKEIRIGHT.FMB source material and orientation bytes, checked by semantic decode and byte-preserving reserialization. The comparison below uses an experimental, non-native SS_ISLAND4_FMEP.FMB record only to show which fields differ. It does not imply that the experimental record was authored by Sandlot.

Native material 0 is a pair of projections, not one universal UV scale

The retained native ENKEIRIGHT material 0 has a bounded, directly observed record:

Field Native ENKEIRIGHT material 0
Paint mode 0 (planar profile in the studied schema)
Correction scalar 6.0
First projection-pair indices (0, 1)
Color/base texture slice 0
Detail/multiplier texture slice 1
Normal texture slice 0
Two remaining projection pairs (-1,-1), (-1,-1)
Additional color/detail/normal slots -1 (unused in the examined material record)

The first projection pair refers to two different orientation records. The native orientation entries are:

Orientation index Euler XYZ degrees Scale XYZ UV offset
0 (90, 0, 0) (7, 7, 7) (0, 0)
1 (90, 0, 0) (100, 100, 100) (0, 0)

Consequently a reconstruction that assumes one global orientation per material, or uses the same texture-array slice for base and detail by default, does not preserve this native ENKEIRIGHT record. That does not establish which orientation dominates a given output pixel: the complete shader sampling/compositing state still matters.

What a controlled non-native comparator did and did not match

A retained FIX3 comparison used a different material 0:

Field Native ENKEIRIGHT Non-native FIX3 comparator
Planar mode 0 0
Correction scalar 6.0 6.0
First projection pair (0,1) (0,0)
Base slice 0 0
Detail slice 1 0
Normal slice 0 0
Orientation count for this binding 2 1
Orientation 0 Euler/scale (90,0,0) / (7,7,7) (0,0,0) / (20,20,20)
Orientation 1 Euler/scale (90,0,0) / (100,100,100) none

This is a material projection/orientation difference, not a different shader name, paint-mode integer or base texture slice. R39 independently had native support for shader selector 0x0202 with config 4 in the selected FMB family; matching the shader selector alone is insufficient to match these material records.

Round-trip evidence and unknown fields

The exact R40 offline decode→re-encode audit reported 3/3 byte-identical records: native material 0 and native orientations 0 and 1. It also retained a four-float auxiliary vector on material 0:

(6.0, 0.5019609928131104, 0.5019609928131104, 0.0)

The 6.0 slot is the studied correction scalar. The downstream meaning of all auxiliary lanes is not fully proven from this isolated record; do not invent gamma, tint or alpha roles merely because two values resemble 128/255.

The native FMB used in the audit was identified by SHA-256 0027ed493827ccfcdc0906f5efb5714c00b68567400fe505f741df756074dd31. This hash identifies one retained binary source, not all EDF6 versions/maps.

Limits on interpretation

  • Source bytes establish the field values and serialization identity. They do not prove the exact GPU coordinate formula for every FMB shader family.
  • A mismatch with an experimental FMB identifies plausible discriminating variables; it does not prove the mismatch caused any black-terrain symptom.
  • ENKEIRIGHT material 0 is one native exemplar. Other HEIGEN FMB leaves and directional variants use different tables and may require config-index remapping.
  • Offline parity is not evidence of new EDF6 map rendering success.
