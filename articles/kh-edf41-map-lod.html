EDF 4.1 — Map Lod (community source notes)

EDF 4.1Community Knowledge HubMaps
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Trees

Tree model classes: MapObject_Tree (11D8B0) calls 11C0E0 at 11DAC2, which holds the vtables of TreeSkinningMo…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-tree-classes

Tree model classes: MapObject_Tree (11D8B0) calls 11C0E0 at 11DAC2, which holds the vtables of TreeSkinningModel (A93540), TreeBrokenModel (A93580) and TreeModel (A935D8), as EDF5's factory E2CF0 does (../edf5/map-lod.md#edf5-tree-classes; the pick between them not read). Slot 1 (init) is 13CE40 on TreeModel, 13E080 on TreeSkinningModel; slot 4 (draw) 13D280 and 13E890; TreeModel's slot 6 (billboard) 13CCC0, slot 8 (mesh) 13DB40.

Basis: fn.py 11D8B0, 11C0E0; scratch vt_name.py, vt_dump.py on the three vtables

Addresses (build-specific RVAs unless indicated): 11D8B0, 11C0E0, 11DAC2, A93540, A93580, A935D8, 13CE40, 13E080, 13D280, 13E890, 13CCC0, 13DB40

The distances: the billboard init 13CAA0 (its two callers: 13D179 in the TreeModel init 13CE40, 13E7CA in the…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-trb-distance-fields

The distances: the billboard init 13CAA0 (its two callers: 13D179 in the TreeModel init 13CE40, 13E7CA in the TreeSkinningModel init 13E080) copies the .trb out struct's +0x14 / +0x18 (rule 0 child 5, [near, far]) to model +0x18 / +0x1C, and when each is positive squares it and multiplies it by the load-time LoD scale [C3F278] (13CC4E..13CC6D); cut-off² at +0x20 from out +0x1C (rule 0 child 4), or 500 m (AB69A4) when that is negative, never scaled (13CC27..13CC76). [C3F278] is 1.0 in the file and is one of the seven globals of the debug command set_lod_distance_scale (rendering.md#lod-distance-scale-command; any kind but "chara" writes it, #edf41-lod-scale-kinds). Before that, 13CE40 passes min(far x scale, cut-off) to the model's slot 7 (13D07B..13D0E2; use unread), as EDF5's 104760 does.

Basis: fn.py 13CAA0, 13CE40, --xref 13CAA0 (2 callers); AB69A4 read as 500.0, C3F270..C3F288 all 1.0 (scratch vt_dump.py f32)

Addresses (build-specific RVAs unless indicated): 13CAA0, 13D179, 13E7CA, 13CE40, 13E080, C3F278, 13CC4E, 13CC6D, AB69A4, 13CC27, 13CC76, 13D07B, 13D0E2

The mesh-to-billboard switch, TreeModel slot 4 13D280, matches EDF5's 104B90 (../edf5/map-lod.mdedf5-tree-bil…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-tree-billboard-switch

The mesh-to-billboard switch, TreeModel slot 4 13D280, matches EDF5's 104B90 (../edf5/map-lod.md#edf5-tree-billboard-switch): x = |tree position - camera position|² x view+0x18 (13D2FF); above cut-off² +0x20 nothing (13D309); pass 2 and passes above 3 draw nothing; near² +0x18 <= 0 or x <= near²: full mesh; between near² and far² +0x1C: mesh plus a band 1 - (x - near²) / (far² - near²) (13D339..13D355, 1.0 at AB6644) handed to 13D3C0 in passes 0 and 3; beyond far²: the billboard (slot 6 13CCC0), pass 0 only, and only when +0x28 is set. The mesh draws through slot 8 (13D381). TreeSkinningModel's slot 4 13E890 was not read.

Basis: fn.py 13D280; AB6644 read as 1.0

Addresses (build-specific RVAs unless indicated): 13D280, 13D2FF, 13D309, 13D339, 13D355, AB6644, 13D3C0, 13CCC0, 13D381, 13E890

Attribution: KH chat 180 (curator, autorun 00v) · 2026-11-14

Stock tree distances over all 4.1 maps (.trb SGOs counted once per map MAC, 96 rows): near is 10 m on almost…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-trb-distance-values

Stock tree distances over all 4.1 maps (.trb SGOs counted once per map MAC, 96 rows): near is 10 m on almost every tree (50 m only on the city street trees sk_gairojyu_13m01, [50, 170], and sk_gairojyu_icho01, [50, 150]); far 110 to 250 m (sk_tree10m01a [10, 110] in cities, [10, 180] in the hills; sk_tree15m01a [10, 210]; sk_sugi20ma [10, 230]; sk_tree20m01a and sk_sugi30ma [10, 250]); cut-off 1000 m on trees, 150 m on sk_tree3m01a, 120 m on the sk_so01branch1 / sk_so01rock3z pieces, 80 m on sk_bush01a. So a 4.1 tree is a full mesh only within 10 m, crossfades out to 110 to 250 m, and is a card to 1000 m: a shorter mesh range than EDF5's 50 m (../edf5/map-lod.md#edf5-trb-distance-values) with a longer crossfade.

Basis: scratch File_Storage/Logs/00v/trb_tally.py edf41 (output e41_trb_tally.txt): every map/*.mac, SGOs whose rules rule 0 child 5 holds two numbers

Buildings

The LOD table per structure part: 1275D0 (handed each part by 129AC0, map-objects.mdedf41-mapo-parts) loads t…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-structure-lod-table

The LOD table per structure part: 1275D0 (handed each part by 129AC0, map-objects.md#edf41-mapo-parts) loads the full model into slot 0 (138A20, with the part's +0x1C, 1276DC..1276EC), then for i = 1, 2 (loop 127710..127827) takes max(def +0x24 / +0x2C, part +0x24 / +0x2C) (127731, 12773A); when that is above 0 and the part names a model (+0x28 / +0x30, offsets relative to the part) it loads it (144800), multiplies the distance by the load-time scale [C3F284] for def categories 2, 4, 5 and 6 (mask 0x74) or [C3F280] for the others (127789..12779B), and stores {model, distance} at [[obj+8]+0x80] + 0x10 x i (1277AE, 1277B9). EDF5's EFBE0 (../edf5/map-lod.md#edf5-structure-lod-table) plus that scale, which EDF5 lacks; both floats are 1.0 in the file (#edf41-lod-scale-kinds).

Basis: fn.py 1275D0 (scratch File_Storage/Logs/00v/e41_1275D0.txt); slot 0's own distance in 138A20 not read

Addresses (build-specific RVAs unless indicated): 1275D0, 129AC0, 138A20, 1276DC, 1276EC, 127710, 127827, 127731, 12773A, 144800, C3F284, C3F280, 127789, 12779B, 1277AE, 1277B9

The render units: 139FF0, called three times from Preload_Structure (127E60) at 12827E, 128299 and 128313 wit…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-structure-lod-units

The render units: 139FF0, called three times from Preload_Structure (127E60) at 12827E, 128299 and 128313 with the capped, scaled, squared draw distance in xmm2 (map-objects.md#edf41-map-draw-distance-scale), appends a 0x38-byte node to the renderer's list (count +0x18), sets its flag bit 0 at +0x14 (13A198), and adds one 0x30-byte unit per LOD slot of a list at +0x90 (0x10 bytes each, count +0xA0), the slot's distance +0x08 going to the unit's +0x28 (13A44C..13A451). How that list relates to 1275D0's table was not traced.

Basis: fn.py 139FF0 (scratch e41_139FF0.txt) and the call sites in 127E60 (kh143_127E60.txt)

Addresses (build-specific RVAs unless indicated): 139FF0, 127E60, 12827E, 128299, 128313, 13A198, 13A44C, 13A451

The per-frame pick is a hard switch, as in EDF5 and EDF6: MapRenderer::ModelRenderer::RenderObject (vtable A9…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-building-lod-pick

The per-frame pick is a hard switch, as in EDF5 and EDF6: MapRenderer::ModelRenderer::RenderObject (vtable A92D48, base xgs::umbra::Object A92D70; made by the structure, model and tree loaders) has slot 0 13A8A0, which passes the object's +0x1C as d to 13A750; for each 0x38-byte node ([obj+0x58], count +0x68) it skips the node when its cull value +0x00 is above 0 and not above d (13A7B5..13A7C1), needs flag bit 0 of +0x14, then walks the units (+0x20, count +0x30, 0x30 bytes each) while d is above the unit's distance +0x28 and keeps the last such unit with a distance of 0 or more in +0x12 (3 = none; 13A7CD..13A80C); only that unit is queued (136EE0, 13A83E). One LOD per node per frame, no blend. A tree's mesh slot 8 13DB40 jumps into the same pick with the model's +0xD0.

Basis: fn.py 13A750, 13A8A0, --xref 13A750 (callers 13A8AF, 13DB47), --xref A92D48 (20 sites); scratch vt_name.py, vt_dump.py

Addresses (build-specific RVAs unless indicated): A92D48, A92D70, 13A8A0, 13A750, 13A7B5, 13A7C1, 13A7CD, 13A80C, 136EE0, 13A83E, 13DB40

The pick's d is the Umbra distance metric, as EDF5's (../edf5/models.mdumbra-object-distance-metric): at 57B5…

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-umbra-object-distance-metric

The pick's d is the Umbra distance metric, as EDF5's (../edf5/models.md#umbra-object-distance-metric): at 57B56C the Umbra code stores the squared distance between the object's +0x30..+0x38 and the camera, each axis scaled by the commander's +0x98 (57B543), to the object's +0x1C, then culls the object when that exceeds its +0x40 (57B571). The writer of the commander's +0x98 was not read.

Basis: fn.py --from 570000 --to 580000 --grep "0x1c\], xmm" --writes (one hit), then 57B4F0..57B5A0 read

Addresses (build-specific RVAs unless indicated): 57B56C, 57B543, 57B571

set_lod_distance_scale (BDD40) has only two kinds: "chara" (9B9560) writes C3F288 alone

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-lod-scale-kinds

set_lod_distance_scale (BDD40) has only two kinds: "chara" (9B9560) writes C3F288 alone; any other kind string writes the other six at once, each s + (1 - s) x K: C3F270 (K 0.1, AB64C8), C3F274 (0.5, AB656C), C3F278 (0.4, AB6550), C3F27C (0.2, AB6510), C3F280 and C3F284 (0.3, AB6530). So the tree scale (#edf41-trb-distance-fields), the map draw distances (map-objects.md#edf41-map-draw-distance-scale) and the structure LOD scales (#edf41-structure-lod-table) always move together through the command.

Basis: fn.py BDD40 (scratch e41_BDD40.txt); constants read with scratch File_Storage/Logs/00v/flt.py; the string with vt_dump.py str; adds to rendering.md#lod-distance-scale-command

Addresses (build-specific RVAs unless indicated): BDD40, 9B9560, C3F288, C3F270, AB64C8, C3F274, AB656C, C3F278, AB6550, C3F27C, AB6510, C3F280, C3F284, AB6530

Stock LOD distances over every 4.1 map (map.mapb defs, weighted by placements

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-building-lod-values

Stock LOD distances over every 4.1 map (map.mapb defs, weighted by placements; def +0x1C the draw distance in meters, +0x24 / +0x2C LOD 1 / 2 in squared meters): category-1 .mosb buildings (4,632) mostly [22500, -1] (150 m, no LOD 2; 3,011), [6400, -1] (80 m; 630), [62500, -1] (250 m; 233), [40000, -1] (200 m; 210 plus 79 drawn to 2000 m), 233 distant enkeibld backdrops with none; LOD 2 only on 41 ([10000, 202500], [22500, 52900], [40000, 160000]). Category-11 houses and containers (2,235): [6400, -1] (80 m; 1,555), [10000, -1] (639). Cars (category 6) [6400, -1] or [10000, -1]; utility poles 2500 (50 m); most props, rocks and trees have none. So most 4.1 buildings switch once, at 150 m (EDF5: 100 to 150 m, often with a second step, ../edf5/map-lod.md#edf5-building-lod-values), houses at 80 m. Part-level values (max with the def's) were not tallied.

Basis: scratch File_Storage/Logs/00v/lodtally5.py edf41 (output e41_lodtally.txt): every map/*.mac's map.mapb, placements counted per def

Shaders for a fade: 4.1's DX11.cpk holds 16 shader/dx11/snd_map_build_.sgo and 4 snd_map_lod.sgo

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-lod-fade-shaders

Shaders for a fade: 4.1's DX11.cpk holds 16 shader/dx11/snd_map_build_*.sgo and 4 snd_map_lod*.sgo; snd_map_build_basic and snd_map_lod take only per-material xgl_user_param values (diffuse, change_color, normal_amount, specular_pow, specular_color, light_smooth, fall_off_*, dirt_adjust; the LOD shader diffuse, specular_pow, specular_color, light_smooth) and a per-draw xgl_transform g_xgl_world: no per-object fade, alpha or dither input, as in EDF5 and EDF6. Unlike EDF5's (../edf5/map-lod.md#edf5-lod-fade-shaders) they are not instanced. snd_map_build_simple_clip has a per-material alpha_clip, snd_map_build_simple_alpha translucent fall-off values.

Basis: DXBC RDEF chunks parsed with scratch File_Storage/Logs/00v/sgo_cb41.py edf41 (output e41_sgo_cb.txt)

Route and open questions

Route for "keep distant trees as full meshes" in 4.1 (00v topic 1): code, one 5-byte patch at 13CC56 F3 0F 11…

Evidence: unverified · Build: steam-57aab039 · Fact ID: edf41-tree-lod-route

Route for "keep distant trees as full meshes" in 4.1 (00v topic 1): code, one 5-byte patch at 13CC56 F3 0F 11 47 18 (movss [rdi+0x18], xmm0) -> F3 0F 11 57 18 (store xmm2, zeroed at 13CC2C): near² 0 for both model kinds, since 13CAA0 serves them both (full mesh to the cut-off); or data, each .trb's rule 0 child 5 near at 0 or below, child 4 for a longer cut-off. 4.1 alone also has the scale [C3F278] (file offset C3D478, by rendering.md#lod-distance-scale-command's offsets): raising it pushes near and far out by its square root on every tree, a softer one-float patch that keeps the crossfade. Risks as in EDF5 and EDF6: draw cost, the map's FarClipZ, block culling. Stock trees are full meshes only to 10 m (#edf41-trb-distance-values), so the patch costs more draw work than in EDF5. Open: TreeSkinningModel's slot 4, the writer of view+0x18 (C3F278 is written by any set_lod_distance_scale kind but "chara", #edf41-lod-scale-kinds, KH chat 181). Nothing here was run in game.

Basis: novae (ajane); the route inferred from #edf41-trb-distance-fields and #edf41-tree-billboard-switch

Addresses (build-specific RVAs unless indicated): 13CC56, 13CC2C, 13CAA0, C3F278

Route for buildings' LOD in 4.1 (00v topic 1b): (a) push the switch out with one float: C3F280 (file offset C…

Evidence: unverified · Build: steam-57aab039 · Fact ID: edf41-building-lod-route

Route for buildings' LOD in 4.1 (00v topic 1b): (a) push the switch out with one float: [C3F280] (file offset C3D480) scales the squared LOD distances of every structure part outside categories 2, 4, 5 and 6, so 4.0 doubles the 150 m and 80 m switches (#edf41-structure-lod-table); [C3F284] (C3D484) does the same for poles, fences and cars. Neither touches the draw cut-off (C3F274 / C3F27C, map-objects.md#edf41-map-draw-distance-scale). EDF5 has no such float (../edf5/map-lod.md#edf5-building-lod-route); EDF6 has one (../edf6/map-lod.md#edf6-building-lod-route). Or, per map, each def's and part's +0x24 / +0x2C (squared meters; the larger wins). (b) A gradual fade needs, as in EDF5 and EDF6, both neighboring units queued inside a band in 13A750, a per-object factor, and modified snd_map_build_* / snd_map_lod* pixel shaders that discard pixels by a dither pattern against it (#edf41-lod-fade-shaders); since 4.1's map shaders are not instanced, the factor could ride in a per-draw constant (inferred, not checked against the draw code). Risks: draw cost of full models farther out; the 80 m houses are the most visible gain. Open: slot 0's distance in 138A20, the node cull value +0x00, the list at +0x90 that 139FF0 reads, the writer of the commander's +0x98, the shadow pass's pick, part-level stock values. Nothing here was run in game.

Basis: inferred from #edf41-structure-lod-table, #edf41-building-lod-pick and #edf41-building-lod-values; file offsets by rendering.md#lod-distance-scale-command's mapping

Addresses (build-specific RVAs unless indicated): C3F280, C3D480, C3F284, C3D484, C3F274, C3F27C, 13A750, 138A20, 139FF0
