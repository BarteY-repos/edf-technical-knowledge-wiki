EDF6 MissionMgr mode transitions: CONFIG loading, lobby state and save risks

EDF 6Missions & ScriptingMissions
Technical reference · Studied native call paths and a historical in-game regression; details apply to the affected build/test setup

EDF6 distinguishes loading mission-mode metadata from changing the active game mode. In a studied custom-pack runtime, invoking an extra high-level MissionMgr::SetMode from a callback not used by vanilla triggered a destructive save/progression regression affecting armor and collected weapons. That historical negative result demonstrates why these operations must not be treated as harmless substitutes.

CONFIG and the native mode loader

The studied game path loads its base CONFIG first and uses MissionMgr::LoadConfig for ModeList source loading. Additional custom ModeList rows were demonstrated through this existing lifecycle in a later historical candidate, rather than constructing private MissionMgr objects or replacing the loader's internal tables by hand.

The native behavior of the stock game is a distinct question from the behavior of an extended CONFIG-less custom-pack loader. The latter is not evidence that base EDF6 distributes arbitrary custom MissionPack rows or that direct reallocation of native mode tables is safe.

SetMode is a state transition, not a harmless setter

A withdrawn experiment injected an additional high-level MissionMgr::SetMode call in the custom-pack callback. On a real game run it produced a regression to saved armor/weapon progression. A later narrower interception of the script-wrapper transition avoided inventing a second native SetMode call, but this must be understood as an extension-specific repair. The reusable native lesson is to preserve call counts and transition ownership when tracing this path.

Online room state is asynchronous

Historical tracing separated room change into request, response and commit stages. A menu selection or pending custom-pack request is not proof the room's committed MissionPack or public/private family has changed. The room's creation family and subsequent committed selections can matter to policy decisions.

For diagnosis, compare the requested MissionPack, selected ModeList row, committed room attributes, and actual loaded LIST before changing save/progression state. The precise request/commit details may differ across game builds and third-party extensions.

Evidence limit

The reported save regression is a direct historical runtime negative for one candidate, not a claim that unmodified vanilla EDF6 spontaneously loses progress. The later CONFIG-less loader branch was a separate qualification path; no new run was performed for this article.

Reconstructed entry-point distinctions

The retained native-code study separated LoadConfig at EDF+0xDA8E0, mode selection/transition at +0xDC460, and LoadPackage at +0xE2AD0 for one specific EDF6 DLL. The LoadPackage path materialized active Package state at manager +0x130; that object included a std::wstring-style save/MST namespace at Package +0x68. The response callback at +0x8ED9DD could later republish the selected MissionPack at manager +0x14FD0. These are different transitions, not synonyms for a write to a single mode number. Read the full native mode/Package layout and asynchronous lobby publication for the verified evidence boundaries.
