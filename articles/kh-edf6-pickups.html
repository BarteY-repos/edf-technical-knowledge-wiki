Observations

Maximum map pickups encoded as constants

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-limits

Pickup limits are immediates: maximum pickups on the map at once 128 (imm32 at 2C79D9, the maxOnMap anchor 2C79D8 + 1), maximum pickups per mission 1024 (imm32 of two cmp ...,0x400 / jae at 2C765A and 2C76A7; keep both equal).

Basis: the patch's anchors and default comments; the bytes 00 04 00 00 (1024) and 80 00 00 00 (128) are there

Addresses (build-specific RVAs unless indicated): 2C79D8, 2C765A, 2C76A7

Attribution: demonized and redone (ChangePickupLimits), novae (ajane)'s EDF6 outside set · 2026-10-16

Enemy item drop chance is a float constant at 17A6D08 (.rdata), default 0.947

Evidence: static · Build: steam-678ccb46 · Fact ID: drop-rate

Enemy item drop chance is a float constant at 17A6D08 (.rdata), default 0.947; lower values drop more items (0 is not recommended).

Basis: the patch's anchor (98 6E 72 3F = 0.947)

Addresses (build-specific RVAs unless indicated): 17A6D08

Attribution: redone (ItemDropRate), novae (ajane)'s EDF6 outside set · 2026-10-16

Item category drop weights

Evidence: static · Build: steam-678ccb46 · Fact ID: drop-category-weights

What an item drops as is chosen by four s32 category weights at 17A6CE8 (06 00 00 00 0F 00 00 00 0E 00 00 00 03 00 00 00): weapon 6, armor 15, small recovery 14, large recovery 3 (sum 38), so each kill's drop is weapon 15.8%, armor 39.5%, small recovery 36.8%, large recovery 7.9% by default. The order is consistent with the item category byte (below 2 = weapon or armor crate, #pickup-range-check). The DropRate anchor at 17A6D08 continues with the floats 0.0, 1.0, 0.5, 0.7 (00000000 0000803F 0000003F 3333333F), which the patch leaves alone and the hub cannot explain.

Basis: the calculator's aob Item_ratio pattern matches once (checked 2026-10-21); the category names and order are the author's

Addresses (build-specific RVAs unless indicated): 17A6CE8, 17A6D08

Attribution: redone (ItemDropRate patch code in the calculator workbook; the calculator's own author is not named) · 2026-10-21

Drop rule (the workbook's text): each enemy kind gives points when killed

Evidence: static · Build: steam-678ccb46 · Fact ID: drop-rate-model

Drop rule (the workbook's text): each enemy kind gives points when killed; when the running total passes DropRate, an item appears, so a lower DropRate gives more items. The calculator's arithmetic, per 100 points: items = 100 / DropRate (105.6 at 0.947, 166.7 at 0.6, a factor of 0.947 / 0.6 = 1.578), split by the category share. Its worked example changes DropRate to 0.6 and the weights to 22 / 21 / 14 / 3 (weapons 36.7%, armor 35%, small 23.3%, large 5%): weapon drops rise 3.67x, armor 1.40x, small and large recovery stay at about 1.0x. Which points each enemy kind gives is not in the workbook.

Basis: the workbook's formulas read cell by cell (E = weight / sum * 100, G = E / DropRate); the point rule is its prose, not checked in the game

Addresses (build-specific RVAs unless indicated): 17A6D08, 17A6CE8

Attribution: EDF6 Calculator for ItemDropRateModificationPatch.xlsx (redone's patch; Japanese and English text), supplied by novae (ajane) · 2026-10-21

The pickup range test is comiss xmm0,xmm1 / jbe at 2C8B97

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-range-check

The pickup range test is comiss xmm0,xmm1 / jbe at 2C8B97; the item's category byte is [rdi+0xC0] there (below 2 = weapon or armor crate). MoistGoat's AutoLoot jumps past the range test for categories 0 and 1, so weapon and armor crates are collected as soon as they spawn, health is left alone.

Basis: the patch's code (cmp byte [rdi+0xC0],2 / jb), anchor decoded

Addresses (build-specific RVAs unless indicated): 2C8B97

Attribution: novae (ajane), novae (ajane)'s EDF6 outside set · 2026-10-16

DropItemManager pickup radius update

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-update

The pickup update is 2C8AC0(DropItemManager, soldier, position, radius xmm3, float, callback): it returns at once when [soldier+0x340] is null; otherwise it walks the item list whose head is [manager+0xDE0] (node +0x00 next, +0x18 the item record), skips records whose byte +0xC4 is set, takes each item's position from its object [rec+0xB0] (call 11B15B0), and collects when radius² > squared distance (#pickup-range-check). Collecting calls 2C7D50(manager, [rec+0xC8], category, soldier) when the GameDataMgr's index +0x38 is not -1 and the int at +0x68 of the node it selects (through +0x20, then +0x10 and that node's offset +8, the layout of an SGO node lookup) is nonzero, then the award routine 2C7540 (#pickup-award-dispatch), then the callback's virtual +0x28 (bool) and, if true, its virtual +0x08(position, category), and sets +0xC4 to 1. The position operand is used by subps xmm3,[r15] at 2C8B48, so it must be 16-byte aligned (an unaligned copy crashes with C0000005).

Basis: decoded with fn.py (2026-11-07); matches EDF6 Clear Loot's source, which hooks it and whose tests reproduce the alignment crash

Addresses (build-specific RVAs unless indicated): 2C8AC0, 2C8ACC, 2C8AEB, 2C8B24, 2C8B48, 2C8BD9, 2C8BEE, 2C8C15

Attribution: novae (ajane), EDF6 Clear Loot 0.1.3 source (momotori01, Unlicense) · 2026-11-07

Soldier per-frame pickup query

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-update-caller

Each soldier calls the pickup update once per update from the soldier base update 59ABB0 at 59B938, with rcx [20B2988] (DropItemManager), the soldier, an aligned stack position, the radius (the larger of [soldier+0x1B48] and a value from the loop over the soldier's list at +0x1A10 times [1C369BC]; replaced by [[soldier+0x1540]+0x258] while [soldier+0x1550] is set with a nonzero +8), the float xmm7 * [soldier+0x1A4C], and a stack callback object (vtable 17D2FE8, the soldier at +8; its slot +0x08 is 5A45D0, slot +0x28 is 5A4610). Raising the radius argument for one call collects every item on the map through the game's own path (EDF6 Clear Loot does this once at mission clear with 1,000,000).

Basis: decoded with fn.py (2026-11-07); the callback slots from the plugin's byte checks, which its tests run on EDF.dll; the four soldier vtables it accepts are AssultSoldier, PaleWing, Engineer, HeavyArmor (damage-model.md#dn-class-vtables)

Addresses (build-specific RVAs unless indicated): 59ABB0, 59B938, 59B8C7, 59B8F8, 59B900, 17D2FE8, 5A45D0, 5A4610

Attribution: novae (ajane), EDF6 Clear Loot 0.1.3 source (momotori01) · 2026-11-07

Pickup award and sound playback routine

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-award-dispatch

The award routine 2C7540(manager, picker, category, xmm3) first plays the pickup sound, SoundController ([20B2950]) 7B2860(controller, L"アイテム取得", 0) with the name at 17A6CF8 (2C756E..2C7584), unless the picker is null or its [+0x128] bit 0 is set (a remote player, player.md#soldier-kinds-by-fields); then dispatches on the category: 0 to 2C766A, 1 to 2C761D, 2 to 2C75E0 (AddHP at 2C75F3), 3 to 2C75A3 (AddHP at 2C75B6, and 549970 when xmm3 is above [1C36980]). So category 2 is the small recovery box and 3 the large (damage-model.md#health-pickup; the order of #drop-category-weights).

Basis: decoded with fn.py (2026-11-07); EDF6 Clear Loot calls the same sound alone as its toggle confirmation

Addresses (build-specific RVAs unless indicated): 2C7540, 2C756E, 2C7584, 7B2860, 17A6CF8, 2C766A, 2C761D, 2C75E0, 2C75A3

Attribution: novae (ajane), EDF6 Clear Loot 0.1.3 source (momotori01) · 2026-11-07

Complete original research record — expand (1,155 characters)

Item boxes are not game objects: DropItemManager (global [20B2988]; allocated 0xE60 in the scene init 7004F0, constructor 2C68D0, stored at 701586; vtable 17A6C30, Singleton base 17A6C08; destructor 2C6FC0) keeps a std::list at +0xDE0 (sentinel node pointer; count +0xDE8; 0x20-byte nodes with the Unit* at +0x18). +0x20: four 0x370-byte model slots from app:/object/ItemModel.mrab (resource of type i at +0x1E0 + i*0x370); types by the model name table 1F57358: 0 Weapon.mdb, 1 Armor.mdb, 2 Healingsmall.mdb, 3 Healingbig.mdb (no fifth kind). +0xDF0 drop accumulator (float), +0xDF8 LCG seed, +0xE00 next box id, +0xE04 boxes picked this mission (limit 0x400), +0xE08 weapon boxes, +0xE0C armor boxes, +0xE10 / +0xE14 result totals, +0xE58 / +0xE5C weapon / armor boxes dropped. Unit (0xE0, vtable 17A6C18: destructor 2C74A0, draw 2C8670): +0x70 matrix (synced each frame, 2CA464; position +0xA0, inferred), +0xB0 / +0xB8 model instance, +0xC0 type, +0xC4 picked / to-delete byte, +0xC8 box id (the online id), +0xD0 manager. Boxes are outside the team walks (5E11D0); a plugin may walk the list on the game thread (no lock: 2CA350 and 2CA610 change it).

Basis: the author's static reading ("H"; matrix row 4 as the position "M")

Addresses (build-specific RVAs unless indicated): 20B2988, 7004F0, 2C68D0, 701586, 17A6C30, 17A6C08, 2C6FC0, 1F57358, 17A6C18, 2C74A0, 2C8670, 2CA464, 5E11D0, 2CA350, 2CA610

Dropped box lifetime and object-death checks

Evidence: static · Build: steam-678ccb46 · Fact ID: dropitem-life

Box life: a death drops through 548AE0(obj, pos*) from the damage function (54849E) when obj+0x380 & 0x20 (may drop), obj+0x590 = 0 (not yet dropped), not & 0x10000000, and this machine decides (7748F0 / 784210); it reads the SGO's game_object_drop_item [1] spread and [2] amount (265 SGOs have it; the frog soldier [0.0, 7.0, 1.69]) and sets +0x590 = 1. A guest asks the host (2C8720, message 3; the host calls 548AE0 from 2C8CEB / 2C88E0). Spawn 2C7950(mgr, pos*, spread, amount) -> 2CA610, broadcast online as message 0 with the seed, so every machine makes the same boxes with the same ids: +0xDF0 += amount, one box per 0.947, none once the list holds 128 (the accumulator still pays), type by weights 17A6CE8, new 0xE0 -> 2C83B0 -> list tail. Update 2CA350 (from 7056CB) clamps each box into the move area (5A9E50, [20B2998]'s x / z), flags boxes below y -1000, deletes flagged ones and syncs the rest; 2CA2A0 (at 705486, mission change) clears all. No timeout and no magnet were found. The pickup ring AreaRender is drawn for ranges above 3.3 m (59B94A).

Basis: the author's static reading ("H"; no timeout or magnet "M")

Addresses (build-specific RVAs unless indicated): 548AE0, 54849E, 7748F0, 784210, 2C8720, 2C8CEB, 2C88E0, 2C7950, 2CA610, 17A6CE8, 2C83B0, 2CA350, 7056CB, 5A9E50, 20B2998, 2CA2A0, 705486, 59B94A

Attribution: hajisensai, All Forces source docs/itembox-re.md sections 2-3 (round 24) · 2026-11-07

Pickup eligibility and effects

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-gates-effects

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Soldier proximity or input gates
  2. Manager update
  3. Collection effects
Complete original research record — expand (1,280 characters)

Picking up, in more detail (#pickup-update-caller): the soldier update gates on [soldier+0x340] at 59B67C and on being alive (+0x2E8 = 0), so only local players (split-screen 2P included) collect; NPCs walking over boxes take nothing. Point = position +0x90 + (0, 1.0, 0); radius = max(3.0 x the accessory value 1 (699380(.., 1) from Weapon_Accessory in the soldier's equipment +0x1A00, else 1.0), +0x1B48) (+0x1B48 = 3.0 from the constructor 58D47C, 4 / 5 / 6 for some classes or states: 552198, 569B34, 569F8C, 583AD9, 584019), or the seat's +0x258 while riding; the fifth argument = accessory value 0 x +0x1A4C (SGO soldier_config[1], 0.35 for players and NPCs). The callback's slot 1 590F10 plays the pickup effect on the picker and its followers. Award (#pickup-award-dispatch): weapon and armor boxes only count (+0xE04, +0xE08 / +0xE0C) offline or on the host (784210), nothing is given at pickup, the result screen draws weapons from the count (2C92E0; 2C8A00 folds +0xE08 / +0xE0C into +0xE10 / +0xE14 by difficulty, caller 8DE765); recovery boxes heal the picker 15% / 30% of max HP (547870) and, with the fifth argument above epsilon, walk the picker's follower list +0x550 recursively (549970), each living follower healed by that factor x the ratio of its own max HP.

Basis: the author's static reading ("H"; class ownership of the 4 / 5 / 6 m sites and the settle timing "M" / "L")

Addresses (build-specific RVAs unless indicated): 59B67C, 699380, 58D47C, 552198, 569B34, 569F8C, 583AD9, 584019, 590F10, 784210, 2C92E0, 2C8A00, 8DE765, 547870, 549970

Attribution: hajisensai, All Forces source docs/itembox-re.md section 4 (round 24) · 2026-11-07

Pickups online (message handler 2C8C80, received at 7557AA): message 0 = spawn replay

Evidence: static · Build: steam-678ccb46 · Fact ID: pickup-online

Pickups online (message handler 2C8C80, received at 7557AA): message 0 = spawn replay; message 1 (guest to host, from 2C7D50's guest branch): the host finds the player's soldier, claims an unpicked box with that id (2C7B10(mgr, id)), counts weapon / armor only when it found it (no double count), applies recovery to its copy of that player, then broadcasts message 2; message 2 (host to all, 2C7B50: type, id, player number [soldier+0x1ED0]+0x48): each machine applies the award to that player when it is a remote copy (+0x128 & 1, fifth argument 0: no followers) and flags the box; message 3: a drop request. The picker's machine acts at once (box removed, heal, effect) and tells the host after, with no rollback; boxes have no owner, the host arbitrates who was first. Box ids may be negative. The author's offline run of the game's own functions (tests/item_pickup_native_audit.py, EDF.dll mapped privately, 83 checks): a weapon box and a recovery box at one spot are both taken by one 2C8AC0 call with radius 0.05, so a small radius does not single out one box; serialization gives [2, kind, id, playerIndex] on the host and [1, kind, id] on a guest.

Basis: the author's static reading ("H") and their offline execution of the game's code (not an in-game test)

Addresses (build-specific RVAs unless indicated): 2C8C80, 7557AA, 2C7D50, 2C7B10, 2C7B50, 2C8AC0

Attribution: hajisensai, All Forces source docs/itembox-re.md sections 4.4 and 9 (round 24) · 2026-11-07

Reported pickup cleanup at certain mission endingsSource: unverified

Evidence: unverified · Build: steam-678ccb46 · Fact ID: text-screen-clear-removes-items

Missions that end on a white or black text screen take the soldier and the remaining items away before "Mission Cleared" appears, so drops left on the field at that point are lost; in other missions the items remain until the result transition.

Basis: EDF6 Clear Loot 0.1.3's README (it collects through the game's own pickup routine on the clear jingle or UI, and since 0.1.3 on the text screen's appearance); the author's in-game test offline; its source (2026-11-07) adds the script order, missions.md#story-window-endings, and its log (CLEAR ... recentRecipient=0 at the banner)

Attribution: EDF6 Clear Loot 0.1.3 (momotori01, bundled with EDF6VR 3.2.15; source in its GitHub repository) · 2026-11-06
