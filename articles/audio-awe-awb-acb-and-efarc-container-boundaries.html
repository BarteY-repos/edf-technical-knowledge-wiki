AWE / AWB / ACB

The retained audio tooling establishes a CRIWARE extraction/inspection path, not a cross-game audio conversion law.

awe_parser.py is documented as an AWE/AWB extractor with AWBE identity handling and endian-tolerant parsing. The retained CLI contract uses -o / --output; an older README spelling --o is stale.

This is enough to:

  • enumerate/inspect AWE voice-name/list data;
  • pair AWE metadata with AWB payload extraction in the supported tool path;
  • preserve archive-relative identity while doing read-only research.

It is not evidence that EDF5 AWE/AWB/ACB can be copied or rebuilt unchanged for EDF6. Codec, cue-table, bank, language and game-specific routing semantics still require native/paired evidence.

EFARC

The corpus identifies EFARC as an EDF6 file/effect-archive research target, but contains no reconciled universal parser or EDF5→EDF6 conversion contract. Its current status is UNRESOLVED.

Do not fill that gap by assuming EFARC behaves like RAB, MARC or CRIWARE audio containers merely because all are archives. Keep it separate until a source/runtime-backed format contract exists.

Practical rule

Use AWE/AWB tooling for extraction and inspection, preserve original audio-bank relationships, and treat audio replacement/conversion as a resource-specific operation. For EFARC, preserve opaque bytes unless a task has format-specific evidence.

See also spatial placement, panning and optional velocity pointer ABI.
