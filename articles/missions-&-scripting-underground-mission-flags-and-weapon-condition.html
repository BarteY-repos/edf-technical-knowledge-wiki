EDF6 underground mission flags, Air Raider support and runtime conditions

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Technical reference · Native binary and three direct runtime observations; scope-bound

A red weapon in the mission menu is not equivalent to blocking its use in the mission. The EDF5→EDF6 underground mission-port research identified separate mechanisms for list metadata, loadout presentation and the weapon-condition state used by the game during actual support/vehicle activation.

This article reports native binary and in-game observations. The bit-field meanings below are scoped to the examined EDF6 mission-list profile, not an assertion that every possible mission flag is decoded identically in all contexts.

Two paths from mission flags to NO_SUPPORT

In the analyzed MissionScriptASImplement metadata application logic (near EDF+0x1DDF50 and EDF+0x1DE770 in the qualified DLL), both of these conditions set raw WeaponCondition=1:

  • flags & 0x20: ordinary underground-profile route. It also performs additional 0x20-specific side effects.
  • flags & 0x200: an independent route from bit 9 that selects the same no-support condition without that 0x20 side-effect block.

The corresponding observed state values are 0 (normal), 1 (no-support) and 2 (force-enable/override family). EDF6 exposes the native AngelScript API SetWeaponCondition(::WeaponCondition). Compatibility checks also consume a weapon's use_underground property, observed at weapon object +0x228 in the examined build.

Why values 8, 9, 40 and 520 are not interchangeable

Decimal flags Hex Menu restriction mask 0x227 Raw gameplay WeaponCondition in the examined apply path
8 0x008 Clear 0 — normal
9 0x009 Hit via bit 0 0 — normal
40 0x028 Hit via bit 0x20 1 — no support
520 0x208 Hit via bit 0x200 1 — no support
552 0x228 Hit via both higher bits 1 — no support

flags=9 is an especially useful discriminator: it can produce an apparently restricted loadout menu without enforcing the gameplay no-support condition. The UI state alone must not be used as a pass/fail test for an underground port.

Native EDF6 cave missions were observed using flags=40, including the M050 comparison mission. A separate vanilla row RM000 ("Today's Plans", using EDFRoom601) uses flags=520 in both OFFLINE and ONLINE lists. This proves 0x200 is a real game-used condition bit, not a user-created magic constant; its broader symbolic name remains unresolved.

What an underground mission should actually do

In native EDF6, incompatible Air Raider equipment may still be selected/equipped before starting the mission and displayed in red. The decisive test is whether the incompatible conventional air raid or vehicle/support request functions during gameplay.

Three custom EDF5-content missions were later retested with the ordinary native-like flag value 40:

Tested custom mission List flags In-mission restriction
MissionPack03 M000 40 Runtime PASS in the reported test
MissionPack03 M001 40 Runtime PASS in the reported test
MissionPack04 DM019 40 Runtime PASS in the reported test

These later tests supersede the older interpretation that M000/M001 were inherently broken or that custom MissionPacks could not apply 0x20. The original diagnosis confused menu restrictions, temporary deployment mismatches and the actual activation criterion.

Conversion and authoring rules

The audited EDF5-derived MissionPack corpus classified 15 underground missions:

  • MP03: M000, M001, M014, M027, M028, M029, M056, M057, M062, M072_2, M204;
  • MP04: DM001, DM007, DM019;
  • MP05: DM007_2.

The documented production metadata policy uses flags=40 on those 15 rows, with standard surface rows using 8. Keep this target list aligned with the correct OFFLINE/ONLINE mission ordinals and companion TXT/image resources; a repair to a stale LIST can affect save identity and presentation independently of weapon restrictions.

Do not replace every underground 40 with 520 or 552. Bit 0x20 has additional native mission-profile effects absent from 0x200; there is no evidence that such a wholesale replacement is safe or necessary. Likewise, adding SetWeaponCondition(NO_SUPPORT) to every mission script was an experimental diagnostic, not a required production architecture.

What remains uncertain

The three tested missions establish correctness for those tested runtime cases. They do not certify every underground mission, DLC combination, game build or custom loader. A fresh case should be investigated by comparing the deployed LIST row, selected mode/mission record, global WeaponCondition during mission setup, and the actual support activation result — not by judging the equipment's color alone.

For the wider metadata rules see shared progression and mission LIST schema and LIST, text and preview images.

Older candidate diagnostics (not current production rules)

The initial M000/M001 investigations also examined a shared OnlineLimitsDisabled UI setter patch, host-side ApplyModeNo refresh and an experimental per-mission SetWeaponCondition insertion. These did not establish a mandatory new mission-authoring policy; the later in-game flags=40 positives above supersede early assumptions about red loadout entries. See scoped diagnostic history.

Historical 29-row diagnostic is not the final two-mode census

The first underground-only list repair changed field10 from 8 to 40 for 15 unique missions but only 29 row instances, because the older MP03 ONLINE list still omitted M000 (112 OFFLINE / 111 ONLINE). The subsequent EDF6 shared-progress correction placed M000 in both 112-row mode lists. Therefore 29 is a historical delta count, not the intended final underground-entry total across all six LIST files; there are 30 mode-scoped occurrences after the unified list correction.

A nearby but unrelated native helper named SetUndergroundSoundReverve() was examined: it supplies 0.25 to SetMapEnvironment_SoundReverve(float). This is an audio reverb adjustment, not a replacement for the mission metadata 0x20 underground condition or a way to enforce support restrictions.
