Class names are not creature names: EDF6 (like EDF5) has no dragons

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-enemy-names

Class names are not creature names: EDF6 (like EDF5) has no dragons. The class DragonSmall and its SGOs (DragonSmall401, RedSmallDragon, YerrowSmallDragon, the _HS variants, e518_frogDragon* models) are the Tadpoles (flying frog-like creatures); only EDF 4.1 has dragons (../edf41/enemies.md#edf41-enemy-names). Nephila is the web-throwing spider, Aranea in EDF5 and EDF6 (Retiarius in EDF 4.1): its web (SpiderStringBullet) can nearly immobilize a player and pull them in. Lines here that say "dragon" for an EDF6 object mean the DragonSmall class, that is a Tadpole, unless they name EDF 4.1's dragons.

Basis: novae (ajane)'s knowledge of the games (2026-11-07)

InsectBase distant pose-update suppression

Evidence: static · Build: steam-678ccb46 · Fact ID: insect-animation-lod-adjust

InsectBase (GiantAnt, Bee, Spider, their EX variants, DragonSmall) skips pose jobs for distant insects as in EDF5 (edf5/models.md#insect-pose-job-skip): N = 1 / 4 / 8 / 16, the job is queued only when frame % N == slot % N, 16 when not drawn. The distance bands are 150 / 300 / 600 m times the SGO key insectbase_AnimationLodAdjust ([InsectBase+0x5D8], default 1.0), so a large value in an enemy's SGO keeps it animating every frame. In shipped data only e665_giantant_medium.sgo (2.5), e667_spider_medium.sgo and e668_giantbee_medium.sgo set the key. The loader is 4A6830 (key UTF-16 at 17C54C0, lea at 4A706C, store at 4A7166; the default comes from the shared 1.0f at 1C36994: do not patch it); the consumer is 4A8FD0 (InsectBase vtable slot 4). A code patch for "never skip" is 4A95AF 0F 84 8D 00 00 00 -> E9 8E 00 00 00 90 (bytes verified, untested).

Basis: novae (ajane); all 3153 .sgo in Root.cpk scanned for the key; not run in game

Addresses (build-specific RVAs unless indicated): 4A6830, 4A706C, 4A7166, 4A8FD0, 4A95AF, 17C54C0, 1C36994

MovingFortress spawn and activation states

Evidence: static · Build: steam-678ccb46 · Fact ID: movingfortress-stand-generators-steps

MovingFortress (vtable 17C6900: slot 4 update 4C67E0, slot 9 messages 4C6240) spawns lying down (mode 0: state ground, no AI) and stands only on a script ObjectAction 0 / 2 or a controller (4C6293..4C634D), through the target mode [+0x1A88] (1 = stand, then it plays wakeup and runs its AI). It has two ObjectGenerators and picks one by a field of the message: 0x20100 (a drop setting) by the int at +0x48 of the message body (4C64AA, unchecked), 0x20103 (get the generator) by the int at +0 (4C6352, < 2); only generators[1] opens the core hatch (4CAA20 -> 4CA980 sets the core-open flag [+0xE68] that the hit filter 4C6650 asks), so a drop on generators[0] leaves the core shut and the fortress unkillable. Walking: it steers away from the map edge (4CBC00) and otherwise takes each step's sideways input from [+0x1970] (4C3244: 0 / 1 left, 3 / 4 right, anything else straight), which only its network sync writes (4C41D2 / 4C9D72), so offline it always walks straight. Its CAS controller is +0x910 (4CB5C4).
