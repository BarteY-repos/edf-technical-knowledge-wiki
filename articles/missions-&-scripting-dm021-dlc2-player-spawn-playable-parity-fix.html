DM021 / DLC2 #3 — player-spawn playable-parity fix

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · Runtime-proven / mission-local

Status: runtime PASS / playable-parity fix. DM021 is closed as a practical mission issue, but the coordinate substitution is not a generic RMPA conversion rule.

The EDF5 source player start converted structurally, but on the stock EDF6 target it landed inside/at incompatible building collision. A delayed SetObjectPosition reapply was a useful negative control: the player was moved upward and then fell back into the same problematic location. This excluded a simple "target overwrites the spawn later" explanation.

Accepted compatibility delta

The mission-local fix reuses an existing unused EDF5 RMPA record 味方/小隊01_2 as a source-owned compatible ground-spawn location:

p1 = [339.10980224609375, -0.024568000808358192, -288.0691223144531]
p2 = [349.52685546875, -0.016409000381827354, -286.95318603515625]

Candidate MISSION.RMPA SHA-256:

47e063354d7a30a2b5dc3476c1fc9417a4d56e69b1733e999bde621526d6829f

The mission AC remained the clean R50 output:

51282b4ef894a98f9b56642804486600788bd44da3e40d400c3901cd2cd5cc0c

Direct user runtime confirmation accepted the resulting spawn as good. R54 records DM021_COMPAT_I = RUNTIME_PASS_PLAYABLE_PARITY.

Why this matters

The compatibility problem was target geometry vs source-authored placement, not evidence that the entire RMPA format was malformed. The fix stays content-side and mission-local. It demonstrates that an unused source semantic record can be a valid compatibility donor when target geometry makes the original location unusable.

Do not generalize blindly

Do not convert this exact coordinate pair into a global RMPA transform, do not globally offset all player spawns, and do not infer that delayed SetObjectPosition is a general repair. A generic source-only placement compatibility algorithm still needs map-aware evidence and fail-closed selection rules.
