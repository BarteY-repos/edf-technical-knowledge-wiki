Mission events: registrations, scheduling and shared state

UniversalMissions & ScriptingScriptingEDF 5EDF 6
Technical reference · Reconciled native scheduler and mission source evidence

Mission control flow is a graph of registrations and handlers, not merely a list of functions in a decompiled BVM. This distinction matters when translating EDF5 mission behaviour into EDF6 AngelScript (MISSION.AC), and it is useful when reading a mission's native event machinery.

Registration versus handler

A registration supplies an incoming trigger/factor set, delay and check policy. A handler is the target event body and owns the event state and counter. Several registrations can point at one target handler without creating several independent target event states.

The relevant research distinguishes:

Element Owns Does not imply
Registration (edge) Trigger factors, delay, check mode A separate copy of the target's state
Event target (node) Handler, persistent state, counter, invocation policy That every incoming factor is one giant combined AND
Scheduler Selection/append of ready registrations A naive textual function-call order

This model comes from native source/target observations and later source/target event reconciliation. An older description with target-owned factors was superseded by the more precise registration-owned factors model.

multi is an exact comparison, not generic truthiness

In the observed EDF5/EDF6 BVM scheduler, multi == 1 means that all ready registrations are appended for processing. Other values select one ready registration according to the scheduler's delay rule. EDF6 AngelScript event types map to:

source multi == 1  → EVENT_TYPE_ASYNC (1)
source multi != 1  → EVENT_TYPE_SYNC  (0)

Using multi != 0 is not equivalent to the observed comparison. The ASYNC wrapper must also avoid the SYNC voice/game-thread handshake (WaitVoice, GetTalkers) when that handshake is not part of the actual source path.

Reachable registrations matter

A decompiler can expose dead compiler-generated registration branches. In the studied exact44 paired set, 2,233 textual RegisterEvent occurrences reduced to 2,214 reachable registrations and 2,106 unique reachable target handlers. IDs are assigned to unique targets in first-registration order, not based on sparse compiler Func_N labels.

These figures describe the studied fixture. They are not fixed counts for all EDF missions.

Repeated and counter-based events

The reconciled authoring model distinguishes three invocation policies:

  • once: run only once;
  • repeat: re-arm after invocation and permit subsequent triggers;
  • nth: share a target counter and invoke only at the specified count.

Multiple once registrations are source-backed OR fan-in: any one qualifying incoming registration may trigger the same target. For a single registration, factors may form AND/OR conditions inside that registration. An arbitrary logical AND spanning unrelated registrations is not established and should not be invented by an importer.

A cycle such as Start → A → B → A may be represented using explicit re-arm policies. Direct self-registration and Start/Main re-entry need separate evidence; they are not automatically safe simply because a cyclic graph can be drawn.

Exact factor distinctions

Some numeric factor codes are easily conflated. The retained mapping includes:

Code Observed factor meaning
9201 Factor_ObjectDestroy
9202 Factor_ObjectEncount
9300 Factor_AiMoveEnd
9301 Factor_AiMoveEndOrDie
9116 Factor_GroupObjectCount
9117 Factor_GroupObjectEncount
9205 Factor_RideVehicle

Do not collapse 9201 and 9202 into the same event merely because their names and use cases are adjacent.

How to interpret an unknown handler

First reconstruct reachability, registration ownership, event identity, factor conditions, and side effects. Only then infer what the handler will do in-game. A source-to-source compiler can preserve these graph properties without asserting that every unobserved engine API has exact target semantics.

Bytecode versus engine call identifiers

A BVM cuscall0 instruction is a bytecode operation with a separate numeric engine-call ID operand. For example, AC D0 07 means opcode 0xAC followed by little-endian ID 2000; it does not introduce opcodes D0 or 07. The shipping invalid/crashing BVM instruction opcode range is 0x39–0x3F in the examined build.

Read BVM bytecode and custom-call translation for API mappings, argument/stack semantics, and cases where an engine operation has no demonstrated AngelScript binding.

Event state allocation, reachability and delay: exact-pair findings

A handler may be armed more than once. The examined 44 exact EDF5 source/official EDF6 pairs contained 2,233 textual RegisterEvent calls, but only 2,214 reachable from Main through direct calls and event-target edges. Those reachable registrations referenced 2,106 unique handler targets. The paired EDF6 MAX_EVENT_ID totals also equal 2,106, supporting the following implementation model:

one handler body (node) -> one persistent event ID / state
many incoming registrations (edges) -> potentially the same handler ID

Allocate event IDs for unique target handlers in first-registration order, not from sparse decompiler labels (Func_27, Func_42, etc.) or once per registration. Unreachable Func_N registrations produced by compiler flattening must not become active mission events. Do not remove ordinary named utility functions solely because they are not called from Main: some target-facing helpers are preserved for external/reference use.

For the inspected RegisterEvent end-event pattern, source delay 100.0f maps to target 100000000.0f only when is_end && source_delay == 100.0f. This is a narrow sentinel rule, not evidence for global scaling of all mission timings. One examined M029 high-level official port normalizes an empty relay chain; that difference does not imply that the source BVM lost its downstream triggers.

Sync/async scheduling in engine terms

The BVM runtime checks the registration's multi field by equality with 1. If it equals 1, all ready registrations are appended. Otherwise one ready registration with the greatest delay wins. The EDF6 AngelScript event scheduler sorts by descending delay, then uses EVENT_TYPE_ASYNC=1 to append ready events or EVENT_TYPE_SYNC=0 to select the first. That is why multi == 1 — not generic nonzero truthiness — is the valid translation for the examined builds.

In the 141-shipping-mission corpus, 5,193 raw registrations reduced to 5,112 reachable registrations: 4,540 with multi=0 and 572 with multi=1. Differences in manually authored official EventType choices for M015/M016/M024/M035 do not rewrite independently measured source scheduler semantics.

Why this matters: if a converter creates duplicate target nodes or guesses event IDs from function names, it can change counters, re-arm behavior, voice ordering and mission completion even when the generated AngelScript compiles successfully. Source-reachable registration topology is therefore a stronger parity check than raw counts of decompiled instructions.

Original EDF5 source examples: shared counters and relay cases (consolidated)

In the exact44 source-paired audit, 2,233 textual RegisterEvent statements reduce to 2,214 reachable registrations, 2,106 distinct target handlers and 2,147 factor sites. The 19 discarded statements reside in unreachable compiler-generated regions. Targets, not sparse compiler Func_N names, identify persistent handler state.

M018 illustrates why shared counters matter: Func_3 is armed twice, and the second execution releases 60 red ants. M029 is a bounded special case where the original BVM arms two empty relay handlers from Main, but the official target port chains them. M041 has a pre-registration call 9000 denoting a body wait, not a factor on the child registration. None is permission to rewrite arbitrary graph topology. Source: EDF5 edf5/mission-vm.md, bvm-event-reachability, bvm-event-slot-per-handler, bvm-handler-counter-guard, bvm-m029-relay, bvm-m041-wait-idiom (source/official static pairing).

Event-body domains: voice and gameplay are not interchangeable

A separate source-matched 44-mission reference event-domain census aligned 1,387 cue-bearing EDF5 Func_N handler bodies by ordered cue signatures: 1,176 aligned to voice_script, 211 to game_script; 6 cue signatures were ambiguous in matching but retained the same resulting domain, and 0 source cue-bearing bodies remained unmatched in the measured reference. This is evidence that collapsing every EDF5 source event into the EDF6 *_game_event_usercode path may discard important game/voice execution-domain separation. It does not establish that the loss causes any specific reported subtitle-scroll symptom.

A conservative proposed classifier that accepted only obviously radio/speech-only or pure Talk transactions assigned 1,121/1,387 bodies. It was correct for 1,035, wrong for 86, and abstained for 266 — 92.33% precision among classified cases, inadequate for automatic source-to-target rewrites. The high correlations of RadioBegin (64/64) and RadioEnd (65/65) with the game domain are a warning that Radio* is not a voice-domain guarantee. TalkBegin and WaitVoice likewise occur in both measured domains. Multiple calls in a handler, not API name alone, determine the supported classification. The 44-entry evidence is a reference corpus; the retained domain census itself warns against claiming it proves every native/Sandlot convention, even though separately verified official 44-mission archives exist.

Multi-registration targets have one shared threshold, not duplicated guards

In the examined M020_5 event graph, two registrations both target source Func_6 and share a counter threshold of 2. In the failing conversion, an outer target wrapper rejected the second invocation (m_counter != 1), while a second counter in the handler body itself rejected the first (Func_6___Counter != 2); together these guards prevented the body on both invocations. The blocked continuation would ordinarily activate the two carrier generators. The source-matched high-level reference instead uses one target-owned guard m_counter != 2 and no second guard inside the event body.

The same bounded reference comparison identified 14 counter-threshold handlers across 11 mission scripts with N > 1. Known examples include M015_3 thresholds 2/3/4/5, M016 threshold 3, and M020_5 threshold 2. These are counter-event semantics: the registration factors remain edge-owned while counter state belongs to the shared target. There is no license to promote a broad counter-pattern rewrite without verifying the source bytecode and effective target branch.

Evidence: EDF5_EDF6_EXACT44_EVENT_DOMAIN_CENSUS_2026-09-05.json (44 reference missions, not a gameplay test); EDF5_EDF6_M020_5_R75_EVENT_COUNTER_OFFLINE_AUDIT_2026-09-05.md and R75_OFFICIAL_MULTI_COUNTER_CENSUS_2026-09-05.json (source BVM/ASM comparison and failing modified-runtime progression symptom).

EDF4.1 source counterexample: a handler body does not prove event registration

A six-mission original EDF4.1 BVM decompilation sample provides a narrow independent illustration of the registration-versus-handler distinction: M002 contains the shared Func1709960674 clear-handler body but zero textual RegisterEvent and AllEnemyDestroy call sites, whereas M001, M003 and M004 each contain one of each. Therefore a decompiler inventory that merely counts named Func... handlers overstates what is demonstrably registered in the source. This finding is EDF4.1 source evidence, separate from the preceding EDF5/EDF6 exact44 scheduler numbers; it is not proof about complete runtime reachability.

The more complex EDF4.1 M012 offers a positive contrast: 19 textual RegisterEvent call sites are paired throughout the source with time, enemy-clear, object-destruction and AI-move factors. In particular, Func455038071 is registered after generator configuration with a 9201 object-destroy factor for the first carrier. Later registrations depend on other factors and mother-object action sequences. These facts establish a staged source event graph, not whether every branch succeeds in a target EDF6 runtime. Exact IDs, source hashes and call-site line numbers are in the six-BVM source census and its R172 CSV evidence.

R174 EDF5 original mission examples: which voice cues run in which event domain?

The earlier Exact44 reference identified 1,387 cue-bearing EDF5 Func_N handler bodies in 44 source-matched missions, with 1,176 matched to voice_script and 211 matched to game_script. The new per-mission crosswalk makes the source cases inspectable rather than reducing them to one percentage. These are reference alignment labels, not proof that an arbitrary runtime RadioVoice or TalkBegin call always executes in one particular game-thread domain.

EDF5 mission Matched cue-bearing Func_N Reference voice domain Reference game domain Notable observation
M079 94 45 49 Mixed domain; 48 of the 86 naive classifier errors occur here
M091_4 60 44 16 Mixed domain; 14 naive errors
M021 54 47 7 RadioBegin, TalkBegin and RadioEnd coexist in game-domain handlers
M020_5 46 44 2 Two FR_AE065B* cue-bearing handlers each have two reference candidates in the game domain
M058 52 51 1 Two further FR_AE065B* cue-bearing handlers each have two candidates in the voice domain
M032_5 33 26 7 AE005_032_E repeats in two source handler matches, both game-domain candidates

All six ambiguous cue-signature matches are confined to these three missions (M020_5, M032_5, M058) and are domain-consistent within each ambiguous match. This narrows the uncertainty: the exact target function identity remains ambiguous, but the available candidates agree on the reference game/voice domain. It does not independently verify the native EDF runtime thread, matching algorithm, audio playback order, or callback timing.

Two named counterexamples prevent overreaching from API names alone:

  • M001 / Func_41 has TalkBegin, three Talk_AddSingle calls and TalkEnd, but the reference places that function under game_script rather than voice_script.
  • M021 / Func_38 combines RadioBegin, TalkBegin, Talk_AddSingle, TalkEnd, RadioEnd, WaitVoice and event creation, yet the source-matched reference is again game_script.

In the 86 wrong predictions made by the old call-pattern classifier, 48 occur in M079 and 14 in M091_4. Thus its error distribution is highly uneven across missions; the earlier global 92.33% classified-case precision must not be interpreted as uniform per-mission reliability. The five R174 CSVs under data/ include all 44 mission totals, all 1,387 source function matches, the six ambiguous pairs and the 86 misclassified examples. The primary source BVM, not a reference AC candidate, remains the strongest authority for event semantics. No new EDF5/EDF6 runtime evidence was generated.
