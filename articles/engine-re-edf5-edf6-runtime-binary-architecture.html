EDF5 vs EDF6 runtime binary architecture

ConversionEngine RE & NetworkingGameplay & AIEDF 5EDF 6
Source-backed research / case study · Exact binary inventory and canonical-hash RE boundary

The useful cross-generation binary comparison is not EDF5.exe ↔ EDF6.exe. The two releases package the main game runtime differently.

Observed shipping layout

For the retained canonical builds:

File Size SHA-256 / role in RE
EDF5 EDF5.exe 19,896,320 B 3512d2a2e61d532c5d12dc0c5fd1ac61f6743e13349ae21301bb8449dd4bae5f — primary monolithic mission/runtime comparison target
EDF5 umbra_sandlot.dll 323,584 B supporting module; do not treat as the EDF5 equivalent of EDF6 EDF.dll
EDF6 EDF.dll 35,869,184 B 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916 — canonical main runtime RE target
EDF6 EDF6.exe 383,488 B 87fadc7dbfb6f50d0f1bfea5b3f51af779aeaa9fa03a90c62a695eb39f1e0989 — small executable, not the primary code-equivalence target
EDF6 LaunchGame.exe 1,100,288 B launcher-side binary; separate from the main runtime module
EDF6 umbra_sandlot.dll 754,688 B supporting module

The retained EDF5 build has no separate main EDF.dll; mission/runtime code is concentrated in EDF5.exe. EDF6 moves the large runtime body into EDF.dll while leaving a much smaller EDF6.exe.

Practical RE rule

When comparing game logic across EDF5 and EDF6, start from:

EDF5.exe  <->  EDF6/EDF.dll

This is especially important for mission/event dispatch, gameplay classes, networking, projectile logic and other systems whose EDF6 implementation lives in the large DLL.

Do not conclude that an EDF5 function “disappeared” merely because it has no useful analogue in the small EDF6 executable. Search the canonical EDF6 EDF.dll first.

Address and hook boundary

Exact EDF6 RVAs, signatures and structure fields in the Engine RE database are tied to the canonical EDF.dll identity above. A semantic function may survive across builds while its address changes.

Implementation rules:

  • verify the target module hash/build before applying an exact RVA claim;
  • prefer semantic signatures/RTTI/xrefs when migrating an RE finding to another build;
  • do not port EDF5 executable RVAs numerically into EDF6;
  • do not assume EDF6.exe owns a gameplay path just because EDF5 kept that path in its executable;
  • plugin/hook work that targets recovered EDF6 gameplay functions must treat EDF.dll as the relevant module unless the specific function is proven elsewhere.

What this does not prove

The packaging split does not by itself identify every responsibility of EDF6.exe, LaunchGame.exe or umbra_sandlot.dll. It is an architecture/comparison rule: where the main runtime moved, not a complete module-ownership map.
