EDF4.1 four-legged fortress on EDF6 MovingFortress — startup, core generator and ObjectAction ABI

Technical reference · Source-exact actor-class ABI and historical M117 crash evidence

Three mismatches with one borrowed class

EDF4.1's Alien4LegTank301 maps to the examined EDF6 MovingFortress class, but both classes disagree about startup state, hatch/core generator identity and the meaning of mission ObjectAction messages. A valid model and collision rig alone cannot resolve any of these mismatches.

The studied compatibility path only runs for actors with edf41_fortress metadata. The native EDF6 E510 fortress path is intentionally left unchanged.

Startup — lying-down target state can prevent any AI

EDF6's MovingFortress constructor begins at mode 0, a ground/lying state without active AI. Native target scripts wake it through a specific command or controller. EDF4.1's source fortress is already standing and its missions do not send the target wakeup command.

The bounded bridge sets the desired target mode to 1 before its native update for a marked EDF4.1 fortress, allowing the existing target transition/animation path to run. This is a state-machine mismatch, not a damaged CAS. A modder seeing a motionless fortress should inspect its class initialization and mission command vocabulary before retuning actor navigation.

Two EDF6 generators versus one EDF4.1 core hatch

EDF4.1's fortress has one ObjectGenerator associated with its core hatch. EDF6's MovingFortress has two and selects one from a message field. The studied target class only opens the critical core hatch for generator [1], which also gates whether the core can take damage. Accidentally routing the old drop through [0] can leave the fortress's vulnerable phase permanently shut.

The bridge rewrites the generator selection to 1 only while the relevant message is being handled, then restores the sender-owned argument field. The studied dispatch contracts are:

  • 0x20100: configure a drop; selection is carried in an integer at offset +0x48 in the message body.
  • 0x20103: retrieve a generator; selection is the body integer at +0x00.

Never make a blanket “generator zero is equivalent” assumption across classes. The class can parse both indices and still pick the wrong physical hatch.

ObjectAction — identical ID, different operations

The EDF4.1 mission ObjectAction message (0x1000000D) uses six part-group switch commands and a destroy action. EDF6 MovingFortress assigns different meanings to its own action table. In the historical M117 case, a source mission sends ObjectAction(1) after an earlier wave; forwarding that as a target-native action tried to spawn rubble at a locator absent from the EDF4.1 model, crashing at the target function.

The correct compatibility boundary interprets the EDF4.1 action number first. Source actions 0–5 enable or disable the intended part group through the class's existing part-control function; action 6 uses the native destroy/death state rather than a guessed HP-only rewrite. The original message is not passed through to the incompatible target action table.

Optional walking decisions

The source fortress chooses each discrete step with a 3/5 straight, 1/5 turn left, 1/5 turn right draw, unless its edge-avoidance policy intervenes. The borrowed target class has its own step-choice field; in the examined offline path that field is mostly filled by network synchronization, not by the source's locally random roaming. An optional source-fidelity adaptation updates the next choice on clip transitions. The startup and action-message fixes do not depend on enabling that optional gait policy.

Scope: This article reports a specific actor-class source/target mismatch, exact-build static RE and a historical M117 crash report. It does not establish all fortress mission parity or a fresh game-runtime PASS. Source: components/compatibility/src/edf41fortress.cpp and edf41fortress_action.h in EDF4.1 R10 HF4 R9.
