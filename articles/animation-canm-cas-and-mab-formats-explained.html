Animation formats — CANM, CAS and MAB

UniversalAnimationEDF 4.1EDF 5EDF 6
Technical reference · Reconciled native and reference research

Overview

EDF animation has three different data roles: CANM stores keyed motion, CAS coordinates named players/controllers, and MAB contains timed events. Those systems must agree with the target MDB skeleton.

Format directory

Format Role Version constraint
CANM Bone/object keyframes, typed and quantized channels EDF4.1, EDF5 and EDF6 channel layouts must be checked individually
CAS Animation players, controller variables and state Missing controller variables are not safe no-ops
MAB Events, timing and resource bindings Pointer base mode 0x03 vs 0x83 varies by generation

Start at Animation for a version-aware guide, then use the detailed findings below for exact layouts and limits.

MAB pointer-base differences

The prior brief MAB note had an incorrect blanket rule. MAB v15 internal pointers are not always absolute: EDF4.1/EDF5 use mode 0x03 (block-relative), while examined EDF6 uses mode 0x83 (owning-struct-relative); the four top-level directory offsets remain block-relative. The bounded source research validated 1,153 EDF4.1, 1,652 EDF5 and 2,487 EDF6 MABs. Read the full measured MAB layout and conversion rule rather than assuming a version-word swap. For event names, SGO parameters and sound ownership, read MAB event clocks.

Exact CANM key kinds and CAS controller ABI

The measured cross-generation CAS/CANM format and conversion gives the real record layouts and field counts: 0x30-byte CAS header, 0x20/0x30 CANM channels, 28-byte clips, 8-byte tracks, four target channel kinds and float32 Euler-to-quaternion behavior. It also records the bounded 836-file CAS round-trip and 230 paired EDF5/EDF6 corpus, including why animated quaternion bits are often not exactly reconstructible from already quantized EDF5 data.

Named CAS player groups and vcontrols explain why importing an old object's clip data without certain named controllers can crash an EDF6 target class, and why trackless donor-state placeholders are preferable to donor-bone animation copying.

The animation findings concern several distinct containers and behaviors, not one “EDF animation version.” A converter that edits only the version number is insufficient when record layouts, rotation representation and cross-references change.

CANM: animated channel data

Observed EDF5 and EDF6 CANM are structurally different:

Property EDF5 EDF6
CANM format version 0x200 / decimal 512 0x300 / decimal 768
Approximate channel record size 0x20 0x30
Rotation/channel interpretation Euler-radian channels in studied profiles Absolute XYZW quaternion representation in studied animated-rotation profiles
Additional channel fields Earlier layout Added XYZW base/multiplier and encoding type

A raw version bump destroys these semantic differences. The observed converter findings require real decoding of older channel values, correct encoding into the target representation and preservation of metadata that the target format expects.

CAS: wrapper data is not the CANM generation

CAS wraps animation/control/group/state information and can contain forward references into trailing CANM/string data. Observed CAS wrapper version words across the games are:

Game CAS wrapper value
EDF 4.1 00020000
EDF 5 03020000
EDF 6 04020000

CAS wrapper generation and embedded CANM generation must be tracked separately. A file's outer CAS version does not tell an importer how to interpret all trailing animation channels. A universal cross-game CAS conversion schema has not been established.

MAB: decoded v15 locators, event tracks and pointer bases (corrected)

The earlier short note described BoneAdjust, AnimationAdjust and FloatGroup record types, gave universal absolute offsets, and quoted 0x08 / 0x10 record sizes. That provisional description is not the validated MAB\0 v15 layout and must not be used to read or convert the examined EDF4.1/5/6 v15 files. Its original text is preserved under the R150 prior-article snapshots of R151 for provenance.

The validated 0x24-byte header at version 0x0F has four block-relative directory offsets at +0x14…+0x20. Header +0x08 specifies the format of internal offsets: 0x03 in the observed EDF4.1/5 sources means block-relative, while 0x83 in examined EDF6 files means owning-struct-relative. The actual decoded record families are 8-byte locator-list headers, 0x20-byte locator records, 0x10-byte event-track headers and 0x10-byte event keys, followed by vectors, optional embedded SGO parameters and strings. Sentinels and ordinary integer fields must not be rewritten as pointers. The source parser validated 1,153 EDF4.1, 1,652 EDF5 and 2,487 EDF6 MABs in its bounded corpus.

MAB stores important animation event timing, locator/muzzle attachments and audio-related event data; it is not a universal static-collision dependency. Pointer-base migration is demonstrably solvable for this v15 family, but a valid converted file may still reference missing target skeleton bones, wrong locations, or target-class event consumers. See the complete measured layout, pointer rule and conversion boundary and event clock/audio ownership.

The 111-root CAS/MRAB reference graph counts .CAS and .MRAB logical paths from an EDF4.1 mission-object compatibility manifest. It contains no explicit .MAB or .CANM paths, which must not be interpreted as evidence those containers do not exist or are not loaded elsewhere.
