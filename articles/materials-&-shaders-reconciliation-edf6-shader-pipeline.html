Source-backed research / case study · Reconciled

At a glance

What it is: EDF6 rendering here is assembled from several kinds of evidence: native DXBC analysis, a contributed shader guide and a separate preview translation.

Where it fits: The page follows material outputs through lighting, reflections, fog and final presentation while marking which relationships were directly observed.

Important distinction: Treat EXACT and source-guide statements differently. A plausible G-buffer model or preview match is not a fully proven, pixel-identical engine renderer.

EDF6 shader pipeline: what the source guide and native shader evidence establish

Evidence labels

  • EXACT_R18: hash-pinned static DXBC / reflected contract from R18.
  • EXACT_NATIVE_STATIC_FIELD: controlled native MAP_FIELD_RENDER DXBC comparison (R4/R6), restricted to inspected FieldRender pixel-shader paths; this is not a complete runtime framebuffer contract.
  • FIELD_TRANSLATION: a source-informed Godot preview translation, not a native GPU texture-layout or compositor proof.
  • SOURCE_GUIDE: supplied third-party guide; useful but not independently re-proven here.
  • RECONCILED: guide and retained exact evidence agree in the relevant scope.
  • CONFLICT_HOLD: guide is more general or contradicts exact family evidence; retain exact evidence.
  • UNRESOLVED: insufficient evidence for a production rule.

1. Pipeline structure

The contributed guide describes an EDF6-style deferred logical pipeline with material drawing producing:

  • albedoRGB
  • specularRGB
  • normalXYZ
  • metallic_roughness
  • viewXYZ_id
  • light_accumulate
  • specular_accumulate
  • z_buffer

followed by scene compositing, fog/distance handling, exposure and two-scale bloom/tonemapping.

This directly addresses the largest R18 gap: R18 had family-specific shader structure/output evidence but deliberately stopped before claiming actual final-frame renderer parity.

Status: SOURCE_GUIDE + CONSISTENT_WITH_R18_ARCHITECTURE.

Note: the guide text says "7 things" but lists eight. Treat the list, not the count, as the semantic statement.

Native EDF6 draw passes: what each pass actually submits

The dated 7 November 2026 EDF6 native-code study (build steam-678ccb46) traces the renderer beyond shader reflection. Umbra produces visible objects for the main, distant and shadow views; the game then submits them to distinct draw passes. These numbers are the engine's pass identifiers, not the count of G-buffer render targets or the count of shader permutations.

PassObserved native useWhat that does and does not establish
0Main-view occluder depth pre-pass; color write mask zeroProvides depth for occlusion; not a shaded color/G-buffer pass.
1Visible ordinary opaque meshes into the main-view G-bufferA material can write multiple MRT outputs here; the pass number is still one.
2Transparent forward meshes, submitted after sorting the corresponding list by distanceMaterial identity alone cannot determine blend, depth-write or final sorting results.
3Depth draw for shadow views/cascadesCan run repeatedly across shadow views; not the same as pass 0.
4Separate main-view list selected through render-node mask bit 27The source identifies the submission; its complete visual purpose is not established.
5Distant-view model submission; the studied AnimationModel path draws opaque and transparent mesh tablesA distant clip plane does not make every object's far draw automatic.

The native Umbra Commander (function 11E2120) collects and classifies visible nodes, executes the depth paths, then submits color and transparent lists. The main-view pass-2 list is distance-sorted (11E0D20), whereas pass 1 is the ordinary opaque G-buffer path. These are static control-flow findings, not a screenshot comparison for each material family.

Two separate visibility gates matter: node cull distance is compared using a cached squared radius/distance limit at node +0x60, while inclusion in the distant view depends on mask bit 0x04000000 (bit 26). A large distant far clip does not force an object lacking that bit to render. The dedicated camera/LightEnv range explanation documents how the weather-side values reach the four render cameras.

Umbra occlusion: frustum, depth queries and CPU/GPU waits

EDF6's studied renderer uses Umbra Occlusion Booster through umbra_sandlot.dll, not merely a hand-written frustum test. The traced camera initialization and pre-resolve calls set Umbra property mask 0xB. In the retained DLL code, its relevant public bits select:

Property bitMapped internal behavior
0x1Frustum culling
0x2Occlusion culling
0x8Depth-pass support for occlusion
0x4 (not in the default 0xB)Leaf-only hierarchy queries, an alternative policy studied by the EDF6VR contributor

The game queries D3D11 occlusion results through ID3D11DeviceContext::GetData in its visibility resolver. The analyzed wait path does not use DONOTFLUSH; under a wait flag, the CPU may poll while the GPU finishes the corresponding visibility work. This can make a performance stall appear in the rendering thread even though the original decision is an occlusion query.

A source-reported VR-only experiment enabling leaf-only queries reduced measured per-frame occlusion waits from 7.9 to 5.5 ms on a virtual headset and 6.2 to 2.1 ms on hardware (frame-time improvements reported as 12.6% and 15%). Those are contributor measurements, not flat-screen EDF6 benchmarks or a universal improvement guarantee. A separate property that reuses last-pass visibility was reported to leave hidden objects hidden; it is not a safe default rendering rule.

Draw work queue and model pose timing

The measured engine hands draw commands from the game side to a separate rendering thread through a command queue. The retained queue study records 16-byte command units with a handler unit followed by a payload; producer reserve/commit and render-side peek/pop are distinct operations. Consequently, the camera/game update and visible mesh submission need not observe the same update's skeletal pose.

In a contributor's EDF6 in-game probes, weapon/body draws ran zero to three updates later than the camera/update thread (tested in October 2026). That is a bounded timing observation, not a universal three-frame renderer delay. The model's CPU bone world matrices, its copied draw-pose array and the GPU skinning constants are different layers. See native model LOD and draw-pose path for the concrete data flow.

This distinction is useful when interpreting a render capture or diagnosing a mismatched attachment: a visually delayed pose does not, by itself, prove that the CAS file, projectile transform or network state is wrong.

2. Albedo and color masks

Guide:

  • base albedo.rgb * diffuse;
  • optional param_cm0_cm1.r/g sequential blend between diffuse, change_color0, change_color1;
  • alpha cutout via albedo.a < alpha_clip;
  • emissive masks remove the emissive fraction from ordinary albedo contribution.

R18:

  • Common_Clip has two independently proven static alpha predicates matching discard if sampled_albedo_alpha < alpha_clip.

Decision:

  • promote the cutout comparison to RECONCILED for known Common_Clip paths;
  • keep color-mask/change-color equations as SOURCE_GUIDE until cross-checked against the exact relevant family program(s).

3. Normal decoding

Guide generic/common-style decode:

x = 2*R*A - 1

y = 2*G - 1

z = sqrt(max(1e-5, 1-x^2-y^2))

then XY are scaled by normal_amount, transformed through normalized T/B/N basis vectors, and final normal magnitude is multiplied by occlusion.

R18 Water R12 HF1 independently proved the same R/A and G source-channel reconstruction for the three Water normal maps. This strongly corroborates the generic decode family.

The inspected native MAP_FIELD_RENDER primary pixel-shader path uses a different decode, established by controlled R4 DXBC comparisons and subsequently reproduced in the R6 preview translation:

x = 2*(R*B - 0.5)

y = -2*(G - 0.5)

z = sqrt(max(1e-5, 1-x^2-y^2))

Decision:

  • RECONCILED for the common/Water-style RA/G decode;
  • EXACT_NATIVE_STATIC_FIELD for the sampled FieldRender R×B, inverted-G decode and its 0/1/2 projection-mode family; native final-MRT semantics and runtime shader selection are separately unresolved;
  • never globalize the generic normal decoder across terrain.

The preview's three RGBA8 ID/weight texture transport remains FIELD_TRANSLATION; it is not the native GPU SRV specification. The exact native decode is compatible with the guide's terrain-exception warning but does not establish final native G-buffer packing. See native FieldRender field offsets and sampler limits.

4. Metallic / roughness packing

Guide:

  • logical output R = metallic;
  • logical output G = roughness;
  • typical packed param texture: metallic = sample.G * material metallic;
  • typical roughness = sample.R * material roughness;
  • _hr roughness = sample.R * sample.A * material roughness;
  • compositor saturates metallic/roughness for normal use.

Decision: SOURCE_GUIDE, suitable for implementation behind per-family contracts. Do not infer this for unknown legacy shaders only from parameter names.

FieldRender remains special: retained FieldRender implementation contract uses fixed metallic=0, roughness=0.980133056640625, specular=0 for the Godot translation of the closed Field material outputs.

FieldRender-specific G-buffer addendum (external source, 17 November 2026): the newly supplied ground-shader interpretation reports specularRGB = float4(0,0,0,1); a weighted normal transformed through rows of g_world_matrix with normalXYZ.w = 1; and no writes by this terrain path to light_accumulate or specular_accumulate. These exact output/write claims remain EXTERNAL_UNVERIFIED until a pinned native shader permutation and MRT/write-mask captures are examined. An omitted write does not define a target's contents or the final frame's lighting. The reported roughness ≈0.980133 agrees with the existing translation but is distinct from the DXBC-derived 0.98000002 tangent-basis adjustment. The exact native Field normal decode (R×B, inverted G) and Mode 2 were already established by the September R4 DXBC comparison; they are not new claims from this note. See the FieldRender G-buffer claim matrix.

5. specularRGB

Guide:

blend = metallic * specular_diffuse_blend

specularRGB = lerp(specular_color, pre_emission_albedo * specular_color, blend)

Decision: SOURCE_GUIDE. It is a strong candidate for Common/BRDF-family material semantics but should not be synthesized for unknown/legacy families without shader evidence.

6. Common_Light / emission: important conflict boundary

Guide general statement:

specular_accumulate = pre_emission_color * light_color * emission

with packed light mask channel inferred from the packed texture family.

R18 exact Common_Light proof (pinned main PS: b87a2d6f4aa3fed08e2b734bf48b527a4e47f6ecd0e3d84b2208c64425f065ab):

SV_TARGET6.rgb = sampled(param_r_m_light_hr).b * light_color.rgb

for the pinned main Common_Light pixel shader window. R18 did not prove an albedo/color multiply in that target write.

The native read is param_r_m_light_hr at t4/s2 (sample instruction 54); instruction 57 multiplies the blue sampled component by xgl_user_param.light_color.rgb from cbuffer byte offsets +32/+36/+40. This concerns SV_TARGET6, not an independently reconstructed scene-final RGB channel. The corresponding MDB/shader ABI reference also specifies the two Common_Clip cutout paths.

Decision: CONFLICT_HOLD.

Implementation rule:

  • for the known R18 Common_Light path, preserve the exact R18 output arithmetic;
  • do not insert a base-color multiply into that MRT solely because the general guide says so;
  • the compositor may later combine that accumulation with material color through another lane/pass, but that must be established rather than assumed.

This is exactly the kind of place where the guide is useful semantically but cannot override hash-pinned program evidence.

7. viewXYZ_id and normal magnitude

Guide:

  • RGB = view-space position;
  • A = floating object/system ID;
  • compositor reconstructs world position using inverse view;
  • length(normalXYZ) is semantically relevant and contributes to lighting;
  • near-zero normal length takes a simplified path.

This is consistent with prior R18/Field findings that system/view-position data is not an ordinary Godot material property.

Decision: SOURCE_GUIDE, architecturally compatible with retained exact output structure.

8. Direct lighting / BRDF compositor

Guide provides a GGX-like distribution/geometry and Schlick-like Fresnel path, including:

F0 = specularRGB * (0.04 + 0.96 * metallic)

and the unusual diffuse split:

light_accumulate + pointDiffuse + (1-metallic)*normalLength*(ambient+directionalDiffuse).

This is important because a stock Godot PBR material cannot be assumed to reproduce the same routing: point diffuse and light_accumulate are not suppressed by the same metallic factor as ambient/directional diffuse.

Decision: SOURCE_GUIDE and implementation-worthy in a dedicated EDF6 native-preview compositor, not as a claim about Godot StandardMaterial3D equivalence.

evidence refinement: ktaro's later static disassembly of the EDF6 lighting compute shader (RVA 0x1FCD4B0) independently describes four directional lights, with shadows applied only to light 0. A G-buffer normal of length at most 0.001 selects the unlit path. Otherwise its normalized direction is used for light directions while its original length scales the ambient and directional diffuse components as material occlusion. The reported diffuse sum is light_accumulate + (1 - metallic) × normalLength × (ambient × AO + directionalDiffuse), multiplied by albedo. This static native-compute evidence strengthens the basic source-guide routing; it does not establish one identical contract for all forward shaders or independently test a game frame. Provenance: Knowledge Hub 5b589ca, edf6/render-lighting-environment-rules.md, fact ktaro-composite-diffuse.

The same source reports two drawn 2048×2048 R32 shadow-depth cascades: view-space ranges 0.1–27.5 m and 27.5–120 m, with a fade toward full light between 70 m and 120 m. An older render-pass reference lists three constant split ranges, the third ending at 200 m. The source did not prove that the third split is rendered as a third shadow slice; keep the constant-table/drawn-resource distinction unresolved. It reports that MAE _sceneType = 1 skips the shadow-depth pass, supported by contributor Cheat Engine observations on cave/night missions, but that is source-reported runtime verification, not a new test performed for this wiki. Sources: ktaro-shadow-cascades, ktaro-scene-type-shadows.

9. Environment reflection

Guide gives the roughness->mip expression:

mipFactor = max(0, 1-(1-roughness)^2)

R18 Water R9/R10 independently recovered the same environment mip-factor shape from the pinned Water shader, which is strong corroboration.

The guide writes reflect(1, N). Do not encode that literal expression as authority. R18 Water R10 has a pinned reflection vector equivalent to the conventional normalized reflection of the incident/eye vector around the surface normal.

Decision:

  • roughness/mip shape: RECONCILED;
  • reflection input vector: use family-specific exact evidence where available; generic guide literal is UNRESOLVED/TYPO_SUSPECTED.

10. Fog ordering

Guide order:

  1. brightness fog computes a lower RGB bound via componentwise max;
  2. ordinary colored fog then lerps toward fog color;
  3. distance fading follows.

R18 Water had exact static terminal dependencies on EDF6 brightness-fog/fog parameters, but not complete scene-wide final compositing.

Decision: use guide ordering in the new preview compositor as SOURCE_GUIDE, while retaining R18 parameter/dependency facts.

Native static refinement: ktaro describes both MAE effects as four components [start, RGBA color, exponent, width]. With d the length of the view-space position, the blend amount is pow(saturate((d - start) / width), exponent) × color.a. The composite first raises each RGB component to at least its brightness-fog color multiplied by that amount, then interpolates the resulting color toward the ordinary fog color using its own amount. This supports the order above and adds the precise distance dependence. Source ktaro-fog-formula is static disassembly; the broader runtime visual equivalence remains untested.

11. Tonemapping and bloom

The guide supplies a practical pipeline:

  • repeated 2x2 downsample to 1/8;
  • high-pass + 15-tap (-7..+7) Gaussian blur for B1;
  • further 4x4 downsample and second high-pass/blur for B2;
  • central crop brightness estimate;
  • vector-length cap;
  • reduction to 1x1;
  • temporal exposure update;
  • final T*C + b1*B1 + b2*B2, then clamp to UNORM.

Supersession of the original guide-only boundary: the Knowledge Hub records ktaro's later static native-shader analysis of exposure and bloom. For both 15-sample blur passes the weight at integer offset i = −7…7 is proportional to exp(−i² / 18) and normalized across the 15 taps (Gaussian sigma 3). The two bloom inputs are, respectively, the 1/8 image and the 1/32 image, each multiplied by current exposure T; the bloom cut-off scales by saturate(L / width + 1 - cutOff / width), followed by a cap of Lmax / L when needed. The final source expression is saturate(T × scene + b1 × blur1 + b2 × blur2). These are no longer merely guessed kernel weights, although exact rendered-frame equivalence has not been performed by this project.

The same source reports the exposure input as the center half of each image dimension at 1/32 resolution (one quarter of its area), individual RGB length limited by Mmax, and measured-source luminance weights (0.298912, 0.586611, 0.114478). Its reported MAE _tone five-tuple is [target, Mmax, center, power, lerp]; a candidate target exposure is approached a fraction lerp per frame. This is a static source claim, not an EDF6 runtime acceptance. An emulator/preview that uses any other kernel still needs to identify that deviation as approximate. Provenance: Knowledge Hub 5b589ca, edf6/render-lighting-environment-rules.md, facts ktaro-exposure-chain, ktaro-bloom-chain, ktaro-mae-tone-bloom-keys.

Post-process ordering: ktaro's static pass trace places the optional FXAA 3.11-like quality pass after deferred lighting, distant-view layering, tone mapping and bloom, but before 2D UI. It uses screen color rather than temporal motion vectors or depth; do not classify it as TAA or MSAA. The cited native chain is RenderToScreenBuffer 0x1978D0 → 0x12C230 → 0x12C5A0 → 0x126CE0 → 0x1785F0 (EDF.dll RVAs). Source: edf6/map-terrain-shader-rules.md#ktaro-fxaa-position, static only.

12. Legacy specular_pow / non-BRDF shaders

No answer is promoted for SND_CHARA_BASIC or other old/non-BRDF families.

There is, however, specific later static evidence for SND_MECH and SND_CHARA_2COLORCHANGE: their EDF6 Deferred programs modify G-buffer albedo using a reflect/fall-off term, unlike the same-named EDF4.1/5 programs. This narrows the unknowns for those two paths only; it does not establish SND_CHARA_BASIC or a universal legacy shader conversion. See the equations, output counts and native vehicle comparison (7 November 2026, static DXBC/source reading).

Existing project evidence already shows that legacy ABI can coexist in EDF6 and that blindly renaming a legacy shader to a BRDF family can create an invalid shader/material ABI. Therefore:

  • absence of BRDF in a name is not enough to classify the compositor path;
  • presence of specular_pow is not enough to translate to metallic/roughness;
  • keep legacy families on a separate research lane until their actual output targets and downstream compositor usage are proven.

See LEGACY_SHADER_LANE.md.

Native DXBC oracle census and the five bounded rendering families

An archived exact-shader reconciliation reports 485 native DX11.cpk entries and 3,449 DXBC programs in its EDF6 shader oracle. These are two different count units: archive entries and compiled shader programs. Neither count alone measures distinct material families, nor does it prove that every program was observed in a frame. The counts are retained reconciliation evidence, not a new byte-level recount of the complete CPK in this wiki release.

The retained isolated analysis covers five practical family groups. The following matrix deliberately separates the kind of contract observed from the still missing frame-level proof:

Cross-generation caution for water and glass: the separately disassembled EDF5 SND_MAP_WATER_TRANSPARENT and SND_MAP_OBJECT_GLASS shaders are forward programs sampling a global cubemap, while EDF5 building windows render an interior-mapped G-buffer and receive local-cubemap lighting later. These bounded EDF5 observations do not authorize an EDF6 snd_BRDF_Map_Water or snd_BRDF_Map_Build_Window shader implementation. See the EDF5 bindings and water alpha calculation and the separate EDF6 Water source scopes.

This static catalog is valuable for locating candidate programs and validating shader resource/constant-buffer contracts, but it is not an exhaustive list of runtime draw permutations. The last necessary verification chain for a specific scene is:

  1. Identify the exact game build and material/MDB or FMEP/FMB resource.
  2. Resolve the actual bound shader bytecode and resource-view identities at the draw.
  3. Read SRV and sampler slots, raw constants, vertex declarations and render-state/depth settings.
  4. Record the bound render targets, blend state, write masks and the pixel-shader outputs.
  5. Follow the downstream compositor pass and compare final pixels with the native game under controlled inputs.

A failed visual comparison should be classified against the relevant step. An ABI-correct material that draws too shiny can have an R/M/O-versus-reflect/spec binding mismatch even when all files load; a correct terrain preview can still be wrong in the final compositor. Neither failure authorizes global shader-name remapping.

BRDF map program and resource matrix

Static. The R2 resource-table census for DX11.cpk finds SND_BRDF_MAP_COMMON (one technique, 3 unique pixel / 9 vertex programs; pixel instruction counts 59, 4, 369 and target counts 5, 1, 1), _COMMON_CLIP (2 pixel / 6 vertex programs, both discard; 62 and 13 pixel instructions) and _COMMON_LIGHT (2 pixel programs, 62 and 4 instructions; the large one writes targets 0–4 plus 6). All three model material techniques bind xgl_system b0 and xgl_user_param b2; albedo/normal/material parameter textures t2/t3/t4 on samplers s0/s1/s2. Model pixel inputs include BINORMAL, EYE_VECTOR, NORMAL, SV_POSITION, TANGENT, TEXCOORD and VIEW_POSITION; a Common variant also has FOG_FADE. Common's additional resources include lighting b3, environment t5/s3, shadow t6, point lights t7 and masks t8–t10.

The model user-parameter byte offsets are m_instancing_array_stride 0 (uint; only reflected in the MDB authoring boundary), diffuse 4 (float3), specular_diffuse_blend 16 and specular_color 20 (float3). Common then uses normal_amount 32, metallic 36, roughness 40; Clip adds alpha_clip 44. Light instead has light_color 32 (float3), normal_amount 44, metallic 48 and roughness 52. This is a shader-program contract, not a proven engine draw-dispatch matrix.

Static. In the two SND_BRDF_MAP_COMMON_CLIP.SGO pixel programs (hashes 1cb6d05adb4b7f1cead43bbc108991e01669053e929e7e31b5cf5d18bf7ef2f4 and 84b03960dbe3a42ef05d690c19d68577500080a9dd04227799386b7600f25e20), one discard each compares sampled_albedo.a - alpha_clip < 0; threshold is xgl_user_param byte 44, at instructions 24 and 10. Common Light: separate emissive target

Static. In a main Light pixel program (hash b87a2d6f4aa3fed08e2b734bf48b527a4e47f6ecd0e3d84b2208c64425f065ab, within a family of eight unique programs), instruction 54 samples param_r_m_light_hr.b, instruction 57 multiplies by light_color.rgb from bytes 32/36/40 and outputs SV_TARGET6.rgb. There is no additional albedo multiply in that pinned path; target 6's engine binding and compositing remain unknown.

R18 bounded model material rules

Static. Pinned model program reads support Clip's albedo-alpha threshold, _hr roughness tex.r × tex.a × roughness, normal X 2 × (tex.r × tex.a − 0.5) and Y 2 × (tex.g − 0.5), plus the Light SV_TARGET6 channel-B mask above. Do not carry these MDB rules into the independent FieldRender terrain path.

Eight logical buffer names are not eight proven render targets

Unverified. The guide lists albedoRGB, specularRGB, normalXYZ, metallic_roughness, viewXYZ_id, light_accumulate, specular_accumulate and z_buffer, while calling them seven in its prose. Their physical target count, slots, formats, writes and lifetime are not thereby proven.

Guide compositor remains a preview recipe

Unverified. The preview guide uses F0 0.04 + 0.96 × metallic, direct diffuse from accumulated/point light plus (1−metallic) × length(normalXYZ) × (ambient + directional), roughness-dependent environment mip, GGX-/Schlick-like terms, and a proposed bloom/exposure chain (2×2 downsample to 1/8, high pass, 15-tap Gaussian B1, 4×4 B2, brightness crop, temporal 1×1 exposure and final T × C + b1 × B1 + b2 × B2). The guide's reflect(1, N) is a typo. None of those whole-frame kernels or timings has native proof; compare the separate game's post-process investigation before implementing parity.

FieldRender terrain: packed map data, projection and shader limits

Terrain is not an MDB/BRDF material

Static. FMEP → FMB FieldRender vertices carry POSITION float3 and NORMAL float3 (stride 24), no vertex UV. World position and orientation matrices determine texture projection; MDB tangent-UV samplers, alpha clip, material roughness packing and normal decode do not transfer to terrain.

FieldRender source binding layout

Static. The reported terrain setup binds array textures g_color_array, g_N_array, 80-byte g_materials, 64-byte g_orientations, 80-byte-per-cell g_mass, 16-byte g_material_id_list, g_mass_size_xz, g_mass_divide_count_xz, g_mass_origin, g_world_matrix and g_normal_interpolation_param.

Material records are 0x50 bytes

Static. Source record offsets: +0x00/+0x08/+0x10 three int2 projection descriptors, +0x18 mapping mode, +0x1C int3 base-color slices, +0x28 int3 detail-color slices, +0x34 int3 normal slices, +0x40 float4 parameters (first float is correction exponent). R4's 315-program sample reads offsets 0x00/0x10/0x18/0x1C/0x20/0x30/0x40 but not padding 0x2C, 0x3C or 0x4C.

Orientation records and reciprocal scale

Static. An orientation source record is 0x20 bytes: Euler float3 in degrees, scale float3 and UV-offset float2. The engine converts degrees to radians and reciprocal scales into the 64-byte projection matrix. An ENKEIRIGHT mode-0 exemplar uses pair (0,1), base slice 0, detail 1, normal 0; its two orientations both rotate (90,0,0) but have scales 7 and 100, not one common UV scale.

Three projection modes, independently of layer count

Static, R4 native primary pixel comparisons (2026-09-17). Mode 0 projects one base×detail pair. Mode 1 projects two planes, (row0,row1) weighted by axis row2 and (row2,row1) by row0. Mode 2 includes both side projections and a row1-projected (row0,row2) plane, choosing slot 1 when dot(N, row1 of pair0) > 0, else slot 2. Directional weight is max(abs(dot(N, axis)), 1e−5) ^ m_correction, normalized over axes: no exponent clamp and no pre-normalization of orientation rows. Guides describing only two modes are incomplete.

Mesh-to-shader row matching

Static. Across 9,753 meshes in 46 stock FMB files, the mesh's +0x28 index points to a seven-dword shader-table row whose first dword agrees with the layer count stored in the high byte of mesh +0x24; pass/flag dwords are zero in this census. The reported shader family MAP_FIELD_RENDER<n>_1_14_<pass>.SGO has 45 files; projection mode and pass are separate axes from layer count. A bad row index produced black terrain patches in the author's experiments.

Cell corners, sparse material IDs and blending

Static. Terrain cell coordinate is (world.xz − g_mass_origin) / g_mass_size_xz, clamped to grid size; fractional position bilinearly interpolates four weight corners. Each 0x50-byte cell stores a 32-bit list selector at 0x00 and 16-byte corners at 0x10/0x20/0x30/0x40; audited corner weights have at most three nonzero bytes, typically sum 253–255. A 16-byte MaterialIDList uses 0xFF for vacant slots, not as a terminator—scan all 16 positions. The reported shade blends as sum(weight × base × detail) / (sum(weight) + 1e−7) over up to 12 local slots; this is a local upper bound, not 12 materials in every cell.

Measured HEIGEN and CAVE grids

Static, 2026-09-11 offline report; exact pixel equation still open in that report. HEIGEN samples use 2×2 world-unit cells (first inspected tile: 80×80 cells, origin 1090,1090); CAVE samples use 1×1. Sampled mass_cell_count = divide_x × divide_z. In the wrapper descriptor at +0x30, the mass grid size is +0x0C, divide count +0x14, origin +0x1C, cell count +0x2C, material list count +0x30 and relative data offsets +0x34/+0x38. Weight bytes after the first three are zero in those samples. CAVE corner sums: 49,246 corners at 254, 22,690 at 255 and 400 at 253.

Array DDS dimensions, formats and address modes

Static; 20 payloads audited. DX10-header Texture2DArray DDS data has depth 1 and full mip chains: 2048²/12 mips full-resolution, 512²/10 LOD color and 128²/8 LOD normal. Slices (color/normal): CAVE501 4/3, CAVE503 4/4, CAVE601_2 5/3, HEIGEN507 8/6, BASE502 12/9. Color is DXGI 71 (BC1), not an intrinsically sRGB DXGI 72; normals are DXGI 77 (BC3) in CAVE samples, DXGI 71 (BC1) in HEIGEN/BASE. Actual view sRGB conversion remains unknown. Reported terrain sampler is linear min/mag/mip and WRAP U/V/W.

HEIGEN507 material slices and unresolved lanes

Static. Six HEIGEN507 material rows use base color A slices 0,2,4,7,6,5, detail color B 1,3,1,1,1,1 and normal 0,1,2,5,4,3, spanning all eight color and six normal slices. One projection descriptor per HEIGEN material contrasts with three in CAVE; planar ground versus three-axis cave mapping is interpretation, not demonstrated runtime behavior. HEIGEN rotations (90,0,0) and scales 7/100 contrast CAVE zero rotation and scales 50/10/40/92. If normalized wrapped UV sampling is eventually confirmed, implied 2048 texture density is ≈292.6, 204.8, 51.2, 40.96, 22.26 and 20.48 texels/world-unit for scales 7/10/40/50/92/100. The descriptor's second integer, auxiliary material float4 Y/Z/W, HEIGEN 2500-unit plane purpose and actual draw sampler state stay open.

Terrain normal decode differs from model and water

Static. FieldRender uses nx = 2 × (tex.r × tex.b − 0.5), ny = −2 × (tex.g − 0.5), nz = sqrt(max(1 − nx² − ny², 1e−5)). Its basis is Tx = normalize(U − N × 0.98000002 × dot(U,N)) and Ty = −normalize(V − N × 0.98000002 × dot(V,N)); weighted normals use a separate 1e−5 Y guard before final normalization. Do not conflate 1e−7 color denominator, 1e−5 normal floor and 0.98000002 basis factor.

Native leaf census and non-native FIX3 control

Static, source-bounded. A HEIGEN native audit covered 1,200/1,200 leaves with a 102-leaf CAVE control, checking geometry, compressed payloads, mass grids, selector bounds and sparse lists. Native ENKEIRIGHT selector 0x0202 with configuration row 4 occurred in 80/118 leaves. A separate non-Sandlot, EDF5→EDF6 FIX3 experiment contained FMB version 0x110, 21 shader rows, a two-triangle/four-vertex type-2 flat leaf, material-list width 2, shader capacity 2, configuration 4 = (2,1,0,0,0,0,0), weights 127+127=254 and 2048²/12-mip arrays (BC1 color DXGI71, BC3 normal DXGI77).

FIX3's projection pair (0,0), detail slice 0 and one zero-rotation/scale-20 orientation differed from native ENKEIRIGHT material 0's (0,1), detail 1 and two (90,0,0) orientations at scales 7 and 100; base slice, mode 0 and correction 6.0 agreed. FIX2→FIX3 also changed carriers/loader path, so is not a single-variable test. A native decode/re-encode restored material 0 and orientations 0/1 byte-identically (3/3). Its four-float auxiliary vector (6.0, 0.5019609928131104, 0.5019609928131104, 0.0) has no proven Y/Z/W meanings. One audited native binary SHA-256: 0027ed493827ccfcdc0906f5efb5714c00b68567400fe505f741df756074dd31.

Portable bridge transport is not engine layout

Unverified. The portable renderer repacks material IDs as three RGBA8 textures and weights as another three RGBA8 textures. This is its own bridge format, not a native GPU buffer census. Neither “always three materials” nor “12 painted materials at every sample” follows.

Reported terrain logical G-buffer values

Unverified as native attachments. The outside guide describes base×detail weighted albedo with alpha 1, specular (0,0,0,1), a normal transformed by g_world_matrix, metallic 0 and roughness 0.980133056640625 (not the 0.98000002 basis value); light/specular accumulators are reportedly not written by this pass. Unwritten is not equivalent to cleared-to-zero or evidence of no later terrain specular response.

Water: pinned forward shader, normal and environment dataflow

Water resources and full user-parameter offsets

Static. SND_BRDF_MAP_WATER has one technique, 2 pixel/6 vertex programs. The four-instruction pixel program shares hash 6f05e9159ecac2474b79be8a1667a6ac3e4bbd8f4a8aabe754449cb0b4fb19a2 with Common and Light; the other Water program has 428 instructions. Both write SV_TARGET0 only. Inputs include BINORMAL, ENV_INDEX, EYE_VECTOR, FOG_FADE, NORMAL, SV_POSITION, TANGENT, TEXCOORD0–4, VIEW_POSITION. Water textures/samplers: three normals t2–t4/s0–s2, bubble_albedo t5/s3, environment cube array t6/s4, scene g_xgl_viewXYZ_id_texture t7, shadow t8 and point-light resources t9–t12, plus additional light b3.

xgl_user_param byte offsets: instancing stride 0; water_color 4 (float3); specular_color 16 (float3); metallic 28; roughness 32; all_scroll_speed 36; all_scroll_angle 40; all_uv_scale 44; normal1_scroll_speed 48 (float2), scale 56, amount 60; normal2_scroll_speed 64 (float2), scale 72, amount 76; normal3_scroll_speed 80 (float2), scale 88, amount 92; bubble1 scale 96, scroll_speed 100 (float2); bubble2 scale 108, scroll_speed 112 (float2); bubble_depth 120; bubble_curve 124; bubble_diffuse 128 (float3); blend_depth 140; blend_curve 144; near_fade 148. The t7 scene-depth read is consistent with reported variant A but does not identify dispatch behavior.

Three water normals have a distinct R×A / positive-G decode

Static, hash-pinned R12. Normals sample normal_map1 t2 at v8.xy (amount byte 60), map2 t3 at v8.zw (byte 76), map3 t4 at v9.xy (byte 92). Each uses xy = (2 × (R×A−0.5), 2 × (G−0.5)), z = sqrt(max(1−dot(xy,xy), 1e−5)), normalizes each amount-adjusted layer, adds three layers and normalizes again after the TANGENT/BINORMAL/NORMAL basis. This is neither a generic RG decode nor FieldRender's R×B / negative-G path.

Water normal proof locations in shader instructions

Static, R12. Samples occur at instructions 47, 58, 71, with per-layer decodes at 48–57, 59–68, 72–81; amounts are at constant-buffer bytes 60/76/92. Resource swizzle R,G,A,B exposes sampled texel alpha to the X decode. The Z floor token 0x3727C5AC represents approximately 9.999999747e−6. Layer sums are L2+L1+L3 at instructions 69/70/82. The shader archive alone does not establish a DXT5nm disk format for those textures.

Water cube-array lookup and revised mip expression

Static R10/R13. The float TextureCubeArray is t6 (RDEF dimension 10) and sampler s4. ENV_INDEX comes from v7.x, UTOF at instruction 402. The reflection-like vector at 116–121 is normalize(r3.xyz − 2 × dot(r3.xyz,r0.xyz) × r0.xyz) but the operands' semantics are not fully qualified. Bytes 32 of user params hold roughness: at 114–115, r1.w = r1.w × (1−roughness) + roughness. RESINFO(t6,mip0) at 400 supplies a mip-related component; SAMPLE_L at 406 chooses LOD RESINFO.w × max(1−(1−r1.w)²,0), the reporter's revised expression. Actual bound SRV/sampler, mip count, array contents, filtering, sRGB path, opcode 136 meaning, branch reachability and final composition still need native capture.

Forward output, not a deferred material attachment

Static. The observed Water program samples environment with ENV_INDEX and roughness-dependent mip selection and writes color to SV_TARGET0 only. It is described as a forward water draw after scene composition, rather than deferred albedo/specular MRT filling; exact real-frame scheduling, blending and depth settings are still unproven.

One bounded native static-water exemplar

Static. In NW_EUROPE01, eu1_nw_field01_water.mdx is a MAPB T1 class-10 object with 33-variable embedded SGO (Type=水, Collision_Enable=−1, durability 0) and one T2 placement. MAPO carries visual MDB, _hk.mdb and HKT, no T50/p58 group; MAD collision is a static hknpCompressedMeshShape with flat footprint. The visual MDB references snd_BRDF_Map_Water (26 named parameters, four samplers). Four inspected maps yielded one static-water material family; two pixel programs do not prove separate river/ocean kinds.

Reported water A/B shading, not mapped to native shaders

Unverified external interpretation. Proposed A reads scene view depth and bubbles: depth_diff=abs(sceneZ−waterZ), depth blend min((depth_diff/blend_depth)^blend_curve,1) times near fade, foam from two bubble-alpha samples with bubble-depth correction; water/foam color, metallic/roughness and alpha then blend (alpha proposed as max(foam,depthBlend) × saturate(FOG_FADE.y)). Proposed B lacks those reads and floors direct-specular roughness at 0.04, alpha saturate(nearFade × water_color.a) × saturate(FOG_FADE.y). Both propose lerp(diffuse,env×color,metallic²) + env×0.2×(1−roughness)×(1−metallic²). The two behavioral sketches are not paired to the two pinned programs; the short shader is not demonstrated to be B.

Reported fog tail and vertex FOG_FADE

Unverified as a full-frame contract. The outside recipe uses bright = pow(saturate(FOG_FADE.z), brightness_fog_curve) × brightness_fog_color.a, fog = pow(saturate(FOG_FADE.x),fog_curve) × fog_color.a, then a bright-color maximum and lerp(color,fog_color.rgb,fog). FOG_FADE is a vertex input, not independently recomputed from fog_mul/fog_add in the asserted pixel flow. R5 pins fog fields in one Water output only; spelling brightness_fog_cursve in the guide was not checked against reflection.

EDF6 DX11.cpk shader SGO containers and native bytecode slots

Source: shader-sgo-container-and-slots.md, a static archive, SGO and DXBC survey. Counts refer to the author's pinned Steam archive, not an all-edition inventory. In particular the pass-slot count below is not reconciled to an earlier 3,449-program claim; neither can silently replace the other.

485 shader SGOs in the Steam DX11 archive

Static census. DX11.cpk has 485 entries, all shader SGOs: 315 under MAP/SHADER/DX11 (all MAP_FIELD_*) and 170 under SHADER/DX11. Prefix breakdown includes SND_BRDF_* 71, SND_MAP_* 34, SND_CHARA_* 13, SND_UI_* 10, SND_UFO_* 5, SND_COMMON_* 4, SND_MECH* 5, SND_DEBRIS_* 2, SND_DINO_* 2, SND_FARMAP_* 2; 22 other entries belong to individual enemies/effects and TEST files. Every sampled shader SGO is little-endian SGO\0 version 0x102.

SGO 32-byte header and raw blob placement

Static. In the shader SGO header, name count is +0x10, name-table offset +0x14, reserved +0x18=0 in every stock file, and raw DXBC area begins at +0x1C. Nodes (top-level then array children) and the name table precede bytecode blobs; one pool of names/strings follows blobs, not before them. Each blob start is 16-byte aligned, though raw-area start itself is aligned in only 373 of 485 files (112 are not); align individual blobs. Of 485 files, 156 reference one shared blob range from multiple raw nodes.

Technique names and one pass per member

Static. Each top-level technique member contains exactly one pass row in the 485 surveyed files; the separate instancing-info array is metadata, not a pass. The 19 observed member names comprise ZPass (485), Deferred (449), Forward (104); their _Skinning1 through _Skinning4 variants (Skinning1 ZPass/Deferred/Forward 156/122/99; skinning levels 2–4 in 82/63/71 files respectively); their _Instancing variants (77/67/30); and XGL_FXGEN_INSTANCING_INFO_ARRAY (77 files). The engine selects a technique and its pass; these are layout slots, not independent unique bytecode counts.

Five-element vertex/pixel pass row

Static. Each row has element0 a raw vertex DXBC, elements1–3 integers that are zero in all 2,237 rows, and element4 a raw pixel DXBC. The selector ["Deferred",0,4] therefore addresses the pixel shader of Deferred pass0. Several slots can point at one bytecode blob. Nonzero meanings for the three intermediate integers remain unknown.

Optional instanced-vertex semantic descriptors

Static with two integer meanings partly inferred. XGL_FXGEN_INSTANCING_INFO_ARRAY has zero rows in 44 files, one in 22 and two in 11. Each row holds five values: type name, 4, 1, member name, semantic. SND_BRDF_COMMON_BASIC.SGO describes float4 m_xgl_instancing_rotation_xyzw as INSTANCING_rotation_xyzw and float4 m_xgl_instancing_trans_xyz_scale_w as INSTANCING_trans_xyz_scale_w, interpreted as rotation quaternion and translation with scale in w. Integer4 likely denotes components; integer1 is not proven.

4,474 shader slots but only 1,103 unique byte sequences

Static corpus scan. The 485 SGOs expose exactly 2,237 vs_5_0 and 2,237 ps_5_0 slots, no geometry/hull/domain/compute stages or other shader models. Every bytecode container has precisely ISGN, OSGN, RDEF, SHEX, STAT chunks and recomputed valid stock checksum. Across slot reuse, there are 1,103 distinct SHA-256 byte sequences. An earlier BarteY survey reported 3,449 DXBC programs for the same 485 entries; its distinct counting unit remains open, so neither tally is presented as a correction of the other.

Retail DXBC checksum is an MD5 variant

Static, checked by source author across 4,474 programs. A DXBC file begins DXBC, 16-byte checksum at +4, word1, total size +24, chunk count +28 and chunk offsets +32; chunks hold {four-byte tag, size, payload}. The shader-model5 program is SHEX whose first word encodes stage in the high half (0 pixel, 1 vertex), 0x50 in low half. The checksum is not plain MD5: it runs MD5 compression over bytes from offset20 using a special final block (bit length in the first word; shifted length OR1 in the last word; 0x80 padding). The author's Python version matched all stock programs, following AMD's DXBCChecksum description.

Native bindings constrain shader replacement

Static. Texture units and constant-buffer slots are assigned by the native engine, not renegotiated by replacement DXBC. A replacement must honor the byte layout and meaning of every constant it reads, including material layouts documented in the BRDF map contract and shader parameter table. Reflection metadata alone does not validate runtime material semantics.

Offline shader repack checks are not runtime parity

Unverified in-game. The author's repacker preserves original RDEF, ISGN, OSGN chunks while accepting a new shader program and STAT, because the engine receives original reflection. It checks identical stage/signature rows, no newly referenced resources, constant buffers no larger than originals, a valid checksum, and for assembly input matching dcl_ declarations. This demonstrates only that the replacement passes the tool's static constraints; no successful visual in-game test is supplied, and the source README explicitly warns that offline validation does not ensure correct rendering.

Foliage reports: independent discard stages and G-buffer hypotheses

Screen-space thinning before sample

Unverified external description, no pinned native variant. Proposed density saturate(0.7 × (SV_Position.z × SV_Position.w) − 2.0) × ALPHA (v3.z); pixel pattern uint(SV_Position.x + SV_Position.y). Retained pixels by ascending density: ≤0.05 none; ≤0.10 pattern&3 == 0 (25%); ≤0.20 pattern&2 == 0 (50%); ≤0.30 pattern&1 == 0 (50%); ≤0.50 all; ≤0.75 pattern&3 != 1 (75%); above 0.75 all. The nonmonotonic 100→75→100% bands may be branch order or transcript error; see the existing detailed foliage table immediately below.

Independent texture-alpha discard

Unverified external description. A separate cutout samples g_map_draw_utility_color_textrure.Sample(s,float3(v3.xy,v5.x)) from an array slice, discarding alpha below 0.8. The unusual textrure spelling was not verified in reflection. It must not be conflated with the model Common_Clip float alpha_clip: the source's 44-material model census gives 42 thresholds of 0.5 and two of 0.3435.

Reported foliage outputs and unresolved disappearing plants

Unverified. The guide proposes albedo tex.rgb × COLOR.xyz, specular 0, normal normalize(NORMAL), metallic 0, roughness 1 and viewXYZ_id=(VIEW_POSITION.xyz,g_xgl_id), with no accumulation targets written. The guess that near-camera vegetation missing when porting EDF4.1 maps to EDF6 comes from thinning is a diagnostic lead only, not a proven root cause or fix.

EDF6 foliage: reported pixel thinning and independent alpha cutout

An externally supplied 17 November 2026 foliage-shader interpretation describes two separate discard stages. The first is a screen-pixel thinning calculation before texture sampling: density = saturate(0.7 * (SV_Position.z * SV_Position.w) - 2.0) * v3.z, with integer pattern = uint(SV_Position.x + SV_Position.y). The source labels v3.z as vertex ALPHA; precise position semantics and threshold comparisons remain EXTERNAL_UNVERIFIED.

Reported density band Pixel retained when Expected retained fraction
<= 0.05 never 0%
> 0.05 through 0.10 (pattern & 3) == 0 25%
> 0.10 through 0.20 (pattern & 2) == 0 50%
> 0.20 through 0.30 (pattern & 1) == 0 50%
> 0.30 through 0.50 always 100%
> 0.50 through 0.75 (pattern & 3) != 1 75%
> 0.75 always 100%

The 100%→75%→100% sequence is nonmonotonic in the supplied description; no native pixel-shader branch inspection has yet established whether this is intentional or a transcription issue. The second discard samples a reported Texture2DArray slice using v3.xy as UV and noninterpolated v5.x as TEXID, then discards samples with tex.a < 0.8. This is not a general replacement for independently measured Common_Clip material-specific alpha thresholds.

The same external foliage report describes albedoRGB.rgb = tex.rgb × COLOR.xyz, zero logical specular, normalXYZ.xyz = normalize(NORMAL), metallic 0, roughness 1, and viewXYZ_id = (VIEW_POSITION.xyz, float(g_xgl_id)), with no writes from that shader to the light/specular accumulation targets. Its precise output signatures and blending remain unverified; an unwritten target is not necessarily zero. Near-camera foliage disappearance in an EDF4.1→EDF6 port is only a diagnostic hypothesis for this thinning path, not a confirmed cause or fix.
