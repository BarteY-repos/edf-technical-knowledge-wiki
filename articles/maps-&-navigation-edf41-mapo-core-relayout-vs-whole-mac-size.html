EDF 4.1 map MAPO conversion: object-row relayout and exact-size traps

ConversionMaps & NavigationMapsEDF 4.1EDF 6
Technical reference · Historical byte/oracle + offline serializer relayout; no runtime qualification

Scope: Source-backed offline reconstruction of one NW_HILLYCITY_LIGHT EDF4.1→EDF6 map. These offsets and counts describe the particular legacy/target MAPO record family, not a universal MAPO revision rule.

The two layers that must not be confused

A MAC file is an outer map container. map.mapo is one embedded payload. Byte positions, sizes and digests for the whole container are therefore not MAPO dimensions. A historical reconstruction mistakenly treated 7,872,840 bytes (whole MAC) as a MAPO-sized figure; that claim and the derived missing-edge hypothesis were disproved.

The verified source MAPO in this case is 3,034,994 bytes, with a 0x58-byte header and 44,213 object rows, each 0x38 bytes. The EDF6-compatible serializer expands the core to a 0x60-byte header and 0x3C-byte object rows.

Core field Older source layout Reconstructed target layout Change
MAPO header 0x58 (88 B) 0x60 (96 B) +8 B
Object row 0x38 (56 B) 0x3C (60 B) +4 B per row
Object rows 44,213 44,213 Preserved in this map
Object table growth — 44,213 × 4 +176,852 B
Header + table growth — 8 + 176,852 +176,860 B

This is a record relayout, not a demand to add 176,860 arbitrary padding bytes at the file end. Pointer tables, offsets and later payloads need to agree with the new locations.

Why the final MAPO is much larger

The converted payload also carries additional target structures including collision and collapse data. In the observed R1D reconstruction these were 291 groups, 2,863 T58 pieces, 8,980 T50 outer records and 386,865 T50 subrecords, with zero T50 edges. Those figures are a case-specific evidence census, not an engine-wide rule that T50 always has no edges; other native EDF6 maps do have substantial collapse-link graphs.

The reconstruction yielded a 6,816,056-byte MAPO candidate. That exactly matches the retained historical target length but does not match its SHA-256. An assembled 7,872,840-byte MAC also matches the old whole-MAC length without matching the historical bytes. Therefore the formerly suspected missing bulk payload was not the remaining problem; ordering, serialization and source semantics remain.

How to validate a converter

  1. Identify the outer container size and the inner MAPO size independently.
  2. Read the actual object-row count before changing a stride; never borrow an object's count from a donor map.
  3. Rebuild offsets and relative references after header and record expansion.
  4. Validate auxiliary T58/T50 placement and source/collision-body identity independently of total byte length.
  5. Compare the exact target digest only when the relevant target build and original bytes are available.

Do not mix MAPO table families

The separate 0x1C (28-byte) MAPO item stride documented elsewhere in this wiki applies to another measured table family. It is not an alternative spelling of this 0x38→0x3C object-row relayout. Always identify the table/record family before reusing a stride.
