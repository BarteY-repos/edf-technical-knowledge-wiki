EDF5 BVM event scheduler: multi=1, delay selection and end-event sentinel

EDF 5Game technical referencesMissions / scheduling
Technical reference · EDF5 source static analysis; no new runtime qualification

The inspected EDF5 BVM runtime stores a registration's delay at record offset +0x18, and its multi flag at +0x20. The scheduler's native comparison is exact: multi == 1 means append all ready registrations; otherwise choose one eligible registration with the greatest delay. This is not a generic nonzero/truthy bit interpretation.

No other multi values appeared in the shipping census. The corresponding EDF6 AngelScript scheduler uses EVENT_TYPE_SYNC=0 (one best ready event) and EVENT_TYPE_ASYNC=1 (all ready events). Thus the appropriate source behavior comparison is multi == 1 versus any other value, not multi != 0. Four official EDF6 source ports—M015, M016, M024, M035—have event-type totals that differ from the EDF5 source; these are observed port authoring deviations, not a discovered extra bit in the original EDF5 flag.

End-event time sentinel

Across the 44 exact original/official mission pairs, a special source end registration whose delay is exactly 100.0f becomes 100000000.00 in the official target representation. Do not apply a blanket time unit multiplication to ordinary delays, and do not equate this special case with all references to 100 in arbitrary scripts.

Distinct factor operations

The mapped factors include 9201 object destroyed, 9202 object encountered, 9300 AI movement end, 9301 movement end or death, 9116 group member count, 9117 group encounter, and 9205 ride vehicle. 9201 and 9202 are distinct registered conditions. The exact44 reachable factor census achieved 2,147/2,147 source/reference sites; it is bounded, not proof of all conceivable mission factors.
