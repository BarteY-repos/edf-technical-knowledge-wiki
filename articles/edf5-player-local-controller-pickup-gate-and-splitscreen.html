EDF5 local versus remote players: controller slots and pickup checks

EDF 5Game technical referencesPlayers / networking
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R133 test

The fact that a game object has player animations or a SoldierBase RTTI type does not prove that a pickup test runs for that object on every peer. EDF5 has a local controller slot stored on the player, and the player-update routine tests it before entering the pickup code.

Recognizing a local avatar

The source identifies player +0x23C as a pad index and player +0x240 as a pointer to the corresponding controller-manager slot. Assigning a valid controller stores both; clearing the association sets the pad index to -1 and the pointer to zero. The native mission-script player-creation path can create an avatar with no local pad.

The normal player update skips the pickup block when +0x240 == 0. Thus a remote avatar does not run the same spatial pickup test in your local player's update. In split screen, the test can run once per locally controlled player per frame. A player's network ID used in a pickup message is not the same as the local controller index.

Why this matters for visualizing multiplayer

Each computer can have local versions of multiple avatars and crates, but the spatial check is gated by controller ownership. A remote player's confirmed pickup still arrives through the online event handler and can award shared loot without that remote avatar ever running your computer's local proximity check. The result is not contradictory: the local check and the network confirmation are two separate routes.

The source notes that this distinction was recovered by static disassembly of the per-player update and four soldier-class update call sites. It does not establish the exact number of supported gamepads or a universal split-screen installation configuration.
