This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Terrain collision

Map terrain collision is collision.hkt inside MAP/map.MAD (50 maps: Root.cpk 4, Chunk01 1, Chunk02 45

Evidence: static · Build: steam-678ccb46 · Fact ID: map-collision-load

Map terrain collision is collision.hkt inside MAP/<map>.MAD (50 maps: Root.cpk 4, Chunk01 1, Chunk02 45; 18 KB to 133 MB, 38 over 10 MB). MapRABInit (190770) opens <map>.mad, looks collision.hkt up by the CRC32 of its name and passes it to 18C5E0. The root holds one hknpPhysicsSceneData plus many hknpMaterialPalette variants named after the bodies (IG_EDFBASEMENT01 has 40 bodies); terrain shapes are mostly hknpCompressedMeshShape with per-triangle palette indices.

Basis: Ghidra decompilation of EDF.dll; every map file

Addresses (build-specific RVAs unless indicated): 190770, 18C5E0

Attribution: ktaro, SHKT report (Usage §5.1, Spec §1.1, §4.2) · 2026-10-16

Map collision body naming convention

Evidence: static · Build: steam-678ccb46 · Fact ID: map-body-names

Map body names are <MDB model name>.<collision node name>|<render node name> (the | part optional), for example com_ym_jihanki_panel1.com_ym_Jihanki_Panel1_Colli|ym_Jihanki_Panel1; the game splits at . and |, builds <name>.hkt and matches the bodies with the MDBs in the map RAB by name.

Basis: Ghidra decompilation; the files

Attribution: ktaro, SHKT report (Usage §5.1, Spec §4.2) · 2026-10-16

Map material dynamic / static friction and restitution (hknpMaterial +0x2A / +0x2C / +0x2E, half floats) are overwritten by the map settings (g_MapMgr).

Havok map material hkConfig property metadata

Evidence: verified · Build: steam-678ccb46 · Fact ID: map-hkconfig

Map material names and shape properties (key 0xF201, an hkStringObject) hold JSON such as {"hkConfig": "p_material=2;p_penetration=0;ai_cost=0;", "name": "AAA_Panel01"} (without hkConfig, as in {"name": "COL_mat"}, all zero). At map load map::havok_FixupShape (183450) packs it as p_material | p_penetration << 8 | ai_cost << 16 into the userData of the material and of every shape; the userData stored in the file (0 everywhere) is unused. Where p_penetration is nonzero the collision layer becomes 26 (per triangle in compressed meshes, per child in compounds). In game: p_penetration=1 lets player and enemy bullets through walls and floors while characters are still blocked; p_material=1 glass (glass-shard effect, no bullet holes); p_material=2 metal (sparks, no smoke); 0 default. ai_cost (bits 16-23, probably AI path cost) is unconfirmed; four object SHKTs (queen ant and others) also carry hkConfig strings, applied or not is unknown.

Basis: Ghidra decompilation; ktaro's in-game tests (whole-map p_penetration=1, p_material=1 / =2)

Addresses (build-specific RVAs unless indicated): 183450

Attribution: ktaro, SHKT report (Usage §5.1, Spec §5.4) · 2026-10-16

Refines map-hkconfig: the code that reads p_material was not found

Evidence: static · Build: steam-678ccb46 · Fact ID: map-hkconfig-usage

Refines #map-hkconfig: the code that reads p_material was not found; its meaning (0 default, 1 glass, 2 metal) rests on names (windows AAA_Win = 1, vending machines AAA_Panel01 and AAA_Body01 = 2; impact sound presets GlassClash and MetalHit) plus the in-game tests; p_penetration = 1 is fixed by the layer-26 partners (collision-layer-partners in physics-shkt.md). Usage in the game data (object SHKTs plus the IG_EDFBASEMENT01 map): p_material=2;p_penetration=0;ai_cost=0 138 times, p_material=1;p_penetration=1;ai_cost=1 73 times (queen ant and bee ragdolls); IG_EDFBASEMENT01 alone has 983 such JSON strings. The four non-map SHKTs with hkConfig are GIANTANT_QUEEN, GIANTBEE_QUEEN, RAGDOLLTEST_HORNET and E505_GENERATOR_SL_BREAK; whether havok_FixupShape (a map function) applies it to object SHKTs is unconfirmed. ai_cost may only matter when navmeshes are generated.

Basis: ktaro's counts over the game data; the curator re-read research/03 §2

Attribution: ktaro, EDF6 SHKT Editor 1.0 (research/03_followup §2, research/04 T10) · 2026-10-19

Hit surface reader for p_material

Evidence: static · Build: steam-678ccb46 · Fact ID: hit-surface-material

A reader of p_material (#map-hkconfig-usage said none was found): the hit surface lookup 1082E0(hit = collector+0x30) calls 11A9B60(out, [20B2958]+0x10, hit) and returns the low byte of out+0x20. 11A9B60: out+0 = the hit's material id (hit +0x58, i.e. collector +0x88; 0xFFFF zeroes the output), out+0x10 = hit +0x5C (the shape tag), out+8 the body's shape (world slots +0x28 material table, stride 0x50 at +0x48; +0x80 the body, shape at +0x78); it descends compound shapes (type byte +0x18 = 0xB) by the shape-key bits to the leaf (out+0x18) and stores the leaf's userData +0x28 in out+0x20, or for a type-8 leaf the material's +0x40. Since map load packs p_material | p_penetration << 8 | ai_cost << 16 into those userData (#map-hkconfig), 1082E0 returns p_material (0 default, 1 glass, 2 metal). Callers include the helicopter's down-ray (654711) and 102979 (a debug print userData=0x%x). SoundPreset 7B3840 maps the surface sound names soil, grass, metal, water to slots +0x30..+0x60 (water the fourth; the author's reading, "M"); whether a seabed shape carries a water value is unknown.

Basis: 1082E0 and 11A9B60 read whole with fn.py here (KH chat 47); the userData link follows from #map-hkconfig

Addresses (build-specific RVAs unless indicated): 1082E0, 11A9B60, 654711, 102979, 7B3840

Navigation meshes

Map high and low navmesh HKT/NVMD pairs

Evidence: static · Build: steam-678ccb46 · Fact ID: navmesh-worlds

Each map has two navmeshes, MAP/<map>.NAVMESH.HKT and .NAVMESH_H.HKT, each with an .NVMD (100 files: Root.cpk 8, Chunk01 2, Chunk02 90). 18F9A0 builds the paths (flag 1 -> .navmesh.hkt, 0 -> .navmesh_h.hkt); MapRABInit loads both; MapMgr::121470 creates AI world 1 (BIG) from .navmesh.hkt and AI world 0 (HUMAN) from .navmesh_h.hkt, and CreateAiCharacter(system, pos, worldId, params) picks the world. World 0: HumanBase (EDF soldiers), RouteGuideBase, vehicles, BombBullet01; world 1: HumanoidBase, Berserker Large, Merman, ShellFish, GiantDango. The debug BATs agree (DISP_HUMAN_NAVMESH.BAT = disp_ai_world 0, DISP_BIG_NAVMESH.BAT = disp_ai_world 1).

Basis: Ghidra decompilation of EDF.dll; debug BAT files

Addresses (build-specific RVAs unless indicated): 18F9A0, 121470

Attribution: ktaro, SHKT report (Usage §5.2, Spec §1.1, §4.3) · 2026-10-16

Both navmeshes hold floor faces only (99.6-100 % of the area faces up

Evidence: static · Build: steam-678ccb46 · Fact ID: navmesh-contents

Both navmeshes hold floor faces only (99.6-100 % of the area faces up; not wall-climbing meshes); the _H mesh has 5-6 times more faces. The root holds one triple per section: NavMesh<n> (hkaiNavMesh), Graph<n> (hkaiDirectedGraphExplicitCost), Mediator<n> (hkaiQueryMediator) (IG_EDFROOM01: 15 sections, 45 variants). Replacing the _H mesh with the BIG one showed no clear difference in game (inconclusive).

Basis: the files; one inconclusive in-game test

EDF Knowledge Hub record — original wording — expand (2,483 characters)

The mission guide line (RouteGuide, vtable 17D64A0): the "line of arrows" is a strip the object draws itself, vertices at +0x270 (0x30 bytes each), texture phase = time x 4 - accumulated distance x 0.667, so the arrows seem to roll forward; RouteGuide_Arrow (GUIDEARROW.SGO, vtable 17D6520) is a separate single arrow made only by the SGO factory 5CAC20, never by DispRouteGuide*. The path comes from the Havok navmesh, not from RMPA routes or the route explorers: an ai::Character created by EBA20 on the global 20B2AB8 (navmesh 0, stored at +0x1B0); each frame 5C9D20 sets start = the player and end = +0x1D0 and requests a search with [char+0x68] |= 0x40; the corners come back at char+0x288, count char+0x2A0. Constructor 5C6C10(this, InitParam*) copies the InitParam to +0x120 (object offset = 0x120 + parameter offset); three callers: 1A7EDC (DispRouteGuideToArea[EX], factory 1B3760 -> 1B38A0; also the snapshot registration 5C5FE0, slot 0 of IRecordable_SceneObject_Registration<RouteGuide>, whose restore flag (parameter +0x28) makes the base constructor 5C6EC9 skip the copy, so a restored line is mode 0 with no target), mode +0x150 = 2, the area center +0x180; 1B4528 (DispRouteGuideToObject[EX], 1B4000 -> 1B4190), mode 1, the object +0x168 / control block +0x170, deleting itself when the object is gone (5C9DA0); 21F681, EDF5 BVM native 1200 (21F380; every number with low byte 0xB0 lands in this case, 213CBA), mode 0 (21F44C mov [rbp-0x49], r14d with r14 = 0). 5C9D20 handles only modes 1 (copies the object's position) and 2 (copies +0x180 to +0x1D0); in mode 0 the end stays the constructor's zero, so a guide line from an EDF5 BVM script points at the map origin (from the code; not seen in game; EDF5 itself did not do this; EDF5 missions M000, M001, M028, M057, M072_2 use native 1200). Fields: +0x190 the fade radius (the line fades when the player is that close, 5C9B60, 5C9A10; from the script), +0x194 drop corners nearer than this to the start (the player; 5C7BF6; default 15 m), +0x198 drop corners nearer than this to the last kept one (5C7CF6; 7 m), +0x19C written into the search settings in place of the default 10000 (a node cap, inferred; 1000), +0x1A0 true = polyline, false = curve (5C804F cmp byte [rcx+0x1A0], 0 / jne skips 5CA140; false, and no vanilla caller sets it), +0x2D8 the frame-to-frame smoothing factor (0.04 written at 5C6CEE; 0.08 when flag 0x20 of the global 20B2890 is set, 5C6D21), +0x2DC curve tension (1.0; 3.0 with that flag).

Basis: the author's static reading ("H"; the node cap "M"); 5C9D20..5C9E06 re-read with fn.py, matching (mode 2 copies +0x180, mode 1 locks the weak object, anything else returns)

Why route guidance can cross walls

Evidence: static · Build: steam-678ccb46 · Fact ID: route-guide-wall-cutting

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Guide-line drawing path
  2. Geometry assumptions
  3. Limits versus collision routing
EDF Knowledge Hub record — original wording — expand (1,409 characters)

Why the guide line cuts through walls: the drawing (5C9710 -> 5C7990; 5C9710 assumed to run each frame, from its vtable slot) copies the corners to +0x290 when the search returns more than 2, else after more than 10 frames uses the straight [player, target] (5C97C0); pass 1 drops corners within +0x194 of the first point (5C7B5B), pass 2 those within +0x198 of the previous (5C7C56); with more than 3 points each is blended by index, p[i] = old[i] + (p[i] - old[i]) x +0x2D8 (5C8BD8..5C8BF9); every point is raised 1 m; then 5CA140 draws a Hermite curve that starts and ends at the midpoints of neighboring segments and uses the corners only as tangents (or, with +0x1A0, a polyline). The navmesh path itself hugs the walls; the line goes wrong because (by weight) the curve cuts corners (the curve's vertex at a corner lies between the corner and the two midpoints, inside the wall; structure read, coefficient inferred), corners within 15 m of the player and closer than 7 m together are dropped, so the line runs straight to a farther corner across the nearest building edge, and the blend pairs points by index, so when the corner count changes it mixes unrelated corners for about 25 frames. A straight line after a failed search only crosses walls when no path exists. Mode is read at 5C9D32, mode 1's object at 5C9DFA. A fix through the line's own parameters: mods/edf6-all-forces.md (RouteGuidePath).

Basis: the author's static reading ("H") and offline tests; not run in game

Addresses (build-specific RVAs unless indicated): 5C9710, 5C7990, 5C97C0, 5C7B5B, 5C7C56, 5C8BD8, 5C8BF9, 5CA140, 5C9D32, 5C9DFA

Map object durability and damage

Evidence: static · Build: steam-678ccb46 · Fact ID: map-object-durability

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. MapObject_Base hit slot
  2. Damage parameter usage
  3. Destruction responses
EDF Knowledge Hub record — original wording — expand (1,474 characters)

Map-object durability: MapObject_Base's slot 13 1267A0 takes the damage (shared by MapObject_Model, AnimationModel, CrashModel, FixedCrashModel, Efs and Fmex; MapObject_Structure's slot 13 142E70 first handles the chunks of an already damaged structure, then tail-calls it); its rdx is laid out like the bullet's damage info (+0x50 damage, +0x60 flags, weapons.md#bullet-break-building-flags). At 1268C1 the durability obj+0x19C drops by the damage, clamped to [0, obj+0x198], only when flag 0x01 (break buildings) is set or the object's category [obj+0x1C8] is 2, 4, 5 or 6 (1 << type & 0x74); otherwise it stays; then 126EF0 decides the collapse. Both start at the definition's +0x18 (125DF3: obj+0x198 = obj+0x19C = [obj+0x1C8]+0x18). The definitions are map.mapb's 0x3C-byte object structs (file-formats.md#mapb-mapo-layout; +0x00 category, +0x18 float durability, matched by values, inferred): on IG_HEIGEN601 the 100 large rocks sk_rock601a_m.mosb are category 11 with durability 1 and sk_randomrock604a / 605a.mdx category 1 with 0 (decorative, inferred unbreakable); on NW_KOUSOUBLD601 the buildings (.mosb) are categories 1 / 3 / 5 / 6 / 8 / 11 with durabilities 0..1500 (often 10, 50, 400, 900, 1200, 1500) and trees (.trb) category 2. So rocks are structures like buildings and break only under the 0x01 flag, at once (durability 1). The area damage 542860 calls the single-target damage 543920 per target (that it reaches slot 13 for map objects was not traced).

Basis: the author's static reading ("H"; the definition block "M") and its read of Chunk02.cpk's maps; 1268C1..126914 re-read with fn.py

Addresses (build-specific RVAs unless indicated): 1267A0, 142E70, 1268C1, 126EF0, 125DF3, 542860, 543920

Stock MAD ground, navmesh HKT bridge and bounded path anomalies

Stock ground and model collision-body lookup

Static stock MAD/source-writer comparison. Map object bodies are identified by model-name prefix <model>.<node>, then transformed by the object's matrix; one composite body carrying all model triangles can collide equivalently to multiple separate pieces, while authored _hk meshes describe collision geometry. Ground is a compound of compressed meshes in the map MAD. Source uses IG_HEIGEN601 as donor for type tables, libraries and physics system; one stock ground tile mixes packed/shared vertices and has some triangleIsInterior bits set. The author's writer round-tripped 33 stock MADs byte-for-byte and used Havok 2020 donor structures; EDF4.1's Havok 2014 MAD tagfile cannot be made EDF6-compatible by merely altering a version marker. This is a file/loader observation, not a newly tested ground-collider writer.

EDF5-to-EDF6 navmesh HKT requires type-aware reconstruction

Static converter and native-file comparisons. EDF5 navmesh uses a 64-bit Havok SDKV20150100 tagfile; EDF6 a 32-bit SDKV20200100 one. Conversion decodes source graph/navmesh then reserializes with EDF6 types, not a header edit. Measured face/edge/vertex sizes are 16/20/16 bytes; graph node/edge 8 bytes, graph connection expands from 16 to 20. Source volume connections may be dropped when the target has none; EDF6 uses annotated streaming-set wrappers, hkaiQueryMediator in place of source hkaiNavMeshQueryMediator and 32-bit narrowed user data. Native TYPE family uses TST1/TNA1/FST1/TBDY/TPAD (89 types, 3,960 bytes), not permissively parsed older TPTR/TSTR/TNAM/FSTR/THSH. Converted navmesh geometry remains source-derived, not a native EDF6 rebake: for example CAVE501 had 21,778 EDF5 vertices versus 6,883 in EDF6 native. An erosionRadius=0 root property is not the NPC's collision radius.

Bounded bridge-through-convex census and one modified-game test

Offline census plus one contributor modified-game run. BarteY examined 18 EDF5 LOW/HIGH navmesh variants for a bridge penetrating a closed convex static collider by ≥0.05 m and ≥90% of its length, at a 1-m agent-height offset. Only three were flagged: DM019 HIGH (one 1.1142-m bridge penetrated a RoomB wall 1.1083 m, 99.47%, between section UIDs 2 and 3), IG_EDFROOM01 LOW (cube39) and IG_EDFROOM02 HIGH (cube8); the remaining 15 variants had no such crossing. Both EDFROOM anomalies were absent in their native-local rebakes. Removing the DM019 HIGH bridge (80 bytes: connection plus two AABBs) changed no observed spider targeting in an EDF5-derived mission run in EDF6: spiders still aimed/fired at allies behind the wall, although actors/web projectiles were stopped. Therefore this bridge is not demonstrated as the cause of targeting through the wall; vision/target selection remains unresolved, and this is not a retail EDF6 defect report.

Further static details: DM019 coarse graph had 84 LOW and 374 HIGH inter-cluster edges from face adjacency; mcpData is a byte pair (interpolant, clearance), faceOffsets are u32 and clearances u8. hkHalf16 in this format keeps the high two bytes of float32; treating it as a normal float produced false path-cost differences. These encodings are source-specific measured contracts, not a generalized AI line-of-sight rule.
