EDF 4.1 highest-LOD foliage failure family

UniversalMaterials & ShadersShadersEDF 4.1EDF 6
Source-backed research / case study · Runtime-observed issue family; exact asset root cause open

Symptom family

Two retained runtime observations point to the same distance-dependent surface:

  • earlier port builds showed black leaves on the highest palm/tree LOD;
  • later feedback reported leaves disappearing at close range and reappearing farther away, with scope/zoom not restoring them.

The visible symptom changed, but both failures are tied to the closest/highest-detail foliage LOD.

Strong suspects

Until the exact affected MDB/material family is identified, the highest-value candidates are:

  • alpha-test / alpha-clip state;
  • opacity texture semantic or channel interpretation;
  • material/shader variant used only by LOD0;
  • highest-LOD material binding;
  • LOD resource-path mismatch.

Distance dependence makes a generic “missing texture payload” explanation too weak by itself: a farther LOD can render while the closest LOD is wrong.

Diagnostic method

For the exact affected tree/palm family:

  1. identify the runtime MDB and material used by the failing close LOD;
  2. identify the next farther LOD that renders correctly;
  3. compare material/shader binding, alpha-test/clip state and opacity texture binding;
  4. compare texture format/alpha semantics only for the actual bound resources;
  5. verify LOD resource paths and model/material table indices;
  6. change only the first evidenced divergence and retest the distance transition.

Cross-project caution

Other EDF6 foliage research has proven that some Common_Clip-family assets legitimately use BC1 transparent mode. That is useful background, not proof that this EDF4.1 port issue is a BC1 problem.

Do not apply a global foliage shader or DDS conversion merely because another foliage asset used alpha clipping.

Status

This remains an open map-rendering/material issue family. The wiki records the stable diagnostic boundary so future work does not restart from “maybe the DDS is missing” or conflate a LOD0 binding bug with all foliage rendering.

Historical same-palm cross-generation discriminator

A recovered historical EDF5→EDF6 Desert case identified a concrete highest-LOD sk_ptree007_11m_shuro palm mismatch. The old leaf MDB used snd_Map_Simple_Clip, alpha_clip=0.5, a single albedo sampler and 44-byte vertices without tangent/binormal. A bad compatibility edit replaced only the shader name with snd_BRDF_Map_Simple_Clip while leaving all other material, sampler and vertex ABI fields unchanged. That mismatched shader/geometry contract, not a missing diffuse DDS, was the demonstrated problem for the historical black-leaf case.

The corresponding native EDF6 palm instead uses snd_BRDF_Map_Common_Clip, 60-byte tangent/binormal-bearing vertices, full albedo/normal/parameter samplers and FNM/FPR resources. The leaf diffuse texture itself matched the historical source, showing that identical diffuse pixels do not make two material ABIs equivalent.

One further historical sk_ptree007_11m_shuro.trb pair had a branch value [0.0,10.0] on the source side versus [0.0] on the native EDF6 side. With its generic schema migration, that one branch change reproduced the native TRB bytes, but a corresponding runtime experiment did not fix the previous black-leaf defect. Do not adopt a global [0,10]→[0] rewrite.

The current EDF4.1→EDF6 converter does not perform the old shader-name-only substitution, and the latest close-range disappearance report has not been tied to that same palm. Therefore this historical evidence narrows the differential diagnosis but does not explain or close the current issue. Source: R10_FOLIAGE_RECON_2026-11-15.md.
