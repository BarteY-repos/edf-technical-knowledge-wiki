EDF6 language controls: separate text and voice values and Chinese voice mapping

EDF 6Game technical referencesNative UI and settings
Technical reference · Static source and contributor checks, with build and open questions noted; no new R131 EDF runtime

In the examined EDF6 executable, language selection is not one interchangeable scalar. The engine has a text-language integer and a neighboring voice-language integer, exposed by separate accessors. This distinction is relevant to UI strings, subtitles, voice lookups and localization testing.

Native text selection

The original accessor at EDF.dll+0xE4000 reads the text-language value at the build-specific global +0x20B2B30, while +0xE4030 writes it. The observed enum order is:

Value Text language
0 Japanese (ja)
1 English (en)
2 Korean (kr)
3 Traditional Chinese (cn)
4 Simplified Chinese (sc)

The source relates these numbers to option-string ordering and distinct Chinese font resources. They are build-specific enum values, not a general locale identifier for all EDF releases.

Voice language is normalized separately

A nearby getter at +0xE4010 reads voice language from +0x20B2B34. Its setter at +0xE4070 maps incoming value 4 to 3, so the two Chinese text-language choices share one Chinese voice-language selection in the studied build. This behavior does not establish that every line in each language has a voiced cue, nor does it imply that text and spoken language must always be the same.

Other globals for input and UI sit in the same overall engine environment but have separate update paths. For example the keyboard-state buffer and the current input-mode byte are not the language controls; changing one is not evidence of a problem with the others.

Evidence: direct static read of native getters/setters for build steam-678ccb46, not a new in-game localization test. The precise voice table resolution for each cue belongs to the audio subsystem.
