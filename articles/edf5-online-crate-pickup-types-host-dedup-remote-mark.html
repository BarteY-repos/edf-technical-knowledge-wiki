EDF5 online pickups: message types 0/1/2, host decisions and duplicate suppression

EDF 5Game technical referencesNetworking / loot
Technical reference · Source static evidence with unverified behavior labelled; no new in-game R133 test

The EDF5 item-drop event handler recognizes three different message types. This resolves a common misunderstanding: a client does not simply delete everyone else's crate because its local physics capsule touched something. It reports the pickup, and the authority-side route distinguishes a request from a confirmed collection.

Type byte Meaning Recipient's effective action
0 Spawn Build a local crate copy with the shared serial/seed
1 Pickup request Authority checks it, resolves the requesting player and can issue the confirmation
2 Pickup confirmed Award the pickup to the appropriate player locally and mark the serial's crate collected

The local pickup reporter records serial, item category and player network ID (SoldierBase net ID at +0xF8 in the studied build). On the authority machine it can publish a type-2 confirmation; elsewhere it sends a request. The host resolves the player and calls the local award path before broadcasting the confirmation.

Why one crate cannot normally be counted twice

For weapon and armor categories the authority checks whether a requested serial is still an uncollected item. The first valid request marks it collected; a second request for the same serial is ignored. This is a source-established de-duplication rule, not a prediction based only on how pickup animations look.

When a client receives type 2, it resolves the player by network ID, applies the collection locally, finds its own crate copy by serial and sets a collected byte. The ordinary cleanup loop then deletes that copy. The source's note that it 'blinks out' describes this state change, not a physical teleport of one globally authoritative crate mesh.

Shared rewards and unresolved timing

A contributor confirmed from play that online weapon/armor pickups are shared rewards. That agrees with the code: each peer processes confirmed collection to its local inventory/reward counters. The original notes leave one issue unresolved—whether a type-1 request arriving after mission result synchronization can be lost to the tally. Do not present a deterministic late-pickup outcome without a controlled runtime trace.

Complete spawn-to-pickup state sequence (consolidated)

The spawn and collection messages form different stages, even though the same logical crate serial is reused throughout. The following describes the investigated EDF5 executable; message numbering does not prove a complete transport-layer wire schema.

Eligible enemy death
  └─ session authority check
      ├─ create local crate copy
      └─ send type 0 {seed, serial, position, two floats}
          └─ each receiver creates and simulates a local crate copy

Local soldier touches weapon/armor crate
  ├─ authority machine: validate serial -> confirm type 2
  └─ other machine: report type 1 {serial, category, player net ID}
                          └─ authority validates -> type 2
                                  ├─ award the appropriate player
                                  ├─ mark local serial collected
                                  └─ delete local crate copy during cleanup

A type-0 spawn message is not a kill-credit/attacker message. The seed/serial establish the crate's reproducible logical identity; its physical trajectory is simulated locally after spawn. Authority was inferred from the inspected native session gate, but the exact authority callback was not fully named in that study. This diagram is a reconstruction of native code flow, not a captured multiplayer packet log.
