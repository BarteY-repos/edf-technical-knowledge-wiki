What Engine RE directly establishes

Weapon-fire direction is not ordinary actor orientation

The recovered fire chain shows a dedicated per-shot transform path sourced from the weapon muzzle.

Key retained sites include:

sender 0x694910 -> per-shot entry+0x50 transform
receiver 0x692540 -> restores that transform before projectile creation
common spread builder 0x691560

Weapon+0xBC8 RNG state can also be transmitted/restored before spread on the relevant paths. The resulting projectile transform seeds the replicated Bullet state rather than merely inheriting Soldier world orientation.

Implementation consequence: fixing shot direction by repeatedly forcing actor orientation is the wrong abstraction when the divergence is in weapon/projectile creation state.

See Weapon fire and projectile direction authority.

NetworkBullet selector state has bounded semantics

The selector work distinguishes current spatial publication, contact-frame state and missile collision/contact records instead of treating the entire projectile as one opaque synchronized blob.

This is important because later class-internal behavior may depend on state that is not present in any selector payload. A correctly delivered selector cannot reconstruct a field that was never serialized.

See NetworkBullet selector contact and state boundaries.

Shipping reliability is above EOS

Normal NetworkBullet selector0/1/2 traffic uses Sandlot's retained reliability path even though physical delivery ultimately uses an EOS P2P UnreliableUnordered wrapper.

Recovered retained path:

mode0 -> 0x12C2DE0 -> retained-record builder 0x12D0AC0
DATA 0x1200
ACK  0x1300

RTTI identifies the retained machinery as eos::packet::Controller::ReliableBuffer, ReliableInfo and ReliableMgr.

Observed semantics include:

  • per-record sequence identity;
  • retained payload bytes;
  • sent-once state;
  • retry threshold and last-send QPC time;
  • initial retry threshold of 700 ms;
  • +1000 ms threshold growth after resend;
  • ReliableMgr+0x98 fault/retry condition once the threshold grows beyond 7000 ms;
  • receiver sequence deduplication;
  • ACK emission even for a duplicate DATA packet;
  • ACK retirement of the sender's matching pending record;
  • receiver dedupe aging on roughly a 40-second scale.

Therefore one transient physical EOS packet loss is not, by itself, sufficient to explain a permanently missing normal selector update while the Sandlot reliable session remains healthy.

See Sandlot RUDP and reconnect lifecycle.

Reliability cannot repair omitted projectile-internal state

R14-R17 leave concrete unsynchronized/internal-state candidates for classes such as:

  • FlameBullet02 motion scalars;
  • LightningBullet01 per-projectile RNG/path state;
  • SolidExpBullet01 detonation countdown.

The next binary frontier is therefore a minimal initial seed/state parity surface, not generic per-frame replication of every projectile field.

Runtime module boundary across EDF5 and EDF6

For cross-generation binary comparison, the useful main-runtime pair is:

EDF5.exe <-> EDF6/EDF.dll

EDF6's small EDF6.exe is not the equivalent home for most gameplay logic that lived in the EDF5 executable. This matters whenever a cross-version search appears to show that a function vanished.

See EDF5 vs EDF6 runtime binary architecture.

Navigation and AI: current documentation boundary

This bounded binary sample does not justify a broad statement such as "EDF6 navigation or AI is fully reverse-engineered." Evidence about those areas comes from:

  • exact native and reconstructed HKT/NVMD evidence;
  • mission API and route semantics;
  • source-format observations of map and mission resources;
  • EDF4.1→EDF6 gameplay-fidelity comparisons;
  • targeted binary/runtime observations where they exist.

No complete NavManager/AIManager type contract follows merely from an incomplete binary survey.

Useful entries:

  • NAV HKT/NVMD compatibility versus native rebake
  • EDF4.1 native geometry, MAPO binding and R1D NAV
  • Mission R37 control-flow/dataflow/API parity

Resource loading and renderer: current documentation boundary

Likewise, do not fabricate a single universal resource-loader or renderer object model from current Engine RE coverage.

The useful recovered contracts are distributed by format/path:

  • CPK/TOC/CRILAYLA/VFS resource lookup in the container documentation;
  • RAB/CMPL/MARC resource packaging in the archive documentation;
  • MDB material and vertex ABI in model/material articles;
  • FieldRender local-slot and projected-texture transport in the map articles;
  • build-specific native WinMM import and MissionMgr resource-load observations.

That is currently more actionable and better evidenced than an invented top-down class diagram.

Interpretation rules

  1. Verify canonical binary identity before applying exact Engine RE RVAs.
  2. Prefer semantic fingerprints/RTTI/xrefs when moving a finding to a different build.
  3. Keep projectile creation state separate from ordinary actor orientation.
  4. Keep physical EOS delivery separate from Sandlot's retained reliability semantics.
  5. Do not claim reliability repairs state absent from serialized payloads.
  6. Do not attribute map/NAV/Havok behaviour to this binary survey unless an exact native site in the surveyed build supports the claim.
  7. When a subsystem lacks a recovered runtime class model, document the exact format/API/runtime contract that is known instead of inventing class names or layouts.

Evidence boundary

Exact native/binary: current R17 database identities, RVAs/signatures for the canonical EDF6 EDF.dll, RTTI-backed reliable transport types and reconstructed fire/projectile paths.

Reconciled: format- and subsystem-specific evidence must retain its original origin, build and test scope.

Unresolved: a complete renderer/resource-loader/navigation/AI class map is not established by R17; the minimal seed/state parity repair for the remaining projectile classes is also still open.
