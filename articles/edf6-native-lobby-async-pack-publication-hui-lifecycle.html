EDF6 asynchronous room/mode publication and HUi lifetime

EDF 6Missions & ScriptingLobby and MissionPack identity
Technical reference · EDF6 build-specific static state-store and HUi callflow; modded-runtime conditions explicitly separated

An EDF6 online room can contain three different representations of a selected mission pack: the local UI/ModeList selection, the request sent through the room-mode change path, and the pack committed back to the central manager after a response. These do not necessarily update simultaneously.

This distinction was recovered while investigating custom pack selection in a studied EDF6 build. The native call and field observations below are distinct from the room restrictions created by third-party extensions: nothing here proves that stock EDF6 imposes the exact same modded-room family rules.

Build-specific state references

The binary examined in the retained analysis is the same EDF.dll documented in native ModeList and Package memory. The global manager pointer was referenced through EDF+0x20B2890; its active physical MissionPack field was at manager+0x14FD0.

An audited response callback near EDF+0x8ED980 contained this sequence (image-relative instruction addresses):

0x8ED9C3  mov r8, [manager_global]
0x8ED9CE  mov rdx, [r8+0x148]
0x8ED9D5  movsxd rcx, dword [rdx+0x8]
0x8ED9D9  mov edx, [rdx+rcx+0x74]
0x8ED9DD  mov [r8+0x14FD0], edx

The instructions use the selected row of a ModeList-like object to republish the active pack ID later in the request/response lifecycle. Consequently, observing the earlier menu/request value or filtering one earlier store is not sufficient proof of the final active MissionPack. The source study enumerated nine direct stores to the active pack field in that binary:

+0x708A06  +0x70C331  +0x791567
+0x8ED9DD  +0x90090A  +0x904B65
+0x91AA62  +0x925A32  +0x925CF7

The nine addresses are a direct-store census for that build; they should not be presented as nine separate online room transitions, and no undocumented meaning is assigned to an individual store here.

Distinguishing the stages

Stage Typical evidence to inspect What that evidence does not establish
Requested mode UI selection, request arguments, selected outer-mode index That the server/room has accepted the change
Selected ModeList row Row fields including mode type (+0x80) and MissionPack (+0x74) That the manager's active pack and the loaded mission resources match
Async response The response callback and currently selected row That an earlier local state filter remains authoritative
Committed pack Manager's +0x14FD0 after response processing That the resource pathname, mission count, package and save namespace are consistent
Resolved content Actual MISSIONLIST_MISSIONPACKNN... request, mission table and Package That remote peers selected identical content or that progression is safe

For an independently observed resource-request-first failure in MP06, see MissionPack identity and mission count. In that case the requested MISSIONLIST_MISSIONPACK06.OFFLINE.LIST.SGO pathname already identified the content while the manager's active pack field was still -1.

Native room/UI object lifetime is not room lifetime

A HUiRoom destructor-like wrapper was located around EDF+0x8F7510; it calls code around +0x8F5950, which installs the examined HUiRoom vtable (0x18180AC40) and operates on an object of size 0xCA0. These data support a class identity and destructor-like operation. They do not show that destroying or rebuilding a HUiRoom UI object always means an online room was closed. The UI may outlive or be recreated independently of a lobby session.

Other researched lifecycle seams were Room Exit near EDF+0x9049BE and RoomCreate_Join near +0x8E69A0. Their applicability as room-ownership reset points was established in a specific extension analysis; they should not be treated as general-purpose stock API functions without checking their native callsites.

UI visibility and room-publication presentation

In the same source study a native HUiRoom synchronous refresh function occupied EDF+0x902B30..0x90315D. Its public-visibility code lay near +0x902F8B; the researcher identified a direct caller at +0x8FFE67. This explains how a UI presentation event could lag behind an already-normalized visibility state in the tested extension. It does not establish a stock EDF6 warning-message policy for custom content.

A separate native room attribute named DLC was observed to carry the selected ModeList's MissionPack ID, not a generic Boolean 'user owns DLC' flag. That field is therefore useful for comparing published room state to local selection, while license/entitlement checks remain separate. See native MissionPack room identity.

Diagnostic reading order

When an offline mission appears but online room selection behaves differently, determine which value diverges before attributing the failure to packet transport:

  1. Source row — does the intended ModeList row exist and have the expected MissionPack and type?
  2. Request — is the selected mode/pack being requested, or is the previous value still being sent?
  3. Response commit — was a later callback allowed to republish a different active pack?
  4. Resource identity — does the subsequent LIST/CONFIG/Package selection use the same pack?
  5. Remote peer — has a real second participant joined and loaded the same mission, rather than merely observing that a host lobby can be created?

Evidence boundary: The native field addresses and assembly come from build-specific static analysis. The public/private room safeguards, warning timing and save-loss incidents used to discover these paths occurred in a modified runtime. They are not asserted to be native policies or bugs of unmodified EDF6. There is no new multiplayer capture or in-game validation in this wiki release.
