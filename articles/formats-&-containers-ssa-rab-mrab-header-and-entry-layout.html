RAB/MRAB SSA binary layout: header, entries and names

UniversalFormats & ContainersFile FormatsEDF 5EDF 6
Technical reference · Maintained source / exact sampled archives

RAB and MRAB archives are named-resource containers. In the EDF5/EDF6 samples we inspected, both use an SSA\0 header. Each entry has its own name, resource type and compressed or opaque payload; the entire archive does not represent one indivisible model or texture. This page describes the measured binary parsing contract, independently of how mods should combine their changes.

Container header

The inspected SSA header occupies 0x28 bytes and consists of ten little-endian 32-bit words. Positions below are relative to the beginning of the archive:

File offset Size Field Meaning
+0x00 4 magic ASCII SSA followed by NUL
+0x04 4 version Container version; observed value depends on input family
+0x08 4 content_start Start of entry payload area in the measured serializer
+0x0C 4 max_comp Maximum entry payload byte length
+0x10 4 max_dec Maximum declared decompressed entry length
+0x14 4 entry_count Number of entry records
+0x18 4 info_pos Absolute offset of entry-record array
+0x1C 4 names_pos Offset of name lookup table
+0x20 4 type_count Number of resource type strings
+0x24 4 type_table Offset of resource type reference table

The tested normalizing writer places info_pos at 0x28. A parser should read these offsets from the header, not hardcode every archive to the normalized writer's layout. Validate info_pos + entry_count × 0x20 <= file_length before reading the table.

One entry is 0x20 bytes

Entry record i starts at info_pos + i × 0x20:

Record offset Size Interpretation in the canonical parser
+0x00 s32 Relative offset from this entry's start to its UTF-16LE name
+0x04 u32 Stored payload byte size (csize)
+0x08 u32 Index into the archive's resource type strings
+0x0C u32 Entry-specific hd attribute
+0x10 u32 ft1 attribute
+0x14 u32 ft2 attribute
+0x18 u32 Absolute file offset to the entry payload (doff)
+0x1C u32 z / additional entry attribute

The two most important offset rules are not interchangeable:

entry_address = info_pos + i * 0x20
name_address  = entry_address + signed_name_relative_offset
payload       = file_bytes[absolute_doff : absolute_doff + csize]

A reader that mistakenly interprets name_rel as absolute will look up unrelated bytes. A reader must reject out-of-range names, unterminated UTF-16 strings and payload spans extending beyond the file.

Name lookup and type-string references

The measured lookup array at names_pos consists of 8-byte records: a 32-bit relative string offset and a 32-bit entry index. The string offset is relative to the lookup record's own address. The type table is an array of 32-bit signed relative offsets; each is likewise relative to its own table word and points to a UTF-16LE type name.

This means there are three distinct identities:

  1. Entry name: case-sensitive resource name, such as a DDS/MDB resource path.
  2. Type string: the semantic resource kind, resolved from the type table.
  3. Type index: a local index into that archive's type table, not a globally portable type identifier.

The exact named entry is the stable merge identity across inputs. A writer may rebuild the local type index when combining multiple archives, but should preserve baseline type-string order and append new types rather than assuming that two input index numbers have identical meanings.

Payload and CMPL boundaries

Each entry's blob is the stored payload. A CMPL blob exposes a big-endian 32-bit uncompressed size at blob offset +0x04. The outer SSA csize measures the stored blob, including its compression envelope. Other entries may contain opaque/uncompressed DDS or MDB bytes. The archive itself does not establish whether the MDB body is suitable for EDF6 rendering.

A lossless container round-trip must compare all entry metadata and payload bytes. In the studied controls, byte-identical parse/rebuild with stable ordering was demonstrated on IG_CAVE503.RAB (5 entries), IG_HEIGEN507.RAB (279) and IG_DESERT508.RAB (424). These are sample counts, not fixed limits.

What this permits — and what it does not

Because entry names and payload bytes are individually addressable, two mods that add different named textures can often be merged at the entry layer without byte-merging texture data. Different edits to the same named DDS/MDB are still a conflict unless another format-specific merger is proven. Mission image RABs may also be coupled to mission LIST/TXT ordering, so an archive-only successful merge does not establish correct menu images.

Evidence: the maintained converter/rab/rab_tool.py parser/writer and its byte-identical control archives; the independently documented RAB/MRAB entry-merge experiments. The header/entry descriptions are verified for this sampled SSA family and are not a claim that every EDF resource or every arbitrary SSA variation has the same semantics.

See RAB/MARC/CMPL overview, resource archive behavior and a measured CMPL corruption case.
