EDF5→EDF6 mission scalars: ten float/global cases and NPC health

ConversionMissions & ScriptingBVM and AngelScript numeric type semanticsEDF 5EDF 6
Technical reference · Source-derived; separates static evidence and the limited modded-runtime results

What fails: EDF5 source MISSION.BVM distinguishes floating-point scalars from integer counters. In an earlier EDF5→EDF6 MISSION.AC reconstruction, some global variables holding fractional values were declared int (or remained ambiguous Object during inference). A fractional 0.8 or 0.9 then became integer 0 before being passed to allied-unit, enemy or generator scale parameters. This is a gameplay-visible type error, not a mere formatting difference.

Source and evidence boundary

An independently regenerated 141/141-source-mission census compared the reconstructed EDF5 BVM semantics against the effective early compatibility corpus. Exactly 10 missions had global scalar declarations that needed float rather than int. The source reconstruction and static syntax checks passed; this was not a ten-mission in-game acceptance sweep. Later conversion builds may differ from this particular early baseline.

The inferred target types were:

  • Assignments containing only integer-valued numeric literals: int.
  • Numeric-only assignment sets containing at least one fractional (., f, exponent) literal: float.
  • Assignments with nonnumeric/object-like values: remain Object until a better semantic type is proven.

The prior heuristic incorrectly handled mixed branches such as 1 and 0.8f. A variable can be declared incorrectly even when its current path happens to use 1.0f; distinguish type drift from a proven visible symptom.

Why DM023 matters

In the source-derived DM023 branches, the level multiplier is a real value: about 1.0 at lower levels of difficulty, 0.9 on Hardest and 0.8 on Inferno. When a variable carrying that multiplier is forced into an int, the caller may receive 0 instead of a fractional scale. A character may then appear to have no normal health budget even though the spawn succeeds. The enemy-level 1.2 on Inferno was also mistyped in an earlier branch. A mission reaching gameplay is not proof of correct difficulty scaling.

Scripting implications

Treat float/int parity as end-to-end value flow: declaration → assignment under each difficulty → temporary locals → argument type at CreateFriend/CreateFriendSquad or generator construction. Count-based script audits will miss a numeric-value error when the same API calls are present on both sides. The later backward-layout switch audit is complementary: even correct floats cannot rescue a difficulty switch reconstructed into if(0 == 3) constant comparisons.

The ten-name declaration-only repair was validated as a minimal syntactic change in the historical compatibility corpus (10/10), but does not establish current retail EDF6 behavior or end-to-end mission parity. For the distinct switch/branch issue see difficulty-switch reconstruction.
