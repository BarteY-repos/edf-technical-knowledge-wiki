EDF6 world snapshots: serialized state versus online player identity

EDF 6Game technical referencesNetworking
Technical reference · Source-code/static interpretation with explicitly labelled contributor gameplay observations; no new game runtime

The examined EDF6 executable contains an in-memory world snapshot facility via xgs::snapshot. Its presence does not mean that ordinary online gameplay has a complete, safe save-and-resume of its multiplayer session. State restoration, peer identity, player ownership and lobby membership are different responsibilities.

Native build and restore wrappers

The static source investigation identified a snapshot creation routine (RVA 0x6B4820 in the surveyed build) that checks state/context, creates a write recorder and invokes a shared world-serialization root. A corresponding restore routine (RVA 0x6B48A0) checks for a retained snapshot, restores relevant renderer/world state and invokes a read recorder over the same root.

The fact that a wrapper exists proves serialization code is present. It does not prove that an arbitrary multiplayer match can be rolled back or migrated live to a new host. The source's context guard was not identified as a blanket prohibition of online snapshots; its precise state eligibility requires separate proof.

Known serialization boundaries

Component Relevant finding
SoldierBase::OnSnapshot Dispatches to the general HumanBase::OnSnapshot implementation in the examined build
Soldier local/remote role at +0x128 Not included in the inspected snapshot record
PlayerInfo Holds actor references; no retained PUID/network-user identity in the observed record
MissionMgr::OnSnapshot Includes a record named script rather than the complete active content package
Lobby/session / EOS users Not demonstrated as reconstructible from world snapshot contents

This explains the chief limitation: a restored actor is not automatically a correctly owned online player. The engine's normal joined-room handshake publishes the active pack and assigns player/member identities through other mechanisms. Those mechanisms are not replaced by merely restoring the snapshot bytes.

Do not confuse three systems

  • World snapshot — in-memory serialization of selected game/world state.
  • Mission sync — the roster/loadout/mission-start exchange among online peers.
  • Application-layer reliable packets (RUDP) — retention/retry/ACK of already serialized network records.

A snapshot alone does not transfer the reliable-manager sequence state; reliable transport alone does not restore missing user ownership; a correct lobby package selection does not imply every scene object was recreated.
