Mission RMPA: binary groups, waypoint IDs and serialization pitfalls

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Technical reference · Reconciled: source-owned writer + exact paired corpus

Scope: The EDF5 → EDF6 source-only mission RMPA profile established from paired mission resources and the retained rmpa_source_only.py writer. Mission RMPA is not the same format contract as map RMPA or the RMPA embedded in an MAE weather resource.

File and group layout

The older source-only writer emits a 0x30-byte initial header span, whereas the newer native-parser reconstruction identifies a 0x28-byte logical file header (signature/version and four section count/offset pairs). The extra 8 bytes of writer footprint are not proven native header fields. Principal fields are big-endian, unlike the little-endian NVMD family. The magic is 00 50 4D 52 (\0PMR) and the examined version is 1.

Four top-level group sections are referenced independently: routes, shapes, camera and spawn points. The audited writer places the first route type header at 0x30 and the first waypoint record at 0x50.

Record Measured footprint Function
File header 0x30 bytes Older writer's initial span; native logical header is 0x28
Group type header 0x20 bytes Older writer's group-type span; native route section 0x1C, other section 0x14
Waypoint 0x30 bytes Global ID, position, links, descriptor
Route group 0x18 bytes Membership and group-level references
Shape 0x24-byte header plus 0x40-byte payload; standard 0x10 metadata Older writer footprint; native shape payload is 0x38, a distinct record-level measure
Spawn point 0x34 bytes Global ID, two positions and name

Some small descriptors are stored little-endian even though primary records are big-endian. In the measured native profile, signed property-string offsets inside 8-byte property entries are little-endian and entry-relative. A route type-header string pointer is reported at +0x18; the +0x1C pointer cited in older notes belongs to an enumeration subheader, not that type header. These offsets are relative to their respective record bases. Do not treat the older 0x20 group writer, native 0x1C/0x14 sections and map-owned RMPA as interchangeable layouts.

Why route IDs change in a conversion

EDF5 route groups can number waypoints locally. The studied EDF6 profile uses one flattened global waypoint sequence. A local outgoing next reference must be translated by the containing route group's starting position.

For MISSION.RMPA specifically, the independently audited mission_rmpa_source_only.py builder flattens waypoint records across source route groups in file order and assigns waypoint.no = 0, 1, …, N−1. Each source waypoint.gid remains a separate, preserved identity, and route-local next indices are rebased to global waypoint indices by adding the route group's cumulative start offset. The 141-mission source/target audit confirms this global numbering, GID conservation, next-link rebasing and width conservation for 5,103/5,103 waypoints.

Do not import a MAPB_T2_count + 3 starting-index rule from a map-owned RMPA/placement writer into the mission-owned profile. The inspected mission_rmpa_source_only.py takes only the original MISSION.RMPA, without MAPB placement count input. Cross-file identifiers, MAPB placement IDs and native NAV semantics remain separate systems. If another tool uses MAPB-based identity construction, that is a distinct format or tool-specific contract requiring its own evidence.

Alignment and string addressing

In the inspected mission writer, per-waypoint next-link arrays are padded to 16-byte alignment when nonempty, and the route-group membership arrays also begin at 16-byte boundaries. The shape and spawn areas have independent 16-byte alignment rules. The shared UTF-16BE string table begins with the writer's two-byte zero anchor; an alleged eight-byte route-list prefix belongs to a different studied writer/packing context and is not a rule of this mission RMPA implementation.

String records are UTF-16BE in the examined source-only profile, with a two-byte zero prefix. Several references are record-relative or field-relative, not absolute file pointers. Treat the base of each offset as part of its individual record's specification.

The record-relative offset base is part of the field contract. For the native route type header, resolve its +0x18 string reference from that type header; do not substitute an enumeration subheader's +0x1C reference or an absolute file offset. Map-owned and MAE RMPA require separately proven record layouts.

Validation

  1. Check \0PMR and version, all four group ranges, and internal section counts.
  2. Confirm the route-local-to-global mapping for every outgoing waypoint link.
  3. Validate string pointer bases, mixed-endian descriptor fields and alignment.
  4. Resolve target IDs to the intended MAPB placements, shapes and scripts.
  5. Treat structural/byte tests and actual mission gameplay as separate evidence.

In the shipping141 source/target research corpus, 5,103 waypoints, 1,355 shapes, 3,387 spawn records and 6,665 literal mission-script-to-RMPA references were accounted for in the offline gate. They are observed test counts, not limits of the binary format.

Source/target proof boundary and one unusual metadata case (R94)

The full 141-mission source-only gate reports 5,103 waypoints, 1,355 shapes, 3,387 spawns and 6,665 AC-to-RMPA literal references, with zero missing generated RMPA names. A later portable source recovery matched the historical R1 output SHA for 141/141 mission candidates. This confirms a repeatable standalone format profile and source-reference closure, not gameplay-runtime acceptance.

The exact target-profile audit found 1,354/1,355 shapes with the standard Usage / 通常 metadata and a single reference-port exception in M061, where one camera-named shape omitted it. Source semantics did not supply a reliable generic discriminator, so the source-only writer uses the standard descriptor and leaves the exceptional port-specific tuning unresolved, not hardcoded for all shapes.
