Direct BVM → AC audit across all 141 missions: reachability, spawn pairing and value-flow boundaries

ConversionMissions & ScriptingScriptingEDF 5EDF 6
Source-backed research / case study · Reconciled

Evidence level: Reconciled static/source audit over all 141 original BVM missions and the reconstructed 1.0.6 AC corpus. This is not a 141/141 gameplay-runtime certification.

Why this audit matters

A mission port can look convincing if only aggregate API counts or generated AngelScript are compared. The R3 direct audit instead decompiled and inspected every original BVM and compared source-side event/spawn structure against the effective AC corpus.

The result is useful precisely because it separates what was actually demonstrated from what remained open.

Corpus coverage

  • original BVM decompilation: 141 / 141, zero decode failures;
  • effective AC corpus: 141 / 141;
  • independent comparison material included the 1.501 mod lineage and Sandlot exact44 subset;
  • source-event graph was built from BVM RegisterEvent and compared with AC internal_CreateEvent reachability.

Named spawn pairing

The direct audit found 3213 reachable source BVM named spawn sites.

  • 3209 paired to the same effective AC function family;
  • 4 used a different function family and required semantic interpretation rather than name equality.

Examples of legitimate transformations include transporter/dropboat source calls becoming neutral/transport-specific target helpers, or route-bearing source spawns becoming an area spawn followed by explicit .SetAiRoute(...).

Therefore API-name equality is not the migration invariant. Actor/resource identity, target behavior and subsequent control calls matter together.

Parameter audit: useful but deliberately incomplete

For 2353 paired sites, at least one simple literal operand could be compared safely between BVM and AC. No confirmed literal differences were found in that bounded subset.

This does not mean 2353 fully verified spawns. Another 860 sites lacked a safe literal comparison in this method, including:

  • 728 unmapped opcodes;
  • 43 non-trivial stack/value flows;
  • 71 sites without a simple same-function API pair;
  • 12 custom AC signatures;
  • 6 cases without a comparable literal.

Even within the 2353 compared sites, variable arguments, branch conditions, difficulty-dependent values and downstream engine effects remain outside the proof.

The M039 bug proves why value flow matters

The direct audit found a concrete gameplay-relevant defect in MissionPack03/M039 (displayed mission 89).

Source BVM difficulty branches use fractional ally level scales such as approximately 0.8, 0.85 and 0.9. The target AC had correct global float declarations, but two local temporaries in separate execution paths were declared as int before feeding CreateFriendSquad / CreateFriend calls.

The fractional value therefore truncated to zero through the local variable path. Nine allied-NPC calls were affected by the problematic level flow.

This bug survived an earlier “global scalar typing” audit because checking the declaration at the origin is insufficient. Type/value parity must be followed through intermediate locals and the call path.

The final 1.0.6 line changes the affected locals to float; exact-release runtime remains a separate qualification tier.

Important false alarms withdrawn by reachability/semantics

M059 / Func_4

The source function contains 12 dragons and is absent from the target AC, but the function has no entry from the reconstructed source RegisterEvent graph. This is not proven loss of an active wave.

M033 / Func_15

The source contains ten CreateEnemy2 calls, but the function is likewise not reachable from Main in the modeled registration graph. Raw call-count comparison alone would falsely classify it as missing gameplay.

M070 / M083 / M098 / DM015

Source CreateEnemy calls for transporters/dropboats were intentionally represented by target-specific neutral/transport semantics, with associated object/crew/control calls retained. Function-name mismatch is not by itself a regression.

M038 / M063 / M078

Source route-bearing spawns are lowered through an area/group helper plus explicit route assignment. Whether motion is perfectly engine-equivalent is a runtime/consumer question, but the route operation is not simply absent.

Open cases from this audit

The direct pass deliberately left unresolved cases rather than forcing parity claims:

  • DM001: one source edge and callback mapping required special compatibility interpretation; later DM001-specific runtime work is the stronger authority for that mission;
  • M065 / M067: the AC has more generated event edges because source logic was split across difficulty branches; path conditions/factors must be compared, not just event counts;
  • general float/int/value-range propagation, counters and generator tempo still require dataflow/CFG or runtime evidence;
  • RMPA, weather/MAE, movement/flight, transporters, physics and navigation remain separate engine/format gates.

What this audit does not prove

It is not a symbolic interpreter for both BVM and AngelScript. It does not prove:

  • all branches execute identically;
  • all variable values are equivalent;
  • every Factor/Action has identical runtime side effects;
  • navigation/physics/resource consumers behave identically;
  • 141/141 missions are gameplay-qualified.

Use the audit as a strong structural/value-flow evidence layer below exact runtime qualification.

Practical conversion rule

When reconciling BVM → AC, prefer this order:

  1. establish source reachability before treating a missing function/call as a bug;
  2. pair semantic actor/resource identity, not only API names;
  3. trace value types through intermediate locals, especially float/int and difficulty branches;
  4. compare event conditions and factors when generated edge counts differ;
  5. keep format/engine consumers (RMPA, MAE, movement, NAV, physics) in their own evidence lanes;
  6. promote to gameplay parity only with appropriate runtime evidence.

How the historical R1 byte-parity gate differs from this direct audit

An older, independent source-only pipeline generated historical R43-era MISSION.AC and R1 mission MISSION.RMPA from EDF5 BVM/RMPA for 141/141 shipping missions, then reproduced those historical outputs with a portable gate on 4 September 2026. Its 141/141 hash matches are exact against those retained historical candidate bytes, not against the later 1.0.6 effective runtime port analyzed in this article. They cannot be used to erase the M039 local-float regression, reachability differences, or other later semantic issues discussed above.

The portable result accepted one missing zero-byte checkpoint package file (mission_util/__init__.py), while remaining exact on 141 mission output pairs and four optional resource variants. It did not promote the old R44 transpiler to current authority. DM006_2 object specialization in that historical reproduction is superseded as a practical gameplay route by the separately tested six-call 3450-OFF compatibility decision. See source-only RMPA pipeline boundary and the 3450 compatibility waiver.

Historical 3,471-transaction audit: distinguish source sites from port-equivalent calls

An earlier R42 scan of the 141-mission EDF5 source extracted 3,471 source-side spawn/generator transactions across 19 BVM call IDs. The subsequent source-order matcher paired 3,465, reported zero ordering failures, and left six mismatches, all from source CreateEnemy call ID 2000 in the same DLC DM006_2/Main handler. In its target AC, those six source-expected literal constructors were inside a compatibility branch using customized armored-frog objects and receiver behavior. Therefore the old 6 missing finding was not proof that six enemy actors failed to appear in live EDF6 gameplay; it was a precise source-code-to-target-transaction matching failure of that candidate.
