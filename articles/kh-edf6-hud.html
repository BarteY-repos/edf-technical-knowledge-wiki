Armor gauge (HUiHudPowerGuage)

The armor gauge keeps armor current and max as floats (FevGrave writes them as SoldierBase+0x5f/+0x2f4

Evidence: static · Build: steam-678ccb46 · Fact ID: armor-gauge-text

The armor gauge keeps armor current and max as floats (FevGrave writes them as SoldierBase+0x5f/+0x2f4; +0x2F4 is max HP, combat.md#entity-fields-kc; +0x5f looks like a typo, current HP is +0x2F8). The bar fill is the cur/max ratio (827010); the text is (int)cur " / " (int)max, formatted by 767CF0 (call at 826AD7).

Basis: FevGrave's Ghidra notes in the patch header

Addresses (build-specific RVAs unless indicated): 827010, 767CF0, 826AD7

Attribution: FevGrave (ArmorDisplayCap), novae (ajane)'s EDF6 outside set · 2026-10-16

HUD text value clamped to 999999

Evidence: static · Build: steam-678ccb46 · Fact ID: armor-gauge-cap

The text is capped at 999999: mov eax,0xF423F at 826AA5 and four cmp/cmovg against the same eax (cur, max, and the stored copies [rbx+0xAE0] / [rbx+0xAE4] of the gauge object), so one imm32 at 826AA6 raises all four. More than 7 digits leave the string's small buffer (SSO 7) and may clip the text box.

Basis: the patch's anchor (unique) and FevGrave's notes

Addresses (build-specific RVAs unless indicated): 826AA5

Attribution: FevGrave (ArmorDisplayCap), novae (ajane)'s EDF6 outside set · 2026-10-16

Where the HUD draws and with what scale: HudPlayer_FollowerDurability's draw 8040E0 makes one call, 804300 (one follower's bar), whose r9 is 8040E0's rdx, the HUD draw context, passed on as rdx to the quad call; its fifth argument is the viewport (+8 width, +0xC height, ints) and rdx a view-projection of four vec4 rows (clip[k] = x vp[k] + y vp[4+k] + z vp[8+k] + vp[12+k]); screen x = W/2 + W/2 ndc.x, y = H/2 - H/2 ndc.y (origin top left), culled when w = 0, |ndc.x| or |ndc.y| > 1 or z outside [0, 1]. The vanilla follower bar is 2 m above the object's +0x90, half width 31 uiW / 1920, half height 3 uiH / 1080 (from 8044B1), where ui = [[2137090]+0x10], +0x20 width and +0x24 height (the game screen; design size 1920 x 1080); nameplate spacing (... + 16) uiW / 1920 (80532A); text scales the same way (0.65 (uiW / 1920, uiH / 1080) at 94E24F, (uiW / 1920, uiH / 1080) at 95CE60, into 113A3F0). Shared UI font glyph cache

Evidence: static · Build: steam-678ccb46 · Fact ID: glyph-cache

The glyph cache ([renderer+0x18]+0x98) is one for all text (menus, class names, the save screen, plugin HUDs): lookup 117B340 (from measure 1139767 / 1139901 and draw 113BEB2 / 113C07D / 113C877; a hit resets the age, 117B470); the key (117B250) = character | half(scale x) << 16 | half(scale y) << 32, so every distinct text size is a separate glyph set; a miss rasterizes with GetGlyphOutlineW (1174150) and allocates a cell in a texture page by row height (117B140; with all pages full it returns null and the character is not drawn); End (the tail of 113C5C0) calls the reclaim 117AFA0, which at most every 0.3 s of wall time (1765A18) ages every entry and frees those older than 2 (117A8B0); the allocator 11795E0 drops empty rows first. Default font descriptor (1137B70): four 1024 x 1024 pages (+0x20 / +0x24 = 0x400, +0x28 = 4; inferred). A HUD whose text size changes every frame (scaled by distance) rasterizes a new set each frame and churns the pages.

Basis: the author's static reading ("H"; the page defaults "M")

Vanilla glyph substitution problem

Evidence: static · Build: steam-678ccb46 · Fact ID: glyph-cache-race

The vanilla game shows a wrong character in place of another (one Japanese class name turning into another) or drops characters, with no mod installed; the glyph cache is not thread-safe: only the GDI rasterizing is locked (1180ED0 spins on the font object's +0x29F0, sleeping when taken; 1180FC0 unlocks), while the glyph map's inserts and deletes, cell allocation and freeing, the 0.3 s reclaim and the page's dirty mark (set at 11743B7, cleared after the upload at 11740E5) are not. Two threads in the cache (one marks a page dirty, the other uploads and clears it) leave a cell on the GPU with its previous glyph. The cache's four entries are lookup 117B340, glyph width 117B5E0 (inserts on a miss too), reclaim 117AFA0 and page upload 11740B0 (10 rel32 call sites in all); All Forces wraps all ten in one critical section. The author's fuzz of the game's own allocator (11795E0 / 117A8B0, 1.2 million random operations) found no overlap, so the race is the cause (inferred; never caught in game).

Basis: the author's static reading ("H" for the locking) and its allocator fuzz; the race itself "L"
