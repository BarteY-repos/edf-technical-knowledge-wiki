Havok MAD / SHKT collision contracts

Source-backed research / case study · Runtime

Evidence level: Exact binary/corpus evidence plus runtime-confirmed Desert MAD baseline. Private Havok material is research-only and must not be redistributed.

Cross-version conversion is structural

EDF5 collision data is based on older Havok representations; EDF6 uses Havok 2020-era hknp structures. SDK/version strings or header patches are not a conversion.

Implementation rule: Re-encode the target structures with independently derived layouts and validate conservation/invariants. Never copy EDF5 hkpMotion bytes into EDF6 hknpMotionProperties; the qualified EDF6 motion-properties record is 104 bytes.

Important measured layout rules

  • corrected hknp shape-type IDs include convex 0, cylinder 3, box 5, compressed mesh 8, compound 11;
  • detailed 52-byte compressed-mesh layouts identify +0x01 dispatch type = 3;
  • a tested carrier family has +0x04 = 14, but historical notes used conflicting member names for that byte. Preserve the measured byte rule without pretending the naming conflict is solved;
  • corrected hknpMaterialDescriptor flags serialize as uint32 0x0000ffff in the qualified path;
  • primitive records with c == d contribute one primitive key/triangle; c != d contributes two.
  • the tested canonical serializer types the bitfield array item at +0x20 as hkUint32;
  • convexRadius is profile/shape dependent: retained native/candidate evidence contains both 0.00 and 0.01, so neither value is universal.

Runtime-safe topology policy

For the accepted Desert compatibility profile:

  • preserve baseline split topology;
  • allow flat→split only when final quantized geometry disqualifies flat;
  • never synthesize split→flat in compatibility mode;
  • production triangleIsInterior is zero.

Accepted Desert gates

The source-only Desert R10C MAD is runtime accepted and byte-reproducible from clean source plus reconstructed schema. High-value gates include:

  • 11,873 / 11,873 FPI sections;
  • 1,100,848 unique primitive keys reachable exactly once;
  • zero missing/extra/duplicate/AABB violations;
  • 181 bodies;
  • 370 terrain meshes;
  • 2,045,747 terrain triangles;
  • 16,132 direct-mesh triangles.

Implementation rule: These are compatibility gates for this established profile, not universal counts for every MAD.

Physical DATA and primitive-index requirements

A structurally valid Havok type graph is not enough: the target physical DATA layout, free pool records and body sentinel values must also be valid. The examined hknpMotionProperties record is 104 bytes, with nonzero default data even in free slots, and some static/no-drag target bodies use mass=-1.0, not 0.0. In the accepted Desert mesh profile, firstPrimitiveIndex is a mesh-global primitive prefix count and an independent audit found 11,873 correctly indexed sections.

See Havok wire layout and primitive indexing for the measured structure, alignment, free-list and triangleIsInterior rules. These remain shape/profile specific; a standalone offline wire PASS is not proof of correct in-game collision behavior.

SHKT and object-specific collision

SHKT/HKX-style object collision must remain tied to the owning gameplay object and its filter/material/query semantics. EDF4.1 Earth Eater and Shield Hector work demonstrates why a visually correct target model cannot substitute for source collision lifecycle/body identity.

Provenance boundary

Implementation rule: Private Havok SDK material may inform research, but distributable tools/artifacts must use independently written serializers and must not reproduce proprietary SDK source or distinctive implementation fragments.

Distinguish a measured byte from its disputed member name

The 52-byte hknpCompressedMeshShape member layout resolves an old report-labeling mistake: +0x01 is dispatchType (3 in the measured examples); +0x04 is numShapeKeyBits (14 in one audited working profile). An August 21 crash-forensics shorthand called the latter value dispatchType=14, but the more detailed August 19 member table distinguishes them. Do not rewrite +0x01 to 14 and do not force every numShapeKeyBits value to 14. This closes the historical member-label dispute, not the general primitive-key derivation rule.

A separate historical converter mapped EDF5 motion types {5:0, 2:2, 3:2}. It silently mapped every unrecognized value to static 0, which is a fidelity risk. The reader-facing rule is to reject unknown source motion types until their target behavior is measured rather than treating this limited mapping as universal.

Object-level SHKT checks beyond parsed tagfile structure

The retained R9 object validator separates body-name links, material/motion-property indices, joint pivots, convex/compound derived bounds, shape mass properties and collisionFilterInfo bit ranges. See SHKT object-graph validation. Physically moved MDB bones can also require refitting SHKT proxies, joint anchors, reference poses and CAS absolute clips. These are source-backed structural invariants, not universal EDF6 runtime PASS.

R12 key-width correction versus independent gate geometry

One standalone MAD audit isolates a subtle collision-serializer defect: using maxShapeKey.bit_length() can make a legitimate maximum key collide with the all-ones invalid sentinel. For the audited profile, the fixed expression is (maxShapeKey + 1).bit_length(). The source audit records 61 corrected meshes and 122 changed mirrored fields, with 61→0 sentinel collisions. See compressed-mesh shape-key validation for examples and the limited native-corpus scope.

The same source tree includes an independent geometry-derived fixture, sk_so_gate501.mdb: inspected frame mesh 1 and panel mesh 0, a dominant panel plane at z=0.373779296875, and a source opening between x=0.361083984375 and x=4.5234375 (width 4.162353515625 source-coordinate units). These values describe that one sampled native MDB, not a generic door collision size, coordinate transform or MAD writer rule.

The recorded 86,838,152-byte combined candidate retained the complete appended gate-tail bytes, changed exactly the 122 R11→R12 key-width bytes relative to the gate-only candidate and reported zero overlapping gate-patch offsets. This establishes orthogonality of two audited byte-level edits, not successful runtime collision/AI behavior or support for arbitrary placement/animation of this gate. No such native runtime test was rerun in this wiki pass.

EDF4.1 original MAD: mesh and compact shapes can satisfy the same MAPO resource reference

An original EDF4.1 MAPO record has separate references for a visual object and a collision .hkt resource. A named collision resource is not guaranteed to be represented by a static triangle mesh in the associated MAD. In four sampled original maps, three names appeared as five distinct original fixed hkp rigid bodies represented with hkpBoxShape or hkpListShape (containing a box), rather than the MOPP/mesh family read by the earlier census. The same five source bodies explain 145 MAPO collision-resource occurrences (70 + 38 + 7 + 12 + 18).

The source normalizer for these bodies produced one primitive and 12 candidate hull triangles each; this is a representation for inspection, not a claim that every face is independently stored in MAD or that a second MOPP collider must be created. The five bodies belong to the original Havok 2014 hkp representation. Neither their convex radius nor body mode can be turned into an EDF6 hknp clearance radius or an hkai traversability rule without separate evidence.

Important correction: “145 MAPO HKT resources missing from MAD” was an overstatement caused by the mesh-only census. Source analysis confirms the compact bodies exist. This finding does not prove their activation by the EDF4.1 loader, the ported EDF6 actor matrix or collision filter parity. See the exact resource/map-name crosswalk.
