Havok MAD wire layout and primitive indexing

UniversalMaps & NavigationCollision & PhysicsEDF 5EDF 6
Technical reference · Exact native / Reconciled with scoped runtime evidence

At a glance

What this page answers: EDF6 MAD/Havok data must satisfy both logical object relationships and physical serialized offsets, alignment and primitive-key rules.

How to read it: Read TYPE/ITEM/DATA relationships alongside the hknp shape/motion flags; class names and triangle counts alone do not validate a body.

Evidence boundary: Static source comparisons are not an in-game contact test. In particular, triangleIsInterior and material response remain separate questions.

A collision archive can carry geometrically correct meshes and still be rejected by EDF6 because its serialized Havok object graph is physically inconsistent. The original EDF5 representation and the target EDF6/Havok-2020 hknp representation differ in shape classes, data alignment, pool records and per-body flags. The following rules are derived from paired native objects and independent wire audits, not from copying an SDK serializer.

Semantic structure versus physical DATA layout

The Havok-2020-style serialization includes a TYPE description, an ITEM graph and physical DATA. It is not enough for a deserialized graph to report the expected class and mesh counts; byte offsets must also satisfy the target's physical alignment and reference semantics.

A known source-only Desert conversion preserved collision content but had 36 physical DATA alignment violations. These were chiefly SIMD/hkVector4 fields represented by zero-local-size aliases that inherited their actual size/alignment from a parent type. A serializer that blindly treats the alias as physically zero-sized can place subsequent DATA at invalid addresses. Independently audited native EDF6 controls from CAVE503, HEIGEN507 and NW_EUROPE01 had zero such alignment violations.

Rule: resolve physical alignment through the reflected parent type chain. A stronger requested alignment may be applied, but must not override a stronger inherited requirement with a weaker one. The maintained experimental writer also requires at least 16-byte object alignment for pointer/object allocations in its qualified path; this is a writer contract, not a universal theorem for all Havok file kinds.

hknpMotionProperties and free pool slots

The compared EDF6 target record for hknpMotionProperties is 104 bytes. A free slot in the target's thread-safe pool is not 104 zero bytes. The independent paired-file audit established the following construction for the examined free-slot class:

  • Start from the native target's deterministic default 104-byte motion-properties record.
  • Overwrite the first dword with the next free-list index.
  • Write the measured free/deactivation marker byte as 0xFF.
  • The pool-head serial is (numAllocated - 1) & 0xFF, producing 0xFF for an empty pool.

An early Desert candidate incorrectly nearly zero-filled 14 free records. That was a physical ABI defect even though the corresponding slots were not active bodies.

Static body mass is not universally zero

For the measured static/no-drag hknpBodyCinfo class, paired EDF6 source uses:

Field Value in this particular class
motionType STATIC
dragProperties null
motionPropertiesId 0xFFFF
massDistribution null
mass -1.0 sentinel

In a source-only Desert candidate 137 such records had mistakenly been written with mass=0.0. They needed the target-class sentinel. Do not convert all static bodies to mass=-1.0: native static bodies with drag properties form a separate class. This is why matching by relevant fields is preferable to guessing one global default.

Primitive keys, triangles and mesh-section indexing

In the examined compressed-mesh primitive representation, c == d means one triangle/primitive key; c != d represents a quad/two primitive keys. Mesh-section metadata includes a firstPrimitiveIndex whose meaning is a mesh-global prefix sum of primitives in earlier sections, not a constant or local reset for every section. The examined triangleIsInterior representation is keyed by sparse shape-key space: the required bitfield span follows maxShapeKey + 1, not simply the number of source triangles.

The accepted Desert profile was checked over 11,873 sections in 387 section arrays, with zero firstPrimitiveIndex mismatches in the independent structural audit. The source-only conservative approach should preserve the section boundaries, ordering and primitive counts. Passing this audit does not by itself certify collision gameplay or correct raycasts.

The triangleIsInterior bitfield is a separate behavioral question

This bitfield describes internal versus exposed triangle semantics. Its available geometry heuristics include adjacency, exposed boundaries, polygon flatness and local convexity. However, the runtime comparison did not establish a universal interior-bit classifier. Changing both mesh topology and interior bits led to failures, and a zero-interior control with the wrong bidirectional flat/split topology also crashed. Therefore, interior bits alone were not the proven cause. The stable profile preserved source-backed topology and used zero interior bits.

Consequently, the accepted Desert compatibility rule uses the zero triangleIsInterior policy and permits geometry-justified flat→split transitions but not a blind split→flat rewrite. The research classifier and higher-fidelity inference remain separate from the runtime-qualified baseline; no generic exact rule for every shape is established. Native CAVE/HEIGEN/EUROPE data contains large numbers of nonzero interior bits; the Desert zero policy is therefore a known compatibility compromise, not a universal native equivalent. See native bit-count and edge-adjacency evidence. Do not promote an offline count/byte match into proof of collision parity.

Validation checklist

A robust writer/validator should independently inspect:

  1. TYPE-parent-derived physical alignment and DATA ranges (including zero-local-size aliases).
  2. ITEM and pointer/reference kinds, overlapping spans and root graph reachability.
  3. Motion-property free-list links, default payloads and pool-head serials.
  4. Body class invariants, including the scoped mass sentinel.
  5. Primitive-key counts and mesh-global firstPrimitiveIndex for all sections.
  6. Triangle interior bits separately from primitive ordering and geometry conservation.
  7. In-game collision, raycasts, AI traversability and destructible behavior when claiming runtime parity.

Evidence levels: paired native file/independent wire audit for alignment/pool/mass; source-only and runtime-profile audits for the Desert mesh/index policy. The investigated early wire-fixed source candidate itself was not runtime-tested at the time of its report. For higher-level context see MAD/SHKT collision contracts and collision versus navigation.

Decoder-side section-key bounds matter independently of serialization

The measured hkcdStaticMeshTree::Section record is 0x60 bytes with firstPackedVertexIndex at +0x48, firstSharedVertexIndex at +0x4C and firstPrimitiveIndex at +0x50. In one exact-build crash a sentinel compressed-mesh key 0xFFFFFFFF became a section index 0xFFFFFF; indexing the section array with that value caused the engine's out-of-bounds read. The invalid inactive-SIMD-lane defect in a source-built candidate was separately real, but the exact causal path from those lanes to the sentinel remained unproven.

For the complete field table and the distinction between shape-type values, dispatch-type values and motion-type mapping, see compressed-mesh shape keys and section records.

Material response and evidence classification

The old materials audit requested fixtures in which two materials share friction and restitution but differ in response/trigger type. This is a necessary test design, not evidence that friction and restitution fully identify a target material. The corresponding target trigger/flag bytes and half-float conversion (including out-of-range values) must be checked against the exact native profile before merging material identities.

Similarly, a native EDF6 serializer round-trip demonstrates that a target file can be decoded and re-emitted under one schema. It does not establish EDF5→EDF6 conversion parity, nor does an earlier 16.9 MB experimental MAD candidate supersede the later independently measured source-only Desert/R10C acceptance profile. Treat body counts, source geometry and final compressed-mesh topology as separate gates. The historical 16,132-triangle direct-mesh view is only one part of the complete Desert terrain collision census.

Width computation is not the sparse interior-bitfield span

For the bounded MAD R12 compressed-mesh writer, numShapeKeyBits = (maxShapeKey + 1).bit_length() reserves the all-ones invalid-key pattern. A previous max-key-only width created 61 conflicts; the source audit repaired 122 mirrored fields and reduced the collisions to zero. This field must not be conflated with the triangleIsInterior bitfield length, which also depends on sparse encoded key space but is a distinct representation. See shape-key sentinel and R12 width evidence.
