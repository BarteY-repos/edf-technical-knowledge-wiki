EDF 4.1 — Globals (community source notes)

EDF 4.1Community Knowledge HubNative UI & Input
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Who builds them

3442B0 calls 341EC0, the builder of every game singleton

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-globals-builder

3442B0 calls 341EC0, the builder of every game singleton. It first calls 5647F0 (at 3422DA), which builds the engine (xgs) systems, then for each global: calls the old object's virtual destructor (call [rax]), stores 0, allocates through the import _aligned_malloc [918698] (MSVCR120; size in ecx, alignment 0x10 in edx), calls the constructor, stores rax. The teardown functions store 0 into the same globals: 342F30 for the game singletons, 564BAA for the engine systems.

Basis: fn.py of 341EC0 (342030..342D74) and 5647F0 (5649E9..564B30), --xref 341EC0 and --xref 5647F0 (one caller each)

Addresses (build-specific RVAs unless indicated): 3442B0, 341EC0, 5647F0, 3422DA, 918698, 342F30, 564BAA

Attribution: novae (ajane), KH chat 157 (autorun) · 2026-11-13

Engine malloc and free function pointers

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-globals-low-block

Below the block, CC71D0 (2007 code operands) and CC71D8 (570) are the game's own free and malloc pointers, copied once by 85DED0 from the MSVCR120 imports free [918948] and malloc [918950]; the game calls through them (call [CC71D0]), so a hook there sees every such free or allocation. They are not object pointers. CC7020 (399 operands, written in 548CB0) and CC7040 (written in 540E80) are set while 5647F0 builds the engine; their builders store no RTTI vtable, so their classes are not known.

Basis: kh157_globals.py edf41 CC7000 CC8400; fn.py of 85DED0; the import names by kh157_iat.py; the role of CC7020 / CC7040 not read

Addresses (build-specific RVAs unless indicated): CC71D0, CC71D8, 85DED0, 918948, 918950, CC7020, 548CB0, CC7040, 540E80, 5647F0

EDF 4.1's save files: the folder string \My Games\EDF4.1\SAVE_DATA\ (A266F0, used in 3E9CB0; A261E4 holds a longer copy used in 3E9350; the base folder comes from SHGetFolderPathW, which folder not read), a saveslot%02d (A270F8) folder per slot, and the names SYSTEM.CFG (with the folder name SYSTEM, A2536C, in place of a slot), COMMON.CFG, TROPHY.DAT, SYSTEMWIN32.CFG (9BE1F8 / 9BE230, in DD5A0 / DD2A0), the mode file %ls_M%02d.MST (9BE178) and MAIN.GST.

Mode configuration file name construction

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-save-file-names

EDF 4.1's mode file name is built by the config loader DC5D0 (DC9EF) from %ls_M%02d.MST with config.sgo's PackageName (9BE198; "DEFP" in the shipped config) and the mode's ModeList row number, into the wide string GameDataMgr+0xD8, so the first mode's file is DEFP_M00.MST as in EDF5; MAIN.GST is the mode's ModeList item 4, read from the mode node [GameDataMgr+0xC0] at 3ED6EA.

Basis: fn.py of DC990..DCA40 and 3ED6DF..3ED740; peek_sgo.py edf41 defaultpackage/config.sgo (PackageName "DEFP", ModeList row 0 item 4 "MAIN.GST")

Addresses (build-specific RVAs unless indicated): DC5D0, DC9EF, 9BE198, 3ED6EA

Attribution: novae (ajane), KH chat 159 (autorun) · 2026-11-13

GameDataMgr save block layout

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-save-blocks

Each EDF 4.1 save file is one block of the GameDataMgr [CC84A0] (0xA858 bytes), the blocks back to back: +0x158 0xC bytes SYSTEM.CFG (save at 3EC922, load at 3ECC36); +0x164 0xD7C COMMON.CFG (save worker 3EE2E0, load 3EE560; wrappers 3ECE50, 3ECF90, 3ED1E0); +0xEE0 0x1710 the mode file DEFP_M<nn>.MST (save 3ED310 -> 3EE7E0, load 3ED4C0 -> 3EEA60); +0x25F0 0x4060 MAIN.GST (save 3ED670 -> 3EECE0, load 3ED820 -> 3EEF60); +0x6650 the trophy store, which CFBE0 packs into the 0x3E8 bytes of TROPHY.DAT (save 3ED9D0 -> 3EF1E0; loads 3EDB10, 3EDE70).

Basis: fn.py of the save cluster 3EC0D0..3EF500 (add rcx, <offset> before each worker; the size in r9d inside each worker, or the job's +0x90)

Addresses (build-specific RVAs unless indicated): CC84A0, 3EC922, 3ECC36, 3EE2E0, 3EE560, 3ECE50, 3ECF90, 3ED1E0, 3ED310, 3EE7E0, 3ED4C0, 3EEA60, 3ED670, 3EECE0, 3ED820, 3EEF60, CFBE0, 3ED9D0, 3EF1E0, 3EDB10, 3EDE70

EDF4.1 save block boundaries and lengths

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-save-blocks-fields

EDF 4.1's save blocks end where the next begins (0x164 + 0xD7C = 0xEE0, 0xEE0 + 0x1710 = 0x25F0, 0x25F0 + 0x4060 = 0x6650). Fields other lines read fall inside: the clear bytes +0xEE8 + class*0x200 + mission in the mode file (missions.md#mission-clear-bits), the class and armor boxes +0x2618 / +0x26BC in MAIN.GST (file-formats.md#edf41-soldierinit-armor-applied); difficulty +0x44 and the list row +0x40 lie below the first block (whether a block keeps a copy not read).

Basis: the offsets of #edf41-save-blocks against the cited lines

Addresses (build-specific RVAs unless indicated): CC84A0

Attribution: novae (ajane), KH chat 159 (autorun) · 2026-11-13

Save and load job classes

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-save-job-crypto

EDF 4.1 saves and loads as jobs: 3EB820 builds a JobSaveDataSave (vtable AA85A8, callback 3EBEF0), 3EB260 a JobSaveDataLoad (AA8590, callback 3EB7F0); JobSaveDataDeleteDirectory and JobSaveData are the other classes. The save run 3E9DE0 opens the file with CreateFileW ([9180F8]), joins the job's buffer list (16-byte {pointer, length} entries), encrypts (#edf41-save-crypto), writes with WriteFile ([9180F0]) and logs SaveComplete:%s %s write_size:%d (A26758).

Basis: fn.py of 3E9DE0, 3EB820, 3EB260; RTTI names by kh151_vtname.py; imports by kh157_iat.py

Addresses (build-specific RVAs unless indicated): 3EB820, AA85A8, 3EBEF0, 3EB260, AA8590, 3EB7F0, 3E9DE0, 9180F8, 9180F0, A26758

Attribution: novae (ajane), KH chat 159 (autorun) · 2026-11-13

AES CTR save encryption implementation

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-save-crypto

EDF 4.1's save encryption: the save run builds two Crypto++ AES (Rijndael encryption) CTR-mode ciphers (D4F90, vtable A90C88), derives their key material with D5360(out, "edf4.1_save" A260C8, "edf4.1" A909C0) (MD5, CryptoPP::Weak1::MD5 vtable A91040 in D5870) and encrypts with 3EAF50 into a StringSink. Not read: which string becomes the key and which the counter, and the file header (the string Data CRC:%x,Header CRC:%x, A26858, no direct code reference found, suggests a checksummed one).

Basis: fn.py of 3EA0B2..3EA0E7, 3EAF50, D4F90, D5360, D5870; RTTI names by kh151_vtname.py

Addresses (build-specific RVAs unless indicated): D4F90, A90C88, D5360, A260C8, A909C0, A91040, D5870, 3EAF50, A26858

Attribution: novae (ajane), KH chat 159 (autorun) · 2026-11-13
