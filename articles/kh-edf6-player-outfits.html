EDF Knowledge Hub record — original wording — expand (2,808 characters)

Outfits (the soldier "appearance"): the save keeps one per local player, GS+0x6E94 + player*0x3E60, -1..3 (-1 = match the mission; a new save writes -1, DEDA0 at DEDD8); E34E0(GS+0x130, class, outfit) = CONFIG.SGO SoldierInit[class][2][outfit] (the battle model) and E3420 = SoldierInit[class][5][1][outfit] (the menu model) do no bounds check, so a value of 4 reads past the table. Colors are per player, class and outfit: GS + 0x6FB0 + player*0x3E60 + (outfit + class*4)*0x188, the main color's 12 swatches as float4 (+0x00..+0xBF) with the selected index +0xC0, the second color the same at +0xC4 / +0x184; read by the battle build (591965..5919C2: ((D8700 outfit + class4)2 + channel)0xC4), the HQ / room 3D view (93B320), the color screens (881060, 87D790) and the room member record (78E9A0, taking the class's four outfits' selected colors at 78EC70..78ECB4 from +0x6EEC and +0x6FB0). Changing outfits unlocks with byte GS+0x300 (in the SYSTEM block, mgr+0x2E8..0x310, SYSTEM.CFG, shared by every mode): the soldier screen's init 8A8CE0 copies it to screen +0x7A4 (8A9B15..8A9B23; 0 selects controls help without the outfit key, 8A9B31) and the popup is built only when it is set (8AB59C cmp byte [rdi+0x7A4],0; je 8ABD44); the mission result 70D879 sets it at 70D933 when it was 0 and DF990(GS+0x57A4) is true (the current mission list's last row cleared on any difficulty by any class); 92ECF and AEF02 are debug "clear all"; the model build ignores it (D8700 / D8730 take the mission table's sixth column, E10F0, only for an outfit < 0). Where the battle model path is taken: only at 5A3FFC in 5A3F90(desc, ...) (E34E0(tables, desc+8 class, desc+0xC outfit)), where desc+0 == -1 marks the soldier remote (5A4087..5A40B5: +0x128 bit 0 remote, bit 1 local); online 591130 fills desc with 595960 (at 591219; desc+0 = -1 for a remote member, 595AE2, the member's +0x10 bit 1 via 12AC420) and builds at 591234; offline 591410 uses 595C80 (desc+0 = the local slot, 595CBD) and builds at 59145B; the offline preload 59DE50 calls D8730(GS, player, class) at 59DE91 (tail jump to E34E0) and the online preload 59DC90(member) calls E34E0 at 59DD27 (called from 1B8E98 / 225FAC); a session member's +0x48 is its in-mission player index (59DCD9 / 5959DD read the record `GS+0x14C78 + index0xD4; EDF6Coop's [Mission] Extendrewrites thecmp 4; jccat5959E1and59DCEA). Menu models: of E3420's callers 93B130(in93B0A0) and 93B24C(in93B210) are dead code (referenced only by .pdata), the live ones 93B426/93BD03sit in the 3D view's OnMessage93B320 (UiHQ_3DModelView, vtable 180FA60slot 3; the view's player at+0x2AC; views exist only for local players, GS+0x14FF4of them), the view constructor938760calls93B320directly at9393D3, and the mission select sends message 3 to "match the mission" players (8A6246..8A6272`).

Basis: the author's static reading ("H": every one of the 13 accesses to 0x6E94 scanned)

  1. UiHQ_3DModelView class
  2. Model rendering job

EDF Knowledge Hub record — original wording — expand (2,128 characters)

The HQ / room 3D soldier view (UiHQ_3DModelView, vtable 180FA60, with HUiHQ3DModel; one per local player, the first at +0x2AC == 0): slot 1 is its per-frame update, slot 3 OnMessage 93B320 (cases 3, 5, 6, 8, 9), slot 5 its destructor; its Async view+0xD0 is built once by the constructor (which sends the first message 3 itself). Model builds run as two std::function jobs, message 3's lambda_1 (180FDB0) and message 6's lambda_3 (180FE20), whose slot 2 _Do_call (9424A0 / 942590) call 93F910(Async+0x28, this+8) and set Async+0x9C = 1 (93F910's only other referrer, 93FFF0, is itself unreferenced); the job carries a copy of the soldier description: +0x20 / +0x4C class number (Ranger 0, Wing Diver 1, Fencer 3), +0x24 / +0x34 the two colors, +0x44 the outfit, +0x48 the weapon count (up to 6), +0x50, +0x54 the weapon table rows (a row by weapon name: E1BA0; a Fencer's list is [hShield01, main], CONFIG's Weapon_Slot1L coming first, the left-hand shield); the menu SGO path is written with the game's wstring::assign 3D450. Message 3 rebuilds the model, 5 recolors one channel (when +0x180 == the class and +0x178 == the outfit), 8 locks out the room's message 6 and 9 unlocks; 8BDE80 broadcasts message 3 to every UI object (through 119D1B0), and a broadcast 8 / 9 does not check the player number (a split-screen second view takes it too); the payload's outfit comes from DE470, which returns an outfit >= 0 unchanged. +0x3EC = 0 shows the model; the camera's four points are +0x2C0 / +0x2D0 / +0x2E0 / +0x2F0, the turn and zoom from input +0x2A4 / +0x308; the player's own look is rebuilt from GS +0x6E90 + player x 0x3E60 and D8700(GS, player); 93C21A is the one comparison of the outfit found. The renderer 93C370 reads change_color[i]: a string first item recolors only the material of that name (110D570), anything else every material. Menu models: the 10 Ranger templates (with _LEADER) all use n601_common_ranger.mrab / .mdb (two colorable materials, body and head), the 10 Wing Divers p606, the 8 Fencers p607, matching the stock menu SGOs (the Ranger's menu SGO is P505's; CAS app:/MenuObject/EDF6ArmySoldier.cas).

Basis: the author's static reading and its offline checks against EDF.dll and Root.cpk (the jump-table cases, the two job vtables, the GS global)

EDF Knowledge Hub record — original wording — expand (2,695 characters)

The 3D view's messages and load chain, in addition: HUiHQ3DModel's constructor 8782C0 makes one view per local player (GS+0x14FF4; new 0x450, view constructor 938760; the room and the one-player HQ have only index 0). UI messages go through 119D1B0(System, id, payload*) with System = 881FE0() = [20B2960] - 0x88, which calls each UI object's vtable slot 3. OnMessage 93B320's cases: 3 {player, class, outfit} full rebuild (description at view +0x318, async build through 93F910); 4 {player, slot, weaponId, ?} swaps one weapon (940100); 5 {player, class, outfit, channel, float4 rgba} live recolor (writes view +0x33C + ch*16 and +0x158 + ch*16); 6 {u8, player, outfit} rebuilds only when the outfit changed, else rereads the colors from GS, ignored while +0x310 != 0; 7 {0} / {1, player} sets +0x304 (zoom / camera state, inferred); 8 / 9 increment / decrement +0x310; 10 {0..3} sets +0x3EC (1: Draw skips, inferred). The description (0x70 bytes) starts with the wstring path at +0. Senders: 8BDE80(player, class, outfit) message 3 (8AD970 shows the player's own look; 881F40 sends 9, 3, 8), the color screens message 5 (882070, 8820E0, 87D973), the room's per-frame 8FDFE0 message 6 at 8FE1F5 only when the GS outfit differs from its cache +0xAC4. Async chain: 7B5660 posts to the job queue [20B29B0], the worker runs 93F910(ModelSlot = Async+0x28, Desc*), which caches Resource_Charactor by an FNV hash of the path, loads in 93AA00 through 84E80(20B28D0, path) (on demand: MENUOBJECT is not in a preloaded resource group), copies the colors to slot +0x78 / +0x88, hangs the weapons (940100, which takes the WeaponTable row through E1CF0(GS+0x130, id), row numbers only) and sets Async+0x9C = 1; each frame 93CE30 moves a ready slot to view +0xE0, then to the shown slot +0x1A0. Draw 93C370 takes each channel's RGB from view +0x218 + i*16 with alpha fixed at 1.0. The renderer reads only menu SGO keys (animation_model with a menu CAS, change_color, random_animation, soldier_weapon_slot); the NPC SGOs N601_* / EDF6VC_NPC_* are DSGOs (soldier_color) and cannot be shown directly (inferred). Camera: a full-screen Ui3DSpace; MENUMODELSETTING.camera_pos [0] = (1.1, -0.9, -3.5) for one player, index 0 / 1 of two players use [1] / [2] (93F619); the eye +0x2B0 interpolates +0x2C0->+0x2D0 and +0x2E0->+0x2F0 by +0x300 / +0x308; fov +0x260 (inferred). AI weapons and the WeaponTable rows that show their models: AiSoldierRifle01 3, FlameThrower01 201, RocketLauncher01 109, Shotgun01 46, SniperRifle02 77, LaserLance01 385, LAZR01/02 430, MNS01 517, IZNR01/02 486, TB01/02 488, HeavyCannon01 803, MiddleCannon01 and HeavyShotGUN01 772, PileBanker01 715, Shield01 747 (Shield01Elite has no row).

Outfit selection popup and saving

Evidence: static · Build: steam-678ccb46 · Fact ID: outfit-popup-save-job

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Soldier screen popup
  2. Appearance choice state
  3. Saving the selection
EDF Knowledge Hub record — original wording — expand (1,913 characters)

The outfit popup and the save job: the soldier screen 8AB310 (vtable 1805788 slot 1) builds a request on the stack (rbp+0xE0, vtable 17621F8; 8AB5A9..8ABB36) of five 0x90-byte options {wstring text, std::function<void(ctx*)>, ...} with the text keys ModelIndexMission, Trainee, Soldier, EDF5Trainee, EDF5Soldier (localized by 957EC0) and lambdas (vtables 1805CF0, ...D28, ...D60, ...D98, ...DD0) that set the outfit -1, 2, 3, 1, 0 (8AD560 and the others write screen +0x7A0 and GS+0x6E94, clear +0x818 and tail-jump to 7E2EB0, closing the popup); the options vector sits at request +0x150 (+0x158 data, +0x160 capacity, +0x168 size; it grows by reserve(cap*2+2), B91D0, and copies each with 89950(vec, dst, src)); +0x128 = 6 (the dialog type), +0x148 the cursor (mapped from +0x7A0), +0x12C = 1; 8ABC10 shows it with 119C600(system, out, type, request). A lambda's impl is {vtable, screen} (screen +0x798 the player slot, +0x7A0 the outfit); the MSVC _Func_impl vtable has six slots (_Copy, _Move, _Do_call, _Target_type, _Delete_this, _Get; _Copy / _Move write their own vtable, 8AD410 / 8AD780). 8AC6E0, a setter, is referenced nowhere. The controls help is looked up by 7A3500 (Sys_Control_Keyboard_Description_SoldierSelect / Sys_Control_Description_SoldierSelect) into screen +0x738 with +0x6F2; an option's destructor is 8E170; 8BDE80(0, class, D8700(GS, 0)) rebuilds the 3D preview. Saving MAIN.GST (GS+0x6E68, 0xDCE8 bytes): 7C2E30 -> 7BCD40 builds a save job with 7BD910 (called at 7BCE7C; its other callers pass 0x3E8, 0x548C, 0x16C4 (a mode save), 0x98, and lengths computed at 7C3080 / 7C36B0), which copies the data into the job's own vector (+0xC0) and sets +0x90 data / +0x98 length (7BD9F4..7BDA1B); running the job (7C1CB0) checksums that copy (7C2228..7C2245: 7C1270(+0x90, +0x98)) and writes it, so a plugin can change what is saved in the job's copy without touching GS (sites 7BCE6D, 7C2F0C).

Basis: the author's static reading ("H"; that UiSoldierSelect 7DB7D0 is a debug menu "M")

Outfit color slots from save to preview and battle

HQ preview, in-battle read and selective palette edits

Static/emulated code paths; source reports byte-equal tests. HQ model build at 93B466..93B4E3 writes saved palette values into soldier description +0x24/+0x34; the battle constructor at 591965..5919FC invokes D8700 for outfit selection and reads the same saved palette at the soldier_color parameter's slot. Live HQ palette edit 93C202..93C249 writes preview target colors +0x158/+0x168 and retained description +0x33C/+0x34C only when local player, class and outfit match the preview; it leaves the other color slot unchanged. Contributor emulation covered two players, four classes, four stock outfits and two slots; this is a bounded native-code check, not an independent in-game color UI acceptance test.
