DDS, packed channels, FPR and runtime texture-binding contracts

UniversalTexturesEDF 5EDF 6
Source-backed research / case study · Reconciled native corpus + runtime-positive EDF6 custom binding + bounded source-guide semantics

Texture handling in EDF6 is not one universal “DDS in, DDS out” rule. Compression, packed channels, sampler meaning, resource admission and shader-family semantics all matter independently.

DDS binary header and DX10 array fields: offsets that matter

DDS is a standard texture container, but the observed EDF6 FieldRender array DDS samples use its DX10 20-byte extension. A strict, read-only R13 shader-research parser independently checks these offsets. All offsets here are file-absolute bytes from the beginning of the DDS file, not game MDB/FMEP material-relative values.

Absolute byte offsetType / sizeInterpretation
0x00, 0x04char[4], u32DDS magic and canonical header size 124
0x08, 0x0C, 0x10Three u32Header flags, height, width
0x14, 0x18, 0x1CThree u32Pitch/linear size, depth, declared mip count
0x4C, 0x50, 0x54u32, u32, char[4]Pixel-format structure size 32, flags and FourCC (e.g. DXT1, DXT5, DX10)
0x6C, 0x70Two u32DDS capability flags and cube/face flags
0x80, 0x84, 0x88Three u32If FourCC=DX10: DXGI format number, resource dimension and miscellaneous flags
0x8C, 0x90Two u32DX10 array size and miscFlags2; for the inspected 2D arrays, resource dimension is 3
0x94 / 0x80Start of payloadFirst texel-block data byte after a DX10 / classic non-DX10 header, respectively

For block-compressed levels, compute a single slice/face size as ceil(width/4) × ceil(height/4) × blockBytes, with blockBytes = 8 for BC1/BC4 and 16 for BC2/BC3/BC5/BC6H/BC7. For example, a 2048×2048 BC1 level-0 slice needs 2,097,152 bytes; BC3 needs 4,194,304 bytes. For each smaller mip use max(1, width >> level) and max(1, height >> level), recompute compressed block dimensions, and account for every slice/face before asserting a complete payload.

Evidence limits: the R13 header-only inspector verifies the magic, header ranges, declared type and presence of one complete level-0 face when block size is known; it intentionally does not assert a valid whole mip chain, actual sampled pixel values, engine SRV reinterpretation or visual correctness. Separately, the native EDF6 terrain audit checked 20/20 full original array DDS payload sizes. Both pieces of evidence distinguish numeric DXGI 71 = BC1_UNORM from 72 = BC1_UNORM_SRGB, and 77 = BC3_UNORM from 78 = BC3_UNORM_SRGB. The on-disk enum never by itself proves the runtime view's transfer function. R13's dimension/size restrictions are limitations of that particular strict offline inspector, not global EDF engine limits.

EDF6 model BC7: native DDS parser and stock corpus

Parser (static, EDF6 Steam 678ccb46): EDF.dll+146B200 checks DDS , a 124-byte header and a 32-byte pixel-format record. The FourCC dispatch at 146B51A maps classic DXT1 to internal format 120, DXT3 to 130, DXT5 to 140, ATI1/BC4U to 150 and ATI2/BC5U to 160; signed BC4/BC5 and numeric legacy float/integer FourCCs have other entries. For DX10, it reads the 20-byte extension at 146B542 and looks up the DXGI number in the native table (1473720, table 2140120; 0x116 records of 0x38 bytes). The resolved format is stored at parser-object +0x84; cube, volume and normalized array-size fields at +0x89, +0x8A, +0x8C. An unknown format or simultaneously set cube and volume flags is rejected.

The source's static simulation of initializer 1471990 records DXGI 71/72 as internal 120/121 (BC1 linear/sRGB), 83 as 160 (BC5), and 98/99 as 180/181 (BC7 linear/sRGB). It also records linear/sRGB alternate indices at entry +0x2C/+0x30. This suggests a common color-path choice for old DXT1 and DXGI-98 BC7, but the code consuming the alternate index and actual sampling behavior were not traced; do not present this as a runtime-verified sRGB conversion.

Counted stock textures, not an engine-wide limit: the source scan of Root.cpk OBJECT, WEAPON and MAP model/map archives found 5,033 old-header HD DDS and 239 DX10-header HD DDS. Of these, 179 DX10 textures in OBJECT/WEAPON are DXGI 98 (BC7_UNORM); the 60 MAP textures divide into 32 DXGI 98, 23 DXGI 95 (BC6H_UF16) and five DXGI 99 (BC7_UNORM_SRGB, sky cubemaps with no sampled model-use precedent). In OBJECT/WEAPON the DX10 entries most often fill param_r_m_occ_light slots (148 bindings); there are also albedo, dirt, normal and window-frame uses. The 179 OBJECT/WEAPON samples generally use DX10 resourceDimension=3, arraySize=1, miscFlags2=0 and full 1×1 mip chains, with one documented E614 cubemap flag exception; a BC7 block takes 16 bytes per 4×4 block and the fixed DX10 header occupies 148 bytes.

LOD pairing: 178 stock DX10 model texture pairs place the small .lod member in TEXTURE before the HD member in HD-TEXTURE. Each reduced side is 1/16 of HD (at least 16 pixels), and the mip chain ends when its long side reaches 2 pixels. Crucially, the small DDS is not necessarily the byte-identical compressed tail of the HD mip chain: 216 of 218 compared pairs differed in the source audit. Forty DX10 MAP pairs had a different mip-count convention (one extra level). Copying a BC7 HD mip tail blindly is therefore not a stock-byte reproduction guarantee; retain the existing separate runtime-positive authored-texture contract for authoring decisions.

The related source note calls the model .lod resource “mip level 4” and reports stock mip reduction by a 2×2 box filter in gamma space and BC5 normal-map green orientation matching DirectX convention. Interpret “mip level 4” as the observed scale relation, not proof that its compressed bytes equal HD mip 4: the paired archive audit above explicitly found that most differed. Nor does a model-family BC5 convention supersede the separately measured BC1/BC3 FieldRender terrain normal arrays. These are source corpus observations, not a universal DDS writer specification.

Source and scope: Hajisensai, All Forces docs/model-quality-1121-bc7.md, with novae (ajane) co-credited for the DDS parser; the Knowledge Hub, Steam 678ccb46, static analysis and corpus sampling only. No new in-game test was performed for these records.

Native BC1 / DXT1 cutout evidence

A retained native Common_Clip foliage texture, sk_pShrub003-df.dds, is classic DXT1/BC1. In its audited top mip:

  • all 32,768 BC1 blocks used transparent mode (color0 <= color1);
  • 427,079 pixels selected palette index 3 / transparent.

This proves a real native one-bit-alpha path. It does not prove that every alpha-cutout texture should be rebuilt as BC1.

A source-authored Common_Clip experiment generated deterministic DXT1 one-bit-alpha DDS with a full mip chain, but that experimental output remained runtime-unverified in the October writer checkpoint. Keep native evidence and new-writer qualification separate.

Cutout mip alpha-coverage preservation

A source-owned Common_Clip diagnostic exposed a concrete mip-generation failure: the 64×64 BC1 top level retained 50% transparent coverage through 8×8, but the original deterministic opaque-majority downsampler collapsed transparency to 0% at 4×4, 2×2 and 1×1. The associated LOD DDS began at 4×4, so the entire distant cutout chain was opaque.

R14 added an opt-in coverage-preserving BC1 mip generator. It tracks fractional per-area alpha during downsampling and chooses the target number of opaque/transparent texels per mip with a deterministic 8×8 Bayer-ranked tie breaker. The top 64×64 BC1 payload remains byte-identical to the original path.

Measured transparent texels for the 50% diagnostic:

Mip Original R14 coverage-preserving Ideal
64×64 2048 2048 2048
32×32 512 512 512
16×16 128 128 128
8×8 32 32 32
4×4 0 8 8
2×2 0 2 2
1×1 0 0 0.5, not representable

This is an offline/source-owned quality fix, not a recovered universal Sandlot mip generator. It is appropriate only for one-bit-alpha cutouts; do not use it for glass/translucency. A controlled EDF6 side-by-side render is still required before treating the policy as production visual authority.

Runtime-positive custom texture binding

The custom-map runtime chain establishes more than filename lookup:

  • R12G: custom albedo identity + authored HD/LOD DDS + canonical RAB insertion rendered correctly;
  • R13A: custom normal identity + authored HD/LOD DDS rendered through the normal sampler;
  • R13B: custom mask identity + authored HD/LOD DDS visibly changed mask-controlled material response.

Therefore albedo, normal and mask slots are each independently runtime-positive with custom resource identities in the tested Sikiita-scaffold path.

The earlier black-texture failure was not evidence that custom names or authored DDS were unsupported. It was traced to noncanonical resource admission/order. New texture resources must be inserted into the canonical contiguous type blocks rather than appended after MODEL entries:

*.lod.dds -> TEXTURE
HD *.dds  -> HD-TEXTURE

For the tested 512×512 / 10-mip DXT1 path, the runtime-positive LOD contract used the HD mip tail beginning at mip level 4, producing a 32×32 / 6-mip LOD resource.

Source-image compiler boundary

The later Source Texture V1 backend accepts a bounded artist-source subset — non-interlaced 8-bit RGB/RGBA PNG and 24/32-bit truecolor TGA — and deterministically emits BC1/DXT1 with a full mip chain under additional constraints. That compiler path was offline-qualified; it inherits useful runtime oracles from the earlier DDS lineage, but it must not be described as if every PNG/TGA conversion output had separately passed in game.

Packed normal conventions are family-specific

For reconciled Common/Water-style paths, the documented packed normal reconstruction is:

x = 2*R*A - 1
y = 2*G - 1
z = sqrt(max(1e-5, 1-x*x-y*y))

normal_amount scales XY before basis transformation, and the retained compositor research gives stored logical-normal magnitude a lighting role. FieldRender terrain is a known exception with a different R*B / signed-G decode. Do not use one normal decoder globally.

Metallic / roughness packing

For the known Common/BRDF-style guide contract:

  • typical metallic = packed G × material metallic;
  • typical roughness = packed R × material roughness;
  • _hr roughness = packed R × A × material roughness.

This is useful behind a known material-family profile. It is not permission to interpret unknown legacy samplers by name alone.

FPR / mask conversion: no universal channel shuffle

Paired EDF5→EDF6 same-asset research shows that some native EDF6 targets underwent real material/texture rebakes. A simple “source mask → destination FPR by fixed channel permutation” worked for some observations but failed to generalize across the corpus.

The safe conversion rule is therefore:

  1. identify the target material/shader family;
  2. use a proven family-specific packed-texture contract when one exists;
  3. preserve the source/unknown texture when no exact migration is established;
  4. never synthesize FPR solely because the destination sampler has an FPR-like name.

Mip / LOD implications

Texture identity and sampler binding are only part of runtime correctness. The tested custom-map path required both HD and LOD resources, correct mip lineage and canonical RAB type-block admission. A correct-looking DDS payload in the wrong resource topology can still fail at runtime.

This is also why model-material migration must move the complete shader/material/sampler/vertex/texture contract rather than just rename a shader or reshuffle channels.

FieldRender texture arrays are separate from static-model packed masks

An original EDF6 terrain corpus of 20 DDS files from five maps used DX10 array headers and exact BC-compressed mip chains. Common dimensions were color 2048²/12 mips and 512²/10 mips; normal 2048²/12 and 128²/8 mips. Native slice counts varied by map (color 4–12, normals 3–9), and normal DXGI format was 77 (BC3_UNORM) in three maps but 71 (BC1_UNORM) in two. Value 71 is BC1_UNORM, not BC1_UNORM_SRGB (72); preserve the raw value where older research called 71 “sRGB”. These are FieldRender terrain-array observations, not rules for the R/M/O packed masks used by static MDB props. See native FMEP texture and material evidence.
