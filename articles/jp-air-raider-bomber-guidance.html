Air Raider bomber requests: parameters and laser-guidance tests

ConversionCommunity Japanese WorkbookGameplay & AIEDF 5EDF 6
Technical reference · Translated contributed workbook notes; sample data, negative experiments and explicitly labeled inferences

Data layers

The Japanese workbook compares bombardment request examples KM6Z4, Phobos Z, Phobos Z4 and a Westa DA entry. Their sampled SGO records contain an object resource, multiple scalar parameters and a pointer to a subordinate projectile. The annotated mapping names fields such as bomber type, aircraft count, delay between aircraft, altitude, speed, attack-direction offset, distribution type and subprojectile node (解析!A417:O447).

The excerpted object paths include app:/object/Bomber501_2.sgo and app:/object/Bomber401.sgo, but their presence in sample rows is not a universal list of allowed bomber objects. Do not infer game-wide aircraft class IDs or network protocol IDs from the displayed record positions.

Source-supported behavior, not yet a general formula

The workbook notes an attack center shown as a blue inverted triangle. One sampled field is thought to select a point from the base toward the tip of the warning zone (zero at the base; approaching one toward the front). Another value apparently influences a forward/downward release trajectory: 0 gives a downward orientation, while increasing it is reported to lead in front of the aircraft. An additional field may describe spacing of aircraft. The author explicitly uses uncertain language for parts of this mapping (解析!H439:H443).

Accordingly, an editor should expose these as observed fields with uncertain semantics, rather than promising a physically accurate predicted impact location. The author notes a visual difference between Phobos Z and another attack that might be caused by gravity, but does not isolate the cause (解析!A481).

Laser-guidance negative experiment

The author asked whether bombs released by a bomber can be actively redirected through a laser guidance device. The experiment reports a negative result in the tested configurations (解析!A483:E491):

Released class or nested construction What the source reports
MissileBullet01 Guidance itself did not operate, even with the laser-guidance flag set to 1
ClusterBullet01 → EfsBullet Some guidance was observed, but not by the laser-designation tool
ClusterBullet01 → MissileBullet01 Some guidance was observed, but not by the laser-designation tool

The author proposes that the bomber's white radar marker, hence perhaps a different team ID, may prevent it receiving laser-designation information. This is explicitly a hypothesis, not a diagnosed root cause. It must not be converted into a rule that all white-team entities reject laser targets. For exploratory team settings see community team matrix.

Tooling recommendations

  • Keep bomber request / aircraft object / projectile instance as separate entities in the authoring model.
  • Do not assume the visible warning-zone triangle uniquely determines actual landing points without trajectory and gravity tests.
  • Mark laser target forwarding as not demonstrated for these examples; avoid silently turning the failed experiment into a successful mechanism.
  • If testing guidance, log the projectile owner/team, actual target selection, guidance flag, target acquisition callback and emitted nested projectile class separately.

Source: mod製作メモ.xlsx, 解析!A417:O491. The experiment is reported by the contributor; no runtime was repeated in this wiki revision.
