Container and conventions

Everything is little-endian

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-conventions

Everything is little-endian; strings are UTF-16LE with a two-byte terminator; most offset fields are relative to the start of the entry that holds the field (resolve as entry start + value), and a zero or negative offset means no string or reference.

Basis: EDF_Tools loaders; 323-file parse with 0 errors

Attribution: CAS/CANM specification (unnamed author), EDF_Tools (AUK233) · 2026-11-01

CAS header (0x30 bytes): magic CAS\0, version (516 in all 323 sampled files), CANM offset (absolute

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-header

CAS header (0x30 bytes): magic CAS\0, version (516 in all 323 sampled files), CANM offset (absolute; the whole CANM body is embedded verbatim there), then count and absolute offset pairs for TControl (+0x0C/+0x10), VControl (+0x14/+0x18), AnmGroup (+0x1C/+0x20) and BoneList (+0x24/+0x28), and the global program offset at +0x2C (non-zero in all 323 files). The instruction width is 9 words for CAS 512 and 13 words (52 bytes) for 515 and 516.

Basis: CAS.cpp ReadData

Attribution: CAS/CANM specification · 2026-11-01

CAS TControl clip reference record

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-tcontrol

TControl (12 bytes): name offset, number of clip references (0 to 4 in the sample, mean 1.10, zero is valid), offset of an array of int32 indices into the CANM's animation names (CANMAnimationList, the AnmData order). Engine meaning: one sequence that joins the referenced clips in order; its length is the sum of the clips' durations; a time past the end is handled by the last clip. Parametric instructions and AnmGroup end and start times refer to TControls by index.

Basis: CAS.cpp ReadTControlData; 7,040 TControl entries all in range

Attribution: CAS/CANM specification · 2026-11-01

CAS VControl variable and input channel

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-vcontrol

VControl (20 bytes) is a named program variable and the game's input channel: name offset, type (0 float: 978 of 1,160 in 375 files, 1 int: 142, 2 4x4 matrix: 40; a matrix stays "unset" until the game sets it and IK instructions using it are skipped), role (0 to 3; the engine never reads it; by name: 0 internal work, 1 input from the game, 2 constant, 3 tuning value read by the game), initial float (+0x0C), initial int (+0x10). Game code finds a variable by name (GetValueIndex 1167170) and writes it each frame (float 116DE10, int 116DE30, matrix 116DF60), so renaming a VControl cuts the game's input (v_move_x, v_aim_target, v_vehicle_grip_l/r_ik_target, v_ik_target_fl/fr/bl/br, v_weapon_grip_ik_target).

Basis: Ghidra read of CASController; the role-by-name split is the document's own inference ("Inferred") over 375 files

Addresses (build-specific RVAs unless indicated): 1167170, 116DE10, 116DE30, 116DF60

Attribution: CAS/CANM specification · 2026-11-01

CAS BoneList mapping by bone names

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-bonelist

BoneList on the CAS side (4-byte entries, a relative offset to a name): at load the engine matches each name against the model's nodes and keeps their world matrices (CASController::Initialize( node not found. : %ls ) in the log when a name is missing); kind-1 node references of the IK instructions index this list. The CANM has its own BoneList; whether the two are the same data is unconfirmed.

State machine and VM

AnmGroup independent state machines

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-anmgroup

Each AnmGroup (12 bytes: name, node count, node array offset) is an independent animation state machine and its nodes are the states. Game code selects a group by name (GetAnimGroupID: for example main, weapon) and a node by name (GetAnimationID) and switches state with SetPlayedAnimationID(group, node, flags) (116BFC0); group and node names must not be renamed.

Basis: Ghidra read

Addresses (build-specific RVAs unless indicated): 116BFC0

Attribution: CAS/CANM specification · 2026-11-01

Node (0x24 bytes): name

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-node

Node (0x24 bytes): name; default transition record (data1); count and array of per-source-node records (data2); parametric1 (program run once on entering), parametric2 (per-frame pose generation), parametric3 (IK after the skeleton update), each 0 when absent; an end-time kind at +0x1C (0 never ends and loops, 1 the float at +0x20 is the end time, 2 the summed length of TControl[+0x20]); kind 2 indexes the TControl order (CASAnimationList), not the CANM names (reading it against the CANM names gave 346 false out-of-range hits in the 323 files). Counts in 375 files: kind 2 6,037, kind 0 577, kind 1 10. The "animation finished" test 116BBE0 is false for a negative end time, else true when end time <= current time + playback speed.

Basis: Ghidra read; census of the sample

Addresses (build-specific RVAs unless indicated): 116BBE0

Attribution: CAS/CANM specification · 2026-11-01

CAS transition record and cross-fade frames

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-transition

Transition record (0x20 bytes): source node (-1 in data1), cross-fade time in frames (common: 16, 12, 6, 8, 4, 0, 60), a program run once right after parametric1, an end-time kind override and its value, a start-time mode (0 the float at +0x18; 1 the summed length of the first +0x1C clips of TControl[+0x18]; any other value keeps the current playback time for phase sync such as walk to run), the start time or TControl index, and the clips to skip. On a transition a data2 record whose source equals the previous node is used, else data1 (bit 1 of the flags forces data1). Counts: start mode 0 8,527, 1 358, 2 7,798.

Basis: Ghidra read; census of 375 files

Attribution: CAS/CANM specification · 2026-11-01

A program block is int32 count plus int32 offset to instructions (relative to the block start)

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-program-vm

A program block is int32 count plus int32 offset to instructions (relative to the block start); instructions are 13 words in EDF6 and run in order, with no branches or loops; word 0 is the opcode and an undefined opcode does nothing. Blocks run: the header program every frame right after all group times advance (CASController::Update 116DFB0, in real data only variable arithmetic, opcodes 13 to 19, and it must not use time mode 2); parametric1 and then the transition record's program on a transition; parametric2 for the pose (from the root group, and a referenced group's parametric2 runs too); parametric3 after the world matrices are updated, called by game code and by opcode 32. Per frame: Update(1.0) (time += speed) and the global program; group times and cross-fade weights; the root group's pose; cross-fade; root motion; write to bones; after the game's skeleton update the IK.

Basis: Ghidra read; 10,356 blocks parsed with 0 type mismatches

Addresses (build-specific RVAs unless indicated): 116DFB0

Attribution: CAS/CANM specification · 2026-11-01

CAS instruction operand encodings

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-operands

Operand forms: a float is (mode, value) with mode 0 a literal, 1 the float of VControl[value], 2 the group's own playback time (other modes read 0); an int is (mode, value) with 0 literal and 1 VControl; a TControl reference follows the int rule with out-of-range and negative values clamped to 0 (the only range check the engine does); a pose is (group, register) with group -1 own group, register -1 the output pose and 0 to 3 scratch poses; an IK node is (kind, index) with kind 0 the matrix of VControl[index] and kind 1 the world matrix of BoneList[index]. Audio and effect events (MAB) in the elapsed interval fire only when the time operand is mode 2. A broken mode or index combination can crash the game.

Basis: Ghidra read

Attribution: CAS/CANM specification · 2026-11-01

CAS opcode interpretation statistics

Evidence: static · Build: steam-678ccb46 · Fact ID: cas-schema-statistics

The statistics that led to the opcode reading: opcode 0 is the first word of an instruction ("schema" in the study), 19 distinct values occur (0, 1, 2, 4, 5, 8, 11 to 18, 24, 30 to 33); the word just before a float-typed word is always 0 (it is the mode word of a literal, so a mode-1 operand holds an int index there); a node's type 2 transition record always carries one opcode-24 set, type 0 always has the end value -1.0 (540 times) with an opcode 12 set or an opcode 24 plus 12 pair. Unused trailing words per opcode (padding candidates, not read): 7 to 12 for opcodes 0, 1, 8, 13 to 16, 30; 10 to 12 for opcode 2; 9 to 12 for 4, 5, 11, 17, 18, 31; 5 to 12 for 12 and 24; 2 to 12 for 32; 3 to 12 for 33.

CANM6 clips (version 768, EDF6)

CANM v768 header layout

Evidence: static · Build: steam-678ccb46 · Fact ID: canm6-header

CANM header (0x20 bytes, same layout as v512): magic CANM, version 768, then count and absolute offset of AnmData (+0x08/+0x0C), Keyframe channels (+0x10/+0x14) and BoneList (+0x18/+0x1C). It is identical standalone and embedded in a CAS. After the table read, the CAS reads the AnmData names a second time into CANMAnimationList (stride 0x1C), which the TControl references index; CASAnimationList is a different list (TControl and node names).

Basis: CANM6.cpp; 323 files, all embedded CANM 768

Attribution: CAS/CANM specification · 2026-11-01

CANM AnmData clip metadata

Evidence: static · Build: steam-678ccb46 · Fact ID: canm6-anmdata

AnmData (0x1C bytes): loop flag (1 loops), name offset, time (duration), speed (time per key), key count, bone count, bone array offset. Time is in game frames (CASController::Update(1.0) per tick); every clip with 2 or more keys (7,509) has time = (keys - 1) * speed; the most common key interval is 4.0 frames. Sampling uses key index = t / speed; past the last key a looping clip wraps and others hold the last key. Playback speed can be changed by scaling time and speed by the same factor. time may be 0 for a one-key static pose (standby, hide in the sample), so code that divides by it needs a guard.

Basis: CANM6.cpp struct; engine sampling read in Ghidra

Attribution: CAS/CANM specification · 2026-11-01

CANM BoneData channel references

Evidence: static · Build: steam-678ccb46 · Fact ID: canm6-bonedata

BoneData (8 bytes of four int16): bone index into the CANM BoneList, then channel indices for position, rotation and scale into the Keyframe table (negative = that element does not animate). Position and scale always point to channels of type 0 or 1 and rotation to type 2 or 3, with no exception in the 323 files.

CANM keyframe channel record structure

Evidence: static · Build: steam-678ccb46 · Fact ID: canm6-keyframe

Keyframe channel (0x30 bytes): base (__m128 xyzw), velocity (__m128), data offset (relative to the entry), type, key count, and a pad at +0x2C that is 0 in all 317,425 entries. Types: 0 static position or scale (base only); 1 dynamic position or scale (3 x uint16 per frame, value = base + raw * velocity); 2 static rotation (base is the quaternion, velocity unused); 3 dynamic rotation (4 x float per frame, the absolute quaternion). Counts in the 323 files: type 0 6,419, type 1 64,813, type 2 8,183, type 3 238,010 (type 2 is 3.3% of rotation channels overall but about 58% for one complex boss, so its share depends on the content). Static channels (0 and 2) have key count <= 1 and velocity 0 everywhere.

Basis: CANM6.cpp struct; bulk parse

CANM frame-data serialization ordering

Evidence: static · Build: steam-678ccb46 · Fact ID: canm6-write-rules

Layout rule for writers: the type-1 frame data is written first as one contiguous block, then the type-3 (float4) block, whose start must be padded to a 16-byte boundary (SSE loads; a misaligned block risks a crash); channel data of different types must not be interleaved. 0 of 238,010 type-3 channels violate the alignment in the game's files.

CANM v512 differences from newer format

Evidence: static · Build: not stated (EDF 4.1 and EDF5 files) · Fact ID: canm512-points

CANM v512 (EDF 4.1 and 5), for reference: the same 0x20-byte header and AnmData and BoneData layouts, but channels (called AnmPoint, 0x20 bytes: int16 type, int16 frame count, base xyz, speed xyz, data offset) use a type system of their own (1 for position and scale; rotation as three Euler-angle channels, or type 625 for an uncompressed 4-component channel, 16 bytes per frame as 4 floats); position, scale and Euler data are 3 x uint16 per frame with the same base + raw * speed rule, and axis rotation matrices are composed in an unconfirmed order. ReadAnimationFrameData is the real reader; the older ReadAnimationPointData is commented out at its call site.

CAS, CANM, MAB and runtime contracts

The records below add format conversion, interpreter use and failure-mode evidence from the Knowledge Hub. Verified marks tests reported by ktaro, not new tests performed for this release. BarteY's cross-game converter and TKW class-port notes are distinguished from vanilla steam-678ccb46 disassembly.

Cross-generation CAS/CANM/MAB conversion

Static multi-game corpus · BarteY: outer CAS versions are EDF4.1 0x200, EDF5 0x203, EDF6 0x204; their command-record strides are respectively 0x24, 0x34, 0x34 bytes. Embedded CANM is 0x200 for 4.1/EDF5 (0x20-byte channels) but 0x300 for EDF6 (0x30-byte channels). EDF4.1's 16-bit quantized XYZ and Euler Rz*Ry*Rx rotations do not map by changing the header version: EDF6 needs independent absolute XYZW quaternion tracks, 16-byte aligned. Commands map by paired state/control semantics, not a uniform opcode offset. BarteY parsed/rebuilt 836 CAS files; of 230 EDF5/EDF6 same-name pairs, 66 converted byte-identically, 21 EDF6 peers were re-authored, 143 mainly differed in quaternion float bytes (69 also in key order). Static quaternion agreement (1,487/1,487) was much higher than animated key agreement (88,038/1,958,796), consistent with prior source quantization. One of 205 studied 4.1 conversions failed for unmapped command IDs. All figures are sample results, not guarantees for any CAS.

Static parser census · BarteY: MAB version 0x0F has a 0x24-byte header and four block-relative directory offsets at +0x14..+0x20. Internal-pointer mode at +8 is 0x03 (block-relative) in EDF4.1/EDF5, 0x83 (owning-struct-relative) in EDF6. This corrected an older false assumption that several adjustment/float-group record offsets were absolute. Sample validation covered 1,153 4.1, 1,652 EDF5 and 2,487 EDF6 MAB files. Locator headers, 0x20-byte locator records, event tracks and keys require selective rebasing: plain integers, sentinels and names are not pointers. Bone names and consuming class event behavior still need verification after a structural conversion.

Static port diagnosis · BarteY/TKW; build unstated: an absolute CANM clip saves local bone transforms, so editing an MDB's bind-pose translation while retaining the old clip makes the animation pull that bone back to its former position. The correction is a named per-bone local translation delta on the base XYZ of affected absolute clips; additive/recoil clips must not receive the same blanket offset.

Static stock-CAS analysis · ktaro, novae: _add clips are pose deltas applied to a base motion by CAS instructions. The instruction defines both which base motion and whether multiplication is base × delta or delta × base. The relationship was checked against all 375 stock CAS files, including additive clips reused over several base motions. Do not infer the base from the additive clip name alone.

CAS VM scripts, variables, loops and callback semantics

Static 375-file census · ktaro: every-frame script (header +0x2C) mainly uses opcodes 13–19, with a single ignored 35 in P_LAUNCHER_ARMAGEDDON; state entry uses 1, 12, 24; post-entry transition uses 12, 24; pose script uses 0–11, 13–18, 24, 30; IK script uses 30–33. In the corpus, opcode 8 used an external state machine as pose A in 4,133 instructions, and v_weapon_grip_ik_target was targeted by 305 opcode-31 instructions. These are observed usages, not hard opcode validation constraints.

Static census and update trace · ktaro: among 7,511 clips in 375 stock CAS files, loop bit 0 of AnmData was set in 1,697 and clear in 5,814. Key lookup and event checks both read it: looped time wraps by fmod; non-looping clips hold their last key and stop firing events. CASController::Update(1.0) is called per tick in the named model/bullet paths; the clip-time unit there is game frames rather than seconds.

Static address-space scan · ktaro: the CAS engine's inspected module routines and 93 structures holding a controller did not directly read VControl role field +8; variables were accessed via named/indexed getters and setters. Role 1 “input” versus role 3 “parameter” is largely an authoring convention, not a verified enforcement bit: only 6 of 491 script writes targeted role-1 inputs, and some role-3 variables are written by scripts. User code still needs correct variable names and types.

Static native receiver analysis · ktaro: opcode 33 routes to class-specific callbacks. SoldierBase value 0 reattaches weapon and refreshes left-hand grip IK; values 1 and 2 are no-ops there. HumanoidBase value 0 likewise refreshes grip, value 1 sets byte +0x7EC, value 2 steers aim toward GetActiveTarget while ramping weight to 1 and writing the target matrix. MonsterBase uses value 0 to correct part-bone local transforms and rebuild hierarchy. These differing receivers preclude a single universal “user callback” meaning.

Static corpus/cross-reference scan · ktaro: soldier and the named giant creature clips use lone opcode-33 value 0; frogs and greys use sequences such as (2,0,1); Martians and Venus examples use value 1. No direct game-binary reader/reset of HumanoidBase's +0x7EC flag was identified in the scanned paths (an enemy-AI script path might still consume it), so treating value 1 as ineffective is bounded by that scan.

Verified, source-reported game test · ktaro: replacing opcode-33 value 0 with 1 or 2 in a soldier's IK program stopped weapon reattachment and grip-target refresh; the left hand stayed at its old position while the arm stretched. This observed symptom agrees with the SoldierBase receiver's value-specific path.

Verified CAS rebuilding and unsafe references

Verified, source-reported in-game tests · ktaro, novae: rebuilding stock CAS control/state/transition/program structures from their semantic contents gave byte-identical layout except for keyframe-data ordering, with original string ordering retained, and the files ran in game. Added, removed and reordered instructions/transitions were likewise tested. A VControl's initial float and integer values live in separate typed fields (+0x0C and +0x10), so a wrong-field initializer silently changes behavior.

Verified, source-reported field edits · ktaro: opcode-0/1 destination registers 0, 1 and 3 accepted a pose but did not become the final output (output is -1); changing opcode-0 motion/time operand modes changed motion and event firing. Opcode 8's pose A/B choices altered aim additions, 30 changed aim bone, 31 shifted grip IK, 32 switched group IK. Six deliberately invalid mode/index edits crashed the game due to wrong-type/out-of-range variables, missing group or registers; the VM offers little general bounds checking (an out-of-range motion alone can fall back to 0). Do not feed arbitrary opcode words from editor presets.

Verified, source-reported game/tool crash · ktaro, novae: every clip track's bone index must refer to a bone in the CANM's own bone list, not merely the MDB's skeleton. A track for a model bone absent from CANM caused a crash between sortie and mission start and in EDF Tools. Add the bone to CANM's list before retaining the track.

Static trace · ktaro, novae: CAS-side IK bone names are looked up in the MDB model, and a missing model bone may crash on an IK instruction. Adding a CAS bone-list name makes it an available IK target only when that same bone exists in the actual model skeleton. This differs from the CANM-local track-list requirement above.

Player-group and variable contracts for class ports

Static class-port diagnosis · BarteY/TKW; build unstated: a class resolves named CAS AnmGroup “players” at construction; the examined path failed via unchecked lookup when a required group was missing, crashing at spawn. A missing motion within a present group was sometimes tolerated. EDF6's UfoCarrier508 resolves in_ring and out_ring; a port from a 4.1 carrier needs those group names even if the groups are empty.

Static class-port write audit · BarteY/TKW: the studied Berserker-like class writes float variables v_move_angle, v_move_velocity, v_tilt_dir, v_tilt_lerp each update and v_damage_reaction_ratio on hit. A target CAS must define each writable name with the correct type.

Static unsafe-lookup diagnosis · BarteY/TKW: on the studied class path, a setter resolves a missing VControl name to index -1 and still writes by that index, corrupting out-of-bounds data and typically crashing after an update or damage event rather than on spawn. Missing getter-only variables returned 0.0 and could silently alter tuning. Distinguish required writable controls from optional readers when grafting CAS files.

Static checked exception · BarteY/TKW: the soldier code checks index -1 before setting v_vehicle_grip_l_ik_target or v_vehicle_grip_r_ik_target. Those two specific fields could be omitted safely in the cited EDF4.1 soldier port; the exception does not generalize to the ordinary setters above.

Provenance: ktaro's CAS_Parametric experiments and stock corpus, novae (ajane) binary analysis, BarteY's R3 CAS/CANM/MAB converter measurements and class-port research relayed by TKW. Preserve the difference between typed variable storage, CANM-local track index, CAS IK lookup against MDB, and runtime class-resolved group/variable names when diagnosing a graft.

CAS serialization, variables and bone-name resolution

Stock CAS section order differs from EDF_Tools output

Static, all sampled stock files. Source writes: header, motion array, per-motion clip-index arrays in motion-name order (even zero-clip motions still occupy an offset in this order), variables, CAS BoneList, update script, machine array; then each machine in machine-name order with its states, each state's default transition and script, outgoing transition list (offset present even empty), outgoing transition scripts, enter/pose/IK scripts; followed by 16-byte alignment, embedded CANM and CAS-side name strings. EDF_Tools can serialize a different order. Preserve relative offsets and semantic ownership; do not require byte-identical section order to parse valid data.

Stock script instruction offset is always +8

Static. Source corpus found every stock CAS script as two 32-bit header words followed immediately by its instruction array, so the relative instruction offset field equals 8. That observed authoring pattern should not be confused with a parser invariant forbidding other valid relative offsets.

CAS and CANM string pooling and frame-data freedom

Static. The CAS and embedded CANM each collect all categories of names, deduplicate and sort by ordinal UTF-16 comparison, then share equal strings within that side. CANM frame data ends aligned to four bytes. The source found no stock ordering rule for frame data by channel, content or name; valid offsets make reordering possible. Do not mistake the two independently deduplicated string sets for one shared absolute table.

Small IK-specific CAS BoneList census

Static, 375 CAS files. Only 20 files have any CAS BoneList entries, at most 17; every surveyed CAS-side name is referenced by an IK instruction and also appears in the corresponding CANM BoneList, though some lists are not alphabetically ordered. These are corpus observations, not a format limit or proof of a general duplication rule.

IK resolves names against model MDB nodes

Static. Controller allocates 0x20-byte runtime entries for every CAS BoneList name without a fixed upper count, matching them against all MDB model nodes, not the CANM BoneList. A found entry holds name +0x00 and node data +0x08..+0x18, notably world-matrix reference +0x10; a missing name logs CASController::Initialize( node not found. : %ls ) and loads on with a zero entry. IK opcodes 30/31 dereference kind-1 entry +0x10 without null/range guard, so a referenced name absent from the MDB (or an invalid index) is a crash risk. Validate against the target skeleton before export.

Initial variable values depend on type, not union guesswork

Static. Initialize 1167520 copies file +0x0C into runtime float for type 0, file +0x10 into runtime int for type 1; matrix variable type 2 reads neither value and clears its matrix-set flag. The other-type field is ignored (zero in the surveyed stock records). Runtime float and int are distinct fields: VM opcodes 12–22 read/write the float; opcodes 24–28 the int. A converter must not infer the active type from a coincidentally nonzero unused lane.

State-machine transition order, frame time and clip sampling

SetPlayedAnimationID first four operations

Static, 116BFC0. Target -1 is ignored; selecting the current state is ignored unless flags bit0 requests restart. If current=-1 (just initialized), new time, blend time and crossfade become zero and the target state's default transition is used, bypassing normal transition start-time/crossfade settings. Otherwise select transition, apply its start-time kind, set blend time to crossfade duration, set weight to 1 when duration>0, and snapshot the current output pose. Then zero pending time, reset root-motion state and assign the target as current. The enter/script and end-time steps below happen after that assignment.

Enter script, transition script, then end-time rule

Static. The last transition operations run target-state enter script and then chosen transition's script. End time takes transition's specified kind if nonzero, otherwise state's: 0 means never end (−1), 1 is literal float, 2 is total length of the selected motion. Thus a transition script can initialize variables before normal pose sampling without making the state machine implicitly advance at its configured end time.

Stock transition scripts initialize only float/int variables

Static. In the surveyed stock CAS data, transition scripts have only opcode 12 (float assignment) and 24 (int assignment). When transition end-time kind is 2 it carries one opcode-24 assignment; kind 0 uses an unobserved value filled as −1.0. Only kinds 0 and 2 appeared in transition end-time records—valid format capacity beyond them should not be assumed impossible.

IsAnimationFinished is a query, not an automatic transition

Static, 116BBE0. True if current state = −1; false if end time<0; otherwise true when endTime ≤ currentTime + playbackSpeed. Crossing that threshold does not change the state. Game-specific code decides whether and where to leave it.

Per-frame pending time and cross-machine pose evaluation

Static. Update(dt) 116DFB0 first adds dt×playbackSpeed to each machine's pending time and then runs the update script, before state-machine pose evaluation; time operand kind2 is invalid in that update-script context. Pose update 1165B40 copies current to previous time, adds pending time, reduces crossfade weight by abs(pendingTime)/blendTime and executes the root machine's pose script. Each machine owns output pose register −1, work poses 0–3 and blend scratch. Referencing another machine's output (group≥0, register−1) reruns that machine's pose script each time; referencing its work register does not.

Sequential clip selection and absent-channel semantics

Static, opcodes 0–5 at 116C420. Motion time walks clips in listed order, subtracting each clip length while time≥length; final clip remains selected even past its end. A motion with no clip references leaves the destination pose unchanged. On actual sample the destination bone channel flags are cleared and only bones with animation tracks are set; missing tracks are not filled from bind/rest pose. Normalized time (opcodes 1/5) clamps to [0,1] and multiplies by total motion length.

Interpolation key and last segment

Static, 11602D0. Key index is integer part of time/keyframeTime, interpolation factor its fraction. If the index reaches keyCount−1, loop flag AnmData+0x00 bit0 wraps modulo keyCount−1; without looping, use final segment with factor 1 to take the last key. This prevents treating the last key as the start of an extra phantom interval.

Crossfade blends only channels present in both poses

Static, 1165F80. After pose script runs and while crossfade weight f>0, interpolate current output toward pre-transition snapshot by f only for channels set on both sides: linear position/scale, spherical rotation. Channels absent in either side are not synthesized from rest pose. Initial f comes from SetPlayedAnimationID, then frame update decays it.

Additive pose operations: order, missing tracks and authoring formula

Opcode 8 channels do not apply a bind-pose subtraction

Static. Additive opcode 8 uses output flags (B.flags&3)|A.flags, position A+B when both have it, rotation B*A in System.Numerics/Hamilton notation when both have it (the source's opcode table writes A×B), and scale only from A. If only one pose owns position or rotation channel, its value is copied directly. In particular a difference-only bone is treated as an absolute local transform, not automatically as an offset from a missing base bone; a B-only scale does not get set.

Only pose scripts compose differences onto a base

Static corpus. Additive combination is invoked by opcode 8 in a state's pose program, not an enter or transition script: 6,588 opcode-8 instances across 101 of 375 CAS files. The difference clip has no intrinsic base identity/order; the caller instruction chooses. Patterns include one state sampling base and difference and combining them, or a separate machine outputting only differences, which another machine references through (group≥0, register −1). Referencing that output evaluates its pose script. The same difference can therefore be reused against different base motions.

Pre-/post-multiplication is an instruction choice

Static. Difference on A yields base then difference (post-multiplied, bone-local rotation); difference on B yields difference then base (pre-multiplied, parent-oriented rotation). Source corpus estimates about 1,250 post-multiplied and 100 pre-multiplied difference clips, latter often large enemy/robot reactions and necks. A clip can be used both ways; its filename does not encode the order. Post mode puts the base on B, so base scale is dropped by opcode 8's A-only scale policy. No difference clip in the census has a scale track, and only 15/6,004 clips have scale anywhere.

The _add suffix is neither necessary nor sufficient

Static. The calling pose instructions, rather than the clip's name, determine if it is a difference: some active differences lack add in their names; other clips named add are never sampled. Some drone state machines play only difference clips and no base; an untracked bone then keeps the current matrix-node value at write-back, not an assumed rest pose. Use graph/dataflow to classify clips.

Restore and re-difference in a modeling editor

Derived from source operation rules. Let B be base, D the stored difference, R the desired visible pose. Position R=B+D, inverse D=R−B. Post-multiplied rotation R=B*D, inverse D=inverse(B)*R; pre-multiplied R=D*B, inverse D=R*inverse(B). Restoring and re-differencing against the same base should preserve D under either order. Some clips use a variable as a time coordinate (e.g. 0..1 turn angle) so keys represent a control parameter, not ordinary elapsed time; preserve key count and intermediate identity-like keys, and only create tracks for modified bones.

Pose-register sampling, blending and root-motion write-back

Blend opcodes 2/3/11 preserve asymmetric scale flags

Static, 116BC30. Channel flag bits: 0 position, 1 rotation, 2 scale. At 0<w<1, output flags are (B&3)|A, position linear and rotation shortest-path spherical interpolation when both own the channel; otherwise copy whichever owns it; scale comes from A. For w≥1, flags (B&3)|(A&4), position/rotation from B, scale still from A; for w≤0, copy A. When neither owns a channel, destination retains its previous value. Do not replace this with a symmetric per-bone complete-transform interpolation.

Sample-two and sample-three motion variants

Static. Opcode 2 samples motion A into destination and B into blend scratch in one step, combining with clamp(w,0,1). Opcode 3 computes s=2w, i=clamp(floor(s),0,1), samples motion i and i+1 and uses clamp(s−i,0,1). Sampling opcodes 4/5 additionally weaken their sampled pose if w≤1 and w≠1 through 116DAD0: position multiplied by w, rotation slerped from identity to pose by w, scale multiplied by w. These operations are distinct from the later crossfade against the transition snapshot.

Rotation-only blend, quaternion operations and subtraction

Static. Opcode 10 (116A200) at 0<w<1 yields flags (B&2)|A, blends rotation if both have it and takes position/scale from A; w≥1 yields (B&2)|(A&5) with B rotation; w≤0 copies A. Opcode 6 combines rotations with source table A×B (System.Numerics product order is reversed in the source's explanation), leaving position/scale from A; opcode 7 uses inverse B. Opcode 9 difference uses flags (B&3)|A, position A−B (−B if only B), rotation A×inverse(B) (inverse B if only B), scale A. Slerp selects shortest arc and falls back to near-linear factors for tiny angles. Preserve the matrix/quaternion convention when porting to Godot; written product order alone is ambiguous across libraries.

Output pose writes only flagged matrix channels

Static; external reset unknown. In 1165B40, a designated root-motion bone (runtime +0x108 nonnegative) contributes position/rotation delta relative to prior frame as model movement; its pose channel is reset to origin/identity. The root output pose then applies flagged channels to model nodes: rotation replaces the 3×3 orientation and multiplies by scale when flagged (otherwise unit scale); scale-only preserves rotation and sets axis lengths; unflagged channels do not overwrite the node's current matrix. Whether some other game code resets untouched channels every frame was not tested. This is why difference-only states can retain pose inherited from another path.

IK script dispatch, matrix-variable guards and geometry

IK matrix inputs need an initialized reference

Static. An IK operand is usable as kind1 (world matrix from a resolved CAS BoneList runtime entry) or kind0 matrix variable whose set flag +0x10 is on; the matrix itself is at variable +0x20, set by game routine 116DF60. Wrong kind or unset matrix variable makes the IK instruction do nothing. This early check does not make an invalid BoneList index/name safe: opcodes 30/31 still dereference kind1 node references without a range/NULL check.

IK uses current world matrices after skeleton update

Static. Game code calls 116C700(controller,group) after skeleton world transforms have been rebuilt; e.g. soldier HumanBase OnUpdate sets left-hand grip target matrix via 116DF60 and invokes the main group's IK. Opcode 32 runs the IK script of current state in the group indicated by its word1. Both return without effect if controller +0x118 (post-procedure callback) is null. IK edits bone world matrices, not local poses, so next frame ordinary pose evaluation may rebuild them.

Opcode 30 aims bone A using B's Z axis and target C

Static, 1168B00. Set theta = acos(clamp(dot(Z_world(B), normalize(C−B)),−1,1)). If |theta|≥0.001, multiply bone A's world 3×3 by a rotation of theta about normalize(Z_world(B)×(C−B)), leaving A position fixed; then rebuild A descendants as localMatrix×parentWorld via 6BF950 → 1100010. Axis-angle routine 3FC0A0 is a row-vector matrix multiplied on the right, analogous to System.Numerics, not automatically Godot's multiplication order.

Opcode 31: rotate, clamp reach, solve elbow geometry

Static, 1169200. Root A, middle B, tip C, target T. Return if |T−C|²<1e−8. Rotate copies of A/B/C around A until A→C aligns with A→T. Let l1=max(|B−A|,1.19e−7), l2=max(|C−B|,1.19e−7) and clamp d=|T−A| to [|l1−l2|×1.001,(l1+l2)×0.998] (abort if interval width too small). Cosine-law projection x=(l1²−l2²+d²)/(2d), y=sqrt(l1²−x²) gives middle point A+x×unit(A→T)+y×unit(perpendicular component of A→B). This retains the bend side; a straight chain lacking perpendicular component cannot fabricate it.

Opcode 31: apply bone rotations and propagate children

Static, continuation of 1169200. Rotate A's 3×3 to take old A→B to A→newB, B's 3×3 from old B→C to newB→T; move B to the solved middle and replace C with the target's whole matrix, including orientation. Rebuild A descendants with A/B/C held fixed (6BF970 clears recompute flags on those nodes) so children of C, including fingers, follow the final tip transform. Do not treat the target as a mere position-only point.

November 2026: SGO, MAB, MTAB corpus and native-reader constraints

This section closes source-ID gaps in ktaro's Specification.md for EDF6 model SGOs, MAB event/point tables and MTAB material-animation data. Eight of the 38 added records were already individually anchored in this chapter; the remaining 30 are added below. The source mostly uses static corpus/dll readings with a few author-tested edits, and does not state one exact game-build marker. The numbers are survey counts, not general format maximums.

SGO file forms, model-setting positions, tools and ChangeParam

Old SGO versus DSGO embedded-resource representations

Static, ktaro and novae (ajane). Both old SGO\0 and DSGO signatures use .SGO extension. Embedded MAB/MTAB is base64 in old-text representation, hex in DSGO, or external files with SGOTT -x. Source reports 3,157 stock SGOs round-tripped by SGOTT 2.1.4/2.1.5inline retaining contents; ADDON.SGO uses another signature and was excluded, and shared-node numbers can change. EDF Tools 0.6.2 broke expression references in 15 E602 files and removed whitespace-only strings. Both tools drop unreferenced DSGO nodes (game does not access those); this is not proof of byte identity after repack.

EDF Tools archive repack caveats

Static, ktaro §6.19.1/3. EDF Tools -pd -mc <folder> repacks with multithreaded compression; the similarly named -mt is a known corrupting option. Output extension follows content: at least two MDBs yield .mrab, one .rab, ESB gives .efarc. Of 994 stock archives extracted/repacked/extracted, inner files matched in 993; in UI\SUBEQUIPGUAGE_R.RAB, five DDS header bytes 0xFF changed to 0 under -in/-mc but not uncompressed -fc. Archive bytes always differ due to compression. Tool also fails unless its executable and input folder share location according to source; treat the original archive as a protected input.

Asset names and case must match loaded resource paths

Static. Filename resolution is case-sensitive in some EDF6 paths, with mostly uppercase archive names and extensions. An SGO resource string should reproduce the on-disk spelling. app:/ refers into root.cpk under the install directory; mod references beginning Mods/ also appear (5 among 2,709 distinct app:/ references, e.g. Mods/Weapon/EFFECT/SpecialWireEffect.efarc). Relative-to-install behavior for those mod references was inferred, not exhaustively resolved.

Model-bearing SGO class keys and model-setting recognizer

Static. OBJECT/WEAPON SGOs with a model carry top-level xgs_scene_object_class; UI/MENUOBJECT model files (205 cases) do not. Recognize a model setting by its child [0] beginning [string,*.mdb,...]; no misses in 2,521 surveyed files. Source counted 2,229 SGOs with MAB (2,056 DSGO, 173 old SGO), 2,209 with points, and 261 with MTAB. Do not generalize the xgs_scene_object_class requirement to UI model objects.

Positional and named model-setting children

Static. LoadFromSGO reads child [1] as CAS only for a string, [2] as MAB only for embedded data, [3] as DamageMap for any pointer; absent entries [1]–[3] are zero placeholders. Named material_animation, accessory_ragdoll, effect are resolved by name and placed after those slots: all 108 surveyed mixed cases used [4] or [5]. Avoid compacting away numeric zero placeholders when adding named content.

Nested model list can hide unused later MDBs

Static. If model setting [0] is a pointer and its [0] is another pointer, LoadFromSGO 6BB890 uses [0][0] as model; entries [0][1] onward are not read. Source found this in 280/3,151 settings (V515/RetroBalam, E510/E513/E509, DragonSmall, ant/bee); 37 contain second or later MDBs (e.g. GiantAnt02B light variants) whose purpose is not proven. This nested model list is distinct from an outer list of complete model settings, e.g. bullet_object=[[model,CAS,MAB,...],...].

LOD list parsed only when [0][2] is a pointer

Static. 6BB890 reads LOD levels when [0][2] is a pointer, with list count potentially zero and no fixed maximum. Each level is [MDB name,squared distance], loaded from archive's Model directory. This fits AnimationModel's squared-distance render walk; a number zero at [0][2] is not a valid LOD-array pointer and is sometimes required to make room for ChangeParam.

DamageMap positional fields are not all child SGOs

Static. Model-setting child [3] starts with division counts and minimum/maximum bounding corners; [3][3] onward are ordinary values (including debris MDB names), not necessarily pointer nodes. DamageMap occurs in 227 SGOs in the source census, none with shared-node/expression references in this region.

Appeal animations own model-independent embedded MABs

Static. appeal_animation holds 110 MABs in [MAB,folderPath] form, likely for character/player appeal motion event tables. Among 2,485 embedded MABs, only those 110 were not reached by model-setting paths in this corpus. Separately, 116 CAS names under a resource list were the only .cas strings not connected to a model setting; those are loadable-resource lists, not orphaned model data.

ChangeParam nested position and tested edit

Verified by source author. ChangeParam entries select material by name in entry [0], read up to four components and write only the material parameter's size (≤16 bytes). Missing parameter skips; missing material name crashes. Position [0][2] belongs to LOD pointer/placeholder, so for two-element model lists add numeric zero at [0][2] before ChangeParam at [0][3]. In stock data 43 DSGOs contain it, always [0][3] (40 entries with four values, 3 with three, 6 with one; categories may overlap). ktaro added an entry and observed the material change in game.

Material precedence: MDB, ChangeParam, class table, then MTAB

Static. Initial MDB material values are overwritten by model-setting ChangeParam, then by class top-level lists (ant_ChangeModelParam, bee_ChangeModelParam, animation_model_param_change_table and other keys of the native class list); live MTAB writes occur above them. Same triple [material,parameter,values] form: a non-string material selector (usually zero) targets every material holding the parameter. Nine source-identified classes read these class keys; ant key appears in four GiantAnt DSGOs, bee in two old-form GiantBee and one BeeEX, animation_model table in old-form E507/E515; Egg's ChangeModelParam and Nephila's nephila_ex_ChangeColor had no stock occurrences. Value types can be double, float or int (E515 has int4 in diffuse); integer conversion semantics remain unverified.

Unusual MDB vertex attributes and LightScroll texture behavior

UI button mesh can intentionally omit normals

Static. Button00_main.mdb from UI\BUTTON00_MAIN.SGO has vertex POSITION, TEXCOORD, BLENDWEIGHT and BLENDINDICES only, with no NORMAL attribute; a preview that expects stored normals can render it black. A generic MDB viewer must inspect its vertex declaration, not assume every skinned mesh has normal data.

UV1 is frequently independent of UV0

Static census. Across 331 LightScroll-shader meshes in 1,156 extracted MDBs: UV1 equals UV0 in 58, is a scale/offset transform of UV0 in 29 and differs in 244; in 81, UV1 differs even where UV0 overlaps (over 90% of E505 line_mat vertices). uv_scroll/uv_scale/uv_scale_center are used by UI SND_UI_SIMPLE_UVANIM as (UV−center)×scale+center+scroll for base color, not general LightScroll speed fields. E505 Flare samples albedo0 at UV0+scroll0 and albedo1 at UV2+scroll1.

LightScroll UV offsets and separate R/G masks

Static. LightScroll vertex shader adds scroll_light0 and scroll_light1 to UV1/UV2 as offsets, not per-second velocities. Pixel shader multiplies sampled light0_scroll/light1_scroll by color and UV0 mask. LIGHTSCROLL2 emission is lerp(1,baseColor×diffuse,light_diffuse_factor)×(light0(UV1+scroll0)×color0×mask.r + light1(UV2+scroll1)×color1×mask.g). mask_light0_light1 R/G correspond to lights 0/1, whereas mask_l1_l2 on E601MARTIANSHIELD represents lights1/2. BEAMSHIELD, E616_VENUS_SHIELD and E601MARTIANSHIELD2 omit UV0 mask and glow from UV1/UV2 light textures alone; second light of UFO_LIGHTSCROLL2 does likewise.

MAB event SGOs, receivers and clip timing

Embedded SGOs and shared event records

Static corpus census. All 21,280 sampled MAB events have embedded SGOs, including 3,048 empty ones. Event keys are sorted by name and their index is renumbered from zero. Some 13,220 embedded event SGOs are shared among 1,390 files, with as many as 419 events referencing one node; a rewriter must preserve logical sharing even if it normalizes physical node indices.

Fixed receiver keys and unsafe omissions

Static receiver reading. se reads name, channel, node, is_trace_node, mask, but not source-data pitch or volume. Missing se_stop.channel, quake.power or distance_adjust, material_animation.name, weapon-event name, or 接地.scale can crash. The referenced MAB point must exist for effect.node/trace_shape, step.point and analogous keys. An empty value in se/voice.name, step.point, or 接地.node/collision can instead suppress the event with no crash. Bone references target MDB nodes, effect esb names come from the model's effect EFARC, material_animation.name targets MTAB item names, and 武器.name uses 発射, キャンセル or 旋回不可.

Common and per-class event receivers

Static EDF.dll/RTTI reading. LoadFromSGO installs eight common event names; 118 class-specific names are registered with exact string comparison via AddMABCallback 116BE30. Later registrations replace earlier callbacks for the same name. Source mapped this registry across 104 classes: an unregistered event name is logged and ignored rather than crashing. Monster501 overrides material_animation and reads index key no; only EDF6_Merman (E603_MERMAN, _LIGHT, _M063) registers 接地.

Event-table census and 60 fps timestamps

Static corpus and runtime reading. Of 92,184 MAB clip tables, 43,663 are empty; the dataset contains 261,407 total events. All 35,829 events in 6,564 sampled tables with both CAS and MAB appeared time-sorted. Event times are 60 fps ticks, not keyframe indices: 98.3% fit within clip length, 62% follow the last keyframe index, and 604 exceed clip length (526 se, 68 voice). The table record's third field +8 is zero and unused in stock. Preserve ascending time for EventCheck's binary-search/early-exit path. Tables bind CAS clips by name, not order; missing clip names are ignored and later duplicate clip-name tables win.

SEPRESET sound-name lookup and verified edit

Static with in-game edit confirmed by source author. se and voice resolve exact top-level keys in SOUND\SEPRESET.SGO (DSGO; 3,268 entries); absent names are silent. All 1,722 se names and 19 voice names in the surveyed event data existed. ktaro changed an se.name and verified different playback. Sound files reside under installation SOUND\PC\; a mod may also add sound under \SOUND\ in root.cpk if the preset points at a valid path.

MAB point geometry, groups and key contracts

Five point-record forms and group indices

Static census of 9,695 game points. Type0 = position/radius/int; Type1 = position/size float3/int; Type2 = position/scale/rotation; Type3/4 = position/radius/end point. Int is always −1, end-point fourth component always 1, unused field +0x18 always 0; every point has an embedded SGO. Group ID equals its position in the group table, but type does not follow group (groups 0 and 2 mix types). Type1 box-size interpretation as half-extents is inferred. In 223 capsules, a nonzero start point appears not to be used by GetMABData.

Parent bones and bounding-box exceptions

Static scan. Of 7,845 model points across 2,161 models, 7,841 parent bones resolve in the MDB; four exceptions are known E602 assets. With model vertex bounds enlarged 50% in bind pose, 99.1% points fall inside; 72 outside are natural camera, effect-spawn and thin-ring positions. These counts describe this dataset, not a compulsory geometric validation rule.

Group readers assume group and point presence

Static EDF.dll reading. Weapons enumerate all group0 muzzles, the first group1 IK point and all group2 shell points. Twenty-six object base classes enumerate group1 target points, six classes group2 damage smoke, five classes group3 hit regions, merging regions by name. The group number is the group table position and consumers do not check the group count (stock MABs have three or four groups). Among 137 name lookup call sites, many dereference absent points or parent bones unchecked, making missing references crash risks. GiantAnt 捕食判定 uniquely assumes point Type0 radius.

Shell-velocity ranges and collision presence flag

Static; shell selection unresolved. Group2 shell points (329 in corpus) may carry three-component velocity_min/max and rotation_min/max ranges; spawn velocity and spin are chosen randomly per axis in weapon space, absent values default zero. A later source sentence suggests only the first shell point is used, while 690660 is documented as selecting index modulo count; keep this conflict open pending call-site verification. For 178 group3 regions, auto_map_collision enables mapping by presence, even when set to zero.

Streamer, eye-look and smoke point metadata

Static point-key reading. PaleWing group0 streamer_* points require float border, fade and width (304 occurrences each); absence crashes, while exact border/fade meaning remains open. MonsterBase look-at uses node_name, rot_max, up_vec (four of each in E504); those keys are also required. Damage-smoke point speed and size default to −1 when omitted, and neither key appeared in the sampled stock data.

Vehicle seat display, rider animation and camera keys

Static point-key reading. The 179 surveyed seat points require integer DispCharacter (zero hides rider). Of those, 39 visible-rider points require Animation, referencing a rider CAS Main-group clip. Among 93 camera points, presence of Type controls further reads: 0 fixes camera to the body; 1 looks at target. LookTarget must name a group0 point in the same MAB when Type is present, while Type1 also requires two-float Param. XAngleAdjust occurred 41 times and defaults to 1. Other Type values remain unverified; missing required seat/camera entries can crash.

Name-based MAB events versus numeric class playback

Partial component updates and valid empty MTAB

Static XML and renderer reading. No general item, material or node count cap was established. The binding resolves material and parameter names against MDB and skips absent pairs; the material's four stored components remain unless that component has a node. Of 3,841 material-parameter pairs: scroll_light0 animated y-only in 111, x-only in 23, xy in 34; color alpha-only in 899; uv_scroll y-only in 106 and x-only in 97.
