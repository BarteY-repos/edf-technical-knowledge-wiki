EDF5/EDF6 relative mouse acquisition and native aim shaping

UniversalPerformance & 120 FPSPerformanceEDF 5EDF 6
Technical reference · Exact EDF6 binary analysis; modified-input perceptual parity not generally runtime-qualified

Native relative mouse input is a sequence of device acquisition → continuous action values → player/class look processing. Changing the first stage does not imply that later sensitivity, inertia or weapon restrictions are accidental. The technical addresses below refer to the studied Windows EDF6 EDF.dll (PE timestamp 0x678CCB46, SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916); other builds require new address validation.

Original relative mouse acquisition

The examined EDF5/EDF6 gameplay path uses the classic cursor position → delta from the window's center → recenter the pointer approach. It reads integer screen coordinates; the relative delta is therefore quantized by desktop-pixel movement and cursor handling. This is different from receiving native Windows WM_INPUT relative device counts directly.

For the examined EDF6 build, source study identified the gameplay relative-motion provider at EDF+0x11831F0 and the direct consumer at EDF+0x1188479. These are build-specific offsets. The menu's absolute pointer and text-entry/IME routes are separate and should not be described as gameplay-relative input.

Two action-data families

The engine exposes different fields for continuous and subsequently filtered mouse actions:

Family Source-observed fields Interpretation
Continuous MouseMoveX/Y +0xE8 / +0xF0 Fresh movement deltas
MouseX/Y/ReverseX/ReverseY +0x108 / +0x110 / +0x118 / +0x120 Downstream filtered or discrete actions

A discrepancy in one family is not proof of an acquisition defect in the other. Cursor quantization, game sensitivity scaling, Fencer heavy-weapon response and vehicle-turret inertia are separable phenomena.

The continuous and filtered families share an initial provider sample but have different consumers. The filtered MouseX/Y/ReverseX/ReverseY generator is in RTTI-identified UiInput (derived from xgs::ui::Input, at ControllerManager+0x5AE8) and uses a real-time dt60 normalization. This cannot be treated as another alias for raw device movement.

Native aiming remains intentional game logic

The original downstream route includes scaling, rate limits, saturation/carry behavior and specialized responses for weapons and vehicles. Observed code includes a /24 factor and set_limit_rate. Bypassing these steps changes native gameplay even if it makes cursor motion feel different. The source does not establish that every disliked aim response is a bug in the mouse sampler.

EDF5 has a homologous player-look function (0x2F64B0 in the examined EDF5 binary) with the same /24, component clamp and default rate-limit semantics. This is evidence of inherited engine design, not proof that every EDF5/EDF6 vehicle, zoom or class consumer behaves identically.

Some input and filtering paths are also tied to frame cadence, including wheel consume/reset, action-suppression countdowns and filters normalized to a 1/60 interval. A higher display frame rate therefore does not imply that all input transitions should update at the same frequency.

When additional render-only frames occur between fixed updates, device acquisition and continuous copying can execute per render, while fixed-step consumers still need the complete accumulated interval. The examined design preserves transient wheel/action events until the next fixed update instead of allowing a zero-step render to consume them. These are input-clock ownership rules, not a reason to run authoritative weapon, AI or networking logic more frequently.

Evidence boundary

The provider/consumer topology is supported by an exact-build static audit (95/95 checks); that is not a universal runtime confirmation of improved feel. The supported conclusion is acquisition-only replacement while retaining intentional game-side response, including Fencer heavy weapons, vehicle turrets, Air Raider targeting and scopes. This article describes native game input semantics, not an external hook setup guide.

See also EDF5 keyboard and XInput and input reconciliation.
