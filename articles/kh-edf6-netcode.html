Transport

One EOS P2P packet carries at most 1170 bytes (the EOS SDK's limit)

Evidence: static · Build: steam-678ccb46 · Fact ID: net-eos-packet-cap

One EOS P2P packet carries at most 1170 bytes (the EOS SDK's limit); the game neither splits larger data nor reports it, so anything above the limit is lost.

Basis: EDF6Coop logs NETLOG OVERSIZE game packet and adds fragmenting ("instead of being refused"); MultiSlot 1.5.34's README: the game drops data past 1170 silently

Attribution: EDF6Coop 2.7.2 (INI [Netcode] Fragments), EDF6MultiSlot README, EDF6Coop src packetfit.h (the 1400-byte check, 2026-11-07) · 2026-11-06

Evidence: static · Build: steam-678ccb46 · Fact ID: net-size-check-1400

The game's own size check is looser than EOS's: the packet controller refuses a record only above 1400 bytes (12D0BE6), so a reliable message between 1170 and 1400 bytes is accepted, refused by EOS on every try and resent until the room drops its members (packetfit.h: eight times over about 26 s; netclass.h gives a reliable record 6 tries, #net-record-format; the two counts were not reconciled).

Basis: the authors' static reading, behind the mission start overflow of #net-mission-start-message

The game flushes its outgoing packet queue on a 90 ms timer and sends only the newest state record then, not…

Evidence: static · Build: steam-678ccb46 · Fact ID: net-flush-90ms

The game flushes its outgoing packet queue on a 90 ms timer and sends only the newest state record then, not every frame's. The interval is a float written by the packet controller's constructor 12CB5F0 at 12CB66C (41 C7 46 58 00 00 B4 42, mov dword [r14+0x58], 90.0f), fixed at start; the controller's update is 12CECC0, its flush 12CEA10.

Basis: EDF6Coop installs its player sync only when the flush-interval site holds the game's 90 ms (log "the packet flush interval at EDF+%X is not the game's 90 ms"); the site and its bytes are named in the source

Addresses (build-specific RVAs unless indicated): 12CB5F0, 12CB66C, 12CECC0, 12CEA10

A datagram of the packet controller (eos::packet::ControllerImpl, vtable 1AF4FF0): records gather per peer in…

Evidence: static · Build: steam-678ccb46 · Fact ID: net-datagram-format

A datagram of the packet controller (eos::packet::ControllerImpl, vtable 1AF4FF0): records gather per peer in a buffer (12CFFD0) that is flushed (12CEA10; called from the send path 12CE99A, the acknowledgements 12CEDBB and the per-peer builder 12D0020) when the next record would pass 1100 bytes (0x44C) and on the 90 ms timer. The flush writes an 8-byte header (two random bytes, a 16-bit datagram number, a CRC32C of the plaintext records taken at 12CEA79), encrypts the records with AES-CTR (7B8060, called at 12CEBAA; same length) and hands the datagram to EOS on the same thread (12D0120 -> vtable slot 3 12D2EF0 -> 12C8BC0, always EOS_PR_UnreliableUnordered). The receive 12CDF20 decrypts with D2360 (at 12CE16B), checks the CRC and drops a datagram whose number and CRC it has seen (12CE1F3..12CE1FE).

Basis: the authors' static reading; their plugin hooks the flush and the encrypt call after checking the bytes

Records inside a datagram start with a u32 size 20 | type and size bytes follow (the receive loop 12CE515 ad…

Evidence: static · Build: steam-678ccb46 · Fact ID: net-record-format

Records inside a datagram start with a u32 size << 20 | type and size bytes follow (the receive loop 12CE515 advances by size + 4). SendUnreliable (12D1040) writes the data record alone, lost with its datagram. SendReliable (12D0AC0) first writes an envelope, u32 0x00401200 (type 0x1200, size 4) and a u32 sequence number, and keeps the record until the peer acknowledges it: 6 tries, the first resend after 700 ms (1FEF040), the wait growing by 1FEF048 each try; the receiver acknowledges every envelope (12CE4FF -> 12CFCD0) and drops a record it already has. Types 0x13xx, 0x14xx and 0x18xx are the controller's own (acknowledgements and the like, 12CE2B7..12CE2D7); a data record's type is ((sub & 0xF) | id << 4) << 8 (12C2E59); the event layer's batches are type 0x3000.

Basis: the authors' static reading

Addresses (build-specific RVAs unless indicated): 12CE515, 12D1040, 12D0AC0, 1FEF040, 1FEF048, 12CE4FF, 12CFCD0, 12CE2B7, 12CE2D7, 12C2E59

Evidence: static · Build: steam-678ccb46 · Fact ID: net-receive-readers

Who reads a received packet: both receive loops ask EOS for any channel (RequestedChannel null: 12C8CC0, xor esi, esi at 12C8CED; 12C9CA0, 12C9CFD; EOS_P2P_ReceivePacket through the import slot 1755058, 12C8D84 / 12C9D5A) and hand every packet to the subscribers (12C71F0, called at 12C8DB5 / 12C9D91) without looking at the channel. Event layer and object messages

Events carry their sender

Evidence: verified · Build: steam-678ccb46 · Fact ID: net-event-sender-key

Events carry their sender. The receive pump 12C8CC0 -> 12C71F0 hands {PUID +0, data +8, bytes +0x10} to subscribers; the packet controller calls a function<void(const UsrIndexKey&, const PacketEventType&, const PACKET*, const void*, size_t)>, for the event layer _Do_call 735D50 (vtable 17EC528) -> EventController receive 74FD50(ctrl, &UsrIndexKey, &type, PACKET*, data, size). UsrIndexKey is an int index into GameImpl's user list (GameImpl vtable 17EC178 slot 0x18 = 734D70: -1 = none, else [[GameImpl+0x30]] + key*16 = shared_ptr<eos::User>; the key is the member's slot, #net-member-slots). 74FD50 reads per event a type word (12B4B80), an event id (12B4B90) and a flag byte (12B4BB0); a negative id is negated and with flag bit 0 the key becomes -1 (a reply to an event this machine started; writer 750380). Handlers are found by (id, key) or made through 74F8A0 -> Factory<T> slot 0x10 -> EventBase constructor 74DE80: handler +0x10 type, +0x14 event id, +0x18 sender key, +0x20 controller; blobs are read with 12B49D0, at most 0x5DC bytes. Sends: 750130 / 750260 create local events (id = seq*4 | [EventController+0x10], key -1), 74E1B0 sends to an existing event; 7504A0 writes type, id, flag and blob and takes its destinations from ICommunucate ([ctrl+0xA8]) slot 0x28 = all remote users (slot 0x18 = one user by key). Event_NoteEventSceneObject::OnEvent 755E50 and Event_DamageObject::OnEvent 754350 copy each blob into a new 0x608-byte block (_Ref_count + eos::Serialize at +0x10) with 79A430 (at 755EC4 / 75445E) and post a lambda; its _Do_calls 7564B0 (756610(7, ...) at 7564E9 -> object lookup -> NetworkObject slot 0x88; 6 -> slot 0x78 via 756500 / 756539 for Event_SceneObject 756020) and 7549E0 (hit replay 769E50 at 7549F0) run later on the game thread. So a received object event names the member who sent it, and a sender addresses every remote member itself, not through the host.

Basis: static trace from EOS_P2P_ReceivePacket to the NetworkObject slots and back (EDF.dll sha1 9e259bcf70efbc21bac6d244c93775f5ef4551da); EDF6Coop's test harness calls the same send entries 74E1B0 / 750130 and hands delivered messages to 74C570; novae (ajane)

The game's byte stream (eos::Serialize, 0x5F8 bytes, vtable 1AF41D0

Evidence: static · Build: steam-678ccb46 · Fact ID: net-stream-encoding

The game's byte stream (eos::Serialize, 0x5F8 bytes, vtable 1AF41D0; built by 79A460; copy-constructor chain 79A430 -> 760120 -> 12B4530, which copies with the memcpy thunk 12DA77A): read position +8, buffer +0x10..+0x5F0 (0x5E0 bytes), length +0x5F0; +0x5EC..+0x5EF are never written or read by the game, since blobs are at most 0x5DC bytes. Writers do not check the bound (12B5200 and the others). Encodings: integers (12B4B90, packed 12B4660) put a tag in the first byte's top 3 bits (0 = a 5-bit signed value in that byte, 1 = 13 bits over two bytes, higher tags wider); a small integer is written by 12B5790; a byte block (12B5200, read 12B4900 / 12B49D0) is tag 0xA0 | length and the bytes; a u16 mask 12B54E0; a u64 12B5690; a scalar float (12B5350) is a 3-byte half when its error stays under 0.1, else 0xC2 and a float32 (5 bytes); a position vec3 (761B20) is three half floats as a 6-byte block (8 bytes; 0.5 m steps beyond 512 m). Readers put the position back with 12B48A0 / 12B4FD0.

Basis: novae (ajane); the rest is the authors' static reading

A room numbers its members by their eos::Users slot (the Users object 12B77E0, one per room, made by the room…

Evidence: static · Build: steam-678ccb46 · Fact ID: net-member-slots

A room numbers its members by their eos::Users slot (the Users object 12B77E0, one per room, made by the room constructor).
