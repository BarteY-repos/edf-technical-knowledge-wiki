Generic-NPC subtitles — lossless VOICETABLE compatibility and pacing boundary

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · Runtime-proven content path; presentation separated

The EDF5-port generic-NPC subtitle problem contains two different layers that must not be conflated:

  1. missing playback-key/caption records in the target VOICETABLE;
  2. presentation timing/scroll behavior for long captions.

The first is a content-composition problem. The second is a separate presentation/runtime concern.

M011 missing-key mechanism — runtime proven

In MissionPack03/M011 (Isolation), three generic-NPC voice lines played from the correct actor at the correct time, but target EN lacked the playback-key rows and displayed the unknown-key fallback.

Runtime-qualified M011 additions are:

AM029BE -> Got it.
AM031BE -> Yes sir!
AM138BE -> That is also possible.

A target-locale EDF6_VOICETABLE.EN.SGO compatibility addition resolves the captions. No M011 AC rewrite and no renderer hook are required to solve the missing-key defect.

Six-key compatibility set

The retained direct-talk set is:

M011: AM029BE, AM031BE, AM138BE
M028: AM027W
M055: AT111DB, AT112DB

R67 records runtime-positive subtitle checks for M028 and M055 with the lossless R3 payload. M011's caption content is correct as well, but its long-caption pacing/scrolling remained visibly late at that point. Thus the six-key lookup/content architecture is supported without pretending that caption presentation timing was already solved by the table alone.

R3 payload SHA-256:

93720e17b44cb913c54787560a3337b072403def1856314bb05a18d4ba0ed73a

Why the first all-six build was quarantined

The early R1 all-six table used an ordinary SGOTT JSON decompile/recompile path that trimmed leading/trailing whitespace. Native EDF6 EN contains 54 whitespace-bearing string blocks referenced by 71 cue records. Rewriting those existing strings changed native caption timing/progression semantics.

The key mappings were not disproven; the full-table rebuild method was lossy.

Canonical lossless composer contract

Production composition therefore works against the user's/local target baseline and is addition-only:

  • preserve all existing cue payloads, table indices, node identities and timing metrics;
  • restore/preserve exact raw UTF-16 string blocks where necessary;
  • add only absent compatibility keys;
  • deduplicate semantically identical provider claims;
  • fail closed on conflicting claims or attempts to mutate existing target rows;
  • run a preservation gate before commit.

The preservation gate retained all 13,869 native baseline cues unchanged while adding the expected EDF5 compatibility rows.

Presentation timing is a separate product boundary

R67 still observed M011 long-caption pacing/scrolling lag despite correct content lookup. That does not invalidate VOICETABLE composition. A separate project, EDF6 Subtitle Scroll Fix v1.0.0, was later released and runtime-confirmed for late long-caption scroll windows. It operates in the presentation path and must not be confused with missing-key compatibility.

Consequently:

  • do not undo the lossless VOICETABLE architecture to chase scroll timing;
  • do not apply a blanket mission timing multiplier;
  • do not use the old lossy R1 provider;
  • do not assume a subtitle presentation plugin can replace missing VOICETABLE rows.

Redistribution boundary

The production composer should operate locally against the user's own target table. The existence of a known merge law is not a reason to redistribute a native EDF6 VOICETABLE donor.

The six-key content findings still hold. Evidence: GENERIC_NPC_SUBTITLE_MISSION_ID_TITLE_CORRECTION_2026-09-04.md and GENERIC_NPC_SUBTITLE_STATIC_MAP_AND_TRANSCRIPT_PROVENANCE_AUDIT_2026-09-04.md.

The six candidate English lines originally came from a community-generated subtitle transcription source, not an official EDF5 English subtitle table. The earlier Chinese subtitles.dll static mapping supports the key associations, not independent official English wording. M011 text received later direct modified-runtime confirmation; the later R67 M028/M055 tests support their displayed captions in the tested game, without converting the entire community transcript into an authoritative native EDF5 text source. This matters when comparing text provenance against native audio and should not be hidden behind the correct six-key lookup mechanism.

The whitespace failure has a precise source-data cause: SGOTT 2.1.5's .trim() on decoded/compiled DSGO strings changed 54 distinct raw string blocks referenced by 71 pre-existing cue records. A JSON-to-JSON equality check could pass after both sides had already been trimmed, while original SGO string bytes were not preserved. The corrected local byte-preserving block roundtrip matched the original baseline SHA-256 (4989a0ff873b072c346b822e01f3c5db3104c37c3c89f2133d3b91fde5d01700), and the final addition-only candidate retained 13,869 baseline records with exactly six new entries. See VOICETABLE_SGOTT_WHITESPACE_TIMING_REGRESSION_AUDIT_2026-09-04.md and VOICETABLE_LOSSLESS_COMPOSER_INTEGRATION_AND_RUNTIME_GATE_2026-09-04.md. These are target binary/layout preservation facts, not proof that SGOTT trimming alone explains every delayed caption in stock EDF6.
