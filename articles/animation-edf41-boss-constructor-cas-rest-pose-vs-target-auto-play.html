Animation constructor traps — EDF4.1 bind pose versus EDF6 auto-started CAS clips

ConversionAnimationEDF 4.1EDF 6
Technical reference · Source-exact CAS constructor and rest pose analysis; pure unit-test evidence

A valid animation file can start the wrong encounter phase

A source object may rely on its model bind pose at spawn and start its first CAS animation only after a mission command. An EDF6 donor class may instead start its default CAS player automatically in the constructor. Both files can parse, both clips can play, and the model can still begin in a phase that is completely wrong for the original fight.

The preserved UfoMother301 case demonstrates this precisely:

  • EDF4.1 hull begins with its main CAS player at rest and does not automatically start a clip; its open/close logic is triggered later by the original state machine.
  • The studied EDF6 UfoCarrier508 constructor starts close_state at playback rate 1.0. In the imported setup, that target name aliases the source close animation, around 987 frames from open to closed.
  • EDF4.1 subsidiary cannons also start at their bind pose. The studied EDF6 EventAnimationObject constructor starts the clip named default, which the source bridge aliased to appear (about 558 frames).

Without intervention the mothership can appear with its belly open and close over roughly 16 s, and ten cannons can unfold for roughly 9 s before the source scripts expect them to wake. This is not evidence that the model or the clip was corrupt; the constructor consumed a different initial animation contract.

Correcting only the initial state

The source bind poses were compared with the imported clips:

Part Source required startup Bounded target action
Hull Closed model bind pose Hold the last pose of close while still in its first source state
Subsidiary cannon Folded/rest bind pose Set appear time to zero and playback speed zero until activation
Hatch, cover, main cannon, panels Already matching source bind or static state in the examined setup No blanket override

The rule applies once, on the object's first frame, only if the original class's own state machine has not already started its action. On an activation command, a cannon explicitly restarts appear at time zero with speed one. Rewinding an already-active clip every frame would freeze the encounter. The rest-state policy is therefore not a global “disable default animation” operation.

Wider lesson for class adapters

A successful CAS/CANM import must validate the native class's constructor, name lookup and initial player state, not only channel decoding, bone references and visual playback. Alias correctness is not enough: an alias can point a built-in constructor to a clip that is only supposed to run later.

The illustrated clip/frame counts and donor class behaviour are exact-source observations. They do not prove that another donor class or EDF6 build starts the same clips or has identical bind poses.

Source: components/compatibility/src/edf41mother_pose.h and companion edf41mother.cpp, EDF4.1 R10 HF4 R9 source archive. The retained pure logic had unit tests but no new gameplay run in this wiki pass.
