How a HUi screen opens

EDF6 UI layout loading chain

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-layout-load-chain

  1. HUi screen open call

Complete original research record — expand (1,164 characters)

A HUi screen opens by path: 845250(uiMgr, out, path, args) calls 119C600(uiMgr+0x48, out, path, args), which normalizes the path (AC8A0), takes the parsed SGO from the resource cache (84E80 on global 20B28D0, refcount +0x70), reads the class name from the SGO variable xgs_ui_object_class (name at [1FEEEC0]), finds the factory in the class registry map (119B7B0) and calls factory vfunc +0x10 (119CAB2) with the parsed SGO at context +8. The weapon select is opened at 8AA4D7 by 8AA250 (called from 8ADEC0) with app:/ui/lyt_HUiHQWeaponSelect.sgo (string 1805C30); its factory 8B2550 creates the screen with constructor 8B4280. The HUi base constructor 83E6F0 stores the parsed SGO at this+0x70; 84A920 (from 83EB2E) reads render_mode, ui_type, lyt_NoSlideScreen and layout_tree and builds the element tree (8436E0 / 841800). Layout values are copied into live elements once at construction and the code then reads only the elements, so a replacement .sgo changes a layout with no code hook, while a memory patch has to write live element fields after the constructor returns, not the SGO buffer. Whether reopening a screen reuses the cached parse was not checked.

Basis: disassembly of EDF.dll

Layout button callback registration by name

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-register-callback

Button callbacks register by name on the HUiLayout base with 850810(layout, std::wstring* name, shared_ptr functor*) (EDF5: 4E9610): the call inserts into a map at layout +0x4E0 (nodes 0x50 bytes, key +0x20, shared_ptr +0x40 / +0x48). The functor is a make_shared object of 0x38 bytes: +0 control-block vtable 18068F0, +0x10 agent vtable 18061E0 (slot 1 8B7890 = invoke), +0x18 / +0x20 weak pointer to the owner, +0x28 a member-function pointer plus adjustor. The handler receives an object whose virtual slot 0 returns a pointer to an int, the pressed element's id. Element events (for example focus on a template) register through 850A00. A plugin could register handlers for new buttons of a modified layout (on paper, untested).

Basis: disassembly of the HUiHQWeaponSelect constructor's calls

Addresses (build-specific RVAs unless indicated): 850810, 850A00, 18068F0, 18061E0, 8B7890

No identified Steam gamepad text-input API use

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-text-entry

Text entry: EDF.dll has no Steam gamepad text-input call (ShowGamepadTextInput and ShowFloatingGamepadTextInput are absent as names), and the online room search and chat phrase screens have no free-text field (layout dumps of ui/lyt_huionline_roomsearchdialog.sgo and ui/lyt_huionline_roomfixphrase.sgo). A soft-keyboard abstraction exists (UiCommon_Softkeyboard, HUiCommon_SoftkeyboardGUI, layouts ui/lyt_huitextboxsteamdeck.sgo and ui/lyt_huitextbox.sgo); its callers were not traced, so whether a PC build can open it is open. ImmGetContext appears only as an import name.

Shared vertical scrolling between columns

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-weaponselect-shared-scroll

All columns share one vertical ScrollInfo, which is why they scroll together: 8B5C90..8B5D2C picks the column with the most cells and calls 7EB0A0(col, axis 1, 3000.0, 1) to create its ScrollInfo; the loop 8B5D60..8B5E2A sets byte [col+0xA9]=1 on every other column and copies [col+0xC0] / [col+0xC8] from the tallest (reference count incremented).

Disabling weapon-select column scroll sync

Evidence: verified · Build: steam-678ccb46 · Fact ID: ui-weaponselect-per-column-scroll

Skipping the copy loop (the cmp r8,rdi / je at 8B5D7A: 74 78 at 8B5D7D changed to EB 78, so the jump is always taken) gives every tall weapon column its own vertical scroll through the generic layout code (7F13D7, 7F1409). But moving left or right keeps the cursor's slot index, so the new column scrolls to show its own slot N (not the same screen row; for example Artillery Units ends at slot 18, and moving right from there to the much longer Request Gunships jumped that column to its slot 18), and the left scroll bar drags only the column the mouse last hovered. Vertical click-and-drag panning felt slower with per-column scroll (cause not read); horizontal drag was unchanged. The next static read for a fix: the left / right navigation handler of the columns (where the slot index carries over), mapping the index through each column's scroll offset (parent+0x214, the offset the hit test reads).

Basis: novae (ajane)'s test session with the layout / code-edit package (Alt+F6 on, Air Raider)

Addresses (build-specific RVAs unless indicated): 8B5D7A, 8B5D7D, 7F13D7, 7F1409

Suppressing flashing New and Up labels

Evidence: verified · Build: steam-678ccb46 · Fact ID: ui-weaponselect-label-hide

Skipping the New! / Up label flash code (jump from 8B84DB to 8B873E, the path state 2 takes) hides the labels the next time the screen opens (they return after turning the toggle off and reopening) and leaves the cell state and the save record untouched; forcing cell+0x48 to 0 does not hide them (state 0 also builds a WeaponNew element, 8B85BC). Hotkeys read in a cave on the update (8BABBC) work on this screen; text sent to the message log (the Notice function) is not visible there. Test result: the hit-test toggle (Alt+F7) responded at once every time, the label toggle (Alt+F8, applies on reopen) seemed to work only about one time in five; cause unknown (without visible feedback a double press or a missed reopen cannot be told from a missed key).

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-button-hit-test

Complete original research record — expand (1,144 characters)

UI clip rectangle center-point interpretation

Evidence: verified · Build: steam-678ccb46 · Fact ID: ui-button-hit-test-center

In the clip test 96A1C0 the branch for a nonzero r9d (96A257) treats the rect's x / y as the box center (x, y, w, h used directly: xmm5 = [rsp] x, xmm2 = [rsp+4] y, xmm4 = [rsp+8] w, xmm3 = [rsp+0xC] h, no half-size offset), while the default branch (96A21E: adds w x 0.5 and 5 + h x 0.5, h + (-18)) treats them as the top-left corner. Forcing the nonzero branch for a top-left rect (jne 96A257 always taken) made only the top half of a weapon column respond, plus a strip above it: with a 361 px column only the top 5 rows reacted to hover and click, the lower part of row 5 did not, and the top edge of row 1 did; turning the patch off restored all 9 rows at once. This corrects the earlier reading "if r9d != 0 the rect is used as is" (it is used as a centered box), so the removal option 96A1DC 75 79 to EB 79 is wrong for top-left rects. A working removal of the dead strip would keep the default branch's math with offset 0 and height h (center y = y + h x 0.5), for example in a cave at 96A1D9; other constant: 0.5 at 1C36990. Untested.

Complete original research record — expand (1,639 characters)

The equipped weapon id of player p, class c, slot s is an int at [20B2890] + 0x6E68 + p*0x3E60 + 0x30 + c*0x18 + s*4 (6 ints per class, slots 0..5, also for classes with fewer slots); the player's current class index is the int at [20B2890] + 0x6E68 + p*0x3E60 + 0x28. Here c is that stored class index (the value the class press 8ADB40 copies from [screen+0x778]), not the class id returned by E3550, which neither the reader nor the writer calls. In screen terms: slot s = int at [screen+0x7A8] + p*0x3E60 + (c+2)*0x18 + s*4 with p = [screen+0x798]; [screen+0x7A8] = mgr+0x6E68 (the player save blocks), [screen+0x778] = selected class index, [screen+0x79C] = displayed class index. Reader: 8AC7A0..8AC7D3 (index = p0xF98 + (class+2)6 + slot ints). Writer: the weapon select's PressButton handler 8BD6F0 refuses when cell+0x54 & 6, else writes the id into the screen's working copy of the save region (this+0x800, 0xDCE8 bytes) and copies it back over mgr+0x6E68 with memcpy (8BD7FE; the id store 8BD740..8BD7A0, class read 8BD76E). There is no ownership, level or duplicate check at the write (cells exist only for owned weapons; duplicates are blocked by the UI's cell bit 1 only). Class Select refresh after a change: 8AC720(screen, [screen+0x79C]) (re-reads ids, records, names into the row table screen+0x800) then 8ACD20(screen) (pushes texts and colors into the rows), as at the end of the weapon select's result callback 8AE630 (mov edx,[rdi+79Ch]; mov rcx,rdi; call 8AC720; mov rcx,rdi; call 8ACD20, 8AE7AD..8AE7C2; plain x64 fastcall). When the save region reaches disk, and whether mission start validates ids, was not traced.

Evidence: static · Build: steam-678ccb46 · Fact ID: ui-soldierselect-update-hook

In the Class Select update 8AB310, the code at 8AB415 (mov r9,rbx; mov r8d,[rdi+798h], 10 bytes, unique in the image) runs only after the screen's input gate passed, with rdi = the screen: a per-frame hook point for keys that should fire only while this screen has input. 8AB403 test rbx,rbx / je 8AB549 (locked weak pointer) and 8AB40C test rsi,rsi / je 8AB549 (input pointer, zeroed when 7E4E30(this) is nonzero) come just before it; no branch in the function jumps into those 10 bytes (asserted by a generator script). Which child screens zero rsi is unverified. [screen+0x7E0] is a std::vector<int> of the slot rows' element ids (begin, end and cap at +0x7E0 / +0x7E8 / +0x7F0); 8AB140 sets end = begin when the rows are removed, so begin < end means "slot panel built". The two refresh functions 8AC720 and 8ACD20 have function starts whose first 22 bytes are not unique in the image, so a Patcher anchor on either needs an interior pattern with a negative label offset.
