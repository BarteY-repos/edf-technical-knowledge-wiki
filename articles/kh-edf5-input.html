EDF5 detaches the IME from its window right after creating it and re-attaches it only while its own text inpu…

Evidence: static · Build: steam-5d11de53 · Fact ID: input-ime-detach

EDF5 detaches the IME from its window right after creating it and re-attaches it only while its own text input is active, through a window-procedure hook that swallows the composition messages and draws its own composition and candidate list; so by default no Windows IME window can appear over the game. IME imports (IAT slots): ImmGetCompositionStringW C97060, ImmReleaseContext C97068, ImmSetOpenStatus C97070, ImmGetContext C97078, ImmAssociateContext C97080, ImmGetCandidateListW C97088 (also DefWindowProcW C97770, SendMessageW C97768). Window creation: CreateWindowExW at 60BBA3 stores the window at [125A9C8]; ImmGetContext at 60BC06 saves the context at [12535E8]; ImmAssociateContext(hwnd, NULL) at 60BC1C; flag [12535FC] = 0. Window procedure 60AE90: unhandled messages go to a hook pointer [12535F0] if set (60B2B8), else DefWindowProcW (60B2F6); on WM_CLOSE (60AF7A) it re-attaches the saved context (60AFBF), releases it and destroys the window. The game's text input: setup near 491856 installs the hook 491EB0 (at 49188A) and sends custom message 0x1000, on which the hook re-attaches the saved context (491F58) and sets the flag to 1; message 0x1001 (sent at 492EC9) detaches again (491F11); 4918C0 removes the hook. The hook swallows WM_IME_STARTCOMPOSITION / ENDCOMPOSITION / COMPOSITION and passes WM_IME_SETCONTEXT on with lParam 0 (hides the system IME windows); its own drawing is in 493040 (via 491E10), which also detaches at 4930A5 when bytes +0x109 and +0x10C of its object are set. No per-frame re-detach was found.

Basis: novae (ajane); replaces the session's first inference from the import names alone. An overlay that attaches the system default context while its own field is typed in, and gives WM_IME_* to DefWindowProcW instead of the game's procedure, passes a host test; the real IME in game with that fix is untested

Addresses (build-specific RVAs unless indicated): C97060, C97068, C97070, C97078, C97080, C97088, C97770, C97768, 60BBA3, 125A9C8, 60BC06, 12535E8, 60BC1C, 12535FC, 60AE90, 12535F0, 60B2B8, 60B2F6, 60AF7A, 60AFBF, 491856, 49188A, 491EB0, 491F58, 491F11, 492EC9, 4918C0, 493040, 4930A5, 491E10

Attribution: novae (ajane) · 2026-11-03

Keyboard snapshot and message pump

The game keeps a keyboard snapshot: a 256-byte GetKeyboardState table at 1253600

Evidence: static · Build: steam-5d11de53 · Fact ID: keyboard-snapshot

The game keeps a keyboard snapshot: a 256-byte GetKeyboardState table at 1253600. The message loop 60BC90 (PeekMessage pump) fills it when flag 12535DB is 0 and sets the flag; the input reader (60E04E in the source; input-pump-focus starts it at 60DF50) copies the table under a critical section (lea rcx,[0x1253600] at 60E184, anchor KeyRef) and clears the flag, so it is refreshed once per input cycle on the pump thread and is safe to read from any thread. It can be read instead of calling an API.

Basis: disassembly; novae (ajane)

Addresses (build-specific RVAs unless indicated): 1253600, 60BC90, 12535DB, 60E04E, 60E184

Attribution: novae (ajane) · 2026-10-12

The pump fills the snapshot with a single call through the GetKeyboardState slot C977B0 at 60BD4F, inside the…

Evidence: static · Build: steam-5d11de53 · Fact ID: keyboard-snapshot-slot

The pump fills the snapshot with a single call through the GetKeyboardState slot C977B0 at 60BD4F, inside the critical section 1255E98 and only while [12535DB] is 0, so replacing that slot (a data write, no code patch) decides what every reader of the snapshot sees. The slot's only other caller is 5A5587 (UI code, role not read), which would see a wrapper too.

Basis: disassembly of 60BD20..60BD5E: lea rcx,[1255E98], call [EnterCriticalSection] at 60BD39, cmp byte [12535DB],0 / jnz, lea rcx,[1253600] at 60BD48, call [C977B0] at 60BD4F, setnz byte [12535DB]; RIP-relative reference scan of the code sections (two callers); novae (ajane)

Addresses (build-specific RVAs unless indicated): 60BD4F, C977B0, 1253600, 1255E98, 12535DB, 5A5587

Evidence: verified · Build: steam-5d11de53 · Fact ID: input-pump-focus

All keyboard and mouse reading happens in the message pump 60BC90, and its focus byte ([sysobj+30], written at 60BDB8 from GetForegroundWindow() == [125A9C8]) gates it: when the byte is 0 the game ignores the keyboard, clears the mouse delta and stops re-centering the cursor, while the keyboard snapshot keeps refreshing. Evidence: verified · Build: steam-5d11de53 · Fact ID: input-pad-unfocused

Evidence: verified · Build: steam-5d11de53 · Fact ID: input-focus-gate-in-game

Making GetForegroundWindow return another window while an overlay is open (by swapping its import slot C97808, no code patch) makes the game ignore keyboard and mouse in the HQ and in missions; restoring it on close with the cursor set to the window rectangle's center gives no camera jump. The message-pump thread never blocks: its loop 60B8F0 (thread object vtable EDFF80, vtable0 = 60B8F0

Evidence: verified · Build: steam-5d11de53 · Fact ID: input-pump-thread-busy

The message-pump thread never blocks: its loop 60B8F0 (thread object vtable EDFF80, vtable[0] = 60B8F0; it calls the pump 60BC90) keeps one logical core busy at all times, 99.7 % busy in game, almost all of it in Windows code (its Sleep(0) and message calls), 30.5 % of the process's CPU cycles in the recording. The thread object is built by 60B4D0 and created suspended by 5BAD60 with start routine 5BADE0. The game-code samples in this thread were only in 60B8F0 and 60BC90.

Basis: novae (ajane); one recording, one setup

Addresses (build-specific RVAs unless indicated): 60B8F0, 60BC90, EDFF80, 60B4D0, 5BAD60, 5BADE0
