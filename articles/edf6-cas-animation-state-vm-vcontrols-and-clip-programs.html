EDF6 CAS animation controller: VControls, states, transition programs and IK

EDF 6Game technical referencesAnimation and state machines
Technical reference · Source-derived; evidence grades and build restrictions described in article; no new EDF runtime

The EDF6 animation system is more than a list of named clips. A .CAS file combines an embedded CANM6 clip container, independent animation groups, named controller variables and compact programs that assemble the pose each update. This account is based on exact-build code analysis and a multi-file parse census, not on new in-game animation testing.

Container and named state identity

In the studied Steam build (steam-678ccb46) a CAS header is 0x30 bytes. All 323 CAS files in the original sampling subset used version 516 (0x204), with an embedded CANM, TControls, VControls, animation groups and bone-name references. The EDF6 instruction format is 13 32-bit words (52 bytes), unlike the earlier 9-word form in CAS 512. Strings are terminated UTF-16LE; most record-local offsets are relative to the referring record.

A TControl is a 12-byte, named ordered sequence of CANM clips, not a bone channel. Its length is the sum of clip durations; sampled files included valid empty TControls. The VControl records (20 bytes) supply float, int or matrix variables; the game finds inputs by name, including v_move_x, v_aim_target and weapon- or vehicle-grip IK targets. Changing a variable name can sever the engine's intended input connection. A separate CAS BoneList resolves node names against the model; a missing node can produce an initialization message.

Each AnmGroup owns its own node/state list. Code selects groups and nodes by name and changes them using SetPlayedAnimationID(group,node,flags). main and weapon are examples; their names are not arbitrary metadata.

Node timing and cross-fades

Record Observed native behavior
Animation node (0x24 bytes) Holds state name, default and source-state transition records, and three programs: entry, pose and post-skeleton IK
End kind 0 Never expires; loops
End kind 1 Uses explicit float end time
End kind 2 Uses the combined duration of a TControl selected by TControl index, not by CANM clip-name order
Transition (0x20 bytes) Includes source-state match, fade time in frames, optional program and a start-time mode
Crossfade start mode 2 Preserves current playback phase rather than unconditionally resetting it

The source's 375-file census counted 6,037 kind-2 nodes, 577 kind-0 nodes and ten kind-1 nodes. A separate 323-file verification found 346 false out-of-range references if kind-2 end times were misread as CANM clip-name indices. This is a concrete example of two valid index spaces inside the same asset.

What the tiny VM actually does

A program is a count plus an instruction-array offset. Its native opcodes do not provide a normal branch/loop language: instructions execute sequentially, while node transitions provide state control. Programs run at different phases:

  1. The global controller program runs after group times advance.
  2. Entry parametric1 and transition programs run when a node is selected.
  3. parametric2 samples/blends the pose; group references can contribute more poses.
  4. The game updates bone/world matrices, then parametric3 supplies IK corrections.
Opcode family Operations found in the source
0–5 Sample a TControl, normalized samples, two/three-way blends, additive sampling
6–11 Rotation compose/difference and weighted blends (some defined but not seen in sampled files)
12–22 Float assignment, arithmetic, interpolation, clamping, magnitudes
24–28 Integer assignment and arithmetic
30, 31 Aim constraint and two-bone inverse kinematics
32 Run the active node's post-update IK program
33 Send a user callback to game code, e.g. weapon hand reattachment

These are VM opcode numbers, not portable commands for arbitrary CAS versions. The source documents a real ignored opcode 35 and invalid operand combinations that can crash the game. The embedded CANM's own BoneList is not proven interchangeable with the CAS BoneList.
