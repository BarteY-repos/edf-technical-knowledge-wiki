Per-category loot descriptor layout

Evidence: static · Build: steam-5d11de53 · Fact ID: dropitem-category-descriptor-code

+0x1D0 + category*0x290 is a per-category descriptor (0x290 bytes, 4 categories) with a body description copied into each crate's physics body. It is built in code, not loaded from data: the init 198260 loops over the 4 categories (19829C, 1983CF), makes a shape with 7232A0 from a per-category vector (constants EE7870 for categories 0, 1 and 3, EE7850 for category 2; 1982C8..1982E8), stores it at desc-8 and desc+0x08, and writes the body constants, among them desc+0x00 = 0x1D (198397), so every crate category has the same collision filter info, layer 29 (physics-havok.md#crate-body-descriptor-init). The source's render node pointer +0x30 and dirty flag +0xD0 were not re-read.

Basis: 198260 read with fn.py; settles the conflict with physics-havok.md#crate-body-descriptor-init (the layer is a constant, not data)

The pickup crate is DropItemManager::Unit, not BoxObject

Evidence: static · Build: steam-5d11de53 · Fact ID: crate-class-unit-not-boxobject

The pickup crate is DropItemManager::Unit, not BoxObject. BoxObject (vtable EC59A8; 0x150 bytes per that note, not re-checked) is an xgs::game::SceneObject (bases SceneObject, enable_shared_from_this<SceneObject>, xgs::umbra::Object), and its vtable is referenced from one place only (48918A, in BoxObject's own code), never from the DropItemManager code; the Unit vtable is referenced at 198A60 (between the spawn method 198640 and its unit-creation call 198B22) and 19AAF5 (destructor 19AAE0), and the pickup check 198E90 walks the manager's list of these units. An earlier note that called BoxObject the crate (now the superseded line boxobject-is-pickup-crate in map-objects.md) is answered by this; what BoxObject is for is unknown. Its slot [0] 489380 is not a constructor, as that note says, but a transform refresh (it reads [rcx+0x120]+0x170 through 646370 into +0x70, the helper the crates use too).

How many crates a kill drops is a running total, not a roll per kill

Evidence: static · Build: steam-5d11de53 · Fact ID: drop-rate-accumulator

How many crates a kill drops is a running total, not a roll per kill. The drop routine 2DB300 reads the object's game_object_drop_item (key EAC970) and passes its second and third values (2DB355, 2DB34F) to 198540, which hands them to the spawn method 198640; there the third value is added to the manager's float +0xA70 (1986B6), and while that total exceeds 0.947 (EE63F8; test at 19870D, loop back at 198C1D) 0.947 is taken off and one crate spawns, unless the field already holds the limit (198757, dropitem-field-limit): the subtraction comes first, so a crate due at the limit is lost. The total is one float for the whole manager, shared by every kill; only the throw direction is random (the generator at +0xA78: 0-9999 x 0.0001 x 2π x 0.5, then its sine and cosine, likely a half angle for a rotation).

Basis: fn.py reads of 2DB300, 198540, 198640 (to 198C60); 0.947 read with File_Storage/Logs/catalog/exe_floats.py

Addresses (build-specific RVAs unless indicated): 2DB300, 2DB34F, 2DB355, 198540, 198640, 1986B6, 19870D, 198757, 198C1D, EE63F8

End-of-mission loot roll

Collecting a crate only counts it (pickup-collect)

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-roll-entry

Collecting a crate only counts it (#pickup-collect); the weapons and armor are chosen at the end of the mission by 1991D0 (rcx = the manager), reached from a script native stub 3E3150 (mov rcx,[125ABD8]; jmp 1991D0, just before ApplyResult 3E3160) and from the network result handlers 60E80 / 60F40. It seeds a local Mersenne Twister (624 words, 0x6C078965) from the global LCG at [1192BC0] and rolls weapon boxes = min([mgr+0xA90] + [mgr+0xA88], [mgr+0xAD8]) and armor boxes = min([mgr+0xA94] + [mgr+0xA8C], [mgr+0xADC]); online (save row [save+0x38] with a nonzero +0x5C, as in 19A6E0) +0xA88 / +0xA8C are first rebuilt as the sums of four {weapon, armor} pairs at [save+0x2457C]. The results go to the record vectors +0xA98 and +0xAB8 (#dropitem-loot-records). +0xA90 / +0xA94 and the caps: #loot-failed-mission-kept, #loot-roll-caps-spawned.

Basis: disassembly (fn.py 1991D0, --xref 1991D0)

Addresses (build-specific RVAs unless indicated): 1991D0, 3E3150, 60E80, 60F40, 1192BC0

Weapon and armor crate spawn caps

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-roll-caps-spawned

The loot roll's caps (#loot-roll-entry) are spawn counts: [mgr+0xAD8] / [mgr+0xADC] count the weapon / armor crates spawned (the spawn method 198640 increments +0xAD8 at 198B82 when the picked kind is 0, +0xADC at 198B90 when it is 1; health crates are not counted). Loot retained after failed missions

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-failed-mission-kept

Boxes kept after a failed mission: [mgr+0xA90] / [mgr+0xA94] (#loot-roll-entry) are written only by the Mission Failed result screen's constructor 54BE90 (built by 54BDE0; text keys MissionFailedResult_weapon, _armor, _tortal). It calls the tally 199120 (mission-flow.md#result-tally-retention), stores its kept-plus-earlier totals into +0xA90 / +0xA94, then zeroes the collected counters +0xA84..+0xA8C and the loot record vectors. The tally keeps trunc(boxes collected x f) with f by [[125AB30]+0x4C]: 0 -> 1.0 (EE6430), 1 -> 0.75 (EE63AC), 2 -> 0.5 (EE633C, also any value above 4), 3 -> 0.25 (EE62D4), 4 -> 0. With that index the difficulty (#loot-roll-level-window reads it as such): Easy keeps every box, Normal 3/4, Hard 1/2, Hardest 1/4, Inferno none. Its output: +0 / +4 weapon / armor boxes collected, +8 / +0xC kept, +0x10 / +0x14 kept plus +0xA90 / +0xA94. The path from this screen to the roll 1991D0 was not read.

Weighted loot allocation among player classes

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-roll-class-share

1991D0 deals each box to one class, box by box, by weight: every class starts at {weapon 100, armor 100}, and the class of each local player ([save + player*0x3E60 + 0x6D4C], players [save+0x2459C]) is set to {600, 250}. With four classes and one player, a weapon box goes to the played class with chance 600/900 (2/3) and to each other class 1/9; an armor box 250/550 (about 45%) and 100/550 (about 18%) each. The class count is [[save+0xF8]+4]. Armor goes out as records {0, class, boxes}, which 199D50 adds to [save + class*4 + 0x6D24]; weapons as records {1, weapon row, ..., 8 star bytes at +0xC}, whose star bytes 199D50 merges as a maximum into the save's entry for that row ([save + row*12 + 0xEA10], flags at +0xEA0C: bit 0 owned, bit 2 set when newly owned).

Basis: disassembly (1993A0-1996E1, 199D84-199DE7); the per-player armor counts after 199E00: player.md#armor-box-counts

Addresses (build-specific RVAs unless indicated): 1991D0, 1994A1, 199D50

ModeList level window for loot drops

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-roll-level-window

The level window of a drop: 1991D0 reads [low, high, spread] = ModeList[mode][6][difficulty][2] of defaultpackage/config.sgo (file-formats.md#modelist-drop-level-values; the mode node at [save+0xF0], difficulty [save+0x4C]) and the mission's place t = [save+0x48] / ([[save+0x178]+4] - 1): the mission's row index in its list over the row count less one (the list's fourth value plays no part). center = low + (high - low) x t, w = max(0.05, (high - low) x 0.05); a weapon is a candidate when center - spread (not below 0) <= its level <= center + w, the + w only for weapons with star stats (nearly all). In shown levels (x 25), main offline Inferno runs from 25-52 at the first mission to 75-102 at the last, Hard from 0-4 to 43-52.

Basis: disassembly; checked against the JP wiki in #loot-roll-level-window-check

Addresses (build-specific RVAs unless indicated): 1991D0, 19978B, 199848, 8B0E0, 8B644

Weighted weapon selection and star values

Evidence: static · Build: steam-5d11de53 · Fact ID: loot-roll-stars

Pick and stars 8B590: each of a class's weapon boxes draws one candidate with weight = the row's rarity (1.0, or 2.0 for 36 Pack 1 rows, which so come twice as often), from the uniform random 8F410. Each star stat then gets s = min(5, floor(6 x r^e)), r uniform in [0, 1), e = b + max(0.3, 0.7 + d), d = (level - center) / w, times 0.3 when the level is above center; b = 0 for a class a local player plays, 0.5 for the others (fewer stars). When s = 5 and the level is not above center, a second roll adds floor(6 x r^(3.25 + 2.5 b)), so up to ☆10; s is then capped at the stat's top star (file-formats.md#weapon-table-loot-columns). Candidates below center thus come with more stars. The power function is 9C8276 (the call in combat.md#credit-reload-merit-compression).

Basis: disassembly; constants read with File_Storage/Logs/catalog/exe_floats.py (EE6234 0.05, EE633C 0.5, EE62EC 0.3, EE638C 0.7, EE65B4 6, EE6538 2.5, EE656C 3.25); not checked in game

Addresses (build-specific RVAs unless indicated): 8B590, 8B63B, 8B81E, 8B89F, 8B8ED
