EDF4.1 objects on EDF6 multiplayer: native identity and a custom per-object event channel

ConversionEngine RE & NetworkingNetworkingEDF 4.1EDF 6
Technical reference · Source-reviewed exact-build native identity semantics + custom event envelope; pure C++ 36 checks PASS; multiplayer runtime pending

Separate the native object network from the mod's messages

In the analyzed target EDF6 build, a script-spawned object receives a native NetworkObject identity. All participating machines execute the mission script, so all can construct the object; the host/owner is then authoritative for the state that needs correction. The retained R9 source describes per-object position/target/damage/kill replication and generation of child identities from a parent's identity.

For a boss made of spawned panels or child turrets, a child is not safely identified merely by its pointer or its name. The native child identity registration consumes a uint16 index, uint16 sub pair under a particular parent hash. The custom adapter tracks these pairs per parent control block to reject duplicates; newly created children can be held with weak references until the parent itself has a registered native identity. This preserves the difference between constructing a local child object and making it recognizable to remote peers.

The same source also defines a mod-provided small-event channel that reuses the object's existing network transport but is not part of the original EDF6 protocol. The custom tag is 12. Stock base GameObjectBase event types are described as 0–3; vehicle events can use 4–5, and other mod features may use 13/14/15. Tag 12 is a choice scoped to the reviewed environment, not guaranteed free in all installed mod combinations.

Wire format: 24-byte header

The custom payload begins with this little-endian Header, followed by a variable-length event body:

Offset Type Field
+0x00 u32 Magic 0x4E313445 (E41N in little-endian byte order)
+0x04 u16 Version, currently 1
+0x06 u8 Event kind; 0 is invalid
+0x07 u8 Payload byte count
+0x08 u64 Random process/sender identity; 0 invalid
+0x10 u32 Sender's sequence; 0 invalid
+0x14 u32 Reserved; required to be 0

The maximum body is 192 bytes (total message maximum 216 bytes). The decoder rejects invalid magic, version, kind, zero sender/sequence, nonzero reserved field and any mismatch between actual bytes and 24 + size. A zero-length body is permitted when the kind is nonzero.

This is not reliable retransmission by itself: the format is a validated, bounded event envelope written through the existing game's stream. The source uses the game's stream small-int/tag writer, block writer and per-object NetworkObject send slot 16; it intercepts receive slot 17 only on copied vtables for selected classes. It peeks using the reader's mark/rewind operations and forwards other tags to the preceding receiver. It does not overwrite every instance of the original native vtable.

Reject repeats, stale messages and wrong owners

A per-object gate retains up to eight sender watermarks (sender ID and newest sequence). A sequence is accepted for a known sender only when unsigned new - previous lies strictly between 0 and 0x80000000 — allowing legitimate 32-bit sequence wrap while rejecting repeats and old packets. If the eight sender slots are full, a ninth sender is refused rather than evicting an existing watermark.

The receive path queues events only for guest copies of a registered object. It binds stored state to the object's control block as well as its memory address, so destroying an object and allocating another at the same pointer does not inherit old sequence gates. The per-object queue is limited to 64 events; overflow drops the oldest. Events are drained at the object's normal update; the queue is not evidence that remote gameplay has been applied immediately.

For child objects, a peer that is not yet registered may wait. Registration is retried from the parent update, using weak references; duplicate (index,sub) values under the same parent's control block fail closed. The retained source reserves ranges such as 1 for parts, 0x0100 for spawned children, 0x4000 for batteries, and 0x8000 for Earth Eater-specific spawn identities. Those ranges are conventions of this compatibility layer, not a universal EDF6 name-to-ID schema.

Qualification and practical use

  • Native network ownership and virtual-slot addresses in the retained source are exact-build observations, not portable binary signatures.
  • The 24-byte format, Gate, float bound checking (finite, absolute coordinate at most 1e7) and ID-range constraints are custom code, not stock EDF6 wire messages.
  • A source regression test executes 36 checks of envelope encoding/decoding, reject cases, sequence wrapping, sender capacity and ID-space guards; that proves pure logic only.
  • The R71 audit independently compiled and ran that pure test in Linux. This is not a two-peer Windows/EDF6 multiplayer PASS. Network message delivery, ownership and cross-mod collisions still require live game testing.
  • Before reusing this pattern, ensure tag ownership is negotiated with other modules; preserve the underlying stock receive path and validate object lifetime, authority and child identity.
