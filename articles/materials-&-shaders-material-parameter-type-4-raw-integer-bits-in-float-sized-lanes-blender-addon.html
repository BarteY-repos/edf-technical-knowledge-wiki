Material parameter type=4: raw integer bits in float-sized lanes

This is a native EDF6 MDB material-format finding.

What was observed

In native EDF6 MDB material records, some scalar controls have type=4. Their 4-byte value lanes are raw u32 bit patterns, not numeric IEEE-754 float values.

Confirmed examples:

  • snd_BRDF_Map_Signboard_Pattern.image_split = raw u32 2;
  • Signboard boolean/direction controls = raw u32 0 or 1;
  • snd_BRDF_Map_Build_Window.interior_wrap_count = raw u32 4.

Why a float-only reader is deceptive

The byte pattern for integer 2 is:

02 00 00 00

If those bytes are interpreted as a float32, the displayed numeric value is approximately 2.8025969e-45.

If a tool later writes the numeric float 2.0, the bytes become:

00 00 00 40

That is a completely different value to the game.

Useful test vectors

Intended raw u32 Native bytes (LE) Same bits interpreted as float32 Wrong bytes if saved as numeric float
0 00 00 00 00 0.0 same
1 01 00 00 00 ~1.4012985e-45 00 00 80 3F (1.0f)
2 02 00 00 00 ~2.8025969e-45 00 00 00 40 (2.0f)
4 04 00 00 00 ~5.6051939e-45 00 00 80 40 (4.0f)

Important nuance: untouched round-trip vs editing

A float-only implementation may accidentally round-trip an imported type-4 value bit-exactly if it reads the 32-bit pattern into a host float and later writes the exact same value back without editing. That does not make type 4 a float semantic.

The dangerous operations are:

  • interpreting it as an ordinary numeric float;
  • emitting numeric float 1.0, 2.0, 4.0, etc. in a type-4 lane;
  • assuming the engine default is always numeric float 1.0;
  • arithmetic on the denormal before writing it back.

The binary distinction is a declared type tag plus a raw 32-bit lane; any external interpretation that turns an integer bit pattern into an IEEE float value changes the stored parameter.
