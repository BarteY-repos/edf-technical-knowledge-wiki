EDF 4.1 R1D: identity and semantic dedupe rules

EDF 4.1Maps & NavigationCollision & Physics
Technical reference · Native source-corpus and exact oracle, offline reconstruction only; no EDF6 in-game runtime tests

At a glance

What this page answers: Collision-body identity, MAPO placement identity and a generated NAV carve footprint are three separate notions of 'the same object'.

How to read it: Read each negative deduplication test against its frozen NW_HILLYCITY_LIGHT source corpus. A matching mesh or transform does not automatically justify merging placements.

Evidence boundary: The rejected alias rules are bounded source findings. They neither prove that Havok has no aliases elsewhere nor close the still-open R1D reconstruction.

Scope: the frozen R32-selected NW_HILLYCITY_LIGHT source group/placement corpus. Evidence: exact parsed source records and offline negative audits. The absence of an alias in this corpus is not a universal claim about Havok across all EDF assets.

Why identity checks matter

An apparently equivalent collision shape may not be an equivalent placement, source asset, MAD body, MAPO component or carve footprint. Historically, a reconstruction of the 4,971 footprint target might have included some source-backed alias or deduplication rule. The latest exact audits rule out several simple explanations.

The body-role audit covered 1,795 source body rows in selected groups and 710 passing max_xz >= 5.75. Among the 479 active body names, all inspected non-name Havok role fields were uniform (including motion type, broadphase metadata and collision response defaults); therefore this class of metadata is not a useful discriminator in the audited population.

Original R100 selected-group identity census — 65-group source table

A direct recount of the preserved R100 machine-readable JSON (EDF41_R1D_SELECTED_GROUP_MULTIBASE_PROVENANCE_2026-11-15_R100.json) reveals a qualification missing from the accompanying short R100 START_HERE description: the text says every selected group has one signature, but the actual 65 all_groups rows contain 63 one-signature records and two zero-signature records. The source audit script uses by.get(g,{}) for a group without an observed resolved MAPO slot, explaining how a zero-length signature list can appear without creating a multi-signature group.

  • 63 distinct selected groups have one captured (base_ref, collision_ref) pair each. Every observed pair has exactly one candidate MAD prefix in this retained dataset.
  • 2 groups have zero captured pairs: sk_bd3020_a01_hk and sk_bd3020_zparts01_hk. They were ranked into the selected group set, but this R100 record cannot establish their placement-local base/collision signature. Do not infer that they lack assets or physical geometry in the game.
  • 0 groups show more than one captured pair. This is evidence against placement-local alternate signatures where a signature was actually captured; it is not a 65/65 uniqueness proof.
  • The slot_occurrences field sums to 11,988 across the 63 resolved group records. It counts sampled resolved MAPO slot occurrences, not distinct MAPB placements, active rigid bodies, or the 4,971 carved footprints; these denominators must not be mixed.

Semantic duplicate classes: the strict versus FixB boundary

47 source-semantic duplicate-shape excess instances decompose into two concrete families:

  1. Strict resolver family: nw_hct_koujihanba1f1_hk ↔ nw_hct_koujihanbarf1_hk; 24 excess instances from 8 distinct semantic shapes over T2 placements 189/190/191.
  2. FixB resolver family: nw_enkeibld2020_01_hk ↔ nw_enkeibld2020_05_hk; 23 excess instances from one semantic shape class.

The R32 reconstructed 4,994 → 4,971 population uses only the naturally scoped 23 FixB removals. Extending deduplication globally to include strict groups would remove another 24 and change the observed population; removing only 23 of those 24 is a count-fit rather than a source-derived rule.

A pre-ranking deduplication of the FixB class can choose either Enkei 01 or 05 as the owner and still preserve 65 groups / 1,405 placements / 4,971 footprints. But both possible owners produce identical complete footprint geometry, SHA-256 315f4be8d53b90bc2d7237755d296a163e50a14e17178b0122d4b30f152b373c. Thus source-body naming/ownership changes do not create an alternate R1D carve geometry through this mechanism.

Source-qualified group membership, base identity and placement identity

An identity-preserving conversion should track group prefix, MAPO base/collision pair, MAPB parent and exact transform, MAD body identity, and source shape semantics separately. Never alias across two different types of identity just because strings or geometry appear similar. The current negative audits significantly narrow the search for a historically compatible 4,971-footprint geometry, but do not recover the original historical filter or HKT bytes.
