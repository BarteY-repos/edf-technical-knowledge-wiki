Map RMPA — binary format and conversion profiles

ConversionMaps & NavigationMapsEDF 5EDF 6
Technical reference · Maintained converter source + historical native profile comparisons (not fresh runtime)

Scope: map.rmpa stored inside a map container, not mission-owned MISSION.RMPA, nor the unrelated RMPA payload embedded in weather MAE. Cross-game map-RMPA data requires structural conversion, not a header-version edit. These measured recipes target particular native EDF6 map families.

Main file and section headers

The retained converter/.../rmpa_tool.py starts its EDF6 output with the four bytes 00 50 4D 52 (\x00PMR), a big-endian version 1, and a 0x30-byte main header. Section-presence and section-offset pairs follow in fixed order:

Main header Section / meaning Constructed profile
0x08, 0x0C Routes presence and absolute header position 1, routes at 0x30
0x10, 0x14 Shapes 1, computed aligned offset
0x18, 0x1C Camera 1, computed after shape data
0x20, 0x24 Spawns 1, computed after camera

Each section has a 0x20-byte header. Important fields include a string-table relative pointer at section +0x08, record/group count at +0x0C, and records relative pointer at +0x10. The route section additionally carries the overall waypoint count at +0x14 and its waypoint base at +0x18.

Routes and waypoint records

The measured target route records are laid out as follows:

Record Size Fields / offsets that matter
Route group 0x18 Name length/pointer, waypoint count, waypoint-index list pointer, back-reference to waypoint table
Waypoint 0x30 +0x00 ordinal, +0x04 next-link count, +0x08 next-link pointer, +0x0C group/global id, +0x14 name reference, +0x18…0x20 position float3, +0x2C metadata/extras reference
Extra metadata entry 0x10 Two little-endian relative string offsets at +0x08/+0x0C
Waypoint-ID list element 0x04 Big-endian waypoint ordinal; list is aligned to 16 bytes

The waypoint metadata refers to rmpa_float_WayPointWidth and -1. The little-endian offsets in extra entries are a genuine exception within an otherwise big-endian file. Ordinary string refs are relative to the record/field scheme chosen by that section; never assume the whole archive uses one global base.

The source profile writes waypoint records from 0x50 and deliberately places the extras after (and partly overlapping the tail of) the waypoint table: extras_base = waypoint_end - 0x30 + 8. The canonical writer serializes extras before waypoint rows so subsequent row writes preserve the intended overlap. Any refactor that writes them in the opposite order must prove it generates the same bytes.

Shapes, camera and spawn records

The measured move_limit shape uses a 0x14 group record, a 0x30-byte shape record, and a 0x5C shape-size body. Its first source rectangle dimensions are preserved from the EDF5 shape data; the target shape header introduces map-specific integer members that must be supplied separately. The camera section may exist as an empty 0x20 header.

A spawn record is 0x34 bytes and includes global id, position float3, look-at float3, name and a relative trailing reference. Strings are stored near the end as UTF-16BE, preceded by a two-byte zero prefix; their offsets are position-sensitive.

Known, explicit per-map parameters

These values are from the retained maintained converter's paired-profile comments and code. They are examples of already measured target profiles, not an algorithm to derive them from arbitrary EDF5 files.

Profile gid_base spawn_gid_base Shape record members (+0x14,+0x18,+0x1C)
CAVE501 4 0x5B (3, 0x474, 0x58)
CAVE503 4 0x30 (0x0A, 0x42C, 0x2D)

Both profiles use fixed shape entries +0x0C=9, +0x10=0x310, +0x20=1, +0x24=0x30, +0x28=1, +0x2C=0x54 in this writer, with the original rectangle dimensions written as big-endian floats. Some maps require an extra EDF6-only waypoint and specific coordinate deltas, supplied explicitly as parameters rather than guessed from source topology.

A reliable conversion/validation approach

  1. Parse actual EDF5 route/shape/spawn records rather than copying bytes across generations.
  2. Specify the target native profile or collect it from a paired EDF6 sample: global-id bases, extra waypoint, coordinate deltas and shape parameters.
  3. Compute aligned section positions, preserve the endianness exception in waypoint extras and recompute all relative offsets after insertion.
  4. Bounds-check section headers, waypoint tables, strings, next-link lists and spawn tables. The retained validate_edf6_rmpa performs these checks for its measured scope; it does not simulate mission AI or guarantee target gameplay.
  5. Validate in the actual map runtime when claiming floor, navigation, spawning or camera parity.

The old bare assertion “RMPA source values were missing” was too broad: the concrete CAVE501/CAVE503 writer profile is recoverable from the Library. What remains unknown is a general algorithm for arbitrary source maps and the full external native paired asset corpus, not the constants in these two profiles.

Evidence: retained first-party rmpa_tool.py consolidating EDF5→EDF6 map converter and validator (including CAVE501/CAVE503 profile comments), plus the historical 12 August 2026 RMPA loader/validator handoff in R6_ALL_HANDOFFS_CHRONOLOGICAL_FULLTEXT.md. Do not confuse dated early collision hypotheses from that handoff with later collision authority.
