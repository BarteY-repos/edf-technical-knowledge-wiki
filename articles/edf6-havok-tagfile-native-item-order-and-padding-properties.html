EDF6 Havok tagfile item order: object closure, 1024-element chunks, string sharing and padding

EDF 6Game technical referencesFile formats / serialized graph
Technical reference · Source analysis only (unless a source fact is contributor-verified); no new EDF runtime test

EDF6 Havok tagfiles are indexed object graphs. Reproducing a native tagfile requires more than emitting each object's fields in any convenient order. The studied files use an item numbering and payload traversal convention that can change every downstream ITEM reference if one reference is serialized too early.

In the native source census, ITEM 1 is the root. Referenced pointer targets enter an object queue in discovery order. After an object, the writer emits what is reachable from it without crossing another object pointer (its local closure), visiting member references in serialized type order and base-class members first. For long arrays, the research found 1024-element chunks. Strings are delayed until after the enclosing item and identical string values share one item.

Every payload item is aligned to its declared tagfile type alignment with zero-fill, and the overall DATA section is padded to a 16-byte boundary. An empty array is represented with a null item reference, not a non-null ITEM with a zero element count. Pointers can target the same object from multiple owners; these references must share the same item identity to preserve the graph.

These conventions were reported to reproduce the native byte organization for 316 object SHKTs, eight navmesh test files and 50 map collision HKTs. The counts belong to the researched corpus and should not be generalized to every possible file from different game versions. This page describes native serialized data invariants, not the architecture of any particular third-party editor.
