EDF5 M020_5: frog-roar subtitle key and nonfiring Outpost

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · Runtime-proven / closed

In Destroy the Outpost: Plan A (MissionPack03/M020_5, displayed mission 30), the frog-roar subtitle and the walking base's nonfiring state are distinct game behaviors.

Literal voice cue and confirmed effects

The tested modified runtime used the literal lookup key:

FR_AE065B*  →  *frog roars*

For both retained roar events, direct runtime evidence showed audible frog roar, the intended newly dropped frog reacting, its reaction_roar animation, the visible subtitle *frog roars*, and no Japanese fallback or empty caption panel. Under-floor spider spawns continued as expected. The correction was a targeted localized VOICETABLE cue, not evidence that all similar FR_* keys are interchangeable.

Plan A Outpost is not a combat turret

The walking base's lack of fire in this mission is intentional EDF5 Plan A behavior. The end sequence activates/moves the Outpost, but does not require active gunfire; that belongs to other encounters such as Plan B. Conflating movement with a weapon-state transition would introduce a behavior difference rather than restore source parity.

Other source/game boundaries

The retained compatibility case also involved SetDropBoatCrew, the map weather sequence and exact-object Talk paths for frog01 and frog02. These were independently exercised in the earlier modded runtime evidence. This article records the resulting game behavior, not patch version hashes, installation details or release sign-off. It does not establish byte-identical stock EDF6 scripting.

How the source mission advances and eventually clears

The source-authored M020_5 carrier phase is gated by two invocations of one event handler, not a simplistic wait for all living enemies. Func_6 receives one Factor_AreaTeamObjectCount("敵エリア01", TEAM_ID_ENEMY, 6) registration and one additional no-factor link from Func_7; when its shared invocation count reaches 2, the continuation progresses via Func_23, an enemy count gate of 32, another gate of 25, and eventually Func_3 → SetEnemyGenerator(carrier01/carrier02). The observed historical state in which the visible carriers remained closed while ordinary enemies had died is consistent with a double counter guard that made that continuation unreachable. Merely forcing their door animation open would not reconstruct the source generator state.

A separate failure occurred much later in the historical candidate, after the walking Outpost rose: the original EDF5 Func_87 schedules final Func_1 with special delay 100.0f, whose target high-level sentinel is 100000000.00. The source does not require AiMoveEnd or a fortress route-completion condition to clear the mission. In the erroneous BVM lowering, cuscall1 1 failed to leave its result on the virtual stack, and the following push 0; jmpne became the impossible target guard if ((0 == 0)) return; immediately before MissionEscapeClear_EDF5(). The numeric delay was not the cause. Treat event registration, VM stack/value propagation, runtime state and source mission design as separate diagnostic layers.

The preceding paragraph explains historical failure mechanisms observed and then addressed in successive modified-runtime tests. It does not supersede the later R97 runtime-positive frog roar, subtitle and intended nonfiring Plan A Outpost observations above. In particular, the existence of an older failed mission-clear candidate is not proof that the currently tested R97 composition still has that failure. The large end-event sentinel is a specific source-to-target rule, not a blanket timescale conversion.

Evidence levels: source ASM/AC static control-flow and the actual earlier progression/terminal runtime symptoms (EDF5_EDF6_M020_5_R75_EVENT_COUNTER_OFFLINE_AUDIT_2026-09-05.md; EDF5_EDF6_M020_5_R77_END_EVENT_VM_STATE_AUDIT_2026-09-05.md). Later R97 audio/caption evidence remains the active scoped runtime authority.

Wildcard audio selection and final caption lookup are not the same key operation

The EDF6 Talk path accepts a literal non-verbal cue such as FR_AE065B*. A native binary trace of the audio/talk-variation resolver (EDF+0x5DABF0, related replacement code at 0x44E90) shows the star being resolved through an eight-entry A–H table for concrete playback variants. The examined E503 frog-object initialization reads game_object_talk_setting and an object talk-variation ID at object +0x464; for the relevant leader frogs, the sampled variation count yielded A/B/C audio variants. These are original recorded behaviors for the examined build, not general rules for every voice cue.

The final caption resolver was subsequently traced independently: the two frog roar calls arrive at EDF+0x7B17F0 with the literal key FR_AE065B* (call site near EDF+0x5DD5CA), not with a suffixed A–H key. This difference explains a failed, apparently plausible compatibility test: adding eight empty FR_AE065BA–FR_AE065BH caption records did not remove the unknown-key message. The native EN VOICETABLE itself contains other valid literal-star caption keys such as AM045B*, AM049B* and AL002B*, without parallel A–H caption rows. Never infer caption lookup spelling directly from audio variation resolution.

Three native ways to express a roar have different semantics

Native script path Audio Reaction / animation Caption behavior and identity boundary
Talk_AddSingle(frog, "FR_AE065B*", "reaction_roar", 0) Yes Yes, chosen object Exact-object Talk path; a missing literal caption key showed the unknown-key fallback
AppealAnimation(frog, "reaction_roar") No, in the measured test Yes No Talk/caption entry; animation alone is not equivalent to a roar
Talk_AddEnemies(1, "FR_AE065B*", "reaction_roar", 0, 0) Yes, observed Yes, observed No caption panel in the first-roar test, but selects from an eligible enemy pool, not the named frog01 object
frog.PlaySe("FR_AE065BA") plus AppealAnimation Native object-position sound method and animation are independently evidenced Script can request it A proposed fixed-variant diagnostic; not a runtime-qualified replacement for the original randomized exact-object path

The native Talk_AddSingle callback (0x1801BB720) and Talk_AddEnemies callback (0x1801BB190) enqueue through distinct routines (0x1805D51C0 versus 0x1805D3510) and differ in a callback-side discriminator byte. In the first-roar test the group route preserved audio, animation and subsequent spider spawning while suppressing the panel; this positive observation does not make group selection equivalent to exact-object selection at the second roar. The final accepted mission instead deliberately retains both original exact-object calls and provides a literal-star *frog roars* caption.

A native special string ***no_subtitle*** is present in the tested Talk presentation code near EDF+0x5DD580: its comparison can bypass normal caption construction. But inserting that text into the experiment's appended VOICETABLE record still produced an empty 「」 panel at runtime. The exact content-loader/field-materialization explanation was not proven. A native sentinel branch observed in disassembly therefore must not be advertised as an accepted content-side solution without a corresponding positive runtime observation. By contrast the final visible *frog roars* caption was verified at both events.

Crew-construction API is a separate source-parity finding

In the examined exact-pair EDF5_NEW_SCRIPT corpus, 16 DropBoat crew sites across M020_5, M023, M034, M044 and M079 use global SetDropBoatCrew(...); none uses the object method .DropBoat_SetCrew(...). Replacing three method calls with the native global form in this mission restored that API-level parity but did not fix the subtitle fallback. Keep these as separate conclusions: an object construction mismatch can be real without being the root cause of a caption-resolution failure.
