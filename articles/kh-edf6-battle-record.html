Where the counters live

Achievement SGO variables and kill counters

Evidence: static · Build: steam-678ccb46 · Fact ID: achievement-sgo-variables

Kill counters and stats are variables defined in APP:/ETC/Achievement.sgo (string 1766608), read by CDD30 (load at CDDDF): its AchievementEvent (CE142) and AchievementVariable (CE158) lists; each variable is [name, 'int'|'float', initial] (type strings matched as INT / FLOAT at CE19F / CE296). Vanilla has 91 variables and 39 events (Steam achievement conditions such as Conquest5: AllClearRatio >= 500). Called from D62C0 (startup) and DB580 / DB880 (reset). A name that is not in this file is never counted, whatever the battle record page lists.

Basis: the string at 1766608 and its load at CDDDF read with fn.py; the rest the author's reading

Addresses (build-specific RVAs unless indicated): 1766608, CDD30, CDDDF, CE142, CE158, CE19F, CE296, D62C0, DB580, DB880

Battle record variable map and event arrays

Evidence: static · Build: steam-678ccb46 · Fact ID: achievement-store

The store is at [20B2890]+0x14B50: +0 the head node of a std::map<std::wstring, variable>, +0x18 / +0x28 the event array (0x38 bytes each, +0x34 unlocked byte). Map node (MSVC): +0/+8/+0x10 left / parent / right, +0x19 is-nil, +0x20 key wstring (length +0x30, capacity +0x38), +0x40 type (0 int, 1 float), +0x44 value, +0x50 the indexes of the events that use it. Lookup CFAB0(store, &out, wstring*) compares UTF-16 units unsigned, then lengths (CFB73..CFBAF, std::wstring::compare); not found returns the head node (== [store]).

Basis: the author's static reading ("H"); more event fields: #edf6-achievement-event-fields

Addresses (build-specific RVAs unless indicated): 20B2890, CFAB0, CFB73, CFBAF

Attribution: hajisensai, All Forces source docs/kill-counter-re.md section 1 (round 24), novae (ajane) · 2026-11-13

Original research (pinned): hajisensai — docs/kill-counter-re.md

How a kill is counted

SoldierBase kill message event handler

Evidence: static · Build: steam-678ccb46 · Fact ID: kill-counter-path

The SoldierBase message handler 598FD0 (Ranger, Air Raider, Wing Diver) takes the kill message 0x10000006 (sent by 547C30 to the attacker when the target's HP first drops to 0) and, when soldier+0x340 (the pad object) is set, calls 5499F0(soldier, victim) at 599101; the other caller is EDF6_Berserker_Equipment_Bomb slot 18 (34A8B4). 5499F0 reads the victim's SGO (+0x100) key game_object_kill_counter (549A53) and calls CF640(store, victim, name, 1, true) at 549B50. CF640 looks the name up (CFAB0); not found: nothing happens; found and int (+0x40 == 0): +0x44 += 1 (CF66A), then CF710 checks the events on that variable. So a missing key or unknown name silently counts nothing (EDF 4.1 names such as HectorKillCount, 4LegTankKillCount, MotherShip401KillCount do not exist in EDF6); only soldiers with a pad object (local players, split-screen 2P included) count kills; NPC and vehicle kills do not go through the soldier handler.

Basis: 599101 and CF640..CF672 re-read with fn.py; the rest the author's reading; NPC and vehicle kills inferred

Addresses (build-specific RVAs unless indicated): 598FD0, 599101, 5499F0, 34A8B4, 549A53, 549B50, CF640, CFAB0, CF66A, CF710

Attribution: hajisensai, All Forces source docs/kill-counter-re.md section 2 (round 24), hub read · 2026-11-07

Online, the store is each machine's own and is never synchronizedSource: unverified

Evidence: unverified · Build: steam-678ccb46 · Fact ID: kill-counter-online

Online, the store is each machine's own and is never synchronized; each machine counts only its local players' kills. Whether an enemy's death on a guest sends the kill message to the guest player's soldier was not traced (damage-model.md#online-hit-kill-only bears on it).

Basis: the author's inference ("M")

Reused enemy counter names across EDF versions

Evidence: static · Build: steam-678ccb46 · Fact ID: kill-counter-name-reuse

Some EDF6 counter names are EDF 4.1's names reused for other enemies: DragonKillCount counts EDF6's tadpoles, Carrier1KillCount the teleportation ships, AntHillKillCount the teleportation devices; DeiroiKillCount and GiantAntKillCount exist in both games. So EDF 4.1 units ported with their own SGO counter names land in the wrong EDF6 row or in none (the 4.1-only names are listed in edf41/ui.md#kill-counters-edf41). The lookup of a missing name returns the head node, and CFC30 then reads its uninitialized +0x40 as the type (#battle-record-page).

Basis: the author's reading of both games' Achievement.sgo and the SGOs ("H")

Addresses (build-specific RVAs unless indicated): CFC30

TROPHY.DAT

Saving: 7C2950 saves CFC50(store, buf) as TROPHY.DAT

Evidence: static · Build: steam-678ccb46 · Fact ID: trophy-dat-layout

Saving: 7C2950 saves CFC50(store, buf) as TROPHY.DAT. CFC50 writes the events' unlocked bytes (+0x34) to buf[0..], zero-padded to 0xC8 (200) bytes, then each variable's +0x44 in map order (UTF-16 order of the names) at buf+0xC8+4i, zero-padded to 200 entries. The variable part has no bound check (CFCE0..CFD42) and buf is 0x3F0 bytes on the caller's stack (7C29A1, cookie at +0x480): more than 200 variables overrun the stack. Loading: 8CD510 / 715A90 copy the file to a 0x3F0-byte stack buffer; D00B0(store, buf) asks Steam for the events again (7C4DD0) and reads the variables in map order from buf+0xC8+4i, with no count check and no names (D0179..D01E5).

Basis: the author's static reading ("H")

Addresses (build-specific RVAs unless indicated): 7C2950, CFC50, CFCE0, CFD42, 7C29A1, 8CD510, 715A90, D00B0, 7C4DD0, D0179, D01E5

Attribution: hajisensai, All Forces source docs/kill-counter-re.md section 3 (round 24) · 2026-11-07

Consequence: the save knows positions, not names

Evidence: static · Build: steam-678ccb46 · Fact ID: trophy-dat-adding-counters

Consequence: the save knows positions, not names. A variable added to Achievement.sgo that sorts between vanilla names shifts every later vanilla counter by one slot when an old save is read (no crash, wrong numbers), and again after uninstalling. Names that sort after all vanilla names (vanilla names start with an uppercase letter; All Forces prefixes edf41_, lowercase, which sorts after any uppercase letter) keep vanilla's slots: an old save reads 0 for them; after uninstalling, vanilla counters stay right and the added ones are lost at the next save. Limit 200 variables (vanilla 91).

Basis: follows from #trophy-dat-layout; the author's reasoning, not tested in game

The battle record page (ui::HUiHQHistory)

EDF6 battle record screen

Evidence: static · Build: steam-678ccb46 · Fact ID: battle-record-page

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. HUiHQHistory class construction
  2. Page layout and data sources
  3. History screen update
EDF Knowledge Hub record — original wording — expand (1,143 characters)

HUiHQHistory (vtable 18031A0): factory 893BD0 (pointer at 1803170) allocates 0x780 bytes and calls the constructor 893C40 at 893BF3 (its only caller). The constructor writes a 90-row table on its stack at rbp+0x270..rbp+0x810 (893CD7..8947C3, rows of 16 bytes {const wchar_t* name; u8 format; float factor}; the stack cookie follows at rbp+0x810, 893C69, so the table cannot grow in place). Formats (switch at 895263): 0 %d, 1 h:m:s, 2 %d + StatusInfo_Count, 3 %d%%, 4 %dm; kill rows are format 0, factor 1.0. Pass 1 (8947E0..8949A6, bound 8949A2: cmp r12d,0x5A) looks each row up in the store, hides rows whose name contains KillCount with value 0, and builds that many cells (BattleRecord_Cells, CellBase01|02); pass 2 (894D50..895164, bound 895161: cmp eax,0x5A) labels each from the text table StatusInfo_ + name (894E42, text lookup 7A3500, empty string 1762240 when missing). The table is read at only five places (8947C9 lea, 894D56, 894F72, 894F90, 895263). A row whose name is not in the store reads the head node's +0x40 as the type; the head node (CDD7C, 0x70 bytes) leaves it uninitialized, so such a row may show a garbage number.

Basis: the author's static reading ("H"; their offline audit tests/killcount_native_audit.py checks each site against EDF.dll); an older comment in the source calling 893C40 "the counter table" is corrected by the author

Addresses (build-specific RVAs unless indicated): 18031A0, 893BD0, 1803170, 893C40, 893BF3, 893CD7, 8947C3, 893C69, 895263, 8947E0, 8949A6, 8949A2, 894D50, 895164, 895161, 894E42, 7A3500, 1762240, 8947C9, 894D56, 894F72, 894F90, CDD7C

Achievement event record layout

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-achievement-event-fields

An achievement event (0x38 bytes, #achievement-store) holds +0x08 its name (a std::string, UTF-8), +0x28 the compare operator (0..5: ==, !=, >, <, >=, <=), +0x30 the threshold (int or float by the variable's type), +0x34 the Steam unlocked byte and +0x35 the Epic one.

Basis: fn.py read of CF710

Addresses (build-specific RVAs unless indicated): 20B2890

Attribution: novae (ajane) · 2026-11-13

Unlock event and variable threshold check

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-achievement-unlock-sites

Every unlock goes through the event check CF710(store, variable**): for each event index in the variable's +0x50 list it compares the value +0x44 with the event's threshold, logs Unlock Achievement Request (%ls) (17668C0, via 50F00) and, if not yet unlocked, calls 7C51F0([20B2AE0], name, &event+0x34) (Steam, at CF888) and 7B4E50([20B2AE8], name, &event+0x35) (Epic, at CF8FC); both are called only there, so one ret byte at each entry stops all unlocks (prologues 40 53 55 56 57 41 54 41 56 41 57 48 83 EC 60 and 48 89 5C 24 10 48 89 6C 24 18 56 57 41 56 48 83 EC 50; CF710 ignores their return). Callers of CF710: the counter increment CF640 (CF67C), the setter D0340 (D037C, six uses in UpdateAchievementCounter DC9E0), the load D00B0 (D0208), CF5B0, CF690, CF9C0, D02C0, D0390.

Basis: fn.py read and --xref; with both ret bytes written at load the game booted and played normally (2026-11-13; whether nothing popped is novae (ajane)'s check, pending)

Addresses (build-specific RVAs unless indicated): CF710, 7C51F0, 7B4E50, CF888, CF8FC, 17668C0, 50F00, 20B2AE0, 20B2AE8, CF640, CF67C, D0340, D037C, DC9E0, D00B0, D0208

Attribution: novae (ajane) · 2026-11-13

Steam achievement unlock function

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-achievement-steam-calls

7C51F0 (AchievementUtility::UnlockTrophy) gets the UserStats interface by SteamInternal_ContextInit (1756778) on context 1F76140 (STEAMUSERSTATS_INTERFACE_VERSION012), calls vtable +0x38 SetAchievement and on success +0x50 StoreStats, then queues the name and the +0x34 pointer at object+0x80 (0x28-byte entries) for the UserAchievementStored_t callback 7C4E30. 7C4DD0 (+0x30 GetAchievement) is called once, at D0114; the constructor 7C48D0 registers callbacks 0x44D and 0x44F (17567B8), calls RequestCurrentStats and runs callbacks for up to 1000 ms. EDF.dll imports ten steam_api64.dll functions (1756770..17567B8).

Basis: fn.py read

Addresses (build-specific RVAs unless indicated): 7C51F0, 1756778, 1F76140, 7C4E30, 7C4DD0, D0114, 7C48D0, 17567B8, 1756770

EOS achievements interface initialization

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-achievement-epic-calls

7B4E50 gets the EOS achievements interface lazily (EOS_Platform_GetAchievementsInterface, pointer 17553A0), registers AddNotifyAchievementsUnlockedV2 (17553B8), calls EOS_Achievements_UnlockAchievements (17553B0) with one name and sets *out = 1 at once. The singletons AchievementUtility (20B2AE0) and EpicAchievementUtility (20B2AE8) are made in 7004F0 and freed in 7021F0.

Basis: fn.py read; RTTI .?AVAchievementUtility@@, .?AVEpicAchievementUtility@@

TROPHY.DAT load and Steam ownership queries

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-trophy-load-reunlock

Loading TROPHY.DAT (D00B0) asks Steam per event which achievements the account has (D0114, into +0x34), reads the variables, then runs CF710 on every variable (D0208), so a save whose counters meet every condition unlocks, at every load, everything the account lacks.

Basis: fn.py read; novae (ajane) had seen dozens of unearned Steam achievements pop after loading a save with everything unlocked

Addresses (build-specific RVAs unless indicated): D00B0, D0114, D0208, CF710

Attribution: novae (ajane) · 2026-11-13

Trophy file offsets and custom battle-stat limits

Achievement events and 91 named variables in TROPHY.DAT

Static/offline save editor reading. After 0x14-byte EDF6 save header, TROPHY.DAT stores 39 event unlock bytes from offset 0x14, in Achievement.sgo order: 32 conquest increments Conquest5..Conquest100, four class mastery events (respective armor thresholds 1000, 550, 1000, 1250), Rescue/SuperRescue (5/50 saves) and Medic (healing damage above zero). The 91 named variables start 0xDC in sorted name order, first AirRaiderArmor and last WingDiverPlayCount at 0x244; selected fields include ArmorCount 0x100 and FrameCount 0x160 (60 frames/second). The original editor author byte-diffed 53 slots and found implausible values in some other played-save fields, so computed clear ratios from MST instead. The whole 91-entry map is not verified in runtime.

Screen row cap is tighter than save capacity

Static contributor source-code reconciliation, not fresh executable disassembly. The save's battle-record variable table has 200 slots, but the stock screen has 90 rows and its row-count compare was interpreted as signed 8-bit; expanding beyond 127 visible rows may need an additional UI engine patch even while save slots remain. The reported EDF4.1 port adds 18 prefixed edf41_* counters, with labels in SC/CN/EN/JA/KR and (4.1) marker only for presentation. NestKillCount accepts alternate AntHillKillCount input without merging into EDF6's native AntHill count, while MotherShip401KillCount combines Earth Eater/Brain. Its source guard refuses extensions when another mod already sorts after the first edf41_ key. Signed-8-bit cap is an inference; migration and >127-row display were not game-tested.
