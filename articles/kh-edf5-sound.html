EDF 5 — Sound (community source notes)

EDF 5Community Knowledge HubAudio
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Facts

EDF5 plays all its audio through CRI ADX2 (CRI Atom), statically linked into EDF5.exe with WASAPI output

Evidence: static · Build: steam-5d11de53 · Fact ID: audio-cri-adx2

EDF5 plays all its audio through CRI ADX2 (CRI Atom), statically linked into EDF5.exe with WASAPI output; the music is in the bank APP:/SOUND/ADX/TIKYUUX_MUSIC.ACB, addressed by cue name. The import table has no XAudio, DirectSound or other audio library; MMDevAPI.dll appears only as a string (D16550), and WINMM has 2 imports (waveOutGetNumDevs among them).

Basis: PE imports and strings only; nothing run in game

Addresses (build-specific RVAs unless indicated): D14EB1, D21051, D16550, EC4B80

Attribution: novae (ajane), tools/audio_probe.py · 2026-10-30

Version strings: CRI NcVoice WASAPI/PCx64 Ver.2.28.00 (D14EB1) and CRI Atom Sound/PCx64 Ver.1.61.00 (D21051),…

Evidence: static · Build: steam-5d11de53 · Fact ID: audio-cri-versions

Version strings: CRI NcVoice WASAPI/PCx64 Ver.2.28.00 (D14EB1) and CRI Atom Sound/PCx64 Ver.1.61.00 (D21051), both built Feb 26 2019. The library keeps its CriAtomExRawPcmVoicePoolConfig string (D1C000), so a raw-PCM voice type is at least compiled in; whether the game creates such a pool is unknown.

Basis: strings in the exe; not run

Addresses (build-specific RVAs unless indicated): D14EB1, D21051, D1C000

Every background-music start goes through one function, 4781C0 (rcx = 125AB90+8, the sound controller), which…

Evidence: static · Build: steam-5d11de53 · Fact ID: bgm-play-choke-point

Every background-music start goes through one function, 4781C0 (rcx = [125AB90]+8, the sound controller), which takes the cue name as a string, so one hook there would see each music request by name. It has exactly four direct call sites: 5C9C9, 11B9ED, 3DF44F, 47C221; no other direct call and no jmp to it.

Basis: disassembly with _tools/fn.py over 1000 to C90000; not run in game, no breakpoint or log confirmed it, and an indirect call was not searched for

Addresses (build-specific RVAs unless indicated): 4781C0, 125AB90, 5C9C9, 11B9ED, 3DF44F, 47C221

Evidence: static · Build: steam-5d11de53 · Fact ID: bgm-log-strings

At the first three call sites the code first formats SoundController::PlayBgm::%s %f (EC4C58); the seek path 47C07C formats SoundController::SeekPlayBgm::%s time(%0.3fms) %f (EC4C80) before its call at 47C221. The strings name the class and the two operations.

Evidence: unverified · Build: steam-5d11de53 · Fact ID: bgm-play-convention

Calling convention of 4781C0 at 3DF44F, read from the code and inferred: rcx = controller+8, rdx = the cue as a narrow char* (the wide input that 3DF3B0 gets in rcx is converted by 5BBD60, whose result has the 0x10 small-string check of a narrow std::string), xmm2 and xmm3 = the float at [EE6430], 5th argument = controller+0x20. The log call 27680 between the conversion and the play clobbers neither rdx nor r9, so it is an empty stub in this build.

Basis: disassembly; inferred, not run

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-bgm-seekplay

47C050 is SoundController::SeekPlayBgm (called at 5CC04 and 11BC49): it formats its own log string at 47C07C (#bgm-log-strings), turns the time argument (xmm3) times [EE6790] into an integer start position, and when controller+0x10 is 0 first stops the playback at controller+0x20 (92B4DC) before playing the cue through 47C221 -> 4781C0 (#bgm-play-choke-point), so a seek-play also passes the one BGM hook.

Basis: fn.py read of 47C050..47C15C

NPC voice lines, the pick: 325820(TalkManager, out, object, table name, ..) finds the table in the object's t…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-talk-line-pick

NPC voice lines, the pick: 325820(TalkManager, out, object, table name, ..) finds the table in the object's talk SGO (+0x2C8, 5BDF30) and makes a weighted random pick over its entries (a value in 0..9999 / 10000 times the summed weights). An entry is skipped when its element 3 is 0 or more and the byte TalkManager+0x59+[object+0x2D0] has none of its bits, or when the float TalkManager+0x5C is outside [element 11, element 12]. A table whose element 2 is 1 draws from TalkManager's own generator +0x68, else from a seed argument. Weight 0 never plays: setting an entry's weight to 0 (or removing it) is the data route to silence a line (untested).

Basis: fn.py read of 325820

Addresses (build-specific RVAs unless indicated): 325820, 5BDF30

Talk entry elements (each table entry in a _talk.sgo is a list): 0 voice cue (wide string, AN001V), 1 animati…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-talk-entry-fields

Talk entry elements (each table entry in a *_talk.sgo is a list): 0 voice cue (wide string, AN001V), 1 animation, 2 weight (float), 3 a bit mask (-1 = always), 4 and 5 a range: 3250D0 draws a value between them, adds a params float and scales it to an int count (unverified: a start delay in frames), 6 the reply table name when its type is 3 (a string), else none, 9 and 10 an integer range drawn for the reply (meaning unread), 11 and 12 the TalkManager+0x5C window above. 3250D0 builds the queued line from the pick and 324650 queues it in one of the TalkManager's channels (325010 picks the channel, 329F10 inserts).

Basis: fn.py reads of 3250D0, 325820, 324650; element numbers from the 12-byte SGO value offsets

Addresses (build-specific RVAs unless indicated): 3250D0, 324650, 325010, 329F10

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-talk-line-start

A talk line reaches the audio in 327BB0(line, ..): the frame countdown line+0x60 runs out, the cue (line+0x10, a wide string) is made narrow (5BBD60) and played on the sound controller [125AB90]: 47CBA0(controller, cue, position block from the speaker's matrix +0xA0, handle line+8, -1, 2) when line+0x68 is 0 (a voice placed in the world, inferred from the arguments), else 47C9D0(controller, cue, handle) (unplaced, radio-like, inferred). One hook at 327BB0, or on those two calls, sees every NPC talk cue by name before it plays: the code route to silence chosen lines (untested).

Basis: fn.py read of 327BB0

Addresses (build-specific RVAs unless indicated): 327BB0, 5BBD60, 125AB90, 47CBA0, 47C9D0

So each NPC keeps one voice actor and a cue names one file per letter (as in 4.1, ../edf41/sound.md#edf41-talk-voice-variant, whose placeholder is %s). Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-bgm-callers

The four callers of the BGM play 4781C0 (#bgm-play-choke-point): 5C910 is the dev console command bgm (registered at 6B00B in the command table 699B0, name E90780); 11B940 is mission script (BVM) native 300 PlayBGM (interpreter case 115AAF, call at 115AB6); 3DF3B0 is the AngelScript PlayBgm of the menu and system scripts (registered at 3DD186); 47C1D0 is the cross-fade play (#edf5-bgm-crossfade-stop), which the seek play 47C050 also reaches. Cross-fade and stop: 47C1D0(controller, cue, int frames) fades out the current music (if controller+0x28 hold…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-bgm-crossfade-stop

Cross-fade and stop: 47C1D0(controller, cue, int frames) fades out the current music (if controller+0x28 holds a playback: 476A30(playback, frames), then 6FB40 releases the handle controller+0x20), plays the cue through 4781C0, and sets the new playback's fade-in (+0x30 = 1, +0x34 = frames x 1/60, +0x38 = 0, the start volume). 476A30(playback, frames): frames 0 or less stops at once (92B4DC, state reset), else it sets fade-out (+0x30 = 2, +0x34 = frames x 1/60). Stop callers: console stop_bgm (5CC80), BVM native 301 FadeOutBGM (case 115AC0, seconds x 60) and AngelScript StopBgmFadeout(int) (3DF4C0, frames; it does not release the handle). Cross-fade callers: console cross_fade_bgm (5CA50) and BVM native 302 FadeInBGM (11BA70, seconds x 60).

Basis: fn.py reads; constants EE66A8 = 60.0, EE61FC = 1/60 read from the exe

Addresses (build-specific RVAs unless indicated): 47C1D0, 476A30, 6FB40, 92B4DC, 5CC80, 115AC0, 3DF4C0, 5CA50, 11BA70

47BE20(controller, frame step) (called each frame at 3D7FF0 in 3D7D30) counts the timers controller+0x30 and…

Evidence: unverified · Build: steam-5d11de53 · Fact ID: edf5-sound-update-volumes

47BE20(controller, frame step) (called each frame at 3D7FF0 in 3D7D30) counts the timers controller+0x30 and +0x34 down, eases a gain +0x3C (10% per frame) toward 1 + 0.5 x min(+0x30 / 30, 1) (also blended by +0x34 / +0x38; not followed), raises +0x88 by 0.01 per frame to 1 while +0x34 is 0, and sets three CRI category volumes through 93BD74: category [+0x18] = save +0x1E0 x (1 + 0.5 x (duck - 1)) x gain; category [+0x40] = save +0x1E4 x duck / gain x +0x88; category [+0xB4] = save +0x1E8 (save = [125AB30], duck = +0xC8, #edf5-talk-update-duck). Inferred: +0x40 is the music category, the save floats the volume options, and a mission music change briefly lowers the music (to 1/1.5) while raising the other category.

Basis: fn.py read of 47BE20..47BFC7; constants 30.0, 0.5, 0.1, 0.01 read from the exe

Addresses (build-specific RVAs unless indicated): 47BE20, 3D7FF0, 3D7D30, 93BD74, 125AB30
