EDF4.1 BVM command 3025 — multiply current object HP without changing maximum HP

ConversionMissions & ScriptingScriptingEDF 4.1EDF 6
Technical reference · Source-level command and exact-build AngelScript/native ABI; no fresh runtime

Source command and target gap

The EDF4.1 native BVM command ID 3025 represents MultiplyObjectHealth(Object,float). In the examined source semantics it scales the object's current durability, not its maximum health. Replacing it with SetObjectDurability or a global max-HP modifier changes difficulty, future damage and possibly mission completion.

The studied target AngelScript API had no directly equivalent public helper. Rather than changing BVM bytecode arbitrarily, the compatibility implementation introduces a scoped global script command named:

void EDF41_MultiplyObjectHealth(const ::Object& in, float percent)

For a resolved object, the source's arithmetic is approximately:

new_current_hp = min(current_hp * (percent / 100.0), max_hp)
max_hp stays unchanged

The lower bound is not shown as a generic zero clamp in the examined native implementation. Percent must be interpreted as a percentage, not an ordinary multiplier. An exporter that replaces this with current * percent or updates max_hp is not source faithful. Source code intentionally preserves the target's SSE MINSS behaviour, whose NaN/special-value details should not be reimplemented by casual arithmetic without tests.

Why a global function still depends on native ABI

The registration takes place when the game builds an AngelScript engine, after the normal bulk registration of stock functions. The inherited implementation wraps the outer call site rather than rewriting the bulk registration routine. That allows another module which independently extends that routine to keep its existing registrations.

The exact-build native bridge has a non-obvious C++/AngelScript calling contract: the first script const ::Object& in is carried as a wrapper argument in RDX, while the float uses XMM2; RCX is not the Object parameter. It resolves the wrapper into an engine object/control-block pair and updates only the current-durability field. The resolved wrapper's strong/weak ownership is then released using the expected native shared-control-block semantics.

Blindly changing a C++ function signature, treating the wrapper as a raw object pointer, neglecting the control-block release or calling the registrar before stock commands exist can crash the game even if the printed AngelScript declaration appears correct.

What is and is not portable

The command's meaning — percentage of current HP, capped by max HP, without altering max HP — is the useful cross-game semantic finding. The engine registration vtable slots, wrapper layout and function addresses belong only to the studied EDF6 DLL build, and this release did not rerun Windows/MSVC/gameplay qualification. Treat them as exact-build research, not a general-purpose extension SDK.

Source: EDF4.1 R10 HF4 R9 components/compatibility/src/edf41missioncmd.cpp; the broader mission-pipeline contract discusses where command 3025 appears in source BVM.
