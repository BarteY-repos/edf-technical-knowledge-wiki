EDF archives and resource lookup: CPK, RAB, MARC and CMPL

UniversalFormats & ContainersFile FormatsEDF 5EDF 6
Technical reference · Reconciled native and source research

A game asset has at least three separate questions: where it is found, how its container bytes are decoded, and whether the decoded content has the correct format for the game that reads it. Passing one stage does not establish correctness of the other two.

CPK: finding an asset in the installed game

Studied EDF6 installations use CRIWARE CPK packages. A read-only catalog can inspect TOC/@UTF records to expose virtual paths without extracting an entire installed game. In one observed installation, Root.cpk, Chunk01.cpk, Chunk02.cpk and DX11.cpk supplied 9,717 virtual asset paths. The number reflects that exact installation, not a universal constant.

For compressed entries, the researched path uses direct random access and CriLAYLA decompression in memory. There was an offline-qualified decoder path for literal, backreference and variable-length-code cases, but that qualification did not by itself prove every shipped compressed asset under a Windows runtime. ITOC was not needed for the four observed TOC-backed CPKs; that does not prove it is unnecessary in all CPKs.

RAB and MRAB: embedded resources still have their own formats

RAB/MRAB are resource-container roles. A reconstructed RAB with a valid archive directory can still hold an invalid MDB, texture, SGO or another payload. EDF5 and EDF6 share enough SSA archive grammar for common tooling but not enough to declare every EDF5 archive byte-copy-safe in EDF6. A source-side conversion needs both a valid target container and target-compatible contained resources.

The observed MDB Simple_Clip/high-LOD foliage repair is an example: archive packaging and the material/shader ABI had to be coherent together for a runtime-positive visual result.

MARC: a specific cross-game difference

The compared EDF5 and EDF6 MARC grammar is similar, but a measured map-entry field u1 has different values: EDF5 2, EDF6 0. This is a verified per-profile difference, not permission to add a global offset transform to all MARC records.

CMPL: corrected token interpretation

The researched CMPL token decoder is:

length = (token & 0xF) + 3;
position = token >> 4;

An older interpretation that used the high nibble for length and the low twelve bits for position was superseded. Wrong token interpretation can appear to decompress some inputs while invalidating conclusions about other data.

Virtual paths and cache freshness

Logical asset identity can span multiple archives and optional mod overlays. Paths and registration names need normalized comparison appropriate to the game's resource namespace. A stale TOC or cached catalog can present the wrong apparent resource inventory even if archive parsing is correct. Never silently resolve an ambiguous resource stem to an arbitrary model.

A resource browser should preserve read-only access to the installed archives, report unresolved identities, and keep archive lookup, decompression, native payload interpretation and actual in-game behavior as separately testable steps.

For deeper detail see CPK and CriLAYLA, RAB/MARC/CMPL measured contracts and resource identity/virtual paths.

Diagnosing “the model is valid but the map crashes”

In one checked desert-map conversion, a byte-valid MDB was delivered under a .trb registration and entered the wrong resource loader. Independently, an obsolete CMPL compressor damaged 45/76 model bodies while preserving their first bytes. These demonstrate two separate checks: typed registration must match the payload, and decoded content must be verified in full. See the detailed case study.
