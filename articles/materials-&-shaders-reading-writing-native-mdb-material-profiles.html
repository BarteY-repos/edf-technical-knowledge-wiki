Reading and writing EDF6 MDB materials: native parameters, textures and shader reflection

EDF 6Materials & ShadersShaders
Technical reference · Observed native EDF6 MDB material profile versus shader reflection; shader-guide models scoped

An MDB model contains geometry and a serialized material. The material identifies a shader, stores typed parameter values and refers to texture samplers. A shader disassembly or reflection database tells you what the shader can accept; it does not necessarily tell you which fields a real MDB material contains, in what order, or what the default values are.

This guide answers the practical question: how do you reconstruct a native-looking EDF6 MDB material without silently changing its meaning? All examples below come from sampled native EDF6 map-model MDB files; they should not be generalized to all character or terrain renderers.

A concrete BRDF example

For the observed snd_BRDF_Map_Common material family, the native parameter sequence is:

Position Material parameter Observed TypeByte/SizeByte Meaning
1 diffuse 2/3 RGB material colour multiplier
2 metallic 0/1 Multiplier for packed metallic
3 normal_amount 0/1 Normal-map tangent-plane perturbation
4 roughness 0/1 Multiplier for packed roughness
5 specular_color 2/3 Specular path colour
6 specular_diffuse_blend 0/1 Metallic-dependent specular mixing

Observed native sampler sequence: albedo, normal, param_r_m_xxx_hr.

The reflected parameter sequence for this shader is approximately diffuse, specular_diffuse_blend, specular_color, normal_amount, metallic, roughness—different from the native list. m_instancing_array_stride may also appear in reflection, despite being absent from examined native MDB per-material lists. That makes the reflection data a capability map, not a ready-to-serialize material template.

What metallic and roughness do

For the studied ordinary Common/BRDF packed param_r_m_* path:

float metallic  = saturate(packed.g * material.metallic);
float roughness = saturate(packed.r * material.roughness);
// For the studied _hr packed map:
roughness = saturate(packed.r * packed.a * material.roughness);

The shader’s metallic=1.0 is not sufficient to make the entire object metallic if the packed texture has a dark green channel. Likewise, setting a single Blender roughness slider ignores the R and sometimes A channel contributions. These rules are family-specific: the legacy snd_Map_* reflect/spec texture system is not interchangeable with BRDF R/M.

For other equations including normal decode, cutout alpha and emissive masks, see MDB shading parameters.

Native vector size is not just a shader reflection width

The shader parameter record carries a type and a size in its native material ABI. A generic reflection-driven model tool may know that a shader variable is a float3 yet choose size 4. In observed EDF6 BRDF map profiles, these vectors commonly have type=2, size=3:

Shader Sampled native field Type/size
snd_BRDF_Map_Common diffuse, specular_color 2/3
snd_BRDF_Map_Common_Light light_color 2/3
snd_BRDF_Map_Build_Window diffuse, interior, specular_color 2/3
snd_BRDF_Map_Signboard_Pattern diffuse, light_color, specular_color 2/3

This is an observed profile rule, not a claim that every native EDF6 float3 has size 3. Older shaders also exhibit 2/4 variants. In an importer/exporter, retain imported (name, type, size, order, raw value) metadata when possible rather than regenerating it from a guessed generic table.

Texture registers are not the same as MDB sampler order

An EDF6 shader may bind texture registers in one order, while the native MDB material serializes its sampler names in another. In the sampled native data:

Shader Observed MDB sampler order
snd_BRDF_Map_Build_Basic_NC param_occlusion, dirt, albedo, normal, param_r_m_xxx_hr
snd_BRDF_Map_Build_Window interior_texture, normal, param_r_m_xxx_hr, window_frame_texture, window_normal
snd_BRDF_Map_Build_Para_NC param_r_m_h, param_occlusion, dirt, albedo, normal
snd_BRDF_Map_Build_DirtScroll param_occlusion, dirt, albedo, normal, param_r_m_cm0_hr
snd_BRDF_Map_Signboard_Pattern switching_mask, param_r_m_occ_light, albedo, normal

These are real serialized orders and are not generally alphabetical or register-sorted. Whether the game strictly requires native ordering in every case is not proven. The safe practice when rebuilding a known native profile is to preserve the observed order.

See the full native shader-family reference for multiple sample profiles and their typed fields.

Not every reflected parameter belongs in the MDB

The reflection catalog exposes variables like m_instancing_array_stride and some sys_* values, but they were absent from the examined native per-material lists. Legacy shaders also have real MDB instances where metallic or roughness are omitted although reflection contains those names. Do not invent an entry merely because the shader is capable of consuming it. A native material may deliberately instantiate a subset.

Raw integer parameters: the type=4 trap

Some MDB fields have 4-byte integer bit patterns inside float-sized storage lanes. For example:

Native shader/parameter Semantic value Four bytes (little endian)
snd_BRDF_Map_Signboard_Pattern.image_split u32 2 02 00 00 00
snd_BRDF_Map_Build_Window.interior_wrap_count u32 4 04 00 00 00

Do not write numeric 2.0f as 00 00 00 40 or 4.0f as 00 00 80 40. A float-only editor can sometimes round-trip untouched bits accidentally, but editing/recreating those values as floats destroys the intended integer meaning. Preserve the raw u32 and declared type. See type-4 raw integer details.

Defaults, clipping and transparent surfaces

Generic “new material: every parameter = 1” is not a native profile rule:

  • In a 44-material observed snd_BRDF_Map_Common_Clip sample, alpha_clip=0.5 in 42 instances and 0.3435 in 2. This is a sampled distribution, not a universal default.
  • Signboard.image_split has raw u32 2 in the studied profile; Build_Window.interior_wrap_count has raw u32 4.
  • snd_BRDF_Map_Common_Light.light_color is intentionally HDR and can exceed 1.
  • Transparent classification cannot be based only on names ending in _Alpha, _Clip or translucent_*: legacy snd_Map_Object_Glass can be transparent with its own render layer/priority/flags.

A native Common_Clip foliage texture sk_pShrub003-df.dds demonstrates actual one-bit-alpha BC1/DXT1 cutout usage. This is a useful known-good example, not a requirement that every cutout use BC1.

Constructing a material safely

  1. Identify the exact shader and observed native profile, not simply the shader name prefix.
  2. Retain existing native fields when doing a round-trip: same names, order, type, size and raw bits.
  3. Retain the observed sampler slots and texture identities in MDB order, not just GPU register order.
  4. Use observed defaults for known fields and real material examples; do not fill everything with 1.
  5. Check the vertex declaration/UV channels demanded by the material. A different shader may require tangent/binormal, additional UV streams and split vertices; a name change alone is not a valid cross-game conversion.
  6. Handle opacity, priority/layer/flags, LOD and cutout families explicitly. An LOD companion can retain the same original shader rather than switching to a universal LOD shader.
  7. Classify the evidence: a byte-consistent writer, a native paired file and an EDF6 runtime-positive result are different degrees of confidence.

For unknown profiles, prefer preserving an imported structure over synthesizing a guessed native structure. Reflection is useful for discovery and editor controls; exact native examples are the stronger source for serialization. A generic Blender PBR preview is useful, but not a byte- or rendering-fidelity oracle.

Scope and evidence

These observations are drawn from existing native EDF6 MDB map-model samples and the independently analyzed rendering/material sources; no new EDF6 executable or game-runtime test was performed for this article. They establish observed profile structures and known mistakes in generic reflection-driven preset creation. They do not prove that reordering any parameter or texture slot always crashes the game, nor that every EDF5/EDF6 material shares the Common shader conventions.
