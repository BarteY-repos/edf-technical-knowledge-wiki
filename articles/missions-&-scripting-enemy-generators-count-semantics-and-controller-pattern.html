Enemy generators: count semantics, lifecycle and controller pattern

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · Reconciled

Evidence: shipping MISSION.AC call corpus and source-level API interpretation. Unknown native caps and exact E505 landing-completion signal remain unresolved.

EDF6 exposes several generator-related concepts that must not be collapsed into one generic “spawn limit”. The shipping mission corpus supports a more specific model.

Generator API families

SetEnemyGenerator

Periodic producer:

SetEnemyGenerator(
    slot,
    resource,
    count,
    level,
    unit_interval,
    wave_interval,
    encountered
)

The strongest shipping-AC interpretation is:

  1. emit count units in one group/cycle;
  2. space individual units by unit_interval;
  3. wait for the next group according to wave_interval;
  4. repeat until cancelled/host lifecycle ends.

Shipping comments describe count as the number generated, unit_interval as the interval per unit, and wave_interval as the interval until the next group generation. There is no established explicit total_limit parameter in this call.

SetInstantEnemyGenerator

Finite producer:

SetInstantEnemyGenerator(
    slot,
    resource,
    count,
    level,
    unit_interval,
    encountered
)

The corpus pairs this call with Factor_WaitGeneratorEnd(host, slot), including missions that start one or multiple finite batches and wait for their completion. This is the strongest evidence that the instant form has a natural finite end after the requested batch is emitted.

CancelEnemyGenerator

Cancels one generator slot on the receiver/host. A historical script/helper addresses slots 0..7; this is evidence for that helper only, not proof that every EDF6 object type implements eight functional slots.

Factor_GeneratorEnemyCount is not live child count

This is the highest-value semantic correction.

Factor_GeneratorEnemyCount(N) tracks a generator-object/host population threshold rather than the number of living children emitted by one pylon.

Corpus evidence distinguishes it from live-object counters:

  • missions use Factor_GeneratorEnemyCount while operating multiple nest/carrier/generator hosts;
  • a retained source comment explicitly distinguishes whether a Mother object is counted as a generator;
  • missions may combine Factor_TeamObjectCount(TEAM_ID_ENEMY, N) and Factor_GeneratorEnemyCount(M) in the same logic, showing that the two predicates observe different state.

Do not use Factor_GeneratorEnemyCount to answer “how many spawned spiders are alive?”

Live-object counters

Use the factor whose ownership matches the desired population:

Need Appropriate factor family
all live enemy-team objects Factor_TeamObjectCount(TEAM_ID_ENEMY, N)
live objects in an area Factor_AreaTeamObjectCount(...)
live objects in a controlled group Factor_GroupObjectCount(group, N)
active generator/host population Factor_GeneratorEnemyCount(N)
finite producer slot completion Factor_WaitGeneratorEnd(host, slot)

Do not substitute one family for another because the names all contain “count”.

No proven native active_limit / total_limit parameters

The recovered mission-script call signatures expose:

slot
resource
count
level
unit_interval
wave_interval (periodic only)
encountered

No evidence-backed generator signature adds native active_limit or total_limit arguments.

This does not prove the EDF runtime has no hidden global/per-host/per-slot population cap. It means such a cap has not been recovered as an exposed mission API parameter and cannot be treated as an established native mission argument.

Deterministic total-spawn limit

When an authored mission needs a real total production cap, use finite batches plus author-owned state rather than pretending the periodic call has a total-limit argument.

Example requirement:

20 enemies per wave
0.5 s per enemy
30 s between waves
100 total emitted

Robust pattern:

spawned_total = 0

repeat:
    current_batch = min(20, 100 - spawned_total)
    SetInstantEnemyGenerator(slot=0, count=current_batch, unit_interval=0.5)
    arm next event with Factor_WaitGeneratorEnd(host, 0)

on finite batch end:
    spawned_total += current_batch
    if spawned_total >= 100:
        CancelEnemyGenerator(0)
        stop
    Wait(30)
    start next finite batch

In EDF6 mission-event terms, Factor_WaitGeneratorEnd is an event factor, not a synchronous/blocking function call.

Incoming Anchor / E505 timing boundary

A retained Incoming Anchor script sequence creates/configures the producer and then triggers E505_GENERATOR_ACTION_FALL. Therefore it does not establish the semantic guarantee “begin producing exactly 20 seconds after landing”.

The corpus did not establish a first-class factor such as:

Factor_E505Landed
Factor_ObjectActionEnd
WaitAnchorLanding

An arbitrary Wait() after Action(FALL) is therefore not exact “time after landing” semantics.

Without a proven landing-completion factor, an action-relative Wait() is only an approximation. Exact timing needs the actual native landing-completion signal.

Runtime questions still open

The retained source/API evidence does not yet settle:

  • whether the native periodic generator has a hidden live-child/global-team/per-host/per-slot cap;
  • whether exceeding such a cap delays, skips or queues a spawn;
  • whether wave_interval is measured from cycle start or from completion of the prior batch in every native path;
  • the exact E505 pylon landing/action-completion signal.

A minimal runtime discriminator should compare periodic batches with survivors left alive, partial kills, global enemy pressure, two slots on one host, two hosts, mid-batch cancellation and host destruction. The native interpretation remains unknown without such observations.

R174 source-call count versus producer capacity: a 141-mission counterexample

An independent audit of 141 original EDF5 BVM mission scripts found 571 cuscall0 2100 and 270 cuscall0 2101 sites, alongside 664 2000 and 722 2001 sites. These are distinct source API transactions, not 841 produced waves plus 1,386 living enemies. For example, M004 contains 162 source-side enemy/generator/drop-boat transactions in the historical corpus, but neither that figure nor its breakdown fixes how many actors exist at once.

The different identifiers and per-mission counts are catalogued in data/R174_EDF5_ORIGINAL_141_MISSION_SPAWN_SOURCE_CALL_CENSUS.csv. Source-site totals must not be substituted for Factor_GeneratorEnemyCount, Factor_TeamObjectCount or Factor_GroupObjectCount: those factors inspect game state, whereas the atlas counts authored instructions. No new first-class active/total limit API, native generator cap, or runtime scheduling rule was proven by this census. The source corpus is EDF5, not the six-file EDF4.1 script subset used in R172/R173.
