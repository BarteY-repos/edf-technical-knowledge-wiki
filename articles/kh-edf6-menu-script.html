EDF 6 — Menu Script (community source notes)

EDF 6Community Knowledge HubScripting
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Menu script routines and a mission without menus (round 24)

AngelScript coroutine constructor registration

Evidence: verified · Build: steam-678ccb46 · Fact ID: createcoroutine-menu-routines

12946F0 is the script function coRoutine createCoRoutine(const string &in) (registered at 129463E with the declaration string at 1AF3118; 1294B00 is the (string, any@) overload). MAINSCRIPT.AS runs its menu routines through it by declaration: string StartToTitle(), string HQMain(), string PlayMission_Offline(); the script also keeps a leftover string Debug_StartOffline() that skips the logos, title, Epic login and slot choice. A hook that swaps the declaration (StartToTitle to Debug_StartOffline, then the first HQMain to PlayMission_Offline with row and difficulty set) starts an offline mission with no menu at all.

Basis: registration and string re-read with fn.py here; the routine names and the swap from autopilot.cpp (its prologue signature checked by the plugin at load); novae (ajane)

Addresses (build-specific RVAs unless indicated): 12946F0, 129463E, 1AF3118, 1294B00

Attribution: EDF6Autopilot (hajisensai, edf6-all-forces, round 24), hub check, novae (ajane) · 2026-11-13

GameDataMgr offline mission and difficulty fields

Evidence: verified · Build: steam-678ccb46 · Fact ID: gamedata-mission-row-difficulty

GameDataMgr [20B2890] holds the offline mission list-row index at +0x48 (zero-based position in MISSIONLIST.OFFLINE.LIST.SGO) and difficulty at +0x4C (0–4). The list row is the displayed offline mission number minus one: row 0 = M1 Base 251 (m000b), row 1 = M2 Enemy Invaders (mission folder m001), row 19 = M20 Melee at the Pier (m018_5), row 20 = M21 The Silver Fleet (m027). A folder name such as m001 is not the zero-based list row. The original short note “M001 is 1” was ambiguous; RM015 at row 13 remains a separate, source-reported example. PlayMission_Offline selects the indicated row and difficulty. Source refinement: Knowledge Hub 5b589ca, fact gamedata-mission-row-difficulty, credited to hajisensai/EDF6Autopilot and novae (ajane).

Basis: autopilot.cpp's kMissionRow, kDifficulty and its notes on the offline list; not traced in EDF.dll here; novae (ajane)

Addresses (build-specific RVAs unless indicated): 20B2890

Attribution: EDF6Autopilot (hajisensai, round 24), novae (ajane) · 2026-11-13

More facts

MainScript Debug_StartOffline mission path

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-debug-start-offline-flow

In MAINSCRIPT.AS (mainscript/mainscript.as in Root.cpk, 56,786 bytes) Debug_StartOffline() (line 1865) runs InitializeAll(), Network_SetLocation(BOOT_COMPLETE), titleSaveDataLoad(true), WaitSearchUpdateAddon(), WaitSaveLoad(), SetMode(GetModeNo(GAME_OFFLINE_SCENARIO,0)), LoadSaveData_ModeSelect() (on failure a Sys_LoadFailed_ToTitle dialog and return "StartToTitle"), UnlockDownloadContents(), then return "HQMain", with no slot choice (the slot is the engine's current slot index; the normal flow sets it in SlotSelect(), line 746, through CreateSlotSelectUi2).

Basis: the script read from Root.cpk in place

Attribution: novae (ajane) · 2026-11-13

PlayMission_Offline result and HQ transition

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-offline-mission-chain

PlayMission_Offline() (line 1087) ends with Result_Common(g_is_mission_clear) and return "HQMain" (line 1303), so after every offline mission the script creates HQMain again: a hook that swaps HQMain for PlayMission_Offline (#createcoroutine-menu-routines) can chain missions, each HQMain a fresh swap point. Other lines: StartToTitle() 442 (calls LoadSystemSaveData() then Title() 675; returns "HQMain" at 481 in one branch), HQMain() 894 (returns "PlayMission_Offline" at 968), LoadSaveData_ModeSelect() 21 (calls ModeSelectLoadSaveData()), ApplyModeNo(int) 1895.

Basis: the script read from Root.cpk in place; the chaining not run

Attribution: novae (ajane) · 2026-11-13

Debug mission launch locks gamepad input mode

Evidence: verified · Build: steam-678ccb46 · Fact ID: edf6-debug-start-pad-mode

A start through the leftover Debug_StartOffline() leaves the game in gamepad mode: in the mission, keyboard movement and mouse look do nothing (Esc, arrows, WASD and Enter still work in menus; the key-config screen shows the pad bindings), even with no pad present. A start that keeps the title (StartToTitle() -> Title(), "Press Start") and a key press there gives keyboard and mouse, and [1FEEE1C] then reads 0. The cause is in the code: only the title's Press Start sets the input mode (system.md#edf6-input-mode-bytes); a debug start could write 0 there itself (untested).

Basis: novae (ajane); the byte during the debug start not read

Addresses (build-specific RVAs unless indicated): 1FEEE1C, 12946F0

Attribution: novae (ajane) · 2026-11-14

MainScript mission result and scene lifecycle

These records summarize contributor static readings of MainScript and build-specific native dispatchers. The separately documented in-game ExitMission offline clear is not a blanket verification of these other script branches.

MissionMgr End, IsRunning and world-step update

Static. Mission manager at [EDF+20B28A8] implements End at 1F67F0: result argument r is stored at manager +0x54, sent to executor virtual slot 3, then passed to 7E3590(2). BVM end slot 220B40 writes result +0x12C and state 3 at +0x128. IsRunning 1F68B0 checks executor state via virtual slot 6; update 1F6F40 steps its virtual slot 4 before completion and has a debug path to End(1). Application world-step callback 705A60 invokes that update once each world step along with main script 718CA0. AngelScript native Mission 70F0B0 loads mission.bvm on first call, yields until not running and returns 1F6820 (slot-7 result). Withdraw as End(2) returns ABORT, after which the scene group is released and a scene reset runs. See executor storage differences: AngelScript does not use the BVM state offsets.

Pause confirm modes and MissionResult enum

Static. HUiPause confirm handler (virtual slot 1, 935210) calls MissionMgr::End from 935340. If choice byte +0x79C=1, a room (+0x798=2) sends result 4 (LOBBY), while offline sends 2 (ABORT). Choice +0x79C=2 calls End(3) (RETRY), then 8D4140. Source COMMONTYPES.INNER.H defines MISSION_RESULT_UNKNOWN=0, CLEAR=1, ABORT=2, RETRY=3, LOBBY=4, RETURNTITLE=5. These meanings are script/native constants, not proof that all result values produce identical screens or saves.

Result_Common applies and saves the result

Static MainScript trace. After Mission, PlayMission_Offline returns Result_Offline, which enters Result_Common (source line 1395). There, ApplyResult updates save data and Save(false,"Contents_AutoSaveRetry",true) writes the autosave; ui_handle.WaitCloseRequest waits for result screen dismissal before returning to HQMain. A commented return "HQMain" at source line 1165 illustrates a developer route to skip results. The contributor proposed re-entering PlayMission_Offline instead, preserving mission/difficulty without showing results or saving; that redirect was an untested plan, not a known safe retry procedure.

Active AngelScript function name and result wait

Static AOB/AngelScript context analysis. Context method 11E6F90 obtains the active function; 11F2110 obtains its name via 11F0100 with this+0x28. The result UI is waiting while the active function is named Result_Common, not Result_Offline. The source patch's comparison with this exact name was used to identify the result-screen wait after loot and upgrades had already been applied; an early return in that query is a proposed hook behavior, not stock UI flow.

Two distinct AngelScript polling waits

Static. 715310 (identified by the contributor as WaitCloseRequest) calls shared query 714C70 at 71533E and gets the active context from 11E5290. A separate fade wait 7077C0 polls context at 7077D8. The documented patch targets only the 714C70 call in 715310; it does not establish a global override for fade, pause-menu or other script waits.

Scene resource group frees and RETRY exception

Static MainScript/native read. Resource groups are TITLE 0, MODE 1, SCENE 2; g_resource.FreeGroup(g) waits for jobs and calls the native free. Scene group frees appear at script lines 211 (title/boot start), 561 (company-logo end), 1136/1138 (PlayMission_Offline pre-mission), 996 (start of PlayMission_Common) and 1058 (after the mission loop ends, including clear/withdraw). Native 70E330 performs reset 118F0A0 only for group 2 when its thread-context check succeeds, after group release and callbacks (7A2EE0, 112A750, 119290). The loop repeats Mission immediately for MISSION_RESULT_RETRY without passing line 1058. Therefore retry does not imply the same scene-group release as a withdraw.

SystemReset is not the ordinary HQ/scene reset

Static script/callgraph census. SystemReset 70FE00 calls the reset at 70FEC6, but its sole main-script caller is ReBoot (stops music, waits jobs, resets, returns Boot), and no normal script routine returns that name. Direct native named-routine starts arise from system-warning handler 7C70F0 (ownership/device errors) and otherwise unreferenced 7C7000. Developer launch switches main_script, main_script2, boot_script recompile scripts via calls B1980/B7B70 and have their own reset path. Regular retreat, clear, HQ and title transitions instead use the scene reset at 70E38E; “never in any possible mod” is not established by this stock callgraph.

Network location and keyboard input table

Network_SetLocation state and locked field

Static header, script and native reads. MainScript/CommonTypes.h uses locations BOOTING 0, BOOT_COMPLETE 1, MENU_LOBBY 2, MENU_ROOM 3, GAME_PLAYING 4, GAME_LOADING 5. Registered native Network_SetLocation(int) (70F500, declaration 17EB178) writes [20B2AC8]+0x1640 under spin lock +0x1644. MainScript sets 5 before mission (line 1004), 3 after Mission returns (line 1081), while the room start handshake also writes 5. Known readers include 7917F0 and 961318. The result screen's function identity is Result_Common; network location 3 alone is not its name or result code.

GAME_PLAYING writers and online sync gate

Static. Mission native equivalent of EDF5 BVM call 10000 writes location 4 in two implementations: inline BVM interpreter (210B83) and table-routed native body 225050 (225107 write; no direct xref). Both check online mode; online calls 7730C0 start synchronization and may set wait byte [ctx+0x70]+0x68=1. Offline, or after the online start gate admits transition, they lock +0x1644 and write 4. Thus location 4 signals that start path, not necessarily a mission that has finished loading every asset or spawned every enemy.

Shared key-state array from game window pump

Static patch/AOB read, not a fresh input test. Window-thread pump 1183928 calls imported GetKeyboardState to populate the game's 256-byte array at 21360E0. A source patch reads a virtual-key byte (high bit means pressed) after comparing imported GetForegroundWindow with main game window [21360A8], to avoid triggering while another window is foreground. These RIP-relative offsets are specific to its code cave and build, and must not be pasted as general module-relative addresses.
