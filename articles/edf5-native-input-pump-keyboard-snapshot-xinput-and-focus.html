EDF5 input: keyboard snapshot, Win32 focus, mouse delta and dynamic XInput

EDF 5Game technical referencesInput and UI
Technical reference · Attribution and grade per source fact; this edition adds no game runtime test

EDF5 on Windows uses a Win32 message-pump keyboard snapshot, a separate dynamically loaded XInput pad path and a focus gate. These are separate from EDF6's later raw-input behavior; replacing one input API does not imply every game input source has changed.

The keyboard snapshot

The studied EDF5 executable maintains 256 bytes of GetKeyboardState data. Its message-pump thread fills the snapshot under a critical section and the consumer copies it and clears a refreshed flag. The source observes a single GetKeyboardState call per pump refresh, not ad-hoc polling of every key by every gameplay subsystem.

The code imports GetKeyboardState, GetKeyState, GetForegroundWindow, cursor and window functions. It does not statically import GetAsyncKeyState, DirectInput or XInput. Instead, the pad loader obtains xinput9_1_0.dll dynamically and uses XInputGetState from its resolved function pointer. Therefore the absence of a static XInput import is not proof that the game lacks controller support.

Focus gates keyboard and mouse, not all input

The pump compares GetForegroundWindow() against its own stored window handle and writes a focus byte. When not focused, the keyboard path is skipped, the mouse delta is zeroed and cursor recentering stops; the keyboard snapshot itself can continue to update. The observed XInput controller path is not gated the same way: contributor tests found pad gameplay could continue when another window was in the foreground while keyboard-derived hotkeys did not work.

The focused mouse path uses GetWindowRect, GetCursorPos and SetCursorPos to measure displacement from the window centre. A menu-controlled byte can temporarily suppress recentering. The source also describes special filtering for WM_SYSKEYDOWN/Alt in PeekMessage dispatch and an IME detach/re-attach policy that affects text entry.

Performance note

In one researcher recording, the message-pump thread remained 99.7% busy and accounted for a substantial share of sampled process CPU cycles; it included Sleep(0) and repeatedly called the Win32 pump. This is a particular profiler observation, not an EDF5-wide constant, and must not be generalized into a fixed FPS performance improvement claim.

Evidence: static Win32 call tracing, binary reading and contributor-controlled focus tests; no new runtime in this edition. Build-scoped example: message pump near RVA 0x60BC90 and keyboard snapshot address 0x1253600 in the investigated EDF5.exe.
