Files and roles

An SHKT (.shkt) is a Havok Physics 2020 data file

Evidence: static · Build: steam-678ccb46 · Fact ID: shkt-hkt-same-format

An SHKT (.shkt) is a Havok Physics 2020 data file; .hkt files have the same format and the game loads both the same way.

Basis: the editor reads and writes both (its Havok 2020 TAG0 tagfile reader / writer); the report confirms it in code (shkt-loader)

Attribution: ktaro, EDF6 SHKT Editor manual 1.1, SHKT report (Usage §1, Spec §1) · 2026-10-15

HKT and SHKT resource loader registration

Evidence: static · Build: steam-678ccb46 · Fact ID: shkt-loader

ResourceManager registers .hkt and .shkt with one loader, 79FE00 (HktFileResource) -> HktReader (11A47A0 / creator? 11A5270) -> findObject(hknpPhysicsSceneData) in the hkRootLevelContainer (F09810, type 1FB4E00) -> for each systemDatas[i] the game's own xgs::havok::InstanceGroup constructor 11B9FD0 creates bodies from bodyCinfos[] and constraints from constraintCinfos[]. Havok's own hknpPhysicsSystem / hknpRagdoll are never created; hknpRagdollData is treated as its base class. Reader accessors: 11A5700(reader, i) = systemDatas[i], 11A5750(reader, out, i, j) = systemDatas[i].bodyCinfos[j].shape (some classes such as EDF6_SpinnerUfo use the shape directly). InstanceGroup creators: RagdollController::LoadRagdollHavokData? 6E8560, BasicAnimationCharacter::Initialize 313530, EDF6_SoftBodyWeapon_Shield 4564D0 and two other places.

Basis: Ghidra decompilation of EDF.dll

Addresses (build-specific RVAs unless indicated): 79FE00, 11A47A0, 11A5270, F09810, 1FB4E00, 11B9FD0, 11A5700, 11A5750, 6E8560, 313530, 4564D0

Attribution: ktaro, SHKT report (Usage §1-2, Spec §5.1) · 2026-10-16

Havok 2014 legacy rigid-body types

Evidence: static · Build: steam-678ccb46 · Fact ID: hkp-physics-migration

Old Havok 2014 physics (hkpPhysicsData: hkpRigidBody, hkpMoppBvTreeShape, hkpStorageExtendedMeshShape, as in EDF 4.1's files) loads on the ragdoll path but not the map path. EDF.dll registers the 2014 tagfile reader (Common::ReadFormatBinaryTagfile2014 at 1FFB548). The ragdoll loader 11A5270, when the container has no hknpPhysicsSceneData, looks for hkpPhysicsData (descriptor 1FF8960 -> reflected type 9710B0, find F09810, at 11A53E7..11A53FC) and runs Havok's migration 160B950(in, out, 0, 0, migrate constraints = 1) (11A541B) into a container of its own; the migration keeps each rigid body's name (160ABC0: cinfo +0x18 from hkpRigidBody+0xB8) and turns MOPP and storage-extended meshes into hknpCompressedMeshShape (160BE90). The map loader 18C5E0 asks only for hknpPhysicsSceneData (18CB31) and uses the answer unchecked (mov rsi,[rax+0x18] at 18CB4B), so an EDF 4.1 collision.hkt crashes the map load; a map finds its pieces' collision by body name (18DD30, <model>.hkt).

Basis: the author's source comments in src/legacymap.cpp (an EDF 4.1 ragdoll, AntHill301, loaded on 2026-10-10 in their runs; the mod hooks 18CB31 to migrate maps too); 11A53C0..11A541B and 18CB2C..18CB4B re-read with fn.py, matching

Addresses (build-specific RVAs unless indicated): 1FFB548, 11A5270, 1FF8960, 9710B0, F09810, 11A53E7, 11A53FC, 160B950, 11A541B, 160ABC0, 160BE90, 18C5E0, 18CB31, 18CB4B, 18DD30

Attribution: hajisensai, All Forces source src/legacymap.cpp (round 24) · 2026-11-07

How the InstanceGroup constructor uses hknpBodyCinfo (x64 in-memory layout, 0xC0 bytes

Evidence: static · Build: steam-678ccb46 · Fact ID: bodycinfo-runtime-layout

How the InstanceGroup constructor uses hknpBodyCinfo (x64 in-memory layout, 0xC0 bytes; it differs from the file's DATA layout): +0x00 shape (the hitbox), +0x08 flags (low 4 bits cleared), +0x0C collisionCntrl, +0x10 collisionFilterInfo (layer replaced later), +0x14 materialId (materials[id] re-registered in the world's material library, new id), +0x16 qualityId, +0x18 name (kept for name lookups), +0x20 userData, +0x28 motionType (overridden when an argument is not 0xFF), +0x30 position, +0x40 orientation, +0x50 / +0x60 linear / angular velocity, +0x70 mass, +0x78 massDistribution, +0x80 dragProperties, +0x88 motionPropertiesId (re-registered; 0xFFFF = none), +0x8C desiredBodyId, +0x90 motionId, +0x94 / +0x98 / +0xA0 lookAhead / localFrame / activationPriority. Constraint cinfos are 0x28 bytes. In memory, hknpPhysicsSceneData.systemDatas is at +0x18; in hknpPhysicsSystemData, materials +0x18, motionProperties +0x28, bodyCinfos +0x38, constraintCinfos +0x48 (hkReferencedObject = 0x18 bytes).

Basis: Ghidra decompilation of EDF.dll

Addresses (build-specific RVAs unless indicated): 11B9FD0

Attribution: ktaro, SHKT report (Usage §2.1, Spec §5.6) · 2026-10-16

Body and shape fields constant in the studied SHKT files

Evidence: static · Build: steam-678ccb46 · Fact ID: shkt-constant-values

Values identical in every game file (an editor can leave them read-only): userData of bodies and shapes (materials almost always 0), bodyCinfo flags 0, collisionCntrl 0, qualityId 255, activationPriority, collisionLookAheadDistance, motionId, attachedBody, gravityFactor, timeFactor, and the material's isExclusive / triggerType / weldingTolerance / maxContactImpulse / combine policies. Values that vary: shape type and convexRadius, mass, collisionFilterInfo, materialId, motionPropertiesId, material friction / restitution, damping and max speeds, motionType. Constraint names are tool defaults (hkRagdollConstraint002) or empty and nothing refers to them.

Basis: statistics over every game SHKT/HKT

Attribution: ktaro, SHKT report (Usage §6, Spec §5.5) · 2026-10-16

Evidence: verified · Build: steam-678ccb46 · Fact ID: shkt-roles

SHKT shapes are the hitboxes of living enemies and vehicles: bullets hit the shapes even where they stick out of the visible model. The same files drive ragdolls (corpses) and accessories (swaying parts).

RagdollController resolution of SHKT body names

Evidence: static · Build: steam-678ccb46 · Fact ID: body-name-lookup

Name resolution in code: RagdollController::BindDependency (6E6A50) reads the mapping tables and links each body (by body name) to an animation node (by bone name), logging ragdoll to animation node not fount when a node is missing; main_rigid_body_name (51E500) and similar keys are resolved by 6EA4B0, which looks the body index up in an FNV-1a hash table of body names.

Ragdoll-to-model mapping through embedded SGO

Evidence: static · Build: steam-678ccb46 · Fact ID: ragdoll-bone-mapping

The ragdoll-to-model link is not in the SHKT but in two tables of the embedded SGO: animation_from_ragdoll rows [body, bone] (corpses: the bone follows the body) and ragdoll_from_animation rows [bone, body] (living: the body follows the animated bone). Each row is [[name, name], position, rotation, scale], the relative placement of body and bone.

Basis: the game's SGOs

Attribution: ktaro, manual 1.3, SHKT report (Usage §3, Spec §5.2: name order checked on all game SGOs) · 2026-10-15

Ragdoll mapping-row position and rotation

Evidence: static · Build: steam-678ccb46 · Fact ID: mapping-row-placement

Meaning of a mapping row's position and rotation: an animation_from_ragdoll row places the bone relative to the body (bone position = body position + body rotation x position; bone rotation = body rotation x rotation); a ragdoll_from_animation row places the body relative to the bone the same way (rotation as a quaternion x, y, z, w). Scale is 1 in every row. Of all 44,159 game rows, 81 % of animation_from_ragdoll and 98 % of ragdoll_from_animation match the MDB bind pose within 1 mm and 0.5 degrees; the rest are fingers, mouth and weapon bones authored in another pose (mostly rotation only).

Basis: every game SGO compared with the MDB bind poses

Attribution: ktaro, SHKT report (Spec §5.2) · 2026-10-16

Moving bodies with the SGO mapping tables updated works normally

Evidence: verified · Build: steam-678ccb46 · Fact ID: body-move-rename-tests

Moving bodies with the SGO mapping tables updated works normally; without updating them, model and hitbox are offset. Moving only the body origins (shapes and joint pivots in place) changes nothing. Renaming a body together with the SGO, or renaming the SHKT and repointing the SGOs, works.

Basis: ktaro's in-game tests (2026-10-09/10)

Attribution: ktaro, SHKT report (Usage §7) · 2026-10-16

SHKT and MDB coordinate conventions

Evidence: static · Build: steam-678ccb46 · Fact ID: shkt-mdb-coordinates

SHKT and MDB use the same coordinate system (no conversion): meters, kilograms, +Y up, the model's left side (_l parts) at +X. Which MDB of which MRAB is used comes from the SGO's animation_model and similar keys.

Basis: the editor overlays models and shapes

Attribution: ktaro, manual 1.4, 2.8, SHKT report (Spec §5.8: body position and orientation in model space, shapes in body space, compound children placed by their own rotation and translation) · 2026-10-15

Ant ragdoll transformation test

Evidence: verified · Build: steam-678ccb46 · Fact ID: body-move-mapping-rows

Moving all 22 ant bodies 2 m up and 45 degrees around the vertical (shapes and joints left in place) with the SGO mapping rows rewritten so each body keeps its relation to its bone (285 rows in 5 SGOs): no change in hitbox, corpse or look (0.3 m / 20 degrees likewise). The same SHKT with unchanged SGOs: hitbox and corpse look "slightly" shifted, much less than the 2 m / 45 degrees would suggest, so the living hitbox may use the mapping rows' position and rotation only in part (open, not investigated).

Basis: ktaro's in-game tests Q05, R04, R05 (2026-10-10), mission M15

SGO transformation round-trip coverage

Evidence: static · Build: steam-678ccb46 · Fact ID: sgo-tool-roundtrip

The SGO conversion tools were round-tripped (SGO to text to SGO) on all 717 SGOs of OBJECT: SGO Transformation Tool: content identical in 717 of 717 (byte-identical only 30; shared-value numbering and the place of embedded MABs differ); EDF Tools: content identical in 702 of 717 and byte-identical in none; it breaks expression references in 15 E602 Berserker SGOs (an expression loaded inside another, for example level-dependent _l values, becomes a reference to a missing mark0), rewrites embedded MABs (same content, different bytes) and writes floats with 8 significant digits (no value changed).

Damage and weak points live in SGO, not SHKT

Evidence: static · Build: steam-678ccb46 · Fact ID: sgo-part-weakpoint-structures

Part damage and weak points live in SGOs, never in the SHKT, and name SHKT bodies: weak_point = { damage_esb: "large_weak_damage.esb", body: "ragdoll_eye", weak_damage_multiply: 1.5, noweak_damage_multiply: 0.2 } (E602_BERSERKER_LARGE and others); humanoid_base_parts_config (33 entries, for example the armor frogs) = [model key, ragdoll key, body-name prefix "RagDollProxys.", [parts...]] with a part = [part name, parent part, HP, damage multiplier, ..., reaction name, [MDB display nodes...], [body-name suffixes...], flags] (head: display C_head_geo and others, hitboxes RagDollProxys.head / RagDollProxys.mouth); also EDF6_JormungandPartsSettings.weak_point.parts, UfoCarrier_CorePartsName (RagDollProxys.catapult_A) and BerserkerSettings.NoSeparationBodies. Renaming or deleting a body therefore also breaks the part and weak-point definitions, not only the mapping tables.

Basis: the game's SGOs (research/03 §4)

Attribution: ktaro, EDF6 SHKT Editor 1.0 · 2026-10-19

accessory_ragdoll is the 5th element of an SGO model setting (animation_model etc.): [ max distance, table of swaying parts, accessory SHKT path, embedded SGO (bone mapping tables) ]. Every game file uses max distance 20 (m from the camera).

Swaying accessory damping and material parameters

Evidence: verified · Build: steam-678ccb46 · Fact ID: accessory-values-from-sgo

For swaying parts, the SGO table's linear damping, angular damping, gravity factor, friction, restitution and collision flag are used instead of the SHKT's material and motion properties. The accessory SHKT needs a gapless joint chain from the skeleton root to the swaying parts; bodies not in the table stay fixed.

Accessories sway for AssultSoldier (Ranger) and PaleWing (Wing Diver); for ants (InsectBase) and frogs (Humanoid_Basic) the accessory is created but does not move (with ants it is left behind where the ant appeared). Accessory creation through AnimationModel loader

Evidence: static · Build: steam-678ccb46 · Fact ID: accessory-update-path

Accessories are created by 6B4FB0, called from AnimationModel::LoadFromSGO (the same for every class), which sets the collision layer of every accessory body to 23; the per-frame update AccessoryRagdoll::Update (6B61D0) is called only from HumanBase::OnUpdate, so accessories move only in HumanBase-derived classes, in practice the four EDF soldier classes (HeavyArmor and Engineer take the same path but are not confirmed in game). Every body of an *_ACCESSORY.SHKT (6 files: P502 / P602 proto Wing Diver hair; P506 / P606 Wing Diver hair and skirt or cloth; P601 proto Ranger scarf) has motionType 2.

Basis: Ghidra decompilation of EDF.dll; the game files

Addresses (build-specific RVAs unless indicated): 6B4FB0, 6B61D0

Attribution: ktaro, SHKT report (Usage §3.1, Spec §5.9) · 2026-10-16

Accessory root bodies and joint continuity

Evidence: verified · Build: steam-678ccb46 · Fact ID: accessory-root-chain

A new accessory needs the skeleton's root bodies in its SHKT, joined without a gap to the swaying parts (the root side as fixed parts): ant antennae made without the root (kao, 4 antennae) were invisible while the ant lived and stood still at the spawn point on the corpse; a Ranger left arm (upper arm, forearm, hand) with koshi, mune and kata_l as fixed parts swayed, and the mapping rows of the included bodies copied from the original ragdoll were enough (P601's scarf has 9 rows, not all bones). Wing Diver booster arms made from a bone chain (cone 30 degrees to the chest) swayed and stayed attached.

Which SHKT values the game uses

SHKT hitbox shape, mass and material effects

Evidence: verified · Build: steam-678ccb46 · Fact ID: shkt-effective-values

Effective in game: shape (size and form of the hitbox), mass (lighter bodies are thrown more), material friction and restitution (zero friction: corpses keep sliding), motion damping, joint limits, collision exclusions (subsystem ID, no-collide ID). No effect: the collision layer (the game overwrites it), gravityFactor (the game handles gravity), the hkaSkeleton (breaking it changes nothing), userData.

Basis: author's in-game tests

Attribution: ktaro, manual 1.5, SHKT report (Usage §7 test table: damping 5.0 harder to knock around, mass x 0.01 knocked away more easily, gravityFactor -0.3 no change, skeleton bone names / reference pose / boneToBodyMap scrambled: no change) · 2026-10-15

Rebuilt shapes and massDistribution runtime test

Evidence: verified · Build: steam-678ccb46 · Fact ID: shkt-rebuild-tests

Rebuilding every shape with the editor's own calculation (hulls, compounds, trees) and removing massDistribution changes nothing; a ragdoll rebuilt from an empty SHKT (ant) works; hitboxes from automatic convex decomposition (pillar, torus, whole ant) behave as the shapes look (bullets pass through the torus hole).

Basis: ktaro's in-game tests (2026-10-09/10)

Attribution: ktaro, SHKT report (Usage §7) · 2026-10-16

Null massDistribution: game-computed mass properties

Evidence: verified · Build: steam-678ccb46 · Fact ID: mass-distribution-null

A body whose massDistribution is removed (null) gets its center of mass and inertia computed by the game from the shape; about half of the game's bodies already have null, and the stored values do not match ones computed from the shape.

Basis: author's in-game test; counts from the game files

massDistribution is null in 2,052 of the 4,251 bodies in OBJECT and WEAPON

Havok derived collision shape data

Evidence: static · Build: steam-678ccb46 · Fact ID: shape-derived-data-rules

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Shape input structures
  2. Reconstructed generated fields
  3. Agreement with sampled SHKT files
Complete original research record — expand (1,303 characters)

How Havok's derived shape data is built, as ktaro reproduced it against all game SHKTs: hull faces run counter-clockwise seen against the outward normal; minHalfAngle = half the smallest angle to a neighbor face (0-90 degrees quantized to 0-255, truncated; the original is smaller in about 30 % of cases); maxAllowedPenetration = the shape's smallest width (convex radius included) x 0.165 (median 0.164 for hulls); hull volume follows the Steiner formula for the convex-radius-rounded shape, center of mass and inertia come from the unrounded polyhedron scaled to that mass and multiplied by the inertia factor; a sphere is one vertex plus radius (71 of 71 match), a capsule two vertices plus radius (1,033 of 1,033), a cylinder a.w = radius, b.w = 0.5 and a 64-sided prism of 128 vertices and 66 faces (59 of 59), a box three rotation columns with half extents in w and center w = 0.5 and an 8-vertex hull (99 hulls match; mass properties approximate); compound child boxes are the rotated, translated child vertex range plus convex radius, key bit count = bit length of the child count (AABB and key count match in 1,842 compounds, bounding radius in 1,532; Havok's is larger in the rest); of 7,934 shapes three flat hulls (E601 / E661 barriers, E614 gate effect, 32 vertices each) cannot be rebuilt.

Basis: checks over all game SHKTs (Spec §8, research/05)

Attribution: ktaro, EDF6 SHKT Editor 1.0 (Spec 0.19 §8) · 2026-10-19

Compound shape trees: simdTree is a 4-way BVH (node 0 a dummy, node 1 the root

Evidence: static · Build: steam-678ccb46 · Fact ID: compound-tree-rules

Compound shape trees: simdTree is a 4-way BVH (node 0 a dummy, node 1 the root; an inner node's data is a child node index, a leaf's data an instance index; empty slots min +3.4e38, max -3.4e38; a single child gives nodes 0, 1 (root), 2 (leaf)); aabbTree is empty in every file and boundingVolumeData.type is 2; instance flags 0x40 always, 0x02 = translation, 0x04 = rotation (27 instances have 0x02 without a translation), no scale, leafIndex, shapeTag and destructionTag all 0xFFFF; numShapeKeyBits 2 for 3 children and 3 for 6. A tree need not equal Havok's: a split on the longest axis with equal counts works.

Basis: every game compound; in-game tests C01, G01, G02

Proposed wheel suspension spring-force relationshipSource: unverified

Evidence: unverified · Build: steam-678ccb46 · Fact ID: car-base-wheels

Wheel spring force = spring strength x the vehicle's in-game mass x compression, so compression at rest is about 9.8 / total spring strength and does not depend on mass. With a soft spring the hull digs into obstacles it climbs and is easily thrown off. Wheel row: cast mode (0 ray, 1 cylinder), [2] mount offset, [3] suspension length, [4] length addend, [5] spring strength, [6]/[7] damping, [8] radius, [9] half width.
