CANM — keyframed animation data and channel encoding

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: A CANM stores animation motion over time, including keyed channels for bones or objects.

Where it fits: CAS organizes animation controllers and playback state, while MAB carries certain timed events and bindings. CANM holds the motion data itself.

Important distinction: An animation can be decoded correctly yet still fail on an incompatible skeleton or controller.

The documented role

The researched CANM content includes bone/object keyframes with typed, sometimes quantized channels. In the examined profiles, CAS can carry or reference CANM clip data. Keep the CAS wrapper version separate from the CANM channel generation when interpreting an animation file.

EDF5 and EDF6 channel differences

Property Examined EDF5 profile Examined EDF6 profile
CANM version 0x200 (512) 0x300 (768)
Channel record size 0x20 bytes 0x30 bytes
Documented animated rotation Euler-radian channels Absolute XYZW quaternion representation
Additional channel metadata Earlier layout XYZW base/multiplier and encoding type

The cross-generation research also measured 28-byte clips, 8-byte tracks and four target channel kinds. These measurements belong to the examined conversion profiles. A simple version-field change is not equivalent to decoding older values and serializing the target channel representation.

Clip and track records

The studied CANM family begins with a 0x20-byte header. Its 28-byte clip records hold a name reference, duration, sampling/frame interval, frame count and track count/location. A track occupies 8 bytes and links a bone to at most three channels:

Track field Stored interpretation
uint16 bone index Identifies the animated target bone in the owning model context
int16 translation channel index -1 means no translation channel
int16 rotation channel index -1 means no rotation channel
int16 scale channel index -1 means no scale channel

An index only establishes a channel connection. Its payload still has to be decoded using the relevant CANM version and channel kind.

How the channel values are encoded

Source-generation CANM 0x200

The examined 0x20-byte channel includes a keyed/static indicator, key count, three float32 base components, three float32 step/multiplier components and a key-data offset. Animated XYZ components are quantized as uint16 values. The source reconstruction evaluates a component as:

float32(base + float32(key_uint16 * step))

For the studied animated rotation channels, the reconstructed XYZ values are Euler radians, with the source rotation composition Rz · Ry · Rx. The float32 evaluation sequence is material when comparing exact converted output.

Target-generation CANM 0x300

The measured channel expands to 0x30 bytes: eight float32 values representing base and multiplier XYZW, followed by four signed 32-bit fields (key offset, kind, count and reserved).

Kind Observed meaning Key representation
0 Static vector Base XYZ
1 Animated vector Quantized uint16 XYZ values interpreted with base and multiplier
2 Static rotation Base float32 XYZW quaternion
3 Animated rotation Float32 XYZW quaternion for each key

The studied native quaternion loading path requires 16-byte alignment of quaternion key blocks. These record kinds and alignment constraints come from the retained target-generation corpus, not from a new parser or a claim about arbitrary future CANM variants.

Why a numerical conversion needs evidence

In the documented EDF5/EDF6 work, animated quaternion values are not always bit-exactly reconstructible from already quantized source values. The measured conversion uses float32 Euler-to-quaternion behavior, and its correctness must be assessed within that precision boundary.

Separately, a structurally valid clip can still fail to animate the intended target if its skeleton, controller names or other cross-references are wrong. Those dependencies belong to the whole animation resource graph, not the CANM bytes alone.

Reading order and validation

  1. Establish the game generation and actual channel layout.
  2. Read each clip and track under its measured record structure.
  3. Decode channel kinds and stored rotation representation before changing them.
  4. Keep metadata and references required by the owning CAS and model skeleton.
  5. Report parse/round-trip correctness separately from observed in-game animation.
