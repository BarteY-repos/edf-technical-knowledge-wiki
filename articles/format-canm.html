CANM — keyframed animation data and channel encoding

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: A CANM stores animation motion over time, including keyed channels for bones or objects.

Where it fits: CAS organizes animation controllers and playback state, while MAB carries certain timed events and bindings. CANM holds the motion data itself.

Important distinction: An animation can be decoded correctly yet still fail on an incompatible skeleton or controller.

The documented role

The researched CANM content includes bone/object keyframes with typed, sometimes quantized channels. In the examined profiles, CAS can carry or reference CANM clip data. Keep the CAS wrapper version separate from the CANM channel generation when interpreting an animation file.

EDF5 and EDF6 channel differences

Property Examined EDF5 profile Examined EDF6 profile
CANM version 0x200 (512) 0x300 (768)
Channel record size 0x20 bytes 0x30 bytes
Documented animated rotation Euler-radian channels Absolute XYZW quaternion representation
Additional channel metadata Earlier layout XYZW base/multiplier and encoding type

The cross-generation research also measured 28-byte clips, 8-byte tracks and four target channel kinds. These measurements belong to the examined conversion profiles. A simple version-field change is not equivalent to decoding older values and serializing the target channel representation.

Worked example: reading animation samples

Consider an illustrative EDF6 clip with four pose samples and a sample interval of 0.1 engine time units. Normally the stored clip duration is (4 - 1) × 0.1 = 0.3 time units. The interval says how far apart samples are; it is not a separate playback-speed multiplier.

  1. At time t = 0.15, the sampler computes t / interval = 1.5.
  2. The integer part, 1, selects the second stored sample (indices start at zero).
  3. The fractional part, 0.5, blends halfway toward the third sample.

The clip duration controls the higher-level lifetime or completion time; the sample interval controls how quickly the stored poses are traversed. The documented EDF6 runtime treats these as separate values. If the declared sample count exceeds the real channel data, an unchecked sample read can reach adjacent bytes and produce invalid poses. This is an explanation of the published runtime findings, not a new in-game test.

Clip and track records

The studied CANM family begins with a 0x20-byte header. Header offsets below are file-relative because the header starts at file offset zero; table-entry references elsewhere are relative to their containing entry in the documented source format.

Header offsetTypeField
+0x00char[4]CANM signature
+0x04u32Version: studied 0x200 / 0x300
+0x08 / +0x0Cu32 × 2Animation-clip count / clip table offset
+0x10 / +0x14u32 × 2Channel count / channel table offset
+0x18 / +0x1Cu32 × 2Bone-name count / bone-name table offset

Each 0x1C-byte clip record has a separate playback clock and sample layout:

Clip offsetTypeMeaning
+0x00u32Loop flag (observed 0 or 1)
+0x04i32Relative UTF-16LE animation-name reference
+0x08f32Clip lifetime/completion time
+0x0Cf32Sample interval
+0x10u32Declared playback sample count
+0x14 / +0x18u32 / i32Track count / relative track-table offset

For multi-sample looping clips, the researched sampler wraps across N - 1 sample intervals; for non-looping clips it clamps at the final sample pair. Single-sample clips need their own interval handling. The three fields lifetime, interval and count are consumed independently. The usual relationship lifetime = (N - 1) × interval describes the examined multi-sample files, not a loader-enforced invariant.

A track occupies 8 bytes and links a bone to at most three channels:

Track field Stored interpretation
uint16 bone index Identifies the animated target bone in the owning model context
uint16 translation channel index 0xFFFF means no translation channel (often represented as signed -1 by tools)
uint16 rotation channel index 0xFFFF means no rotation channel
uint16 scale channel index 0xFFFF means no scale channel

An index only establishes a channel connection. Its payload still has to be decoded using the relevant CANM version and channel kind. The examined EDF6 runtime bone-mapping cache uses an 8-bit matched-bone index; that suggests a practical ceiling of 255 mapped bones for that consumer, not a u8 file field or a proven universal format limit.

How the channel values are encoded

Source-generation CANM 0x200

The examined 0x20-byte channel includes a keyed/static indicator, key count, three float32 base components, three float32 step/multiplier components and a key-data offset. Animated XYZ components are quantized as uint16 values. The source reconstruction evaluates a component as:

float32(base + float32(key_uint16 * step))

For the studied animated rotation channels, the reconstructed XYZ values are Euler radians, with the source rotation composition Rz · Ry · Rx. The float32 evaluation sequence is material when comparing exact converted output.

Legacy exception to check: the EDF_Tools-derived CANM v512 source note also describes a channel tag 625 (0x271) with four uncompressed float32 values per frame (0x10 bytes/key). This is a guide-reported alternate encoding, not EDF6's kind 2/3 and not a demonstrated member of every EDF4.1/EDF5 file. The retained R10 HF4 R9 converter accepts only the separately measured old keyed/static flag 0/1 profile and rejects other channel tags. Do not silently decode 625 as three uint16 Euler values or claim that the converter covers it.

Target-generation CANM 0x300

The measured channel expands to 0x30 bytes: eight float32 values representing base and multiplier XYZW, followed by four signed 32-bit fields (key offset, kind, count and reserved).

Kind Observed meaning Key representation
0 Static vector Base XYZ
1 Animated vector Quantized uint16 XYZ values interpreted with base and multiplier
2 Static rotation Base float32 XYZW quaternion
3 Animated rotation Float32 XYZW quaternion for each key

The studied native quaternion loading path requires 16-byte alignment of quaternion key blocks. These record kinds and alignment constraints come from the retained target-generation corpus, not from a new parser or a claim about arbitrary future CANM variants.

November 2026 alignment correction: the channel table itself must also start at a 16-byte-aligned address in the examined EDF6 loader. Track evaluation uses an aligned SIMD read (movaps) of channel quaternion/base values; the 0x30-byte row stride preserves alignment only if the table start is aligned. The source compared a stock aligned table (for example 0x1680) with a tool-generated CAS table at 0x6DDE4 (4 mod 16) and a matching crash dump. This is a source-reported dump and engine-code observation, not a fresh test here. Do not confuse channel table alignment with the separate quaternion key-block requirement.

Why a numerical conversion needs evidence

In the documented EDF5/EDF6 work, animated quaternion values are not always bit-exactly reconstructible from already quantized source values. The measured conversion uses float32 Euler-to-quaternion behavior, and its correctness must be assessed within that precision boundary.

Separately, a structurally valid clip can still fail to animate the intended target if its skeleton, controller names or other cross-references are wrong. Those dependencies belong to the whole animation resource graph, not the CANM bytes alone.

Reading order and validation

  1. Establish the game generation and actual channel layout.
  2. Read each clip and track under its measured record structure.
  3. Decode channel kinds and stored rotation representation before changing them.
  4. Keep metadata and references required by the owning CAS and model skeleton.
  5. Report parse/round-trip correctness separately from observed in-game animation.
