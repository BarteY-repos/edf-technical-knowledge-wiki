EDF4.1 Earth Eater: original panel ragdoll layers 0/7 versus EDF6 EAO layer 17

EDF 4.1Engine RE & NetworkingCollision & PhysicsEDF 6
Technical reference · Source executable static RE and original source SGO/SHKT, no EDF6 runtime validation

The MotherShip401/Earth Eater in EDF 4.1 distinguishes between ordinary panel ragdolls and the keyframed core. In the inspected source binary, most ragdolls retain their authored SHKT collision layer 0, while the core's SGO takes a separate branch that changes its ragdoll to layer 7. A native EDF6 EventAnimationObject constructor used by the investigated conversion instead assigns the constructed ragdoll to layer 17 (0x11). These are concrete, build-scoped engine facts, not proof that changing the converted object's layer alone fixes the observed enemy AI/physics anomaly.

EDF4.1 SGO policy: which panel is keyframed?

The retained source corpus contained 18 Mother401 part SGO records. Exactly one has is_keyframe_ragdoll=1: UFOMOTHER401_COREPANEL.SGO (Class=UfoMother401_Core, ragdoll MotherShip401_CenterShaft.shkt). The remaining 17 examined SGOs have no such enabled field, including panel, weak-panel, generator, cannon, final-generator and battery components.

The EDF41.exe PanelBase shell-builder function at RVA 0x26FAB0 reads is_keyframe_ragdoll:

EDF4.1 condition Observed source action Loaded panel ragdoll layer
Absent/zero key Ragdoll loader mode 1; no later ragdoll-layer override in this branch Retains source SHKT-authored 0
Non-zero key (core) Ragdoll loader mode 2, then source RagdollSetLayer at RVA 0x334370 with argument 7 7

All 13 source MotherShip401 SHKT files, representing 29 examined bodies, carry authored collision layer 0. The layer 7 on the core is therefore a runtime branch decision, not a pre-authored core SHKT layer.

Why layer 13 must not be applied to ordinary panel ragdolls

The non-keyframed branch additionally changes a different component reached via object+0x3F0, setting that component's collision-filter low layer bits to 13 through the source helper around RVA 0x0EEC00. This component is not the loaded panel ragdoll. The complete recovered source flow therefore does not say that all ordinary ragdolls run on layer 13.

Three values belong to three different entities: 0 (ordinary ragdoll), 7 (keyframed core ragdoll) and 13 (separate non-keyframed helper). Merging them is a collision-modeling error.

Target EDF6 behavior and limits of the comparison

The inspected EDF6 EventAnimationObject creates a ragdoll and forces its collision layer to 0x11 / decimal 17. Its native ragdoll setter was identified at EDF RVA 0x6E9320; the generation comparison also identified native ragdoll disable/enable control at 0x6E97C0 / 0x6E9840.

The source-compatible candidate restores 0 or 7 after target object construction but before pre-activation removal from the physics world; when the panel is activated the same ragdoll is re-enabled. Restoring the layer through EDF6's native setter preserves non-layer filter/grouping bits. This is a source-informed compatibility hypothesis; it has not yet been confirmed in a Windows EDF6 gameplay test. Battery objects are excluded from this candidate.

Three separate gameplay/physics questions

  1. Before activation: does a panel have an active collision body in the world when EDF4.1 would not? This is a lifecycle/world-membership question, independent of collision layer.
  2. After activation: does the panel have the correct ragdoll layer, filter group, body set and collision/query behavior? This is the 0/7 versus 17 comparison.
  3. AI and interaction: even a source-consistent filter does not prove that spiders, Deroye, flying enemies, explosions and grounding queries behave identically. A direct mixed-enemy runtime regression is still necessary.

The tester's reported problem—enemies spawning/standing on inactive panels, later climbing or sticking to active panels and sometimes leaving the map—was observed in the port, not demonstrated as a stock EDF6 bug. There is no justification for changing global collision filters, blindly writing layer 13 to ragdolls, or claiming all Mother401 variants share the core's layer.

R175 exact native query-container and EDF6 visibility decision

The earlier layer 0/7/13 distinction is correct but incomplete without the native query stage. In the pinned EDF4.1 PanelBase branch, the main ragdoll wrapper is at object+0x328. Its separate, legacy query/collision container is reached through object+0x3F0 (= ragdoll+0xC8). The non-keyframed path at RVA 0x26FC52 calls helper 0x0EEC00, assigning layer 13 to the container's primary and linked bodies while retaining other filter fields. The keyframed path at 0x26FC43 instead calls RagdollSetLayer(ragdoll, 7); it does not turn all normal panel rigid bodies into layer 13.

In the examined EDF6 build, the relevant area-damage query uses query layer 13 (RVA 0x106070). The target EventAnimationObject initially sets the created ragdoll to 17 at RVA 0x5B6401; its main-body array/count reside at +0x78/+0x88 in the studied wrapper. A target group-filter table can be read via the identified vtable path (0x17E0788, table offset +0x58). This is a build-scoped description of the original engine's visibility mechanism, not a stable public API or a claim that these numeric offsets work on another patch.
