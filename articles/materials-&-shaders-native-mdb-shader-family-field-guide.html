Native MDB shader families: practical parameter and sampler reference

EDF 6Materials & ShadersShaders
Technical reference · Mixed: sampled native MDB corpus and supplied guide

Overview

A shader family is a contract between MDB mesh attributes, ordered native material parameters, sampler slots and render state. A shader identifier alone is not enough to reproduce the original material, and shader-reflection order cannot be assumed to be serialization order.

Material workflow

  1. Identify the actual shader family and required vertex attributes.
  2. Read parameters in native MDB order, preserving their stored types.
  3. Keep texture samplers in their native slot order.
  4. Preserve blend, alpha and family-specific render state.
  5. Validate visually in the target renderer, not just by parsing the MDB.

See Shaders for the central reference and the snd_BRDF_Map_Common example.

Starting from a real material

For a self-contained implementation guide, read How to read and write native MDB materials. It explains why these observed sampler and parameter tables are not interchangeable with shader reflection and demonstrates Common metallic/roughness channels and integer controls.

An MDB material is not defined by its shader name alone. The shader family, the ordered parameter records, the ordered sampler bindings, their states, and the mesh vertex declaration form a contract. Changing only the shader identifier can create an apparently valid file that renders incorrectly.

This page describes ordinary EDF6 MDB materials, including map props and building models. It does not describe the separate FMEP/FieldRender terrain pipeline.

Common BRDF material: the basic interpretation

For sampled snd_BRDF_Map_Common materials, the useful logical model is:

Input Meaning in the observed/common guide-backed path Important caveat
diffuse Multiplies sampled albedo RGB Colour customization can interpolate in additional colours first
metallic Scales the packed metallic channel Typically packed.G × metallic, then clamped downstream
roughness Scales the packed roughness channel Typically packed.R × roughness; _hr can multiply alpha too
normal_amount Multiplies normal-map tangent-plane perturbation Affects normal direction before normalization, not stored normal length
specular_color Participates in the specular/Fresnel term Not equivalent to tinting the final diffuse colour
specular_diffuse_blend Mixes specular colour behaviour as metallic increases Formula is based on a supplied rendering guide; not independently established for every shader

The retained guide models the packed channels as:

metallic  = clamp(packed.G × material.metallic,  0, 1)
roughness = clamp(packed.R × material.roughness, 0, 1)
roughness_hr = clamp(packed.R × packed.A × material.roughness, 0, 1)

These formulas apply to the identified common packed R/M path. They do not license a universal channel reinterpretation of arbitrary EDF5/EDF6 textures. The same shader guide describes a Fresnel baseline resembling specularRGB × (0.04 + 0.96 × metallic); use it as a reference-derived compositor model, not as a proven exact fragment-program identity for every material.

Normal textures: packed channels and occlusion

For the common-model path described by the supplied guide:

nx = (R × A × 2) - 1
ny = (G × 2) - 1
nz = sqrt(max(0.00001, 1 - nx² - ny²))

The tangent-space perturbation is scaled by normal_amount, transformed through the tangent/binormal/geometric-normal frame, then normalized. Normal-map strength and stored normal-vector length are separate concepts. The guide describes a later normalXYZ = normalizedNormal × occlusion operation. Its author subsequently clarified that normal length enters diffuse/specular/compositor lighting in different ways; those detailed downstream rules are guide-derived and should not be generalized across every shader family without more binary evidence.

What native material sampling establishes

The audited ordinary MDB map-model corpora contained the following material samples. Counts are sampled occurrences, not global EDF6 usage statistics.

EDF6 shader family Studied occurrences Notable verified structure / use
snd_BRDF_Map_Common 101 Albedo, normal and packed R/M sampler set; six familiar BRDF parameters
snd_BRDF_Map_Common_Clip 44 Common parameters plus alpha_clip; sampled 60-byte mesh profile
snd_BRDF_Map_Common_Light 5 Includes light_color; sampled packed light mask and dedicated emissive path
snd_BRDF_Map_Build_Basic_NC 28 Five samplers including occlusion and dirt; sampled 76-byte profile and three UV uses
snd_BRDF_Map_Build_Para_NC 9 Parallax parameters; sampled 76-byte material/mesh ABI
snd_BRDF_Map_Build_DirtScroll 7 Dirt-scroll controls, sampled 76-byte profile
snd_BRDF_Map_Signboard_Pattern 1 Animated/switching controls including integer-bit (type=4) lanes; sampled 68-byte profile

For Build_Basic_NC, sampled geometry uses TEXCOORD0 for close-range sampling, TEXCOORD1 for occlusion and TEXCOORD2 for macro/dirt data. A generic renderer that feeds every sampler from UV0 discards that relationship.

Alpha cutout is not general transparency

In the sampled Common_Clip path, fragments are discarded when sampled albedo alpha falls below the material's alpha_clip threshold. Within the 44 sampled Common_Clip materials, alpha_clip was 0.5 in 42 and 0.3435 in 2. These are observed defaults, not a game-wide invariant.

A native foliage texture (sk_pShrub003-df.dds) demonstrated actual BC1/DXT1 one-bit transparency. BC1 cutout is therefore a valid native example, not the sole permitted cutout encoding.

Common_Light is a real exception to generic emission assumptions

An exact inspected snd_BRDF_Map_Common_Light path wrote an emission accumulation equivalent to:

emissionAccum.rgb = packedLightMask.B × light_color.rgb

No base-colour multiply was established for that exact write. Do not turn a guide's more general emissive model into a compulsory rule for Common_Light, or claim that this exact write describes every emissive family.

Raw integer parameter lanes (type=4)

Some material parameters occupy a four-byte lane but represent a raw 32-bit integer, not a numeric float. An unmodified bit-preserving round trip may happen to work through a float container; creation/editing through float arithmetic is not safe. Preserve the declared type and raw bits; expose known fields as integer/flag controls. For example, reinterpreting raw 0x00000001 as IEEE float produces a subnormal number, not the numeric value 1.0.

What a model viewer or exporter should do

  1. Identify the model's actual shader family, parameter list and sampler order.
  2. Decode the material-specific texture packing, not a global RGBA assumption.
  3. Use the mesh's actual semantic streams, including extra UVs and tangent/binormal data.
  4. Preserve unknown fields and type=4 raw bits.
  5. Label a stock Principled/glTF preview approximate when it does not reproduce EDF's compositor and lighting rules.
  6. When converting EDF5 materials, use a compatible full target profile; a shader-name substitution is not a complete migration.
