The game source, target AngelScript interface and tested modified runtime do not always have identical semantics. The examples below are specific game-behavior boundaries recovered from the cross-generation mission research, not instructions for installing or releasing a particular mod package.

Difficulty, branch and event-state parity

A mission may load successfully but still use an incorrect difficulty branch, enemy threshold or event registration. Seven concrete BVM source-parity cases are tabulated in BVM branch and event semantics. Other cross-generation examples include:

  • M039 / displayed mission 89: two integer locals truncated source-authored fractional friendly NPC levels around 0.8–0.9; the corrected form uses floating-point values. Source/static parity exists, but there is no exact finalized whole-package runtime certificate.
  • M065 / displayed mission 68: a historical softlock involved event/control-flow reconstruction from BVM. A later source repair is not by itself proof of all difficulty-specific runtime cases.
  • M050 / displayed mission 59: a FLAG-index identity mismatch caused a softlock; the corrected source-index mechanism was tested in a modified runtime. See 21-mission flag-index defect.
  • M081 / displayed mission 108: Boolean-domain comparison syntax matters at the EDF6 script ABI; a previous successful candidate was followed by a distinct regression in a later composition. See typed API boundary.

Mission-owned actors and unresolved behaviors

  • M035 / Titans: a historical route2 partial pass and route3 failure establish that compile/load does not certify all navigation. The earlier candidate was intentionally carried forward without declaring route parity.
  • DM017 Barga: an early player-Barga case failed; a later start probe confirmed the NPC Barga constructor path. The late five-Barga sequence was not fully qualified in the retained evidence.
  • M079 Barga: the intended logic distinguishes 14 NPC CreateFriendTransporter Bargas from 1–4 player-owned CreateTransporter Bargas. Constructor-type parity does not alone certify the later encounter or multiplayer ownership.

Correct evidence interpretation

An offline static BVM/AC comparison is not the same as a complete gameplay test. Conversely, an untested final package is not evidence that these missions are broken. Preserve exact source behavior, then qualify the affected runtime branch and mode. Technical release manifests and patch-version history are retained outside the public wiki.

Later source-derived DLC mission and result-flow distinctions

  • An independent 29-mission DLC1/DLC2 source-corpus audit found 25/29 ACs exact to its clean-script lineage and 27/29 mission RMPAs exact to its target reference. The non-exact cases were already classified compatibility deltas, not automatic fresh defects. The complete DLC1/DLC2 evidence matrix documents all names and the DM017 route watch item.
  • A separate 141-mission scalar census identified 10 globally mistyped numeric missions in an earlier port lineage. Its M039 global finding is distinct from the later, more serious local float/int regression found by direct value-flow review. See the exact ten-mission census.
  • Final EDF5 DLC missions have a MainScript-side ending distinct from in-mission FinalMissionClear_EDF5. The result/ending-flow reference explains the original EDF5 cue/layout, EDF6 custom-ID branch mismatch and missing target audio-bank confirmation.

The retained two-mission runtime audit supplies successful tested EDF5 → EDF6 conversion observations for vehicle motion. The success belongs to the specified scene and candidate, not a universal stock-game or geometry guarantee. The source-scripted Archelus in M032_5 has separate durability/retreat semantics documented in its own source case.

Native EDF6 re-grounding of the EDF5 M018 Escape mission route

The EDF5-source/EDF5_OLD_SCRIPT M018 mission route and the later native EDF6 DLC variant RM018 are unusually clean evidence for mission-local vertical route tuning. Both RMPAs are 2,286 bytes and have the same high-level inventory: 4 route groups, 11 waypoints, 1 shape group and 2 spawn groups. In the examined pair, all 11 waypoint vertical (Y) values differ, while X/Z, all spawn records, and shape records are unchanged. One waypoint's next list reverses neighbor order ([10,8] → [8,10]) without changing its neighbor set.

The particularly diagnostic 小隊ルート01 endpoint changes Y = 20.827400 in source/OLD_SCRIPT to Y = 9.368332 in native RM018, a −11.459068-unit delta at the same X/Z. Its initial waypoint changes Y = 8.918897 to 9.806118. The source mission's opening enemy wave is armed by Factor_AiMoveEndOrDie(squad01), whereas its Factor_Wait(5.0f) starts only the opening dialogue sequence. The source and native counterpart both set SetAiMoveSpeed(squad01, 0.4). Consequently a delay in the opening ant wave can be explained by movement/route grounding, without inventing a stretched 5-second timer or missing spawn registration.

The observed native Y retune is not a global MISSION.RMPA coordinate offset: 11 waypoints in this exact mission are adjusted individually and by different amounts. The historical minimal two-waypoint candidate was static-qualified, runtime pending and superseded as a proposed solution. The later complete native RM018 donor overlay was actually tested in the modified game and passed the opening route/pacing gate on 6 September 2026; the first-wave timing was accepted, and no mission-AC change was required. This later runtime result supersedes the old description that the full donor still needed a gameplay test; it does not confer universal nav parity or validate the earlier isolated R1 candidate.

See mission RMPA native/target differences for why reusing stock target RMPA cannot be treated as an always-correct global algorithm. Source: EDF5_EDF6_M018_ESCAPE_R1_ROUTE01_TARGET_Y_STATIC_AUDIT_2026-09-06.md, EDF5_EDF6_M018_ESCAPE_RM018_RMPA_OVERLAY_AUDIT_2026-09-06.md, and stock OLD/NEW RMPA corpus comparison.

Distinct runtime outcomes must not be collapsed into one mission-port verdict

The DM024 (DLC2) compatibility case contains a direct user runtime acceptance of the tested DropBoat_SetCrew-family object-return type repair: the DM024 R50 candidate worked fully in that test. The return-type handling is therefore runtime-supported for this mission, not proof that every other drop-boat constructor or the separate M075 caller is qualified. This is the result recorded in DM024_R50_RUNTIME_PASS_2026-08-28.json, rather than a generic projection from all mission compilation gates.

An earlier M034 / displayed mission 38 route investigation observed railgun09 and railgun03 trapped near rock starts, and railgun05 caught by a tree/stump. In M032_5 / displayed mission 37, maser08 and maser10 were blocked. The first limited AC-only discriminator proposed setting SetAiNavMesh_StraightMode(false) for only those five vehicles; its proposal was not a runtime pass. The later 11 September user runtime results instead passed mission-specific spawn/waypoint corrections with StraightMode(true) kept. The corrected M032_5 case included EMC10 spawn p1.y: 0→1 and EMC08 first waypoint Z 353.990997→350.990997; M034 used 12 reconstructed railgun waypoint-position differences. The older mode-toggle hypothesis is thus superseded for these tested convoy cases, while sporadic nondeterministic navigation snags still warrant scope-specific monitoring. Sources: NEXUS346_M37_M38_RUNTIME_ROUTE_AUDIT_2026-09-10.json and EDF5_EDF6_M37_M38_RUNTIME_PASS_AUDIT_2026-09-11.json.

A separate R54 recorded DM021/DLC2 #3 player spawn as playable-parity runtime-positive, the current DM001 as practically accepted without a surviving mission blocker, and MissionPack metadata V3 as runtime-positive for the tested campaign/maps/limits/outfits/drop behavior. None of those broad acceptance statements supplies missing frame-by-frame observations for every older DM001 diagnostic. Original evidence: R54_RUNTIME_STATE_2026-09-01.json.
