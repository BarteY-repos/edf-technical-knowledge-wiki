EDF 5 — Map Placement (community source notes)

EDF 5Community Knowledge HubMaps
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Placement (map.mapb, map.mapo)

EDF5 places map objects from map.mapb like EDF6 (edf6/file-formats.mdmapb-mapo-layout) with a shorter record:…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapb-record

EDF5 places map objects from map.mapb like EDF6 (edf6/file-formats.md#mapb-mapo-layout) with a shorter record: C3650 walks the records (offset mapb+0x20, count +0x24) at a stride of 0x44 bytes (EDF6 0x48): +0x00 def offset relative to the record, +0x04 / +0x08 / +0x0C position xyz, +0x10 / +0x14 / +0x18 rotation xyz in degrees (x pi / 180, EE6560 / EE66F4). The def: +0x00 type, +0x04 offset (relative to +0x04) to an embedded parameter SGO (checked for "SGO" and version 0x102 at C3B38), +0x0C name offset (relative to +0x0C). The map.mapo entry is [mapo+0x08] + index x 0x1C, as in EDF6. The loaders open map.mapb at C2131 (in C1CC0) and C29C2 (in C22A0).

Basis: fn.py C3650, --xref of the map.mapb string E94290; constants with scratch exe_floats.py; not compared with a map file

Addresses (build-specific RVAs unless indicated): C3650, EE6560, EE66F4, C3B38, C2131, C1CC0, C29C2, C22A0

A placed object's world matrix is built on the stack in C3650 (C386D-C3A51): rotation about x, then y, then z…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapb-matrix

A placed object's world matrix is built on the stack in C3650 (C386D-C3A51): rotation about x, then y, then z from the record's degrees, the translation row from +0x04..+0x0C with w 1, and no scale term; the matrix pointer goes to the object's Preload_Base::InitParam (vtable E95228) at +0x08, with the parent loader +0x10, the parameter SGO +0x18, the record +0x20, the def +0x28, the mapo entry +0x30 and the record index +0x38. A hook after C3A51 sees every placed object's matrix once, at load.

Basis: fn.py C3650 (the stores to [rsp+0x30]..[rsp+0x6C] and [rbp-0x80]..[rbp-0x48]); RTTI with scratch File_Storage/Logs/catalog/vt_name.py

Addresses (build-specific RVAs unless indicated): C3650, C386D, C3A51, E95228

C3650 picks the class by the def name's extension: .mosb - Preload_Structure (0x280 bytes, ctor F02E0), .fmep…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapb-classes

C3650 picks the class by the def name's extension: .mosb -> Preload_Structure (0x280 bytes, ctor F02E0), .fmep -> Preload_Fmex (EAC00; its .fmb and grass.merge.sgo named at C3D05-C3D6E, InitParam@Preload_Fmex E951E8), .mdx -> Preload_AnimationModel (E8AF0) when its parameter SGO has HAS_ANIMATION, else Preload_Model (ED040), .shfb -> Preload_Shf (EF330, with .cols.sgo and .norm.sgo; InitParam@Preload_Shf E95208); .trb and .mlb records are skipped here and read by C4720, MapObject_Fmex_GrowObjects (vtable E96070, slot 4 DB940) and MapObject_Shf_GrowTree (E96310, slot 3 DC880). Def type 2 is skipped while the global 124DD5C is over 5, types 4 to 9 while it is not 0; 1141D0 (mission teardown) resets it to 0 and no other direct writer was found.

Basis: fn.py C3650 and --xref of the extension strings (E94490, E94480, E945B0, E94590, E94548, E945D0, E945C0) and of 124DD5C; class names from the ctors' vtables with vt_name.py

Addresses (build-specific RVAs unless indicated): C3650, F02E0, EAC00, C3D05, C3D6E, E951E8, E8AF0, ED040, EF330, E95208, C4720, E96070, DB940, E96310, DC880, 124DD5C, 1141D0

Render vs collision of a placed object both follow its def's name: Preload_Model (ED040) reads the name throu…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-map-collision-by-name

Render vs collision of a placed object both follow its def's name: Preload_Model (ED040) reads the name through the def at obj+0x28 (+0x0C, ED109), takes its stem (5BD270, inferred to drop the extension), and only when the def's +0x10 is non-zero (ED1EB) appends .hkt (E95458, ED25D) for the collision; it also appends .mab (E95418, ED2FD). Def +0x10 is -1 on 1,309 of the 1,317 defs over all 24 maps and 0 on 8 (categories 2, 3 and 6), so it acts as a "has collision" switch (inferred). Preload_Fmex (EAD32), Preload_AnimationModel (E8CE9) and Preload_Structure (F0A2E) use the same .hkt suffix; the map's collision.hkt (E97690) is opened in 10BD40. As in EDF6, no record id ties a body to a placement; how the bodies are built and posed: map-placement.md#edf5-map-collision-pose.

Basis: fn.py ED040 ranges and --xref of the two suffix strings and collision.hkt; def +0x10 tallied with scratch File_Storage/Logs/catalog/mapb5.py edf5 f10

Addresses (build-specific RVAs unless indicated): ED040, ED109, 5BD270, ED1EB, E95458, ED25D, E95418, ED2FD, EAD32, E8CE9, F0A2E, E97690, 10BD40

Collision bodies take the same world matrix as the render: Preload_Model (ED040) looks up the hkt resource (k…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-map-collision-pose

Collision bodies take the same world matrix as the render: Preload_Model (ED040) looks up the hkt resource (kind string E95D28, EDD50) and calls DA450(hkt, obj+0x110, InitParam matrix, layer), which fills a Havok rigid-body info (757170), sets its first dword (collisionFilterInfo, physics-havok.md#havok-body-filter-info) to the layer, friction 0.8 and 0.5 (EE63C4, EE633C), byte 5 (motion type fixed, inferred from Havok's enum), poses it with 625200 and the placement matrix, and builds the bodies (E03B0; DFC50 for a one-shape hkt); 110CE0 then links them to the object with its record index +0x3C.

Basis: fn.py ED040, DA450; strings and floats with scratch vt_dump.py

Addresses (build-specific RVAs unless indicated): ED040, E95D28, EDD50, DA450, 757170, EE63C4, EE633C, 625200, E03B0, DFC50, 110CE0

Map collision layers follow the def category (Preload_Model EDDCC-EDEA8): 3 - 17 (0x11), 2 and 4 to 6 - 20 (0…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-map-collision-layers

Map collision layers follow the def category (Preload_Model EDDCC-EDEA8): 3 -> 17 (0x11), 2 and 4 to 6 -> 20 (0x14), 10 -> water (E8A80, no body), others -> 15 (0xF). Preload_Structure (F02E0) uses the same rule (F0820-F085E) but merges the .hkt shapes of all its parts, each at its own local position and quaternion (F0C50-F0C6B), into one fixed body posed by the placement matrix (F0D31-F0D77). Grown trees (E46B0) get a capsule (E45E0: from (0,0,0) to (0, rule 0 child 1's y, 0), radius half its z) on layer 20, posed by the tree's matrix (E49E2-E49F2).

Basis: fn.py ED040, F02E0, E45E0, E46B0 (E4960-E4A60); what each layer collides with not read (physics-havok.md#collision-layer-matrix)

Addresses (build-specific RVAs unless indicated): EDDCC, EDEA8, E8A80, F02E0, F0820, F085E, F0C50, F0C6B, F0D31, F0D77, E46B0, E45E0, E49E2, E49F2

EDF5's map.mapo per-record entry (0x1C bytes at mapo+0x08, count +0x0C = the record count

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapo-entry

EDF5's map.mapo per-record entry (0x1C bytes at [mapo+0x08], count +0x0C = the record count; the MAPO header's other pairs unread) has EDF6's fields (../edf6/file-formats.md#mapb-mapo-layout): +0x00 the .fmep piece pair (.fmep records only), +0x04 / +0x08 offset / count of self-relative pointers to part structs (count 1 on every .mdx, 1 to 127 on .mosb), +0x0C float 1000 on .mosb (0 on .mdx), +0x10 / +0x14 model and collision names on 16,771 of the 69,931 records over all 24 maps, always a _gr pair (sk_bd1020_gr01.mdb / .hkt; buildings, category 1: 6,898 .mdx and 8,292 .mosb; category 11: 612; category 6: 965; category 5: 4), +0x18 offset to a second {offset, count} part list (910 category-1 .mosb records). Who reads the _gr names was not found (_gr read as 瓦礫 gareki, rubble: inferred from the names).

Basis: scratch File_Storage/Logs/catalog/mapb5.py edf5 mapo and mapotally (output mapotally5.txt); the ten imul ..., 0x1C sites in C3650-C5937 only hand the entry to the InitParams

Preload_Structure reads its mapo entry with F1980 (from F0637): for each pointer in the +0x04 list and then t…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapo-parts

Preload_Structure reads its mapo entry with F1980 (from F0637): for each pointer in the +0x04 list and then the +0x18 list, a part struct with +0x08 offset to a rotation quaternion (turned into a matrix at F1B0D-F1C16), +0x0C offset to a position, +0x10 offset to a vec4 (default 1, 1, 1, 1), +0x20 offset to a model name (parts without one skipped), handed to EFBE0; the constructor then caps the def's draw distance +0x1C by the entry's +0x0C (F0673-F067D, squared) and by the +0x18 block's float +0x08. The structure's own part records (DA5E0, D27E0) carry the same layout plus +0x04 a .hkt name, +0x1C a distance and +0x24 / +0x2C LOD name and distance pairs. Def +0x1C is the draw distance in Preload_Model too (squared when over 0.01, ED715-ED72A; rocks 100 / 250 / 350), with +0x20 / +0x28 / +0x30 (name offset, distance) LOD pairs.

Basis: fn.py F1980, F02E0, DA5E0, D27E0, ED040; mapb5.py edf5 lods on ig_heigen507

Addresses (build-specific RVAs unless indicated): F1980, F0637, F1B0D, F1C16, EFBE0, F0673, F067D, DA5E0, D27E0, ED715, ED72A

Grown plants and small objects (.trb, .mlb)

On FMB ground (MapObject_Fmex), DBD40 walks the plant grids like EDF6's 140570 (edf6/file-formats.mdfmb-plant…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-grow-walker-fmex

On FMB ground (MapObject_Fmex), DBD40 walks the plant grids like EDF6's 140570 (edf6/file-formats.md#fmb-plants-cables): groups of 0x88 bytes at [[obj+0x160]+0x70] (+0x04 cell size, +0x08 columns, +0x0C rows, +0x10 / +0x14 origin x / z, +0x30 jitter byte grid, +0x50 type byte grid with 0xFF empty, +0x70 type records of 0xC8 bytes, +0x00 kind); jitters 16 bytes {angle, x, z, size} from [obj+0x160]+0x90; position ((column or row + jitter) x cell size + origin) through the ground's matrix (obj+0x70, +0x90, +0xA0); ground height per occupied cell from the mapo ground record ([[obj+0x160]+0x18], as in EDF6). It calls the visitor's slot 4 with (type record, cell index, x, height, z, angle, size); a visitor whose slot 3 is the default DB630 takes kind 0 (grass), MapObject_Fmex_GrowObjects (slot 3 DB930) kind 1.

Basis: fn.py DBD40 and its caller C5F10 (builds the GrowObjects visitor with vtable E96070 on the stack); not compared with a map file

Addresses (build-specific RVAs unless indicated): DBD40, DB630, DB930, C5F10, C5FC9

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-grow-walker-shf

On heightfield ground (MapObject_Shf), DDDB0 (called from DCE90, which builds the MapObject_Shf_GrowTree visitor, vtable E96310) walks one grid per heightfield: block at [[obj+0x160]+0x78]+0xA8 (+0x08 / +0x0C width / height, +0x18 / +0x1C size x / z, +0x4C offset to a grow block {+0x00 cells per heightfield step, +0x04 offset to type records of 0x28 bytes, +0x10 offset to 16-byte jitters}); 2 bytes per cell {type, jitter index}, type 0xFF empty. It calls slot 3 (DC880) with (type record, cell pointer, cell index, x, z, angle) and does not pass the jitter's size.

Basis: fn.py DDDB0, DCE90

Both grow visitors build a placed object's matrix as a yaw (the jitter angle

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-grow-object-matrix

Both grow visitors build a placed object's matrix as a yaw (the jitter angle; sine / cosine at 9C8246 / 9C8240) plus translation, with no scale: DB940 (Fmex) at DB9B7-DBA1A, y = the cell's ground height + the type record's float +0x0C; DC880 (Shf) at DC9F5-DCA5B, y from DC5F0, a downward ray from 505 (500 + 5) over 800 units at (x, z) (7542E0, 753A90), + the type record's +0x08. The Fmex walker passes the jitter's size factor as an 8th argument and DB940 never reads it, as EDF6's 140230 ignores its size range. Then by the type name's extension: .mlb -> E5480 (MapObject_AnyObject, 0x160 bytes), .trb -> E46B0 (MapObject_Tree, 0x110 bytes), with an InitParam {+0x00 loader, +0x08 index, +0x10 parameter SGO, +0x18 byte 1, +0x1C -1}; the index is the cell index (Fmex) or cell index + jitter index (Shf).

Basis: fn.py DB940, DC880, DC5F0; constants EE6750 500, EE65A8 5, EE6780 800 with scratch File_Storage/Logs/catalog/vt_dump.py; extensions E945C0 .mlb, E945D0 .trb

Addresses (build-specific RVAs unless indicated): DB940, DB9B7, DBA1A, DC880, DC9F5, DCA5B, DC5F0, 7542E0, 753A90, E5480, E46B0

MapObject_Tree (E46B0, vtable E966B8) copies the visitor's matrix, then E0BA0 reads the .trb SGO (rules, stri…

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-tree-build

MapObject_Tree (E46B0, vtable E966B8) copies the visitor's matrix, then E0BA0 reads the .trb SGO (rules, strings) with a 64-bit LCG (x 0x5D588B656C078965 + 0x269EC3) seeded by the InitParam index, so every tree's draws are the same on each load: a weighted pick of the model (rule 0 child 0), the stump model (child 3, or none), and a yaw rand(0..9999) x EE6178 (1/9999) x 2 pi; E4874-E48A6 rebuild the matrix rows from that yaw (a scale put into the visitor's matrix would be lost there) and keep the translation. Three leaf-record values get base + rand x span (rule 2 children 3, 4, 5 -> out +0x150, +0x154, +0x158; meaning unread); no size or height is randomized. A Havok body (E45E0, 757170, 625200 with the object's matrix +0x10) is built only when the rule's category (out +0x34) is not 0 (E497E).

Basis: fn.py E46B0, E0BA0; rule children matched to the field reads by their node offsets

Addresses (build-specific RVAs unless indicated): E46B0, E966B8, E0BA0, EE6178, E4874, E48A6, E45E0, 757170, 625200, E497E

.trb files (in the MAC

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-trb-rules

.trb files (in the MAC; 19 in ig_heigen507.mac, read as SGOs) hold rules with four records and strings (model names, then miki trunk and eda branch bones): rule 0 {0 model pick [[weight, [string index]]], 1 a vec3 like [0.5, 9.0, 0.5] for a 17 m tree and [1.0, 33.5, 1.0] for a 40 m one (-> out +0x40; the trunk's collision size, inferred), 2 category (2 on trees, 0 on bushes: no collision), 3 stump pick or 0, 4 [1000] on trees, [500] on a 4 m tree, [400] / [80] on bushes (-> out +0x1C; first taken for a durability, unverified; it goes to a Havok body property, map-objects.md#edf5-trb-1000-body-property, and is also the draw cut-off, map-lod.md#edf5-trb-distance-fields), 5 [50, 150] (-> +0x14 / +0x18; the billboard switch's near and far, map-lod.md#edf5-trb-distance-fields), 6 ["樹木" (tree)] (-> +0xF8)}; rule 1 the LOD model and two [value, 0.5] pairs (width and height of the far card, inferred); rule 2 the leaves (texture pick, then pairs like [2.0, 1.5], [2.5, 0.75], [5.0, 1.0], [6.0, 0.25], tint colors); rule 3 sway angles per bone. Model names carry the height (sk_ptree013_40m_sugi), so a map's tree sizes are a fixed set of models.

Basis: scratch File_Storage/Logs/catalog/trb_dump.py edf5 mac map/ig_heigen507.mac rules against E0BA0's reads

MapObject_AnyObject (E5480, vtable E96678

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mlb-anyobject

MapObject_AnyObject (E5480, vtable E96678; the .mlb small objects) reads its rule with E1D50: a weighted model pick, then a scale (out +0x00..+0x08, always 1.0), an offset (child 6 plus a random draw within child 3, E1C50), a rotation in degrees (child 5 plus a random draw within child 2, x pi / 180 EE669C, built at E212A-E215D), a color (x 1/255), and floats from children 8 and 9. E5480 multiplies the scale diagonal into the rotation (E5636-E567C, A5900) before adding the offset, so small objects already carry a per-object scale slot that the game leaves at 1. ig_heigen507's one .mlb (12 models: rocks, weeds, a can, mushrooms; inferred to be the .mlb) has child 2 [0, 360, 0] (a random yaw) and [[100], [100, 200]] in children 8 and 9.

Basis: fn.py E5480, E1D50; trb_dump.py

Addresses (build-specific RVAs unless indicated): E5480, E96678, E1D50, E1C50, EE669C, E212A, E215D, E5636, E567C, A5900
