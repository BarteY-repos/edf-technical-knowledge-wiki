Effects (EFS / ESB / EFARC)

EDF 6DocumentationFile Formats
Technical reference · Community-provided Japanese memo; source-specific and not independently rerun

At a glance

What this page covers: EDF6 effect content spans an EFARC archive and its effect, model and texture resources; an EFS/ESB entry is not interchangeable with an ordinary MDB material or audio bank.

How to use it: Read the effect-node tables as field-level experiments on named samples. A successful edit or a failure in EFS Tool is not, by itself, an observation of how the game runs.

Evidence boundary: The original workbook says an older NodeShape_Plane conversion-tool issue was later fixed; a separate modified ID1 case reportedly crashed in-game. Keep those two incidents distinct.

EDF6 effects are assembled from effect definitions, models and textures. They should not be confused with ordinary model materials or audio banks.

File and node hierarchy

Format/name Role
.efarc Archive resembling RAB; contains EFFECT, MODEL, TEXTURE folders in the tested examples
.esb Binary definition of an individual effect, typically referenced under EFFECT
EFS Effect-system graph/description; some weapon classes are EfsBullet or EfsMuzzleFlush
Singleton Contains a set of NodeTransform, RenderInfo and NodeColor components in the documented profile
Emitter A separate sibling component with emission geometry and timing

The workbook reports extraction/repacking through EDF Tools (repacking could produce .rab, then be renamed to .efarc) and XML conversion through EFS Tool. Tool support is incomplete. The workbook initially described EFS Tool conversion trouble with NodeShape_Plane, but its later efs!T12 note says that tool issue was fixed. This is separate from the in-game crash reported for a modified ID1 experiment at efs!B132:D133.

RenderInfo_Texture: experiment-backed fields

Source sample: E609_JORMUNGAND.efarc, head_large_laser_fire.esb, Singleton1. The author changed fields one at a time.

Field Observation Confidence
Texture Referenced DDS path, e.g. FLASHRING10.DDS Direct sample

Do not replace unk* values with invented enum names. The XML tool labels are partial, and many observations are subjective comparisons.

RenderInfo visual carriers: texture, model and trail are different data

EDF6 EFS RenderInfo is a family of components, not one universal material block. The dated community format notes describe an array of lighting-effect components first in each known RenderInfo subtype, followed by subtype-specific fields:

RenderInfo subtypeDocumented payload and purposeDo not assume
RenderInfo_TextureTexture path, scale, RenderMode 0–3, additional unknown switches, candidate PixelType 0/1, optional NodeMesh shape.RenderMode numbers reveal a proven native blending equation or GPU shader choice.
RenderInfo_ModelMDB model path within the effect archive, scale, reported RenderMode 0 normal / 1 translucent, two incompletely interpreted flags, and ChangeModelParams animation of material parameters.These settings replace the model's native MDB parameter ABI; a curve changes values, not the file-format contract.
RenderInfo_LocusExtendLineTextured trail extending behind a moving emitter/singleton; lifetime in frames, color, texture reference and an animated width curve.The trail is a rectangular sprite or has one fixed physical length independent of its history.
RenderInfo_RenderInfo_ExtLineTextured line from the original motion position toward the current point; length parameter in frames, color, texture and width curve.Its length/timing behavior is identical to LocusExtendLine just because both are line effects.

These are community-described serialized component roles, not disassembled EDF6 pixel-shader semantics. They explain why RenderInfo_Texture flags observed in ktaro's experiments cannot automatically be carried into Model, Locus or ExtLine effects. The original English/Japanese community notes also disagree on the direction of one rotation switch; this page keeps that field sample-specific rather than choosing an unsupported universal meaning. Underlying entries: Knowledge Hub 14 November edf6/effects.md#efs-renderinfo-*, based on EDF Modding Wiki's dated RenderInfo references.

Effect lifetime is not one global frame counter

Several levels carry their own time fields: an EFS root entry has a delay Timing (frames before dispatch), the contained Effect has SystemLifetime, an Emitter has its own emission rate and MaxParticle, a NodeParticle_Particle2D/3D carries particle Life in frames, and trail renderers carry length/lifetime fields. Animation curves can drive speed, scale, rotation and color independently. These should be read as separate inputs to different subsystems, not combined into a fabricated single effect_duration scalar.

That distinction is consistent with the contributor's 19 root-timing experiments below: the emitter, light and entire effect sometimes disappear at different times, and adjacent anim_frames values do not change visibility monotonically. Those experiments constrain the interpretation; they do not establish how every internal timer is updated by the engine.

Interpolation and emission geometry

NodeCIScale_All / scale > type was tested with these interpretations:

  • 0 and 4: the tested object was invisible;
  • 1: smooth-looking interpolation with potential overshoot;
  • 2: linear interpolation;
  • 3: step / no interpolation.

For NodeShape_Plane, the contributor observed that a rotation node changes emission direction; two float dimensions controlled rectangle width/height. In the tested setup, setting ID1 from 0 to 1 caused a crash. Other field meanings remain unverified.

RenderInfo_Model can reference an MDB and contains ChangeParams, including time-varying shader parameter channels such as diffuse RGBA. See Shaders for the ordinary MDB material path, which is not interchangeable with an ESB effect node.

Space/orientation caveat

The normal vector at an impact generally affects how an impact effect is oriented. In the DEMOMISSILE_VSRING.EFARC examples, certain NodeParticle_Particle3D > NodeVector_XYZ and NodeParticle_Particle2D > XScale/YScale values behaved relative to world axes. The workbook did not establish a universal world-space override for all nodes.

Workbook's 19 EFS-root timing probes (source-bounded)

The original workbook contains 19 named source-parameter combinations for root EFS unk1 and anim_frames, tested using a Tempest Final Option projectile (efs!B87:D112). In the author's observations: three combinations remained visible until impact; six lost the entire effect after about one second; six lost only the emitter plus point light; and four lost only the emitter. Examples:

unk1 anim_frames Contributor observation
−1 0 or 600 Elements remained visible until impact
0 0 Elements remained visible until impact
0 60 Emitter and point light disappeared after ~1 s
0 600 Whole effect disappeared after ~1 s
1 0 Only emitter disappeared after ~1 s
1 60 or 600 Whole effect disappeared after ~1 s

These observations are not monotonic in anim_frames; nearby configurations exhibit different lifetime outcomes. Thus there is no evidence for one universal “frame count = lifetime” equation covering every effect subcomponent. The author tentatively suspected interaction with another Effect unk2 field, without proving it. The full 19-case ledger, including negative results, is reference/R154_EFS_TIMING_19_SOURCE_EXPERIMENTS.csv. This is an original contributor gameplay experiment, not a new game run in the current wiki edition.

The NodeShape_Plane warning above is also historical and superseded within the original workbook: efs!T12 says the noted unsupported-case tool issue was subsequently fixed. The workbook still reports an in-game crash in a specific modified NodeShape_Plane ID1 test at efs!B132:D133, which must not be conflated with that XML tool bug.
