EDF5 versus EDF6: where T50 comes from

In the matched NW_EUROPE01 map pair, EDF5 has no native T50 or p58 tables at header offsets +0x50/+0x58, while EDF6 has 3,264 T50 rows and 77 p58 rows. The five active building families map across 751 building placements with identical T2 indices and matched piece cardinalities, so EDF6's graph is a new derived layer, not a verbatim converted EDF5 table.

The earlier source-owned convex/SAT proximity heuristic is not the native Sandlot collapse generator. In four paired building samples, it generated 17,020 vs 753, 24,531 vs 1,156, 29,161 vs 1,230, and 14,028 vs 617 edges, respectively. None matched native destination graphs; the sampled per-edge scalar had zero bit-exact matches. Nevertheless, every native edge in those four samples appeared among the much larger candidate graph. The missing semantic is how EDF6 prunes/selects candidates and derives its scalar, not how to write a T50 row.

Simplistic geometric threshold classifiers remained insufficient (F1 roughly 0.49–0.56 across four tested native graphs; the best measured single-example candidate gave F1 ~0.784 but still 188 false negatives and 123 false positives). Preserve native graphs when doing native reuse, and never label the old SAT graph a verified Sandlot cascade algorithm.

For authored static/dynamic prop bodies rather than cross-module links, see native destructible static/dynamic Havok bodies. For numeric collision-validator pitfalls, see Havok broadphase validation.

A destructible EDF6 building is not necessarily a collection of independent breakable meshes. The inspected native map data contains explicit connectivity between physical pieces of different building modules. MAPO carries this connectivity as T50, alongside p58 piece/support records, and the EDF6 CrashModel implementation consumes it as a pre-authored relationship graph.

This article explains the observed binary/runtime contract. The numeric observations below come from retained NW_EUROPE01 native data and a specific EDF6 EDF.dll build. They are not engine-wide constants.

Which resources are responsible?

Component Observed responsibility
MAPB T1 Resource/class identity, such as a .mosb building family
MAPB T2 Placement of a building resource
MAPO slot ranges Pieces/modules belonging to the placement
MAPO p58 Piece/support representation and per-slot grouping
MAPO T50 Pre-authored links between indexed pieces
MAD / Havok Physical bodies and collision representation; not a substitute for T50
CrashType in prop SGO Relevant structure-preload behavior; not itself the T50 graph

A complete reconstruction must keep these identities consistent: a T50 destination is meaningful only if its piece index resolves to a valid p58 piece and the intended runtime body.

Layout recovered from the MAPO loader

In the studied EDF6 loader, the MAPO header uses:

MAPO-relative offset Field
+0x50 T50 outer table address/reference
+0x54 T50 outer row count
+0x58 p58 outer table address/reference
+0x5C p58 outer row count

The parser walks existing 12-byte outer rows. A T50 row leads to per-piece 8-byte records, which each lead to a list of 8-byte edge records. For the examined edge record:

edge + 0x00 : 32-bit scalar / exporter metadata (float32-shaped)
edge + 0x04 : uint32 destination piece index

The original parser's distance_bits nickname for the first field was an inference, not a verified gameplay distance. There are also offsets inside rows and nested data; a parser must honor their own measured reference-base convention rather than treating the diagram above as a complete standalone serializer.

What the game actually consumes

Static EDF6 binary analysis followed this path:

MAC "map.mapo"
  -> MAPO parser / existing T50 row indexed by T2
  -> MapObject_CrashModel initialization
  -> CrashModel object's stored T50 reference
  -> runtime body-relationship builder

The identified runtime relation builder reads the T50 destination at edge+4, finds the corresponding physical body, and inserts a relation only if the bodies are valid. It checks existing pairs in both orientations before insertion, treating connectivity as undirected for deduplication.

In the complete inspected builder function, the edge+0 scalar is not read at the graph site; no scalar is passed into relation construction there. This is a strong reason not to expose the field as a mapper-facing distance control. It does not prove that no other executable path or tool uses those bytes.

The inspected loader reads T50 and p58 from already-authored MAPO data. It does not generate the entire graph from collision geometry when these tables are absent.

How much cross-module topology exists in native buildings?

The measured NW_EUROPE01.MAC census mapped native class-1 .mosb buildings from T1/T2 through slots, p58 pieces and T50 relationships.

Count in investigated set Result
Active building placements 751
Distinct referenced T50 templates 742
All T50 edges 708,064
Cross-slot edges 322,114 (45.49%)
Cross-slot structural-to-structural edges 290,461 (41.02% of all edges)
Building placements with cross-slot dependencies 751/751
Out-of-range edge destinations 0

This shows the links are not merely attachments to signs or other props. Observed chains directly connect 1F → middle → roof in native building families, and in other cases 1F → 2F → roof. Therefore destroying each authored floor independently cannot reproduce the native support graph.

A separate, broader native T50 check covered 722,757 edges and found zero self-edges or reverse duplicate pairs in that set. Native encoding uses the canonical lower source-piece index and higher destination index for such relationships. This is a wire observation, not a guarantee for arbitrary malformed files.

Creating a new cross-module collapse graph

A bounded source-owned writer can author undirected Collapse Links between module pieces, serialize each exactly once as (min(indexA,indexB), max(indexA,indexB)), and reject self-links, duplicates, reversed duplicates and out-of-range indices.

In the examined offline authored profile, each module deliberately had one p58 group and one p58 piece. One two-module example produced two pieces and one T50 link, while MAD and RAB remained unchanged. This established a format-level authoring method, not an EDF6 runtime PASS. A temporary zero scalar in newly authored edges is experimental; only a real game test can confirm that it preserves the intended collapse behavior.

Actual destruction propagation, debris/collision stability, save/reload and exact Sandlot collapse parity for newly authored T50 edges remain unverified in the examined sources. Preserving a native building's original graph is a different case from authoring a new one.

Checks for a parser, converter or editor

  1. Resolve a T50 outer row using the correct T2 placement index; validate table bounds.
  2. Derive piece indices through the actual slot/p58 ownership graph.
  3. Validate every link destination before assigning it to a body.
  4. Do not infer collapse from MDB visuals or static MAD geometry alone.
  5. Preserve native T50 metadata byte-semantically when doing native reuse.
  6. For new graphs, canonicalize undirected pairs and keep the unknown scalar hidden/experimental.
  7. Separate offline parse/export/graph tests from observed in-game building collapse.

See map prop SGO and CrashType, MAPB records and advanced authoring systems.

Evidence: native NW_EUROPE01 T50 census (five active building families), later full edge-pair census, static EDF6 CrashModel binary consumer analysis and bounded source-owned topology proof. Neither a universal edge-scalar rule nor in-game acceptance of newly authored collapse links has been established.

Exact native EDF5/EDF6 NW_EUROPE01 MAPO difference

A matched native-map pair shows that EDF5 and EDF6 do not merely differ in the size of the same T50 payload:

MAPO header datum EDF5 EDF6
Object count (+0x08) 3,088 3,264
Slot count (+0x20) 14,194 14,370
Descriptor +0x30 / +0x38 / +0x40 175 / 16 / 33 175 / 16 / 33
T50 count (+0x50) 0 3,264
p58 count (+0x58) 0 77

The paired EDF5 collision/body data can constrain how native EDF6 p58 and T50 were derived, but EDF5 offers no T50 bytes to copy. Four representative EDF6 T2 instances contain only 753/1156/1230/617 native edges, whereas an overinclusive source collision-proximity rule produced 17,020/24,531/29,161/14,028 candidate edges. Geometry proximity does not recover the proprietary selection rule.

The native loader path in the checked EDF.dll is anchored at EDF+0x117F90 (map.mapo), EDF+0x11FE90 (normalization), EDF+0x11F410 (T50 parsing), EDF+0x11EF30 (p58 parsing), EDF+0x118CD0 (T2-indexed T50 handoff), EDF+0x12C2C0 (CrashModel construction), and EDF+0x13A520 (body relation creation). The inspected relation builder uses the edge+4 destination and deduplicates A↔B pairs. These offsets apply only to EDF.dll SHA-256 0d5092393a1b9d8f1b75b0c93d8a8f65615a36a92c46e40349c2b66c733d0916.

A separate full static census found 9,022 distinct float32-shaped patterns across 708,064 native NW building edge records. The simple p58 radius/center/support-distance metrics had weak correlations (highest examined structural cross-slot absolute Pearson correlation about 0.225). The scalar is not a small categorical flag. Later engine inspection, however, showed the first scalar not being read by the identified CrashModel relation constructor. These statements are compatible: stored numerical variation does not prove the examined gameplay code consumes it.

For the separate case where identical rock families carry multiple T50 graphs within one slot, see HEIGEN507 rock-set T50 variants.
