Trees

EDF5 tree model construction and .trb loading

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-tree-classes

Tree classes: MapObject_Tree (E46B0) reads its .trb with E0BA0 (out struct at rbp+0x190) and builds its render model with the factory E2CF0 (E48E6): TreeSkinningModel (vtable E973E8, 0xF0 bytes) when a check on the loaded model resource (its slot 1, E2DDD) passes, else TreeModel (E97480); with the factory's flag argument 1 it builds TreeBrokenModel (E97428, constructor 1054D0, 0x1C0 bytes) plus its own TreeRenderer_Umbra node (vtables E974F0 / E974D8, constructor 106670), a path used only by E6910 (from E4230, E3350; it builds a Havok body first, inferred to be the felled tree). The factory calls the model's slot 1 with the out struct at E313F.

Basis: RTTI names and vtables (scratch rtti.py), fn.py E46B0, E2CF0, 1054D0, 106670, --xref E2CF0, --xref E6910; the felled-tree reading inferred

Addresses (build-specific RVAs unless indicated): E46B0, E0BA0, E2CF0, E48E6, E973E8, E2DDD, E97480, E97428, 1054D0, E974F0, E974D8, 106670, E6910, E4230, E3350, E313F

Standing tree registration in MapTreeMgr

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-tree-blocks

Standing trees are filed into MapTreeMgr: E4979 calls 103E90 on the manager at map loader [125ABA8]+0x278 (the loader's C7570 makes it, with TreeBlocks from constructor 103930; MapTreeMgr vtable E973D8, MapTreeMgr::TreeBlock E973B8). TreeBlock slot 1 103E20 draws a block: 104170 walks its list at +0x70 and 103D40 / 1042C0 call each model's slot 4 (+0x20). TreeRenderer_Base has vtable E97528; TreeRenderer_Billboard and TreeModel_Particle have RTTI names but no vtable of their own.

Basis: fn.py --xref on the TreeBlock and MapTreeMgr vtables and on 103930; fn.py C7570, 103E20, 104170, 103D40, 1042C0

Addresses (build-specific RVAs unless indicated): E4979, 103E90, 125ABA8, C7570, 103930, E973D8, E973B8, 103E20, 104170, 103D40, 1042C0, E97528

Tree billboard distance initializer

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-trb-distance-fields

The distances: the billboard init 104490 (called from the TreeModel / TreeBrokenModel init 104760 at 104A82 and from the TreeSkinningModel init 105B80 at 1061B1, its only two callers) copies the .trb out struct's +0x14 / +0x18 (rule 0 child 5, [near, far]) to model +0x18 / +0x1C and squares each when positive (10463E, 104651), and stores model +0x20 = cut-off², the cut-off from out +0x1C (rule 0 child 4) or 500 m (EE6750) when it is negative (10462A, 10462C). So child 4, [1000] on most trees, is the draw cut-off as in EDF6; the same value also goes to a Havok body property (map-objects.md#edf5-trb-1000-body-property). 104760 first passes min(far, cut-off) to the model's slot 7 (1049C3..1049EB; use unread).

Basis: fn.py 104490, 104760, --xref 104490 (2 callers); EE6750 read as 500.0 (00 00 FA 43)

Addresses (build-specific RVAs unless indicated): 104490, 104760, 104A82, 105B80, 1061B1, 10463E, 104651, EE6750, 10462A, 10462C, 1049C3, 1049EB

Tree mesh-to-billboard selection formula

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-tree-billboard-switch

The mesh-to-billboard switch, in TreeModel / TreeBrokenModel slot 4 104B90: x = |tree position - camera position|² x view+0x18 (104BFC); above cut-off² +0x20 nothing is drawn (104C06); pass 2 and passes above 3 draw nothing; with near² +0x18 <= 0 or x <= near² the full mesh; between near² and far² +0x1C mesh plus a band value 1 - (x - near²) / (far² - near²) (104C3A..104C56, 1.0 at EE6430) handed to 104CD0 in passes 0 and 3 (leaf cards, inferred from EDF6's 178010); beyond far² only the billboard (slot 6 1046B0), in pass 0 and only when the texture +0x28 exists. The mesh goes through the map-prop draw 100D30 (104C8B; models.md#map-prop-lod) when slot 8 is the stock 1053C0. TreeSkinningModel's slot 4 106290 has the same cut-off and billboard tests but no band: full mesh up to far² (106321..10635D).

Basis: fn.py 104B90, 106290; EE6430 read as 1.0; pass meanings not read

Addresses (build-specific RVAs unless indicated): 104B90, 104BFC, 104C06, 104C3A, 104C56, EE6430, 104CD0, 1046B0, 100D30, 104C8B, 1053C0, 106290, 106321, 10635D

Stock EDF5 tree LOD distance census

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-trb-distance-values

Stock tree distances over all EDF5 maps (149 .trb SGOs counted once per map MAC): near is 50 m on every tree and 10 m on bushes and a few city trees (sk_tree10m01a, sk_tree15m02a); far 100 to 180 m on trees ([50, 150] 38, [50, 100] 24, [50, 120] 21, [50, 170] 14), 50 m on small plants; cut-off 1000 m on trees, 500 m on the 4 m sk_ptree001_4m_kakuremino, 400 m or 80 m on bushes and shrubs, 150 m on one ([10, 250]). So a tree is a full mesh only within 50 m, crossfades out to 100 to 180 m, and is a billboard card to 1000 m.

Basis: scratch File_Storage/Logs/00v/trb_tally.py edf5 (output e5_trb_tally.txt): every map/*.mac, SGOs whose rules rule 0 child 5 holds two numbers

Buildings

Structure part LOD table

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-structure-lod-table

The LOD table per structure part: EFBE0 (called per part by F1980, map-placement.md#edf5-mapo-parts) loads the full model into slot 0 (FFB90, with the part's +0x1C), then for i = 1, 2 (loop EFD20..EFE13) takes max(def +0x24 / +0x2C, part +0x24 / +0x2C) (EFD3D, EFD43), and when that is above 0 and the part names a model (+0x28 / +0x30, offsets relative to the part) loads it and stores {model, distance} at [[obj+8]+0x80] + 0x10 x i (EFD8B, EFD96). Unlike EDF6's 151310, no global multiplier is applied: the data value goes in unchanged. 100080 (called three times from Preload_Structure's constructor, F069C..F0702) turns each slot into a 0x38-byte LOD unit, the distance at unit +0x30 (1008A5..1008B1).

Basis: fn.py EFBE0, F02E0, 100080 (scratch File_Storage/Logs/00v/e5_*.txt); slot 0's own distance (set in FFB90) not read

Addresses (build-specific RVAs unless indicated): EFBE0, F1980, FFB90, EFD20, EFE13, EFD3D, EFD43, EFD8B, EFD96, 100080, F069C, F0702, 1008A5, 1008B1

Hard per-frame map LOD transition

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-building-lod-pick

The per-frame pick is a hard switch, as in EDF6: 100EC0 (beside the instanced-draw vtable E96610) passes the node's +0x24, the Umbra object distance metric (squared camera distance x the commander's +0xD8, models.md#umbra-object-distance-metric), to 100D30; for each 0x50-byte node ([obj+0x68], count +0x78) it skips the node when its cull value +0x00 is above 0 and not above d (100DB0..100DBC), needs flag bit 0 of +0x24, then walks the units (+0x30, count +0x40) while d is above the unit's distance and keeps the last such unit with a distance of 0 or more in +0x22 (100DE4..100E00); only that unit is queued (FEC80, 100E3D). One LOD per node per frame, no blend; the same pick draws trees' meshes (#edf5-tree-billboard-switch) and .mdx props.

Basis: fn.py 100D30, 100EC0, --xref 100D30 (callers 100ECF, 104C8B, 1053C7)

Addresses (build-specific RVAs unless indicated): 100EC0, E96610, 100D30, 100DB0, 100DBC, 100DE4, 100E00, FEC80, 100E3D

Stock LOD distances over every EDF5 map (map.mapb defs, size 0x38, weighted by placements

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-building-lod-values

Stock LOD distances over every EDF5 map (map.mapb defs, size 0x38, weighted by placements; def +0x1C the draw distance in meters, squared at load, map-placement.md#edf5-mapo-parts; +0x24 / +0x2C LOD 1 / 2 in squared meters): type-1 .mosb buildings (8,365 placements) mostly [22500, -1] (150 m, no LOD 2; 2,854), [10000, 90000] (100 / 300 m; 2,014), [10000, 40000] (100 / 200 m; 773), [22500, 40000] (495), [10000, 62500] (385), [22500, 62500] (249), houses [6400, 22500] (80 / 150 m; 244), 105 with none; all drawn to 1000 m. Type-3 .mosb (5,487) [22500, 90000] or none; .mdx props 2500 to 40000 or none, poles and fences drawn only to 100 to 300 m. So most buildings switch at 100 to 150 m, as in EDF6 (../edf6/map-lod.md#edf6-building-lod-values).

Basis: scratch File_Storage/Logs/00v/lodtally5.py edf5 (output e5_lodtally.txt): every map/*.mac's map.mapb, placements counted per def

Shaders for a fade: EDF5's DX11.cpk holds 16 shader/dx11/snd_map_build_.sgo and 4 snd_map_lod.sgo

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-lod-fade-shaders

Shaders for a fade: EDF5's DX11.cpk holds 16 shader/dx11/snd_map_build_*.sgo and 4 snd_map_lod*.sgo; snd_map_build_basic and snd_map_lod are instanced (g_instancing_array, g_instancing_inv_array, xgl_user_param m_instancing_array_stride +0x00) and take only per-material xgl_user_param values (diffuse, change_color, normal_amount, specular, light_smooth, metallic, roughness, fall-off, dirt_adjust; the LOD shader a shorter set): no per-object fade, alpha or dither input, as in EDF6 (../edf6/map-lod.md#edf6-lod-fade-shaders). snd_map_build_simple_alpha and _simple_clip exist (not read).

Basis: DXBC RDEF chunks parsed with scratch File_Storage/Logs/00v/sgo_cb5.py (output e5_sgo_cb.txt)

Route and open questions

Data-only proposal for distant full-mesh treesSource: unverified

Evidence: unverified · Build: steam-5d11de53 · Fact ID: edf5-tree-lod-route

Route for "keep distant trees as full meshes" in EDF5 (00v topic 1): data, set each .trb's rule 0 child 5 near to 0 or below and raise child 4 for a longer cut-off (.trb files sit in each map's MAC; child 4 also feeds Havok body property 7, whose reader was not found); or code, one 5-byte patch at 104642 F3 0F 11 4F 18 (movss [rdi+0x18], xmm1) -> F3 0F 11 57 18 (store xmm2, zeroed at 104624): near² 0 for every tree, both model kinds, since 104490 serves them all (state 0 to the cut-off); a longer cut-off in code needs a cave around 10465A (the cut-off² store). Risks as in EDF6: draw cost (every leaf mesh out to 1000 m), the map's FarClipZ, the TreeBlock's culling. Open: the writer of view+0x18 (an Umbra Commander scale like models.md#umbra-object-distance-metric's +0xD8, inferred), the model's slot 7 (min(far, cut-off)), whether 100D30 also switches a tree mesh's own _lod units, and the leaf card scaling in 104CD0. Nothing here was run in game.

Basis: novae (ajane); the route inferred from #edf5-trb-distance-fields and #edf5-tree-billboard-switch

Addresses (build-specific RVAs unless indicated): 104642, 104624, 104490, 10465A, 100D30, 104CD0

Attribution: KH chat 171 (curator, autorun 00v) · 2026-11-14

Proposed building LOD distance overrideSource: unverified

Evidence: unverified · Build: steam-5d11de53 · Fact ID: edf5-building-lod-route

Route for buildings' LOD in EDF5 (00v topic 1b): (a) push the switch out in data, per map: each map.mapb def's +0x24 / +0x2C (squared meters, so 4x the value doubles the distance) and the mapo part's +0x24 / +0x2C, since EFBE0 takes the larger of the two (#edf5-structure-lod-table); EDF5 has no global float like EDF6's [17698D8] (../edf6/map-lod.md#edf6-building-lod-route), so the code route is a hook at EFD3D..EFD47 (the load and maxss, about 10 bytes; read the bytes first) that multiplies xmm6 by a factor, once per part at load; (b) a gradual fade needs, as in EDF6, both neighboring units queued inside a band in 100D30, a per-instance factor, and modified snd_map_build_* / snd_map_lod* pixel shaders that discard pixels by a dither pattern against that factor (they have no fade input today, #edf5-lod-fade-shaders). Open: slot 0's distance in FFB90, the node cull value +0x00 (copied from the part's +0x60 at 1007E0), the writer of the Umbra commander's +0xD8 (a zoom factor would move the switch), the shadow pass's pick. Nothing here was run in game.

Basis: inferred from #edf5-structure-lod-table, #edf5-building-lod-pick and #edf5-building-lod-values

Addresses (build-specific RVAs unless indicated): EFBE0, EFD3D, EFD47, 100D30, FFB90, 1007E0
