RAB — named resource archive and SSA entry layout

File FormatsSource-scoped referenceEDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: A RAB is an archive of individually named game resources, such as models and textures. Think of it as a directory containing separate assets, each with a name, type and stored location.

Where it fits: The studied EDF5/EDF6 RAB family uses an SSA header and directory entries. Individual resources can be stored plainly or wrapped in CMPL compression.

Important distinction: A RAB tells the game where a resource is; the resource's own format determines how to interpret its contents.

File-level structure (measured SSA family)

The examined container header occupies 0x28 bytes with ten little-endian 32-bit words. Key fields include:

Offset Field Role
+0x00 magic SSA\0
+0x04 version Observed 0x110 in the cited archive profile
+0x08 content_start Entry payload region in the studied serializer
+0x0C Maximum stored member size Must be recomputed after changing members
+0x10 Maximum decompressed member size May come from a different member than the maximum stored size
+0x14 entry_count Number of resource entries
+0x18 info_pos Absolute entry-table offset
+0x1C names_pos Name-lookup table offset
+0x20 / +0x24 type_count / type_table Type string directory

An entry occupies 0x20 bytes. Its measured layout is:

Entry offset Stored value Interpretation in the cited sources
+0x00 Relative name offset Relative to this field; points to a UTF-16 name
+0x04 Stored payload size Includes the compression envelope, if present
+0x08 File type index Index into the archive-local type table
+0x0C Fourth word Documented as 1 for HD-TEXTURE, otherwise 0 in the examined guide; round-trip writer preserves the original value
+0x10 Eight bytes Original guide calls this a Win32 FILETIME; in the shipped data examined by the later round-trip source, these bytes were zero
+0x18 64-bit absolute data offset Stored payload position in the outer archive

The name pointer is relative to the entry record, while the payload offset is absolute. Confusing those bases leads to invalid extraction. The two sources have different evidence scopes for +0x10: a field label from the format guide versus observed zero bytes in the tested stock archives. The zero observation does not establish that every possible RAB uses zero there.

Name lookup and archive order

  • The studied name index has 8-byte records: relative UTF-16 name offset plus file index. It is sorted case-sensitively, so uppercase Z precedes lowercase a.
  • The type-name table has 4-byte entries, each pointing relatively to a type string.
  • The source's round-trip comparison found that the order of names in the string pool and sorted index can differ among shipped archives. The author preserves each archive's existing order when editing it; the research does not supply a universal regeneration rule.
  • The studied payloads follow the tables without padding. A decoder should use the stored offsets, not assume fixed alignment.

What may be stored inside

The researched RAB records can contain texture and model resources as named payloads, including DDS and MDB bytes. A payload may have a CMPL compressed envelope. A valid RAB entry only proves the resource is packaged; it does not establish that the inner model is compatible with every EDF renderer.

In the bounded source controls, byte-identical SSA round-trips were reported for RABs with 5, 279 and 424 entries. These are sample sizes, not a format limit.

Names, types and conflicts

The entry name, type string and archive-local type index are three different identities. Type indices are not globally portable across archives. When studying a resource, resolve its name and type string rather than treating the numeric index as universal.

Source research on mod compatibility describes entry-level merging by unique resource name. Two edits to the same named model or texture can still conflict; packaging success does not validate the inner data or mission image ordering.

Loading order matters

In the EDF6 OBJECT/ archives examined by the native-loader study, archive members appear in directory-table order: low-resolution TEXTURE resources first, then MODEL, then HD-TEXTURE. The loader resolves textures from its current table while the model loads. Consequently, putting the texture member after the model can leave that model with an unbound texture, reported as a black rendering result. Later HD-texture streaming is a different stage. This is a measured rule for those archives, not a general promise about every archive consumer.
