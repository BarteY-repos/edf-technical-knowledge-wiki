EDF6 Weapon Selection UI Layout and Callback Ownership

EDF 6Community Knowledge HubNative UI & Input
Technical reference · Editorial synthesis of contributor static/game observations; per-claim grades below

Overview

The EDF6 weapon-selection interface is backed by loaded layout assets and native UI classes. A custom picker must preserve the layout callback contract and avoid treating a visual resource edit as sufficient behavioral integration.

Format, API or behavior

The contributed analysis identifies the layout-load chain, callback registration, weapon-select layout and window-skin geometry. Native layout instances and named callbacks determine whether a button activates real game behavior.

Ui layout load chain — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (1,164 characters)

A HUi screen opens by path: 845250(uiMgr, out, path, args) calls 119C600(uiMgr+0x48, out, path, args), which normalizes the path (AC8A0), takes the parsed SGO from the resource cache (84E80 on global 20B28D0, refcount +0x70), reads the class name from the SGO variable xgs_ui_object_class (name at [1FEEEC0]), finds the factory in the class registry map (119B7B0) and calls factory vfunc +0x10 (119CAB2) with the parsed SGO at context +8. The weapon select is opened at 8AA4D7 by 8AA250 (called from 8ADEC0) with app:/ui/lyt_HUiHQWeaponSelect.sgo (string 1805C30); its factory 8B2550 creates the screen with constructor 8B4280. The HUi base constructor 83E6F0 stores the parsed SGO at this+0x70; 84A920 (from 83EB2E) reads render_mode, ui_type, lyt_NoSlideScreen and layout_tree and builds the element tree (8436E0 / 841800). Layout values are copied into live elements once at construction and the code then reads only the elements, so a replacement .sgo changes a layout with no code hook, while a memory patch has to write live element fields after the constructor returns, not the SGO buffer. Whether reopening a screen reuses the cached parse was not checked.

Ui register callback — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (732 characters)

Button callbacks register by name on the HUiLayout base with 850810(layout, std::wstring* name, shared_ptr functor*) (EDF5: 4E9610): the call inserts into a map at layout +0x4E0 (nodes 0x50 bytes, key +0x20, shared_ptr +0x40 / +0x48). The functor is a make_shared object of 0x38 bytes: +0 control-block vtable 18068F0, +0x10 agent vtable 18061E0 (slot 1 8B7890 = invoke), +0x18 / +0x20 weak pointer to the owner, +0x28 a member-function pointer plus adjustor. The handler receives an object whose virtual slot 0 returns a pointer to an int, the pressed element's id. Element events (for example focus on a template) register through 850A00. A plugin could register handlers for new buttons of a modified layout (on paper, untested).

Ui weaponselect layout — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (1,409 characters)

The equipment screen's list shows 5 rows because of layout values in ui/lyt_huihqweaponselect.sgo (Root.cpk, 17,928 bytes unpacked; xgs_ui_object_class HUiHQWeaponSelect): the viewport WeaponSelectArea and each column WeaponColumns are 201 px tall and a cell WeaponSel_CellBase is 40 px (201 / 40 = 5); nothing in code sets a row count. Elements (position; rect w x h; flags; params): WeaponSelectArea (18, 67); 1162 x 201; [2048, 32768]; scroll_mergin [200, 0, 200, 0], stencil 1 (clips the columns). WeaponColumns 355 x 201; [256, 2048, 4]; scroll_bar_info [LeftScrollBarBase, LeftScrollBarKnob], scroll_mergin [0, 22, 0, 22]. WeaponSel_CellBase (Button, callback PressButton) 355 x 40, font_size [24, 24]. WeaponLevelCell x 250 and WeaponQualityCell x 293, each 43 x 40, font 24. WeaponIndexArea (column headers) (18, 23); 1162 x 39; [2048, 128] (horizontal scroll). WeaponNew (skin WeaponNew01_skin.sgo) and WeaponUp (WeaponUp01_skin.sgo): each its own 45 x 15 element at (204, 1) in the cell. Frames WindowUpper (191, 147) 1187 x 302 and WindowLower (256, 468) 1130 x 498 use window skins whose base SGO ui/window06_weaponsel1.sgo is a 3D model (animation_model Window06_WeaponSel1_merge.rab / .mdb, with .b.rab and .c.rab variants, perhaps story-dependent backdrops; unverified). Flag 800h scrolls to keep the focused child in view, inset by scroll_mergin (../edf5/ui-menus.md#settings-scroll-by-focus).

Ui weaponselect layout edit — verified

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (978 characters)

A loose Mods/UI/LYT_HUIHQWEAPONSELECT.SGO with 13 float values edited in place shows 9 weapon rows instead of 5, and the resized frames (upper window taller, lower window moved down and shortened) keep clean corners and edges. The stat-line area WeaponDescParam neither clips nor scrolls: with its height cut from 364 to 204 px (28 px per line, room for 7), a gunship weapon with 10 stat lines drew its last three lines (Shots, Laser Sight, Zoom) outside the window, down to the guide bar. The description text (WeaponDescArea) does scroll with the mouse wheel in its shorter area. Edited values: WeaponColumns and WeaponSelectArea height 201 to 361, LeftScrollBarBase area height 245 to 405, UnderScrollBarBase y 279 to 439, WindowUpper height 302 to 462, WindowLower y 468 to 628 and height 498 to 338, WeaponDescArea and WeaponDescParam height 364 to 204, ScrollBarBase area height 451 to 291, TextDownButton y 476 to 316, DescSeparatorLine y / height 516 / 412 to 676 / 252.

Ui skin window corners — static

This detailed research record is also present in the linked source appendix. Read the original source and evidence context; the literal duplicate is preserved below for comparison.

Full duplicated research record — expand (988 characters)

ui::Skin_Window (vtable 17F6308, per-instance class vtable 17F6358, factory slot 7 7F7830, 0x620 bytes; sgo params base, size, scale, animation_model, material_animation, prog_control_color, Color) sizes its 3D frame by moving four corner nodes: setup 7F78C0 looks up the nodes LT, RT, LB, RB (strings near 17F6348) and stores their indices at model +0x600 / +0x604 / +0x608 / +0x60C; update 7F7AE0 (slot 3) builds node matrices with the diagonal equal to the scale [this+0xB0] and translations LT (x, y), RT (x+w, y), LB (x, y+h), RB (x+w, y+h) (7F7B8F..7F7D23, via 1100280), then 1100F10 and two 1104100 draws. The corners move at a constant uniform scale; the model is not scaled. Whether that reads as a 9-slice depends on the .rab's skin weights (not read; but see ui-weaponselect-layout-edit: the frames stretch and shrink cleanly in height). 7F7040 is slot 3 of ui::Skin_Texture (vtable 17F6228), not Skin_Window (it interpolates a rect and multiplies by the render context scale).
