EDF6 native map resource families: grass, water, LOD and destructible structures

EDF 6Maps & NavigationMaps
Source-backed research / case study · Reconciled

Map vegetation, static water, LOD and destructible parts are not a single binary prefab/resource mechanism. The following findings are from named EDF6 native resource studies; some later conversion/serialization experiments remain runtime-unverified.

Vegetation: grass registry and GRB regions

The EDF5-derived DESERT508 port contained grass.merge.sgo with one species and ig_grassdens2small.grb; the independently examined native EDF6 HEIGEN507 had five registry species but no explicit .grb MAC block. The Desert example is an EDF6 runtime-accepted compatibility profile, not a native-EDF6 authoring oracle. Consequently, T1 Class 6 is not a universal 'no grass' mask. The exact roles must be interpreted per map/resource family.

Two species profiles studied in conversion experiments were sk_grassleaf504a (exact EDF5-derived port source, not native EDF6 oracle) and sk_grassleaf501a (a distinct HEIGEN profile). The source-ported Desert case had a positive EDF6 runtime observation, but newly authored regions and alternate-species substitutions lack equivalent runtime evidence. Structural build success by itself does not prove native EDF6 density/culling/visibility.

Water: shader and texture dependencies

The retained four-map material census found one ordinary snd_BRDF_Map_Water MDB family and no reason to invent separate universal River/Ocean shader families. Related source parameters include bubble and water-normal DDS/LOD resources, color/specular/roughness, blend/depth, UV scaling/scrolling, two bubble-layer controls and three normal-layer controls.

This is a bounded source-family observation. It is not proof that arbitrary user-generated water will have correct transparency, depth, scrolling or physics in EDF6.

LOD: geometry and material are separate choices

A reduced-geometry model does not automatically require snd_BRDF_Map_LOD; ordinary shaders can appear on valid distant model assets. Exact asset stems and runtime linking are family-specific. See native LOD/FarMap evidence.

Destructibles: Havok bodies and collapse edges

In a bounded native HEIGEN donor model, sk_rock501a_l.mdx has a static primary sk_rock501a_l.polymsh1 body (motionType=0) and a dynamic debris sk_rock501a_l_hk.polymsh1 body (motionType=2, mass=5.0, motionPropertiesId=1). This does not establish those values as universal for every EDF6 destructible.

The MAPO T50 collapse-graph research found 708,064 edges across 751 active building placements, including 322,114 cross-slot links. The recovered CrashModel consumer uses edge destination indices; the earlier distance_bits label was not an established field meaning. See MAPO T50 graph.

FieldRender terrain is a separate renderer path

FMEP projected field-terrain weights, ordinary MDB/static model materials and vegetation resources must not be fed through one universal material schema. Source descriptions of a drawing feature are not proof of a native EDF6 resource class.

Evidence boundary: Specific native resource/corpus observations above are source-backed. Broadly authored grass/water/LOD/debris or collapse combinations require game-runtime confirmation rather than inheriting offline serialization PASS.

Native MAPB/MAPO and map authoring contracts

Source: hajisensai / All Forces docs/xmorph-maps.md, docs/edf41-map-mac-format.md and docs/edf41-sk-terrain.md, build steam-678ccb46. These are source-attributed static claims unless marked unverified; reported game checks are not newly reproduced.

MAPB structures, pointer relocation and writer order

Static: MAPB has a shared 0x90-byte version-2 header in 4.1/5/6: strings +8/+0xC, defs +0x18/+0x1C, records +0x20/+0x24, point blocks A/B +0x78/+0x7C, and twelve self-relative SGO slots. EDF4.1/5 use slots for weather/light, EDF6 mostly zeros them and keeps two empty SGOs at +0x70/+0x88 because weather moved to MAE. The apparent unused slots are part of the serialization contract.

Static paired census: EDF6 inserted one dword at definition +0x20, expanding the EDF5/4.1 stride 0x38 to 0x3C. This alignment matched all 1,179 same-name paired defs; an incorrect +0x24 insertion produced 178 mismatches. The new word is 1 in 165 EDF6-only defs and zero elsewhere. Existing name/LOD self-relative fields beyond it shift by four bytes.

Static: MAPB placement grows 0x44→0x48, adding EDF6 word +0x44, zero in the surveyed corpus. Both generations retain def, XYZ, Euler, child-record index list +0x2C and GUID +0x34. Point block A contains vec3s and named u16-quartet lists; B contains electric-wire points, pairs and self-relative wire-name pointers. Rebase those internal names if relocating B.

Static 92-file inspection: each embedded MAPB SGO is self-contained and 4-aligned. EDF6 writer order: header, defs, child lists, records, block A, block B, def SGOs in index order, slot SGOs +0x88 and +0x70, then first-use-ordered UTF-16 strings. Earlier games sort strings and serialize SGOs in different order; equal decoded semantics need not mean byte-identical output.

Static stock-derived example: no-wires/no-routes MAPB from IG_CAVE605/NW_RINKAI01 still includes the two empty slot SGOs, point A's zero-count block and a pointer to elec_wire_default.elec, plus point B's stock six-word block {0,0,0,0,-4,1}. “No wires” is not permission to null all B references.

Static generator example: MAPB def uses type 3 for ground, 1 for others, relative SGO/name pointers, +0x10=-1, +0x18=100, +0x1C=1000 far draw cutoff, +0x28/+0x30=-1, rest zero. Ground SGO is adapted from IG_TEST_BLUEFLD; filenames, Disappear, Durability and Type are changed for buildings. The earlier “near cull” label for +0x1C is corrected.

Static orientation test: Y rotation θ sends local X to (cosθ,0,-sinθ) and local Z to (sinθ,0,cosθ). The author compared NW_DANTI01 fence neighbors (282 matching pairs versus 162 under opposite sign). Tool-generated GUIDs derive from map/index; record +0x1C=0 invokes the GUID-sum seed, not an arbitrary per-instance animation flag.

MAPO companions and generation-specific tables

Static: MAPO header is 0x58 in 4.1/5, 0x60 in EDF6 with a new nested +0x58/+0x5C table. Object stride is 0x38 in 4.1 and already 0x3C in EDF5/6. Named rows +0x50/+0x54 are empty in older games, one per placement in EDF6. Its writer serializes vectors, object rows and pointers, per-record entries, grass, nested tables, named rows and final deduplicated UTF-16 strings in this order.

Static correction: MAPO 0x1C-byte companion holds grass pair +0, object array slice +4/+8, float +0xC, model/collision name offsets +0x10/+0x14 and +0x18 pointing into the +0x10 (int,int,float) array, not the new +0x58 table. Old 4.1 empty entries may hold uninitialized words; EDF5/6 largely clear them. Named row is decimal placement index plus float/int pairs.

Static stock-example writer: a plain object gets a 0x3C row referencing <model>.hkt, zero vec3, <model>_hk.mdb, <model>.mdb; one self-relative object pointer, one 0x1C companion, one 0x0C decimal-index name row and sorted strings. The named _hk.mdb need not exist in the RAB: IG_TEST_BLUEFLD itself lacks it.

FMB terrain, shader texture and collision dependency

Static loader scan: the examined EDF6 binary has no shfb, fld2mgrid or cols.sgo reader strings; terrain uses FMB .fmep pieces and color/normal texture arrays. The author's Havok migration helper also cannot represent older heightfields. This does not rule out a third-party loader but precludes a direct stock SHFB conversion assumption.

Static 9,753-mesh census: each stock leaf's FMB word +0x24 uses layer count times 0x101 in the observed equal-count layout; +0x28 selects its shader table row. The per-layer 0x50-byte records specify tile orientation and color/multiplier/normal slices. Further 6.0/1.0 constants have unknown meaning; the writer copies following stock tables from IG_HAIKYOPLANE01, not from a proven universal generator formula.

Static: FMB terrain binds RAB entries <map>_color.dds and <map>_normal.dds; the binary builds names at 152A06. ig_flat_normal.dds appears in stock IG_CAVE603 as a valid plain-normal sample.

Static limitation of the examined map shader: no direct per-vertex terrain-layer color blending is provided on this ordinary model path; the generator bakes the ground's layers into a top-down 0.125-m/texel image (power-of-two side 64–2048). This is a workaround, not a claim custom shaders cannot blend.

Static construction: the generated MAD copies stock physics/type/library data from IG_HEIGEN601.MAD, has no heightfield and registers a named static triangle body per collision-bearing model. Runtime uses model-name lookup and each placed object's transform. The source deliberately leaves vegetation/small clutter without collision bodies.

From-scratch RAB/MDB and bounded load evidence

Static generator design: MDB 0x20 with one bone and one object partitions meshes by 65535/3 triangles for u16 indices. The chosen 64-byte vertex packs half4 normal/tangent/binormal, float3 position, float2 UV, fixed one-bone weights and index zero. Material families are opaque snd_BRDF_Map_Common, clipped _Clip with alpha_clip 0.5, or translucent _Alpha with falloff parameters. These are design choices, not caps for every legal MDB.

Static archive design: RAB version 272 stores TEXTURE LOD DDS, MODEL MDB and HD-TEXTURE full DDS with matching flags/compression. It reuses flat BC5 normal and DXT1 RMO; opaque textures use DXT1, alpha-tested/translucent DXT5, with mip chains. Dummy wire_test.dds satisfies a wire class lookup even on no-wire maps, avoiding a warning.

Source-reported in-game load tests: five authored maps (526–631 models, 2,707–6,159 placements, 83–257 MB RAB, 9–18 MB MAD) entered a temporary test mission, drew normally and supported the player on generated ground; committed process memory was ~3.4–3.9 GB. Weather, sky, light/reflections and navigation were borrowed from stock maps, hence AI pathing on new terrain was not established.

Unverified diagnosis: three trial loads froze on a loading screen at roughly 2.1–2.25 GB memory for over two minutes but loaded on subsequent attempts (Finland files byte-identical). Failed/stuck game or driver starts preceded them; environmental trouble was suspected, while a rare map bug remained possible. Do not treat this as a reproducible format failure.

Cross-game control corpus

Static 21-pair census: EDF5 and EDF6 share 21 named maps, yet no whole MAC was byte-identical; EDF6 changed route files, some tree/MAB/texture assets, member order and weather location. After semantic conversion, cave MAPO for IG_CAVE501/503/504 and two MAPBs (IG_CAVE503, IG_TESTLIGHTMAP) matched bytewise. Other differences added CrashType, defs/placements, collision-name changes and nested/named tables. Embedded MAB pointer mode changed 0x03→0x83; runtime acceptance of older mode was not tested.

Scope: details complement EDF6 File Formats. This authoring case study separates binary layout, generator-specific defaults, limited reported gameplay results and remaining unverified behavior.

Provenance correction

A later audit overturned the label “native EDF6 exact GrassDens2Small” for the Desert profile. See native EDF6 grass registry versus EDF5-derived regional GRB. The HEIGEN source registry remains genuinely native, but absence of a .grb consumer prevents generalising the ported Desert density rules.
