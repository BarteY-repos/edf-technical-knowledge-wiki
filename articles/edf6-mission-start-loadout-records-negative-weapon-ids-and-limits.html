EDF6 mission start: loadout packets, player records and weapon IDs

EDF 6Game technical referencesNetworking
Technical reference · Source-code/static interpretation with explicitly labelled contributor gameplay observations; no new game runtime

EDF6 does not spawn an online squad purely from whatever a player's local equipment menu last displayed. At mission start, the game synchronizes per-player loadouts, then constructs the online player objects from the received GameStatus records. This explains why client weapon-table compatibility matters even when the lobby and mission resources appear to load correctly.

The examined native loadout record

The code audit identified a 0xD4-byte (212-byte) stride for GameStatus player records beginning at GameStatus+0x14C78, with four native slots. Eight audited indexing sites use this stride in creation, mission synchronization, colors or UI. The small +0x118 pickup count discussed in the source is a record-relative memory field used on the appropriate object/access path, not an additional 0x118 bytes that must be appended to a 0xD4-byte on-wire record.

Every participating machine calls MissionSync_Begin() and advances MissionSync_Update() until the synchronized start state completes. The host gathers player replies and produces the start message, including the player count and compact serialized loadout entries. The receiver reconstructs records and then creates player objects. The wire representation varies in size and is not automatically identical to the fixed 0xD4-byte in-memory stride.

Layer Observed distinction
GameStatus in memory 4 × 0xD4 record stride in the native build
Mission-sync wire records Compact fields; varying lengths, not direct raw record memcpy
Player count Separate synchronized value at GameStatus+0x14FF8
Room member slot Network identity used to match replies, distinct from the HUD player number

Weapon IDs: negative values matter

The examined native equipment lookup has a nonobvious convention:

  • -1 means empty weapon slot.
  • IDs less than -1 can encode a table row as abs(id) - 2.
  • Regular IDs resolve through the weapon table according to the observed native lookup path.

The source documents a mixed-mod session where a stock-table guest crashed after a host equipped a weapon added to the table by a mod. This is an observed cross-installation incompatibility, not evidence that ordinary matching stock EDF6 installations crash from standard weapon choices. The problematic remote path lacked a sufficient bound check for the host's weapon index. Resolving a weapon in a packet and rendering its name in the lobby are separate operations.

Record size and EOS packet limits

The source discusses a modified eight-member test reaching an estimated 1180-byte mission-start message, exceeding the separately audited 1170-byte physical EOS bound. That result is reported as unverified mod-configuration evidence and must not be attributed to the four-player stock message size. It does illustrate why adding more members stresses serialized start records, not just the room UI.
