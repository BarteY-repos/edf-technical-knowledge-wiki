Why running identical code on every peer can be wrong

The examined EDF6 modding layer models objects on all peers, but not all instances represent one registered network object. A vehicle with a registered network identity has a machine responsible for its core simulation. A plugin-created aircraft, drone or summoned creature may be unregistered and exist separately on each peer. The first category requires single-authority decisions; the second may require per-peer simulation while allowing the damage result to count only once.

This article describes the specific researched EDF6 engine/version and compatibility adapter. It is not a universal law saying EDF6 never replicates any spawn, nor does it replace direct network protocol analysis.

Network flags and authority inputs

In the retained online_authority.h model, the network-object word at object +0x128 includes:

Bits Meaning in the examined path
bit 0 (0x01) Object is remote/operated elsewhere
bit 1 (0x02) Object is locally operated
neither No registered network identity — a local copy

A vehicle's native operator resolver uses seat-0's current rider, then possibly the previous rider, then host fallback. This can be wrong for additional plugin work when seat 0 is now empty: after a client leaves, native “last driver” state may still select that client, while the host's NPC controller would also run its work. The bounded adapter assigns host authority when there is no live registered seat-0 rider.

For an unregistered object, each peer can continue simulating its local copy. A separate CopyOwner marker (host, here, elsewhere) records the player who created that logical entity so the authoritative damage result is not multiplied across peers. This owner marker is adapter-owned metadata, not a magic bit stored by the original game for every spawn.

Four decisions that must not be collapsed into one boolean

Question Relevant behavior
Who simulates the object? Registered object: its authority; unregistered local copy: every peer simulates its copy
Who performs host-only actions? One host handles room-wide operations, such as assigning certain NPC drivers
Where does its damage count? Registered vehicle: its authority for NPC/vehicle-owned weapons; unregistered copy: the recorded copy owner
Who is the attacker of a locally fired gun? Online, a player firing a registered vehicle's gun may need to be named as attacker so hit authority resolves to that player's machine

A player firing a registered vehicle's local gun is a special case: the player's input and the vehicle simulation may be owned by different machines. Treating “vehicle is remote” as “this player cannot fire” breaks that use case. Conversely, every peer applying an NPC turret's damage independently doubles or triples damage.

For online rounds whose attacker is named as the player, the mod also had to preserve the native rule that a vehicle-mounted gun does not immediately damage its own ridden vehicle. Merely ignoring the attacker pointer is insufficient when the player and the player's current vehicle are distinct objects; explosive splash has a separate filter and is not automatically solved by a single direct-hit exclusion.

Lifecycle and safety rules

  • In offline sessions, normal local behavior can remain enabled; in online sessions with unknown build-specific session hooks, fail closed rather than declare each peer authoritative.
  • Do not use a stale former seat-0 rider as authority for added NPC/vehicle behavior.
  • For local copies, separate simulation from who owns the outcome; spawning on every peer is not the same as counting the result on every peer.
  • Ensure weak identity/control blocks are checked across object destruction and recreation. Object addresses can be reused; a stale raw pointer is not durable identity.
  • Verify host/client, enter/exit seat, NPC seat adoption, local player gunner, unregistered summon/drone and restart/rejoin paths independently.

Evidence and limits

The retained source includes pure Authority, RunsHere, ShotCounts, ShooterIsAttacker, SparesRide and MaySeatNpc decisions and historical exact-build native-address research. It documents an actual class of desynchronization/double-damage risks. It does not show that every such path was runtime qualified for every multiplayer configuration in R64.

Source: EDF4.1→EDF6 R10 HF4 R9 components/compatibility/src/online_authority.h, supported by the preserved edf41net.cpp network-object identity discussion. The addresses and hooks are build-specific; the semantics are the transferable findings.

Team identity is not projectile authority

An actor's native TeamManager relation and a controlled-boss PvP lease are separate from per-peer object simulation and damage ownership. Native team roles and relation overlays explain target/hazard roles, while typed emitter team propagation and spawn rollback explains why changing a root's team alone may leave bullets and newborn parts in the wrong faction.

For a worked example of a custom, bounded per-object event envelope that reuses native NetworkObject send/receive slots without redefining stock messages, see EDF4.1 tag-12 event wire and native child identities.
