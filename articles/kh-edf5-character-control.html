The walk controller

xgs::havok::CharacterControl_Walk has a vtable in EDF5 (EE0D40, RTTI 11B4C48

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-walk-controller

xgs::havok::CharacterControl_Walk has a vtable in EDF5 (EE0D40, RTTI 11B4C48; EDF6's has none): constructor 6281E0, init 6283F0 (writes the gravity scalar +0xA0 and the push-down speed +0xA4 = 6.0 at 62845D / 628463), slot 1 628680. Owners and offsets (from the destructors that restore the vtable, named with vt_owner.py): HumanBase +0x4B0 (soldiers and civilians), HumanoidBase +0x7F0 (Colonists), MonsterBase +0xC70 (Archelus and kin), AlienTrailer +0x8C0 (Shield Bearer), VehicleBegaruta +0x1370 and its BegarutaCtrlWalk (walk at +0), Vehicle501_FortressRobo (Barga, Balam; the move write at +0x17B0 puts it at +0x1760, inferred).

Basis: RTTI and fn.py --xref EE0D40; owners by vt_owner.py on the destructors 1CE6B0, 2275B0, 26D340, 33B6B0, 35F840, 35AF40

Addresses (build-specific RVAs unless indicated): EE0D40, 6281E0, 6283F0, 62845D, 628463, 628680

EDF5 shared walking controller step

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-walk-step

The walk step is one function, 628B80(walk), called once per update by each owner (HumanBase 2EDF02 in slot 2 2ED6C0, HumanoidBase 22C931, MonsterBase 26FBEB, AlienTrailer 1D0F4D, FortressRobo 33E8C6, Begaruta's walk 35D21D). It builds an hkStepInfo with dt 1/60 (0x3C888889, inverse EE66A4) and calls the character body's checkSupport ([walk+8], vtable slot +0x18 = 7DADA0) into an hkpSurfaceInfo at walk+0xB0: +0xB0 dword supportedState (0 unsupported, 1 sliding, 2 supported), +0xC0 surface normal, +0xD0 surface velocity, +0xE0 distance excess, +0xE4 byte surface is dynamic.

Basis: fn.py reads of 628B80 and 7DADA0; fn.py --xref 628B80

Addresses (build-specific RVAs unless indicated): 628B80, 2EDF02, 2ED6C0, 22C931, 26FBEB, 1D0F4D, 33E8C6, 35D21D, 7DADA0, EE66A4

Attribution: novae (ajane) · 2026-11-14

Walk controller fields versus EDF6 offsets

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-walk-fields

Walk fields as the step uses them (EDF6 offsets in brackets, edf6/character-control.md#walk-controller-layout): +0x50 the wanted move velocity [+0x20], +0x60 the ballistic velocity, y +0x64 [+0x30], +0x70 the velocity sent [+0x40], +0x90 and +0x1D0 two one-step extra velocities, cleared at the step's end (628E42, 628E5A) [+0x60, +0x1C0], +0xA0 gravity per second (x 1/60 EE61FC per step) [+0x80], +0xA4 push-down speed [+0x84], +0xF0 byte launch flag [+0xD0]. Sum sent: +0x50 (projected on the ground when supported) + +0x90 + +0x1D0 + +0x60 (628D00..628D65), set through hkpCharacterRigidBody::setLinearVelocity 7DBB00 (628D9C).

Basis: fn.py read of 628B80

Addresses (build-specific RVAs unless indicated): 628E42, 628E5A, EE61FC, 628D00, 628D65, 7DBB00, 628D9C

Walking contact and launch state transitions

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-walk-step-states

The step's states, as EDF6's #walk-step-states: unsupported one step after standing without the launch flag: move y = -+0xA4 (hug a slope); otherwise unsupported or sliding: +0x64 += g; supported without the launch flag: +0x60 cleared and the move projected on the ground; supported, then if +0x60 points away from the normal (dot above EE6164, 1.2e-7) the state is set to 0 and g added (lift-off); no body in the world (7DAD90 = [charBody+0x20] is null): +0x60 cleared; +0xF0 cleared once +0x64 < 0 (628DBB).

Basis: fn.py read of 628B80

Addresses (build-specific RVAs unless indicated): 7DAD90, 628DBB, EE6164

HumanBase jump velocity transfer

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-walk-humanbase

HumanBase's jump launches like EDF6's: a pending jump (+0xEE0, speed +0xEE4) writes walk +0x64 (HumanBase +0x514) = speed, state +0x560 = 0 and launch flag +0x5A0 = 1 (2EDDF7..2EDE16), just before the step; about 20 more sites write +0x5A0 = 1 with state 0 (2E5061, 2F1767, 30EF2A ...). The move velocity +0x500 is built from HumanBase +0xE40, +0xE60 and, when +0x29C == 2, +0xD40 (2EDDA3..2EDDE8); the one-step slot +0x540 (walk +0x90) is added to at 2ECAB8 and 2F9547.

Basis: fn.py --grep over 2D0000..310000 for writes of +0x540 / +0x5A0 / +0x514; read of 2EDD60..2EDE22

Addresses (build-specific RVAs unless indicated): 2EDDF7, 2EDE16, 2E5061, 2F1767, 30EF2A, 2EDDA3, 2EDDE8, 2ECAB8, 2F9547

Moving ground (00v topic 4)

Walk step ignores supporting-body movement

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-moving-ground-stock

The stock walk step ignores the ground's motion, as in EDF6: 628B80 reads from the surface info only the state +0xB0 and the normal +0xC0, never the surface velocity +0xD0 or the dynamic flag +0xE4; no code in the walk class reads them, and HumanBase code reads only the state (HumanBase +0x560, about 25 sites in 2D0000..310000; no read of +0x580 / +0x594 there). So a soldier on a moving body keeps its own world velocity: the body slides away under it and only contact pushes move it.

Basis: fn.py --grep of the walk class (628330..629130) and of HumanBase's range; a whole-exe scan for +0x580 / +0x584 / +0x588 / +0x594 found no HumanBase read

Addresses (build-specific RVAs unless indicated): 628B80

Attribution: novae (ajane) · 2026-11-14

Havok support info computes surface velocity

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-get-ground-velocity

Havok fills that surface velocity anyway: checkSupport 7DADA0 calls getSupportInfo (slot +0x20, 7DAEC0) and, when supported, getGround (slot +0x28, 7DB8B0) with useDynamicBodyVelocities = 0 (xor r8d, r8d at 7DAE2B). getGround averages over the support contacts (stride 0x40, body at +0x20): each contact's own velocity +0x30, plus for a keyframed body (motion type +0x160 == 4) its point velocity, linear +0x230 + angular +0x240 x (point - center of mass +0x1C0); a fixed body (5) adds nothing; a dynamic body sets the dynamic flag and adds its point velocity only when the flag argument is set. So stock fills +0xD0 for keyframed supports only.

Basis: fn.py reads of 7DADA0 and 7DB8B0; the names are Havok 2012's hkpCharacterRigidBody methods, matched by vtable slot and behavior (inferred)

Addresses (build-specific RVAs unless indicated): 7DADA0, 7DAEC0, 7DB8B0, 7DAE2B

Attribution: novae (ajane) · 2026-11-14

Ragdoll part update modes versus EDF6

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-ragdoll-part-modes

EDF5's ragdoll part records have EDF6's modes (edf6/corpses.md#ragdoll-component-records): 3CB3E0(record, mode) keeps the mode at +0x9C (forced to 0 unless +0xA4 is set), mode 2 or 3 makes the part's body (+0x58) keyframed with 75F4B0(body, 4, 1, 0), mode 4 makes it dynamic with the record's type +0x68, mode 1 takes it out of the world. HumanBase turns its parts (+0xBB0, stride 0xC0) to mode 4 at death (2EDFD8). The per-frame code that drives mode-2 parts in EDF5 (EDF6's 6ED800, edf6/character-control.md#edf6-keyframed-ragdoll-drive) was not found.

Basis: fn.py read of 3CB3E0 and 2EDF60; the search for the drive stopped at the island deactivation 763FB0 and the contact callback 3CB8E0

Addresses (build-specific RVAs unless indicated): 3CB3E0, 75F4B0, 2EDFD8

Route for standing on moving objects in EDF5 (00v topic 4Source: unverified

Evidence: unverified · Build: steam-5d11de53 · Fact ID: edf5-moving-ground-route

Route for standing on moving objects in EDF5 (00v topic 4; untested): (a) carry: in the step, add the surface velocity +0xD0 when +0xB0 == 2, e.g. a hook on the 7-byte addps xmm3, [rbx+0x90] at 628D00 (unique bytes 0F 58 9B 90 00 00 00) that also adds [rbx+0xD0]; (b) for vehicles and other dynamic bodies, turn on getGround's dynamic flag: 45 33 C0 at 7DAE2B to 41 B0 01 (mov r8b, 1; getGround keeps only the low byte), which changes only +0xD0, read by nothing in stock; (c) turning with the ground needs the support body's angular velocity, which Physics2012's surface info lacks: hook getGround 7DB8B0 and keep the body pointer. Unlike FevGrave's EDF6 plugin (edf6/character-control.md#edf6-moving-ground-route) it may need no contact-list walk, as long as Havok's velocity is right for EDF5's bodies.

Basis: inferred from the lines above; bytes read with bytes_at.py (628D00 7 bytes once in the file, 7DAE20..7DAE33 once)

Addresses (build-specific RVAs unless indicated): 628D00, 7DAE2B, 7DB8B0

EDF5 HumanBase raw and smoothed aim

Pitch/yaw fields, limit guards and recoil

Evidence: static · Fact ID: edf5-humanbase-aim-fields · Build: steam-5d11de53

HumanBase stores raw pitch/yaw at +0xE80/+0xE84 and smoothed pitch/yaw at +0xE90/+0xE94. Look input +0xB40 changes raw aim, which is clamped by optional pitch/yaw limits +0xEA0/+0xEA4 and pitch ±π/2; NaN components are reset. Smoothing follows smooth += (raw - smooth) × coefficient, where +0xEB0 defaults to 0.3 when invalid. Placing the soldier sets pitch zero and yaw from atan2(forward.x, forward.z) of world-matrix forward row +0x90, then copies the raw pair to smoothed aim. Weapon recoil affects both, with pitch reclamped. These fields are 0x3B0 below EDF6 counterparts.

Smoothed yaw as heading, not move direction

Evidence: static for readers; heading interpretation inferred · Fact ID: edf5-humanbase-yaw-readers

Known consumers of smoothed yaw +0xE94 include follow AI's look error, network-sender conversion of stick input into world x/z and numerous weapon/action routines. For yaw ψ the forward unit vector is (sin ψ, 0, cos ψ), right is (cos ψ, 0, -sin ψ). Online synchronization sends the raw aim pair while the movement conversion uses the smoothed value. Thus +0xE94 is best interpreted as the look/camera-driven soldier heading, not necessarily walking direction; roughly 25 additional reads were identified but not individually decoded.
