Poster and dispatch

UI notice poster and text payload

Evidence: static · Build: steam-5d11de53 · Fact ID: notice-poster

The notice poster is 460BE0(rcx unused, rdx = const wchar_t* text, r8 = object or 0): it builds a std::wstring, pairs it with r8 and calls 61E950(uiMgr, 12, &payload), where uiMgr = [125AB70] − 0x88 (the pointer is loaded at 460C4F, function +0x6F, and the game does not null-check it). The test rax,rax; je at 460C56 only skips the -0x88 adjustment: with no UI manager 61E950 still runs with rcx = 0 (rbx zeroed at 460C1B) and reads [rcx+0x18] at 61E988.

Basis: disassembly; the null path re-read with fn.py in KH chat 63

Addresses (build-specific RVAs unless indicated): 460BE0, 61E950, 125AB70, 460C4F, 460C56, 460C1B, 61E988

Attribution: novae (ajane) · 2026-10-12

UI manager listener notification event

Evidence: static · Build: steam-5d11de53 · Fact ID: notice-dispatch

61E950 enters the UI manager's critical section (+0x60) and calls vtable[+0x18](listener, 12, payload) on every listener in two lists. The 27680 call inside it is an empty debug-print stub.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 61E950, 27680

Attribution: novae (ajane) · 2026-10-12

Formatted notice text callers

Evidence: static · Build: steam-5d11de53 · Fact ID: notice-callers

Callers of the poster: 460AB0(?, key, &params) (a text-table key to formatted text), used by 411E00 / 411F40 for "player down" OnlineSys_PlayerDown (from 2DAD06), the rescue OnlineSys_PlayerRescue and the Air Raider requests OnlineSys_VehicleRequest / OnlineSys_IndirectRequest (from 181149); the chat line poster 5A54AC ("name: text"); and plain text with r8 = 0: Online_NoInput_Warning (41040B) and a list replay (411C31).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 460AB0, 411E00, 411F40, 2DAD06, 181149, 5A54AC, 41040B, 411C31

Attribution: novae (ajane) · 2026-10-12

Listener

UiNotice event handler and message storage

Evidence: static · Build: steam-5d11de53 · Fact ID: notice-listener-uinotice

The listener is UiNotice (RTTI, vtable EDC1B0, event handler 595360: on event 12 it copies payload +8, the wstring, into its queue at +0xF8). It is created by 594CC0 inside UiChat_WatchDog (5A3CE0, factory name ui_chat_watchdog), which is created from data, not from code.

Basis: RTTI; disassembly

Addresses (build-specific RVAs unless indicated): EDC1B0, 595360, 594CC0, 5A3CE0

Attribution: novae (ajane) · 2026-10-12

Why debug ui_show_message is not a notice

Evidence: static · Build: steam-5d11de53 · Fact ID: notice-unsuitable-paths

Not suitable for a mod's notices: the debug command ui_show_message (608C0) opens a modal message box (lyt_HUiMessageBox.sgo); the script native Notice_Message (4295F0) is a menu-script dialog helper.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 608C0, 4295F0

Attribution: novae (ajane) · 2026-10-12

Facts (merged from inbox)

Early HUD notice posting timing limitationSource: unverified

Evidence: unverified · Build: steam-5d11de53 · Fact ID: notice-post-during-loading

Posting a message-log line through 460BE0 from the radar HUD's first frames (which probably run during the mission loading screen) crashed the game at once; posting once the mission runs is fine (several patches). Rule until traced: post only on a user action or after a mission event. Evidence: one run (2026-10-15): a test patch posted "loaded" once, on the first call of its hook at the radar's last draw call (4CDF0A), guarded by [125AB70] != 0 exactly like another radar patch; instant crash on the loading screen as the mission was about to start, no crash dump. the test's other code was re-read and matches its emulator-tested design; a variant (identical except it posts only on a key press) loaded missions without a crash the same day, and its message appeared. The loading-screen post was not retried alone.

Basis: inferred from one crash and one clean run; novae (ajane)

Addresses (build-specific RVAs unless indicated): 460BE0, 4CDF0A, 125AB70

Attribution: novae (ajane) · 2026-10-15

Lazily initialized UI manager global

Evidence: static · Build: steam-5d11de53 · Fact ID: ui-manager-lifetime

The UI manager global 125AB70 is created lazily by 4CA550 (destroys any old one, allocates 0x90 bytes, vtables ECAE20 / ECADD0, stores obj+0x88), called from about 20 places, each only when the global is null (for example 4D7887, 4CA371), and cleared only at shutdown (60FA4E); so a stale manager pointer is an unlikely cause of notice-post-during-loading. The listener side (UiNotice, created per scene by UiChat_WatchDog from data) during scene loading was not traced.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 125AB70, 4CA550, ECAE20, ECADD0, 4D7887, 4CA371, 60FA4E

Attribution: novae (ajane) · 2026-10-15

Ten-second message log entry lifetime

Evidence: static · Build: steam-5d11de53 · Fact ID: message-log-lifetime

Message-log entries are created by 595460 with a lifetime of 10.0 s loaded at 595E1D (movss xmm3,[rip+X], a shared 10.0 constant); entry +0x2C age, +0x34 lifetime, +0x38 alpha (fades 0.1 per frame after expiry), +0x30 remove flag. NoticeLifetime_v01 points that load at its own float (default 2.0 s), which affects every log line, ours and the game's.

Basis: disassembly and emulation; not tested in game

Addresses (build-specific RVAs unless indicated): 595460, 595E1D

Attribution: novae (ajane) · 2026-10-04

EDF5 UI notice listener and thread-safety boundaries

One locked manager listener list, one unlocked

Evidence: static · Fact ID: notice-dispatch-lists-lock · Build: steam-5d11de53

Notice dispatcher 61E950(mgr, event, payload) walks two MSVC std::list listener chains. The first, at manager +0x18, is visited while holding critical section +0x60. The second, at +0x28, is visited after releasing that lock. Disabled listeners (object flag +0x18 bit 1) are skipped and active listeners receive vtable callback +0x18. Concurrent UI creation/destruction could mutate the unlocked list, a possible source of notices posted during loading; which list owns UiNotice was not confirmed.

UiNotice event append races with update traversal

Evidence: static · Fact ID: uinotice-vtable-slots

UiNotice vtable EDC1B0 slot 1 594DF0 updates its message list at +0xF8 every frame, slot 2 5952B0 draws, slot 3 595360 appends notice entries to that same list without its own lock, and slot 5 594D60 destroys the object. Posting through 460BE0 from another thread can race with an update walk; posting inside the update thread's slot-1 hook avoids that particular inter-thread overlap. The manager's first-list critical section does not protect the UiNotice internal list, and this is a static race analysis, not a reproduced crash.
