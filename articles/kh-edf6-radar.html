Observations

Radar entity RGBA color constants

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-color-constants

Radar icon colors are RGBA float constants: neutral units 1F77980, allied units 1F77990, items 1F779A0, enemies 1F779B0, vehicles 1F779C0 (16 bytes each). Weapon icons 1F779F0. KittopiaCreator's MapIconColour and WeaponIconColour write these directly (the values in KittopiaCreator's patches are KittopiaCreator's choices, not the game's defaults).

Basis: KittopiaCreator's patches

Addresses (build-specific RVAs unless indicated): 1F77980, 1F77990, 1F779A0, 1F779B0, 1F779C0, 1F779F0

Attribution: KittopiaCreator, EDF6 research (MapIconColour, WeaponIconColour) · 2026-10-16

Radar item iteration and icon drawing loop

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-item-loop

The radar's item loop: entry at 82B975 (call 82A890 = draws an icon set), per-item test at 82B9AD, end at 82BB3D/82BB42; the item's category byte is at +0xC0 of the item (0 weapon, 1 armor, 2 and 3 health: the patch loops 0..3 and colors 2 and 3 alike, as EDF5 does). KittopiaCreator's CustomisableItemRadarColours runs the loop once per category with its own color (jumping back to 82B97A, skipping to 82BAE5, continuing at 82B9B4).

Basis: KittopiaCreator's patch (also in novae (ajane)'s outside set); novae (ajane)

Addresses (build-specific RVAs unless indicated): 82B975, 82A890, 82B9AD, 82BB3D, 82BB42, 82B97A, 82BAE5, 82B9B4

Attribution: KittopiaCreator, EDF6 research (CustomisableItemRadarColours) · 2026-10-16

Radar icon types are set up at 82BC18 (calls 82B220, icon type in r8d, then 82A890 with a color pointer)

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-team6-icon

Radar icon types are set up at 82BC18 (calls 82B220, icon type in r8d, then 82A890 with a color pointer); KittopiaCreator's Addteam6MinimapOverride adds icon type 6 for team 6 there (returning to 82BC1D).

Basis: KittopiaCreator's patch and MapColourExperiment.CT

Player slot colours on the radar

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-player-slot-colors

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Four-entry colour table
  2. Player ID lookup
  3. Icon rendering
EDF Knowledge Hub record — original wording — expand (1,163 characters)

The radar draws each player's icon in a color picked by player id from a 4-entry RGBA table: id 0 yellow (1, 1, 0, 1), id 1 green (0, 1, 0, 1), id 2 blue (0, 0, 1, 1), id 3 red (1, 0, 0, 1); the color follows the player id, not the soldier class. The radar player-icon function 82A030 fills a stack table at [rbp+0x150] (82A0EB..82A123, four movaps from the 16-byte RGBA constants 1768E00, 1C36A80, 1765B70, 1765B40, in id order) and indexes it at 82A6CD and 82A743 (movsxd rax,[rsp+0x44], shl rax,4, lea r9,[rbp+0x150], add r9,rax). [rsp+0x44] is written by 7FFBD0 (called at 82A205, KittopiaCreator's name "GetPlayerName"): player id = [[soldier+0x1ED0]+0x48], and its other output [rsp+0x48] = class, read from [20B2890] + id*0xD4 + 0x14C78; the class only picks the icon's rotation constant (82A249..82A27C). Other callers of 7FFBD0: 801828, 804EBF (not decoded; possibly the name plates, which show the same palette by eye in novae (ajane)'s screenshots). Online, novae (ajane) sees friends in green / blue / yellow and confirms the last slot is red; whether ids follow the room's player-list order, and whether the host is always the same id, is unverified.

Basis: capstone disassembly of EDF.dll; novae (ajane)'s online play for the colors

Addresses (build-specific RVAs unless indicated): 82A030, 82A0EB, 82A123, 82A6CD, 82A743, 7FFBD0, 82A205, 82A249, 82A27C, 801828, 804EBF, 1768E00, 1C36A80, 1765B70, 1765B40

Attribution: novae (ajane), function pointers from KittopiaCreator (EDF Discord) · 2026-10-29

Kruul pods are kept off the radar by call 548E50 at 3FA46C (KittopiaCreator: "TeamManager exclusion"

Kruul pods are kept off the radar by call 548E50 at 3FA46C (KittopiaCreator: "TeamManager exclusion"; the next instruction sets bit 0x2000 of [r12+0x380]); KittopiaCreator's KruulPodsOnRadar NOPs the call, and optionally forces the pod's team to 4 (combat.md#team-4-enemy).

The radar's rotation uses only the yaw of the angles it is given

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-heading-yaw

The radar's rotation uses only the yaw of the angles it is given; with a level pitch it skips its pole fallback at 82B743, which would otherwise overwrite the yaw. The soldier it reads is the SoldierBase from the dynamic_cast at 82B598 (held in rsi).

Basis: the EDF6VR source's comments (its radar-heading hook checks the call and its stack set-up)

Addresses (build-specific RVAs unless indicated): 82B743, 82B598

Attribution: EDF6VR source (momotori01, Unlicense; round 23) · 2026-11-07

HUD radar center and rotation fields

Evidence: static · Build: steam-678ccb46 · Fact ID: radar-center-sides

Radar center, rotation and sides: ui::HUiHudRader (vtable 17FCF10, slot 2 82B4D0) locks its own HUD's weak pair +0x778 / +0x780 and casts the object to SoldierBase (82B541..82B59D, into rsi); there is no global player 1. Heading: the soldier's axes +0x70 / +0x80 (82B671 / 82B675), or the vehicle's basis vehicle+0x208 when riding, go through 4E100 (pitch = -atan2(y, hypot(x, z)), yaw = atan2(x, z)); past pitch +0.75 the code uses +0x70, below -0.75 its reverse, so a near-vertical forward axis keeps a yaw. 82B767..82B79E build the rotation float4x4 at rsp+0x60 and 82B7A5 loads the center from the soldier's +0x90 into rsp+0x50; every dot, name, marker, line and map edge uses that center and matrix (82C690 subtracts the center, then scales by HUD+0x8B0 and cuts by distance). The two hostile walks (82B89A, 82BB80) read the soldier's team +0x314 and enumerate with 5E0F20 over the relation table in red (1, 0, 0, 1); the friendly group hard-codes team 2 at 82BB42 through 82B220 in cyan (0, 0.75, 1, 1); team 4 white, team 5 yellow.

Basis: the author's static reading, checked by their native audit script on the DLL

Addresses (build-specific RVAs unless indicated): 17FCF10, 82B4D0, 82B541, 82B59D, 82B671, 82B675, 4E100, 82B767, 82B79E, 82B7A5, 82C690, 82B89A, 82BB80, 5E0F20, 82BB42, 82B220

Attribution: hajisensai, All Forces source docs/enemy-control-radar-re.md (round 24) · 2026-11-07

Radar scale, clipped positions and team-dot rows

Scope: four static EDF6 radar.md additions, compared by the contributor with EDF5 radar behavior; addresses refer to the cited EDF6 build and are not runtime screenshot measurements.

Two independently stored scales: the HUiHudRader constructor 828030 initializes marker-size multiplier +0x8B4 = 1.2 and position multiplier +0x8B0 = 0.6 (8280D0/8280DB), analogous to EDF5 but shifted 0x30 in the object. The author's scan of HUD code range 800000..860000 found no other writes to either field; it did not identify a user-controlled zoom. The player icons and radar position helper read these fields separately. This is a bounded native scan, not a claim that an external plugin cannot patch them.

Marker rectangle: drawer 82A890 reads size at +0x8B4 (82A9A0) and constructs a centered quad from -5s to +5s on each axis (width/height 10s), with normalized sprite tile (0,0,0.25,0.25). Constants are associated with 17B6084, 1765A44 and atlas 17FD090. Dot size therefore depends on the 1.2 scale independent of radar reach.

Range and vertical projection: 82C690(radar,out,pos,center,clamp) negates center offset, computes horizontal X/Z distance and compares with 200 m (1765A70). With edge clamp enabled, it draws outside targets on the 200-m rim and marks out+0xC=0 (1 means inside). X/Z then multiply by +0x8B0=0.6, giving 120 radar units to the rim. Unlike EDF5, vertical difference is scaled by 0.5, not another +0x8B0, and clamped to ±80. Because the 200.0 constant has dozens of other readers, a safe experimental range change would target this load rather than overwrite its shared constant; such a modification was not tested here.

Team positions, not object identities: update 82B4D0 calls 82B220(hud,list,team) to clear list size +0x18, choose the team's 0x38-byte TeamManager row from [20B2978]+0x38, iterate its MSVC std::set tree and append each object's position +0x90 as a 16-byte element (list data/capacity/size at +8/+0x10/+0x18). The output has no object pointer or class, so later dot rows cannot be attributed to entities from the list alone. Four direct call sites include team 4 twice and friendly team 2 at 82BB50. A mounted soldier possibly adds another dot at the same vehicle position, while an AI tank's invisible Dummy driver likely does not; those latter conclusions were not paired with a fresh radar screenshot.
