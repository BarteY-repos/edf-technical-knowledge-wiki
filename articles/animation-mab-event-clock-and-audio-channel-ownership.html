MAB animation events — clip clocks, event parameters, and owned sound channels

UniversalAnimationEDF 4.1EDF 5EDF 6
Technical reference · Source-confirmed event records; exact-build class sound behavior; no new runtime test

Why a valid animation may still be silent or mistimed

CAS/CANM describes the animation controller and joint tracks, while MAB can supply named, timed events associated with a CAS clip. An importer that moves bones but discards MAB event tracks can silently lose sounds, muzzle actions, attack windows or hitboxes. The same event name may be meaningful only to a specific source class; do not treat all events as engine-wide commands.

For the validated MAB v15 family, a track record is 0x10 bytes: first-key offset, key-end pointer, UTF-16LE track-name pointer and key count. Each 0x10-byte key holds an event-name string reference at +0, float32 time at +4, zero at +8, and an embedded SGO\0 parameter pointer at +0x0C. Offset bases depend on MAB pointer mode (0x03 = MAB-relative, 0x83 = owning-struct-relative). Full decoder: MAB format and pointer migration.

A concrete event list

The retained MAB reader reconstructs data like:

clip_name -> [
  (event_name, event_time_seconds, event_params),
  ...
]

Observed object-specific event families include se, se_stop, the DragonBig401 pair 火炎開始 / 火炎終了, and UfoRobo events whose parameter SGO includes names such as collision, damage, quake, scale and charge_frame. The embedded SGO can change an event's meaning; dispatching only its bare name is not complete semantic preservation.

Channel ownership is part of the sound lifecycle

For the studied EDF4.1 se / se_stop mechanism, an event includes a channel. A negative channel means fire-and-forget, with no retained channel handle. For a nonnegative channel, a new play event stops that channel's old sound first, then owns the resulting handle. A corresponding stop event, replacement, state exit, or object destruction can end that handle. There is no universal fixed playback time limit.

The retained compatibility implementation models these rules in Channels<Handle> and Timeline (edf41_sound_channels.h). Its timeline reads the animation state and time before/after the update:

  • Crossing multiple key times in one update dispatches every crossed event in order.
  • Polling the same timestamp repeatedly must not replay a key.
  • A clip/state change resets the relevant event clock.
  • A valid next clip within a multi-clip state may retain channels; a full state exit cancels them.
  • A backward time jump must be interpreted as a clip restart or reset according to the state's known clip layout.

This is a source-backed model for specific EDF4.1 class behavior, not a generic promise that every MAB event should be converted to this dispatcher unchanged.

An easy-to-miss attack/sound difference

One studied UfoRobo weapon group owns separate charge and shot audio handles. Charge audio ends when leaving its charging state. A looping shot cue persists across rounds only while its play handle remains active; finite shot tails are not indiscriminately cut off on the next round. Replacing this with a single global “play sound at fire” call loses the intended behavior.

Relating MAB, sound banks and the game

An event may identify its cue by name, but that name still must resolve to an audio bank. In the EDF4.1→EDF6 research, many source cue names collide with EDF6's resident names. The correct semantic route must distinguish bank identity, cue identity, channel ownership and clip timing. See EDF4.1 SE/voice bank lookup and lifetime.

What is and is not proven

Source and exact-build RE evidence: MAB key structure, recognized event/argument examples, channels, timeline ordering and the class-specific sound lifecycle. Not proven by this article: that every arbitrary EDF6 class consumes imported MAB event names, that a copied clip has identical timing under a different animation controller, or that every source cue is present in a newly built bank.

Sources: retained mab_legacy.py (mab_events, mab_event_params) and edf41_sound_channels.h in the EDF4.1→EDF6 R10 HF4 R9 source package; source comments cite exact historical EDF4.1/EDF6 binary investigations. No fresh runtime sound-playback test was performed in R63.
