MapObject_Base

MapObject_Base: destructible scenery class

Evidence: static · Build: steam-5d11de53 · Fact ID: mapobject-base-class

MapObject_Base (vtable E95568, 17 entries) is the base class of all destructible scenery: MapObject_CrashModel, MapObject_FixedCrashModel, MapObject_Structure and others derive from it.

Basis: RTTI

Addresses (build-specific RVAs unless indicated): E95568

Durability and damage

MapObject_Base takes damage in slot 11 CF660 (not a per-frame tick

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapobject-durability

MapObject_Base takes damage in slot 11 CF660 (not a per-frame tick; the hit info in rdx: +0x50 float damage, +0x5C flags, laid out like EDF6's with its flags 4 bytes earlier, ../edf6/map-collision.md#map-object-durability): after the pre-check CFB30 and slot 14 (+0x70, base 24980 returns 0; a subclass that takes the hit itself returns 1), the durability +0x128 drops by the damage, clamped to [0, max +0x124], only when hit flag 0x01 is set or the def's category [[obj+0x150]+0x00] is 2, 4, 5 or 6 (1 << category & 0x74, CF6B1-CF6F8, the same mask as EDF6's 1268C1). CF340 then rules the collapse: hit flags 0x04 or 0x08, or a mask category hit with flag 0x02, or durability <= 0. The constructor CED40 (vtable E95568) sets max = current = the def's float +0x18 (CEE83-CEE9F), -1 when there is no def; the def at +0x150, the mapb record at +0x148, the record index at +0x15C.

Basis: fn.py CF660, CF340, CED40 (from --xref E95568) and a --writes scan of +0x124 / +0x128 over C0000-F5000; flag meanings by analogy with EDF6 (0x01 break buildings, 0x02 explosion, 0x04 force break), not read in EDF5's bullet code; not run in game

Addresses (build-specific RVAs unless indicated): CF660, CFB30, 24980, CF6B1, CF6F8, CF340, CED40, E95568, CEE83, CEE9F

Attribution: KH chat 140 (curator) · 2026-11-13

Map-object hit checks without state writes

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapobject-damage-check

Slot 10 CF550 is the matching check with no writes: it returns 1 when a hit would change the durability or collapse the object, and 0 when the object is already at 0, or slot 15 (CF3C0: max <= 0 or category 3) says it cannot be damaged, or its NetworkObject (+0xC0, slot 2 when not the default CF3A0) refuses. Slot 6 CF3E0, a NetworkObject message handler, runs a hit for message 0x80000000: check (slot 10), pass it through the NetworkObject (402C00), apply (slot 11 +0x58), and set bit 0 of the hit's byte 3 when the object reached 0; message 0x20002 sets max +0x124 to 0, making the object undamageable from then on (meaning of the message inferred).

Basis: fn.py CF550, CF3C0, CF3E0; who sends the messages not traced

Addresses (build-specific RVAs unless indicated): CF550, CF3C0, CF3A0, CF3E0, 402C00

Attribution: KH chat 140 (curator) · 2026-11-13

Durability-changing hit event dispatch

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapobject-collapse

On a hit that changes the durability, CF660 calls slot 12 (+0x60) while +0x120 is still 0, first storing in +0x120 whether this hit collapsed the object, so slot 12 runs on every damaging hit up to the collapse (base: 23390, empty; MapObject_Structure DEFA0, map-objects.md#mapobject-structure-cascade; Model DC0E0, AnimationModel CDF50). On the collapse it reads the record's +0x2C offset to {int offset, int count} child record indices (as in EDF6's record, ../edf6/file-formats.md#mapb-mapo-layout) and calls C6EF0 (map loader [125ABA8]), which calls each child's slot 13 and posts it to 97190; then it zeroes +0x128 and posts its own record index to 97190 (manager [125AC00]; a ring of {manager, index, 1} messages, consumer not read). Slot 13 (CDE30) destroys at once: sets +0x120 and calls slot 12.

Basis: fn.py CF660, C6EF0, 97190, CDE30; slot lists with scratch vt_dump.py

Addresses (build-specific RVAs unless indicated): CF660, 23390, DEFA0, DC0E0, CDF50, C6EF0, 125ABA8, 97190, 125AC00, CDE30

Attribution: KH chat 140 (curator) · 2026-11-13

Map-object instruction-byte sequence at CF726

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-mapobject-hit-hook-site

The 13 bytes at CF726 (48 8B 03, 48 8B CB, 40 88 B3 20 01 00 00: mov rax, [rbx], mov rcx, rbx, mov byte ptr [rbx+0x120], sil) sit in the damage slot CF660, not a tick: rbx is a map object taking a damaging hit before its collapse, and sil is 1 only on the hit that collapses it (map-objects.md#edf5-mapobject-collapse). A destroy-only hook there must test sil.

Basis: fn.py CF660; corrects the superseded line mapobject-base-destroy-hook-site

Addresses (build-specific RVAs unless indicated): CF726, CF660

Attribution: KH chat 140 (curator), novae (ajane), session 1 · 2026-11-13

Def categories (map.mapb def +0x00

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-map-def-categories

Def categories (map.mapb def +0x00; EDF5's defs are 0x38 bytes, EDF6's 0x3C) and their durabilities +0x18, counted over the records of all 24 EDF5 map MACs: 1 buildings (.mosb 8,365 records, mostly 100 to 400, up to 700; .mdx 7,155, mostly 50); 2 trees and shrubs (.trb 9,405, durability 10 or 1; .mdx shrubs 568, mostly 1); 3 ground and track pieces, durability 0 (.mdx 4,929, .mosb 5,487, .fmep 22); 4 poles (signals, street lamps, utility poles; 7,789, mostly 10); 5 fences, guardrails and signs (10,296, durability 1 or 10); 6 vehicles and street props (cars 50 to 70, vending machines 10, many lamps 1; 14,095); 10 water surfaces (18, durability 0); 11 rocks (100) and some sheds and gates (847 .mosb, mostly 50); 8 five records. So in EDF5 any hit wears down trees, poles, fences and street props and an explosion flattens them, while buildings and rocks need the break flag (map-objects.md#edf5-mapobject-durability).

Basis: scratch File_Storage/Logs/catalog/mapb5.py edf5 census (def size 0x38 from the def table to record table gap and readable names; defs per map)

MapObject_Trees (vtable E966F8

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-trees-damage

MapObject_Trees (vtable E966F8; inferred to hold the placed .trb trees, which C3650 leaves to C4720) overrides the damage slots: slot 10 E3640 walks the hit's contact list ([hit+0x78], count [hit+0x88], 0x30 bytes each) and finds each struck body in a hash table at +0x178 (FNV-1a over the body pointer), slot 11 E3920 jumps straight to slot 12 E3930, and slot 13 E3D10 takes a tree index (+0x1C8 list, count +0x1D8). Basis: fn.py E3640, E3920, E3D10; vtable lengths from the next class's COL pointer in vt_dump.py output

Addresses (build-specific RVAs unless indicated): E966F8, E3640, E3920, E3930, E3D10, E966B8, E96678

Tree contact behavior without durability

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-tree-falls-any-hit

Grown trees have no durability: the Trees check slot E3640 passes when a contact's body is a registered tree whose handler slot 2 says yes (MapObject_Tree: 4D510, always 1; MapObject_AnyObject: E1BA0, its byte +0x51), with no damage threshold, and slot 12 E3930 then calls the handler's slot 3 with the contact index and hit, queues the tree (list +0x1F0) and sets bit 0 of the hit's byte +3. MapObject_Tree slot 3 E5350 fells it: E4C00 turns the hit (+0x40 direction, used only when +0x58 > EE6168, 1e-6) into a fall at the tree's base, +0xF4 is halved (EE633C, 0.5), and a pending body at +0x98 is built through DA450 on layer 17 (0x11) and cleared. AnyObject's slot 3 is the empty 23390.

Basis: fn.py E3640, E3930, E5350, E4C00; vtables with scratch vt_dump.py (Tree E966B8: 7 slots; AnyObject E96678); which weapons' hits reach the Trees slots not read; not seen in game

Addresses (build-specific RVAs unless indicated): E3640, 4D510, E1BA0, E3930, E5350, E4C00, EE6168, EE633C, DA450, 23390

TRB vegetation field 1000 is not tree HP

Evidence: static · Build: steam-5d11de53 · Fact ID: edf5-trb-1000-body-property

The .trb rule's [1000] (out +0x1C, written as a float, -1.0 when absent, E0EDD-E0EF6) is not a tree durability: E46B0 passes it at E4A3D to 110BB0, which stores Havok body properties (110180 -> hkpWorldObject property add 754770; array at body +0xB8, 16 bytes per entry) under keys 4, 6, 7 (this value) and 3; MapObject_GrowObject (E5E4B) passes its own +0x1C the same way, base map objects -1 (D3A1F), structure parts a per-part value (DAB56). Its reader was not found: the property getter 754810's game callers (C9B87, 110690) ask key 0 only, and no code compares a property key with 7.

Basis: fn.py 110BB0, 110180, 754810 and its --xref; a code-wide grep for cmp d[reg], 7 (4 hits, all in library code)

Addresses (build-specific RVAs unless indicated): E0EDD, E0EF6, E46B0, E4A3D, 110BB0, 110180, 754770, E5E4B, D3A1F, DAB56, 754810, C9B87, 110690

EDF5 map-object instanced rendering

Evidence: static · Build: steam-5d11de53 · Fact ID: map-instanced-draw

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. DrawIndexedInstanced path
  2. Per-instance world transforms
  3. Batch construction and draw
EDF Knowledge Hub record — original wording — expand (1,571 characters)

Every map model is drawn instanced (DrawIndexedInstanced at 5B3120) from 102920(pool, group, ctx, table, phase), which fills a CPU array of 32-byte poses (float4 rotation quaternion xyzw, float4 translation xyz + uniform scale w) at [pool+0x30] (capacity 0x1770), uploads it with 5D5E90 and draws; the instancing shaders read it as t0 g_instancing_array at index InstanceID*m_instancing_array_stride + BLENDINDICES.x - 1, with t1 g_instancing_inv_array a 4x4 per node. RTTI vtables: MapRenderer E97258; ModelRenderer::RenderObject E96610 (slot 1 100EC0 per-frame update, calls 100D30); RenderObject::Unit E96668 (its one virtual 101BC0 writes the pose); RenderObject_Nodes E972E0; RenderGroup E97228; RenderUnit has only a destructor slot, RenderUnit_Static no vtable. MapRenderer slots 5 FF3D0, 7 FF7B0 and 10 FFA60 call 102920 with phase 0, 1 and 2 (mapping to the Commander's phases not checked). RenderGroup (0x30 bytes, one per model LOD): +0xC unit count, +0x10 unit chain head, +0x18 next group, +0x20 model. Unit (0x38): +0x10 next, +0x24 fade, +0x28 placement; pose source: translation/scale float4 at [placement+0x10], quaternion [impl+0x90][word [placement+0x20]] (0xFFFF = identity). Per-frame list: 100D30 picks a unit's LOD by distance and calls FEC80(impl+0xD8, group, unit); FF340 clears the lists at view begin; a second list at [impl+0xE8] is unread. No shader-name field was found in the material record or the pass object (5B2900 pass object: VS at +0x20, PS at +0x48); telling a material family apart needs the model pointer or the SGO effect loader.

Basis: novae (ajane); the instancing vertex shaders of snd_map_build_window disassembled with D3DCompiler_47; the quaternion convention is taken from the shader's names (m_rotation_xyzw, m_trans_xyz_scale_w); not run in game

Crash debris, structure breaks and instancing

These records extend the earlier EDF5 map-object appendix with source-attributed findings on build steam-5d11de53, from novae (ajane). Unless explicitly marked unverified, they are static code/asset readings; inferred timing and proposed patches are not verified game experiments.

CrashModel InitParam, queue and piece construction

Static · novae: D1300 constructs a MapObject_CrashModel::InitParam with vtable E95E90, default +0x68=22500.0, SGO effect keys DosyaEffectType, BoundEffectType, CrashEffectType and an optional Type transformed into a map_<Type> identifier of unresolved use. Structure part breaks and MapObject_Model / AnimationModel collapse paths construct this InitParam. Dosya suggests soil/rubble dust by name; that etymology does not establish an effect-type mapping.

Static · novae: the Structure break caller at DF170 passes the structure's SGO, part/index and shape data, seed, local positions, flags and effect/sound settings into InitParam. Important positions include +0x60 effect flag, +0x70..0xA0 part data, +0x84 part flags, +0xB0 seed, +0x150 part condition, +0x158 CrashSoundType, +0x160 position-related value and +0x170 position. Its +0xB8 list contains part records for creating bodies. This layout is for the observed constructor/caller, not a generic serialized file record.

Static · novae: C6B70 queues CrashModel InitParams in the map manager at +0x130..0x148; the drain C71A0 later calls CB8F0 → CD070 → D3430, allocating the 0x300-byte CrashModel object. Three queue sources are the collapse/break paths for AnimationModel, Model and Structure. A one-update delay between break and visible piece is inferred from queueing, not frame-timed in game. The enqueue site itself is not the allocation site.

Static · novae: constructor D3430 rejects pieces outright when parameter +0x84 bit 8 or +0x61 is set; otherwise it selects detail level 0–4 from squared distance to the nearest of four view cameras. Base thresholds are about 27, 50, 90 and 200 m, with adjustments from source flags and global piece pressure; +0x84 bit 0x10 forces level 4. Over 50 or 160 global pieces can promote lower levels to 3 or 4. The exact appearance/physics differences among levels were not fully traced.

Static · novae: a single MapObject_CrashModel holds many 0x190-byte Havok-backed body records through a vector of 0x10-byte entries at +0x1E0. The builder visits part nodes, skips disabled node flags and associates each valid node with a shape from its part table; it initializes each body's start height at +0x160/+0x164 from the world pose. One CrashModel is therefore not one rigid body.

Static · novae: detail levels 0–1 reference class counter 124DD68 and levels 2–4 124DD6C. If the selected counter is already over 300 or 800 respectively, construction yields no bodies. Creation increments global piece counter 124DD64, class counter and object count +0x178; freeing bodies and the CrashModel decrements them. These are dynamic resource-pressure checks, not a 300-body-per-map static allocation limit.

Crash-piece pose, rest state and synchronized sinking

Static · novae: D8140 converts each Havok body's position and rotation into a draw pose, composing its local rotation/offset; D8220 writes the result to the associated render node (+0x30 quaternion, +0x40 position) and its child chain. The pair runs during creation and ticks. An effect attached to a moving fragment can read these node poses each frame; no scaling transform is handled in this observed path.

Static · novae: the body tick D7830 classifies a body as rested based on low squared speed and a frame counter beyond ~90 (or a secondary count reaching 3). Once allowed to sink it switches to Havok layer 30 and moves downward every update. Other counters at +0x178 and position/height test +0x164 are present, but their complete completion predicate was only inferred.

Static · novae: CrashModel's update ticks each child body and waits until over 95% have rested, then sets the group's sink flag +0x252. Bodies move to layer 30 and sink together, becoming finished when their draw y falls more than 10 m below the stored start height. Finished bodies decrement counters; once all are gone and the accompanying effect finishes, the CrashModel destroys itself. This group gate is why single fragments need not sink immediately on their own rest event.

Structure part hits and pending break records

Static · novae: Structure damage slot DEE20 distinguishes a hit on the root from one on a non-root piece. Root damage follows the base durability path; a non-root hit breaks the affected part through DFAF0 without reducing whole-structure durability. The part table at model +0x260 has 0x38-byte entries and a class-specific subtable selection; a referenced 0x50-byte entry has a breakable flag at +0x24. Collapse slot DEFA0 visits breakable parts and then root.

Static · novae: a part break at DFAF0 obtains a per-structure random seed, creates a 0x200-byte break record via DF170, files a copy in a hash table through E0550/DF690 (its consumer unresolved), then finalizes through DF5D0. Finalization is not merely free: when record +0xD0 is set, it queues the CrashModel InitParam via C6B70, then frees the record.

Map renderer, instance stream and shader families

Static · novae: map render objects include MapRenderer, ModelRenderer::RenderObject, Unit, RenderObject_Nodes and 0x30-byte RenderGroups for model/LOD; Units are 0x38 bytes with +0x10 next, +0x24 per-instance scalar and +0x28 placement. The visible LOD list [impl+0xD8] is built by per-frame 100D30; FF340 clears lists at view start. Draw phases invoke 102920 from slots 5/7/10; their exact correspondence to Commander stages was not established. The scalar +0x24 was initially mislabelled fade and is now identified as interior_random_seed.

Static · novae: 102920 fills a CPU buffer with 0x20-byte per-instance pose records (rotation quaternion xyzw and translation xyz/uniform-scale w), uploads them, and draws via DrawIndexedInstanced at 5B3120. Vertex shaders sample g_instancing_array using InstanceID, stride and bone index, with a separate inverse matrix array. This shared path underlies map models and many broken pieces, not an object-by-object draw call per placement.

Static correction · novae: Unit +0x24 is interior_random_seed, not camera fade. Model setup reserves an offset for this named material parameter; 109640 copies the unit float to each instance's stream record and fills additional named 12-byte per-instance entries (including likely change colors) from row data or defaults. Only shaders that declare the parameter use its value, especially the window-interior family.

Static D3D11 path · novae: helper 5F0250 maps a dynamic vertex-buffer ring for the per-instance stream in slot 1: it uses WRITE_NO_OVERWRITE until wrap and WRITE_DISCARD at wrap, binds the stride/offset via IASetVertexBuffers and is unmapped in 102920. These attributes travel next to the pose array, as vertex inputs; they are not automatically pixel-shader-visible alpha controls.

Static shader census · novae: surveyed EDF5 map shaders do not expose a general per-prop fade/alpha/dither attribute. Clip shaders use per-material alpha_clip; translucent glass/alpha families use forward lighting and falloff settings; some solid-build shaders accept change_color; the window shader alone exposes the cited interior_random_seed and wrap count. All named map families use instancing. A seed input cannot be assumed to be a transparency amount in stock shaders.

Static · novae: the MapRenderer maintains [impl+0xD8] for ModelRenderer::RenderObject and [impl+0xE8] for RenderObject_Nodes, which includes CrashModel fragments and Trees. G-buffer draw FF7B0 switches g_xgl_id between values 1 and 0 around the two lists. That ID reaches the G-buffer alpha/ID lane and affects decals' tests, explaining why collapsed building parts render with a different decal identity.

Unverified proposal · novae: a camera-near per-prop fade would need a per-instance value, replacement map-material shaders that actually consume it and a deliberate shadow-pass policy. Unit +0x24 could be reused through a hook, if compatible materials could declare/read it; stock prop shaders do not presently dither against that value. The material authoring and input-layout compatibility questions remain open, and no game test was provided. Do not present this as an existing EDF5 feature.

Model suffix identities and non-building debris

Static · novae: the model name suffix builder CF850 maps role 0 to nothing, 1 to _lod, 2 _lod2, 3 _lod3, 4 _hk, 5 _gr. Its observed AnyObject constructor caller passes zero, a LOD-table value and zero; no direct constant-five call was found. Rubble _gr names therefore appear as complete names in the mapo data, not evidence that the builder invents them from every base model.

Static call-site correction · novae: ModelDebris factory and constructor paths were used by enemy/vehicle systems (including insect death) and had no known map-object caller. Its tick increments a frame-time counter and destroys the object after 3.0 time units. Despite the class name, it is not the Structure/CrashModel building-rubble system; older “building debris” wording is corrected by this call-site census.

Provenance: novae (ajane), static reverse engineering of steam-5d11de53 with related shader and Havok references. This appendix keeps the discovered correction to interior_random_seed, the proposed fade's unverified status and inferred queue/sinking timing explicit.
