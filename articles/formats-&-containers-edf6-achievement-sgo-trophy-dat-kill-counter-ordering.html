EDF6 kill counters and TROPHY.DAT: why variable order matters

UniversalFormats & ContainersFile FormatsEDF 4.1EDF 6
Technical reference · Reviewed Python source containing exact-build reverse-engineered save/UI assumptions; no new runtime save migration

From an enemy's SGO to battle statistics

The examined EDF6 kill-counter path reads a name such as game_object_kill_counter from the dying object's SGO and increments the matching variable in the in-memory achievement map. This is name-based at runtime: a missing name does not automatically create a new persistent category, so an imported EDF4.1 enemy can die normally while not affecting the intended battle-record row.

The variables originate in APP:/ETC/Achievement.sgo under AchievementVariable, represented in the retained source as rows of the form:

["variableName", "int", 0]

The UI labels are resolved separately from text keys constructed as StatusInfo_ plus the achievement variable name. Adding an SGO variable without its corresponding localized text and battle-record UI row is only a partial implementation.

The compatibility trap: save slots are ordered, not namespaced

The source RE describes TROPHY.DAT as retaining 200 integer variable slots, with the values written by position in the achievement map's UTF-16 name ordering. Consequently, merely appending a new name to an editable AchievementVariable list is not necessarily safe: a name that sorts before an existing stock variable may shift the existing variable's saved index and make old values appear under the wrong category.

The EDF4.1 compatibility mapping explicitly uses names beginning with lowercase edf41_ because those names sort after the known stock uppercase-key domain in the studied build. It also rejects the extension if the current achievement table already contains a different name sorting after the first new edf41_ key. This conservative failure is necessary: in the presence of another mod's later-sorting variable, assuming the new rows cannot change saved positions would be unjustified.

The rule is about the actual game's comparator and target build. It is not a universal guarantee that adding any lowercase string will preserve arbitrary modified saves.

Battle-record table capacity and localization

The retained RE identifies the battle-record constructor as using a fixed 90-row stock table. Its row-count comparison is a signed 8-bit limit; therefore a compatible extension must not assume more than 127 rows without an additional engine patch. The save's 200 variable slots and the UI's 127-row bound are two independent capacity constraints: the smaller bound may win even when the save format still has room.

The studied EDF4.1 port adds 18 categories of its own. For example:

  • MotherShip401KillCount is treated as the source's Earth Eater/Brain category, with one counter rather than inventing two separate saved tallies.
  • NestKillCount accepts the source's AntHillKillCount alias while keeping its own 4.1 category; it must not collapse into EDF6's unrelated AntHill category.
  • Categories for Hector, Deiroi, Nephila and the two flying drones retain distinct keys.

Labels were provided separately for SC, CN, EN, JA and KR. A marker (4.1) in each language differentiates these ported rows from similarly named EDF6 rows; this marker is a presentation policy rather than part of the actual counter identity.

Implementing a safe extension

  1. Determine the native counter name supplied by each imported object's SGO.
  2. Resolve that name to a stable, collision-free new variable name. Keep explicit aliases where old and new class labels differ.
  3. Inspect the existing AchievementVariable table, including other mods' additions, and verify the proposed names preserve every preexisting name's ordinal position.
  4. Check both 200 persistent variables and the battle record's row capacity in the specific build.
  5. Add the corresponding StatusInfo_… strings in each supported locale; verify actual character encoding and UI display separately.
  6. Test with an existing saved profile and compare all prior counts before and after installation, removal and reinstallation. The retained source-only mapping does not constitute that runtime/save-migration test.

Evidence and limits: R9 components/objects/pylib/edf41kills.py includes these names, ordering guards, exact-build EDF.dll offsets and map/save assumptions. The current article is a code-level reconciliation of that source, not a new disassembly or confirmation that every game build uses the same save format.
