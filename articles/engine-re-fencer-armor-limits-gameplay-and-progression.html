Fencer armor limits: mission-entry caps versus earned armor

UniversalEngine RE & NetworkingGameplay & AIEDF 5EDF 6
Technical reference · Runtime-positive for the tested EDF5-port campaign families; exact-binary for no-cap path

EDF separates the armor value selected by the player, the maximum permitted on mission entry, and persistent armor growth earned by collecting crates. A mod that brings EDF5 campaigns into EDF6 must not confuse these mechanisms. The values below are observed in the tested EDF5-content port running under EDF6, not a universal table for every installation or arbitrary mission.

What the mission-entry cap does

When armor limits are enabled, the observed Fencer mission-entry behavior is:

mission_start_armor_raw = min(selected_armor_raw, translated_mission_cap_raw)

A selected amount below the mission cap remains unchanged. The cap is an upper bound; it does not fill armor up to the cap. Selecting more than the cap clamps the value before entry. The same cap was observed both in the user interface and in actual gameplay in the tested cases.

EDF5-content campaign hosted in EDF6 Tested mission/difficulty Observed Fencer mission cap Evidence
Base Mission 47, Easy 1069 HP UI and gameplay; below/above-cap controls
DLC1 Mission 11, Easy 1644 HP Gameplay; below-cap preservation
DLC2 Mission 3, Easy 2034 HP Gameplay cap

On base Mission 47, deliberately selecting 250 HP entered at 250 HP; selecting approximately 900 HP entered at that selection; selecting above 1069 entered at 1069. A Wing Diver control remained at 559 HP in both the UI and mission, showing that the tested Fencer-specific translation did not inadvertently change that class.

For comparison, independently checked native EDF6 control values were 1382 HP (main campaign Mission 116, Easy), 2012 HP (DLC1 Mission 18, Easy), and 2286 HP (DLC2 Mission 38, Easy). These native controls are separate from the EDF5-port translation and must not be substituted for the port's limits.

Armor Limit OFF is a different branch

The native EDF6 MissionSync path uses a negative cap sentinel -1 for an unrestricted room. In the examined binary, the mission cap candidate is initially 0xFFFFFFFF; it is replaced with a normal nonnegative cap only when cap-lock conditions apply.

At the gameplay serializer, selected raw armor is loaded from loadout+0x24. The cap sign is tested (test ebx,ebx); the js branch skips clamping when the cap is negative. Thus the native behavior for cap = -1 is to preserve the selected armor value.

The examined Fencer translation path explicitly ignores negative caps and therefore preserves this branch. This is exact static evidence, not a separately completed runtime test of Armor Limit OFF for every lobby topology. A safe translator must never silently turn an unrestricted room into a restricted one.

Armor crates and saved progression are not mission caps

A runtime test credited seven Fencer armor crates and observed a maximum-armor gain of 4 HP. This is consistent with the EDF6 Fencer growth factor retained in the research (0.595 HP per credited armor crate, versus 0.80 for EDF5 Fencer), subject to the game's normal accumulation/rounding. The intended port behavior was to keep EDF6-native persistent armor progression, even while translating the mission-entry cap for EDF5 campaign content.

In other words, changing SoldierInit, armor-box rewards or save progression merely to imitate EDF5 armor gains would be a separate behavioral change, not a required part of fixing the Fencer mission limit.

Why a shared raw cap cannot reproduce all EDF5 class HP limits

For the examined difficulty profile, the native engine computes a common raw cap from mission position, then applies class-specific armor conversion. The useful simplified relationship is:

cap_hp(class) = base_hp(class) + floor(common_raw_cap * class_growth(class))

The measured class conversion parameters are:

Class EDF5 base HP EDF5 growth EDF6 base HP EDF6 growth
Ranger 200 0.64 200 0.56
Air Raider 200 0.64 200 0.56
Wing Diver 150 0.40 150 0.35
Fencer 250 0.80 250 about 0.595

For Ranger, Air Raider and Wing Diver, the EDF5/EDF6 growth ratio is the same: 8/7 ≈ 1.142857. Fencer instead requires 0.80 / 0.595 ≈ 1.344538. Therefore one shared change to the raw armor_limit curve cannot recreate all four EDF5 class caps while keeping native EDF6 SoldierInit growth. This is a structural consequence of the class parameters, not an arbitrary tuning preference.

A retained source-profile example demonstrates the difference. The observed raw cap came from mission index divided by mission_count - 1, not from the LIST source's progression float (field9). With profile endpoints [4500,8000]:

EDF5 original: 4500 + 3500 * 5/110 ~= 4659 raw
Port layout:    4500 + 3500 * 6/111 ~= 4689 raw

The one-row offset is associated with preserving the technical tutorial mission M000 in the installed port's LIST. It is a small independent ordinal shift; changing or removing M000 to hide it can break saved mission identity and is not a legitimate fix for the Fencer class-growth mismatch.

At approximately 4689 raw, EDF6 class conversion gives 2825 HP Ranger/Air Raider, 1791 HP Wing Diver, 3039 HP Fencer. With the original EDF5 raw value around 4659, EDF5 class conversion gives 3181 HP Ranger/Air Raider, 2013 HP Wing Diver, 3977 HP Fencer. These numbers belong to this specific profile/mission example and must not be mixed with the separate 1069/1644/2034 gameplay-cap controls above.

Important boundary: the synchronized MissionSync message carries a common raw cap, not a hidden Fencer-only network cap field. The observed class difference is due to later class conversion, so changing network packet shape is not a justified cure. The class field and player slot identity must also be kept distinct: an earlier interpretation of NetworkUser+0x48 as SoldierType was withdrawn; the more complete dataflow identified a player/slot index instead.

Implementation boundary

  • Apply a class-specific cap translation only where the pack identity and requested cap are proven; do not rewrite all classes.
  • Preserve player-selected armor below the cap and preserve cap < 0 unchanged.
  • Keep mission-entry clamping separate from persistent armor growth and rewards.
  • Do not infer that a user-interface-only success guarantees gameplay behavior; the observed cases were checked inside missions.
  • Do not infer multiplayer safety or foreign MissionPack/namespace collision safety from single-player or isolated online checks.

Still unqualified in the retained evidence: cross-provider namespace rebasing, unrelated third-party MissionPack false-positive controls, and the full two-peer host/client/rejoin/transition matrix. The underlying arithmetic for the tested three EDF5-port campaign families is runtime-positive.
