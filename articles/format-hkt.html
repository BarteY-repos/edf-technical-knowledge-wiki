HKT — Havok collision data and its EDF container context

File FormatsSource-scoped referenceEDF 4.1EDF 5EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: HKT stores Havok physics and collision data: shapes and related structures used by the game's physics system.

Where it fits: An HKT payload can appear inside a MAD map archive. EDF4.1-era collision structures are different from those used by EDF6.

Important distinction: Collision data is not the same as visible terrain or a navigation mesh; decoding a file is not proof that the game accepts its physics graph.

Where HKT occurs

The inspected native EDF6 map .MAD files use a MARC version-5 archive wrapper. In a bounded sample of 50 map MADs, each archive contained one member called collision.hkt, with a native Havok TAG0 tagfile as its payload. The archive wrapper begins with MARC, whereas the embedded collision data begins at the documented payload offset 0x24.

That observed pattern describes those 50 native examples. It does not prove that every possible MAD or object-specific collision resource has exactly one HKT member.

Havok version and data structure matter

EDF4.1's documented original collision source includes Havok 2014-era hkp structures. EDF6 uses Havok 2020-era hknp data. Moving the outer bytes, swapping an SDK/version string or reusing one generation's shape/motion records is not a proven binary conversion.

The measured EDF6 native corpus includes explicit shape classes, motion/material records, collision filter data and type/data/index sections. An acceptable HKT needs a coherent serialized object graph and physical data layout, not merely a recognizable file signature.

EDF6 TAG0 tagfile: known section structure

The original EDF6 Havok source-corpus notes identify the studied payloads as Havok 2020.1 binary tagfiles, with the SDK version text 20200100. A section begins with an 8-byte header: a big-endian 32-bit word containing the two high kind bits and a 30-bit size (including the header), followed by a four-character tag. In that source profile, kind 0 is a nested container and kind 1 is a data section.

Tag Observed purpose
TAG0 Outermost tagfile container
SDKV SDK version string (20200100 in the studied files)
DATA Object and array payloads; serialized numeric fields are little-endian
TYPE Type-description container
TST1, TNA1 Type-name strings, declarations and template arguments
FST1, TBDY Field-name strings and type-member/layout descriptions
INDX, ITEM References to indexed objects, arrays and strings

Mixed byte order matters: the section-size header word is big-endian while the measured DATA values are little-endian. Reading every u32 with one global endianness setting is not supported by this profile.

The surveyed EDF6 native files did not include THSH hashes or a PTCH patch table. That is a bounded corpus observation, not a general prohibition in Havok tagfiles outside EDF6.

Collision is not navigation

HKT can supply collision bodies and their shape/filter semantics. Navigation data and route acceptance are separate evidence. A map can have parseable collision payloads without establishing that NPCs use the intended traversability, body assignments or filter rules.

Object-specific SHKT/HKT-style resources likewise have owner and lifecycle constraints. A visually correct object or collision mesh does not establish body identity, ragdoll references or correct gameplay reactions.

Known limits

  • The collision.hkt membership and TAG0 position stated above are from the bounded EDF6 MAD corpus.
  • Source-derived physical layout rules are profile- and shape-dependent.
  • Private Havok SDK materials are research-only; the wiki does not redistribute those originals.
  • Offline decoding or byte-level reconstruction must not be reported as a native runtime collision/NAV pass.
