Startup logos and two documented skip paths

Evidence: static · Build: steam-678ccb46 · Fact ID: startup-logos

Startup logos, two ways: metoxys's NoSplashscreens hooks 718A2F (the call that receives MAINSCRIPT.AS in memory) and, when esi is 0xDDD2, writes // at [r14+0x2EF8], commenting out the script's CompanyLogo(); call (straight to the title screen); MoistGoat's NoSplashScreen NOPs a 7-byte lea rax,[...] at 8BFA40 (anchor 8BFA3A + 6) and lands on the "press Enter" screen.

Basis: the patches' anchors and code

Addresses (build-specific RVAs unless indicated): 718A2F, 8BFA3A

Attribution: metoxys (NoSplashscreens), MoistGoat (NoSplashScreen), novae (ajane)'s EDF6 outside set · 2026-10-16

Worker-thread pool sizing by logical processors

Evidence: static · Build: steam-678ccb46 · Fact ID: worker-thread-pools

Worker threads: EDF.dll makes its pools with one thread per logical processor less one, so no setting raises the count: 116F430 the pool "CASMtCalculate" (GetSystemInfo().dwNumberOfProcessors - 1), 1191360 "xgs::sysmte::functional" (the game's spelling; std::thread::hardware_concurrency() - 1), 10E8B0 "FieldRender::Initialize" (the same, for a map's set-up: 65B90 makes a pool, 65E90 hands out jobs, 65F10 waits, fork and join from the game loop's thread, 1198DA0 called by 705530).

Basis: the EDF6VR source's comments (read from the file)

Addresses (build-specific RVAs unless indicated): 116F430, 1191360, 10E8B0, 65B90, 65E90, 65F10, 1198DA0, 705530

Dynamically loaded XInput interface

Evidence: static · Build: steam-678ccb46 · Fact ID: imports-pad-poll

Imports and the pad: EDF.dll resolves XInput with GetProcAddress rather than importing it (its import slot is 1755578); D3D11CreateDevice is imported at 1756728. The pad poll 1188380 first decides which slot to read: it reads the pad when a predicate or the byte [2136F71] is set, else uses slot -1 (no pad); when [2136504] is 1, slots 0 and 1 swap.

Basis: the EDF6VR source's comments (import directory parsed offline; the poll's instructions quoted)

Addresses (build-specific RVAs unless indicated): 1755578, 1756728, 1188380, 2136F71, 2136504

Attribution: EDF6VR source (momotori01) · 2026-11-07

ExitApp quit path and close-state lock

Evidence: static · Build: steam-678ccb46 · Fact ID: exitapp-quit

1183190 is the game's own quit (ExitApp): under a lock (50BC0 / 50BE0) it sets the may-close byte [21360B8] to 1 and [21360B9] to 0, then calls the USER32 import at 1755F40 with the game window [21360A8] and message 0x10 (WM_CLOSE). Basis: Quit() in autopilot.cpp; 1183190 re-read with fn.py here, matching

Mouse look sampling in the foreground window

Evidence: static · Build: steam-678ccb46 · Fact ID: mouse-look-recenter

Mouse look: the frame loop 1183880, while the game believes its window is in the foreground, reads GetCursorPos every frame, takes the offset from its window's center as the look, then SetCursorPos back to the center (1183B7D, also 11845D1). So a game told it is in front pulls the desktop's cursor; the author's background plugin gives the whole process a virtual cursor instead. Also (EDF6VehicleFPS 0.1.66's source, checked by hajisensai, docs/vehiclefps-0.1.66-re.md): the in-battle cursor read is GetCursorPos at 1183A82 (call [1755F80]), [1FEEE1D] == 0 means the mouse is locked, the main and second window handles sit at 21360A8 / 21360B0; the game's own Present call is at 1118B45 (9 bytes, unverified) and mesh DrawIndexed calls at 10FF556 / 10FF5C1.

Basis: autopilot.cpp's comments, from the author's runs (BACKGROUND log rows); the busy window thread, the sum's gate and its take: #edf6-window-thread-busy-loop, #edf6-mouse-look-sum-gate, #edf6-mouse-total-take; the Present site at 1118B45 seen working, frame-pacing.md#edf6-present-hook-site

Addresses (build-specific RVAs unless indicated): 1183880, 1183B7D, 11845D1, 1183A82, 1755F80, 1FEEE1D, 21360A8, 21360B0, 1118B45, 10FF556, 10FF5C1

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Controller and keyboard inputs
  2. Per-frame action decoding

EDF Knowledge Hub record — original wording — expand (1,373 characters)

Where a soldier reads its movement and look keys (answers #input-keyboard-vs-xinput's open point): the left-stick reader 56D920 and the right-stick reader 56DBC0 take the pad path when the controller object's +0x2D68 is non-zero or 1183D70 (movzx eax, byte [1FEEE1C]) is true: the sticks are the controller's own +0x0C / +0x24 (move: right positive, forward negative) and +0x3C / +0x54 (look: right / down positive) (56DA0C, 56DE6C). Otherwise the keyboard path reads the record [human+0xD40] (stride 0xA80) in the controller object: key bytes +0x610 forward, +0x628 left, +0x640 back, +0x658 right (56D99D..56D9E4: x = -[628] + [658], y = -[610] + [640]) and the mouse's per-frame motion +0x66C / +0x684, divided by 24 (1766014, 56DD40). [human+0xD40] is the soldier class's key-configuration record, not a player number: HumanBase (56AAF6) and AssultSoldier (Ranger) write 0, PaleWing (Wing Diver) 1 (57CD80), Engineer (Air Raider) 2 (563706), HeavyArmor (Fencer) 3 (5652C8); the controller object holds the four classes' records. The pad bound to a player is [human+0x338], set by 54ED40 (player.md); the mission's player creation 22AB90 passes its 5th argument, the pad, and skips the call for a negative one (22ACFB: a remote online user, -1); 54EDB0 / 54E830 reset it to -1 for a soldier with no pad, so this machine's first local player has pad 0 offline and online.

Basis: the author's static reading (2026-10-21 and 10-24) and a fix it needed in game (WASD read through this record); 56D994..56DA0C re-read with fn.py (matches)

Addresses (build-specific RVAs unless indicated): 56D920, 56DBC0, 1183D70, 1FEEE1C, 56DA0C, 56DE6C, 56D99D, 56D9E4, 1766014, 56DD40, 56AAF6, 57CD80, 563706, 5652C8, 54ED40, 22AB90, 22ACFB, 54EDB0, 54E830

EDF6 pause reasons in game system

Evidence: static · Build: steam-678ccb46 · Fact ID: system-pause-bits

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Game system pause mask
  2. Pause and resume call sites
  3. Per-subsystem behaviour
EDF Knowledge Hub record — original wording — expand (1,259 characters)

Pause: the game system (xgs::game::System, [20B2958], vtable 1AE2278) keeps pause-reason bits at +0xCD8 and the bits that take effect at +0xCDC; the game is paused when they share a bit. 1196FC0(system, bits, bool set) sets or clears bits of +0xCD8 and, when the paused state flips, calls slot 11 (+0x58, argument = paused) of every listener in the vector at +0xCC0 (end +0xCD0); 1195630 changes +0xCDC. The pause menu sets bit 2: HUiPause's constructor at 934A46, its destructor clears it at 934ED3. The system update 1198DA0 stops adding time when paused (1198DFE) and skips the whole scene update (every object, vehicle input included) at 11990C7 (20 bytes from 11990C0) straight to 119953B; from there it still steps the four view slots (system +0x4D8, 0x188 apart) with 118DF40 (the camera's slot 4, F86A0 for CharacterGhostCamera, then 11D4440 for each HUD on it) and renders (HUD draw 11D43F0 -> each HUD's slot 3), so cameras and HUD keep running under the pause menu. In normal frames too the camera steps only there: the object loop 1199250 skips objects with bit 4 of +0x18. The HUD layouts (for example lyt_HudRader01.sgo) and lyt_PauseBG.sgo carry a transition_slide (0.3 s to (0, 1080), off the bottom); whether pausing plays it was not checked.

Basis: 1196FC0 re-read with fn.py (+0xCD8 or / and-not, test against +0xCDC, listeners [rcx+0xCC0] called through [rax+0x58]); the rest the author's reading ("H"; the camera stepping only there "M"); settles globals.md#game-system-fields' "+0xCD8 paused?"

Addresses (build-specific RVAs unless indicated): 20B2958, 1AE2278, 1196FC0, 1195630, 934A46, 934ED3, 1198DA0, 1198DFE, 11990C7, 11990C0, 119953B, 118DF40, F86A0, 11D4440, 11D43F0, 1199250

EDF6 shutdown and bank cache order

Evidence: static · Build: steam-678ccb46 · Fact ID: shutdown-order-bank-cache

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Application destructor
  2. System and resource teardown
  3. Sound and cache lifetime
EDF Knowledge Hub record — original wording — expand (1,206 characters)

Shutdown order: the application destructor 7021F0 (called at 70293F) destroys the singletons; every stock owner gives its sound-bank references back inside it, before it deletes the sound system (vtable call at 70248C) and nulls [20B2948] (702493) (the author's exit marker on M019: 12 to 19 cache nodes, each count 1 and registered, on entry; 0 at the atexit). The atexit leak reporter 1750870 logs SoundBank::Release error ref count for each bank still counted (its log call 17508B5 -> 3E4A0), then runs the bank cache's destructor 7A9850 -> 7A9670 -> 7A99D0 -> 7AABC0, which for a bank still registered calls 7ADCE0 with the null sound system and faults at 7ADCFB (mov rdi,[rcx+0x40], rcx 0): so a plugin holding a counted reference into a game cache must give it back before 7021F0 finishes (sound.md#sound-raw-cue-bank-cache). An earlier EDF.dll atexit destructor (the object at 111822C: 113CBE0 -> 175280 -> 175690, releasing an array of D3D11 objects) can make d3d11 / dxcore end the process with NtTerminateProcess(-1, 0xC000004B) (STATUS_THREAD_IS_TERMINATING), a silent clean exit that never reaches the bank cache; which way an exit goes seems to depend on the D3D objects still held (inferred).

Basis: the author's static reading and its diagnostic in-game runs of 2026-10-17 (exit markers, crash dumps, an NtTerminateProcess hook; the crash was its own sound bank kept "for the process")

Addresses (build-specific RVAs unless indicated): 7021F0, 70293F, 70248C, 20B2948, 702493, 1750870, 17508B5, 3E4A0, 7A9850, 7A9670, 7A99D0, 7AABC0, 7ADCE0, 7ADCFB, 111822C, 113CBE0, 175280, 175690

Object-manager frame update ordering

Evidence: static · Build: steam-678ccb46 · Fact ID: object-manager-frame-order

The object manager's frame order: the main loop (705715) calls 1198DA0 with the object manager [20B2958] (its only call site), which walks in one function: the +0x488 list calling slot 7 (1199131), after a dispatch and wait on the +0x358 list (65E90 -> 65F10 at 1199174 / 119917D, parallel jobs with a join, inferred, finished before the next loops); the object list calling slot 4 (1199261; vehicles' per-frame update); the +0xCC0 list calling slot 8 (119939B); the +0x448 list calling slot 5 (119940D, children recursively through 1199BC0); all plain loops on one thread (DAC5B0 / DB04B0 between them are empty profiling stubs, ret 0). An object created with 1194280 on that manager (e.g. a bullet from an IndirectFireUnit, 2B9F61 / 2B9F68) runs its slot 5 after every vehicle's slot 4 in the same frame.

Window thread loop and Sleep(0)

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-window-thread-busy-loop

The window thread 1184460 loops call 1183880 and then Sleep(0) (import 1755728, at 11844EA), with no wait, so EDF6 calls GetCursorPos about 500,000-600,000 times a second, not from the frame limiter. 1183880 drains messages with PeekMessageW (1755FE0, then translate and dispatch), tests the foreground ([1755EA0] against [21360A8], into [rbx+0x30]), and while in front calls GetWindowRect (1755EB0) and GetCursorPos at 1183A82 and puts the rect's center in [1FEEE40] / [1FEEE44]. By state [rdi+0x18] the thread calls 1183470, 1183880 or 1184BA0 / 1184880; it ends when [rdi+0x29] != 0.

Basis: fn.py read; in game a tally of GetCursorPos return addresses for 70 s in a mission found only 1183A88 and 1183C6F (about 11.7 million each in 39 s), both in 1183880, whose only caller is 11844D8

Addresses (build-specific RVAs unless indicated): 1184460, 11844D8, 11844EA, 1183880, 1183A82

Attribution: novae (ajane) · 2026-11-13

Mouse cursor delta accumulation under lock

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-mouse-look-sum-gate

1183880 adds (cursor - center) to the floats [1FEEE20] / [1FEEE24] inside lock 2136000 (enter 50BC0, leave 50BE0) only when the cursor is off center and the timer 66D00(rbx+0x40) exceeds [1C36990] (1183AF1..1183B01; what the timer measures is unread). Then, if [1FEEE1D] == 0, it sets the cursor back to the center (1183B7D); otherwise it clears the total.

Basis: fn.py read; in game a background plugin's virtual cursor moves (mouse 300 0, mouse 1500 0) were recentered (1,642 SetCursorPos calls) but did not turn the camera, while the pad's right stick did

Addresses (build-specific RVAs unless indicated): 1183880, 1183AF1, 1183B01, 1183B7D, 1C36990, 1FEEE20, 1FEEE24, 2136000

Game-thread mouse delta consumption and reset

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-mouse-total-take

The game thread takes the mouse total once per input refresh: 1188270 calls 11831F0(out, reset=1) at 1188479 (E8 72 AD FF FF, the only caller); 11831F0 (33 bytes, a leaf with no .pdata entry: 0F 28 05 29 BC E6 00 48 8B C1 66 0F 7F 01 84 D2 74 0E 0F 28 05 27 29 5E 00 0F 29 05 10 BC E6 00 C3) copies the 16 bytes at [1FEEE20] with movaps and zeroes them from [1765B30], without the lock; the caller adds x and y to [rbx+r13+0x480] / +0x484 (stride 0x4A0). So each 1/60 s step gets the mouse reports that arrived since the last one (camera.md#edf6-mouse-125hz-aliasing).

Basis: fn.py read; novae (ajane)

Addresses (build-specific RVAs unless indicated): 1188270, 1188479, 11831F0, 1FEEE20, 1765B30

Input-mode and mouse-lock state bytes

Evidence: static · Build: steam-678ccb46 · Fact ID: edf6-input-mode-bytes

The input-mode byte [1FEEE1C] (1 pad, 0 keyboard and mouse) and the mouse lock [1FEEE1D] (0 locked) are 01 01 in the file and change only when a device presses Start on the title screen: the setter 1184610 writes [1FEEE1C] = cl and [21360BF] = 1; the title's Press Start handler 8D1150 sets 1 for a pad press (8D13E2) and 0 for a key (8D1441); its other callers are 8CEBF1 (in 8CEBD0) and 8D07A1. Then the lock setter 11845F0(0) writes [1FEEE1D] (eight UI callers: 810DA8, 877370, 8CEBFC, 8D13E9, 8D7B05, 8DECDB, 934B7E, 95C992); 11845B0 also locks after recentering. A start that skips the title stays in pad mode with the mouse unlocked (menu-script.md#edf6-debug-start-pad-mode).

Basis: fn.py read, imports named with pefile; the pad mode after a debug start seen in game

November 2026: system hooks, renderer slots and pause clocks

This section reconciles previously missing exact source IDs from system.md into the existing EDF6 system appendix. Three source records about DLL detach, save rewrites and the 1080p command-line option were already individually anchored elsewhere and remain there. Addresses describe contributor-specific ELF/PE analysis of EDF.dll, not universal addresses for other editions.

Import address table and protected slot swaps

Static. EDF6's import directory at EDF+1755000 spans 0x1990 bytes in read-only .rdata, so an IAT hook needs VirtualProtect. USER32's 56 slots occupy 1755E60–1756018 (GetForegroundWindow 1755EA0, GetKeyboardState 1756008); EOSSDK adds 125 imports from 1755030, unlike EDF4.1/EDF5. EDF5's table at C97000 spans 0x1140 and 4.1's at 918000 0xE80, also read-only. EDF6.exe imports one EDF.dll function via slot 0x2000; game code resides in the DLL. XInput is loaded through GetProcAddress, not a direct static import, in all three.

Startup mutex blocks second instance

Static. Startup caller 6FEEA0 invokes 702E60 (alongside SteamAPI_Init); CreateMutexW(NULL,TRUE,name) at 702E98 stores its handle at object +0x18. On GetLastError==0xB7 the code displays a localized MessageBoxW and returns1, rejecting duplicate launch. The mutex name lives at 17E8510 but was not printed. An early-loaded plugin could theoretically rename the CreateMutexW import at 1755688 or bypass the branch; the source does not assert such a bypass was tested.

Renderer-static swap-chain pointer

Static. The global renderer instance begins at EDF+2136FF0 (627 code references calculate its base); its +0x90 holds IDXGISwapChain*, hence the pointer is readable at EDF+2137080. The sole game Present reads through [rsi+0x90]; direct xrefs of 2137080 do not exist because code references the base plus offset. For comparison, EDF5 uses 1256C98, EDF4.1 CC4708 (renderer base CC4640+0xC8).

Sleep(0) poll-thread load remains unverified

Unverified. The contributor suggested the Sleep(0) input polling loop can keep a CPU thread near 100% load, and 哈吉千歳 reported fixing a related issue in their own work without naming the mod or mechanism. The source gives no independent CPU profiler trace or patch, so treat the full-load claim as a hypothesis, not an established benchmark.

Paused update advances camera and step counter, not game time

Static. System::update 1198DA0 receives a count of 1/60-second steps. When paused, game clock +0xCE4 and 112BAA0 do not advance, while step counter +0xCE0 increments regardless. Pause listeners' virtual slot3 and scene update callbacks 1193C70/1193D50 normally run only unpaused (without an active scene both callbacks still run), but 1195F20 always runs. Paused loop reaches 119953B: four view cameras step through 118DF40 (camera clock +0x530 advances), 11BEBE0 on system +0x250 and jobs at +0x358 keep running. Script look-at frame counts halt with gameplay time.

Paused world draw is demand-driven

Static with screen-frame behavior inferred. Renderer 11978D0 draws every unpaused frame, but during pause only if redraw byte system+0xAF0 is 1 (1198F76–1198FA4), then clears it. Writers include view fade setters 1198C8B/1198CE6, free-camera update 101C1D and unexamined 11916A2/1E757C. A paused screen is thought to retain its last scene image between redraws, but this was not directly traced. This describes the searched codepaths, not a proof that no outside executable component binds keys.

UI virtual pad, keybind guards and device-mode separation

UI input records: one device takes 0xDD0 bytes; 7B550 binds gamepad/mouse entries below +0x410 (around +8..+0x2C0) and keyboard binding +0x410+0x18i for game code 0x12+i, using Key%s and name table 11856F0. This is the menu's device-object layout, not the two 0x4A0-byte gameplay poll slots.

Menu virtual pad: 7CDC0 ORs gamepad directions with W (+0x620), S (+0x5C0), A (+0x410), D (+0x458) into up/down/left/right bits 1/2/4/8; arrows use +0xB30/B48/B60/B78 under the +0x4558 arrow gate. BackSpace/Escape cancel; Return/Space confirm; T and left Control have dedicated UI shortcuts, and mouse +0x2C0 activates hovered controls (+0x2F0 only in keyboard mode). Keyboard paths require device enabling at [[20B28A0]+0xA048+device]. These fixed menu keys bypass gameplay key configuration; E/F are not such UI shortcuts.

Class/vehicle-page rebind guard: 7CCD50 dispatches to 7CD9B0 for page kinds 3..10, denying a key already assigned to Common-page actions 0x16..0x21 for the same player and set. The Drive page (kind 5) permits the explicit S/W exceptions (codes 0x24/0x28). Class pages and vehicle pages are not compared against one another. Return 0 routes to OptionPlayer_KeyCantChange; this is a native UI restriction, not an input device polling rule.

Common-page reverse guard: for page kind 2, 7CD2D0 checks relevant class/vehicle pages from table 17F35F0 (kinds 3..10, current-class set except shared 3/4), with explicit exceptions for drive accelerate W and brake S. A collision returns 1 and offers OptionPlayer_KeyAlreadyChosen, which may clear competing assignments. The source audited guard and dialog code but did not launch a game rebinding test.

Keyboard versus pad mode: EDF6's Press Start chooses an input mode; in keyboard mode player 1 has keyboard/mouse but pad 0 is directed to player 2. In pad mode slot 0 includes pad 0 plus low-level keyboard channels, yet soldier move/look (56D920, 56DBC0) follow the stick branch and the keyconfig UI shows pad pages. This is more separation than EDF5's input merge. Proposed mixed-mode hooks at 118837E..118838A and soldier mode checks were not implemented/tested here; whether all action bindings then merge was not traced.

Steam Deck mode hypothesis: 1188230 assigns pad-merge flag [2136F70] from a boolean at SteamUtils010 vtable +0x110, with sites 8D07DE/95B735 and clear at 95B413. It could be IsSteamRunningOnSteamDeck (SDK method index 34 fits), which would share pad 0 with keyboard slot 0, but the interface method was **not** confirmed against the SDK or tested on a Deck. Treat the method name and behavior as an inference.

Wheel click thread-affinity lead · unverified: game-step code uses GetKeyState(1) while window message pump 1184460 owns PeekMessageW/GetCursorPos. No AttachThreadInput import was found; whether Windows reports an unowned game-thread key-state edge consistently was not resolved. Unlike the source author's EDF4.1/possible EDF5 report, there is no confirmed EDF6 repro or fix. Menus additionally use the window snapshot described above.

Player-two device binding and split-screen verification

Second-player enrolment: state handler 95B500 only activates when [rcx]==0. It first checks player-one record +0xDBC bit 0x80 for a sound/dialog path, else scans device records 1..3 (stride 0xDD0) for +0x89 and optional Deck +0xB9 press. On success it calls 76E00([20B28A0],1,d) to bind player-two controller slot 1 and 770D0 for Steam Input linkage, plays feedback and sets state 1. The Steam virtual-interface side effects were not fully traced.

UI player-count gate: ui::HUiModeSelect slot 1 8C3ED0, at 8C3FB6, is the lone writer found in searched code range 7C0000..900000 of local count [20B2890]+0x14FF4. After 95B500 signals player two, it writes count 2, sets +0x798=2 and opens confirmation; state 2 resets transient mode fields. The search was not a full-binary proof of uniqueness.

Contributor-verified split-screen harness: at HQMain→PlayMission_Offline transition (game thread, 9.6 s), setting local count to 2 and calling 76E00/770D0 for controller slot 1/device 1 produced M2 Easy with two Rangers, two vertical viewports, HUDs and radars, and camera slot 1. In the reported two-second stick-up probes pad index 1 moved only player 2 (12.39 m vs player 1's 0.03 m), while index 0 moved only player 1 (12.26 m vs 0.01 m); no crash, reported hidden-window 56–58 fps. Player 2 showed Armor 200, same three weapons and “Player 2” label. This **verified** claim is the contributor's run, not a newly repeated menu-driven split-screen test.

Mouse-look continuous input and rate limiter

Continuous look path: 1188479 calls classic cursor-warp delta provider 11831F0 (integer screen-pixel movement around window center, not WM_INPUT raw counts). Sites 1188738/1188756 publish analog values through 1182A00 at action +0x48, then ActionUpdate 1182BC0 copies to wrapper +0x0C before repeat/threshold bookkeeping. Fresh MouseMoveX/Y fields are +0xE8/+0xF0; filtered MouseX/Y/ReverseX/ReverseY at +0x108/+0x110/+0x118/+0x120 are constructed by RTTI-identified UiInput using real-time dt60. These are source static audits, not a raw-mouse-input patch validation.

Controller binding and player look: outer controller at 77030 has stride 0x2D70, selected sub-block outer+0x348+active*0xA80; 78890 maps continuous mouse movement wrappers +0x318/+0x330, with final normal-look axes at outer+active*0xA80+0x66C/+0x684. 56DBC0 is used by normal look at 57068B (R8=0) and accumulating look at 5730DD (R8=1). Main look 570650 scales by active-controller sensitivity +0x328*0.05, not render-frame delta time.

Rate limiter and transient input warning: console set_limit_rate handler 5785F0 changes global 1F6CC18 (default 26, accepted command range 0..100). Look helper then uses inherited /24 scale and per-component clamp [-16,+16]. Wheel consumption/reset, action suppression countdowns and dt60 filtering depend on frame cadence: inserting presentation-only frames without separating input refresh can consume a short wheel/press pulse before a fixed simulation step. No general 120-fps fix follows from these observations.
