EDF5 → EDF6 MDB conversion: geometry, names, materials and native paired evidence

ConversionModels & MDBModelsEDF 5EDF 6
Source-backed research / case study · Reconciled

EDF5 → EDF6 MDB migration is a semantic conversion, not a version-field rewrite. The findings below come from bounded paired native-model corpora and modded-game compatibility experiments; they do not establish a single universal MDB layout or a stock-game crash rule for every variation.

Paired-corpus measurements

  • HEIGEN: 63/63 source models passed structural and independent audit, with approximately 2.0 MB of semantic vertex lanes examined.
  • NW_EUROPE: 163/163 source MDBs passed source-integrity/binary checks, with approximately 31 MB examined.
  • DESERT: 76/76 models passed audit, including approximately 6.5 MB of vertex data.

These are validation counts on the studied corpus, not counts of distinct renderer profiles or proof of universal game compatibility.

MDB vertex declaration formats

Code Observed representation Width
1 float32 ×4 (BLENDWEIGHT in examples) 16 bytes
4 float32 ×3 12 bytes
7 float16 ×4 (often POSITION / NORMAL / TANGENT / BINORMAL) 8 bytes
12 float32 ×2 (TEXCOORD) 8 bytes
21 uint8 ×4 (BLENDINDICES) 4 bytes

Legitimate EDF6 material/geometry families in these samples include 60-, 68-, 76- and 84-byte layouts; several native-compatible records have repeated TEXCOORD occurrence orders such as 0,2,1 or 1,0. Therefore the visible UV-channel index and the physical declaration occurrence order are separate pieces of information. No evidence here shows that every alternative semantically equivalent ordering crashes the game.

Tangent space and precision changes

In the studied compatibility path, POSITION, TEXCOORD, BLENDWEIGHT and TANGENT were preserved while BINORMAL became (-x,-y,-z,w) across the game boundary. 16,796 half-float and 1,093 float32 binormals matched this sign rule; 1,093 float32 tangents were byte-exact. This is a cross-game relationship, not an instruction to negate binormals inside already-valid EDF6 data.

A set of 12 high-precision DESERT source meshes retained float32 lanes. Compatible 76-/84-byte layouts occurred elsewhere in native EDF6 even when the exact same shader-plus-layout combination was uncommon. Source precision should not be assumed incompatible simply because half-float is prevalent in another sample.

Bone, object name and entry-offset identity

Keeping the EDF5 source bone graph and its blend indices coherent proved a defensible compatibility strategy; matched EDF6 targets sometimes re-authored helper-bone order or count, so this is not a claim that the source bone graph is native-identical.

In EDF6/v32, the first Object dword behaved as the dedicated object NameTable reference; the second reference retained the linked bone/node role. For 165/165 paired target objects, the two names resolved to the same semantic string, although the NameTable integer indices need not be equal.

Offsets into Name, Texture, Material, MaterialParameter, MaterialTexture, Object, MeshInfo and declaration entries were consistently treated as relative to the entry containing the offset in the studied corpus. Any additional target-specific offset role must be established from its own records.

Shader and material migration is not a rename

Of 38 paired EDF5 source materials using snd_Map_Simple_Clip, only one native EDF6 target used snd_BRDF_Map_Simple_Clip. Other targets used Common, Common_Clip, Build or LOD families; even the one BRDF Simple Clip target changed its material ABI.

A matched palm leaf demonstrates the geometric implication:

Studied feature EDF5 source EDF6 native target
Leaf shader Legacy Simple_Clip BRDF Common_Clip
Samplers Albedo only Albedo + normal + packed parameters
Vertex stride 44 bytes 60 bytes
Tangent space No tangent/binormal Tangent and binormal included
First leaf mesh 888 vertices, 1944 indices 1380 vertices, 1944 indices
Second leaf mesh 36 vertices, 144 indices 72 vertices, 144 indices

The unchanged index counts with greater vertex counts are consistent with tangent/normal/UV seam splitting rather than new triangles. In a tested modded-game conversion, swapping only the shader name while keeping the old material/geometry contract produced black leaves; restoring a coherent legacy contract removed the symptom. That test does not establish the full native BRDF rebake for every asset.

EDF6 native counterparts can have genuinely re-authored packed textures. No universal source-mask → FPR channel shuffle is supported by these comparisons. See native MDB material profiles and packed R/M/FPR semantics.

162-material R5 ABI census: why a shader-only change is detectable

A separate source/target material audit of the studied DESERT508 R5 RAB inspected 162 material records against the native EDF6 HEIGEN507 and NW_EUROPE01 shader signature corpus. All 162 shader names were represented in that corpus, but exactly one material had a previously unseen parameter/sampler ABI for its selected shader: leaf material 1 of sk_ptree007_11m_shuro.mdb. It was also the only shader-name change from the EDF5 source. This is an independently bounded structural anomaly; it does not imply all shader/material mismatches necessarily crash.

The original EDF5 palm asset is byte-identical between DESERT508 and HEIGEN507 (decompressed MDB 53,806 bytes, SHA-256 b9bc10fcca56383701e0b1fe325f0adeb8667e061be1c1bf9b6f5bc7522b2caa). Its legacy snd_Map_Simple_Clip leaf material declares diffuse, specular_pow, specular_color, light_smooth, alpha_clip, and an albedo-only sampler. By contrast, the only sampled native snd_BRDF_Map_Simple_Clip material declares diffuse, specular_color, specular_diffuse_blend, metallic, roughness and an albedo sampler. Replacing just the shader string therefore creates an unobserved hybrid ABI.

Across the 38 paired legacy snd_Map_Simple_Clip source materials: HEIGEN507's 30 mapped to 17 Common, 12 Common_Clip and 1 LOD material, while NW_EUROPE01's 8 mapped to 3 Common, 1 Common_Clip, 1 Simple_Clip and 3 different Build-family shaders. The exact palm's native target requires Common_Clip, extra texture maps, tangent/binormal data and vertex splitting; keeping the source's coherent legacy Simple_Clip material avoids the invalid hybrid in the bounded compatibility path. A full native-style rebake is a different operation, not accomplished by merely renaming a shader.

This exact 162/162 inspected, 1 anomalous material result is an offline structural finding; the reported black-leaf observation belongs to a modified-game test. Scope and limits

These findings describe bounded paired assets and compatibility tests. They do not prescribe the implementation of any third-party model editor. Unknown shader families and opaque declarations need separate source evidence rather than forced normalization.
