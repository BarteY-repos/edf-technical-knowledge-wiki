MAD — map collision archive and embedded Havok resources

File FormatsSource-scoped referenceEDF 4.1EDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: MAD is a map collision archive, not the collision geometry format itself.

Where it fits: In 50 examined EDF6 map files, the outer MAD uses a MARC version-5 wrapper containing a collision.hkt Havok payload.

Important distinction: To understand collision, first unpack the MAD wrapper, then read the HKT payload using the correct Havok generation.

EDF6 MARC v5 wrapper (measured native sample)

The retained exact binary audit examined 50 EDF6 map MADs. Each sampled archive had version 5, a single collision.hkt member and a native TAG0 payload beginning at 0x24.

Offset Meaning in the measured EDF6 family
+0x00 Signature MARC
+0x04 Version 5
+0x08 Payload offset 0x24
+0x0C Name-block offset relative to +0x24
+0x10 Payload byte size
+0x14 Directory offset relative to its own field
+0x18 File count 1
+0x1C Absolute name-block offset
+0x20 UTF-16 name length including terminator (14 code units)

The contained payload is padded to a 16-byte boundary before the trailing UTF-16LE member name. In the inspected examples the stored name is collision.hkt plus a terminating NUL. The detailed entry record and byte-for-byte sample verification remain in the linked exact source article.

What's inside MAD

An outer MAD wrapper identifies and positions a Havok collision payload. It does not define the physics object graph by itself. The contained HKT may include type/data/index sections, bodies, shapes, materials, motion properties and collision filters whose interpretation depends on the engine generation.

Original EDF4.1 collision work includes Havok 2014 hkp structures; EDF6 uses Havok 2020 hknp structures. Renaming a member or editing a wrapper version does not convert the embedded collision data.

What the observed format does not guarantee

  • The one-member rule is confirmed for those 50 native EDF6 map archives, not every unknown MAD profile.
  • Valid MARC offsets do not prove a correct embedded HKT.
  • Valid collision geometry does not alone prove object binding, filter parity, NPC navigation or successful runtime behavior.
  • A shape conversion must preserve the measured profile-specific structural invariants rather than forcing one universal radius, mesh topology or physics record.
