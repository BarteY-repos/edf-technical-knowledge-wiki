EDF 5 — System (community source notes)

EDF 5Community Knowledge HubNative UI & Input
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Observations

The "close the game?" question: the jz at 60AFA3 decides whether mov byte 1412535FA,1 runs

Evidence: static · Build: steam-5d11de53 · Fact ID: close-game-dialog

The "close the game?" question: the jz at 60AFA3 decides whether mov byte [1412535FA],1 runs; Quarri6343's SkipCloseGameDialog NOPs the jz, so the flag is always set and the question is skipped (what the flag means exactly is not decoded).

Basis: the patch's anchor, decoded

Addresses (build-specific RVAs unless indicated): 60AFA3, 1412535FA

Attribution: Quarri6343 (SkipCloseGameDialog), novae (ajane)'s EDF5 outside set · 2026-10-16

Invalid online mission ID table crash

Evidence: static · Build: steam-5d11de53 · Fact ID: mission-id-bounds

Online, an invalid mission id crashes the game: at 556297 the code indexes a table of 12-byte entries with r12 (lea rcx,[r12+r12*2] / lea rax,[rdx+rcx*4], then follows two relative offsets at +8) without a bounds check. Souzooka's InvalidMissionIDFix calls a check that compares the index with the count dword at [table-8] and skips the entry when out of range.

Basis: the patch's code; the original instructions decoded at the fixed address

Addresses (build-specific RVAs unless indicated): 556297

Attribution: Souzooka (InvalidMissionIDFix), novae (ajane)'s EDF5 outside set · 2026-10-16

Plugin detach at shutdown

WM_CLOSE leads to DLL_PROCESS_DETACH in the tested exit path

Evidence: verified (source-reported) · Build: steam-5d11de53 · Fact ID: edf5-plugin-detach-at-quit.

When EDF5 quit after a WM_CLOSE to its window, an EDFModLoader plugin received DLL_PROCESS_DETACH in DllMain. A small file-size/time check or move may be possible then, but it must avoid blocking work or lock acquisition while the Windows loader lock is held. The game-menu Quit route and crashes were not observed, so this should not be presented as a guaranteed always-run cleanup callback.

Basis: source-reported shutdown observation in the Knowledge Hub export.

EDF5 boot display and process-exit paths

The following is contributor static disassembly of EDF5 at the cited executable build, except for the previously reconciled source-reported plugin detach run. Addresses are relative to EDF5.exe and do not transfer to EDF6.

Window dimensions from desktop and SYSTEMWIN32.CFG

Static. Boot 3D6170 first reads desktop width/height through GetSystemMetrics(0/1). Loader 91E90 reads SYSTEMWIN32.CFG via JobSaveDataLoad into a local settings struct. Its dwords +0x14/+0x18 replace width/height only if neither exceeds desktop dimensions; byte +0xE is fullscreen and +0x10 indexes the set {1,2,4,8,16} (purpose not read). Window-thread starter 60AD90 stores dimensions in [125A9D0]/[125A9D4]. Later resize 60B3F0 can change them. Neither this settings load nor the indexed option was newly tested in-game.

Boot -screen_mode, -fullscreen and -windowed options

Static wcsstr command-line parse. -screen_mode recognizes 4k 3840×2160, 1800p 3200×1800, 3k 2880×1620, 1080p 1920×1080, 900p 1600×900 and 720p 1280×720. The recognized value is expected exactly one character after the option in the source's read. This override bypasses the saved-size desktop check. -fullscreen sets and -windowed clears the fullscreen flag sent to 60AD90. Intended harness use to choose boot dimensions without editing CFG was not tested.

First DXGI swap chain descriptor

Static native descriptor mapping. The initial swap chain at 5E0F30 uses width/height from [125A9D0]/[125A9D4], refresh rate 60/1, DXGI format 0x1C (28), sample descriptor from parameter +0x10, usage 0x20, one buffer, window from parameter +8 (retained at [1256BE8]), windowed when parameter +0x19=0, discard swap effect 0 and mode-switch flag 2. It also computes 0.1 of each screen dimension and the remainder into [12595A0..12595AC], possibly a safe-area margin (unverified). Render-size globals [1256C00]/[1256C04] are separate and were not crosscompared; do not treat them as the same resize contract.

WM_CLOSE and the may-close byte

Static window procedure read. At WM_CLOSE case 60AF7A, game reads [12535FA], prints a stripped true/false debug value and tests the unchanged byte. If already set, it sets the byte and destroys the window; otherwise it branches to 60AFEE, whose presumed confirmation dialog was not decoded. This makes [12535FA] the process may-close/loop exit flag. Writing 1 before posting WM_CLOSE to [125A9C8] is a plausible no-question exit path, explicitly untested. The separate source-reported DLL_PROCESS_DETACH check does not validate this direct flag manipulation.

No game-side mutex/window single-instance import found

Bounded static import-table census. EDF5.exe had neither the expected Mutex nor FindWindow imports under the contributor's IAT inspection, unlike the separate EDF6 single-instance mutex path. This supports only the absence of those game-side imported checks; Steam's launcher or a different indirect restriction may still prevent two instances. No attempt to launch two copies was performed.

Saves, Steam achievements and redirect limits

Documents/Steam-derived EDF5 SAVE_DATA directory

Static. 47E860 obtains Documents via SHGetFolderPathW(CSIDL=5), with fallback through two as-yet-unidentified Steam interface vtable calls if GetFileAttributesW fails. 47F4D0 appends \My Games\EDF5\SAVE_DATA\ and a %llu\ numeric subfolder (presumably Steam ID; exact interface not identified); 47EA10 creates intermediate directories through CreateDirectoryW. Source text pointers include EC51D0, EC51F0 and EC5250. Two other consumers of the folder resolver (590A10, 592D80) were not traced.

In-place save path redirection remains untested

Source: unverified inference. As a possible analogue to EDF6, replacing the same-length UTF-16 directory strings at EC51D0/EC51F0 in .rdata before the first save job might redirect EDF5 save reads and writes. The author suspected SYSTEMWIN32.CFG would follow because it loads through the same job class. Neither the full callsite scope nor a save/read/write round trip was tested. Treat this as a potential research route, not a safe patch recipe.

Achievement SGO and Steam interface unlock call

Static. Rules come from APP:/ETC/Achievement.sgo (AchievementEvent/AchievementVariable, read in 80370). 810C0 logs the unlock request and calls AchievementUtility::UnlockTrophy at 4874B0, whose Steam context path invokes interface vtable +0x38 with a name and then +0x50 under a lock, consistent with SDK SetAchievement/StoreStats order (mapping inferred). Source notes an early return could prevent unlock calls, but no bypass was implemented here. Script AchievementAddCount/UpdateAchievementCounter counters reside in save trophy storage, so redirecting saves and blocking Steam unlocks are distinct operations. RTTI references include UserStatsReceived_t and UserAchievementStored_t.

Process main thread, engine thread classes and worker pools

Game loop is on EDF5.exe main thread

Static CRT/WinMain callchain. CRT entry 9C78A0 invokes WinMain 3D9010, then 3D8DC0, which calls game loop 60FC80 in the same process main thread. No separate sgs::th::Thread startup is the EDF5 game loop. This contrasts with EDF6's DLL-hosted main-thread description; “game thread” here does not mean the renderer or a worker. The reported CPU sample pointing to 60FC80 is supporting evidence, not a new runtime thread identity trace.

sgs::th::Thread wrapper, handle and OS thread id

Static native/RTTI. EDF5's engine thread object sgs::th::Thread has vtable EDD580; 5BAD60 starts threads through a suspended CreateThread (entry 5BADE0) followed by ResumeThread. Object +8 holds a handle and +0x10 the OS thread-ID dword. Naming function 5BAE80 raises debugger naming exception 0x406D1388, not a traced GetThreadDescription call. This mechanism assigns debugger-visible names but does not turn a plugin's current thread into the game thread.

Named engine thread-start callsites

Static fourteen-start census. Named/classed calls to 5BAD60 include sgs::fs::Io::AsyncWriter (248A0), sgs::fs::CpkContentFileReader (24FB0), sgs::fs::FileReader.lzss (25570), ai::System (96390), ResourceLoader (471D70), GenericJobQueue (47DD10), sgs::th::SimpleJobQueue::Thread (5C1100), Windows message pump xgs::platform::WindowThread (60B4D0) and renderer [1256BD0] starting at 5E133F (thread ID [1256BE0]). The remaining classes and their counts are recorded separately below; this enumeration is of native start sites, not an exact count of live OS threads at every instant.

Resource stream, network, archive and movie thread classes

Static class/vtable ownership. Remaining 5BAD60 native starts resolve by class rather than a quoted thread name: singleton xgl::ren::StreamResourceManager at 1192A10 (vtable EDE8C8), net::SessionManagerImpl thread at its object +0xF0 (vtables EC1B50/EC1B38, started by 447DA0), sgm::res::SgmResStreamArchiveReader (start 5C2390, vtable EDD4D8), and a thread per MFMoviePlayer instance (start 49FA60, thread at player +8, vtable EC8000). Multiple movie instances mean this is not a fixed always-active single movie worker.

StreamResourceManager static object and busy count

Static. Static initializer C94490 assigns EDE8C8 vtable to xgl::ren::StreamResourceManager at 1192A10. Boot 60F680 calls 5E45A0 to start it, installing renderer [1256BD0] at object +0x28, zeroing +0x30 and count +0x34, then retaining thread ID at 1192A20. Mission-loading natives increment/decrement that +0x34 field, but it is the resource stream manager's busy count, not a uniquely mission-specific state flag.

Job pools, Havok and middleware thread families

Static starts/imports. SimpleJobQueue pools through 5C0E20→5C1100 are created for FieldRender::Initialize (hardware thread count −1) and CASMtCalculate (processors −1). Havok uses a separate CreateThread wrapper 68B0B0 from callers including FileWatcherThread and other unnamed starts; assigning all unnamed ones to Havok is partly inferred. A distinct _beginthreadex family at 991C40 with affinity/priority helpers looks like CRI middleware by its logged error style, not proven by RTTI. Umbra has initThreads at 625BD1. Therefore sgs::th::Thread's start-site list is not the complete process OS-thread inventory.

Plugin thread-ID comparison, partly inferred

Source: unverified mapping. Main/game thread is the one executing loop 60FC80; renderer is most likely the thread ID at EDF5+1256BE0, resource stream manager ID at EDF5+1192A20, and a measured worker in 931000..99C2EC is probably CRI due to the 991C40 start family. A plugin can compare GetCurrentThreadId with these ID fields or capture a call within the game loop. The labels “Present thread” and “CRI thread” were inferred from samples/call ownership, not verified by directly tracking their start and execution across builds.

Frame timer, step count and main-loop control

Main loop drains messages, steps simulation and queues rendering

Static. 60FC80 is called once by 3D8DC0 using app object allocated by 3D6170 (vtable EE0528, global [1253708]). Each iteration drains Win32 PeekMessageW/TranslateMessage/DispatchMessageW, honors close byte [12535FA] or [loop+0x14], waits on frame timer, gets step count, calls the app's virtual +8 with seconds and steps at 60FEFC, then schedules frame render and Present. This extends the main-thread identity evidence above with loop order.

Deadline timer at 60 Hz with late-frame reset

Static. Loop timer starts at +0x18; its rate is 60 and interval is float 1/60 (0x3C888889, set at 60F594). The clock is +0x1C and next deadline +0x20. Ready check 5A86B0 advances one period when elapsed time reaches the deadline, resets to current clock when over 0.1 s late (no burst of timer ticks), and rebases QPC after 3600 s. These are timer-internal offsets, distinct from the outer loop fields used by the console command.

Idle limiter yields with Sleep(0)

Static. Frame wait 60FDE0..60FE1A calls Sleep with an integer formed by truncating a sub-second positive time estimate (remaining period minus 1 ms, capped at 1.0 s), so in normal frame periods the argument is zero. It yields the game thread's slice while repeatedly polling readiness rather than performing a frame-length Sleep(16). This is consistent with the contributor's measured top game-thread function, but is not a new CPU-usage benchmark.

Three known loop-side cadence callsites

Static callsite census. Timer readiness 5A86B0 is called at 60FDD6 and 60FE13, and step count 62AA10 at 60FE49, all in 60FC80. Source says neither routine has another caller. These addresses localize instrumentation candidates; no patch or high-FPS behavioral test was performed.

Fixed 1/60-second steps, 90-percent early tick and maximum three

Static. 62AA10 derives whole 1/60 s periods from QPC time since [1259C38] and consumed time [125AB10]; near 90% of the next interval it may return one step early. The loop caps returned steps at three (60FE58), discarding greater backlog. Loop FPS is stored at [loop+0x10] and [125AB00]; measured update load at [125AB04]. A faster presentation loop therefore need not imply faster simulation.

One-shot load flag clears elapsed update time

Static. Byte [loop+9], initialized to one and set from 3E0DA0, is consumed on the next iteration. The loop clears it and passes zero simulation steps and zero elapsed seconds to update, dropping a loading interval rather than catching it up.

set_fps changes loop rate, not the fixed-step counter

Static. Debug-console set_fps handler 69940 (twice registered under 699B0, string E917B8) writes desired timer rate [loop+0x20] and reciprocal period [loop+0x30], defaulting to 60. The step counter stays at 1/60 s. Higher loop rates may produce zero-step draws between simulation updates; this alone is not a safe gameplay FPS unlock claim.

Zero-step redraw, DXGI present and measured load

Scene redraws unchanged state on a zero-step loop

Static. System update 611BB0 retains its step count and calls renderer 6126A0 before reaching the step-count branch. With zero steps it jumps from 611DF1 to function tail 612659, skipping object and camera updates; its seconds argument is overwritten before use. Thus the scene still renders, but simulated objects are not advanced. This resolves the earlier source question on zero-step behavior without a runtime FPS test.

Render completion event allows at most one queued frame

Static. Before submitting Present, 5E2FA0 waits indefinitely on event [12594E0]; the rendering thread signals it through command 5E2D40 queued after the prior Present (5E2C60). The submit path then calls 5E2240 for pending screen-mode/AA changes. This serializes frame dispatch, not proof that the render thread performs every part of the CPU update.

Present toggles SyncInterval after a catch-up frame

Static. [loop+0xC] is set to eight when more than one simulation step ran and decremented each loop. Present submit 5E2FA0 encodes [loop+0xC] == 0 as SyncInterval alongside renderer [1256BD0]; render handler 5E30D0 invokes Present through renderer vtable slot +0x40 on swap chain [1256C98]. Ordinary frames use interval 1 (vsync); eight loops after catch-up use interval 0. This describes game-selected parameter values, not whether a driver overrides them.

Update load percent and FPS are written without EDF5.exe readers

Static. Main loop samples QPC immediately before virtual update (60FEAE) and after (60FF0F), storing elapsed seconds times 100 divided by 1/60 at [125AB04] (60FF54). FPS goes to [125AB00]. Contributor's cross-reference census found only stores in EDF5.exe, unlike an EDF6 crash-piece reader; a plugin may inspect values later, but that is not demonstrated as existing native HUD behavior.

Frame cadence questions still open after zero-step trace

Unverified. The original question “does a zero-step iteration update the scene?” is superseded by the static redraw/skip trace above. Still open: whether a stable 60 FPS mission takes exactly one simulation step per loop under real pacing, the render thread's full work loop, and end-to-end behavior of a higher set_fps rate with vsync disabled. The exact observed parity to EDF6 has not been game-tested.

EDF5 paused-frame simulation and redraw path

Source edf5/pause-free-camera-post.md, static native findings. A pause suppresses object simulation without necessarily suspending the entire render loop.

Step counter advances, camera updates, objects stop

Evidence: static · Fact ID: edf5-pause-clocks

System update 611BB0 advances step counter +0x9B8 on every logic step whether paused or not. Pause-listener slots 3 and 4 run only if not paused; render preparation 6126A0 occurs every frame before the step loop. A paused step skips ordinary object updates and resumes at camera update block 612447. The EDF6-style game-clock and redraw request fields had not been investigated in this specific source record.

No EDF6-style redraw-request gate in EDF5

Evidence: static · Fact ID: edf5-pause-no-redraw-request

Further native reading of 611BB0 finds no separate game-clock write or redraw-request byte. It calls renderer 6126A0 unconditionally each frame, so a paused EDF5 scene is repeatedly drawn; free-camera update A79D0 touches System for pause bits and camera fields, not to request a scene redraw. Renderer byte +0x9BC is propagated to view draw options, not used as an EDF6-style redraw request; its option meaning was not decoded.

Always-run safe-update callbacks before rendering

Evidence: static · Fact ID: edf5-pause-safe-update

xgs_scene_object_safe_update in renderer 6126A0 visits System list +0x188 (count +0x198) through each object's slot 0, then camera slot 3 for each of four views at +0x238. It runs every rendered frame whether paused or not, as in EDF4.1; EDF6 instead conditions a paused safe-update on redraw request. Which objects populate the list and how EDF5 particles advance were not traced.
