EDF4.1 boot display, IAT and process checks

Desktop, SYSTEMWIN32.CFG and boot window setup

Static native read. Builder 341EC0 starts with a 1920×1080 default, reads desktop bounds through GetSystemMetrics(0/1), then loads SYSTEMWIN32.CFG via DD1B0/DD5A0. When available, settings struct dwords +0x18/+0x1C become width/height unless they exceed the desktop. Byte +0x2 is fullscreen, while +0/+0x3 are other window flags; +0x20 indexes {1,2,4,8,16} (purpose not read). Byte +1 and clamped float +0x14 also reach other globals including mouse setting [C50FC4]. Window creation 560750 precedes device/swap chain 524560. This boot behavior was not newly tested.

EDF4.1 -screen_mode/-fullscreen/-windowed options

Static wcsstr parse. Builder 341EC0 accepts -screen_mode followed by one separator and 4k (3840×2160), 1800p (3200×1800), 3k (2880×1620), 1080p (1920×1080), 900p (1600×900) or 720p (1280×720). This overrides saved size without the desktop-size guard. -fullscreen sets and -windowed clears the saved fullscreen flag. Window title is EarthDefenceForce 4.1 for Windows. Booting a resolution harness by these flags was a source proposal, not an observed run.

Read-only IAT, Win32 imports and legacy MSVC runtime

Static PE import inspection. EDF41.exe IAT is a 0xE80-byte block in read-only .rdata from 918000, with 41 USER32 imports at 9189D0..918B10 (GetKeyboardState 918A08, GetForegroundWindow 918A48). This executable links MSVCR120/MSVCP120, unlike EDF5/EDF6's universal CRT. No overlay SDK import was found in this census, so an explicitly memory-protected IAT slot swap is expected to remain at the inspected site; that is an inference from imports and protections, not an independently proven hook lifetime.

No Mutex/FindWindow single-instance import found

Bounded static IAT search. The examined EDF41.exe had neither a Mutex nor a FindWindow import used for a game-side single-instance guard. This differs from an identified EDF6 mutex path but does not exclude indirect process checks or Steam refusing a second launch. The contributor did not attempt a two-process run.

Documents save folder and achievement dispatch

EDF4.1 save directory and corrected wide-string start

Static. Resolver 3E91B0 gets Documents through SHGetFolderPathW(CSIDL=5), with fallback via unidentified SteamUtils/SteamApps vtable calls if folder attributes fail. 3E9CB0 appends \My Games\EDF4.1\SAVE_DATA\ (source A266F0) and %llu\ for a Steam-derived numeric ID (presumably Steam ID, not fully identified). 3E9350 creates intermediate directories using sources A26120 and A261E8. A previous note gave the latter as A261E4, but those first four bytes are a float value near 3.14159; the UTF-16 path string begins at A261E8. This resolves an exact address error without claiming a live save redirect.

Three-string save redirection remains hypothetical

Source: unverified. The source suggests equal-length wide-string replacement before first save job could redirect EDF4.1 save reads/writes, analogous to EDF5/EDF6, but this game requires three candidate source strings, not two: A26120 (parent), A261E8 (created folder), A266F0 (path builder). SYSTEMWIN32.CFG may follow the same redirected job path via JobSaveDataLoad; this was not traced or exercised. Neither the mutation nor any save/load test was performed; treat addresses as research leads, not a verified patch.

Achievement SGO, event rule and Steam StoreStats route

Static. Achievement rules load from APP:/ETC/Achievement.sgo (roots AchievementEvent/AchievementVariable, reader CEA20). CF950 compares rule int/float values, skips already-marked byte +0x34, marks the event and calls AchievementUtility::UnlockTrophy at 3EF7B0 on [CC8558]. It invokes the SteamUserStats interface's +0x38 then +0x50 under a lock, consistent with SetAchievement/StoreStats (specific interface labels inferred). Script counters UpdateAchievementCounter/AchievementAddCount live in the trophy save block; they are not interchangeable with Steam unlock calls. The source mentions a possible early-return interception but no unlock/achievement modification was implemented here.

EDF4.1 main game thread, worker classes and CRI range

CRT-to-WinMain callchain settles main-thread loop

Static xrefs. EDF41.exe CRT entry 666B34 invokes WinMain 344500, which calls 3442B0 and then runs game loop 564E20 in the process main thread. This replaces the earlier “most likely” classification in the thread-start census with a concrete callchain, and aligns with EDF5 while differing from EDF6's DLL-hosted main-thread context. A worker-thread name or high CPU sample alone should not be used to identify this loop.

sgs::th::Thread wrapper and twelve start sites

Static import/vtable/callsite census. sgs::th::Thread vtable AAFFF8 uses starter 517C70 with suspended CreateThread (517CC4, entry 517CF0); object +8 holds handle and +0x10 OS thread ID. Twelve starts include Io::AsyncWriter (8F130), CpkContentFileReader (8F960), FileReader.lzss (8FF80), ResourceLoader (3DE2C0), GenericJobQueue (3E8740), CASMtCalculate (5828D0), WindowThread (560EC0), renderer CC4640 (524C16, ID CC4650), stream resource manager C64930 (528020), and three unnamed sites 34EAB0, 3A9B60, 51E720. Another CreateThread wrapper 599E70 had unknown ownership. Absence of EDF6-specific named AI/main DLL threads is a bounded comparison, not proof all engine jobs are absent.

Static StreamResourceManager object and thread id

Static RTTI/xrefs. The EDF4.1 object at C64930 is xgl::ren::StreamResourceManager (vtable AB0520, assigned by 527FC6 and static initialization), started at 528020. Its thread-ID dword is C64940. This is the same architectural worker class as in EDF5, but EDF4.1 object and ID offsets belong only to EDF41.exe; do not transplant EDF5/EDF6 resource manager offsets.

CRI middleware code range and separate thread entry

Static string/import-range census. Around 420 EDF4.1 functions loading CRI error codes matching E20 plus eight digits are clustered in the early .text interval approximately 10F0..73E60. CRI-related helper 598E8 starts threads through a separate _beginthreadex thunk 666E78, with a logged failure string E2008073001. The range is useful as a source-specific sampler classification lead, not evidence that every instruction in it or every worker using another start routine is CRI. Other games have different CRI address ranges.

EDF4.1 ModLoader and Patcher host compatibility

Reconciled edf41/mod-loading.md source for Steam build 57aab039. These findings inspect native byte patterns and EDFModLoader v1.0.10 source; they are not a fresh end-to-end test of every replacement file.

EDF41.exe loader host and plugin entry point

Evidence: static · Fact ID: edf41-modloader-host

EDFModLoader v1.0.10 recognizes EDF41.exe by module name, runs plugin export EML4_Load (EDF5 uses EML5_Load, EDF6 EML6_Load) and uses the early MSVCR120.dll!_initterm hook rather than EDF5's UCRT or EDF6's own boot function. EDF41.exe imports _initterm at IAT 9188D0 (thunk 667102) and winmm.dll symbols at 918B20/918B28, supporting the winmm.dll proxy load. Plugin search remains Mods\Plugins\*.dll, subject to the loader's documented keep rules.

Three native signature matches for hooks

Evidence: static · Fact ID: edf41-modloader-patterns

The three EDF5-pattern signatures in the inspected EDF41.exe each match exactly once: CRI CriFsIo file open 8ED80 for Mods\ override, std::wstring::assign 91580, and debug-print function 91790. Thus the loader has a concrete file-open interception target on this build, but a successful replacement of a specific resource from Root.cpk was not observed in game in this source record.

Patcher EML4_Load and grammar inheritance

Evidence: static · Fact ID: edf41-patcher-host

The Patcher exposes EML4_Load alongside EDF5/6 exports and resolves the current game executable through GetModuleHandleW(NULL). Consequently the EDF5 Patcher's patch-file grammar and ordering apply to the EDF4.1 host. A fifteen-file external 4.1 patch collection is cited as a concrete input set; this does not certify every patch as safe or reproducible on other builds.

Retail debug-print stub and loader game.log

Evidence: static · Fact ID: edf41-game-debug-print

Native 91790 accepts printf-like wide/narrow debug output but in the retail build its body saves arguments and returns without printing. Call sites still construct messages such as WM_CLOSE:%s and Reject DamageInfo 0x%p. With GameLog=True in ModLoader.ini, the loader hooks that stub and writes the messages to game.log, a potentially useful trace not otherwise visible in the stock executable.

Unverified mod-replacement and folder scope

Evidence: unverified · Fact ID: edf41-mod-loading-open

Still open: an in-game check showing that an EDF4.1 resource is actually replaced through Mods\, the exact set of resource folders occupied by 4.1's Root.cpk (important for avoiding collisions with mod-owned paths), and whether the game includes EDF5-equivalent AngelScript files. Native hook signatures are evidence for integration, not substitutes for these checks.

EDF4.1 game loop and 60 Hz simulation

Frame timer poll, Sleep(0) and three-step catch-up

Evidence: static · Fact ID: edf41-game-loop-wait · Build: steam-57aab039

Main loop 564E20, constructed by 5646E0 and stored at [CC3158], waits on timer 4F83A0. Its computed Sleep duration is a fractional number of seconds less than one and truncated to an integer, so it calls Sleep(0), yielding while spinning. Step counter 5799D0 counts elapsed 1/60-second periods from QPC base [CC8490]; the loop limits the number of updates in one pass to three and calls virtual +8 with count and elapsed seconds. Unlike EDF5's loop, this function does not pump PeekMessageW events. Logic cadence is nominally 60 Hz despite a separate limiter period.

Timer deadline, rate console and fixed step

Evidence: static · Fact ID: edf41-frame-timer

Frame timer at loop+0x18 starts with limiter period [loop+0x30] = 1/60 second (5646E0). Ready test 4F83A0 advances deadlines by one period, catches up to wall clock when over 0.1 seconds late, and rebases QPC after 3600 seconds. Developer-console set_fps handler C0780 sets requested rate at [loop+0x20] and its reciprocal period at +0x30 (default 60), not the simulation step length.

Ninety-percent early step and temporary Present flag

Evidence: static · Fact ID: edf41-game-loop-details

Step counter 5799D0 may return one even before a whole period has passed, once 90% has elapsed (unlike EDF6's observed counter). The loop records FPS in [loop+0x10] and [CC8480] and update-load percentage in [CC8484]. A pass with more than one logic step loads [loop+0xC] with 8; that byte counts down each loop and [loop+0xC] == 0 goes into Present enqueue 526430. Loop termination watches window-close [CC302F] and its own stop flag [loop+0x14].

Limited native probes for timer and step count

Evidence: static · Fact ID: edf41-loop-probe-sites

The timer-ready function 4F83A0 has loop call sites 564EE2 and 564F28; step counter 5799D0 has only 564F68. The native source census found no other calls to either function. These are possible instrumentation sites, with no user-visible performance change demonstrated by the source itself.

Zero-step iteration still renders and performs safe updates

Evidence: static · Fact ID: edf41-zero-step-redraw

System update 566B80 runs render preparation, post chain and a safe-update phase on every pass. With zero simulation steps, branch 56788D → 568124 skips object simulation and the per-step camera block, then executes the tail; the same simulation state may be redrawn. The precise behavior of camera virtual slot 3 in the always-run safe-update phase and the treatment of its elapsed-seconds parameter were not traced.

FPS and update-only frame load counters

Evidence: static · Fact ID: edf41-frame-load

[CC8480] records FPS, whereas [CC8484] records the QPC-measured update time divided by 1/60 second, multiplied by 100. QPC is sampled before and after the update's virtual call (564FB1..56504C), excluding full render/present time. The inspected executable only stores these globals and contains no observed readers; the load percentage is not a complete per-frame CPU/GPU load.

Remaining limiter caveats

Evidence: unverified · Fact ID: edf41-game-loop-open-3

Static code explains rate control through [loop+0x30], fixed-step 60 Hz updates and redraws with zero steps. Higher present rates would also require compatible vsync behavior. Still unknown is the writer of skip flag [loop+9]; the loop's main-thread identity is supported by the separate system-thread audit. No live FPS unlock was verified.

Direct3D 11 swap chain, Present and vsync policy

Renderer globals and DXGI CreateSwapChain

Evidence: static · Fact ID: edf41-swapchain

EDF4.1 imports D3D11CreateDevice (IAT 918BF0) and calls it at 524749 without creation flags (so no explicitly requested BGRA support). Renderer global CC4640 holds D3D device at +0xB8 ([CC46F8]), swap chain at +0xC8 ([CC4708]), adapter at +0xD0 and factory at +0xD8. 5252C0 creates the swap chain through DXGI factory CreateSwapChain, using dimensions at [CC46B0]/[CC46B4] and storing the selected size in renderer +0x30/+0x34.

Render-queue command executes Present

Evidence: static · Fact ID: edf41-present-site

The observed Present is the swap-chain virtual call [rax+0x40] at 526661 inside queue handler 5265B0. That handler consumes a 16-byte command holding renderer pointer and SyncInterval; it runs on the render-queue consumer, while the main loop enqueues work. Hooking the call site or slot 8 of the swap chain at [CC4708] would observe presented frames, but no hook implementation or thread-identity proof was supplied.

One frame in flight and catch-up vsync suppression

Evidence: static · Fact ID: edf41-present-sync-interval

Enqueue routine 526430 waits without timeout on event [CC6EF0], keeping no more than one queued frame in flight, then pushes the renderer/SyncInterval command to 5265B0. It uses SyncInterval 1 normally and 0 for eight iterations following a multi-step catch-up pass, explaining the countdown at [loop+0xC]. It is a conditional present policy, not a claim that setting the limiter alone yields unrestricted display rate.

Untraced render thread and resize path

Evidence: unverified · Fact ID: edf41-present-open-2

Open questions remain the exact render-thread identity and worker loop, and the confirmed ResizeBuffers call path. Candidate routine 525A30 reads swap chain [CC4708]; 526430 transfers there at its end, analogous to EDF5's mode-change code. A candidate reference is not a decoded resize call.

EDF4.1 Havok CharacterControl_Walk contract

Source: edf41/character-control.md, Steam build 57aab039. These are native-code static findings for characters and some large actors; their state transitions are not newly tested in-game.

Walk class, vtable and owning objects

Evidence: static · Fact ID: edf41-walk-controller

xgs::havok::CharacterControl_Walk has vtable AB0E38 (seven slots), slot-0 hkpContactListener callback 576150, deleting destructor 575E70, constructor 575D50, init 575F10, and step 5763A0. Owners include HumanBase+0x3B0 (soldiers and civilians), Shield Bearer AlienTrailer+0x770, Hector+0xF70, Monster501+0xAF0, Vehicle501_FortressRobo+0x1510, and Proteus's VehicleBegaruta::BegarutaCtrl::BegartaCtrlWalk subclass (vtable AA0510).

Walk velocity, gravity and contact fields

Evidence: static · Fact ID: edf41-walk-fields

walk+0x08 is the Havok character-body handle; desired movement is +0x20, ballistic velocity +0x30 (vertical component +0x34), submitted velocity +0x40, angular velocity +0x50, one-step extra velocity +0x60 (cleared after step), gravity per second +0x70, downward slope-hug speed 6.0 at +0x74, launch flag +0xC0, wall-angle threshold +0xC4, and setup-scaled value +0xC8. The field layout is shifted from EDF5; a second EDF5-style extra-velocity slot is absent here.

Once-per-update step and support data

Evidence: static · Fact ID: edf41-walk-step

Each owner updates the walk once: AlienTrailer 1D6011, Hector 221B9F, Monster501 231832, HumanBase 29C2C8, FortressRobo 2DC32D and Proteus 2ED7DD. Step 5763A0 uses fixed hkStepInfo dt 1/60 and character-body checkSupport 658370. Surface info at walk+0x80 contains support state (0 unsupported, 1 sliding, 2 supported), normal +0x90, surface velocity +0xA0, excess distance +0xB0 and dynamic-surface byte +0xB4.

Support, slide, launch and gravity transitions

Evidence: static · Fact ID: edf41-walk-step-states

Immediately after losing support without launch, movement y takes -walk+0x74 to hug a slope without gravity. Other unsupported or sliding states integrate gravity into ballistic y. When supported without launch, ballistic velocity clears and desired motion projects onto the ground; a velocity pointing away from the support normal can trigger lift-off and gravity. With no Havok world attached, ballistic velocity clears instead of applying it. The one-shot launch flag clears once vertical ballistic velocity becomes negative.

Final linear and angular body velocities

Evidence: static · Fact ID: edf41-walk-send

The step combines desired +0x20 movement (projected onto ground if supported), one-step extra +0x60, and ballistic +0x30. It writes the sum to +0x40 and submits it through 6590B0, inferred to be setLinearVelocity from field comparisons. Angular +0x50 goes through 659190. This is commanded world velocity, without automatic additive ground-surface velocity.

Wall resistance and ceiling hit callback

Evidence: static · Fact ID: edf41-walk-contacts

Contact listener 576150 ignores bodies with a Havok property key carrying the high bit and protects state with lock +0xD0. A normal-y below threshold +0xC4 counts as a wall; the callback retains the strongest opposing horizontal push and its point/normal at +0x100..+0x130. A normal-y below -0.7 is treated as a ceiling, removing upward ballistic motion and setting head-bump flag +0xE0. Step completion copies impact data into the owner's exposed region and resets per-step collision accumulators.

HumanBase movement contributions and jump impulse

Evidence: static · Fact ID: edf41-walk-humanbase

HumanBase virtual slot-2 path 29BB80 sets walk move at HumanBase +0x3D0 to computed input plus fields +0xB70 (state-dependent), +0xC60 and +0xC80. Pending jump +0xD00 with speed +0xD04 sets support state +0x430 to zero, launch flag +0x470 to 1 and vertical ballistic velocity +0x3E4 to jump speed. Numerous other character-state sites can also set the launch flag; jump is not its only cause.

EDF4.1 moving-ground velocity: available but unused

Havok getGround computes support point velocity

Evidence: static · Fact ID: edf41-get-ground-velocity · Build: steam-57aab039

checkSupport 658370 calls getSupportInfo and, when supported, getGround 658E80 with useDynamicBodyVelocities = 0. It averages support contacts. Fixed Havok bodies (motion type 5) contribute no surface velocity; keyframed bodies (type 4) add linear velocity +0x230 and angular velocity +0x240 crossed with point-to-center-of-mass displacement. For other bodies it sets the dynamic flag and adds their point velocities only if that optional argument is enabled. Thus stock EDF4.1 fills support velocity +0xA0 for keyframed supports, not arbitrary dynamic bodies.

Stock step discards calculated moving-surface velocity

Evidence: static · Fact ID: edf41-moving-ground-stock

Walk step 5763A0 reads support state +0x80 and normal +0x90, but not ground velocity +0xA0 or dynamic flag +0xB4. The constructor, init, contact callback and inspected HumanBase sites likewise lack relevant reads. The source therefore concludes a soldier standing on moving scenery retains its own world velocity rather than inheriting ground movement; how far it slides in a given map was not measured.

Two source-identified moving-ground patch locations

Evidence: static for unique signature matches; behavioral result untested · Fact ID: edf41-moving-ground-sites

The source identifies a six-byte supported-state read at 576404 immediately after checkSupport as space for a jump to a helper that could consume ground velocity. Separately, xor r8d, r8d at 6583FA is a three-byte place to enable dynamic-body contributions by changing the argument to getGround. Both byte signatures reportedly match once in the inspected executable. These are candidate binary patch sites, not verified working movement fixes.

Other movement controllers and HumanBase aim

Cling and flying character controllers

Evidence: static · Fact ID: edf41-other-controllers

Two other hkpContactListener-derived controllers lie outside the walk step: xgs::havok::CharacterControl_Cling (vtable AA30E8, used by GiantAnt at +0x320) and FlyingCharacterControl (vtable AA3088, with references in multiple flying/enemy and vehicle paths). Their owners and step implementations were not fully decoded here; do not apply the walk controller's supported-state rule to them without another audit.

Raw and smoothed aim angles, placement and recoil

Evidence: static · Fact ID: edf41-humanbase-aim-fields

HumanBase stores raw pitch/yaw at +0xCA0/+0xCA4 and smoothed pitch/yaw at +0xCB0/+0xCB4, 0x1E0 below EDF5 counterparts. Input adjusts angles unless control mask +0x320 bit 1 blocks it; per-axis limits at +0xCC0/+0xCC4 apply when nonnegative and pitch is further clamped to ±π/2. NaN resets the affected lane; smoothing coefficient +0xCD0 falls back to 0.3 if invalid. Placing a soldier zeroes pitch and derives yaw from the world matrix's forward vector, then copies to smoothed aim. Recoil shifts both angles and clamps both pitches; follow-AI steering reads the smoothed pair.

EDF4.1 pause-mask ownership and simulation gating

Reconciled edf41/pause-free-camera-post.md static code for Steam build 57aab039. A menu pause, debug freeze and online-mode pause mask have distinct effects on simulation.

System pause bits and effective mask

Evidence: static · Fact ID: edf41-pause-bits

xgs::game::System at [CC8528] stores requested pause bits at +0xBA0 and eligible pause mask at +0xBA4. The game is paused when their bitwise AND is nonzero. Each writer directly sets or clears its own bits and calls 569C70(system) to notify listeners only if the effective paused state changes; there is no single shared setter to hook. Free-camera update, base-camera step and LightEnv apply all test the same expression.

Pause-bit writers: free camera, menu and debug viewers

Evidence: static · Fact ID: edf41-pause-bit-users

Value 1 belongs to the debug free camera (constructor E7A18, update toggle E8E61/E8E66, destructor clear E93A5). Value 2 belongs to UiPause_Base menu lifecycle (4CDE80/4CE330). Value 0x10 is set/cleared by debug cubemap_mode_set and lod_mode_set handlers. Application callback slots at 343D1B and 343D60 zero all requested bits. No writers of 4 or 8 were found in the inspected source.

Online mode disables menu pause, not debug pause

Evidence: static · Fact ID: edf41-pause-mask-offline

Mode setter D97E0 reads the selected node's online flag at +0x5C. In an online mode it clears mask bits 0xE (2, 4, 8) and restores them in offline mode or mode -1. The pause menu's bit 2 therefore does not freeze the local online simulation, while debug free-camera bit 1 and debug-viewer bit 0x10 still can. This describes local gating only, not synchronized online pause.

Work that continues during pause

Render/post, counters and camera stepping survive pause

Evidence: static · Fact ID: edf41-pause-clocks

In system update 566B80, render setup and post chain 5479D0 run every frame before the logic-step loop, without a pause gate. Each logic step still advances counter +0xBA8 and invokes 568B60 and 5691B0. Pause-listener slot 3/4 calls on list +0xB88 occur only when not paused. Paused steps skip ordinary object updates but enter xgs_scene_camera_update, which advances the four view cameras and attached camera components. This routine does not write an EDF6-style separate game clock.

Always-run safe object and camera phase

Evidence: static · Fact ID: edf41-pause-safe-update

xgs_scene_object_safe_update at 566D1C runs before steps whether paused or not. It visits entries in the system list at +0x128 (count +0x138) through their slot 0, then camera slot 3 for each of four view slots at +0x1D8. The exact objects registered in that list and EDF4.1 particle progression were not traced; this per-frame work differs from the EDF6 pause-redraw gate.

LightEnv and controller vibration frozen

Evidence: static for gates, vibration label inferred · Fact ID: edf41-pause-holds-lightenv

The per-frame apply part of LightEnv skips when the effective pause expression is set (103353..10335A). Base-camera step EB430 likewise skips a controller-output path at EB478, interpreted as vibration from pad/output fields. Thus a paused frame can still render and move debug cameras while withholding selected environment and controller updates.

EDF41.exe PE fingerprint and section map

Image size, timestamp and section RVAs

Evidence: static · Fact ID: edf41-exe-pe-layout

For the inspected EDF41.exe build, PE TimeDateStamp = 0x57AAB039 and SizeOfImage = 0xD98000; the source describes this pair as a plugin build fingerprint. Section starts: .text 0x1000 (0x916ACF bytes), .rdata 0x918000, .data 0xC2F000, .pdata 0xCD9000, _RDATA 0xD39000, .rsrc 0xD3A000 and .reloc 0xD82000. EDF5 and EDF6 have different timestamp/image-size pairs, so the EDF4.1 RVAs in this appendix must not be transferred to them without revalidation.
