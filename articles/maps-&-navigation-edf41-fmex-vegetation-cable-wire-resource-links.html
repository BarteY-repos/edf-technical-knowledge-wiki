EDF4.1 foliage and power lines in EDF6 — FMEX cells, MAPO heights and wire ownership

ConversionMaps & NavigationMapsEDF 4.1EDF 5EDF 6
Technical reference · Exact-source field/table census, engine-static analysis and offline converter tests; real-game validation pending

Why a correctly rendered map can still lose plants

EDF4.1's SK heightfield .shfb stores vegetation in its own source tables. EDF6's outdoor vegetation is reconstructed from FMB table 2 and table 3 together with a per-occupied-cell height list in the terrain's MAPO record. Removing SHFB while leaving the FMEP/MAPO grass pair empty makes vegetation disappear even if the ground mesh and textures are correct.

The later 2026-10-17 reverse engineering corrected an earlier false assumption that all stock FMEP ground pieces had empty vegetation. 17 native EDF6 outdoor ground records in the examined set used populated vegetation. The exact data relationship is more useful than the old assumption.

FMEX / FMB table and MAPO height contract

The observed FMB table 2 (header +0x14) begins with {group_count, 8}. Each vegetation group carries a 0x28-byte descriptor with group name, cell size, columns, rows, origin X/Z, type count, grid-byte arrays and type references. Grid arrays are column-count × row-count, with row along world Z; 0xFF denotes no object. The type records are 0x40-byte entries containing kind, referenced name and file, colour, size range and associated SGO data.

FMB table 3 supplies a 256-record jitter table (angle, X/Z offsets and size factor). A ground MAPO entry starts with {height_count, 8} followed by one float32 height per occupied vegetation cell, across the groups in row-major order. Its count must match the sum of occupied grid cells; it is not arbitrary padding. For the measured IG_HEIGEN507 reference, that count was 159 441. A 240-sample comparison between mapped vegetation heights and FMB terrain reported differences below 5 cm.

The source SK vegetation table itself has a 0x28-byte type record with source kinds 1 (grass/flower) and 2 (model). In the inspected reconstruction, grass and flowers become one EDF6 vegetation group. Trees, bushes and small placed models become three additional model groups, matching the native EDF6 four-group pattern. SK_HEIGEN02 generated counts in that historical offline pass: 202 275 grass/flower instances, and model groups of 1820 trees, 714 bushes, 853 small objects. These are sample counts, not universal distributions for all SK maps.

File identity and format conversion for tree types

An EDF6 type can point to <model>.tree or <model>.mls, backed by resource .trb and .mlb respectively. The examined EDF4.1 .trb first rule omits a field present in the EDF6 reader. In the target corpus, 79 of 83 first-rule instances used zero for that additional integer. Appending the extra zero and rebuilding the depth-first SGO made two source tree files match corresponding EDF6 native files byte-for-byte. .mlb did not require this same structural change in the examined profile.

Missing plant models and their DDS/MDB dependencies remain a separate resource-resolution risk. Correct grids do not prove the objects draw, collide, or choose the right randomized dimensions in game; those were explicitly pending real runtime verification.

Why power lines can be missing even when RMPA parses

Several source routes labelled cable_elec_wire_* / cable_SoudenTettou_* carry links to MAPB 0x7C wire points, not just positions in the current route. A naive route-local index conversion may discard those links or connect unrelated points. The audited repair matched wire-point coordinates back to their actual route sections and repaired 156 HILLYCITY, 22 KASENJIKI and 140 SINSUIKOUEN references in the historical dataset; two still could not be resolved.

However, the EDF6 rendering path was traced primarily through the MAPB 0x7C point-pair table rather than the editable RMPA cable route. Therefore rewriting RMPA links alone is not demonstrated to restore visible wires.

A second plausible explanation, missing wire_test.dds inside MAC, was subsequently deprioritized: the engine's common map texture lookup container also resolves textures stored only in RAB, including terrain colour arrays, grass.merge.dds and tree textures. The study recorded the distinct resource packing patterns — all 24/24 examined EDF6 maps with power-line pairs had wire_test.dds in MAC, versus 0/26 maps without such pairs — but this correlation does not prove that copying the DDS into MAC fixes rendering.

Follow-up checks found MAPB point-pair sets retained across the conversion, compatible .erb references and no confirmed downstream map-dependent culling in the traversed drawing code. Whether missing lines stem from tower objects, runtime path or another cause requires a game/runtime observation, not another guessed metadata rewrite.

What to check when debugging

  1. For missing grass, compare FMB group grids and occupied-cell count against MAPO's float-height list, then check per-grid terrain interpolation and .dds/.trb/.mlb resource identity.
  2. For missing trees, check the additional EDF6 TRB first-rule field and that the referenced model and textures are actually resolvable.
  3. For missing wires, inspect MAPB wire-point and paired-edge tables before RMPA; do not label the DDS packing discrepancy the root cause without observing lookup failure.
  4. For wrong terrain colour, check the FMB mesh shader-table index and the colour/multiplier array, not only foliage.
  5. Distinguish source-data + offline validation, engine-static analysis and confirmed behaviour in the running game.
