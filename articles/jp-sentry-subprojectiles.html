SentryGunBullet01: nested bullet experiments

Data-backed sentry weapon families

The workbook lists these sentry weapon ↔ child ammunition classes (解析!B2015:G2021):

Weapon sample Direct child bullet class
ZER-GUN, ZE Sniper, ZERA-GUN SolidBullet01
ZE Launcher RocketBullet01
ZE Blaster LaserBullet01
FZ-GUN FlameBullet02

The third table column indicates that an ammomodel entry was not necessary for those reported direct children. This is a tested-sample list, not a complete mapping of every possible sentry profile.

Reported limitation and workaround

The author could not find a node within SentryGunBullet01's ammo_customparameter that specifies the child bullet's own AmmoModel, which appeared to constrain sentry spawning a sentry. A proposed workaround is to have the sentry emit a different ammunition class capable of emitting subprojectiles itself:

SentryGunBullet01
  -> ClusterBullet01   (reported to run without its own AmmoModel)
       -> grenade-like child (reported successful test)

The source states that ClusterBullet01 worked without an AmmoModel in the tested profile (PWEAPON230 example), and that a grenade child was demonstrated through this nested approach (解析!B2026:B2029). It also says “sentry from sentry is not possible” in that experiment (B2030); this must not be presented as a universal engine impossibility without a class/serialization audit.

Tooling boundaries

  • SGO fields are class-specific; a child bullet model or custom-parameter block cannot always be inferred from the parent.
  • Successful nested grenade emission is not proof that arbitrary recursive SentryGunBullet01 trees are valid or safe.
  • If a converter is asked to produce unsupported nested sentry behavior, it should fail visibly rather than silently dropping missing child resource references.
  • Separate projectile construction, actual firing, model instantiation and replicated/network publication when testing in multiplayer.
