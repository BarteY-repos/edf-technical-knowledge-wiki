DSGO — binary layout, typed nodes and expressions

File FormatsSource-scoped referenceEDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: DSGO is a structured data format used in EDF6. Like SGO, it stores typed values, but its binary header and node layout are different.

Where it fits: The researched DSGO nodes are 16 bytes wide and can represent structures, values and expressions. Some DSGO resources still have .SGO filenames.

Important distinction: Look at the file signature before parsing; ordinary SGO and DSGO are not interchangeable.

Identification and header

The documented DSGO signature is the four bytes 44 53 47 4F (DSGO). The observed header layout is:

Offset Field Documented value or meaning
0x00 Signature DSGO
0x04 Header size 0x10 in the documented profile
0x08 Entry count Number of data entries
0x0C First-node offset 0x10 in the documented profile

Each node occupies 16 bytes: the first eight bytes are node data, followed by eight bytes describing the node type. A structure node points to a separate 16-byte sub-header.

Structure sub-header offset Field
0x00 Name-table offset
0x04 Name-table size
0x08 Variable-table offset
0x0C Variable-table size

Node kinds

Type Documented meaning
0 Number, represented as a double; the game converts to integer/float as required
1 String, using a relative offset to wide-string data
2 Embedded file, often MAB or SGO
3 Structure, with a relative pointer to the structure sub-header
4 Expression evaluated from other DSGO nodes and operations

The older third-party format description marked some details as uncertain. The table is a summary of those documented claims, not independent verification of every possible DSGO resource.

Expression nodes in EDF6

A type-4 node references a program of u32 opcodes, represented in the documented source by a byte size and offset. The measured EDF6 native evaluator uses a value stack. The observed opcode groups include:

  • End, immediate double, UTF-16 string and reference to another node.
  • Call to a built-in function.
  • Addition, subtraction, multiplication, division and integer-rounded remainder.
  • Integer shifts and bitwise AND/OR.

The reported built-ins include pow, log2, min, max, clamp, saturate and lerp. The precise opcode cases, function addresses and exceptional semantics remain in the source-attributed EDF6 research, under fact IDs dsgo-expr-opcodes, dsgo-expr-survey and dsgo-expr-inputs.

For build steam-678ccb46, one source census reported 1,194 distinct expression nodes, 1,948 keys and 114 SGO-named resources, within a bounded object/ corpus. Those numbers describe the measured research set, not all possible DSGO files or other EDF builds.

Where a DSGO resource is encountered

In the studied mission-resource pipeline, a normal ...LIST.SGO file is DSGO-encoded even though its suffix is .SGO. The corresponding normal text/name table can be classic SGO version 258. Some observed override text files were also DSGO-encoded, but their actual runtime loading was not established by that evidence.

Weather DSGO resources have profile-specific schemas. Neither numeric similarity nor matching field names alone proves that values can be copied or scaled across game versions.

Interpreting a DSGO safely

  1. Detect the DSGO signature, independently of the extension.
  2. Validate the header, entry bounds and nested structure/name-table ranges.
  3. Preserve embedded resources, unknown fields and expression structure.
  4. Interpret values against the schema of the particular mission, weather or object resource.
  5. Keep native static decoding, reconstructed serialization and actual in-game testing separate.

For the earlier classic container format, see SGO — structure and typed nodes.
