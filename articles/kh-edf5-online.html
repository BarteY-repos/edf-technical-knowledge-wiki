Drops and crate spawn

Drops happen where the killing hit is processed

Evidence: static · Build: steam-5d11de53 · Fact ID: drop-death-paths

Drops happen where the killing hit is processed. The drop routine 2DB300(obj, pos) reads the object's game_object_drop_item parameter and calls 198540; its callers are the HumanoidBase vslot 14 22CFC0 (call at 22D34B), a generic object damage / death virtual 2DB370 (call at 2DB88F; used by many classes via 2DAC60) and, found in the session-6 review, 235A40 (call at 236452; slot 12 of a secondary HumanoidBase vtable, per that review).

Basis: disassembly

Pickup protocol

Pickup online: each machine runs the pickup check (198E90) for its own player

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-online-report

Pickup online: each machine runs the pickup check (198E90) for its own player; on a hit, before 199000, the same network condition calls 19A190(mgr, serial, category, player), which dynamic_casts to SoldierBase, takes the player's net id (+0xF8) and has 19A4B0 serialize a message (type byte 2, serial, category, player id); the other machines remove that crate.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 198E90, 199000, 19A190, 19A4B0

Shared online weapon and armor pickups

Evidence: verified · Build: steam-5d11de53 · Fact ID: loot-shared-online

Weapon and armor loot is shared online: a pickup by any player counts for everyone (novae (ajane): true in all EDF games). It matches how a common instant-pickup patch behaves: one player running it makes crates vanish for everyone at spawn, because its pickup message removes the crate on every machine.

Basis: user-confirmed (play experience); novae (ajane)

Attribution: novae (ajane) · 2026-10-12

Host pickup broadcast event and serial

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-protocol-host

Host-authoritative pickup: the local pickup 19A190 broadcasts type 2 (serial, category, player net id +0xF8) via 19A4B0 if this machine may decide (19A6E0, the host), otherwise it sends a request. The receiver 19A7A0 (from Event_ItemDrop_Handler at 3FA15B) reads a type byte: 0 = spawn (a copy of the crate); 1 = request (host: authority check 19A6E0, look up the player, collect 199000, broadcast type 2); 2 = picked up: look up the player by net id (4045D0) and call collect 199000(mgr, thatPlayer, category) on this machine too (that is how loot is shared: every machine counts every pickup), then find the crate with that serial and mov byte [crate+0xAC], 1 at 19A87A, so the cleanup loop destroys it next frame (it blinks out). Hooking 19A87A lets a patched machine shrink remotely collected crates instead.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 19A190, 19A4B0, 19A6E0, 19A7A0, 3FA15B, 199000, 4045D0, 19A87A

The host de-duplicates pickups (session 5): 19A6E0 = "am I the authority?" (offline 1

Evidence: static · Build: steam-5d11de53 · Fact ID: host-dedup-pickups

The host de-duplicates pickups (session 5): 19A6E0 = "am I the authority?" (offline 1; online a session vcall). For a client's request (type 1) for weapon or armor (category ≤ 1) the host counts it only if 199ED0(mgr, serial) finds that crate still uncollected (it then marks it collected); a second request for the same serial is ignored. So several patched players sweeping the same crates cannot double-count, and the host does not check whether the requesting player is alive.

Steamworks peer-to-peer transport

SteamNetworking005, SteamUser019 and session layers

Static, EDF5 steam-5d11de53. Steam API context initialized at 872F0 provides SteamNetworking005 at +0x40, SteamUser019 at +8 and SteamMatchMaking009 at +0x20. The EDF5 stack includes net::Steam_Module (vtable EC0298), per-peer Link, AsyncMigrateGame, Steam lobby and room classes (RoomImpl EC2488, 22 vtable slots), and SessionControllerImpl above these peer links. Callback families include P2P request/failure/auth validation plus Steam lobby create/enter/list/chat/data updates. EDF6's EOS transport and handshake must not be assumed compatible with this Steamworks interface.

Accept only known SteamID links

Static. Setup 419550 registers P2PSessionRequest_t (1202) handler 419140 and P2PSessionConnectFail_t (1203) handler 419200. The request accepts AcceptP2PSessionWithUser only when its SteamID maps to a known link at module +0x118. Connection failure before first success (link+0x88=0) sets status +0x28=0x101; otherwise the link is closed. Steam ticket exchange here takes the role of an auth layer; no equivalent EDF6-style 20-second EOS hello deadline was found in the decoded EDF5 route.

Three Steam channels and their send modes

Static. Link sends serialize under critical section link+0x78 and connection guard 4190D0. Routine 41ABE0 sends session game bytes with k_EP2PSendUnreliable on channel 0; 41AC90 uses k_EP2PSendUnreliableNoDelay on channel 1; 41ADF0 first obtains up to 0x400 bytes of Steam authentication ticket using GetAuthSessionTicket, then sends that ticket reliably on channel 2, recording ticket/link status. SessionControllerImpl slots 4 and 5 reach the first two senders. Application traffic uses the unreliable modes and depends on higher-level reliability rules.

Steam P2P session lifecycle calls and reliability boundary

Static. Other located ISteamNetworking calls are AcceptP2PSessionWithUser (slot +0x18, 4191D6), CloseP2PSessionWithUser (+0x20, 419B2A/41ADAB) and GetP2PSessionState (+0x30, 41B108). The source found no reliable Steam send mode for ordinary game-data channels; any retransmission/ack mechanism is owned by the game above Steam, rather than inherited automatically from channel-2 tickets. Its complete resend implementation is separate from these three interface calls.

Channel poll, 2048-byte buffer and deferred session queue

Static. 41A380 polls channels 0, 1 and 2 with IsP2PPacketAvailable/ReadP2PPacket into the static 1259CA0 0x800-byte buffer. Unknown SteamID senders, absent from link map Steam_Module+0x118, are discarded. Channel 2 tickets invoke BeginAuthSession against link SteamID +0x184, with result affecting link+0x1DC. Channel 0/1 data use 41A770 and link user key +0xC4 to notify each receiver at module +0x88; session receiver 4335A0 appends to locked queue +0x478 through 435540 for later decode. This queue is not itself evidence of a world-state snapshot.

Session datagram checks, encryption and record decoding

680-byte record threshold and CRC32C/AES wrapper

Static. Per-peer records accumulate in 434CD0 until the next would exceed 680 bytes (0x2A8) or a 90 ms flush timer fires. 434F20 emits an eight-byte header with 16-bit packet sequence at +2 and CRC32C of plaintext records at +4, then encrypts records through AES routine 4377B0. A per-datagram key uses MD5 85320 over a session-held string and decimal CRC32C of that string plus eight header bytes; which session string is used remains unread. Sequence counter at +0x48 increases after flush, then 4361D0 sends it and increments counters. Header bytes +0/+1 are unexplained; do not equate the wrapper with EDF6's exact constants or a proven cryptographic security guarantee.

Drain packet queue, decrypt and reject CRC/replay

Static. Session update 4336F0 enters 435670, swaps deferred queue +0x478 under lock +0x430, and dispatches kind-1 link events to registered handler slots +0x18/+0x20. Packet records rebuild the per-datagram key above, decrypt with 84830, and are discarded when stored CRC32C mismatches or repeats the last CRC for that datagram sequence number (table at +0x10, indexed under mask +0x20-1). Accepted records execute in wire order. The author did not identify which concrete thread runs the update or decode all record types.

Tagged compact integers, float tolerance and blobs

Static native writer/reader. Integer encoding (463190 writer, 4649E0 reader) uses first-byte top-three-bit tags: 0 represents a signed 5-bit value in one byte, 1 13 bits over two bytes, 2 21 bits over three, 3 a following little-endian 32-bit value, 4 a following little-endian 64-bit value; tags 5–7 decode as zero. Float writer chooses a three-byte half representation with tag 0xC2 when the conversion error is at most 0.1, otherwise 0xC0 plus float32 (five bytes). The source notes that an EDF6 description assigns 0xC2 differently, so cross-game tag equivalence needs byte-level comparison. Blob writer 463B30 stores 13-bit length followed by bytes; receive trusts the initial low-five-bits and second byte without checking the tag. Float/vector readers 464B20/464D50 were located but not decoded.

Transport details still not decoded

Source: unverified/open. Datagram header bytes 0–1, the exact session key-seed string, first resend wait, record type 0x1300, 1000 ms timer activity, the 40-second queue entry at 4344B0, net::Transmit (vtable EC28C0) and 45E120 object contents, and the session update's thread ownership remain unknown. This is a bounded missing-evidence list, not a license to infer behavior from EDF6's EOS transport.

Network event classes and typed controllers

Event class registry and NetworkObject families

Static EDF5 RTTI. net::EventBase vtable EBE788 has derived event families DamageObject, Debug, DebugCameraSync, Generator, ItemDrop, Mission, NoteEventSceneObject, SceneObject, SynchronizeGate, System, TalkManager (the ItemDrop receiver is already covered above). Object side includes net::NetworkObject (vtable E955F8, 17 slots), NetworkBullet and HumanCharacter/WalkCharacter sync controls. EDF5 adds WeaponBulletSyncTable, DamageCollector, DamageLogUtil and SerializeIntervalCtrl helper classes. RTTI similarity to EDF6 identifies families, not binary vtable compatibility.

Factory IDs 1–10 and 100–101; no type 5 factory

Static factory vtables. Factory slot 1 yields u16 event type and slot 2 constructs it: 1 DamageObject (82C00), 2 Generator, 3 Mission, 4 SynchronizeGate, 6 SceneObject, 7 NoteEventSceneObject, 8 ItemDrop, 9 System, 10 TalkManager, 100 Debug and 101 DebugCameraSync; no class factory for 5 was found. 402130 registers nine factories through 4019B0, excluding System and SynchronizeGate. The debug handler passes int 10000 into EventBase, whose exact meaning was not read. Types 6/7 are EDF5's scene object message envelopes, as in EDF6.

EventBase identity, timing and OnEvent dispatch

Static. Constructor 3E6A40 builds event handler fields: type u16 +0x10, event id +0x14, two-int/eight-byte sender key +0x18, controller +0x20, self reference +0x28, performance-counter time +0x30, constructor integer +0x38 and a sign-derived byte +0x3C. Locally made events set bit 1 at +8, whereas received events do not. Each subclass has destructor and OnEvent vtable entries, e.g. DamageObject 3F8BD0, SceneObject 3FABE0, NoteEvent 3FAEF0. Do not assume the +0x38 debug value is a timeout without a reader.

Per-type choice of two session controllers

Static. Typed sender 3F82A0 calls selector 3F8420 over a jump/byte table indexed by event type minus one: event types 1/2/3/5/6/7/8/10/100/101 use session controller +0x1F8, whereas 4 SynchronizeGate and 9 System use +0x200; unknown IDs do not send. The table's type-5 entry does not imply an implemented type-5 factory. A sync-point sender 467220 passes type 4 directly to maker 3E7A70. This routing prevents naive assumptions that every event uses a single generic queue.

Event buffers, receive path and object routing

Two 250-byte event stream builders

Static. net::EventController ctor 3E6C60 builds two 45E120(obj,session,4,250,0) buffer objects kept at controller +0x100/+0x110; stored record selector +0x178 is (param+0x18)<<12 | 0x400, resembling EDF6 data-record subchannel four (cross-game interpretation not verified). EDF6's exact reliable envelope 0x00401200 and 1100-byte limit were not found in EDF5 immediate/data searches. Sharing the 250 threshold alone does not make the formats binary-identical.

Buffer threshold and reliable versus bare record selection

Static. Builder 3E8C20 writes a header into the 45E120 stream buffer at +0x50. Threshold 250 in +0x10 triggers delivery when accumulated length +0x48 crosses it. Byte +0x50 selects bare record send through 45EAD0/432D20 or the custom reliable queue 45E960. EventController makes both its streams with selection zero (the reliable branch); that game-managed reliability is distinct from the earlier Steam send-mode choice.

Record-filter wrapper, per-event decode and queued work

Static. Session record wrapper SessionController::Event<SmartPtr<EventController>> (vtable EC1558) accepts a record when its low 20 bits equal controller selector +0x178; slot 2 442420 feeds 3E7CB0. It reads event type, id and flag through compact integer reader 4649E0, followed by up-to-1500-byte blob with 13-bit length. Handler identity is searched as (id, sender key) in map ctrl+0x88, else built from factory map +0x98 through 3E7520. Receive then queues (flag, sender key, blob) in handler list +0x58, count +0x60, for later dispatch; reading the record is not the same as immediately running OnEvent.

Eight-byte sender key differs from EDF6 index

Static. EDF5 event identities use an eight-byte/two-int sender key, drawn from dispatcher +0x4A0/+0x4A8, as seen in DamageObject debug log's key=%d,%d and in receiver 3E7CB0. EDF6 uses a narrower integer sender index. EDF5's handling of negative IDs, used for replies in EDF6, was not observed in this decoder; matching replies remains unverified. Preserve the full pair when correlating event IDs.

Posted object-event work and NetworkObject slots

Static. OnEvent checks session authority through 7E6E0, copies the blob into a stream (463070) and posts work to a later queue. For type 6 SceneObject or 7 NoteEventSceneObject, worker 3FA9F0 resolves target by 112B20, accesses NetworkObject slot 3 and dispatches slot 12 +0x60 (ReceiveEvent) or slot 14 +0x70 (ReceiveNoteEvent), respectively. The DamageObject worker is a separate path; the relevant HumanBase/vehicle receive bodies were not decoded. There is no evidence here that authority or object ownership is identical to EDF6.

Remaining reply, queue-thread and damage-event gaps

Source: unverified/unread. The flag byte's meaning, matching a negative reply ID, event work-list +0x58 runner/thread, HumanBase and vehicle ReceiveEvent functions, who emits each HP update kind and how frequently, posted DamageObject replay, and the NetworkObject ownership bit at +0x18 remain unresolved. NetworkObject slots and object registration

EDF5 event send/receive vtable differs from EDF6

Static, EDF5 steam-5d11de53. net::NetworkObject vtable E955F8 has seventeen slots. Slot 11 +0x58 (403360) sends type 6 SceneObject events; slot 13 +0x68 (4036F0) sends type 7 NoteEvent events, both through typed sender 3F82A0 after authority check 7E6E0. Receive slots 12 +0x60 (403AC0) and 14 +0x70 (403AF0) default to “not overridden” error logging. Slot 15 +0x78 samples performance counter; base slots 2 and 16 are abstract. EDF6 uses different slot positions for these sends/receives, so binary vtable patch offsets cannot be copied across generations.

Hit decision and network message admission

Attacker's machine decides damage; other copies require forced flag

Static, EDF5 steam-5d11de53. Generic damage 2DB370 calls 2DBA50(target,info) to decide whether a hit counts. Offline returns true. Online, a target slot 28 +0xE0 can supply a class-specific verdict; otherwise attacker identity comes from damage record +0x10, with attackerRemote from info byte +2 when +1 is set, else NetworkObject ownership bit +0x18 &1. Forced hit is info +0x5C &0x40. GameObjectBase slot 27 2DBBA0 returns true for local attacker, forced for remote attacker; absent attacker also passes. Thus the attacker's machine ordinarily computes damage, while remote copies accept only replay-marked hits. A rejected damage entry can still process negative amount as a heal. Other subclasses' slot 27/28 implementations were not audited.

Online gate rewrites hits without a living attacker

Static. Every incoming object hit passes 402C00(NetworkObject,object,message,info), invoked by GameObjectBase message slot 7 and map object handlers. Offline or unregistered target (netPart+0x28=0) passes through. Online, message 0x80000000 clears info byte-3 bit 0 and passes when forced flag +0x5C &0x40 is set or attacker's shared pointer at +0x18 remains live. With absent attacker, session host/authority test may permit it; otherwise the gate logs Reject DamageInfo and converts the message into dropped form 0x4000004. Other message kinds can route through 404050 to generator type-2 events or 40EB80. Host interpretation of that session test remains inferred rather than peer-tested.

Killing transition marks damage-info byte three

Static. GameObjectBase message handler 2DAC60, hit case 0x80000000, samples whether HP +0x1FC was positive, calls 2DB370, and sets info[3] |= 1 only if that hit changed a living object to HP at or below zero (2DADBF). Survivors and already-dead targets skip the write. This is the kill transition bit, not a universal “death state” for every subsequent hit; it matches the concept in EDF6 at different native addresses.

Local kill notice, attribution and save counters

Damage death route sends attacker message 0x80000005

Static. On crossing zero HP, generic death 2DB370 sets object +0x280 & 4, conditionally drops loot when the relevant +0x280 flag, online host test and byte +0x3E8 permit it, then resolves attacker's handle from hit info +0x10 and sends kill-notice message 0x80000005 carrying hit info and victim through the attacker's slots 7/6/8. Team merit is credited separately through 32BDD0. The same death routine can run on guest replay, but the recipient there is the guest's replica of the host's soldier, not automatically the player owning the save.

Only locally controlled soldier increments persistent kill counter

Static. Soldier-family slot 6 307FC0 handles 0x80000005, optionally plays a kill voice cue under enemy/team/talk flags, then checks local controller at +0x240. Only a locally controlled killer reads victim SGO key game_object_kill_counter and increments its matching integer entry in save map +0x14A10 before achievement check 810C0. Remote soldier copies receive the notice but do not update that save count. VehicleBase forwards notices to occupied riders through seat list +0x418; HumanoidBase can play an enemy-killed cue. Guest kill attribution from replayed attacker, not loot crate

Evidence: static · Fact ID: edf5-online-kill-credit · Source: edf5/online.md

A loot crate does not itself encode its killer. Instead a killing-hit record carries attacker network ID, and each peer's replay resolves that ID to its local killer object before invoking the same death routine. The death sends attacker message 0x80000005; only a soldier with a local controller increments persistent kill stats. Thus a guest can attribute a received kill to the killer without being the authority for the host-only loot drop. The underlying packet, receiver and kill-notice routes are already documented immediately above; this record reconciles their cross-cutting conclusion rather than adding a second network mechanism.

Listener 3FD310 scans entity property entries at +0xB8 (count +0xC0) for keys 0 and 4. This links physics entity monitoring to object identity machinery; IGame::UniqueKeyExchange (slot 0 438F00) remains unread.
