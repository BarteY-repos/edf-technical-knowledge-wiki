Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Drops and crate spawn

Drops happen where the killing hit is processed

Evidence: static · Build: steam-5d11de53 · Fact ID: drop-death-paths

Drops happen where the killing hit is processed. The drop routine 2DB300(obj, pos) reads the object's game_object_drop_item parameter and calls 198540; its callers are the HumanoidBase vslot 14 22CFC0 (call at 22D34B), a generic object damage / death virtual 2DB370 (call at 2DB88F; used by many classes via 2DAC60) and, found in the session-6 review, 235A40 (call at 236452; slot 12 of a secondary HumanoidBase vtable, per that review).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 2DB300, 198540, 22CFC0, 22D34B, 2DB370, 2DB88F, 2DAC60, 235A40, 236452

Attribution: novae (ajane) · 2026-10-12

The death paths take a damage record (r8 / rdx) whose +0x50 is the damage and +0x10 an object handle of the a…

Evidence: static · Build: steam-5d11de53 · Fact ID: damage-record-attacker

The death paths take a damage record (r8 / rdx) whose +0x50 is the damage and +0x10 an object handle of the attacker (resolved with 6D730 / 189380; combat.md#lethal-damage-message has the full record). Humanoids store it at enemy+0xA20, apparently as "last attacker" (the source's reading).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 6D730, 189380

Attribution: novae (ajane) · 2026-10-12

Offline the drop always runs

Evidence: static · Build: steam-5d11de53 · Fact ID: drop-authority-check

Offline the drop always runs; online it runs only if [[125AC08] → 7E6E0(...)] vcall +0x18 returns true, an authority check (almost certainly the host: the source's inference). 125AC08: globals.md#global-network-session.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 125AC08, 7E6E0

198540 spawns the crate locally (198640, RNG seeded from [mgr+0xA78], serial [mgr+0xA80]) and, when the network condition [[125AB30]+0x38] != -1 && [...+0x5C] != 0 holds, broadcasts it with 199F20 (seed, serial, position, two floats). The message has no killer field.

Evidence: static · Build: steam-5d11de53 · Fact ID: crate-spawn-receive

Receivers: Event_ItemDrop_Handler (vtable EBF0C8, slot 1 = 3FA120) calls 19A7A0, which spawns the same crate locally. Each machine then simulates its own copy of the crate's physics: no per-crate position sync was found; the serial is the shared id (online-crate-serial).

Basis: disassembly

Addresses (build-specific RVAs unless indicated): EBF0C8, 3FA120, 19A7A0

Pickup protocol

Pickup online: each machine runs the pickup check (198E90) for its own player

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-online-report

Pickup online: each machine runs the pickup check (198E90) for its own player; on a hit, before 199000, the same network condition calls 19A190(mgr, serial, category, player), which dynamic_casts to SoldierBase, takes the player's net id (+0xF8) and has 19A4B0 serialize a message (type byte 2, serial, category, player id); the other machines remove that crate.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 198E90, 199000, 19A190, 19A4B0

Attribution: novae (ajane) · 2026-10-12

Weapon and armor loot is shared online: a pickup by any player counts for everyone (novae (ajane): true in al…

Evidence: verified · Build: steam-5d11de53 · Fact ID: loot-shared-online

Weapon and armor loot is shared online: a pickup by any player counts for everyone (novae (ajane): true in all EDF games). It matches how a common instant-pickup patch behaves: one player running it makes crates vanish for everyone at spawn, because its pickup message removes the crate on every machine.

Basis: user-confirmed (play experience); novae (ajane)

Attribution: novae (ajane) · 2026-10-12

Host-authoritative pickup: the local pickup 19A190 broadcasts type 2 (serial, category, player net id +0xF8)…

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-protocol-host

Host-authoritative pickup: the local pickup 19A190 broadcasts type 2 (serial, category, player net id +0xF8) via 19A4B0 if this machine may decide (19A6E0, the host), otherwise it sends a request. The receiver 19A7A0 (from Event_ItemDrop_Handler at 3FA15B) reads a type byte: 0 = spawn (a copy of the crate); 1 = request (host: authority check 19A6E0, look up the player, collect 199000, broadcast type 2); 2 = picked up: look up the player by net id (4045D0) and call collect 199000(mgr, thatPlayer, category) on this machine too (that is how loot is shared: every machine counts every pickup), then find the crate with that serial and mov byte [crate+0xAC], 1 at 19A87A, so the cleanup loop destroys it next frame (it blinks out). Hooking 19A87A lets a patched machine shrink remotely collected crates instead.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 19A190, 19A4B0, 19A6E0, 19A7A0, 3FA15B, 199000, 4045D0, 19A87A

Attribution: novae (ajane) · 2026-10-12

The remote pickup mark: 19A7A0 finds the crate by serial (+0xB0) among the uncollected crates of the manager…

Evidence: static · Build: steam-5d11de53 · Fact ID: remote-pickup-mark

The remote pickup mark: 19A7A0 finds the crate by serial (+0xB0) among the uncollected crates of the manager list [mgr+0xA60] (skips +0xAC ≠ 0), calls FnFindPlayer / 199000 to credit the player, then mov byte [rcx+0xAC],1 at 19A87A and jmp 19AA75 (epilogue, al = 1; volatiles dead).

Basis: disassembly; novae (ajane)

Addresses (build-specific RVAs unless indicated): 19A7A0, 19A87A, 19AA75

Crate serial: Unit +0xB0 = DropItemManager+0xA80 at spawn (passed to the crate init 19AB90)

Evidence: static · Build: steam-5d11de53 · Fact ID: online-crate-serial

Crate serial: Unit +0xB0 = [DropItemManager+0xA80] at spawn (passed to the crate init 19AB90); it is the network crate id the remote-pickup handler matches, so it is identical on every machine. +0xB8 holds the manager pointer (not free). Restates drop-items.md#crate-unit-serial-and-manager; adds the init and the network role.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 19AB90

Attribution: novae (ajane) · 2026-10-12

The host de-duplicates pickups (session 5): 19A6E0 = "am I the authority?" (offline 1

Evidence: static · Build: steam-5d11de53 · Fact ID: host-dedup-pickups

The host de-duplicates pickups (session 5): 19A6E0 = "am I the authority?" (offline 1; online a session vcall). For a client's request (type 1) for weapon or armor (category ≤ 1) the host counts it only if 199ED0(mgr, serial) finds that crate still uncollected (it then marks it collected); a second request for the same serial is ignored. So several patched players sweeping the same crates cannot double-count, and the host does not check whether the requesting player is alive.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 19A6E0, 199ED0

Attribution: novae (ajane) · 2026-10-12

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-award-counters

The collect path in the pickup check (198F5F+5) calls 19A190 (network report, online) and 199000(mgr, player, category, xmm3 amount): the health categories heal the player; weapon (0) and armor (1), only if 19A6E0 (authority / session check) returns true and [mgr+0xA84] < 0x400 (the ChangePickupLimits immediates at 1990CC / 1990EC), do [mgr+0xA84]++ (total) and [mgr+0xA88]++ (weapons) or [mgr+0xA8C]++ (armor). Restates drop-items.md#pickup-collect and #dropitem-collect-cap; adds the xmm3 amount. The source says "confirmed" (session 6) without naming a test.

Basis: disassembly

The result tally 199120(mgr, out) reads +0xA88 / +0xA8C, multiplies them by a retention factor chosen by 125A…

Evidence: static · Build: steam-5d11de53 · Fact ID: result-tally-detail

The result tally 199120(mgr, out) reads +0xA88 / +0xA8C, multiplies them by a retention factor chosen by [[125AB30]+0x4C] (a 0-4 index, presumably the difficulty; one case gives 0) and adds +0xA90 / +0xA94 (mission-flow.md#result-tally-retention). The counters +0xA88 / +0xA8C are reachable through the drop manager global ([125ABD8]).

Basis: disassembly; novae (ajane)

Local players

player+0x240 is the player's local controller slot: 2DBBC0(player, pad) sets +0x23C = pad and +0x240 = &Contr…

Evidence: static · Build: steam-5d11de53 · Fact ID: local-controller-slot

[player+0x240] is the player's local controller slot: 2DBBC0(player, pad) sets +0x23C = pad and +0x240 = &ControllerManager.slot[pad] ([125AB38]+8+pad*0x2A10, RTTI ControllerManager, created at 3D6C3B; globals.md#global-controller-manager); 2DBCC0 clears both (-1, 0). The mission script's player creation (11D284) assigns a pad only when its pad index is ≥ 0, otherwise it sets -1 / 0.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 2DBBC0, 125AB38, 3D6C3B, 2DBCC0, 11D284

Attribution: novae (ajane) · 2026-10-12

The per-player update (308AE0, called from the four soldier classes' updates 2DFFE0 / 2E2550 / 2E4A0B / 2F9C2…

Evidence: static · Build: steam-5d11de53 · Fact ID: pickup-local-players-only

The per-player update (308AE0, called from the four soldier classes' updates 2DFFE0 / 2E2550 / 2E4A0B / 2F9C26) skips the whole pickup block when +0x240 == 0 (3094D6), and the pickup check itself returns at once for such a player. So the pickup check, and any hook on it, runs only for locally controlled players: online never for remote avatars; in split screen once per local player per frame.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 308AE0, 2DFFE0, 2E2550, 2E4A0B, 2F9C26, 3094D6

Attribution: novae (ajane) · 2026-10-12

In the per-player update 308AE0 (its code continues in the .pdata chunks starting 3091B3 and 3094EC), 3094D6…

Evidence: static · Build: steam-5d11de53 · Fact ID: per-player-update-local-gate

In the per-player update 308AE0 (its code continues in the .pdata chunks starting 3091B3 and 3094EC), 3094D6 does cmp qword [rdi+0x240],0 and (after a mov r13,[rsp+0x1B0]) je 30979F at 3094E6, to the end, for non-local players; so the gate site 30952D and the example hook site 3094EC only ever see local players (drop-items.md#player-update-pickup-chunk). [obj+0x240] is the "local player" test, also used by the pickup check 198E90; a "local players only" tracking rule in a hook is therefore a harmless safety net, not a needed fix. The source says "confirmed" (session 6) without naming a test.

Basis: disassembly; novae (ajane)

Addresses (build-specific RVAs unless indicated): 308AE0, 3091B3, 3094EC, 3094D6, 30979F, 3094E6, 30952D, 198E90

Attribution: novae (ajane) · 2026-10-12

Player list and team records

4045D0(id) / 404440 iterate the container at 125AB80+0x38 (TeamManager, RTTI

Evidence: static · Build: steam-5d11de53 · Fact ID: player-list-walk

4045D0(id) / 404440 iterate the container at [[125AB80]+0x38] (TeamManager, RTTI; std::map-style nodes, object at node+0x20, nil flag node+0x19), __RTDynamicCast (9C8228) each member to SoldierBase and compare the net id +0xF8. Player positions are at +0xA0. That is enough to find the nearest player to a crate (for "fly to the nearest player" online and for split-screen targets). The same walk: combat.md#combat-teammanager-walk.

Basis: disassembly

Addresses (build-specific RVAs unless indicated): 4045D0, 404440, 125AB80, 9C8228

Attribution: novae (ajane) · 2026-10-12

Team list layout (session 6): 125AB80+0x38 points to an array of 0x38-byte team records

Evidence: static · Build: steam-5d11de53 · Fact ID: team-records

Team list layout (session 6): [125AB80]+0x38 points to an array of 0x38-byte team records; many functions index it as [[TM+0x38] + team*0x38 + 0x18], a per-team relation table read with [...+other*4] (values 1/2). Record +0 is a std::map head pointer; FnFindPlayer 4045D0 / 404440 walk team 0's members (in-order MSVC tree: +0 left, +8 parent, +0x10 right, +0x19 isnil, +0x20 object).

Basis: disassembly; novae (ajane)

Addresses (build-specific RVAs unless indicated): 125AB80, 4045D0, 404440

Attribution: novae (ajane) · 2026-10-12

Evidence: unverified · Build: steam-5d11de53 · Fact ID: team0-members-not-only-players

Team 0's members are not only players (hence the __RTDynamicCast to SoldierBase): allies and vehicles are likely in it too; which ones is not known.

Attribution: novae (ajane) · 2026-10-12

Each 0x38-byte team record starts with a {head, size} container whose member count is the qword at record +8

Evidence: static · Build: steam-5d11de53 · Fact ID: team-member-counts

Each 0x38-byte team record starts with a {head, size} container whose member count is the qword at record +8; summing the sizes of the teams that team 0's relation row marks hostile (value 2) gives a live enemy count. The constructor 32BA90 builds the record prototype with size 0; the relation row is the vector data pointer at record +18 (7 dwords), and 32C7D0 reads 2 as hostile. Confidence medium: dead members may stay in the container for a while.

Basis: disassembly only, not read in the running game; novae (ajane)

Addresses (build-specific RVAs unless indicated): 32BA90, 32C7D0
