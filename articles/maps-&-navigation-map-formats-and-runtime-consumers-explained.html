Map resource architecture

UniversalMaps & NavigationNavigationEDF 4.1EDF 5EDF 6
Technical reference · Reconciled sampled binary and runtime research

An Earth Defense Force map is not one mesh file. The studied EDF5/EDF6 map packages contain multiple resources with different consumers: registrations and resource identities, placed objects, field/terrain rendering, physical collision and navigation. A map can render while its collision is wrong; a table can parse while the game's object references still point to the wrong resource.

The relevant formats

Format or subsystem Known role / practical question
MAC Map container/identity and related map resource structure
MAPB Map registration and references to resource roles, including model, object and field resources
MAPO Object/placement tables and relationships to map/collision content
Ordinary MDB model Individually referenced props, buildings, objects and their model materials
FMB / FMEP / FieldRender Terrain/field and its specialized rendering/material transport
MAD / SHKT / HKT Distinct physical/collision and Havok-related data paths, depending on profile
NVMD, NAV and map RMPA Navigation/road/area/portal/related map semantics; not mission-owned route/spawn RMPA

These are roles observed in the studied assets, not a promise that every map contains every file or that one rule works across all generations.

Map registration and object placement: MAPB / MAPO

Observed paired EDF5 → EDF6 MAPB conversion includes structural record changes:

Record family EDF5 stride EDF6 stride Specific observed edit
T1 56 bytes 60 bytes Insert zero dword at entry +0x20; old +0x20 moves to +0x24
T2 68 bytes 72 bytes Add four zero bytes at the end; rebase relative references

MAPB registration suffixes such as .mdx, .trb, .mosb and .fmep identify different resource roles. Globally changing suffixes is not a conversion strategy.

The corrected MAPO object-table element at the studied +0x08 table has a 0x1C (28-byte) stride, not eight bytes. Placement/object identity and associated collision bindings remain separate validation tasks.

Terrain is not an ordinary MDB material

FMB/FMEP field content uses FieldRender; it should not be treated as a large ordinary MDB model. In a recovered FieldRender material bridge:

  • A cell has 12 local material slots.
  • Three RGBA8 ID textures carry four slot IDs each; three RGBA8 weight textures carry matching corner weights.
  • 0xFF (255) is the invalid material-slot sentinel.
  • Material colors come from texture arrays, not the simple ordinary-MDB sampler layout.
  • The sampled terrain normal decoder differs from the Common/Water MDB R×A convention.

See FieldRender local slots and texture arrays for the exact division dimensions, record strides and normalization behavior.

Collision and navigation are independent proof obligations

A successful FieldRender initialization does not demonstrate correct floor collision. Likewise, correct-looking static geometry does not prove Havok shapes or navigation route/portal semantics. EDF4.1 → EDF6 work illustrates why donor navigation can load and still be a fidelity compromise, and why unknown road/portal reconstruction details must remain unresolved.

For collision structures read MAD/SHKT contracts; for NAV geometry and MAPO binding see EDF4.1 navigation research. For mission-owned RMPA, see the separate mission scripting and RMPA guide.

If you are writing an importer or converter

Follow the relationships instead of rewriting one file type in isolation:

map identity / MAC
  → MAPB resource registrations
  → MAPO placements and references
  → ordinary-model or field-render payloads
  → collision and navigation consumers

Keep file-local/profile-specific rules explicit. A version bump or a parse-only PASS cannot establish identical in-game map behavior.

Why file suffixes can crash an otherwise valid map

A real EDF5→EDF6 port showed a MAPB/T1 reference to an ordinary model under a .trb resource role. The target game chose the tree/TRB header parser, but the decompressed payload was actually a 53,806-byte MDB; the in-memory MDB buffer itself was correct. Reading the MDB's +0x28 field as a TRB entry count produced 0x300000, leading to invalid tree-table traversal.

For a converter, this means resource identity, suffix/type registration and payload ABI must agree. The fix is not a global .trb→.mdx replacement: some .trb entries are genuinely typed TRB resources. See Typed dispatch and CMPL failures.

A visual object and its physical body need not share a registry

Source visual objects are discoverable through RAB/MDB and MAPB/MACO-style resource references, whereas physical collision can be represented by separately named bodies in MAD and the map's collision ownership graph. Missing a model name in one resource list does not establish that the physical shape is absent. This is important for destructible props, gates and map-specific foliage. See map prop SGO, CrashType and resource ownership.

Collapse connectivity is authored map data, not inferred at load

EDF6 MAPO contains T50 connectivity and p58 piece/support tables. Static engine analysis shows the map loader parses these already-authored tables and passes T50 entries through MapObject_CrashModel to a body-relationship builder. Merely copying visual building meshes, collision bodies or MAPB placement rows does not preserve their collapse graph. The complete bounded observations are in T50 / CrashModel.

When multiple placements are cloned, matching MAPB/MAPO counts, fresh GUIDs, rebased pointers and parent-child closure are independent from physical MAD/HKT update. See MAPB/MAPO placement duplication.
