EDF 4.1 — Missions (community source notes)

EDF 4.1Community Knowledge HubMissions
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Facts

EDF4.1 mission scripts found within EDF5 project

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-bvm-in-edf5-tree

The EDF5 game tree examined by the EDF5-to-EDF6 transpiler project contains an EDF 4.1 subtree with 126 MISSION.BVM files.

Basis: file-tree census (335 BVM files classified)

Attribution: EDF5-to-EDF6 mission transpiler R37 section 4 (Bartey drop) · 2026-08-26

SetEncountReportRadius BVM native 3000

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-set-encount-report-radius

SetEncountReportRadius(object, radius) is EDF 4.1's script native table 1 id 3000 (14B2E5): it pops the radius (float, top) and the object handle (int) and writes the float to the object's +0x240, which the SGO's game_object_encount[0] fills at 28CF66 (re-read). EDF6's BVM executor routes table-1 id 3000 to no handler (../edf6/missions.md#encount-report-radius-bvm); the author says EDF5 has no native for it, while the hub knows an EDF5 custom call 3024 SetEncountReportRadius (../edf5/mission-vm.md, EDF5 +0x2E4), so the author likely means the table-1 form. DLC mission M508 sets it on its 18 Deiroi.

Basis: the author's static reading; 28CF66 re-read with fn.py

Addresses (build-specific RVAs unless indicated): 14B2E5, 28CF66

Attribution: hajisensai, All Forces source src/edf41natives.cpp (round 24) · 2026-11-07

The EDF41-to-EDF6 project translated EDF 4.1 missions M001, M004, M012 and M014 through its semantic engine

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mission-vm-partial

The EDF41-to-EDF6 project translated EDF 4.1 missions M001, M004, M012 and M014 through its semantic engine; M002 had an event-slot / zero-RegisterEvent ambiguity and M003 one unresolved custom-call family cuscall0 901. Offline only.

Basis: the project's mission engine checkpoint

Attribution: EDF41-to-EDF6 handoff (Bartey), TECHNICAL_HANDOFF_ORIGINAL section 8 · 2026-10-14

Custom call 3019 max-HP percentage

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-call-3019-durability

Custom call 3019 (object, percent) multiplies an object's max HP +0x168 by percent / 100 (AB6884 = 100.0) and sets current HP +0x16C = min(current x percent / 100, the new max), as in EDF5 (../edf5/mission-vm.md#bvm-call-3019-durability): a durability factor on one object after its spawn. The natives switch takes id & 0x7F (byte table 14C9F8, RVA table 14C8A8, head 14B41D); 3019's case 14C097 calls 153E80(script, handle, percent), its only caller. A second native at case 14C2F9 scales only the current HP (capped at max; id not identified). Scripts apply 3019 to the handle a single CreateEnemy returned: 62 calls in 10 of the 98 online-list scripts (tanks and NPCs too, e.g. m113's tanks at 50 % / 20 %).

Basis: fn.py; the switch tables read from EDF41.exe (scratch File_Storage/Logs/catalog/switch_case.py); usage counted over the edftools disassembly (scratch bvm_dis.py --game edf41 all, File_Storage/Logs/catalog/bvm41/)

Addresses (build-specific RVAs unless indicated): 14C097, 153E80, 14C9F8, 14C8A8, 14B41D, 14C2F9, AB6884

Attribution: KH chat 78 (curator) · 2026-11-10

Fallen Flagship Shield Bearer HP call sequence

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-m201-3019-twice

Mission 86 Fallen Flagship (m201) calls 3019 on its first Shield Bearer (shield01, AlienTrailer401_L) twice, once after its own spawn and again after the second Shield Bearer's, whose handle (shield02, AlienTrailer401) gets none: the first is weakened twice (percent x percent: Easy 25 %, Hard 49 %, Hardest 64 %, Inferno 100 %), the second not at all, most likely a script slip. The three extra-large fixed Shield Bearers get the percent once.

Basis: m201 disassembly read (edftools); _tools/bvm_eval.py gives the same

Attribution: KH chat 78 (curator) · 2026-11-10

Mission clear marks (round 10, novae (ajane)'s outside set; source: pickups.md header)

On a clear, 34BAF0 loops over players and classes

Evidence: static · Build: steam-57aab039 · Fact ID: mission-clear-bits

On a clear, 34BAF0 loops over players and classes; the difficulty is [r8+0x44] (34BC73), and vanilla EDF 4.1 sets only the cleared difficulty's bit (mov eax,1 / shl al,cl / or [rdx+8],al at 34BC8E) in the byte [save + 0xEE8 + class*0x200 + mission]: Easy 0x01, Normal 0x02, Hard 0x04, Hardest 0x08, Inferno 0x10. Clearing Inferno does not mark the lower difficulties (EDF5 and EDF6 mark the lower ones for Normal and Hard: ../edf6/missions.md#mission-clear-cascade-v2). FevGrave's InfernoClearsAll_EDF41 ORs a per-difficulty mask instead; FevGrave reports the table version works in game (2026-10-06). Cryswar's ClearCreditsLowerDifficulties (supplied 2026-11-01, written "with Claude") changes the same 7 bytes to B0 02 D2 E0 FE C8 90 (mov al,2 / shl al,cl / dec al / nop), so the stored mask is (2 << difficulty) - 1 (an Inferno clear sets 0x1F); its anchor B8 01 00 00 00 D2 E0 08 42 08 41 8B C1 matches once at 34BC8E; no in-game result is stated.

Basis: FevGrave's disassembly notes; anchor unique; the difficulty load decoded; Cryswar's patch bytes decoded and its anchor checked in EDF41.exe (2026-11-01)

Addresses (build-specific RVAs unless indicated): 34BAF0, 34BC73, 34BC8E

Attribution: FevGrave (InfernoClearsAll_EDF41), novae (ajane)'s EDF 4.1 outside set (ExtraPatches), Cryswar (ClearCreditsLowerDifficulties) · 2026-10-16

BVM event registration versus reachable handlers

RegisterEvent presence is not handler existence

Static decompiled scripts. EDF4.1 RegisterEvent is cuscall0 2. Mission M002 contains clear-handler function Func1709960674 but has no textual registration and no AllEnemyDestroy call, unlike M001, M003 and M004 which each register a corresponding completion handler. Finding a compiled function is therefore insufficient to infer that mission can run it; mission-flow tools must construct registration and reachability edges.

M012 nineteen registration/factor call sites

Static. M012 contains 19 RegisterEvent calls with time factor 9000, all-enemy-destroy 9100, object-destroy 9201 and AI-move-end 9300. Handler Func455038071 registers after generator setup with factor 9201 on the first carrier. Func508242891 registers with six 9300 carrier references. Whether these compose as AND, sequence or delay is not established. One function Func1974397686 registers Func801877805, but that registration function is itself unreachable from the Main closure, so this event cannot be assumed live from a textual search.

Single, group, path and friendly spawns are distinct calls

Static six-script comparison. EDF4.1 M014 calls cuscall0 2001 twenty times: eleven for Nephila and nine for SpiderNet20/40/80, sometimes sharing a named map location. It also calls path-mob native 902 twice and friend native 1010 seven times. M002 uses cuscall0 2000 ten times for single enemies, whereas M001 and M003 use group creation 2002. These different call categories must not be collapsed into one generalized spawn route. EDF4.1 M014 is not EDF5's mission with a similar index.

Game and table namespace matter for native IDs

Static compatibility reading. EDF4.1 native table 1 / 3000 is SetEncountReportRadius (the editor's compatibility path requires plugin table-1 ID 3003 for it), while EDF5 cuscall0 3450 is SetAiSearchRadius, modifying a different object field. A similar function label is not evidence of API equivalence across games or native-call tables.

Community 4.1 mission and localization dataset census

89 mission folders, four BEFORE scene pairs

Static dataset inventory. The community edf41port data enumerates 89 missions, with scripts from the EDF5 tree's EDF4.1 subtree and text/art from EDF4.1 MISSION/MISSION*. The folder inventory begins M190, M515, M191, M192, M104..M108, M016, M110, M111_2, M112 and includes DLC-style MP001..MP004; this dataset order is not the game mission-select order. Exactly M190, M192, M016 and M015 have extra BEFORE.BVM/BEFORE.RMPA alongside MISSION.BVM/MISSION.RMPA. Other 85 have only mission pairs. A pre-mission scene interpretation of BEFORE is based on naming, not proven execution. Each mission has title and briefing in JP, EN, Traditional Chinese (OpenCC-converted), Simplified Chinese (community patch), and Korean (here equivalent to EN).

407 translated weapon SGO entries and provenance limits

Static translations.json census. Weapon-localization table has 407 entries keyed by SGO filenames, from AssultRifle01.sgo (AF14) through names including Weapon001.sgo (AF14RA) and Weapon002.sgo (AF14ST) up to Weapon770.sgo. Each holds name and description for Traditional Chinese (OpenCC conversion), Simplified Chinese (community patch), and Korean; Korean item names retain Latin AF14 model names. AF14 text attributes development to 2011 and service in a war eight years earlier. The source did not establish whether Korean strings were official or community-authored; translation completeness and game display were not retested.

EDF4.1 MainScript boot and coroutine entry

These records come from edf41/mission-flow.md, build steam-57aab039, and are static code/script readings. Potential plugin modifications mentioned below are hypotheses, not instructions tested in a live game.

MainScript origin and first routine inventory

Evidence: static · Fact ID: edf41-mainscript-routines

mainscript/mainscript.as from Root.cpk has 1,418 lines, 39,531 bytes and a UTF-8 BOM. At boot loader 346AA0 compiles it from app:/MainScript/MainScript.as on the MainScript object [CC84D0]. Routines and line starts include main 30; Boot 180; Invite 197; TitleScene 296; CompanyLogo 375; Title 435; SlotSelect 525; ModeSelect 564; MainMenu 626; PlayMission_Common 681; PlayMission_Offline 735; PlayMission_Online 761. Save-loading routines begin at 130–164. Unlike EDF6 it has no leftover Debug_StartOffline; unlike EDF5 it lacks the IsTGSMode show-demo branch.

Remaining result, lobby and versus functions

Evidence: static · Fact ID: edf41-mainscript-routines-2

The remaining named MainScript routines include Result 790, Result_Common 801, Result_Offline 830, Result_Online 862, _OnlineMode 881, InviteOnlineMode 1036, OnlineMode 1042, PreLobby 1049, Lobby 1057, CreateRoom 1179, SelectDLCContents 1222, PreRoom 1274, Room 1282, VersusMode 1336 and PlayVersus 1393. Local split-screen versus is a 4.1-specific MainScript branch absent from EDF5.

GetStartupRoutine and engine-node override

Evidence: static · Fact ID: edf41-startup-routine

main chooses Boot unless native GetStartupRoutine 3470D0 returns a non-empty string. Registration 345270 adds this native; it looks up engine node mainscript and reads the wide-string field at +0x100 (EDF5 uses +0xC8). Constructor 344F10 initializes that string empty, length at +0x110, small-string capacity at +0x118. A hypothetical plugin write of the routine name before startup could redirect entry, but no writer of this field or live override was inspected.

AngelScript coroutine declarations and call sites

Evidence: static · Fact ID: edf41-createcoroutine

main launches each routine through createCoRoutine("string " + name + "") and waits. Native coRoutine createCoRoutine(const string &in) is 91CD0 (registration 92B38), and its overload with any @+ is 91AD0 (92AFD), within add-on registration 92850. The hook point resembles EDF6's coroutine-declaration substitution but the stock EDF4.1 script does not supply a debug routine to jump to.

CScriptBuilder add-section path

Evidence: static · Fact ID: edf41-mainscript-builder-section

346AA0 uses builder entry A9FD0; include-once gate 9A210 precedes 9A880 at call AA098 to add script text, length and section name, then 9BC20 builds the AngelScript module. AA49E is another section-add call on include files. The loader at 3943F0 also reaches AA098, so any proposed module-injection hook would require correct section identification; adding a custom MainScript section here is explicitly untested.

EDF4.1 mission path, mode and slot state

Offline title-to-mission route

Evidence: static · Fact ID: edf41-offline-menu-path

Stock route: Boot → Title → SlotSelect → ModeSelect → MainMenu (HQ) → PlayMission_Offline → Result_Offline → MainMenu on a clear. Boot resets all state and can choose Invite. Title clears invitations, handles logos, resets controller assignment and loads save/add-on state. SlotSelect presents UISLOTSELECT_NORMAL. ModeSelect resets mode state, invokes SetMode(GetUiExitCode), loads mode save data, unlocks DLC and updates counters, then branches among HQ, OnlineMode and VersusMode. MainMenu opens ui_hq and leads to PlayMission_Offline on UIHQ_GOTO_MISSION. Offline launch runs Before, chat creation, then the shared mission loop.

Shared mission loop and retry codes

Evidence: static · Fact ID: edf41-playmission-common

PlayMission_Common (line 681) increments sortie counts, sets Network_SetLocation(GAME_LOADING), waits on Network_Wait_MissionSync, selects used weapons, resets the network session and calls Mission, repeating while the result is MISSION_RESULT_RETRY. The enum is 0 unknown, 1 clear, 2 abort, 3 retry, 4 lobby. The invitation flow reaches online play after save and invitation-specific slot selection, but it still shows a slot selector: it is only a nearer stock path to menu-free startup, not one.

GameDataMgr row, difficulty and save slot

Evidence: static · Fact ID: edf41-gamedata-row-difficulty-slot

GameDataMgr [CC84A0] stores mode at +0x38, mission row at +0x40, difficulty at +0x44, save slot at +0x48, eight bytes below EDF5's corresponding fields. Constructor D8100 initializes mode -1, row 0, difficulty 1 (Normal), slot 0. COMMON.CFG wrapper 3ECE50 uses that slot for saveslot%02d. Bypassing SlotSelect therefore leaves slot 0 unless another writer intervenes; slot-select and HQ writers were not decoded here.

SetMode native and mode data loading

Evidence: static · Fact ID: edf41-setmode-native

void SetMode(int no) is native 348D80, jumping to GameDataMgr setter D97E0 (no observed bounds check, unlike EDF5's bool-returning variant). It selects a mode config through manager +0x20, calls config loader DC5D0 and D8C60, stores no at +0x38 and recomputes the pause mask. TitleLoadSaveData is 34BDA0; ModeSelectLoadSaveData is 34C290. The native's lack of an observed range check is not a tested safe-input guarantee.

Mission native return and script-state loop

Evidence: static · Fact ID: edf41-mission-native-state

int Mission (34A0D0) builds a /mission.bvm path, clears a mission-script object field at +0x232, and calls MissionMgr start routine 148DB0. While the script object's state +0xF8 is 1 or 2, it invokes the script-context virtual callback at +0x1A0 (interpreted as suspend) and returns result +0xFC after the loop; without an object, it uses manager +0x30. The names “started” versus “playing” for 1/2 rely on EDF5 analogy and are not native EDF4.1 labels confirmed here.

No script-side RestoreMissionSelect reapplication

Evidence: static · Fact ID: edf41-no-restore-mission-select

No RestoreMissionSelect native string is present in the inspected executable, and PlayMission_Common does not call a mode-selection reapply routine before Mission. Unlike the EDF5 script, it does not visibly overwrite row [CC84A0]+0x40 or difficulty +0x44 with a stored selection at that point. A different native called on the route could still change those fields; not all such writers were traced.

EDF4.1 loading and result-state signals

MissionScript states and loading counter

Evidence: static · Fact ID: edf41-mission-loading-state · Build: steam-57aab039

Native path 15463D writes mission state 2 after zeroing timers +0x1B0..+0x1E8, setting word +0x230 to 1 and decrementing counter [C64964]. The counter's matching increment is at 15447F, in a presumed BeginLoading body not independently decoded. State 1 is written at 14ADFB. The reading that both states participate in the loading phase is inferred from the code bodies and EDF5 comparison, not a measured UI loading interval.

Network location does not distinguish all menus

Evidence: static · Fact ID: edf41-network-location · Build: steam-57aab039

Network_SetLocation native 34B430 writes integer [CC8548]+0x228, with EDF4.1's four enum values: 0 MENU_LOBBY, 1 MENU_ROOM, 2 GAME_PLAYING, 3 GAME_LOADING. PlayMission_Common writes 3 before and after the mission; on its offline route it does not restore a menu value, so 3 may also remain when the player is back in HQ. Mission script custom-call 10000 handler writes 2 during play. Therefore value 2 can distinguish play from other phases, but value 3 alone is not proof of an active loading screen.

Result UI is reached only for a mission clear

Evidence: static · Fact ID: edf41-results-screen-window · Build: steam-57aab039

PlayMission_Offline returns Result_Offline only for MISSION_RESULT_CLEAR; other outcomes return to MainMenu (the online path is likewise gated). Result_Common at MainScript line 801 runs ResolveResult, creates ui_missionresult, applies the result, saves, waits for UI and save-load completion, then clears the result. Unlike EDF5/6, EDF4.1 does not send every offline mission ending through that result window.

Local mode, split-screen count and pad binding

Online-mode flag and pause-mask proxy

Evidence: static · Fact ID: edf41-online-mode-read · Build: steam-57aab039

Mode setter D97E0 stores the selected mode at [CC84A0]+0x38, with -1 meaning no mode. It tests an online flag in the selected config's variable-length data, then updates the pause mask; the mask at [CC8528]+0xBA4 lacks bit 2 exactly while an online mode is selected in this static reading. A plugin reading the same fields off the game thread was only suggested by inference, not proven thread-safe.

Four local player-count writers

Evidence: static · Fact ID: edf41-split-screen-count-writers · Build: steam-57aab039

Player count is [CC84A0]+0xA800. ResetControllerAssign 34D1F0 resets it to 1 and controller bindings. In UiModeSelect_Main, choice callback 4A67D0 opens UiModeSelect_PlayerNum if the mode requires count selection, or writes the count from the mode object otherwise. PlayerNum stores the selected number at dialog +0x19D0, and callback 4A9330 commits it; player-two poll cancellation is the fourth write restoring 1. For counts above one the mode flow shows GameMode_Player2Assign. This differs from EDF5/6's second-pad-on-mode-screen counting behavior.

Second controller poll and assignment

Evidence: static · Fact ID: edf41-player-two-pad-poll · Build: steam-57aab039

40EA90 polls in the update handlers for UiModeSelect_Main and UiModeSelect_PlayerNum. Input records are 0xD98 bytes per device, with player one's index at object +0x4400. Inferred cancel bit 0x80 at the first player's +0xD8C resets the player count to 1 and state to 2. Otherwise it finds the first device index 1–3 with byte +0x89 set, binds that device to player two through AB120, records the ID at controller manager +0x57DC and advances to state 1. The meaning of the cancel bit remains an inference.
