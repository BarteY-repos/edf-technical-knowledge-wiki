EDF 5 — Rendering (community source notes)

EDF 5Community Knowledge HubShaders
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Facts

The game's IDXGISwapChain is stored at 1256C98 (written in 5E0F30, read in 5E2240)

Evidence: static · Build: steam-5d11de53 · Fact ID: swapchain-pointer

The game's IDXGISwapChain* is stored at [1256C98] (written in 5E0F30, read in 5E2240); EDF5 renders with Direct3D 11 (D3D11CreateDevice imported, D3DCOMPILER_47).

Basis: disassembly cross-references; Eiton's EDF5-Damage-Number-Display reads the same pointer (GetPointerAddress(base, {0x1256c98, 0})) and hooks the object's vtable Present and ResizeBuffers with Detours from a thread that polls every second until the pointer is set; not run in game

Addresses (build-specific RVAs unless indicated): 1256C98, 5E0F30, 5E2240

Attribution: novae (ajane), EDF5-Damage-Number-Display by Eiton (MIT, 2022; in novae (ajane)'s EDF5_Modding_Archive.zip) · 2026-10-14

DXGI swap-chain vtable under ReShade proxy

Evidence: verified · Build: steam-5d11de53 · Fact ID: swapchain-reshade

With ReShade 6.6.2 installed as a dxgi.dll proxy in the game folder, the swap chain at [1256C98] has its vtable in ReShade's dxgi.dll; a plugin that swaps that vtable's Present slot (8) draws fine but before ReShade's effects, and the same swap chain object stays in use from the HQ menu into a mission. Raised from unverified by the 2026-10-20 test; the first wording ("the object is ReShade's wrapper", inferred from how proxies work) was confirmed in substance. Present = vtable slot 8, ResizeBuffers = slot 13 (standard IDXGISwapChain order).

Basis: novae (ajane); on-screen diagnostics (two screenshots): "Vtable memory owner" and "Present code owner" both <game folder>\dxgi.dll, "ReShade loaded: YES", system dxgi.dll and d3d11.dll from System32; the same swap chain pointer at 569 presents (HQ menu) and at 4899 presents (in a mission)

Addresses (build-specific RVAs unless indicated): 1256C98

Attribution: novae (ajane), first stated unverified in session 02 (2026-10-14) · 2026-10-20

The swap chain's backbuffer format is DXGI format 28 (R8G8B8A8_UNORM

Evidence: verified · Build: steam-5d11de53 · Fact ID: present-swap-under-reshade

The swap chain's backbuffer format is DXGI format 28 (R8G8B8A8_UNORM; novae (ajane)'s run was 2560 x 1440 at 60 FPS). ReShade's depth-of-field blurs part of an ImGui window drawn through the Present swap (ReShade samples the scene depth behind it); novae (ajane) sees the same blur on the game HUD. Drawing after ReShade would need ReShade's add-on API or a hook on the real swap chain below the proxy (not tried).

Basis: same test and screenshots as #swapchain-reshade

Attribution: novae (ajane) · 2026-10-20

Damage Number Display Present hook

Evidence: static · Build: steam-5d11de53 · Fact ID: damage-number-present-hook

Eiton's Damage Number Display hooks IDXGISwapChain::Present with Microsoft Detours (an inline hook on the function taken from a swap chain's vtable, VMT_PRESENT) and draws with its own statically linked Dear ImGui context. A plugin that hooks Present by vtable-slot swap runs before it, so the damage numbers draw over that plugin's drawing. The 2026-10-20 test's "Present code owner" names only the module of the slot's address and does not follow an inline jump, so Eiton's hook on the same function was not visible there.

Basis: source reading (Eiton's plugin, modding archive copy); the order consequence is inferred from how the two hooks work, not tested together

Attribution: novae (ajane), Eiton (EDF5 Damage Number Display, MIT) · 2026-10-20

Render resolution read on first Present

Evidence: static · Build: steam-5d11de53 · Fact ID: render-size-globals

Eiton's plugin reads the game's render width and height as two ints at 1256C00 / 1256C04 on its first Present (afterwards it takes them from ResizeBuffers) and scales its 1920-wide layout by width / 1920, adding (height - width x 9/16) / 2 to y for non-16:9 windows. Code that reads these globals sits in the swap-chain code near 5E0C25 and 5E22F8 (rip-relative scan).

Basis: source reading; references found by a rip-relative scan (KH chat 20), the writer not read

Addresses (build-specific RVAs unless indicated): 1256C00, 1256C04, 5E0C25, 5E22F8

Attribution: Eiton (EDF5-Damage-Number-Display, MIT) · 2026-10-28

D3D11 device creation flags and Direct2D support

Evidence: static · Build: steam-5d11de53 · Fact ID: d3d11-device-flags

EDF5 creates its Direct3D 11 device with no creation flags (no D3D11_CREATE_DEVICE_BGRA_SUPPORT), so Direct2D cannot draw on the game's device or swap-chain surfaces unless that flag is added at device creation. A mod overlay that wants Direct2D must hook device creation before the game's first call, or render on a second device and share the result.

Basis: disassembly of the only D3D11CreateDevice call (call qword ptr [C97EC0] at 5E10F8): adapter 0, driver type from a local list (also stored to [1256C38]), software module 0, Flags 0 (xor r9d,r9d at 5E10F0), one feature level, SDK version 7; feature level stored to [1256C3C]. d3d11.dll's only import is D3D11CreateDevice; nothing is imported from d2d1.dll or dwrite.dll. Not run in game

Addresses (build-specific RVAs unless indicated): 5E10F8, 5E10F0, C97EC0, 1256C3C, 1256C38

Attribution: novae (ajane) · 2026-10-14

Main simulation and render thread workloads

Evidence: verified · Build: steam-5d11de53 · Fact ID: thread-layout-measured

EDF5's CPU work sits mainly in two threads besides the busy message pump (input.md#input-pump-thread-busy): one game thread (38.5 % of process CPU cycles, about 6 ms of work per 16.67 ms frame at the 60 fps cap) and the Present thread, which also submits the draws (12.7 %). An NVIDIA driver thread (7.4 %), a worker running EDF5 code at 931000-99C2EC (1.2 %) and an umbra_sandlot.dll occlusion thread (1.0 %) follow. On a Ryzen 9 5900X at 60 fps no thread is saturated. The game thread's top function is 5A86B0 (15.7 % of its busy samples), then 60FC80, 5AE3B0, 3C8600, 5BE280; the Present thread's top functions are 5CDE30 (material bind, models.md#models-material-bind-cache) 10.4 %, 5CD150, 5AE1D0, 5AC2F0 (model submit), 5CD0C0, 5B2900, 5EDBC0, 5B3000 (mesh draw).

Basis: novae (ajane); which job the "game thread" does (update vs other) is inferred, not traced; 5A86B0 is unnamed

Addresses (build-specific RVAs unless indicated): 5A86B0, 60FC80, 5AE3B0, 3C8600, 5BE280, 5CDE30, 5CD150, 5AE1D0, 5AC2F0, 5CD0C0, 5B2900, 5EDBC0, 5B3000, 931000, 99C2EC

Attribution: novae (ajane) · 2026-10-25

EDF5 view request queue

Evidence: static · Build: steam-5d11de53 · Fact ID: view-requests-queue

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Main and shadow view requests
  2. Request scheduling
  3. Renderer consumption
EDF Knowledge Hub record — original wording — expand (1,983 characters)

Each view (the main view and every shadow view) is rendered from a view request the game thread submits (main 626C40, called at 612FC9; secondary/shadow 6271C0, called in a loop at 612BC8, sets view kind 1 at 6272A3), deep-copied (626F50) and queued with 95AE0 into the global ring queue 1259468 as job 626A80. That job runs on the render ("Present") thread (likely) with the view's own Umbra camera ([V+0x40]) and visibility query, and every view reuses the single Commander serially (built at 625C74, stored at [S+0x10], S = [125B080]), so several views per frame are normal for this engine. 627660 pops records {Umbra camera [V+0x40], V, Commander [S+0x10], blob} pushed by 627790 (at 626E9A); 626C40(S, _, req*) does not drop a request while [V+0x74] is set: it first resolves the previous query (C97F80/C97F88) and re-queues. A view's Umbra camera is set up by 6226E0(V, params) (sole caller 6129E6). Request layout (read at 626D0F-626DAC): [0] view id, [8] view object (Umbra camera at +0x40), +0x30..+0xB0 matrices copied from the game camera chain [[[[125B080]+8]+8]+8] (camera.md#camera-eiton-view-chain). Job 626A80: camera blob 6259B0, fetch {Umbra camera, Commander} 627660, copy blob to commander+0xC0 (627920), scene system 626000, then processVisibility (626B04). One query in flight per Umbra camera object: flag [V+0x74] (626CD6); resolveVisibility (C97F88) runs at the top of the next submit for the same camera (626CC2, 627242). The visible list is not stored by the game: Commander command 3 reads it from Umbra (getDataCount/getObjectData/getUserPointer, C98088-C98098) into per-Commander phase lists, cleared at the end of command 1. All D3D11 work is immediate-context calls on [ctx+8]; no FinishCommandList (vtable +0x390) call in 1000-800000. For a second view (planar reflection, extra camera): submit one more request with a changed camera and its own view object V' (own Umbra camera and in-flight byte); the Commander and the renderer targets are shared.

Basis: novae (ajane); consumer loop of the queue not traced; not run in game

Addresses (build-specific RVAs unless indicated): 626C40, 612FC9, 6271C0, 612BC8, 6272A3, 626F50, 95AE0, 1259468, 626A80, 625C74, 627660, 627790, 626E9A, 6226E0, 6129E6, 6259B0, 627920, 626000, 626B04, 626CD6, 626CC2, 627242, C97F80, C97F88, C98088, C98098

Per-view xgl_system camera matrix upload

Evidence: static · Build: steam-5d11de53 · Fact ID: camera-writer

Per view, 5DAFE0(R, _, view*, proj*) writes the camera into the renderer's xgl_system CPU copy (R = [1259680]): the transposed view at R+0x10 and projection at R+0x90, and derives view_inverse (R+0x50), view_projection (R+0xD0) and its inverse (R+0x110). One of its 12 callers is 614F00, slot +0x18 (EE0590) of the scene-listener vtable EE0578, reached from Commander command 2 (62CF0F -> 626120 -> 614F00). The listener is a sub-object at this+0x28 of the render-scene class (ctor 610600), registered at 610800-61084D into the listener vector [125B080]+0x30. Matrix source: Umbra getCellToCameraMatrix times a Y rotation by the float at EE6560 (pi), and getProjectionMatrix; stored in Commander+0xE0 / +0x120 and the camera blob (view at blob+0x20, projection at blob+0x60; blob at Commander+0xC0). The prior 'only caller' claim was corrected by camera-writer-2 and edf5-camera-writer-callers.

Basis: novae (ajane)

Camera matrix writer: 12 callers, in-place overwrite

Evidence: static · Build: steam-5d11de53 · Fact IDs: camera-writer-2, edf5-camera-writer-callers.

Static xrefs identify twelve callers of 5DAFE0: scene listener 614F00, 5DB3BE, player-camera render step A11A7 (within A0E00), and HUD/2D draw paths 48D15F, 48D378, 499BC4, 49C03D, 4A17E7, 4A187E, 4A6284, 4A631B, 4B445E. It overwrites [1259680] in place, including matrices at offsets +0x10, +0x50, +0x90, +0xD0, +0x110 and scalar fields +0x6A0/+0x6A4, without retaining an older copy. A post-render hook may therefore see the last written camera rather than the main scene camera (inference; not checked live).

Basis: new cross-reference scan in the Knowledge Hub, source grade static.

Forward-pass pre-sort hook function

Evidence: static · Build: steam-5d11de53 · Fact ID: forward-pass-hook-site

The call 62CDAF call 626480 runs once per main view right before the phase-2 (forward/translucent) sort and draw loop, after the scene-color target and depth are bound (5DB970 at 62CC89), and its rel32 at 62CDB0 is 16-byte aligned, so a plugin can retarget it with one atomic 32-bit store to a near thunk (no code copied) and get control there with the Commander in rdx. Bytes at 62CDA1: 4D 8B C7 49 8B 55 10 48 8B 0D D1 E2 C2 00 E8 CC 96 FF FF (mov r8, r15; mov rdx, [r13+10h]; mov rcx, [125B080]; call 626480). 626480(holder = [125B080], cmd, blob) calls vtable slot +0x50 of each entry of the holder's list ([holder+30h], count [holder+40h]) and returns void (the caller overwrites rax at 62CDB8); prologue 48 89 5C 24 08 48 89 6C 24 10 48 89 74 24 18. After the phase-2 loop, 62CE4C loads [[r13+10h]+8] and calls its vtable slot 0x378 (ID3D11DeviceContext::Flush, slot 111), which confirms that the Commander's +8 is the immediate context. A texture bound once here does not reach the water draw (#srv-wipe-before-water).

Basis: disassembly (fn.py edf5 62CD54 --to 62CE30, fn.py edf5 626480); novae (ajane)

Addresses (build-specific RVAs unless indicated): 62CDAF, 62CDB0, 62CDA1, 626480, 62CDB8, 62CE4C, 62CC89

Extra t16 and t17 resource bindings in forward pass

Evidence: verified · Build: steam-5d11de53 · Fact ID: srv-wipe-before-water

A pixel-shader texture bound once with a raw PSSetShaderResources (slots t16/t17) at the forward-pass hook site does not reach the water draw (SND_MAP_WATER_TRANSPARENT): the state reset 5EF5C0 (flag 8) wipes all 128 SRV slots per stage several times a frame (shaders.md#srv-binding-cache). Re-binding after each pixel-shader wipe (the call FB8F0 at 5EF75B, bytes E8 90 C1 B0 FF, retargeted) makes the binding reach the water. Over 300 frames: 7365 pixel-shader wipes, 2990 on the render thread (re-bound), 4375 on other threads; on the render thread the reset was called per frame from return addresses 5DBD23 (1x), 5DBF1F (2x), 5E2F8A (1x), 62BF0D (3x), 62C17C (1x), 107C17 (1x), 1084C9 (1x). Which of these falls between 62CDAF and the water draw is not settled. Side observation (cause unknown): with the water painted pure green, soldiers beside the river and metal tanks beside the harbor water took a green tint while objects away from the water did not; possibly the local cubemaps (LocalCubeMap@ren@xgl) are captured at run time and include the forward water; not checked.

Basis: novae (ajane)

Addresses (build-specific RVAs unless indicated): 5EF5C0, FB8F0, 5EF75B, 62CDAF, 5DBD23, 5DBF1F, 5E2F8A, 62BF0D, 62C17C, 107C17, 1084C9

Rasterizer state creation and flush site

Evidence: static · Build: steam-5d11de53 · Fact ID: rasterizer-state-flush

Rendering: local cubemaps, weather and depth consumers

Provenance: EDF Knowledge Hub revision 5b589ca, EDF5 build steam-5d11de53. Findings are source-attributed static code or resource observations and not independent runtime tests. The camera-writer and twelve-callers source records were reconciled earlier in this article and retain their existing IDs; this section covers the remaining records.

Map weather selection and LightEnv configuration

Weather from scripts (static): mission call 14 LoadMapResource(map,weather,group) preloads the map and named weather RAB, while call 100 SetMap(map,weather) asks the map manager to instantiate them. Main/MP script observations include fine, cloudy, cloudy2, finecloud, evening, sunset and night variants.

LightEnv matching (static): map loader C22A0 constructs map/<map>_<weather>.rab, retains the weather name and asks parser C7C70 to find a case-insensitive match among up to nine LightEnv SGO Name fields, otherwise choosing the first entry.

Not a weather-only hot swap (static): C30D0 checks whether the map was loaded and its weather changed, but then takes the full map-loader route through C1CC0/C22A0. The conditional helper C3310 was not read, so its exact cleanup behavior remains open.

Map resource census (static): outdoor .mac files commonly contain six LightEnv variants and matching weather archives; caves/interiors normally have one. Each variation can select its own shared sky cubemap and associated local environment textures, not merely an intensity multiplier.

LightEnv field families (static): source maps 116 keys covering fog, three directionals/sub-light, sky/ground, sun/halo, bloom, tone, DOF, wind, clips, EnvmapArea and EnvmapTexture. Rain, snow and dust are not activated by a LightEnv key in that sample; those effects have separate mission-script commands.

In-mission light animation (static): custom calls 5013/5014 drive EventLightTool at 124DDA0 to fade indexed light RGBA or scalar properties over seconds. Script helper FadeMainLight drives light indices 0, 1 and 12; the exact meaning of every index was not traced.

Baked local cubemap arrays, grid and fallback behavior

Archive coverage (static): 21 of the 22 surveyed map/*.mac archives in Chunk01.cpk contain local-cubemap area records; ig_cave501_test has EnvmapTexture without corresponding EnvmapArea/local_cubemap shapes. This is a census of that package, not a claim about all releases.

Map-time load (static): C7C70 obtains EnvmapArea RMPA rectangle volumes and a baked EnvmapTexture cubemap-array texture, builds a LocalCubeMap and queues it to the renderer's +0x610. These textures are loaded with map data; the observed game route does not render a new probe in play.

Volume lookup grid (static): C90A0 fixes a 25×25×25 cell grid. 5E6570 encodes up to eight distinct local cubemap indices from a cell's corner influences into a 0x30-byte structured record and uploads a shader-readable grid with world-bounds parameters.

Resource class (static): LocalCubeMap@ren@xgl uses a texture-resource/multiple-base vtable arrangement, rather than a separate visible top-level LocalCubeMap vtable. The shared ownership block starts with TextureBase methods in the examined binary.

Single-map environment fallback (static): absent a local grid, parser C7C70 loads EnvmapTexture as a single cubemap or ultimately default_env.dds. The renderer starts with an empty local cube resource; freeing the map resource group can clear both single and local resources.

Developer bake tools (static): console commands cubemap_mode_set, create_cubemap_parts, CSV/RMPA variants and load_local_cubemap_array implement six-face capture and file-based baking/reloading. Exported face names such as px.dds/nx.dds follow the code shape; the shipped cubemap contents were not visually reviewed.

Water tint boundary (static with hypotheses): these map-time static local cubemaps cannot be a live accumulation of green water color on nearby objects; water is drawn in a later forward pass. Bloom, transparency or another post pass are suggestions, not a resolved cause of the observed tint.

Depth format, reverse-Z patch surface and postprocess readers

Depth render target (static): 6153A0 constructs two R16G16B16A16_FLOAT color targets and one R32_TYPELESS depth texture, exposed as R32_FLOAT SRV and D32_FLOAT DSV; no stencil format is involved. Long-range precision consequences remain inferred from the ordinary projection.

Dormant reverse-Z gate (static): a Commander view byte at +0x160 selects depth GREATER_EQUAL with clear zero versus LESS_EQUAL with clear one; constructor initializes the flag off. A valid reverse-Z patch would also need to change command-zero clear and the camera projection's z row. The survey found no later store enabling the flag in the renderer.

Ambient-occlusion depth (static): 1183A50 samples minimum depth from each 2×2 group and linearizes with near/far using z=n×f/(f−d(f−n)) then negates it. Its near/far constant-buffer writer was not traced; reversing depth needs attention to this code path.

Decal G-buffer conversion (static): 1141270 reconstructs view depth/normals with baked-in near 0.1 and far 1000 rather than projection-derived parameters; those values would remain stale if camera clip planes were patched independently.

Sky/deferred lighting (static): three lighting compute shaders use the view-space G-buffer rather than raw depth and mark sky by a very large view-z magnitude. A separate depth-to-view-Z shader uses inverse projection but hard-codes a sky result when depth is at least one, another review point for reverse-Z experiments.

Other sampled depth (static): the investigated SSR and AO blur comparisons use absolute depth differences, and dormant SSR hi-Z paths are not active in the ordinary render route. They do not automatically require the same kind of reversed-Z comparison edit, though re-testing an actual reverse-Z build is still necessary.

EDF5 deferred bloom/tone post command

Render-thread queue and final compute combine

Evidence: static · Fact ID: edf5-post-chain-dispatch

System renderer 6126A0 calls enqueue routine 5DE3B0, which submits render command 5DE540 with bloom/tone defaults. The command calls the post worker 5DDB30, the only source-observed caller. That worker unbinds targets, runs resize/blur helpers 5F3EE0, 5F4190, 5F4490, 5F4D10 and 5F48B0, then combines via constant buffer at post +0xBA0/+0xBB0, shader at +0xB80 and a compute Dispatch. Setup 5D6BD0 builds the combine resource at [1259680]+0xB70 and 0x40-byte cbuffer at +0xB90; object identity from matching field offsets is inferred.
