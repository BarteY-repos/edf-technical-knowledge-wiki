The useful model for the three games is shared lineage with subsystem-specific migration, not “the same engine with version numbers changed.” Some containers remain recognizable, some ABIs change structurally, and some runtime systems are rewritten while preserving familiar names.

Where EDF5 is a useful intermediate oracle for EDF4.1 → EDF6

EDF5 is especially valuable where EDF5 and EDF6 already agree on the rewritten target-side runtime contract.

A concrete example is Vehicle404: EDF4.1 uses a different class generation and source control values, while EDF5 and EDF6 share the target-era Vehicle404_Tank contract and the same [0, 2] nested main-cannon tuple. In such cases EDF5 helps distinguish a deliberate generation change from an EDF6-specific regression.

EDF5 also provides paired same-asset evidence for model/material migration: it exposes what the older asset looked like immediately before the EDF6 BRDF/material generation, making native EDF6 same-asset targets useful conversion oracles.

Where EDF5 is not a safe universal bridge

Do not assume “EDF4.1 → EDF5 → EDF6” is always composable as two mechanical converters.

Examples:

  • EDF4.1 source gameplay semantics may need to be preserved even when EDF5/EDF6 rewrote the underlying runtime class.
  • NAV/Havok geometry must be judged against the source mission/map and target runtime; donor EDF5/EDF6 topology is not automatically source-faithful.
  • shared container names such as SGO, RAB, MAC or RMPA do not prove identical embedded schemas.
  • common save encryption does not prove common offsets or table meaning.
  • a native EDF6 asset can be a target ABI oracle without being a semantic donor for the EDF4.1 content.

Three different kinds of “same”

When reconciling generations, classify similarity explicitly:

  1. Container same — parser/container family is recognizable, but payload schema may differ.
  2. Runtime ABI same — target-side field/class behavior matches across generations, as with some EDF5/EDF6 vehicle contracts.
  3. Semantic same — gameplay/visual behavior is actually equivalent.

Only the third is gameplay parity. The first two are useful evidence, not substitutes for runtime or source-semantic validation.

Practical conversion policy

For every format or subsystem, prefer this order:

source semantics -> measured source structure -> paired target-native oracle -> target writer/runtime contract -> runtime validation

Do not replace it with:

copy bytes -> bump version -> rename resource -> assume parity.

That distinction is the central cross-generation rule of this wiki.
