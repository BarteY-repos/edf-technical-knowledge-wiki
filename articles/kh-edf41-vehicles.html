VehicleBase

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-vehiclebase-ctor-keys

The VehicleBase constructor 2E6FD0 (after the GameObject constructor 28CBD0; vtables AA0028 and secondary A9FF98 written at 2E7016 / 2E7020) reads the SGO keys animation_model (A055C0), ragdoll (A055F0), vehicle_riding_position (A05630), vehicle_weapon_setting (A05600 / A056D0) and vehicle_damage_effect (A05110 / A050E0: [0] a float, [1] an int, [2] four floats); a missing weapon node logs VehicleBase::VehicleBase( weapon node not found. %ls) (A05660). Vehicle weapon setting vector entries

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-vehicle-weapon-seats

Vehicle health and weapon damage setup

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-vehicle-setup-hp

SetUp's base 2E8A10 sets HP and the weapon damage factor as EDF5 does (../edf5/vehicles.md#edf5-vehicle-setup-hp): max and current HP (+0x168, +0x16C) = durability +0x160 x setup[0][0] x a, and +0x398 = setup[0][1] x b. When the flags byte +0x2A has bit 3, a = f / 10 (AB6790) x ModeList[mode][6][difficulty][5][0] and b = f / 10 x [5][1] (f the level factor +0x25C, difficulty [save+0x44], config [save+0xC0], save [CC84A0], as in enemies.md#edf41-hp-same-steps); otherwise a = b = +0x39C (1.0 from the constructor). So ModeList value 5 is [vehicle HP, vehicle damage] (offline all [1, 1]; online, Easy to Inferno, [1.8, 1.8], [2.0, 1.5] twice, [1.8, 1.5] twice, as KH chat 130 read them from config.sgo), applied only to vehicles with bit 3.

Basis: fn.py read of 2E8A10

Addresses (build-specific RVAs unless indicated): 2E8A10, AB6790, CC84A0

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-vehicle-update

The update 2E8310 runs 2E6C20 on every weapon entry and calls slot 31 for a weapon whose +0x864 is 1; it sets the team from the riders as EDF5's does (../edf5/vehicles.md#edf5-vehicle-update): while HP +0x16C > 0 and flags +0x2A bit 3 is clear, the team is that of the live rider in the highest-numbered occupied seat (rider seat+0xD8, its control seat+0xE0; team +0x180; default 5), and on a change the vehicle leaves the old team list (2C9390 on [CC8510]) and joins the new one (EE300), flag +0x1E8 bit 6 (2E8487..2E85AE; EDF5 calls 2DBE20 instead). Then it clears the seat change bits, word +0x348 &= +0x344 (2E85B4), and copies +0x390 / +0x394 to each seat's +0x170 / +0x174 before clearing them (EDF5 +0x480 to seat +0x2F0). The change bits are read per class (Car, Tank, Begaruta, the helicopters, e.g. Helicopter302 2FE782); no shared boarding-sound function like EDF5's 355630 was found.

Vehicle-to-map contact damage

EDF4.1 run-over.md, Steam build 57aab039. The following are static native-code findings, not newly reproduced runtime tests. Contact damage is directed at map props, not established as a hit on civilians.

RigidBodyContactDamageControl layout and ownership

Evidence: static · Fact ID: edf41-vehicle-contact-component

RigidBodyContactDamageControl implements hkpContactListener (vtable AA3338, constructor 339200, callback 339730, deleting destructor 3392D0). VehicleBase constructs it at vehicle+0x3A0 (2E708F; the EDF5 analogue is at +0x490). Owner +0x30, subscribed-body vector +0x38, hit record +0x60, per-target queue +0xD0, and mode / once flag / impulse scale / blast +0x118/+0x11C/+0x120/+0x124. The record contains team +0x7C, point +0x80, impulse +0x90, initial damage zero +0xA0, blast +0xA4, flags +0xA8 and hit points +0xB0. Twelve constructors, including non-vehicle enemies, allocate such a component.

Contact callback filters map objects

Evidence: static · Fact ID: edf41-vehicle-contact-callback

339730 skips mode 0 and an event already marked handled. It identifies the subscribed collision body, possibly reverses the normal, and looks up Havok property key 0 on the other body. RTTI cast 8D8F9C requires MapObject_Base; then predicate 109E70 checks the prop. Mode 1 accepts only categories 2, 4, 5, 6 (mask 0x74); mode 2 accepts any prop passing the other gates. NetworkObject slot 2 must return zero. The callback invokes the hit under a lock and sets the once-per-contact marker. A character does not pass the specified map-object cast.

Impulse, blast and deferred hit delivery

Evidence: static · Fact ID: edf41-vehicle-contact-hit

339C60 takes the owner's team at +0x180, the contact point and impulse normal multiplied by component scale +0x120. Blast +0x124 applies only to a flagged mode-2 prop outside categories 2, 4, 5 and 6; otherwise blast is zero. 28C410 queues the record per target. VehicleBase slot 1 (2E7DE0) eventually flushes the queue with 28C820 at 2E82E5. The path pushes or breaks map props, not character targets.

Single- and multi-body subscriptions

Evidence: static · Fact ID: edf41-vehicle-contact-setup

3393E0 initializes one body and 339550 an array, storing owner, mode and once flag and installing listeners with 6083F0. VehicleCarDefault (also bike and Striker) reads car_map_object_destruction from SGO as [mode, scale], applying scale at vehicle+0x4C0 on body vehicle+0x1048. VehicleBegaruta reads begaruta_map_object_destruction; VehicleHelicopterBase uses mode 1 and scale 1.0 on body +0x1168.

Tank, GroundRobo and FortressRobo modes

Evidence: static · Fact ID: edf41-vehicle-contact-modes

VehicleTank constructor 304D10 takes the mode as its third argument. RescueTank, Rocket, Tank403 and the Tank301 factory use mode 1, whereas Tank404 uses mode 2. When present, tank_rot_skid_scale supplies the impulse scale at vehicle+0x4C0, otherwise 1. Vehicle502_GroundRobo creates its component at +0x1350 with mode 1, and Vehicle501_FortressRobo at +0x1700 with mode 2, subscribed to one or multiple part bodies.

FortressRobo keyframed-contact event

Evidence: static for callback; unverified for interpretation · Fact ID: edf41-fortress-keyframe-contact

Vehicle501_FortressRobo::KeyframeCollisionControl (vtable A9FD48), slot-4 callback 2E1550, sets event +0x3C to 1 when the other root collidable is a rigid body with Havok property key 5. That this rejects the contact and lets the body pass a keyframed robot part is inferred and untested. Key 5's meaning remains unknown.

Vehicle self-damage and civilian boundary

RigidBodyContactSelfDamage algorithm

Evidence: static · Fact ID: edf41-vehicle-self-damage

RigidBodyContactSelfDamage (vtable A9F8E8) listens through setup 2D33B0 and filters only another MapObject_Base (slot 8 2D3600). Calculation 2D3680 multiplies closing speed by scale, optionally by the positive head-on velocity component; values below a minimum threshold become zero, otherwise the result is multiplied by factor a. Slot 7 2D3490 sends the owner a damage message 0x80000000. Setup fields store factor, scale and threshold at +0xF0/+0xF4/+0xF8, with owner at +0x100.

Bike and helicopter damage configuration

Evidence: static · Fact ID: edf41-vehicle-self-damage-users

VehicleBike::SetUp (2F55D0) installs self-damage at vehicle+0x14C0, using bike body, maximum HP as factor a, bike_contact_damage_scale, minimum 0.02 and head-on flag. VehicleHelicopterBase::SetUp (2FDC50) installs one at +0x1210 with heli_contact_damage_scale, minimum 0.05 and flag; a rotor instance at +0x1320 uses roter_contact_damage_scale, minimum zero, flag off and has no body yet. Both are prop-contact self-damage mechanisms.

No demonstrated run-over damage to civilians

Evidence: unverified · Fact ID: edf41-civilian-no-run-over-hit

The two vehicle contact routines require MapObject_Base and the source found no other contact-to-character hit path. The conclusion that civilians are merely pushed by the solver without damage or knockdown is an inference; the civilian walking-body collision layer versus vehicle bodies was not inspected and the behavior has not been game-tested.

Hit processing, HP and healing (EDF4.1)

Further edf41/run-over.md native findings explain how a hit record could affect a human or object after an eligible hit has been emitted. They do not supply a missing vehicle-to-civilian hit callback. Build steam-57aab039; evidence is static.

GameObjectBase hit acceptance and friendly fire

Evidence: static · Fact ID: edf41-human-hit-path

Message 0x80000000 enters the damage handler 28E1F0. It rejects a self-originating hit for a vehicle-flagged object (+0x2A bit 3). A friendly hit (team-table relation 1) requires record flags +0x48 bit 0x20, then is scaled by difficulty-table A91D68: 0.1, 0.25, 0.5, 0.75, 1.0 from Easy to Inferno. Virtual slot 10 (+0x50) accepts or rejects; refusal or object flag +0x1E8 bit 0x800 requires forced flag 0x40 to continue. Slot 11 (+0x58) is the OnDamaged callback.

Local versus remote hit processing

Evidence: static · Fact ID: edf41-damage-process-here

28E840 determines whether the current machine processes the hit. It returns true offline (save byte +0x5C zero) or for a non-network attacker. Otherwise the attacker-remote flag comes from record bytes +1/+2 or attacker +0xC8 bit 0; forced is flags +0x48 bit 0x40. The result delegates to the target virtual callback +0xA8(attackerRemote, forced). Key record fields: attacker handle +0x10, team +0x1C, signed damage at +0x40 (negative means healing) and flags +0x48. This authority decision is separate from collision detection.

AddHP clamp and known call sites

Evidence: static · Fact ID: edf41-addhp

AddHP 28ED20(obj, delta) ignores a dead object (+0x1E8 bit 0x10) and otherwise clamps HP +0x16C after adding delta between minimum +0x164 and maximum +0x168. Its non-network callers cover damage, healing, two crate-collection routes (1AF070, 1A8310) and the SupportUnitBullet01 TeamManager heal-device callback. An online receiver instead writes through 28EE10, so AddHP is not the sole HP writer across networking.

Positive damage, negative healing and invincibility

Evidence: static · Fact ID: edf41-damage-hp-branches

When processed locally, nonnegative damage subtracts damage multiplied by object factor +0x1FC and the friendly-fire factor, via 28ED20. Negative damage heals and sends attacker credit message 0x80000003 with actual HP gained. When processed elsewhere, negative damage only sends the credit with proposed gain min(maxHP-HP, -damage) and does not change local HP. Object flag +0x1E8 bit 1 skips both unforced paths. The encounter step follows the HP update, then an HP value at or below zero sets death bit 0x10. Local credit and remote HP authority must not be conflated.

Human hit response and knockdown limits

HumanBase accept callback

Evidence: static · Fact ID: edf41-human-accept

HumanBase slot 10 29C4C0 rejects enemy/teamless hits while its +0xB84 gate is positive. Blast above 1e-6 sets state +0xB88 to 1 for non-hostile or zero for hostile hits. The callback also rejects hits while the action state machine at +0xBC0 is in state 2A44F0. These are checks for an already supplied hit, not a proof of run-over detection.

Blast knockdown, friendly-fire difficulty and flinch

Evidence: static · Fact ID: edf41-human-knockdown-gate

HumanBase::OnDamaged 29C580 exits for nonpositive damage. For blast above 1e-6, zero gates +0xBF1 and +0x204 permit transition into down state 2932A8, unless already down. If the controlled player is hit by a different friendly teammate, difficulty table A91D7C (0,0,0,1,1) instead allows friendly knockdown only on Hardest or Inferno. Non-knockdown impact starts a 30-frame flinch timer at +0xC28. A blast in this function is conditional on a hit already arriving.

Ragdoll launch speed, direction and part impulses

Evidence: static · Fact ID: edf41-human-knockdown-velocity

For ragdoll +0x9A0, the blast launch 29CB33..29CF85 computes the direction from hit position to a ragdoll point, blending toward up with factor 0.5 × (R - distance)/R where R is blast radius. Speed is max(8 × ln(R), 0), then random spin is added. Each hit point matching a ragdoll part receives an impulse proportional to max(8 × ln(max(R - distance, 0)), 0). A separate non-blast impulse branch for active ragdolls at 29D03F is identified but was not fully traced; its 0.0125 and 10 constants should not be treated as a proven formula.

People NPC class and pain dialogue

Evidence: static · Fact ID: edf41-people-class

People (primary vtable A9DD78, secondary A9DCE8 at +0xB0) overrides HumanBase slot 11 OnDamaged at 2AA2E0 and several update/animation/capture slots. With object +0x2A bit 3, positive damage, cooldown +0x130C expired and state +0x204 not 2 or 3, it may play the ダメージ (“damage”) talk entry via 2C2890, then waits 300–599 frames before repeating. It ends in HumanBase::OnDamaged. people_reaction_run is read in 2A9EC0, while people_reaction_stand, _find_panic and people_color_table had no direct code reference in this source pass. This class's hit response does not identify who emitted the original hit.

EDF4.1 boarding during roll and Fencer uncertainty

Roll-state restriction word permits vehicle boarding

Evidence: static · Fact ID: edf41-roll-boarding · Build: steam-57aab039

EDF4.1 ride gate 29DD70 checks bit 2 of action-restriction word +0x320. Both roll states (292160 and 293670) write 0x38 to that word, leaving bit 2 clear, so this native gate permits boarding during the roll. EDF5's roll value 0x63C has the blocking bit set. Additional EDF4.1 actions write different literal or computed words and several other routines check bit 2; the precise field values are build-specific and this observation does not promise every vehicle accepts every timed roll input.

Fencer dash/boost boarding still unverified

Evidence: unverified · Fact ID: edf41-fencer-boarding-open

Native action words 0x3D and 0x29 appear at 295EF2 and 2962D1, matching the numeric values EDF5 uses for Fencer air dash (which blocks boarding) and air booster (which does not). By analogy the first would block and the second permit boarding in EDF4.1, but this source did not read EDF4.1's Fencer movement states or message handler. Treat this as an open hypothesis, not a confirmed class-specific restriction.
