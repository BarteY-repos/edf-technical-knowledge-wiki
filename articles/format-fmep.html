FMEP — field/terrain resource role and loader boundary

File FormatsSource-scoped referenceEDF 6
Reader-oriented technical reference · Existing research only · Version-specific profiles, where documented

At a glance

What it is: FMEP is a terrain-related resource identity in EDF's map-loading system. It helps connect a map's registrations to its field-rendering assets.

Where it fits: In one researched EDF6 loading path, a .fmep registration leads the loader to a related .fmb resource; this is a lookup relationship, not proof that both files have the same format.

Important distinction: Do not treat a successful resource lookup as proof that the terrain is rendered or that collision works.

What is actually established

The existing map-stack research documents .fmep registrations alongside MAPB, FMB and FieldRender resources. In one studied EDF6 loader path, MAPB can name .fmep while the runtime derives and looks up a related .fmb resource. This is a measured loader relationship, not proof that the two file formats are interchangeable.

The separate FMB resource must be correctly registered through the MAC's externals.sgo in that observed path. Merely placing parseable FMB bytes on disk does not establish that they will be found or used at runtime.

How the observed EDF6 resource chain fits together

The measured FieldRender path makes the roles clearer when read in order:

Stage Resource or consumer Known responsibility
Registration MAPB definition with .fmep name Identifies a terrain/field placement type in the map graph
Resource lookup Preload_Fmex Resolves an associated .fmb resource name in the observed EDF6 path
Availability MAC externals.sgo Must register the looked-up FMB for the studied loader path
Geometry/render data FMB and FieldRender Supplies terrain records, leaves, material relationships and rendered instances
Collision MAD/HKT references Separate physical data; a visible field does not prove its collision

The native-loader experiment identified a missing-FMB lookup fault before the field reached successful rendering. Registering the FMB removed that particular lookup failure from the subsequent diagnostic, but later work encountered a separate MAC-directory problem. Neither observation proves a finished custom FMEP route in the game. The case is useful because it separates resource discovery, binary decoding, drawing and collision into different contracts.

The independently sampled native terrain corpus successfully decoded 1,477 FMB leaves and checked 20 DDS mip payloads against reported sizes. Those are FMB/DDS validation figures, not an FMEP-header census or a general FMEP serializer specification.

Distinguishing the nearby formats

Resource Documented role
MDB Ordinary model geometry, bones and material bindings
FMB Field/terrain geometry, render and spatial data in studied profiles
FMEP Field/terrain registration or associated role in the map stack
MAPB Registration and resource linkage for the owning map

The distinctions above are about observed consumers and resource roles, not a universal binary-layout table. The preserved R193 sources have substantially more detailed FMB binary evidence than a standalone, exhaustively decoded FMEP container specification.

What remains unproven

  • A general FMEP header/record grammar covering all EDF generations.
  • A universal FMEP conversion law derived from ordinary MDB materials.
  • The conclusion that field parsing or rendering success proves native floor collision or navigation parity.

These are explicit evidence boundaries. Unknown fields must not be replaced by guessed values to make the page appear more complete.
