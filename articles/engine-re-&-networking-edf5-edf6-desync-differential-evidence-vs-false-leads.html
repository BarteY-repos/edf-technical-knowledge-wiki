EDF5 versus EDF6 desync: proven network differences and rejected root causes

ConversionEngine RE & NetworkingNetworkingEDF 5EDF 6
Technical reference · Cross-version binary comparison and previously observed symptoms; repair runtime remains separate

The EDF5→EDF6 network investigation produced several exact binary differences, but no universal, runtime-proven fix for every desync symptom. Treat a player's pose, aim, HP and projectile motion as separate state flows that share some transport layers. The evidence below tells a debugger what to instrument and which historical assumptions were already disproved.

Verified architecture by layer

ordinary scene transform    → class 3 / 0x3300 ───────────────────┐
DamageObject / game event   → class 4 / 0x3400 → retained RUDP ───┤
NetworkBullet update        → class 5 / 0x3500 → retained RUDP ───┤
                                                                ▼
                                          EDF6 ordinary EOS physical send
                                       (coalescing, then UnreliableUnordered)

The fact that the lower EOS send uses UnreliableUnordered does not mean that class 4 and class 5 have lost their application-level reliability. They are ACKed by Sandlot RUDP before being physically sent over the same lower layer. In EDF5, the matching RUDP flush likewise reaches the ordinary Steam Unreliable physical slot; it does not use the UnreliableNoDelay slot.

Reconnect and retry are separate lifetimes

The native physical p2p::Link can be replaced while the logical peer UserSession and reliable send/receive state survive. If the old READY bit remains set when a new Link enters INITIAL, the normal retry and handshake cycle can be skipped. This is different from removing a peer, which destroys the logical session. Do not reset RUDP sender sequence numbers or dedupe tables simply because the physical Link changed.

Retained RUDP DATA is 0x1200; its sequence ACK is 0x1300. The timeout interval starts at 700 ms, grows by 1000 ms after each resend, and marks fault after the running interval passes 7000 ms in EDF6 (versus 20000 ms in the studied EDF5 homolog). The roughly 25.9 s vs 204 s cumulative no-ACK exposure follows from the progression; these are not seven-second and twenty-second one-shot timers.

Minimal evidence to collect for an actual reproduction

  1. Record monotonic timestamps from both peers, local/remote object identity and which peer owns each object.
  2. Track physical EOS result, aggregate size, Link READY, INITIAL entry, and reconnect notifications.
  3. Record outgoing/received class3 0x3300, then the deferred SceneObjectReceiver enqueue → parse → apply result; the receive path clears a pending flag before the target apply gate, which can drop one staged batch.
  4. Independently record class4 0x3400 EventController protocol IDs and RUDP sequences/ACKs, especially DamageObject protocol 1.
  5. Record class5 0x3500 bullet selector/mode and the projectile's serialized versus private state.
  6. Repeat an ordinary walk and a class-specific jump. Observe the outgoing jumper's state separately from the jumper's remote view.

No plugin build, trace run or in-game reconnect repair was performed during this reconciliation. The reported results are retained earlier observations and source/binary reconstructions; the two candidate repairs still require clean Windows game A/B qualification.

See packet/event registry, player-state lanes and RUDP lifecycle.

Cross-layer causal interpretation of captured desync

The retained R7 two-PC physical-payload matches and the approximately 183-world-unit remote-position divergence are detailed in SceneObject's R7/R8 receive-frontier study. They rule out a simple missing physical EOS packet as the sufficient explanation for that captured run, not all connection-related faults. A successful physical receive is not proof of SceneObject staging, Soldier transform application or a successful DamageObject event.

The practical diagnostic separation is:

  • Class 3 positional divergence: distinguish 0x3300 physical delivery, individual fragment/type staging, 16-bit sequence freshness and concrete Soldier application. Different fragments may legitimately share a sender batch sequence, so a global equal-sequence filter is unsafe.
  • Class 4 event divergence: use the 0x3400 event identity plus Sandlot's reliable DATA sequence and ACK; a recovered reliable message may still be applied to the wrong object or with wrong game state.
  • Class 5 projectile divergence: 0x3500 retained selectors cannot replace Flame/Lightning/SolidExp constructor-internal RNG or detonation state that was never serialized.
  • Transient reconnect failure: separate physical p2p::Link replacement/READY from the packet Controller/UserSession/ReliableMgr lifetime. A persistent READY flag and no ACK can create a different failure chain, but has not been proven to cause ordinary R7 position drift.

The later R8 29-hook and R9 31-hook diagnostic candidates are static-qualified only in the retained sources; they did not retroactively repair or re-run the R7 two-computer capture. This source lineage is not an argument for automatically installing a global transport rewrite or for treating a per-type staging hypothesis as fully proven.
