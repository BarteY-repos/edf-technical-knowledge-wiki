Where the caps act

Offline mode has no ModeList cap values

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-offline-modes-no-caps

The offline main mode holds no caps: in config.sgo's ModeList, mode 0 (GameMode_Scenario) has integer 0 in every difficulty's value 6 and value 7, which the cap getters D99F0 / D9990 read as no list, no cap (as EDF5's, ../edf5/online-caps.md#edf5-offline-modes-no-caps); its mode value 7 (node +0x5C, the online flag) is 0 as well. The Mission Packs' offline modes have value 7 = 0 too (file-formats.md#edf41-dlc-modelist); their value 6 and 7 lists were not re-read here.

Basis: scratch File_Storage/Logs/catalog/modeprobe2.py edf41 0 (config.sgo read in place)

Addresses (build-specific RVAs unless indicated): D99F0, D9990

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-cap-flag

The weapon-cap flag is the byte save+0xA7D5 (save object [CC84A0]; EDF5's save+0x24571, ../edf5/online-caps.md#edf5-cap-flag): the online session update 377CD0 sets it to 1 at 37929B when the room's weapon switch [session+0x284] > 0 and the cap D99F0 > 0, with the notice OnlineSys_WeaponCapLock (A195F0), else 0 at 379322 with OnlineSys_WeaponCapUnlock (A19688). Weapon select lacks EDF5-style cap predicate

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-weaponselect-cap-marks

The weapon select UiHQEquipment_SelectWeapon (vtable AAABD8) has no installed predicate as EDF5's does: its slot 0 43A1B0 (the per-frame update) calls 43A040 (43A1F3), which returns unless the current mode node's value 7 is nonzero (43A072 cmp d[rax+r8+0x5C], 0, setne al, test al, al, je 43A19E; bytes 42 83 7C 00 5C 00 0F 95 C0 84 C0 0F 84), then for every cell (0x40 bytes, in groups of 0x20 bytes at screen +0x1928, count +0x1938) sets byte +0x3C = flag set (43A088) and level above the cap (43A13B..43A179, the same test as 389440). So the marks are recomputed every frame, online only.

Basis: fn.py reads of 43A040, 43A1B0; --xref 43A040, --xref 43A1B0; vtable by vt_name.py / vt_dump.py; bytes by rd.py

How over-cap weapons are rendered in menu

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-weaponselect-cap-refusal

What a mark does in 4.1's weapon select: the draw slot 1 43A5D0 draws a marked cell's text (the weapon's string from the screen's text_table, its name by inference) red, RGBA (1, 0, 0, 1) from AB7770, else white (AB7F00) (43A92A..43A93C, 43A9EA cmp b[rcx+rdi+0x3C], 0, cmove). Unlike EDF5 (../edf5/online-caps.md#edf5-weaponselect-cap-colors) a marked weapon cannot be picked: on confirm (input bit 0x40, 43A347) 43A35B cmp b[r9+0x3C], r15b (r15 = 0), jne 43A40D (bytes 45 38 79 3C 0F 85 A8 00 00 00) skips the pick silently. An accepted pick writes the weapon id to save+0x261C + 4 x (0x407 k + 4 class + slot) (43A39A; k [screen+0x18C0], slot [screen+0x1944]), sends message 4 through 56E740 and plays the cue 決定.

Basis: fn.py reads of 43A5D0..43AB40, 43A300..43A480; colors by scratch File_Storage/Logs/00v/flt.py; bytes by rd.py

EDF4.1 Steamworks network transport and lobby structures

Shared EDF4.1/EDF5 net classes, with missing EDF5 additions

Static RTTI/vtable census. EDF4.1 has Steamworks net::Steam_Module (AA46B0), Link, AsyncMigrateGame, LobbyImpl, RoomImpl (AA5390), SessionControllerImpl (AA5448), EventController, eleven Event classes, NetworkObject (A92538), NetworkBullet and WalkCharacterSyncControl. EDF5 adds named helpers that EDF4.1 lacks in this census, including DamageCollector, DamageLogUtil, SerializeIntervalCtrl, WeaponBulletSyncTable and new room/mission/script management classes. Shared class names guide analysis, not equal instruction addresses or identical packet semantics.

Three Steam P2P channels and authentication ticket path

Static. Link send operations take a critical section and check 3802D0. 381D40 sends SteamNetworking channel 0 with type 0 unreliable, from SessionControllerImpl slot 4 3B5610; 381DE0 sends channel 1 with type 1 unreliable-no-delay from slot 5 3B5750. 381F80 creates a SteamUser auth ticket (slot +0x68, up to 0x400 bytes) and transmits reliably on channel 2. 381E90 cancels ticket/auth session and closes peer session; 3821B0 queries peer state beside a QPC timer. Interface method names inferred from Steamworks slot order.

SteamNetworking receive poll, 2048-byte buffer and link authentication

Static. EDF4.1 uses imported SteamNetworking accessor 918C40 rather than EDF5's context member. Receive 381510 polls into static 2048-byte buffer CC7230, locates sender's SteamID link via Steam_Module+0x100/+0x118 and answers channel 2 through SteamUser BeginAuthSession (slot +0x70, 3817DD), clearing link flag +0x1CC. Other channels are delivered inline to receivers held at module +0x88. This is the EDF5 transport pattern with differing object offsets and callback layout.

EDF4.1 datagram cipher and resend remain unconfirmed

Unverified. The EDF4.1 executable's inspected RTTI has no CRC32C class; flush candidate 3970E0 writes header fields +2/+4 but its summarized calls did not reveal EDF5's AES/MD5/CRC32C wrapper. Resend checker, record handlers and uses of MSVC rand constants in append 396E90 remain unread. Do not claim wire compatibility or absence of all encryption solely from missing RTTI.

RoomImpl and Steam lobby callbacks

Static. net::RoomImpl (vtable AA5390, 22 slots, constructor 3B58F0) derives from room/communication/session interfaces and registers Steam callbacks 505 (LobbyDataUpdate_t) and 506 (LobbyChatUpdate_t), via handler address values 3B7C40 and 3B8120 whose exact pairing was not read. Room construction also installs timeout constants 5000 and 15000; their state-machine role remains undecoded.

Steam lobby member limit from public and private slots

Static. CreateLobby call 3BBB6B chooses public type 2 when room public-slot count +0x64 is above one, otherwise private type 0, with member limit +0x64 + +0x68. Room name derives from save [CC84A0]+0xA18. After creation it writes public_slot, private_slot, open_public, chat_enable, ugc_enable, game_mode and search metadata; 3BC3B0 reads slot counts back. This call does not itself hardcode four members; other UI/game limits remain possible.

Join result codes and bounded missing difficulty gate

Static text/code reading. Join result handler 4BE0B0 maps code 2 to OnlineError_RoomError, 3 to OnlineError_RoomFull and 4 to Lobby_NotHaveContents (likely missing mission pack by label). Room browser exposes Lobby_Difficulty, Lobby_WeaponCap and Lobby_ArmorCap. EDF4.1 lacks the specific Lobby_Join_Impossible text for EDF5's final-mission difficulty gate, but no complete gate search was done; absence of that one string does not prove every analogous restriction absent.

EDF4.1 script watchdog, migration and world snapshot boundary

Eight watchdog enum states and host-migration mission exit

Static Root.cpk script/header reading. States 0–7 are NONE, RETURNROOM, RESTART, DISCONNECT, MIGRATEHOST, PLUS_CHECK, SIGNOUT_ERROR, NETWORK_ERROR; EDF5's extra SHAREPLAY_1P_ALERT is absent. Watchdog_Critical polls every five frames and responds to return/restart/disconnect with mission exit or retry notices. MIGRATEHOST updates room metadata but ends an active mission, with a different in-room notification. The presence of AsyncMigrateGame is therefore not evidence of uninterrupted running-world migration.

Watchdog queue and current-location enum

Static. Watchdog_PeekState handler 38D820 reads a queued state at session [CC8548]+0x200 when count +0x220 is nonzero (EDF5 uses a different +0x250 location). Script GetCurrentLocation enum values are 0 lobby, 1 room, 2 playing, 3 loading. These are script-facing states; exact native queue producers are not decoded.

No located EDF6-style xgs world snapshot in EDF4.1

Bounded negative static search. Inspected EDF4.1 RTTI has no xgs::snapshot class, and the only snapshot strings found are CRI audio texts around 93AF40..93B0C0; even EDF5's named havok_world_snapshot job is absent. Startup uses scripted barriers, followed by Event_SynchronizeGate type 4, Generator type 2 and Mission type 3, whose Mission handler AA3DB0 was not read. With the watchdog behavior above, no evidence supports restoring a running mission after host migration. This is a bounded absence finding, not proof against undiscovered snapshot code.

EDF4.1 event factories, receiver queues and object identities

Factory event IDs 1–4, 6–10, 100 and 101; type 5 absent

Static vtable factory read. Event IDs match the EDF5 family: 1 DamageObject (AA4208), 2 Generator (AA41E8), 3 Mission (AA4248), 4 SynchronizeGate (AA41C8), 6 SceneObject (AA4228), 7 NoteEventSceneObject (AA4288), 8 ItemDrop (AA4268), 9 System (AA40E8), 10 TalkManager (AA4188), 100 Debug (AA4108) and 101 DebugCameraSync (AA41A8). No type-5 factory was located. Each factory's slot 1 returns the ID and slot 2 constructs an EventBase via 3515A0; Debug/SceneObject use timeout value 10000.

Two registration passes for ordinary and system/gate factories

Static. Registrar 36AC80 installs nine ordinary event factories through 36A460 using session [CC8548]; 36ABD0 registers System and SynchronizeGate plus Debug vtable through the same helper. Event_*_Handler RTTI classes (vtables around AA3D10..AA3E30, three slots) exist for regular types except Debug and NoteEventSceneObject. Their base RTTI retains original spelling ICommunicate::SerialzieHandlerBase. Registry membership does not prove all subclasses' receive bodies decoded.

Record controller filters, 1500-byte cap and queued event handlers

Static. SessionController::Event<SmartPtr<EventController>> (AA48B8) slot 1 3A4C60 checks a sign-extended low 20-bit record ID against controller +0x178, then slot 2 3A4C80 calls 352940. The decoder caps blob length at 1500 bytes, looks up handler map at +0x88, enqueues work at handler +0x58 (count +0x60) and constructs events through 352130. Separate wrappers accept record types 0x3300 and 0x3500. This is structurally EDF5-like, not a packet compatibility test.

NetworkObject 17-slot vtable and scene event dispatch

Static. net::NetworkObject vtable A92538 has seventeen slots: slot 11 36BD10 sends type-6 events, slot 13 36C070 sends type 7, both through session helper 360830 at [CC8548]+0x198; slots 12 36C3E0 and 14 36C410 are default receivers that print failure messages; slot 15 36BC50 reads QPC. The network part lives at object +0xB0, unlike EDF5's +0xC0. MapObject_Base retains default receive slots in the inspected vtables.

Eight registration families and remote ownership flag clearing

Static. Native 377350 clears network-component u16 flags via 0xFFFE/0xFFFD, reached by seven entries through 377650 and map-object entry 376190 directly. Registration records handed to 371700 include family 1 script spawns (375F30), 2 map objects (376190), 3 generator releases (376310), plus families 4 (376570), 5 (376880), 7 (376E60), 8 (3770E0) and special vehicle printer 376B90. Meanings of 4/5/7/8 remain unread.

EDF4.1 GameObject notes and SoldierBase net masks

GameObjectBase type-6 event only decodes target kind 1

Static. GameObjectBase::ReceiveEvent type 6 (28FB40) runs while HP at object +0x16C is positive. It handles kind 1: read an integer, look it up through 37B950, call 1D04F0(object, result) when found or clear network part target references +0x1F8/+0x200/+0x1F0 when missing. Treating it as target set/clear is inferred. Unlike EDF5's base class, this receiver has no sequenced-vector kind 2 or HP-delta kind 3; subclasses may still override.

GameObjectBase type-7 HP and encounter note variants

Static. Network part vtable A9CA38 overrides slots 2, 12, 14 and 16. Type-7 receiver 28F850 recognizes kind 0 as directional HP update around current +0x16C (live applies 28EE10, mirrors to +0x310; dead-positive calls object slot +0xD0, possible revive); kind 1 performs one-time encounter action, calls slot +0x78 and 28F6C0; kind 2 writes minimum HP +0x164. Offsets are object-local and are approximately 0x90 below EDF5's corresponding fields.

SoldierBase writes a byte mask in its NetworkObject slot 4

Static. SoldierBase main vtable A9E170 has 61 slots (EDF5 has 79); network part vtable A9E360 is at object +0xB0. Overrides include slot 4 writer 2B6050, slot 5 reader 2B6270, slots 12/14 event receivers and slot 16. EDF4.1 constructs a one-byte mask within the write method and emits it via 3C4370, then fields via main slot +0xF0; zero mask returns false. EDF5's separate main slot 77 and u16 mask are not portable to EDF4.1. Player/AI sync-checker RTTI classes are also present.

Player and AI soldier frequency masks omit EDF5 extra bits

Static. Writer 2B6050 uses part counter +0xF4C. Controlled soldiers send base 0x58, position bit 0x01 at count % 6 = 3, aim 0x02 at % 6 = 0 and conditional 0x04 when field +0x380 clears; dead/riding reduce to 0x48 plus position. Ragdoll bit 0x80 uses doubling back-off. Alive AI soldiers send 0x03 every 30, 0x20 every 120 and conditional 0x04 every 10 writes; dead AI sends nothing. EDF5's mask bits 0x100/0x200/0x400 are not part of this byte-level format.

Event stream, response and authority questions still open

Unverified. Byte/float readers 3C5B30/3C5C60 have not been compared with EDF5's packed stream encoding; second event maker 3527E0, replies, handler ownership and OnEvent authority test, helper 1D04F0 and subclass ReceiveEvent overrides remain unread. Matching event type numbers alone is not a substitute for those dispatch and payload checks.

Scripted online start, UserSync and MissionSync

Forty-four script-native online functions

Static. Registrar 38BF00 declares 44 online functions (EDF5 has 70), including Synchronize (38DD90), IsHost (38D930), IsConnected, GetCurrentLocation, session create/update/destroy, Watchdog_PeekState and PeekNotify, dialogs and debug room tools. Session_Destroy at 8E1E0 is empty; Session_IsActive at 8F210 returns false. EDF4.1 lacks EDF5's Watchdog_GetState, Invitation_* and PlayTogether_* declarations. Function presence is source API scope, not evidence that every path is active.

Two AngelScript barriers instead of EDF5's three

Static Root.cpk script review. network/network.as defines Sync_MissionStart with Synchronize(100000), UserSync begin/update/finally and MissionSync begin/update/finally in one coroutine; Sync_MissionResult has Synchronize(200000) and ResultSync. EDF5 splits UserSync into a third 110000 prestart barrier. EDF4.1 waits through Network_Wait_MissionSync 34B590 and result wait 34B6F0, with no separate Network_Wait_MissionPreSync. Steps return next sync number or -1 and use shared five-code RET_SUCCESS/BUSY/ABORT/TIMEOUT/DISCONNECT enum.

Native wrapper/worker pairs and sync point registration

Static. UserSync Begin/Update/Finally wrappers 38E280/38E2A0/38E300 call 38ECD0/38FAB0/38F350; MissionSync 38E320/38E340/38E3A0 calls 390BF0/391C30/391850. ResultSync Begin/Update 38E3C0/38E3E0 and Finally reuse 38E3A0. Update wrappers return -1 on their workers' timeout flags. Synchronize at 38DD90 registers a point in session registry [CC8548]+0x198 with IsHost flag through 360BB0/3C7540.

IsHost calls session game-object slot three, true offline

Static. Session base is [CC8548], with these host-test fields 0x60 below EDF5's equivalents. IsHost (38D930) returns true without active +0x148/+0x120 session objects; otherwise calls game-object slot 3 (+0x18) at session +0x150 or +0x128. This is the ownership predicate also used by spawn natives. The registered sync table is at +0x198, not EDF5's +0x1F8.

UserSync assigns per-room-member player indices at +0xF8

Static. Host-side UserSync_Begin worker 38ECD0 uses the same inline host test as above and walks members with their player index at +0xF8. UserSync_Update worker 38FAB0 stores received indices into members' +0xF8 (debug text PlayerIndex = %ls,%d). The source traces host assignment/guest write, not an upper bound on member count.

MissionSync player-table stride 0x101C with only negative index guard

Static. Update worker 391C30 writes mission/difficulty to save +0x40/+0x44, then each record's class at +0x6764 + index×0x101C, four weapon IDs at +0x6768 + index×0x101C + class×0x10, and another integer at +0x6808 + index×0x101C (armor count by EDF5 analogy, unconfirmed here). At 392298 it guards only negative index, with no seen comparison to four, unlike most EDF5 record fields. Received player count goes to save+0xA804, local count read from +0xA800. This is a static bounds observation, not a tested exploit or proof of >4-player admission.

Script-owned spawns, seeded simulation and sync open questions

Host owns scripted spawns; guests receive no local soldier controller

Static. Twelve native spawn calls from 14D390..153600 pass is-guest predicate 375480 as remoteOwned to 14DEC0(script, object, remoteOwned, index, float). Online registration keys by script bytecode offset [ctx+0xE0] - [[ctx]+8] through 375F30. On a guest, soldier copies set controller +0x1A0=-1. Player soldier spawn 14FE30 also registers through 375F30. This shares EDF5's ownership idea at different object offsets.

Online object seed combines spatial inputs and save seed +0xA7D8

Static. Online seed routine 28FCC0, reached from GameObjectBase construction 28CBD0 and two other paths, combines weighted position/vector input and save seed +0xA7D8; resulting object RNG words are +0x210=n+0xDEADBEEF and +0x250=n+0xBEEFDEAD. Mothership part builder 24FFF0 inlines similar arithmetic. No writer of save+0xA7D8 was found by direct offset search; EDF5's spawn-bytecode seed increment should not be presumed present.

Seven constructors use WalkCharacterSyncControl

Static. net::WalkCharacterSyncControl (vtable A97BA0, constructor 1EC170) is constructed by seven functions: 1EC010, 1F5B30, 203180, 20C640, 2150B0, 239490 and 2E2210. This mirrors an EDF5 family but the EDF4.1 callsites have not been matched individually to enemy/character classes, so class-level ownership remains uncertain.

Unresolved UserSync records, cap ownership and reader bounds

Unverified. Open items are UserSync's initial integer and member-record details, whether start message 390BF0's host test applies armor cap solely on host, timeout flag at 38FAB0, and the player table's imul 0x101C readers. Lack of a MissionSync upper-index check is not itself proof of end-to-end memory corruption or an achievable fifth room member.

EDF4.1 hit gate, ownership and lethal-hit batch

Shared GameObjectBase hit gate recognizes network damage forms

Static. 36B3B0 is the sole user of Reject DamageInfo 0x%p, analogous to EDF5 402C00. It is called by GameObjectBase main slot 7 28DB20 across enemy/soldier/vehicle classes and by 109FC0/11BE90 (map-object identity of latter two inferred). Its GameDamageInfo serializer 35D040 is nearby. Rejection semantics depend on the gate predicates below, not on every arbitrary damage message.

Forced hits, registered objects and message rewrite rules

Static. Gate passes all offline and unregistered objects (network part +0x28 absent). Locally owned kind-0 object messages are serialized (36C800) as event type 2; generator release 0x20103 enters family-3 handler 376310. Network forms map 0x4000001→0x80000000 (hit, unwrap info), 0x4000002→0x20100, 0x4000003→0x20101. A hit clears info byte-3 bit 0 and passes when forced bit 6 of info +0x48 is set or the attacker's reference at +0x10 is live. EDF5 uses different info-field offsets.

Missing attacker falls back to the session host test

Static, host classification inferred from IsHost. Without a living attacker the gate calls slot 3 on session object [CC8548]+0x150 or +0x128, selected by active flags +0x148/+0x120; absent session objects permit the event. A false result logs Reject DamageInfo and rewrites the message to dropped kind 0x4000004. This matches EDF5's authority idea, with session offsets 0x60 lower; it does not show that every damaging actor has an owner in all online modes.

Lethal transition marks byte-three kill bit before collection

Static. GameObjectBase handler 28DB80 remembers whether target HP +0x16C was positive, calls damage 28E1F0, and at 28DC0A sets info byte-3 bit 0 only when an initially living target becomes zero-HP or less. Collector 35BD20 skips forced/replayed hits (info +0x48 bit 6) and selects records by byte-3 flags (mask 0x39 and kill bit). Thus the decoded replication path is focused on lethal transitions, not guaranteed streaming of every damage tick.

DamageObject event type 1 batches serialized lethal hits

Static. GameObjectBase main slot 8 10A0D0 (shared by 93 vtables) calls 36BA80 on the network part; for online hit 0x80000000 without forced bit and with registered object entry it uses 35BD20 to append serialized GameDamageInfo through 35D040. Collector lives at game +0x228 (or session fallback +0xD0) and has no EDF5-style net::DamageCollector RTTI name. Special +0x20=-1 registration handler calls 39F4D0 on game +0xC0, still unread.

Per-update collector sort and type-1 event send

Static. Game update 39CE50 tail-jumps to 35C860(game+0x228), sorting pending entries through 35F530 and comparator 35C840 before transmitting event type 1 with session helper 360830. A counter at collector +0x70 counts down from eight (EDF5 has +0x80). This is evidence of sorted batching and an update/send boundary, not measured network packet frequency.

Remote lethal replay, drop owner and local kill statistics

Event_DamageObject receive posts message 0x4000001 per target

Static. Type-1 handler slot 1 360FD0 (vtable AA3D10) selects collector at game +0x228 or session +0xD0, then calls 35C130 to decode a batch, print %x : damage:%f:%d and deliver 0x4000001 to each target. The hit gate transforms that message into the local damage path with forced replay guard.

Received lethal record reconstructs killer ID and forced bit

Static. Record-head reader 35DC30 decodes attacker network ID and resolves it through 39D860 into hit-info attacker reference +0x10, marks status and sets forced bit 0x40 at info +0x48 (35DD2E). Receiver 35C130 calls 28EE10 to set/clamp victim HP between +0x164/+0x168 and clear death flag bit before sending 0x4000001 for replay. The remote event can reproduce death without being re-collected as a fresh local kill.

Dying-object owner drops loot; local killer alone updates saved counter

Static. Damage death 28E1F0 marks object +0x1E8 bit 4; loot-drop route (1AE060) requires owning object (+0xC8 copy bit clear) and eligible +0x1E8 bit 5, rather than EDF5's extra host test. It then sends attacker notice 0x80000002 with hit info and victim through slots 7/6/8. Soldier handler 2B1010 may play an enemy-kill cue, but updates victim-keyed game_object_kill_counter in save only when killer has a local controller +0x1A8. HavokCarBase forwards notices to riders. Owner-drop and local-save updates are different conditions, preventing a remote soldier copy from writing that player's kill counter.

GiantAnt network pacing and remaining EDF4.1 gaps

GiantAnt sends one-byte pose/state mask on variable intervals

Static. GiantAnt NetworkObject writer slot 4 208900 (vtable A98068) emits nothing from remote copies (part+0x18 bit 0) or dead ants (HP part+0xBC). Write counter +0xC10 yields pose interval 40/90 or active 3/12, with minimum 9 in another state. Bit 1 carries pose when changed or forced; object status bit 3 allows state bit 8 every 80 or bit 4 every six, with one additional bit-4 trigger. Unlike EDF5, the EDF4.1 one-byte mask has no timer bit 2 or extended 0x10/0x20/0x40 fields.

Online script mission and room request handler addresses

Static registration only. Request_MissionExit and Request_ExitNetwork both register handler 38DC10; Request_TitleReset uses 38DC00, Request_MissionRestart 38DC20, Request_UpdateRoomInfo 38DB30, Mission_CreateGame 38D980 and Mission_DestroyGame 38DB20. The worker bodies were not traced; common registration does not establish equal results for different request names.

Unresolved soldier read, correction and vehicle replication fields

Unverified. Soldier reader 2B6270, field writer at main slot +0xF0, individual mask field semantics, remote NetworkUpdate correction/checkers, ride events in ReceiveEvent 2B8790 and ReceiveNoteEvent 2A2990, class overrides and vehicle serializers remain to be decoded. EDF5's field layout is a guide, not a mapping for EDF4.1's 0xB0-offset network component.

Remaining insect ownership, hit and random-seed research

Unverified. Seven WalkCharacterSyncControl constructor classes, network families 4/5/7/8, 39F4D0's collector role for +0x20=-1 entries, hit-decision vtable slots 27/28, writers of save seed +0xA7D8, and bullet send routes are not yet established.
