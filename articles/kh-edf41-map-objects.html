EDF 4.1 — Map Objects (community source notes)

EDF 4.1Community Knowledge HubMaps
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Placement

Two-pass EDF4.1 map.mapb loader

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapb-record

EDF 4.1 reads map.mapb in two passes, both from FEF60: FD9B0 -> FF420 builds the Preload_* objects (render units and collision bodies) and FE090 -> 100410 the MapObject_* objects. Both walk the records as EDF5 does (../edf5/map-placement.md#edf5-mapb-record): offset mapb+0x20, count +0x24, stride 0x44; +0x00 def offset relative to the record; position +0x04 / +0x08 / +0x0C (w 1); rotation +0x10 / +0x14 / +0x18 in degrees (x pi AB674C / 180 AB68E4); the def's +0x04 an embedded parameter SGO (checked for "SGO" and version 0x102), +0x0C its name; the map.mapo entry [mapo+0x08] + index x 0x1C.

Basis: fn.py 100410, FF420 and --xref of CBCFAC and of the .mosb strings 9D1198, 9D14A0; the MAPB header of nw_kousoubld01.mac (defs +0x18 / +0x1C, records +0x20 / +0x24)

Addresses (build-specific RVAs unless indicated): FEF60, FD9B0, FF420, FE090, 100410, AB674C, AB68E4

MapObject class dispatch by file extension

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapobject-classes

Classes by the def name's extension, MapObject pass 100410: .mosb -> MapObject_Structure (107AC0 -> 117C60), .mdx -> MapObject_AnimationModel (107C60) or MapObject_Model (107E30) by the same test, .trb -> one MapObject_Tree per record (11D8B0, 0x110 bytes), .mlb -> MapObject_AnyObject (11E870), .shfb -> MapObject_Shf (107FF0, with a .mat). Tree random seed from placement record

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-tree-seed

A 4.1 tree's seed is its record's +0x1C when that is not 0, else the sum of the record's +0x34, +0x38, +0x3C and +0x40 (101049-101061); it goes to the MapObject_Tree constructor with the .trb parameter SGO and the placement matrix.

Basis: fn.py 100410 (101019-1010F1); what the seed draws: #edf41-tree-build (KH chat 143)

Addresses (build-specific RVAs unless indicated): 101049, 101061, 11D8B0

MapObject_Tree transforms and seeded reader

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-tree-build

MapObject_Tree (11D8B0) copies the placement matrix to +0x10..+0x4F and +0x50..+0x8F, seeds its reader with the InitParam's seed (11AE00), and 119E50 reads the .trb with EDF5's 64-bit LCG (x 0x5D588B656C078965 + 0x269EC3, 119EBC, 11A0BC): a yaw rand(0..9999) x 1/9999 (AB63D8) x 2 pi (AB6774) (11A0BC-11A0FB). 11DA33-11DA98 then rebuild the rows at +0x10 from that yaw and keep the translation, as EDF5's E4874-E48A6 do (../edf5/map-placement.md#edf5-tree-build): the record's rotation, the grid's angle and any scale are lost there; the copy at +0x50 keeps them. The model and stump picks were not read.

Basis: fn.py 11D8B0, 119E50, 11AE00; floats read from EDF41.exe

Addresses (build-specific RVAs unless indicated): 11D8B0, 11AE00, 119E50, 119EBC, 11A0BC, 11A0FB, AB63D8, AB6774, 11DA33, 11DA98

Heightfield GrowTree visitor creation

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-grow-walker-shf

On heightfield ground, 116230 builds the MapObject_Shf_GrowTree visitor (vtable A929F8) and 1172B0 walks the grid, EDF5's DDDB0 (../edf5/map-placement.md#edf5-grow-walker-shf) at other offsets: block [[[obj+0x130]+0x50]+0x90] (+0x08 / +0x0C width / height, +0x18 / +0x1C size x / z, +0x4C the grow block {+0x00 cells per step, +0x04 0x28-byte type records, +0x10 16-byte jitters}); 2 bytes per cell {type, jitter index}, 0xFF empty. A cell's x is column x (size x / cells per step) + size x x jitter +0x04 (z likewise with +0x08), turned to world X and Z by the object's matrix (+0x60..+0x98); slot 3 gets (type record, cell, cell index, x, z, jitter +0x00 as the angle); jitter +0x0C is not read. MapObject_Shf_GrowGrasses (116320, vtable A92A20) was not read.

Basis: fn.py 116230, 1172B0 (117430-117511)

Addresses (build-specific RVAs unless indicated): 116230, A929F8, 1172B0, 116320, A92A20

EDF4.1 MAPO per-record layout

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapo-entry

EDF 4.1's map.mapo per-record entry has EDF5's layout (../edf5/map-placement.md#edf5-mapo-entry): 0x1C bytes at [mapo+0x08], count +0x0C equal to the record count on all 18 maps (42,388 records); +0x04 / +0x08 the part-pointer list (count 1 on every .mdx, 1 to 562 on .mosb), +0x0C float 1000 on .mosb, 0 on .mdx, +0x10 / +0x14 a _gr model and .hkt pair on 7,010 records (category 1: 4,323 .mosb and 2 .mdx; category 11: 2,235 .mosb and 243 .mdx; category 6: 145 .mosb and 62 .mdx), +0x18 a second part list on 838 category-1 .mosb records.

Basis: scratch File_Storage/Logs/catalog/mapb5.py edf41 mapo and mapotally (output mapotally41.txt, summed by kh143_agg.py)

Tree and shrub MAPO record differences from EDF5

Preload_Structure MAPO entry reader

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapo-parts

Preload_Structure (127E60) reads its mapo entry with 129AC0 (from 1281E6), EDF5's F1980 (../edf5/map-placement.md#edf5-mapo-parts): the +0x04 list, then the +0x18 list; per part +0x08 a quaternion (to a matrix, 129C7D-129D86), +0x0C a position, +0x10 a vec4 (default 1, 1, 1, 1, AB7F00), +0x20 a model name (parts without one skipped), handed to 1275D0. Its draw distance is the smaller of the entry's +0x0C and the def's +0x1C (12820E-128260), then the +0x18 block's float +0x08 against def +0x1C (1282BF-1282FC). The structure's own part records were not read.

Basis: fn.py 127E60, 129AC0

Addresses (build-specific RVAs unless indicated): 127E60, 129AC0, 1281E6, 129C7D, 129D86, AB7F00, 1275D0, 12820E, 128260, 1282BF, 1282FC

Preload draw-distance scaling and cap

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-map-draw-distance-scale

4.1's map preloads scale a capped draw distance before squaring it: Preload_Structure (12824E / 128258, 1282EA / 1282F4), Preload_Model (1253A2 / 1253AC, 125964 / 12596E; def +0x1C only when over 0.01 at AB644C, else -1, no cap) and Preload_AnimationModel (1236F2 / 1236FC) multiply by C3F27C for categories 2, 4, 5 and 6 (mask 0x74) and by C3F274 for the others. EDF4.1 map-object damage pathway

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapobject-durability

EDF 4.1's map-object damage is EDF5's (../edf5/map-objects.md#edf5-mapobject-durability) at other offsets: the base constructor 109BD0 sets max +0xF0 = current +0xF4 = the def's float +0x18 (-1 without a def; def at +0x118, record at +0x110); damage slot 11 10A220 (after 10A610 and slot 14, which on 1 hands the hit to slot 12) lowers +0xF4 by the hit's float +0x40, clamped to [0, max], only with hit flag +0x48 bit 0 or a category in mask 0x74 (2, 4, 5, 6); 109F10 rules the collapse (flags 0x04 / 0x08, a mask category hit with flag 0x02, or durability <= 0); slot 15 109F90 makes max <= 0 and category 3 undamageable.

Basis: fn.py 10A220, 109F10, 109F90, 109BD0 (stores to +0xF0 / +0xF4); flag meanings by analogy with EDF6; not run in game

Addresses (build-specific RVAs unless indicated): 109BD0, 10A220, 10A610, 109F10, 109F90

On a hit that changes the durability or collapses the object, 4.1's 10A220 calls slot 12 (+0x60)

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-mapobject-collapse

On a hit that changes the durability or collapses the object, 4.1's 10A220 calls slot 12 (+0x60); on the collapse it posts the record's child list ([rec+0x2C]) through 102D70 (manager [CC84F8]) and zeroes +0xF4. Unlike EDF5's CF660 (../edf5/map-objects.md#edf5-mapobject-collapse), no +0x120-style "collapsed" byte is stored before slot 12.

Basis: fn.py 10A220 (10A2CF-10A33B)

Addresses (build-specific RVAs unless indicated): 10A220, 102D70, CC84F8

Grown trees lack durability in EDF4.1

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-tree-falls-any-hit

Grown trees have no durability in 4.1 either (../edf5/map-objects.md#edf5-tree-falls-any-hit): MapObject_Tree is not a MapObject_Base class, its slot 2 is B3630 (always 1), and MapObject_Trees' check slot 10 11CB10 and slot 12 11CD50 call the struck tree's slots 2 and 3 with no damage test. Tree slot 3 11E770 fells it like EDF5's E5350 (11DE70 turns the hit into a fall, +0xF4 halved by AB656C) but builds no new body. So the .trb defs' durability 10 / 100 is not read by the tree.

Basis: fn.py 11E770, 11CB10, 11CD50; vtables A92DC8, A92E08 with vt_dump.py

Addresses (build-specific RVAs unless indicated): B3630, 11CB10, 11CD50, 11E770, 11DE70, AB656C

EDF4.1 collision layer differences from EDF5

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-map-collision-layers

EDF 4.1's map collision layers differ from EDF5's numbers (../edf5/map-placement.md#edf5-map-collision-layers): Preload_Model (125BB2-125C5B) and Preload_AnimationModel (12340F-123491) put category 3 on layer 15 (0xF), categories 2 and 4 to 6 on 17 (0x11), 10 on water (122F00, no body) and the rest on 13 (0xD), through 114380; 148BA0 then takes a second value per layer (0 for 17, 3 for 15, 2 for 13; meaning unread). EDF5's map is 3 -> 17, 2 / 4-6 -> 20, others 15.

Collision, CrashModel and map-port geometry

These source IDs reconcile novae (ajane)'s EDF4.1 build steam-57aab039 static analysis with BarteY's 4.1→EDF6 map-port offline measurements. A converted asset, geometric candidate, pathing hypothesis and a game-tested result are distinct levels of evidence; no fresh runtime tests were performed for this release.

Collision filtering and CrashModel lifetime

Static · novae: constructor EBC70 initializes Havok collision layers 1–27 to collide with layer 0 and then enables 118 additional layer-pairs through 5E7050. The source's full pair census distinguishes layer 11 (bullet stop query: map 13/15/17) from layer 10 (hit query: layers 5–8 and 12). Layer 27 has no extra partner; 28–31 retain an unexamined initialization from 5E6F90. This EDF4.1 table is not interchangeable with the EDF5/6 collision masks; a second constructor-like function EC530 remains unread.

Static · novae: CrashModel constructor 10D340 chooses detail level 0–4 at +0x238 using the nearest of four cameras, base distance breaks 27/50/90/200 m and adjustments for InitParam flags and global part pressure. Flag +0x84 bit 0x10 forces level 4; more than 50 or 160 global pieces can move lower levels to 3 or 4. The level is a runtime choice, not a number encoded identically in all debris assets.

Static · novae: levels 0–1 use piece counter CBCFB0, levels 2–4 CBCFB4, declining to make bodies when their counter is already over 300 or 800; each body increments global CBCFB8. Levels 3/4 within 180 m take another box-query branch (20,0,20 size and 800 constant) that was not fully analyzed. These controls parallel EDF5 while having distinct addresses.

Static · novae: 139B10 writes a full 4×4 draw transform to a body node at +0x80..0xBF, optionally applying node-local scale/offset and propagating through children at body+0x278. A fragment-following marker in 4.1 should use this matrix; EDF5's corresponding pathway writes a separate quaternion and position. Copying EDF5 node offsets blindly would be wrong.

Static · novae: body update 111AB0 classifies rest by velocity and frame count (>90 or a second count reaching 3), then when the group flag permits sinking writes collision-body field +0x4C=27 (layer inference), moving down 0.02 per tick or 0.001 if already layer 27. It finishes after falling >10 m below start y or after a level-dependent wall timer (2500/1500/1000/700/400 seconds for levels 0–4). Whether EDF5 has that timer was not checked.

Static · novae: CrashModel update 110920 iterates 0x10-byte entries in its +0x1B8 body list, ticks children and drops completed bodies while decrementing counters. Once more than 95% have rested, it sets +0x221 to authorize coordinated sinking. At zero bodies it sets +0x222 and destroys the parent after its effect completes. Thus the body's own rest threshold is not the whole debris-group completion rule.

Static · novae: Structure damage slot 117FE0 distinguishes hit parts from root via 117FA0: non-root hits break eligible 0x38-byte part records through 118BF0 and skip overall durability; root hits call the base damage path. Collapse slot 118130 breaks all eligible parts and then root. 118BF0 seeds a break record, queues it through the structure's record system and closes it; physical fragment creation is downstream.

MAPB/MAPO, MAD collision bodies and HillyCity conversion

Static offline census · BarteY: in nine non-SK 4.1 cities, 39,252 MAPB placement records included 17 group owners and 169 distinct child indices, without a shared child or nested owner; five owners/40 children belonged to NW_HILLYCITY_LIGHT, ten/126 to NW_KOUSOUBLD01. Another 16-map census reports 18 groups/193 links with a different denominator; do not sum them. Linked indices do not themselves prove parent-transform or collision activation. MAPO-to-MAD lookup saw 5,944 explicit mesh-body names, 5,469 def-based matches, 145 compact-shape references and 27,694 unmatched references; unmatched is not evidence of absent collision.

Static offline port resolver · BarteY: 40,920 nonempty MAPO collision references included 27,018 natural base.hkt/base_hk.hkt pairs, 420 literal/base matches, 12 special station-window slots, 1,945 direct list/MOPP body bindings and 3,988 pair-alias matches. The resolver bound 33,383 references and deliberately left 7,537 unresolved, including nine MOPP-over-extended-mesh aliases (1,858 references). These are the tool's resolution counts, not a proof that the EDF4.1 runtime ignores unmatched bodies.

Static conversion measurement · BarteY: source NW_HILLYCITY_LIGHT MAPO is 3,034,994 bytes, a 0x58 header with 44,213 object rows of 0x38 bytes; EDF6 uses a 0x60 header and 0x3C rows for the comparable table. This alone shifts following offsets by 8 + 44,213×4 = 176,860 bytes. The author's converted MAPO is 6,816,056 bytes with extra T58 and T50 structures; its whole MAC is 7,872,840 bytes, a size previously misreported as MAPO. Its 8,980 T50 outer records have no edges in this sample; other native EDF6 maps do have collapse links.

Static geometry experiment · BarteY: a four-tile HillyCity navmesh baseline had 1,562 vertices and 2,928 triangles. An offline carve of 277 triangles under static bodies left 2,651 and produced an 18,040-byte NVMD plus 381,544-byte LOW/HIGH HKT. Its census contained 65 groups, 1,405 placements and 4,971 body footprints (filter max_xz ≥ 5.75 m). A previously targeted 381,512-byte output was not reproduced naturally: the closest was 32 bytes larger. The carved navmesh had no EDF6 agent/pathing validation.

Offline state plus modified-game observations · BarteY: all sixteen 4.1 map families initially reused native EDF6 donor HKT/NVMD despite mismatched source terrain; reported allies/enemies snagged or detoured, particularly underground. Only HillyCity has a source-derived navmesh pilot, itself not gameplay tested. Its body-footprint reconciliation yields 4,994 pre-dedup instances minus 23 semantic removals = 4,971; natural area ranking instead yielded 5,026, and one bus-body mesh remained unparsable. Seven SK heightfield maps use conservative material/winding-preserving splits, while nine others require strict Havok 2014→2020 MAD conversion with rejection of unrepresentable shapes. Port-specific results do not establish original EDF4.1 AI behavior.

SK heightfields, vegetation and geometric contact candidates

Static parser · BarteY: the seven SK_* source maps store terrain as <model>_fld2mgrid.shfb. Header fields include 1001×1001 samples, 2×2 m cell size, 33 blocks of 32 cells, height bounds, material/blend pools and packed heights. Each grid point is a half-float elevation plus a strongest-material u16; world placement is origin + (column×2, height, row×2), with rows along Z. Source terrain triangles use diagonal A-B-D / A-D-C; transposing rows or flipping diagonals breaks alignment/contact. SK_HEIGEN02 ranges roughly -10.2266 to 47.25 m in the decoded sample.

Static port parser/census · BarteY: SHFB vegetation uses 0x28-byte records of kind 1 (grass/flower) or 2 (model). SK_HEIGEN02 yielded 202,275 grass/flower, 1,820 tree, 714 bush and 853 small-object instances in the conversion sample. Adding the EDF6 reader's first-rule zero field and rebuilding depth-first SGO made two 4.1 .trb trees byte-identical to native EDF6, with .mlb unchanged. Wire RMPA routes refer to MAPB +0x7C point-pair entries; coordinate matching found 156/22/140 links in three named maps and two unresolved. Repairing RMPA alone does not prove rendered wires reappear.

Static offline geometry census · BarteY: seven SK maps yielded 1,770 recognized static-object placements with 505,633 placed source triangles; 1,766 placements were wholly covered by heightfield bounds and four partly outside (two crater roads, valley water and road). One valley bridge is a child of a linked MAPB owner, explaining an earlier flat-walk omission. Of 265 SK_HEIGEN02 MAD static placements, 166 source meshes tested as closed 2-manifold solids and 99 as open surfaces; a 0.45 m radius, 1.8 m high capsule on 4 m cells flagged 243 closed-solid candidates and 495 open-surface hints. These geometric labels are not game agent collision or pathing results.

Static offline contact diagnostics · BarteY: 81 selected placements generated 28,956 unique sampled edges and 4,673 terrain intersections; 14,838 source triangles crossed 46,606 terrain facets, yielding 5,020 raw segments and 151 closed-loop/787 open-chain contours. Full 505,633-triangle pass reported 147,094 facet-intersection observations. Four partly outside placements were clipped from 6,040 triangles into 10,179 welded segments with 100 seams. The chosen A-B-D/A-D-C terrain diagonal matters; none of these segment/loop counts is a measured Havok contact, pathable region or agent obstacle.

Static local case test · BarteY: sk_rockm01 (172 triangles, 14 boundary edges) is open and generated two open-surface hint cells; sk_rockm02 (96 triangles, zero boundary edges) is a closed-manifold candidate with one interior-positive 4 m cell at (241,202). The 243 closed-solid candidate cells in the broader census combine 158 point-in-solid cells and 85 segment-proximity additions. A watertight-edge test is not a self-intersection proof and does not determine the game's actual blocking or navmesh policy.

Provenance: novae (ajane)'s native EDF4.1 engine analysis; BarteY's R3 map/nav/Havok conversion and offline geometry case studies. The same source-record boundaries allow map porters to distinguish byte layouts, inferred runtime edges, geometric candidates and tested in-game outcomes without merging them into one unsupported success claim.

EDF4.1 original MAD collision-body census

Source edf41/map-collision.md, static file-level Havok 2014 and native reads in the Knowledge Hub. Serialized state is not equivalent to runtime activation or collision-layer assignment.

18 original maps and 18,520 root collision shapes

Evidence: static · Fact ID: edf41-mad-root-shape-census

The 18 original EDF4.1 map .MAD Havok 2014 Binary Tagfiles contain 18,520 serialized hkpRigidBody entries and one hkpPhysicsSystem per file. Their root-shape classes are hkpListShape 16,301; hkpMoppBvTreeShape 1,608; hkpConvexTranslateShape 168; hkpConvexVerticesShape 164; hkpConvexTransformShape 156; hkpBoxShape 90; hkpCylinderShape 32; hkpSphereShape 1. Each file record has active=1, but that does not prove all bodies were registered in a running Havok world. Counts concern root shapes, not child shapes or triangle primitives.

Serialized motion values 5, 3 and 2

Evidence: static · Fact ID: edf41-mad-motion-type-census

Of the 18,520 body rows, hkpMotion.type is raw value 5 in 17,660, value 3 in 849, and value 2 in 11. The source does not assign official names to these numeric enum values. The 860 bodies marked 2 or 3 need a separate activation check before treating all their geometry as fixed obstacles.

Fifteen motion/root-shape cohorts

Evidence: static · Fact ID: edf41-mad-cohort-census

Motion 2 has eleven list shapes. Motion 3 splits into list 790, convex transform 31, convex vertices 17, cylinder 6, convex translate 4 and MOPP 1. Motion 5 splits into list 15,500, MOPP 1,607, convex translate 164, convex vertices 147, convex transform 125, box 90, cylinder 26 and sphere 1. Together these are fifteen distinct (motion value, root shape) cohorts; their serialized bodies lack collision-filter fields.

CollisionFilterInfo field absent, not zero

Evidence: static · Fact ID: edf41-mad-filter-info-absent

Although EDF4.1's Havok type registry declares hkpTypedBroadPhaseHandle.collisionFilterInfo, that serialized field is absent in all 18,520 map bodies. Their broadPhaseHandle.type=1 is the handle type, not collision layer 1. Neither zero nor EDF5 layer values should be substituted for this missing field; runtime filtering must be read from the separate CollisionFilter table rather than inferred from the MAD dump.

Placement identities and semantic overlap

Evidence: static · Fact ID: edf41-hillycity-identity-audit

Across the 1,405 selected HillyCity T2 placements, no two share a GUID, a raw placement core after excluding GUID, or the tuple of parent/transform/group-set identity. Map placement pose and ray filter behavior

EDF4.1 T2 pose layout across MAC relayout

Evidence: static · Fact ID: edf41-mapb-pose-fields

EDF4.1's map.mapb T2 placement record is 0x44 bytes, while EDF6's is 0x48 due to four appended bytes. Both store translation floats at +0x04/+0x08/+0x0C and Euler degrees at +0x10/+0x14/+0x18. Matrix builders FF420 (EDF4.1) and 1169B0 (EDF6) convert to radians with arithmetic consistent with row-vector Rx × Ry × Rz. Six pose-float fields across all 42,388 placements in 18 MAC files are byte-identical after layout conversion, which is not a bitwise audit of matrix evaluation or floating-point runtime results.

Spawn-point ray uses layer-19 collision filter

Evidence: static for native filters; effect on enemy spawning inferred · Fact ID: edf41-map-ray-filter-spawn-ray · Build: steam-57aab039

Of thirteen native hkpWorld::castRay sites through 602FD0/6030D0, ten pass filter info 0x13 (layer 19), including spawn-point ray 14D0F0; one passes 0x14 and two pass zero. Layer 19 intersects layer 13 under the inspected filter matrix, explaining why Earth Eater panels can be hit as ground by spawn and climb probes. The spawn-point function casts downward first from one meter above the drop point, then from its hit point or selected height toward -1000. Actual enemies spawning or climbing those panels is an inference, not a fresh runtime observation.
