GST and MST save/progress tables — reference boundaries

UniversalFormats & ContainersFile FormatsEDF 4.1EDF 5EDF 6
Source-backed research / case study · Reference only

The retained save-format research is useful for inspection and compatibility diagnostics, but it is not a license to treat EDF4.1, EDF5 and EDF6 save structures as byte-identical.

GST

The historical GST reference records the same encryption IV/keys across EDF4.1–EDF6. That is an encryption-layer observation only; it does not prove complete structural parity.

The retained format notes contain many offsets for armor/progress/stat counters and identify a large weapon-stat table. A reconciled summary records 2,068 entries × 0x0C bytes for that table. Individual entries are documented as carrying an ID/index-like field plus eight one-byte stat-level values, but some older field labels remain tentative.

Some raw notes label the EDF6 GST/DAT version as “3?”; the question mark matters. Do not turn that annotation into an exact cross-version conversion rule without a fresh paired-save audit.

MST

MST is documented as a Mission Save Table. In the retained EDF6-oriented layout:

  • version field is at +0x04 and historically annotated 3?;
  • Ranger mission table: +0x1C, size 0x200;
  • Wing Diver: +0x21C, size 0x200;
  • Air Raider: +0x41C, size 0x200;
  • Fencer: +0x61C, size 0x200.

Each class chunk uses additive difficulty bits per mission:

Difficulty Bit
Easy 0x01
Normal 0x02
Hard 0x04
Hardest 0x08
Inferno 0x10

Later parts of the documented MST include lobby/password and unknown fields, but those unknowns remain unknown.

Save-format conversion evidence boundary

The corpus does not establish a general EDF5→EDF6 MST or GST binary conversion rule. A mistaken association between mode identity, mission-pack namespace and save fields can change the resulting progress state. Any hypothesis about on-disk compatibility requires version-specific verification; a modified-environment experiment is not evidence that the original game rewrites progression in the same way.

The live package namespace is separate from the MST file layout

In the studied EDF6 manager, the native package materialization path included an MSVC std::wstring-style package/MST namespace at active Package+0x68, while the active Package object itself was held at manager +0x130. Those are live-memory layout observations, not fields at on-disk offsets 0x68 and 0x130 in .MST or .GST files. Confusing the two would produce a false save-format specification. See native mode and Package memory. A real modified-runtime test that injected an extra mode transition resulted in saved progression loss; this is a bounded integration regression, not a property of the unmodified save format.
