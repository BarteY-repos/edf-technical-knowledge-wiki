EDF 4.1 — Rendering (community source notes)

EDF 4.1Community Knowledge HubShaders
Source-backed research / case study · Contributed research; per-claim static, verified, unverified; not independently re-tested

This is a source-attributed research appendix, not a chronology or a replacement for topic reference pages. The observations were contributed in the EDF Knowledge Hub export, snapshot 2026-11-14, revision 54f89cd, compiled by novae (ajane).

Read each statement with its evidence grade and exact build. Verified means a reported game test, static means reverse engineering or source inspection without a reported game test, and unverified is a hypothesis. None of these observations was newly tested for this wiki release.

Observations

EDF4.1 anti-aliasing pixel shader

Evidence: static · Build: steam-57aab039 · Fact ID: aa-pixel-shader

Anti-aliasing: a pixel shader drawn every frame just before the UI is 0x448 bytes of DXBC at A6A120 (.rdata, 0x5E4 past the descriptor 04 00 00 00 48 04 00 00 E4 05 00 00 at A69B3C); it is created at 55BE8D (rcx = bytecode, rdx = size). Without a patch the game's anti-aliasing setting only smooths the HUD in normal play. metoxys's AntiAliasing swaps in a 0x1924-byte shader that keeps the original's work and adds post-process anti-aliasing modeled on EDF6's shader at that place (chosen over EDF5's as better optimized; about 187 instruction slots).

Basis: the patch's anchors (unique) and hook code; the shader blob is in the patch file

Addresses (build-specific RVAs unless indicated): A69B3C, A6A120, 55BE8D

Attribution: metoxys (AntiAliasing), novae (ajane)'s EDF 4.1 outside set · 2026-10-16

Reflections: environment maps are 1024x1024 without mip levels (metoxys)

Evidence: static · Build: steam-57aab039 · Fact ID: reflection-compute-shader

Reflections: environment maps are 1024x1024 without mip levels (metoxys); the reflection compute shader is DXBC at C477E0 (.data, 0x2C24 bytes) and is created at 550034. metoxys's ImproveReflections swaps in a 0x45CC-byte shader: an angle-dependent 25-tap blur, sharp head-on and smeared, colored reflections at glancing angles.

Basis: the patch's anchors (unique) and hook code; what the shader is: lighting-cs-global-cubemap

Addresses (build-specific RVAs unless indicated): C477E0, 550034

Attribution: metoxys (ImproveReflections), novae (ajane)'s EDF 4.1 outside set, novae (ajane) · 2026-10-16

Deferred-lighting reflection shader correction

Evidence: static · Build: steam-57aab039 · Fact ID: lighting-cs-global-cubemap

The "reflection compute shader" at C477E0 is the whole deferred-lighting compute shader (the variant with sun shadows; shadowless variants at C4A410 and C4D0A0), and its reflections come from one global environment cubemap (g_xgl_compute_environment_map); EDF 4.1 has no local cubemaps and no screen-space reflections anywhere in the exe (no blob binds Hi-Z, intersection or SSR names). Inputs t0 g_albedoRGB, t1 g_specularRGB, t2 g_normalXYZ, t3 g_smooth_reflection_specpow, t4 g_light_accumulate, t5 g_specular_accumulate, t6 g_depth, t10 g_xgl_compute_environment_map (TextureCube), point-light arrays sbuf11-14, t15 g_shadow_depth (only C477E0); outputs uav0 g_color_out, uav1 g_view_z_out; cbuffers xgl_system (b0), xgl_ren_compute_lighting_setting (b2). A full-screen PS at file offset C505D0 also samples g_xgl_environment_map with the G-buffer.

Basis: RDEF of all 131 DXBC blobs in EDF41.exe read with a small reflection script; not run in game

Addresses (build-specific RVAs unless indicated): C477E0, C4A410, C4D0A0

Attribution: novae (ajane) · 2026-11-03

Deferred base-color pixel shader output

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-material-base-color-output

In EDF 4.1's SND_MECH.SGO and SND_CHARA_2COLORCHANGE.SGO Deferred pixel shaders the base color output is o0.rgb = b (albedo x diffuse, unchanged by the reflect term), o0..o3 are written (4 targets), and the reflect term f (reflect.R x the view-dependent fall_off_* factor) goes to o3.y with the texture-weighted specular_pow in o3.z. Stock materials: Vehicle301_tank.mdb / Material9 uses snd_Mech (specular_pow 100, fall_off_amount 0.3, fall_off_scale 0.2, fall_off_offset 0.1); Engineer.mdb / metal in ARMYANDENGINEER.MRAB uses snd_Chara_2ColorChange (60, 0, 0, 0.08); Hector301.mdb / ufosurface uses snd_UFO_LightScroll (100, 1, 0.7, 0.2). EDF6 differs (crosswalk/deferred-lighting-reflections.md).

Basis: the author's disassembly of DX11.cpk's shaders with D3DDisassemble (SND_MECH sha256 efe70b69cda0ea26330b1065b508f2529b3368f06ac06ca54fb44d1a27cda934, SND_CHARA_2COLORCHANGE 7a12f60be7e4cefa9594641f47efa41d1843b1e613fe039fbc962c63685af3df) and their read of the three archives; the build id is the hub's EDF 4.1 build, the note names none

Attribution: hajisensai, All Forces source docs/edf41-material-shader-contract.md (round 24) · 2026-11-07

Original research (pinned): hajisensai — docs/edf41-material-shader-contract.md

Debug LOD distance scaling command

Evidence: static · Build: steam-57aab039 · Fact ID: lod-distance-scale-command

EDF 4.1 keeps a debug script command set_lod_distance_scale(string kind, float s) (registered at C25B5, handler BDD40) that writes seven load-time LoD distance scales at C3F270..C3F288 as s + (1-s)*K; all seven are 1.0 in the file image and nothing else writes them. The kind "chara" writes only C3F288, which the character model loader multiplies into each squared LoD threshold (320D28), so the distance factor is its square root. K is 0.1, 0.5, 0.4, 0.2, 0.3, 0.3 for the six other globals and 0.2 for "chara"; a data patch changes the floats at file offset C3D470..C3D488. EDF5 and EDF6 do not have this command string.

Basis: novae (ajane); not run in game

Addresses (build-specific RVAs unless indicated): C25B5, BDD40, C3F270, C3F288, 320D28

Attribution: novae (ajane) · 2026-11-04

EDF4.1 effect generator mapping for porting

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-effect-generators

EDF4.1 depth conventions

Dormant reversed-Z switch in the commander's view block

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-depth-compare-flag.

The Umbra commander's view-block flag at +0xA0 (commander +0x120) switches the depth compare from 4 (LESS_EQUAL) to 7 (GREATER_EQUAL) in 57A190 and its callback 57A6B0. It also selects the clear value: 1.0 in the stock direction, 0.0 in reversed-Z (57A452 / 57A47B). Constructor 573F30 initializes the flag to zero at 574078, and the source's code scan found no subsequent commander write. This is a dormant code path, not evidence that EDF4.1 actually renders with reversed Z.

Basis: source static disassembly and store scan.

Depth-reading shaders assume a 1.0-depth sky

Evidence: static · Build: steam-57aab039 · Fact ID: edf41-depth-sky-tests.

Six executable DXBC shaders treat 1.0 as the sky: deferred-lighting compute shaders C477E0, C4A410, C4D0A0, depth-to-view-Z compute shader C5ADF0, and light pixel shaders C511F0, C545E0 (the last pair discards beyond 0.9999). Under reversed Z the sky is 0.0, so changing the depth-function toggle alone would break these branches. All six would need an appropriate comparison/literal change plus valid DXBC container checksums; this is a proposed compatibility route, not tested in game. EDF4.1's DX11.cpk particle/decal material shaders were outside the source audit.

Basis: disassembled executable shader blobs in the source; no runtime reversed-Z modification.

D3D11 render targets and scene projection

Float32 depth target and attachment formats

Static, steam-57aab039. Allocator 56A3C0 builds two R16G16B16A16_FLOAT targets at +0x50/+0x80 (SRV/RTV/UAV), one R8G8B8A8_UNORM at +0xB0, and depth at +0xE0. Depth texture is R32_TYPELESS (DXGI 0x27) with SRV/DSV binds, DSV D32_FLOAT (0x28), shader view R32_FLOAT (0x29), one sample and one mip; thus no stencil or MSAA depth format. Plain texture creators 521C60/521B40 call D3D11 texture and relevant SRV/RTV/UAV creation slots. The caller that makes this the main scene target was not traced.

Actual ClearDepthStencilView sites

Static call-site audit. Twenty-five executable call sites resemble vtable slot +0x1A8, but only three are actual D3D context clears: 57A452 and 57A47B in Umbra step 57A190 (flag-dependent), plus 57A763 in callback step zero (always depth 1.0, constant AB6644). The other matching vtable calls, e.g. 34743F/38CA91, dispatch on game objects and are not D3D depth clears. DSV clear flags are 3 in these sites, even though the texture itself has no stencil plane.

Perspective builder uses standard Z

Static. 51B230(out,fov,aspect,near,far) builds right-handed Direct3D standard-Z with depth 0 at near and 1 at far, z row -far/(far-near) and -near*far/(far-near). Scene camera defaults near 0.1, far 1000; map FarClipZ affects far. The standalone builder alone does not establish what projection is handed to the scene: the Umbra route below supplies that separate missing link.

Umbra viewer writes scene view/projection matrices

Static. xgs::umbra::Commander vtable AB1028 and callback 57A6B0 are installed by 579CC0/5740A0; the commander lives at [CC89D0]+0x10. View step 57B282 (default switch +0x123=1) calls Viewer::getProjectionMatrix(m,3) at 57B341 and getCellToCameraMatrix at 57B34E, applies a pi-based rotation, stores view matrices +0x280/+0xA0 and projection +0x2C0/+0xE0 and hands block +0x80 to 574550. A reversed-Z conversion would need to alter the drawn projection's z row after the Umbra call, preserving its culling matrix. The meaning of argument 3 was not decoded; no projection patch was tested.

Blend, depth/stencil and rasterizer cache layout

Static. Renderer 531830 flushes cached D3D11 blend descriptor at +0x5C (RT0 mask +0x80), depth/stencil descriptor +0x178 (write mask +0x17C, DepthFunc +0x180, initialized to LESS=2 by 531756), and rasterizer descriptor +0x1B0 (fill/cull +0x1B0/+0x1B4). Dirty bits at +0x58 mark blend (1/2), depth (4), rasterizer (8), topology (0x10); missing descriptors are created through device slots +0xA0/+0xA8/+0xB0 and depth state bound through context slot +0x120. The Umbra commander's step addresses are 0x20 further than this struct. A code scan found no additional renderer CreateDepthStencilState routine beyond 531A07; existing dormant compare-flag entry above covers its commander writers.

Depth-reading shaders, light fog and environment

Depth reconstruction depends on inverse scene projection

Static RDEF/DXBC disassembly. Eight of the 131 EDF41.exe shader blobs read scene depth, plus depth-to-view-Z shader C5ADF0's g_src. Reconstruction in lighting shaders uses xgl_system.g_xgl_view_projection_inverse (cbuffer0 rows 16–19), visible in shader variants including C4D0A0 and C523D0; it follows the written scene matrix instead of an independent hard-coded camera. The existing sky-depth special cases above remain additional reversed-Z patch requirements.

Opaque deferred fog from reconstructed distance

Static shader analysis. Deferred lighting variants C477E0/C4A410 calculate distance d from depth/inverse projection, then f=saturate(d*g_xgl_fog_mul+g_xgl_fog_add)*g_xgl_fog_color.w and lerp(lit,g_xgl_fog_color.rgb,f). Alpha is 1-saturate((d-cb2[0].z)/cb2[0].w); when distance reaches z+w, the sky color cb2[1] replaces scene output. Variant C4D0A0 instead scales lighting by 1-f, without mixing fog color. The examined EDF4.1 path lacks ambient-occlusion input; neither formula proves runtime postprocessor parity.

Single global cubemap, no EDF5-style local array

Static strings and LightEnv parsing. 103C80 reads EnvmapTexture, with no EnvmapArea; EDF41.exe lacks local_cubemap, create_cubemap_parts and load_local_cubemap_array string routes. Its sole located cubemap command is cubemap_mode_set. This is evidence for an EDF4.1 global envmap pipeline, not support for EDF5/EDF6 map-placed local cubemap behavior or proof that no unseen binary-only route exists.

Skinning, UV scroll and render-resource ownership

LoD phase draws consume swappable bone pose arrays

Static. AnimationModel vtable slot 0 322E40 takes the selected LoD instance at [lod+0x58] and, before each phase 0–3 draw, calls 50B070(inst,ctx,inst+0x28) to apply bone records spaced 0x100 (list count at inst+0x10, inverse bind at record +0x20) to draw-pose entries [pose_list+8]+i*0x40; mesh draw then enters 50C150. Bone lookup 50B210(inst,wstring*) linearly scans names rather than EDF5's name map. Weapon ModelConstraint resolves bone at weapon+0xAE8. A draw hook may swap pose per phase, but the author did not find the pose writer or perform a runtime swap.

SGO material_animation versus explicit scroll-light helpers

Static reference scan. About 160 class setup sites read material_animation SGO keys and hand them to 32F9E0 (inner record fields unread); Hector weapon construction 225560 is one. A separate route looks up scroll_light0/scroll_light1 using 32FEF0 and updates them in code: Flying Vehicle 2802E0, ufo401 2861E0, carrier 24CCF0, mothership pieces; Deroy uses deiroi_mat_uv_scroll, tank scroll_texture for its tracks. Whether the Hector body reads material_animation remains open; no matching SGO was inspected in this pass and no live UV-scroll test.

D3D11 xgl resource ownership differs from EDF6

Static RTTI. EDF4.1 has the xgl::gs D3D11 shader layer (pixel shader template vtable AB0730, vertex AB0770, compute A93188) but uses sgs::ut::SmartPtr for graphics resources as EDF5 does, whereas EDF6 uses std::shared_ptr. No EDF6-like efs/atf classes were found in this EDF41.exe RTTI census. An effect-system port must handle ownership and ABI differences; class-absence scans alone are not an executable port or test.

EDF4.1 SceneCamera and player camera structure

Source edf41/pause-free-camera-post.md, Steam build 57aab039. Static native camera findings; fields described as inferred retain that scope.

SceneCamera FOV, view matrix and attachment fields

Evidence: static · Fact ID: edf41-scene-camera-fields

xgs::game::SceneCamera (constructor 56F0C0, vtable AB0D38) stores base and vertical FOV at +0x10/+0x14 (initially π/4), near/far +0x18/+0x1C (0.1/1000), view slot +0x50, viewport rectangle +0xE0..+0xEF, Umbra camera +0xA0, HUD/2D gate +0x150 and attachment list +0x158. Matrix rows +0x170..+0x1A0 represent right/up/forward/eye. GameCameraBase (vtable A92040) adds an identity 3×3 at +0x1D0 and camera control state +0x1B0..+0x250.

View slot, weak camera and followed character

Evidence: static · Fact ID: edf41-camera-character-chain

Weak handle lock B29D0 uses a control block with strong count, weak count and object pointer at +8, unlike EDF5's MSVC-style pair. View slot 0 begins at system [CC8528]+0x1D8, each slot 0x258 bytes apart. Its camera is obtained from the slot's weak control block; CharacterGhostCamera follows the character through its own weak pointer +0x260. Camera rows +0x170..+0x1A0 give pose/eye, while copied character rows +0x60..+0x9F suggest character position +0x90 (inferred).

CharacterGhostCamera input, FOV and state step

Evidence: static · Fact ID: edf41-player-camera-step

CharacterGhostCamera (vtable A91E18), step slot 4 DF230, locks the followed character and copies camera-related character blocks: pose to +0x270, additional target state to +0x2B0, a character byte to +0x2F0 and zoom to +0x310. Vertical FOV becomes π/4 ÷ zoom. The state machine at +0xAA0 computes view rows and 2D gate; an optional GameDataMgr flag applies the camera's 3×3 transform, and another gates shake/vibration fields. Rows and FOV are finalized by DF424; option semantics beyond those gates remain inferred.

Pre-step pose copy used by render step

Evidence: static · Fact ID: edf41-camera-prev-pose

Before step DF230, CharacterGhostCamera slot 3 DEC40 copies live rows +0x170..+0x1AF to previous-pose area +0xA50..+0xA8F and float +0x3E8 to +0xA90. Render slot 5 E0E80 reads both previous and current matrix rows and the previous float. The precise destination of a matrix built from the previous pose was not traced, so this is a known temporal data path rather than a proven interpolation formula.

HUD/2D camera switch and scripted look-at

Camera byte gates per-view 2D/HUD draw

Evidence: static; HUD interpretation inferred · Fact ID: edf41-camera-2d-switch

Camera byte +0x150 gates view draw 5714D0. When zero it skips 2D rendering; otherwise it draws the camera's own slot 5 and each attached list entry's slot 3. The player-camera state step DF5B0 recomputes this byte every update: zero if copied character flag +0x2F0 is set and scripted-look activity +0x251 is zero, else one. Directly writing zero is temporary; the next state step can overwrite it. The flag's full gameplay meaning was not decoded.

Scripted shake and look-target message flow

Evidence: static for callback; custom-call ID inferred · Fact ID: edf41-script-look-camera

CharacterGhostCamera message callback EB740 handles 0x80000018 (shake), 0x80000019 (priority-gated look start with target point and frame count), and forwards 0x8000001A to HUD attachments. Its update decrements remaining look frames even without a local pause test and flags active look at +0x251. Script sender 14F660 converts a duration float to frames at 60 Hz; its exact BVM custom-call ID is only tentatively identified as 420 from neighboring dispatch patterns. No separate area-target form or explicit end message was observed. Active look keeps 2D drawing enabled under the condition above.

EDF4.1 built-in debug FreeViewCamera

Retail FreeViewCamera class and pause-on-creation

Evidence: static · Fact ID: edf41-free-view-camera · Build: steam-57aab039

The retail executable retains FreeViewCamera (vtable A91F60, size 0x4D0, constructor E7070, update E7CC0, slot-7 cleanup E9350). It derives through GameCameraBase and SceneCamera, binds 18 named inputs, derives starting eye/angles from its pose rows and builds a Havok controller at +0x438 on layer 0x1B. Constructor sets local pause flag +0x436 and System pause bit 1, freezing ordinary world simulation immediately; cleanup clears the bit. FOV starts at π/4. The debug ray-result and related helper object fields were not fully decoded.

Console command free_camera and view-slot allocation

Evidence: static · Fact ID: edf41-free-camera-create

Debug-console free_camera handler BAA90 accepts view-slot and input-device integers below four, reads view 0's current camera pose, then invokes E9540. That helper rejects creating another free camera if any of four player-camera lists already contains one. It builds InitParam with copied pose, slot, viewport and device, allocates the 0x4D0-byte object and registers it with the system through 568AF0. The precise subsequent view-to-camera switch was not followed, so command registration alone does not prove a specific on-screen UI activation path.

Eighteen named controller bindings and pulses

Evidence: static · Fact ID: edf41-free-camera-bindings

5600A0 binds each named input from a selected controller device, using records 0x18 bytes long. Inputs cover both stick axes, both triggers, both stick-press buttons, LB/RB, directional Up/Down and face buttons A/B/X/Y plus Start/Back (offsets +0x260..+0x3F8). Analog value appears at record +0xC, held/pressed/released at +0x10/+0x11/+0x12, repeat pulse at +0x13 (after sixteen frames and then every two). Whether keyboard/mouse devices expose the same named bindings was not read.

Start/Back stepping, camera reset and debug ray actions

Evidence: static · Fact ID: edf41-free-camera-buttons

In update E7CC0, Start toggles local flag +0x436 and System pause bit 1; Back repeat sets +0x435, allowing one unpaused logic step before pausing again. Pressing one thumb stick while the other is held resets pose and FOV. Y without B reaches E9870, a bullet-spawn path whose projectile type was not read. B+Y casts from the camera eye and forwards a hit to an unread handler ED890; a separate debug Havok cast-test flag +0x437 has no identified writer. These are developer/debug controls, not standard gameplay input guarantees.

Movement, collision toggle and camera rotation

Evidence: static · Fact ID: edf41-free-camera-update

Left stick movement applies a 0.08 dead zone and 1.08696 rescale; triggers provide vertical motion. Holding X chooses speed scale 0.25 or 1.5 under the source's branch. When its Havok controller is in state 7 and world is unpaused, movement goes through the controller (60× speed and position readback); otherwise eye point +0x410 changes directly. A toggles controller collision layer 0x13 versus 0x1B. Right stick controls pitch +0x420 clamped to ±π/2 and yaw +0x424, with sensitivity scaled by FOV; roll is +0x428. The camera rebuilds matrix rows from eye and angles, applying its extra 3×3 transform.

Trigger-independent LB/RB field-of-view zoom

Evidence: static · Fact ID: edf41-free-camera-zoom

Each step adjusts FOV +0x14 by tan(FOV/2) × (LB analog - RB analog) × 0.02. Holding both shoulder buttons resets FOV to π/4, and values clamp to 0.001..2.0 radians (roughly 0.06°–115° vertical). The source identifies this as the same free-camera zoom law as EDF5, without a fresh controller test.

EDF4.1 bloom and tone post-processing pipeline

LightEnv tone defaults and dirty apply

Evidence: static · Fact ID: edf41-lightenv-tone · Build: steam-57aab039

LightEnv parser 103C80 initializes bloom/tone values at environment +0x1E0..+0x210 (same numerical defaults as the EDF5 source). Explicit named fields are v2_Brightness +0x208=0.5, v2_BrightnessLerp +0x20C=0.5 and v2_ToneIntensity +0x210=0.9. The dirty apply copies environment +0x1E0..+0x21F into system +0x40..+0x7F, updates four players' tone state and clears dirty byte +0x1D8. The exact mapping of earlier bloom keys relies on EDF5's known order; only the three brightness/tone names were traced here.

Scene thread queues post command for render thread

Evidence: static · Fact ID: edf41-post-chain-dispatch

Scene update 566B80 calls post enqueue 5479D0 at 5676AC, which registers command 547B60 on render queue CC6E78, submits post object [CC7040] plus bloom/tone parameter block and wakes the consumer event. The render-queue handler pops the block and calls 5471C0(post, renderContext, targets, params); this is the only source-observed caller of 5471C0. Post-processing is a queued render-thread operation even when the simulation is paused.

Blur passes and 16×16 compute combine dispatch

Evidence: static · Fact ID: edf41-post-chain-combine

5471C0 unbinds targets and runs resize/blur helpers 54D990 (five calls), 54DC40 (two), 54DF40 (four) and 54E370. Its final compute pass updates constant buffer resource post+0x898, binds shader +0x878, writes to the output UAV and issues Dispatch(ceil(width/16), ceil(height/16), 1). Shader resource C4C8F0 is created at post+0x868, with a 0x40-byte constant buffer at +0x888; the bound fields refer to their internal object offsets. The full GPU resource graph was not reproduced from a running frame.

Static combine and auto-exposure arithmetic

Evidence: static · Fact ID: edf41-post-formulas

The inspected C4C8F0 final shader matches EDF5's combine instruction sequence: output RGB is scene RGB multiplied by tone, plus two separately weighted blur contributions. Auto-exposure shader C58E60 updates tone by lerp × (target / (saturate(power) × (L - target) + target) - tone), where L samples the shrunk scene at texel (0,0) with RGB weights 0.298912/0.586611/0.114478. This describes the shader math, not a measured display luminance or a claim that 4.1 implements depth of field.

Evidence: unverified · Fact ID: edf41-post-pass-hook-point

A new full-screen effect at this boundary remains an engineering hypothesis shared with EDF5/6 designs. No injected pass, resource lifetime test or actual render hook was run.
