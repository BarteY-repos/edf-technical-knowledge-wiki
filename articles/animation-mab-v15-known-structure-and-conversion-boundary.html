MAB v15 — known structure and conversion boundary

ConversionAnimationEDF 5EDF 6
Source-backed research / case study · Validated v15 MAB parser/converter plus historical 1,318-pair research; no new gameplay test

Scope and evidence. This is the decoded, bounded MAB\0 version 0x0F family in the retained EDF4.1/5/6 weapon/object resources. It is based on a tested parser/converter (mab_legacy.py) and recorded paired-file research, not a fresh gameplay test. Unlike the earlier short MAB reference, the source does establish a concrete generational difference: 0x03 versus 0x83 changes the interpretation of internal offsets. The old rule that MAB offsets are always absolute was incorrect.

The one crucial compatibility difference

Header word at +0x08 Observed generation Where internal pointers are relative to
0x03 EDF4.1 and EDF5 Start of the MAB block (absolute within that block)
0x83 EDF6 Start of the owning 8-, 16- or 32-byte struct (record-relative)

The four top-level directory offsets in the header at +0x14 through +0x20 remain relative to the start of the MAB block in both variants. The change applies to the offset fields inside list headers, records, tracks and keys. Sentinel -1 is not a pointer and must remain -1.

For an internal pointer field at address p, with the start of its owning struct base, a previously absolute target t becomes:

EDF4.1/5: raw_value = t
EDF6:     raw_value = t - base
Reader:   target = raw_value + (base if header_flag == 0x83 else 0)

Do not globally subtract a base from every 32-bit value. Some fields contain literal counts, floats, enum kinds, zero fields or sentinels. The converter must recognize the layout and rewrite only proven offset fields, then validate that their decoded destinations are unchanged.

Header layout — 0x24 bytes

Offset Width Meaning in the examined family
0x00 4 ASCII MAB\0
0x04 4 Version 0x0F
0x08 4 Pointer-mode flag 0x03 / 0x83
0x0C 2 Number of locator lists
0x0E 2 Number of animation-event tracks
0x10 2 Number of vec4 values
0x12 2 String-area length in bytes
0x14 4 List-header table offset, normally 0x24
0x18 4 Track-table offset (end of locator records)
0x1C 4 Aligned vec4 table offset
0x20 4 String table offset; offset + length equals MAB size

The following region order is enforced by the tested parser:

header (0x24)
locator-list headers (8 bytes each)
locator records (0x20 bytes each)
event-track headers (0x10 bytes each)
event keys (0x10 bytes each)
0xBA padding to the next 16-byte boundary
vec4 table (16 bytes per value)
embedded SGO argument objects (if present)
UTF-16LE string area

An EDF5 file may contain nonzero unreferenced bytes in its string area. EDF6's exporter zeroes unused string-area bytes, so exact-byte comparisons need to account for this normalization.

The actual record layout

Each locator-list header has uint16 list_kind, uint16 record_count, and an int32 pointer to its first record. In the studied corpus list_kind equals its list index and records are contiguous. Each locator record is 0x20 bytes:

Record offset Interpretation
+0x00 Pointer to locator-name UTF-16LE string
+0x04 Pointer to bone/node-name UTF-16LE string
+0x08 Locator kind, observed 0 through 4
+0x0C Pointer to position vec4
+0x10 Pointer to vec4 for kinds 1/2; inline float for 0/3/4
+0x14 Pointer to rotation/auxiliary vec4 for kinds 2/3/4; -1 for 0/1
+0x18 Reserved zero in validated family
+0x1C Pointer to an embedded SGO\0 data block

The position vector is expressed in the named node's frame. For kinds using a rotational vec4, source observations describe Euler radians composed as Rz · Ry · Rx; the locator's local +Z is used as the weapon/muzzle firing direction in a known engine path. This is a sampled class convention, not an assertion that every arbitrary MAB field follows the same semantic contract.

Animation events live in MAB, not only CAS

A track header is 0x10 bytes: pointer to first key, pointer to end of keys, pointer to track name, and key count. A key is also 0x10 bytes: UTF-16LE event-name pointer, float32 time, zero/reserved integer and a pointer to its embedded SGO arguments. Event track names match CAS clip names. A working parser returns structures such as:

fly_attack:
  火炎開始, time=t0, args={...}
  火炎終了, time=t1, args={...}

Known examples include UfoRobo event parameters such as collision, damage, quake and scale, and audio events using se / se_stop with cue or channel metadata. For a new reader, the MAB event-track table is a first-class source of gameplay timing; static bone locators alone are not the entire format. See MAB event timing and sound ownership and DragonBig401 flame behavior.

Conversion and source-pair evidence

The retained parser recorded full layout validation on 1,153 EDF4.1 flag-0x03 MABs, 1,652 EDF5 flag-0x03 MABs, and 2,487 EDF6 flag-0x83 MABs. The documented conversion accepted every examined source 0x03 block in that bounded corpus. The source converter rewrites only recognized offset fields, sets 0x83, zeroes unreferenced string slack and validates decoded pointers after writing.

In 1,318 paired EDF5/EDF6 resources, the converted source was byte-identical in 592 cases (including 340 that needed unused string-area zeroing). The other 726 paired resources had genuine content changes, not a different unknown pointer codec:

  • 416 changed locator vec4 values (e.g., reauthored IK/muzzle positions);
  • 191 changed locator names or skeleton-node names;
  • 114 changed record/track/key/embedded-SGO counts;
  • 5 changed key times or embedded SGO data.

Interpretation: the pointer migration is solved for this validated MAB family, but semantic model/weapon retargeting is not solved by that migration. A parseable, re-encoded source may still aim a muzzle at the wrong position, refer to a bone that does not exist or omit a required target animation event.

Exact string-area behavior for exporter authors

The studied EDF6 weapon MAB writer deduplicates strings and orders them by their CP932 (Shift-JIS) byte encodings while storing their content as UTF-16LE. Each string is padded to a slot of (CP932_bytes + 1) UTF-16 code units. The preserved writer reports exact regeneration of 1,676 EDF6 weapon MABs with this ordering; UTF-16 ordering failed to match 132, and unpadded slots failed 382. This is an exact-byte reproduction property of that writer/corpus, not a Unicode collation rule for arbitrary game data.

Implementation and validation checklist

  1. Check MAB\0, version 0x0F, and one of the recognized pointer-mode flags.
  2. Bounds-check header counts, 0x24-byte starting directory and string-region length.
  3. Resolve each recognized pointer with its owning struct base only for 0x83.
  4. Validate known locator kinds, vector targets, key counts, embedded SGO\0 signatures and UTF-16LE terminators.
  5. Preserve raw SGO payloads, key times, unknown values and sentinel -1 while migrating pointer mode.
  6. Validate that old and new resolved pointers reach the same logical content, then inspect target skeleton semantics independently.
  7. Claim in-game parity only after a target-class animation and weapon/audio behavior test, not after byte-level round-trip alone.

Unknowns: compatibility outside the observed 0x0F / 0x03 / 0x83 family, generalized cross-model retargeting and whether all untested MAB event consumers have identical behavior across generations. This is not a generic collision-file format. A desert collision crash previously attributed to MAB was disproven; the studied map had no MAB payloads.
