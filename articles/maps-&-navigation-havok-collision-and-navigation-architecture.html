Collision and navigation architecture

UniversalMaps & NavigationNavigationEDF 4.1EDF 5EDF 6
Technical reference · Mixed: exact native collision, offline reconstruction; partial unresolved

At a glance

What it is: EDF treats what you see, what physically blocks an actor and where AI may travel as related but distinct world data.

Where it fits: Visual geometry comes from MDB/FieldRender resources; physical shapes from Havok collision data; navigation uses its own HKT/NVMD graph and runtime consumers.

Important distinction: A correct-looking shape is not automatically an AI obstacle. Havok generations, body identities and traversal graphs need separate validation.

A rendered map and a usable game world are different products. Visual terrain, placed objects, their collision bodies and the geometry consulted by navigation do not all come from the same file or the same generation of Havok structures. This is especially important when taking EDF4.1/EDF5 map content into EDF6.

Which data answers which question?

Need Relevant data family What it does not establish by itself
Which map resources exist? MAC, MAPB, related asset registry Collision behaviour or AI walkability
Which objects appear where? MAPO, placed MDB resources Exact collision-body identity from a name alone
What is drawn? Ordinary MDB or separate FMEP/FieldRender terrain All physics surfaces
What can physically collide? MAD, SHKT/Havok-derived shapes and bodies AI route decisions or mission triggers
Which bodies can a bullet or explosion actually hit? The body's Havok filter info, the query's layer and the game-specific direct-hit or area-damage collector That every rendered or physically existing body receives a damage event
What is considered traversable? Navigation HKT/NVMD lineage That a mission-specific RMPA route exists
How mission actors are routed/spawned? Mission RMPA and mission scripts Map-owned navigation or map RMPA identity

The categories overlap in space but must not be collapsed into one interchangeable converter.

In particular, a valid SHKT shape, a successful bullet stopping ray, a damage sphere hit and an area-damage candidate are four different results. The studied EDF6 default bullet uses separate stop/damage query layers 12/11, while a surveyed area-damage path uses 13. See the reconciled collision-filter example and the full 32-layer reference for body-class exceptions and evidence limits.

Havok generation changes require structural conversion

The studied EDF5 collision data uses older Havok-style structures, while EDF6 uses 2020-era hknp structures. Changing a header or version marker does not make old hkp motion/shape records into valid target records.

Measured/qualified facts include:

Field or layout Observed rule
Selected hknp shape types convex 0, cylinder 3, box 5, compressed mesh 8, compound 11
Qualified EDF6 motion-properties record 104 bytes; not a dump of EDF5 hkpMotion
Material-descriptor flags in a qualified path uint32 0x0000ffff
Compressed-mesh dispatch type at +0x01 3 in the studied 52-byte record family
Canonical serializer bitfield array entry at +0x20 hkUint32
Primitive with c == d One triangle/primitive key
Primitive with c != d Two triangles/primitive keys

These observations concern particular audited profiles. The same investigation found different valid convexRadius values (0.00 and 0.01), so either value as a global hard-coded constant would overstate the evidence.

Native body identity is more than a similar filename

The EDF4.1 collision/MAPO study contains 40,920 non-empty collision references. Their resolution, reconstructed through structural source relations, yielded:

Binding class Resolved references
Strict base + collision pair 27,018
Base-only empty .hkt family 420
Unique StationWindow fallback 12
Additional list-shape groups 1,945
Dual base/collision-source identity 3,988
Resolved 33,383
Unresolved without unsafe guesses 7,537

These are corpus counts, not an EDF-wide constant. The remaining entries cannot be assigned with approximate string matching without introducing unproven collision-body ownership.

A navmesh with correct triangle counts need not be the correct navmesh

One sampled historical four-tile navigation case has an exact base geometry of 1,562 vertices / 2,928 triangles. A second target has 1,562 vertices / 2,651 triangles, a difference of 277 removed triangles. Reaching those counts is necessary but not sufficient: triangle choice, geometry semantics, binary layout and hash must all match the native target when claiming byte-exact reconstruction.

The study recovered natural map-body selection of 65 groups / 1,405 placements (251 unrotated, 1,153 yaw-only and one mixed-XZ). The blocker is the historical creation of 4,971 active body-level collision footprints before classification. A 277-face candidate produced incorrect HKT bytes despite matching important summary counts and NAV metadata. This is an open reconstruction problem, not a solved general clipping algorithm.

What should an exporter or map editor validate?

  1. Resource identity and object placements separately from visual mesh content.
  2. Collision shapes, materials and filter/query semantics separately from texture/rendering data.
  3. Ownership of each placed collision body, including ambiguous source pairs.
  4. Navmesh geometry and serialization separately from mere in-game visual correctness.
  5. Mission route data separately from native navigation surfaces.
  6. Offline parse/build checks separately from in-game collision/pathfinding tests.

See Map formats and runtime consumers, Havok MAD / SHKT exact observations, EDF4.1 NAV reconstruction details and Mission RMPA.

Evidence status: sampled native assets, independently recovered Havok-derived structures, exact/offline reconstruction and specific runtime-qualified MAD compatibility cases. No blanket gameplay parity or fully recovered R1D classifier is claimed.

Do not conflate mesh quantization with a collision seam

A measured EDFROOM MAD conversion retained 297,951 post-filter triangles and 166,084 reachable unique compressed-mesh shape keys. In 20 audited wall/collider records, decoded coordinates were quantized relative to source coordinates yet shared-section seam discontinuity was zero under the exact source-key comparison. Independent runtime observation confirmed physical wall/projectile blocking while AI targeting remained anomalous. See EDFROOM physical collision reconstruction.

Closed MAD obstacle solids versus open MAD surfaces: a source-grounded counterexample

An original EDF4.1 SK_HEIGEN02 MAD/MAPB example isolates why contact with a triangle does not establish the presence of an interior solid obstacle. The tested weld tolerance was 0.0001 m and the closed-solid gate required every undirected edge to have exactly two incident oriented faces in opposite directions. It was not a full self-intersection proof.

Source placement / mesh Original triangles Boundary edges 2-manifold closed? Supported interpretation
sk_rockm01, MAPB record 96 172 14 No open-surface contact hints only; no interior carve
sk_rockm02, MAPB record 154 96 0 Yes closed-solid candidate; one interior-positive 4 m cell at (241,202)

Using a hypothetical 1.8 m high, 0.45 m radius upright capsule, the same two records produce two open-surface hint cells for the first rock and one closed-solid candidate cell for the second. The point-in-solid-only method does not detect arbitrary capsule-to-face proximity; the later 3D segment/triangle check adds that separate evidence. The reported one closed cell is an offline hypothesis, not measured EDF4.1/EDF6 object blocking or NPC behavior.

In the complete one-map SK_HEIGEN02 recognized static-placement sample, closed/open instance counts were 166 / 99. At 0.45 m hypothetical capsule radius the survey found 243 unique closed-candidate cells, versus 158 interior-positive cells from the earlier point-only method (all 158 are contained, 85 additional distinct cells arise from proximity). 495 other unique cells were classed as open-mesh contact hints; they were not automatically deleted from NAV. Distinct cells are deduplicated across placements and are not counts of individual collision contacts. See the native 4 m source NAV sample.

Do not assume: closed topology guarantees an impassable body, an open mesh is decorative, source object transform equals target actor matrix bit-for-bit, the example capsule is an EDF6 agent, or the count proves original game walkability. These results characterize geometry, not Sandlot's runtime controller/navmesh policy.
