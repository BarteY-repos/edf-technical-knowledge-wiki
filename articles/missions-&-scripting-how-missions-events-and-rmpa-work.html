EDF missions: BVM, events, AngelScript and mission RMPA

UniversalMissions & ScriptingScriptingEDF 4.1EDF 5EDF 6
Technical reference · Reconciled sampled binary and source research

The game-specific mission logic and its referenced spatial data are related but not the same format. We have reconstructed important behavior from EDF5/EDF6 mission bytecode and EDF4.1 sources, including event registration, script calls, route/shape/spawn references, and differences exposed when converting them. This page is an entry point; the linked articles contain exact instructions and caveats.

What is a BVM mission script?

MISSION.BVM is a compiled mission-logic representation in the studied EDF source games. It describes events, factors/conditions, actions and calls into the game's mission API. Conversion research decompiled original BVM and reconstructed EDF6-compatible AngelScript (.AC) logic.

This is more complicated than replacing function names. A faithful converter has to preserve control flow, argument types and value flow, event-target identity, loops and re-arm conditions, counts and ordering. A syntactically compiling script can still behave incorrectly in game.

Event registration and event state

The studied source event model uses RegisterEvent registrations and EDF6-side internal_CreateEvent constructs. A single target handler can have several registrations with different factors. That does not necessarily mean several independent persistent event states.

In one exact native comparison subset, 2,214 reachable registrations mapped to 2,106 unique reachable targets. Those targets determine persistent handler/event-state identity; compiler-generated function numbering alone is not the event ID. Reachability analysis must start at Main and follow relevant helper, wrapper and event-target edges rather than count every decompiled branch as live.

Event multi semantics also matter: source multi == 1 has a specific multi-ready registration behavior in the studied schedulers. Preserving that requires more than translating event names.

For examples and exact constraints see event-state and reachability findings, opcode and API catalog and direct BVM → AC comparison.

What mission RMPA contains

Mission RMPA is not map RMPA. Mission RMPA contains mission-owned routes, waypoints, shapes, cameras and spawn records. Its source/target conversion is a specialized structural task, not a generic byte-copy or header-version patch.

In the studied EDF5 → EDF6 mission-RMPA source/target dataset:

Fact Observed value
Target signature / version \0PMR, version 1
Route type-header size 0x30 bytes
Waypoint record size 0x50 bytes, with 0x30-byte waypoint body
Header string pointer +0x18 (not +0x1C)
Route-local numbering Rebased to global target indexes while retaining IDs and links
Next-link region Variable size, followed by 16-byte alignment

A paired source-only 141-mission audit covered 5,103 waypoints, 1,355 shapes and 3,387 spawn records, with 6,665 script-to-RMPA literal references resolved. That is strong static/semantic closure, not a claim of 141/141 gameplay-runtime parity.

SetAiPath(obj, "navigationmap") refers to native navigation semantics; it should not be misinterpreted as a mission-RMPA route reference. For conversion details see mission RMPA source-only profile.

Missions, maps and shared resources

A mission references a map and other resource identities; it is not intrinsically the same thing as that map. In the studied authoring contract, one map can be reused by multiple missions, while a bundle can contain multiple maps and missions. Resource references and namespace ownership must remain coherent when packing a mission for EDF6.

For current modeled relationships see Workspace, map references and Mission Bundles; for earlier-game differences see EDF4.1 MissionBundle and gameplay research.

For the practical multi scheduler rule, shared event target state, once/repeat/nth policies and factor ownership, see Mission event registration and scheduling. For resource ownership, see Maps, missions and bundles.

Important unknowns and pitfalls

  • The presence of a bytecode instruction or exported event function is not proof that it is reachable from actual mission entry points.
  • Compile success does not establish event timing, runtime API behavior, AI parity or multiplayer correctness.
  • Mission RMPA and map RMPA must not share a converter merely because the extensions are identical.
  • EDF4.1 differs from EDF5/EDF6 in behaviors, object lifecycle, friendly NPCs and navigation; reusing the intermediate game's data is not a universal translation.
  • Third-party mods can be useful comparisons, but cannot by themselves establish what original Sandlot game binaries do.

Mission command IDs do not have universal actor semantics

Even when a message ID and argument list exist in both games, a borrowed target class may assign different meaning. In the examined EDF4.1 four-legged fortress, the exact ObjectAction and generator contract distinguishes legacy group switches from EDF6's unrelated target commands. A correct command translator must know the recipient class and source-era semantic contract.
