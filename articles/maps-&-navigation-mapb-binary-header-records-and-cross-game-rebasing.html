MAPB: header, T1/T2 records and cross-game rebasing

ConversionMaps & NavigationMapsEDF 5EDF 6
Technical reference · Maintained source + paired native structural measurements

At a glance

What it is: MAPB helps a map register the resources it uses and connect those resources to placed instances.

Where it fits: In the examined map family, one table describes resource records (T1) and another records placements or references (T2). The actual model, terrain and collision data may live elsewhere.

Important distinction: A valid placement record does not, by itself, prove that the referenced object will load or behave correctly.

Worked example: count-based MAPB growth

In the studied contiguous EDF5→EDF6 MAPB table profile, suppose the file has three T1 resource rows and two T2 placement rows. Each grows by four bytes:

TableEDF5 sizeEDF6 sizeGrowth
3 × T13 × 0x38 = 0xA83 × 0x3C = 0xB40x0C (12 B)
2 × T22 × 0x44 = 0x882 × 0x48 = 0x900x08 (8 B)
Tail displacement0x14 (20 B)

The arithmetic 4 × 3 + 4 × 2 = 20 gives the shift of data after both tables in this contiguous example. It does not mean every pointer gets +20: T2 starts 12 bytes later, individual T1 record positions depend on their index, and signed relative references must be recomputed from their own field address. Preserve 0/-1 sentinels and insert the T1 dword at +0x20, not +0x24.

Header: where the data is

The verified parser reads a little-endian MAPB magic at offset 0x00, followed by nine uint32 fields starting at 0x04:

File offset Field Meaning
0x00 MAPB Magic bytes
0x04 version The measured parser expects 2
0x08 stringOffset Absolute start of string material
0x0C stringLength UTF-16 string-table length in code units in the newer EDF6 native source (older conversion parser labels this field stringCount)
0x10 auxArrayOffset Offset of an integer-pair auxiliary array in the newer native source (older converter calls this sgoOffset)
0x14 auxArrayCount Count of auxiliary integer pairs (older converter calls this sgoCount)
0x18 t1Offset Start of resource descriptors
0x1C t1Count Count of resource descriptors
0x20 t2Offset Start of placements
0x24 t2Count Count of placement records

These offsets belong to the MAPB header, not to an individual T1 record. In a known contiguous table profile, t2Offset - t1Offset equals t1Count × stride(T1), so it is a useful way to distinguish the measured generations. If that relation does not hold, the file is ambiguous for this heuristic; do not guess the stride. The later EDF6 source also identifies ten additional (offset, count) pairs at +0x28…+0x77. An earlier source classified the +0x78/+0x7C region provisionally as point/route data. the Knowledge Hub's native reader instead identifies a grass-area polygon block at +0x78 in all eight examined GRB-bearing maps: its negative offsets are relative to the block, the vertices are three floats each, the area records are 12 bytes and the indexed triangle records are 8 bytes. This more specific observation supersedes the old inferred description of +0x78 for those source profiles; it does not establish the meaning of +0x7C or every MAPB variant. See native grass registries and GRB polygons. Source lineage: 5b589ca, edf6/map-placed-object-rules.md#map-grb-areas (ktaro; native static reading). The old conversion's weather-pointer zeroing is a profile-specific transformation, not a universal explanation of these native fields.

Table widths and exact conversion

Structure EDF5 EDF6 Examined change
T1 resource descriptor 0x38 / 56 B 0x3C / 60 B One zero dword inserted at entry +0x20
T2 instance/placement 0x44 / 68 B 0x48 / 72 B One zero dword appended

The T1 insertion occurs at entry offset +0x20, not +0x24. In particular, the EDF5 field previously at +0x20 is moved to +0x24 in EDF6. The two known LOD-relative references occupy the old +0x20 and +0x28 slots and must be moved/rebased to the examined target positions. Blindly inserting four bytes after the wrong field makes the record look plausibly sized but corrupts its meaning.

The later EDF6 native-loader study gives the following field-level anchors within those same target strides, beyond the older conversion's width-difference analysis:

RecordOffsetSource-observed field
T1 0x3C+0x00Definition type (3 used for examined terrain/far definitions)
T1+0x04 / +0x08Embedded SGO parameter offset (relative to +0x04) and size
T1+0x0CUTF-16 resource/definition name reference, relative to +0x0C
T1+0x10 / +0x1CObserved -1 sentinel / near-cull distance
T2 0x48+0x00Relative reference to the owning T1 definition
T2+0x04 / +0x10Position XYZ / rotation XYZ (degrees)
T2+0x1CPlacement variant/seed; zero uses the sum of four GUID dwords in the examined loader
T2+0x2CRecord-relative child-index-list reference
T2+0x34 / +0x4416-byte GUID / far-only flag

GUID is not a unique placement key: the native source found 4,546 guardrail instances sharing one GUID in the surveyed DLC maps. The loader retains the placement's own record index and matrix; do not deduplicate objects, collision or child links by GUID. These fields and the GUID counterexample are source-reported static/corpus findings for the examined EDF6 build, not a new runtime test of modified maps.

Native EDF6 MAPB fixup routines (exact build)

In the native-source reconstruction for steam-678ccb46, the measured MAPB fields above are connected to three distinct source-observed routines:

RVARole in parsing / pointer reconstruction
0x11FA40MAPB header endian/fixup path; anchors the version, string offset/length and table offset/count fields.
0x120A40Placement-record fixup for target 0x48-byte T2 instances and their record-relative references.
0x1210A0Definition-record fixup for target 0x3C-byte T1 entries, including embedded SGO and name references.

These are build-scoped, static source-derived addresses, not universal entry points for EDF5, another EDF6 executable or a runtime-tested patch site. They explain why applying only a header size change cannot substitute for the corresponding record-reference fixups.

The source parser identifies selected T1 relative references at +0x04 (embedded SGO), +0x0C (UTF-16LE resource name), +0x14 and the two LOD locations. A relative reference is computed from the address of the dword containing the relative value, not from the start of the file:

reference_target = entry_file_offset + field_offset + signed_relative_value

The examined reference sentinels are 0 and -1; leave them as sentinels rather than rebasing them. A T2 placement's first signed dword is likewise relative to its own record address and must point to a valid T1 record boundary. The correct target relative value changes when the T1 table stride changes.

Rebuilding without silently changing the map

The measured conversion preserves source T1 and T2 counts. If the source tables are contiguous, their size increase shifts subsequent data by:

shift = 4 * t1Count + 4 * t2Count

Every absolute pointer into the moved tail must be adjusted by that shift; the pointer's own position and interpretation determine its relative correction. In the retained conservative implementation, the tail is kept byte-identical and moved as a unit. It re-bases known absolute table pointers, T1 embedded SGO/string/LOD refs and all T2→T1 parent refs. The measured EDF6 weather-pointer span 0x28..0x5C in the MAPB header is zeroed in this conversion profile; do not generalize that operation beyond the verified family.

map.mapb normally exists inside the enclosing MARC/MAC map archive. map.mapo is converted separately. A valid MAPB cannot tell you whether MAPO placement, physics collision, terrain rendering or navigation also work.

Embedded prop SGO semantics are a second conversion

A well-formed T1 pointer can still resolve to an SGO whose property schema is incompatible with EDF6. In a paired EDFROOM test, 30 of 30 matched prop SGOs confirmed the target CrashType schema extension (int32(0) in the measured family). A separate older Desert build had runtime-positive behavior while preserving missing CrashType, so a fixed-index insertion cannot be declared universally mandatory.

Classic SGO variable-node records in that context are 12 bytes, not 16. An obsolete 16-byte hardcoded insertion corrupted relative strings/pointers. Implementation rule: resolve the embedded SGO by its graph/name and transform only the relevant semantic family; never patch it as a generic positional byte array.

Practical checks

  1. Validate magic, header fields, table bounds and the T1/T2 contiguous-stride relation.
  2. Resolve each relative resource/SGO reference within the file, checking UTF-16LE termination and target magic where known.
  3. Validate every T2 parent pointer lands exactly on a T1 record boundary.
  4. Confirm the target has the expected inserted/append-only fields and that source cardinalities are preserved.
  5. Parse relevant embedded SGOs semantically rather than applying one global property insertion.
  6. Test actual resource dispatch and map runtime behavior separately from byte/offset correctness.

Evidence: maintained converter/mac/mac_tool.py parser and structural conversion, paired native MAPB measurements and EDFROOM prop-SGO evidence. Target conversion remains constrained by the chosen MAPO profile and other resource payloads, not solved by MAPB alone.

A correct header does not guarantee a compatible prop

One target-only prop-SGO field, CrashType, was present as int32(0) across 30/30 paired EDFROOM T1-linked SGOs, while a separate Desert runtime-positive profile did not require a universal insertion. The safe rule is to parse and translate the actual named SGO graph, not to insert an arbitrary fixed-index record. See map prop SGO and CrashType.

The parallel MAPO record count, object row identity and child-index remapping matter when duplicating a placement, not just when converting record strides. See the source-derived map cloning/relative-reference guide for a bounded MAPB/MAPO edit algorithm and its collision/NAV limitations.
