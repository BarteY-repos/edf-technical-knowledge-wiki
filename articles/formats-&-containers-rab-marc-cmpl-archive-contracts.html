RAB, MARC and CMPL archive contracts

UniversalFormats & ContainersFile FormatsEDF 5EDF 6
Source-backed research / case study · Runtime

Evidence level: Reconciled structural rules with runtime-positive rendering evidence for the RAB/MDB simple-clip path.

RAB

RAB is an archive/container layer. Embedded MDB and related payloads still require their own ABI conversion; archive rebuilding cannot make an incompatible model/material payload native.

Observed native behavior: The palm/high-LOD leaf rendering regression was fixed through the combined RAB/MDB simple-clip material ABI work. This is runtime-positive evidence that archive reconstruction and material ABI must be treated together.

Do not assume: A RAB that parses successfully means every embedded payload is semantically valid.

MRAB and the shared-SSA boundary

The retained cross-game reconciliation classifies RAB / MRAB as CONVERT_REQUIRED. Their SSA archive grammar is shared enough to support common tooling, but that does not make an EDF5 archive byte-copy-safe in EDF6. EDF6 archive type conventions and every embedded payload's own ABI still control correctness.

Implementation rule: rebuild/normalize the archive for the target profile and convert each contained resource according to its owning format contract. An MDB, SGO, CMPL or other payload does not become EDF6-native merely because it sits inside a structurally valid RAB/MRAB.

Do not assume: .rab and .mrab are interchangeable extensions, that archive grammar proves payload parity, or that a successful extraction/repack establishes runtime identity.

MARC: entry records, names and version-specific flags

The researched MARC envelope uses magic MARC, a 0x24-byte header in the measured version-5 family, and 24-byte entry records. A known entry has six 4-byte words:

entry +0x00  name_off  (relative offset to UTF-16 name)
entry +0x04  addr      (payload address)
entry +0x08  size      (payload length)
entry +0x0C  u1        (profile-dependent entry flag)
entry +0x10  u2        (zero in the measured normalized form)
entry +0x14  u3        (zero in the measured normalized form)

The historical measured entry table starts at 0x14 + header[5] in the documented parser profile; do not generalize that formula without checking the version and header interpretation of the actual file. The EDF5 desert-map samples frequently had u1=2; the normalized EDF6 map-entry profile used u1=0. A later conflict review explicitly warns that EDF5 values are content/profile dependent, so u1=2 is not a universal EDF5 rule.

Implementation rule: retain the original entry order, names and payload identity, then apply only the exact target-profile differences that are supported by a paired asset. A header/version edit alone cannot make incompatible entry contents or offsets valid.

CMPL

The current corrected CMPL token decode uses:

len = (tok & 0xF) + 3
pos = tok >> 4

The older interpretation using the high nibble as length and low 12 bits as position is superseded.

Implementation rule: A corrected exact encoder/decoder is preferred over the old literal-only safety workaround. Historical conclusions reached with the wrong token decoder must not be reused as format evidence without rechecking them.

Cross-layer rule

Implementation rule: Archive/container correctness, payload format correctness and runtime behavior are separate gates. A parseable container with structurally wrong MDB/MAD/SGO content is not a successful conversion.

RAB/MRAB as named-entry SSA containers

The measured RAB and MRAB samples use the shared SSA\0 container grammar. A reader can distinguish archive-level entry names, type strings, entry attributes and opaque payload bytes. An archive is not a single indivisible resource.

In a lossless parse/rebuild control (preserve_order=True), these exact RAB samples were byte-identical after reserialization:

Control archive Entries Size
IG_CAVE503.RAB 5 34,932,784 B
IG_HEIGEN507.RAB 279 88,866,805 B
IG_DESERT508.RAB 424 217,373,434 B

The sampled E506 MRAB archives parsed through the same SSA tool: E506_BIGGREY.MRAB had 71 entries (52 DDS, 19 MDB), E506_HA_BIGGREY.MRAB had 47 (36 DDS, 11 MDB), and E506_HA_WEAPON.MRAB had 28 (24 DDS, 4 MDB). These are sample measurements, not universal entry counts.

Entry identity is its exact case-sensitive name; entry state comprises its type string (rather than a transient numeric type-table index), hd, ft1/ft2, z and the payload bytes/hash. The hd flag was a real per-entry attribute in the samples. Duplicate exact/case-folded names were absent in those three RAB controls, but case-fold collisions should still trigger a warning in a composer.

When two mods modify one RAB/MRAB

A viable composition strategy is a baseline-relative, named-entry three-way merge, with the contained DDS/MDB and other assets treated as atomic blobs:

Scenario Default treatment
Different named entries modified or added Merge
Same entry set to identical final state Deduplicate
Same entry changed to different final states Conflict
One mod deletes an entry another edits Conflict
One deletes, other leaves unchanged Delete
No proven semantic identity within an atomic DDS/MDB blob Do not byte-merge

Maintain baseline type-string order and append genuinely new types. Exact case-sensitive names remain distinct, but case-fold collisions should be surfaced. In private custom resource families, namespace-rebasing the whole coherent closure can be safer than merging two conflicting roots.

Cross-file exception: a mission-image .image.rab is coupled to mission LIST and localized TXT resources through CONFIG. Named entry merging does not prove that LIST row insertions/reordering still select the correct mission preview image. Later R29 native-resource evidence resolves the identity for the studied EDF6 mission-list profile: use LIST field2, replace / with _, append .dds. That corrects an older September 1 unresolved-note, while preserving the requirement to validate any newly composed LIST/TXT/image relationship. See the exact thumbnail lookup guide.

The named-entry merge was tested in offline PoCs; those tests establish a deterministic archive operation, not game-runtime acceptance for every merged pack.

A measured CMPL failure: header preserved, payload corrupted

In a tested EDF5→EDF6 desert archive, a faulty LZ recompressor produced entries whose MDB0 first eight bytes survived, but 45/76 decompressed MDB bodies failed independent byte-for-byte round-trip. A simple version check therefore returned a false sense of correctness. Rebuilding the affected RAB from pristine source with the tested literal-only CMPL fallback yielded 76/76 MDB bodies correct (aside from the sanctioned version byte), plus 348/348 DDS byte-identical. This is evidence for a specific obsolete encoder defect, not evidence that CMPL LZ is intrinsically broken or that literal-only is the optimal current encoder.

Recommended diagnostic: require independent full-body decompression checks before attributing a loader crash to the MDB ABI. See Typed resource dispatch versus CMPL corruption.

Implementing an SSA reader

The SSA header and entry-layout reference gives the measured 0x28-byte header, 0x20-byte entry records, UTF-16LE name/type offsets, distinction between relative string offsets and absolute payload addresses, and the safe bounds checks for parsing.

Its central lesson is that archive-level type indices are local: the type string and exact resource name supply the meaningful identity. A valid SSA archive can still contain a wrongly compressed or incorrectly typed MDB. Entry-level three-way merge also does not establish the safety of a coupled LIST/TXT/image-RAB change.

MARC header and payload/name addressing (verified parser)

The maintained MARC parser/rebuilder permits the following version-5 envelope inspection (the checked code handles the measured 0x24-byte family):

Offset in MARC Meaning in the examined record
0x00 MARC magic
0x04 Parsed version, 5 in emitted controls
0x08 Header start/size value 0x24 in the emitted profile
0x0C Length of the data region including inter-file padding: string_table_offset - 0x24 in the measured EDF6 MAC profile
0x10 Sum of embedded payload sizes excluding alignment padding in the emitted profile
0x14 Entry-table address relative to 0x14
0x18 Number of 24-byte entries
0x1C Absolute string-table address
0x20 UTF-16 code-unit count of the strings

An entry at entryOffset contains <iIIiii: signed name offset relative to the entry itself, absolute payload offset, payload length, u1, u2, u3. Names are null-terminated UTF-16LE, not ASCII. The measured rebuilder aligns payload and table regions to 16 bytes. A historical ASCII-written collision.hkt block name was a real bug even when the embedded Havok payload was correct. Do not interpret entry-relative name pointers as absolute offsets or generalize a measured u1 value to every MARC variant.

EDF6 MAC: native directory, strings and lookup

For the EDF6 MARC-v5 MAC profile, the retained native-source/encoder study reports 45/45 shipped MAC files rebuilt byte-identically. It gives the following serialization and lookup contract; this does not certify unrelated MARC variants or changed embedded payloads.

Region or native routineExact observed rule
Payload regionBegins at 0x24; embedded files are packed in directory-authoring order, with each subsequent payload beginning at the next 16-byte boundary. Alignment bytes are zero.
String tableStarts at align16(last_payload_end); unique names are sorted by code point and written as NUL-terminated UTF-16LE.
DirectoryStarts at align16(string_table_end), with 0x18-byte entries in the builder's original file order, not name-sorted order. Header +0x14 is a displacement relative to 0x14.
Entry layout+0x00 signed entry-relative UTF-16 name pointer; +0x04 absolute payload pointer; +0x08 payload size; +0x0C/+0x10/+0x14 zero dwords in all 45 sampled EDF6 MACs.
LookupLinear, case-sensitive wcscmp over the directory; no hash table or checksum in this studied profile. The sorted name pool does not make the directory itself sorted.
Exact-build native RVAs0x1186F0 directory addressing; 0x118713 map.mapo lookup; 0x11878A map.mapb lookup (build steam-678ccb46, source-derived static addresses).

Version boundary: the final three entry dwords are zero in this sampled EDF6 MAC family; an older EDF5 desert entry may contain u1=2. Neither the EDF5 flag nor the all-zero EDF6 profile may be applied to every MARC archive by filename extension alone. The 45-file byte-for-byte reconstruction is an offline/source-backed format result, not proof that a modified game loads every rebuilt resource.

MAE uses the same enclosing MARC grammar but has an additional internal resource-identity rule: see weather DSGO-to-RMPA binding.

Mission preview images are a coupled resource

A mission-image RAB can be valid and merge cleanly while its images remain invisible in the menu. In an observed EDF5-content deployment the game requested the shared MISSIONLIST.OFFLINE.IMAGE.RAB name, not arbitrary pack-local image filenames. The archive, LIST ordering and localized TXT need joint validation. See mission LIST and preview-image identity for the runtime-derived case and its scope.

For multi-mod composition, a RAB/MRAB is an SSA archive of named entries, not an atomic blob. See entry-level merge policy and cross-file coupling before assuming last-wins or byte-level patching.
