EDF6 Air Raider deliveries: replicated smoke, transporters and vehicle IDs

EDF 6Game technical referencesNetworking
Technical reference · Source-code/static interpretation with explicitly labelled contributor gameplay observations; no new game runtime

A delivered vehicle in EDF6 is not necessarily a vehicle object fully serialized by the host and transmitted to the client. In the examined native chain, every peer can create a corresponding local object using the same mission and SGO resources, then register it under a derived network identity. This applies to the studied smoke-candle / Transporter508 delivery path, not all game vehicles in every circumstance.

Source-observed object chain

  1. The smoke-candle/bullet mechanism creates a transporter and, in a room, establishes a derived registration ID.
  2. Transporter508 creates its container and registers that container in the online object system.
  3. The container's unloading state loads the vehicle from a referenced SGO object path.
  4. The game sets the delivered vehicle's team/state, initializes/equips it, derives its network identity from the parent and a counter, and registers it.
  5. The delivery container is subsequently removed.

The source identifies an SGO vehicle path at the container's +0xB80 and a registration counter at +0xC30 in the examined build. Those are build-scoped object offsets, not universal SGO file offsets.

Why identical game resources matter

A synchronized event and object identity do not include a complete copy of the vehicle's SGO/model/archive resources. The receiving machine still needs the appropriate game resource path. This explains why a modded delivery can work on one computer but crash another computer that lacks the referenced SGO, despite their network session itself having started successfully.

The stock/source-derived chain creates each local copy, then the engine assigns ownership roles. The source reports owner/guest values in the network copy flags, but the precise downstream control/seat behavior remains a separate system.

What this does not establish

  • It does not prove that every custom vehicle object is safely synchronized just by using an equal SGO filename.
  • It does not prove that the host sends the entire SGO to peers (the analyzed behavior indicates the opposite).
  • It does not override vehicle seat eligibility or per-seat camera locators; those are separate native data.
  • It does not imply that object registration, vehicle physics and local equipment input all use the same authoritative peer.

For the other native pieces, see vehicle seats and masks, vehicle ride camera, and object network ownership.
