EDF6 mission AngelScript ABI: MovingFortress types, booleans and fog

UniversalMissions & ScriptingMissionsEDF 5EDF 6
Source-backed research / case study · Runtime-proven compile/load classes

Syntactically valid target AngelScript calls may still have incorrect typed argument domains or incomplete visual semantics. The retained EDF5→EDF6 source and modded runtime evidence established three useful independent boundaries.

Object::MovingFortress_Activate symbolic domains

In the studied EDF6 script API, the object method accepts symbolic weapon and mode domains, not arbitrary interchangeable raw integers. The following pairs were used in the runtime-qualified modified missions M007, M021, M020 and M035; qualification concerned compile/load and this call domain, not complete fortress AI/pathing.

Raw source value EDF6 symbolic parameter
1 MOVINGFORTRESS_BIG_CANNON
2 MOVINGFORTRESS_CANNON
4 MOVINGFORTRESS_SMALL_CANNON1
8 MOVINGFORTRESS_SMALL_CANNON2
16 MOVINGFORTRESS_SMALL_CANNON3
32 MOVINGFORTRESS_SMALL_CANNON_GREEN
Mode 0 MOVINGFORTRESS_FORT
Mode 1 MOVINGFORTRESS_MOVING

The native logical values and API type declarations are separate; do not infer that arbitrary numeric literals retain the correct typed domain.

Boolean-domain source conversion

A source expression written in the form:

IsOnlineMode() == 0

required target-domain Boolean semantics in the tested M081 case:

IsOnlineMode() == false

An earlier test passed at compile/load, but a later combined candidate had a separate regression. The observed lesson is about the target function's Boolean return domain, not proof that any integer-to-Boolean replacement is always legal in every mission.

SceneEffect_Fog native public binding versus visual composition

The recovered live public script call was:

SceneEffect_Fog(float, float, float, float)

Direct use of an internal fog implementation was not an accepted substitute. In a tested modified runtime, M200 and M201 both compiled and loaded with the public four-float ABI, yet visual parity failed: their fog remained weak relative to the source. The retained binary analysis recorded EDF6 internal particle count 400 and particle size 10.0; the missing density was not explained simply by discarding a source particle count. The dense-fog scene uses particle fog together with environmental fog distance/color/background state.

This demonstrates why a correct call signature is not sufficient to reproduce a complete effect. See MAE weather environment bindings.

Scope and evidence

The historical runtime sweep tested compile/load for numerous missions but was not a complete mission-clear or multiplayer parity campaign. The exact retained examples above are bounded to their call family, source and target game build. Other runtime failures were environmental or content-specific; they do not change the identified script ABI.

Native dense fog is a composition, not a single particle call

The exact EDF6 runtime SceneEffect_Fog(float,float,float,float) binding constructs particles using a fixed 400 instances (0x190) and particle size 10.0; its script duration/speed/horizontal parameters are forwarded through the registered callback. The examined native mission helper Merman_FogScene(second, near, far, apply_ratio) combines five components:

  1. EVENT_LIGHT_ENV_FADE_FOG_BG_APPLY;
  2. EVENT_LIGHT_ENV_FADE_FOG_COLOR;
  3. EVENT_LIGHT_ENV_FADE_FOG_DISTANCE;
  4. SceneEffect_Fog(...);
  5. SceneEffect_StartFade(...).

In the examined modified EDF5-content runtime, M200 and M201 moved from compile/load failure to compile/load PASS but visually weak fog. Therefore a correct public fog ABI cannot by itself prove the map's source-authentic short-visibility effect. M200 used NW_JYOUSUICITY / cloudy, whereas M201 used NW_KITAGUNICITY / cloudy, with distinct mission event sequences; it is unproven that the two have an identical missing carrier. Likewise the M020_5 sandstorm failure was traced to environmental map/profile behavior despite closely matching high-level mission script calls on the native EDF6 IG_2000MCITY601 / evening comparison.

The specific negative tests do not justify an arbitrary fog-distance multiplier, replacement of source weather with a similarly named map, or copying native 601 weather assets into a separate map profile. The original evidence is EDF6 MAE environment binding plus the bounded EDF5_EDF6_FOG_WEATHER_RUNTIME_FRONTIER_R66B_2026-09-05.md runtime report.

Distinguishing a failed script compilation from failed in-game behavior

In an early M008 build (visible mission 12), the apparent black screen was traced to a direct AngelScript compiler error rather than an inferred map or resource-loading failure:

Can't implicitly convert from 'bool' to 'int&'.

The generated carrier-wait loops discarded IsAiMoveEnd(carrier01/2/3) query results, assigned Boolean expressions to integer/counter fields and had a while(true) path lacking the correct terminating break. The working EDF5 source/official target comparison instead forms a Boolean OR of negated movement-completion queries, conditionally includes carrier01_4 on higher difficulty, yields and exits once all relevant carriers have completed movement. A targeted control restored that intended polling structure without changing weather, mission RMPA or map geometry.

The later broad R65 runtime sweep explicitly reports M008 compile/load PASS. Thus the early black-screen mechanism is important as a BVM-to-AC typing/control-flow pitfall, but the old M008 failure is not the latest known blocker. The early uppercase-preload experiment failed as a root-cause test; do not present it as the successful M008 fix. Likewise, R65 tested many missions for compile/load, not full mission-clear parity. Evidence: M008_BLACKSCREEN_COMPILE_ROOT_CAUSE_UPDATE_2026-09-04.md and EDF5_EDF6_R65_RUNTIME_SWEEP_ACCEPTANCE_AND_R66A_FRONTIER_2026-09-04.md.

The later runtime resolution of the two fog missions

The weak-visibility failure reported above is an earlier implementation state, not the latest verified status for those two missions. Both M200 (displayed #58, NW_JYOUSUICITY) and M201 (displayed #72, NW_KITAGUNICITY) received a subsequent direct modified-game runtime PASS for loading and effective fog/visibility behavior with source-derived, map-local e5cloudy weather profiles. This was not a new patch to the four-argument SceneEffect_Fog binding alone.

The accepted profile path kept the original EDF5 CLOUDY RAB bytes under distinct E5CLOUDY names, used a source-derived weather RMPA representation, and changed the mission PreloadMap/Map weather choice from cloudy to e5cloudy. It did not overwrite the stock EDF6 cloudy profile, retune an arbitrary fog constant, or revive an internal fog callback. The two source maps and their weather assets were verified separately; the runtime PASS is for the tested mission/profile combinations, not a universal theorem about every EDF5 fog event or every source map.

This is a useful causal sequence: script ABI repaired -> mission loads but environment differs -> source weather selection repaired -> direct mission runtime accepted. If documenting the earlier failure, also document the later positive result. Evidence: EDF5_EDF6_FOG_WEATHER_RUNTIME_FRONTIER_R66B_2026-09-05.md, EDF5_EDF6_M200_M201_R81_E5CLOUDY_SOURCE_WEATHER_AUDIT_2026-09-05.json, EDF5_EDF6_M200_M201_R81_E5CLOUDY_RUNTIME_PASS_2026-09-06.md. Independent mission-specific runtime confirmations and stale backlog entries

The early broad R65 backlog explicitly mixed runtime-positive cases, source/compile repairs awaiting smoke and separate regression watch reports. Its older M008 black-screen note was a compiler and Boolean-query control-flow defect, later superseded by compile/load success for the targeted carrier polling path. Its M200/M201 R66B visual failures were later superseded only for the tested E5CLOUDY runtime compositions, not by the generic fog callback. Conversely, early M072_3 and AI route watch items are not converted into successes by the R65 source gates alone.

Three scoped runtime observations worth keeping distinct:

  • DM024: direct modified-game PASS for a DropBoat_SetCrew object-return type compatibility repair, while its independent M075 use site remained a separate optional test (DM024_R50_RUNTIME_PASS_2026-08-28.json).
  • DM021, DM001, and mission metadata V3: the R54 user test accepted the specific DLC2 #3 spawn, practically accepted the then-current DM001, and confirmed tested campaign/limits/resource/drop metadata. The inherited R18–R32 DM001 diagnostic branches were not all separately retested (R54_RUNTIME_STATE_2026-09-01.json).
  • M018 (Escape): native EDF6 DLC RM018/MISSION.RMPA returned direct PASS for opening NPC route pacing, with 4 route groups / 11 waypoints and unchanged shape/spawn records. It is mission-local vertical grounding, not a global RMPA transform (EDF5_EDF6_M018_ESCAPE_RM018_RMPA_RUNTIME_ACCEPTANCE_2026-09-06.md).

These are reported user runtime observations in modified content, not source-only checks or claims that the whole ported 141-mission campaign was replayed. See cross-gameplay cases for the exact M018 and convoy lineage.

Patch 1.0.2 versus 1.0.3: do not conflate static overlays with native gameplay

The 1.0.2 RC1 offline validation covered 32/32 MISSION.AC files, 0 validator errors and one explicitly non-gating absent UTF-8 BOM in M003. A separately checked overlay simulation copied 41/41 payload files, preserved 11/11 inherited critical assets, kept all 6/6 LIST/TXT resources unchanged and left 145 physical mission directories including historical non-LIST residues. Its static assertions checked four-argument public fog ABI, E5CLOUDY/E5EVENING names and specific mission resource references. Those checks do not prove a combined RC gameplay regression.

The 1.0.3 archive is a further incremental overlay over 1.0.2, with eight production files (two Desert508 MAEs and two RABs, the English VOICETABLE, M018 route RMPA, M020_5 AC and DM018 AC), packaged with 10 ZIP entries and 0 static pre/post ZIP validation errors. It is not a stand-alone replacement for 1.0.2, and its static PASS alone certifies no new mission behavior. The contemporaneous R85 runtime ledger directly reports M200/M201 R81 fog PASS, but lists the current exact-RC smoke and private two-peer testing as qualification gaps, and DM019 AI-wall as a historical runtime failure needing a current retest. An R79 caption suppression fix was still pending at the time of R85, independently of the later R97 subtitle observation.

This corrects the most common bad reading of the release lineage: package-validation PASS, particular in-game mission PASS, and unperformed exact-package smoke are three separate evidence levels.
