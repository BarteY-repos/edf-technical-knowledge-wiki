Body wrapper and ids

EDF6 hknp Body wrapper and size

Evidence: static · Build: steam-678ccb46 · Fact ID: havok-body-wrapper

xgs::havok::Body is EDF's wrapper of one hknp body: 0x110 bytes (11AEF00: new 0x110, then the constructor 11B0580), held by a shared_ptr (RTTI _Ref_count<VBody@havok@xgs> near 11AA979), no vtable. +0x00 / +0x08 a weak_ptr to itself (enable_shared_from_this; 11AD220 locks it), +0x10 a 0x50-byte material copy (from the material library at hknpWorld +0x920, by +0xF4; inferred), +0x60 a copy of its hknpMotionProperties (0x70 bytes), +0xD0/+0xD8 and +0xE0/+0xE8 two shared_ptrs passed to the constructor (inferred), +0xF0 the hknp body id (low 24 bits the index, 0xFFFFFF none), +0xF4 u16 material id (= hknpBody +0x8A), +0xF6 u16 motion-properties id (= hknpWorld +0x90[id & 0xFFFFFF] +4), +0xF8 u16 set to 2 by the constructor (meaning unknown), +0x100 the world wrapper W, whose +0x58 is the hknpWorld X. Agrees with corpses.md#ragdoll-body-array (+0xF0 id).

SceneObject physics body array traversal

Evidence: static · Build: steam-678ccb46 · Fact ID: bodies-of-object

hknpWorld, bodies and motions

hknpWorld constructor and three vtables

Evidence: static · Build: steam-678ccb46 · Fact ID: hknp-world-vtables

The hknpWorld X is built by DA3140 and has three vtables: [X] = 18BC720 (main), [X+0x18] = 18BC740 (the write interface, "write slot n" below = [18BC740 + n*8]), [X+0x20] = 18BC9C0 (the read interface, which the map raycast calls, bullet-collision.md#map-raycast). Write slot 28 is E50720 (set motion properties) and slot 32 E4FBF0; a check of slot 32 against E50720 (All Forces' own jet code did that) never matches. Every write slot first posts an API command to X+0x868 (command number in 0x00XX0200).

Basis: the author's static reading ("H": q(18BC740 + 28*8) = E50720, q(... + 32*8) = E4FBF0); corrects the author's own jet notes

Addresses (build-specific RVAs unless indicated): DA3140, 18BC720, 18BC740, 18BC9C0, E50720, E4FBF0

Evidence: static · Build: steam-678ccb46 · Fact ID: hknp-motion-layout

What the velocity and impulse write slots (20 to 26) do: nothing when the body is not added (flags & 2 == 0)

Evidence: static · Build: steam-678ccb46 · Fact ID: hknp-write-wakes

What the velocity and impulse write slots (20 to 26) do: nothing when the body is not added (flags & 2 == 0); when it is in the world (+0x88 != 0), neither static nor active (flags & 9 == 0) and the activation argument is 0, they wake it with DAFF20(X, id, 0) (E4FE46..E4FE64); then they write the velocity and clamp it to the maximum at motion +0x6C. EDF's wrappers always pass 0, so setting a velocity wakes a sleeping body.

Basis: the author's static reading ("H"; DAFF20's signature "M")

Addresses (build-specific RVAs unless indicated): DAFF20, E4FE46, E4FE64

Motion properties and gravity

Motion properties library: lib = X+0x928, entries lib+0x40, count (int)lib+0x48, 0x70 bytes each

Evidence: static · Build: steam-678ccb46 · Fact ID: motion-properties-library

Motion properties library: lib = [X+0x928], entries [lib+0x40], count (int)[lib+0x48], 0x70 bytes each. E155D0(lib, |g|) builds the five defaults, index 0 to 4 STATIC, DYNAMIC, KEYFRAMED, FROZEN, DEBRIS (a switch in DCFA10): DYNAMIC max linear speed 200, max angular 100, gravity factor 1; KEYFRAMED gravity factor 0; DEBRIS 100 / 10 with damping 0.01 / 0.5; every preset writes time factor 1.0. Layout: +0x00 isExclusive (must be 0 for de-duplication), +0x04 flags, +0x08 gravityFactor, +0x0C timeFactor, +0x10 maxLinearSpeed, +0x14 maxAngularSpeed, +0x18 linearDamping (DEA61F: v *= max(0, 1 - d x dt)), +0x1C angularDamping, +0x20 on solver and deactivation values (DEBRIS: +0x20 0.2, +0x24 |g| x a constant), +0x54 5 / maxLinear, +0x58 0.005 / maxLinear. So a thrown dynamic body is capped at 200 m/s unless its properties change. (All Forces' own HavokRelay.h had gravity at +0x24 and time at +0x20: wrong.)

Character contact impulse behaviour

Evidence: static · Build: steam-678ccb46 · Fact ID: character-contact-impulse-uncapped

Reading map

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Character proxy contact setup
  2. Impulse computation
  3. Missing or different caps
EDF Knowledge Hub record — original wording — expand (1,537 characters)

Character contacts with no impulse cap: the character proxy builds its vertical contact constraint in 11DDFD0 as a block at [rsp+0x40] = {0 or 1.0, maxImpulse, 1.0}, and 11DE049 (movss xmm0, [18474B0]) always loads maxImpulse with HK_REAL_HIGH (infinite). The character's maxForce at [character+0x70] (copied from cinfo +0x98 by the constructor at 11DD07F / 11DD085, default 1000) is never used on this path; EDF5's hkp character limited contacts with dynamic bodies to maxForce x dt, EDF6's hknp lost that step, so a giant (Barga, huge monsters) standing on or pressed against a moving mothership, ragdoll or debris gets an unlimited impulse (thrown, or pushed into the ground). The engine's own test when a character pushes a body (D95D38): test [body+0x54], 5 (static or keyframed: skip), then test 2 (dynamic), then push with [rdi+0x70]; so a cap belongs only on flags & 7 == 2. Havok multithreading: queue, events and reset hazards

Provenance: EDF Knowledge Hub revision 5b589ca, hajisensai (edf6-all-forces), docs/havok-mt-re.md, EDF6 steam-678ccb46. The 29 records below are reported static native-code analysis; contributor measurements are described as reported, not independently reproduced by this wiki. Any threading modification requires separate runtime validation.

Pool, worker lifecycle, TLS and mission-reset boundaries

Holder and default pool (static): global 20B30A0 has a thread pool at +8 and task queue at +0x20. Pool processTaskQueue, waitForCompletion and queue-subobject close are identified by vtable slots. The shipped game constructs this pool with zero worker threads, so ordinary graph tasks execute on the game thread unless a mod attaches workers.

Worker entry (static): worker 13102B0 sets its Havok thread-context slot, initializes a per-thread monitor stream when needed and waits on a semaphore when idle rather than spinning. It leaves the loop when the queue is closed.

TLS and allocator (static): Havok memory entry 97A6B0 obtains a per-thread context from TLS +8, initializing it lazily through 97E1D0. The author's 57-function TLS survey found Havok monitor contexts and MSVC static initialization, but no separate game-owned thread_local storage. Thread safety of the underlying memory-router heap was inferred, not disassembled.

Critical reset hazard (static): destructor 118EC70 closes the queue, then releases the pool and queue. By contrast reset 118F0A0 frees/rebuilds them without first closing the queue. That is benign with zero workers, but a mod attaching workers must stop and join them before reset or risk stale queue use/hangs.

Reset callers (static and contributor run): 118F0A0 is reached at mission-scene resource cleanup 70E38E and SystemReset 70FEC6. The author's test plugin reported 20 mission restarts and three reboots with worker recreation on these boundaries, but no blanket compatibility guarantee.

Contributor performance measurements (reported): a worker-enabled probe used seven workers on a 16-thread machine; across 20 restarts and 42,896 world-task executions it observed no overlap between world-level event tasks. In one heavy stress scenario the mean frame time reportedly fell from 63.26 to 47.87 ms, and in another from 124.39 to 108.20 ms; lighter cases were near the frame cap. Online behavior, collision sounds and damage parity remained untested.

Simulation phases, task graph dependencies and game-thread waits

Simulation phases (static): PreCollide DACD80 fires its world signal before the task graph on the game thread. Collision tasks execute modifier code; PostCollide DAC840 dispatches commands/signals; PreSolve DAD360 fires the next signal and dispatch; solver tasks then compute Jacobians and contact modifications.

Three persistent world tasks (static): hknpPostCollideTask, hknpPreSolveTask and hknpPostSolveTask are allocated at simulation +0x6A8, +0x6B8, +0x6D0. Each requests one instance at a time and invokes the corresponding phase routine.

Explicit ordering (static): graph edges are word pairs at graph+0x328 with count +0x330. The traced graph places all collide tasks before PostCollide, then PreSolve, then solver completion and PostSolve; the collide graph had 18 tasks and 30 edges in the author's reconstruction.

Unresolved subgraph ordering (static with open dependency): 9EC7A0 can append a separately rebased solve subgraph without an explicit edge to the main graph, except that its exit precedes PostSolve. Its builder and contents were not traced; do not extrapolate the three world tasks' nonoverlap to every possible subgraph task.

Graph wait (static plus reported observation): game thread 9EDDB0 can execute tasks while awaiting graph completion. The examined world-event callbacks are serialized by the graph, but their thread identity may change with workers, and tasks without a dependency edge could still overlap.

Game-object update boundary (static): System::update 1198DA0 takes one scoped critical section earlier in the frame, but no encompassing lock across both physics steps. AI, input, object update and target-selection virtual calls occur outside physics task execution at their specified stage; that placement matters when considering callbacks that touch game state.

Havok signals, collision modifiers and game-state writes

Signal slot layout (static): hkSignal slots hold vtable, flagged next pointer, object and member callback; the trigger E75F50 invokes subscriber slot +0x18, with global body ID 0xFFFFFF. The examined event dispatcher functions are its direct callers.

PostSolve versus immediate events (static): DACA60 merges/distributes deferred events, signals world+0x870 and clears per-step contacts. Immediate events outside a step dispatch through hknpInternalCommandProcessor on the caller's (normally game) thread.

Merge does not schedule to game thread (static): E76850/E76B70 aggregate trigger enter/exit counts and cancel opposing events within the same step. Dispatcher fields +0x78/+0x80 do not provide a cross-thread deferral mechanism.

Subscriber census (static): registered listeners include MapDestruction and crash models; shell cases, Deroy feet, Berserker bomb, Dango, Merman, transport containers, vehicle and helicopter contacts, character cling/walk and ragdolls, rigidbody damage, trigger volumes and character bodies. The source gives per-class RVAs and signal kinds; this is not evidence all listeners are safe to parallelize independently.

Other world subscribers (static, incomplete): scene-object add/remove and UniqueKeyHolder begin callbacks are associated with body registration, ordinarily on the game thread. The author did not audit every World::Initialize lambda, and a task that adds a body could change their executing thread.

Callback locking (static call closure): helper 50BC0/50BE0 scopes EnterCriticalSection/LeaveCriticalSection for several damage or helicopter callbacks. The bounded direct-call search saw few other locks and did not resolve every virtual target.

Shared mutable fields (static, qualified): MapDestruction decrements 20B2BD4 and Berserker equipment increments/decrements 20F4C68 via plain non-atomic operations. They remain race-sensitive if future graph changes allow concurrent instances. Contact-related handlers largely enqueue under a scoped lock; one walk callback has its own spin lock.

Damage application boundary (static): physical-contact callback 541FF0 deduplicates and enqueues pending hit records; the actual ApplyDamage 547C30 route is reached later through game-thread settlement 543920. Enqueueing during physics is not the same as applying HP changes during physics.

Modifier boundaries (static): registration includes Havok and Sandlot FlipBackface implementations and MassChangerModifier. The examined custom modifiers change per-pair flags/Jacobian output and query shape properties; the source identified broadphase and tag-codec routines mostly reading shared tables and writing per-call outputs.

Cling callback dispatch (static): the insect-family cling path uses a secondary vtable at creature +0x5C0. Patching only the main object vtable does not intercept this callback for ants, bees, spiders and tadpoles.

Asynchronous query batches versus synchronous casts

Batch command bodies (static): ray and shape-to-body tasks execute at 11AA7D0 and 11AA800. A bounded code-reach scan found Havok reference-count atomics but no direct global writes in these query paths.

MTQueryQueue (static): flush 11BE590 and ray/shape batch posters enqueue collision-query tasks through the same holder task queue, sizing the task count from the number of workers plus one. They complete query postprocessing on the game thread through 11BE100.

Per-bullet collectors (static with ownership inference): ray batch entries point at bullet+0x8F0 collectors; shape entries use bullet-owned shared pointers to hknpClosestHitCollector or hknpAllHitsCollector. The source inferred, but did not prove in a scheduler trace, that each entry is processed by only one task instance.

Synchronous paths and unreachable routine (static): broadphase 11A70B0 and direct ray 11A7EE0 use immediate/custom collectors instead of the queue. The author found no code references to 11A8000 outside unwind metadata and classified it as dead; no claim is made about dynamically computed calls beyond that search.

Piece +0x250/+0x260 store rotation/position from Havok transform 98BDB0, translated from +0x30 at 137D5D–137D72. The wipe's work +0x20 is its starting vector, and +0x24 its height, clamped to InitParam +0x90 when above +0x94. Body +0x1F8 is copied from the shape's InitParam +0x48 and also compared against 1.5. Update ticks pieces, effects and an unresolved one-second timer

CrashModel vtable slot 5 135580(this,dt) ticks its phase machine, submits effect job 176AF50 when +0x330 exists and calls 13A2C0 to tick body machines (time +0x100, frames +0x104). A body in final state 137C00 is removed and its shape count subtracted from 20B2BD0 and owner +0x270; with no bodies or outstanding effect it deletes itself through 118A1B0. A separate comparison involving timers +0x2E0/+0x2F0 seems to delete after one second, but that conflicts with 200-frame rest conditions; +0x2E0 is also passed to unread 1337D0. Its true lifetime meaning is unresolved, not a general “all fragments last one second” rule.

ModelDebris is reached from enemy callers, not map objects

ModelDebris constructor 2F9920 has three callers (2F8530, 2FB920, 2FCE40). 2F8530 is reached only from 2FBD30, whose 25 callers fall in enemy code (30D940–538460), including humanoid hit 4915D0 and insect blast 4A8DA0, with none in the 120000–150000 MapObject region. Accordingly the earlier “building fragments” label in an older havok-runtime.md reading was corrected: map building debris is CrashModel/SimulationBody, not ModelDebris. This call graph does not mean every enemy always emits ModelDebris.

Structure part hit versus root durability and collapse

MapObject_Structure damage slot 13 142E70 checks slot 16 1432A0 for a hit missing the root part ([[obj+0x190]+0x300], via 197A20/197BA0). It walks a 0x120-byte part array at [obj+0x190]+0x310 (count +0x320), breaking touched, linked (+0x118 != −1), still-standing parts through 1432E0, setting the hit flag byte +3 bit 0 and bypassing root durability. A root hit proceeds to base damage slot 1267A0. Collapse slot 14 143530 (when 126EF0 agrees) breaks all standing non-root parts first and then the root. This resembles EDF5's separate structure-part route, but not an assertion of identical assets or break graphs.

Per-part breaker 1432E0 draws one shared seed into obj+0x1F0 (generator 1F54128), then 141AB0 builds a record using SGO CrashSoundType, part, seed, structure center [obj+0x190]+0x30, part vector +0xB0 and hit flag bit 11 at +0x60. Havok event dispatcher 16-bit index overflow and patch audit

Scope: static native-code analysis, edf6/havok-event-dispatcher-overflow.md, not a reproduced gameplay fix. The source's offline Unicorn emulation used stubbed allocators. This event-subscription node limit is distinct from the 1,024-agent ai::World issue and from the ragdoll pool's 256/512 cost budget.

Base and derived hknpEventDispatcher identity

RTTI identifies hknpEventDispatcher, vtable 18C1628, size 0x78, and hknpEventMergeAndDispatcher, vtable 18C1678, size 0x90. EDF6 uses the derived variant in its Havok world at hknpWorld+0x980. The registry links event-type-specific hkSignal subscriptions for a body or globally through 16-bit node indexes, plus a separate free list. Index width—not the number of bodies alone—is the failure boundary.

World constructor chooses the two dispatcher types

The world constructor tests [cinfo+0x85]: when set, DA2863 requests 0x90 bytes through Havok allocator 97A6B0 and DA2878 calls derived constructor E76640; otherwise DA287F/DA2894 construct 0x78-byte base E75980. DA2899 installs the pointer at world +0x980. Derived construction calls the base, writes its own vtable, initializes +0x78 and clears the merged-event array at +0x80. The source found no third game constructor, though an external plugin or swap command could bypass that assumption.

Common base fields and dispatch context

At +0x08 is the referenced-object word initialized to 0xFFFFFFFF; +0x10 is the hkSecondaryCommandDispatcher field initialized to 1; +0x18 is the owning world. World +0x40 supplies current body count and its +0x20 virtual slot +0x60 yields initial body capacity. Dispatcher +0x20/+0x28/+0x30 are callback-context fields written or cleared around world steps (DAC919–DAC940, DAD65C–DAD688, E781D0) and copied to stack during dispatch. These context fields are not indexed subscription arrays.

Chain-head arrays, free list and derived merged events

+0x38 stores a uint16 free-node head, 0xFFFF meaning empty. +0x40 is the 16-byte-node hkArray (size +0x48, capacity/flags +0x4C, initially reserved for 0x100). +0x50 is a uint16 head for each body (body index masked with 0xFFFFFF), +0x60 the global head, +0x62 a dispatching flag and +0x68 a uint16 pending-free-head array (size +0x70, capacity +0x74). During dispatch, removal queues heads for later release. Derived +0x78 is a merge flag and +0x80 holds 0x24-byte merged events. The native audit found unreferenced alignment gaps +0x3A..+0x3F and +0x63..+0x67, a precondition for the proposed in-place widening.

Sixteen-byte subscription node layout

Node +0 is uint16 next (also free-list link; sentinel 0xFFFF), +2 is uint16 event-type key compared against [event+4], and +8 is a flagged hkSignal pointer, fired by E75F50, released via 97B7C0 or destroyed by 97B440. Bytes +4..+7 have no reader/writer in the inspected family; the relocation at E758EF–E7590B copies only the next/key words and the pointer, so this gap was treated as available, pending an external-subscriber audit.

Subscription allocation, firing, removal and reclamation call family

The related code is concentrated at E75840–E76E10: reserve E75840 moves 16-byte entries, base constructor E75980 initializes heads and capacity, destructors E75AC0/E76680 free arrays, and E75C20 allocates a new entry by free-list pop or appending (uint16)size. Dispatchers E75D30/E76850/E76B70 traverse global/body chains and fire matching event types; E76010 frees a chain; E76080 can unlink one node but had no identified caller. E76120 obtains global signals (bodyId=0xFFFFFF), E76180 per-body signals and E76460 processes body removal. This is the audited native function family, not an externally stable plugin API.

Base and merged dispatcher vtable slots

Base 18C1628 and derived 18C1678 share slot 0 978A40, slot 2 978D50 and slot 4 E762A0 (command switch types 0–0x4D, no node-index access). Slot 1 is deleting destructor E75AC0 versus E767A0 (derived first frees +0x80); slot 3 E75D30 versus E76850 is command dispatch, and slot 5 E76000 (return immediately) versus E76B70 dispatches merged events. These differing slots require distinguishing base from derived when auditing readers.

Truncated index aliases an old node beyond 16-bit capacity

At E75C5E, movzx esi,word ptr [rcx+0x48] truncates the node array's size to 16 bits for the returned link index, while E75C71 addresses the new 16-byte record using the full signed size shifted four. Once size reaches 0x10000, the new index aliases an earlier node (size−0x10000); writes to its next link can fuse chains and produce cycles. Even before that, 0xFFFF collides with the end-of-chain sentinel. The defect is in subscription-entry indexing and is not an unconditional body-count ceiling.

Cyclic chain can hang removal at mission exit or mid-mission

World body-removal loop DA8B00 invokes E76460 at DA8E1F; it removes the body's head from +0x50[body] (first writing 0xFFFF at E7648C–E7649B) and calls E76010 to walk/free nodes until the sentinel. A corrupted cyclic next chain never reaches that value and can loop without terminating. When dispatch is active, the old head is instead queued in +0x68. The same path exists for removing a body during ordinary play; “exit hang” is not limited to the end-of-mission transition.

Event-type keys must stay 16-bit during widening

The 36 operations involving [node+2] or [event+4] and comparisons such as cmp ax,0xc, sub ax,0xd, cmp ax,0xb process event type keys, not list indices. Index-related E75CE0/E75CED use [rcx+r8*2] with r8=2*id, already an effective four-byte stride after changing head arrays. During node relocation, the old 16-bit key copy at E758FA/E75900 becomes redundant if the proposed qword copy covers bytes 0–7. Treating every 16-bit machine instruction as a candidate index edit would corrupt event matching.

Equivalent hkArray reserves for two- and four-byte heads

Functions A55860 (2-byte elements) and 978600 (4-byte elements) are 0x82-byte twins except for the element-size immediate and two relative call displacements. Both use 97C750 for overflow and 97C890 to reallocate, with allocator in RCX, requested capacity EDX, old pointer R8, old count R9D and capacity/flags pointer at [rsp+0x20]. Their maximum hkArray capacity is 0x3FFFFFFF. This comparison supports the in-place widening proposal but does not test its integration with all signal consumers.

Source-proposed uint32 index layout and install-time guard

Proposed widening uses the node's unused +4 for a uint32 next index, moves the free head to +0x3C and global head to +0x64, changes the arrays at +0x50/+0x68 to 4-byte heads with reserve 978600, and uses sentinel 0xFFFFFFFF. Relocation copies a qword covering node bytes 0–7; node size 16 and dispatcher sizes 0x78/0x90 remain. It must run before the dispatcher is constructed; the author's guard refuses installation when file-system global 20B2880 or physics-system global 20B30A0 is already initialized. Physics init originates from application path 7004F0→11A3340→11A3410; the world is created by 11AD340. This is a static patch design, not a safely verified drop-in binary patch.

External consumers mostly use world pointer or context fields

The author's all-.text scan found 46 loads of world +0x980 or related +0x968 and no external direct read/write of dispatcher fields +0x38..+0x74. Sites include world constructor/destructor (DA2210, DA28C5, DA3319, DA3B11, DAF471), signal wrappers (DAB920/DAB960/DAD14D/DAD184), step-context writes (DAC90E–DAC944, DAD652–DAD690) touching only +0x20/+0x28/+0x30, virtual calls (DACB99 slot 5, E68A9A slot 3) and remove-body DA8E06. Similar instructions in E8C120, EA7C14, E2E730 and C02B9B belonged to other types. This is evidence of a scoped search, not a proof that dynamic plugins cannot access those fields.

Emulated subscription pressure and freed-node reuse

Contributor's offline Unicorn run executed patched game-code fragments with Havok alloc/realloc substituted by stubs. 24,000 bodies ×3 event subscriptions +2 global signals requested 72,002 nodes. Unmodified code handled 300 bodies but failed near body 21,844 (around node 65,534) in the 24,000-body attempt. Under the widened code, deleting half the bodies and subscribing again reused available nodes instead of growing the array; removing 2,000 bodies while dispatching went through deferred-free +0x68, and after all bodies were removed the free count equaled total nodes minus global subscriptions. These are emulator results, not in-game stress evidence or proof of thread safety.

Remaining creation, subscriber and live-reclamation gaps

hknpSetEventDispatcherCommand could replace a dispatcher, and a third-party plugin might instantiate one outside the audited constructor family. hknpWorld constructor DA2020 has uncalled direct-entry candidates DA3140/E23B69 whose reflection/serialization role is guessed. The claim that node bytes +4..+7 are unused rests on incomplete subscriber coverage (helpers 97B5E0, 97B7C0, 97B440 had no negative offsets in this audit). Whether every body removal really returns its nodes should be checked in a live session by reading array size +0x48 and the free list after mission teardown. The static/emulated evidence leaves these questions open.
