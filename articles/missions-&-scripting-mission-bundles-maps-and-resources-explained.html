Maps, missions and Mission Bundles relate

EDF 6Missions & ScriptingMissions
Technical reference · Reconciled authoring contracts; native format boundaries separate

A map describes a reusable world, a mission describes gameplay that runs on one map, and a Mission Bundle groups and packages missions plus their required resources. This distinction is useful when inspecting native mission resources or designing an authoring pipeline.

The detailed ownership below is a reconciled authoring model, not a claim that every EDF release exposes a public Mission Bundle file with exactly these editor-side fields.

The key relationships

Map A  ← Mission 1 ← Bundle X
       ← Mission 2 ← Bundle X
       ← Mission 3 ← Bundle Y

Map B  ← Mission 4 ← Bundle X

In the reconciled authoring contract:

  • each mission has exactly one canonical map;
  • a map may be referenced by many missions;
  • a mission may be reused by more than one bundle without silently changing its map;
  • maps remain independently authored and are not permanently owned by the bundle;
  • for a complete bundle with Y enabled missions using X unique maps, Y >= X;
  • an unused map can exist in the workspace, but an enabled bundle should not publish an unreferenced map as part of its used-map set.

There is no bundle-global same-map rule. An authoring tool must allow different missions in one bundle to select different maps.

Map editor versus mission editor

Map-authoritative data: terrain/topology, geometry, material and texture resources, object placements, foliage, water, collision, navigation, destruction and map builds.

Mission-authoritative data: mission ordering/membership, scripts/events, actors and objectives, per-mission map choice, dialogue/audio usage, resource registration and bundle packaging.

A mission editor should consume a published map build rather than becoming another writer of map binary formats. Likewise a map editor should not silently rewrite a mission's game-script semantics just because a map object changed.

Identity and freshness

A custom map in the studied Workspace V1 authoring model is identified by:

project_id + map_family

A build revision is distinguished by the Workspace manifest SHA-256. The representation uses metres and Y-up coordinates. Older workspace data without canonical identity can be previewed read-only, but should not be silently accepted as an authoritative mission map binding.

A map can change while the mission still references its previous revision. This should produce an explicit freshness/rebind decision, not an automatic rewrite of every mission-local object or transform.

Resource paths and packaging

Verified map build resources are projected to bundle asset references with the runtime path:

Map/<resource.path>

The authoring model distinguishes external/global dependencies, bundle overrides and bundle-owned resources. These are packaging/ownership semantics; they should not be confused with the game's normal resource lookup or native container structure.

The mission scene owns its references to placed objects and its gameplay. A map refresh does not justify deleting mission-local authored entities or regenerating gameplay placements without review.

Native game-format boundary

Mission BVM/AngelScript, mission RMPA, map RMPA, MAPO, MAD and native navigation are distinct layers. For example, a mission call such as SetAiPath(obj, "navigationmap") should not be treated as a mission-RMPA path reference without evidence: navigationmap refers to the native navigation/pathing semantics in the investigated sources.

Practical questions answered

Question Answer under the recovered authoring contract
Can two missions share one map? Yes
Can one bundle contain multiple maps? Yes
Does copying a mission into another bundle change its map? No, not implicitly
May a mission rebind to a new map revision? Yes, explicitly, with checks
Should mission build tools write MAD/FMEP themselves? No; consume authoritative map publication
Is mission RMPA interchangeable with map RMPA? No
