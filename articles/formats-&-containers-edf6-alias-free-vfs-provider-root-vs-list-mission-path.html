EDF6 alias-free VFS: why a working MissionPack LIST can still start a black screen

EDF 6Formats & ContainersFile Formats
Technical reference · Prior user runtime PASS for loader+LIST+mission gameplay; bounded source-only path correction; not all builds

A loader that correctly redirects a custom MissionPack LIST is not automatically able to open the mission directory named by a row inside that LIST. An EDF6 A-to-Z runtime case demonstrated this distinction: a custom MP07 LIST became selectable via a direct alias-free VFS provider, yet the first mission initially opened to a black screen. The underlying AC/RMPA data was later proven usable after correcting a stale path identity.

The two-stage lookup

Stage 1 — select a MissionPack and load its LIST:

/cri_bind/MISSION/MISSIONLIST_MISSIONPACK07.OFFLINE.LIST.SGO
    → validate exact managed slot 07
    → resolve bundle/pack provider and its LIST bytes

Stage 2 — start a mission from the LIST row:

LIST row mission path
    → game-root-relative mission directory
    → MISSION.AC and MISSION.RMPA

The first stage was runtime-positive while the second initially failed. The generated row still pointed to the old global loose-Mods layout:

./mods/MISSION/MissionPack07/MISSION_001

The actual authored mission tree lived in the alias-free provider cache:

Mods/.edf6ml/providers/p/bundle_project/main/MISSION/MissionPack07/MISSION_001

The corrected source profile generated a game-root-relative LIST row like:

./Mods/.edf6ml/providers/p/<bundle_id>/<pack_id>/MISSION/MissionPackNN/<mission_id>

Implementation rule: Resolve and validate the LIST's actual mission-folder path, rather than merely checking that a request-based VFS redirect can supply the LIST itself. In the retained correction, mission_pack_view_v2.py performs an independent game-root-resolution test and verifies it reaches the exact authored mission directory.

Provider precedence in the offline-qualified source profile

The historical alias-free source architecture used precedence:

PACK
  > BUNDLE
  > generated global .edf6ml shadow
  > legacy Mods
  > native/CPK

Provider roots were written below Mods/.edf6ml/providers/p/<bundle>/<pack> and Mods/.edf6ml/providers/b/<bundle>. The root .mppNNp and .mppNNb junctions were transitional qualification plumbing, not part of the final intended resource model. The VFS resolution rewrite and the LIST-row path writer must agree on this provider model; otherwise loading a pack list can succeed while launching the listed mission fails.

That precedence is a profile of the qualified source branch, not permission for all mods to override each other's virtual paths. Provider ownership, content scope, and semantic conflicts must still be resolved separately.

What the later game test actually proved

The September 30, 2026 runtime log and human evidence documented an EDF6 offline A-to-Z pass for physical MP07:

  • no root .mpp07p alias;
  • base VFS configless/LIST redirection successful;
  • direct mission-folder path opened through the alias-free provider;
  • custom RC2 Golden map loaded;
  • the player spawned, 10 GiantAnt01 spawned and could be defeated;
  • Mission Cleared appeared;
  • map test payload restore completed successfully.

The trial closed the earlier MP06 selection divide-by-zero and the subsequent MP07 black-screen path issue for that exact game, DLL, mission, pack and loader build. It did not prove a universal arbitrary-provider policy, two-player networking, unrelated legacy packs or later editor/runtime revisions.
