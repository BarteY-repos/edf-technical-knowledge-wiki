The AI attack state

Shared NPC soldier attack state and vtable

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-ai-attack-state

The shared AI attack state of Ranger (AssultSoldier), Air Raider (Engineer) and the base SoldierBase is vtable slot 91, function 58FF70. It copies the fire intent [soldier+0x1CEC] into the fire button byte +0xD70 (movzx eax,[rbx+1CEC]; mov [rbx+D70],al, 590245) and ends with call AiMove (59D6E0) at 590259 (rcx = soldier, rdx = pointer to the target-minus-self xyz vector at [rbp-0x20]). It presses no other button, so vanilla Rangers and Air Raiders never use a secondary fire, a backpack item or a weapon swap. The Wing Diver AI attack 57EDD0 runs a flight helper 57E7A0 and then jumps into 58FF70, so it reaches the same final call. Whether the Fencer AI passes through it was not checked (the patch notes it is not hooked).

Basis: the patches' anchors and comments; the call site read from the patch's own aob

Addresses (build-specific RVAs unless indicated): 58FF70, 590245, 590259, 59D6E0, 57EDD0, 57E7A0

Attribution: FevGrave, NpcAiPlus v5 (comments of NpcAiPlus_EDF6.txt, make_NpcAiPlus.py), KittopiaCreator, weapon-swap prototype (slot 91) · 2026-10-29

AI button bytes shared with player controls

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-button-bytes

Button bytes an AI can set on SoldierBase (a player's pad sets the same bytes): fire +0xD70, secondary fire +0xD72, Wing Diver boost +0xD7B; +0xD7C is the held dash (player.md#palewing-dash). A byte per weapon index from +0xD82 is the weapon-swap request (+0xD82 + i; the prototype sets it to 1). The soldier keeps its own 64-bit random state at +0x490: state = state * 0x5D588B656C078965 + 0x269EC3, value = the high 32 bits scaled to a range with imul and shr 32 (the same generator as player.md#npc-fire-duration; a 1-in-N chance per frame is value(N) == 0).

Basis: the patches' code reads and writes these bytes; the generator decoded from the stub

Wing Diver boost

Wing Diver boost input-mask checks

Evidence: static · Build: steam-678ccb46 · Fact ID: wingdiver-ai-boost

The boost is read by the PaleWing update 5808B0 from button byte +0xD7B, and only when the input mask [soldier+0x158C] & 0x400 is set, the soldier is on foot, the emergency flag +0x2FC is 0 and the energy check 590D70(soldier, 2) passes. Vanilla AI Wing Divers never set the byte. NpcAiPlus pulses it (writes 1 only when it was 0 the frame before) while the target is at least 20 m away, energy [+0x308] is at least 0.3 of max [+0x304] and a 1-in-90 chance per frame hits; it recognizes a Wing Diver by the soldier's vtable 17D0FF8 (combat.md#soldier-vtables-update). The author's setting WD_BOOST affects every Wing Diver NPC, vanilla ones too.

Basis: the stub's checks and the author's comments (not run by the hub)

Backpack throws and limpet detonation

Player-link requirement for backpack button

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-subweapon-throw

The backpack (sub-weapon) button is handled by 5A1D70 only for soldiers with a player link (+0x340 non-zero, combat.md), which is why AI soldiers never throw. The throw at 5A1FC1 is three steps: the word at [[set0+0x40]]+0xEC4 = 0; [set0+0x140] = the Weapon_Sub; [soldier+0x1588] |= 0x1000; then StateMachine_SetState 5A0A60(set0+0x110, UseSubWeapon state 5A28A0, 0), where set0 = [soldier+0x1970] (the current weapon set). NpcAiPlus repeats those steps for an NPC and then clears [soldier+0x1A20]. The game's own network packet for the throw is not sent on this path, so other players may not see it (the author's warning).

Basis: the stub's code and comments; not run by the hub

Addresses (build-specific RVAs unless indicated): 5A1D70, 5A1FC1, 5A0A60, 5A28A0

Attribution: FevGrave, NpcAiPlus v5 · 2026-10-29

The game's backpack path in full (All Forces' reading; adds to soldier-subweapon-throw and soldier-subweapon-gates). Input: slot 5 59ABB0 calls 5A1D70(human, dt) for every soldier at 59AC65; it returns (5A2147) when the pad +0x340 is 0 (5A1DA4) or the sub-slot count +0x1A10 is 0 (5A1DB8). Per sub slot i (records: weapons.md#soldier-template-sub-slots; loop from 5A1DD3): gate = !(+0x5D0 & 4) and !(+0x39C & ~2) and (+0x158C & (i == 0 ? 0x2000 : 0x4000)) (5A1DD3..5A1E06; +0x158C bits: 0 move, 1 look, 4 trigger, 11 roll, 13 / 14 backpack slots 0 / 1); the button byte +0xD7F + i feeds the record's held counter, tap and long-press flags; the weapon is +0x1950[record+0] cast with __RTDynamicCast 12DA7AA (TypeDescriptors WeaponBase 2045768, Weapon_Sub 20476E8): a Weapon_Accessory (the Fencer's passive parts) fails and nothing happens; busy (skip) when set 0's +0x140 is set and +0x1A20 is 0, or +0x5D0 & 4, or +0x1A28 set with +0x1A30 >= 1. A tap: +0x1588 |= 0x1000 / 0x2000, and when the gate passes and rounds left +0xBE8 > 0: (if +0x140 is set and +0x1A20 too, first 5A0A60 to 5A2730, ending the old use), the four writes at 5A1FC1..5A1FF8; online and not a copy (+0x128 & 1 = 0) it writes a stream 79A460(buf, 0x40), 12B5790(buf, 0x10), 12B5790(buf, i) and sends it through human+0x120 (NetworkObject) vtable +0x70 (slot 14), destructor 760180 (5A2013..5A207A). A long press: when the weapon's +0x690 != 0 it sets +0x13B = 1 (5A208B), the weapon's own reload press (the weapon update 6935C1 takes it as a press edge); else, with sub+0x1678 & 4, it calls vtable +0x98 on every sub weapon (the limpet / remote-bomb detonation, inferred). The state 5A28A0(set, phase) of the set's machine (set+0x110, 5A0A60(machine, state, 0)): enter plays the animation number from 6ACE60 on human+0xB90 (or, with +0x1678 bit 0, the whole-body action 5A0540), calls 695F10 on all weapons and 696150(sub, 1) (the weapon's show / hide setter, weapons.md#weapon-state-fns-dual, re-read with fn.py: it writes +0x78C; the note calls it pulling the trigger); update goes back to 5A2730 when the animation ends (116BBE0); exit 6ACED0, 696150(sub, 0), 695830, set+0x140 = 0. The weapon fires from its own animation along the soldier's view. Receiver on other machines: 59E210 (NetworkObject slot 15, this = human+0x120), message type byte - 0xC through the jump table 59E870, type 0x10's entry (59E880) = 59E6FD: reads the slot, takes and casts the weapon the same way, with no pad, mask or ammo gate, and does the same writes (59E76B..59E7DE, ending an old use first); a slot past the count yields null and nothing happens. Not traced (the author): the upper-body action layer +0x1A68 and whether the action-set change 5781D0 needs more for AI soldiers.

Weapon swapping by range

KittopiaCreator weapon-swap prototype hook

Evidence: static · Build: steam-678ccb46 · Fact ID: ai-weapon-swap-by-range

KittopiaCreator's prototype hooks the same state (anchor vtable91_site, 590252) and requests a weapon swap by range: it walks the soldier's weapon vector (data [+0x1950], count [+0x1960], in vector order) and takes the first weapon whose effective range [weapon+0x224], squared, is greater than xmm0, then writes 1 to the swap byte +0xD82 + i of that index and continues with the displaced lea rdx,[rbp-0x20]; mov rcx,rbx and a jump back to the call AiMove at 590259. xmm0 is not set by the prototype, so it holds whatever the state computed before the call; it is presumably the squared distance to the target (inferred from the compare, unverified). The prototype does not check ammo or which weapon is held. +0x224 is the estimated range the AI uses as attack range (weapons.md#weaponbase-ctor-nodes).

Basis: the prototype's code and comments (not run by the hub); xmm0 meaning inferred

Addresses (build-specific RVAs unless indicated): 590252, 590259

EDF Knowledge Hub record — original wording — expand (1,262 characters)

Behavior of v8.11 (the author's description): squad members far behind their leader sprint, dash, boost or roll to catch up (distance 25 m, 1 in 20 per frame; with the option on, only squads led by a local player); a squad member standing inside the player's weapon-light cone (apex at the held weapon, or the player position + 1.4 m when unarmed or the weapon reports a position over 3 m away; half-angle = FireAccuracy x 1.5 + 15 deg, capped at 25 deg; 80 m long, at least 1.5 m wide) steps straight out of the beam and sometimes rolls; a member within 1.5 m (2 m high) of its captain steps straight away from it, and then from the root player; during an attack it also dashes (Ranger 15 m 1 in 240, Wing Diver boost 20 m 1 in 90) or rolls (10 m, 1 in 120); a Fencer chains a dash and jumps on a 60-frame cycle; the weapon swap of the prototype is built in (1 in 30, range factor 0.5, minimum 25 m); grenade chance 1 in 240 between 10 and 45 m, drones an extra 1 in 8. Rolls are used only when this frame's stick is at least 22.5 degrees off straight forward or back; in the follow case the look direction turns 45 degrees so the roll is diagonal. Conflicts named: anything editing 590245-59025D or 590686-5906CC. Online: grenade throws skip the game's packet.

Basis: the patch's header and settings block, not run by the hub; the numbers are the file's defaults

Evidence: static · Build: steam-678ccb46 · Fact ID: soldier-ai-think-intent

This source note combines several technical details. Its evidence grade, game build and contributor credit above still apply to the entire record. Follow these topics, then expand the complete original text for offsets, exceptions and caveats.

  1. Soldier state-machine agent
  2. Think or target selection
  3. Movement and firing behaviour
EDF Knowledge Hub record — original wording — expand (2,748 characters)

There is no AI class: the AI is a state machine inside the soldier, StateMachine::Agent<SoldierBase> at h+0x1BF0 (vtable 17D2480), whose states are SoldierBase virtuals: 89 590710 guard, 90 590280 follow, 91 58FF70 engage (HeavyArmor's 91 is 566290). The per-frame entry is vtable slot 7, Think void(Human*, const float* dt): AssultSoldier (17CDF28) and Engineer (17CF100) 596B50; HeavyArmor (17CF5B8) 567080, which calls 596B50 first; PaleWing (17D0FF8) 580460 (jmp 596B50). Think clears the intent block at its start (596BAE call 56D300(h+0xD50)) and the state machine refills it; the player's input writes the same block (570650); slot 4 572DF0 consumes move and look (573B72 -> 56D350), slot 5 59ABB0 the buttons, and slot 4 does not clear the block for a non-player with h+0x1A & 8 (on the AI list, "M"). On a remote copy (h+0x128 & 1) Think writes nothing and slot 54 595F50 writes the replicated +0x1E00 / +0x1E10 into +0xD50 / +0xD60 ("M"). The intent block: +0xD50 vec4 move, local (x, 0, z, 1), world direction x (cos ψ, 0, -sin ψ) + z (sin ψ, 0, cos ψ) with ψ = +0x1244; +0xD60 the look delta (Δpitch, Δyaw), h+0x1230 += d60 with +0x1240 (pitch, negative up) / +0x1244 (yaw) following smoothly; +0xD70 / +0xD71 the triggers of weapon sets 0 / 1 (set k's trigger is d70 + k, sets 0x150 apart at h+0x1970; 59ACE2 / 59B15E); +0xD74 / +0xD81 next / previous weapon; +0xD75 reload; +0xD76 / +0xD77 jump or evade pressed / held; +0xD82..+0xD84 select weapon 0..2 ("M"). Looking at a target, as MoveAndLook 5A2B50 does (5A2FFB): 4E100(out, dir) gives out[0] = -atan2(dy, horizontal distance) and out[1] = atan2(dx, dz), then d60 = wrap(out[0] - +0x1240) x gain, d64 = wrap(out[1] - +0x1244) x gain. The target: every 60-119 frames (h+0x1CE0) EnumConflictObject takes the nearest engaged enemy, with no distance limit and no line of sight, stored as the weak h+0x1CD0 / +0x1CD8 through 58EB40(&h+0x1CD0, &{obj, ctrl}). EDF6: ai::World agent IDs, capacity and stress

Evidence: reverse-engineered static native sites, one author's stress runs and one unverified research plan from edf6/ai-world-agent-ids-and-stress-limits.md. This is the per-ai::World navigation/avoidance agent table, not the existing soldier squad maximum or ragdoll budget. RVAs apply only to the analyzed Steam build; a plugin's byte patch is a source report, not an installation recommendation or a verified portable fix.

World object size, constructors and release paths

ai::World (RTTI .?AVWorld@ai@@; vtable 1768A48) occupies 0x2180 bytes. Its creation path EBE40 calls the Havok-routed allocator 97A6B0 with that size, constructor EE020 and initializer EF180, then stores a shared pointer in the manager; its control-block vtable is 17688E8. The two call sites from 121470 (122A76, 122ABE) permit two distinct Worlds in one scene. Release proceeds through deleting destructor EED00 and EE770 to sized free 97A760, whose requested size is set at EED25; an alternate flag-4 branch at EED41 also references 0x2180. This matters for any widened-allocation proposal; the shared pointer does not imply a global single World.

World field offsets and lock-protected registry

World+0x50 owns CostModifier; +0x58 contains the critical section (initialized through 50C90; entered/left by 50BC0/50BE0). The inline agent-pointer table spans +0x80 through +0x2087: 0x401 qword slots for indices 0–0x400, with ID 0 never issued. The vector<uint16> free-ID stack begins at +0x2088 (data +0x2090, capacity +0x2098, count +0x20A0), the AvoidanceFilter at +0x20D8 and an agent linked list at +0x2100. Allocation, registration, unregistration and list reclamation are inside the critical section; +0x20E0/+0x20F0 are observed fields with incomplete semantics.

Issue, return and reclaim IDs

EF180 clears 0x401 pointer slots and reserves an ID stack of 0x401 entries, pushing IDs 1–0x400 in ascending order; LIFO allocation therefore issues 0x400 first. F1EF0 registers an existing agent and F2540 creates/registers one; they pop an ID, store it through E7C60 into agent+0x40 and associated Havok character +0x18, then fill the table slot at F1F54/F260C. With no free ID they instead pass the sentinel 0xFFFF to E7C60 without filling a table entry. F3740/F37D0 unregister, zero the indexed slot and push back its ID. Reclamation F3AA0 walks the separate +0x2100 linked list, removes reference-count-1 agents, clears their slots (F3B3D) and returns IDs (F3B76).

16-bit agent identity and non-cap constants

Identity passes from E7170 to B7E5E0, a 32-bit value at +0xC4 and a qword at character +0x18; consumers including F14FC, F3E83, F4164/F4170 zero-extend the low 16 bits. IDs up to 0xFFFE fit this observed path. The other 0x400 constants at EAEDF, F4C84 and F5248 govern other containers, while 0xFFFF in the constructor, character reset or ray-query filters is a sentinel, not an additional 1,024-agent limit. This scope excludes untraced Havok-side readers of +0xC4.

Indexed readers in CostModifier and avoidance filters

The source identifies table reads at F3E90 (inside World vtable slot 5 F3E60, testing only whether the ID is nonzero), F1526 (CostModifier vtable slot 5), and four accesses in AvoidanceFilter vtable slots 3/4: F4168, F4175, F41C4, F41EA. The avoidance pair functions F4160/F41B0 are leaf functions without .pdata; they read two Havok-character IDs and then dereference the returned agents at +0xE8 without a null check. F41B0 compares just the second ID to 0xFFFF. These pointers require compatible allocation size, index validity and initialization, not merely 16-bit field storage.

How the table-access audit was performed and revised

Searching all .text qword/LEA forms [base+index*8+0x80] yielded 33 sites: 11 attributed to World table access and 22 to four other functions with non-World bases; 14 matching byte patterns were byte/XMM operations. Alternate address-construction forms, including precomputing World+id*8 then adding 0x80, were scanned separately without an additional World hit. The audit expanded from .pdata functions to no-.pdata leaf code and first eight virtual slots of World, CostModifier and AvoidanceFilter: 653 units, 51 in the World region, 9 lacking .pdata. The earlier .pdata-only review missed the four avoidance accesses—a serious false-completeness lesson for binary patch reviews. Access from outside the chosen code range or through aliases may still evade this search.

Empty free-ID stack writes far beyond the World object

After 1,024 issued IDs, the free stack is empty but the registration path still places 0xFFFF in the agent/character ID fields. That agent has no table entry; later unregister/reclaim clears slot[0xFFFF] (roughly 512 KiB beyond the original World allocation) and pushes the invalid ID back. Reader F3E60 then indexes and dereferences it, matching a contributor-reported AI-thread crash at EDF.dll+0xF3E9D in stress:100 with 1,082 soldiers. A test with 1,123 ants plus 662 allies did not fail: the author inferred ants do not each consume an ai::World ID while soldiers do. Thus raw entity count is not synonymous with agent-ID demand; it also does not rule out other, earlier performance limits.

Contributor's guarded widening patch and residual hazards

The source's src/aiworld_capacity.cpp modifies a known binary build by allocating 0x82188 bytes instead of 0x2180 at EBE5F, EED25 and EED41; it moves the inline lookup table from +0x80 to +0x2180, expands the clear loop at EF5C8/EF5CF to 0x10001 slots, updates 11 table displacement sites (F1526, F1F54, F260C, F3766, F380E, F3B3D, F3E90, F4168, F4175, F41C4, F41EA), and reserves free IDs 1–0xFFFE through EF613. The extra space is roughly 512 KiB per World plus 128 KiB for the ID stack. Original-byte verification covers 17 patch locations; any mismatch refuses the patch and a failed partial install rolls back writes in reverse. This is a static implementation report, not independent validation: a missed pointer-table reader would access uninitialized old inline storage, possibly crashing immediately, and a wider ID range does not remove external Havok/thread/memory ceilings.

Unverified ceilings and incomplete pointer-flow coverage

Unsettled items include Havok character/avoidance capacities, path-thread pressure, the Havok heap budget, precise handling of 0x82188-byte allocations by 97A6B0, and Havok-side consumers of the 32-bit field +0xC4. The tracker followed arguments and one level of [x+0x18] but discarded volatile registers at calls, so it may miss indirect or external readers of the old +0x80 table; the chosen AI module boundary E4000–F8000 was based on symbols/vtables. The proposed stress:100 rerun with the plugin's separate MAX_SQUADS=120 limit removed was a future test plan, not a completed validation.

Reported stress timings: game-thread CPU saturation

Contributor's Steam-build runs: stress:1 spawned 180 enemies and 53 friends with average 16.7 ms frames and 17% GPU 3D load; stress:10 had 583/242, 32.9 ms, 4% GPU; stress:30 had 1,123/662, 74.9 ms, 3% GPU. At N=10/30 the game thread saturated a CPU core near 98%, while rendering/audio ran on separate threads. The contributor's plugin was loaded: its own soldier ThinkHook accounted for 63%/60% of game-thread time, particularly WastedFire target selection (58%/52%); Havok 7–14%, effects and ModelDebris under 2%. These figures profile that modded stress configuration, not stock EDF6 performance or a universal 1,024-agent speed threshold.
